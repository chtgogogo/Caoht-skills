# 判定标准与结论映射

## 1. 五态判定（每个检查项必须落在其中之一）

| 符号 | 含义 | 证据要求 |
|---|---|---|
| ✅ 通过 | 检查过且达标 | 证据（命令/输出/文件:行号/测量落盘） |
| ❌ 未过 | 检查过且不达标 | 证据 + 修法建议 |
| ⚠️ 风险 | 能用但有隐患 | 隐患说明 + 触发条件 |
| ⬜ 未测 | 本次没测成 | 原因 + 补测方法（不许静默略过） |
| ➖ 不适用 | 该项目无此项 | 一句理由 |

判定语句示例（报告里照此写）：`❌ 依赖未锁定（无任何 lock 文件，requirements.txt 只有裸包名）｜修法：pip freeze > requirements.txt 或迁移到 pyproject+uv.lock`。

## 2. 问题分级 P0 / P1 / P2

| 级别 | 定义 | 典型例子 |
|---|---|---|
| **P0** | 上线即事故：数据丢失、安全洞、核心链路坏、评测污染、宣称与事实打架 | 密钥泄露、SQL 注入、CI 红叉但文档宣称质量达标、评测集泄漏进知识库、幻觉 API、无备份的关键数据 |
| **P1** | 显著缺陷，上线前必须修 | 无死循环护栏、降级路径从未验证、错误率超标、N+1、反馈闭环断裂 |
| **P2** | 改进项/技术债，进待办 | 冗余依赖、文档缺口、TODO 偏多、无监控（个人项目） |

## 3. 结论映射（不许自由发挥，不许和稀泥）

```
不通过     = 第一层任何 ❌  或  任何层出现 P0
有条件通过 = 无 P0，但有 P1   （报告必须列"转通过条件清单"）
            或 无 P0 无 P1 但存在必需门槛 ⬜（§3 封顶条款）
通过       = 无 P0 且无 P1，且适用项里 ⬜ 数量 = 0   （P2 允许，进待办清单）
```

**数据不足封顶规则**：
- 出现任一 P0 → 结论最多「不通过」（已是最低，无需封顶逻辑）。
- 第三层因无评测集整体 ⬜，或第二层实测项大面积 ⬜ → 结论最高「有条件通过」，并在结论处写明："因 XX 未测，无法给出通过结论"。
- **不存在"缺数据但判通过"的路径**——证据不足时宁可给低结论，不给高结论。

🔴 **必需门槛实测状态表（每张报告 §6 必出，这是「通过」的前置闸）**：
- 分母 = Phase 0 判定的**适用项全集**（各层固定清单去掉判 ➖ 的项），逐条给五态之一，一行不许省。
- **判定式**：`通过` 要求适用项里 **⬜ 数量 = 0**。出现任一 ⬜ ⇒ 结论降为「有条件通过」，并把该 ⬜ 逐条写进转通过条件（[条件] → [验证方式]）。
- ⬜ ≠ ➖：➖ 必须有 Phase 0 的适用性理由（"非 AI 项目，第三层整体不适用"），**无理由的 ➖ 视同 ⬜** 参与封顶——把"没测"粉饰成"不用测"是这项规则要堵的头号漏洞。
- 典型必测却常被判 ⬜ 的：单测未跑、评测集缺失、并发未压、外部依赖未演练兜底、无障碍人工项未做（只跑自动扫描 = ⬜ 不是 ✅）。

🔴 **扫描覆盖不足同样封顶（与门槛数量无关的另一条）**：画像脚本 `coverage.insufficient=true`，或凭据/红旗扫描未披露「被排除数量 + 截断原因 + 未检查目录清单」时——相关项最高只能 ⚠️/⬜，对应结论不得是无条件「通过」，报告 §6b 必须原样抄出覆盖声明行。

**"有条件通过"的条件清单格式**：逐条写 [条件] → [验证方式]，如：`条件1：修复 session_id 路径穿越（验证：用 ../../ 攻击串重放请求返回 400）`。条件全数验证通过后，下一次验收方可改判「通过」。

**动态发现二轨规则**：只有**实证发现**（D-n，探针跑出证实证据）参与结论映射与 P0–P2 分级；**假设**（H-n）进报告假设区，不参与结论、禁止给 P 级；**证伪记录**（X-n）进排除区留痕。固定清单项照旧按五态判定，不受此条影响。

## 4. 示例参考值表（**不是契约阈值**；正式阈值只认项目 `ACCEPTANCE.md`）

| 指标 | 参考值 | 性质 | 说明 |
|---|---|---|---|
| 单元测试 | 100% 通过，0 个说不清理由的跳过 | **硬性** | 与项目定位无关的底线，无契约也照判 ❌ |
| 扩充题准确率 | ≥80% | 示例 | 行业常见起点；正式阈值须由项目定 |
| 回归题 | 100% | **硬性** | 回归题的意义就是全对 |
| Hit@5 / 工具首选正确率 | ≥70% | 示例 | RAG/Agent 项目常见起点 |
| 幻觉 API 抽检 | 0 处 | **硬性** | 用户会照抄，出现即 P0 |
| 未知题编造率 | ≤40% | 示例 | 越低越好；阈值该跟"错了会怎样"定，不该跟示例定 |
| 稳定性波动（N 轮） | ≤5 个百分点 | 示例 | 抽 10-20 题 |
| 本地 P95（对话/检索类） | ≤3s；纯接口 ≤1s | 示例 | 强依赖场景与部署位置 |
| 错误率（负载下） | <1% | 示例 | 本地单机口径 |
| 单次任务成本 | ≤ ACCEPTANCE.md 预算线 | **契约依赖** | 无预算线时本次测得值建立基线，标"阈值待定" |
| 内存（15-30 分钟） | 无单调爬升 | **硬性** | 单调爬升是缺陷（疑似泄漏），不是阈值问题 |

**怎么用这张表（口径纪律，防"拿示例当契约判 ❌"）**：
- **硬性项**：没写进 ACCEPTANCE.md 也按红线判 ❌/P0–P1。
- **示例项**：只能用来**排序与提示**，不得单独据此判 ❌。项目契约没定阈值时，把本次实测值记为**基线**，指标旁标「阈值待定（本次为基线）」，并进 §6 的"待用户拍板"清单；判 ⚠️ 的唯一合法理由是**趋势劣化**（有基线可比且劣化超一截）或**绝对值烂到明显是缺陷**（如 P95 从 2s 变 40s），不是"没到示例值"。
- **契约项**：ACCEPTANCE.md 写了就以它为准，本表整列作废。
- 红线理念：**示例值只是护栏，不是圣旨**——首次验收后的最重要产出之一，就是和用户一起把符合项目定位的阈值写进 ACCEPTANCE.md 固化。之后阈值改动必须在项目 CHANGELOG 里留痕（防止"改红线凑通过"）。
