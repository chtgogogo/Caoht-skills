# 《项目验收报告》模板（照此落盘，不许自创结构）

> 落盘路径（**两选一，报告元信息必须写明选了哪个**）：默认 `<项目根>/acceptance/ACCEPTANCE_REPORT_<YYYYMMDD>_<级别>.md` + 复制一份 `acceptance/latest.md`；被验项目根不在本机工作区/不便写入时，落**集中验收工作区** `<验收工作区>/<项目>/ACCEPTANCE_REPORT_...md` + `latest.md`（本机该工作区路径见同目录 `personal.local.md`，若存在）。历史对比只在同一落盘根里找上一份。
> 原始证据（命令输出/评测明细/压测数据）存 `acceptance/evidence/`（或集中工作区的 `evidence/`），报告里引用文件路径而非转录数字。
> ❌ 与 ⚠️ 项在报告中用 **粗体** 突出（markdown 无红字）。


## 写作纪律

1. 每个表格的"证据"列必须填真实路径或 `文件:行号`，不许写"已验证"三个字搪塞。
2. 数字必须带口径列；两份报告的同一指标口径不同时，历史对比要标注口径差异。
3. 结论只用四个词：通过 / 有条件通过 / 不通过（+封顶说明）。禁止"基本通过""大体OK"这类和稀泥词。
4. 报告面向三类读者写：现在的用户（要能照着修）、三个月后忘光的自己（要能看懂上下文）、以及可能存在的"背调者"（每个数字经得起追问）。
5. 🔴 **报告与证据里不得出现明文凭据**：疑似凭据一律写成 `文件:行号 + 键名 + 掩码值 + confidence`，原文留在现场由人去看的。从 gitleaks/detect-secrets 等工具输出粘贴进报告前先掩码；commit message 同样不得带明文。
6. 🔴 **有 ⬜ 就不许写无条件「通过」**：§6a 门槛表是硬闸，⬜ 数量 > 0 ⇒ 结论降「有条件通过」并把补测逐条写进转通过条件（判 ➖ 的必须带理由）。
7. 🔴 **阈值分「契约 / 硬性 / 基线待确认 / 示例」四种来源，§2 表必须写清是哪种**：只有前两种能判 ❌；拿 skill 自带示例值（80%、70%、≤40%、≤3s…）当项目承诺判不达 = 本报告口径错误，重写。
8. 🔴 **覆盖范围不足要显式抄进 §6b**：`insufficient=true`、被排除数量、截断原因、未检查目录清单，四要素缺一即视为隐瞒覆盖面。
