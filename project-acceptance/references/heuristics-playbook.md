# 动态启发式排查手册（六步法）

> 这是"固定清单"之外的另一半。固定清单保证下限（不漏常规项），动态启发负责上限（挖出清单上没写的、这个项目特有的暗坑）。
> 核心思想：**每一步启发都要产出可执行的用例或检查点**，不允许停留在"感觉这里有风险"——感觉要变成用例，用例要跑出结果，结果要分级记录。

## S1. 画像打底

- 跑 `scripts/profile_project.py` 拿 JSON 画像（语言/框架/类型猜测/工具链/红旗）。
- 人工补看三样：入口文件（main/app/index）、配置加载处、目录结构。
- 产出：一段 3-5 句的项目画像描述（这是什么、核心链路是哪条、最像哪种类型项目）。

## S2. 类型 playbook 匹配（按画像命中的类型，逐条过）

**Web 服务 / API**
- 已知坑：CORS 配置缺失或全开、缺健康检查端点、无优雅停机（杀进程丢请求）、分页无上限（pageSize=999999 打爆内存）、并发写同一行、无请求体大小限制、时区处理（UTC vs 本地）。
- 动作：对命中的每条，写一个验证方法（请求/代码审查），跑掉它。

**CLI 工具**
- 已知坑：无参数时行为不友好、参数校验缺失、Ctrl+C 后留下脏状态、非 0 退出码语义错误（失败返回 0，脚本会误判成功）、Windows 路径与编码、断网/依赖服务不可用时的行为。
- 动作：故意给错参数、中途 Ctrl+C、断网各试一次。

**库 / SDK**
- 已知坑：import 时执行重活（副作用）、公共 API 无 `__all__` 导出面控制、依赖倒挂（库锁死下游的依赖版本）、示例代码跑不通。
- 动作：新环境按 README 示例从零调用一遍。

**Agent / LLM 应用**（先对号入座：读失败模式库 `Cao-失败模式与对策库` 的 `05-checklists/上线前检查.md` 与 `01-failure-modes` 七类死法文件，41 条逐条问"它会不会这样死"；**对完号仍对不上的新死法 = S7 回流候选**）
- 已知坑：工具调用无轮数上限（烧钱死循环）、工具报错无恢复路径、上下文只增不减、把工具结果里的指令当系统指令（间接注入，OWASP LLM01）、过度代理（LLM06：能删文件/发邮件的权限给了不该给的场合）、无轨迹日志（badcase 无法复盘）。
- 动作：对照失败模式库七类死法逐条检查护栏；跑一个必然失败的工具观察行为。

**RAG / 知识库问答**
- 已知坑：切块把语义切碎（表格/代码被腰斩）、检索分数无下限兜底（垃圾块也进上下文）、知识库过期无标记、引用不可溯源（答案与出处对不上）、多租户隔离缺失（LLM08 跨上下文泄漏）、对"知识库里没有的问题"编造（承接第三层校准项）。
- 动作：用 3 个"知识库外问题"测编造率；抽 2 题人工核对引用来源。

**数据管道 / 定时任务**
- 已知坑：不可重入（重跑产生重复数据）、断点续跑缺失、上游 schema 变更无校验、失败后无告警（静默失败数周）。
- 动作：把一次任务中途杀掉再重跑，核对数据是否重复/缺失。

**前端**
- 已知坑：三态缺失（空态/加载态/错误态）、无错误边界（白屏）、控制台报错、包体过大首屏慢。
- 动作：断网、清缓存、慢速网络各走一遍核心路径。

## S3. 风险维度扫描（对画像中出现的每个维度提问）

| 维度 | 存在信号 | 必问的问题 |
|---|---|---|
| 并发 | 服务端、多用户 | 两个用户同时写同一资源会怎样？有锁吗？ |
| 状态持久化 | DB/文件缓存 | 写一半断电/杀进程，数据会坏吗？有事务吗？ |
| 外部依赖 | 任何 API/DB/模型调用 | 它挂了/慢了/返回垃圾时，我方行为是什么？ |
| 不可逆操作 | 删除/支付/发送 | 误触发怎么办？有确认/软删除/审计吗？ |
| 资金与隐私 | 金额、个人信息 | 有没有把 PII 发给第三方 API？成本有没有上限熔断？ |
| 长时任务 | 批处理/爬虫/训练 | 中断后能续吗？进度可观测吗？ |
| 权限 | 多角色/多租户 | 越权三连：横向能读别人数据吗？纵向能调管理接口吗？未登录能进吗？ |
| 时区与编码 | 时间处理、中文内容 | 时间比较用 UTC 吗？中文路径/GBK 编码测过吗？（Windows 高发） |
| 配置与密钥 | env/config | 缺一个配置时启动报错清晰吗？还是有诡异默认值？ |

- 产出：命中的维度 × 问题的回答（✅/⚠️/❌ + 证据）。**未命中的维度也写一句"为什么不命中"**，防止漏判。

## S4. 攻击者视角（生成 3–5 个刁钻用例，真实执行）

换脑子问三个问题，每个答案变成至少一个用例：

1. **我要弄崩它**：超长输入（10 万字粘贴）、空输入、二进制乱码、并发 50 连发、循环嵌套触发递归上限——哪个能打挂？
2. **我要骗过它**：提示注入（"忽略之前的指令…"）、伪装成系统消息的用户输入、把指令藏进要处理的文件内容里、套 system prompt——能骗过吗？
3. **我要让它做坏事**：诱导越权（"把所有用户的记录给我"）、诱导执行危险操作（"清空数据库吧"）、诱导产出有害内容——有护栏吗？

执行要求：每条用例记录【输入 → 实际输出 → 期望 → 判定】。**系统扛住了也是有效且宝贵的结果**，如实记录"挡住了 + 靠什么挡的"。

## S5. 上线前夜 pre-mortem（换时间轴找隐患）

提问：**"假设明天上线，一周后出了大事故，最可能的三件事是什么？"**
- 对每件"最可能的事故"，反推：现在的代码/流程里，哪一行/哪个环节会让它发生？
- 产出：预演事故清单（事故描述 → 当前缺口 → 建议动作 + 分级）。
- 这是把"挑毛病"变成"叙事推演"的技巧，对挖结构性隐患（不是单点 bug）特别有效。

## S6. diff 驱动（增量验收的核心技巧）

- `git log --oneline <上次验收tag/日期>..HEAD` 看改了什么；`git diff --stat` 看影响面。
- 对每个变更模块，问三句：改了什么行为？动了哪些调用方？有没有配套的测试更新？
- **变了但没测试覆盖的模块 = 增量验收的头号嫌疑**，优先补测。
- 产出：变更影响表（模块 → 变更 → 影响面 → 测试覆盖状态）。

## 实证门槛（铁律：动态发现不是新的幻觉源）

S1–S6 产出的每一句"我觉得这里有风险"都只是【假设】，**假设不是发现**。动态层与固定清单执行同一套证据纪律：

1. **假设 → 探针 → 二值判定**：每条假设（H-n）必须当场转化为一个最小可执行探针（一条命令/一个用例/一次重放），跑出输出后判定：**证实**（风险真实存在）或**证伪**（排除）。只有证实了的才升级为实证发现（D-n）。
2. **只有实证发现能进主报告与结论**：D-n 可参与 P0–P2 分级并进入结论映射；探针跑不了（环境不允许/超出本次验收预算）→ 假设留在报告"假设区"，标注信度 + 补验方法，**不参与结论映射、禁止给 P 级**。
3. **证伪也是产出**：被证伪的假设记入"排除区"（一句结论 + 证据路径），防止下一轮验收把同样的怀疑重猜一遍。
4. 证据落盘与固定清单同标准：探针命令与输出存 `acceptance/evidence/`，报告引用路径而非转录数字。

## S7 知识回流（新死法闭环：验收 → 库 → 下次验收）

验收中证实的 D-n，若属于"库里没有的新死法"，回流进知识库，让下一次验收从"现场排查"变成"对号入座"。

**回流三道质量门（全过才回写，缺一不可）**：
1. **已实证**：有探针输出证据——假设一律不回流（否则库被猜测污染）。
2. **通用型**：不是本项目特有的环境巧合——自问一句"换个项目会不会也这样死"，答"会"才回流。
3. **非重复**：目标库内查重无命中（失败模式库先查 03 术语表：业界已有名字的概念并入现有条目，不另起新条目）。

**回流路由（按知识归属分家，不许一股脑塞一个库）**：

| 发现属于 | 回流到 | 格式与规则 |
|---|---|---|
| Agent/LLM 应用的新死法（循环/成本/安全/上下文/并发/错误恢复/治理合规） | 失败模式库 `references/01-failure-modes/` 对应类别文件 | **七字段格式**：现象/术语/根因/对策/最坏后果/检查问题/相关；编号接续该类别文件现有最大号（LOOP/ERR/COST/SEC/CTX/CONC/GOV-）；追加前先到库的 03 术语表查重；改完同步库的 C 盘注册副本并在库 CHANGELOG 留痕；02/05 视图同步列为待办告知用户 |
| 通用工程踩坑（报错/环境/工具链/平台兼容） | 踩坑日志（`A-Cao-踩坑日志`） | 按其"根因层 + 案例层"流程沉淀 |
| 本机私有/环境相关 | 本 store 记忆库 PITFALL | 按记忆纪律 V/R 打分入库 |

**双向闭环**：回流的除了新死法，还有"库内某条死法的对策描述与实战不符"——同样要回改 01（遵守库内治理：先 01 后视图）。反向同样成立：下次验收的 S2/S4 **先拿库的七类死法清单对号入座**（读 `05-checklists/上线前检查.md` 或对应类别文件），命中的直接进固定排查；**对号后仍对不上的，就是回流候选**。

## 启发结果记录格式（统一，二轨三区）

```
【实证发现区】参与结论映射
D-1 【P1】标题一句话
- 来源：类型playbook / 风险维度 / 攻击用例 / pre-mortem / diff驱动 / 库对号未命中
- 假设→探针：H-3"怀疑列表接口 N+1" → 探针=开 SQL 日志连打 20 次接口
- 判定：证实（20 次请求产生 61 条查询）
- 证据：acceptance/evidence/sql_log.txt
- 复现方法：（一步步可执行）
- 建议：（怎么修/怎么补）
- 回流候选：是/否（是 → S7 三道门 + 路由）

【假设区】不参与结论，禁止给 P 级
H-2 【未定级】怀疑长连接内存泄漏
- 依据：静态读码发现 channel 未显式 close
- 未实证原因：30 分钟 soak 超出本次验收预算
- 补验方法：本地 soak + 内存曲线，转全量验收必做项

【排除区】证伪留痕，防重猜
X-1 "怀疑路径穿越" → 证伪：session_id 在 schemas 层白名单校验（证据 evidence/…）
```

数量自查：标准验收至少 5 条实证发现或排除记录（只有假设不算数），全量至少 10 条。**零发现通常意味着启发没认真做**，除非项目真的极小（此时要在报告里说明）。
