## v1.5.0（2026-10-12）· 凭据扫描射程与「没有发现 ≠ 扫过了」两处 P0 收口（外部审查二轮·卡06）

**来源**：GPT 外部审查报告（基线快照 06a20a9）判定的六大 P0 之一，经 2026-10-11 复核后落成任务卡 `卡06-项目验收官.md`。两条主线：① `profile_project.py` 读了配置文件却又因不属源码扩展名而跳过、`.env` 不进扫描集合，"没发现凭据"被误读成"扫描完整"；② 无障碍把"政务/医疗/公共"标签直接映射成全站 AAA，以及把 skill 自带示例数字当项目红线判 ❌。

### 增加了什么功能
- **凭据扫描成为独立通道**（`scripts/profile_project.py`）：覆盖面 = 源码扩展名 ∪ 配置文件（.json/.yaml/.yml/.toml/.ini/.cfg/.properties/.env 及 `.env.*`）∪ 不看扩展名的特定文件名（`.env`、`credentials`、`.netrc`、`*.pem`、`*.key`、`id_rsa`）。每条命中带 `channel`（special-name/config/text/other）与 `confidence`（高/中/低）+ `value_shape`，人工复核可按 confidence 排队。
- **生成即脱敏**：命中值在生成阶段就掩码（前若干字符 + 长度），finding 结构里**删掉了明文 `snippet` 槽**——报告、证据 JSON、commit message 拿不到明文，需要原文时人去现场看。
- **覆盖声明成为结论的一部分**：`coverage` 输出 `insufficient` / `declaration` / `limits_triggered[{kind,cap,excluded,detail}]` / `unchecked_dirs` / 两通道各自的扫描与跳过计数；新增 `--strict-coverage`（覆盖不足退出码 3，给 CI/门禁接住）。
- **报告新增两个硬槽位**（`references/report-template.md` §6a/§6b）：**6a 必需门槛实测状态表**（⬜ 计数 > 0 ⇒ 结论封顶"有条件通过"）、**6b 扫描覆盖声明**（四要素 + `placeholder_filtered`/`shape_rejected` 计数 + 已补跑的成熟组件）。
- **凭据补扫组件命令落地**（`references/tooling-cheatsheet.md` 新小节）：gitleaks / detect-secrets / TruffleHog 三件的**当前文档口径**调用式与安装渠道，外加"外部组件报告默认含明文 ⇒ 落盘即敏感件"的红线。
- **`personal.local.md`（新，个人适配层，不入发布仓）**：本机两种落盘根的实测路径与"什么时候用哪个"。

### 优化了哪些地方
- **语言分析与凭据扫描彻底分开**：两通道各自独立文件数上限与计数，文档明写"别拿 languages 统计到 300 个文件当作凭据扫过了 300 个文件"。
- **误报治理**：赋值型命中必须过值形态闸（表达式 `idm.group(1)`、含中文的自然语言、`true/null` 常量、模板串一律不报，但**计数留痕**在 `shape_rejected`，不静默丢）；源码信道不启用"无引号赋值"规则（等号右侧不带引号在 Python/JS 里必然是变量引用）；占位符名单先过滤。已知盲区三条同步写进脚本 `notes` 与 `layer1` 第 13 项。
- **阈值口径重排**：`scoring-and-verdicts.md` §4 表头改"示例参考值表（不是契约阈值）"并加「性质」列区分硬性/示例/契约依赖；`layer2`/`layer3` 的 P95、错误率、忠实度、编造率、Hit@5 全部改示例口径；`ACCEPTANCE总装模板.md` D 节"留空则用验收官内置默认"改为"**留空 = 未定**，记基线 + 标阈值待定，不据此判 ❌"。判 ❌ 的权力只属于项目写下的契约和硬性项。
- **无障碍等级去标签化**（`layer5-accessibility.md`）：删除"政务/医疗/公共项目统一默认 AAA"，改为版本与等级由项目适用要求确定、无书面要求时以 AA 作工作基准；引 W3C 原文说明 AAA 不宜作全站普遍政策，并引"no tool alone can determine…"固定人工检查项；P 级映射注明"级别来自该项目书面要求，不来自项目标签"。
- **落盘根改成两选一**：项目内 `acceptance/` 与集中验收工作区 `<验收工作区>/<项目>/latest.md` 盘上都在用（2026-10-12 现采 `find` 为证），报告元信息必须写明选了哪个、历史对比只在同一落盘根里找。
- **与 `acceptance-criterion-audit` 的分工写死**（SKILL.md §8）：本 skill 量"项目达不达标"，那张卡量"判据本身有没有鉴别力"；默认只跑本 skill，被测对象本身是判据/评测集/CI 门禁时才交出去，防同一次验收重复跑。

### 解决了什么问题
- **"扫描完整"的假象**：这是 P0 级缺陷——报告写"未发现硬编码密钥"而实际根本没打开配置文件。现在覆盖范围、被排除数量、截断原因、未检查目录清单四项缺一即本项判 ⚠️ 不判 ✅，`insufficient=true` 时措辞只允许"覆盖范围内未命中"。
- **判定被示例数字绑架**：此前 skill 自带的 80%/70%/≤3s 等数字会被当成项目承诺去判 ❌，等于验收官替用户编红线。现在示例值只出实测值与基线，不产出"不达标"结论。
- **AAA 一刀切**：把标签当要求，既让验收官对着 W3C 不建议的档位判失败，也掩盖了"该项目实际适用哪一版哪一级"这个必须先问清的问题。
- **明文凭据二次扩散**：脱敏从"报告写作时注意"前移到生成阶段，且删字段而非加提醒——靠自觉的掩码迟早漏。

### 质量记录（证据在任务包 `evidence\卡06\`）
- 合成夹具红→绿：同一假凭据放 `.py`/`.json`/`.yaml`/`.env` 四处，旧版只报 `.py`（红证 `_red-old-version.txt`），新版四处全报且输出零明文。

## v1.4.0（2026-10-11）· 第六层新增 D 节「首用理解与信任走查」（真实 PM 六连批注归因立节）

**来源**：业财单据中枢真实 PM 首用六连批注（2026-10-11）：默认域转嫁知识结构 / 内部检索分「相关度 113.8923」上屏 / 工单流转·可见性·权限三问无屏上交代 / 9 单样本对标行业均值 / 决议面板权重倒挂成侧边脚注 / 宽屏整屏无用途空白。**六条全部不是 bug**——功能全对、测试全绿、数字真实，但业务人看不懂、不信、被冒犯。这是与"45 轮全绿但入口不存在"（2026-09-30，B 节立节依据）不同型的第二型缺陷，促成 D 节。

### 增加了什么功能
- **`references/layer6-deliverability.md` 新增 D 节六项固定清单**（编号 8-13 接续）：⑧内部结构不转嫁（默认值=最不会错的选择）⑨内部原始值不上屏（无上界不可比值转标签）⑩机制黑箱屏上交代（流转到哪/谁处理/多久回/我能看到吗 四问 + 管理操作视觉隔离）⑪小样本与对标诚实（分母<20 披露 n 或降"—"，说明一句话人话+口径折叠）⑫页面第一任务=首屏焦点（动线权重）⑬宽屏空白有用途（修比例≠拉宽正文）。每项给"怎么查 / 通过标准 / P 级"。
- **判定联动加一条**：D 节 ≥3 个 P1 → 报告必须加结论句「功能实现完整，但尚不可直接交付给非开发者用户」并进最弱项点名。
- SKILL.md 第六层行、执行纪律教训锚点（第二锚点）、description 触发词（首用走查/PM或用户批注了问题）同步；metadata v1.4.0。

### 优化了哪些地方
- **把归因写进执行纪律而非只写清单**：D 节节引明确"作者视角对这六类问题天然免疫（知识诅咒），禁止用开发者知识补偿理解；每屏问『一个不懂这个系统的人看到它会产生什么疑问？这个疑问在屏上有答案吗？』"——防验收官自己又用作者视角走过场。
- 与既有 A/B/C 节分工显式化：A 节测"交付物定义"，B 节测"动作能不能完成"，**D 节测"能完成的人愿不愿用、敢不敢信"**。

### 解决了什么问题
- **为什么开发者（尤其 AI）验收六连漏**：AI 与开发者默认用"实现心智模型"看界面——知道域是什么、分数是什么、密钥框是干嘛的，因此永远无法以"第一次见到"的眼光看它；且逐行 review 天然只看局部（每个布局决策局部都合理，合成结果动线倒挂）。D 节把"客户视角首用走查"从靠自觉变成固定清单，六类问题变成可判定检查项。

## v1.1.0（2026-09-25）· 动态层反幻觉 + 新死法回流闭环

**来源**：外部建议（用户转达）——"动态发现也必须走证据落盘+是否判定，不能变成新幻觉源；库外新死法按失败模式库七字段回流 01"。采纳并做两点加强（假设/实证二轨分流；回流加质量门与路由分家）。

### 优化了哪些地方
- **动态层从"记录格式"升级为"实证门槛铁律"**（heuristics-playbook.md）：原 v1.0.0 只要求动态发现附证据与复现方法，未堵死"没跑验证就把猜测写成分级发现"的通道。现在假设（H-n）必须当场转化为最小探针跑出证实/证伪，才可升级为实证发现（D-n）。
- **报告第 4 节改为二轨三区**（report-template.md）：实证发现区（参与结论）/ 假设区（不参与结论、禁止 P 级）/ 排除区（证伪留痕防重猜）。
- **结论映射补一条二轨规则**（scoring-and-verdicts.md）：只有 D-n 参与结论映射与 P 分级；验收官自查清单新增 2 项（二轨分离检查、回流质量门检查）。

### 增加了什么功能
- **S7 知识回流闭环**（新增章节）：验收 → 库 → 下次验收的双向循环。回流三道质量门（已实证/通用型/库内查重非重复）；回流路由按知识归属分家——Agent/LLM 新死法按**七字段格式**（现象/术语/根因/对策/最坏后果/检查问题/相关）写进失败模式库 `01-failure-modes` 对应类别（编号接续 LOOP/ERR/COST/SEC/CTX/CONC/GOV-、先查 03 术语表、同步 C 盘注册副本、库 CHANGELOG 留痕、02/05 视图同步列待办）；通用工程坑回踩坑日志；本机私有进 store PITFALL。
- **库→验收方向补全**：S2 的 Agent/LLM 行改为"先读失败模式库七类死法逐条对号入座，对不上号的即回流候选"，形成双向闭环。

### 解决了什么问题
- **动态层幻觉通道**：v1.0.0 的动态启发若 AI 只"感觉有风险"就写进报告，会绕过固定清单的证据纪律。现在假设与实证强制分流，结论只认探针证据。
- **知识不回流、踩坑重复踩**：验收发现的新死法此前只留在当次报告里；现在回流进失败模式库/踩坑日志，下次验收从"现场排查"变"对号入座"。
- **回流污染风险**：直接照建议"无条件回流 01"会让库被猜测和项目特例污染——三道质量门 + 路由分家 + 查重先行解决了这个隐患。

## v1.0.0（2026-09-25）· 首发版

**从零建成**，基于用户 CaoHT 提出的"四层漏斗 + 固定清单 + 动态启发"验收框架，经权威实践扩充后产品化。

### 增加了什么功能
- **四层漏斗验收流程**：第一层基础工程（拦截级，任何 ❌ 直接打回）→ 第二层指标性能（硬指标红线）→ 第三层 AI 特有质量（定量分数，评测体系健全性先行）→ 第四层业务兜底（闭环级，兜底链路必须真实触发一次验证）。每层独立清单文件，每项带"查什么/怎么查/通过标准/证据要求"，共 40+ 固定检查项。
- **动态启发六步法**（references/heuristics-playbook.md）：画像打底 → 项目类型 playbook（7 类项目已知坑清单）→ 风险维度扫描（9 维提问表）→ 攻击者视角刁钻用例（弄崩/骗过/诱导做坏事）→ 上线前夜 pre-mortem → diff 驱动增量验收。
- **五态判定 + P0/P1/P2 分级 + 结论映射表**：通过/有条件通过/不通过的判定完全规则化，含"数据不足封顶"规则（关键项未测时禁止给"通过"），杜绝和稀泥结论。
- **九节报告模板**（references/report-template.md）：含诚实暴露弱点、能力缺口与未测项、历史对比三节，报告落盘 `acceptance/` 目录并支持跨轮趋势对比。
- **项目画像脚本**（scripts/profile_project.py，纯标准库）：一键产出语言/框架/项目类型猜测/工具链/红旗（.env 被 git 跟踪、无锁文件、疑似硬编码密钥等 8 类）JSON 画像，降低 Phase 0 的探索 token 成本。
- **验收级别分级**：快检（15-40 分钟）/ 标准（默认）/ 全量，对应不同深度与 API 花费；付费评测先报预算。
- **项目级定制接口**：支持项目根 `ACCEPTANCE.md` 覆盖默认红线；首轮验收自动生成草稿，红线固化后改动须留痕（防"改红线凑通过"）。
- **生态互认**：证据形态对接 `A-Cao-测试纪律`、结论可证伪对接 `A-Cao-抗幻觉纪律`、新坑沉淀对接 `A-Cao-踩坑日志`、Agent 失败模式参考 `Cao-失败模式与对策库`、增量审查参考 `代码审查-双轴PR改动审查`。

### 解决了什么问题
- **AI 编数字填表问题**：原构想是纯 Prompt，AI 可能在无法实测时编造 P95/准确率。本版以"四条军规 + 三禁（禁改测试凑通过/禁编数字/禁硬测不适用项）+ 五态判定 + 数据不足封顶"硬性约束，编造无门。
- **"不适用项被迫硬测"问题**：原清单对非 AI 项目、无用户体系项目没有豁免机制。本版引入 ➖不适用态 + Phase 0 画像驱动的适用性判定。
- **动态启发无方法论问题**：原构想只有"针对本项目特征排查"一句口号。本版给 AI 六步可执行流程 + 7 类项目 playbook + 9 维提问表，启发项强制带 P 级、证据、复现方法。
- **验收结论口径不一问题**：原构想四层判定原则各说各话（打回/高危/定量/闭环）。本版统一为 P0/P1/P2 + 规则化结论映射。
