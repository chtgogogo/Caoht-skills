# 模式判定（启动路由的判定依据）

> 主 skill 启动时：**先 `resume` 读权威记录**（有未完成项目就照它续，不重新问档），
> 无未完成项目才走本文件定档。
> **先给推荐+理由，再让用户拍板**——但"拍板"只在判不出来的时候才发生（见 §三）。
> 定档不是人肉印象分：计分规则写死在 `scripts/pipeline_state.py` 的 `decide_tier()`，可复算、可被探针打红。

## 一、三档＋一条路由

| 档／路由 | 适用信号 | 走的步骤 | 建的文件 |
|---|---|---|---|
| 轻量 | 改 bug / 小功能 / 单文件改动 / 用户说"快改一下" | ①③⑥⑧⑬⑫ | `state.json` + `台账.md`（**不建任务板/卡库/选型文件**） |
| 标准 | 新功能 / 新模块 / "做一个 XX"且范围可控 | ①②③④⑤⑦⑥⑧⑩⑪⑬⑫ | + `任务板.md`（有卡才建） |
| 企业 | 全新项目 / 多模块 / 多人或多分身协作 / 长周期 | 全十二步 | 同上（复杂＝企业的别名） |
| 跳步优化 D | **已有项目**："帮我优化/检查/升级"而非从零开发 | 见 §五 | 按勾选到的阶段建账（档位记 `标准`） |

别名口径：`轻/标/企/复杂/跳步优化` 都能接受，落账时归一到 轻量/标准/企业 三档之一——
`state.json` 的 `mode` 只有这三个值，**"跳步优化"是路由不是档位**（它决定"先扫缺口再选阶段"，不决定步骤集合）。

## 二、信号表（只有这些键参与判定）

`py scripts/pipeline_state.py mode --decide --signal 键=值 --signal 键=值 …`

**A. 定档信号**（进 `decide_tier()` 计分）

| 键 | 值 | 计分红线（代码里的原话） |
|---|---|---|
| `files_touched` | 整数：这次动几个文件 | ≤3 且非从零、不动代码 ⇒ 轻量 +3；≤3 且单模块单卡 ⇒ 轻量 +2；≥4 ⇒ 标准 +2 |
| `modules_touched` | 整数：跨几个模块 | ≥2 ⇒ 标准 +2；>4 ⇒ 企业 +2 |
| `cards` | 整数：预计切几张卡 | ≥2 ⇒ 标准 +1；>8 ⇒ 企业 +2 |
| `team_agents` | 整数：几个分身／人协作 | ≥2 ⇒ 企业 +2（默认 1） |
| `estimated_days` | 整数：预估几天 | ≥3 ⇒ 企业 +1 |
| `has_code` | true/false | 参与"轻量 +3"的与条件 |
| `from_zero` | true/false | true ⇒ 企业 +2；同时否掉两条轻量判据 |
| `new_feature` | true/false | true ⇒ 标准 +2 |

**B. 点亮信号**（不定档，只决定可选重步骤跑不跑，见 §四）

`deploy` · `public_net` · `compliance` · `eval_set` · `external_claims` · `parallel_cards`

**C. 不参与计分的键会被点名**

写了不在 A/B 表里的键（拼错、或者以为工具认识），输出里会有一行
`🔴 [不参与计分的信号键] xxx ⇒ 拼错或本尺子不认，别把它们当成已评估的依据`。
判据：**"我给了个信号"和"这个信号被评估了"是两件事**——以前用假键名（`user_says_quick` 之类）跑出来的推荐，看着像评估过，其实整条被忽略；现在必须显式报警，不然假绿比没绿更坏。

## 三、什么时候才问用户

```
mode --decide 判得出档  → 自动定档，**告知即可，不追问**（退出码 0）
mode --decide 平档同分  → 退出码 1，打印「判不了（X／Y 同分）」→ **这时才**把选项摆给用户
mode --decide 一个信号都没给 → 落最低档（轻量），why 行明写「本行是默认值不是判定」，不因此问用户
```

- **平档才问**：只有三档里最高分并列（判据明写"置信度不足"）才交回用户；其余一律自动定档。
  想强制交回用户看推荐再确认，加 `--ask`。
- **无信号不问你**：没给信号＝落最低档，宁少步骤也不产空文档堆；但输出会明写
  「未收到任何信号 ⇒ 落最低档……**本行是默认值不是判定**」，防止下次有人拿它当"已经评估过了"。
  要问的是"这次改动涉及几个文件"，不是"你要哪个档"。
- **用户显式点了档**（"就要企业档"/"随便快点"）→ `mode --set 企业 --apply`，档位来源记 `user`，自动结果让位。
- 🔴 **固定提问是缺陷不是纪律**：每个阶段开新窗口先问一遍"模式是什么/落盘在哪/要不要并行"，
  等于把已经说过、已经授权的事再问一遍。要向用户确认的事**先 `answer --id <项> --check`**，
  答过就直接用（细则=`台账模板.md` §五）。

## 四、可选重步骤按特征点亮（不全部默认跑）

| 步骤 | 点亮条件 | 不点亮时 |
|---|---|---|
| `security_L1` | **常开**（铁律 10：静态自检＋敏感信息/本机绝对路径泄漏扫描，纯文档项目也跑） | 没有"不跑"这一档 |
| `security_L2` | `deploy` 或 `public_net` | 未部署/不公网 ⇒ 不跑 |
| `security_L3` | 企业档 或 `compliance` | 非企业档且无合规要求 ⇒ 不跑 |
| `model_eval` | `eval_set` | 无评测集 ⇒ 不跑（**不编基线**） |
| `multi_agent` | `parallel_cards` ≥3 且 `team_agents` ≥2 | 默认接力不并行 |
| `outward_claims` | `external_claims`（有 README/简历/汇报等对外陈述物） | 记 `na` |

轻量档只保留 `security_L1` 与 `outward_claims` 两项，其余一律不跑——**这一条是"轻量档对陌生项目也安全"的落地**：
小改动不该被拉去建卡库、跑评测、开多代理，更不该留下一堆空文件。

## 五、跳步优化（模式 D）执行法

1. 拿"十二步检查表"逐项扫描当前项目，问自己三个问题：
   - 这个环节的产出物存在吗？（有没有 CHANGELOG？有没有评测集？有没有台账？）
   - 存在的话质量如何？（评测数字新鲜吗？文档与代码一致吗？）
   - 有没有明显的低垂果实（一次小改动就能补的短板）？
2. 产出**缺口清单**（每项：缺什么 / 补了有什么好处 / 大约代价），按性价比排序给用户勾选；
3. 用户勾选的每项 → 按对应阶段的细则直接执行（不重走 ①②③），执行结果照常写进权威记录。

示例：对一个"有 README 无评测集、CHANGELOG 停更、文档与代码不同步"的项目，缺口清单可能是：
1. 建最小评测集（补量化验收能力，半天）；
2. 修文档与代码的 3 处不一致（防面试穿帮，1 小时）；
3. 补 CHANGELOG 迭代记录（展示工程素养，1 小时）。

## 六、给用户的第一条消息（只在平档时发）

> 查了权威记录，没有未完成的项目。按你描述的改动范围（{复述用户意图}），信号计分是
> 轻量 {n}／标准 {n}／企业 {n}，前两档同分 ⇒ 我判不出，请你拍板：
> - 轻量（只建 state.json + 台账，不建任务板）
> - 标准（切卡 + 任务板 + 双评审）
> - 企业（全十二步）
> - 跳步优化（已有项目只补短板——我先扫缺口清单给你勾选）
> 选哪个？也可以直接告诉我你的顾虑，我重新推荐。

判得出档时**不发这条**：直接一句"按 {X} 档走（理由：{一条计分判据}），要改随时说"，然后开工。
