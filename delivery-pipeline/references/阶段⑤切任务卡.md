# 阶段⑤ 切任务卡 + 阶段⑦ 验收先于实现

> 产出物（三层任务文档体系，v1.5 起固定）：
> - **L1 双清单**：`<项目根>/docs/pipeline/` 下**任务板**（AI 认领用）与**记录清单**（人看轨迹用）
> - **L2 纲要卡**：`<项目根>/docs/pipeline/cards/卡N_标题.md`（一卡一文件，禁止单文件巨石计划）
> - **L3 施工图卡**：`<项目根>/docs/pipeline/具体任务卡/<编号>-<卡名>/任务卡.md`（中/大卡才有，执行窗口唯一施工依据；
>   配套 `执行回执.md` 与 `evidence/`——三件套分工见 §5 引言）
> 每张卡经脚本登记进权威记录（§2 第 4 条），台账/任务板行由 `render` 生成（铁律 17，禁手写登记）。

> **卡号三律**（全链一条，照抄不发挥）：
> ① 卡号＝「波次字母＋序号」（A1、B2；无波次可纯数字），序号至多两位数；
> ② 同一卡号贯穿 L2 文件名／L3 目录名／`card --id`／任务板／验收行引用，不造第二套号；
> ③ 字面只认 `卡+可选大写字母+数字`——`spec_check` 认卡（CARD_ID）、tasks.md 勾选对账（TASK_ID）
>    都按这个字面匹配（判据=`scripts/spec_check.py` 正则），带空格、小写、多字母或三位序号的卡号机械尺认不出。

## §1 粒度判定（切卡前先定档，LLM 分析→用户拍板）

| 档 | 卡粒度 | 执行者 | 文档层 | 模板 |
|---|---|---|---|---|
| 小卡 | 子代理一次对话能完成（约 2~5 分钟人类等价，涉及 ≤3 个文件） | 子代理自动执行 | L2 纲要卡即可 | §4.1 实习生标准 |
| 中卡 | 一个新窗口半天内完成 | 用户复制提示词/子代理 | L2 纲要卡 + **L3 施工图（轻量 9 节）** | §4.2 + §5.2 |
| 大卡 | 多天/多刀/企业模式大改动 | 人工窗口分刀执行 | L2 纲要卡 + **L3 施工图（全量 18 节）** | §4.2 + §5.1 |

**判定顺序（先机械后主观，三步定档）**：
1. **数文件与模块**——涉及 ≤3 个文件且 ≤1 个模块 ⇒ 候选小卡；>3 个文件或跨 ≥2 个模块 ⇒ 至少中卡；
2. **看工期与刀数**——预估超一个窗口、需分多刀、跨多天 ⇒ 大卡；
3. **看验收**——验收写不成「一条命令或一张可勾选清单」⇒ 这不是降档的理由，是卡太大或目标太糊，
   **回炉重切**（对标 spec-kit tasks 模板反模式「模糊任务/同文件冲突」，每任务独立可完成、独立可验证——B 级，2026-10-15 实测模板原文，见 §7）。

平手判据：拿不准就先按小卡切，执行时发现不够再升级（与 Anthropic 多代理派遣的「自包含任务＋独立上下文窗」同构，B 级，见 §7）。
**升级触发器**（执行中命中任一 ⇒ 升中卡、补 L3 施工图，升级记进回执）：要动第 4 个文件／验收要点在小卡模板里写不清／要动生产码防线（变异验证记录无处落，§5.1 第 8 节）。
> 本节管的是**卡的粒度**（小/中/大三档），与**流程档**（轻量/标准/企业，`state.json` 的 `mode`）是两条轴——别拿流程档猜卡档。

## §2 三层任务文档体系（v1.5 新增，双层清单+三层文档的分工）

| 层 | 文件 | 给谁看 | 谁维护 | 内容 |
|---|---|---|---|---|
| L1 任务板 | `docs/pipeline/任务板.md`（**生成视图＝派生物**，标准/企业档且有卡才生成） | **AI 执行窗口** | 由 `pipeline_state.py render` 生成；"删除一项"＝把卡状态改 `done`，**不手改文件** | 卡号、标题、【依赖】、可并行、验收要点、阻塞原因与"需要谁"；认领/做完的命令直接印在板头 |
| L1 记录清单 | `docs/pipeline/交付记录清单.md`（或用户自命名副本） | **人**（项目主） | 人记录完成轨迹；AI 也可代填完成行 | **人手维护，不是派生物**：完成后条目不删、打勾记日期与关键数字——它是人的轨迹本，工具不替它的一致性背书 |
| L2 纲要卡 | `docs/pipeline/cards/卡N_*.md` | 主会话/调度层 | 切卡窗口 | 一句话目标/分刀/验收要点/回执区。**权威资料 URL、参考仓库+代码位置、全局纪律写在这里**（任务板只承载状态，不承载资料——资料进生成物会被下次生成覆盖） |
| L3 施工图卡 | `docs/pipeline/具体任务卡/<编号>-<卡名>/任务卡.md` ＋ `执行回执.md` ＋ `evidence/`（三件套分工见 §5 引言：**正文冻结、回执与证据外置**） | **执行窗口** | 深写窗口（可在 L2 定稿后统一深写，或切卡时直接深写） | 全量 18 节/轻量 9 节（§5），执行时**唯一施工依据** |

**四条分工纪律**：
1. **索引 → 纲要 → 施工图，颗粒度递增，缺哪层补哪层**：任务板条目只有三行没关系，但中/大卡必须有 L3 施工图——"拿着三行摘要去施工=质量全凭执行者发挥"，这是不可控的；
2. **执行窗口认领任务的标准动作**（任务卡状态机）：**认领**（`card --id <卡号> --state doing --executor 谁 --apply`，卡号按头部「卡号三律」）→ **拉上下文**（读 L3 施工图→L2 纲要→现查 git status 与相关代码）→ **执行** → **写回**（回执 + `card --state done --metric 实测数字` + 记录清单打勾 + 模块地图回写）。四步缺一不算完成；任务板是写回后 `render` 重画出来的，**不是手改出来的**；
3. **双清单与权威记录的关系**：`state.json` 是**唯一权威记录**（断点续传真源），`台账.md`／`任务板.md` 都是它生成的视图（细则=`台账模板.md` §一）；记录清单是**人的轨迹本**（手维护）。
   老口径"AI 删任务板条目前必须先写台账，否则出现'任务没了、台账没记'的丢失窗口"现在由机制保证：
   **删除动作根本不存在**——卡片状态改成 done，板上的条目自然不再列出，而状态与历史都留在权威记录里（`rev` 与 `history` 可追溯）。
4. **切卡即落账（卡文件与权威记录同步落，⑤ done 前逐张登记完）**：每张卡的卡头字段经脚本登记进 `state.json`——
   `card --id <卡号> --state todo --title "标题" --module <模块>（可重复）--depends <前置卡号>（可重复）--parallel-ok 0/1 --acceptance "验收要点" --apply`。
   卡只在盘上不在账上 ⇒ **三处空转**：⑤ 的 MODULE.md 硬闸读的是账上卡的 modules（文件卡头标了、账上没有 ⇒ 闸查不到＝空过）；
   任务板 `render` 只画账上的卡（板上没条目）；`spec_check` C07 对账没燃料。命令全表=`台账模板.md` §二（指针不重抄）。

## §3 切卡原则

1. **垂直切片优于水平分层**：先切"能跑通一条最小流程"的卡，再切增强卡（tracer bullet）；切片前若存在"让实现变容易"的预备重构（ tangled code 硬啃会翻车），先切 **prefactor 卡**（make the change easy, then make the easy change）；
2. **依赖显式标注 + 波次编排**：卡与卡的依赖写在卡上与任务板上；无依赖的卡标【独立】/【P】可并行（[P] 语义＝不同文件、无依赖，同 spec-kit tasks 模板口径，B 级见 §7）；有顺序要求时按波次字母编排（A 地基→B 叠加→…），同波默认可并行，跨波看【依赖】标注；
3. **每卡必写"怎么验证"（硬性要求）**：评测集 / 测试脚本 / 肉眼验收清单，形式不限但没有就是不许开工；
4. **MVP 卡组必含用户视角验收卡（铁律 12）**：由「不会敲命令的目标用户」人设真实操作核心业务动作——浏览器点击、禁 API 直调作弊、卡壳如实记录；通过才算 MVP 完成。卡型：人设剧本（含唯一允许的命令行动作清单）→逐步操作与截图→卡壳清单就地修→交付物定义逐条对照（达成与否如实标注）；
5. 既有测试/评测验收盖不住用户视角——"725 测试全绿"与"会计朋友能用"是两个维度（案例：45 轮无一卡=非开发者操作成功）；
6. **YAGNI**：PRD 里 P2 的功能不切卡，等 P0 全绿再说。
7. **首卡波次立模块地图骨架**（细则见 `模块地图.md`）：从 PRD 功能列表 + 设计纪要推导模块划分意图（AI 起草→用户确认边界），落 `<项目根>/docs/pipeline/模块地图.md`；此后**每张卡头必须标【动到的模块】**，与【依赖】并列为卡头必填——它是 ⑥执行回写地图、人定向找模块的索引锚。
8. **依赖与需求号咬合：AI 起草候选，人拍板，审卡前不进 ⑥（v1.12）**：卡切完先跑两件事，都是**只出候选、不自行定案**——
   ① **依赖候选推导**：按「A 的产出文件是否被 B 读」「B 的验收是否需要 A 的行为先成立」两条判据，AI 列表给每对疑似依赖（`B3 ← A2：都要动 stores/booking.ts`），标出"我判断不成立的理由"；人逐条拍板后写进卡头【依赖】与 `card --depends`。**AI 不许把自己推的候选当既成事实写进卡**（推错一次的代价是整波次串行化，白白慢一倍）。
   ② **需求号咬合**：跑 `py <skill根>/scripts/spec_check.py check --root <项目根>`，C05（卡引用了主规格与增量里都没有的号）与 C06（主规格每条需求都有卡接住）必须绿——这是"先有规格再有卡"与"没有悬空条款"的机械证明。🔴 卡头【覆盖需求号】必须写 **`R-` 号字面**（机械尺按 `R-` 正则扫卡文取集合；写成"覆盖取消相关需求"的散文＝扫不到＝C06 假红）。
   🔴 **两道都得过**：`plan-review` 审卡（SKILL.md ⑤ 行"切完先过 plan-review 再进 ⑥"）**在先**，机械校验在后，谁都不许绕过谁——人拍的依赖靠 `plan-review` 的洞审，机器的咬合靠 `spec_check`，两套判据盖的不是同一件事。
9. **模块卡随首卡波次立骨架**（v1.13.0 补）：每个被卡触碰的模块建/更新其模块卡（`<模块目录>/MODULE.md`，必填 6 项见 `项目文档与上下文规范.md` §3.2：职责/不负责/文件路径/依赖谁与被谁依赖/影响面三问/怎么验证）。测试案例 L0 期先内嵌在「怎么验证」格（3–5 条＋1 条界面验证步骤），L1 再整段搬 `TESTS.md`。卡头【动到的模块】与模块地图、模块卡三处对准；**模块划分理由只进地图 §2，模块内部设计理由只进模块卡/模块 ADR**（`项目文档与上下文规范.md` §0，不两处写）。🔴 **v1.14.0 起有硬闸**：`stage ⑤ --state done` 时脚本逐模块验 `<模块>/MODULE.md` 在不在盘上——卡头标了模块却没有模块卡 ⇒ 退 4 拒写（Qoder 实测：④⑤ 未完成就施工，模块卡整层缺失）。
   **模块名的机械口径**：卡头【动到的模块】写**模块目录相对路径字面**（如 `app/rules`）——硬闸按字面拼 `<项目根>/<模块名>/MODULE.md` 找文件；卡头标记、地图「模块」列、目录名三处任一改名 ⇒ 三处同改（`模块地图.md` §1.1 同口径，指针不重抄）。且必须经 §2 第 4 条落账——卡头只在 md 文件里标、账上没登记 ⇒ 硬闸查不到＝空过。
10. **界面三件——有 UI 的 MVP 卡组至少一卡带（v1.28.0）**：「好看/一致」没人管是缺口，机械面能红的红掉，审美判定权照旧归人：
    ① **截图基线对比**：Playwright `toHaveScreenshot()` 或任何截图＋像素 diff（装了就用；没装=人工截屏对照并把基线图落 evidence/）；
    ② **axe-core 扫描**：有 WCAG 义务的项目 0 critical 才过（工具装了就用；没装=降级人工走查并在卡里写明降级路径）；
    ③ **VLM 审美意见**：按 Nielsen 十条启发式出意见，**必须换异家族模型**（铁律 20②/评审4 模型级独立性同款——同家族共享审美盲区）；意见=**建议级不阻断**，采不采纳人拍板，禁止把审美意见伪造成退出码。
    三件都装不了的环境给最小兜底＝人工走查 Nielsen 十条 checklist 落卡。验收口径：截图 diff 超容差或 axe critical>0＝该卡不过（可红面机器判）；「好不好看」人说了算（审美面）。

## §4 L2 纲要卡模板

> 两张模板的公共底座（机械尺按字面读，散文写法＝没标）：卡号按头部「卡号三律」；【动到的模块】＝模块目录
> 相对路径字面；【覆盖需求号】＝`R-` 号字面——口径同 §5.1 第 0 节，此处不重抄。

### §4.1 小卡模板（实习生标准——热情但没判断力，所以必须写到零歧义）

```markdown
# 卡 {卡号}：{一句话标题}          ← 卡号=波次字母+序号（如 A1）；文件名 卡A1_标题.md
- 目标：{做什么，一句话可验证}
- 动到的模块：{模块目录相对路径，可多个；与模块地图、<模块>/MODULE.md 同字面}
- 覆盖需求号：{R- 号字面，可多个；不接需求号的卡写「经确认：无（依据，如纯文档卡）」}
- 涉及文件：{精确路径列表，含要新建的}
- 前置依赖：{卡X 已完成 / 无}
- 实现要点：{函数签名 / 接口定义 / 关键逻辑说明——写到零歧义，但不代写全部代码}
- 验收（怎么算做完）：{精确命令与预期输出，如 python -m pytest tests/test_x.py 全绿；
  评测集 xx 指标不低于基线；肉眼验收清单逐项打勾}
- 禁止：{不改哪些文件 / 不加未要求的功能 / 不引入新依赖}
- 完成后动作：{跑验收命令并把完整输出落 evidence/、`card --state done --metric 实测数字` 写回权威记录
  （metric 空=脚本退 4）、记录清单打勾、模块地图回写、给主会话三句话摘要}
```

> 动生产码的小卡同样先红后绿——变异验证要求不因卡小而豁免（豁免条件同 §5.1 第 8 节；记录可并入验收行）。

### §4.2 中/大卡纲要模板（成人标准——写给有判断力的执行者）

```markdown
# 卡 {卡号}：{标题}
- 卡头：{波次/【依赖】或【独立】/【P】可并行/【动到的模块】/【覆盖需求号】——字段口径同 §5.1 第 0 节，不重抄}
- 你要做什么：{思路与目标，引用 PRD 章节}
- 材料位置：{PRD 路径 / 相关文件 / 上游卡的产出 / 施工图卡路径}
- 怎么算做完：{验收清单——每条可机械判定，判据同 §5.3 第一条}
- 边界提醒：{不要动什么 / 容易踩的坑}
```

## §5 L3 施工图卡模板（v1.5 核心：让执行 AI「目的明确、边界清晰、验收机械」）

> 生成时机：L2 纲要定稿后统一深写（一个窗口按波次批量），或切卡时直接深写。
> 深写者必须现查代码与文档，禁止凭纲要脑补「现状」。
> 两档：**全量 18 节**（大卡/企业模式）与**轻量 9 节**（中卡/半天刀），轻量档不许再裁。
> **三件套分工**（目录 `<具体任务卡>/<编号>-<卡名>/` 下）：`任务卡.md`＝施工图正文，写卡后 0–17 节**冻结**
> ——它是审卡对象（plan-review 审的就是它）与「写卡时点」快照，执行中不回改，改卡＝回 ⑤ 重审；
> `执行回执.md`＝执行窗唯一续写处（§5.1 第 18 节只列应填字段，实际回执写这里）；`evidence/`＝验收命令
> 原始输出落盘处（铁律 13）。

### §5.1 全量档（18 节）

```markdown
# 施工图卡 {编号}-{名称}（L3 · 全量档）
0 卡头：编号/名称/波次/【依赖】或【独立】/【P】可并行/【动到的模块】（写模块目录相对路径字面，如 app/rules
   ——⑤ 硬闸按它拼 <项目根>/<模块名>/MODULE.md 找文件，与地图「模块」列、目录名三处同字面，改名三处同改）/
   【覆盖需求号】（写 R- 号字面，对齐 specs/，C05·C06 的燃料——机械尺按 R- 正则扫卡文）/预估刀数与天数/
   执行者（留空待认领）。卡头须是全文第一个「卡N」字面出现处（spec_check 从文件名→正文首个匹配认卡）。
   卡头→登记旗标对照：编号→--id／名称→--title／【依赖】→--depends（可重复）／【P】→--parallel-ok 1 或 0／
   【动到的模块】→--module（可重复）／执行者→--executor／验收要点→--acceptance（命令表=台账模板.md §二）
1 一句话目标（大白话，目标用户也能懂）
2 背景与动机：对标结论/停车场编号/拍板编号——引用来源（哪个检索、哪条台账）
3 现状快照：相关文件清单 + 每处给「现查指令」（grep/sed 命令）+ 当前行为描述；
   🔴 禁止只写死行号——行号标注「写卡时点，开工须复现」
4 设计思路：方案、为什么这么选、数据流/表结构草图
5 决策分列：已定案（🔴 不许改，列拍板编号）vs 拍板项（执行窗可提异议，标 🔴 待天拍）
6 技术选型：库/版本/理由/替代方案对比（含"为什么不选 X"）
7 分刀施工计划：每刀=可独立提交单元（目标/改哪些文件/步骤/预期 diff 规模）；
   依赖顺序写「谁先谁后」不写行号（对标 spec-kit「models 先于 services 先于 endpoints」，B 级见 §7）
8 测试设计：用例表逐条列（编号/输入/预期/机械判据，验收场景用 Given/When/Then 式）+
   先红后绿要求（改生产码先在旧代码上跑出失败面）+ 全量回归基线（当前测试数）+
   **变异验证必选（2026-10-11 天令，动生产码的卡不许裁）**：对本次改动的每个防线/判据打
   畸形变异 → 定向测试变红 → 还原复绿（沿用项目 mutate_* 三臂模式）——变异不红＝
   该处测试没看住＝等于没有，卡不过；无生产码防线变更的纯文档/文案卡可豁免并在本节写明豁免理由；
   **期望值独立推导**——断言的期望值必须手算/另路算出，禁让被测代码自己算（镜像断言＝恒真假绿）；
   **mock 纪律**——mock 不挣断言、只 mock 慢与外部依赖层、mock 结构镜像真实结构、仅测试用的方法进 test utils；
   **Review Focus**——预列 3~5 类"规格沉默但最可能咬人"的输入/失败模式，逐条钉进本卡测试
9 验收清单：可勾选、每条可机械判定（grep 断言/pytest 断言/SQL 直查/肉眼清单）
10 完成定义 DoD：验收全过+测试绿+证据落盘+回执写回+`card --state done --metric 实测数字` 与
   `stage` 四字段写回权威记录（台账/任务板由 render 重画，不是手改项）+记录清单打勾
   ——DoD 是执行者的停止信号，全部满足才许宣布完成
11 禁改清单：他窗在途文件、红线行为（安全三闸/宁红勿绿/只读红线等，按项目红线引用）
12 涟漪影响：先判断是否触碰评测缓存指纹/对外数字/口径文档的**被覆盖文件**（列判断依据：
   哪些文件在指纹集/口径表内、本卡动不动它们）——**触发**才写"合并烧数"等义务（严禁单刀重算）；
   **不触发**也必须写明"不触发的判断依据"，防止执行窗机械照抄产生无意义 diff 或漏报义务
13 回滚方案：改坏了怎么退（git tag/备份/schema 迁移可逆性）
14 陷阱预填：项目已知坑按相关性预填（编码页/中文路径/缓存指纹/并发竞态等——
   来源=项目踩坑日志与卡文已登记坑，不让执行窗重踩）
15 参考资料：URL+GitHub 仓库+代码位置，分「必读/可选」，标注检索日期
16 术语表：卡内术语逐个大白话解释（目标用户不懂技术，执行者也要能给用户讲清）
17 升级路径：什么情况必须停下来问人（拍板项/花钱/资损面/口径变更）、
   什么情况自行决定（纯技术细节）——防止两种失败：自作主张与束手束脚
18 回执区（列应填字段：窗口/开工时间/刀数/测试证据路径/拍板项裁决/遗留——实际回执写 `执行回执.md`，
   本节不回填，正文保持「写卡时点」冻结）
```

### §5.3 深写质量自检（每张施工图写完必过，任何一项缺=没写完）

- [ ] 验收条条有机械判据（一条命令/一次勾选能判定，无"基本完成""大致符合"类模糊词）
- [ ] 测试用例表逐条列出且含先红后绿要求；动生产码的卡含变异验证记录（红→还原→绿，豁免须写理由）；期望值独立推导（无镜像断言）；mock 使用符合纪律
- [ ] 跨卡符号/类型一致性：本卡引用他卡产出的符号名/类型签名逐一核对（clearLayers vs clearFullLayers 这类一字之差＝对接即翻车）
- [ ] 禁改清单明确（含他窗在途与红线行为）
- [ ] 现状全部现查过（行号标注"写卡时点"）
- [ ] 陷阱预填与本项目已知坑对过（有则填、无则写"未发现相关已知坑"）
- [ ] DoD 含完成后动作全链（回执 / `state.json` 写回 / 记录清单打勾 / 模块地图回写；台账与任务板是生成视图，不是手写项；轻量档＝8-9 行内的完成定义一行）；涟漪影响节有判断依据（触发与不触发都要写明凭什么判断）
- [ ] 拍板项与已定案分列清楚（执行者一眼知道哪些能改哪些不能）
- [ ] 参考资料带检索日期且可达（URL 只收真实存在过的，未核实标注；新增检索标"深写时新增"；行业口径引用无法命中原出处时，补同构定义佐证并如实标注）
- [ ] 卡头【覆盖需求号】已填且与 `specs/` 对得上（`spec_check` C05/C06 绿）；本卡若是某变更包的最后一张卡，DoD 里含「归档五步」（`规格层-主规格变更与归档.md` §5）
- [ ] 卡头三处字面对准：【动到的模块】＝模块目录相对路径（＝地图「模块」列＝`<模块>/MODULE.md` 落点）、【覆盖需求号】＝`R-` 字面、卡号贯穿文件名/目录名/`--id`
- [ ] 本卡已登记进权威记录（§2 第 4 条的 `card` 命令，`--module`/`--depends` 与卡头一致；⑤ done 前全量登记完）

## §6 验收先于实现（阶段⑦）

**项目级基线（＝阶段⑦ 的阶段产物，第一张卡开工前就绪）**：
1. 全量测试/评测集先跑一遍记下基线分，**原始输出落 `<落盘目录>/evidence/`**（铁律 13：没落盘的输出不算实测）；
2. `stage ⑦ --state done` 的四字段照此填（铁律 19）：产物位置＝基线输出路径；完成条件＝「基线已跑且落盘」；恢复点＝「从 ⑥ 派第一张卡继续」。
   依赖口径：⑦ 只前置 ③（可先于 ④⑤ 跑），但 ⑥ 开工硬闸要求 ⑦④⑤ 全 done——**基线必须在施工开始前就位，不能边施工边补**。

**卡级（每张卡开工前）**：
1. 把该卡的验收命令/评测用例准备好（动生产码的卡先在旧代码上跑出失败面——先红后绿）；
2. 确认验收是"客观可判定"的（一条命令能跑出对/错，或清单可逐项打勾）；反例打回：「效果明显提升」「基本可用」这类判不出对错的写法＝没写验收（§5.3 第一条同款）；
3. 基线记录写进卡文件——数字写进卡的验收节（L2）与施工图第 8-9 节（L3），完成时对照，防"感觉做完了"。

> 灵魂来自 TDD（先看到失败再实现；对标 spec-kit tasks 模板「先写测试、确保实现前失败」，B 级），但不强制测试形式：评测基线、手动清单同样是合法的"先看到失败"。

## §8 资产卡（非代码资产：模型/数据集/数据管线，v1.28.0）

> 分工边界：EARS/specs/ 管**系统对资产的调用行为**（"系统应在模型超时 3s 后降级"是规格条款）；
> 资产卡管**资产本身的质量**（准确率漂移/数据分布/授权链）——**资产自身质量不进 specs/**，
> 防两处双写（同铁律 21① 分工逻辑）。硬塞 EARS 句式描述"模型行为"＝层错位，禁。

**六栏卡头**（随卡落 `docs/pipeline/cards/`，一资产一卡）：

```markdown
# 资产卡 {资产名}
- 资产名与版本/来源：{模型或数据集名、版本号、来源 URL 或内部路径}
- 评测集与基线分数：{评测集名/条数/当次基线分（原始输出落 evidence/，禁只写"效果不错"）}
- 已知失效模式：{什么输入会翻车（如长尾类别/对抗输入/超长文本），各配一条复现样例}
- 数据来源与授权：{训练/微调数据的来源与许可证；🔴 NC 协议素材禁入（全队资源红线照搬）；来源不明的写「未核实」并标 🔴}
- 复现命令：{加载/推理/评测各一条命令，下一个窗口拿到就能跑}
- 免责边界：{这卡不管什么（如"不承诺线上 p95"——那是宪章阈值的事），防验收时两头都来查这张卡}
```

（装了就用；没装=评测脚本/人工评测集对照，写明降级）；数据资产配 ODCS 式契约节（YAML 或表格皆可，判据=字段齐：
schema/质量规则/SLA 三段在盘）。资产变更（换版本/重训）＝开新卡对照旧基线，基线分只降不升时按阻断处理。
