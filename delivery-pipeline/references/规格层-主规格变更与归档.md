# 规格层：主规格 · 变更包 · 归档回路（挂在 ③立约 / ⑤切卡 / ⑥过卡 / ⑫定稿）

> **是什么**：一层机器可查的**行为契约**。它回答"系统现在承诺了什么行为、这次改动把哪条承诺改成了什么、改完并回主规格了没有"。
> **补的是本 skill 原有两个缺口**（2026-10-15 天点名，详案 → 修订记录·规格层移出节）：① 变更做完没有"并回主规格"这一步；② 没有任何东西能在被改坏时报警。
> **给谁用**：接手窗口读 `specs/` 三十秒知道系统承诺了什么；执行窗按变更包施工并按归档步骤收口；人拿 `spec_check.py` 一条命令看红绿。
> 产出物：`<项目根>/specs/<能力>/spec.md`（主规格）＋ `<项目根>/changes/<slug>/`（变更包）＋ `<项目根>/changes/archive/<日期>-<slug>/`（历史）。
> 反指针（要看代码里的判据原文）：`<skill根>/scripts/spec_check.py`；要看文档层分工：`项目文档与上下文规范.md` §0／§1。

## §1 布局（约定优先，工具可换）

```
<项目根>/
├── specs/                      ← 主规格：系统「当前」行为的唯一真相源
│   ├── booking/spec.md         ← 一个能力一个目录，目录名用能力名（短横线）
│   └── room/spec.md
├── trace/matrix.json           ← 追踪矩阵（v1.20.0）：条款↔符号↔测试↔走查↔卡的机读面，
│                                  由 scripts/trace_matrix.py gen 生成、check 验活性（别手改）
├── changes/                    ← 进行中的变更（一个变更一个包）
│   ├── add-cancel/
│   │   ├── proposal.md         ← 为什么改（问题＋收益，不写方案）
│   │   ├── design.md           ← 怎么改（技术决策，引用既有 ADR/选型记录）
│   │   ├── tasks.md            ← 勾选视图：本变更涉及哪几张卡
│   │   └── specs/booking/spec.md  ← 增量（ADDED/MODIFIED/REMOVED）
│   └── archive/2026-10-15-add-cancel/   ← 归档＝并回主规格后整包搬进来
```

**前缀可换**：装了 OpenSpec 之类的第三方 CLI 就整体搬进 `openspec/`（`openspec/specs/`、`openspec/changes/`）；`spec_check.py` 两种布局都自动识别，无需改代码。🔴 **换前缀≠搬结构**：`openspec/` 树里的需求块仍按本章 §3 的 `#### R-x | 标题`＋EARS（＋可选场景块）写，`spec_check` 才接得住；若按 OpenSpec 官方形态写成 `### Requirement:`＋`#### Scenario:`，那是 **OpenSpec-canonical 文件**，归它的 `openspec validate` 管（v1.19 起双尺口径：canonical 文件送外尺、house 格式送自尺，两把尺结论都落 `evidence/`）。**没装也照上面这套走**——本细则要的是机制（增量＋归档＋校验），不是某个工具。

🔴 **别把规格层写成第二份 PRD**：PRD 讲"要做什么、什么优先级"，主规格讲"系统当前承诺什么行为"。同一句话两处写＝两处会分叉（铁律 17）。

## §2 权威分工（六问六答，先定这个再动笔）

| 你想知道… | 唯一真相源 | 别处只准放指针 |
|---|---|---|
| 系统现在承诺什么行为 | `specs/<能力>/spec.md` | PRD 的功能列表只写编号与一句话，不复述条款 |
| 这次改动打算把它改成什么 | `changes/<slug>/specs/**` | 卡片只引用需求号，不抄条款原文 |
| 什么算做完（范围与优先级） | `PRD.md` | 卡的验收行引用编号 |
| 本项目不可违背的约束 | `PRD.md` 头部「项目宪章」节（5–8 条） | `AGENTS.md` 红线格只放一句指针 |
| 走到哪了 / 谁在动手 | `docs/pipeline/state.json` | 台账、任务板、`tasks.md` 全是派生视图 |
| 为什么这么分模块 / 这么选技术方案 | 模块地图决策记录节＋ADR | 地图正文不写理由全文 |

**冲突时以哪份为准**：行为看 `specs/`，进度看 `state.json`，范围看 `PRD.md`。第三条被改而前两条没动 = 规格在骗人，`spec_check` 会红。

## §3 主规格怎么写（判据就是这几行字，写歪了尺子会红）

需求块格式（**一条需求一个块，块内块级行只放一句可判定断言；场景块另计，见下**）：

```markdown
#### R-3 | 会议已开始不得取消

若预约的开始时刻早于当前时刻，则系统应拒绝该预约的取消请求。

- 状态：生效
- 验收：卡B3 tests/test_cancel.py
```

**EARS 五型**（需求句式的五种合法形状；判据＝行首与"系统应"的相对位置）：

| 型 | 中文句式（口径与脚本正则对齐） | 英文句式 | 什么时候用 |
|---|---|---|---|
| 普适型 | `系统应…`（行首） | `The system shall …`（行首，大小写不敏感） | 无条件成立的性质（不涉及触发时机） |
| 事件驱动 | `当/每当…时，系统应…`（"时"后必须逗号；`则/该/本`可插在"系统应"前） | `WHEN …, the system SHALL …` | 有明确触发点：点了、提交了、到期了 |
| 状态驱动 | `在/当…（状态/期间/情况下），系统应…`（行首到状态词 ≤20 字） | `WHILE …, the system SHALL …` | 只在某状态持续期间成立 |
| 不期望行为 | `若…则系统应…`（**逗号可省**；若→则、则→系统应各 ≤60 字且中间不得断句） | `IF …, THEN the system SHALL …` | 出错/违规/拒绝路径（异常反馈全放这型） |
| 可选功能 | `若/如…启用…，系统应…`（启用词前后各 ≤20 字） | `WHERE … is enabled, the system SHALL …` | 特性开关、按配置生效的行为 |

- 英文句型补注：`When/If/While/Where` 四型允许关键词与 `system shall` 出现在**行内任意位置**（两段间隔 ≤200 字）；`The system shall` 与中文各型则必须**行首**。全部大小写不敏感。

- 🔴 **一个块只准命中一种型**（命中两种＝你把两条需求塞进了一条，C03 红）；写成散文（一种都不命中）也红。C03 的机械口径＝块内非元信息行的**命中型名集合大小恰为 1**：同型两句连写**不会红**（机械尺查不出，别钻这个空子，语义面靠测试兜，见 §6 边界 1）；判型**按行**——一句断言必须一行写完，折行判不出。
- 原版 EARS 允许 While＋When 组合的 Complex requirements（见 §9）；**本库判据不认组合句**——要表达"某状态下发生某事件"，拆成两块各写一条。
- **元信息行不算断言**：以 `状态：`／`验收：`／`关联：`／`来源：`／`备注：`／`优先级：`／`负责人：`／`关键定位：` 这 **8 个前缀**开头的行不进句式校验（行首允许 `-`/`*` 短横，冒号全/半角均可）——它们是勾稽字段。**第 9 种前缀没有**：块里塞别的字段行（如"前置依赖：无"）不享受豁免——块内只放断言＋这 8 类勾稽行。
- **需求块标头统一写 `#### R-x | 标题`**：脚本宽容（2–5 个 `#`、全/半角竖线、标题可省都认），但**产出只准这一种写法**——两个窗写出两种样子就是漂移。需求号字符集＝字母/数字/下划线/点/短横。
- **需求号发出去就不回收**：删了 R-2 也别把 R-2 发给新需求（历史卡片、旧归档包、旧提交记录都还指着它）。
- 🔴 **禁行号锚点**（C13）：定位写「文件 + 标识符」，如 `api/booking.py 的 check_time_window()`。卡片里可以写行号（`阶段⑤切任务卡.md` §5.1 第 3 节明确允许"写卡时点，开工须复现"），**规格层不行**——规格活得比卡片久。
- **裸占位禁令**（C12）：没东西可写就写 `经确认：无（2026-10-15，依据：grep X 未命中）`，不许只写一个"无"（铁律 20）。

**场景块写法（v1.19.0 起，可选增强；OpenSpec 同款回流）**——一句 EARS 是契约的"纲"，多分支行为的"目"用场景块挂在同一条需求下：

```markdown
#### R-x | 标题

<一句 EARS 条款>

- 状态：生效
- 验收：<去向>

#### 场景：<场景名>

- **WHEN** <具体触发（对象＋操作＋数值）>
- **AND** <前置或叠加条件，可选，可多条>
- **THEN** <可观察结果（行为＋response）>
```

- 场景块口径（C15，真源＝脚本）：**写了就必须**粗体 WHEN/THEN 各至少一条（`AND` 可选、可多条），场景内 bullet 只准 WHEN/AND/THEN——夹带散文或场景之后拖行都翻红；**不写不红**——整文件零场景被聚合记一条**警**当场点名（推荐多分支需求逐条给，一对一目了然的行为不要硬凑）。
- 块内次序建议：条款句 → 8 类元信息 → 场景块。**场景段从其标头起吞到下一个场景标头或本需求块尾**——不能回到块级，别想着"场景后面再补一句备注"。
- **C03 的场景豁免**：句式校验只看场景之外的块级行——场景 bullet 里写"系统应…"、`when … the system shall …` 不会把该需求判成双型（哨兵用例 S33 钉死）。
- **与卡验收层 GWT 不重抄**（阶段① §3.2）：场景块答"这条承诺拆开是哪几种触发→结果"（契约面，进主规格）；卡的例表答"怎么验这一卡"（施工面，留卡里）。同一触发两边各写一遍＝分叉开始（铁律 17）。

## §4 变更包：增量只有三种动词

增量文件（`changes/<slug>/specs/<能力>/spec.md`）按标头切段，段内用与 §3 完全相同的需求块格式（**含场景块**：ADDED/MODIFIED 块可挂 `#### 场景：`，口径同主规格；REMOVED 段只写号不写句、不出场景）：

```markdown
## ADDED Requirements
#### R-5 | 取消后时间段释放
当一次预约被取消时，系统应将该时间段对后续预约重新开放。
- 状态：生效
- 验收：卡B3 tests/test_cancel.py

## MODIFIED Requirements
#### R-3 | 会议已开始不得取消
（这里写**改完之后**的整条新句子，不写"把'三点'改成'四点'"这种 diff 口语）

## REMOVED Requirements
### R-1
```

| 动词 | 语义 | 尺子怎么查 |
|---|---|---|
| ADDED | 主规格里**还没有**这条 | C04：ADDED 的号已在主规格 ⇒ 红（那是 MODIFIED） |
| MODIFIED | 主规格里**已经有**这条，整条重写 | C10：号不在主规格 ⇒ 红 |
| REMOVED | 主规格里**已经有**这条，行为作废 | C10 同上；C05 把 REMOVED 的号算"曾经存在"，否则归档之后老卡会全部误红 |

**开变更包的门槛**：只要这次改动**影响用户可观察的行为**就得开（哪怕只是"取消按钮变灰的条件改了"）。纯内部重构、纯改注释/文案不开包——但它若改了模块边界，走 `模块地图.md` §1 的回写。没有行为变化就别开空包（C08 会要求 `specs/` 增量非空）。

**增量文件三条机械口径**（判据真源＝脚本，此处抄录；不一致时以脚本为准并回改本细则）：
1. 标头必须是「`ADDED|MODIFIED|REMOVED`＋`Requirements`」**独占一行**（大小写不敏感，1–5 个 `#` 均认）；写成 `## ADDED 需求` 或标头后带尾巴（如 `## ADDED Requirements (booking)`）都不认。
2. **同一个动词只写一节**——同动词出现两个标头时脚本只认最后一节，前一节**静默漏检**（不红，比红更危险）。
3. REMOVED 段只写号不写句（`### R-1`，标题可带可不带），脚本对 REMOVED 段不做句式校验；OpenSpec 另有第四个动词 `RENAMED`，本库不收——改名用「REMOVED 旧号＋ADDED 新号」表达即可（依据见 §9）。

## §5 归档回路（天点名的那一步，五步，缺一不算收口）

**为什么必须归档**：变更包不并回，`specs/` 就永远停在"改动前"，三个窗口后没人分得清哪条是现状——主规格失去"这就是现状"的地位，这层就退化成第二份 PRD，白做。

1. **并回**：把增量的 ADDED 段整块追加进 `specs/<能力>/spec.md`；MODIFIED 段用新句**原地替换**旧块（保留需求号）；REMOVED 段把旧块整块删掉。并回的是"最终文本"，不是把 diff 抄进去。**REMOVED 要带引用清理**：把引用被删需求号的卡片改为指向承接号——C05 的"历史号豁免"只对还挂在 `changes/` 的增量生效，整包搬进 archive 后增量不再被扫描，引用已删号的卡会让 C05 红；清理必须做在搬包之前。
2. **搬包**：整个变更包目录移进 `changes/archive/<YYYY-MM-DD>-<slug>/`，原位置不留残骸（C09 就是查"卡全 done 却还挂在 changes/"）。
3. **记账**：`py <skill根>/scripts/pipeline_state.py action --root <项目根> --id archive-<slug> --kind 归档 --idem-key <slug> --evidence docs/pipeline/evidence/spec_check-<日期>.txt --done --apply`（不带 `--apply` 是干跑，只打印不落账）——幂等账保证续传窗口不会把同一个包归档两遍：续传先跑同一条命令换成 `--check`，**退 0＝已归档过，整套五步跳过；退 1＝没做过，继续**。
4. **跑尺**：`py <skill根>/scripts/spec_check.py check --root <项目根>`，退出码必须 0（或团队约定的严格档 `--strict`）。
5. **落盘**：把第 4 步的**原始输出**存进 `docs/pipeline/evidence/`，别只写"已跑过校验"（`testing-discipline`：没落盘的输出不算实测）。

🔴 **顺序即载荷，五步不许换序**：并回之后、搬包之前跑尺**必红**（主规格已含 ADDED 的号 ⇒ C04 红；主规格已删 REMOVED 的号 ⇒ C10 红）——这两红是"增量已并回、包还挂在 changes/"的**中间态信号**，不是让你回头改主规格；按顺序走完到第 4 步再跑尺就是绿的。

归档时机绑在过卡链上：`阶段⑥执行与派遣.md` §2.5 的第 5 步之后加"本卡若做完了一个变更包的最后一张卡 ⇒ 走 §5 五步"。

## §6 一把能红的尺：`spec_check.py`

```
py <skill根>/scripts/spec_check.py check --root <项目根> [--strict]
py <skill根>/scripts/spec_check.py selftest [--tmp-root <目录>]   # 只写临时树，不碰真实项目
```

退出码：`0` 全绿（可含警）｜`1` 有红（`--strict` 时含警）｜`2` 根目录不对。⚠️ 退 2 不是"没问题"，是"没查"。

**19 条断言**（编号即输出里的编号，标题与代码里的 `CHECKS` 一字不差；C01–C14 为 v1.12 原生，C15/C16 为 v1.19.0 OpenSpec 实测回流，C17–C19 为 v1.20.0 实测回流）：

| 号 | 标题 | 红/警 | 这条在防什么 |
|---|---|---|---|
| C01 | 规格层骨架在位且主规格有需求块 | 红 | 整层没建，或建了目录里没条款 |
| C02 | 验收指向的测试文件真在盘上 | 红 | 验收行写着 `tests/x.py` 而文件不存在＝空头承诺 |
| C03 | 每条需求有且只有一句 EARS 句式 | 红 | 写成散文／一块塞两条断言 |
| C04 | 需求号不得重复定义（ADDED 不得已在主规格） | 红 | 同一个号两处定义，或 ADDED/MODIFIED 用错 |
| C05 | 卡片引用的需求号必须存在于主规格或增量 | 红 | 先写卡后补规格（规格沦为说明书的附录） |
| C06 | 主规格每条需求都被至少一张卡接住 | 红／无卡时降警 | 条款写在天上没人施工 |
| C07 | tasks.md 勾选与 state.json 卡状态一致 | 红 | 勾与账打架 |
| C08 | 变更包四件齐（proposal/design/tasks/增量 specs） | 红 | 只有"改法"没有"为什么"，或空包 |
| C09 | 归档闭环：卡全 done 的变更包必须已归档并回主规格 | 红 | §5 缺失——本细则存在的首要理由 |
| C10 | MODIFIED/REMOVED 增量引用的需求号必须在主规格里 | 红 | 改动一条根本不存在的承诺 |
| C11 | PRD 含项目宪章 5–8 条，每条带阈值、零模糊词 | 红／无 PRD 时降警 | "高性能""要友好"这类不可判定约束 |
| C12 | 规格层与 PRD 禁裸占位「无／暂无」 | 红 | 铁律 20 在规格层的落地（不只扫 specs/＋PRD——扫描面见下注） |
| C13 | 规格层禁行号锚点（只准文件＋标识符） | 红 | 铁律 16 的快照禁令，扫 `specs/`＋`changes/`＋PRD＋模块地图（**不扫卡片**，卡片按 §3 允许） |
| C14 | 每条需求有验收去向（卡号或测试文件） | 红 | 有条款没验收＝无法证明它成立过 |
| C15 | 场景块：写了必须 WHEN/THEN 粗体成对（零场景文件记警） | 红／零场景聚合警 | 场景写半套＝"看着像验过"的空头；零场景＝多分支行为没有契约锚——可选增强，警级不强迫（OpenSpec 同款） |
| C16 | proposal 顶层三节锚齐（为什么/改哪些需求/影响面，英文同义可） | 警 | 只有"改法"没站住"为什么"（OpenSpec 同款三节；结构自定义可容忍，但当场点名） |
| C17 | 追踪矩阵活性（矩阵里的符号/测试/卡必须真在盘） | 红／无矩阵时降警 | 「关键定位」退化成死指针：条款指着一个早改名的符号，下一个人照着读空气 |
| C18 | 现状面声称计数与实测一致 | 警 | 手写「26 条／14 条断言／11 张卡」这类数字与实测不符——数字面漂移的当场点名 |
| C19 | 状态源唯一（归档后台账不得复活、视图必须带 AUTO 标记） | 警 | `state.json`／台账／清单三处并存，接手要交叉验证 |

**两把词表与一个扫描面**（C11/C12 判据，真源＝脚本常量 `FUZZY`/`THRESHOLD`/扫描清单，改判据先改脚本再同步此处）：模糊词＝尽量/大致/合适/高效/高性能/友好/良好/合理/较快/差不多/应当挺好——宪章条目含任一即红，**有数字也救不回**；阈值＝含数字或 不得/禁止/必须/只允许/≤/≥/零/唯一 之一——不含模糊词但无阈值词同样红。C12 与 C13 是**同一扫描面**：`specs/`＋`changes/` 全部 .md＋PRD＋模块地图（**不扫卡片**，卡片按 §3 允许写行号）；行号锚的机械形状＝「文件名.扩展名:数字」，且只认 py/md/js/ts/tsx/jsx/vue/sql/json/java/go/rs/html/css/sh 这批扩展名（`config.yaml:12` 这类查不到，别以为全防住）。

**这把尺已经自证过能红**（`selftest` 断言条数跑命令现采，正文不抄数）：合法树零红零警（地基）＋每条断言"做坏必须翻红"＋哨兵与反查＋**变异探针**（每臂打坏后点名用例必须翻 FAIL，原样对照臂全绿）。原始输出不落盘就不算做过——见 §5 第 5 步。

🔴 **它的三条边界，别对外吹**：
1. **只查机械面**：条款有没有句式、号对不对得上、文件在不在盘上。**语义漂移查不到**（`项目文档与上下文规范.md` §6.2）——代码把"若…则拒绝"改成"若…则警告"，尺子不会响，那靠测试与出题验收。
2. **不是 CI**：不装 hook、不进流水线、不联网；谁改完规格层谁自己跑一次。团队要自动化是另一个决定，别在细则里假装已经有。
3. **判据是这套文件形态约定**：`#### R-x | 标题`、`## ADDED Requirements` 写歪了它就不认。换工具（真装 OpenSpec）就按它的格式改夹具，别指望它替你判断写得对不对。
4. **细则与脚本的同步规则**：本细则抄录的判据口径（五型正则、8 个元信息前缀、两把词表、扫描面、增量标头形状）**以脚本为真源**——发现不一致，改脚本方为正着，然后回改本细则；只改细则不改脚本＝尺子没变、说明书变了，更危险。

## §6.5 追踪矩阵与 AGENTS.md 生成区（v1.20.0：把「人读的追踪」变成「机读的追踪」）

**它解决的问题**：条款里的「关键定位／验收」原本只有人能读——下一个窗口接手时，要在一堆 Markdown 里 grep 拼出"这条需求到底指哪几个符号"，而"该不该读后端"这种判断更是纯靠猜。

```
py <skill根>/scripts/trace_matrix.py gen   --root <项目根> [--apply]   # 生成 trace/matrix.json（默认干跑）
py <skill根>/scripts/trace_matrix.py check --root <项目根>             # 只读校验：死指针／矩阵过期／测试反标
py <skill根>/scripts/render_agents.py      --root <项目根> [--apply] [--init]   # 刷新 AGENTS.md 的生成区
```

**矩阵的内容**（每条形如 `{specKey, code:[{file,symbol}], tests:[{file,symbol}], walkthrough:[27], cards:["E1"], reverseTests:[…]}`），数据源全是现成件、**不需要人工登记**：

| 字段 | 从哪抽 | 抽不到时 |
|---|---|---|
| `code` | 需求块的 `- 关键定位：<路径> 的 <符号>（…）` | 该条只校验文件存在 |
| `tests` | 需求块的 `- 验收：<tests/…>::<用例>／… 的 <用例>a~d` | 空数组 |
| `walkthrough` | 验收行里的 `走查清单第 4、17 条` | 空数组 |
| `cards` | 验收行里的 `卡E1`／`卡 D1/D2` | 空对象 |
| `reverseTests` | **测试代码里的反标**：`@pytest.mark.req("R-36")`／`# req: R-36`／`// req: R-36` | 空 |

**「代码即追踪」的用法（推荐）**：在测试里给每条用例打一个反标（`// req: R-36`），矩阵的 `reverseTests` 就由代码自己声明；验收行仍是权威（T03 只记警：反标了但验收行连这个测试文件都没提 ⇒ 当场点名）。

**三条判据（`check`，C17 复用同一套语义）**：T01 活性（符号/用例/卡必须真在盘，死指针记**红**）｜T02 时效（specs/PRD/卡库 md5 与矩阵指纹不符＝矩阵过期，记**警**）｜T03 反标（文件级比对，记**警**）。**矩阵不存在只记一条警**——可选增强，不许借此炸老项目。

**AGENTS.md 的生成区（`render_agents.py`）**：渲染「现状读数／改动落点速查（文件→条款→符号）／模块路由」三块，**整块覆盖**而非增量 patch（增量更新的病是生成件停在半新半旧、最后没人知道哪行是真的；整体覆盖只有两种结果：完全反映当前真相，或失败时完全不动）。三个硬规矩：

1. 只碰 `<!-- AUTO-BEGIN … -->` 与 `<!-- AUTO-END -->` 之间；**缺标记时拒绝猜**（要插入必须显式 `--init`），防止把人的正文吞掉；
2. 人写区只留**红线/禁忌/代码风格/命令/「什么时候读哪份文档」**——凡是"数字"与"路由"一律不手写（这正是下一节 C18 要抓的）；
3. 写后**读回自证**（标记各 1 处＋生成区在位），不符就退 1 而不是当成功。

> **取舍说明（为什么不做"文档目录拆 auto/hand"）**→ 修订记录·规格层移出节：拆目录要动几十处引用与归档脚本，收益不如"文件内 AUTO 标记＋C19 认标记"；等真有第二个消费者再拆。

**外部评审回流的两条（2026-10-18，鲸桥咨询后当场补）**：

1. **T03 认目录形式**：验收行常写「`tests/api/` 全量回归」而反标落在具体文件——判据＝**父目录至少两级**（`tests/api`）且出现在验收行原文里也算登记；单独一个 `tests` 不算（几乎每行都出现，认了等于关掉 T03）。selftest 有正例哨兵。
2. **生成件之间的时效链**：生成区是矩阵的投影，矩阵变了而生成区没重跑＝两处分叉无人报警。修法＝生成区末尾写 `矩阵快照 <md5 前 12 位>`，`spec_check` C17 比对现值，不一致记警点名重跑。

（评审提了但没采的两条与理由 → 修订记录·规格层移出节。）

## §9 外部对标与依据强度（升级≠背书，别拿去当权威；检索/实测明细 → 修订记录·规格层移出节）

- **EARS 句式**：**B 级**（原始论文＋作者一手站已核对）。与本库差异两条：① 原版允许 While＋When 组合的 **Complex requirements**，本库"一块一型"是**收紧约定**（机械可判定优先于表达力）；② 五型的中文名与中文句式是本库约定，论文只有英文构式。
- **Delta/增量＋归档**：**B 级**（官方仓库文档核对＋2026-10-17 本机 CLI 对真实项目全流程实测通过，含中文能力目录名）。OpenSpec 的 `## Purpose` 字数与 ≤500 字符类**体量规定不采**——字数不等于契约质量。
- **宪章（Constitution）**：**B 级**（github/spec-kit 官方仓库核对）；旁证 ISO/IEC/IEEE 29148:2018"需求须可验证、避免主观语言"。
- **ADR（架构决策记录）**：**B 级**（Nygard 2011 原文＋adr.github.io）；五节短文档实践。
- **机械/语义漂移切分、"禁行号"、"单一权威状态源"、"一块一型"收紧**：**本库约定型**，有效性由 `spec_check` 自证；外部权威只证方向一致，不替本库盖章。

> 一句话口径：这层的价值不在"用了哪个工具"，在**行为契约与代码之间多了一条可机械复核的咬合链**，而且这条链能被证明会响。
