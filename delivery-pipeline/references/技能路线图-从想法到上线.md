## §1 主干图：想法 → 上线

```
【我有个想法】
      │
      ▼
① 磨设计 ── grill-me（深度追问审查）：盘问到无死角
      │        · 有代码库、且有 CONTEXT.md／ADR／术语表 → 走 B 分支（决策实时写回文档）
      │        · 什么都没有                            → 走 A 分支（纯对话，零写入）
      │        · 它开场自己探测、自己报走哪条，不用你指定
      │
      ├── 判据 A：每个问题都能在对话里定下来吗？
      │      否（状态模型对不对、界面长什么样，得跑起来才知道）
      │           → 绕道 prototype（原型设计）：用一次性代码答这一个问题
      │             两头用 handoff 桥接（本库未装 → 见 §6 降级写法）
      │             纪律：**留下答案，删掉代码**
      │      是 → 直接往下
      │
      ├── 判据 B：这是要跨多个会话干的活吗？
      │      是 → ③ to-prd（需求转PRD）把这段对话拧成 PRD
      │           → ⑤ to-issues（需求转Issue）把 PRD 拆成**可独立领取**的工单
      │           → 每张卡开一个全新会话跑 ⑥ implement（工单之间清空上下文，见 §3）
      │      否 → 就在当前会话里直接 ⑥ implement
      │
      ▼
⑥ implement（功能实现）── 内部驱动 tdd（测试驱动开发），一次一个红-绿切片
      │        红＝先写一个会失败的测试；绿＝写最小实现让它通过；然后重构
      ▼
⑦ 验收基线就绪（卡开工前就该就绪，不是做完才补；v1.18 起更是 ⑥ 开工的**硬前置**——
      │        ⑦ 未 done ⑥ 不许 doing，全 DAG 顺序闸，依赖表在脚本里现读，口径见 模式判定.md §七）
      ▼
⑪ code-review（代码审查）── 双轴审这份 diff：Standards 规范轴 ＋ Spec 需求轴
      ▼
⑫ 收尾（评测全跑＋CHANGELOG＋台账归档＋模块地图定稿＋可选推送）
```

**单独拿出来用的两件**：只想测试先行地做一个具体行为、不写整套 spec → 直接调 `tdd`；只想审一个分支或 PR 相对某个固定点的改动 → 直接调 `code-review`。

## §2 两个分支判据（这两问是主干的岔路口，别跳过）

| 判据 | 问自己 | 是 | 否 |
|---|---|---|---|
| **A** | 每个悬而未决的问题，都能**在对话里**定下来吗？ | 直接进判据 B | 绕道 `prototype`：有些问题（状态模型合不合手感、这个界面到底长什么样）只有跑起来才答得了。用一次性代码答它，**答案留下、代码删掉** |
| **B** | 这是**要跨多个会话**干的活吗？ | `to-prd` → `to-issues` → 每卡一个新会话跑 `implement` | 当场 `implement`，不必先造 PRD 与工单 |

判据 A 的绕道两头都要**过桥**：出去时把当前思路压成一份交接文件，回来时把学到的东西写回原来那条思路里（桥的写法见 §6）。

"哪些问题悬而未决"别凭感觉数：进 ① 盘问时按 `大计划产物模板.md` §1 的 **12 维检查单**逐项过（v1.15 起），哪一维当场给不出结论，哪一维就是判据 A 的绕道候选。

## §3 上下文卫生（这条最容易被忽略，代价最大）

- **①到⑤ 保持在同一个不间断的会话窗口里**——盘问、PRD、拆工单三步必须建立在**同一份思考**上。中途压缩或清空，等于让后面两步接着一个已经断片的脑子干活。
- 上限是 **smart zone（清醒区）**：模型还能锐利推理的那个窗口大小，当前一流模型约 **12 万 token**（出处：aihero.dev 的 AI coding dictionary，原 ask-matt 引的同一个源）。上下文一长、模型表现掉多少的**量化实证**在 `项目文档与上下文规范.md` §4 末注——本图不抄数。
- **接近上限还没拆完工单，别硬扛**——硬扛的代价是全程降质，且降质是静默的（不会报错，只会答得越来越钝）。正确动作：写交接文件，换新窗口接着干（§6）。
- 每一个 `implement` 反过来**都从干净窗口开始**，只带那张工单进去。工单之所以要"可独立领取"，就是为了这一步能干净起步。

## §4 入口匝道（不是从想法开始的活，从这里汇入主干）

```
【bug 和请求堆成山】                    【有东西坏了】
      │                                       │
      ▼                                       ▼
  triage（工单分流）                    diagnosing-bugs（缺陷诊断）
  把工单推过分流状态机，                 专治硬的那些：一眼看不出的、
  产出"可直接派给 agent"的工单           时好时坏的、两个已知良好状态之间
      │                                 悄悄溜进来的回退
      │                                 🔴 它拒绝在拿到**紧反馈环**之前讲道理
      │                                    ——先要一条"在这个 bug 上已经变红"的命令
      │                                    然后带一个回退测试去修
      │                                       │
      │                                       ▼
      │                                 事后复盘若发现真问题是"没有一道合适的缝
      │                                 能把这个 bug 锁死" → 交给
      │                                 improve-codebase-architecture
      ▼
  汇入主干 ⑥ implement 领取
```

🔴 **`triage` 只管不是你建的工单**——bug 报告、外来的功能请求、任何以原始形态到的东西。
`to-issues` 拆出来的工单**已经**是可直接派工的形态，**别再拿去分流一遍**（那是空转，还会把状态机搞浑）。

## §5 代码库保养 与 底层词汇（跑在其它技能底下）

**保养（不是功能开发）**

- `improve-codebase-architecture`（代码架构优化）——有空闲就跑，让代码库对 agent 保持友好。它扫出的是**深化机会**；挑中一个就**生出一个新想法**，拿回主干 ① 去盘问。它是找候选的勘测，`codebase-design` 是设计选中那个的工作台。

**底层词汇（两支都是"被别的技能调用"的参考件，各是其词汇的唯一事实源）**

- `domain-modeling`（领域建模）——磨项目的**领域语言**：质疑一个含糊的术语、拆开一个身兼三职的词（比如"账户"到底指哪个）、把难以回退的决定记成一份 ADR。它就是 `grill-me` B 分支驱动的那套纪律，用来让 `CONTEXT.md` 保持成一份干净的术语表。
- `codebase-design`（代码库架构设计）——**深层模块**词汇（模块、接口、深度、缝、适配器、杠杆、局部性），用来设计一个模块的**形状**：小接口后面藏大量行为、且落在一道干净的缝上。`tdd` 与 `improve-codebase-architecture` 都讲这套话。

**什么时候直接调它们**：当出问题的是**词**而不是**流程**时（同一个词两个意思、一个概念没名字）。否则让上层技能自己把它们拉进来。

## §6 跨会话，与本库的降级写法

| Matt 原工作流里叫 | 本库现状 | 怎么办 |
|---|---|---|
| `/handoff` | **未装** | 让当前 agent 把结论写成一份 `handoff.md`（交接文件），新会话开头引用它。作用一样：把对话压成一个 markdown 文件带过去 |
| `/compact` | **不是 skill**，是宿主内建 | 长会话上下文靠平台自动压缩。用在**阶段之间的刻意断点**上；**别在一个阶段中间压**——agent 会丢线索 |
| `/teach` | **未装** | 用 `education`（教学辅导助手） |
| `/writing-great-skills` | **未装** | 用 `skill-creator`（技能创建器） |
| `/setup-matt-pocock-skills` | **未装** | 上游用它一次性配好「工单落在哪＋分流标签词表」。本库降级：开工前当场问用户两件事——① 工单落在 GitHub（用 `gh` 命令行）还是本地 markdown 工单文件；② 本仓库实际的标签串是什么（`ready-for-agent`／`ready-for-human`／`needs-info`／`needs-triage`／`wontfix` 是**规范角色名**，不等于仓库里真实的标签串）。两件确认前只给建议、不建单不改标签。受影响三支 `to-prd`／`to-issues`／`triage` 已在各自 SKILL.md 就地写了降级句 |
| `/grilling` | **不是独立支**，内容在 `grill-me` 里 | 上游把盘问做成一个共用原语，`grill-me` 与 `grill-with-docs` 都调它。本库对应 `grill-me`（深度追问审查）的「共通盘问法」一节；要「边盘问边把决策写回 `CONTEXT.md`／ADR」那半截，走 `grill-me` 的**第 0 步自动判分支 → B 分支（文档锚定）**，它开场自己探测项目在不在这些文档，不必手工判。受影响两处：`triage` 工作流第 4 步已就地改成点 `grill-me`（2026-10-14 修）；`improve-codebase-architecture` 里「挑中候选后 run `/grilling`」那句**至今未就地修**（2026-10-15 实测仍在）——见到就按本行解，并待后续批次把那句就地改掉 |

**`handoff` 与 `compact` 的分水岭**：`handoff` 是**分叉**（开新会话，当前对话被保存下来带过去）；`compact` 是**继续**（留在同一个会话，早期轮次被摘要掉）。
要新窗口但需要保住当前对话 → 用交接文件。不介意丢掉逐字历史、只想留在原地 → 用压缩。

**进了流水线的项目**：换窗时机与交接文件的最小格式（四格路条）按 `项目文档与上下文规范.md` §4.1 走——那边管"什么时候必须换、带什么过去"，这里管"两个词各是什么、本库没装的件拿什么顶"，两边不互抄。

## §7 主线之外（独立件，不挂在主干上）

- `prototype`（原型设计）——一个小的、用完就扔的程序，只答一个设计问题。从第一天就是抛弃式的：**留答案，删代码**。它是判据 A 的那条绕道，但只要一个设计问题在纸上定不下来，随时可以拿它用。
- `research`（技术调研）——把读书的腿脚活派给一个**后台 agent**：它对着**一手来源**查一个问题，然后在仓库里留一份带引用的 markdown。它读的时候你继续干别的。它产出的那份文件是**拿进主干 ①** 的料——调研喂思考，不替代思考。
- `education`（教学辅导助手）——跨多个会话学一个概念，拿当前目录当有状态的工作区。
- `skill-creator`（技能创建器）——写好、改好一支 skill 的参考件。

**前置条件**：无需前置配置。工单跟踪用 GitHub（`gh` 命令行）或本地 markdown 工单文件都可以，开工前与用户确认用哪种。

## §10 为什么把 ask-matt 降成一张图（降级的依据）

> 五条依据（主干与流水线同条/独有价值是判据与外围/原路由表有死键/每轮注入税/渐进披露同向）→ 修订记录·技能路线图移出节。要点一句：**一支自称"路由器"的技能，路由表里有死键，比没有路由器更毒**；降成细则后按需加载，不占每轮启动税（铁律 9）。
