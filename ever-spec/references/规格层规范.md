# 规格层规范：主规格 · 变更包 · 归档回路（EverSpec 活正本）

> **是什么**：一层机器可查的**行为契约**。它回答"系统现在承诺了什么行为、这次改动把哪条承诺改成了什么、改完并回主规格了没有"。
> **给谁用**：接手窗口读 `specs/` 三十秒知道系统承诺了什么；执行者按变更包施工并按归档步骤收口；人拿 `spec_check.py` 一条命令看红绿。无管线可独立用（§三 纪律 5 的降级口径），也可作交付流水线的规格层适配（§7）。
> 产出物：`<项目根>/specs/<能力>/spec.md`（主规格）＋ `<项目根>/changes/<slug>/`（变更包）＋ `<项目根>/changes/archive/<日期>-<slug>/`（历史）。
> 反指针（要看代码里的判据原文）：`<EverSpec根>/scripts/spec_check.py`。
> 沿革：本件由交付流水线 `references/规格层-主规格变更与归档.md` 于 2026-10-27 抽出为活正本（判据原文逐条保真；管线叙事收进 §7）——管线侧那份自 v1.27.0 起冻结为适配快照。

## §1 布局（约定优先，工具可换）

```
<项目根>/
├── specs/                      ← 主规格：系统「当前」行为的唯一真相源
│   ├── booking/spec.md         ← 一个能力一个目录，目录名用能力名（短横线）
│   └── room/spec.md
├── trace/matrix.json           ← 追踪矩阵：条款↔符号↔测试↔走查↔卡的机读面，
│                                  由 scripts/trace_matrix.py gen 生成、check 验活性（别手改）
├── changes/                    ← 进行中的变更（一个变更一个包）
│   ├── add-cancel/
│   │   ├── proposal.md         ← 为什么改（问题＋收益，不写方案）
│   │   ├── design.md           ← 怎么改（技术决策，引用既有 ADR/选型记录）
│   │   ├── tasks.md            ← 勾选视图：本变更涉及哪些工作项
│   │   └── specs/booking/spec.md  ← 增量（ADDED/MODIFIED/REMOVED）
│   └── archive/2026-10-15-add-cancel/   ← 归档＝并回主规格后整包搬进来
```

**前缀可换**：装了 OpenSpec 之类的第三方 CLI 就整体搬进 `openspec/`（`openspec/specs/`、`openspec/changes/`）；`spec_check.py` 两种布局都自动识别，无需改代码。🔴 **换前缀≠搬结构**：`openspec/` 树里的需求块仍按本章 §3 的 `#### R-x | 标题`＋EARS（＋可选场景块）写，`spec_check` 才接得住；若按 OpenSpec 官方形态写成 `### Requirement:`＋`#### Scenario:`，那是 **OpenSpec-canonical 文件**，归它的 `openspec validate` 管（双尺口径：canonical 文件送外尺、house 格式送自尺，两把尺结论都落 `evidence/`）。**没装也照上面这套走**——本细则要的是机制（增量＋归档＋校验），不是某个工具。

🔴 **别把规格层写成第二份 PRD**：PRD 讲"要做什么、什么优先级"，主规格讲"系统当前承诺什么行为"。同一句话两处写＝两处会分叉（单一真相源纪律，SKILL.md §三）。

## §2 权威分工（六问六答，先定这个再动笔）

| 你想知道… | 唯一真相源 | 别处只准放指针 |
|---|---|---|
| 系统现在承诺什么行为 | `specs/<能力>/spec.md` | PRD 的功能列表只写编号与一句话，不复述条款 |
| 这次改动打算把它改成什么 | `changes/<slug>/specs/**` | 工作项只引用需求号，不抄条款原文 |
| 什么算做完（范围与优先级） | `PRD.md`（在项目根或 docs/ 下均可，脚本两处都认） | 工作项的验收行引用编号 |
| 本项目不可违背的约束 | `PRD.md` 头部「项目宪章」节（5–8 条） | `AGENTS.md` 红线格只放一句指针 |
| 走到哪了 / 谁在动手 | **有管线**：`docs/pipeline/state.json`；**无管线**：变更包 `tasks.md` 勾选或项目自带任务清单/issue（写一句降级声明） | 台账、任务板、`tasks.md` 全是派生视图 |
| 为什么这么分模块 / 这么选技术方案 | 模块/架构决策记录（ADR 类） | 决策记录正文不抄进规格 |
| 资产自身质量过不过（素材/模型卡这类资产本身） | 资产卡（管线侧阶段⑤ §8 六栏卡头；无管线项目自设等价卡） | specs/ 只写系统对资产的调用行为，不评资产自身质量 |

**冲突时以哪份为准**：行为看 `specs/`，进度看当期权威（state.json 或降级声明指的那份），范围看 `PRD.md`。第三条被改而前两条没动 = 规格在骗人，`spec_check` 会红。**无管线项目必须在 PRD 或 README 写明进度权威降级到哪份**（SKILL.md §三 纪律 5），禁两处各写各的。降级声明长什么样 → `examples/最小项目/README.md`（30 秒上手样例，`spec_check check` 实测退 0、只含降级警组）。

## §2.1 决策记录（ADR）：何时立、怎么立（MUST-15/04，v1.11.0 · K12）

§2 表「为什么这么分模块／这么选技术方案」那一行的真源实体＝ADR（架构决策记录）。与变更包 `design.md` 的分工：design.md 写"这次怎么改"并**引用**既有 ADR（§1 布局注释同款），不复述决策全文——同一决策两处各写一遍＝分叉开始。

**何时立——准入门槛三条，满足任一即立，一条不沾就不立**（随手写＝没人回看，ADR 贵在少而真）：
1. **翻盘付代价**：这个决策如果回头改，要动多处代码／契约／数据；
2. **不可逆**：对外发布、数据迁移、删除后难以撤销；
3. **曾有分歧**：两个合理方案真争过——拍板理由不写下来，下次还得从头吵一遍。

**怎么立**：模板＝`templates/ADR/`（MADR-lite 形状：状态／背景／决策／取代双向字段在场可机检；形状对标 MADR，四元组已登记 → `references/供应链登记.md` #6）。状态用 §3 状态机四态（草案→生效→已取代／废弃），写了才查（同 C23 口径）。

**supersede 纪律**：新 ADR 推翻旧 ADR 时，新旧两份各写一行——新份 `- 取代：<旧 ADR 路径>`，旧份改「状态：已取代」＋`- 被取代：<新 ADR 路径>`。文档级路径指针由 doc_lint D02–D04/D16 咬合（§6.8）；决策落到具体需求条款时用需求号指针，由 C30 咬合（§3 supersede 约定）。两套指针不混用：路径归路径、需求号归需求号。

### §2.2 设计期前奏（发散／收敛／重组三模式，v1.22.0 · K23 · 天令）

**新能力动笔前，先走一步"想清楚"**——三模式按诉求任选，全部是**指针引用编排件、不复制不依赖**；编排件缺席（换宿主/单装本件）就落自问清单，链不断：

| 模式 | 什么时候用 | 编排件（本机 skill 指针，缺席即降级） | 缺件自问清单（降级面） |
|---|---|---|---|
| **发散** | 只有一句模糊需求，要灵感与备选 | 头脑风暴-先想清再写码（superpowers brainstorming 同构，登记 #7） | ①这个能力一句话说清了吗②有没有更简单的等价做法③砍到只剩核心还剩什么④谁会用它、什么时候用 |
| **收敛** | 备选有了，要敲定细节 | 深度追问审查-盘问计划设计／带文档追问审查-边查文档边盘问（grill 与 grill-with-docs 同构，登记 #8） | ①边界条件列全了吗②错误输入会怎样③验收怎么判（EARS＋场景块「但是」）④哪条不可逆（立 ADR） |
| **重组** | 存在同类优秀 skill/模块，想拆解重组 | 走 **K11 逆向升格同构链路**（依赖图→现状清单→测试跑通→人审签收→转正），把"优秀件"当棕地资产反提 | ①优秀在哪（逐条挂证据）②哪些直接复用哪些重写③与本体系判据冲突处听谁的（本件口径优先，冲突登记） |

三条纪律：①编排件产出的**结论**要进规格仍走正常链路（变更包/需求块），不代表免检；②模式可跳过——需求已清晰时直接立约（§3），前奏不是强制闸门是减速带；③引用件与结论的取舍由人拍板，AI 只铺料。

## §3 主规格怎么写（判据就是这几行字，写歪了尺子会红）

需求块格式（**一条需求一个块，块内块级行只放一句可判定断言；场景块另计，见下**）：

```markdown
#### R-3 | 会议已开始不得取消

若预约的开始时刻早于当前时刻，则系统应拒绝该预约的取消请求。

- 状态：生效
- 验收：tests/test_cancel.py
```

**EARS 五型**（需求句式的五种合法形状；判据＝行首与"系统应"的相对位置）：

| 型 | 中文句式（口径与脚本正则对齐） | 英文句式 | 什么时候用 |
|---|---|---|---|
| 普适型 | `系统应…`（行首） | `The system shall …`（行首，大小写不敏感） | 无条件成立的性质（不涉及触发时机） |
| 事件驱动 | `当/每当…时，系统应…`（"时"后必须逗号；`则/该/本`可插在"系统应"前） | `WHEN …, the system SHALL …` | 有明确触发点：点了、提交了、到期了 |
| 状态驱动 | `在/当…（状态/期间/情况下），系统应…`（行首到状态词 ≤20 字） | `WHILE …, the system SHALL …` | 只在某状态持续期间成立 |
| 不期望行为 | `若…则系统应…`（**逗号可省**；若→则、则→系统应各 ≤60 字且中间不得断句） | `IF …, THEN the system SHALL …` | 出错/违规/拒绝路径（异常反馈全放这型） |
| 可选功能 | `若/如…启用…，系统应…`（启用词前后各 ≤20 字） | `WHERE … is enabled, the system SHALL …` | 特性开关、按配置生效的行为 |

- 英文句型补注：`When/If/While/Where` 四型允许关键词与 `system shall` 出现在**行内任意位置**（两段间隔 ≤200 字）；`The system shall` 与中文各型则必须**行首**。全部大小写不敏感。

- 🔴 **一个块只准命中一种型**（命中两种＝你把两条需求塞进了一条，C03 红）；写成散文（一种都不命中）也红。C03 的机械口径＝块内非元信息行的**命中型名集合大小恰为 1**：同型两句连写**不会红**（机械尺查不出，别钻这个空子，语义面靠测试兜，见 §6 边界 1）；判型**按行**——一句断言必须一行写完，折行判不出。
- 原版 EARS 允许 While＋When 组合的 Complex requirements（见 §9）；**本库判据不认组合句**——要表达"某状态下发生某事件"，拆成两块各写一条。
- **元信息行不算断言**：以 `状态：`／`验收：`／`关联：`／`来源：`／`备注：`／`优先级：`／`负责人：`／`关键定位：`／`取代：`／`被取代：`／`有效至：`／`待决问题：` 这 **12 个前缀**开头的行不进句式校验（行首允许 `-`/`*` 短横，冒号全/半角均可）——它们是勾稽字段。**清单之外没有第 13 种前缀**：块里塞别的字段行（如"前置依赖：无"）不享受豁免——块内只放断言＋这 12 类勾稽行。后四个前缀的语义与机检见下方「文档状态机与读取集」「TBD 占位约定」两节与 §4「歧义冻结」节。
- **需求块标头统一写 `#### R-x | 标题`**：脚本宽容（2–5 个 `#`、全/半角竖线、标题可省都认），但**产出只准这一种写法**——两个窗写出两种样子就是漂移。需求号字符集＝字母/数字/下划线/点/短横。
- **需求号发出去就不回收**：删了 R-2 也别把 R-2 发给新需求（历史工作项、旧归档包、旧提交记录都还指着它）。
- 🔴 **禁行号锚点**（C13）：定位写「文件 + 标识符」，如 `api/booking.py 的 check_time_window()`。施工单（卡/任务）里可以写行号（写卡时点，开工须复现），**规格层不行**——规格活得比施工单久。
- **裸占位禁令**（C12）：没东西可写就写 `经确认：无（2026-10-15，依据：grep X 未命中）`，不许只写一个"无"（必填项禁裸占位纪律，SKILL.md §三）。
- **验收行写阈值必须带得起测量**（C20，阈值三件套·规格侧）：验收行里出现阈值形状（数字×比较符或计量单位，如 `p95<500ms`、`≤200 条`），就必须同行带**测量命令**（如 `- 验收：接口 p95<500ms，测量命令：py bench_api.py`）或**测试引用**（`tests/test_perf.py`——测试本身就是 fitness function，pytest 即测量命令）；两者皆无＝阈值只活在散文里、测试写不出红灯，记警当场点名。三件套＝**指标名＋数值＋测量命令**，缺一不可。
- **验收去向三形态**（C14）：验收行指向**卡号**、**测试文件**（`tests/test_x.py` 或 `test_*` 函数锚）或**走查清单条目**（`- 验收：走查清单第 4、17 条`）都算合法去向。走查清单建议住 PRD「用户视角走查清单」节（C18 会数它的条数）；**走查＝验收即演示动线**——同一张清单开发验收跑一遍、面试/交接现场再跑一遍，条目级证据（截图/读数）落 `evidence/`。

**文档状态机与读取集**（MUST-06，v1.9.0 · K04 起地基；机检＝C23）——`状态：` 字段收口四个值，写了别的值＝C23 红：

| 状态值 | 语义（承诺面） | 读取集（谁必读） | 典型转移 |
|---|---|---|---|
| `草案` | 起草中，**不进承诺面** | 开工/重锚时必读；对外承诺查询跳过 | →生效（签收后） |
| `生效` | 现行承诺 | 必读（默认档） | →已取代／废弃 |
| `已取代` | 历史版本，被更新条款替代 | 只在溯因/读历史时读 | 终态，必带取代指针 |
| `废弃` | 不再承诺且无替代 | 默认跳过 | 终态 |

- **值收口，不写不红**：四态之外的值（「已完成」「生效中」「上线」各写各的）＝机器认不出承诺面，C23 红；**不写状态行的块不查**——字段是增强约定，存量项目零冲击。
- **supersede 双向字段**（K12 卡承接，机检＝C30，v1.11.0 起）：`取代：R-x`＝本块替代了它；`被取代：R-x`＝本块被它替代。**双向缺一即红**：只写单边、对侧块不在场（指针落空）、对侧不回指、自指 ⇒ C30 红——被替代的历史块以「状态：已取代＋被取代：新号」墓碑**留在主规格**，别整块删了让指针落空。状态改「已取代」时二选一在场（人读纪律不变）。指针值形态分工：`R-x` 需求号形态归 C30（本尺）；`references/旧版.md` 这类路径形态是文档级指针，归 doc_lint D02–D04/D16 咬合（§6.8），两套指针不混用。C30 只管成对回指，被取代侧的状态转移时点归 §5 归档纪律人审。
- **读取集消费方**（约定面，机检随后续卡只追加）：开窗重锚的必读清单按状态过滤；目录生成器含状态列；provenance/引用面只认生效块。
- **归档转移纪律**：变更包并回时，被 MODIFIED/REMOVED 的主规格块同步改「已取代/废弃」＋带指针——不转移＝两块同讲一个行为；语义面尺子不查，靠归档五步的人审（§5）。

**TBD 占位约定**（MUST-13 地基，v1.9.0 · K04 起；机检＝C24＋C29）：需求块内可写 `TBD` 标记「暂定、等补」，但**同块必须带 `- 有效至：YYYY-MM-DD`** 元信息行（ISO 日期，如 2027-01-31）——没有到期日的 TBD＝永远赖账，C24 红。**C24 只管形状**；到期判红＝C29 收口断言（v1.10.0 · K10 追加，MUST-13 收口）：有效至日期**早于今天** ⇒ C29 红（到期日一过还在 TBD＝赖账坐实，补内容或销账）；**今天及以后不红**；形状过但日期值非法（如 `2027-13-45`）⇒ C29 不咬（不越权管值合法性，后续只追加）。`有效至` 是通用 ttl 字段：谁必须带由断言点名（当前＝含 TBD 的块），后续只追加。

**域规格头部写什么**（`specs/<能力>/spec.md` 开头，人读的三件，机器不查、语义面归人判）：①**核对日期沿革**——何时立约、何时并回哪个变更包，一行一事，新事件追加不涂改；②**对照的事实**——本域规格对照需求/设计纪要的哪几节，防"条款凭空长出来"；③**全局口径声明**——全域统一的解释口径（如「时段区间左闭右开 `[开始, 结束)`，紧邻不算冲突」），写一次、全域引用，防同词异解。

**场景块写法（可选增强；OpenSpec 同款回流）**——一句 EARS 是契约的"纲"，多分支行为的"目"用场景块挂在同一条需求下：

```markdown
#### R-x | 标题

<一句 EARS 条款>

- 状态：生效
- 验收：<去向>

#### 场景：<场景名>

- **WHEN** <具体触发（对象＋操作＋数值）>
- **AND** <前置或叠加条件，可选，可多条>
- **THEN** <可观察结果（行为＋response）>
```

- 场景块口径（C15，真源＝脚本）：**写了就必须**粗体 WHEN/THEN 各至少一条（`AND` 可选、可多条），场景内 bullet 只准 WHEN/AND/THEN——夹带散文或场景之后拖行都翻红；**不写不红**——整文件零场景被聚合记一条**警**当场点名（推荐多分支需求逐条给，一对一目了然的行为不要硬凑）。
- **反向断言用「但是」（K22·v1.21.0，Gherkin 中文关键字全表）**：`假设/假如/假定`＝Given｜`当`＝When｜`那么`＝Then｜`并且/而且/同时`＝And（补同类）｜**`但是`＝But（补反向：不应该出现什么用它，正反断言一眼分开）**——全用「并且」会把正反两类断言混在一起，将来接 Cucumber/Behave 自动化也难分；本件只取写法，不装 BDD 工具（L0 档口径）。
- 块内次序建议：条款句 → 12 类元信息 → 场景块。**场景段从其标头起吞到下一个场景标头或本需求块尾**——不能回到块级，别想着"场景后面再补一句备注"。
- **C03 的场景豁免**：句式校验只看场景之外的块级行——场景 bullet 里写"系统应…"、`when … the system shall …` 不会把该需求判成双型（哨兵用例钉死）。
- **与施工验收层 GWT 不重抄**：场景块答"这条承诺拆开是哪几种触发→结果"（契约面，进主规格）；施工单的例表答"怎么验这一项"（施工面，留施工单里）。同一触发两边各写一遍＝分叉开始（单一真相源纪律）。

### 锚点分级（v1.19.0 · v3-K18）：关键定位行从"写给 AI 看"升级为"机器咬得住"

- **v0（缺省，存量零冲击）**：关键定位写自由文本（文件＋标识符），尺子不查链接形态——存量规格与只读镜像不受波及。
- **v1（块级自标记 `- 锚点：v1`）**：该块的关键定位行必须写成**仓库内相对链接**＋标识符（形状样例＝`- 关键定位：[spec_check.py](../scripts/spec_check.py) 的 run_checks()`，这条就是真锚——指向本件自己的尺子），且目标**必须在盘**——链接目标不在盘＝代码改名/删除未回改规格，**C31 红**。这是「用户直接改了代码，Agent 会知道」的机械半边；行为变了的那半边仍归[漂移分类学](漂移分类学.md)的人判流程。
- **存量迁移三步**（AI 重排，人不逐条搬）：①AI 按本节判据把存量关键定位行批量改写为链接；②跑尺红清零；③**人抽查锚点真实性**（AI 只重排不裁决，抽中的锚点由人开文件确认指向真函数）。
- API 契约（OpenAPI/接口 schema）是代码工件，不入 specs/——锚点只咬行为契约与代码之间。

## §3.5 棕地反提三步＋逆向升格四步（存量项目怎么长出 specs/）

**适用**：项目已有代码与测试、没有 `specs/`。**灵魂＝现状/承诺分离**——反提件描述"代码**现在**干的事"，不因写成了 EARS 就变成承诺；三步走完、人审签收之前，`specs/` 不存在。

1. **依赖图打底**：装了 dependency-cruiser 就用它（JS/TS 生态顺手；Python 项目走零依赖 ast import 图，骨架如下）——先知道"谁 import 谁"再挑模块起草，防把挂点写错层。🔴 `from 包 import 子模块` 要按「module 本身 ∪ module.alias」候选匹配，只按包名匹配会把全包注水成假入边（实测踩过：60+ 假边全由此来）。

   ```python
   import ast
   from pathlib import Path
   mods = {}
   for p in Path("app").rglob("*.py"):
       rel = p.with_suffix("").as_posix().replace("/", ".").removesuffix(".__init__")
       mods[rel] = p
   edges = set()
   for rel, p in mods.items():
       for node in ast.walk(ast.parse(p.read_text(encoding="utf-8", errors="replace"))):
           cands = [a.name for a in node.names] if isinstance(node, ast.Import) else (
               [node.module] + [f"{node.module}.{a.name}" for a in node.names]
               if isinstance(node, ast.ImportFrom) and node.module and node.level == 0 else [])
           edges |= {(rel, c) for c in cands if c in mods and c != rel}
   # edges＝模块级依赖边；挑挂点层先看目标模块的入边（谁依赖它）
   ```

2. **AI 起草「现状行为清单」**：从依赖图挑能力挂点模块，起草 EARS 块（写法同 §3），**头部显式标 `> status: 现状描述（反提）`**，存 `<项目根>/reverse/<能力>-反提草案.md`——`reverse/` 自 v1.16.0 起纳入 spec_check 扫描面，但**只查证据坐标与签收闸三面**（反提件不是契约：句式/状态机/场景判据不进，见下方逆向升格四步）；每条带「关键定位：文件＋标识符」（禁行号，同 §3）与「拟验收：现有测试文件」。需求号转正时才分配（草案编号不作数，避免占掉"发出去不回收"的号）。
3. **现有测试跑通当覆盖度验证＋人审签收才转正**：现有测试全绿（原始输出落 evidence/）；人逐条核对草案与代码一致、分配正式需求号、签收（签收人＋日期写进草案）后**去反提标、状态改「生效」**，整块移进 `specs/<能力>/spec.md`，跑 `spec_check check` 必须全绿。**未签收不转正**——带反提标记的需求块混进 specs/ 吃 C21 红。

🔴 **疑似缺陷单列交人拍板，禁静默写进规格**：反提中发现的疑似 bug／已知边界（含模块自己 docstring 登记的遗留）一律单列成清单交人拍板——修复、或如实规格化（条款＋备注注明来源与取舍）、或不收；**反提的最大风险就是把现状的缺陷镀金成契约**。样板＝本件自带 `evidence/reverse-u16/audit-chain-反提草案.md`（真实存量项目走通三步的实测件：依赖图＋11 条草案＋23 测跑通＋疑似缺陷 3 条＋签收栏）。

**逆向升格四步（v1.16.0 · K11 · MUST-14）**：反提草案不是写完就完——它要能**转正成契约**，转正链路每一步都有尺子咬合：

1. **草案必带证据坐标**：每条现状条款带「关键定位：文件＋标识符」——缺坐标吃 C21 红（条款挂在空气上，转正后无人能核对；C21 扩容面①）。
2. **带行号锚也红**：证据坐标只准文件＋标识符，行号是快照必漂（同 C13 口径；C21 扩容面②）。
3. **转正三动作**：人审签收（签收人＋日期写进草案）→ 分配正式需求号＋去反提标＋状态改「生效」，整块移进 `specs/<能力>/spec.md` → 构成不可逆决定的立 ADR（§2.1，模板带取代双向字段）。
4. **未签收不转正**：`specs/` 或增量的需求块若带「来源：reverse/…」，指向的草案**不在盘或缺「签收：」行** ⇒ C21 红（面③）——人审闸门被跳或转正溯源断链。签收行住在草案里，**不进主规格块**（S104 哨兵钉住这个反误伤面：补签收后来源转正必须零红）。

**三把尺分工**（防重复机检）：文档级取代＝doc_lint（D02–D04，路径形态）；需求号级取代双向＝C30（K12）；反提件证据坐标与签收闸＝C21 扩容。模板＝`templates/逆向推断件.md`。

## §4 变更包：增量只有三种动词

增量文件（`changes/<slug>/specs/<能力>/spec.md`）按标头切段，段内用与 §3 完全相同的需求块格式（**含场景块**：ADDED/MODIFIED 块可挂 `#### 场景：`，口径同主规格；REMOVED 段只写号不写句、不出场景）：

```markdown
## ADDED Requirements
#### R-5 | 取消后时间段释放
当一次预约被取消时，系统应将该时间段对后续预约重新开放。
- 状态：生效
- 验收：tests/test_cancel.py

## MODIFIED Requirements
#### R-3 | 会议已开始不得取消
（这里写**改完之后**的整条新句子，不写"把'三点'改成'四点'"这种 diff 口语）

## REMOVED Requirements
### R-1
```

| 动词 | 语义 | 尺子怎么查 |
|---|---|---|
| ADDED | 主规格里**还没有**这条 | C04：ADDED 的号已在主规格 ⇒ 红（那是 MODIFIED） |
| MODIFIED | 主规格里**已经有**这条，整条重写 | C10：号不在主规格 ⇒ 红 |
| REMOVED | 主规格里**已经有**这条，行为作废 | C10 同上；C05 把 REMOVED 的号算"曾经存在"，否则归档之后老工作项会全部误红 |

**开变更包的门槛**：只要这次改动**影响用户可观察的行为**就得开（哪怕只是"取消按钮变灰的条件改了"）。纯内部重构、纯改注释/文案不开包——纯文案改动的文档层各归各的维护流程。没有行为变化就别开空包（C08 会要求 `specs/` 增量非空）。

**增量文件三条机械口径**（判据真源＝脚本，此处抄录；不一致时以脚本为准并回改本细则）：
1. 标头必须是「`ADDED|MODIFIED|REMOVED`＋`Requirements`」**独占一行**（大小写不敏感，1–5 个 `#` 均认）；写成 `## ADDED 需求` 或标头后带尾巴（如 `## ADDED Requirements (booking)`）都不认。
2. **同一个动词只写一节**——同动词出现两个标头时脚本只认最后一节，前一节**静默漏检**（不红，比红更危险）。
3. REMOVED 段只写号不写句（`### R-1`，标题可带可不带），脚本对 REMOVED 段不做句式校验；OpenSpec 另有第四个动词 `RENAMED`，本库不收——改名用「REMOVED 旧号＋ADDED 新号」表达即可（依据见 §9）。

**零增量逃生口（Skip-Specs 声明，v1.9.0 起；机检＝C08 豁免＋C25）**：纯流程变更（只改 proposal/design/tasks，无任何行为变化）也允许开包，但**必须在 proposal 里显式声明**——顶层写 `## Skip-Specs` 节（标题即声明，内容自由）或元信息行 `- skip-specs：true`（大小写不敏感）。声明了 ⇒ C08 不再要求 specs/ 增量（对标 OpenSpec `skip_specs: true`——机制同构，载体从 yaml 换成本库 proposal，不引工具）；**没声明的空包照红**。声明与事实矛盾（声明零增量却带着 specs/ 增量）＝C25 红——豁免口被滥用＝静默漏检，两头骗比不声明更坏。

**provenance 来源强制（v1.9.0 起；机检＝C26）**：变更包是需求块出生的地方——增量 **ADDED/MODIFIED 块必须带 `- 来源：<出处>` 行**（出处写到能找回原话的坐标：`PRD §功能列表`、`需求纪要 2026-10-15`、`对话 2026-10-20 客户原话` 都算；裸「来源：无」不算溯源）。缺＝「这条哪来的」验收时无人能答，脑补口径混进承诺面（P0-6）。主规格与 REMOVED 段不查（存量项目零冲击；REMOVED 只写号没句子）。

**歧义冻结（v1.9.0 起；机检＝C27）**：转条款时遇到歧义，当场在块内登记 `- 待决问题：<问题原文>`（英文 `open-questions：` 同认）——登记了就必须把状态冻结在「草案」，问题解掉才许转「生效」；登记了却停在生效（或干脆没写状态行）＝C27 红。没登记标记的块不查（写了才查）。与 TBD 的分工：**TBD＝内容暂缺等补**（带有效至，C24 管）；**待决问题＝口径有分歧等拍板**（冻结草案，C27 管）。

**Capabilities 能力面（可选增强，v1.9.0 起；机检＝C28 警）**：proposal 可写 `## Capabilities`（或「能力面」）节列本次涉及的能力目录（`- booking: specs/booking/spec.md`，### New/### Modified 分小节）——**写了就查**：节内 `specs/<能力>` 必须真在盘（主规格或本包增量），查无 ⇒ C28 警点名（写错字当场暴露）。没写节不查。**评估结论：近重复能力名（booking vs bookings）不机检**——机械相似度判据误伤率高，机械尺不装懂，语义面归人审；C28 的路径在场已把「列了不存在的能力」兜住，本节当 proposal→specs 路径契约用，警级不强迫。

**漏捕对账（MUST-12 · P0-7，人工兜底）**：换窗/交接时口头答应的需求最容易蒸发——把交接块里的**需求性陈述**（"应该要支持…"、"客户要…"）逐条对照已落盘的变更包与主规格：有承接 ⇒ 写明落在哪个变更包/条款号；没有 ⇒ 列**漏捕候选**交人拍板（收编成变更包／丢弃／挂起，签收人＋日期落表）。这是人工兜底不是机检——机械尺判不出"这句话算不算需求"，别指望 C25–C28 替你做这件事。模板＝`templates/漏捕对账.md`（三栏：陈述／承接去向／裁决）。

### 对账（reconcile，v1.20.0 · v3-K19）：代码动了，哪些条款被波及

`py scripts/reconcile.py check --root <项目根> [--since <rev>] [--write-skeleton]`——两个受影响面：**锚点面**（关键定位目标不在盘）＋**变更面**（目标文件在 git 变更集内，需 --since）。输出四列表（条款/证据锚/怎么验/**判定留空**，模板＝`templates/对账四列.md`）；`--write-skeleton` 产出四件齐变更包草案（过 C08 结构面，占位块 C03 红＝待人填的预期信号）。🔴 AI 不裁决一致性：对账只举证，判定列永远归人（[漂移分类学](漂移分类学.md)）。

## §5 归档回路（五步，缺一不算收口）

**为什么必须归档**：变更包不并回，`specs/` 就永远停在"改动前"，三个窗口后没人分得清哪条是现状——主规格失去"这就是现状"的地位，这层就退化成第二份 PRD，白做。

1. **并回**：把增量的 ADDED 段整块追加进 `specs/<能力>/spec.md`；MODIFIED 段用新句**原地替换**旧块（保留需求号）；REMOVED 段把旧块整块删掉。并回的是"最终文本"，不是把 diff 抄进去。**REMOVED 要带引用清理**：把引用被删需求号的工作项改为指向承接号——C05 的"历史号豁免"只对还挂在 `changes/` 的增量生效，整包搬进 archive 后增量不再被扫描，引用已删号的工作项会让 C05 红；清理必须做在搬包之前。
2. **搬包**：整个变更包目录移进 `changes/archive/<YYYY-MM-DD>-<slug>/`，原位置不留残骸（C09 就是查"工作项全 done 却还挂在 changes/"）。
3. **记账（可选：有台账/状态系统则记）**：宿主有幂等账就记一笔"已归档"（交付流水线适配模式＝`py <管线根>/scripts/pipeline_state.py action --root <项目根> --id archive-<slug> --kind 归档 --idem-key <slug> --evidence <证据路径> --done --apply`；不带 `--apply` 是干跑）——幂等账保证续传窗口不会把同一个包归档两遍。**无台账的项目跳过此步**，靠第 4 步的落盘输出当"做过"的凭证。
4. **跑尺**：`py <EverSpec根>/scripts/spec_check.py check --root <项目根>`，退出码必须 0（或团队约定的严格档 `--strict`）。
5. **落盘**：把第 4 步的**原始输出**存进 `evidence/`（本件或项目内均可，路径写进交接说明），别只写"已跑过校验"（测试证据纪律：没落盘的输出不算实测）。多批证据要防事后翻改 → 证据哈希链（§6.6）。证据实务三条：①多主题分组按 `evidence/<主题>-<日期>/` 建目录，别全平铺成一个大海；②**作废件改 `作废-` 前缀保留为证词**，不删除不覆盖（证词不改史）；③红绿对照的原始输出可直接放变更包内 `evidence/` 子目录（如 `evidence/红-import即红.txt`＋`evidence/绿-测试全过.txt`），整包搬 archive 时证据随包走。

🔴 **顺序即载荷，五步不许换序**：并回之后、搬包之前跑尺**必红**（主规格已含 ADDED 的号 ⇒ C04 红；主规格已删 REMOVED 的号 ⇒ C10 红）——这两红是"增量已并回、包还挂在 changes/"的**中间态信号**，不是让你回头改主规格；按顺序走完到第 4 步再跑尺就是绿的。

**两把词表与一个扫描面**（C11/C12 判据，真源＝脚本常量 `FUZZY`/`THRESHOLD`/扫描清单，改判据先改脚本再同步此处）：模糊词＝尽量/大致/合适/高效/高性能/友好/良好/合理/较快/差不多/应当挺好——宪章条目含任一即红，**有数字也救不回**；阈值＝含数字或 不得/禁止/必须/只允许/≤/≥/零/唯一 之一——不含模糊词但无阈值词同样红。C12 与 C13 是**同一扫描面**：`specs/`＋`changes/` 全部 .md＋PRD＋模块地图（**不扫施工单**，施工单按 §3 允许写行号）；行号锚的机械形状＝「文件名.扩展名:数字」，且只认 py/md/js/ts/tsx/jsx/vue/sql/json/java/go/rs/html/css/sh 这批扩展名（`config.yaml:12` 这类查不到，别以为全防住）。

**这把尺已经自证过能红**（`selftest` 断言条数跑命令现采，正文不抄数）：合法树零红零警（地基）＋每条断言"做坏必须翻红"＋哨兵与反查＋**无管线模式哨兵**（docs/ 整棵缺失必须零红，只准警）＋**变异探针**（每臂打坏后点名用例必须翻 FAIL，原样对照臂全绿）＋**文档面自咬**（SKILL.md/本细则自称的断言条数与冻结区间被 S60 绑进 selftest，漂移＝自证红）。原始输出不落盘就不算做过——见 §5 第 5 步。

🔴 **它的四条边界，别对外吹**：
1. **只查机械面**：条款有没有句式、号对不对得上、文件在不在盘上。**语义漂移查不到**——代码把"若…则拒绝"改成"若…则警告"，尺子不会响，那靠测试与人工验收。
2. **不是 CI**：不装 hook、不进流水线、不联网；谁改完规格层谁自己跑一次。团队要自动化是另一个决定，别在细则里假装已经有。要挂强制触发点（pre-commit 样例＋三态 waiver 纪律）→ `templates/hooks/README.md`。
3. **判据是这套文件形态约定**：`#### R-x | 标题`、`## ADDED Requirements` 写歪了它就不认。换工具（真装 OpenSpec）就按它的格式改夹具，别指望它替你判断写得对不对。
4. **细则与脚本的同步规则**：本细则抄录的判据口径（五型正则、12 个元信息前缀、两把词表、扫描面、增量标头形状）**以脚本为真源**——发现不一致，改脚本方为正着，然后回改本细则；只改细则不改脚本＝尺子没变、说明书变了，更危险。

## §6.5 追踪矩阵与 AGENTS.md 生成区（把「人读的追踪」变成「机读的追踪」）

**它解决的问题**：条款里的「关键定位／验收」原本只有人能读——下一个窗口接手时，要在一堆 Markdown 里 grep 拼出"这条需求到底指哪几个符号"，而"该不该读后端"这种判断更是纯靠猜。

```
py <EverSpec根>/scripts/trace_matrix.py gen   --root <项目根> [--apply]   # 生成 trace/matrix.json（默认干跑）
py <EverSpec根>/scripts/trace_matrix.py check --root <项目根>             # 只读校验：死指针／矩阵过期／测试反标
py <EverSpec根>/scripts/render_agents.py      --root <项目根> [--apply] [--init]   # 刷新 AGENTS.md 的生成区
```

**矩阵的内容**（每条形如 `{specKey, code:[{file,symbol}], tests:[{file,symbol}], walkthrough:[27], cards:["E1"], reverseTests:[…]}`），数据源全是现成件、**不需要人工登记**：

| 字段 | 从哪抽 | 抽不到时 |
|---|---|---|
| `code` | 需求块的 `- 关键定位：<路径> 的 <符号>（…）` | 该条只校验文件存在 |
| `tests` | 需求块的 `- 验收：<tests/…>::<用例>／… 的 <用例>a~d` | 空数组 |
| `walkthrough` | 验收行里的 `走查清单第 4、17 条` | 空数组 |
| `cards` | 验收行里的 `卡E1`／`卡 D1/D2` | 空对象 |
| `reverseTests` | **测试代码里的反标**：`@pytest.mark.req("R-36")`／`# req: R-36`／`// req: R-36` | 空 |

**「代码即追踪」的用法（推荐）**：在测试里给每条用例打一个反标（`// req: R-36`），矩阵的 `reverseTests` 就由代码自己声明；验收行仍是权威（T03 只记警：反标了但验收行连这个测试文件都没提 ⇒ 当场点名）。

**三条判据（`check`，C17 复用同一套语义）**：T01 活性（符号/用例/卡必须真在盘，死指针记**红**）｜T02 时效（specs/PRD/卡库 md5 与矩阵指纹不符＝矩阵过期，记**警**）｜T03 反标（文件级比对，记**警**）。**矩阵不存在只记一条警**——可选增强，不许借此炸老项目。

**AGENTS.md 的生成区（`render_agents.py`）**：渲染「现状读数／改动落点速查（文件→条款→符号）／模块路由」三块，**整块覆盖**而非增量 patch（增量更新的病是生成件停在半新半旧、最后没人知道哪行是真的；整体覆盖只有两种结果：完全反映当前真相，或失败时完全不动）。三个硬规矩：

1. 只碰 `<!-- AUTO-BEGIN … -->` 与 `<!-- AUTO-END -->` 之间；**缺标记时拒绝猜**（要插入必须显式 `--init`），防止把人的正文吞掉；
2. 人写区只留**红线/禁忌/代码风格/命令/「什么时候读哪份文档」**——凡是"数字"与"路由"一律不手写（这正是 C18 要抓的）；
3. 写后**读回自证**（标记各 1 处＋生成区在位），不符就退 1 而不是当成功。

**生成件之间的时效链**：生成区是矩阵的投影，矩阵变了而生成区没重跑＝两处分叉无人报警。修法＝生成区末尾写 `矩阵快照 <md5 前 12 位>`，`spec_check` C17 比对现值，不一致记警点名重跑。T03 认目录形式：验收行写「`tests/api/` 全量回归」而反标落在具体文件——判据＝**父目录至少两级**（`tests/api`）且出现在验收行原文里也算登记；单独一个 `tests` 不算（几乎每行都出现，认了等于关掉 T03）。

**活目录（`catalog.py`）**：`py <EverSpec根>/scripts/catalog.py gen --root <EverSpec根> [--apply]` 一次扫描 SKILL.md＋四目录，产出同源派生物 `references/catalog.md`（人读）＋`references/catalog.json`（机读：逐件 sha256＋提及式反向索引＋源集哈希）；`check --root <EverSpec根>` 复算比对——**手改派生物或源已变目录陈旧都当场红**（MUST-07 生成物哈希对账）；gen 幂等（产物零时间戳），runs.log 接线同 §6.7。

**开窗重锚（`reanchor.py`，MUST-10/11）**：接手窗口第一件事跑 `py <EverSpec根>/scripts/reanchor.py open --root <项目根>`——按读取集（open/promise/history）出本步必读清单＋断点状态摘要＋证据链尾外部锚，`list`／`show [--no-scenarios]` 是过滤读法；口径与诚实边界见脚本头（本件只留指针，不复制内容）。

## §6.6 证据哈希链（`evidence_chain.py`：把「点时证明」串成「期间持续受控」）

§5 第 5 步落盘的原始输出是**点时证明**；要「一段时间内持续受控」的可验证声明，就把多批证据串成防篡改链：

```
py <EverSpec根>/scripts/evidence_chain.py append --file <项目>/evidence.ndjson --action <动作名> --artifact <产物路径> [--note 备注]
py <EverSpec根>/scripts/evidence_chain.py check  --file <项目>/evidence.ndjson [--art-root <目录>] [--tip <外部记录的链尾哈希>]
py <EverSpec根>/scripts/evidence_chain.py selftest
```

- 每行一条：前条哈希(prev)＋动作(action)＋产物 digest(sha256)＋时间戳(ts)＋本行哈希(hash)；首条 prev=`GENESIS`。
- **check 判据**：断链（prev 咬合不上/序号断档）、中间行被改（内容与行哈希不符）、产物被改（digest 与落链值不符）＝**红**；产物移档不在盘＝**警**（链仍自洽，点名 digest 未能复核）。
- **append 拒笔**：链损坏时不延长坏链（先修复或另起新链）；产物必须在盘（没有 digest 不落账）。产物路径推荐**在证据目录内就地追加、写裸文件名**——check 按链文件所在目录解析相对路径。
- 🔴 **诚实边界**：链证明「落链之后没人动过」，不证明「落链那一刻产物是真的」（产物真伪靠生成它的工具与人工验收）；**链尾截断链内查不出**——check/append 都会打出链尾哈希，抄进台账/交接说明当外部锚，下次 `check --tip <记录值>` 对不上＝尾巴被动过。
- 🔴 **链只收定稿即冻结的证据件**（2026-10-28 天拍板，选项 A）：`evidence/` 下的原始输出、走查记录、复核清单这类落盘后不再改的件；**活文档（SKILL.md／细则／references 正文／脚本）与生成物（catalog 等派生物）不进链**——它们随每张卡正当演进，入链＝下张卡收工验链必红（2026-10-28 实证红 2→6 全部由此而来）；已有历史跳留作证词，红数封顶不再涨，此后验链见红必是真翻改；确需收会变的件，按「点时快照」办理（动作名带「快照·时点」，语义＝只证明那一刻的状态，日后变红属预期）。
- 自证：selftest 20 条（地基绿/逐条做坏必红/哈希灵敏度反查/变异探针臂/runs.log 接线臂/分母闸），只写临时树。

## §6.7 运行读数与机读输出（runs.log ＋ `check --json`）

**runs.log（运行读数流水账）**：本件六支带判据的脚本（spec_check／trace_matrix／evidence_chain／catalog／reanchor／doc_lint）每跑一次命令，就向**本件自己的** `evidence/runs.log` 追加一行读数（append-only）。目标项目零写入——「只读不改」承诺不变，读数只落 EverSpec 根目录的 `evidence/` 里。

- 行格式（真源＝各脚本 `_append_runs_log` 实现，四处一致；不一致时以脚本为准并回改本细则）：`<本地ISO时间>｜<工具名>｜<动作>｜<对象>`，对象＝`root=<项目根>`（spec_check/trace_matrix/catalog）或 `file=<链文件>`（evidence_chain）；其后按动作可选追加 `红 N｜警 M` 与尾注（gen 干跑带 `干跑`、--apply 带 `--apply`、链 append 带 `seq=N`）。
- **退 2（根目录不对/用法不对）与拒笔（链损坏）不记读数**——没查成/没落成的操作不算跑过。
- **尽力而为**：读数写不进去（只读盘、目录不可建）就静默跳过，绝不影响主流程退出码——读数是流水账不是证据本体，证据本体仍按 §三 纪律 2 落盘原始输出。
- 环境变量 `EVSPEC_RUNS_LOG` 改落点——selftest 用它把读数重定向进临时树（零写入纪律），日常不设。
- 用法：接手窗口先看一眼「尺子最近什么时候跑过、结果如何」；**别拿「跑过」当「证据」**——读数只有一行摘要，判据仍看原始输出。

**`check --json`（机读面，对标 OpenSpec `validate --json`）**：`py <EverSpec根>/scripts/spec_check.py check --root <项目根> [--strict] [--json]`——加 `--json` 时 stdout **只打一行 JSON 对象**（人读面归零），可直接管道喂 `json.load`；输出统一 `ensure_ascii`（纯 ASCII 转义，跨编码管道安全）：

| 字段 | 含义 |
|---|---|
| `tool`／`version` | `spec_check` 与脚本版本 |
| `root`／`ts` | 检查根（绝对路径）与本地时间 |
| `strict`／`exit_code` | 严格档开关；退出码（0/1/2，语义与人读面完全一致） |
| `red`／`warn`／`assertions` | 红条数／警条数／CHECKS 断言总数 |
| `items[]` | 每条红/警 `{code, level, where, msg}`（与人读行同源） |

退出码 2（根目录不对）同样打 JSON（`error` 字段点名原因）。非 `--json` 模式行为零变化；runs.log 接线对两种模式同样生效。

## §6.8 文档体系尺（`doc_lint.py`：把「文档互指」变成「能红的图」）

**它解决的问题**：文档一多，三类漂移没人查——指针指到不存在的文件（断链）、新文档没人知道（孤儿）、同一术语两处各写各的（双定义分叉）；加上 supersede 只写单边（取代了它、它却不知道）和 waiver 逾期不销（豁免变长期通行证）。这把尺把这些面变成 `check` 一条命令的红绿。

```
py <EverSpec根>/scripts/doc_lint.py check  --root <文档树根>   # 文档图五查＋waiver 审计（全查）
py <EverSpec根>/scripts/doc_lint.py waiver --root <项目根>     # 只跑 waiver 审计（K14 三态走查/审计用）
py <EverSpec根>/scripts/doc_lint.py graph  --root <文档树根>   # 打印提及图：边表＋孤儿＋统计（入边出边核对面）
py <EverSpec根>/scripts/doc_lint.py selftest [--tmp-root <目录>]
```

退出码：`0` 全绿（可含警）｜`1` 有红｜`2` 根目录不对。runs.log 接线（§6.7 第六支），目标树零写入。

**边识别三形态与分工**：①markdown 链接（方括号标题紧连圆括号相对路径）＝严格指针，断链记**红**（D01）；②反引号纯路径（带扩展名文件或 `/` 结尾目录）与③冒号元信息行路径（如 Capabilities 的 `- booking: specs/booking/spec.md`）＝提及形态，断链记**警**（D17）——目录提及（`specs/`、`changes/` 占位）不判。与 `catalog.py` 的分工：catalog 的提及式反向索引是**粗索引导航**（substring，宁滥勿缺）；本尺管**严格闭合**（链接形态查断链，MUST-08）。豁免面：代码围栏内的命令示例、引用块（`>` 开头）的沿革证词、生成派生物（`catalog.md` 等）、外链 URL 与盘符绝对路径（归供应链登记四元组管）、`evidence/` 证据目录。

**supersede 分工**：指针值是**文件路径形态**（含 `/` 或带扩展名）才算文档级、归本尺（如 `- 取代：references/旧版.md`）；「取代：R-3」这类**需求号指针**归 `spec_check`（K12 卡承接）。文档级纪律：取代/被取代必须成对（D02）、已取代终态必带指针（D03，§3 状态机表）、链不许成环（D04）、双向齐则被取代侧状态必须收口「已取代」（D16）。

**waiver 审计（K14 点名的机检命令）**：审计不变式（真源＝`templates/hooks/README.md`「waiver 记录」节）——每个归档变更包（`changes/archive/<目录>/`），要么包内有绿读数（`check --json` 的 `"exit_code": 0` 行落盘），要么有 `waiver.md` 在案且在期；两者皆无＝D06 红点名。waiver 七字段、有效期、销账、slug 一致性分别由 D07/D08/D10/D13/D14 把关。🔴 **诚实边界**：机械面只判「绿读数记录存在」，判不了「存续期内持续绿」的时间窗口语义（点时 vs 期间）——那层靠人工抽查；waiver 审计是对 `--no-verify` 静默跳过的事后兜底，不是提交闸门（尺子不装 hook，§6 边界 2）。

**它的边界，别对外吹**：①只查机械面——「该不该链」「术语值谁对」是语义判断，尺子不装懂；②提及按相对路径解析（文档同目录→树根两级），**裸文件名提及**（写 `spec_check.py` 不写 `scripts/spec_check.py`）与**内嵌子项目**（子项目根不是 `--root`，如本件 `examples/最小项目/`）会产生已知警——指针请写路径形态，内嵌项目以子项目根跑；③孤儿/提及断链是警级导舐藏，红面只锁链接断链与契约违约（supersede/术语冲突/waiver 违规）；④selftest 38 条（地基绿＋17 条 bad-sample 全红＋警哨兵＋反恒真＋真出口＋runs.log 接线＋五变异探针臂＋真根活体绑定＋分母闸），只写临时树。

## §6.9 标级映射（红＝MUST 机检强制，警＝SHOULD 点名不拦；RFC 2119/8174，v1.11.0 · K12）

本尺输出只有两级，映射 RFC 2119（BCP 14）的需求级关键词；出处官方文本已按四元组登记 → `references/供应链登记.md` #4/#5（RFC 8174 澄清：只有全大写才算 RFC 2119 关键词，本映射按其精神执行）：

| 输出级 | RFC 2119 关键词 | 语义 | 机器行为 |
|---|---|---|---|
| 红 | MUST / REQUIRED / SHALL（必须） | 绝对要求，违反即违约 | 退出码 1；pre-commit 样例红即拦；`--strict` 下警也拦 |
| 警 | SHOULD / RECOMMENDED（建议） | 默认照办，例外须有理由并留痕（waiver 纪律，§6.8） | 点名不拦，退出码 0；`--strict` 才当红 |
| （不设级） | MAY / OPTIONAL（可以） | 真可选 | 不设第三输出级——可选面用「写了就查／不写不红」的形状承载（如 C23/C27/C28） |

- 与中文口径的对应：条款与文档里「必须/不得/禁止」＝MUST 面，「建议/应尽量」＝SHOULD 面——`[红]`/`[警]` 两个输出前缀即此映射的输出面，不增设第三种前缀。
- 一致性钉（标级不漂移的机械保证）：CHECKS 注册表条目数＝本细则断言表行数（selftest 活体绑定钉死）＝文档自称数（C22）——三者任一漂移，selftest 当场红；哪条断言该红该警由 selftest 逐条点名用例钉住，机械尺不装懂。
