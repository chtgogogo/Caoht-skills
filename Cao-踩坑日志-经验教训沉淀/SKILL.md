# 踩坑日志（Pitfall Log）

一种**省 token** 的踩坑 / 经验教训沉淀方式：维护一份**极轻索引**，加**根因层**与**案例层**两层明细，而不是把所有教训内联进同一个会越写越大的文件。核心价值是「渐进式披露」——索引常驻上下文，细节按需加载。

## 何时使用

**查阅（先想这一步）：**

- 遇到报错 / 失败 / 反常现象 / 反复排查不下的问题 → **先去检索**，别一上来就改代码。
- 用户说「看看踩坑记录 / 教训 / 之前怎么解决的 / 有没有类似的坑」。

**记录：**

- 踩了一个非显然的坑、或想沉淀一个可复用经验 → 记一条。
- 解决完一个棘手问题后，主动提议帮用户记一条。

## 两层结构

```
<log-root>/
├── pitfall-log.md              # 极轻索引（单一事实源）：根因索引表 + 分组的案例清单
├── roots/                      # 根因层：一个根因一个文件（检索入口）
│   └── RT-<三位编号>-<slug>.md
└── pitfalls/                   # 案例层：一条坑一个文件（深读用）
    ├── _template.md
    └── YYYY-MM-DD-<slug>.md
```

- `<log-root>`：默认 **`D:\Deepseek-ALL\踩坑日志`**（本机统一）；但**第一次用先和用户确认存储位置，别写死**（换机器 / 换环境时可改）。路径保持稳定，索引才不会指错。
- **索引**（`pitfall-log.md`）：每次会话都读，必须保持极短。
- **根因层**（`roots/RT-*.md`）：**检索先落到这里**——一句话根因、识别信号、通用对策。
- **案例层**（`pitfalls/*.md`）：完整过程与细节，根因层不够用时才深读。

## 为什么分两层

**从坑里能捞出来的最大价值不是"这次怎么修的"，而是"为什么会踩、下次怎么一眼认出来"。**

同一类问题会在毫不相干的场景反复出现。比如"中文编码"这个根因，一次是 PowerShell 脚本乱码，一次是 git 命令误删整个目录——症状完全不一样，根因是同一个。如果只按案例平铺，这两条永远看不出关系，下次换个场景照样踩。

所以：**根因是一级公民，案例挂在根因下面**。检索时先命中根因 → 拿到通用对策与识别信号；根因层解决不了，再往下翻具体案例找灵感。

## 索引格式

两部分，**根因索引在前**（与 `assets/index-template.md` 保持一致）：

**① 根因索引表**

```
| 根因 | 一句话 | 案例数 | 命中 |
|---|---|---|---|
| [RT-001](roots/RT-001-xxx.md) | 中文出现在跨进程 / 跨工具边界 → 先怀疑编码 | 2 | 🔥0 |
| [RT-002](roots/RT-002-xxx.md) | 依赖隐式上下文（cwd / 工作目录 / 会话状态） | 2 | 🔥0 |
```

**② 案例清单（按根因分组，组内新 → 旧）**

```
### RT-001 中文出现在跨进程 / 跨工具边界

| 日期 | 记录者 | 标签 | 一句话标题 | 命中 | 文件 |
|---|---|---|---|---|---|
| 2026-09-15 | 小鲸鱼 | Git/中文路径 | 中文路径当 git 子命令参数会误删整个目录 | 🔥0 | [详情](pitfalls/xxx.md) |
```

- `记录者`：谁记的（助手标识 / 人名 / `shared`）。用稳定短标识。
- `标签`：逗号分隔关键词，便于检索。
- `命中`：见「命中计数」。`🔥0` = 还没被用上；`⭐` = 已升华。

## 根因文件格式

复制 `assets/root-template.md`，命名为 `roots/RT-<三位编号>-<slug>.md`。文件头 frontmatter 记状态：

```yaml
---
root_id: RT-001
title: 中文出现在跨进程 / 跨工具边界 → 先怀疑编码
cases: 2          # 该根因下挂了几条案例
hits: 0           # 该根因的通用对策被直接套用（未深读案例）的次数
escalated: false
---
```

正文四节：

- **一句话根因**：这类问题的共同病根，一句话说清。
- **识别信号**：出现哪些迹象就该往这里想——**最有用的部分**，它是"提前认出来"的钩子。
- **通用对策**：不针对任何具体案例的做法，最好能直接照做。
- **挂载案例**：该根因下的案例清单（表格，与索引保持一致）。

根因编号 `RT-001`、`RT-002`… **只增不改**——别人可能引用它，改号就断链。

## 案例文件格式

复制 `assets/entry-template.md`，命名为 `pitfalls/YYYY-MM-DD-<slug>.md`。文件头 frontmatter：

```yaml
---
root: RT-001       # 挂在哪个根因下（必填）
hits: 0            # 检索命中并真正解决问题的累计次数（权威值）
last_hit: —        # 最近一次命中的日期
escalated: false   # 是否已升华成铁律
---
```

正文五节（标题用 `# 坑：<一句话标题>`）：上下文 / 为什么（根因）/ 解法 / **能否借鉴（通用规律）** / 来源。

「能否借鉴」仍是最有价值的字段——它和 `root` 的分工是：**`root` 说「这属于哪一类」，能否借鉴说「这一类里可迁移的规律」**；案例内的「为什么（根因）」写**本案例**的具体原因，别和根因族混起来。

文末固定带命中明细：

```
## 命中记录

| 日期 | 场景 | 解决了什么 |
|---|---|---|
| — | — | — |
```

## 检索流程（先根因，后案例）

1. 读 `pitfall-log.md`（极省）。
2. **先扫「根因索引表」**——有没有哪个根因的识别信号对得上当前问题。
3. 对上了 → 读那个 `roots/RT-*.md`，拿通用对策先试。
4. 根因层不够 → 再挑该根因下的具体案例深读，找灵感。
5. 解决了 → 按「命中计数」给**真正帮上忙的那一个** +1，并告知用户。
6. 一个都对不上 → 自己排查；解决后按下面的流程记一条新的。

## 记录流程

1. 确定稳定的 `<log-root>`（没有就建 `roots/` 与 `pitfalls/`）。
2. **归因**：这个坑的根因是什么？先在 `roots/` 找有没有现成的同根因文件——
   - 有 → 直接挂上去，案例数 +1；
   - 没有 → 新建一个根因文件（注意想清楚"**一类**问题"，而不是"这一个问题"）。
3. 复制 `assets/entry-template.md` 写案例，填全各节，frontmatter 写上 `root:`。
4. 索引两边同步：根因表更新案例数；案例清单在对应分组下加一行（`🔥0`）。
5. 若索引有 `updated:` 日期则更新。

## 命中计数

**为什么要有计数。** 「能否借鉴」里写的规律有没有真救过场，光看记录看不出来。计数把"这条坑有用"从感觉变成数字。

**什么时候 +1。** 四个条件同时成立才算：

1. **发生了检索动作**——真的去读了索引；
2. **翻看了具体记录**——至少读了对应的 `roots/RT-*.md` 或 `pitfalls/*.md`；
3. **从记录里获得了启发**，并用它解决了当前问题（不是"看着相关"就给分）；
4. **问题真的解决了**。

**明确排除：事后发现"这两个坑同根因"不算命中。** 没有检索动作、没有翻看、没有从中获益，只是事后归类而已。**同根因 ≠ 命中。**

只是扫到了没用上、或最后没解决，都不算。**宁可少记，不要虚高**——虚高的数字等于没有数字。

**计数落在两处，必须同步：**

- **索引**：案例行的 `命中` 列 `🔥N`（N=0 也写 `🔥0`）；根因表的 `命中` 列同理。
- **文件**：frontmatter 的 `hits` 是**权威值**；文末 `## 命中记录` 追加一行（日期 / 场景 / 解决了什么）。

两者不一致时**以文件为准**，并回头修索引。

**根因层与案例层各自独立计数：**

- 只走根因层（读了 RT 文件、用通用对策解决）→ **根因 +1**；
- 深读具体案例并获益 → **该案例 +1**；
- 两层都走了、都帮上忙 → 各 +1。

## 升华

**触发条件（满足任一）：**

- 某条**案例** hits ≥ 3 → 它已被反复验证；
- 某个**根因**下案例数 ≥ 3 → 这类问题反复出现，值得提炼成规则。

**动作：**

1. 索引对应行标 `⭐`；
2. 文件置 `escalated: true`（根因文件则标注已升华），记升华日期；
3. **同步写入记忆 CORE 铁律区**（`E:\Zcode-memory\CORE.md`，编号接 R-00X，来源注 `RT-xxx` / `pit-<slug>`）——此后每次会话强制加载。

**全处同步铁律。** 本 skill 的**规则、模板、索引格式、条目结构**任一处升级，所有副本必须同时改——本机 `SKILL.md`、`assets/` 下模板、log-root 下的 `_template.md`、现有索引与条目、以及对外发布的详解页。改一半等于埋雷：下次照旧模板写出的条目会和新格式对不上。

## 原则

- **单一事实源**：一份日志，不要各助手 / 各端各写一份导致漂移。
- **根因优先**：检索从根因入手，别一上来就翻案例。
- **渐进式披露**：索引常驻上下文，细节按需加载——这是它随体量增长仍省 token 的关键。
- **沉淀可迁移经验**：「能否借鉴」字段把一次性修复变成可复用知识。
- **位置稳定**：`<log-root>` 固定，索引路径才不会断。
- **索引有界**：案例超 ~50 条时，把冷条目归档到 `pitfalls/archive/`，索引保留「→ archive/文件名」指针。
- **统一储存**：所有 agent 共用一个 `log-root`（本机默认 `D:\Deepseek-ALL\踩坑日志`），靠「单一事实源」避免各写一份漂移；**先和用户确认位置，别写死**。

## 与记忆 PITFALL 层的关系

- **踩坑日志** = 跨 agent 共享的「教训沉淀」（谁踩谁记、大家都能查），不评分、不衰减。
- **记忆 PITFALL 层** = agent 自己的「记忆管理」（给坑打分 / 衰减 / 升华成铁律）。
- **边界**：坑的原始记录记在踩坑日志（共享）；反复出现的坑「升华成铁律」才进记忆 CORE。避免同一坑记两遍。
