# 踩坑日志（Pitfall Log）

一种**省 token** 的踩坑 / 经验教训沉淀方式：维护一份**极轻索引**加**每条坑一个独立文件**，而不是把所有教训内联进同一个会越写越大的文件（那样每次会话都会全量加载，越来越费上下文）。核心价值是「渐进式披露」——索引常驻上下文，细节按需加载。

## 何时使用

- 用户报告 bug / 报错 / 反复失败 / 反复修的 bug / 反复排查的问题 / 踩坑 / 失误 / 吸取教训 → 记录一条坑。
- 用户想沉淀一个非显然的修复或可复用经验 → 记录一条坑。
- 用户说「看看踩坑记录 / 教训 / 之前怎么解决的 / 有没有类似的坑」之类 → 查阅日志。
- 解决完一个棘手问题后，主动提议帮用户记一条。

## 目录结构

```
<log-root>/
├── pitfall-log.md           # 极轻索引（单一事实源）
└── pitfalls/
    ├── _template.md         # 每条坑复制此模板（也可从 assets/entry-template.md 取）
    └── YYYY-MM-DD-<slug>.md # 每条坑一个文件
```

- `<log-root>`：默认 **`D:\Deepseek-ALL\踩坑日志`**（本机统一）；但**第一次用先和用户确认存储位置，别写死**（换机器 / 换环境时可改）。路径保持稳定，索引才不会指错。
- **索引**（`pitfall-log.md`）：每次会话都读，必须保持极短——一行一条 + 简短「为什么」说明。绝不在索引里内联完整条目。
- **条目**（`pitfalls/*.md`）：完整细节，仅在被命中时深读，平时不进上下文。

## 索引格式

**表格一行一条，新在上**（与 `assets/index-template.md` 保持一致）：

```
| 日期 | 记录者 | 标签 | 一句话标题 | 命中 | 文件 |
|---|---|---|---|---|---|
| 2026-09-03 | 小鲸鱼 | PowerShell/编码 | 中文 .ps1 不带 BOM 会被 GBK 解码成乱码 | 🔥0 | [详情](pitfalls/xxx.md) |
```

- `记录者`：谁记的（助手标识 / 人名 / `shared`）。用稳定短标识。
- `标签`：逗号分隔关键词，便于日后检索。
- `标题`：一句话说清症状或解法。
- `命中`：该条被「检索命中并真正解决问题」的累计次数（见「命中计数与升华」）。`🔥0` = 还没被用上；`⭐` = 已升华成铁律。

## 条目格式

复制 `assets/entry-template.md`，命名为 `YYYY-MM-DD-<slug>.md`（`slug` = 核心主题的小写连字符英文）。每条含：

文件头是负责计数的 frontmatter：

```yaml
---
hits: 0            # 检索命中并真正解决问题的累计次数（权威值）
last_hit: —        # 最近一次命中的日期
escalated: false   # 是否已升华成铁律（hits ≥ 3 时置 true）
---
```

正文六节：

- **坑是什么**：一两句说清遇到的错 / 难 / 坑。
- **上下文**：当时在做什么、什么项目、什么前提。
- **为什么（根因）**：表面现象下的真实原因。
- **解法**：最终怎么解决（关键步骤 / 命令 / 文件）。
- **能否借鉴**：这类问题在别处是否也会遇到、通用规律是什么——**最有价值的字段**，记录可迁移的经验而非仅本地修复。
- **来源**：日期 / 谁记的 / 关联任务或对话。

文末固定带一节命中明细，每次命中追加一行：

```
## 命中记录

| 日期 | 场景 | 解决了什么 |
|---|---|---|
| — | — | — |
```

## 工作流

**记录一条新坑：**

1. 确定一个稳定的 `<log-root>`（没有就建 `pitfalls/`）。
2. 复制 `assets/entry-template.md` 到 `pitfalls/YYYY-MM-DD-<slug>.md`，填全各节（frontmatter 留 `hits: 0`），重点写好「能否借鉴」的通用规律。
3. 在 `pitfall-log.md` 表格顶部追加一行（`命中` 列填 `🔥0`）。
4. 若索引有 `updated:` 日期则更新。

**查阅日志：**

1. 用户提到过往教训时，先读 `pitfall-log.md`（极省）。
2. 按标题 / 标签匹配相关条目。
3. 只深读命中的 `pitfalls/<slug>.md`，不要整目录加载。
4. 若该坑的经验确实解决了当前问题 → 按「命中计数与升华」+1，并告知用户。

## 命中计数与升华

**为什么要有计数。** 「能否借鉴」里写的通用规律有没有真救过场，光看记录看不出来。计数把"这条坑有用"从感觉变成数字。

**什么时候 +1。** 三个条件同时成立才算：

1. 查阅时**检索命中**了这条坑（真读了它的 `pitfalls/<slug>.md`）；
2. 该坑的经验**确实被用于**解决当前问题（不是"看着相关"就给分）；
3. 问题**真的解决了**。

三条都满足 → +1，并明确告知用户「这条坑命中生效，已 +1」。只是扫到了没用上、或最后没解决，都不算。**宁可少记，不要虚高**——虚高的数字等于没有数字。

**计数落在两处，必须同步：**

- **索引行**：`命中` 列写 `🔥N`（N=0 也写 `🔥0`，保持表格整齐）；
- **条目文件**：frontmatter 的 `hits` 是**权威值**，同时文末 `## 命中记录` 追加一行明细（日期 / 场景 / 解决了什么）。

索引给人一眼看，条目给审计用。两者不一致时**以条目为准**，并回头修索引。

**升华：命中累计 ≥3 次。**

反复被检索命中并解决问题的坑，说明它是高频规律而非偶发教训。此时：

1. 索引 `命中` 列标 `⭐`（如 `🔥3 ⭐`）；
2. 条目 frontmatter 置 `escalated: true`，文末记升华日期；
3. **同步写入记忆 CORE 铁律区**（`D:/WorkBuddy记忆系统/CORE.md`，编号接 R-00X，来源注 `pit-<slug>`）——此后每次会话强制加载。

**全处同步铁律。** 本 skill 的**规则、模板、索引格式、条目结构**任一处升级，所有副本必须同时改——本机 `SKILL.md`、`assets/` 下两个模板、log-root 下的 `_template.md`、现有索引与条目，以及对外发布的详解页。改一半等于埋雷：下次照旧模板写出的条目会和新格式对不上。

## 原则

- **单一事实源**：一份日志，不要各助手 / 各端各写一份导致漂移。
- **渐进式披露**：索引常驻上下文，细节按需加载——这是它随体量增长仍省 token 的关键。
- **沉淀可迁移经验**：「能否借鉴」字段把一次性修复变成可复用知识。
- **位置稳定**：`<log-root>` 固定，索引路径才不会断。
- **索引有界**：索引只留一行摘要；条目超 ~50 条时，把冷条目归档到 `pitfalls/archive/`，索引保留「→ archive/文件名」指针，避免索引本身变成长文件。
- **统一储存**：所有 agent 共用一个 `log-root`（本机默认 `D:\Deepseek-ALL\踩坑日志`），靠「单一事实源」避免各写一份漂移；**先和用户确认位置，别写死**。



## 与记忆 PITFALL 层的关系

- **踩坑日志** = 跨 agent 共享的「教训沉淀」（谁踩谁记、大家都能查），不评分、不衰减。
- **记忆 PITFALL 层** = agent 自己的「记忆管理」（给坑打分 / 衰减 / 升华成铁律）。
- **边界**：坑的原始记录记在踩坑日志（共享）；反复出现的坑「升华成铁律」才进记忆 CORE。避免同一坑记两遍。
