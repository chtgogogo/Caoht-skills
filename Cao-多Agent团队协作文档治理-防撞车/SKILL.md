# 多Agent团队协作文档治理

## 概述

本 skill 为「多个 AI agent 角色 + 用户本人」共同协作的项目，建立一套**纯文档化**的协作治理机制。它不依赖 agent 之间的实时通信（大多数环境本来就没有），而是用三份治理文件 + 信箱文件夹替代"开会/拉群"，解决两个核心痛点：

1. **多人同时改同一处** → 靠"编辑锁（带超时/抢占）"标记。
2. **用户被甲问完乙又问同一件事** → 靠"统一决策入口"，用户只在一个地方拍板。

> 本 skill 提炼自真实跑通的天倾（Godot 游戏）多 agent 协作项目，契约已转正 v1.0、决策已收敛到 D-01~D-20、信箱已双向投递，机制经实战验证可落地。v1.1 增补：编辑锁超时/抢占、决策生命周期（撤销/修订）、新人 onboarding、规模自适应与治理退役、治理体检脚本。v1.2 增补：结构化「交接卡/接力信」、Agent 工具级 grep/ls 指令（含 Windows 兼容）、看板 Mermaid 甘特图、体检脚本 Windows 编码。v1.3 增补：决策生命周期简化（替代型只记新结论、禁止历史叙述；抛弃型 grep 确认无引用后直接删除）、活跃/历史分区与决策压缩（>30 条并入归档）、轻量信箱强制升级阈值（>20 条或 7 天）、新人检查单改为按主责 grep 不读全文。**v1.4 增补（把"文档上的规矩"变成"机器能拦的机制"）**：① 编辑锁升级为**真实文件锁** `scripts/edit_lock.py`——原子获取（独占创建）、租约+心跳、超时接管带**写入代次（generation）**校验，旧写者接管后任何写入动作被退出码 6 拒绝；② 新增**单写队列**（`spool` 投件 / `queue` 取件），共享文件在合并前一个字节都不动，落地"独立工作区 + 单一集成者合并"；③ 信箱积压从"整文件判 `状态:done`"改为**逐条消息统计**（每条独立 ID + 接收方 + 状态），同文件混合状态不再漏报；④ 决策**不删历史**——失效条目连原文进历史区/归档，`supersedes`/`revoked` 事件生成当前有效视图，幽灵引用与历史被删可机检；⑤ 体检输出**检查覆盖率与未检查项**，治理构件为零时判「未配置」（退出码 3）而不是「健康」。

## 何时使用

用户表达以下意图时触发：
- "多个 agent / 角色一起做项目""团队分工""建立协作机制"
- "agent 之间怎么沟通""建个信箱""别让我分别回复甲乙"
- "避免多人改同一处""防止撞车""统一决策入口"
- 项目里已出现多个 agent 各自生成文档、需要治理。
- "遇到/担心某个 agent 在自己负责区死磕、成员间进度差距过大""瓶颈交接""切换会话聚焦下一个成员"。
- 补救场景："项目已经乱了""文档互相矛盾""谁改的忘了""帮我做一次治理体检"。

## 核心设计：三层治理（+可选第四层）

| 层 | 文件 | 职责 | 解决什么 |
|---|---|---|---|
| L1 决策真相源 | `DECISIONS.md` | 所有待拍板/已拍板决策的唯一入口，去重登记；含生命周期状态 | 用户被重复追问 |
| L2 协作契约 | `团队分工与协作契约.md` | 角色表、文件 ownership、编辑锁规则、冲突裁决 | 多人改同一处 |
| L3 异步信箱 | `沟通/<角色>/` 文件夹 | 跨 agent 协作请求/信息传递，命名 `X对Y.md` | 实时沟通缺失 |
| L4（升级版·可选） | `状态看板.md` | 任务进度一览，谁在做哪条、状态 | 进度不透明 |

**规模自适应**（启动时按项目规模选档，见步骤 0）：
- **轻量模式**（1~2 agent / 小项目）：只建 `DECISIONS.md` + 一页契约（角色/ownership/纪律浓缩），信箱退化成单文件 `沟通/投递.md`（所有人往里追加）。不建 L4、不跑体检。
  - **强制升级阈值**：`投递.md` 信件超过 **20 条**或最早未处理信超过 **7 天**，必须升级为标准模式（拆信箱文件夹）。单文件信箱本质仍是"中央派工单"，靠硬阈值防止它悄悄长成 token 黑洞（体检脚本 [6] 会报警）。
- **标准模式**（3~5 agent）：建 L1~L3 全套。
- **大型模式**（>5 agent / 长周期项目）：建 L1~L4，并启用治理体检脚本（见后），定期跑健康度。

## 工作流

### 步骤 0：收集信息（用 AskUserQuestion）

在生成任何文件前，先确认：
- **项目根目录**：默认当前 workspace；确认治理文件放根目录还是子目录。
- **团队角色列表**：用户本人 + 各 agent 角色（如"游戏设计师/技术美术/脚本工程师"）。用 AskUserQuestion 的 multiselect 给常见原型（设计师 / 技术美术 / 工程师 / 架构 / 测试 / 项目管理），用户可加自定义（Other 自由输入）。
- **是否需要 L4 看板**：是 / 否。
- **项目规模档位**：轻量 / 标准 / 大型（决定建哪些文件，见"规模自适应"）。

> 不要跳过收集直接建文件——角色和根目录决定模板里填什么；规模档位决定建几层。

### 步骤 1：防重复建设扫描（关键）

生成前**必须**先 Glob/Read 检查项目里是否已存在同类治理文件：
- `团队分工与协作契约.md` / `DECISIONS.md` / `沟通/` / `团队分工与协作公约.md` / `待决事项看板.md` / `状态看板.md` 等。
- **若已存在**：不要重建。改为（a）读取现有文件、（b）在用户确认下合并/补充缺失层、（c）若发现多套冲突治理（如同时有"契约"和"公约"），发出重定向说明让其一并入，避免两套纪律打架。
- **若不存在**：按模板新建。

### 步骤 2：生成治理文件

读取 `references/` 下对应模板，按收集到的角色填充：
- 写 `DECISIONS.md`（见 [决策看板模板](references/决策看板模板.md)）
- 写 `团队分工与协作契约.md`（见 [契约模板](references/契约模板.md)）
- 建 `沟通/` 目录 + 每个角色一个子文件夹（简称命名）；轻量模式改为建单文件 `沟通/投递.md`
- （可选 / 大型模式）写 `状态看板.md`（字段见 [信箱与看板说明](references/信箱说明.md)）
- 真实锁无需预建目录：`edit_lock.py` 首次 `acquire`/`spool` 时在项目根自动创建 `.治理锁/`（锁记录 + `queue/`）。

> 想先跑通再讲规矩？照 [示例-最小可运行治理包](references/示例-最小可运行治理包.md) 建最小集合（一份 DECISIONS + 一份契约 + 一个信箱 + 一条锁命令），五分钟能拦下第一次并发写。

### 步骤 3：播种示例 + 说明用法

- 在契约 §7 接力区放一条"请各 agent 认领"的引导。
- 在每个 `沟通/<角色>/` 放一份简短 `README.md` 说明"这是 X 的收件箱"；轻量模式在 `沟通/投递.md` 顶部写用法。
- 给用户的收尾说明要讲清三点：
  1. 以后**拍板只看 `DECISIONS.md` 的「待用户拍板」区**，一次回复全员生效。
  2. 想看"谁在跟谁对接"→ 翻 `沟通/` 信箱（轻量模式看 `沟通/投递.md`）。
  3. 各 agent 开工先读自己信箱 + DECISIONS，改非自己主责文件先加编辑锁。
- 大型模式额外告知：可定期跑 `scripts/governance_check.py` 做治理体检。

## 四条核心纪律（必须写进契约）

1. **编辑锁 = 真实锁，不是注释**：改**别人会同时改的文件**（代码、配置、共享文档）前，用 `scripts/edit_lock.py acquire` 抢一把带租约的锁；动笔前 `guard`、长任务 `heartbeat`、改完 `release`。锁记录里带**写入代次**，超时被他人接管后，旧写者手里的代次当场作废——它再执行 heartbeat/guard/release 一律被拒（退出码 6），**从机制上杜绝"两个写者静默覆盖"**。纯自己主责、无人并行的文档改动，可继续用 §3 的文字锁标记（轻量、可读，但无拦截力）。
2. **统一决策入口铁律**：任何需用户拍板的事，**禁止**在各自对话追问；必须登记进 `DECISIONS.md` 并去重；用户拍板一次全员生效。决策被推翻须走"生命周期"流程登记 `supersedes`/`revoked` 事件（见「决策生命周期」），**不得静默覆盖，也不得删除历史原文**。
3. **信箱投递（逐条计账）**：跨 agent 请求走 `沟通/<接收人>/X对Y.md`（轻量模式追加到 `沟通/投递.md`），不依赖实时对话。**每条消息自带 ID + 接收方 + 状态**，一个文件里可以有多条、状态可以不同；闭环的那几条移入 `已处理/`（或就地标 done），**未闭环的那几条仍算积压**——体检 [4] 按条报，绝不因文件里出现过"已处理"字样就判整个信箱干净。详见 `references/信箱说明.md`。
4. **交接原则**：自身陷入瓶颈或判断更适合他人接手时，必须在当前对话窗口及时告知用户并建议切换到对应成员/会话，不原地死磕（详见「交接原则」节）。

## 共享文件写入：真实锁与单写队列（v1.4）

文字标记挡不住并发写。凡涉及**多个角色可能同时改同一个文件**，用 `scripts/edit_lock.py`（纯标准库、跨平台，不依赖 git 或本机特有工具）把"谁能动笔"变成一次可查询、可拒绝的事实。

```bash
# 1) 抢锁（独占创建；别人已持有且租约未过期 ⇒ 退出码 1，不动笔）
python scripts/edit_lock.py acquire --target src/battle.gd --holder 数值策划 --lease 3600

# 2) 动笔前自查（代次失效 ⇒ 退出码 6 ⇒ 立刻停手，别写）
python scripts/edit_lock.py guard --target src/battle.gd --holder 数值策划 --gen 1

# 3) 长任务续心跳（≤12h 一次，否则 24h 后被视为过期锁可被抢占）
python scripts/edit_lock.py heartbeat --target src/battle.gd --holder 数值策划 --gen 1

# 4) 改完释放（退出码 0 才算释放成功）
python scripts/edit_lock.py release --target src/battle.gd --holder 数值策划 --gen 1

# 看全局：谁持有什么、哪些已过期、队列里压了几件
python scripts/edit_lock.py status
```

**超时接管（旧写者崩了/忘了）**：只有**租约已过期**的锁才允许被接管；接管会把**代次 +1**，旧写者恢复后的一切动作被拒（码 6），新写者拿到的代次是唯一有效凭证。有效租约内强行接管需显式 `--force`，并把理由写进 `--note`。

**单写队列（更省心的默认路径）**：当"改的人多、合并的人一个"时，与其排队抢锁，不如让每个角色**只投件不碰共享文件**：

```bash
python scripts/edit_lock.py spool  --target docs/design.md --holder 技术美术 --file my-draft.md   # 投递草稿
python scripts/edit_lock.py queue  --target docs/design.md                                       # 集成者看队列
python scripts/edit_lock.py queue  --target docs/design.md --done <队列件>                        # 集成者销件
```

> **独立工作区 + 单一集成者合并**（推荐的标准姿势）：每个角色在自己的工作区/分支产出改动与草稿，**不直接写共享文件**；投递进队列后，由**唯一的集成者**（契约 §2 里点名的那个角色）串行取件、合并、销件。并发的自由度留在各自工作区，共享文件的写入点收敛成一个，撞车概率从"取决于几个人的时机"变成"取决于有没有集成者"。

退出码：`0` 成功 ｜ `1` 他人有效持有 ｜ `2` 用法/路径错 ｜ `3` 无锁记录 ｜ `5` 租约过期需 takeover ｜ `6` **代次失效（被接管了，停手）** ｜ `7` 接管被抢先 ｜ `8` 锁记录损坏。锁状态存放在项目根的 `.治理锁/`（可用 `--store` 指定），体检脚本 [9] 会直接读它，把过期锁、坏锁、残留接管标记和队列积压报出来。

## Agent 工具级执行指令（省 token，别整文件读）

开工三查，用 shell 命令代替「读整个文件」，省 token 且不易漏：

```bash
# 查自己信箱（只看根目录，绝不递归 已处理/）
ls 沟通/<我的角色简称>/                 # PowerShell: dir 沟通\<我的角色>\

# 查全局有效文字锁（Bash）
grep -r "EDIT_LOCK:.*状态:wip" --include="*.md" --include="*.py" --include="*.gd" .

# 查全局有效文字锁（Windows PowerShell，无 grep 时用）
Get-ChildItem -Recurse -Include *.md,*.py,*.gd | Select-String "EDIT_LOCK:.*状态:wip"

# 查真实锁与单写队列（谁持有、是否过期、队列压了几件）
python scripts/edit_lock.py status

# 查待拍板事项（只读 DECISIONS 的待拍板区块，不是全文）
grep -n "状态：todo\|状态:todo" DECISIONS.md
```

## 信道分工（避免重叠）

- 决策类（需用户拍板）→ `DECISIONS.md`，不进信箱。
- 文件改动类 → 真实锁 `edit_lock.py`（并发风险高的文件）或文字锁标记（低风险文档）。
- 多人提交、一人合并 → 单写队列（`spool` 投件 / `queue` 取件 + `--done` 销件）。
- 协作请求 / 信息传递 / 任务接力 → 信箱（每条消息独立 ID + 接收方 + 状态）。
- 瓶颈告知 / 会话切换请求 → 直接在当前对话告知用户，不进信箱、不进 DECISIONS。

## 决策生命周期（替代即换血 · **历史不删**）

`DECISIONS.md` 的**活跃区**只记录"现在是什么"，不记录"曾经是什么"——这是省 token 的读区约定。但**不记录 ≠ 不保存**：失效决策连**原文**一起留在历史区/归档，靠事件（`supersedes` / `revoked`）机械地生成当前有效视图。这与全局铁律「勘误不改史」同源：治理文件是审计对象，删掉的原文无法再生。

**替代型（有新决策接棒）**：
1. 新结论按正常流程登记新条目（D-xx + 结论五要素），并在条目里写 `替代：D-01`。
2. 旧条目**整段搬进历史区**，前面加一行事件标记：
   ```
   - 事件：supersedes ｜ D-01 → D-05 ｜ 2026-09-18 ｜ by 设计角色 ｜ 理由：用户改判为 3D 俯视角
   ```
   搬过去的是**原文**（结论、理由、实现指向都在），不是一行摘要。
3. 主文档回灌照旧：原 owner 48h 内把新结论同步回所有引用旧决策的主文档，防止"文档还写着旧方案"。
4. **活跃区禁止历史叙述**这条保留——不要在现行条目里写"（之前的 2D 横板格斗被推翻）"；旧方案的字样只出现在历史区那条的原文里。读者默认只读活跃区，代价不变。

**抛弃型（作废且无接棒）**：
1. owner 先 `grep` 全项目搜决策编号与关键词，确认没有任何主文档引用它；
2. 无引用 → 条目移入历史区并标 `事件：revoked ｜ D-07 ｜ 日期 ｜ by ｜ 理由`，**仍保留原文**；有引用 → 先清理引用，再移入历史区。
   > v1.3 曾规定"直接删除、不留记录"，v1.4 撤销该做法：删除会让"当初为什么不做 D-07"变成不可追溯的口头记忆，而幽灵引用（别的 agent 记忆里的旧编号）也就无从查证去向。省 token 的目标已由"活跃区瘦身 + 归档压缩"达成，不必靠销毁原文再省一次。

**状态枚举**：活跃区只有 `approved` 生效 ｜ `todo` 待拍板 两种；失效条目一律出活跃区，进历史区带事件标记（`supersedes` 或 `revoked`）。

**当前有效视图**（不用人工维护）：`DECISIONS.md` 只负责"登记 + 事件"，"现在到底是什么"由脚本算出来：

```bash
python scripts/governance_check.py --root <项目根> --decision-view   # 打印现行有效决策（活跃 approved + 未被替代的 todo）
```

**决策压缩（防越用越肥）**：活跃区 `approved` 条目超过 **30 条**或每两周一次，把历史区整体并入 `DECISIONS_归档.md`，主文件顶部留一行"历史决策见归档"；**归档是搬运，不是销毁**——体检脚本会核对被移出的条目原文是否确实能在历史区或归档里找到（找不到 ⇒ 报「历史被删」），并核对有没有条目引用了已失效却无处可查的编号（⇒ 报「幽灵引用」）。体检脚本 [7] 监控活跃区规模。

> 详细模板与历史区/事件格式见 [决策看板模板](references/决策看板模板.md)。

## 新人 Onboarding 必读检查单

异步环境下新 agent（或用户新拉一个角色）加入已运行的项目时，容易"凭空开工"造成重复/冲突。本 skill 要求：任何新成员开工前**先完成以下检查单**（可贴在契约 §7 接力区或信箱 README）：

1. **按主责搜索决策，不读全文**：`grep -n "<我的角色名>\|<我的主责文件名>" DECISIONS.md` 只读命中条目，再扫一遍「已拍板决策」活跃区标题；确认自己负责的任务是否已有决策（历史区与归档不用读）。
2. 读 `团队分工与协作契约.md` 的 §2 Ownership，认领自己主责的文件/模块，并在 §7 注明。
3. 读自己信箱 `沟通/<我>/`（轻量模式读 `沟通/投递.md` 中 @我的部分），处理未读。
4. 若要做跨块改动，先按 §3 抢锁：并发风险高的文件用 `edit_lock.py acquire`（拿到代次才动笔），一般文档用文字锁标记；若发现过期锁（>24h），按抢占规则 `takeover` 接管——接管会把代次 +1，旧写者随后的一切写入都会被拒。
5. 确认自己负责条目的决策状态不是 `supersedes`/`revoked` 的**被替代侧**（`--decision-view` 打印的就是现行有效视图，直接看它最省事），避免基于已废决策开工。

## 交接原则（瓶颈及时告知 · 切换会话）

解决「协同推进失衡」：多 agent 并行时，若某成员在自己主责区死磕，既浪费轮次又拖垮整体，导致成员间进度差距过大。本原则要求 agent 在**该让位时主动让位**——把"卡住"转化为"让用户去下一个成员那里"。

**触发告知（满足任一即必须告知用户）：**
1. **自身陷入瓶颈**：在自己主责任务上连续受阻（反复尝试无进展、缺关键依赖/信息、方案被卡死），且短时间内预计无法突破。
2. **更适合他人接手**：判断该任务交给另一成员推进更高效（对方有专长、已具备前置上下文、或接力比原地强攻更顺）。

**必须做的行为：**
- 在**当前对话窗口（或发往用户的消息）**用自然语言**明确告知用户**：卡点是什么、为什么、建议切换到哪个成员/会话。
- 给一句「建议下一步」，例如："这块数值平衡交给【数值策划】接力更顺，建议你切到 TA 的会话推进"。
- 若已启用治理机制，同时按信箱规则把接力请求投递到目标成员信箱（`沟通/<接收人>/X对Y.md`，轻量模式追加到 `沟通/投递.md`），并（若启用 L4 看板）把自己的任务标记 `blocked` + 备注阻塞原因/等待谁——让对方被切换过去时一眼看到上下文。

**交接卡格式（结构化输出，让切换会话零摩擦）：**

```markdown
### 🔄 交接卡：[当前任务] -> [目标角色]
- **卡点原因**：[缺依赖 / 超能力范围 / 反复尝试无进展]
- **已尝试方案**：[简述，避免接手人重试]
- **建议接手人**：[目标角色]
- **接力信箱**：已投递至 `沟通/[目标角色]/[我的角色]对[目标角色].md`
- **下一步建议**：请切换到 [目标角色] 的会话，TA 开工时会读到接力信。
```

**目标：** 让用户能主动切换会话、把注意力聚焦到下一个该推进的成员身上，避免在一个成员处死磕导致进度差距过大。

## 规模自适应与治理退役

**规模自适应**：见"核心设计"节的轻量/标准/大型三档。档位决定建哪些文件与是否跑体检，避免小项目被重流程拖垮、大项目缺纪律失控。

**治理退役（项目收尾）**：当项目冻结/合并/移交时，治理文件不应无限堆积，应有序退役：
1. **决策回灌**：把 `DECISIONS.md` 中仍有效的 `approved` 条目，摘要回灌进项目的 README / 设计主文档 / 架构说明，让知识脱离"治理专用文件"也能被后人读到。
2. **清退锁**：先 `python scripts/edit_lock.py status` 看真实锁与队列——残留锁逐个 `release`（未释放的队列件先合并或作废再 `queue --done`）；再扫描并移除文档里的文字 `EDIT_LOCK` 标记。`.治理锁/` 目录随之可整体归档。
3. **契约封存**：将 `团队分工与协作契约.md` 重命名为 `团队分工与协作契约_归档.md`（或移入 `归档/`），顶部标注"本项目已退役，契约仅供追溯"。
4. **信箱归档**：`沟通/` 整体移入 `归档/沟通_YYYYMMDD/`，不再作为活跃收件箱。
5. **体检收尾**：退役前跑一次 `scripts/governance_check.py`，确认无过期锁/未决决策残留，再封存。

## 治理体检（可选自动化）

大型模式或项目混乱时，用内置脚本做健康度自检：

```bash
python scripts/governance_check.py --root <项目根目录>
python scripts/governance_check.py --root <项目根> --decision-view   # 只看"当前有效决策"视图
python scripts/governance_check.py --root <项目根> --mailboxes-only  # 只跑信箱
```

**九项检查**（缺对应构件的那项标「未配置」并计入未检查清单，不当作通过）：

| # | 检查项 | 报什么 |
|---|---|---|
| 1 | 文字编辑锁 | `EDIT_LOCK` 中 `状态:wip` 且距心跳 >24h 的过期锁、缺时间戳的怪锁 |
| 2 | 重复决策 | `DECISIONS.md` 待拍板区标题/结论高度相似的条目（违反去重铁律） |
| 3 | 角色名漂移 | 信箱子目录简称、契约 §1/§2 角色表、`DECISIONS.md` 分工矩阵三处角色名不一致 |
| 4 | **信箱逐条积压** | 逐条消息（独立 ID + 接收方 + 状态）统计待处理；**同文件混合状态逐条报**，不因文件里出现过"已处理"字样就整批放过；`已处理/`、`归档/` 内的不计积压但单独报数 |
| 5 | 看板漂移 | L4 看板与 `DECISIONS.md` §4 执行跟踪同一任务状态矛盾；`blocked` 任务提醒 |
| 6 | 轻量信箱规模 | `投递.md` 消息 >20 条或最早未处理 >7 天 ⇒ 提示升级标准模式 |
| 7 | 决策规模 | 活跃 `approved` >30 条 ⇒ 提示压缩（搬运归档，不删原文） |
| 8 | **决策事件一致性** | `supersedes`/`revoked` 指向不存在的编号；失效条目仍留在活跃区；**原文既不在历史区也不在归档 ⇒ 报「历史被删」**；主文档引用已废且查无去向的编号 ⇒ 报「幽灵引用」 |
| 9 | **真实锁与队列** | 读 `.治理锁/`：租约过期锁、损坏锁记录、残留 `*.takeover` 标记、单写队列积压件数（并提示接管会推代代次） |

**退出码**：`0` 全部通过 ｜ `1` 发现问题 ｜ `2` 根目录不存在/用法错 ｜ `3` **未配置**（治理构件为零，一项检查都没跑起来）。

> 🔴 **`3` 不等于"健康"**，也不等于脚本坏了。一个空目录跑体检如果回一句"治理健康，无发现问题"并退 0，那是**空集恒绿**——报告里没有任何检查真正执行过。脚本因此在末尾**必打印检查覆盖率**：

```
=== 检查覆盖率 ===
实跑 6/9 项 ｜ 未检查 3 项：
  - [5] 看板漂移（无 状态看板.md）
  ...
```

覆盖率分母固定为 9，未检查项逐条点名并说明缺哪个构件；`governance_present()` 判定为零时直接给「未配置」结论并退 3，指引读者去 `references/示例-最小可运行治理包.md`。同理，信箱里有信件文件却**一条消息都解析不出来**时判「尺子作废」，报"格式不认识"而不是"没有积压"。

> 脚本位置：[scripts/governance_check.py](scripts/governance_check.py)。轻量/标准模式可不跑。

## 与现役协作机制对接（不要另造平行机制）

很多项目不是从零开始，而是**已经有一套在跑的广播/账本机制**（一个追加式文件、多个窗口往里写）。此时本 skill 的职责是**对接**它，不是再建一个 `沟通/` 让两边都半死不活。判据三条：

1. **先映射再补**：把现役字段映射到本 skill 的概念上——现役的"提及某人"= 消息的**接收方**字段；现役的"这条办完了"= 消息的**状态**；现役的"行首编号"= 消息的 **ID**。映射表填进契约，现役文件格式**不改**（改格式会让所有在写的窗口同时瞎掉）。
2. **取号必须原子**：多个窗口/角色往同一个追加式文件写，编号冲突是必然事件。用**原子占号**（独占创建，抢到即占用）而不是"读最大号 +1"——后者两个窗口同一瞬间读到同一个号，写出来才发现撞，而且撞的时候已经覆盖过别人的行了。没有现成取号器时，退而用 `edit_lock.py acquire --target <账本文件> --holder <角色>` 把"取号 + 追加"整段串行化。
3. **销号只动自己那一行**：现役账本多为"只追加"设计（多人共写，把邻居整行圈进替换范围会吞掉别人的历史且零报错）。因此"处理完"应当是**追加一条销号事件**，或**只改自己那一条的状态字段**，绝不重排、不删别人的行；体检 [4] 逐条统计时认的就是这种逐条状态。

> 本机已落地的对接细节见同目录 `personal.local.md`：**若技能目录存在 `personal.local.md`，读取并以其覆盖上述通用默认值；不存在则走通用流程**（缺文件不报错、不断链）。该文件属个人适配层，不随发布仓分发。

## 副本落点与维护须知

本 skill 以「通用版」发布。若你在本地有多个 agent 宿主（例如 某宿主 与 Codex 各加载一份，或有一份冷存档），请在这些宿主的 skills 目录里各放一份**逐字一致**的副本，并：

- 保持 frontmatter 的 `name` 为 `multi-agent-team-governance` 不变；
- 任一副本改动后，整体同步其余副本（覆盖 + sha256 逐字校验），并各跑一次 `quick_validate.py`，避免多宿主规则漂移。

> 说明：多宿主环境下若只改一处、不同步其余，会导致不同宿主行为不一致。历史上就发生过漏同步冷存档、靠后续比对才发现的事故。
>
> 更稳的做法是**不留副本**：让各宿主的技能目录用链接指向同一份权威库（本机即如此，细节见 `personal.local.md`），从源头消灭"两份必打架"。链接方式因平台而异（Windows `mklink /J`、类 Unix `ln -s`），本平台用户可继续用逐字副本 + sha256 校验。
