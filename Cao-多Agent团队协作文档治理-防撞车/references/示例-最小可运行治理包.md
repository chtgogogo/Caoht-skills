# 示例 · 最小可运行治理包（五分钟起步）

> 用途：陌生项目里第一次建立协作治理时，**照抄这一份**就能拦下第一起并发覆盖。不需要一次建齐三层四看板——那是标准/大型模式的事。
> 本文件里的路径都是相对项目根的示例路径，直接可用；`<项目根>` 请换成你的实际目录。
> 判据：**能拦下一次写入才叫治理，写在文档里的规矩不算**。所以 §5 的验证别跳过。

## 1. 目录树（只建这五件）

```
<项目根>/
├── DECISIONS.md                 # 唯一决策入口（含事件标记，见 §2）
├── 团队分工与协作契约.md          # 角色表 + ownership + 锁规则（见 §3）
├── 沟通/
│   ├── 设计/README.md            # 每个角色一个收件箱目录
│   └── 工程/README.md
└── .治理锁/                       # 由 edit_lock.py 自动创建，不用手建
    ├── locks/
    └── queue/
```

> 一个人就一个角色目录；角色名要和契约 §1 的角色表**逐字一致**（体检 [3] 就是查这个漂移）。

## 2. `DECISIONS.md` 最小骨架

> 下面这份骨架是**体检脚本认的格式**（关键字必须逐字这么写）：活跃条目用 `### D-xx 标题`，替代关系写 `supersedes：<旧编号>`，历史区用 `- D-xx（… 事件：supersedes/revoked …）` 起头、紧跟 `- 原文结论：…` 保留原文。写成别的样式，脚本会当成"历史被删"或根本看不见这条事件。

```markdown
# {项目名} 决策与分工总表（DECISIONS.md）

> 单一决策真相源。动手前先读，别向用户重复追问已决事项。
> 创建：2026-01-01 ｜ 由 设计 依据用户拍板收敛。

## 0. 协作纪律
1. 需用户拍板的事只登记本文，禁止在各自对话追问。
2. 同一决策只登记一次，登记前先搜同类条目。
3. 用户回复一次即对全员生效。
4. 失效决策**连原文移入历史区**并登记事件，不删除。

## 1. 已拍板决策（APPROVED）

### D-01 战斗视角采用 3D 俯视
- **结论**：3D 俯视角，非横板。
- **实现指向**：`scenes/battle/`、`Camera3D`
- supersedes：D-00
- owner：设计 ｜ 状态：approved

## 2. 待拍板决策（TODO）

| ID | 决策 | 候选方案 | 负责人 | 状态 |
|---|---|---|---|---|
| D-02 | 存档格式 | JSON / 二进制 | 工程 | todo |

## 3. 历史区（失效决策的原文留档，不删）

- D-00（被 D-01 替代 ｜ 事件：supersedes ｜ 2026-01-01 ｜ by 设计 ｜ 理由：用户改判）
  - 原文结论：2D 横板格斗
  - 原文实现指向：scenes/battle_2d/
```

要点三条：**活跃区只写现行结论**（省 token）、**历史区保留原文**（可审计、可查幽灵引用）、**事件写清"谁替代了谁"**（脚本据此生成有效视图）。

查看"现在到底信哪条"不用人脑算：

```bash
python scripts/governance_check.py --root <项目根> --decision-view
```

## 3. `团队分工与协作契约.md` 最小骨架

```markdown
# {项目名} 团队分工与协作契约（v0.1）

> 发起：设计 ｜ 状态：生效
> 背景：agent 之间无实时通信，靠"文档即会议记录 + 真实锁 + 统一决策入口"替代开会。

## 1. 成员与角色
| 成员 | 角色 | 一句话职责 |
|---|---|---|
| 用户 | 最终拍板人 | 定方向、拍板决策 |
| 设计 | 机制与数值 | 设计文档、数值表 |
| 工程 | 代码实现 | `src/` 全部代码 |

## 2. Ownership（每个文件只有一个主责）
| 文件 / 模块 | 主责 | 协作 | 备注 |
|---|---|---|---|
| `docs/design.md` | 设计 | 工程 | 核心语义源头 |
| `src/` | 工程 | 设计 | |
| `DECISIONS.md` | 设计 | 全体 | 统一决策入口 |

## 3. 共享文件写入规则
- 并发风险高的文件：**先抢真实锁**（`edit_lock.py acquire`），动笔前 `guard`，改完 `release`。
- 多人改同一份、合并只有一人：不抢锁，改为 `spool` 投件 + 集成者 `queue` 取件。
- 纯文档小改：可用文字锁标记，**五要素缺一不可**——前缀 `EDIT_LOCK`、角色、时间、改动摘要、状态，外加 `心跳` 时间戳（漏心跳就判不出过期，只能永远人工确认）。完整写法见 [契约模板](契约模板.md) §3。
- 改完就地收尾，别把 `wip` 留在文档里：状态改 `done` 或直接删掉标记。

## 4. 信箱
- 跨角色请求写进 `沟通/<接收人>/X对Y.md`，**每条消息一个标题**，标题下带 `来源：`/`接收方：`/`状态：`。
- 一个标题塞多条消息 ⇒ 逐条统计会把编号和状态对错人（脚本按 `来源：` 再切，先出现的字段会漏到上一条）。
- 开工先 `ls` 自己信箱根目录（不递归 `已处理/`），处理未闭环条目。
```

> 契约 §1 角色表里列出的每个角色，都要有一个同名信箱目录（`沟通/<角色>/`）——体检 [3] 专查这个漂移，写了角色没信箱＝那个角色收不到东西还以为自己在协作。

## 5. 一次锁与一次体检（复制即用）

```bash
# 甲：抢锁 → 动笔 → 释放
python scripts/edit_lock.py acquire   --target src/battle.gd --holder 工程 --lease 3600
python scripts/edit_lock.py guard     --target src/battle.gd --holder 工程 --gen 1
python scripts/edit_lock.py release   --target src/battle.gd --holder 工程 --gen 1

# 乙：同一时刻也想抢 ⇒ 退出码 1，锁纹丝不动（这就是"拦住了"）
python scripts/edit_lock.py acquire --target src/battle.gd --holder 设计
echo $?    # 期望 1

# 投件路径：谁都不碰共享文件，由集成者串行合并
python scripts/edit_lock.py spool --target docs/design.md --holder 设计 --file 我的草稿.md
python scripts/edit_lock.py queue --target docs/design.md
python scripts/edit_lock.py queue --target docs/design.md --done <队列件名>

# 体检：九项检查 + 覆盖率；退出码 0 通过 / 1 有问题 / 2 路径错 / 3 未配置
python scripts/governance_check.py --root <项目根>
```

**验证（必做，不做等于没建）**：上面乙那条 `acquire` **必须返回 1**。若它返回 0，说明锁没生效（两个写者都能拿到），此时问题在环境或用法，不在文档——先修它再开工。

## 6. 常见误用

| 误用 | 后果 | 正解 |
|---|---|---|
| 只在文档里写"我来改这段" | 别人看不见，照样同时写 | 高风险文件用 `acquire`，或 `spool` 投件 |
| 抢锁成功后拿旧代次继续写 | 被接管后一律退出码 6 拒绝，改动落不了盘 | 每次 `acquire`/`takeover` 都记下报出的 `GEN=` |
| 信件里一条写"已处理"、另一条没写 | 整文件被当成已处理，积压静默消失 | 每条消息独立 ID + 接收方 + 状态（`references/信箱说明.md`） |
| 空目录跑体检看到"无发现问题" | 误以为健康 | 退出码 3＝**未配置**，看覆盖率那一段 |
| 决策被推翻就删掉旧条目 | 后来人无法解释旧文档为何这么写 | 登记 `supersedes` 事件 + 原文进历史区 |

> 想扩到标准/大型模式（L4 看板、轻量信箱升级阈值、退役流程）→ 见 [契约模板](契约模板.md)、[决策看板模板](决策看板模板.md)、[信箱与看板说明](信箱说明.md)。
