## 0. 核心原则

1. **文档即会议记录**：所有决策、分工、争议都写进文档，不依赖口头/对话传递。
2. **领地有责 · 写入有锁**：每个文件/模块有唯一主责 agent，别人要改先走 §3 的机制——**并发风险高的文件用真实锁（§3.1），多人写一份的走单写队列交集成者合并（§3.2），只有低风险文档才允许文字锁标记（§3.3）**。写在文档里的约定不算锁。
3. **用户拍板一次生效**：需要用户决定的事只进 `DECISIONS.md`，用户回复一次即对全员生效（§4）。
4. **异步信箱 · 逐条计账**：跨 agent 协作请求 / 信息传递走 `沟通/<接收人>/` 信箱（§8），**每条消息独立编号 + 接收方 + 状态**，闭环的归档、没闭环的算积压。
5. **交接原则**：自身瓶颈或更适合他人接手时，在当前对话及时告知用户并建议切换会话，不原地死磕（§9）。

## 3. 共享文件写入机制（三档：真实锁 / 单写队列 / 文字锁）

**目的**：agent 看不到彼此的实时编辑。只把规矩写在文档里，挡不住两个人同时写同一个文件——所以按并发风险选档，**能用机制就不用约定**。

### 3.1 真实锁（默认推荐给并发风险高的文件：代码、配置、数值表）

由本 skill 自带的 `scripts/edit_lock.py` 提供（纯标准库、跨平台，锁状态落在项目根 `.治理锁/`）。

```bash
# 抢锁（独占创建；他人有效持有时退出码 1 ⇒ 不动笔）
python scripts/edit_lock.py acquire --target <文件> --holder {角色} --lease 3600
# 动笔前自查（代次失效 ⇒ 退出码 6 ⇒ 立刻停手）
python scripts/edit_lock.py guard   --target <文件> --holder {角色} --gen <GEN>
# 长任务每 ≤12 小时续一次心跳
python scripts/edit_lock.py heartbeat --target <文件> --holder {角色} --gen <GEN>
# 改完释放
python scripts/edit_lock.py release --target <文件> --holder {角色} --gen <GEN>
# 看全局（谁持有、哪些过期、队列压了几件）
python scripts/edit_lock.py status
```

**超时接管与写入代次（本节的关键）**：
- 租约（`--lease`，默认 3600 秒）内他人**不得**并行改；过期后他人可 `takeover` 接管。
- 接管必然把该锁的**代次（generation）+1**：旧写者手里的代次当场作废，它再跑 `heartbeat` / `guard` / `release` 一律**退出码 6 被拒**。这一条就是为了根治"接管之后旧写者回来继续写、把新改动静默覆盖"。
- 有效租约内不允许接管；确需强夺要显式 `--force` 并把理由写进 `--note`（留痕）。
- 退出码：`0` 成功｜`1` 他人有效持有｜`2` 用法/路径错｜`3` 无锁记录｜`5` 租约过期需 takeover｜`6` **代次失效**｜`7` 接管被抢先｜`8` 锁记录损坏。

### 3.2 单写队列 + 单一集成者（多人改一份、合并只有一人时更省心）

任何人**都不直接改共享文件**，只投递自己的草稿；由 §2 主责表点名的**集成者**一人串行取件、合并、销件。

```bash
python scripts/edit_lock.py spool --target <共享文件> --holder {角色} --file <我的草稿.md>
python scripts/edit_lock.py queue --target <共享文件>                    # 集成者看待合并
python scripts/edit_lock.py queue --target <共享文件> --done <队列件名>   # 合并完销件
```

> **独立工作区 + 单一集成者合并**：并发的自由度留在各自工作区（草稿、分支、自己的目录），共享文件的写入点收敛成一个。撞车概率从"取决于几个人的时机"变成"取决于有没有集成者"——后者是可以明确写进 §2 主责表的。

### 3.3 文字锁标记（降级档：低风险文档、或环境不能跑脚本时）

**锁标记格式**（五要素：角色 | 时间 | 摘要 | 状态 | 心跳）：
- 文档（Markdown / HTML 注释）：
  ```
  <!-- EDIT_LOCK: <agent名> | <YYYY-MM-DD HH:MM> | 改动摘要 | 状态:wip | 心跳:<YYYY-MM-DD HH:MM> -->
  ```
- GDScript / Python（行注释 `#`）：
  ```
  # EDIT_LOCK: <agent名> | <YYYY-MM-DD HH:MM> | 改动摘要 | 状态:wip | 心跳:<YYYY-MM-DD HH:MM>
  ```
- TypeScript / JS / C# / C++（行注释 `//`）：
  ```
  // EDIT_LOCK: <agent名> | <YYYY-MM-DD HH:MM> | 改动摘要 | 状态:wip | 心跳:<YYYY-MM-DD HH:MM>
  ```
  > 上面三段是**格式示例**，别原样抄进真实契约：体检 [1] 会把带 `状态:wip` 的行当成一条真锁。填的时候要么补当前时间与心跳、要么改完就删。

**规则**：
- 要修改**非自己主责**的文件，或对自己主责文件做**结构性/跨段落**改动，先在目标段落首部加锁标记并写入当前时间戳。
- 改动完成并移除锁；若跨多段，每段独立加锁或段首统一加一处。
- 读到带 `状态:wip` 锁的段落时，**不要同时改**，先留接力说明等对方释放，或协商合并。

**超时与抢占（防死锁）**：
- 任何 `状态:wip` 锁应带 `心跳:` 时间戳。加锁者长任务每 **≤12 小时**更新一次心跳，避免被误抢占。
- 若某 `wip` 锁距其心跳已超过 **24 小时**未更新，视为**过期锁**，任何 agent 可**抢占**：在原锁内追加一行 `> 由 <接管者> 于 <时间> 接管（原锁超时）`，改写心跳续锁后继续改。
- 抢占前若不确定原改动是否完成，先在锁内留协商说明，等原 owner 在对话/信箱回应；仍无回应且已超时，按上述接管。
- ⚠️ 文字锁的"抢占"只是约定，**没有拦截力**：旧写者不会被告知锁已被接，两边都可能写完。同一文件一旦有两人以上真的会同时动，请改用 §3.1 或 §3.2。

**示例**（已释放的锁，可安全留在文档里）：
```
<!-- EDIT_LOCK: {角色} | {日期} | 改动摘要 | 状态:done -->
```

**Agent 自检指令（开工前查全局锁，别整文件读）**：
```bash
# Bash
grep -r "EDIT_LOCK:.*状态:wip" --include="*.md" --include="*.py" --include="*.gd" .

# Windows PowerShell（无 grep 时）
Get-ChildItem -Recurse -Include *.md,*.py,*.gd | Select-String "EDIT_LOCK:.*状态:wip"

# 真实锁与队列现状
python scripts/edit_lock.py status
```

## 4. 统一决策入口：DECISIONS.md（解决"回复甲又回复乙"）

**铁律 1（禁止分散追问）**：任何需要用户拍板的事项，**禁止**在 agent 自己的对话里直接追问用户；必须先登记进 `DECISIONS.md` 的「待用户拍板」区。
**铁律 2（去重）**：同一决策只登记一次。登记前先搜 `DECISIONS.md` 是否已有同类条目，有则补充而非新建。
**铁律 3（一次拍板全员生效）**：用户在 `DECISIONS.md` 或对话里对某条目拍板一次，即对全员生效，任何 agent 不得再次追问同一问题。
**铁律 4（登记方负责同步）**：决策登记方负责把结论同步到相关文档，并在 `DECISIONS.md` 标 `状态：approved`，同时在相关文档标注来源编号。
**铁律 5（改判走事件，历史不删）**：决策被推翻时，新条目写 `supersedes：<旧编号>`，旧条目**连原文移入历史区**并留事件行（`- D-01（被 D-05 替代 ｜ 事件：supersedes ｜ 日期 ｜ by ｜ 理由）` + `- 原文结论：…`）；纯作废无接棒的写 `事件：revoked` 同样留原文。**禁止原地覆盖旧结论、也禁止删条目**——删掉的原文无法再生，后来人也没法解释旧文档为什么这么写。"现在到底信哪条"由脚本生成：`python scripts/governance_check.py --root <项目根> --decision-view`。

## 5. 冲突裁决顺序

4. 评审建议若与新决策冲突，以新决策为准，评审方负责标注「已撤销」。

## 8. 异步信箱：沟通/ 文件夹（跨 agent 正式沟通渠道）

**规则**：
- 谁要对某人说话，就在 `<接收人>` 文件夹下生成 `X对Y.md`（X=说话人简称，Y=接收人简称）。例：{角色A}要对{角色B}说，生成 `沟通/{角色B}/{角色A}对{角色B}.md`。
- **🔴 逐条计账（一个文件可以装多条消息）**：每条消息**自己一个标题行**，标题下写 `来源：/接收方：/状态：`（可加 `消息号：MSG-001`）。状态取值 `pending|open|todo|wip|blocked` 算积压，`done|closed|已处理|已回复|已闭环` 算销号；**写不认的取值一律按未处理计**（宁可多报不漏报）。
  - 一个标题下塞多条消息 ⇒ 逐条统计会把编号和状态对错人（脚本按 `来源：` 再切，先出现的字段会漏到上一条），所以**一条一个标题**。
  - 同一文件里 2 条已处理 + 1 条待处理 ⇒ 体检 [4] 报**那 1 条**积压，不会因文件里出现过"已处理"就整批放过。
- **所有人每次开工先读自己信箱文件夹（仅根目录，不要递归 `已处理/`）**，处理未读信件。
- **🔴 已处理归档（省 token）**：每个信箱下建 `已处理/` 子目录；信件闭环（回执已收 + 无后续待办 + 对应决策已决/任务已交接）由接收人（或发件人经确认）`mv` 进 `已处理/`，待办信留根目录直到闭环。agent 巡检只列举根目录、不读 `已处理/`（体检同样跳过 `已处理/`、`归档/`、`archive/` 三种目录名）。
- **信道分工（避免重叠）**：
  - 决策类（需用户拍板）→ `DECISIONS.md`（§4 铁律），不进信箱。
  - 文件改动类 → 真实锁 / 单写队列 / 文字锁（§3）。
  - 协作请求 / 信息传递 / 任务接力 → 走信箱（本 §）。

> 详细命名约定、信件结构与 `已处理/` 归档规则见本 skill 的 `references/信箱说明.md`。

## 9. 交接原则（瓶颈及时告知 · 切换会话）

**目的**：避免某成员在自己主责区死磕、导致成员间进度差距过大。

**触发告知（满足任一即必须告知用户）：**
1. **自身陷入瓶颈**：主责任务连续受阻（反复无进展、缺关键依赖/信息、方案被卡死），短时无法突破。
2. **更适合他人接手**：交给另一成员推进更高效（对方有专长、已具备前置上下文、或接力比原地强攻更顺）。

**必须做的行为：**
- 在**当前对话窗口**明确告知用户：卡点是什么、为什么、建议切换到哪个成员/会话。
- 若启用 §8 信箱，同步把接力请求投递到目标成员信箱（`沟通/<接收人>/X对Y.md`）。
- 若启用 L4 看板，把自己的任务标记 `blocked` 并备注阻塞原因 / 等待谁，让对方被切换过去时一眼看到上下文。

**交接卡格式**（结构化输出，见 SKILL.md「交接原则」）：

```markdown
### 🔄 交接卡：[当前任务] -> [目标角色]
- **卡点原因**：[缺依赖 / 超能力范围 / 反复尝试无进展]
- **已尝试方案**：[简述]
- **建议接手人**：[目标角色]
- **接力信箱**：已投递至 `沟通/[目标角色]/[我的角色]对[目标角色].md`
- **下一步建议**：请切换到 [目标角色] 的会话。
```

## 10. 规模自适应（按项目档位裁剪）

本契约默认按"标准模式"完整建立。若为**轻量档**（1~2 agent / 小项目），可裁剪：仅保留 §1 成员角色、§2 ownership、§3 编辑锁、§4 统一决策入口四节；§5/§8/§9 浓缩为一句"详见多Agent团队协作文档治理 skill"；信箱退化为单文件 `沟通/投递.md`；不建 L4 看板。**大型档**（>5 agent / 长周期）除全套外，启用 `scripts/governance_check.py` 定期体检（字段见 SKILL.md「治理体检」节）。

## 11. 治理退役（项目收尾）

项目冻结/合并/移交时，治理文件有序退役：
1. 把 `DECISIONS.md` 仍有效的 `approved` 条目摘要回灌进 README / 设计主文档 / 架构说明（用 `--decision-view` 打印现行有效条目，别手抄历史区）。
2. **清退锁**：先 `python scripts/edit_lock.py status` 看真实锁与队列——在持的逐个 `release`，队列里未合并的件先合并或作废再 `--done` 销件（**别直接把 `.治理锁/` 删掉**：那等于把"谁在什么时候持有过什么"的证据一起扔了）；再扫描文档里残留的文字 `EDIT_LOCK` 标记并移除。
3. 本契约重命名为 `团队分工与协作契约_归档.md`（或移入 `归档/`），顶部标注"已退役，仅供追溯"。
4. 退役前跑一次治理体检，确认无过期锁 / 未决决策残留；**注意退出码 3 是「未配置」不是"通过"**——构件已被你拆掉，报告自然没得查。
