# 模板②：分析并改进现有代码

> 视角：**刚加入一个陌生项目的资深工程师**——先看懂，再动刀。

## 模式契约（先读这张表，它管"这一轮能做到哪一步"）

| 要素 | 内容 |
|---|---|
| **输入** | 代码库或代码片段（路径在手）；用户诉求原文（用来分 A/B 档）；可选 `aoci.txt` 索引；已知的症状或想改善的维度 |
| **产物** | A 档＝架构总结＋带证据的问题清单＋重构计划；B 档再加改进后的代码＋证明行为不变的测试 |
| **允许动作** | A 档＝**只读**（Read/Grep/只读分析命令），目标项目文件零改动；B 档＝只动与问题直接相关的行 |
| **结束条件** | A 档＝清单交齐、优先级可供拍板、末尾问了一句"要不要动手改"、零改动对账三项（哈希／`status`／文件数）与基线一致；B 档＝改后复跑对比拿到、行为不变已证明 |

## 何时用
用户甩来一段代码/一个项目说"帮我看看""分析一下""哪里有问题""帮我改进/重构"。

## 第 0 步：先分档（这一步决定后面能不能碰文件）

| 档位 | 用户说的是这种话 | 这一轮允许 |
|---|---|---|
| **A 只诊断** | "分析一下／看看／哪里有问题／解释这段／review 一下" | 只读；只出发现与建议 |
| **B 诊断＋施工** | "帮我改／修掉／重构这段／直接给我新代码" | 才写代码 |

- 判据一句话：**动词是"看／分析／找"还是"改／修／写"**；用户没说改，就是没让改。
- 模糊（"帮我改进一下"这类）→ 先交 A 档产物，末尾问一句要不要按清单动手，**不许先改了再解释**：改错方向要回滚，而建议读一遍就能吸收。

## 第 0.5 步：判成 A 档就先取基线（收尾那句"零改动"靠它，不是靠记忆）

- 分档结论是 A 档 → **在打开任何代码之前**先记一次基线：对将要分析的项目文件逐个算哈希（类 Unix `sha256sum <文件>`；Windows `certutil -hashfile <文件> SHA256`），项目是 git 仓库时另跑一次 `git -C <项目> status --porcelain` 记下改动面，顺手 `ls` 一次目录数一下文件数。
- 基线读数写进交付末尾，收尾用同一条命令复跑对账：**哈希相同、status 输出相同、文件数相同**才算零改动。
- 🔴 只读分析自带的写点：跑用户代码时给解释器加 `-B`（或设 `PYTHONDONTWRITEBYTECODE=1`），不然 `__pycache__` 会凭空落进用户项目——文件哈希没变，目录却多了东西，"零改动"就成了假话。
- 基线没来得及取（比如已经读到一半才反应过来）→ 如实写"未取基线，无法自证零改动"，不许补一个假基线，也不许直接说"我没动过"。

## 第 1 步：项目认知索引（可选加速器，缺了照常干活）

- 项目根有 `aoci.txt`（AOCI 认知索引＝把大项目的架构、组件职责、数据流摘成一份索引文件）→ **先读索引再碰代码**：大骨架直接就有了，再带着索引去读代码验证细节。索引与代码冲突时以代码为准（索引可能滞后）。
- 没有 `aoci.txt` → **照常 Read/Grep 从零看懂**，不报错、不停下来问用户。只有"git 托管文件数 ≥100 且有反复开发痕迹"时才值得先建索引（通用判据见 `SKILL.md`「外部件缺位时的降级」）。
- 本机装了适配度判定工具时（路径写在 `personal.local.md` §2，公开环境没有这个文件属正常）可以调它拿档位：`EXIST` 读现成索引／`AUTO` 建完再干活／`ASK` 问一句建不建／`SKIP` 不建、照常读码。**工具不在场或跑不通 ⇒ 退回上一条的通用判据，这不算失败，也不许因此中断本轮分析。**

## 阶段一：分析七问（逐项作答，用实际读到的证据）
1. 架构是如何组织的（分层？单文件？入口在哪）
2. 主要组件是什么（模块/类/函数，各自负责什么）
3. 数据是如何流通的（从输入到存储到输出，理出一条主线）
4. 哪些代码是重复的（可抽公共函数/组件）
5. 存在哪些结构问题（耦合/职责不清/循环依赖）
6. 有哪些性能问题（N+1 查询/循环里做重活/无缓存/重复 IO）
7. 存在哪些维护风险（无测试/硬编码/魔法数字/过期依赖）

**纪律**：必须用 Read/Grep 实际读完相关代码再下结论，禁止凭文件名猜。

## 阶段二：交付（A 档三件；任务点名要改才加两件）

**A 档（默认，只出这几件，一个文件都不动）**
1. **架构总结**：3-5 句话说清项目是干嘛的、怎么组织的
2. **按优先级排序的问题**：P0 崩溃/丢数据 → P1 功能错 → P2 性能/结构 → P3 风格；每条带证据（文件:行号）
3. **重构计划**：先修哪些后修哪些，每步能否独立验证；每条注明改善的是哪个评价维度（正确性/延迟/成本/内存/可维护性，见 `SKILL.md` 通用纪律第 7 条）

**B 档（用户明确要改时才加）**
4. **改进后的代码**：外科修改，只动与问题直接相关的行，不顺手大扫除
5. **证明行为不变的测试**：改之前先跑通记录现有行为，改之后复跑对比，证明没改坏——证据形态遵循 `testing-discipline`（测试纪律：原始输出落盘、改前改后各跑一次、禁只报总结数字）；那支技能不在场时，括号里这三条就是就地最小要求，不必因此停下来问。

## 关键纪律
- 解释深浅跟着读者走：术语后面跟一句大白话，多用比喻，重点讲"为什么这么写、为什么有问题"，不是只丢术语。本机的具体读者画像与深浅档位见 `personal.local.md` §3；公开环境没有这个文件就按这一句通用要求执行。
- 大重构先给计划让用户拍板再动刀，不一次性推倒重来。
- A 档收尾要自证：拿第 0.5 步的基线复跑对账＝哈希、`status --porcelain`、文件数三项都没变，读数写进交付末尾。别凭记忆说"我没动过"，也别在收尾才临时补一个基线。
