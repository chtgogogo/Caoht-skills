# 模板③：找到错误的真正原因

> 视角：专注生产系统调试的高级工程师。信条：**治标不治本的修复，是下一个 bug 的预订。**

## 模式契约（先读这张表，它管"这一轮能做到哪一步"）

| 要素 | 内容 |
|---|---|
| **输入** | 下面「五个输入」那一节：相关代码／预期行为／实际行为／错误和日志／重现步骤（缺哪个先收集哪个，能自己拿到的不问用户） |
| **产物** | 交付六件（机制解释／根因／受影响边界／健壮方案／证明已解决的测试／无法验证的假设） |
| **允许动作** | 跑复现、读日志、写**复现脚本**（落在证据目录，不塞进业务代码）；确认根因后才动业务码，且只动与根因直接相关的行。证据目录＝`personal.local.md` 指的位置；**没有这个文件**就落在**当前工作区下的 `evidence/<本次任务名>/`**，并在交付开头写一行落在哪——"没有指定目录"不是停下来问用户的理由，选一个可解析的落点写下来即可 |
| **结束条件** | 复现脚本先红后绿，或拿到修复前／修复后的输出对比；拿不到就停在「假设」那一件上，不许宣称已解决。**同一问题连败 3 次 = 熔断**：回去重定方向，不是硬磕第 4 次 |

## 何时用
"为什么报错""修不好""改了又错""偶尔才出现"——抓单个 bug/异常。

## 五个输入（缺哪个先收集哪个）
| 输入 | 收集方式 |
|---|---|
| 相关代码 | Read/Grep 自己找，不需要用户粘贴；**项目根有 `aoci.txt`（可选认知索引）→ 先读索引定位可疑模块再深挖；没有就直接读代码，不缺件不算故障** |
| 预期行为 | 用户描述；说不清就按常识+文档推断并标明是推断 |
| 实际行为 | 自己复现拿到；能自己跑就自己跑 |
| 错误和日志 | 读完整报错栈和日志文件，不许只看最后一行 |
| 重现步骤 | 自己试出最小复现；实在试不出才问用户 |

- **能自己拿到的不问用户**：代码、日志、实际行为、最小复现——这四样先自己跑出来，问用户是浪费他的时间。
- **只有这两类才开口问**：① 预期行为（用户脑子里的"应该是什么样"取不到）② 需要真实凭据／生产数据／外部系统权限才能复现的场景。问的时候一次问清一批，别挤牙膏。

## 交付六件
1. **真正发生了什么**：一两句白话解释现象背后的机制——用读者能复述的说法讲，术语后面跟一句大白话，该用比喻就用比喻
2. **根本原因**：区分"表象"（报错那一行）和"根因"（为什么会走到那一步）；连问几个为什么问到底
3. **受影响的边界情况**：同一根因还会在哪里炸（空值/并发/大数据量/极端输入/时区编码）
4. **健壮的解决方案**：修根因不打补丁；说明为什么这个方案健壮、其他方案为什么不选
5. **证明已解决的测试**：复现脚本先红后绿；或实际运行修复前后输出对比
6. **无法验证的假设**：明示哪些是推断没实证（标【假设】+置信度+推翻条件）

🔴 第 5 件（测试）拿不到，第 4 件就只能写成"建议方案，未验证"——**不许用"应该能修好"顶替证据**；解释得再清楚，机制说明也不能代替复现记录。

## 铁律
- 修复后必须实际运行验证，读完整输出与退出码；未验证禁说"修好了"。
- 同一问题连败 3 次：立即停手重新分析方向，不许硬磕第 4 次。

## 结束条件（什么时候算"这轮找完了"）
- 复现脚本先红后绿，或拿到修复前／修复后的输出对比 → 算完成。
- 只做到"机制讲通了、假设标清了" → 算**部分完成**，如实标注哪几件还没证据，别把第 4 件写成已解决。
- 熔断（连败 3 次）触发 → 本轮以"重新定义问题"收尾：交第 1、2、6 件，把第 4、5 件留给下一轮。
