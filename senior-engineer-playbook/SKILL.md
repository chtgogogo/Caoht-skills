# 资深工程师五模板（senior-engineer-playbook）

> 一句话：给 5 种高频工程任务各配一套「固定视角 + 固定交付清单」，保证产出不缺项、不跑偏。原版是给人复制粘贴的提示词，本 skill 已转成 某宿主 直接执行的工作流——触发后不是念模板，而是按模板的清单干活。

> **本机适配**：若本技能目录存在 `personal.local.md`，读取它并按其中的值覆盖本文件的默认路径 / 盘符 / 偏好；不存在则按本文件写的通用默认值走——缺这个文件不是错误，不要因此停下来询问。

## 第一步：对号入座（选模板）

| 用户场景（听上去像） | 模板 | 读这个文件 |
|---|---|---|
| "帮我做一个……应用/网站/工具/项目" | ①构建 | references/build-app.md |
| "分析这段代码/这个项目，哪里有问题，帮我改进" | ②审查 | references/review-code.md |
| "为什么报错 / 修不好 / 又出问题了" | ③根因 | references/debug-root-cause.md |
| "设计一个系统/架构，要能扛……用户" | ④架构 | references/design-architecture.md |
| "我有个想法，帮我规划一下 / 能不能做" | ⑤计划 | references/idea-to-plan.md |

- 命中几个场景就读几个文件；只命中一个就只读一个，省上下文。
- 拿不准②还是③：用户要"整体分析改进"走②，抓"某一个 bug"走③。
- 五个模板可串联成完整生命周期：⑤想法 → ①构建 → ③调试 → ②审查。

## 五模式的边界（每个模式的输入／产物／允许动作／结束条件）

四个要素的**完整表在各模板文件开头**（那一节就叫「模式契约」，只读命中那个文件就够了）；这里放一列最容易越界的东西——允许动作，即"这一轮能不能动手改文件"：

| 模式 | 允许动作（默认） | 结束条件（一句话） |
|---|---|---|
| ①构建 | 按任务要求**写代码**（新建项目时才动笔） | 照「安装说明」在本机真跑到能访问/能出结果，读了完整输出与退出码 |
| ②审查 | **只读**：只输出发现与建议，改代码要任务里点名 | 交完「问题清单＋优先级＋重构计划」，未被要求施工即结束 |
| ③根因 | 先复现（可写复现脚本），**修根因**才动业务码 | 复现脚本先红后绿，或修复前后输出对比拿到 |
| ④架构 | **不动代码**：只出方案与权衡 | 九件齐＋每个重大决定有一行权衡取舍，用户能据此拍板 |
| ⑤计划 | **不动代码**：只出计划书文件 | 十件齐、红旗已直说，用户拍板后可接力① |

🔴 「只读」不是客套：②④⑤ 三个模式产出的每一个字都应当**不需要改动别人的文件也能交付**。想顺手改代码，先按下一节分流判一次。

## 「分析一下」与「帮我改」分流（②专用，最容易越界的一处）

- **只诊断**：动词是"看／分析／解释／找问题／review"——交付发现＋建议＋优先级＋重构计划，**目标项目文件一个字节都不改**；收尾可以问"要不要按 P0 清单动手改"，但不许先改再解释。
- **诊断＋施工**：动词是"改／修／重构／加／写"——才进入"改进后的代码＋证明行为不变的测试"。
- **拿不准**：一律先按只诊断交产物。判据一句话：**用户没说改，就是没让改**；改错了方向要回滚，而建议读一遍就能吸收。
- 判据要落盘，而且要**先取基线**：②开工第一件事就对目标项目文件算一次哈希记下（类 Unix 用 `sha256sum <文件>`，Windows 用 `certutil -hashfile <文件> SHA256`；项目是 git 仓库时另加一句 `git -C <项目> status --porcelain`），收尾再算一次对账＝零改动。这是本模式唯一的自证方式，别凭记忆说"我没动过"；收尾才想起哈希已经没有基线可比了。🔴 **只读分析也自带写点**：跑用户代码时给解释器加 `-B`（`py -B 脚本.py`／`python3 -B 脚本.py`，或先设 `PYTHONDONTWRITEBYTECODE=1`），否则 `__pycache__` 里的 `.pyc` 会落进用户项目——文件哈希没变，目录却多了东西。本机该用哪个解释器命令，按 `personal.local.md`／本机编码纪律点名的那个走。

## 通用交付纪律（所有模板生效前先读）

1. **coding-behavior 照守**：本 skill 与《编码行为准则》（`coding-behavior`）叠加使用，那边内联的纪律条数一条不少——**条数与名单去对方正文现查，本文件不抄一份会过期的副本**（见下面「让位规则」）。
2. **缺信息先问的边界**：只有"缺了会白干"的重要信息才问（如：给谁用、数据要不要存、部署到哪）；无关紧要的选型自己定，说一句理由就开工，不反问用户。
3. **数字不脑补**：凡 [数字]/[数据] 占位，用户没给就标"未知"，给分档方案，禁止编造精确值。
4. **验证纪律落地**：交付"完整实现/测试/修复"类产物，必须实际跑通再声称完成；写明无法验证的假设。**证据形态遵循 `testing-discipline`（测试纪律）：原始输出落盘、改前改后各跑一次、禁止只报总结数字**——这三条同时是它不在场时的就地最小要求，缺那支技能不是错误，不许因此停下来问用户。
5. **磁盘红线**：优先把新项目建在非系统盘（落点取 `personal.local.md` §1–§2；没有这个文件就落在当前工作区下的项目目录，并在开工说明里写一句落在哪）。🔴 **红线禁的是"系统盘里的用户目录默认落点"（`C:\Users\...` 下的 Documents/Downloads/AppData 这类），不是"系统盘上的一切路径"**——工作区本身就在系统盘时，落在**工作区内的项目子目录**是合法档位（照旧写一行落在哪，并附一句"想换盘告诉我"），别为了躲 C 盘往摸不着的目录乱写，更不要因此停下来问用户。容量**一律现场读取**，正文与产物里都不许出现写死的"某盘只剩 X G"——读法（把 `<盘符>` 换成目标盘）：`py -c "import shutil,sys;print(shutil.disk_usage(sys.argv[1]).free//2**30,'GB')" <盘符>:/`；装了《磁盘缓存纪律》时也可以跑它的 `disk_check.py`。数字只在本次交付里有效，隔天必过期。
6. **不讨好**：想法有缺陷、方案有坑，直说 + 给解法；绝不为让用户开心而弱化问题。
7. **优化／重构先定评价维度**：任何"更快／更省／更好维护"的建议，先钉住改善的是哪一维——**正确性／延迟／成本／内存／可维护性**（五维任选，可多维但要排序）。同一处代码在不同维度下的正解常常相反（加缓存换延迟＝花内存，批量化换吞吐＝加延迟）；任务没给维度、上下文也推不出来就问一句「这次主要想改善哪一项」，并把各维的代价摆出来。已给的每条方案都要标"它在哪个维度上成立、在哪个维度上是退步"——没标维度的优化建议按未完成处理。

## 与相邻技能的让位规则（一次任务只认一个主流程）

| 任务实际在干什么 | 主流程归谁 | 本 skill 这一轮提供什么 |
|---|---|---|
| 看懂一段代码／定位问题／要一份结构化交付 | **本 skill** 对应模式 | 走完整清单 |
| 具体改哪几行、怎么改不跑偏 | `coding-behavior`（编码行为准则·共通十条） | 只给交付清单的**形状**；纪律条款本身不重述、不另起一套流程 |
| 整个项目从需求到交付的多阶段编排（切任务卡、台账、断点续传、验收闭环） | `delivery-pipeline`（交付流水线） | 让位：已在流水线里的任务**不再套①的八件套**，只补它当前缺的那一件产物 |
| 审的是尚未实施的方案能不能开工 | `plan-review`（评审计划） | 不触发本 skill（⑤只管把想法磨成计划书，不裁能不能开工） |

- 🔴 **让位目标不在场时不空转**：本文件点名的外部件（让位表那三支、降级节那几件）只要有一件在本机找不到，**本模板就自己把对应清单走完**——归谁做谁没来，活儿不停在"找不到那支技能/那个工具"上，也不许因此报错退出或反问用户。交付里写一行"X 不在场，本轮按通用判据自己走完"就够。
- 机械含义：**别同时加载两套完整清单**——重复的纪律文件只多交一份上下文税（占内存又挤占你的对话窗口），还容易两条规则打架。
- 触发词重叠时的处理：先按上表归口，归口结论在交付开头写一行"本轮主流程＝X，本模板只补 Y"，让人看得见是谁在主导。
- 与①构建的分工：小工具／单页／一次性脚本走①；要跨窗口接力、有多张任务卡、需要台账断点的走流水线。

## 外部件缺位时的降级（AOCI 索引是可选加速器，不是前置件）

`aoci.txt`（项目认知索引＝把一个大项目的架构、组件职责、数据流摘成一份索引文件）和它的建索引工具都是**增强件**：在场就用，不在场直接 Read/Grep 从零看懂。🔴 **缺件不是错误，不许因为找不到工具就停下来问用户或报错退出**。

- 判"这个项目值不值得先建索引"的通用判据（零依赖，谁都能自己数）：
  - git 托管文件数 ≥ 100（`git -C <项目> ls-files | wc -l`）**且**有反复开发痕迹（同一项目已有多条历史记录/多个阶段在改）→ 值得先有索引；
  - 两条都不满足 → 不必建索引，照常读代码。
- 本机装了判定工具时（路径见 `personal.local.md` §2），按它输出的档位走：`EXIST`＝读现成索引／`AUTO`＝直接建／`ASK`＝问一句／`SKIP`＝不建；**跑不通或没有该工具就退回上面那条通用判据**。
- 索引与代码冲突时**以代码为准**（索引会滞后，滞后比没有更害人）。

## 交付自检（收尾过一遍）

- [ ] 对应模板的交付清单逐项齐了（真不需要的项注明为什么省略）
- [ ] 代码类产物实际运行验证过，读了完整输出与退出码
- [ ] 占位数字没有编造，未知项已标明
- [ ] 没有预埋用户没要的功能
- [ ] ②审查模式且任务没要求改码：目标项目文件零改动（改前改后哈希对账，读数落盘）
- [ ] 优化／重构类建议：每条都标了评价维度（哪个维度变好、哪个变差）
- [ ] 缺件降级如实写了：用了／没用哪个外部件，缺一件时结论有没有受影响
