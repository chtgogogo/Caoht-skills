## 五步工作流

1. **【定范围】** 先报出这个 Agent 的四轴画像：工具会不会真的改东西或往外发（副作用）、单流还是多流（并发）、单租户还是多租户、碰不碰密钥/个人信息（敏感度）——然后跑 `py scripts/fm_catalog.py select --side-effect 写 --concurrency 多 --tenant 多 --sensitivity 敏感`，它只列结构性适用的条目并打印「加载范围：命中 X ／ 总数 Y（跳过 Z 条）」。**单点故障不再全量穷举**；首次设计评审或不确定画像时才全量问（`select --format checklist` 不带参数＝默认单流只读画像，加满四轴＝全库）。死法逐项问的判据不变："我这个 Agent 会不会这样死？"
2. **【命名】** 命中的每条，到 01-failure-modes 查专业术语。**问题有了名字，才能搜到现成的药**——你不需要发明解法，只需要知道这病叫什么。
3. **【选药】** 到 02-patterns 查对策的「最小实现」，优先挑计数器级（几行代码）的先上：迭代上限、预算上限、超时，比复杂的检测算法划算十倍。
4. **【查漏】** 代码写完后，喂给 06-prompts 的模板，让 AI 扮演挑剔的 SRE/安全工程师再列一遍问题，做差距分析（哪些已有防护、哪些在裸奔）。
5. **【门禁】** 上线前过「上线前检查」的凌晨三点十问 + 八项硬门禁，产出《风险清单表》。

## 库内治理（源与视图，改库前必读）

本库一条知识只允许一个**事实源**，其余位置是**视图**：

- **01-failure-modes 是唯一事实源**：死法的现象/术语/根因/对策/检查问题的权威版本都在这里。
- **02（对策库）、03（术语表）、05（检查清单）是 01 的视图**：02 是"药柜"（对策的实现细节），03 是"字典"（术语的一句话解释），05 是"问卷"（检查问题的按场景重组）。三者头部均有派生声明。
- **04（案例）和 06（提问模板）是独立资产**：不派生自 01，各自独立维护。
- **修改顺序**：新增/修改死法 → 先改 01（编号接续该类最大号）→ 再同步 02/03/05 中受影响的条目。只改视图不改 01 = 违规。
- 向 01 追加新条目前，先到 03 术语表查重：业界已有名字的概念，优先收进现有死法的相关字段，而不是另起新条目。
- **容量数字只有一个来源**：入口 SKILL.md 的 AUTO 块与 `references/01-failure-modes/_目录索引.md` 由 `py scripts/fm_catalog.py render --apply` 从条目**现扫**生成。散文里再写第二处条数＝`check` 直接判红，**写对了也红**——第二处数字本身就是下一个漂移点，改对一次管不住下次扩容。交叉引用（"见 XX-YY / R-XX"）由 `check` 查悬空编号，禁止凭记忆写；扩容后的核对方式是 `check`，不是 grep 旧值。（教训来源见 CHANGELOG v1.1.2 元教训 1/2 与 v1.2.0 的 43↔41 收口）
- **本机落点**：母本＝本目录（权威库，受 git 管控）；宿主注册副本路径、个人在用的 Agent 清单等**本机状态**一律写进 `personal.local.md`（与本文件同级；存在则先读它覆盖默认值，不存在就走通用流程）。该文件按 `*.local.md` 规则**永不进发布仓**，所以本库里除了这个文件之外不出现个人机器路径。大改前先确认工作树干净、靠 git 回滚，不再新增 `*.bak` 手工副本（发布仓本就按 `*.bak*` 排除它们）。

## 条目字段格式（向 01/02 追加新条目必须遵守）

```markdown
### LOOP-1 无限循环（同一错误反复试）
- 现象：Agent 反复调同一个工具，没有进展
- 术语：Livelock / Non-progress detection（活锁 / 无进展检测）
- 根因：模型陷入局部循环，或工具持续失败但未上报
- 对策：迭代上限 + 状态指纹做进展判据 + 熔断器
- 最坏后果：烧 token、卡死任务、上下文污染
- 检查问题：最近 N 轮状态有没有变化？同一工具同参数调了几次？
- 相关：Circuit breaker, Exponential backoff
- 适用条件：副作用=任意｜并发=任意｜租户=任意｜敏感度=任意
```

八项必填（缺一项 `check` 判红），两项可选：`案例`（挂真实/构造事故）、`运行边界`（这条对策拦在哪一步、拦不住什么）。**适用条件的四个轴只准取受控词表**：副作用=任意/有写、并发=任意/多流、租户=任意/多租户、敏感度=任意/敏感——写"任意"＝任何画像都得问这条，写具体条件＝结构性不可能发生这种死法时才跳过；别为了少加载而把普遍死法标成条件项（那等于把防线藏起来）。

编号规则：`LOOP-`(循环与终止) `ERR-`(错误与恢复) `COST-`(成本与预算) `SEC-`(安全与权限) `CTX-`(上下文与状态) `CONC-`(并发与顺序) `GOV-`(治理与合规)，序号接续该文件现有最大号（`check` 会查重号与断号）。

## 脚本通道（唯一允许改盘与出数字的地方）

`scripts/fm_catalog.py`，六条子命令，默认**只读**（写盘只有 `render --apply` 一条路，且带写后读回验收）：

| 命令 | 它回答什么 |
|---|---|
| `scan` / `counts` | 现扫条目与容量总账（死法/类/对策/术语/案例/清单/模板各多少） |
| `select --side-effect … --concurrency … --tenant … --sensitivity …` | 按画像只挑适用条目，打印「加载范围：命中 X ／ 总数 Y（跳过 Z 条）」 |
| `render [--apply]` | 生成入口 AUTO 块与 `_目录索引.md`；不带 `--apply` 是干跑，先看 diff 再落盘 |
| `check` | 逐条判据（R1 编号唯一连号、R2 字段齐＋四轴受控、R3 交叉引用不悬空、R4 散文不复述容量、R4b 入口数字等于现扫、R5 分类/维度数不过期、R6/R7 评估已接入可观察行为、R8 药柜覆盖） |
| `selftest` | 合成夹具上跑全套断言：每条判据都配一个"只破坏它"的红样本＋一个不冤枉它的绿样本；先加条目、再验数字自动跟着变＝扩容演练 |

退出码：`0` 通过／`1` 有红项／`2` 分母闸失效（目录缺失或扫到 0 条——空集上的"全绿"不算通过）。

## 和近亲 skill 的边界（不抢活）

- **coding-behavior**：写码九纪律照常叠加，本库只管"Agent 会怎么死"，不管"代码怎么写"。
- **senior-engineer-playbook 模板⑤**：管"想法→计划"；本库在计划之后、写码之前做"风险审计"，两者可接力。
- **pitfall-log**：管你自己踩过的坑；本库管业界已知的 Agent 死法。新踩的 Agent 坑两边都可记：经验教训进 pitfall-log，通用的死法按七字段格式追加进本库 01。
- **缺陷诊断/调试类 skill**：普通业务 bug 走那边；只有 Agent 特有的失败模式（循环/熔断/预算/越权）走本库。

## 交付自检（收尾过一遍）

- [ ] `select` 定范围内的死法逐条问过（未命中的注明"为什么结构性不会发生"，不是跳过）；范围外的条目在《风险清单表》里写明画像与跳过理由
- [ ] 每条对策写清**拦在哪一步**：预算是调用前预留还是返回后累计、幂等是同键重放还是拒绝、循环检测比的是最近一轮还是历史集合（拦在半路才算防线，事后记账只算报表）
- [ ] 每个命中的死法都有对策，且对策在代码/配置里有明确落点
- [ ] 上线前硬门禁全勾：八项基础 + 涉及真实用户/合规时的四项企业级附加（未上线的产物注明"仅设计评审"）
- [ ] 产出《风险清单表》：编号/现象/严重度/术语/解法/修复成本/本轮是否处理
- [ ] 本次新发现的自有坑，按七字段格式追加进 01，案例按标注规范追加进 04
