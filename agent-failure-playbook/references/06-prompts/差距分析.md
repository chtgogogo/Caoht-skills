# 提问模板：差距分析（06-prompts）

> 用法：跑完「生成问题清单.md」拿到问题清单后，第三步追问。这一步把"问题清单"变成"行动清单"——哪些已有防护、哪些在裸奔、先修哪个。

## 三段追问（照抄）

**第一段：对照打标**
```
对照我的代码（[再贴一次代码，或说"用刚才那段"]），
把上面的问题清单逐条标注：
【已有防护】/【裸奔】/【部分防护】，
已防护的请指出防护在代码的哪个位置（文件+函数/行），
不许凭空说"应该有防护"——找不到落点就算裸奔。
```

**第二段：出表**
```
输出一张七列的风险清单表：
编号 | 现象 | 严重度(高/中/低) | 专业术语 | 业界解法 | 修复成本(计数器级/中等/架构级) | 本轮是否处理

修复成本定义：
- 计数器级 = 一个计数器或一个 if 能解决（迭代上限、重试上限、超时）
- 中等 = 需要一个独立小模块（状态指纹、熔断器、预算累计、幂等键）
- 架构级 = 需要改整体设计（权限体系、事务化、多 Agent 仲裁）
```

**第三段：要答案**
```
按"严重度 × 修复成本"排序，给我最划算的前 3 项——
优先"高严重度 + 计数器级"的。
每项给一句话的落地位置建议（加在哪个函数/哪一层）。
"本轮不处理"的行保留，作为已知风险台账。
```

## 产出物去向

这张七列表就是《风险清单表》——与 05-checklists/上线前检查.md 里的模板同款，直接作为上线评审的交付物。设计时检查、AI 查漏、凌晨三问的结果都汇到这一张表，**一张表管上线**。

## 判断标准（防 AI 和你自己自欺）

- 「已有防护」必须有代码落点，"我觉得应该会处理"不算（对应死法 ERR-3 假成功的同款心理）。
- 修复成本报"架构级"要警惕：很多"架构级"的说法是在逃避十行代码能堵住的洞。先逼问一句："计数器级真的挡不住吗？挡不住的最小反例是什么？"
