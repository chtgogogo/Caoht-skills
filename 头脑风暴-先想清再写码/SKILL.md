# 头脑风暴：把想法变成设计

通过自然协作对话，把模糊想法打磨成完整设计与规格。

先理解当前项目上下文，再**一次一个问题**地澄清，直到你清楚要做什么；然后呈现设计并取得用户批准。

<HARD-GATE>
在呈现设计并获得用户批准之前，不得调用任何实现类 skill、不得写任何代码、不得搭建项目骨架、不得采取任何实现动作。无论项目看起来多简单都适用。
</HARD-GATE>

## 反模式："太简单了不需要设计"

每个项目都要走这个流程——待办清单、单函数工具、配置改动，全都算。简单的项目恰恰是最容易被"想当然"坑掉、浪费最多工的地方。设计可以很短（真简单的话几句话即可），但你**必须**呈现它并拿到批准。

## 检查清单

你必须为以下每一项创建任务，并按顺序完成：

1. **探索项目上下文** — 查看文件、文档、近期提交
2. **适时提供可视化伴侣** — 不要一上来就提。当某个问题"用看的比用说的更清楚"时，再单独发一条消息提议；用户同意后浏览器标签页为你打开。若全程没有可视化问题，绝不主动提。见下方"可视化伴侣"一节。
3. **提出澄清问题** — 一次一个，理解目的 / 约束 / 成功标准
4. **提出 2-3 个方案** — 带取舍与你的推荐
5. **呈现设计** — 按复杂度分节呈现，每节后征求用户认可
6. **写设计文档** — 存到 `docs/specs/YYYY-MM-DD-<topic>-design.md` 并提交
7. **规格自审** — 快速内联检查占位符、矛盾、歧义、范围（见下）
8. **用户审阅写好的规格** — 请用户在继续前审阅规格文件
9. **转入实现规划** — 设计批准后，进入实现规划（可直接制定实现计划，或调用你已有的规划类 skill）

## 流程

**理解想法：**
- 先查看项目当前状态（文件、文档、近期提交）
- 提问前先评估范围：若需求描述多个独立子系统，立即指出，先分解
- 若项目过大无法用单份规格覆盖，帮用户拆成子项目；每个子项目走各自的 规格→计划→实现 循环
- 对范围合适的项目，一次一个问题澄清
- 尽量用选择题，开放也行
- 每条消息只一个问题
- 聚焦：目的、约束、成功标准
- **每问必带推荐答案与分析（v1.1）**：提问前先给出你的推荐选项和理由（适用场景/优缺点/学习成本），用户零基础也能拿着现成选项做决策，而不是面对开放问题发呆。用户选了非推荐项时，先确认是否理解了取舍再继续

**探索方案：**
- 提 2-3 个不同方案，带取舍
- 对话式呈现，附你的推荐与理由
- 先给推荐项并解释为什么
- 每个方案必须如实列出**已知缺陷与翻车场景**（v1.1：只说优点不提坑 = 卖文创收智商税）
- 无情践行 YAGNI —— 从每个方案和设计里砍掉不必要功能

**呈现设计：**
- 理解要做什么后呈现设计
- 每节按复杂度缩放：简单几句话，复杂 200-300 字
- 每节后问是否对路
- 覆盖：架构、组件、数据流、错误处理、测试
- 不对劲就回去澄清

**为隔离与清晰而设计：**
- 拆成小而目的单一、接口清晰、可独立理解的单元
- 对每个单元能答：做什么、怎么用、依赖什么
- 小且边界好的单元更易推理与编辑；文件变大往往是它做了太多的信号

**在已有代码库中工作：**
- 改之前先探索现有结构，遵循既有模式
- 现有代码有问题且影响本次工作，把针对性改进纳入设计
- 不提议无关重构

## 设计之后

**文档：**
- 把验证过的设计（规格）写到 `docs/specs/YYYY-MM-DD-<topic>-design.md`（用户偏好覆盖此默认）
- 提交到 git

**规格自审：**
写完后以全新眼光看：
1. 占位符扫描：有无 TBD / TODO / 不完整 / 含糊？修掉
2. 内部一致性：章节矛盾？架构与功能描述匹配？
3. 范围检查：是否聚焦到单份实现计划，还是需分解
4. 歧义检查：需求能否两种解读？能就选一种并写清
内联修复，无需重复审。

**用户审阅门：**
自审通过后，请用户审阅写好的规格再继续：
> "规格已写好并提交到 `<path>`。请审阅，若要在开始制定实现计划前改动请告诉我。"
等用户回复。要改就改并重跑自审循环。批准才继续。

**实现：**
- 设计批准后进入实现规划（可直接制定实现计划，或调用你已有的规划类 skill）
- 不要急着写代码，先有可执行的计划

## 可视化伴侣

基于浏览器的伴侣，用于头脑风暴时展示原型、图表、可视化选项。作为**工具**而非模式——接受伴侣只意味着它可用于"适合可视化"的问题，不代表每个问题都走浏览器。

**适时提供（just-in-time）：** 不要一上来就提。等到某个问题确实"用看的比用说的更清楚"（真实原型 / 布局 / 图表问题，而不只是个 UI 话题）时，再单独发一条消息提议：
> "接下来这部分如果我展示给你看可能更容易——我可以在浏览器标签页里现做原型、图表和对比。它还比较新，可能比较费 token。要开吗？我帮你打开。"

这条提议**必须单独成一条消息**，只含提议，等用户回应。接受则用 `--open` 启动服务器让浏览器自动打开首屏；拒绝则继续纯文本，不再提，除非用户自己提起。

**逐题决定：** 即便用户接受，也要对**每个问题**判断用浏览器还是终端。判断标准：用户"看到"是否比"读到"更易懂？
- 用浏览器：原型、线框、布局对比、架构图、并排视觉设计
- 用终端：需求问题、概念选择、取舍清单、A/B/C/D 文字选项、范围决策

若用户同意，启动前先读详细指南：本 skill 目录下的 `visual-companion.md`
