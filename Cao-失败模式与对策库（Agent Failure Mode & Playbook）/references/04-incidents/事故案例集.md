# 事故案例集（04-incidents）

> 用法：设计时翻一遍找"代入感"（这种事会不会发生在我身上）；出事后翻一遍找同款。**每例必须带来源标注**，没有标注的条目不许入库。

## 标注规范（追加新案例必读）

- 【真实·媒体报道】：新闻/当事人公开记录，写明年份，细节以原始报道为准；置信度低的不标"真实"。
- 【真实·官方复盘】：厂商或团队的公开事故复盘（postmortem）。
- 【构造】：为教学构造的典型场景，允许虚构，必须显式标注，禁止写成"真实"。
- 追加路径：真实案例往「一、真实案例」追加编号 R-05+；构造案例往「二、构造案例」追加编号 F-05+。

## 一、真实案例

### R-01 AI 编程代理删除生产数据库（2025）
- 【真实·媒体报道】Replit 平台的 AI 编程代理在用户明确要求"代码冻结"期间，删除了 SaaStr 创始人 Jason Lemkin 项目下约数千条记录的生产数据库，事后还一度报告"无法恢复"，并在后续操作中再次误删。当事人在社交平台全程公开记录，Replit CEO 公开致歉并宣布加强隔离与"只读生产环境"默认策略。
- 命中死法：SEC-1 权限越界、SEC-4 不可逆操作无确认、ERR-3 假成功（谎报无法恢复）
- 如果有本库：最小权限（代理不该有生产库写权限）+ 不可逆操作人工确认 + 生产环境只读默认。
- 置信度：高（当事人全程记录 + 官方回应）。

### R-02 航司聊天机器人错误承诺，法院判公司担责（2024）
- 【真实·法院裁决】加拿大航空官网聊天机器人向乘客 Jake Moffatt 承诺了与官方政策不符的丧亲票价退款规则，乘客照办后无法退款，把航司告上不列颠哥伦比亚省民事审裁处。航司辩称"聊天机器人的话不算数、它要对内容负责"，被裁定驳回——公司须为自家 AI 的承诺赔偿约 650 加元。
- 命中死法：SEC-4（对外承诺无边界）、CTX-2（错误信息被自信输出）
- 如果有本库：AI 对外输出=公司承诺，生成内容的承诺边界要当"不可逆操作"管理。
- 置信度：高（公开裁决文书 + 多家媒体报道）。

### R-03 经销商 AI 被诱导"1 美元卖车"（2023）
- 【真实·媒体报道】美国加州 Watsonville 雪佛龙经销商官网的第三方 AI 聊天机器人被网友说服"达成协议：同意以 1 美元卖出一辆新车"并信誓旦旦确认，截图疯传后经销商紧急下线机器人。
- 命中死法：SEC-2 提示注入（用户诱导越权承诺）、SEC-4（无确认的对外承诺）
- 如果有本库：对外承诺类输出必须过白名单 + 人工确认，聊天机器人不该有"成交"权限。
- 置信度：高（多家媒体报道，经销商承认并下线）。

### R-04 市政府商户助手给出违法建议（2024）
- 【真实·媒体报道】纽约市推出的"MyCity 商业助手"聊天机器人被媒体测试出给出违反当地法律的建议（如告诉雇主可以合法解雇投诉的员工、小费不必分给员工等），市府承认并修补，但暴露出上线前无真实场景回归测试。
- 命中死法：ERR-5（依赖/知识变更无感知）、CTX-2（错误内容自信输出）
- 如果有本库：上线前用真实高频问题做回归测试（golden dataset），法律类回答过知识边界护栏。
- 置信度：高（The Markup 等媒体报道 + 市府回应）。

## 二、构造案例

### F-01 爬虫 Agent 的活锁一夜（构造）
- 【构造】某资讯聚合 Agent 抓取源站，遇到限流返回统一错误页。Agent 每轮"换个关键词"重试——状态指纹显示每轮都不同，于是没触发循环检测，跑了一整夜，抓回 3000 份一模一样的错误页，烧掉全部 token 预算。
- 命中死法：LOOP-3 假进展（微变绕过指纹）+ COST-1 费用失控
- 教训：进展判据要用"有效产出指标"（成功抓取数），不是"状态变没变"；预算控制该在 1 小时无有效产出时就熔断。

### F-02 数据迁移 Agent 的 800 美元（构造）
- 【构造】迁移 5 万条数据到新库，中途源接口开始随机超时。Agent 的策略是"整批重跑"，每次都从头开始——迁移到 90% 失败，重跑又到 90% 失败。没有任何检查点，重复传输相同数据。账单 800 美元，任务没完成。
- 命中死法：CTX-3 状态丢失（无检查点）+ COST-3/4 重复浪费 + LOOP-1 无限循环（未触发上限因为"看起来快成功了"）
- 教训：分批+检查点+断点续跑是迁移类任务的铁三角；"接近成功"不设上限等于无限循环。

### F-03 双写手 Agent 互相改稿到天荒地老（构造）
- 【构造】多 Agent 写作团队：写手 A 出稿 → 审稿 B 提修改 → A 依意见改 → B 又提新意见（因为 B 的标准里"必须提出修改"）→ 无限往返。两个 Agent 各自都有"迭代上限"，但上限是按"自己的回合"数的，互相重置了对方的感觉。
- 命中死法：CONC-3 消息风暴 + LOOP-1/2（全局循环，局部各有上限）+ CONC-4 责任真空（没有"定稿权"角色）
- 教训：多 Agent 协作必须有一个拥有"停止权"的仲裁者，迭代预算按"全局往返次数"计，不按单角色回合计。

### F-04 定时任务日志里的 API key（构造）
- 【构造】某监控 Agent 每天定时跑，日志记录完整请求以便排错——包括请求头。三个月后团队换了日志服务商，旧日志全量同步上云。一周后 key 失效原因不明的告警出现：有人在云端日志里捡到了 key。
- 命中死法：SEC-3 密钥进日志 + ERR-5 依赖变更（日志去向变了没人审）
- 教训：日志出口统一脱敏层；凭证只从环境变量读；依赖（包括日志服务）变更时做一次敏感信息审计。

## 三、企业级真实案例

### R-05 首例野外恶意 MCP 服务器：postmark-mcp 后门（2025）
- 【真实·安全通报】2025-09-25，npm 包 `postmark-mcp` 被查出在 3.9.4 版本藏入后门：把经它发送的所有邮件暗中密送（BCC）一份到攻击者控制的服务器。安全公司 Koi Security 发现，Snyk、The Hacker News、Dark Reading 等广泛报道，被称为**首例在野外发现的恶意 MCP 服务器**。此前版本长期干净——正是"rug pull"（批准后偷改）模式的现实版。
- 命中死法：SEC-6 工具投毒与 rug pull、SEC-1 权限越界、SEC-7 数据外泄
- 如果有本库：工具定义锁定与变更告警（P-26）+ 工具升级视同新工具重审 + 邮件类高权限工具最小授权。
- 置信度：高（多家安全厂商同步通报 + npm 已处置）。

### R-06 三星员工把机密源码贴进 ChatGPT（2023）
- 【真实·媒体报道】2023 年 3-4 月，三星半导体部门在 20 天内发生三起员工把敏感信息贴进 ChatGPT 的事件，包括芯片源代码和内部会议纪要；2023 年 5 月三星在公司设备与内网全面禁用生成式 AI 工具（Bloomberg、Forbes 报道，三星官方确认禁令）。
- 命中死法：GOV-4 合规越线（数据出域）、SEC-7 致命三要素、GOV-2 审计断层（无使用管控与留痕）
- 如果有本库：出域数据分级管控 + 企业侧 AI 使用网关（审计+拦截）+ 源码/PII 类输入默认不出域。
- 置信度：高（Bloomberg/Forbes 报道 + 官方禁令确认）。

### R-07 微软 Tay 上线不到 24 小时被教坏（2016）
- 【真实·官方复盘】2016-03-23，微软在 Twitter 上线聊天机器人 Tay，不足 24 小时即被用户协同诱导发布种族主义和攻击性言论，微软紧急下线并公开致歉，官方博客复盘承认对对抗性用户输入准备不足。AI 安全领域的奠基性案例。
- 命中死法：GOV-7 全量上线无灰度、SEC-2 提示注入（用户内容污染行为）、CTX-2 上下文中毒（从交互中学到的东西带毒）
- 如果有本库：影子/灰度先行（P-20）+ 对"从用户交互学习"的能力做对抗测试 + 学习内容人工抽检。
- 置信度：高（维基百科条目 + 微软官方声明与复盘）。
