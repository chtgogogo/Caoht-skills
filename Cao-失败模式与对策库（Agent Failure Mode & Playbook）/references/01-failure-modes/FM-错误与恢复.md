# 失败模式：错误与恢复（ERR）

> 这一类死法的共同点：**出错不可怕，可怕的是错得没人知道、错了一直重来、错了留一地垃圾**。

### ERR-1 工具持续失败但同法重试
- 现象：某个工具已经连挂 10 次，Agent 换个说法继续调它，从不尝试别的工具
- 术语：Retry storm / Missing escalation（重试风暴 / 缺失升级策略）
- 根因：没有按工具记失败计数；可用工具列表固定，模型没有"此路不通"的信号
- 对策：熔断器（连挂 N 次暂时移出可用列表）+ 策略升级（强制换路或上报人工）
- 最坏后果：一个坏掉的工具拖死整个任务，其他好工具闲置
- 检查问题：每个工具有独立失败计数吗？达到阈值后模型能看到什么？
- 相关：Circuit breaker, Escalation

### ERR-2 重试风暴（无退避并发重试）
- 现象：服务一抖，Agent（或多个 Agent）立即满速重试，把刚恢复的服务再次打挂
- 术语：Retry storm / Thundering herd / Exponential backoff（重试风暴 / 惊群 / 指数退避）
- 根因：失败后立即原速重试，无等待、无抖动、无上限
- 对策：指数退避 + 随机抖动 + 重试上限 + 熔断器
- 最坏后果：自我 DoS——Agent 自己把自己的依赖服务打死，还反过来怪服务不稳定
- 检查问题：重试之间的等待是怎么算的？有没有封顶和随机化？
- 相关：Exponential backoff, Circuit breaker

### ERR-3 假成功（错误被吞）
- 现象：工具实际失败（写了一半的文件、返回 500），但返回内容里没有明确的失败信号，模型以为成功了，带着错误结果继续往下走
- 术语：Silent failure / Error swallowing / False success（静默失败 / 错误吞没 / 假成功）
- 根因：工具把错误码藏在正文里或干脆吞掉异常；Agent 只看"有没有返回"不看"返回什么状态"
- 对策：工具统一返回结构化结果（成功标志+错误码）；执行后校验（文件真的写进去了吗？数据真的查到了吗？）
- 最坏后果：错误像滚雪球，越往后修复成本越高；最终产物看似完整实则空壳
- 检查问题：每个工具的失败会以什么形式暴露？Agent 的循环判断的是退出码还是猜内容？
- 相关：Input validation, Structured output

### ERR-4 中断残留（半成品垃圾）
- 现象：任务跑到一半被 Ctrl+C / 超时 / 崩溃打断，留下半写的文件、临时目录、未释放的锁，下次运行和新任务全部被污染
- 术语：Orphaned state / Zombie artifacts / Cleanup hook（孤儿状态 / 僵尸产物 / 清理钩子）
- 根因：只在正常路径做清理；多步写没有事务性（要么全成要么全不算）
- 对策：清理钩子（正常和异常退出都触发）+ 事务式写（先临时区后原子提交）+ 启动时扫描上次残留
- 最坏后果：脏数据进正式产物；临时文件堆积爆盘；锁不释放导致后续任务全部死锁
- 检查问题：进程被强杀后，磁盘上会留下什么？下次启动时谁负责认领和清理？
- 相关：Cleanup hook, Transaction

### ERR-5 依赖变更全挂
- 现象：依赖的 API 改了字段名、模型服务换了响应格式、第三方页面改版——Agent 一夜之间从"正常工作"变成"全量报错"
- 术语：Breaking change / Contract test / Dependency pinning（破坏性变更 / 契约测试 / 依赖锁版本）
- 根因：对依赖只测过"当时能用"，没有版本锁定和变更感知
- 对策：依赖版本锁定 + 上线前契约测试（用固定样例验证工具仍按预期返回）+ 失败时给出"是不是依赖变了"的提示
- 最坏后果：静默的格式变更导致数据错乱（不报错但全是错的），比报错更危险
- 检查问题：我的依赖（API/模型/页面结构）锁版本了吗？它们变了我会以什么方式知道？
- 相关：Dependency pinning, Golden dataset
