# 失败模式：并发与顺序（CONC）

> 这一类死法只在**多个执行流**（多任务、多 Agent、并行工具调用）出现。单个 Agent 不会遇到，一上并发全来了。

### CONC-1 并发写冲突
- 现象：两个并行任务同时改同一文件/同一行数据，后写的覆盖先写的；两边都"成功"了，数据却是错的
- 术语：Race condition / Lost update / Optimistic locking（竞态条件 / 丢失更新 / 乐观锁）
- 根因：共享资源无锁无版本；"读-改-写"三步被打断穿插
- 对策：串行化与锁（按资源 key 排队）+ 乐观锁（带版本号提交，版本不对就重读）+ 尽量让任务边界不重叠
- 最坏后果：数据静默错乱——没有任何报错，只有错误的结果
- 检查问题：哪两个任务可能同时写同一个东西？同时写时谁赢？
- 相关：Serialization, Optimistic locking

### CONC-2 依赖顺序错乱
- 现象：B 依赖 A 的产物，但 B 先跑了，拿着空数据往下走；或并行批次里 C 需要 B 的结果却和 B 同时启动
- 术语：Dependency graph / Topological order / DAG（依赖图 / 拓扑排序 / 有向无环图）
- 根因：任务间依赖没有显式声明；调度靠"我觉得顺序差不多是这样"
- 对策：显式依赖声明（任务图，先算拓扑序再调度）+ 前置产物存在性校验（B 启动前先验 A 的产物在不在）
- 最坏后果：整条下游链基于空数据运行，全链报废
- 检查问题：任务图里每条边（谁依赖谁）写下来了吗？启动前验前置产物吗？
- 相关：Input validation, DAG

### CONC-3 多 Agent 消息风暴
- 现象：多个 Agent 互相广播状态/请求，消息量自我繁殖（每条消息又触发更多消息），系统忙于通信不干活
- 术语：Message storm / Chatter / Broadcast amplification（消息风暴 / 噪聒 / 广播放大）
- 根因：广播式通信（人人喊所有人）；无消息预算；状态更新太频繁
- 对策：定向通信（只发给需要的）+ 每 Agent 消息数预算 + 状态变更合并上报（攒批）
- 最坏后果：token 和队列全被通信吃掉，有效工作趋近于零
- 检查问题：一条状态更新会触发几条新消息？放大系数是几？
- 相关：Budget governor

### CONC-4 多 Agent 死锁与责任真空
- 现象：Agent 甲等乙的结果，乙在等甲的；或者一件事出了问题，两个 Agent 都觉得"对方会处理"，没人处理
- 术语：Deadlock / Responsibility gap / Arbitration（死锁 / 责任真空 / 仲裁）
- 根因：循环等待无超时无打破机制；任务边界含糊导致"都以为归对方"
- 对策：等待一律带超时（超时上报仲裁者）+ 每个任务有且只有一个 owner + 设一个总协调者做最终裁决
- 最坏后果：互相等待全体挂死；问题无人认领直到用户发现
- 检查问题：画出等待关系图，有环吗？每个任务能指出唯一负责人吗？
- 相关：Timeout, Arbitration

### CONC-5 信息截留与传递失真
- 现象：多 Agent 协作中，上游只传结论不传前提、或为省 token 砍掉关键上下文；下游基于残缺信息错误推理，还以为拿到了全貌
- 术语：Information withholding / Information loss / Telephone game（信息截留 / 信息损耗 / 传话游戏效应，MAST"代理间失准"大类）
- 根因：Agent 间传递靠"转述"而不是"引用原始依据"；消息限长时砍掉的是上游"觉得不重要"的部分
- 对策：传递带原始依据（结论+关键前提+出处）+ 关键信息结构化传递（schema 固定字段）+ 下游可回查上游原始产物
- 最坏后果：错误在传递链上逐级放大（传话游戏），末端 Agent 自信地执行一个早已失真的任务
- 检查问题：下游收到的消息里有原始依据吗？还是只有上游的转述？砍上下文时谁决定砍什么？
- 相关：MAST Inter-Agent Misalignment, Structured output
