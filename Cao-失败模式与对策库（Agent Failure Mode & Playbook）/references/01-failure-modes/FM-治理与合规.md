# 失败模式：治理与合规（GOV）——企业级

> 这一类死法**单机跑不死你，上了企业级才要命**：多人协作、多环境、多租户、有合规义务、有审计要求时才显形。本类含 UC Berkeley MAST 分类法（arXiv:2503.13657）归纳的"规格类"失败——业界最高频的结论恰恰是：**大多数 Agent 失败不是基础设施问题，而是任务没说清楚**。

### GOV-1 弱规格与角色错位
- 现象：任务描述含糊（"把数据整理一下"）、多个 Agent 职责重叠或没人认领、验收标准不可验证（"做好一点"），Agent 只能瞎猜标准
- 术语：Specification issues / Weak specification / Role misalignment（规格问题 / 弱规格 / 角色错位，MAST 第一大类）
- 根因：把"想清楚"的活推给了 Agent；任务没有可判定的完成标准；角色边界没画
- 对策：任务规格三件套（目标可验证 + 边界明确 + 验收标准可机器判定）+ 每个 Agent 一句话唯一职责
- 最坏后果：Agent 100% 执行了错误的理解；多 Agent 互相推诿或重复干活；事后无法判定"到底谁错了"
- 检查问题：把任务描述给一个新人，他不追问就能开工吗？验收标准能写成断言吗？
- 相关：MAST, Task verification, Task decomposition

### GOV-2 审计断层（谁让 Agent 干的说不清）
- 现象：出了事要复盘，发现回答不了基本问题：这条删除是谁发起的？Agent 当时依据的是哪个版本的指令？用户口头改过的需求没有痕迹
- 术语：Audit trail / Chain of custody / Non-repudiation（审计链 / 证据链 / 不可否认性）
- 根因：只有技术日志没有治理日志；指令变更、人工确认、权限授予没有留痕
- 对策：审计日志与责任链（每次人工确认、指令变更、权限授予都留"谁+何时+批准了什么"）+ 技术日志与治理日志关联
- 最坏后果：合规审查/法律纠纷时拿不出证据链；无法界定人和 Agent 的责任边界
- 检查问题：随机抽一条 Agent 的危险操作，能在一小时内回答"谁批准的、依据哪版指令"吗？
- 相关：Structured logging, Human-in-the-loop

### GOV-3 多租户数据串扰
- 现象：A 客户的 Agent 会话里出现了 B 客户的数据；共享缓存/向量库没按租户隔离，检索跨租户命中
- 术语：Tenant isolation / Data leakage / Noisy neighbor（租户隔离 / 数据泄露 / 喧闹邻居）
- 根因：缓存、向量库、会话状态按"内容相似"而非"租户边界"存取；prompt 模板里租户标识靠模型自觉
- 对策：多租户隔离（存储/缓存/检索全部带租户键强制过滤）+ 跨租户访问在代码层直接拒绝而非靠提示词
- 最坏后果：客户数据互串 = 最大的商业信誉事故 + 合规责任；一个租户的负载拖垮全体
- 检查问题：拿两个租户的账号做交叉测试，A 能通过任何路径（检索/缓存/文件）看到 B 吗？
- 相关：Tenant isolation, Idempotency key

### GOV-4 合规越线（PII / 数据出境 / 删除权）
- 现象：用户的个人信息（PII）被发给了境外模型 API；用户行使"删除权"时发现数据已进第三方供应商的训练或日志，删不干净
- 术语：Data residency / Right to erasure / Data processing agreement / GDPR（数据驻留 / 删除权 / 数据处理协议 / 通用数据保护条例）
- 根因：选型时没把"数据流向哪"当需求；第三方供应商的数据保留政策没审
- 对策：数据流图先行（画出每类数据去了哪些服务、什么区域）+ PII 出域脱敏或本地模型 + 供应商数据处理协议审查
- 最坏后果：监管处罚、被应用商店/云市场下架、集体诉讼
- 检查问题：用户的一条 PII 从输入到日志到第三方，完整路径画得出来吗？每一站都合法吗？
- 相关：PII, Redaction, Vendor lock-in

### GOV-5 供应商锁定与模型退役
- 现象：核心流程深度绑定某家模型的私有特性；该模型宣布退役/涨价/降智（silent downgrade），切换成本高到动不了
- 术语：Vendor lock-in / Model deprecation / Portability（供应商锁定 / 模型退役 / 可移植性）
- 根因：用了不可替代的私有接口；prompt 是对着特定模型脾气调的，换模型全要重调
- 对策：关键链路做抽象层（模型可替换）+ 定期用第二家模型跑对比测试 + 关注供应商退役公告（大厂模型通常有退役时间表）
- 最坏后果：供应商一次价格调整或退役公告，变成全公司的紧急项目
- 检查问题：明天这家供应商倒闭，我的切换周期是小时级还是月级？
- 相关：Model routing, Model drift

### GOV-6 无评估基线的静默漂移
- 现象：换了模型版本/改了 prompt/升级了依赖，没人知道变好还是变坏；两周后才发现某类任务成功率从 95% 掉到 70%，中间没有任何报警
- 术语：Model drift / Eval regression / Golden dataset / Silent downgrade（模型漂移 / 评估回归 / 黄金标准集 / 静默降级）
- 根因：没有固定的评估集和成功率基线；"改完手动试了几个例子"就当验证过了
- 对策：评估回归套件（固定样例集+每版本必跑+成功率阈值报警）+ 上线前新旧版本对比（LLM-as-judge 或人工抽检）
- 最坏后果：质量持续滑坡数周无人察觉，基于错误输出下游又建了一堆东西
- 检查问题：上一版和这一版，同一批测试题的通过率各是多少？说不出数字就是没有基线
- 相关：Golden dataset, Eval regression, Canary release

### GOV-7 全量上线无灰度
- 现象：新版 Agent 直接对全部用户/全部流量生效，出问题就是全量事故；没有"先 5% 流量观察"的缓冲
- 术语：Canary release / Shadow mode / Feature flag / Blue-green deployment（金丝雀发布 / 影子模式 / 功能开关 / 蓝绿部署）
- 根因：把 Agent 当普通函数部署，忘了它的输出质量是概率性的、必须实测
- 对策：影子与灰度发布（影子模式只观察不影响用户 → 金丝雀小流量 → 逐步放量；feature flag 可随时一键回退）
- 最坏后果：一个坏 prompt 变更让全部用户体验劣化数小时甚至数天
- 检查问题：这次变更能在 10 分钟内回退吗？新版本先见过真实流量的样本吗？
- 相关：Feature flag, Eval regression, Kill switch

### GOV-8 配置漂移（多环境不一致）
- 现象：开发环境好好的，生产环境行为诡异——排查发现两边 prompt 版本不同、温度参数不同、工具白名单不同，全靠手工改
- 术语：Configuration drift / Config as code / Environment parity（配置漂移 / 配置即代码 / 环境一致性）
- 根因：prompt、模型参数、工具清单散落在各处（代码、后台界面、某人的笔记），没有版本管理
- 对策：配置即代码（prompt/参数/白名单全进版本库，变更走评审）+ 环境一致性校验（部署时比对配置指纹）
- 最坏后果："在我机器上是好的"成为常态；事故复盘发现原因是一个三月前手工改了没记录的参数
- 检查问题：生产环境的 prompt 是从版本库部署的，还是有人能在界面上直接改的？
- 相关：Config as code, Dependency pinning
