# 对策模式库（02-patterns）

> **派生声明**：本文件是 01-failure-modes（唯一事实源）的"药柜"视图——每条对策防哪些死法以 01 的"对策"字段为准；本文负责给出实现细节与常见误区。修改顺序：先改 01，再同步本文件。
>
> 用法：在 01-failure-modes 里命中死法后，来这里查对策的「最小实现」。**选型原则：计数器级（几行代码）永远优先于检测算法级**——先挡住 80% 的死法，剩下的再上复杂手段。格式：是什么 / 防哪条死法 / 最小实现 / 常见误区。

### P-01 迭代上限（Iteration limit）
- **防**：LOOP-1 无限循环、COST-1 费用失控。
- **最小实现**：主循环加计数器 `step_count`，超过 `MAX_STEPS`（如 25）立即停，向用户报告"已尝试 N 步未完成，当前进展是……"。**总步数上限 + 单工具调用次数上限**两层都要。
- **常见误区**：只设上限不设"到期时说什么"——停了但要交代停在哪、已完成的产物在哪；上限设太大等于没设。

### P-02 状态指纹（State fingerprint）
- **防**：LOOP-2 活锁、LOOP-3 假进展。
- **最小实现**：每轮把"任务关键状态"（待办列表、产出物哈希、当前步骤）序列化后取哈希，存最近 N=5 个指纹；新指纹与历史全同 → 判死循环，触发熔断。
- **常见误区**：把时间戳、随机 id 等天然变化项算进指纹——那会掩盖"其实啥也没干"；指纹只收语义状态，不收噪声字段。

### P-03 进展度量（Progress metric）
- **防**：LOOP-3 假进展（状态微变绕过指纹）。
- **最小实现**：定义"离目标多远"的标量：剩余待办数、已验证通过的比例、产出物完成度。要求每轮此指标必须非增（对剩余量而言），连续 3 轮不降 → 判无进展。
- **常见误区**：用"调用了新工具""生成了新文字"当进展——活动量不等于进展量。

### P-04 超时与截止（Timeout / Deadline）
- **防**：LOOP-4 死等、COST-2 时间失控。
- **最小实现**：每个工具调用包一层超时（如 60s）；整个 Agent 任务设总截止时间（如 10 分钟）；外部事件等待一律带 `deadline` 参数，到期走降级路径。
- **常见误区**：只给单次调用设超时，不给整体设——可以无限次"每次都不超时"地跑下去。

### P-05 指数退避重试（Exponential backoff）
- **防**：ERR-2 重试风暴、COST-1 费用失控。
- **最小实现**：重试等待 `min(base * 2^n, cap)` 秒（如 1s, 2s, 4s, 8s…封顶 60s），加随机抖动（jitter）防同时重试；重试上限 3~5 次，超了转熔断。
- **常见误区**：立即重试或线性重试——服务刚恢复就被重试洪峰再次打挂；重试同参数同 prompt 却期待不同结果。

### P-06 熔断器（Circuit breaker）
- **防**：ERR-1 工具持续失败、ERR-2 重试风暴。
- **最小实现**：给每个工具记"连续失败数"，达到阈值（如 5）→ 打开熔断：一段时间内（如 5 分钟）直接拒绝调用并提示模型换路或上报；冷却后半开试一次，成功才恢复。
- **常见误区**：全局一个熔断器——应该按工具/服务分路；熔断后静默丢弃错误而不告诉模型，模型继续盲试。

### P-07 预算控制（Budget governor）
- **防**：COST-1 费用失控、COST-2 时间失控。
- **最小实现**：累计每次调用的 token/费用（查响应的 usage 字段），设硬上限（如 $2 或 200k token）；每轮检查，超限立即收尾：汇总已有进展，报告"预算耗尽"。
- **常见误区**：只在任务开始时看一眼价格表——必须边跑边累计；软预算（只告警不停）管不住失控的循环。

### P-08 幂等键（Idempotency key）
- **防**：COST-3 重复调用、CONC-1 写冲突。
- **最小实现**：对"会产生副作用"的调用（写库、发消息、支付），用任务 id+步骤号生成唯一键，服务端按键去重：同键重复请求返回上次结果而不是再执行一遍。
- **常见误区**：只防"完全相同的请求"——重试时请求体里若带时间戳就绕过去了；幂等键要从语义生成，不能从请求体哈希生成。

### P-09 输入校验（Input validation）
- **防**：SEC-5 幻觉调用、ERR-3 假成功。
- **最小实现**：工具执行前校验参数：文件路径存在吗？id 在库里吗？数值在范围内吗？schema 对得上吗？不过关直接返回结构化错误（哪个字段、为什么），让模型改了再试。
- **常见误区**：只校验类型不校验语义（路径格式对但文件不存在）；错误信息太笼统（"参数错误"），模型改不对又进入循环。

### P-10 权限门与人工确认（Permission gate / Human-in-the-loop）
- **防**：SEC-1 越权、SEC-4 不可逆操作。
- **最小实现**：把操作分三级——只读（直接放行）、可逆写（放行+留痕）、不可逆/敏感（删数据、发外部消息、花钱、改配置）必须暂停等人确认；Agent 的工具白名单按任务最小授权。
- **常见误区**：给 Agent 一个万能管理员凭证图省事；确认门做成"默认 10 秒后自动同意"——等于没门。

### P-11 输出截断与告知（Output truncation）
- **防**：CTX-1 上下文爆窗。
- **最小实现**：工具返回超长（如 >10k 字符）时：截断保留头尾（结构信息多在头尾），插入明确标记 `[输出已截断，原文 N 字符，省略 M 字，可用 offset 参数分页获取]`。
- **常见误区**：静默截断不告知——模型不知道被砍，基于残缺内容自信作答；只留头不留尾——结论常在尾部。

### P-12 上下文压缩（Context compaction）
- **防**：CTX-1 爆窗、CTX-2 中毒、COST-4 重复传输。
- **最小实现**：历史超过水位（如 70% 窗口）时：保留系统提示 + 最近 K 轮原文，更早的压缩成结构化摘要（目标/已完成/关键决定/未决问题），错误结论复核后再入摘要。
- **常见误区**：压缩时把关键约束压丢了——摘要必须保留原始任务目标和硬性限制；从不清理失败尝试的完整报错堆栈。

### P-13 结构化输出（Structured output / Schema）
- **防**：CTX-4 格式漂移、ERR-3 假成功。
- **最小实现**：让模型按 JSON schema 输出（工具的 structured output / JSON mode），解析失败带错误重试一次，再失败升级处理；关键字段做枚举约束。
- **常见误区**：从自由文本里用正则抠数据——模型换个说法就崩；校验失败后把原始大文本塞回去重试，快速烧掉上下文。

### P-14 结构化日志与追踪（Structured logging / Tracing）
- **防**：CTX-5 不可观测、SEC-3 泄密。
- **最小实现**：每步记一行 JSON：`{step, tool, args摘要, 结果状态, token数, 耗时, 任务id}`，用任务 id 串起整条链路；日志出口统一过脱敏（密钥、手机号、token 打码）。
- **常见误区**：只记成功不记失败；把完整参数（含密码字段）原样进日志。

### P-15 串行化与锁（Serialization / Lock）
- **防**：CONC-1 写冲突。
- **最小实现**：共享资源（同一文件、同一表、同一订单）的写操作按资源 key 加锁或排入单写队列；读可以并行，写必须排队。
- **常见误区**：锁粒度太粗（全局一把锁，并发优势全无）；忘记设锁超时，死锁后全员卡死。

### P-16 清理钩子与事务（Cleanup hook / Transaction）
- **防**：ERR-4 中断残留、SEC-4 不可逆操作。
- **最小实现**：多步写操作包成事务或"先写临时区，全部成功后原子提交"；进程退出（正常/异常）都触发清理钩子，删临时文件、解锁、关闭连接。
- **常见误区**：只在正常路径清理——异常路径（Ctrl+C、超时被杀）才是残留重灾区；"原子提交"实现成了"依次提交"。

### P-17 策略升级（Escalation）
- **防**：ERR-1 重复同法失败、LOOP-1 局部循环。
- **最小实现**：同一目标用同一方法失败 N 次（如 3 次）→ 强制换策略：换工具、换参数、拆小任务，或降级为"报告人工"。禁止第 4 次还用老办法。
- **常见误区**：换策略靠模型自觉——要在代码里强制（失败计数达到阈值后从可用工具列表里移除该工具）；只有"继续重试"和"放弃"两档，缺"换路"和"求助"中间档。

### P-18 置信度路由升级（Confidence-based escalation）
- **防**：SEC-4 不可逆操作、GOV-1 弱规格、LOOP-6 提前收工。
- **最小实现**：让模型同时输出"答案 + 自评置信度（或选项概率）"；低于阈值（如 80%）的操作转人工/转更严格路径。高危操作一律不看自信值、直接进确认。
- **常见误区**：模型自评置信度偏乐观，阈值要按实测校准而不是拍脑袋；用"语气是否肯定"判断自信——不行，要结构化的置信输出。

### P-19 中断续跑（Interrupt / Resume）
- **防**：SEC-4 需要人介入时的状态丢失、CTX-3 重启断档。
- **最小实现**：把工作流设计成"可在任意步安全暂停"：暂停时状态持久化（做到哪、等谁批、批完从哪继续），人批准后从断点原地继续而不是重跑。参考 LangGraph 的 interrupt/resume 模式。
- **常见误区**：等待确认靠轮询占着进程；批准后从头重跑（重复副作用，连着 COST-3）。

### P-20 影子与灰度发布（Shadow mode / Canary / Feature flag）
- **防**：GOV-7 全量上线无灰度、GOV-6 静默漂移。
- **最小实现**：三级放量——影子模式（新版与旧版同跑，只记录不生效，对比差异）→ 金丝雀（5%~10% 真实流量，盯质量指标）→ 全量；全程 feature flag 包裹，任何一级可秒退。
- **常见误区**：影子模式跑得"差不多"就直接全量——影子只证明"看起来行"，金丝雀才算"真行"；灰度期间没有定义"差异多大算异常"的量化阈值。

### P-21 评估回归套件（Eval regression suite / LLM-as-judge）
- **防**：GOV-6 无评估基线的静默漂移、CTX-6 知识过期、ERR-5 依赖变更。
- **最小实现**：固定"考卷"（golden dataset：真实高频任务 30~100 条+标准答案/评分标准），每次改 prompt/换模型/升依赖必跑，成功率跌破阈值即报警；开放性任务用 LLM-as-judge 按评分标准打分，关键场景人工抽检复核。
- **常见误区**：考卷全是能考好的题（幸存者样本）——必须包含历史踩坑题和对抗样例；judge 用同一个模型自评自——评分标准和抽检要对齐。

### P-22 模型路由与级联（Model routing / Cascading）
- **防**：COST-1 费用失控、GOV-5 供应商锁定。
- **最小实现**：按任务难度分流——简单分类/抽取走小模型，复杂推理走大模型；级联模式：先小模型答，置信度不够再升级大模型。同时天然降低了单一供应商的依赖面。
- **常见误区**：路由规则拍脑袋不评估——每档路由单独跑考卷；为了省钱把关键推理也路由到小模型，错误率悄悄上升（接 P-21 防回归）。

### P-23 审计日志与责任链（Audit trail / Chain of custody）
- **防**：GOV-2 审计断层、SEC-4 不可逆操作追责。
- **最小实现**：治理事件单独留痕（区别于技术日志）：谁、何时、批准/修改/授予了什么，不可篡改（append-only）；技术日志的每步操作关联到发起的治理事件 id，形成"指令→确认→执行"完整链条。
- **常见误区**：只有技术日志没有决策日志——查得出"做了什么"查不出"谁让做的"；审计日志可编辑。

### P-24 多租户隔离（Tenant isolation）
- **防**：GOV-3 数据串扰。
- **最小实现**：所有存储（会话状态、缓存、向量库、文件）的每条记录强制带租户键；检索/读取在代码层注入租户过滤，不依赖模型或提示词自觉；跨租户访问直接拒绝并告警。
- **常见误区**：只隔离了数据库忘了向量库和语义缓存——检索是最容易跨租户漏的地方；靠 prompt 里写"你只属于租户 A"来隔离（一注入就穿）。

### P-25 配置即代码（Config as code）
- **防**：GOV-8 配置漂移、GOV-1 规格失控。
- **最小实现**：prompt、模型参数、工具白名单、预算阈值全部进版本库，变更加评审；部署时下发配置指纹，运行时校验"当前跑的配置=版本库里的配置"；提供后台改配置入口的一律废除或改为"改完提 PR"。
- **常见误区**：留着一个"紧急热修"后门直改生产配置——后门就是漂移的入口；prompt 散落在各处函数里而不是集中管理。

### P-26 工具定义锁定与变更告警（Tool definition pinning）
- **防**：SEC-6 工具投毒与 rug pull。
- **最小实现**：接入每个外部工具/MCP 服务器时记录其定义（名称/描述/参数 schema）指纹并审批；运行时定期比对指纹，定义变更即告警+暂停该工具待重审；升级工具版本视为"新工具"重新走审批。
- **常见误区**：只在首次接入时人工看一眼描述——rug pull 的全部意义就是"审批之后才变"；自动无脑跟随工具升级。
