### 0. 起源：作者的四框架方法论（2026-09-23 首轮对话，原文全量留档）

**核心洞察（作者原话）：**

> "AI 只能回答你问的问题。你问"限制器怎么做"，它答"限制器有四种做法"。它不会反问你："你为什么要限制器？你担心的是什么？是无进展、是成本、还是安全？"你缺的是 what（需要什么）和 why（为什么需要）→ AI 不会主动替你生成。问题意识不是靠"想到"，而是靠"系统地穷举"。你不需要天才般的灵感，你需要一套检查框架。每次设计 Agent，按框架逐项问，问多了就变成直觉。"

**框架一：按"失败模式"穷举（作者原表，12 行）**

| 失败模式 | 对应手段 | 术语 |
|---|---|---|
| 无限循环 | 迭代上限 | Iteration limit |
| 原地打转 | 活锁检测 | Livelock detection |
| 状态没变 | 状态指纹 | State fingerprint |
| 工具老失败 | 熔断器 | Circuit breaker |
| 花钱太多 | 预算控制 | Budget governor |
| 重复调用 | 幂等键 | Idempotency key |
| 输出太长 | 截断 + 告知 | Output truncation |
| 参数错误 | 执行前校验 | Input validation |
| 权限越界 | 权限门 | Permission gate |
| 上下文爆了 | 历史压缩 | Context compaction |
| 模型卡住 | 超时 | Timeout |
| 并发写冲突 | 串行化 | Serialization |

作者用法原话："每次设计 Agent，对着清单问："我这个 Agent 会不会出现这种情况？""

**框架二：从其他领域借（作者原表，7 行）**

| 你担心的问题 | 哪个领域解决过 | 去搜什么 |
|---|---|---|
| 无进展循环 | 分布式系统 | livelock detection |
| 状态没变 | 版本控制 / 缓存 | state hash, ETag |
| 服务雪崩 | 微服务 | circuit breaker |
| 重试风暴 | 网络协议 | exponential backoff |
| 重复提交 | 支付系统 | idempotency key |
| 资源耗尽 | 操作系统 | resource quota |
| 死循环 | 程序验证 | termination analysis |

作者要点原话："你不需要自己发明，你需要知道"这个问题别人解决过，叫什么名字"。"

**框架三：从"运维视角"倒推（作者原话）**

> "问自己：如果这个 Agent 上线了，凌晨三点我被叫醒，最可能是什么问题？它卡住了？→ 需要迭代上限 + 活锁检测；它烧了 1000 美元 API 费？→ 需要预算控制；它删了用户数据？→ 需要权限门；它反复失败刷屏？→ 需要熔断器；它上下文爆了？→ 需要历史压缩。运维视角是最容易生成"需求"的视角。 因为运维关心的是"出了什么事"，而不是"功能对不对"。"

**框架四：每次写完，问 AI 一个元问题（作者原话）**

> "这是最实用的技巧。你不需要自己想到所有问题，你可以让 AI 帮你生成问题清单。不要问："帮我实现一个限制器。"要问："这是一个 Agent 的工具执行代码。请你扮演一个挑剔的运维工程师，列出这个 Agent 上线后可能出现的所有问题，按严重程度排序。不要给解决方案，只列问题。" AI 会给你一份"问题清单"，你再从清单里挑要解决的。然后追问："这些问题里，哪些是可以用简单计数器解决的？哪些需要更复杂的检测？分别对应什么专业术语？业界通常怎么解决？"这样你就从"让 AI 写代码"变成了"让 AI 帮你生成需求"。"

**作者的四维提问模板（原文）："我在设计一个 Agent，它的工具执行部分是这样的：[贴代码] 请你扮演一个挑剔的 SRE / 运维工程师 / 安全工程师，按以下维度列出这个 Agent 上线后可能出现的所有问题：1. 循环与终止（无限循环、无进展、活锁）2. 错误与恢复（工具失败、重试、熔断）3. 成本与预算（token、API 费用、时间）4. 安全与权限（越权、注入、数据泄露）5. 上下文与状态（上下文爆、状态丢失、重复调用）6. 并发与顺序（写冲突、依赖顺序、并行安全）。每个问题请给出：问题的具体表现 / 对应的专业术语 / 业界标准解法 / 如果我不处理，最坏后果是什么。先不要给代码，只给问题清单。"**

**语料积累（作者原话）："这个语料库，可以通过两个途径快速积累：让 AI 帮你生成问题清单（上面的模板）；看真实事故报告：搜"AI agent incident report""LLM agent failure case study"。"**

**AI 注解（2026-09-24 补记，说明本库与作者成长主线的关系）**：作者曾自我诊断，自己的核心瓶颈是"不知道有哪些东西存在"（而非学不会已知的东西）。本库就是把 Agent 领域"存在哪些死法、各自叫什么名字、业界怎么解"变成一份可查的清单——**治的不是某个 bug，是"不知道该问什么"这个元问题**。它与作者的 RAG 问答助手项目是同一哲学的两个实例：那边用评测集对抗"不知道答得准不准"，这边用死法清单对抗"不知道会怎么死"。

### 1. ADR-1 单封装，不拆四卡（2026-09-23，作者拍板）

- 作者原话："封装成一个吧，然后中文目录名设计成Cao-失败模式与对策库（Agent Failure Mode & Playbook）"
- 理由（AI 论证、作者采纳）：①四框架触发场景同源（都是"设计/审查 Agent"），拆四个 skill 会互相抢触发，调度器分不清；②四张卡是一条流水线的四个站点不是四件独立工具（卡1 穷举失败模式 → 卡2 查术语 → 卡3 换运维视角查漏 → 卡4 让 AI 复盘补漏）；③官方最佳实践（skill-creator：SKILL.md 轻入口 + references 按需读）正好支持"一个箱子四个抽屉"；④维护成本：一套触发词 vs 四套。
- 框架与目录的映射：框架一→01+02，框架二→03，框架三→05，框架四→06；04 事故案例库是新增承接"真实语料积累"的长期需求。

### 3. ADR-3 七字段条目格式（2026-09-23，作者设计，原文照录）

作者原话："然后再分：现象：Agent 反复调同一个工具，没有进展 / 术语：Livelock / Non-progress detection / 根因：模型陷入局部循环，或工具持续失败但未上报 / 对策：迭代上限 + 状态指纹做进展判据 + 熔断器 / 最坏后果：烧 token、卡死任务、上下文污染 / 检查问题：最近 N 轮状态有没有变化？同一工具同参数调了几次？ / 相关：Circuit breaker, Exponential backoff"

- 字段意图（AI 注解）：现象=识别、术语=外查钥匙、根因=理解、对策=行动、最坏后果=排优先级、检查问题=可复用为清单、相关=扩展跳转。每个字段回答一个不同的问题，缺一个这条知识就断一环。
