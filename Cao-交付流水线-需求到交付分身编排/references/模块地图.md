# 模块地图（Module Map）——项目级框架表，挂在⑤立骨 / ⑥回写 / ⑫定稿

> **是什么**：一张项目级表格，回答"这个项目有哪几个模块、每个模块管什么、谁依赖谁、改 X 该去哪"。
> 它补的是卡级施工图盖不住的全局视野：每张卡知道自己动哪几个文件，但没人知道项目整体长什么样。
> **给谁用**：新接手的 AI 窗口读它定向（不必浏览全部代码）；主会话派遣时按图喂上下文；人改功能时按图找模块。
> 产出物：`<项目根>/docs/pipeline/模块地图.md`。与台账/state.json 同级，是项目导航资产。

## §1 三个维护时点（缺一就是断档）

| 时点 | 动作 | 产出 |
|---|---|---|
| **⑤切卡：首卡波次立骨架** | 从 PRD 功能列表 + 设计纪要推导模块划分意图（AI 起草→用户确认模块边界），每个卡头标【动到的模块】 | 骨架图（职责/依赖按意图填，定位可留空） |
| **⑥执行：每卡完成回写** | 卡的 DoD 链加一步：用真代码校准本卡动到的模块行（补定位/改依赖），随台账更新一起做 | 逐卡校准的活地图 |
| **⑫收尾：定稿校准** | 对照最终代码全表过一遍：定位逐条抽查、依赖重新核对、状态列定稿；记录校准 commit | 定稿地图（新窗口的第一读物） |

## §2 表模板（字段从使用场景反推：定向/派活/改功能各取所需）

```markdown
# 模块地图 · {项目名}
> 最后校准：{commit 或日期} · 校准人：{卡号/收尾} · 接手者先跑 §4 三步

| 模块 | 职责（一句话） | 关键定位（文件+标识符） | 实现的功能（PRD 编号） | 联动（调用↔被调） | 依赖（前置） | 设计要点 | 状态 |
|---|---|---|---|---|---|---|---|
| auth | 登录/会话/权限 | api/auth.py: login(); stores/auth.ts | F-3 | approval 读它鉴权 | — | HttpOnly cookie+内存会话 | ✅ |
| approval | 审批决议 | api/approvals.py: decide(); views/ApprovalDetailView.vue | F-5 | 调 rag 取制度依据 | auth, rag | 台账 append-only | 🔧 |

## 模块划分决策记录（为什么这么分——记决策，不记快照）
- 2026-10-11：rag 独立成模块而不塞进 approval——制度问答与审批归因共用语料（决策来源：设计纪要 §X）
```

字段取舍：**"设计要点"只写一句话 + 指向决策记录**；实现细节不进地图（代码自己会说话，地图只负责给"针"）。

## §3 防漂移五规则（违反任何一条 = 地图开始骗人，比没有更毒）

1. **禁行号**：定位一律写「文件路径 + 标识符」（函数/类/路由/表名）。行号是时点快照必漂——ADR 哲学同样适用于地图：**记决策与锚点，不记快照**。
2. **每卡完成必回写**（绑定铁律 10）：执行窗口的 DoD 链 = 回执 + 台账 + state.json + 任务板 + **地图回写**，缺地图回写不算过卡。回写只动本卡模块行，不重构全表。
3. **信任前先抽查**：新窗口接手时先抽 2 条定位验证（grep 标识符是否存在）——失效即触发重建，不许拿未校准的地图直接开工。地图头部"最后校准"就是为此存在的。
4. **小改顺手改，大改立专项**：卡内改动回写由执行卡顺手做；跨模块重构先在地图加"🔧 更改中+日期"标记，收口再摘。
5. **单字段语义**：状态列只用 ✅（与代码一致）/ 🔧（更改中+日期）/ ❓（未校准）三态——出现第五种解释就是该重建了。

## §4 新窗口接手三步（写进派遣提示词的标准动作）

1. 读模块地图（30 秒知道全局）；
2. 抽查本卡涉及模块的 2 条定位是否成立；
3. 成立 → 按图施工；不成立 → 先修图再干活（修图 diff 也算交付物）。

## §5 与 aoci 的关系（有现成体系就挂，不重造）

项目已建 **aoci 代码认知索引**（扫描生成、带指纹、能自动检测过期）时：模块地图**指向 aoci 作为活读数**，本文件只保留"模块级导航 + 决策记录"两层 aoci 覆盖不了的内容——避免同一信息两处手写（快照禁令：会自变的信息禁手写副本）。aoci 条目格式即「功能 / 相关代码 / 接口 / 备注」，与本表 §2 字段同构，可互相导出。无 aoci 的项目按 §2 模板手写最小版（先有骨架，收尾校准补齐）。

## §6 权威依据（检索 2026-10-11）

- **ADR（Architecture Decision Records）**：Martin Fowler / M. Nygard / Red Hat——架构文档记"决策+上下文+后果"，不记时点快照；快照必腐烂，决策长期有效。本文件 §2 决策记录节与 §3 规则 1 的依据。
- **Diagrams as Code（Structurizr/C4）**：图从单一模型生成而非手画，从机制上消灭图与代码的漂移。§5 挂 aoci（扫描+指纹）的依据。
- **预计算系统地图**（AI 代码库 onboarding 实践共识，2026）：把架构/模块边界/数据流预先算成机器可读地图，让 agent 每次会话不必重新推导全文代码；地图须配验证环（§4 抽查）防幻觉照抄。
- **Claude Code best practices（Anthropic）**：先 Explore→Plan 再 Implement；"describe what you want, Claude figures out how"——模块地图是给"Plan"供料的静态部分，每卡的动态部分仍靠现查（施工图"现状快照禁止只写死行号"与 §3 规则 1 同源）。
