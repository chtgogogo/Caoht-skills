# 模式判定（启动路由的判定依据）

> 主 skill 启动时：先查台账（断点恢复），无未完成项目则走本文件判定模式。
> **先给推荐+理由，再让用户拍板**——LLM 只推荐，决定权在用户。

## 四选项

| 模式 | 适用信号 | 走的步骤 |
|---|---|---|
| A 轻量 | 改 bug / 小功能 / 单文件改动 / 用户说"快改一下" | ①一句话磨需求→③一行 PRD→⑥执行卡→⑧台账→⑫收尾 |
| B 标准 | 新功能 / 新模块 / 用户说"做一个 XX"且范围可控 | ①磨设计→③PRD→⑤切卡→⑥派遣→⑧台账→⑩回看→⑫收尾 |
| C 企业 | 全新项目 / 多模块 / 多人或多分身协作 / 长周期 | 全十二步（含选型深选、卡库、双评审、总评审、工具箱外挂） |
| D 跳步优化 | **已有项目**：用户说"帮我优化 / 检查 / 升级"而非从零开发 | 见下 |

## 跳步优化（模式 D）执行法

1. 拿"十二步检查表"逐项扫描当前项目，问自己三个问题：
   - 这个环节的产出物存在吗？（如：有没有 CHANGELOG？有没有评测集？有没有台账？）
   - 存在的话质量如何？（评测数字新鲜吗？文档与代码一致吗？）
   - 有没有明显的低垂果实（一次小改动就能补的短板）？
2. 产出**缺口清单**（每项：缺什么 / 补了有什么好处 / 大约代价），按性价比排序给用户勾选；
3. 用户勾选的每项 → 按对应阶段的细则直接执行（不重走①②③）。

示例：对一个"有 README 无评测集、CHANGELOG 停更、文档与代码不同步"的项目，缺口清单可能是：
1. 建最小评测集（补量化验收能力，半天）；
2. 修文档与代码的 3 处不一致（防面试穿帮，1 小时）；
3. 补 CHANGELOG 迭代记录（展示工程素养，1 小时）。

## 提问模板（给用户的第一条消息）

> 查了台账，没有未完成的项目。基于你的描述（{复述用户意图}），我推荐走 **{X} 模式**，因为 {一句话理由}。
> 四个选项：
> - A 轻量（适合小改动）
> - B 标准（适合新功能）
> - C 企业（适合全新大项目）
> - D 跳步优化（适合已有项目只补短板——我会先扫出缺口清单给你勾选）
> 选哪个？也可以直接告诉我你的顾虑，我重新推荐。
