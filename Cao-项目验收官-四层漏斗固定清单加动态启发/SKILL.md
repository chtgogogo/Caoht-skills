# 项目验收官（四层漏斗 · 固定清单 + 动态启发）

> 一句话：像严苛的验收官一样给项目做全量体检——**固定清单保覆盖，动态启发挖暗坑，证据链保诚实**。
> 产出：一份落盘的《项目验收报告》，给出 通过 / 有条件通过 / 不通过 的结论，附最弱项与 Top3 行动计划。

---

## 0. 验收官四条军规（先读，凌驾于一切效率考量）

1. **只诊断，不修复**。验收过程中发现的问题一律记录进报告，禁止顺手改代码、改测试、改配置来"让验收变好看"。用户明确说"验收+修复"模式时除外，且每处修复同样要留证据。
2. **证据为王**。每条结论必须附证据：命令与退出码、`文件:行号` 引用、或落盘的测量输出（存到 `acceptance/evidence/`）。与 `A-Cao-测试纪律`（数字必须有落盘证据）和 `A-Cao-抗幻觉纪律`（事实/假设/未知分离）同源执行：测不出来的写「⬜未测」，不确定的写「未知」，禁止脑补数字。
3. **三禁（反作弊）**：禁止修改/删除测试、放宽阈值、缩小评测集来凑"通过"；禁止编造任何数字（一份编造数据的报告比没有报告更糟）；禁止把不适用的检查项硬测出结果——写「➖不适用」并给一句理由。
4. **非破坏 + 先报价**。不删数据、不压测生产/外部环境、不做不可逆操作；压测只打本地或测试环境。需要调付费 API（如跑评测集）时，先报预估消耗（题目数 × 轮数 × 单次 token），超过默认 5 万 token 预算须等用户确认。

## 1. 验收级别（用户没指定就用「标准」）

| 级别 | 范围 | 耗时 | 花 API 钱 |
|---|---|---|---|
| **快检** | Phase 0 + 第一层全量 + 各层里静态可查的动态项 + 报告 | 15–40 分钟 | 否 |
| **标准**（默认） | 快检 + 第二层本地实测 + 第三层（有评测集就跑）+ 3–5 个刁钻用例 + 第四层静态项与兜底触发实测 | 0.5–1.5 小时 | 可能 |
| **全量** | 标准 + 并发压测 + 稳定性 N 轮复跑 + 降级演练 + judge 人工对齐抽样 | 2 小时以上 | 会 |

- 用户可裁剪（如"只跑第一层"），裁剪范围必须写进报告元信息。
- 项目无法本地运行时：第二层及以下的"实测项"整体标 ⬜未测 并给原因，这不丢人；编数字才丢人。

## 2. 流程总览

```
Phase 0 项目画像 → 第一层（拦截） → 第二层（硬指标） → 第三层（AI质量）
        → 第四层（兜底闭环） → 生成报告 → 收尾沉淀
（每一层内部：固定清单全量核对 → 动态启发 → 层内判定）
```

### Phase 0 项目画像（必做，决定后面所有"适用性"）

1. 运行画像脚本：`python "<本skill目录>/scripts/profile_project.py" "<项目根目录>"`（纯标准库，输出 JSON 画像：语言/框架/项目类型猜测/工具链/红旗）。脚本报错或信息不足时，人工补查（看 manifests、入口文件、README）。
2. 读项目根的 `ACCEPTANCE.md`（若存在）：里面的红线值、评测集路径、验收范围、豁免项**优先于本 skill 默认值**。不存在则用内置默认红线（见 `references/scoring-and-verdicts.md`），收尾时为其生成一份草稿。
3. 明确三件事并写进报告：
   - **项目类型判定**（Web 服务 / CLI / 库 / Agent / RAG / 数据管道 / 前端…，可多选）+ 判定证据；
   - **验收范围**：全量，或增量（`git log` 找上次验收以来的变更，增量也要保第一层全量）；
   - **不适用项初判**：如非 AI 项目第三层整体 ➖；无用户体系则鉴权项 ➖。逐项给理由。
4. 若用户未指定级别，直接按「标准」开跑（自主执行，不要反复问）；唯一必须停下来等确认的是：付费评测超预算、或需要对生产/外部环境做任何操作。

## 3. 四层漏斗（每层动手前先读对应清单文件）

| 层 | 定位 | 判定 | 固定清单文件 |
|---|---|---|---|
| 一 · 基础工程 | **拦截级**：不过直接打回，不许进下一层 | 出现任何 ❌ → 报告结论即「不通过」 | `references/layer1-engineering.md` |
| 二 · 指标性能 | 硬指标：触红线记高危风险 | 触红线 → P0/P1 风险 + 优化方案 | `references/layer2-metrics.md` |
| 三 · AI 特有质量 | 灵魂：必须定量，拒绝主观 | 分数对比红线 + 稳定性 + 最弱项点名 | `references/layer3-ai-quality.md` |
| 四 · 业务兜底 | 闭环：看系统会不会自救 | 兜底链路必须**真实触发一次**验证 | `references/layer4-business.md` |

执行纪律：
- 固定清单**逐项核对、逐项给判定符号**，不许跳项（跳项 = 验收作废重来）。
- 每层做完固定清单后，必须做**动态启发**（方法论见 `references/heuristics-playbook.md`）：结合 Phase 0 画像，产出"清单上没写、但这个项目特有"的隐患，逐条编号（D-1、D-2…）并给 P0/P1/P2 分级。
- 第一层出现 ❌ 时：仍可继续往下层收集信息（报告更完整），但结论锁定「不通过」，且在报告中显式声明"按漏斗规则本应打回，以下内容仅供参考"。

## 4. 判定与分级（速查；完整规则见 `references/scoring-and-verdicts.md`）

**每个检查项五态判定**：

| 符号 | 含义 | 要求 |
|---|---|---|
| ✅ 通过 | 检查过且达标 | 附证据 |
| ❌ 未过 | 检查过且不达标 | 附证据 + 修法建议 |
| ⚠️ 风险 | 能用但有隐患 | 说明隐患与触发条件 |
| ⬜ 未测 | 本次没测成 | 写明原因 + 补测方法 |
| ➖ 不适用 | 该项目无此项 | 一句理由 |

**问题分级**：P0 = 上线即事故（数据丢失/安全洞/核心链路坏/评测污染）；P1 = 显著缺陷，上线前必须修；P2 = 改进项，进待办。

**结论映射（不许自由发挥）**：
- **不通过** = 第一层任何 ❌，或任何一层出现 P0；
- **有条件通过** = 无 P0 但有 P1（必须列明转「通过」的条件清单）；
- **通过** = 无 P0 无 P1（P2 允许，进待办）；
- **数据不足封顶**：关键项 ⬜ 太多（尤其第三层整体未跑）时，结论最高只能给「有条件通过」，并写明"因 XX 未测，无法给出通过结论"。

## 5. 报告输出（模板见 `references/report-template.md`，必须照模板落盘）

- 路径：`<项目根>/acceptance/ACCEPTANCE_REPORT_<YYYYMMDD>_<级别>.md`，另复制一份为 `acceptance/latest.md`；原始证据存 `acceptance/evidence/`。
- 报告九节：元信息 → 验收结论 → 核心指标数据（每格带口径与证据文件）→ 四层清单达标表 → 动态发现的风险 → 诚实暴露的弱点（最差 1–3 项，点名不藏拙）→ 能力缺口与未测项 → Top3 行动计划（具体到文件/函数）→ 历史对比（有上次报告时做趋势对比）。
- **不给虚假的综合总分**：权重会掩盖最弱项。用"分项达标表 + 最弱项点名"代替。
- 报告中数字一律标注测量口径（环境、轮数、温度、时间窗），无口径的数字视为无效。

## 6. 动态启发方法论（六步，详见 `references/heuristics-playbook.md`）

S1 画像打底（脚本+读码）→ S2 项目类型 playbook 匹配（每类项目一份已知坑清单）→ S3 风险维度扫描（并发/状态/外部依赖/不可逆操作/资金隐私/长时任务/权限/时区编码/配置密钥，逐维提问）→ S4 攻击者视角（"我要弄崩它、黑进它、骗过它，从哪下手"→ 每个想法变成一个用例）→ S5 上线前夜 pre-mortem（"假设明天就出事故，最可能是哪三件事"）→ S6 diff 驱动（git 变更影响面聚焦）。

第三层要求至少产出 **3–5 个刁钻动态用例**并真实执行：模糊输入、提示注入/越狱、超长上下文、边界值、恶意格式输入。执行结果如实记录（含"它扛住了"也是有效结论）。

**实证门槛（动态层的反幻觉铁律）**：启发产出先落为【假设 H-n】，假设不算发现——必须当场转化为最小探针跑出"证实/证伪"，证实才升级为【实证发现 D-n】；只有 D-n 参与结论映射与 P 分级，跑不动的假设进报告"假设区"（标补验方法，不给 P 级），证伪的进"排除区"防重猜。**动态层与固定清单同守证据纪律，不许变成新的幻觉源。**

**新死法回流（闭环）**：证实的 D-n 若是库里没有的新死法，过"已实证/通用型/非重复"三道质量门后回流——Agent/LLM 域按**七字段格式**（现象/术语/根因/对策/最坏后果/检查问题/相关）写进失败模式库 `01-failure-modes` 对应类别（编号接续、先查重、同步注册副本）；通用工程坑回踩坑日志；本机私有进 store PITFALL。详见 `references/heuristics-playbook.md` S7。

## 7. 收尾（每轮验收必做）

1. 项目根没有 `ACCEPTANCE.md` 时，**以 `references/ACCEPTANCE总装模板.md` 为底稿**复制生成草稿（A/B/C 三节按项目类型裁剪，D 节按本次验收发现的合理红线填好），供用户改定（红线一旦写入，下次验收以它为准）。
2. 知识回流（S7，按归属分家）：Agent/LLM 域的**新死法**过三道质量门（已实证/通用型/非重复）后按七字段格式回流失败模式库 `01-failure-modes`；通用工程坑 → 沉淀到踩坑日志（`A-Cao-踩坑日志`）；本机私有坑 → 记忆库 PITFALL。
3. 提醒用户按其铁律更新项目 CHANGELOG（若项目因本次验收要做修复）。
4. 增量验收时，把本次报告路径记入项目工作区，供下次历史对比。

## 8. 生态互认（不重复造轮子）

- 证据形态规范 → 执行时遵循 `A-Cao-测试纪律-测试证据形态规范`（testing-discipline）。
- 结论可证伪 → 遵循 `A-Cao-抗幻觉纪律-结论必须可证伪`（anti-hallucination-discipline）。
- 逐个 bug 的根因诊断 → 交给 `缺陷诊断`/`A-Cao-踩坑日志`，本 skill 只定位与分级，不深入修。
- 增量改动的小范围代码审查 → 可调 `代码审查-双轴PR改动审查`；本 skill 管全量体检。
- Agent 类项目：先拿 `Cao-失败模式与对策库` 七类死法对号入座（库→验收），验收发现的新死法再按 S7 七字段回流进库（验收→库），双向闭环。

## 9. 维护

- 本 skill 的版本与变更记录见同目录 `CHANGELOG.md`；优化后按"权威库 → C 盘注册副本 → lint 体检"流程同步，权威库永远保持最优版。
