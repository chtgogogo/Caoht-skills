# 第四层 · 业务与兜底验收（闭环级）

> 判定原则：验收不是只挑毛病，更要看系统**有没有自我修复的能力**。本层的灵魂是"真实触发一次"，代码里"有这个功能"不算数，要按一遍链路。
> 面向外部用户的服务的闭环项权重高于内部工具；个人毕设类项目允许闭环项 ⬜ 偏多，但必须写进能力缺口。

## A. 兜底链路（必须实测，不许只读代码）

**1. 答不上来的兜底**
- 怎么查：构造一个系统答不上来的输入，真实走一遍：是否触发工单/转人工/引导式降级话术？兜底后用户拿得到什么？
- 通过标准：真实触发成功且用户侧有明确交代；"静默编一个答案"或"裸报错" = P1（对外服务 P0）。

**2. badcase 回流闭环**
- 怎么查：①点赞点踩数据真的落库了吗（点一次查一次库）②能一键导出成下一轮评测候选吗（真的导出一条试试）③导出的题进了评测集后，下次回归会跑它吗。
- 通过标准：三步都通；断在哪一环，断点就是 P1。**反馈只收集不消费 = 反馈黑洞**。

**3. 边缘场景清单**
- 怎么查：结合动态启发（S3/S4）列出尚未覆盖的边缘场景，逐条标注风险等级（高=会出事故/中=体验受损/低=瑕疵）与"要不要现在补"。
- 通过标准：报告有清单且分级；"完全没想过边缘场景"本身记 ⚠️。

## B. 故障韧性（降级与容灾）

**4. 降级演练（全量级必做；标准级做静态确认）**
- 怎么查：把主依赖弄挂——本地模拟主模型 API 超时/断网（改 baseURL 到不存在的地址、或用 mock 拦截），看系统行为：优雅降级回复 / 明确报错+重试引导 / 裸栈崩溃？
- 通过标准：降级路径真实可走且对用户友好；"代码里有 try-except 但从未验证过它真的兜得住" = ⬜ 升级为全量必测项。

**5. 回滚方案**
- 怎么查：上一版本能否一键回退（git tag / 镜像版本 / 备份配置）？回滚步骤写下来了吗？回滚演练过吗？
- 通过标准：有方案且有记录；没演练过 = ⚠️（没演练过的回滚 = 没有回滚）。

**6. 备份与恢复**
- 怎么查：有备份机制吗（DB dump / 数据目录快照）？**恢复演练过吗**（从备份真恢复一次到测试环境）？
- 通过标准：备份存在 + 恢复验证过；只有备份没验证 = ⚠️；关键数据无备份 = P0。

## C. 可观测与运维（对外服务必备，个人项目按需降级 ➖/⬜）

**7. 监控告警（SRE PRR 核心项）**
- 怎么查：有指标采集吗（错误率/延迟/用量）？告警打给谁、多久能发现核心链路挂了？有看板吗？
- 通过标准：核心链路有至少一个"症状级"告警（用户已经受影响的信号），而不是只有"进程死了"这种原因级。
- 个人项目无监控 = ⚠️（记录为能力缺口）。

**8. 审计与追溯**
- 怎么查：出问题时能还原现场吗——关键请求有无日志/落库（谁、什么输入、什么输出、何时）？
- 通过标准：能从一次坏回答反查到当时的输入与中间过程（对 AI 应用尤其重要：没有轨迹日志就无法 debug badcase）。

**9. 运维手册（runbook）**
- 怎么查：常见故障（API 挂了/知识库异常/额度耗尽）的处理步骤写下来了吗？
- 通过标准：至少覆盖 Top3 可能故障；无 = ⚠️。

## D. 知识与内容治理（有知识库/内容生产的系统）

**10. 知识更新通道**
- 怎么查：知识库能不重新部署就更新吗（热更新）？加一条新知识的完整流程走一遍要多久？
- 通过标准：有明确流程且 ≤30 分钟走完一次更新；"改知识要改代码重新发版" = ⚠️。

**11. 过期知识清理**
- 怎么查：过期/失效知识有识别与清理机制吗？有 last_updated 元数据吗？
- 通过标准：有过期标记或定期审查机制；完全没有 = ⚠️（RAG 系统答旧不答新的根源）。

## E. 业务闭环的灵魂拷问（动态启发，报告里必须向用户提出 2–3 个）

结合项目实际，至少提出并尝试自答这些方向的问题：
1. **反馈黑洞检查**：用户提交的反馈/工单，谁看？多久响应？证据是什么（还是"应该有人看"）？
2. **迭代断点检查**：这次的 badcase，到下一次评测集更新之间隔几步手工活？步骤越多，闭环越容易断。
3. **承诺检查**：项目对外宣称的能力（README/简历/汇报里的数字），每一个都有落盘证据吗（与 P0-1 型"宣称与事实打架"交叉核对）？
4. **单人风险检查**：只有创建者一人能跑通部署/修复吗？文档能不能让第二个人接手？
