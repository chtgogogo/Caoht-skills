# 第五层 · 无障碍与包容性验收（按需专项层）

> 判定原则：本层**不拦截**（区别于第一层），但它把"能不能被用"从主观感受变成逐条可核对的客观项（WCAG 2.1 的 4 Principles × 13 Guidelines，A + AA 两级共约 50 条，AAA 按需）。
> 灵魂与第三层同源——**没有实测数值就没有结论**：看一眼 DOM 觉得"有 alt"不算 ✅，键盘没真按过不算 ✅。
> 启用条件：项目有面向人或对外的 UI（Web / H5 / App / 小程序 / 桌面）；纯后端、CLI、库、数据管道整层 ➖。
> 合规目标默认 **AA**；政务 / 医疗 / 公共教育 / 有明确法规要求或企业交付合同写了无障碍 → **AAA**（写进 ACCEPTANCE.md 后本层转为红线级，失败按 P 级正常参与结论）。

## 0. 先定三件事（写进报告元信息）

| 项 | 取值 | 说明 |
|---|---|---|
| 合规目标 | AA（默认）/ AAA / 仅 A | AAA 场景多一条额外要求（如 1.4.6 对比度 7:1、2.2.x 更严） |
| 审计范围 | 全量页面 / 核心链路 N 条 / 增量 diff 涉及页 | 快检级只做"核心链路 + A 级全项" |
| 审计模式 | 自动扫描 / 人工走查 / 两者 | **自动扫描只能覆盖约一半违规**（axe-core 官方口径），其余必须人工；只用自动结果下结论 = ⬜ 未测，不是 ✅ |

## 1. 四个最小探针（本层的"实测"就靠这四个）

**P-1 对比度算数值**（覆盖 1.4.3 / 1.4.6 / 1.4.11 / 1.4.1）
取前景色与背景色的 sRGB → 线性化 `c/255`，若 ≤0.03928 则 `c/12.92`，否则 `((c+0.055)/1.055)^2.4`；
相对亮度 `L = 0.2126R + 0.7152G + 0.0722B`；对比度 `= (L亮+0.05)/(L暗+0.05)`。
判定：正文 ≥4.5:1（AAA 7:1）、大字（≥18.66px 粗体或 ≥24px）≥3:1、UI 组件与图形 ≥3:1。
证据写法：`首页搜索按钮 文字#8A8A8A/底#FFF → 3.0:1，要求≥4.5 → ❌（截图 acceptance/evidence/contrast-search.png）`。

**P-2 键盘走查**（覆盖 2.1.1 / 2.1.2 / 2.4.3 / 2.4.7 / 2.4.1 / 3.2.1 / 3.2.2）
只用 Tab / Shift+Tab / Enter / Space / Esc 走完一条核心链路，记录：能不能走完、焦点顺序是否与视觉顺序一致、焦点是否可见（focus ring）、有没有被困在弹层里、跳页链接是否可达。
证据：逐步键位与结果（`Tab×6 → 焦点进入日期控件后 Shift+Tab 出不来 = 键盘陷阱 ❌ P1`）。

**P-3 辅助技术快照**（覆盖 1.1.1 / 1.3.1 / 2.4.2 / 2.4.6 / 3.3.2 / 4.1.2 / 4.1.3）
读浏览器可访问性树（DevTools Accessibility 面板 / a11y snapshot / `npx pa11y` / `@axe-core/cli` / Lighthouse a11y 类目），逐项确认：非文本有名称、结构用 h1-h6 与语义标签、每页 title 有描述性、表单控件有 label、动态状态消息有 `aria-live`。
Windows 手测用 NVDA（免费）；没装就标 ⬜ 并写补测方法，不许用"看起来有 aria-label"顶替。

**P-4 缩放与窄口**（覆盖 1.4.4 / 1.4.10 / 1.4.12 / 1.3.4）
文本放大 200% 与视口 320px 各截一次图：不得横向滚动、不得裁字、不得重叠；文字调整行距字距不破坏布局；不强制横屏。

## 2. A 级项（Level A，一律必测，任何一条 ❌ 即本层结论"未达 A"）

| 编号 | 要求 | 怎么查（探针） |
|---|---|---|
| 1.1.1 | 非文本内容等效文本 | P-3：img/button/icon 逐个看名称；装饰图应显式置空 |
| 1.2.1–1.2.3 | 音视频替代/字幕/描述 | 有媒体才测，否则 ➖（写"项目无媒体资源"）|
| 1.3.1 | 结构与关系可由代码确定 | P-3：标题层级、列表、表格 header、landmark |
| 1.3.2 | 呈现顺序即阅读顺序 | P-2 + 源码：DOM 顺序 vs 视觉顺序（不靠 CSS 重排救）|
| 1.3.3 | 不只靠形状/颜色/位置传达 | 找"点红色那个按钮""左侧列表"这类文案 |
| 1.4.1 | 不只靠颜色 | 错误态是否"红字 + 图标 + 文字"三重 |
| 1.4.2 | 自动播放音频可控 | 有自动播放才测 |
| 2.1.1 / 2.1.2 | 键盘可达 / 无陷阱 | P-2 全链路 |

| 3.2.1 / 3.2.2 | 聚焦不跳变 / 输入不自动提交 | P-2 + 表单一遍 |

## 3. AA 级项（合规目标 AA 起必测；AAA 场景再加 AAA 专条）

1.2.4 / 1.2.5 媒体描述 · 1.3.4 不锁屏幕方向 · **1.3.5 表单 autocomplete**（AA，勿误记为 A）· 1.4.3 对比度（P-1）· 1.4.4 放大 200% · 1.4.5 不用图片替文字 ·
**1.4.10 Reflow（320px 不横向滚动）** · **1.4.11 非文本对比度 ≥3:1** · 1.4.12 文字间距可调 · 1.4.13 hover/focus 内容可关可达持续 ·
2.4.5 多种定位方式 · 2.4.6 标题与标签清晰 · **2.4.7 焦点可见** ·
3.1.2 段落语言 · 3.2.3 / 3.2.4 导航与标识一致 · 3.3.3 错误修正建议 ·
**3.3.4 法律/财务/数据类不可逆操作可撤销·可校验·可确认**（AA）。
（加粗四项 + **4.1.3 状态消息可播报 `aria-live`** 是真实项目里最常翻车的，优先测；4.1.3 在 W3C WCAG 2.1 里是 **AAA**，市场插件那份清单把它标成 AA，照抄会错——AAA 目标场景必测，AA 场景记 ⚠️ 建议做。）

## 4. 本层 P 级映射（对齐 scoring-and-verdicts.md，不许自创分级）

| 情形 | 级别 | 理由 |
|---|---|---|
| 文档/README/交付材料宣称"符合 WCAG AA"而实测未达 | **P0** | 宣称与事实打架，属 P0 定义 |
| 3.3.4 失败且操作涉及资金/数据/不可逆提交（无确认或不可撤销） | **P0** | 上线即事故面 |
| A 级任一条 ❌（键盘不可达、无 alt、无标签、焦点陷阱） | **P1** | 核心链路对辅助技术用户即坏 |
| AA 级 ❌（对比度不足、无 focus ring、320px 横向滚动） | **P1**（对外/政务场景按红线处理） | 显著缺陷，上线前必修 |
| AAA 细节项、非核心页的同类问题 | **P2** | 改进项，进待办 |
| 只跑了自动扫描、人工项未做 | ⬜ 未测 | **禁止**因"axe 没报错"给 ✅ |

## 5. 结论（只用四档，禁止"基本符合"）

```
未达 A  = 任一 A 级 ❌
达 A    = A 级全 ✅，AA 有 ❌/⬜
达 AA   = A + AA 全 ✅ 且证据齐（数值/键位/快照路径）
达 AAA  = 上述 + AAA 专条全 ✅
不可判定 = 人工项大面积 ⬜ → 报告必须写 not-determined，禁止给等级
```
与全局结论的关系：本层 ❌ 不自动打回整个验收（不同于第一层）；但出现 P0 时按既有规则直接判「不通过」，出现 P1 时结论封顶「有条件通过」并写入转通过条件清单。

## 7. 专项动态启发（报告里必须问 2–3 个，走 D-n 实证流程）

- 假设一个**只用键盘**的人：这条链路他会在第几步彻底走不下去？（→ 当场变成一个 P-2 用例）
- 假设一个**屏幕阅读器用户**：这个"提交成功"他能感知到吗？（→ P-3 探针，`aria-live` 有没有）
- 假设在**强光下 / 单手持机 / 老年用户**：这块小灰字与 32px 热区扛得住吗？（→ P-1 + P-4）
- 动效与无障碍的交叉坑：`prefers-reduced-motion` 有没有尊重？自动轮播有没有暂停键？

> 来源与边界：清单结构取自 WCAG 2.1 官方 4 Principles × 13 Guidelines（50 条 A/AA，另 AAA 按需），2026-09-30 由市场插件 `product-design:access` 的清单化结构吸收而来，**判定纪律（五态、证据落盘、P 级映射、禁止自动扫描顶替）改为本库标准**——原插件的 finding 字段无证据槽，未采纳其判定段。
