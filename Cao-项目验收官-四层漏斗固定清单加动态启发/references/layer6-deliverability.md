# 第六层 · 用户可交付验收（有"给别人用"目标才启用）

> 判定原则：这一层的灵魂是"**交付物定义被一个真实的人验证过**"。测试全绿、指标达标都盖不住它——45 轮/725 测试全绿但目标用户不能用的教训（2026-09-30 业财单据中枢）就是本层存在的理由。
> 启用判定：Phase 0 画像时问"这个项目的产出是给谁用的"——有明确"给别人用"目标（团队/客户/开源用户）→ 启用；纯自用/学习项目 → 整层 ➖ 并注明。

## A. 交付物定义（没有定义=整层 P0）

**1. 交付物定义存在且可验证**
- 怎么查：项目台账/PRD/README 里找一句"谁用（具体角色）/怎么用（一次真实操作）/第一次交付长什么样"的可验证定义
- 通过标准：存在且一句话可判定真伪；不存在 = P0（验收无基准，一切"能用"都是开发者自说自话）

**2. 部署可达性（目标用户视角）**
- 怎么查：从零开始按项目自己的部署文档走一遍——命令条数、前置依赖、失败点；目标用户（非开发者）能否独立完成启动
- 通过标准：部署步骤≤项目自定义上限（自托管产品建议 ≤5 条命令）且每步可复制粘贴；文档里写"很简单"但实际 20 步 = ❌

**3. 使用手册存在且自足**
- 怎么查：手册是否覆盖核心动作全流程（含截图）；零项目上下文的新人能否按手册走通；术语是否有人话解释
- 通过标准：新人自读走通核心动作；手册引用"内部黑话"无解释 = ⚠️

## B. 核心动作真实操作验证（灵魂项，禁作弊）

**4. 目标用户人设端到端演练**
- 怎么查：以"不会敲命令的目标用户"人设走完交付物定义的核心动作——浏览器/界面真实点击（禁 API 直调、禁开发者知识补偿如手改数据库）；全程录屏或逐步截图
- 通过标准：核心动作全部完成且有证据；每处卡壳如实记录（卡壳清单+修复引用）；"我们演示过"不算——演示者=开发者时不算用户验证

**5. 错误路径的用户体验**
- 怎么查：人为制造 3 种用户会犯的错（传错格式/缺必填/重复提交）——用户看到的是人话+下一步指引，还是裸栈/英文堆栈？
- 通过标准：错误信息=人话+行动指引；裸异常直达用户 = P1

**6. 数据持久与恢复的用户交代**
- 怎么查：用户操作到一半重启/断电——数据还在吗？用户怎么知道数据在？
- 通过标准：重启后状态可恢复且用户可见（列表/状态/提示）；静默丢失 = P0

## C. 反馈闭环

**7. 用户反馈的采集通道**
- 怎么查：用户遇到问题怎么办——有反馈入口/联系方式/已知限制页吗？
- 通过标准：至少一条通道+已知限制公开（三段式：知道存在/为何不修/修法是什么）；"装了就失联" = ⚠️

## D. 首用理解与信任走查（"能用"之上的"可懂 / 可信 / 不冒犯"）

> 教训锚点（2026-10-11 业财单据中枢，真实 PM 首用六连批注）：默认域转嫁知识结构、内部检索分「相关度 113.8923」上屏、工单流转/权限三问无屏上交代、9 单样本对标行业均值、决议面板权重倒挂成侧边脚注、宽屏整屏无用途空白——**六条全部不是 bug**：功能全对、测试全绿、数字真实。这是与 A/B 节不同型的第二型缺陷：B 节测"动作能不能完成"，D 节测"能完成的人愿不愿用、敢不敢信"。
> 执行纪律：走查必须以"**第一次见面的业务人**"人设逐屏过——作者视角（知道实现）对这六类问题天然免疫（知识诅咒），禁止用开发者知识补偿理解；每屏问"一个不懂这个系统的人看到它会产生什么疑问？这个疑问在屏上有答案吗？"

**8. 内部结构不转嫁给用户（心智模型检查）**
- 怎么查：列出所有要求用户"先选 / 先懂"才能正确操作的界面元素——知识域 / 模块 / 分类树 / 环境 / 模式开关 / 内部 ID。逐个问：用户不看文档能选对吗？默认值是不是"最不会错"的那个？
- 通过标准：默认值 = 最不会错的选择（例：跨全部检索，而非锁死单个内部域），系统内部分类降为进阶选项 + 结果标注（命中后展示"来自 xx 域"）；默认逼用户先选内部结构项 = P1

**9. 内部原始值不上屏（数字可读检查）**
- 怎么查：grep 前端所有直接渲染的内部计算值——检索分数 / 置信度原始值 / token 数 / 耗时毫秒 / 内部状态码 / 原始 JSON（管理诊断视图除外）。逐个问：业务人能解读吗？有上界吗？跨查询可比吗？
- 通过标准：用户可见面上的数字要么有业务含义（百分比 / 金额 / 个数），要么转标签（"最匹配"）；BM25 / 余弦原始分等无上界、非百分比、跨查询不可比的值直接上屏 = P1；落库保留、仅从界面撤下不算丢证据

**10. 机制黑箱有屏上交代（去向透明检查）**
- 怎么查：对每个"提交后去哪了"的功能（工单 / 反馈 / 申诉 / 审批 / 异步任务），以首用人视角问四问：**流转到哪 / 谁处理 / 多久回 / 我能看到吗**——当前屏上有答案吗？管理类操作（密钥 / 重建 / 配置 / 清库）与普通操作是否视觉隔离？
- 通过标准：四问至少在屏上有一句话交代（哪怕答案是"演示版无流转，管理员就地处置"——如实说也算答案）；管理操作折叠或独立入口；管理密钥 / 口令输入框裸露在普通用户面板 = P1

**11. 小样本与对标诚实（指标可信检查）**
- 怎么查：所有与外部基准（行业均值 / 竞品 / 目标值）同屏的比率指标：分母多大？分母 <20 还做对标暗示吗？指标说明一行塞了几段信息（口径 / 来源 / 年份 / 厂商名）？
- 通过标准：小样本强制披露 n 或降为 "—"；说明默认一句话人话，口径与来源折叠进悬停提示；同屏多个比率指标的口径关系能一句话讲清，讲不清 = ⚠️

**12. 页面第一任务 = 首屏焦点（动线权重检查）**
- 怎么查：每个页面先写一句"这个页面的第一任务是什么"（详情页 = 拍板 / 列表页 = 找到 / 问答页 = 提问），再看首屏最大色块、最大按钮、标题层级落在哪里——两者一致吗？
- 通过标准：第一任务的入口 = 首屏视觉权重最高元素；最重要操作视觉权重 ≤ 次要信息或证据展示 = P1

**13. 宽屏空白有用途（布局比例检查）**
- 怎么查：≥1280px 视口逐屏走查：主内容两侧与下方的空白在干什么？窄栏居中 + 整屏空白 + 细长输入条 = 内容撑不起布局。
- 通过标准：空白被重排内容吃掉（侧栏 / 网格 / 铺开）或为刻意留白设计；正文行宽不超 ~70ch（**修比例 ≠ 拉宽正文**）；无用途整屏空白 = P2

## 判定联动

- 本层任何 P0（定义缺失/核心动作未验证/静默丢数据）→ 项目结论封顶「不通过」（对"给别人用"的项目）
- 手册缺失/部署超限 = P1 → 封顶「有条件通过」
- D 节六项问题全是"功能对、体验/信任错"，单条通常 P1/P2——但 **≥3 个 P1 = 报告必须加结论句「功能实现完整，但尚不可直接交付给非开发者用户」**，并进最弱项点名（2026-10-11 业单六连批注即为 6/6 全中的实例）
- 纯自用项目整层 ➖ 时，报告须记一句"若未来交付他人，本层全部项需补验"
