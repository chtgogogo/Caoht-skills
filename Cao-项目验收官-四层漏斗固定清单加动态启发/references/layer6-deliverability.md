# 第六层 · 用户可交付验收（有"给别人用"目标才启用）

> 判定原则：这一层的灵魂是"**交付物定义被一个真实的人验证过**"。测试全绿、指标达标都盖不住它——45 轮/725 测试全绿但目标用户不能用的教训（2026-09-30 业财单据中枢）就是本层存在的理由。
> 启用判定：Phase 0 画像时问"这个项目的产出是给谁用的"——有明确"给别人用"目标（团队/客户/开源用户）→ 启用；纯自用/学习项目 → 整层 ➖ 并注明。

## A. 交付物定义（没有定义=整层 P0）

**1. 交付物定义存在且可验证**
- 怎么查：项目台账/PRD/README 里找一句"谁用（具体角色）/怎么用（一次真实操作）/第一次交付长什么样"的可验证定义
- 通过标准：存在且一句话可判定真伪；不存在 = P0（验收无基准，一切"能用"都是开发者自说自话）

**2. 部署可达性（目标用户视角）**
- 怎么查：从零开始按项目自己的部署文档走一遍——命令条数、前置依赖、失败点；目标用户（非开发者）能否独立完成启动
- 通过标准：部署步骤≤项目自定义上限（自托管产品建议 ≤5 条命令）且每步可复制粘贴；文档里写"很简单"但实际 20 步 = ❌

**3. 使用手册存在且自足**
- 怎么查：手册是否覆盖核心动作全流程（含截图）；零项目上下文的新人能否按手册走通；术语是否有人话解释
- 通过标准：新人自读走通核心动作；手册引用"内部黑话"无解释 = ⚠️

## B. 核心动作真实操作验证（灵魂项，禁作弊）

**4. 目标用户人设端到端演练**
- 怎么查：以"不会敲命令的目标用户"人设走完交付物定义的核心动作——浏览器/界面真实点击（禁 API 直调、禁开发者知识补偿如手改数据库）；全程录屏或逐步截图
- 通过标准：核心动作全部完成且有证据；每处卡壳如实记录（卡壳清单+修复引用）；"我们演示过"不算——演示者=开发者时不算用户验证

**5. 错误路径的用户体验**
- 怎么查：人为制造 3 种用户会犯的错（传错格式/缺必填/重复提交）——用户看到的是人话+下一步指引，还是裸栈/英文堆栈？
- 通过标准：错误信息=人话+行动指引；裸异常直达用户 = P1

**6. 数据持久与恢复的用户交代**
- 怎么查：用户操作到一半重启/断电——数据还在吗？用户怎么知道数据在？
- 通过标准：重启后状态可恢复且用户可见（列表/状态/提示）；静默丢失 = P0

## C. 反馈闭环

**7. 用户反馈的采集通道**
- 怎么查：用户遇到问题怎么办——有反馈入口/联系方式/已知限制页吗？
- 通过标准：至少一条通道+已知限制公开（三段式：知道存在/为何不修/修法是什么）；"装了就失联" = ⚠️

## 判定联动

- 本层任何 P0（定义缺失/核心动作未验证/静默丢数据）→ 项目结论封顶「不通过」（对"给别人用"的项目）
- 手册缺失/部署超限 = P1 → 封顶「有条件通过」
- 纯自用项目整层 ➖ 时，报告须记一句"若未来交付他人，本层全部项需补验"
