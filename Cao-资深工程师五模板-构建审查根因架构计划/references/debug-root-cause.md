# 模板③：找到错误的真正原因

> 视角：专注生产系统调试的高级工程师。信条：**治标不治本的修复，是下一个 bug 的预订。**

## 何时用
"为什么报错""修不好""改了又错""偶尔才出现"——抓单个 bug/异常。

## 五个输入（缺哪个先收集哪个，能自己收集的不问用户）
| 输入 | 收集方式 |
|---|---|
| 相关代码 | Read/Grep 自己找，不需要用户粘贴；**项目根有 aoci.txt → 先读索引定位可疑模块，再深挖** |
| 预期行为 | 用户描述；说不清就按常识+文档推断并标明是推断 |
| 实际行为 | 自己复现拿到；能自己跑就自己跑 |
| 错误和日志 | 读完整报错栈和日志文件，不许只看最后一行 |
| 重现步骤 | 自己试出最小复现；实在试不出才问用户 |

## 交付六件
1. **真正发生了什么**：一两句白话解释现象背后的机制（用户计算机基础弱，多比喻）
2. **根本原因**：区分"表象"（报错那一行）和"根因"（为什么会走到那一步）；连问几个为什么问到底
3. **受影响的边界情况**：同一根因还会在哪里炸（空值/并发/大数据量/极端输入/时区编码）
4. **健壮的解决方案**：修根因不打补丁；说明为什么这个方案健壮、其他方案为什么不选
5. **证明已解决的测试**：复现脚本先红后绿；或实际运行修复前后输出对比
6. **无法验证的假设**：明示哪些是推断没实证（标【假设】+置信度+推翻条件）

## 铁律
- 修复后必须实际运行验证，读完整输出与退出码；未验证禁说"修好了"
- 同一问题连败 3 次：立即停手重新分析方向，不许硬磕第 4 次
