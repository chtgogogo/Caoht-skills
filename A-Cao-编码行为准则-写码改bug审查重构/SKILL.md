# 编码行为准则（任务专用）

> 触发原则：**宁多触发，勿少触发**。只要任务涉及任何「代码 / 编程 / 技术实现 / 系统设计」就触发，拿不准时一律触发。

## 触发范围（只要沾边就触发）

- **写/生成**：写代码、生成代码、写脚本、写函数、写 SQL、写配置、写接口
- **改/修**：改 bug、调试、报错、排查、修复、改功能、实现功能、新增功能
- **审/重构**：代码审查、review、评审、重构、refactor、优化
- **设计**：设计系统、技术框架、架构、代码结构、模块划分、数据库设计、接口设计、技术选型、方案设计
- **分析/答疑**：分析代码、解释代码、读代码、代码题目、编程题、算法题

> 一句话：**只要沾代码就触发**；日常纯闲聊、纯写作、纯翻译等不涉及代码的任务才跳过。

## 九条纪律（内联本体，换机自足）

1. **思考优先**：不确定先问，禁止猜了继续干；动手前先想清楚方案再落键；交付前列出所有不自信的点——结论分【事实/假设】并标置信度，证据不足写「未知」。
2. **极简**：只做明确要求的事，禁止预埋未来功能、禁止顺手大扫除。
3. **外科修改**：只改与任务直接相关的代码，不碰无关行，改动面最小化。
4. **目标驱动**：动手前先定可验证的成功标准（什么现象出现=做成了）。
5. **验证纪律**：声称完成前必须实际运行验证、读完整输出与退出码；未验证禁说"应该可以/修好了"；同一问题连败 3 次立即停下重新分析，不许硬磕。
6. **遇错先查坑**：遇到报错 / 反复失败 / 反常现象，**先检索踩坑日志**（skill `pitfall-log`，根目录 `D:\Deepseek-ALL\踩坑日志`）——先扫「根因索引表」看识别信号对不对得上，对得上就照通用对策试；不够再翻该根因下的案例找灵感。别一上来就自己硬想，也别重踩别人踩过的坑。
7. **证明优先**（对抗式审查 + 消融实验）：声称「修好了/更快了/更准了」之前先当自己的对手——假设这个改动是错的，主动找反例、跑边界、构造让它翻车的输入；效果类改进（性能/精度/召回）必须做消融：拆掉新加的零件重跑评测，分数掉了才证明零件值钱，没掉就删掉。检验：每句「有用/提升」后面都指得出可复现证据（Prove it, don't tell me）。
8. **溯源调试**（第一性原理）：修 bug 三连问，一问不过就不许动手写补丁——复现了吗（先造稳定复现步骤）→ 测试红了吗（先让测试失败）→ 根因是什么（连问三层为什么）；治根因不治症状，往旧结构上打补丁前先问「半年后会不会变成第二个 bug」。检验：bug 修复必附复现方法，说不出复现方法的修复视为未验证。
9. **结构自觉**（高内聚，低耦合）：一件事的代码住一起（内聚）；模块之间只走明面接口，不伸手进别人抽屉（耦合）；同一条常量/规则只许出现在一个文件里，其他地方一律 import（单一事实源）；动手前自问「改这个功能要动几个文件」——超过 3 个先停下画草图再决定。

## 执行

1. 按上面九条纪律执行任务（本文件自足，无需外部依赖）。
2. 需要更细的展开解释时，才读共享源 `D:\Deepseek-ALL\记忆规则\行为准则\编码行为准则.md`（缺失不影响本 skill 使用；共享源按铁律只读、停留在五纪律版，7–9 条以本文件为准）。
3. 简单任务（改错字 / 明显单行修改）可自行判断，不必走全部流程。
