# 模板②：分析并改进现有代码

> 视角：**刚加入一个陌生项目的资深工程师**——先看懂，再动刀。

## 何时用
用户甩来一段代码/一个项目说"帮我看看""分析一下""哪里有问题""帮我改进/重构"。

## 第 0 步：项目认知索引（有则必读；没有先判定要不要建）
- 项目根有 `aoci.txt`（AOCI 认知索引）→ **先读索引再碰代码**：架构、组件职责、数据流的大骨架直接就有了，再带着索引去读代码验证细节。索引与代码冲突时以代码为准（索引可能滞后）。
- 没有 `aoci.txt` → 跑 `py E:\Zcode-memory\tools\aoci_fit.py <项目路径>` 判定：
  - **AUTO**（大工程+反复开发）→ 直接 init+scan 建索引再干活，完成后告知用户
  - **ASK**（单信号）→ 弹窗（AskUserQuestion）问用户建不建，等答复
  - **SKIP**（小项目）→ 照常 Read/Grep 从零看懂

## 阶段一：分析七问（逐项作答，用实际读到的证据）
1. 架构是如何组织的（分层？单文件？入口在哪）
2. 主要组件是什么（模块/类/函数，各自负责什么）
3. 数据是如何流通的（从输入到存储到输出，理出一条主线）
4. 哪些代码是重复的（可抽公共函数/组件）
5. 存在哪些结构问题（耦合/职责不清/循环依赖）
6. 有哪些性能问题（N+1 查询/循环里做重活/无缓存/重复 IO）
7. 存在哪些维护风险（无测试/硬编码/魔法数字/过期依赖）

**纪律**：必须用 Read/Grep 实际读完相关代码再下结论，禁止凭文件名猜。

## 阶段二：交付五件
1. **架构总结**：3-5 句话说清项目是干嘛的、怎么组织的
2. **按优先级排序的问题**：P0 崩溃/丢数据 → P1 功能错 → P2 性能/结构 → P3 风格；每条带证据（文件:行号）
3. **重构计划**：先修哪些后修哪些，每步能否独立验证
4. **改进后的代码**：外科修改，只动与问题直接相关的行，不顺手大扫除
5. **证明行为不变的测试**：改之前先跑通记录现有行为，改之后复跑对比，证明没改坏

## 关键纪律
- 用户当前诉求是"看懂自己的代码"（求职冲刺期）：解释要通俗、多比喻，重点讲"为什么这么写、为什么有问题"，不是只丢术语
- 大重构先给计划让用户拍板再动刀，不一次性推倒重来
