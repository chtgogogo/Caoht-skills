# 资深工程师五模板（senior-engineer-playbook）

> 一句话：给 5 种高频工程任务各配一套「固定视角 + 固定交付清单」，保证产出不缺项、不跑偏。原版是给人复制粘贴的提示词，本 skill 已转成 ZCode 直接执行的工作流——触发后不是念模板，而是按模板的清单干活。

## 第一步：对号入座（选模板）

| 用户场景（听上去像） | 模板 | 读这个文件 |
|---|---|---|
| "帮我做一个……应用/网站/工具/项目" | ①构建 | references/build-app.md |
| "分析这段代码/这个项目，哪里有问题，帮我改进" | ②审查 | references/review-code.md |
| "为什么报错 / 修不好 / 又出问题了" | ③根因 | references/debug-root-cause.md |
| "设计一个系统/架构，要能扛……用户" | ④架构 | references/design-architecture.md |
| "我有个想法，帮我规划一下 / 能不能做" | ⑤计划 | references/idea-to-plan.md |

- 命中几个场景就读几个文件；只命中一个就只读一个，省上下文。
- 拿不准②还是③：用户要"整体分析改进"走②，抓"某一个 bug"走③。
- 五个模板可串联成完整生命周期：⑤想法 → ①构建 → ③调试 → ②审查。

## 通用交付纪律（所有模板生效前先读）

1. **coding-behavior 照守**：本 skill 与编码五纪律叠加，五纪律（思考优先/极简/外科修改/目标驱动/验证纪律）一条不少。
2. **缺信息先问的边界**：只有"缺了会白干"的重要信息才问（如：给谁用、数据要不要存、部署到哪）；无关紧要的选型自己定，说一句理由就开工，不反问用户。
3. **数字不脑补**：凡 [数字]/[数据] 占位，用户没给就标"未知"，给分档方案，禁止编造精确值。
4. **验证纪律落地**：交付"完整实现/测试/修复"类产物，必须实际跑通再声称完成；写明无法验证的假设。
5. **磁盘红线**：新项目一律建在非系统盘（默认 E:\Zcode-work\ 下按项目建目录）；大文件写入前先查目标盘剩余空间。
6. **不讨好**：想法有缺陷、方案有坑，直说 + 给解法；绝不为让用户开心而弱化问题。

## 交付自检（收尾过一遍）

- [ ] 对应模板的交付清单逐项齐了（真不需要的项注明为什么省略）
- [ ] 代码类产物实际运行验证过，读了完整输出与退出码
- [ ] 占位数字没有编造，未知项已标明
- [ ] 没有预埋用户没要的功能
