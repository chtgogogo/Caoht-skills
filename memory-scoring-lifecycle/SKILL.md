# 记忆纪律（自包含入口）

> 规则正文 **v3.5**（2026-09-01）；入口封装 **v4.1-sc3.2**。版本号只在 frontmatter 维护（唯一版本源）；沿革逐条见同目录 ../修订记录/A-Cao-记忆纪律-跨会话存整召评分衰减升华.md。
> 启发词：`【记忆纪律 v3.1】`——固定的入口引导卡名，不随规则版本变动。
> **自包含承诺：单凭本文件可执行全部核心流程。** 完整规则源 `<你的共享层>\记忆规则\`（00–12）与 `references/详解手册.md`（调参与溯源）均为扩展阅读，冲突时以本文件为准。

## 0. 通用性约定（解耦原则）

1. **规则共享一份，store 各自建**：规则里不写死任何宿主路径/盘符；store 根看宿主 `AGENTS.md`/`MEMORY.md` 或环境变量，没有就按 §1 在非系统盘新建。
2. **常驻卡放宿主真正注入的文件**：宿主注入面不止一处时用 `resident-manifest.json`（§0.7）登记，禁止两份各写一套。
3. **工具各自复制**：`tools/` 的召回/整理/取号三件复制到 store `tools/` 同目录；缺脚本按 §9.2 手工降级。
4. **双副本同步**：注册副本与权威库逐字一致；store 版若比包内多能力，先反查（`--dedup` 等），再决定回流/覆盖。
5. **本机事实进 `personal.local.md`**：盘符、宿主名、路径只写这里；不存在就按通用写法执行，缺文件不报错。

## 0.7 第一次拿到本 skill：自适配 → 自排查 → 自修

> 新 Agent 只拿到本文件时按这节走；先发现，不先问路径。

### A. 自适配（先找事实，再建结构）

1. **找 store 根**：读宿主 `AGENTS.md`/`MEMORY.md` 里的 `MEMORY_ROOT`；没有就按 §1 新建。
2. **找常驻面**：列出宿主实际注入的文件，写 `resident-manifest.json`：
   ```json
   {"schema":1,"host":"<host>","files":[{"path":"...","scope":"global|project|store-card|shared-core|shared-l1|skill","budget_bytes":10240}],"skill_version_source":"SKILL.md","card_source":"MEMORY.md","resident_pointer":"AGENTS.md","aliases":{"别名":"路径"},"moved":[{"id":"...","path":"...","trigger":"...","pointer":"..."}]}
   ```
3. **找工具**：store `tools/` 是否有 recall/organize/next_id；缺哪个按 §9.2 降级。本包自检：`py tools/skill_selfcheck.py`（有宿主 manifest 时加 `--manifest`）。
4. **写个人适配层**：本机盘符、宿主名、路径写进 `personal.local.md`。

### B. 自排查（先机械项，再语义判断）

| 症状 | 先查 | 处置 |
|---|---|---|
| 版本对不上 | SKILL frontmatter / 修订记录 / 宿主指针 | 以 frontmatter 为单源；三处互证，不同步报红 |
| 常驻层变胖 | manifest `budget_bytes` + 实际字节 | 超了先移出，不加新规则 |
| 两份常驻打架 | 逐字重复/版本/「注入/不注入」声明 | 留一处，另一处改指针 |
| 工具副本漂移 | recall/organize 与权威源 md5 | 先反查 store 版是否带私有开关（§0 第 4 条），再决定回流/覆盖 |
| 改了文件没生效 | 宿主是否要新会话/重注入 | 记录「需新会话」；当前会话旧基线不算验收 |
| 不知道注入了哪份 | 宿主 session/log 能否解出实际消息 | 能解→对比 manifest；不能解→标「未验证」，不许报绿 |
| manifest 缺失/字段不全 | A2 的 files/路径/别名 | 先建 manifest；路径/别名校准后再跑 gate |
| 宿主自带记忆也在写 | 宿主原生注入/自动写入/内置库 | 按 `references/宿主原生记忆接管审计.md` 判三类障碍；先迁后下闸 |

### C. 自修（顺序不可反）

**备份/冻结 → 移出（三件套：路径+触发词+一行指针，缺一不迁）→ 加新规则 → 跑 gate（没有就按 B 表手工）→ 新会话取注入证据 → 记账/更新系统状态。**

### D. 三态出口

- **绿**：机械项全过 + 有注入证据；
- **黄**：机械项过、注入证据缺失/宿主不支持 → 明写「未验证」；
- **红/blocked**：版本/预算/声明冲突未修 → 不许说「已优化」。

### E. 宿主适配

每个宿主在自己的 `resident-manifest.json` 里声明注入面；manifest 是部署实例，不进 `PAIRS` md5，由 gate + git 备份管。

## 1. store 结构（CORE + 七库）

```
<store根>/
├── CORE.md        ← L0 核心层：每次会话全读，硬上限 150 行（画像摘要+路由表+铁律）
├── PROFILE/       ← L1 画像：用户是谁、偏好、红线        [pinned 永久]
├── WORK/          ← L2 工作：做了什么、做到哪、卡在哪    [fast 7天]
├── DETAIL/        ← L3 细节：事实、参数、环境、非显然结论 [normal 14天]
├── PITFALL/       ← L4 踩坑：症状→根因→解法→验证        [slow 30天]
├── REJECTED/      ← L5 否决：试过证明不行（负知识，高价值）[slow 30天]
├── DECISION/      ← L6 决策：为什么选 A 不选 B           [pinned 永久]
├── TRASH/         ← 确认无用待清理
└── FORGOTTEN/     ← V≤0 归档（索引保留，正文压 1-2 行）
```
每库一个 `index.md`，**一行一条**（上限 80 行/60 条，超了拆子索引）。

## 2. 写入闸门：三记五不记

**三记**（满足任一才写）：
1. 得出了**非显然**结论（模型本来不知道、要推理/调查才得到的）；
2. 用户显式要求记（"记住这个"）；
3. 失败 ≥2 次才解决的问题。

**五不记**：
1. 模型本来就知道的通用知识（记=污染）；
2. 一次性临时信息（"帮我算 23×47"）；
3. 未验证的猜测（可暂存但必须标 `[推测]`，验证后才转正）；
4. 与已有记忆重复（**加固旧记录，不新建**）；
5. 用户随口一提没下文、且 V < 5。

**时机**：对话进行中只做心里标记，段落结束/结论落定再写。判据：**这个结论三个月后还会用到吗？**

## 3. 双轨评分（V + R）

**固有分 V**（0-100，落盘，会衰减），初始分按量表打，不凭感觉：
```
V = 5（基础）
  + 影响范围：本次对话 0 / 单项目 10 / 跨项目通用 20
  + 复发性　：一次性 0 / 可能再遇 5 / 反复遇到 15
  + 获取成本：随手可得 0 / 查了才知道 5 / 踩坑才得到 15
  + 稀缺性　：模型本来就知道 0 / 只有这里才知道 10
  + 用户显式强调（"记住/重要/别忘了"）20
```
V 分层含义：80+ 铁律级（应已升华）｜50-79 核心知识｜20-49 稳定有用｜10-19 边缘｜1-9 垂死｜≤0 归档 FORGOTTEN。

**情境分 R**（0-10，每次检索临时算，**不落盘**）：
```
R = 相关性（触发词精确命中 6 / 语义相关 3 / 弱相关 1）
  + 新近性（7 天内命中过 4 / 30 天内 2 / 更早 0）
```

**排序分 = (V/10) × 0.6 + R × 0.4**　（V 保基本盘，R 让"此刻恰好相关的冷门记忆"翻上来。）

**关键加扣分**（命中除加分，同时 `strength+1`，上限 10）：

| 事件 | V | 附加 |
|---|---|---|
| 检索命中且真用上 | +2 | 重置衰减计时 |
| 用户主动提起 | +3 | 重置衰减计时 |
| 用户确认有用 | +5 | — |
| **用户纠正**（"不对，应该是X"） | **+8** | **强制改写内容**（最强信号） |
| 同类再现（N≥2） | +5 | **不新建，追加证据** |
| 被证伪/过期 | -50 | 转 superseded 或 REJECTED |

**惰性衰减（读时结算，零进程）**：`应扣 = 周期数 × (1 + ⌊V/25⌋)`；`实际周期 = TTL档 × (1 + strength/10)`——被反复想起的记忆衰减变慢（间隔重复）。

**排序与实现同源**：召回器用的**就是上面这条公式**，不自带第二套权重。四条落地口径：
- **V 未登记 ⇒ 按 0 计**，入选原因明写 V 来源（正文 `score` / 索引「分」列 / 未登记）；工具不得凭感觉补基线分（补分＝掩盖未评分）；
- `draft` 检索降权 50%（§8 模板注释），`superseded` / `archived` **不参与排序**（排序前就被 §4 第②道工序剔除）；
- **同分 tie-break 固定**：排序分降序 → 日期新→旧 → 正文路径字典序升序 ⇒ 同一 store、同一查询连跑两次，Top-K 逐字一致（可机械复核的性质）；
- 每条结果**必须输出入选原因**（相关性分档 + 命中词 + V 来源 + 新近度 + 状态）——无原因＝不可采信。

## 4. 检索协议（渐进披露 + 硬预算）

**绝不一次性读完任何库**（唯一例外 CORE.md）。流程：
```
CORE.md（含路由表 ≤30 行）→ 路由直达 1 个分区 index → 挑 ≤3 条
→ 只读 frontmatter + 「一句话结论」（~20 行/条）→ 挑 1 条 → 读全文
```
**硬预算**：寻址 ≤800 + 展开 ≤1200 + **总计 ≤2000 token**；超了强制停，并告知用户"可能有遗漏"。
省 token 三招：单 index >60 条拆子索引；同会话已读条目不重读；先读头部不够再下探。
**路由表**（CORE.md 内 ≤30 行）：触发词 → 分区 index 或热记忆直达文件；V≥50 加直达项，V≥80/升华结论直接进铁律区，V<30 移除。
**触发词按需分层（冷启动不硬凑，防写到第 50 条开始敷衍）**：
- **现象词必填**（2-5 个）：用户会怎么口头描述，用原话别用术语——**召回主力**；
- **排除词按需**：已发生过误触发才加，不预防性堆砌；
- **实体词尽量填**：真实文件/函数/表名，供精确匹配；
- **本质词 = RT 号**（有根因的坑类记录才填，见 §7）——受控词表替代自由发挥，不同人/不同 agent 填出的粒度才一致。

### 4.1 先过滤，再排序（硬工序，顺序不许颠倒）

**工序颠倒＝把"没有合适记忆"伪装成"召回了"**（pit 族事故：旧版 Top-K 混入已删/过期/零重合条目且退 0）。召回必须按固定顺序过六道工序，每道单独计数并在报告里给出「进入 N → 出局 M（按原因）」：

| 序 | 工序 | 出局条件 | 为什么要单列 |
|---|---|---|---|
| ① | 权限范围 | 解析后落在 store 根之外；`archive`/`TRASH`/`FORGOTTEN`/`tools` 目录（默认排除，`--include-archived` 才纳入） | 越界行会把别人的记忆当本 agent 的记忆注入 |
| ② | 有效状态 | `superseded` / `archived`；`draft` 不出局但降权 50% | 已被替代的结论是**负知识**，用一次就错一次 |
| ③ | 未过期 | `valid_until` 早于今天 | 限期记忆到期即失效，§5「失效处理」要求旧条标注而非删除，靠的就是这道闸 |
| ④ | 文件存在 | 索引行在、正文文件没了（断链） | 旧版只降权不丢弃 ⇒ 召回报"有这条"，读者按路径去开才扑空 |
| ⑤ | 相关性门槛 | 相关性分档 < `--min-rel`（默认 3） | 门槛在前、排序在后，Top-K 里不存在"顺便塞进来的无关条目" |
| ⑥ | 排序 | 按 §3 公式排，取前 K | — |

**⑤ 相关性门槛按「去重后的查询片段数」计，不按命中次数**：分档 = 触发词整词入句 6 / ≥3 个不同片段落在触发词 6 / ≥2 个片段 3 / 只有 1 个片段 1。同一偶然重合在触发词列和正文各撞一次，按**次数**数会凑成 2 个信号，把零相关抬成"语义相关"——门槛就此形同虚设。语料读两遍：第一遍只吃索引；过门槛的不足 K 条时才补读候选池正文（triggers / title / 一句话结论），否则"触发词只写在正文里"的真库会被漏召回。

**检索字段必须同步进索引**（这是 §8 索引行的存在理由）：命中判定先吃索引语料，索引里没有「状态 / 有效期 / 分 / 日期」时，工具只能对候选池逐条开正文（每份 ≤1600 字节、封顶 `top×3` 份）。**代价是线性的**：库越大越贵，且日期缺列时排序拿不到新近度。整理器会把每库的字段齐备度作为一节报出来，缺哪列补哪列。

### 4.2 三态出口（不许用无关结果冒充成功召回）

| 状态 | 含义 | 退出码 |
|---|---|---|
| `state=matched` | 至少一条过了全部六道工序 | 0 |
| `state=no_match` | 索引读到了，但没有一条过相关性门槛（**本次没有合适记忆，不是故障**） | 1 |
| `state=index_error` | 索引找不到 / 一行都解析不出而库里却有正文 / 索引文件读不了 ⇒ **本报告不可采信** | 3 |
| `state=tool_error` | 工具自身异常 ⇒ 绝不复用 1，否则"崩了"被读成"库里没有相关记忆" | 4 |
| 参数错误 | 未知参数 / 缺参数值（绝不静默改用别的目录） | 2 |

三条判据：**退 3 时"没召回"推不出"库里没有"**；`--dedup` 类开关不参与判定；状态同时写进人读的那一行**和 stderr**——调用方只看其中一路也不会漏判。

## 5. ⚠️ Probe 纪律

**原则：记忆落笔那一刻，应该是"核实过、可执行"的，而不是"看起来像对的"。**

- **写前 probe**：
  1. **先占号再写正文**——跑 `py tools/next_id.py <store根> <库名> --claim`，用 `O_CREAT|O_EXCL` **原子登记**号位到 `<store根>/.id_claims/<号>.claim` 再报号。占用集合 = **文件系统 ∪ 索引登记 ∪ 占号登记** 三者取并集，任一维度有的号都跳过；`--claim` 抢不到就顺延（顺延 >50 次退 5）。四步写流程：
     ① `--claim` 拿号（退出码非 0 先处理，别按报出的号落盘）→ ② 写正文 `<id>.md` → ③ 往该库 `index.md` 追加一行 → ④ 复跑只读查询，确认 `next` 已前进。
     🔴 **占号文件永不删除**：它代表"这个号已经发出去了"。后来正文没写，代价只是一个号被跳过（无害）；删掉它，代价是下一次撞车（有害）。不带 `--claim` 时取号器一个字节都不写。**手工编辑索引的并发不在本工具加锁范围内**，防撞靠"先占号"这一条消除 ID 维度的撞车。
  2. **环境类记忆写入前实地核实**——路径/版本/配置类信息，先 ls/查证一次再落笔；
  3. **指针必须自带降级路径**——引用外部文件时必须同时内嵌"指针失效时按什么执行"。裸指针 = 记忆里的悬空引用。
- **用前 probe**：引用记忆里的路径/数字/他人维护文档的口径之前，花一次工具调用核实仍然成立。
- **值不值得 probe**：易漂移的（路径、数字、版本号、别人维护的文件）必核；稳定事实（用户偏好、红线、决策理由）不核。
- **probe 预算**：每条 ≤1 次工具调用；不得借"核实"之名突破 §4 检索预算。
- **失效处理**：发现记忆过期 → 旧条标 `superseded` 不删除 + 写修正版；用户纠正按 +8 强制改写。

## 6. 兄弟 skill：pitfall-log（踩坑日志）——互认与边界

- **它是什么**：跨 agent 共享的踩坑沉淀库（根因层+案例层，根因优先检索）。本机 log-root 见 `personal.local.md`；skill 已注册本机（`pitfall-log`）可直接调度；**skill 不可用时直接读其入口索引文件，功能不中断**。
- **何时去查**：遇到报错 / 反复失败 / 难修 bug，先查本 store PITFALL 库；没命中再去踩坑日志扫「根因索引表」。**反复出现 / 连败 3 次的 bug，动手前强制翻一次踩坑日志找灵感。**
- **边界（不重复存储）**：通用 / 跨工具坑的正文记踩坑日志（共享单一事实源）；仅本 agent 环境私有的坑正文记本 store PITFALL；交叉相关时另一方只放一行指针（含根因号/日期），不复制正文。
- **升华回流**：踩坑日志某根因 / 案例 hits≥3 → 按其升华流程写进本 CORE 铁律区（来源注 RT-xxx）。

## 7. 冲突与升华

**冲突不删除，只失效**：同主题 + 关键词重合 >60% + 结论方向相反 = 矛盾 → 旧条 `status: superseded` + `valid_until` + `superseded_by` 反向指回；检索只返回 `active`。
**双向写入**：新证据回头修订旧记忆（矛盾→改结论句 V+8；互补→补边界 V+5；新证据→追加 V+5 不新建）。

**升华**（三级形态：用得越多，变成加载成本越低的形态）：
- **同型判定用受控词表**：每条坑类记忆的 `root_cause_signature` 格式 = **`RT-xxx|一句话短语`**（如 `RT-003|静默失败未查退出码`）；**判同型 = RT 号相同**（`|` 后短语仅供人读，不参与判定）。RT 词表 = 踩坑日志 `roots\` 的受控根因目录（RT-001 起，`_template.md` 可扩新）；旧条无 RT 号不强制回填，归不进现有 RT 的写 `RT-new|短语`，体检时沉淀为新 RT 文件。
- 触发（任一）：**同 RT 号**的坑累计 **≥7 条** / 某条 V ≥ 80 / 用户说"写成规则"。
- 路径：原始记录（≤120 行）→ index 摘要行（命中 ≥2 次时写）→ **铁律 1-2 行进 CORE**（零检索成本，停衰减，转 `pinned`）。
- 产物格式：一句话规则 + 关键约束 + 反例 + 来源指针（pit-xxx 等）。
- **谁来数**：分组计数交给整理器，不靠 agent 的印象——`memory_organize.py` 的「同根因聚合」节按 RT 号分组，输出 `达标 N 组 / 未达标 M 组 / 待沉淀 RT-new K 组 / 无 RT 号 J 条`，达标组逐条列出**成员号 + 日期跨度 + §7 产物草稿 + CORE 铁律行草稿**，未达标组明写「还差 x 条」（阈值是不是活的，一眼可查）。
  - `RT-new|短语` **不并入任何现有组**（归不进受控词表的先当新根因，体检时沉淀成 RT 文件后再合流）；
  - 🔴 **只报候选，不自动升华、不改正文**：升华是语义判断，脚本给的是"够条件了"，不是"该升了"；
  - 计数、衰减、归档这些"必须每次一样"的机械量由工具维护；agent 只负责判断与落笔。

## 8. 记录模板（自包含版）

```markdown
---
id: pit-003          # 类型前缀+号：pro/work/det/pit/rej/dec
type: pitfall        # profile|work|detail|pitfall|rejected|decision
title: <一句话标题>
triggers: [现象词(必填)..., 实体词..., RT号...]   # 见 §4：现象词必填，实体词尽量填
root_cause_signature: RT-xxx|一句话短语            # 坑类必填，判同型=RT号相同（§7）
exclude: [误触发词...]
score: 45            # V，按 §3 量表
strength: 0          # 0-10，命中+1
ttl: slow            # pinned|slow|normal|fast
created: 2026-09-23
last_hit: 2026-09-23
valid_until: null    # 非空=已失效（不删除）
status: draft        # draft(检索降权50%,第2次命中转正)|active|superseded|promoted|archived
superseded_by: null
promoted_to: null
links: []            # 相关记忆 id
evidence: 1
confidence: high     # high|medium|low（低=标[推测]）
---
## 一句话结论        ← 必须放最前（性能设计：先读 20 行就能决策）
## 适用边界          ← ✅ 什么情况适用 / ❌ 什么情况不适用
## 本质（根因/规律）
## 细节（完整过程、数据、判断依据）
## 证据链
```

**index 行格式**：`| ID | 触发词 | 一句话结论 | 分 | 状态 |`（缺省位置式）。三件工具共用**同一个索引解析器**（`memory_recall.parse_index`，整理器与取号器 import 它——两把尺子各量一遍是 pit-001 同族事故），解析口径：
- **列按表头映射，与列序无关**：`触发词/结论/分/状态/日期/有效期/RT/排除/类型/路径/编号` 各认各的表头名；**没有表头时才退回位置式默认**。⇒ 想加「日期 / 有效期 / RT 号」三列就加，不用重排既有列；
- **两种体都认**：ID 表体（`| pit-001 | … |`）与链接体（一行以 `- [标题]` 开头，紧跟圆括号包着该条详情文件的相对路径，再 ` · 类型 · 日期 — 钩子`）可混排在同一库；多段 ID（`pit-a-001`）也认（旧版会静默丢行）；
- **认不出行号的行不许当可删行**：整理器 `--apply` 遇到"解析出记录但定位不回原文行号"时，列入「宁可不删」清单并明写，绝不按近似行号删；
- 🔴 **一行一条记忆，索引与正文必须同步写**：只写正文不登记 index ⇒ 取号器报「有正文却没登记」（黄），只删 index 不删正文 ⇒ 留成孤儿（整理器 WARN），正文删了 index 没动 ⇒ 断链（FAIL，`--apply` 可自动移除该行）。

**CORE.md 结构**：用户画像摘要（≤5 行）→ 铁律区（R-xxx 永久不衰减）→ 路由表（≤30 行）→ 系统状态（≤8 行，只留指针）。

## 9. 收尾与体检

- **收尾 A（每场必做）**：读 `ledger.md` 尾 10 行；@本家/@全体未销号→处理+销号≤120 字；**无 @ 事项=零登记**，不写"已阅"。**B（条件触发）**：写过 store/共享层 → `memory_maintain.py check --write-health` + 更新系统状态；每日首场/改共享件 → `patrol_check`；用过 LLMwiki 卡 → `kb_track`。
- **预算红线**：常驻卡 ≤2 KB/宿主；L1 ≤16 KB；skill 正文 ≤35 KB；准铁律 ≤8 条；账本 ≤120 行、单条 ≤400 B；90 天零触发 → 季度复核降级。预算巡检由 store 的 `patrol_check.py` 实测，不靠自觉。
- **定期体检（10 次会话/30 天）**：脚本项=`memory_organize`（断链/孤儿/重复/容量/冷记忆/同型/字段齐备/分数漂移/状态/衰减）；AI 项=冲突检测 + 3 条环境类漂移抽查。

### 9.1 随包三件（复制到 store `tools/`，必须同目录）

| 工具 | 干什么 | 何时用 |
|---|---|---|
| `memory_recall.py` | 先过滤再排序的召回器；只读索引，按 §3 公式排 top-K，每条给入选原因 | 检索记忆前先跑 |
| `memory_organize.py` | 整理体检；默认 dry-run，`--apply` 只移除断链/合并重复，正文不动 | 10 次会话/30 天 |
| `next_id.py` | 取号器；`--claim` 原子占号，抢不到顺延；只读时不写盘 | 写库前 |

三件关系：organize/next_id 都 import recall 的索引解析器；缺 recall 两件退 3，不许自造第二套正则。

### 9.2 未随包维护件与降级

| 件 | 现状 | 拿不到时 |
|---|---|---|
| `memory_maintain.py` | store 收尾件，各家分叉，不随包 | 按 §9 手工体检，报告写"手工，未用脚本" |
| `patrol_check.py` | store 部署件，随部署走 | 手工按 §9 清单；双副本 md5 逐文件比 |
| `--dedup`/`--session` 等私有开关 | 个别 store 的召回器是超集 | 覆盖前先 `grep` 反查；命中保留 store 版或先回流 |

**底线**：缺脚本 ≠ 不体检，更 ≠ "查过了没问题"；手工也要先过滤再排序、写前先占号。

### 9.3 收口证据

- 本包自检：`py tools/skill_selfcheck.py [--manifest ...]`；红=先修，黄=有未验证项。
- 常驻层改动：`gate`（有则跑）+ 新会话注入证据；没证据=未验收。
- 工具改动：`verify`/读回；没读回=没改。
- 版本改动：frontmatter/头部/修订记录 三处互证；缺一报红。

### 9.4 产出分流与天令落位

> 常驻卡第 8 条（2026-10-30 漂移复盘增补）的细则单源。会话产出先分流再落盘——落错家＝产出漂移，比不产出更贵。

**① 新产出三分流**：
- **行为规则类**（天令立的规矩/铁律/全局纪律）→ 共享 GBR（`global-behavior-rules.md`，本机路径见 `personal.local.md`）。落节＝**四件缺一即漂**：正文家（GBR 落节）＋宿主 AGENTS 镜像＋记忆库 CORE 镜像＋共享账本登记。实证：2026-10-30 铁律 17（复杂任务交付含提示词与窗序）落位走全四件套——漏任何一件，其他窗口或下次会话读到的仍是旧规则。
- **知识资产类**（外部资料/方法论/金句/行业数字）→ LLMwiki 资产卡＋WORK 留痕；不进 GBR，也不写成 store 正文。
- **项目工程类**（代码/项目产物）→ 工作区真源＋窗志。

**② 天令立新规则前先打开 GBR 找正文家**：先看该主题已有哪些节、措辞口径是什么，再决定落新节还是并入旧节。自指规则（如「细则源＝本文件 §N」）写在正文家头里——不打开文件就看不到，凭印象落位必与既有节撞车或双写分叉。

**③ 机制设计类工作产生的坑同样走共享踩坑日志三步**（roots→pitfalls→索引两侧同步，边界与回流见 §6）：流程/机制设计不是写码，但踩的坑（口径漂移、落位缺件、双写分叉）与代码坑同型——别因为「不是 bug」就不记；跨宿主可复现的记共享层，仅本环境私有的记本 store PITFALL。

**④ 定时滚动窗收尾替代口径**：不承担账本读取职责的滚动窗（定时任务窗），收尾＝**真源回写＋锁 ended 行**，不强制走本节收尾 A 档的读账本/销号；账本扫描由用户问询窗/常驻窗承担。判据＝该窗有没有被注入「读账本」职责：没注入就不欠这笔——与 §9 收尾分档同一判据（仪式步数跟真实职责走，不跟窗型走）。

## 10. 冷启动（新 agent 第一次用）

1. **先按 §0.7 自适配 + 宿主原生记忆接管审计**：保证跨会话记忆只有一份真源；宿主原生面壳化/降格/停用，砍前先迁回 store。
2. 建 store：`MEMORY.md` 顶部放常驻卡（模板见下）+ 各库空 index；第一条记 PROFILE。
3. 复制三件 `tools/`；缺脚本按 §9.2 手工，不阻塞。
4. 写 `resident-manifest.json`，先跑 `py tools/skill_selfcheck.py --manifest ...`，再跑 `patrol_check.py gate`（若有）；没有 gate 就按 §0.7 B 表手工。
5. 改动后新会话取注入证据，写 notes/系统状态。
