# 宿主原生记忆接管审计（装载本 skill 后第一步必跑）

> 版本联动：sc2.2 起（2026-10-18，版本源 SKILL.md frontmatter）。
> 触发时机：冷启动新 agent、给既有 agent 首次装载本 skill、宿主配置或版本升级之后。
> 目标一句话：**收尾保证跨会话记忆数据只有一份真源（跑本 skill 的 store）；宿主内部的原生记忆面，要么壳掉/停用，要么降格为"指针＋会话暂存"——绝不允许两个真源并行运转。**

## 0. 裁决底座（三守则，先立后查）

1. **单一真源**：长期记忆数据写在谁那里就只在谁那里算真；常驻层只放指针/路由——同一个指针出现在多处也算成本（2026-10-17 Codex 三注入收敛两处判例：同指针三处＝漂移面 ×3，每轮多烧 ~1.5KB）。
2. **可对账优先**：真源必须能 md5 核对、双副本巡检、报告可读；藏在宿主程序私有库（非文件、肉眼不可见）里的记忆＝审计盲区，本 skill 管辖范围内一律不当真源。
3. **不硬砍**：宿主机制关不掉/不可配置时降格处理，不硬删；同时"放任共存"也不是方案——两个通道都在写＝慢性臃肿＋口径打架，迟早烂。

## 1. 盘点——宿主原生记忆面清单（逐类排查，至少过这五类）

| 类别 | 找什么 | 常见落点 |
|---|---|---|
| 常驻注入 | 每轮会话被塞进上下文的记忆面 | AGENTS.md / CLAUDE.md / MEMORY.md / 全局 memory 机制 / summary 文件 |
| 自动写入 | 没叫它写它也写的东西 | auto memory / 自动摘要 / 会话 checkpoint / 星标记忆 |
| 出厂库 | 宿主自带的记忆存储本体 | 宿主内置 memory 文件或库 / 项目目录 `.memory` 类 |
| 项目级分层 | 跟着项目走的记忆 | 项目内 AGENTS.md / 规则文件等 |
| 检索通道 | 宿主自己的记忆检索/召回 | 宿主内建检索（自动召回其自带记忆基座） |
→ 每项记五栏：机制名 ｜ 路径 ｜ 何时注入/何时写 ｜ 能否关/可配置（找不到开关就记"未见开关"，别猜） ｜ 隔离档位（全局共享／项目隔离／用户级——宿主记忆若是全局共享型，串项目串agent的风险要在声明块里点名）。

## 2. 三类障碍判定（逐条打分，判完就处置）

- **A 术语冲突**：同一名词两边定义不同（典型：宿主管它的星标摘要叫"记忆"，本 skill 的"记忆"是七库 store）→ 立**术语条约**：本 agent 常驻卡声明"记忆口径以本 skill 为准；宿主原生层 XX 仅作注记/指针"，并把宿主侧相关注记改口径。
- **B 双层/多层记忆**：同一事实存在两处真体（宿主自动存档一份＋store 一份；或常驻注入与项目文件各一份同内容）→ 按 §0 判真源归属，非真源层**壳掉/停用/降格**；⚠️ 下闸前先迁移：被下闸层里已有的历史记忆，先迁回 store（先占号→写入→条数/md5 对账），再动开关——**容器可以退役，数据不许火化**。
- **C 混乱/臃肿**：同一内容在一轮会话被注入多次 / 常驻字节超预算 / 两条检索通道轮番吐近似结果 → 削重复源：常驻卡只留手工维护的那份；原生自动注入面去重；与 store 同内容的项目级层降格或停用。**运行时仲裁**：真源通道（store 召回）优先，两通道打架以 store 为准并把冲突案例记进 store（LLM 有确认偏置，并行旧话本不清场只会越缠越紧）。
- **沿革条的老态处置**：被新事实顶替但原文没删的旧条（superseded 未清）→ 要么改状态行注明取代关系（权属链接），要么在整理器体检里挂候选收编；**检索端用'来源权威＋版本＋范围＋新鲜度'四把尺子垫底**——写时挡不住的全靠读时兜住。

## 3. 裁决决策树（每个原生面走一遍）

```
原生记忆机制还在写吗？
├─ 有开关/可配置 且它不必当真源 → 壳化/停用（常驻处留一行指针）
│   （开关名实查：Claude Code 类 = settings 的 autoMemoryEnabled / 环境变量 CLAUDE_CODE_DISABLE_AUTO_MEMORY；
│     ChatGPT 类 = Settings→Personalization→Memory 关闭；
│     还有别家就进其设置页找 memory 项，找不到开关＝记进盘点表"未见开关"档）
├─ 关不掉（写死路径/系统级注入）→ 降格：明写"宿主原生层＝注入指针＋会话暂存，
│   长期记忆一律写 store"（Qoder 宿主托管接法判例——E 盘 store 定为唯一真源）
├─ 宿主机制自称更优？→ 只有三条全满足才可作"镜像"（依旧不作真源）：
│   ① 记忆是文件、肉眼可见 ② 能 md5 对账 ③ 字段同构、可持续自动写入 store；
│   缺一条就不得双镜像并存（无主从的双镜像＝冲突之母）
└─ 拿不准/机制被宿主私有封装 → 把实况写下来，交用户拍板，agent 不越权代决
```

## 4. 记档回写（收尾 A/B 分档管辖：改动进账本）

- 本 agent 的 `MEMORY.md` 加一段**「记忆接管声明」**块（≤10 行）：真源是谁／宿主层现状（壳／降格／停用三态）／砍了什么带走的是什么／术语条约金句。**幂等重跑**：声明块已存在时做增量复查（delta 更新该块，不重复追加整块——协议自身不许膨胀）。
- 动过共享规则四面（账本头/注入卡/接入指南）→ 共享账本一行记账（≤400 字节）。
- 本机有 patrol 巡检的：把"壳文件状态/原生面文件体积"加进 `check_budget` 检查项（2026-10-17 Codex `memory_summary.md` 壳化 275B 的判例模式——壳要防复活）。

## 5. 运转验证——"顺利运转下去"靠三道实测，不靠口头

1. **读写闭环**：`next_id.py --claim` 取号 → 写一条真记忆 → `memory_recall.py` 真召回一次（要看到入选原因）→ `memory_organize.py` dry-run FAIL 0。
2. **常驻预算**：注入卡 ≤2KB 且与原生重复内容为 0（逐面比对）。
3. **口径扫尾**：grep 共享规则/常驻卡/接入文档各面，确认没有哪一面还在声称"宿主原生层是真源"或残留第二套评分口径。

## 6. 哨兵——复查防复活（进常驻卡收尾清单）

宿主升级常会**自动重开** auto memory / 自动摘要（重启即恢复出厂）；且实测**删文件不等于关功能**——宿主下一次会话照样重建（Claude Code 社区就报过"删了 ~/.claude/projects/*/memory/ 照样复活"）。所以双保险＝**开关关到设置层＋重开就再壳化**；别指望删目录一劳永逸。写进常驻卡 B 档触发词：**「宿主升级后首场：重跑 §1 盘点，确认原生层没有复活未对账」**。复活即重新壳化＋本条哨兵例记踩坑。
