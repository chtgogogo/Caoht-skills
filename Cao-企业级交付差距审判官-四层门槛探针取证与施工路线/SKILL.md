# 企业级交付差距审判官（四层门槛 + 探针取证 + 施工路线）

> 一句话：像最挑剔的企业采购一样审判项目——**它能不能直接交给企业真实业务用？差哪些？怎么补？要多久？**
> 产出：一份落盘的《企业级交付差距报告》，含四层门槛判定、逐项差距与执行建议、分阶段施工路线、以及可直接用于面试/汇报的差距话术。

---

## 0. 审判官六条军规（先读，凌驾于一切效率考量）

1. **回代码取证，禁止照抄文档待办**。这是本 skill 存在的最重要理由——见 §0.1 血泪教训。文档里的"待办清单"是**时间快照**，只有代码是**现状**。每一句"XX 未做/已做"都必须有 `文件:行号` 或命令输出支撑。

2. **只审判，不施工**。发现差距一律记录进报告，**禁止顺手改代码把它"补上"让报告好看**。用户明确说"审判+施工"模式时除外，且施工必须另立步骤、单独留证据。

3. **区分「做不到」与「不需要」**。这是本 skill 与普通缺陷清单的最大区别。四层门槛里，**第二层多数靠客户给料、第三层一半是资质与运维组织**——不是代码问题。报告必须把这类明确标出，而不是笼统列成"待办"。用户要的正是这个区分。

4. **判不了的写「判不了」**。触发条件不明确、指标无埋点、现状无法从代码确认时，如实写「⬜未测」或「未知」。**绝不脑补数字**，绝不把"我没查"写成"它没有"。与 `A-Cao-抗幻觉纪律`、`A-Cao-测试纪律` 同源执行。

5. **外部判据必须联网取，且标明出处与日期**。法规要求、行业标准、竞品功能、失败案例——**一律联网检索**，禁止用训练记忆里的"我印象中是"下结论（模型知识有截止日、且会记错版本号）。每条外部判据必须带：来源名 + 日期 + 可信度标注。检索不到就写「未检索到权威来源」，**不编**。

6. **区分「行业普遍状况」与「本项目的差距」**。联网搜到的"90% 企业做不到 X"是**行业背景**，不是本项目的结论。只有当本项目探针实测同样缺 X 时，才写成"本项目的差距"。**行业数据用来定严重度（这件事有多致命），代码探针用来定有无（本项目做没做）**——两者不可混用。

### 0.1 血泪教训：为什么本 skill 的第一条军规是"回代码取证"

2026-10-08 实战复盘（业财单据中枢 P9 卡）：

- 初版差距清单**照抄了项目旧文档的「待办表述」**，列出 8 项"现在就该做"的任务。
- 回代码逐项 `grep` 核实后发现：**8 项里 5 项早已完成**——因为那份旧文档自己的头部就写着「11 条已全部处置」，它的"待办"字样在优化批之后已经过时。
- **教训**：**写"待办清单"类报告，每条必须回代码核实，不能抄文档的待办段。** 这与该项目一贯纪律「判任何一张卡的状态，按 CHANGELOG ＋ 真代码 ＋ git status 三处对齐」完全一致。

> **正确姿势**：文档的"待办"只用来**生成假设**，代码用来**验证假设**。先假设"它可能没做"，再 grep 去找证据；找不到证据才算"未做"。

## 1. 四层交付门槛模型（判据框架）

**核心认知（必须在报告开头讲清，这是本 skill 的灵魂）**：

> **"企业级"不是一条线，是四道门槛，每道门槛考的东西完全不同。**
> 所以不要笼统说"还差得远"——要说清楚"差在哪一层、那一层考什么、谁决定能不能过"。

| 层 | 门槛性质 | 谁决定能不能过 | 典型判据 |
|---|---|---|---|
| **第一层：演示与试用** | 工程能力 | **项目方自己** | 能跑通全流程、公网可访问、有操作文档、测试绿 |
| **第二层：单企业内部试点** | 外部资源 | **客户给不给** | 真实数据样本、企业系统对接（ERP/银行）、真实 ROI 数字、客户身份体系 |
| **第三层：正式生产（每天在用）** | 运维 + 资质 | **组织能力，不是代码** | 并发与高可用、监控告警、合规资质（等保等）、备份恢复演练、故障响应 SLA |
| **第四层：多客户 SaaS** | 商业模式 | 需要才做 | 多租户隔离、计费、多可用区 |

**判定纪律**：
- 每层必须给**明确结论**：✅已过 / 🔶部分 / 🔴未过 / ⬜不适用
- **第二层要特别标注"哪几项靠客户给"**——这是最容易被误判为"能力不足"的一层
- **第三层要特别标注"哪几项不是代码问题"**（资质、SLA）——这是本 skill 最有价值的判断

## 1.5 外部判据锚（联网取来的"行业尺子"）

> **四层门槛是"纵向"判据（本项目能走到哪一层）；外部判据锚是"横向"判据（同行都做到哪了）。**
> 两者交叉，才能回答用户真正关心的问题：**"我这项目在市场上算能交付的吗？"**

**用法**：把下表当**检索关键词表 + 判据对照表**。每条锚 = 去网上找什么 + 拿回来跟本项目哪一项对。

### 锚一 · 生产安全八域（PSF · Production Safety Framework）

行业最系统的"AI 系统上生产要过哪些关"框架，八域 32 项控制。**这八域可直接当第三层（生产）的判据骨架**：

| 域 | 管什么 | 本项目对应探针 |
|---|---|---|
| PSF-1 **输入治理** | 进来的数据有没有校验/清洗/去重 | 入库前的 schema 校验、脏数据拦截 |
| PSF-2 **输出验证** | 出去的结果有没有把关（置信度/规则闸） | LLM 输出是否有 policy gate、置信阈值 |
| PSF-3 **数据保护** | 敏感数据、PII、加密、最小权限 | 权限模型、字段级脱敏、审计日志 |
| PSF-4 **可观测** | 有没有 trace/指标/告警，能不能定位失败 | `/api/metrics`、决策日志、trace 表 |
| PSF-5 **部署安全** | 发布流程、回滚、环境隔离 | 迁移器、回滚预案、staging |
| PSF-6 **人工监督** | 人在哪一环、能不能否决、审批队列 | 审批流、例外队列、override 日志 |
| PSF-7 **安全** | 认证、授权、限流、防注入 | auth 中间件、rate limit、RBAC |
| PSF-8 **供应商韧性** | 依赖的外部服务挂了怎么办 | 超时/重试/降级/熔断 |

> **判读**：八域全无 ⇒ 离第三层很远；有 4-5 域 ⇒ 处于"部分就绪"。**注意：多数开源/个人项目在 PSF-6 人工监督上意外地强（因为有审批流），却在 PSF-4 可观测和 PSF-8 韧性上意外地弱**——这个反差是最值得写进报告的洞察。

### 锚二 · 七个生产就绪门（Datawhisper）

更偏"组织/运营"的一套门，**用来判第二层→第三层的跨越**：

1. 业务成果与所有权（谁为结果负责）
2. 权限与决策边界（agent 能自主做到哪一步）
3. 数据与集成就绪（真实数据 + 真实系统）
4. 服务可靠性（SLA、可用性）
5. 保证与证据（审计证据链）
6. 运营模型（谁值守、怎么响应）
7. 受控变更（改配置/模型怎么控）

> **最有用的一条警告信号**：**"只有构建团队能解释失败 = 尚未成为运营服务"**。若项目无告警、无值班、失败只能靠开发者看日志 ⇒ 第四门明确未过。

### 锚三 · 五域就绪评估（Digital Applied）

集成就绪 / 评估基础设施 / 监控可观测 / 组织所有权 / 范围与数据就绪。
对应三条落地实践：**① AI 运维先于放量 ② 评估框架先于扩展 ③ 窄范围先行**。

### 锚四 · 法规与标准时间线（会过期，**必须联网复核**）

| 时间 | 事件 | 对本项目的含义 |
|---|---|---|
| **2026-08-02** | **EU AI Act 广泛执法要求生效** | 若产品服务欧盟用户，需评估是否落入高风险类别 ⇒ 文档、日志、人工监督成硬要求 |
| 2026 起 | 多地要求 AI 透明度与披露 | 对外系统需留评估方法学文档（不论司法辖区） |
| 2026 起 | SOC 2 Type II / ISO 27001 成采购门槛 | 面向企业采购时，缺认证会卡在供应商评估阶段 |

> ⚠️ **这张表必须联网更新**。检索关键词：`EU AI Act 执行 时间线 <当前年份>`、`AI 监管 最新要求 <行业> <当前年份>`。

### 锚五 · 行业命中率基线（用来定"严重度"，不是定"有无"）

联网可得的行业事实（**引用时必须带来源与日期，且只用于定严重度**）：

- 仅约 **14%** 的 AI agent 以完整安全/IT 审批上线 ⇒ 若本项目卡在第 3 层，**属于常态而非失败**
- **82%** 高管自信现有策略能防护，但仅 **21%** 真有可见性 ⇒ "自信 ≠ 就绪"
- 约 **90%** 组织为加速 AI 而放松了安全控制
- 约 **80%** 无法解释非人类身份的特权行为
- 约 **46%** 组织称"与现有系统集成"是最大部署障碍 ⇒ 集成难是**行业性**问题，不是本项目独有
- McKinsey 2025：约 **1/3** 组织才刚开始规模化 AI，**2/3** 卡在试点/PoC
- Gartner：**63%** 组织缺或不确知 AI-ready 数据；预测 **60%** 缺 AI-ready 数据的 AI 项目将被放弃
- Gartner 警告：**40%+** agentic AI 项目将在 2027 年前被取消
- **AP/财务自动化专属基线**（Ardent Partners / APQC）：
  - 平均手动处理单张发票 **$9.84**，世界级 **$2.65**，复杂低量场景 **$12.88–$19.83**
  - 头部 AP 团队**人均处理量是末位的 3 倍以上，单票成本低近 4 倍**——差距几乎全由自动化程度决定
  - 交付一个"抓取+识别+匹配+异常路由入 ERP"的闭环，**报价量级 $5,000–$15,000**；若需先做供应商主数据治理或无干净集成路径，**升到 $15,000–$50,000**

> **用法**：报告里写"本项目缺 X"时，附一句"行业里 Y% 的组织同样缺 X，因为……"——**既定严重度，也避免用户误以为是自己能力差**。

## 1.6 业务场景差距判别法（"跑得通" ≠ "用得上"）

> 这是本 skill 最容易被忽视、也最贴近用户实际痛点的一节。
> **用户问"和实际业务场景的差距怎么判别"——答案是：不看你有没有这个功能，看这个功能在真实场景下会不会被用、用了会不会出错、出错谁来兜。**

行业里 AP 自动化的失败模式高度一致（联网共识），可直接作为**判别清单**：

### 判别一 · 主数据是否可对齐（最高频失败点）

**行业原话**：*"项目不是死在抽取上，是死在主数据上。"* 供应商主数据有重复、命名不一致、无可信 join key 时，**再准的抽取也无法自动匹配**——系统分不清这张票是哪个"Acme"。

**判别探针**：
```bash
# 有没有供应商/客户主数据治理机制？（去重、标准化、唯一键）
grep -rn "normalize\|dedup\|去重\|unique.*vendor\|标准化" <源码根> --include=*.py | head
# 有没有唯一键约束
grep -rn "UNIQUE" <schema目录>
```
**判读**：无规范化层、无唯一键 ⇒ **主数据风险未解**，即使抽取准确率 100% 也无法自动匹配。

### 判别二 · 异常是否有归属（"有队列" ≠ "有归属"）

**行业原话**：*"'供应商不在主数据里' 与 '数量偏差 3%' 是不同人的不同问题。"* 异常若全扔进一个无差别队列，等于没处理。

**判别探针**：
```bash
grep -rn "exception\|异常\|exception_queue\|状态.*待处理" <源码根> --include=*.py | head -20
```
**判读**：看**异常是否按原因分类**、**是否带原因与责任方路由**。只有"待处理"一个状态 ⇒ **异常无归属**。

### 判别三 · 置信阈值是否可配、是否有分档推进

**行业原话**：*"置信阈值是最重要的一个数字，且它是业务决策而非技术决策。"* 且**必须分档推进：影子模式 → 建议模式 → 窄范围自动过账**，跳过这个序列会造成信任崩塌（"三周项目变二十周"）。

**判别探针**：
```bash
grep -rn "confidence\|阈值\|threshold\|shadow\|影子\|auto_post\|自动过账" <源码根> --include=*.py | head -20
```
**判读**：有硬编码阈值但无配置项 ⇒ 🔶部分；有影子/建议/自动三档开关 ⇒ ✅。

### 判别四 · 写回 ERP 是否被验证（**行业公认最难的一环**）

**行业原话**：*"ERP 写回始终是最难的阶段——不是集成不可能，而是'跨实体、跨币种、跨科目表正确过账'需要对这套 ERP 实例的实际配置有详细理解。"* 且必须在试点期**验证失败路径**：不仅测成功过账，还要测**被拒记录、重试、状态回写**。

**判别探针**：
```bash
ls <集成脚本目录>
grep -rn "retry\|rollback\|status\|回写\|writeback" <集成脚本目录> | head -20
# 有没有针对失败路径的测试
grep -rn "reject\|失败\|retry" <测试目录> | head
```
**判读**：只有 happy path 脚本、无重试/回滚/状态回写、无失败路径测试 ⇒ **写回未验证**，属于行业公认的高风险区。

### 判别五 · 基线是否先立（**最常被跳过的一步**）

**行业原话**：*"先给人工流程埋点——若你测不出团队现在做到什么水平，就没有基线，也就没有阈值可放进回滚条件。"*

**判别探针**：
```bash
# 有没有改前改后的对比记录、成本/时长基线
ls <项目文档目录> | grep -i "基线\|baseline\|benchmark\|对比"
grep -rn "cycle_time\|cost_per\|touchless\|直通率\|异常率" <源码根> <文档目录> | head
```
**判读**：无基线记录 ⇒ 即使功能做完了，**也无法证明 ROI**，卡在第二层（客户要真实 ROI 数字）。

### 判别六 · 失败可逆性分级（决定"能不能自主跑"）

**行业共识**：*"决定性判据是可逆性。"* 可回滚、可审批、可升级的动作才能放给 agent 自主。**若一个错误动作无法被检测或回滚，无论基准分多高，设计都太宽。**

**判别探针**（读代码判风险等级）：
```bash
grep -rn "无审批\|direct\|commit\|支付\|payment\|删除\|delete" <源码根> --include=*.py | head -20
```
**判读**：把动作分三级——**只读（低危）/ 可逆写（中危，需审批）/ 不可逆（高危，需双人复核）**。高危动作无管控 ⇒ 第三层未过。

### 判别七 · 指标是否按"业务成果"而非"活动量"计

**行业警告**：*"tokenmaxxing"* ——优化 token 消耗/任务发起数/输出条数这类**活动量**，而非**已验证的业务成果**，会产出忙碌但低质的工作。

**判别探针**：
```bash
grep -rn "metrics\|指标\|KPI\|count\|统计" <源码根> --include=*.py | head -20
```
**判读**：指标全是"处理了多少条/调用多少次" ⇒ 活动量指标；有"直通率/异常率/纠错率/单票成本" ⇒ 业务成果指标。**前者必须补后者**。

> **七条判别总结成一句话**：**场景差距 = 主数据能不能对齐 + 异常有没有归属 + 阈值能不能分档 + 写回有没有验证 + 基线有没有先立 + 失败能不能回滚 + 指标是不是业务成果。**

## 2. 探针取证法（防过时的核心）

**探针 = 一条可执行命令 + 一个判据**。报告里每一条结论，背后必须有一个探针。

### 2.1 通用取证流程（五步）

```
1. 定假设  —— 从文档/经验生成"它可能没做 X"的假设
2. 写探针  —— 设计一条能证实或证伪的命令
3. 跑探针  —— 实际执行，拿到原始输出
4. 判读    —— 按判据下结论（已做/部分/未做/判不了）
5. 留位置  —— 记录：文件:行号 或 命令 + 原始输出片段
```

### 2.2 探针模板（按判据类型）

> ⚠️ 具体探针必须**按项目技术栈现场设计**，下表是**通用形态**，不是固定清单。
> 这份表的价值在于"教你问什么问题"，不在于"给你现成答案"。

| 判据类型 | 探针形态 | 判读要点 |
|---|---|---|
| **某项能力是否已实现** | `grep -rn "关键词" <源码目录> --include=*.py` | **先假设未做**；有命中要区分是**实现**还是**注释/文档字符串**；注释里提"要做 X"≠做了 |
| **架构是否已收口** | 看目录结构与关键文件：`ls <可疑目录>` + `grep` 反模式在业务码中的残留 | 若同类定义已集中到单一目录，且业务码零残留 ⇒ 已收口 |
| **是否有监控/观测** | `grep -rn "metrics\|埋点\|count\|prometheus" <源码>` | 有端点 ≠ 有数据；要确认**采样点**真的在调用链上 |
| **是否有持久化** | `grep -rn "落库\|persist\|_meta\|持久化" <源码>` | 区分"内存态"与"入库"；日志里写"已持久化"要回代码确认 |
| **是否有索引** | `grep -rn "CREATE INDEX" <schema目录>` | 直接看 schema 定义，不猜 |
| **配置是否已生效** | 读配置文件原文（nginx/部署脚本） | **配置文件中被注释掉的 ≠ 生效**；要区分"注释里的计划"与"打开的行" |
| **是否有迁移/兼容机制** | 找 `migrations`/`alembic`/版本账本 | 有版本表 + runner ⇒ 迁移器已建 |
| **并发/性能现状** | 找锁、信号量、worker 数、超时配置 | 判"能不能起多实例"看状态存储位置 |
| **依赖外部系统** | 找集成脚本目录 `scripts/` | 区分"演示替身"（对接通用开源件）与"生产对接"（对接客户真实系统） |

### 2.3 判读口径（必须严格区分四种状态）

| 状态 | 定义 | 证据要求 |
|---|---|---|
| ✅ **已完成** | 代码里有实现，且在调用链上 | `文件:行号` + 代码原文 |
| 🔶 **部分完成** | 有一半（如：有 Odoo 镜像但没有通用导出） | 分别给"有的"和"没有的"证据 |
| ❌ **未做** | grep 无实现 | 给出**grep 命令与空结果**作为证据（"没找到"也是证据） |
| ⬜ **判不了** | 无法从代码确认（如需真实环境） | 说明为什么判不了 + 需要什么才能判 |

> **反面案例**：`grep` 命中"优化清单新5：列表页按 created_at 排序"这类**注释**，只能说"看到相关注释"，必须再去 schema 文件确认 `CREATE INDEX` 真的存在——注释可能是计划，不是事实。

## 2.5 联网取证（本项目"没有的"，同行有没有？法规要不要？）

> **探针看"本项目现状"，联网看"外部要求"。两者缺一不可。**
> 只有探针 ⇒ 你知道自己缺什么，但不知道**这件事有多要紧**；只有联网 ⇒ 你知道行业在聊什么，但不知道**自己中没中招**。

### 2.5.1 三条固定检索线（每次审判必跑）

| 线 | 检索什么 | 落进报告哪一节 |
|---|---|---|
| **① 法规/标准线** | 该项目品类的**最新合规要求与生效时间**（如 EU AI Act 时间点、行业数据规范、等保要求） | §三 合规阻塞 |
| **② 竞品功能线** | **同赛道玩家的业务功能清单**（做到哪些能力、集成哪些系统、认证有哪些） | §二/§三 差距对照 + §新增「竞品对照」 |
| **③ 失败案例线** | **该品类真实落地失败/翻车原因**（为什么试点变不了生产） | §1.6 场景判别 + §五 施工路线的"坑"栏 |

### 2.5.2 检索关键词模板（按项目品类替换）

**通用模板**：
```
① <品类> <当前年份> 合规要求 最新 监管
② <竞品A> <竞品B> <品类> 功能对比 <当前年份>
③ <品类> 项目 失败原因 落地 <当前年份>
```

**财务/AP 自动化类**（业财单据中枢所属赛道，可直接用）：
```
① 发票 电子发票 财税合规 最新要求 <当前年份> / EU AI Act 时间线
② Stampli Vic.ai Tipalti 每刻 金蝶 AP自动化 三单匹配 功能对比
③ AP自动化 发票处理 落地失败 ERP集成 数据质量 原因
```

### 2.5.3 竞品对照的取证口径（**取功能，不取吹嘘**）

联网拿回竞品资料后，**只提取可验证的功能事实**，做成三列表：

| 能力维度 | 竞品普遍水平（来源+日期） | 本项目（探针实测） | 判读 |
|---|---|---|---|
| 三单匹配（PO/收货/发票） | 主流产品标配两层/三层匹配，含容差配置 | grep 探针 → ? | 🔴/🔶/✅ |
| 异常分类路由 | 按原因分队列路由到责任人 | 探针 → ? | |
| 置信阈值分档 | 影子→建议→自动，阈值可配 | 探针 → ? | |
| ERP 集成 | 主流做 70+ 预置 ERP 连接器 | 探针 → ? | |
| 供应商主数据治理 | 含去重/标准化 | 探针 → ? | |
| 直通率（touchless rate） | 头部 70–85%（需 18 个月干净历史数据） | 探针/基线 → ? | |
| 审计追踪 | 每票全时间戳留痕 | 探针 → ? | |
| 认证 | SOC 2 Type II / ISO 27001 | 探针 → ? | |
| 支付执行 | 多币种/多通道/税务合规 | 探针 → ? | |

> **⚠️ 竞品对照三条纪律**：
> 1. **引用竞品公开数据必须标来源与日期**（评级/功能会变）；
> 2. **不拿"竞品宣传的直通率"当本项目目标**——行业明确提醒：*"高直通率通常反映的是窄分母，要问含不含无 PO 的服务类发票"*；
> 3. **竞品有而本项目无 ≠ 必须补**。要过 §Step 4 的标签：是🧩能力、还是⬜本就不匹配（如面向国内中小企业的项目不需要 196 国支付通道）。

### 2.5.4 联网判读的四条铁律

1. **外部数据只能定严重度，不能定有无**。"行业 90% 缺 X" ≠ "本项目缺 X"，后者必须靠代码探针。
2. **带日期引用**。法规与竞品数据是**强时变**的，报告里每条外部判据都要写"来源 · 日期"。
3. **优先一手来源**。法规查官方/权威媒体；竞品查其官网功能页与第三方评测（G2/Capterra/权威对比评测），**不采信二手转述**。
4. **检索不到就写检索不到**。若某维度搜不到权威来源，报告写「未检索到权威来源，本项按行业经验判断（标注为经验判断）」——**绝不用模糊记忆冒充检索结果**。

## 3. 审判执行流程（八步）

> **全局顺序**：认路 → 初判 → **联网取尺子** → 代码取证 → 场景判别 → 打标签 → 出路 → 落盘
> **关键**：Step 3（联网）在 Step 4（探针）**之前**——先知道"外面要求什么"，探针才知道该重点查什么。

### Step 1 · 项目画像（先认路）

- 技术栈、规模（代码量/测试数）、部署形态（单机/容器/云）
- 有没有现成的架构文档、演进表、优化清单、README 边界声明
- **关键**：找出项目自己**已声明的边界**（如 README「当前栈是演示规模的最适配解，不是生产栈」）——这些声明是"诚实的证据"，要在报告里肯定
- **顺手记**：项目属于哪个品类/赛道（决定 Step 3 搜什么竞品）

### Step 2 · 四层门槛初判

按 §1 模型，快速给出四层的初始判定。此时允许"粗判"，Step 4 再逐项证实。

### Step 3 · 联网取尺子（**外部判据**）

按 §2.5.1 跑**三条固定检索线**：
1. **法规/标准线** → 品类最新合规要求与生效时间（对照 §1.5 锚四，复核时间线）
2. **竞品功能线** → 同赛道玩家功能清单（按 §2.5.3 做成对照表）
3. **失败案例线** → 该品类真实落地失败原因（喂给 §1.6 场景判别）

同时核对 §1.5 的八域/七门/五域锚，看**本项目所属品类该过哪几域**。

**产出**：一张「外部要求清单」（含来源与日期）+ 一张「竞品功能对照表」（半成品，留待 Step 4 填本项目列）。

### Step 4 · 逐项探针取证（最耗时，也最值钱）

对每一层的每一项判据：
1. 生成假设（**默认假设"未做"**）
2. 设计探针 → 执行 → 判读（按 §2.3 四态）
3. 记录证据

**必须覆盖的维度**（按层展开，**按项目实际裁剪**）：

**第一层（演示）**：跑通性、可访问性、文档完备度、测试状态
**第二层（试点）**：
- 真实数据 vs 合成数据（**问：有没有真实样本？占比多少？**）
- 外部系统对接（**问：对接的是通用替身还是客户真实系统？**）
- 商业数字（**问：是实测还是折算？有没有标"假设"？**）
- 身份体系（**问：白名单还是企业 IdP？**）
- **基线**（**问：有没有改前改后的成本/时长基线？**——行业公认最常被跳过的一步）

**第三层（生产）**：
- 并发能力（**问：能不能起多实例？状态存哪？**）
- 数据层（**问：什么库？迁移成本算过吗？**）
- 可观测（**问：有没有指标端点？有没有告警？失败只有开发者能解释吗？**）
- 合规资质（**问：要不要等保？数据出境？要不要 SOC 2？**）
- 运维（**问：备份有没有演练？有没有 SLA？能不能回滚？**）
- **韧性**（**问：外部依赖挂了怎么办？有超时/重试/降级吗？**——对应 PSF-8）

**第四层（SaaS）**：多租户、计费、多可用区（多数项目应判"明确不做"）

**收尾**：把 Step 3 的竞品对照表**补齐"本项目"列**——同一个能力维度，别人怎样、本项目怎样。

### Step 5 · 业务场景贴合度判别（按 §1.6 七条）

逐条跑 §1.6 的七个判别点：主数据对齐 / 异常归属 / 阈值分档 / 写回验证 / 基线先立 / 失败可逆性 / 指标口径。
**这一步回答的是"跑得通≠用得上"**——第一层过了不代表第二层能用。

### Step 6 · 区分「做不到」与「不需要」

对每一项差距，打上标签：
- 🧩 **能力问题**：需要工程能力，项目方能自己解决
- 🤝 **资源问题**：需要客户/外部提供（真票、真实系统访问）
- 🏛️ **资质问题**：需要官方认证/组织（等保、SLA、SOC 2）
- ⬜ **目标不匹配**：明确不需要（如求职项目不需要 SaaS 化）

> **这一标签是报告的灵魂**。它把"我还不够好"转化为"我知道差什么、也知道缺的那部分不是我写代码能补的"。
> **交叉检查**：竞品有的能力若打了 ⬜，必须写明理由（如"竞品面向跨国企业，本项目面向国内中小企业，不需要 196 国支付"）。

### Step 7 · 出分阶段施工路线

- **阶段一：现在就能做**（不依赖外部资源）
- **阶段二：有第一个真实客户后**
- **阶段三：规模/合规（按需）**

每项给：**动作 + 验收标准 + 工作量 + 坑**
排序原则：① 不依赖外部资源的先做 ② 能写进简历/汇报的先做 ③ 需客户的往后排
**"坑"栏必须结合 Step 3 的失败案例线**——行业踩过的坑要前置警告。

### Step 8 · 落盘 + 复检

- 报告落盘（默认与项目文档同目录，或用户指定）
- **必须回读一遍**，检查所有"已做/未做"结论都有证据
- 若发现报告里任何一句是"照抄文档"来的，**回到 Step 4 补探针**
- 检查所有外部判据**是否都带了来源与日期**

## 5. 输出纪律

1. **报告必须落盘**，不能只在对话里讲。路径默认 `docs/企业级交付差距报告-YYYYMMDD.md`，或用户指定。
2. **每条结论带证据**。没有证据的结论宁可不放。
3. **状态有时间戳**。报告头部写明"判据截止 YYYY-MM-DD"——因为**代码会变**，这份报告是快照。
4. **不承诺工期**。工作量写"量级"（如"2-3 天"），并注明"为估量级，非承诺值"。
5. **对外数字受项目自身口径约束**（若项目有《对外数字口径表》等唯一数字源，一律以其为准）。
6. **外部判据必须三件套：来源 + 日期 + 可信度**。联网得来的每条法规/竞品/行业数据，都要能溯源。**无来源的外部数字一律不写进报告**。
7. **联网检索清单要留在报告里**。报告 §十一 诚实声明中列出本次实际执行的检索词与来源，让读者能复核——也让人知道这份报告"外面的尺子是哪天量的"。

## 6.5 联网取证速用（一句话触发）

用户说以下任何一句，**直接升格为全量审判（含联网）**：

- 「联网看看我们和竞品差什么」
- 「查查最新要求，我们还差哪些」
- 「同行业都做到哪一步了」
- 「这项目放到市场上算能交付吗」

**执行**：跑 §2.5.1 三条固定线 → 按 §2.5.3 出竞品对照 → 按 §1.6 出场景判别 → 合进报告。

## 7. 附：探针速查（示例形态，需按项目裁剪）

> 以下为**通用形态示例**，展示"怎么把判据翻译成命令"。实际执行时按项目技术栈改写。

```bash
# 判据：数据层是否已收口（业务码里还有裸建表吗）
grep -rn "CREATE TABLE" <源码根> --include=*.py | grep -v "<schema目录>"

# 判据：是否有指标端点
grep -rn "metrics" <源码根> --include=*.py | head -20

# 判据：是否有索引（直接读 schema）
grep -rn "CREATE INDEX" <schema目录>

# 判据：配置是否真生效（注意区分注释与打开的行）
grep -n "gzip" <部署配置>

# 判据：是否对接了真实外部系统（还是演示替身）
ls <脚本目录>
```

**判读示例**：
- `grep "CREATE TABLE" | grep -v schema` → 输出全是**注释**（以 `#` 开头或在 docstring 里）⇒ **已收口**，不是未做
- `grep "gzip"` → 命中行以 `#` 开头 ⇒ **未生效**；命中 `gzip on;` 无 `#` ⇒ **已生效**

### 7.1 业务场景贴合度速查（配 §1.6 七条判别）

```bash
# 判别一：主数据可对齐（行业最高频失败点）
grep -rn "normalize\|dedup\|去重\|标准化" <源码根> --include=*.py | head
grep -rn "UNIQUE" <schema目录>

# 判别二：异常是否有归属（分类 + 责任人路由）
grep -rn "exception\|异常\|待处理" <源码根> --include=*.py | head -20

# 判别三：置信阈值是否可配 + 是否分档推进
grep -rn "confidence\|阈值\|shadow\|影子\|auto_post" <源码根> --include=*.py | head -20

# 判别四：ERP 写回是否验证（含失败路径）
grep -rn "retry\|rollback\|writeback\|回写\|status" <集成脚本目录> | head
grep -rn "reject\|失败\|retry" <测试目录> | head

# 判别五：基线是否先立（改前改后对比）
ls <项目文档目录> | grep -i "基线\|baseline\|对比"
grep -rn "cycle_time\|cost_per\|touchless\|直通率\|异常率" <源码根> <文档目录> | head

# 判别六：失败可逆性分级（高危动作有无管控）
grep -rn "payment\|支付\|delete\|删除\|commit" <源码根> --include=*.py | head -20

# 判别七：指标口径（活动量 vs 业务成果）
grep -rn "metrics\|KPI\|count\|统计" <源码根> --include=*.py | head -20
```
