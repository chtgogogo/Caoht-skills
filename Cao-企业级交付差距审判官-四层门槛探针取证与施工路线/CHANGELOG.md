## v1.1.1 · 2026-10-11

**只修 frontmatter 的可解析性，正文与描述文字一字未动**。

- **解决了什么**：`description` 原先写成双引号标量（`description: "…"`），而这段文字里含**未转义的英文双引号**（`…想判断"能不能交给企业真实业务使用"时触发`）。标准 YAML 解析器在这里报 `while parsing a block mapping … expected <block end>, but found '<scalar>'`——整块 frontmatter 解析失败，`name` / `version` / `description` 一并读不到，宿主按 description 决定调不调本 skill 的机制随之失效。旧体检脚本只查"字段齐不齐"，对这一支报绿，所以这个硬伤携带了很久。
- **怎么解决的**：改成折叠块标量 `description: >-`（多行文本读成一行、结尾不吃空格），去掉首尾那对 `"`，描述内容逐字保留（现 500 字符，在开放标准 1,024 上限内）。
- **怎么验证的**：PyYAML（标准解析器 + 拒绝重复键）与内置严格子集解析器两种模式都能解析，且读到的 `description` 完全一致；重写后的 `library_check.py` 对本支不再有红项。命令输出落盘：`<你的任务包>\evidence\卡01\_fix-frontmatter-output.txt`。
- **版本号**：v1.1.0 → v1.1.1（补丁级：只动元数据写法，判据、门槛模型、探针规则均无变化）。

## v1.0.0 · 2026-10-08

**首次创建**。

### 缘起
CaoHT 于 2026-10-08 提出：「检查企业级交付那个东西做成 skill，让使用这个 skill 就会对项目审判，将其和真正企业级交付的差距全部都找出来，并给予执行建议，类似现在的 P9 卡」。

### 素材来源
- **P9 卡**（`<你的项目工作台>/content/P-项目内功/P9-企业级交付差距与升级路线.md`）：四层交付门槛模型的原始提出
- **业财单据中枢项目**：探针取证法的实战来源
- **关键复盘事件**：P9 卡初版照抄旧文档待办清单，回代码 grep 核实后发现「8 项里 5 项早已完成」——**这个误判直接催生了本 skill 的第一条军规**

### 核心设计决策

1. **为什么不做成"固定清单"**
   - 固定清单必然过时（P9 卡初版翻车就是这个原因）
   - 故本 skill 的灵魂是**探针取证法**（§2）：教"怎么取真相"，而非"背答案"
   - 清单只用作**生成假设**，代码用来**验证假设**

2. **为什么"区分做不到与不需要"是灵魂**
   - 四层门槛里，第二层多数靠客户给料、第三层一半是资质与运维组织
   - 笼统列成"待办"会让人误以为"能力不足"
   - 故每项差距强制打标签：🧩能力 / 🤝资源 / 🏛️资质 / ⬜目标不匹配

3. **为什么设"只审判不施工"军规**
   - 继承 `Cao-项目验收官` 的同款纪律
   - 防止"顺手改代码让报告好看"——那会让报告失真

### 与既有 skill 的分工
- **Cao-项目验收官-四层漏斗固定清单加动态启发**：判「现在质量合不合格」（体检）
- **本 skill**：判「离企业级还差哪些路」（差距地图 + 施工路线）
- 建议协同：先验收官（确认现状），再本 skill（判差距）
