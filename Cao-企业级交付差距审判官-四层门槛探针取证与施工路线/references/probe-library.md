# 探针库（Probe Library）

> 探针 = 一条可执行命令 + 一个判据。
> **用法**：按项目技术栈**改写**下表命令，不要直接复制（路径、后缀、关键词都要按实际调整）。
> **纪律**：探针是用来**证伪**的——先假设"它没做"，再找证据推翻；推翻不了只算「**未找到**」，不算「未实现」（判据见 `../SKILL.md` §2）。

---

## 一、判读铁律（比探针本身更重要）

> 🔴 2026-10-12 v1.2.0 订正：下表原先写「grep 零命中 ⇒ "未做"的有效证据」和「配置有 `gzip on;` ⇒ 已生效」，**两条都是错的判读**，已按三态口径改写。原先那样写会让审计报告把"我没搜到"当成"它没有"、把"文件里写了"当成"线上跑着"。

| 看到什么 | 结论 | 陷阱 |
|---|---|---|
| grep 有命中，但是在 `#` 注释或 docstring 里 | **不能说"已实现"** | 注释常写"计划做 X" |
| grep 有命中，但命中的是**变量名/文件名** | 要**打开看** | 关键词撞名 |
| grep 零命中 | **只能得「未找到」**（记 §2.3 三件套） | 能力常在依赖库/框架内建/网关/配置中心/生成物里——先把 `../SKILL.md` §2.2 六个位置走完 |
| 配置文件有未注释的 `gzip on;` | **文本在场，生效未验证** | 要走"加载确认→部署版本确认→运行行为观察"三步（§2.6）；带 `#` 更是未生效 |
| 依赖清单里有带该能力的库 | 只能说"**可能由依赖提供**"⇒ 未验证 | 要确认它真被配置并使用（初始化代码、调用点、生效范围） |
| 测试文件存在 | 不等于**被执行过** | 要跑一遍或看 CI 记录 |
| 有 metrics 端点定义 | 不等于**有数据** | 要看采样点是否在调用链上 |
| 仓库里有这份配置/这段代码 | 不等于**线上跑的就是它** | 要对账镜像 tag／构建号／commit sha ↔ 发布记录 |

## 二、通用探针（按判据类型）

### 2.1 能力是否已实现

```bash
# 形态（Python 项目）
grep -rn "<关键词>" <源码根> --include=*.py | head -30

# 判读：
#  - 确认命中行是代码（非注释）：看行首是否 # 或是否在 """ 内
#  - 找到定义后，还要确认它被**调用**（grep 调用点）
```

**示例（判断"日计数持久化"是否做了）**：
```bash
grep -rn "持久化\|persist" <源码根> --include=*.py
# 命中 "优化清单新4：限流日计数持久化装配" ⇒ 看到线索
# 再打开该文件确认真的有落库调用 ⇒ 才算已做
```

### 2.2 架构是否已收口

```bash
# 反模式残留检查：业务码里还有没有重复定义
grep -rn "CREATE TABLE" <源码根> --include=*.py | grep -v "<集中目录>"
```

**判读**：
- 输出**全是注释** ⇒ **已收口**
- 输出有可执行语句 ⇒ **未收口**

**示例（业财单据中枢实证）**：
- `grep "CREATE TABLE" backend/app | grep -v "app/schema/"` → 全是注释
- `ledger/models.py:266` 原文：「本模块不写 CREATE TABLE（**建表文本只有一个家**，`test_schema_single_source` 钉着）」
- ⇒ **结论：已收口**（还可能有测试钉着，一并 grep）

```bash
# 顺带查是否有测试守卫
grep -rn "single_source\|schema_single" <测试目录>
```

### 2.3 是否有监控/观测

```bash
grep -rn "metrics\|prometheus\|埋点\|count" <源码根> --include=*.py | head -20
```

**判读**：
- 找到**端点定义**（如 `@router.get("/api/metrics")`）⇒ 端点已做
- 再找**采样点**（中间件里有没有 `metrics.record(...)`）⇒ 确认真的在记
- 找不到**计数逻辑** ⇒ "有处理但无观测"

### 2.4 是否有持久化

```bash
grep -rn "<存储表名>\|持久化\|persist" <源码根> --include=*.py
```

**判读**：区分"进程内存态"（`threading.Lock` + 实例变量）与"入库"（SQL 调用）。

### 2.5 是否有索引

```bash
grep -rn "CREATE INDEX" <schema目录>
```

**判读**：直接读定义，不猜。顺带看注释里引用的业务查询是否真存在该列。

### 2.6 配置是否真生效（🔴 本节是 v1.2.0 重写过的，旧判读作废）

```bash
grep -n "<配置项>" <部署配置文件>
```

**第一步只能得到「文本在场」**：
- 命中行**有 `#`** ⇒ 连文本都不算生效声明，直接记 ⬜**未验证**（多半是变更说明或计划）。
- 命中行**无 `#`** ⇒ 也只证明"这行写在仓库的这个文件里"。**旧版写的"无 `#` ⇒ 生效"是错的**，已作废。

**要下"已生效"必须先过主文 `../SKILL.md` §2.4 的三步**：

```bash
# 步 1 加载确认：运行时读的是不是这个文件
ps -ef | grep "<进程名>"                      # 启动参数 -c/--config 指到哪
grep -rn "include" <部署配置目录>              # include 链是否真的覆盖该文件
grep -rn "<环境变量名>" <部署清单 compose/k8s>  # 环境变量指向的路径在容器里存在吗
ls <容器或线上主机的配置目录>                   # 仓库里有 ≠ 线上有

# 步 2 目标部署版本确认：跑着的是不是含这条配置的那个版本
docker inspect <容器> --format '{{.Config.Image}}'   # 镜像 tag ↔ 发布记录
git rev-parse HEAD                                   # ↔ 线上构建号对账

# 步 3 运行行为观察：外部看得见变化（最硬的一手证据）
curl -sI -H "Accept-Encoding: gzip" <URL> | grep -i content-encoding
```

**判读（三态口径）**：
- 三步中任意一步拿不到证据 ⇒ ⬜**未验证**，写明"已有线索 + 缺哪一步 + 补验证需要什么"（需要线上访问权就写"需要客户/运维提供"）。
- 只有步 3 的原始响应/日志/指标 ⇒ ✅**已验证**，并把命令与原始输出片段抄进报告。
- **注意**：配置文件中常见"变更说明"段落用 `#` 写，里面会提到该配置——那**连文本在场都不算**。

**反例（本 skill 旧版自己踩的，2026-10-12 订正）**：
```bash
grep -n "gzip" deploy/nginx-*.conf
# :23  #   ⑤ proxy_read_timeout ... ＋ 新增 gzip 块   ← 注释说明，不算
# :51      gzip on;                                  ← 未注释，但也只算「文本在场」
```
旧版在第 51 行就写"压缩已生效"；正确写法是"配置文本在场，生效未验证——缺加载确认／部署版本／响应头观察"。

### 2.7 是否有迁移/兼容机制

```bash
ls <schema目录> | grep -i "migrat\|dialect\|version"
grep -rn "schema_migrations\|alembic" <源码根>
```

**判读**：有版本账本表 + runner ⇒ 迁移器已建。

### 2.8 并发/多实例能力

```bash
grep -rn "worker\|Lock\|Semaphore\|threading" <源码根> --include=*.py | head -20
grep -rn "workers" <部署配置>
```

**判读**：
- 状态存在**进程内存** ⇒ 不能起多实例
- 状态存在**外部存储**（Redis/DB）⇒ 可多实例
- 看锁的粒度与持有时长（持锁期间有没有外部调用）

### 2.9 外部系统对接（真实 vs 替身）

```bash
ls <脚本目录>          # 看有哪些集成脚本
grep -rn "odoo\|kingdee\|yonyou\|金蝶\|用友" <源码根> | head
```

**判读**：
- 对接**通用开源件**（Odoo 等）⇒ **演示替身**
- 对接**客户真实系统**（用友/金蝶/客户 API）⇒ 生产对接
- README 里常自己承认（如"不等于企业 ERP 落地能力"）——**引用它，别自己编**

### 2.10 真实数据 vs 合成数据

```bash
grep -rn "golden\|黄金集\|合成\|synthetic\|real" <评测目录> | head -20
ls <数据目录>
```

**判读**：看清构成比例（如"70 合成 + 30 脏图 + 20 公开集"），**别把公开集当真实业务样本**。

## 三、组合探针（常见判据的完整取证链）

### 3.1 判定"某优化项到底做没做"

```bash
# 第 1 步：找线索（可能命中注释）
grep -rn "<优化项关键词>" <源码根>

# 第 2 步：找到疑似实现点，打开看
# （用 Read 工具读该文件相关行）

# 第 3 步：确认是否在调用链上
grep -rn "<函数名>" <源码根>
```

### 3.2 判定"某文件/目录的变更是否已入账"

```bash
# 若项目有哈希台账（防漂移机制）
<项目自带的核对脚本>
# 或手动算
sha256sum <文件>
```

## 四、六个藏身位探针（下「未实现」之前必须逐个走完）

> 判据在主文 `../SKILL.md` §2.2：**只查第 1 处就判"未做"是本 skill v1.2.0 之前最大的方法缺陷**。
> 这一节的每条探针都只产出两种结果：**找到线索**（回 §一 判读铁律继续）或 **未找到**（记主文 §2.3 三件套）。
> 六处全走完且无痕迹，才准写「未实现（在本报告检查范围内）」＋一句翻案条件。

### 4.1 位置① 本仓库源码内联实现

```bash
grep -rn "<关键词>" <源码根> --include=*.<后缀> | head -30
```
**判读**：命中非注释行 ⇒ 找到实现点，还要 grep 调用点确认在链上；零命中 ⇒ **本位置未找到**，继续 4.2。

### 4.2 位置② 依赖库自带（最容易漏判的一档）

```bash
# 先把依赖清单读全（一个项目常有多份）
cat requirements*.txt pyproject.toml package.json 2>/dev/null | grep -iE "<能力关键词>"
ls poetry.lock uv.lock requirements-dev.txt package-lock.json yarn.lock 2>/dev/null
pip show <库名>        # 或：npm ls <包名>   —— 确认装了什么、什么版本
```
**判读**：
- 依赖里有 retries / resilience / validation / auth 类库 ⇒ 该能力**可能由依赖提供** ⇒ ⬜**未验证**，下一步要找配置点与调用点：
  ```bash
  grep -rn "import <库名>\|from <库名>\|<库名>." <源码根> | head    # 有没有被用起来
  grep -rn "<库的装饰器或类名>" <源码根>                            # 如 @retry / Retry( / CircuitBreaker
  ```
- 装了但全项目零引用 ⇒ 「依赖在场、未使用」，仍算 **未验证**（不是"已具备"也不是"未实现"）。
- **同一个业务判断的三种合法来源**：自写循环 / 依赖库 / 网关配置。审判报告写的是**能力**，不是关键词命中位置——见主文 §2.2 红框例。

### 4.3 位置③ 框架与平台内建（默认值随版本变，必须记版本）

```bash
grep -rn "fastapi\|flask\|django\|spring\|express\|next" requirements*.txt pyproject.toml package.json 2>/dev/null
pip show fastapi django 2>/dev/null | grep -i version
```
**判读**：
- 会话、CSRF、密码散列、超时、连接池、约束检查常常是框架/数据库**内建默认**——这时"源码里搜不到"是正常现象，不等于没做。
- 要查的是**所用版本号 + 该版本默认行为**（默认值会变，如会话 cookie 的 SameSite 默认），并把版本写进报告证据行。
- 框架文档没读、默认行为没核实 ⇒ ⬜**未验证**（不许写"框架自带 ⇒ 已具备"）。

### 4.4 位置④ 代理层 / 网关 / 中间件 / 基础设施

```bash
ls deploy/ infra/ .github/workflows/ k8s/ chart/ 2>/dev/null
grep -rn "gzip\|limit_req\|proxy_next_upstream\|auth_request\|cache" deploy/ 2>/dev/null | grep -v "^\S*: *#"
```
**判读**：鉴权、限流、重试、压缩、缓存、TLS **经常根本不写在应用源码里**。
- 在部署件里命中 ⇒ 仍要回 §2.6 走三步（这份部署件真被线上加载了吗）。
- 仓库里**没有**部署件 ⇒ 「未找到（基础设施不在本仓库内，需运维/客户提供）」，**这不是"没配"**。

### 4.5 位置⑤ 动态配置与运行时数据

```bash
grep -rn "getenv\|environ\|config_center\|nacos\|apollo\|feature_flag\|开关" <源码根> | head -20
grep -rn "settings\|参数表\|config" <schema目录> | head
```
**判读**：
- 代码读的是环境变量/配置中心/数据库参数表 ⇒ 仓库里的**默认值不代表线上值**，一律记 ⬜**未验证**，补验证＝查运行环境实际值（需要客户提供）。
- ERP / 支付通道 / 审批流常常**在客户系统里已经配好**——审判报告必须写"若客户侧已提供该能力，本结论作废"这类翻案条件。

### 4.6 位置⑥ 生成代码与构建产物

```bash
ls migrations/ alembic/ db/migrate/ prisma/ generated/ dist/ build/ 2>/dev/null
grep -rn "CREATE TABLE\|CREATE INDEX\|UNIQUE" migrations/ generated/ 2>/dev/null | head
docker history <镜像> 2>/dev/null | head    # 或：进容器/构建产物里找该文件
```
**判读**：schema、脚手架、IaC、镜像内文件是**生成出来的**，源码 grep 不到属正常。产物不在仓库（CI 生成／镜像里）⇒ 「未找到（需构建产物访问权）」。

### 4.7 六处走完后怎么收口（模板行）

```
| 判据项 | 六处结果（①…②…③…④…⑤…⑥…） | 结论态 | 翻案条件 |
| 失败重试 | ①未找到 ②依赖含 urllib3 但未搜到调用点 ③未核实 ④deploy/nginx 无 proxy_next_upstream ⑤无 ⑥无 | ❓未找到（不可写"未实现"） | 若网关/SDK 侧统一重试，本结论作废 |
```

## 五、业务场景贴合度探针（"跑得通" ≠ "用得上"）

> 这一组探针查的不是"功能有没有"，是"**功能在真实场景会不会被用、用了会不会出错、出错谁兜**"。
> 行业共识：**AP/AI 自动化项目不是死在模型上，是死在主数据、异常归属、阈值分档、写回验证这四个地方**。
>
> 🔴 **三条适用前提（v1.2.0 加）**：
> 1. 本节的**行业原话只是提问线索**（抗幻觉口径里的 C 级证据），**不作为本项目结论的依据**。要引用进报告必须去 `references/industry-ap-finance.md` §二 登记表拿带**来源·日期·版本·适用范围·可信度**的条目；登记表里标 `未采到`／`二手` 的，报告里就得照样标，且**不许拿去给项目打分**。
> 2. 本节只适用于**财务应付／三单匹配／单据自动化**这一类场景。审别的品类时照那包的五节结构另建行业包，别套用发票内容（判据见主文 §4.4）。
> 3. 下面每条"判读"里的"无 X ⇒ 风险未解"，都只在**六处（§四）走完且三件套记全**之后才成立；否则结论是 ❓**未找到**，风险分按主文 §5 Step 7 记「下限估计（证据不全）」。

### 5.1 主数据可对齐（**最高频失败点**）

```bash
grep -rn "normalize\|dedup\|去重\|标准化\|canonical" <源码根> --include=*.py | head
grep -rn "UNIQUE" <schema目录>
```
**判读**：无规范化层、无唯一键 ⇒ **主数据风险未解**。即使抽取准确率 100%，也无法自动匹配（"分不清这张票是哪个 Acme"）。

### 5.2 异常归属

```bash
grep -rn "exception\|异常\|exception_queue\|待处理" <源码根> --include=*.py | head -20
```
**判读**：只有"待处理"一个状态 ⇒ **异常无归属**；按原因分类 + 带责任方路由 ⇒ ✅。
行业原话：*"'供应商不在主数据里' 与 '数量偏差 3%' 是不同人的不同问题。"*

### 5.3 置信阈值分档

```bash
grep -rn "confidence\|阈值\|threshold\|shadow\|影子\|auto_post\|自动过账" <源码根> --include=*.py | head -20
```
**判读**：硬编码阈值 ⇒ 🔶；有**影子 → 建议 → 自动**三档开关 ⇒ ✅。
行业纪律：**跳过这个序列会造成信任崩塌**（"十二周项目变二十周"）。

### 5.4 ERP 写回验证（**行业公认最难一环**）

```bash
ls <集成脚本目录>
grep -rn "retry\|rollback\|writeback\|回写\|status" <集成脚本目录> | head
grep -rn "reject\|失败\|retry" <测试目录> | head
```
**判读**：只有 happy path、无重试/回滚/状态回写、无失败路径测试 ⇒ **写回未验证**。
行业原话：*"ERP 写回始终是最难的阶段——不是集成不可能，而是跨实体、跨币种、跨科目表正确过账需要对这套 ERP 实例的实际配置有详细理解。"*

### 5.5 基线是否先立（**最常被跳过**）

```bash
ls <项目文档目录> | grep -i "基线\|baseline\|benchmark\|对比"
grep -rn "cycle_time\|cost_per\|touchless\|直通率\|异常率" <源码根> <文档目录> | head
```
**判读**：无改前改后基线 ⇒ 即使功能完备，**也无法证明 ROI**，卡在第二层。
行业原话：*"先给人工流程埋点——测不出团队现在的水平，就没有基线，也就没有阈值放进回滚条件。"*

### 5.6 失败可逆性分级

```bash
grep -rn "payment\|支付\|delete\|删除\|commit\|无审批" <源码根> --include=*.py | head -20
```
**判读**：动作分三级——**只读（低危）/ 可逆写（中危，需审批）/ 不可逆（高危，需双人复核）**。高危无管控 ⇒ 第三层未过。
行业共识：*"决定性判据是可逆性。若一个错误动作无法被检测或回滚，无论基准分多高，设计都太宽。"*

### 5.7 指标口径（活动量 vs 业务成果）

```bash
grep -rn "metrics\|KPI\|count\|统计" <源码根> --include=*.py | head -20
```
**判读**：全是"处理了多少条/调用多少次" ⇒ **活动量指标**（行业警告叫 `tokenmaxxing`）；有"直通率/异常率/纠错率/单票成本" ⇒ **业务成果指标**。前者必须补后者。

## 六、联网取证探针（外部判据）

> 探针查"本项目现状"，联网查"外部要求"。**外部数据只能定严重度，不能定有无。**
> 外部锚的**现值**（版本号、生效日期、是否强制）一律以 `references/external-benchmarks.md` 为准，本节只管"怎么搜、怎么落表"。

### 6.1 三条固定检索线

| 线 | 检索词模板 | 落进报告哪一节 |
|---|---|---|
| ① 法规/标准 | `<品类> <当前年份> 合规要求 最新 监管` ／ `<标准名> <最新版本号> release` | 报告 §三 合规阻塞、§五 5.1 法规时间线 |
| ② 竞品功能 | `<竞品A> <竞品B> <品类> 功能对比 <当前年份>` | 报告 §五 5.2 竞品功能对照 |
| ③ 失败案例 | `<品类> 项目 失败原因 落地 <当前年份>` | 报告 §六 场景判别 + §七 施工路线"坑"栏 |

**财务/AP 类的现成检索词**见 `references/industry-ap-finance.md` §四；用之前把年份换成**当次检索的实际年份**（写死年份的检索词＝过期证据）。

🔴 **检索年份必须用"当前年份"**（模型知识有截止日，拿训练记忆里的"最新"当最新是本项目最常见的假外部判据）。核标准版本时优先查**官方仓库的 releases / 官方发布页**，而不是二手综述文章。

### 6.2 外部判据落表格式（🔴 v1.2.0 起改成七列，少一列就标 `未采到`）

```
| 判据 | 外部要求/竞品水平 | 来源（机构＋标准/报告名＋版本号或年号） | 发布日期 | 我方检索日期 | 适用范围 | 可信度（一手/二手/未采到） | 本项目探针结论（三态） | 判读 |
```

- 「版本号或年号」是**必填**：写"OWASP ASVS"不合格，写"`ASVS 5.0.0`（2025-05-30 发布）"才合格——版本一变条款号与判据一起变。
- 「本项目探针结论」列只能填三态之一，且必须由 §二～§四 的探针输出支撑。

### 6.3 联网判读铁律（与主文 §4.2 五条同源）

1. **外部数据只定严重度**（"行业 90% 缺 X" ≠ "本项目缺 X"）。
2. **带版本号与日期引用**（法规/竞品/标准是强时变数据；无年号的标准名一律降级为"待核实"）。
3. **优先一手来源**（官方原文/官方仓库/官网功能页/G2·Capterra 等第三方评测）；引不到原文就标 `二手`。
4. **搜不到就写搜不到**，并把实际用的检索词记进报告 §十一，绝不拿模糊记忆冒充。
5. **采不到一手锚的框架只能当提问清单**：例如 Production Safety Framework 的"八域 32 控制"这类在官方处找不着一手锚的说法，**禁止写成"本项目符合/不符合该框架"**，也禁止用它给项目打分（细则见 `references/external-benchmarks.md` §二）。

## 八、探针设计练习（自测）

拿到一个新项目，回答这些问题该用什么命令？

1. 它的数据层收口了吗？
2. 它有监控吗？是端点还是真有数据？
3. 它能不能起多实例？
4. 它对接的是真实系统还是替身？
5. 它的评测数据是真实的还是合成的？
6. 它的某条"优化项"到底做没做？
7. **它的主数据能对齐吗？（最高频失败点）**
8. **它的异常按原因分类路由了吗？**
9. **它的置信阈值能配、能分档推进吗？**
10. **它的 ERP 写回验证过失败路径吗？**
11. **它有没有改前改后的基线？**
12. **它的指标是业务成果还是活动量？**
13. 🔴 **你这条"未实现"把 §四 六个藏身位走完了吗？三件套（范围／关键词／未检查范围）写得出来吗？**
14. 🔴 **这个能力如果不在源码里、而在依赖库或网关里，你的探针还能发现它吗？换个什么命令能发现？**
15. 🔴 **你说"配置已生效"——加载确认、部署版本对账、运行行为观察这三步各跑了吗？拿哪条原始输出当证据？**
16. 🔴 **同一项业务能力的两种实现（自写循环 vs 依赖库/网关）在你的报告里给出的是同一个业务判断吗？为什么会不一样？**

> 1-6 答不出 → 回 §二 找通用探针形态。
> 7-12 答不出 → 回 §五 找场景贴合探针。
> 13-16 答不出 → 回 §四（六个藏身位）与主文 §2.1／§2.3／§2.4（三态、三件套、三步）。
> 记住：**探针的价值不在命令本身，在"你知道该问什么、以及看到输出该怎么判"。**
