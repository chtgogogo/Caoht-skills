# 行业参考包 · 财务应付（AP）/ 三单匹配 / 单据自动化

> **这是什么**：一支**行业示例包**——把「审某个具体行业时要问的业务问题、该行业公认的失败模式、外部对标数字」从主文里搬出来单独住。主文（`../SKILL.md`）不含任何行业专有内容。
> **为什么需要它**：2026-10-11 外部审查指出，本 skill 原先把财务/AP 的行业内容直接内联在主文里，导致「审一个客服机器人」也得先读一遍发票匹配规则，而且读者会误以为那些行业数字是通用判据。
> **怎么用**：审判**财务/AP/单据类**项目时读本包。**审别的品类时照本包的结构另建一份行业包**（同一套五节：判别清单 / 外部判据登记表 / 竞品对照 / 检索线 / 已知缺口），不要套用本包的发票内容。

**三条硬纪律**

1. **本包只定「严重度」和「该问什么」，不定「本项目有没有」。** 后者只能靠代码探针，且必须按主文 §2 的三态（已验证 / 未找到 / 未验证）落账。
2. **本包所有数字都是检索快照**（采集于 2026-10-08），**引用前必须重新联网复核**并按 §二的登记表补齐「来源 / 日期 / 版本 / 适用范围 / 可信度」五列。缺列就写「未采到」。
3. **本包是二手资料为主**——§五 逐条写明了哪些没有一手出处。没有一手出处的条目**不得写成"行业标准"**，只能写成"某机构报告称"。

## 一、业务场景七条判别（"跑得通" ≠ "用得上"）

> 行业共识：这类项目不是死在识别模型上，是死在主数据、异常归属、阈值分档、写回验证上。
> 每条给出：**行业原话 → 判别探针 → 判读 → 三态归口提示**（探针没跑到的那一档必须落「未验证」而不是「未做」）。

### 判别一 · 主数据是否可对齐（最高频失败点）

**行业原话**：*"项目不是死在抽取上，是死在主数据上。"* 供应商主数据有重复、命名不一致、无可信 join key 时，再准的抽取也无法自动匹配——系统分不清这张票是哪个 "Acme"。

**判别探针**：

```bash
# 有没有供应商/客户主数据治理机制（去重、标准化、唯一键）
grep -rn "normalize\|dedup\|去重\|标准化\|canonical" <源码根> --include=*.py | head
grep -rn "UNIQUE" <schema目录>
```

**判读**：有规范化层 + 唯一键约束 ⇒ 已验证；只有其中一项 ⇒ 已验证（范围受限，注明缺的那半）；两处都搜不到 ⇒ **未找到**（≠ 没有主数据治理：治理可能在 ERP 侧、在数据库约束里、在导入脚本里、在人工流程里，按主文 §2.2「能力可能藏身的六个位置」走完才能升格为"未实现"）。

### 判别二 · 异常是否有归属（"有队列" ≠ "有归属"）

**行业原话**：*"'供应商不在主数据里' 与 '数量偏差 3%' 是不同人的不同问题。"* 异常若全扔进一个无差别队列，等于没处理。

**判别探针**：

```bash
grep -rn "exception\|异常\|exception_queue\|待处理" <源码根> --include=*.py | head -20
```

**判读**：看异常**是否按原因分类**、**是否带责任方路由**。只有"待处理"一个状态 ⇒ 已验证（有队列）＋已验证（无归属）两句话分开写，别合并成"异常处理没做"。

### 判别三 · 置信阈值是否可配、是否分档推进

**行业原话**：*"置信阈值是最重要的一个数字，且它是业务决策而非技术决策。"* 必须分档推进：**影子模式 → 建议模式 → 窄范围自动过账**，跳过这个序列会造成信任崩塌（"三周项目变二十周"）。

**判别探针**：

```bash
grep -rn "confidence\|阈值\|threshold\|shadow\|影子\|auto_post\|自动过账" <源码根> --include=*.py | head -20
```

**判读**：硬编码阈值但无配置项 ⇒ 已验证（阈值存在）＋未验证（能否按客户改）；有影子/建议/自动三档开关 ⇒ 已验证。**代码里搜不到三档不等于没有**：分档常写在配置中心、数据库参数表或运维手册里，按主文 §2.2 六个位置走完再判。

### 判别四 · 写回 ERP 是否被验证（行业公认最难一环）

**行业原话**：*"ERP 写回始终是最难的阶段——不是集成不可能，而是'跨实体、跨币种、跨科目表正确过账'需要对这套 ERP 实例的实际配置有详细理解。"* 试点期必须**验证失败路径**：不仅测成功过账，还要测被拒记录、重试、状态回写。

**判别探针**：

```bash
ls <集成脚本目录>
grep -rn "retry\|rollback\|status\|回写\|writeback" <集成脚本目录> | head -20
grep -rn "reject\|失败\|retry" <测试目录> | head
```

**判读**：只有 happy path、无重试/回滚/状态回写、无失败路径测试 ⇒ 已验证（做过成功路径）＋**未验证**（失败路径没跑过）。"失败路径未验证"和"没有重试代码"是两句不同的话，报告里必须分开。

### 判别五 · 基线是否先立（最常被跳过的一步）

**行业原话**：*"先给人工流程埋点——若你测不出团队现在做到什么水平，就没有基线，也就没有阈值可放进回滚条件。"*

**判别探针**：

```bash
ls <项目文档目录> | grep -i "基线\|baseline\|benchmark\|对比"
grep -rn "cycle_time\|cost_per\|touchless\|直通率\|异常率" <源码根> <文档目录> | head
```

**判读**：无基线记录 ⇒ 即使功能做完也无法证明 ROI，卡在第二层（客户要真实 ROI 数字）。**基线常常在客户那边而不在代码里**（客户的人工处理时长他们才知道），这一条最常落成「未找到（需客户提供）」而非「未做」。

### 判别六 · 失败可逆性分级（决定"能不能自主跑"）

**行业共识**：*"决定性判据是可逆性。"* 可回滚、可审批、可升级的动作才能放给 agent 自主。**若一个错误动作无法被检测或回滚，无论基准分多高，设计都太宽。**

**判别探针**：

```bash
grep -rn "无审批\|direct\|commit\|支付\|payment\|删除\|delete" <源码根> --include=*.py | head -20
```

**判读**：把动作分三级——**只读（低危）/ 可逆写（中危，需审批）/ 不可逆（高危，需双人复核）**。高危动作无管控 ⇒ 第三层不过。**注意审批/复核常在 BPM 工作流引擎或 ERP 自带审批流里**，本仓库搜不到 ≠ 没有。

### 判别七 · 指标是否按"业务成果"而非"活动量"计

**行业警告**：*"tokenmaxxing"* ——优化 token 消耗、任务发起数、输出条数这类**活动量**而非**已验证的业务成果**，会产出忙碌但低质的工作。

**判别探针**：

```bash
grep -rn "metrics\|指标\|KPI\|count\|统计" <源码根> --include=*.py | head -20
```

**判读**：全是"处理了多少条/调用多少次" ⇒ 活动量指标；有"直通率/异常率/纠错率/单票成本" ⇒ 业务成果指标。前者必须补后者。

> **七条一句话总结**：主数据能不能对齐 + 异常有没有归属 + 阈值能不能分档 + 写回有没有验证 + 基线有没有先立 + 失败能不能回滚 + 指标是不是业务成果。

## 二、外部判据登记表（本包的数字都用这张表管）

**表头固定六列，缺一不可**：

```
| # | 事实主张 | 数值 | 来源（机构 + 报告名 + 版次/年份） | 检索日期 / 发布日期 | 适用范围（哪个市场/哪类企业/是否强制） | 可信度 |
```

| 项 | 现值/口径 | 出处要求 | 适用范围 | 强制吗 |

| 等保（中国大陆） | 现行核心标准 GB/T 22239-2019（等保 2.0），五级定级 | 以公安部/全国网安标委正式文件为准，注明标准号与年号 | 在中国境内运营的网络系统 | **法定**（网络安全法要求），但"该不该定级、定几级"要看系统归属与监管口径 |

**三条对照纪律**

1. 引用竞品公开数据必须标来源与日期（评级/功能会变）。
2. 不拿"竞品宣传的直通率"当本项目目标——高直通率通常反映窄分母，要问含不含无 PO 的服务类发票。
3. **竞品有而本项目无 ≠ 必须补**。要过主文 §3 Step 6 的标签：是 🧩 能力差距，还是 ⬜ 目标本就不匹配（如面向国内中小企业的项目不需要 196 国支付通道）。打 ⬜ 必须写理由。

## 四、检索线关键词模板（本行业版）

```
① 法规线：发票 电子发票 财税合规 最新要求 <当前年份> / 数电票 政策 时间线
② 竞品线：Stampli Vic.ai Tipalti 每刻 金蝶 用友 AP自动化 三单匹配 功能对比 <当前年份>
③ 失败线：AP自动化 发票处理 落地失败 ERP集成 数据质量 原因 <当前年份>
④ 认证线：等保 2.0 定级 要求 <当前年份> / ISO 27001 现行版本 / SOC 2 Type II 区别
```

**复核方法**（每次审判都要重跑，不许引用本包现值）：每条命中记「机构 + 页面标题 + URL + 发布日期 + 我方检索日期」，回填 §二 的登记表；搜不到权威来源就写「未检索到权威来源」，**绝不拿本包的旧值冒充最新**。

## 五、本包已知缺口（诚实清单）

1. **AP-01～AP-04 没有一手 URL**（当时只记了机构名与数字）。引用时必须保留 `二手` 标注，或重查后升格。
2. **AP-05、AP-06 连机构都没锁定**（可信度 `未采到`）：这两条**只能当提问线索，不能当论据**，更不允许写进对外的汇报数字。
3. 本包的行业原话引语出自 2026-10-08 的检索结果，**未逐条留出处**，若要在正式报告里引用需重找原文。
4. 本包**不是**任何其他行业的判据。别的项目品类（客服、风控、制造、医疗……）请照本包结构新建行业包。
5. 法规/认证/竞品数据都是**强时变**的。本包任何条目被引用时，先按主文军规 5 重跑检索；**过期不是本包的错，不复核就用是报告的错**。
