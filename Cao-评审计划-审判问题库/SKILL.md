# 评审计划（plan-review）——计划审判问题库

> 一句话：拿着一张越审越厚的审判问题库，逐题过堂还没动工的计划，把麻烦在开工前挖出来。**库只增不删：每次审判发现的新问题类型，审完必须沉淀回库——这是本 skill 的命根子，审完不沉淀=本次审判只值一半。**

## 何时读问题库
触发后先读 [references/审判问题库.md](references/审判问题库.md)（10 类 50 题起步），再按下方流程过堂。要学本案完整攻防过程，读 [references/案例-LLMwiki计数装置三轮.md](references/案例-LLMwiki计数装置三轮.md)。

## 与邻居的分工
| 拿到的东西 | 用谁 |
|---|---|
| 还没动工的计划/方案/设计 | **本 skill** |
| 已建成的项目要交付验收 | project-acceptance（项目验收官） |
| 写好的代码要审 | coding-behavior / senior-engineer-playbook 模板② |
| 要盘问的是"计划作者本人"（访谈式） | grill-me / grill-with-docs |
| 要给 skill 打分优化 | skill-quality-auditor |

## 审判流程（五步）
1. **通读+要素清单**：把计划里全部「承诺（铁则/口号）/机制（怎么运转）/验收（怎么算成）」列成一张表——后面每道题都对着这三类要素问。
2. **逐类过堂**：按问题库全部类别（A~N，随库生长）逐题判定三态。**E 类（验收与度量）过堂时，验收标准的证据形态遵循 `A-Cao-测试纪律`（原始输出落盘/改前改后各跑/口径标注/禁只报总结数字）——计划里的"测试全绿""效果良好"若无证据形态，按中招处理**：
   - ✗ **中招**：引计划原文为证 + 何时会爆 + 修法建议
   - ? **存疑**：信息不足，列出要问谁、要实测什么
   - ✓ **通过**：一句话理由
   不讨好：批语对事不对人但绝不放过；被审方反驳就进入交锋，谁有理听谁的，裁决过程全部留痕。
3. **分级聚焦**：中招项分 致命/重要/细节 三级；报告结尾只保留**最致命 ≤3 条**。
4. **复审闭环**：计划方修订后，对上轮中招/存疑项逐条销账复核；修订引入新嫌疑则该类重过。全绿才算过堂。
5. **沉淀回库（必做）**：本次新发现、库里没有的问题类型，按库内条目格式**追加**进审判问题库（编号只增不重排、注明来源案例与日期；作废题标 `retired` 保留编号）；典型单点坑另按其流程沉淀踩坑日志（pitfall-log）。

## 可靠性主张四问（最锋利的一组，审任何机制先过这四问）
1. **爆炸半径**：它挂了会怎样？损失上限？（警告：**有界≠可靠**——代价可控不等于不用补强，金库损失有上限仍需要门）
2. **发现机制**：它挂了**谁**、在**哪个必做动作**里会发现？（必须挂进既有 checklist 必做项；"写在文档里/记得去看"=没挂）
3. **兜底自检**：降级链的兜底是不是就是原始病？（兜底="AI 凭记忆手动干"而病根恰是"AI 凭记忆不可靠"→视为未兜底）
4. **档位与前提**：可靠性按用途定档（参考级/榜单级/审计级）；**档位成立的限定条件必须显式写**（典型："只作参考+任何动作必人工确认"；未来若接自动化，必须按高档重评）。碰巧做对的防护要升格为"边界成立的前提条件"，机制会被人优化掉，写进论证的前提不会。

## 《审判报告》骨架
```
# 《XX计划》审判报告（第 N 轮）
- 一句话结论：能否动工（能 / 修订后能 / 不能）+ 最致命 ≤3 条
- 逐题裁决表：A~J 十类 × 三态；中招项附[证据原文｜何时爆｜修法]
- 存疑清单：要问谁、要实测什么
- 复审记录：上轮中招项销账情况
- 沉淀：本轮新增问题 Qxx（已回库，CHANGELOG 已记）
```

## 沉淀纪律
- 问题库**只增不删**；作废标 `retired` 保留编号（防历史引用失效）
- 每题必有四要素：问什么 / 为何是坑 / 何时爆 / 怎么查；有真实案例的附来源
- 新题编号=读库取当前最大号+1，禁止沿用记忆中的旧号
- 版本号只在 SKILL.md；问题库与流程的改动记 CHANGELOG
