## 第 0 章 五分钟速览

1. **它管的是五个问题，不是三个**。别人给了你一个 GitHub（全球最大的代码托管网站）仓库链接，或者只丢一句「找个同类实现参考参考」，你都要在几十分钟内回答：**看哪个（选靶）→ 能不能用（许可证边界）→ 值不值得看（价值评级）→ 怎么拿回来（取证与解码）→ 沉到哪里（沉淀与回注）**。正文把中间三问答得很硬，第一问几乎空白、最后一问只给了模板——本页第 4 章补前者，第 8 章扩后者。
2. **七步流水线，顺序不能乱**：识别工程上下文 → 查询 → 价值判断 → 下载决策 → 文档更新 → 编码注意 → 完成检查（即 `SKILL.md`「工作流」§1–§7）。前一步的产出是后一步的输入，跳步的代价逐条列在第 10 章。
3. **拉取一律优先 `gh` CLI（GitHub 官方命令行工具，登录后自带鉴权）**，匿名直连 API（不登录的程序化访问接口）只作兜底（兜底＝主路走不通时的备用路）。本页取证当天实测鉴权后核心配额 **5,000 次／小时**、搜索配额 **30 次／分钟**（数法：读 `rate_limit` 返回体的 `resources.core.limit` 与 `resources.search.limit` 两个字段）；正文断言的匿名 60 次／小时未独立复核。**配额差是数量级的，这就是「优先 gh」的全部理由**。
4. **许可证（License，作者写的「你能怎么用这份代码」的法律条款）查表判定，不许凭感觉**：六行决策矩阵（正文「§4 下载决策矩阵」）把 MIT／Apache／CC0、GPL／AGPL、无 License、Private、超大仓库、纯文档索引六种情况各自的**动作**和**存放位置**都写死了。这张表的立场很清楚：**边界层有权否决判断层**——仓库再有用，许可不允许就是不允许。
5. **一条会救命的补查规则，本页把它扩成三级**：API 的 `licenseInfo`（许可证元数据字段）经常返回 null（空值），多数时候仓库其实是有许可证的。正文只要求「null 时再查根目录 LICENSE 文件」；本页取证当天实测到一类**根目录也没有许可证文件、许可证写在 README 里**的仓库（`jlevy/the-art-of-command-line`：实测 REST 的 `.license` 为 null、根目录按 `licen|copying` 匹配列出的文件是**空清单**、README 里有一节 `## License` 声明 CC BY-SA 4.0；实测 162,396 star）——所以补了第三级。
6. **base64 解码是结构性防线，不是提醒**：`contents`（按路径点取单个文件的接口）返回的 `content` 是编码后的字符串（base64＝把任意字节翻成纯文本字符的编码方式），直接落盘（写进硬盘文件）会得到「文件名正常、打开全是乱码」的源码。规则把解码写死在唯一推荐的命令里，让这类事故在结构上发生不了。
7. **分析完必须沉淀**（沉淀＝把结论写成文件留在仓库里，而不是留在对话里）：流程第一步就检查有没有文档体系，没有就先建 `DOCS_INDEX.md`（文档总索引）再开始分析，否则下一轮会话全部归零。这条把「容器先于动作」写进了顺序，是整套 SOP 最反直觉也最值钱的设计。

**一句话设计目标**：把「逛开源仓库」这件最容易变成瞎逛的事，变成一条**每个环节都有可执行判据（能拿一条命令跑出真／假的标准）、越权动作会被表挡住的流水线**。

## 第 1 章 这套系统在解决什么问题

不装这套 SOP 的人，翻开源仓库时会撞上九种具体故障。下面这张表是本页的骨架：每一行都是一个「真实会让人返工」的场景。

| # | 故障 | 表现（不修会怎样） | 本 skill 的解法（正文出处／本页补） |
|---|---|---|---|
| ① | **没有靶子** | 用户只说「找个同类实现」，你现场随便挑一个看起来火的仓库，读完发现许可证不对、或者三年没维护 | 正文**未覆盖**（「触发条件」原文只认「用户提供 GitHub 仓库链接或列表」）；本页第 4 章按官方检索限定符补一层可执行选靶判据 `[本页补]` |
| ② | **限流掐断** | 匿名直连 API 翻两个仓库就被拒，后面所有查询集体失败，任务卡在「还没看到代码」 | 「§2 查询阶段」：优先 `gh` CLI 鉴权拉取，`api.github.com` 直连仅作兜底 |
| ③ | **License 雷** | 凭「看起来是开源的」就把代码抄进工程，日后商用时才发现原作者只给了学习权限 | 「§4 下载决策矩阵」＋版权红线句：禁止商用素材绝不纳入 |
| ④ | **误判无许可证** | `licenseInfo` 返回 null 就直接当「没许可证」处理，把一份 MIT 仓库判成不可用，白白放弃 | 「License 检测补充」段：null 时额外检查根目录 `LICENSE`／`COPYING`／`LICENSE.md` |
| ⑤ | **乱码沉睡** | base64 原文当源码存盘，文件名正常、大小也对，几周后要用才发现全是乱码，且早忘了来自哪个仓库 | 「文件内容解码落盘」条：解码写死在 `--jq '.content' \| base64 -d` 这条管道里 |
| ⑥ | **结论蒸发** | 分析全在对话里，会话一结束归零；同一个仓库下周被重新分析一遍，还得出不同结论 | 「§1 识别工程上下文」＋「§5 文档更新」：没文档体系先建，再开始分析 |
| ⑦ | **中文写坏** | 用 PowerShell 管道（Windows 自带命令行的命令流传递机制）传中文，写进文件变成问号；分析报告直接不可读 | 「§6 编码注意」：指定 utf-8 写、写后验证「中文字符数 > 0 且问号数 = 0」 |
| ⑧ | **好坏凭感觉** | 「这仓库挺牛的」不算判据，两个仓库到底抄谁的思路，最后靠嗓门大决定 | 「§3 价值判断矩阵（5 维度）」＋六档星级；同类实现追加方法对比表 |
| ⑨ | **照抄命令就报错** | 正文命令表里的字段名与工具实际字段名不一致，第一次跑的人把报错理解成「我没权限／仓库不存在」，排障方向整个跑偏 | 正文**未修**；本页 §5.3 实测出**三套命令族三套字段名**这一结构性原因，并给出各自的正确名 |

**其中 ①③④ 最贵**——②⑤⑦ 浪费的是时间，返工就能补回来；①③④ 浪费的是「已经交付出去的东西」：选错靶子会把整轮工时投在一个用不上的仓库上，踩许可证雷要拆已经上线的资产。**所以第 7 章（许可证层）写得比第 5 章（拉取层）还细，第 4 章（选靶层）是正文没有、本页硬补的一层；这个篇幅分配是刻意的，不是失控。**

**还有一个隐性故障不在这张表里**：把「读仓库」做成「读 README」。README（项目自我介绍文档）写得漂亮不等于代码可用，很多真价值藏在 `autoload/`、`src/core/` 这类目录结构和几个关键源文件里。所以正文「§2 查询阶段」把元数据、目录树、README、关键源码列成**四个并列字段**，各配一条命令（实测该表共 4 行，数法：数正文表格的数据行数）。四个字段是四类**互相独立的事实**，少任何一个，后面的结论就有一部分是想象出来的。

## 第 2 章 术语表

本页所有术语在这里给一句大白话。中文行话同样解释——不认识词的人不该被迫回头查词典。

| 术语 | 一句大白话 |
|---|---|
| **仓库 / repo** | 一个项目的所有文件加上历史记录，托管在 GitHub 上的那一份 |
| **克隆 / clone** | 把仓库整份拉到本地（连同历史），一条命令下载整个项目 |
| **点取** | 不整份下载，只按路径单独取几个文件；正文对大仓库就是这么规定的 |
| **拉取 / pull** | 从远端把新内容取下来；本页泛指「把仓库内容弄到本地」，不特指 git pull |
| **上游** | 代码的原始出处，即你抄思路的那个仓库；改坏了还能回到上游重看 |
| **元数据** | 描述仓库的数据：star 数、许可证、主语言、更新时间，不含任何代码 |
| **目录树 / tree** | 仓库里所有文件路径的清单，递归（连子目录一起列）一次可拿到全部条目 |
| **骨架** | 只要目录结构和少量关键文件，不要完整内容——学组织方式用，不用于跑起来 |
| **`gh` CLI** | GitHub 官方命令行工具；登录后可直接查仓库、拉文件，自带鉴权 |
| **鉴权** | 让服务器知道「你是谁」，因此配额更高、私有内容才读得到 |
| **API / 直连** | 程序化访问的接口；「直连」指不借助 `gh`，自己发 HTTP 请求 |
| **REST 接口** | 一种按「路径＋动作」组织的老式接口家族（`/repos/{o}/{r}` 那一族） |
| **GraphQL** | 另一种「你自己声明要哪些字段」的查询接口家族，`gh repo view --json` 走的是它 |
| **字段名家族** | 同一件事在不同接口里叫不同名字；本页 §5.3 的三条报错全部源于此 |
| **限流 / 配额** | 服务器按时间窗口限制你能问多少次，超了就拒绝；实测鉴权核心 5,000 次／小时、搜索 30 次／分钟 |
| **兜底** | 主路走不通时的备用路，本 skill 里＝用 Python 标准库 `urllib.request` 直连 API |
| **检索式 / query** | 你向搜索接口提交的那串条件，例如「语言是 GDScript 且 star 大于 100」 |
| **限定符 / qualifier** | 检索式里的筛选小词，形如 `language:`、`stars:`、`topic:`，一个词管一个条件 |
| **召回** | 一条检索式一共捞出多少候选；捞太少叫召回不足，捞太多叫噪声大 |
| **`total_count`** | 搜索接口报告「这条检索式总共命中多少个」，不等于它这次给你的条数 |
| **`incomplete_results`** | 搜索接口自报「这次结果不完整」的是／否字段；为真时不能当全量用 |
| **代码检索 / code search** | 按文件内容找代码的接口；官方说明它由老一代引擎供数据，结果可能与网页上看不一致 |
| **归档 / archived** | 仓库被作者标为「不再维护」；读它的设计可以，指望它当依赖不行 |
| **探针** | 只检查不改东西的脚本或命令；用来回答「这个仓库到底多大、有没有 LICENSE 文件」 |
| **判据** | 可执行的判定标准，能一条命令跑出真／假；「感觉挺有用」不是判据 |
| **base64** | 把任意字节翻成纯文本字符的编码，接口用它塞文件内容，**用前必须解码** |
| **落盘** | 把内存里的数据写成硬盘上的文件 |
| **`--jq` / jq** | 一个在命令行里从 JSON（一种用键值对表数据的文本格式）里挑字段的工具 |
| **管道** | 把上一条命令的输出直接喂给下一条命令，形如 `A \| B` |
| **raw 头** | 请求时声明「我要纯文本而不是 JSON」的那个 HTTP 头，值为 `application/vnd.github.raw` |
| **License / 许可证** | 作者写的「你能怎么用这份东西」的法律条款，决定你允许下载、修改还是发布 |
| **SPDX 标识** | 许可证的标准短代号（如 `MIT`、`AGPL-3.0`），机器认它不认人话 |
| **NOASSERTION / Other** | GitHub 认不出许可证种类时的占位值：**不等于随便用**，必须读原文 |
| **copyleft（著佐权）** | 一类要求你的衍生作品也用同样许可证的条款，GPL／AGPL 是代表 |
| **CC0 / 公共领域** | 作者放弃所有权利，随便用不用致谢，是资产类素材最理想的状态 |
| **CC-BY-NC** | 署名且**禁止商用**的创作共用许可；本 skill 的硬红线是绝不纳入工程 |
| **价值判断矩阵** | 把「有没有用」拆成 5 个互不遮挡的维度分别看的表 |
| **转译** | 不抄代码，把另一种语言／框架的设计思路搬过来用（如把 C# 的做法改成 GDScript） |
| **抽象阶梯** | 从「这行代码怎么写」往上走到「它到底解决什么问题」；提炼有用内容的核心动作 |
| **六档星级** | ★★★★★ 核心参考 → ☆ 无用，正文给的分级刻度 |
| **沉淀** | 结论写成仓库里的文件，而不是一句对话；下次能被搜到 |
| **回写** | 把新结论写回已有的固定文档位置，而不是新建一份散落文件 |
| **双文档体系** | 同一份内容写两份：一份给 AI 读（结构化、给模型看），一份给人读（顺、能读通） |
| **DOCS_INDEX** | 文档总目录文件，新增一份分析就往里登记一行，防止文档变成无人认领的散页 |
| **前缀命名** | 下载文件时冠上来源缩写（`VS_` ＝ vampire-survivors），保证任何文件都能反查上游 |
| **勾稽** | 两处数字能互相对上；如「清单条目数＝文档里的章节数」 |
| **幂等** | 重复做结果不变；重复下载同一仓库不该产生两份副本 |
| **回注** | 把内容重新塞回 AI 的上下文窗口；沉淀下来的文档下次能被读进来 |
| **上下文窗口** | 一次对话里模型能同时装下多少文字；超了就把早期的挤出去 |
| **渐进披露** | 先只加载最轻的目录，用到才读下一层文件；Agent Skills 规范推荐的组织方式 |
| **`references/` `scripts/` `assets/`** | skill 的三种分包目录：技术文档、可执行脚本、静态模板与数据 |
| **冷启动** | 工程里还没有任何文档体系、第一次跑这套流程的状态 |
| **star** | GitHub 上别人给仓库点的「收藏」数，热度信号，**不是质量判据** |
| **sha256 / md5** | 把文件压成一串固定长度指纹，用于比对两份副本是否逐字一致 |
| **可证伪** | 结论附带「什么输入会推翻它」；本页每条数值都给得出复算方法 |
| **一手来源** | 信息出自产生它的那个地方（仓库自己的 LICENSE 原文），不是别人的转述 |
| **延迟暴露** | 错误当场不报，几周后才现形；base64 原文落盘是教科书案例 |
| **降级** | 主判据拿不到时改用较粗的判据，并在条目里写明降级了；**降级不是不判** |

### 3.2 四层归并的分工理由

把七步归并成四层，是这套 SOP 能被讲清楚的关键（**这层归并是本页的组织方式，属 `[推演]`**；正文只给七步平铺。反证：若不归并，读者容易把 §6「编码注意」误当成可选步骤——按层看它是「保真层」，属于「产出必须能被读」这一硬性要求。`[推演]` 的具体失效输入：把 §6 当可选、改用 PowerShell 管道写中文分析报告，第二天打开满屏问号，整份文档无法回注给下一次会话，当初那批检索式与判断依据也一起作废）。

- **定位层（§1）**：先问「我在哪个工程里」。同一个仓库，对游戏工程和对 Web 工程的价值完全不同——正文的五维表特意给了游戏／Web／AI 三列示例，就是为了这一步能把上下文带进后面的判断。
- **取证层（§2 ＋ 本页第 4 章的选靶）**：只拿事实，不下结论。这一层最忌讳「顺手判断一下」——一旦在取证阶段就带偏好，后面的价值判断会退化成给直觉找证据。
- **判断层（§3）＋边界层（§4）**：两套**互不替换**的判断。§3 问「有没有用」，§4 问「允不允许用」。常见误用是拿前者覆盖后者：仓库有用 → 下载了 → 许可证其实不允许。§4 的设计立场很明确：**边界层有权否决判断层，而且它只加限制、不加许可**。
- **沉淀层（§5）＋保真层（§6）＋验收层（§7）**：这三个是「让这次劳动能留下」的闭环。§5 写、§6 保证写进去的是能读的字、§7 保证没漏。

### 3.3 判定顺序：四条判定链（顺序不可交换）

**链 0：选靶判定（漏斗形，逐级收窄）`[本页补]`**

```
1. 需求 → 写成一条可执行的检索式（限定符：语言、许可证、topic、stars、pushed）
2. 读 total_count 看召回规模：太大就加限定符；为 0 就拆掉最严的一条限定符
3. 候选表凑满 3 个才进入评级（少于 3 个说明检索式写歪了，回去改检索式）
4. 逐个查 archived、pushed、license —— 这三条都能一票否决
5. 剩下的才进链 A 与链 B
```

`[推演]` 失效输入：跳过第 3 步，第一个搜到的仓库就直接深读两小时，读完才发现它是三年前停更的教程型仓库，而且教的是另一套框架的写法（正文没有这一层，所以这个洞只能靠链 0 堵）。

**链 A：许可证判定（严格串行，第一个命中即终止）**

```
1. licenseInfo 有值？ → 用它；但 other / NOASSERTION 等同 null，必须继续往下
2. null → 列仓库根目录，找 LICENSE / LICENSE.md / COPYING
3. 找到 → 读原文首行（或 SPDX 标识）再判定
4. 根目录也没有 → 补查 README 的 License 章节有无声明   ← 本页在第 7 章新增的一级
5. 全无 → 判「无 License」：只下骨架、标注不可抄码
```

**链 B：价值判定（五维并行，不串行）**：五个维度各自独立打点，一个仓库可以同时「①不可直接用、③设计提炼极高」。串行化会把「只有设计价值」的仓库误杀成「无用」。

**链 C：完成判定（6 项全勾才算完）**：清单里任何一项未过，本次交付物视为未完成。

> 为什么链 A 串行、链 B 并行：**链 A 判的是法律事实，必须唯一答案**（一份仓库在同一个工程里不能既「可全量下载」又「不可抄码」）；**链 B 判的是多维度价值，允许多个答案并存**。把两者顺序写反，会出现「因为设计价值高所以放宽许可证判定」这种灾难逻辑。链 0 之所以放在最前，是因为**它决定后面三条链判的是哪个对象**——选靶错了，三条链全绿也只是把错的东西判得很准。

## 第 4 章 选靶层：把「该看哪个仓库」变成可执行判据 `[本页补]`

正文没有这一层（实测出处：`SKILL.md`「触发条件」原文只认「用户提供 GitHub 仓库链接或列表」）。但这支 skill 的名字里就有「检索」两个字，正文对「怎么检索」却只字未提——**名与实之间这段空缺就是本章**。本章外部依据取自两个检索靶子：GitHub 官方文档站关于仓库检索与代码检索的说明，以及取证当日的真实调用；取不到的数值一律写「未检索到」，不编。

### 4.1 官方仓库检索语法里，哪些限定符能当判据

**外部依据**：GitHub 官方文档站的仓库检索一节。该节地址不是本页臆造——它由 `gh search repos --help` 当日原样打印为 `docs.github.com/search-github/searching-on-github/searching-for-repositories`（`[实测]`）。下表把官方所载限定符按「它替你回答哪个问题」重排，**重排是本页做的**。

| 它回答的问题 | 官方所载限定符 | 拿来当判据的姿势 |
|---|---|---|
| 是不是我要的那种技术栈 | `language:`、`topic:`、`in:name`／`in:description`／`in:topics`／`in:readme` | 语言与 topic 先粗筛。**`in:` 决定你在哪个字段里找词**：官方说明默认只搜「名称＋描述＋topic」三个字段，README 内容要显式 `in:readme` 才搜得到 |
| 我能不能用它 | `license:`（按许可证类型或家族筛） | **选靶阶段就把许可证不合的仓库挡在候选表之外**，比下完再判省一整轮工时。本页认为这是这支 skill 最该吸收的一条外部能力：正文把许可证判断放在 §4，位置太靠后 |
| 它有多健康 | `stars:`、`forks:`、`followers:`、`topics:`（数量区间）、`good-first-issues:`、`help-wanted-issues:` | 数字用比较符（`>`、`>=`、区间）写。**这批是热度信号，不是质量判据**（§4.4） |
| 它还活着吗 | `pushed:`、`created:`、`archived:true/false` | `archived:true` 一票否决「拿来当依赖」，但不否决「读它的设计」；官方要求日期写成 ISO8601（即 `YYYY-MM-DD`）格式 |
| 是不是别人 fork／模板化的 | `fork:true`／`fork:only`、`template:true/false`、`mirror:true/false` | fork（派生副本）出来的仓库常停在旧版本，选靶阶段就该排除 |
| 是不是我要找的那个具体对象 | `repo:owner/name`、`user:`、`org:`、`is:public`／`is:private` | 用户给了链接时用它；`is:` 系列顺带当「我有没有越界访问私有库」的探针 |
| 它有多大（提前估体积） | `size:`（**官方明确单位是千字节 KB**） | 直接对接正文 §4「>100 MB 不 clone」那一行——**搜索阶段就能估体积，不必等下载**；注意单位与正文的 MB 阈值之间要换算 |
| 其它信号 | `is:sponsorable`、`has:funding-file`、`props.<组织自定义属性>:`、`deployable:`／`deployed:` | 这些是「作者收不收钱」「有没有关联部署」的信号，本页**不采纳**为判据（理由见 §4.4 与第 15 章未采纳项） |

官方该节还记了三条会影响判据可复现性的规则（`[外部依据]`，本页转述要点）：**检索一律忽略大小写**；**含空格的词组必须加引号**；**自定义属性限定符必须先指定单一组织**。这三条的意义是：同一条检索式换个写法结果就不同，**所以判据要能被别人重跑，就得把检索式原文一起沉淀进条目**——这正是 §7.6 入库三字段里「复核条件」该写的内容。

### 4.2 `gh search repos` 暴露的同一批判据（当日实测）

`[实测]`：`gh search repos --help` 当日输出的可用旗标清单（数法：数帮助文本 `FLAGS` 段的条目行）与官方限定符基本同批——`--language`、`--license`、`--topic`、`--stars`、`--forks`、`--size`（帮助里明写单位为 kilobytes）、`--updated`／`--created`、`--archived`、`--include-forks {false|true|only}`、`--match {name|description|readme}`、`--sort {forks|help-wanted-issues|stars|updated}`（默认 `best-match`）、`--order {asc|desc}`、`--owner`、`--visibility`、`--number-topics`、`--good-first-issues`、`--help-wanted-issues`、`--limit`（默认 30）。

为什么这一节不是 §4.1 的重复：**同一批判据有两种写法**（裸检索式 vs 旗标），两种写法的转义规则不一样。`gh search --help` 还专门提示「检索词里含连字符时先看 `gh search --help`」——也就是说**连字符可能被当成语法的一部分而不是词的一部分**，这是选靶阶段最容易写出「悄悄漏条件」的检索式的地方。

`[推演]` 具体失效输入：需求是「找带 godot-ecs 风格的示例」，你把带连字符的词直接塞进检索式，工具按语法把它拆开处理，结果召回一批与 ECS（实体-组件-系统，一种把数据与行为拆开的代码组织法）无关的仓库；返回数量看着完全正常，**不报错**。这类故障属于静默失效：判据错了但结论有值，比报错更难发现。退路：给这类词加引号，或改走 `--topic` 用标签而不是用文本匹配。

### 4.3 一条检索式怎么收窄出候选表（当日实测，可照抄）

实测对象是一个真实需求形态：**用户没给链接，只说「找 GDScript 写的 Roguelike（一局随机生成、死了重来的那类游戏）实现参考参考」**。

```
gh api "search/repositories?q=roguelike+language:GDScript+stars:>100&per_page=5" \
     --jq '{total:.total_count, incomplete:.incomplete_results}'
```

`[实测]` 当日返回 `total = 7`、`incomplete_results = false`（数法：读返回体的 `total_count` 与 `incomplete_results` 两个字段）。也就是说这条检索式在全库范围总共命中 7 个仓库，结果完整——**候选数刚好踩在链 0 第 3 步「≥3」的下限上，可以继续，但不宽裕**；如果只回 2 个，正确动作是回来放宽 `stars:` 条件，而不是硬着头皮往下读。

同一批候选改用旗标写法取详细字段（**注意字段名，与 §5.3 的坑直接相关**）：

### 4.4 为什么 star 数只允许出现在检索式里，不允许出现在星级里

官方文档把 `stars:`／`forks:`／`good-first-issues:` 全部归在「检索筛选」名下，从没把它们列为质量指标——这不是巧合，是分类学上的诚实：热度信号衡量的是**被多少人收藏过**，与「它的某个机制能不能解你现在的问题」几乎不相关。

- `[推演]` 具体失效输入：需求是「找批量 2D 对象的低开销实现」，你按 `stars:>50000` 筛，把 9,633 star 的官方演示集合（第 12 章的真实靶子）筛掉了——而它恰恰是这类实现密度最高的样本库。**过滤条件写在检索式里，一旦错，候选表连「被误杀」的痕迹都不留**，你永远不知道自己错过了什么。
- 本页给的硬判据：**star／fork 只用于召回（写进检索式）或用于排序（写进 `--sort`），不用于评级（不许填进星级）**。排序键不删候选、只改顺序，所以安全；过滤条件会删候选，用热度当过滤就是拿嗓门当筛子。
- 同一条逻辑推广：`is:sponsorable`、`has:funding-file` 与代码可迁移性零相关，本页明确不采纳（登记在第 15 章「未采纳项」）。

### 4.5 代码检索是另一套规矩，而且官方自己声明了不一致

正文「§2 查询阶段」的四字段表里没有代码检索的位置——它默认你已经知道要看哪个文件路径。**当你不知道时，才需要代码检索。**

`[实测]` 当日一条真实调用：

```
gh api "search/code?q=repo:godotengine/godot-demo-projects+extends+Node2D&per_page=2" \
     --jq '{total:.total_count, incomplete:.incomplete_results, paths:[.items[]?.path]}'
```

当日返回 `total = 53`、`incomplete_results = false`，前两条路径是 `2d/glow/beach_cave.gd`、`viewport/2d_in_3d/pong.gd`。

`[实测]` 更要紧的是 `gh search code --help` 开头那段官方口径提示（本页转述其要点）：**这些结果由一个「现在的（legacy＝遗留的）老一代代码检索引擎」提供，结果可能与你在 `github.com` 网页上看到的不一致，网页上新增的能力（例如正则检索）尚未通过 API 提供**。同一条 help 列出的代码检索旗标是 `--extension`、`--filename`、`--match {file|path}`、`--repo`、`--owner`、`--language`、`--size`（KB）、`--limit`（默认 30）。

「网页与 API 不一致」这条声明为什么要单列一节：它推翻了新手的一个默认假设——「我在网页上搜到了，脚本里也应该搜得到」。

- `[推演]` 具体失效输入：用户在网页上用正则找到了那段实现，把结果截图发给你，让你「按这个抓下来」。你换成 API 的普通关键词写法去搜，返回 0 条；你于是下结论「该仓库没有这段代码」——而真实原因只是**接口家族能力不同**。退路（本页给的降级顺序）：正则 → 关键词＋`--match file` → 用目录树按路径名筛（正文 §2 那条路）；走过降级就在沉淀条目里标注「本条结论基于降级判据」。
- 代码检索需要哪种鉴权、索引覆盖多少仓库、单次结果上限是多少——**这三项本页均未检索到官方数值**，因此不写成数字判据。可执行的做法只有一条：读返回里的 `incomplete_results`，它为真时禁止把当次结果当全量使用（`[实测]` 当日两条调用均为 false）。

### 4.6 选靶层与配额的冲突：30 次／分钟是硬天花板

`[实测]` 当日 `gh api rate_limit` 读到的关键四个数：`resources.core.limit = 5000`（次／小时）、`resources.core.remaining = 4969`、`resources.search.limit = 30`（次／分钟）、`resources.search.remaining = 30`（数法：逐字段读 `rate_limit` 返回体）。

两个配额是两个池子，但**搜索那个池子小得多**（30 次／分钟 vs 核心 5,000 次／小时 ≈ 折算 83 次／分钟）。这就是选靶阶段的节奏约束：

- 一次「改检索式 → 看 total」的漏斗循环消耗一次搜索配额；穷举式试错（拿十种写法各搜一遍再对比）会在几分钟内把 30 次打完。
- `[推演]` 具体失效输入：脚本里写了个循环，对 40 个候选仓库逐个调搜索接口做去重。打到第 31 个时返回 403（拒绝访问的状态码），脚本没检查状态码，于是把后面 9 个候选都当成「没匹配」，最终结论是「这批仓库都不相关」——**配额耗尽的静默失败在这里以「召回为 0」的形态出现，比在拉取阶段出现更难怀疑**，因为「没有」看起来像一个正常答案。
- 本页给的做法（`[本页补]`）：**先用少量精确检索式把候选表收敛出来（搜索调用压在 30 次内），随后一律切到核心池做四字段取证**；任何一次搜索返回 0，先怀疑检索式，再下结论。

### 4.7 选靶层的六个失效模式（本章小结）

| 失效 | 征兆 | 退路 |
|---|---|---|
| 检索式过宽，召回上千 | `total_count` 是四位数 | 加限定符（许可证／语言／topic），或把搜索字段从默认三字段收窄成 `in:name` |
| 检索式过窄，召回 0 | `total_count = 0` | 拆掉最严的一条（通常是 star 区间），而不是一口气全改——全改就失去了「哪一条太严」的信息 |
| 候选只有 1–2 个就开工 | 做不出方法对比表 | 回 §4.3 扩写法；候选少于 3 时「谁的更好」这个问题在物理上无法回答 |
| 热度条件误杀 | 明知某个仓库相关却不在候选里 | 把 star 条件从过滤改成排序（`--sort`），见 §4.4 |
| 连字符／引号写法改变语义 | 结果数量正常但内容不对 | 把检索式原文记进条目；对照 `gh search --help` 的连字符说明改写法 |
| 把 API 代码检索结果等同网页 | 网页有、API 无 | 已知不一致（§4.5 官方口径）；按降级顺序换判据，条目里标「降级判据」 |

## 第 5 章 取证拉取层：四字段、三种接口家族与四个陷阱

### 5.1 正文给的字段对照表（照抄其结构）

| 字段 | 推荐命令（`gh`，鉴权） | 兜底 API 路径 |
|---|---|---|
| 元数据 | `gh repo view {o}/{r} --json ...` | `/repos/{o}/{r}` |
| 目录树 | `gh api repos/{o}/{r}/git/trees/HEAD?recursive=1` | 同路径 |
| README | `gh api repos/{o}/{r}/readme -H "Accept: application/vnd.github.raw"` | `/repos/{o}/{r}/readme` |
| 关键源码 | `gh api repos/{o}/{r}/contents/{p} --jq '.content' \| base64 -d` | `/repos/{o}/{r}/contents/{p}` |

（出处：`SKILL.md`「工作流 §2 查询阶段」的表格。`{o}/{r}` 是「组织名／仓库名」的占位写法，正文用它表示**任何靶子都能套同一条命令**，这也是这套 SOP 能自称通用的原因。）

### 5.2 为什么优先 `gh`：配额差是数量级的

- `[实测]` 取证当天用 `gh api rate_limit` 实读：鉴权核心配额 **5,000 次／小时**（当次剩余 4,969，说明鉴权真在生效）、搜索接口配额 **30 次／分钟**。
- `[实测（正文断言，未独立复核）]` 匿名直连 60 次／小时这个数出自 `SKILL.md`「§2 查询阶段」的引文「已登录鉴权、无匿名 60 次／小时限流」。本页**没有**做匿名压测（会真消耗配额，且结果随出口 IP 变），只按正文口径引用，并在第 15 章「未核实项」登记。
- 为什么这条值得写进正文：**限流是无声失败**。匿名跑到配额见底时接口返回 403，脚本不检查状态码就会把后半批仓库全部读成「空」，于是你得出「这批仓库都没内容」的错误结论。把「优先 gh」写成规定，本质是**把一类不会报错的错**从流程里删掉。

### 5.3 陷阱一（正文缺陷）：三套命令族三套字段名，正文写错了一处、还埋着一处

正文「§2 查询阶段」元数据行写着 `--json stars,licenseInfo,primaryLanguage,description,repositoryTopics`。本页在同一环境实测：

```
$ gh repo view godotengine/godot-demo-projects --json stars
Unknown JSON field: "stars"
```

`[实测]` 同一条命令当日改用 `stargazerCount` 就正常返回（原样字段值）：`stargazerCount = 9633`、`licenseInfo = {key: mit, name: MIT License}`、`primaryLanguage = GDScript`、`repositoryTopics = null`、`updatedAt = 2026-10-08T23:59:30Z`。工具在报错后自己列出了可用字段清单，star 数对应的是 **`stargazerCount`**；`licenseInfo`、`primaryLanguage`、`description`、`repositoryTopics` 四个名字在这条命令里有效。

**更关键的发现（本页实测，正文没有）**：`gh search repos` 那套 `--json` 用的是**另一批字段名**。实测：

```
$ gh search repos "roguelike" --json fullName,licenseInfo
Unknown JSON field: "licenseInfo"
```

当日该命令打印的可用字段清单里，同类信息分别叫 `license`、`stargazersCount`、`isArchived`、`size`、`pushedAt`、`fullName`、`defaultBranch`、`forksCount`、`openIssuesCount`、`visibility`、`url` 等。汇总成一张对照表：

| 命令族 | 它背后的接口家族 | 同一件事的字段名（当日实测） |
|---|---|---|
| `gh repo view --json` | GraphQL（声明式查询） | `stargazerCount`、`licenseInfo`、`primaryLanguage`、`repositoryTopics`、`updatedAt`、`nameWithOwner` |
| `gh api /repos/{o}/{r}` | REST（老式路径接口） | `.stargazers_count`、`.license.spdx_id`／`.license.key`、`.language`、`.size`（KB）、`.default_branch`、`.pushed_at` |
| `gh search repos --json` | 搜索接口的包装 | `stargazersCount`、`license`、`isArchived`、`size`、`pushedAt`、`fullName` |

- **为什么会中招**：三族命名规则两两不同（驼峰 vs 下划线 vs 驼峰但词表不同），而它们出现在同一支 skill 的同一张命令表里。照抄一族的名字用到另一族上，必然报 `Unknown JSON field`。
- **这是「照抄正文命令就报错」级别的缺陷，而且有两处**：`--json stars`（正文原写）、`--json licenseInfo`（正文没写，但读者从 §2 表格把字段名迁移到搜索命令时一定会这么写，本页实测即撞上了）。
- **修法建议**（属本页提议，不改权威库，见第 15 章）：元数据行字段名改成 `stargazerCount`；并补一句「**字段名跟着命令族走，不许跨族迁移；拿不准就让工具自己打印可用字段清单**」（这条几乎零成本：写错字段名时工具会把正确清单吐给你）。
- 顺带一条实测细节：`[实测]` 当日 `godotengine/godot-demo-projects` 的 `repositoryTopics` 返回 **null**——而 topic 检索限定符（§4.1）在别的仓库上明明可用。**同一件事在不同接口一个有值一个空**，这类不一致只能靠「不迷信单一字段」来防。

### 5.4 陷阱二：`Accept: raw` 与 `--jq` 不能同时用

正文 README 行写的是 `gh api ... -H "Accept: application/vnd.github.raw"`。

- `[实测]` 只带 raw 头 → 正常返回纯文本，第一行是仓库 README 的标题。
- `[实测]` 额外加 `--jq '.'`（想「统一用 jq 处理」的顺手操作）→ 报错 `invalid character '#' looking for beginning of value`，因为 `--jq` 预设输入是 JSON，而 raw 返回的是 Markdown（一种用井号写标题的纯文本格式），第一个字符就解析失败。
- **为什么会中招**：同一条命令里前面几个字段查询用 `--jq` 很顺，读者会惯性带上。
- **两条可选写法**：要纯文本就别加 `--jq`；要结构化就别加 raw 头（那样返回 JSON，里面 `content` 是 base64，需解码，见第 6 章）。

### 5.5 陷阱三：`HEAD` 别名与默认分支

- `[实测]` `gh api repos/{o}/{r}/git/trees/HEAD?recursive=1` 在 `godotengine/godot-demo-projects` 上直接可用（返回 4,645 条目录项）。`HEAD`（当前检出的那个版本指针）在这里被 API 接受为「默认分支」的别名，省掉先查默认分支名这一步；当日实测该仓库默认分支为 `master`。
- 正文没写这条为什么值得注意：**如果仓库默认分支不是最新的开发分支，或者你要对比历史版本，`HEAD` 就不够用**，得显式指定分支或 tag（版本标记）。
- `[推演]` 反例输入：用户说「按 v2.0 的写法参考，我们线上还是 v2.0」，你拿 `HEAD` 拉回来的是最新分支状态，把已经废弃的实现当现役方案抄进文档，还顺手给出「建议」——**这一条错误会顺着沉淀条目传到下一次会话**，而且带着一份看起来很正式的出处。

### 5.6 陷阱四：目录树会被悄悄剪掉，判据看 `truncated`

- `[实测]` 中等仓库不触发截断：`godotengine/godot-demo-projects` 递归树返回 `truncated=false`、条目数 4,645（数法：读返回的 `.truncated` 布尔字段与 `.tree` 数组长度）。
- `[实测]` 巨型仓库会截断：对 `torvalds/linux`（Linux 内核仓库）递归取树，返回 **71,638 条**且 **`truncated=true`**——清单不完整，但**不报错、状态码正常**。
- 正文的措辞是「大仓库 trees 递归可能很大，按需取关键路径即可」（`[实测]` 出处：`SKILL.md`「文件内容解码落盘」条末句）。
- **截断阈值本页未检索到官方数值**，因此不写成数字判据；可执行的判据是**读 `truncated` 字段**，它为 true 时禁止把树当全量清单使用。
- 为什么这是真故障：拿到截断的树之后做「目录结构／架构分层」判断（第 8 章维度④），你看到的是一份**被剪过的**结构，却以为看完了整个工程。`[推演]` 具体失效输入：某大仓库的真实分层里「数据层排在第三个顶层目录」，而它排在 71,638 条之后被剪掉了，于是你在条目里写「该工程没有独立数据层」——这是一条会被后人当事实引用的**错误否定结论**，比漏看更贵。
- 换法：只取关键路径，用 `contents/{目录}` 单层列，或用 `--jq` 在客户端筛。**当日实测一条很划算的写法**：对递归树问 `[.tree[].path|select(endswith("project.godot"))]`，一次拿到全部「这是一个独立子项目」的标记文件（`[实测]` 前 8 条见第 12 章 §12.2）。

### 5.7 兜底直连什么时候真的需要

正文「兜底直连」条给的场景是：**GitHub 域名被 hosts 文件拦截／`gh` 不可用**，此时用 Python 标准库 `urllib.request`（Python 自带的网页请求模块）直连 `api.github.com` 绕过 DNS（域名解析）。

- `[推演]` 具体什么输入会让它出问题：本机 hosts 把 `github.com` 指到不可达地址时，浏览器打不开仓库页、`gh` 报连接错误，但 `api.github.com` 可能仍通——这时只有绕开域名解析的直连能干活。这条规则的价值是**保留一条不通浏览器也能取证的路**。
- 注意：匿名直连即回到正文断言的 60 次／小时，兜底路要省着用；正文没有规定「兜底时优先查哪三个字段」，本页在第 14 章速查表按正文的四字段表给了优先级建议：**元数据 → 目录树 → README，源码按命中路径点取**。

## 第 6 章 落盘保真层：base64 解码与中文编码

这一层管的是「拿回来的东西能不能被打开、写下去的东西能不能被读」，对应正文 §2 的解码条与 §6「编码注意」整节。

### 6.1 事实：`content` 字段是 base64，不是源码

正文「文件内容解码落盘」条（`SKILL.md`「§2 查询阶段」内）说得很直接：`contents/{path}` 与 `readme` 接口返回的 `content` 是 base64 字符串，**切勿把 base64 原文当源码落盘**。

`[实测]` 本页当日拿一个真实文件量化了这句话（对象见第 12 章的示例仓库）：

| 项 | 值 | 数法／复算 |
|---|---|---|
| 原始字节数 | 1,357 | 接口返回的 `.size` 字段 |
| `content` 字符数 | 1,843 | 接口返回 `.content` 字符串长度 |
| `.encoding` | `base64` | 接口字段直接标明 |
| 膨胀比 | ≈36% | 复算：1,357 字节 → 向上取整(1357/3)＝453 组 → 453×4＝1,812 个 base64 字符；接口每 60 字符折一行 → 向上取整(1812/60)＝31 行 → 31 个换行 → 1,812+31＝**1,843**，与实测完全对上 |

为什么给这个数：**膨胀比是「你一眼就能认出这是没解码的原文」的判据**。落盘文件比接口报告的 `size` 大三分之一、开头是一串密集的字母数字而没有换行语义，就是忘了 `base64 -d`。

### 6.2 正文规定的两条解码写法

```
gh api repos/{o}/{r}/contents/{p} --jq '.content' | base64 -d > 本地路径
# 或
Python: base64.b64decode(content) 后写文件
```

- `[实测]` 第一条按正文原样跑通：管道不做任何额外处理即可解码成功（不需要手工去掉折行），落盘 37 行，第一行是 `extends Node2D`（一种游戏脚本语言的开头），说明解码正确。
- 为什么两种写法都要给：**`base64 -d` 依赖 Git Bash 之类的环境**（Windows 上的 Bash 兼容命令行）；纯 PowerShell 环境（Windows 自带的脚本外壳）里这个命令不存在，此时 Python 是唯一路。**只给一条命令的 SOP 会在另一种 shell 里当场失效。**

### 6.3 为什么这个坑值得单独设一条规则

正文只写了一句警告，但把它写进规则的理由值得展开——这是本 skill 里「延迟暴露」（错误当场不报，几周后才现形）最典型的一类故障：

- 报错会在**几周后**才出现：文件躺在那儿，名字正常、大小正常、目录列表看不出任何异常，只有当你真的复制那段代码去用时才发现是乱码。
- 那时**上游已经找不回来了**：当初从哪个仓库、哪个路径拉的，没记。这是第 9 章命名规则与沉淀条目里「本地路径」字段存在的原因（`[推演]`：没有这两个字段，几周后没人能把乱码文件和来源勾稽上——勾稽＝两处数字能互相对上）。
- 所以解法是**结构性的**：把解码写死在唯一推荐的命令里，而不是写一句「记得解码」。写进命令里，坑掉不进；写成提醒，总有忘了看提醒的一次。

### 6.4 中文编码：一条硬验证判据

正文「§6 编码注意」三条（`[实测]` 出处即该节）：中文用 `Python open(path, "w", encoding="utf-8")` 写；避免 PowerShell 管道传中文（会损坏）；**写后验证「中文字符数 > 0 且问号数 = 0」**；文件路径尽量用英文，避免中文路径跨平台兼容问题。

- 为什么这条判据写得这么好：它把「有没有写坏」变成一个**数出来的数**，而不是「我看上去挺正常」。问号数＝0 是个红判据——中文在错误编码下最常见的落盘形态就是问号，所以数问号等于数事故。
- `[推演]` 具体失效输入：用 PowerShell 的管道把分析结论写进文件（形如 `某命令 | Out-File 报告.md`），中文全变问号，而文件字节数正常、命令退出码为 0。没有这条验证判据时，这个文件会被当成「已完成」交付。
- `[推演]` 第二条：路径用中文（`reference_repos/参考代码/helper.py`）在跨平台或跨工具时踩编码不一致；这也是正文 §4「存放」列与 §6 第 3 条一起把路径压成英文的理由。

### 6.5 落盘位置的三条约束（正文分散在 §4 与 §6）

| 约束 | 正文出处 | 为什么 |
|---|---|---|
| 存放目录二选一：`{工程}/third_party/` 或 `reference_repos/` | §4 决策矩阵「存放」列 | 「第三方依赖」（要参与构建）与「只读参考」（不许进构建）混在一层，日后清理时不知道哪些能删 |
| 无许可证仓库加 `_NO_LICENSE` 后缀 | §4 矩阵「无 License」行 | 让法律状态写进文件名，搜索和打包时躲不开它 |
| 文件路径尽量用英文 | §6 编码注意第 3 条 | 中文路径在跨平台（不同操作系统之间迁移）时容易踩编码不一致 |

- `[推演]` 会出问题的具体输入：把一份无 License 仓库的脚本存成 `reference_repos/参考代码/helper.py`（既没加 `_NO_LICENSE`，又用了中文目录），之后打包脚本按目录整体收集 → 未经授权的代码进了可发布构建，而且文件名上没有任何拦截信号。

## 第 7 章 许可证边界层：六行矩阵、三级补查与两条红线

这一章是本 skill 法律风险的总闸门，也是全文最长的一章——**因为它挡的是不可逆的损失**。

### 7.1 六行决策矩阵（逐行照正文 §4，含动作与存放）

| 条件 | 决策 | 存放 |
|---|---|---|
| MIT／Apache／CC0／公共领域 | 可全量下载，自由参考修改 | `{工程}/third_party/` 或 `reference_repos/` |
| GPL-3.0／AGPL | **只下 README 学方法论，不下载源码，不抄码转译** | 文档标注警告 |
| 无 License | 只下骨架学方法论，标注「无 License，不可抄码」 | `reference_repos/` 加 `_NO_LICENSE` 后缀 |
| 作者标注 Private／保密 | 只参考公开设计理念，**不下载任何文件** | 仅记录思路 |
| 仓库 >100MB | 选择性下载关键文件，不 clone 全库 | 按需 |
| 纯资源索引／文档 | 不下载，在线浏览 | 文档记 URL |

（出处：`SKILL.md`「工作流 §4 下载决策矩阵（License 红线）」。）

**注意这张表把两类东西混在一起了，而且是有意为之**：前四行判「能不能用」，后两行判「要不要占磁盘」。合并的理由是**执行时点相同**——都是「下载之前」问的问题；拆成两张表反而会让读者只看第一张就动手。

### 7.2 每一行的「为什么是这个动作」

- **MIT／Apache／CC0 → 全量下载**：这三类的共同点是「允许修改与再发布，只需保留版权声明」。允许下载全量是为了做架构分层与算法细节的深读，这类阅读无法靠 README 完成。Apache 比 MIT 多一条专利授权条款，本页不展开（正文没写；不编造条款内容）。
- **GPL-3.0／AGPL → 只读 README、不下载源码、不抄码转译**：这三条限制是**连在一起**的，正文写得很硬。逻辑是：copyleft（著佐权，要求衍生作品同许可）类许可证会「传染」你的工程——只要把源码抄进、或机械翻译进你的可发布构建，你的工程就被要求以同样条款开源。所以 SOP 干脆把动作降到「只学方法论」：**学思路不是许可问题，抄代码才是**。
- **无 License → 只下骨架**：没有任何许可证的公开仓库，默认是「保留所有权利」，**公开≠可复制**。骨架（目录结构＋少量标记文件，如各子项目的配置文件）读的是组织方式，风险最低。
- **Private／作者标注保密 → 一个文件都不下**：这一行的判据来自作者的明示。`[推演]` 反例输入：作者在 issue（问题工单）里写过「这份实现暂不开放复用」，但仓库本身仍可下载——按本行精神，只要作者表达了保密意图就落到「仅记录思路」，不许下载。
- **>100MB → 选择性下载，不 clone**：见 §7.4 的实测。
- **纯资源索引／文档 → 不下载，只记 URL**：这类仓库（清单式 awesome 列表、题库、文档站）价值在链接聚合，全量下载不产生任何额外可读信息，还占磁盘。

### 7.3 `licenseInfo` 为 null 的三级补查（正文规则 ＋ 本页扩到三级）

正文「License 检测补充」段（`SKILL.md` §4 末尾，📌 标记）给的原始规则：API `licenseInfo` 字段常因仓库仅在根目录放 `LICENSE`／`COPYING`／`LICENSE.md` 而返回 null；null 时**额外检查根目录是否存在上述文件**再判定，不要直接当「无 License」处理。

`[实测]` 本页当日在公开仓库上验证了这条规则会漏，并补了第三级：

| 级 | 检查什么 | 命令形状 | 当日实测证据（可按 §12.10 重跑） |
|---|---|---|---|
| L1 | 元数据字段 | `gh repo view --json licenseInfo`；REST 侧读 `.license.spdx_id` | `godotengine/godot-demo-projects` → `MIT`（key `mit`），直接结束 |
| L2 | 根目录许可证文件 | 列仓库根，找 `LICENSE`／`LICENSE.md`／`COPYING` | 同一仓库根目录确有 `LICENSE.md`（专门的 license 端点当日返回 `name: MIT License, path: LICENSE.md`） |
| L3 | **README 里的许可声明** | 在 README 原文中搜 `License` 章节 | **`jlevy/the-art-of-command-line`**：REST `.license` 当日实测为 **null**；根目录按 `licen|copying` 匹配的清单当日实测为 **空**；但 README 有一节 `## License`，明确声明 **CC BY-SA 4.0**（署名-相同方式共享，创作共用的一种）。实测 162,396 star、`size` 2,772 KB |

- 为什么 L3 必须补：**L2 只能证明「没有许可证文件」，不能证明「没有许可证」**。上面那个实测仓库把许可证写在 README 里，走两级检查会被判成「无 License，只下骨架」——结论方向没错（骨架优先总是保守），但**判据是错的**：真实风险其实来自 BY-SA 的「相同方式共享」条款（衍生文档要用同样条款共享），而不是「无授权」。判据错了，你无法向别人解释为什么这么决定。
- `[实测]` 另一个方向的坑：**认不出≠没有**。`MoonTechLab/LunaTV` 当日实测 REST 许可证值为 `key: other / spdx: NOASSERTION`（GitHub 无法归类）；读根目录 `LICENSE` 原文首行是 **Attribution-NonCommercial-ShareAlike 4.0 International**（禁止商用的创作共用）。**只看元数据，这个仓库会被当成「许可证不明」甚至「普通开源」处理。**
- 因此本页给一条硬判据（可执行）：**`licenseInfo` 为 `other`／`NOASSERTION` 时，等同 null 处理，必须进 L2/L3 读原文**。正文的补充只覆盖 null；这是同一逻辑的自然延伸，属 `[推演]`，反例输入即上面的 `LunaTV`（NOASSERTION）与 `CompVis/stable-diffusion`（当日实测同为 `key: other`，73,487 star——「Other」绝不能当 MIT 用）。

### 7.4 体积行（>100MB）的实测与单位陷阱

- `[实测]` `godotengine/godot-demo-projects` 的 REST `size` = **567,682**（单位 KB，约 555 MB），远超 100 MB → 矩阵第 5 行触发：**不 clone 全库**（clone＝整份拉到本地），改为点取关键路径；本次取证**一个字节都没有整仓克隆**。
- `[实测]` 更极端的对照：`signalapp/Signal-Android` 当日 `size` = **2,628,553 KB（约 2.5 GB）**，同仓库许可证实测为 `AGPL-3.0`——**两行同时命中**（既属 copyleft 只读行，又属超大仓库行），这种「双重限制」在 §12.6 有处理定序。
- 为什么阈值定在 100 MB 而不是 1 GB（本页观点，`[推演]`）：这类演示／资产型仓库的体积大头是美术与音频，而你要读的是代码与结构；**下载 555 MB 里可能有 540 MB 是你这次根本不看的东西**。阈值再高（1 GB）就形同虚设，因为多数参考仓库都在几百 MB 量级；再低（20 MB）会把大量纯代码仓库也踢进「只点文件」模式，读不到完整目录结构。
- 复算方法：`gh api repos/{o}/{r} --jq '.size'` 得到 KB 数，除以 1024 得 MB。**注意单位是 KB 不是字节**——这是最容易读错的一处，把 567,682 当字节的会觉得只有 0.5 MB 从而放行 clone。
- `[推演]` 会出问题的输入：把 `.size` 当字节解释 → 判定「<100MB，可以整仓克隆」→ 一次克隆吃下 555 MB 磁盘（`Signal-Android` 那种则是 2.5 GB）。顺带一条环境纪律：落盘位置要事先定，不要把大包克隆进系统盘的缓存位置。

### 7.5 版权红线（正文原句的精神）

正文 §4 的警告块写死了两条（`[实测]` 出处：`SKILL.md`「§4 下载决策矩阵」下的 ⚠️ 版权红线句，正文称其为「用户硬规矩」）：

1. **禁止商用（CC-BY-NC 等）素材绝不纳入工程**——不是「谨慎使用」，是绝不。
2. 外部参考代码若「保留所有权利」，仅作只读参考，**不整段照搬进可发布构建**。

- 为什么第 1 条这么硬：资产类文件（贴图、音频、模型）**无法像代码那样重写来「绕开」许可证**，用了就是用了；而代码还能靠「只学思路自己实现」脱敏。风险不对称，所以最硬的一条只给资产。
- 为什么第 2 条留「只读参考」的空间：方法论与结构不受人物化表达的保护（本页不给法律结论，只复述 SOP 立场）。判据是可执行的一句：**最终构建产物里不许存在与上游逐字相同的段落**。

### 7.6 联动纪律：产出即外部智慧，当次入库

`[实测]` 出处：权威库 `SKILL.md` 正文首条引用块（2026-10-02 全库链式审计补挂，**本仓库副本暂缺此条**，见页眉跟踪状态）——检索到的权威资料／设计智慧／行业数字**当次**沉淀进「外部智慧入库区」，一卡一智慧，卡面至少含**来源 URL ＋ 检索日期 ＋ 复核条件**；事实与数据另遵循本库的抗幻觉纪律（一手来源核实／结论可证伪／不确定标未知）。

- 三个字段各自的必要性（本页组织，`[推演]`）：**URL** 让下次能回到同一份材料；**检索日期** 让「上游已经变了」可被发现（第 10 章的失效模式之一）；**复核条件** 是最容易被省掉、却最值钱的一条——它写的是「怎样重跑一遍来确认这条结论今天还成立」。本页第 12 章每条数字后面带的「数法／复核命令形状」就是这个字段的落地样例。
- 为什么「当次」而不是「批量补」：会话结束时上下文窗口（一次对话能装下的文字量）会被清掉，事后补卡只能凭记忆重写结论，而记忆重写出来的东西**没有复核条件**——这正是本页第 10 章失效模式 7 的入口。
- 本页为什么全页不出现任何本机路径：这条纪律的落盘位置属于本机环境指纹，公开仓库一律抽象化。

| ① 可直接使用 | 资产／插件／配置立即可用 | shader（着色器，决定画面怎么算颜色）、粒子预设、CC0 素材 | 组件库、CSS 框架（网页样式的可复用规则集） | 预训练模型、prompt（提示词）模板 |

### 8.2 为什么恰好是这五个，少一个会怎样

这五个维度不是罗列得好看，它们各自挡住一种误判（`[推演]`，但每条都给得出反例输入）：

| 维度 | 它单独存在的理由 | 缺了它会发生的误判（含具体失效输入） |
|---|---|---|
| ① 可直接使用 | 唯一能立刻换成工时的价值 | 会高估。失效输入：读完觉得「这套状态机思路真好」就开工，实际上它的实现绑死在另一个引擎的节点系统上，你的工程里一行都落不了地 |
| ② 可提取转译 | 语言不同但思路可搬 | 会漏判。失效输入：一个 C# 写的仓库被直接归为「我们又不用 C#，用不上」，而它里面那套对象池做法正是你卡在内存上的解 |
| ③ 设计提炼 | 机制与决策，与代码无关 | 会误抄。失效输入：把别人的实现当别人的设计，抄了一整段代码却没拿到那个可迁移的取舍（「为什么它把碰撞检测放在主循环外」），换语言后代码废了、设计也没留下 |
| ④ 架构分层 | 目录组织本身就是知识 | 会低估小仓库。失效输入：只看行数，把一个几万行但分层混乱的工程排在几百行、分层极清楚的示例工程之前 |
| ⑤ 视觉／规范 | 参数与规范是可直接落地的资产 | 会错配。失效输入：把「代码写得好」当成「视觉也能抄」，最后卡在没人给出调色参数与字号规范 |

- 五维**必须并行独立打分**（第 3 章链 B）。判定顺序化会带来系统性偏差：①不满足就停，于是「只有设计价值」的仓库被误杀成 ☆。
- 三个示例列（游戏／Web／AI）不是装饰：正文定位是「通用 SOP，适用于任何工程类型」（`[实测]` 出处：正文标题下的引用块）。同一维度在不同工程类型里长得不一样，示例列是**把抽象维度钉回具体动作**的那颗钉子。

### 8.3 六档星级：正文给的刻度与每档的动作含义

`[实测]` 出处：`SKILL.md`「§2 查询阶段」末尾「判断价值等级」条：★★★★★（核心参考）→ ★★★★（重要参考）→ ★★★（有借鉴点）→ ★★（边缘相关）→ ★（存档查阅）→ ☆（无用）。

| 档 | 正文语义 | 建议动作（本页补，`[推演]`） | 是否进分析文档 |
|---|---|---|---|
| ★★★★★ | 核心参考 | 深读关键源码，做方法对比表 | 必进，且排在文档最前 |
| ★★★★ | 重要参考 | 读目录树＋README＋若干源码 | 必进 |
| ★★★ | 有借鉴点 | 读 README 与命中路径 | 进，一行式条目 |
| ★★ | 边缘相关 | 只登记不深读 | 可进可不进，进则标 ★★ |
| ★ | 存档查阅 | 只记 URL | 记 URL 即可，不下载 |
| ☆ | 无用 | **明确写下「为何无用」** | 建议进（负知识也是知识，能防止下次重扫） |

- 为什么留 ☆ 一档而不是直接不管：**「扫过、判定无用」是有效结论**。不写下来，下一个人（或下一次会话）会重新扫一遍、重新得出同一个结论，白花一轮时间。这与本库「否决也要留档」的一贯立场一致。
- 星级的分母是**当前工程的价值**，不是仓库的质量。一个 9,633 star 的官方演示集合（第 12 章实测），对某个不需要这类示例的工程就是 ★★；反过来 §4.3 候选表里 179 star 的教程仓库，如果它正好讲你卡住的那个机制，就是 ★★★★★。
- `[推演]` 具体会出问题的输入：把 star 数当价值等级填进星级——「四十五万 star，那就 ★★★★★ 吧」。这样做出来的表在下次评审时完全无法解释当初为什么值得抄它，而**解释不了的结论无法被回注**（回注＝把内容重新塞回上下文继续用），只能重做。

### 8.4 评级层的四个失效模式

| 失效 | 具体失效输入（`[推演]`） | 退路 |
|---|---|---|
| 一维否决 | 「不能直接用 → ☆」，把设计价值最高的仓库扔掉 | 五维并行打点，星级取最高维度而不是最低维度 |
| 串行打分 | 按①②③④⑤顺序判，中途 break | 明确写「每维都要给一个值，哪怕是『无』」 |
| 用热度代替维度 | 星级列填 star 数 | 见 §4.4 硬判据：热度只进检索式不进星级 |
| 跨工程复用别人的评级 | 直接引用另一支 skill 或别人的仓库清单里的星级 | 评级分母是**你的**当前工程；换一个工程必须重打，条目里保留工程标识 |

## 第 9 章 抽象与沉淀层：从别人的仓库搬进自己的体系

正文在这层给的是**容器**（§5 文档更新、条目模板、方法对比表、命名规则），没给**动作**（怎么把读到的东西变成自己能用的东西）。这一章是本页对「通用提炼有用内容」这半句名字的补齐；标注如下：§9.1 的四步是 `[本页补]`（`[推演]`），§9.2–§9.5 全部有正文出处。

### 9.1 抽象四步：把「一段代码」提炼成「一条能用的决策」`[本页补]`

```
第 1 步 定位决策：这段实现到底在回答哪个问题（不是「它怎么写的」）
第 2 步 剥离表达：把语言、框架、目录、命名这些「表达方式」全部去掉
第 3 步 换表达重述：用你自己工程的语言把那条决策重新表述一遍
第 4 步 反向验证：在你自己的工程里做最小实现，验证那条决策仍然成立
```

- **第 1 步**的产出形状是一句「问题句」，不是代码。`[推演]` 失效输入（跳过第 1 步）：看到 `player.gd` 里用了一个数组存子弹，于是也给自己加一个数组——两周后你的子弹管理崩了，因为你抄的是**答案**，而它回答的问题（「不用节点系统、用逻辑与碰撞批量管理大量对象」）你根本没确认过。第 12 章 §12.4 的实测里，那行注释本身就是问题句的来源。
- **第 2 步**是最容易偷懒的一步，也是最容易踩许可证的一步。`[推演]` 失效输入：跳过剥离，直接把 GPL 仓库的 C# 类「翻译」成 C# 变量名改一改的 GDScript——**机械转译不改变衍生性质**，正文对 GPL／AGPL 那一行明写「不抄码转译」（`[实测]` 出处：§4 矩阵第 2 行）。剥离的正确产物是「它把 X 放在 Y 外面，因为 Z」这样一句不带代码的话。
- **第 3 步**要求你写出与上游**不同形**的东西。判据（本页给，`[推演]`）：把你的产出与上游文件做逐段比对，**不许出现连续逐字相同的段落**——与 §7.5 第 2 条红线共用同一条可执行判据。
- **第 4 步**是唯一能防止「提炼出一堆正确的废话」的步骤。`[推演]` 失效输入：从三个仓库各提炼一条「分层要清晰」，全进文档，但你的工程分层一点没变——因为那条决策太抽象，**无法被证伪也无法被验证**。做法：每条抽象结论后面必须能接一句「所以我改哪个文件」。

四步跑完后，产出的不是代码而是**一条决策 + 一次验证结果**，这两样东西才是可以进第 9.3 节条目模板、可以在下次会话被回注的东西。

### 9.2 方法对比表（同类仓库给出不同实现时追加）

`[实测]` 出处：`SKILL.md`「§5 文档更新」末句。四列结构：**维度 ｜ 参考仓库方案 ｜ 当前工程方案 ｜ 谁的更好 ｜ 建议**（正文用「维度」打头，最后一列是行动项）。

- 为什么必须是这张表：读完两个仓库各自的实现，人脑里留下的是一团模糊的印象。表格强迫你把「比什么」写成一列（维度），「各是谁的做法」写成两列，「结论」和「下一步」写成两列。
- **这张表通常是一次分析里唯一三个月后还有用的部分**——具体实现会被重构掉，而「为什么选了这一种」不留下来就会重演一遍。
- `[推演]` 失效输入：同一次分析读了两个候选（§4.3 的表里就有 4 个），只给前一个写了条目，没写对比表。三个月后没人记得为什么选了它，于是有人把另一个再读一遍——这就是第 1 章故障 ⑥ 的完整闭环。

### 9.3 命名与存放：一个前缀换来可溯源

`[实测]` 出处：`SKILL.md`「§4 下载决策矩阵」末尾「下载命名规则」段：前缀标来源 `{Repo缩写}_{原名}`，同仓库统一前缀（正文给了两个例子：`VS_` ＝ vampire-survivors、`HS_` ＝ HordeSurvival），保持原扩展名。

| 细则 | 挡住的故障 | 反例（不加会怎样，`[推演]`） |
|---|---|---|
| 前缀标来源 | 几周后面对一堆文件，不知道哪个来自哪个仓库 | `bullet_manager.gd` 躺在参考目录里，与你自己写的同名文件混在一起，改名时谁也不敢动 |
| 同仓库统一前缀 | 同一仓库的零散文件看起来像来自十个仓库 | 无法批量清理：作者换了许可证，你要挨个文件判断归属 |
| 保持原扩展名 | 扩展名（`.gd`／`.png`／`.json`）丢了，工具链与语言识别全乱 | 把脚本存成无扩展名文件，编辑器不高亮、构建脚本不打包 |

- 「统一前缀」带来一个额外收益：**它能和沉淀条目做勾稽**（两处数字对得上）。条目里写「本地路径：`reference_repos/VS_*/`」，磁盘上一次目录列举就能数出实际文件数，两边不一致就是漏登记。
- `_NO_LICENSE` 后缀（`[实测]` 出处：§4 矩阵「无 License」行的「存放」列）是本层唯一的**法律状态写进文件名**的设计。理由：文件名的可见性远高于文档里的一个备注字段——打包脚本、目录列表、代码搜索都会碰到它，想装看不见都难。

### 9.4 沉淀位置：按工程文档状况分三条路（正文 §5）

| 工程状况 | 正文规定的动作 | 为什么这么分 |
|---|---|---|
| 双文档体系（AI 侧＋人看版） | 同步两份正文 ＋ 两份 `DOCS_INDEX` | 两份会各自漂移；只更新一份，另一份就成了错的入口 |
| 单文档 | 更新主文档 ＋ 索引 | 最少可用闭环 |
| 无文档 | 根目录建 `REFERENCE_ANALYSIS.md` ＋ 在 README 加链接 | 冷启动（第一次建立体系）时必须留一个入口，否则新文件没人能找到 |

（出处：`SKILL.md`「工作流 §5 文档更新」。）

- 关键设计：**§1 就要求先确认文档体系，没有就先建再开始分析**（`[实测]` 正文 §1 原句：「若无文档体系，建议先建一个 DOCS_INDEX.md ＋ 架构总览，再开始分析，否则分析成果无法沉淀」）。把「建容器」放在流程开头而不是结尾，是因为**结尾没人会执行**——会话在交付结论那一刻就结束了。

### 9.5 每个有价值仓库的条目模板（正文代码块逐字结构）

```
### N. {owner}/{repo}
- Stars / Language / License / Updated
- 价值等级
- 一句话评价
**对本工程价值**：可直接用 / 可学方法 / 设计提炼
**License 警示**（如有）
**本地路径**（如已下载）
```

六个字段的必要性（本页展开，`[推演]`）：

| 字段 | 它回答的问题 | 缺了会怎样（具体失效输入） |
|---|---|---|
| `{owner}/{repo}` | 上游是谁（上游＝代码的原始出处） | 无法复查，也无法向别人交代抄了谁；半年后作者换许可证你查不到 |
| Stars／Language／License／Updated | 热度、技术栈、法律、时效 | 缺 `Updated` 时你不知道自己看的是不是三年前的废弃实现（§4.3 候选表里两个仓库的最近推送就在 2024 年） |
| 价值等级 | 六档星级 | 排序做不了，评审时无依据 |
| 一句话评价 | 强迫你压缩结论 | 长段落结论下次没人读，等于没写 |
| **对本工程价值** | 三类归属（可用／可学／设计） | 只留下「好厉害」，不留下「所以我该改哪里」——见 §9.1 第 4 步 |
| License 警示／本地路径 | 法律状态与实物位置 | 第 6 章的乱码沉睡与第 7 章的雷，都从这里复发 |

### 9.6 完成检查清单（正文 §7，实测共 6 条，数法：数 `- [ ]` 开头的行）

1. 所有仓库 License 已检查并标注（含 `licenseInfo` 为 null 时查根目录文件）
2. 应下载文件已下载到正确目录（内容为解码后的真实源码，非 base64 原文）
3. 文档已同步到所有必须更新位置
4. `DOCS_INDEX` 已更新，快速导航已添加
5. 涉及代码对比的已追加对比章节
6. 中文内容已通过编码验证（0 个问号）

清单的编排逻辑（本页归纳，`[推演]`）：**第 1、2 项查法律与实物，第 3、4 项查沉淀，第 5 项查深度，第 6 项查可读性**——四条验收线，缺任一条本次交付都不算完成。

### 9.7 多副本同步纪律

正文版本引用块（`SKILL.md`「版本：v1.1」下方那句）规定：若环境里有本 skill 的多份副本，任一改动后请整体同步其余副本并做 sha256（一种文件指纹算法）校验，避免漂移。

- 这条和第 9.3 节的命名规则是同一个哲学的两次应用：**把「将来会被忘记的信息」编码进「将来一定会被看见的位置」**——前者写进文件名，后者写进指纹。
- `[实测]` 本页取证时确实撞见了副本漂移：仓库副本 102 行／6,454 字节／md5 前 12 位 `7b5b25c4c771`，权威库 104 行／6,845 字节／md5 前 12 位 `1cd9f89d1952`，差的正是那条「联动纪律」引用块。这条纪律要治的现象，在这支 skill 自己身上正在发生。

## 第 10 章 失效与恢复：它怎么坏、怎么发现、怎么退

本章按「一个机制的死亡方式」来写。每条都给**发现方式**（征兆／自检）和**退路**（降级动作）。

| # | 失效模式 | 怎么发现（征兆／自检） | 退路 |
|---|---|---|---|
| 1 | 检索式静默漏条件（连字符／引号／默认搜索字段） | 结果数量正常但内容不对 | 回 §4.2；把检索式原文记进条目；加引号或改走 `--topic` |
| 2 | 候选只有 1 个就深读 | 做不出方法对比表 | 回 §4.3 扩写法，凑满 3 个候选（链 0 第 3 步） |
| 3 | 搜索配额打爆，召回被当成 0 | 连续几条检索式都返回空／403 | 停在搜索池，切核心池做取证；见 §4.6 |
| 4 | 把 API 代码检索结果等同网页结果 | 网页搜得到、API 搜不到 | 按 §4.5 降级顺序换判据，条目里标「降级判据」 |
| 5 | 配额耗尽的静默失败（拉取阶段） | 连续几个仓库「都是空的」；返回 403（拒绝访问的状态码） | 切 `gh` 鉴权；仍不够就按优先级点取（元数据→树→README），见 §5.2 |
| 6 | `--json stars` 直接报错 | 报错 `Unknown JSON field: "stars"` | 改用 `stargazerCount`，或走 REST `.stargazers_count`（§5.3 实测） |
| 7 | 把 `--json licenseInfo` 迁移到搜索命令 | 报错 `Unknown JSON field: "licenseInfo"` | 搜索族用 `license`／`stargazersCount`／`isArchived`；让工具打印可用字段清单（§5.3 实测） |
| 8 | raw 头 ＋ `--jq` 组合崩 | 报错 `invalid character '#' looking for beginning of value` | 去掉 `--jq`（或去掉 raw 头，自己解码）（§5.4 实测） |
| 9 | `HEAD` 当「用户要的那个版本」 | 条目里写的实现与线上版本不符 | 显式指定分支／tag；先查默认分支名（§5.5） |
| 10 | 目录树被截断却当全量用 | 返回里 `truncated=true`（实测巨型仓库 71,638 条即为此值） | 放弃全树，改单层 `contents/{目录}` 逐层点取；架构分层判断（维度④）降级为「抽样判断」并在条目里标注 |
| 11 | base64 原文落盘 | 落盘字节数比接口 `.size` 大约 1/3；文件里没有语法正确的开头 | 用正文的管道重取；条目里的「本地路径」字段核对文件名与上游路径（§6.1 的 1,357→1,843 就是尺子） |
| 12 | 许可证误判为「无」 | `licenseInfo`／`.license` 为 null 或 `other`／`NOASSERTION` | 走三级补查（§7.3）：根目录文件 → README 声明；仍无才落「无 License，不可抄码」 |
| 13 | 抄答案不抄问题（抽象第 1 步跳过） | 抄完之后原问题仍在，代码还多了两套 | 回 §9.1：每条结论后面必须能接一句「所以我改哪个文件」 |
| 14 | 机械转译 copyleft 代码 | 与上游存在连续逐字相同段落 | 立即从可发布构建里撤出，只保留「问题句＋决策」重述（§7.2、§9.1 第 2 步） |
| 15 | 上游漂移（内容变了） | 条目里的 `Updated` 与你实际看到的文件不符；复核条件跑不通 | 以检索日期为准重跑取证，并在原条目**追加**「复核记录」而不是覆盖——保留历史判断 |
| 16 | 结论没回写 | `DOCS_INDEX` 里没有这一条；磁盘有文件但文档无条目（勾稽不上） | 先补条目再补内容；条目缺了，这份下载等于匿名资产 |
| 17 | 中文写成问号 | 正文 §7 第 6 项验收：中文字符数 > 0 且问号数 = 0 | 改用 Python 指定 utf-8 重写；不要走 PowerShell 管道传中文（§6.4） |
| 18 | 多副本漂移 | md5／sha256 指纹不一致（实测两种副本差 2 行、391 字节） | 以权威库为准整体同步，逐份校验（§9.7 正文纪律） |
| 19 | 整仓克隆打爆磁盘 | 大仓库 clone 到默认位置，几百 MB 起步（实测 555 MB 一例、2.5 GB 一例） | 遵守 §4 矩阵第 5 行：选择性下载关键文件；落盘位置先定（§7.4） |
| 20 | Private／保密越界 | 作者明示过「不开放复用」，而你已下载 | 立即停止使用并删除本地副本，条目改为「仅记录思路」；这是 §4 矩阵第 4 行的回滚路径 |

**恢复的总原则**（本页组织，`[推演]`）：**这套流程的每一步都可重放（重放＝用同一条命令再取一次），所以失效不需要「猜」——只需要重跑对应命令并比对指纹或数值**。第 12 章末给出的七条复核命令（§12.11）就是这个原则的落地，任何一条跑不通都能立刻定位到章。唯一不能靠重放恢复的是 #14 与 #20（法律与授权类），它们的退路只有「撤出来」，所以这两条宁可提前挡在第 7 章的表里。

## 第 11 章 例行体检：怎么验证它真在生效

本 skill 没有「自动衰减」这类机制（衰减是记忆类 skill 的概念，正文里没有对应物），所以这里体检的含义是：**验证这套 SOP 有没有真的在约束行为，还是只躺在文件里**。

### 11.1 八条探针（探针＝只检查不改东西的脚本或命令）

| # | 探针 | 命令形状 | 判定它「真在生效」的样子 |
|---|---|---|---|
| P1 | 配额可用 | `gh api rate_limit --jq '.resources.core'` | 能读出 `limit`（实测 5,000）与 `remaining`；说明鉴权在，不是降级路 |
| P2 | 元数据字段名正确 | `gh repo view <某公开仓库> --json stargazerCount,licenseInfo,primaryLanguage` | 有 JSON 返回，不报 Unknown JSON field |
| P3 | 检索旗标可用 | `gh search repos <词> --license mit --stars ">100" --json fullName,license,stargazersCount` | 返回候选表；说明选靶层的判据在你的环境里跑得通（§4） |
| P4 | 树可读且知道完整度 | `gh api repos/{o}/{r}/git/trees/HEAD?recursive=1 --jq '{n:(.tree\|length),t:.truncated}'` | `t=false`；为 true 时说明靶子过大，需换点取 |
| P5 | 解码管道通 | `gh api repos/{o}/{r}/contents/{p} --jq '.content' \| base64 -d` 后看首行 | 首行是真实源码语法，不是一串 base64 字符 |
| P6 | 许可证三级补查通 | 元数据 → `gh api repos/{o}/{r}/contents`（列根目录）→ README 原文搜 `License` | 任一级给出明确许可证即停；三级全空才允许写「无 License」 |
| P7 | 沉淀真的落了 | 在工程文档里搜 `{owner}/{repo}`；`DOCS_INDEX` 里数条目 | 文档条目数 ≥ 磁盘参考目录数（勾稽） |
| P8 | 中文没写坏 | 数新写文档里的中文字符数与 `?` 数 | 中文字符数 > 0 且问号数 = 0（正文 §7 第 6 项） |

- **P7 是最关键的一条**，也是唯一不能纯靠命令行完成的：它要求「这次分析在别人（或下一次的你）眼里可找到」。前 6 条全绿、P7 空，就是典型的「流程执行了，产出没沉淀」——这支 skill 的全部价值都在 P7 上兑现。
- P3 是本页新增的探针（正文没有选靶层，所以也没有对应自检）。`[推演]` 它要防的失效输入：换了环境或换了工具版本后 `--license` 旗标不存在，你的检索式静默退化成不带许可证过滤的版本，候选表照样满页，许可证雷重新回到下载之后才被发现。

### 11.2 生效性抽查（建议每轮分析结束后做，成本 5 分钟）

1. 随机挑一条**已登记**的仓库条目，不看正文只按条目里的字段复现一次取证——复现得了＝条目自洽。
2. 检查条目里 `License` 字段与「License 警示」是否**同时**存在（只有前者、没有后者的仓库，正是最容易出事的那批：`other`／`NOASSERTION` 全在这一批里）。
3. 检查是否有任何文件的**内容仍是 base64**：列参考目录，看文件大小是否与接口报告的原始字节数量级一致（§6.1 的 36% 膨胀比就是尺子）。
4. 检查一次前缀纪律：随机挑三个下载文件，看能否只靠文件名反推出来源仓库（§9.3）。
5. 检查中文问号：把分析报告读一遍，问号（`?`）成片出现＝§6.4 的编码纪律被绕过了。

### 11.3 本 skill 自身的版本体检（每升版一次）

- `[实测]` 正文 frontmatter 有**重复的 `metadata` 顶层键**：同一份 frontmatter 里出现两次 `metadata:`（当日实测 `^metadata:` 计数＝2），两次都含 `agent_created: true`，只有第二次带 `version: 1.1.0`。多数 YAML 解析器（把配置文本读成结构化数据的工具）以最后一次为准，因此版本号仍读得到，但**这是隐患**：换更严格的解析器可能直接报错或整段丢字段。修法：两个键合并为一个。本页不改权威库（不在写入权限内），只如实登记。
- `[实测]` `CHANGELOG.md` 的 v1.1 节三个小标题里，「解决了什么」「怎么解决的」两条**原文标注「未记录」**。本页不替它编造变更理由，第 15 章「诚实留档」再记一次。
- `[实测]` 版本写法在本库内**三套并存**（详见 §15.4）：本支 frontmatter 用 `1.1.0`（无 v 前缀），同库另一支用 `v1.1.0`，还有支用 `v3.5-sc1.5` 这种带后缀的复合写法（2026-10-09 起 17 支正文全部带 `version`，原先缺字段那一格已消除）。

## 第 12 章 端到端走查：从「没有链接」到一个可用条目

**本章是一条可照抄的真实路径**：起点是用户**没给链接**（这是正文没覆盖、第 4 章补的那类输入），终点是一条沉淀条目。所有数字都是本页取证当天（2026-10-09）用真实命令跑出来的，复核方法在 §12.10。

### 12.0 前置：§1 识别工程上下文

假设当前工程是一个 Godot（一款开源游戏引擎）游戏项目：技术栈标记文件是 `project.godot`（Godot 项目的入口配置文件，正文 §1 把它和 `package.json`／`requirements.txt`／`Cargo.toml` 并列为「用什么栈」的判据文件）；参考资产约定放 `reference_repos/`；文档体系为单文档（一份分析主文档＋`DOCS_INDEX.md`）。三条都确认了才往下走。

**用户输入原文（假设的、可照抄的形态）**：「找个 GDScript 写的 Roguelike 参考一下，我想把满屏子弹那段做好。」

### 12.1 选靶（§4 链 0）：构造检索式

```
gh api "search/repositories?q=roguelike+language:GDScript+stars:>100&per_page=5"
     --jq '{total:.total_count, incomplete:.incomplete_results}'
→ 当日实测 total = 7、incomplete_results = false
```

链 0 第 2 步判读：7 不算过宽也不算 0 → 可以进候选表；链 0 第 3 步判读：凑满 3 个（实测拿到 4 个）→ 允许进入评级。

### 12.2 选靶：取候选表并做三个一票否决

```
gh search repos "roguelike" --language GDScript --stars ">100" --sort updated --limit 4
   --json fullName,stargazersCount,license,size,pushedAt,isArchived
```

当日实测四行（完整表见 §4.3）。逐个过筛：`isArchived` 四条都是 false（归档关通过）；`license` 四条都是 MIT（许可证关通过）；`size` 最大 14,038 KB ≈ 14 MB（体积关通过，都远低于正文 §4 的 100 MB 线）；`pushedAt` 有两条落在 2024-10（时效关：**不否决但要降级**——教程型仓库停更两年不影响读设计，影响的是「它能不能在新引擎版本上跑起来」，条目里要写这句）。

## 第 13 章 反模式清单：16 种「不要这样用」

| # | 反模式 | 后果（说清是哪一层塌了） |
|---|---|---|
| 1 | 只读 README 就下结论「这仓库没东西」 | 取证层塌：维度④架构、维度③设计都藏在目录与源码里，README 只讲功能不讲取舍 |
| 2 | 匿名直连硬跑批量任务 | 拉取层塌：配额打到上限后返回空／403，批量结论集体失真（§5.2） |
| 3 | 照抄正文的 `--json stars`，并把报错当成「仓库不存在」 | 排障方向整个跑偏：真正的问题只是字段名（§5.3） |
| 4 | 把 `gh repo view` 的字段名迁移到 `gh search repos` | 同上，报错长得一模一样、原因毫不相干（§5.3 实测） |
| 5 | `Accept: raw` 之后顺手加 `--jq` | 拿到报错却找不到原因（§5.4） |
| 6 | `licenseInfo` 为 null 就直接判「无 License」 | 判断层塌：冤枉一份 MIT 仓库，或漏读 README 里的 CC BY-SA（§7.3） |
| 7 | 元数据显示 `Other`／`NOASSERTION` 就当宽松许可 | 边界层塌，最贵的一种：法律结论建在一个占位字符串上（§7.3） |
| 8 | base64 原文落盘，文件名照样起好 | 保真层塌：几周后才暴露，且上游信息已丢失（第 6 章） |
| 9 | 下载文件不带来源前缀 | 溯源能力塌：文件与仓库对不上号，改名与清理全线冻结（§9.3） |
| 10 | 对 >100 MB 仓库直接 clone 全库 | 磁盘与时间双塌，且大头是你不会看的资产（§7.4 实测 555 MB／2.5 GB 两例） |
| 11 | 把 REST 的 `.size` 当字节读 | 判据反向：567,682「字节」看着远小于 100 MB，于是放行了本不该放行的整仓克隆（§7.4） |
| 12 | 把 star 数当价值等级 | 判断层塌：星级不再能解释「为什么值得抄它」（§8.3） |
| 13 | 分析结论只写在对话里，没进文档与索引 | 沉淀层塌，整套流程白跑：下一次会话归零（第 9 章） |
| 14 | 用 GPL 仓库的源码「翻译」成自己项目的代码 | 边界层塌：机械转译不改变衍生性质，正文对 GPL／AGPL 明写「不抄码转译」（§4 矩阵第 2 行） |
| 15 | 用热度条件（`stars:`）当过滤做选靶 | 选靶层塌且无痕：真正对口的中小仓库被静默删掉，候选表不显示「被误杀」的痕迹（§4.4） |
| 16 | 拿 API 代码检索的 0 结果当「这段代码不存在」 | 取证层塌：官方已声明 API 与网页结果可能不一致（§4.5）；否定结论必须有第二个判据支撑 |

**一条总原则**：这套 SOP 允许你「看不值钱」，不允许你「不知道自己能用什么」。所以第 6、7、14、16 条（判据与边界类）排在第 1、12 条（效率类）之前——**判错法律与判错存在性，比看错价值贵得多**。

## 第 14 章 速查表（Cheat Sheet）

**四问四查**：**看哪个**（检索式＋候选表，链 0）／**能不能用**（License 六行，链 A）／**值不值得看**（五维六档，链 B）／**沉到哪里**（条目模板＋索引＋6 项清单，链 C）。

**七步**：识别上下文 → 查询 → 价值五维 → License 六行 → 文档更新 → 编码验证 → 6 项清单。

**选靶三件**：检索式（`language:`／`license:`／`topic:`／`stars:`／`pushed:`／`archived:`）→ 读 `total_count` 与 `incomplete_results` → 候选 ≥3 再评级。代码检索另记：**API 引擎与网页可能不一致**，正则不可用（官方口径）。

**四字段取证**：元数据（`gh repo view --json stargazerCount,licenseInfo,primaryLanguage,description,repositoryTopics`）／目录树（`git/trees/HEAD?recursive=1`，**必看 `truncated`**）／README（`readme -H Accept:...raw`，**别加 `--jq`**）／关键源码（`contents/{p} --jq '.content' | base64 -d`）。

**三套字段名**：`gh repo view`＝GraphQL 名（`stargazerCount`、`licenseInfo`）｜REST＝下划线名（`stargazers_count`、`.license.spdx_id`、`.size` 单位 KB）｜`gh search repos`＝搜索族名（`stargazersCount`、`license`、`isArchived`、`size`、`pushedAt`）。**跨族迁移必报错**。

**三级许可证补查**：`licenseInfo` → 根目录 LICENSE／LICENSE.md／COPYING → README 的 License 节 → 全空才判「无 License」。`other`／`NOASSERTION` **等同 null**，必须读原文。

**六行下载矩阵**：MIT／Apache／CC0＝全量可用 ｜ GPL／AGPL＝只读 README，不下源码不转译 ｜ 无 License＝只下骨架＋`_NO_LICENSE` ｜ Private＝零下载 ｜ >100 MB＝点取不 clone（REST `size` 单位是 KB）｜ 纯文档索引＝在线浏览记 URL。两条同时触发时**取保守的一条做动作，把宽松那条写进备注**。

**五维**：可直接用／可转译／设计提炼／架构分层／视觉规范（并行独立，不串行；星级取最高维度不取最低）。**六档**：★★★★★ → ☆（☆也要写下为何无用）。

**抽象四步**：定位决策 → 剥离表达 → 换表达重述 → 反向验证。每步产出分别是「问题句／不带代码的一句决策／与上游零逐字相同的重述／本工程一次最小实现」。

**两条红线**：禁止商用素材绝不纳入；保留所有权利的参考代码不整段进可发布构建（判据：**构建产物里不许有与上游连续逐字相同的段落**）。

**命名**：`{Repo缩写}_{原名}`，同仓统一前缀，保留原扩展名；无许可证加 `_NO_LICENSE`。

**配额**：鉴权核心 5,000 次／小时（实测）、搜索 30 次／分钟（实测）、匿名 60 次／小时（正文断言，未独立实测）。

**验收数字**（复算方法在第 12 章）：示例仓库 9,633 star／MIT／GDScript／555 MB／树 4,645 条未截断／单文件 1,357 字节→base64 1,843 字符（膨胀 ≈36%）；巨型仓库树 71,638 条且**截断**；`AGPL` 一例 2.5 GB；`NOASSERTION` 一例原文为「禁止商用的创作共用」。

**30 秒回忆法**：**先问靶子从哪来，再问许可允不允许，再问对本工程哪一维有用，最后问这条结论沉在哪个文件里**——四问都答得出，这轮分析才算完成。

| `description` | 折叠成单行后约 **290 余字符／630 余字节**（数法：取 frontmatter 的 `description` 值，按 YAML 折行规则拼成一行，在 UTF-8 环境下统计字符数；中文一字＝1 字符＝3 字节） | 见 §15.2 的三上限说明。**这三个数是量级判读，不是逐字符复算值**——读者若需精确数，按上述数法自己跑一次即可 |

### 15.2 description 长度与三个并存的上限（不许合一）

本库口径对描述字段长度**同时**记录着三个不同来源的数字，各自含义不同，本页按纪律并列保留：

| 值 | 来源口径 | 用途 |
|---|---|---|
| **1,024** | 开放标准与上传校验 | 规范层允许的上限 |
| **1,536** | 某宿主常驻清单的截断位 | 装载层实际截断的位置 |
| **200** | 某帮助中心的上传口径 | 平台侧的更严口径 |

本支描述约 290 余字符：**未超 1,024 与 1,536，超出 200 那一档**。这条差异要如实登记——既不要说「合规」也不要说「超限」，三个口径各自对应不同环节。本页不修改正文（不在写入权限内）。

同时，正文 `description` 的写法是本库的一贯规范：**做什么 ＋ 何时触发 ＋ 覆盖范围 ＋ 内置红线 ＋ 不适用转介**（末句「不适用：非 GitHub 仓库的普通网页抓取」把边界外的事明确转给别的技能）。**写清「不适用」和写清「触发」同样重要**——调度靠这两句决定要不要把你叫进来。

### 15.3 🔴 真缺陷一：全部知识压在一份文件里（递归 2 个文件），什么时候开始失效

**事实**（`[实测]`，当日递归清点）：本支递归文件总数 **2**（`SKILL.md` ＋ `CHANGELOG.md`），没有 `references/`、没有 `scripts/`、没有 `assets/`。同库对照（同一把尺子当日实测，数法：递归数文件）：**交付流水线 51 个文件**、**失败模式库 21 个**、贴身导师 8 个、LLMwiki 入库 1 个（且无 version 字段）。

**外部依据**：Agent Skills 规范（agentskills.io 的规范页）明确建议——主文件正文控制在 **500 行以内（约 5,000 tokens）**，**长流程、复杂边界情况、密集技术说明应当移出正文**，交给按需加载的分包文件；组织方式是**三层渐进披露**：清单（`name`＋`description`）先常驻 → 命中任务才读 `SKILL.md` 正文 → 需要时才读被引用的文件；三个分包目录各司其职：`scripts/` 放可执行程序、`references/` 放技术文档、`assets/` 放静态模板与数据；**交叉引用只允许一层深**。

**为什么现在还不算坏**：本支正文 104 行／6,845 字节，约在 500 行建议额度的两成。**单文件在正文短小时是最优形态**：少一层跳转、少一处漂移面、读者一眼读完。所以这条缺陷的正确表述是**「规模化风险」而不是「已发生的故障」**——把两者混着写会让读者以为这支护不住。

**临界判据（本页给，`[推演]`）**：用「主体字节 ÷ 递归文件数」当压缩度指标——本支 6,845÷2 ≈ **3,423 字节／文件**（意味着全部知识挤在一页），失败模式库 7,610÷21 ≈ 363，交付流水线 18,310÷51 ≈ 359。**当一支 skill 的正文超过约 300–400 行、或开始出现下面任何一类内容时，单文件形态就开始失效**，应当把对应内容拆进分包：

1. **表类**（本支已有三张：四字段命令表、五维矩阵、六行许可矩阵）——再长就必须外置成 `references/`；否则宿主读到第 4 张表时，第 1 张表已经被挤出上下文窗口（上下文窗口＝一次对话能装下的文字量）。
2. **清单类数据**（下载前缀缩写表 `VS_`／`HS_`／`GDP_`、许可证家族表、已分析仓库清单）——这是**数据不是规则**，规范把它归给 `assets/`。留在正文里会让规则文件越长越不像规则。
3. **可执行判据**（三级补查、体积复算、编码验证）——这些本可以是一个真探针脚本（`scripts/`）。对照同库磁盘缓存那一支就带了一个可执行体检脚本。**没有 `scripts/` 的直接代价：本页 §11.1 那 8 条探针全部要靠人（或模型）照着文字手敲，所以「它有没有真在生效」永远无法自证。**
4. **项目上下文**（正文提到另有一个项目专用派生版承载回写位置、已分析清单、缩写表）——这正是「通用 SOP ＋ 专用配置」分离，说明作者已经在用**另一支 skill** 来解决同一件事；分包机制能把它降级成一个 `references/project-profile.md`。

**`[推演]` 具体失效输入（这条是本章的核心）**：把 §4 选靶层（本页补的，约 200 行）真按原样并回正文——正文从 104 行涨到 300 行以上，五维矩阵与六行矩阵被推到文件后半段。某次用户说「参考这个 GPL 仓库把它的战斗系统改一改」，命中的 agent 按渐进披露读完正文前半段，上下文已被检索式模板与命令表占满，**§4 矩阵里「GPL／AGPL 只读 README、不抄码转译」那一行没进窗口**，它于是按前半段「MIT 可全量下载、自由参考修改」的记忆处理 GPL 仓库 → 边界层失效，而且失效位置恰好是全 skill 最贵的那一行。**同一条内容放进 `references/license-matrix.md` 并让正文只留一行指针，就不存在这个洞**——这是分包的真实收益，不是排版洁癖。

**第二个失效面（协作）**：单文件意味着**任何改动都动同一份文件**。本库存在多窗口并行改动的常态（同库多 Agent 治理那一支整支都在讲防撞车），17 支并行产出时，本支若要同时补「选靶层＋抽象四步＋许可证三级」，三个改动全部落在同一个 104 行文件上，冲突面是 100%；分包后三个改动落在三个文件，冲突面接近 0。`[推演]` 输入例子：两个窗口分别往正文 §4 前后各插一段，后写的窗口整块覆盖前写的段落——**丢掉的那半张许可矩阵不会报错**。

### 15.4 🔴 真缺陷二：三种版本号写法在本库并存，且会骗过一致性检查

**事实**（`[实测]`，当日 grep 全库 frontmatter 的 `version:` 行所得；只列与本缺陷直接相关的写法形态）：

| 写法形态 | 例（同库内的支） | 特征 |
|---|---|---|
| 纯数字三段 | **本支 `1.1.0`**、交付流水线 `1.5.0`、贴身导师 `1.2.0`、踩坑日志 `1.5.1`、LLMwiki 入库支 `1.0.0` | 无 v 前缀 |
| 带 v 前缀 | 企业级审判官 `v1.1.0`、失败模式库 `v1.1.1`、项目验收官 `v1.3.0`、useskill `v2.5`（两段） | v 前缀 ＋ 段数不一（2 段与 3 段混用） |
| 复合带代号后缀 | 记忆纪律 `v3.5-sc1.5` | 版本号里塞了体系代号后缀，已不是纯 SemVer |

**为什么这不是美学问题，而是判据问题**：本库有「全库体检」这类检查（口径文件本身就记载了主控方两次被尺子骗到的实测：某检查按「后缀等于 `.bak`」判备份件，对真实文件名（`.bak` 之后还挂着一串 8 位日期）**永远零命中**；首批表用单层目录数附属件，把递归 51 个文件的支数成了 50 或 13）。**版本号写法不统一会让同一类错误发生在版本一致性检查上**：

- `[推演]` 具体失效输入一：体检脚本用正则「两段落号」抓版本（形如 `version: v?\d+\.\d+`），本支 `1.1.0` 三段式被截成 `1.1` 后丢掉尾段，`v3.5-sc1.5` 匹配到 `3.5` 丢掉后缀——脚本报告「全库版本一致」，而真实情况是四种形态并存。**这类检查会永远绿**。
- `[推演]` 具体失效输入二：有人想把「比 v1.1.0 更新的支」列出来，按字符串排序得到 `1.1.0` 与 `v1.1.0` 分成两组、`v1.10.0` 排在 `v1.9.0` 之前——**字符串比较对版本号是错的**，但结果看起来完全正常，不会报错。
- `[推演]` 具体失效输入三：本支正文无「版本」节（§15.1），意味着**想核对「正文声称的版本 == frontmatter 的版本」这条检查时，本支无法参与**——不是不一致，而是**没得比**，检查把它跳过了。这正是主控方复测口径修正 #9 的动机：把 frontmatter／正文／CHANGELOG 三通道分开采，才能发现「磁盘缓存正文自述 v1.1 而 frontmatter 写 v1.0」这类真冲突（同库另一支的实测）。本页按同一把尺子如实登记本支三通道。

**修法建议（登记，不代改）**：① frontmatter 统一纯数字 SemVer（`x.y.z`，**不带 v**），显示层需要「v1.1.0」时由渲染方加前缀；② 体系代号从版本号里拆出去，放 `metadata` 的独立字段；③ 每支正文都开一节「版本」自述当前值，让三通道检查真能跑；④ 检查脚本按「三段数字」归一化后再比较，并显式统计**匹配失败清单**（匹配失败不许静默跳过——**一条会跳过的检查等于一条没有的检查**）。

### 15.5 边界与相邻技能（正文声明的分工）

- **不适用**：非 GitHub 的普通网页抓取（正文 description 末句明确转介给网页工具类技能）。

### 15.6 冷启动：第一次用这套流程的人需要什么

正文 §1 已经内建了冷启动处理（无文档体系 → 先建 `DOCS_INDEX.md` ＋ 架构总览）。补三条实操顺序（本页给，`[推演]`）：

1. 先建**一个空的**分析主文档＋索引，再开始拉第一个仓库——不要「攒够三个再一起写」。`[推演]` 失效输入：攒够三个再写，会话在第 2 个仓库后被打断，三个仓库的分析全部只存在于对话里，产出为零。
2. 第一次只跑元数据 ＋ 目录树 ＋ README 三件，不下载任何文件；目的是熟悉矩阵而不是一次做完。
3. 第一次务必亲手走完一次 base64 解码并核对字节数（§6.1 的 1,357 与 1,843）——这一条只有做一次才不会忘；第 6 章的延迟暴露故障全部来自「没做过一次」。
4. 第一次选靶时把 `--limit` 压到 3–5（默认 30），先看清 `total_count` 再说；搜索配额 30 次／分钟，别拿它试错。
