# Cao-GitHub仓库检索提取（github-repo-extract v1.1.0）

> [← 返回总目录](../README.md#skills-index)

## 五分钟速览

如果只有五分钟，记住这六句。

1. 拉取优先 gh CLI 鉴权，匿名 API 每小时 60 次的限流问题直接消失。gh 不可用再用 Python 直连兜底。
2. License 用决策矩阵查表说话，不许凭感觉。MIT/Apache/CC0 可全量下载，GPL 系只学方法论，无 License 标注后禁抄码。
3. API 的 licenseInfo 字段经常返回 null，多数时候仓库其实有 License。null 必须补查根目录的 LICENSE/COPYING 文件再判定。
4. contents 接口返回的 content 是 base64 编码，必须先解码再落盘，否则文件名正常、打开全是乱码，而且你可能几周后才用那段代码才发现。
5. 价值判断拆五个独立维度打分，从核心参考到无用共六档，好不好用让表说话。
6. 分析完强制沉淀进文档体系，没有文档体系就先建一个再开始分析。

一句话概括设计目标，**把「看开源项目」变成标准流水线，怎么拉、允不允许用、值不值得看、看完沉到哪，四问各有一层机制兜底**。

## 它在解决什么问题

参考开源项目这件事，大多数人卡在四个地方。

| 故障 | 表现 | 对应设计 |
|---|---|---|
| 限流掐断 | 匿名 API 每小时 60 次，翻两个仓库就被掐 | gh CLI 鉴权拉取 + urllib 直连兜底 |
| License 雷 | 凭感觉下载，雷埋进项目里等爆 | 下载决策矩阵 + null 陷阱规则 |
| 乱码沉睡 | base64 原文落盘，几周后才发现全是乱码 | 解码规则写死在命令里 |
| 结论蒸发 | 分析散在对话里，下一轮归零 | 强制沉淀进文档体系 |

## 拉取层详解

每个字段都有对应的 gh 命令，元数据、目录树、README、关键源码各一条，规则里给了对照表。兜底路径也想好了，GitHub 域名被 hosts 拦截或 gh 不可用时，用 Python `urllib.request` 直连 `api.github.com`（绕过 DNS）。

**base64 这个坑值得单独讲**。`contents/{path}` 与 `readme` 接口返回的 `content` 字段是 base64 字符串。直接落盘的话，文件名正常，大小看着也对，打开全是乱码。最坑的是它不立刻暴露，你可能几周后要用那段代码才发现，那时连当初是从哪个仓库拉的都忘了。规则把解码写死在命令里（`--jq '.content' | base64 -d`），让这个坑在结构上不可能发生。

大仓库的 trees 递归可能很大，按需取关键路径即可，不整棵拉。

## License 层详解

下载决策矩阵一次判清。

| 条件 | 决策 |
|---|---|
| MIT / Apache / CC0 / 公共领域 | 可全量下载，自由参考修改 |
| GPL-3.0 / AGPL | 只下 README 学方法论，不下载源码，不抄码转译 |
| 无 License | 只下骨架学方法论，文件标注「无 License，不可抄码」 |
| 作者标注 Private | 只参考公开设计理念，一个文件都不下载 |
| 仓库 >100MB | 选择性下载关键文件，不 clone 全库 |
| 纯资源索引/文档 | 不下载，在线浏览 |

**null 陷阱**是这层的精华。API 的 `licenseInfo` 字段经常返回 null，多数时候仓库其实有 License，只是作者把 LICENSE 文件放在根目录、元数据里没标。直接判无 License 会冤枉仓库，判反了会惹麻烦。所以规则要求 null 时必须额外查根目录的 LICENSE 或 COPYING 文件再判定。

外加一条硬红线，禁止商用的素材（CC-BY-NC 等）绝不纳入工程。抄代码一时爽，License 出事是真麻烦，这条矩阵就是防它的。

## 价值层详解

「这个仓库对我有没有用」是个坏问题，答案全凭感觉。拆成五个独立维度就清楚了。

| 维度 | 含义 |
|---|---|
| ① 可直接使用 | 资产、插件、模型拿来就用 |
| ② 可提取转译 | 跨语言/框架移植设计模式（C# 的思路搬到 GDScript） |
| ③ 设计提炼 | 核心机制、算法、架构决策 |
| ④ 架构分层 | 目录结构、模块划分可参考 |
| ⑤ 视觉规范 | UI 模式、设计语言可借鉴 |

打完分落入六档，★★★★★ 核心参考到 ☆ 无用。哪个仓库值几个星，表说了算，不再是人嘴上说「感觉挺牛」。

同类仓库给出不同实现时，追加方法对比表（维度、参考仓库方案、当前工程方案、谁的更好、建议），让对比结构化地留下来。

## 沉淀层详解

分析完不落盘，下一轮归零。所以流程第一步就确认文档体系，没有就建议先建一个 DOCS_INDEX 再开始分析。结论按工程类型沉进 docs/，每个有价值的仓库至少记五样，元数据与价值等级、一句话评价、对本工程的价值类型、License 警示、本地路径。

还有一层编码自卫。中文内容用 Python 指定 utf-8 写，避免 PowerShell 管道传中文（会损坏）。写完验证，中文字符数大于 0 且问号数等于 0。这个「问号数等于 0」的验收标准，本身就是从踩坑日志的中文编码根因里长出来的。

## 跟手动翻的区别

| 手动参考 | 这套流水线 |
|---|---|
| 匿名 API 每小时 60 次 | gh CLI 鉴权，配额不是问题 |
| License 凭印象，雷埋进项目 | 决策矩阵查表，null 陷阱已排 |
| base64 落盘几周后才发现乱码 | 解码规则写死在命令里 |
| 好不好用凭感觉 | 五维分开打分，六档价值等级 |
| 结论在对话里蒸发 | 强制沉淀进文档体系 |

## 什么时候不用

不是 GitHub 仓库的普通网页抓取，那是另一类活。只想看看 README 了解概念，在线浏览就行，不用起流水线。
