# Cao-GitHub仓库检索提取（github-repo-extract v1.1）

> [← 返回总目录](../README.md#skills-index)

## 一句话

把"看开源项目"这件事变成一条标准流水线：怎么拉、值不值得看、License 允不允许用、看完沉到哪。

## 它解决什么问题

- **匿名 API 限流。** GitHub 匿名请求每小时 60 次，翻两三个仓库就被卡住，还得等。
- **看到好代码，不确定能不能用。** 没有 License 的仓库、GPL 的仓库、标注 Private 的仓库，处理方式完全不同，凭印象判断迟早出事。
- **分析完了没地方放。** 上次怎么看的、结论是什么，全在对话里，下一轮重头再翻一遍。
- **base64 当成源码存了。** GitHub 的 contents 接口返回的是 base64，直接落盘就得到一堆乱码。
- **中文写进文件变成问号。** Windows 上用 PowerShell 管道传中文，编码一坏，文档全废。

## 核心机制

**拉取优先走 gh CLI。** 已经登录鉴权，没有匿名限流。`api.github.com` 直连只作兜底——域名被 hosts 拦截时，用 Python 的 `urllib.request` 绕过 DNS 直连。

元数据、目录树、README、关键源码各有对应的命令，规则里给了对照表，不用每次现查。

**文件内容必须解码后再落盘。** contents 和 readme 接口返回的 `content` 是 base64 字符串，得先 `base64 -d` 或者用 Python 解码。**把 base64 原文当源码存下来是个很隐蔽的错误**——文件名对、大小也像那么回事，打开才发现全是乱码。

**5 维度价值矩阵。** 每个仓库从五个角度过一遍：能不能直接用（资产、组件、模型）、能不能跨语言转译（C# 转 GDScript 这类）、有没有设计可提炼（核心算法、架构决策）、架构分层能不能学、视觉规范能不能参考。用星级标价值等级，从核心参考到无用分六档。

**License 红线决策矩阵。** 这是整套流程里最不能含糊的部分：

| License | 决策 |
|---|---|
| MIT / Apache / CC0 / 公共领域 | 可全量下载，自由参考修改 |
| GPL-3.0 / AGPL | **只下 README 学方法论，不下载源码，不抄码转译** |
| 无 License | 只下骨架学方法论，目录加 `_NO_LICENSE` 后缀标注 |
| 作者标注 Private / 保密 | 只参考公开设计理念，**不下载任何文件** |
| 仓库 > 100MB | 选择性下载关键文件，不 clone 全库 |

另有一条硬规矩写在最上面：**禁止商用（CC-BY-NC 等）素材绝不纳入工程。** 外部参考代码保留所有权利的，只作只读参考，不整段照搬进可发布构建。

**下载文件带来源前缀。** 用 `{仓库缩写}_{原文件名}`，同一个仓库统一前缀（`VS_` 对应 vampire-survivors，`HS_` 对应 HordeSurvival）。以后翻到一个文件，一眼知道它从哪来、以什么授权来的。

**中文编码验证。** 写文档用 Python 的 `open(path, 'w', encoding='utf-8')`，避开 PowerShell 管道。写完之后验证：中文字符数大于 0，问号数等于 0。两个条件都过才算写成功。

## 一个很隐蔽的坑

GitHub API 返回的 `licenseInfo` 字段会**假报 null**。

有些仓库的 License 不是走标准流程加的，只是往根目录丢了一个 `LICENSE` 或 `COPYING` 文件。这种情况下 API 的 `licenseInfo` 返回 null——如果你直接按"没有 License"处理，就会把一个 MIT 仓库当成保留所有权利，白白放弃可用的资源。

规则里现在的做法是：`licenseInfo` 为 null 时，**额外检查根目录有没有 LICENSE / COPYING / LICENSE.md 文件**，确认过再下判断。

这个坑是靠实际比对发现的：API 说 null，仓库根目录躺着一个 LICENSE 文件。

## 和同类方案比，差在哪

| 常见做法 | 本 skill |
|---|---|
| 匿名 API 拉取，被 60 次/小时限流 | gh CLI 鉴权优先，直连仅作兜底 |
| 凭感觉判断能不能抄 | License 决策矩阵，五类情况分别对应动作 |
| licenseInfo 为 null 就认定无授权 | 补查根目录 LICENSE 文件再判定 |
| base64 原文直接落盘 | 强制解码后再写，避免存成乱码 |
| 下载文件混作一团，来源不明 | 文件名带仓库前缀，来源与授权可追溯 |
| 分析完散在对话里 | 固定文档模板 + 索引更新 + 完成检查清单 |
| Windows 下中文写坏 | Python utf-8 写入 + 写后问号数校验 |

## 3 分钟上手

1. 把文件夹放进 skills 目录（见[总目录](../README.md#skills-index)）；
2. 丢一个 GitHub 仓库链接过来，说"分析一下""看看能不能借鉴"即可触发；
3. 它先识别你的工程上下文（技术栈、有没有文档体系），没有文档体系会建议先建一个，否则分析成果没地方沉淀；
4. 分析结果落到固定模板里，同类仓库还会追加方法对比表。

## 实战绩

v1.1 的规则全部来自真实使用。上面那条 `licenseInfo` 假报 null 的坑、以及"base64 原文被当源码落盘"的失误，都实际发生过并写进了检查清单。

版权红线是硬规矩，不是建议——这条来自一个更早的原则：不用任何禁止商用的素材。

天倾项目另有一份专用版本（`github-repo-extract-tianqing`），作为项目配置不随通用版发布。

## 适用 / 不适用

- ✅ 拿到 GitHub 链接要分析、参考、借鉴、转译、评估的场合；需要批量评估多个仓库价值的场合
- ❌ 非 GitHub 的普通网页抓取（那个走网页工具那条路）
