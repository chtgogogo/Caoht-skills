## 第 0 章 五分钟速览

1. **它管的是一件很具体的事**：别人给了你一个 GitHub（全球最大的代码托管网站）仓库链接，你要在几十分钟内回答四个问题——**能不能用、值不值得看、怎么拉回来、看完沉到哪里**。
2. **七步流水线，顺序不能乱**：识别工程上下文 → 查询 → 价值判断 → 下载决策 → 文档更新 → 编码注意 → 完成检查（即 `SKILL.md` 的「工作流」§1–§7）。前一步是后一步的输入，跳步的代价在第 10 章逐条列出。
3. **拉取一律优先 `gh` CLI（GitHub 官方命令行工具，登录状态下自带鉴权）**，匿名直连 API（不登录的程序化访问接口）只作兜底。实测鉴权后核心配额是 5,000 次／小时，正文断言的匿名配额是 60 次／小时——差 80 多倍，这就是「优先 gh」的全部理由。
4. **License（许可证，即作者写的「你能怎么用这份代码」的法律条款）用查表判定，不许凭感觉**：六行决策矩阵（`SKILL.md` 的「§4 下载决策矩阵」）把 MIT／Apache／CC0、GPL／AGPL、无 License、Private、超大仓库、纯文档索引六种情况各自的**动作**和**存放位置**都写死了。
5. **一条会救命的补查规则**：API 的 `licenseInfo`（许可证元数据字段）经常返回 null（空值），多数时候仓库其实是有许可证的。规则要求 null 时必须再查根目录的 LICENSE／COPYING 文件；本页第 6 章把它扩成**三级补查**，因为实测遇到一种「根目录也没文件、但 README 写了许可证」的情况。
6. **base64 解码是结构性防线，不是提醒**：`contents` 接口返回的是编码后的字符串，直接落盘（写进硬盘文件）会得到「文件名正常、打开全是乱码」的源码。规则把解码写死在命令里，让这类事故在结构上发生不了。
7. **分析完必须沉淀**（沉淀＝把结论写成文件留在仓库里，而不是留在对话里）：流程第一步就检查有没有文档体系，没有就建议先建 `DOCS_INDEX.md` 再开始分析，否则下一轮会话全部归零。

**一句话设计目标**：把「逛开源仓库」这件容易变成瞎逛的事，变成一条**每个环节都有可执行判据（能拿命令验证的标准）、越权动作会被表挡住的流水线**。

## 第 1 章 这套系统在解决什么问题

不装这套 SOP 的人，翻开源仓库时会撞上七个具体故障。下面这张表是本页的骨架：每一行都是一个「真实会让人返工」的场景。

| # | 故障 | 表现（不修会怎样） | 本 skill 的解法（正文出处） |
|---|---|---|---|
| ① | **限流掐断** | 匿名直连 API 翻两个仓库就被拒，后面所有查询集体失败，任务卡在「还没看到代码」 | 「§2 查询阶段」：优先 `gh` CLI 鉴权拉取，`api.github.com` 直连仅作兜底 |
| ② | **License 雷** | 凭「看起来是开源的」就把代码抄进工程，日后商用时才发现原作者只给了学习权限 | 「§4 下载决策矩阵」＋版权红线句：禁止商用素材绝不纳入 |
| ③ | **误判无许可证** | `licenseInfo` 返回 null 就直接当「没许可证」处理，把一份 MIT 仓库判成不可用，白白放弃 | 「License 检测补充」段：null 时额外检查根目录 LICENSE／COPYING／LICENSE.md |
| ④ | **乱码沉睡** | base64（把二进制塞进纯文本的编码方式）原文当源码存盘，文件名正常、大小也对，几周后要用才发现全是乱码，且早忘了来自哪个仓库 | 「文件内容解码落盘」条：解码写死在 `--jq '.content' \| base64 -d` 这条管道里 |
| ⑤ | **结论蒸发** | 分析全在对话里，会话一结束归零；同一个仓库下周被重新分析一遍，还得出不同结论 | 「§1 识别工程上下文」＋「§5 文档更新」：没文档体系先建，再开始分析 |
| ⑥ | **中文写坏** | 用 PowerShell 管道（Windows 的命令流传递机制）传中文，写进文件变成问号；分析报告直接不可读 | 「§6 编码注意」：指定 utf-8 写、写后验证「中文字符数 > 0 且问号数 = 0」 |
| ⑦ | **好坏凭感觉** | 「这仓库挺牛的」不算判据，两个仓库到底抄谁的思路，最后靠嗓门大决定 | 「§3 价值判断矩阵（5 维度）」＋六档星级；同类实现追加方法对比表 |

**其中 ②③ 是最贵的**——①④⑥ 浪费的是时间，②③ 浪费的是「已经交付出去的东西」。前者返工，后者可能要把上线的东西整块拆掉换资产。所以第 6 章（License 层）写得比第 4 章（拉取层）还细，是刻意的。

**还有一个隐性故障不在这张表里**：把「读仓库」做成「读 README」。README（项目自我介绍文档）写得漂亮不等于代码可用，很多真价值藏在 `autoload/`、`src/core/` 这类目录结构和几个关键源文件里。所以「§2 查询阶段」把元数据、目录树、README、关键源码列成**四个并列字段**各配一条命令（实测该表共 4 行，数法：按正文表格的数据行数）。

## 第 2 章 术语表

本页所有术语在这里给一句大白话。中文行话同样解释——不认识词的人不该被迫回头查词典。

| 术语 | 一句大白话 |
|---|---|
| **仓库 / repo** | 一个项目的所有文件加上历史记录，托管在 GitHub 上的那一份 |
| **克隆 / clone** | 把仓库整份拉到本地（连同历史），一条命令下载整个项目 |
| **拉取 / pull** | 从远端把新内容取下来；本页泛指「把仓库内容弄到本地」，不特指 git pull |
| **上游** | 代码的原始出处，即你抄思路的那个仓库；改坏了还能回到上游重看 |
| **元数据** | 描述仓库的数据：star 数、许可证、主语言、更新时间，不含任何代码 |
| **目录树 / tree** | 仓库里所有文件路径的清单，递归（连子目录一起列）一次可拿到全部条目 |
| **骨架** | 只要目录结构和少量关键文件，不要完整内容——学结构用，不用于跑起来 |
| **`gh` CLI** | GitHub 官方命令行工具；登录后可直接查仓库、拉文件，自带鉴权 |
| **鉴权** | 让服务器知道「你是谁」，因此配额更高、私有内容才读得到 |
| **API / 直连** | 程序化访问的接口；「直连」指不借助 `gh`，自己发 HTTP 请求 |
| **限流 / 配额** | 服务器按时间窗口限制你能问多少次，超了就拒绝；正文写的匿名 60 次／小时即此 |
| **兜底** | 主路走不通时的备用路，本 skill 里＝Python 标准库 `urllib.request` 直连 API |
| **探针** | 只检查不改东西的脚本；用来回答「这个仓库到底多大、有没有 LICENSE 文件」 |
| **判据** | 可执行的判定标准，能一条命令跑出真／假；「感觉挺有用」不是判据 |
| **base64** | 把任意字节翻成纯文本字符的编码，接口用它塞文件内容，**用前必须解码** |
| **落盘** | 把内存里的数据写成硬盘上的文件 |
| **License / 许可证** | 作者写的「你能怎么用这份东西」的法律条款，决定你允许下载、修改还是发布 |
| **SPDX 标识** | 许可证的标准短代号（如 `MIT`、`AGPL-3.0`），机器认它不认人话 |
| **NOASSERTION / Other** | GitHub 认不出许可证种类时的占位值：**不等于随便用**，必须读原文 |
| **copyleft（著佐权）** | 一类要求你的衍生作品也用同样许可证的条款，GPL／AGPL 是代表 |
| **CC0 / 公共领域** | 作者放弃所有权利，随便用不用致谢，是资产类素材最理想的状态 |
| **CC-BY-NC** | 署名且**禁止商用**的创作共用许可；本 skill 的硬红线是绝不纳入工程 |
| **价值判断矩阵** | 把「有没有用」拆成 5 个互不遮挡的维度分别看的表 |
| **转译** | 不抄代码，把另一种语言／框架的设计思路搬过来用（如 C# 的做法改成 GDScript） |
| **六档星级** | ★★★★★ 核心参考 → ☆ 无用，正文给的分级刻度 |
| **沉淀** | 结论写成仓库里的文件，而不是一句对话；下次能被搜到 |
| **双文档体系** | 同一份内容写两份：一份给 AI 读（结构化、给模型看），一份给人读（顺、能读通） |
| **DOCS_INDEX** | 文档总目录文件，新增一份分析就往里登记一行，防止文档变成无人认领的散页 |
| **回写** | 把新结论写回已有的固定文档位置，而不是新建一份散落文件 |
| **前缀命名** | 下载文件时冠上来源缩写（`VS_=vampire-survivors`），保证任何文件都能反查上游 |
| **勾稽** | 两处数字能互相对上；如「清单条目数＝文档里的章节数」 |
| **幂等** | 同一件事重复做，结果不变；重复下载同一仓库不该产生两份副本 |
| **回注** | 把内容重新塞回 AI 的上下文窗口；沉淀下来的文档下次能被读进来 |
| **冷启动** | 工程里还没有任何文档体系、第一次跑这套流程的状态 |
| **star** | GitHub 上别人给仓库点的「收藏」数，热度信号，**不是质量判据** |
| **sha256 / md5** | 把文件压成一串固定长度指纹，用于比对两份副本是否逐字一致 |
| **可证伪** | 结论附带「什么输入会推翻它」；本页每条数值都给得出复算方法 |
| **一手来源** | 信息出自产生它的那个地方（仓库自己的 LICENSE 原文），不是别人的转述 |

## 第 3 章 结构与分层：七步流水线拆成三层

### 3.1 七步总表（正文「工作流」§1–§7 的逐层职能）

| 步 | 正文章节名 | 职能层 | 输入 | 产出形状 | 跳步的直接代价 |
|---|---|---|---|---|---|
| §1 | 识别工程上下文 | 定位层 | 当前工程目录 | 类型／技术栈／文档体系／目录约定四条确认 | 分析成果无处可沉，等于白看 |
| §2 | 查询阶段 | 取证层 | `{o}/{r}` 仓库路径 | 元数据、目录树、README、关键源码四类原始数据 | 后面所有判断建在想象上 |
| §3 | 价值判断矩阵（5 维度） | 判断层 | §2 的数据 | 每仓库一行：五维归属＋六档星级 | 决策凭感觉，两个仓库争执无解 |
| §4 | 下载决策矩阵（License 红线） | 边界层 | 许可证事实 | 允许／限制／禁止＋存放位置 | 把法律风险带进可发布构建 |
| §5 | 文档更新 | 沉淀层 | §3＋§4 的结论 | 分析条目（固定字段）＋索引行 | 结论在下一次会话归零 |
| §6 | 编码注意 | 保真层 | §5 要写的文件 | 中文可读、0 个问号 | 报告写了等于没写 |
| §7 | 完成检查清单 | 验收层 | 全部 | 6 项复选框逐条勾（实测正文清单共 6 条，数法：数 `- [ ]` 行） | 「我以为做完了」 |

### 3.2 三个层的分工为什么这样切

把七步归并成三层，是这套 SOP 能被讲清楚的关键（**这层归并是本页的组织方式，属 [推演]**；正文只给七步平铺。反证：若不归并，读者容易把 §6「编码注意」误当成可选步骤——按层看它是「保真层」，属于「产出必须能被读」这一硬性要求）。

- **定位层（§1）**：先问「我在哪个工程里」。同一个仓库，对游戏工程和对 Web 工程的价值完全不同——正文的五维表特意给了游戏／Web／AI 三列示例，就是为了这一步能把上下文带进后面的判断。
- **取证层（§2）**：只拿事实，不下结论。这一层最忌讳「顺手判断一下」——一旦在取证阶段就带偏好，后面的价值判断会退化成给直觉找证据。
- **判断层（§3）＋边界层（§4）**：这是两套**互不替换**的判断。§3 问「有没有用」，§4 问「允不允许用」。常见误用是拿前者覆盖后者：仓库有用 → 下载了 → 许可证其实不允许。§4 的设计立场很明确：**边界层有权否决判断层**，而且它只加限制、不加许可。
- **沉淀层（§5）＋保真层（§6）＋验收层（§7）**：这三个是「让这次劳动能留下」的闭环。§5 写、§6 保证写进去的是能读的字、§7 保证没漏。

### 3.3 判定顺序：三条判定链（顺序不可交换）

**链 A：许可证判定（严格串行，第一个命中即终止）**

```
1. gh repo view 的 licenseInfo 有值？ → 用它，但 Other/NOASSERTION 必须再读 LICENSE 原文
2. null → 列仓库根目录，找 LICENSE / LICENSE.md / COPYING
3. 找到 → 读原文首行（或 SPDX 标识）再判定
4. 根目录也没有 → 补查 README 的 License 章节有无声明    ← 本页在第 6 章新增的一级
5. 全无 → 判「无 License」：只下骨架、标注不可抄码
```

**链 B：价值判定（五维并行，不串行）**：五个维度各自独立打点，一个仓库可以同时「①不可直接用、③设计提炼极高」。串行化会把「只有设计价值」的仓库误杀成「无用」。

**链 C：完成判定（6 项全勾才算完）**：清单里任何一项未过，本次交付物视为未完成。

> 为什么链 A 串行、链 B 并行：**链 A 判的是法律事实，必须唯一答案**（一份仓库在同一个工程里不能既「可全量下载」又「不可抄码」）；**链 B 判的是多维度价值，允许多个答案并存**。把两者顺序写反，会出现「因为设计价值高所以放宽许可证判定」这种灾难逻辑。

## 第 4 章 拉取层：查询阶段的四条命令与三个陷阱

### 4.1 正文给的字段对照表（照抄其结构）

| 字段 | 推荐命令（`gh`，鉴权） | 兜底 API 路径 |
|---|---|---|
| 元数据 | `gh repo view {o}/{r} --json ...` | `/repos/{o}/{r}` |
| 目录树 | `gh api repos/{o}/{r}/git/trees/HEAD?recursive=1` | 同路径 |
| README | `gh api repos/{o}/{r}/readme -H "Accept: application/vnd.github.raw"` | `/repos/{o}/{r}/readme` |
| 关键源码 | `gh api repos/{o}/{r}/contents/{p} --jq '.content' \| base64 -d` | `/repos/{o}/{r}/contents/{p}` |

（出处：`SKILL.md`「工作流 §2 查询阶段」的表格。）

### 4.2 为什么优先 `gh`：配额差是数量级的

- [实测] 本页取证当天用 `gh api rate_limit` 实读：**鉴权核心配额 limit = 5,000 次／小时**，搜索接口配额 **30 次／分钟**（数法：读 `resources.core.limit` 与 `resources.search.limit` 两个字段）。
- [实测（正文断言，未独立复核）] 匿名直连 60 次／小时的数字来自 `SKILL.md`「§2 查询阶段」的引文「已登录鉴权、无匿名 60 次／小时限流」。本页**没有**做匿名压测（会真消耗配额，且结果随出口 IP 变），只按正文口径引用。
- 为什么这条值得写进正文：**限流是「无声失败」**。匿名跑到第 61 次时接口返回 403，脚本里如果没检查状态码，后半批仓库会全部读成「空」，你会得出「这些仓库没什么内容」的错误结论。

### 4.3 陷阱一：`--json stars` 是错的字段名（正文命令表的实测缺陷）

正文「§2 查询阶段」的元数据行写着 `--json stars,licenseInfo,primaryLanguage,description,repositoryTopics`。本页在同一环境实测：

```
$ gh repo view godotengine/godot-demo-projects --json stars
Unknown JSON field: "stars"
```

工具随后列出的可用字段里，star 数对应的是 **`stargazerCount`**；`licenseInfo`、`primaryLanguage`、`description`、`repositoryTopics` 四个字段名有效。

- [实测] 上面的报错原文与字段清单都是当场跑命令得到的。
- **为什么会中招**：REST 接口（兜底路径）里这个字段叫 `stargazers_count`，`gh` 走的是 GraphQL（GitHub 的查询语言），那边叫 `stargazerCount`。两个接口家族命名不一致，照 REST 习惯写就会红。
- **换成兜底路径就正确**：`gh api repos/{o}/{r} --jq '.stargazers_count'` 可用（本页第 12 章即这么取）。
- **修法建议**（属本页提议，不改权威库）：把元数据行的字段名改成 `stargazerCount`，或注明「REST 用 `stargazers_count`、`gh repo view` 用 `stargazerCount`」。
- 这条为什么重要到单独成节：**它是「照抄正文命令就报错」级别的缺陷**。第一次跑这套 SOP 的人会把报错当成「我没权限」或「仓库不存在」，然后走上一条完全不同的排障路。

### 4.4 陷阱二：`Accept: raw` 与 `--jq` 不能同时用

正文 README 行写的是 `gh api ... -H "Accept: application/vnd.github.raw"`。实测：

- [实测] 只带 raw 头 → 正常返回纯文本，第一行是仓库 README 的标题。
- [实测] 额外加 `--jq '.'`（想「统一用 jq 处理」的顺手操作）→ 报错 `invalid character '#' looking for beginning of value`，因为 `--jq` 预设输入是 JSON，而 raw 返回的是 Markdown（一种用井号写标题的纯文本格式），第一个字符就解析失败。
- **为什么会中招**：同一条命令里前面两个字段查询用 `--jq` 很顺，读者会惯性带上。
- **两条可选写法**：要纯文本就别加 `--jq`；要结构化就别加 raw 头（返回 JSON，里面 `content` 是 base64，需解码，见第 5 章）。

### 4.5 陷阱三：`HEAD` 别名与默认分支

- [实测] `gh api repos/{o}/{r}/git/trees/HEAD?recursive=1` 在 `godotengine/godot-demo-projects` 上直接可用（返回 4,645 条目录项）。`HEAD`（当前检出的那个版本指针）在这里被 API 接受为「默认分支」的别名，省掉先查默认分支名这一步。
- 正文没写这条为什么值得注意：**如果仓库默认分支不是最新的开发分支，或者你要对比历史版本，`HEAD` 就不够用**，得显式指定分支／tag（版本标记）。[推演] 反例输入：用户说「按 v2.0 的写法参考」，你拿 `HEAD` 拉回来的是 master 最新状态，把已废弃的实现当现役方案抄。

### 4.6 目录树的规模与截断：判据看 `truncated` 字段

- [实测] 中等仓库不触发截断：`godotengine/godot-demo-projects` 递归树返回 `truncated=false`、条目数 4,645（数法：读返回值 `.tree` 数组长度与 `.truncated` 布尔字段）。
- [实测] 巨型仓库会截断：对 `torvalds/linux`（Linux 内核仓库）递归取树，返回 **71,638 条**且 **`truncated=true`**——也就是说清单不完整，但**不报错、状态码正常**。
- 正文的措辞是「大仓库 trees 递归可能很大，按需取关键路径即可」（[实测] 出处：`SKILL.md`「文件内容解码落盘」条末句）。
- **截断阈值本页未检索到官方数值**，因此不写成判据；可执行的判据是**读 `truncated` 字段**，它为 true 时禁止把树当成全量清单使用。
- 为什么这是真故障：拿到截断的树之后做「目录结构／架构分层」判断（第 7 章维度④），你会看到一份**被剪掉的**结构，却以为看完了整个工程。
- 换法：只取关键路径，用 `contents/{目录}` 单层列（[实测] 本页对 `.../contents/2d` 跑通，返回该层目录名清单），或用 `--jq` 在客户端筛（本页用的就是 `[.tree[].path | select(endswith("project.godot"))]`，一次性拿到所有「这是一个独立子项目」的标记文件）。

### 4.7 兜底直连什么时候真的需要

正文「兜底直连」条给的场景是：**GitHub 域名被 hosts 文件拦截／`gh` 不可用**，此时用 Python 标准库 `urllib.request`（Python 自带的网页请求模块）直连 `api.github.com` 绕过 DNS（域名解析）。

- [推演] 具体什么输入会让它出问题：本机 hosts 把 `github.com` 指到不可达地址时，浏览器打不开仓库页、`gh` 报连接错误，但 `api.github.com` 仍可能通——这时只有绕开 DNS 解析的直连能干活。这条规则的价值是**保留一条不通浏览器也能取证的路**。
- 注意：匿名直连即回到 60 次／小时的配额，兜底路要省着用；正文没有规定「兜底时优先查哪三个字段」，本页在速查表（第 14 章）按正文的四字段表给了优先级建议：元数据 → 目录树 → README，源码按命中路径点取。

## 第 5 章 解码与落盘：把「乱码沉睡」变成结构上不可能

### 5.1 事实：`content` 字段是 base64，不是源码

正文「文件内容解码落盘」条（`SKILL.md`「§2 查询阶段」内）说得很直接：`contents/{path}` 与 `readme` 接口返回的 `content` 是 base64 字符串，**切勿把 base64 原文当源码落盘**。

[实测] 本页拿一个真实文件量化了这句话（对象见第 12 章的示例仓库）：

| 项 | 值 | 数法 |
|---|---|---|
| 原始字节数 | 1,357 | 接口返回的 `.size` 字段 |
| `content` 字符数 | 1,843 | 接口返回 `.content` 字符串长度 |
| `.encoding` | `base64` | 接口字段直接标明 |
| 膨胀比 | ≈36% | 复算：1,357 字节 → ⌈1357/3⌉=453 组 → 453×4=1,812 个 base64 字符；GitHub 每 60 字符折一行 → ⌈1812/60⌉=31 行 → 31 个换行 → 1,812+31=1,843 |

为什么给这个数：**膨胀比是「你一眼就能认出这是没解码的原文」的判据**。落盘文件比接口报告的 `size` 大三分之一、且开头是 `[A-Za-z0-9+/]` 密集串而没有换行语义，就是忘了 `base64 -d`。

### 5.2 正文规定的两条解码写法

```
gh api repos/{o}/{r}/contents/{p} --jq '.content' | base64 -d > 本地路径
# 或
Python: base64.b64decode(content) 后写文件
```

- [实测] 第一条按正文原样跑通：管道不做任何额外处理，落盘 37 行，第一行是 `extends Node2D`（一种游戏脚本语言的开头），说明解码正确。
- 为什么两种写法都要给：**`base64 -d` 依赖 Git Bash 之类的环境**（Windows 的 Bash 兼容命令行）；纯 PowerShell 环境（Windows 自带的脚本外壳）里这个命令不存在，此时 Python 是唯一路。

### 5.3 为什么这个坑值得单独设一条规则

正文只写了一句警告，但把它写进规则的理由值得展开——这是本 skill 里「延迟暴露」最典型的一类故障：

- 报错会在**几周后**才出现：文件躺在那儿，名字正常、大小正常、`ls` 看不出任何异常，只有当你真的复制那段代码去用时才发现是乱码。
- 那时**上游已经找不回来了**：当初从哪个仓库、哪个路径拉的，没记；这是第 8 章命名规则和第 9 章沉淀条目里「本地路径」字段存在的原因（[推演]：没有这两个字段，几周后没人能把乱码文件和来源勾稽上）。
- 所以解法是**结构性的**：把解码写死在唯一推荐的命令里，而不是写一句「记得解码」。写进命令里，坑掉不进；写成提醒，总有忘了看提醒的一次。

### 5.4 落盘位置的三条约束（正文分散在 §4 与 §6）

| 约束 | 正文出处 | 为什么 |
|---|---|---|
| 存放目录二选一：`{工程}/third_party/` 或 `reference_repos/` | §4 决策矩阵「存放」列 | 「第三方依赖」与「只读参考」混在一层，日后清理时不知道哪些能删 |
| 无许可证仓库加 `_NO_LICENSE` 后缀 | §4 矩阵「无 License」行 | 让法律状态写进文件名，搜索和打包时躲不开它 |
| 文件路径尽量用英文 | §6 编码注意第 3 条 | 中文路径在跨平台（不同操作系统之间迁移）时容易踩编码不一致 |

- [推演] 会出问题的具体输入：把一份 `无 License` 仓库的脚本存成 `reference_repos/参考代码/helper.py`，之后打包发布脚本按目录整体收集 → 未经授权的代码进了可发布构建，且文件名上没有任何拦截信号。

## 第 6 章 License 判定层：六行矩阵、三级补查与硬红线

这一章是本 skill 法律风险的总闸门，也是全文最长的一章——**因为它挡的是不可逆的损失**。

### 6.1 六行决策矩阵（逐行照正文 §4，含动作与存放）

| 条件 | 决策 | 存放 |
|---|---|---|
| MIT／Apache／CC0／公共领域 | 可全量下载，自由参考修改 | `{工程}/third_party/` 或 `reference_repos/` |
| GPL-3.0／AGPL | **只下 README 学方法论，不下载源码，不抄码转译** | 文档标注警告 |
| 无 License | 只下骨架学方法论，标注「无 License，不可抄码」 | `reference_repos/` 加 `_NO_LICENSE` 后缀 |
| 作者标注 Private／保密 | 只参考公开设计理念，**不下载任何文件** | 仅记录思路 |
| 仓库 >100MB | 选择性下载关键文件，不 clone 全库 | 按需 |
| 纯资源索引／文档 | 不下载，在线浏览 | 文档记 URL |

（出处：`SKILL.md`「工作流 §4 下载决策矩阵（License 红线）」。）

**注意这张表把两类东西混在一起了，而且是有意为之**：前四行判「能不能用」，后两行判「要不要占磁盘」。合并的理由是**执行时点相同**——都是「下载之前」问的问题；拆成两张表反而会让读者只看第一张就动手。

### 6.2 每一行的「为什么是这个动作」

- **MIT／Apache／CC0 → 全量下载**。这三类的共同点是「允许修改与再发布，只需保留版权声明」。允许下载全量是为了做架构分层与算法细节的深读，这类阅读无法靠 README 完成。Apache 比 MIT 多一条专利授权条款，本页不展开（正文没写；不编造条款）。
- **GPL-3.0／AGPL → 只读 README、不下载源码、不抄码转译**：这三条限制是**连在一起**的，正文写得很硬。逻辑是：copyleft（著佐权，要求衍生作品同许可）类许可证会「传染」你的工程，只要把源码抄进或机械翻译进你的可发布构建，你的工程就被要求开源。所以 SOP 干脆把动作降到「只学方法论」——**学思路不是许可问题，抄代码才是**。
- **无 License → 只下骨架**：没有任何许可证的公开仓库，默认是「保留所有权利」，公开≠可复制。骨架（目录结构＋少量标记文件，如各子项目的配置文件）读的是组织方式，风险最低。
- **Private／作者标注保密 → 一个文件都不下**：这一行的判据来自作者的明示。[推演] 反例输入：作者在 issue（问题工单）里说「这份实现暂不开放复用」，仓库本身仍可下载——按本行精神，只要作者表达了保密意图就落到「仅记录思路」。
- **>100MB → 选择性下载，不 clone**：见 6.4 的实测。
- **纯资源索引／文档 → 不下载，只记 URL**：这类仓库（awesome 式清单、题库、文档站）价值在链接聚合，全量下载不产生任何额外可读信息，还占磁盘。

### 6.3 `licenseInfo` 为 null 的三级补查（正文规则 ＋ 本页扩到三级）

正文「License 检测补充」段（`SKILL.md` §4 末尾）给的原始规则：

> API `licenseInfo` 字段常因仓库仅在根目录放 `LICENSE`／`COPYING`／`LICENSE.md` 文件而返回 null。当 `licenseInfo` 为 null 时，额外检查仓库根目录是否存在上述文件再判定，不要直接当「无 License」处理。

[实测] 本页在公开仓库上验证了这条规则会漏，并补了第三级：

| 级 | 检查什么 | 命令形状 | 实测证据（今天可复核） |
|---|---|---|---|
| L1 | 元数据字段 | `gh repo view --json licenseInfo` 或 REST `.license.spdx_id` | `godotengine/godot-demo-projects` → `MIT`（key `mit`），直接结束 |
| L2 | 根目录许可证文件 | 列仓库根，找 `LICENSE`／`LICENSE.md`／`COPYING` | 同仓库根目录确有 `LICENSE.md`（`gh api .../contents` 列出） |
| L3 | **README 里的许可声明** | 在 README 原文中搜 `License` 章节 | **`jlevy/the-art-of-command-line`**：REST `.license` = null、专门的 `/repos/{o}/{r}/license` 端点返回 **404**、根目录列出的文件里**没有任何** LICENSE／COPYING——但 README 有一节 `## License`，明确声明 **CC BY-SA 4.0**（署名-相同方式共享，创作共用的一种） |

- 为什么 L3 必须补：**L2 只能证明「没有许可证文件」，不能证明「没有许可证」**。上面那个实测仓库把许可证写在 README 里，走两级检查会被判成「无 License，只下骨架」——结论方向没错（骨架优先总是保守），但**判据是错的**：真实风险其实来自 BY-SA 的「相同方式共享」条款（衍生文档要同样许可），而不是「无授权」。判据错了，你无法向别人解释为什么这么决定。
- [实测] 另一个方向的坑：**认不出≠没有**。`MoonTechLab/LunaTV` 的 REST 许可证值是 `NOASSERTION`（GitHub 无法归类），根目录只有一个 `LICENSE` 文件；读原文首行是 **Attribution-NonCommercial-ShareAlike 4.0 International**（CC BY-NC-SA 4.0，禁止商用的创作共用），原文里就有「commercial advantage or monetary compensation」的限定句。**如果只看元数据，这个仓库会被当成「许可证不明」甚至「无许可证的普通开源」处理。**
- 因此本页给一条硬判据（可执行）：**`licenseInfo` 为 `other`／`NOASSERTION` 时，等同 null 处理，必须进 L2/L3 读原文**。正文的补充只覆盖 null；这是同一逻辑的自然延伸，[推演]，反例输入即上面的 `LunaTV`（NOASSERTION）与 `CompVis/stable-diffusion`（元数据返回 `key: other / name: Other`，73,487 star——「Other」绝不能当 MIT 用）。

### 6.4 >100MB 这一行的实测

[实测] `godotengine/godot-demo-projects` 的 REST `size` 字段 = **567,682**（单位 KB，约 555 MB），远超 100 MB → 决策矩阵第 5 行触发：**不 clone 全库**（克隆＝整份拉到本地），改为点取关键路径（第 12 章全程如此，本次取证**一个字节都没有整仓克隆**）。

- 为什么阈值定在 100 MB 而不是 1 GB（本页观点，[推演]）：这类演示仓库体积大头是美术与音频资产，而你要读的是代码与结构；**下载 555 MB 里可能有 540 MB 是你这次根本不看的东西**。阈值再高（比如 1 GB）就形同虚设，因为多数参考仓库都在几百 MB 量级；再低（比如 20 MB）会把大量纯代码仓库也踢进「只点文件」模式，读不到完整目录结构。
- 复算方法：`gh api repos/{o}/{r} --jq '.size'` 得到 KB 数，除以 1024 得 MB。**注意单位是 KB 不是字节**——这是最容易读错的一处，把 567,682 当字节的会觉得只有 0.5 MB 从而放行 clone。
- [推演] 会出问题的输入：把 `.size` 当字节解释，判定「<100MB，可以整仓克隆」，于是一次克隆吃下 555 MB 磁盘。顺带一条环境纪律：本机对落盘位置有单独纪律（禁止把缓存与大文件堆进系统盘），大仓库克隆更要先定位置。

### 6.5 版权红线（用户硬规矩，正文原句的精神）

正文 §4 的警告块写死了两条（[实测] 出处：`SKILL.md`「§4 下载决策矩阵」下的 ⚠️ 版权红线句）：

1. **禁止商用（CC-BY-NC 等）素材绝不纳入工程**——不是「谨慎使用」，是绝不。
2. 外部参考代码若「保留所有权利」，仅作只读参考，**不整段照搬进可发布构建**。

- 为什么第 1 条这么硬：资产类文件（贴图、音频、模型）**无法像代码那样重写来「绕开」许可证**，用了就是用了；而代码还能靠「只学思路自己实现」脱敏。风险不对称，所以红线只把最硬的一条给资产。
- 为什么第 2 条留「只读参考」的空间：方法论与结构不受人物化表达的保护（本页不给法律结论，只复述 SOP 立场）。判据是可执行的一句：**最终构建产物里不许存在与上游逐字相同的段落**。

### 6.6 联动纪律：产出即外部智慧，当次入库

[实测] 出处：权威库 `SKILL.md` 正文首条引用块（2026-10-02 全库链式审计补挂，本仓库副本暂缺此条）——检索到的权威资料／设计智慧／行业数字**当次**沉淀进「外部智慧入库区」，一卡一智慧，卡面至少含**来源 URL ＋ 检索日期 ＋ 复核条件**；事实与数据另遵循本库的抗幻觉纪律（一手来源核实／结论可证伪／不确定标未知）。

- 三个字段各自的必要性（本页组织，[推演]）：**URL** 让下次能回到同一份材料；**检索日期** 让「上游已经变了」可被发现（第 10 章的失效模式之一）；**复核条件** 是最容易被省掉、却最值钱的一条——它写的是「怎样重跑一遍来确认这条结论今天还成立」，本页第 12 章每条数字后面带的「数法／复核命令形状」就是这个字段的落地样例。
- 本页为什么全页不出现任何本机路径：这条纪律的落盘位置属于本机环境指纹，公开仓库一律抽象化。

## 第 7 章 价值判断层：五个维度为什么必须分开

### 7.1 矩阵原文结构（正文 §3，四列示例）

| 维度 | 含义 | 游戏示例 | Web 示例 | AI 示例 |
|---|---|---|---|---|
| ① 可直接使用 | 资产／插件／配置立即可用 | shader（着色器，决定画面怎么算颜色）、粒子预设、CC0 素材 | 组件库、CSS 框架（网页样式的可复用规则集） | 预训练模型、prompt（提示词）模板 |
| ② 可提取知识／转译 | 跨语言跨框架的设计模式移植 | C#→GDScript（Godot 引擎的脚本语言） | Java→Python | PyTorch→TensorFlow（两套深度学习框架之间搬家） |
| ③ 设计提炼 | 核心机制、算法、架构决策 | Roguelite 循环、难度曲线 | 状态管理、路由 | 模型架构、训练策略 |
| ④ 架构分层 | 目录结构／模块划分 | `autoload/`、`entities/`、`ui/` | MVC／MVVM（两种「界面与逻辑分开」的分层法） | 数据→模型→服务→API |
| ⑤ 视觉／规范 | UI 模式与设计语言 | 粒子参数、调色规律 | 组件规范 | 可视化规范 |

（出处：`SKILL.md`「工作流 §3 价值判断矩阵（5 维度）」。）

### 7.2 为什么恰好是这五个，少一个会怎样

这五个维度不是「罗列得好看」，它们各自挡住一种误判（[推演]，但每条都给得出反例输入）：

| 维度 | 它单独存在的理由 | 缺了它会发生的误判 |
|---|---|---|
| ① 可直接使用 | 唯一能立刻换成工时的价值 | 会高估：看完觉得「思路真好」就开工，其实一行都拿来用不了 |
| ② 可提取转译 | 语言不同但思路可搬 | 会漏判：跨语言仓库被直接归为「用不上」，而它常常是最有价值的一类 |
| ③ 设计提炼 | 机制与决策，与代码无关 | 会误抄：把「别人的实现」当「别人的设计」，抄了代码却没拿到可迁移的决策 |
| ④ 架构分层 | 目录组织本身就是知识 | 会低估小仓库：一个几百行的示例工程，目录划分可能比几万行的项目更清楚 |
| ⑤ 视觉／规范 | 参数与规范是可直接落地的资产 | 会错配：把「代码写得好」当成「视觉也能抄」，最后卡在没人给配色参数 |

- 五维**必须并行独立打分**（第 3 章链 B）。判定顺序化会带来系统性偏差：①不满足就停，于是「只有设计价值」的仓库被误杀成 ☆。
- 三个示例列（游戏／Web／AI）不是装饰：正文定位是「通用 SOP，适用于任何工程类型」（[实测] 出处：正文标题下的版本引用块）。同一维度在不同工程类型里长得不一样，示例列是**把抽象维度钉回具体动作**的那颗钉子。

### 7.3 六档星级：正文给的刻度与每档的动作含义

[实测] 出处：`SKILL.md`「§2 查询阶段」末尾「判断价值等级」条：★★★★★（核心参考）→ ★★★★（重要参考）→ ★★★（有借鉴点）→ ★★（边缘相关）→ ★（存档查阅）→ ☆（无用）。

| 档 | 正文语义 | 建议动作（本页补，[推演]） | 是否进分析文档 |
|---|---|---|---|
| ★★★★★ | 核心参考 | 深读关键源码，做方法对比表 | 必进，且排在文档最前 |
| ★★★★ | 重要参考 | 读目录树＋README＋若干源码 | 必进 |
| ★★★ | 有借鉴点 | 读 README 与命中路径 | 进，一行式条目 |
| ★★ | 边缘相关 | 只登记不深读 | 可进可不进，进则标 ★★ |
| ★ | 存档查阅 | 只记 URL | 记 URL 即可，不下载 |
| ☆ | 无用 | 明确写下「为何无用」 | 建议进（负知识也是知识，能防止下次重扫） |

- 为什么留 ☆ 一档而不是直接不管：**「扫过、判定无用」是有效结论**。不写下来，下一个人（或下一次会话）会重新扫一遍、重新得出同一个结论，白花一轮时间。这与本库「否决记录」的一贯立场一致。
- 星级的分母是**当前工程的价值**，不是仓库的质量。一个 9,633 star 的官方演示仓库（第 12 章实测），对某个不需要这类示例的工程就是 ★★；反过来一个几百 star 的小仓库可能命中你正卡住的那个机制，就是 ★★★★★。
- [推演] 具体会出问题的输入：把 star 数当价值等级填进星级——「两万个 star，那就 ★★★★ 吧」。这样做出来的表在下次评审时完全无法解释当初为什么值得抄它。

## 第 8 章 命名与存放层：一个前缀换来可溯源

### 8.1 正文规则原文

[实测] 出处：`SKILL.md`「§4 下载决策矩阵」末尾「下载命名规则」段：前缀标来源 `{Repo缩写}_{原名}`，同仓库统一前缀（正文给了两个例子：`VS_` = vampire-survivors、`HS_` = HordeSurvival），保持原扩展名。

### 8.2 三条细则各自挡什么

| 细则 | 挡住的故障 | 反例（不加会怎样） |
|---|---|---|
| 前缀标来源 | 几周后面对一堆文件，不知道哪个来自哪个仓库 | [推演] `bullet_manager.gd` 躺在参考目录里，与你自己写的同名文件混在一起，改名时谁也不敢动 |
| 同仓库统一前缀 | 同一仓库的零散文件看起来像来自十个仓库 | 无法批量清理：作者换了许可证，你要挨个文件判断归属 |
| 保持原扩展名 | 扩展名（`.gd`／`.png`／`.json`）丢了，工具链与语言识别全乱 | 把脚本存成无扩展名文件，编辑器不高亮、构建脚本不打包 |

- 「统一前缀」还带来一个额外收益：**它能和第 9 章的沉淀条目做勾稽**（两处数字对得上）。文档条目里写「本地路径：`reference_repos/VS_*/`」，磁盘上一次 `ls` 就能数出实际文件数，两边不一致就是漏登记。
- `_NO_LICENSE` 后缀（[实测] 出处：§4 矩阵「无 License」行的「存放」列）是本层唯一的**法律状态写进文件名**的设计。理由：文件名的可见性远高于文档里的一个备注字段——打包脚本、目录列表、代码搜索都会碰到它，想装看不见都难。

### 8.3 与「多副本同步」纪律的关系

正文版本引用块（`SKILL.md`「版本：v1.1」下方）有一条：若环境里有本 skill 的多份副本，任一改动后请整体同步其余副本并做 sha256（一种文件指纹算法）校验，避免漂移。

- 这条和第 8 章的命名规则是同一个哲学的两次应用：**把「将来会被忘记的信息」编码进「将来一定会被看见的位置」**——前者写进文件名，后者写进指纹。
- [实测] 本页取证时确实撞见了副本漂移：仓库副本 102 行／6,454 字节，权威库 104 行／6,845 字节，md5 前 12 位分别是 `7b5b25c4c771` 与 `1cd9f89d1952`，差的就是一条纪律引用块。这正是该条纪律要治的现象。

## 第 9 章 沉淀层：分析成果落在文档的哪个位置

### 9.1 按工程文档状况分三条路（正文 §5）

| 工程状况 | 正文规定的动作 | 为什么这么分 |
|---|---|---|
| 双文档体系（AI 侧＋人看版） | 同步两份正文 ＋ 两份 DOCS_INDEX | 两份会各自漂移；只更新一份，另一份就成了错的入口 |
| 单文档 | 更新主文档 ＋ 索引 | 最少可用闭环 |
| 无文档 | 根目录建 `REFERENCE_ANALYSIS.md` ＋ 在 README 加链接 | 冷启动（第一次建立体系）时必须留一个入口，否则新文件没人能找到 |

（出处：`SKILL.md`「工作流 §5 文档更新」。）

- 关键设计：**§1 就要求先确认文档体系，没有就先建再开始分析**（[实测] 正文 §1 原句：「若无文档体系，建议先建一个 DOCS_INDEX.md ＋ 架构总览，再开始分析，否则分析成果无法沉淀」）。把「建容器」放在流程开头而不是结尾，是因为结尾没人会执行——会话在交付结论那一刻就结束了。

### 9.2 每个有价值仓库的条目模板（正文代码块逐字结构）

```
### N. {owner}/{repo}
- Stars / Language / License / Updated
- 价值等级
- 一句话评价
**对本工程价值**：可直接用 / 可学方法 / 设计提炼
**License 警示**（如有）
**本地路径**（如已下载）
```

六个字段的必要性（本页展开，[推演]）：

| 字段 | 它回答的问题 | 缺了会怎样 |
|---|---|---|
| `{owner}/{repo}` | 上游是谁（上游＝代码的原始出处） | 无法复查，也无法向别人交代抄了谁 |
| Stars／Language／License／Updated | 热度、技术栈、法律、时效 | 「Updated」缺失时你不知道自己看的是不是三年前的废弃实现 |
| 价值等级 | 六档星级 | 排序无法做，评审时无依据 |
| 一句话评价 | 强迫你压缩结论 | 长段落结论下次没人读，等于没写 |
| 对本工程价值 | 三类归属（可用／可学／设计） | 只留下「好厉害」，不留下「所以我该改哪里」 |
| License 警示／本地路径 | 法律状态与实物位置 | 第 5 章的乱码沉睡与第 6 章的雷，都从这里复发 |

### 9.3 方法对比表（同类仓库给出不同实现时追加）

[实测] 出处：`SKILL.md`「§5 文档更新」末句。四列结构：**维度 ｜ 参考仓库方案 ｜ 当前工程方案 ｜ 谁的更好 ｜ 建议**（正文用「维度」打头，最后一列是行动项）。

- 为什么必须是这张表：读完两个仓库各自的实现，人脑里留下的是一团模糊的印象。表格强迫你把「比什么」写成一列（维度），「各是谁的做法」写成两列，「结论」和「下一步」写成两列。**这张表通常是一次分析里唯一三个月后还有用的部分**。

### 9.4 完成检查清单（正文 §7，实测共 6 条，数法：数 `- [ ]` 开头的行）

1. 所有仓库 License 已检查并标注（含 `licenseInfo` 为 null 时查根目录文件）
2. 应下载文件已下载到正确目录（内容为解码后的真实源码，非 base64 原文）
3. 文档已同步到所有必须更新位置
4. `DOCS_INDEX` 已更新，快速导航已添加
5. 涉及代码对比的已追加对比章节
6. 中文内容已通过编码验证（0 个问号）

清单的编排逻辑（本页归纳，[推演]）：**第 1、2 项查法律与实物，第 3、4 项查沉淀，第 5 项查深度，第 6 项查可读性**——四条验收线，缺任一条本次交付都不算完成。

## 第 10 章 失效与恢复：它怎么坏、怎么发现、怎么退

本章按「一个机制的死亡方式」来写。每条都给**发现方式**（征兆）和**退路**（降级动作）。

| # | 失效模式 | 怎么发现（征兆／自检） | 退路 |
|---|---|---|---|
| 1 | 配额耗尽的静默失败 | 连续几个仓库「都是空的」；返回 403（拒绝访问的状态码）；匿名调用打到第 61 次 | 切 `gh` 鉴权；仍不够就按优先级点取（元数据→树→README）；见本页 4.2 节 |
| 2 | `--json stars` 直接报错 | 报错 `Unknown JSON field: "stars"` | 改用 `stargazerCount`，或走 REST `.stargazers_count`（本页 4.3 节实测） |
| 3 | raw 头 ＋ `--jq` 组合崩 | 报错 `invalid character '#' looking for beginning of value` | 去掉 `--jq`（或去掉 raw 头，自己解码）（本页 4.4 节实测） |
| 4 | 目录树被截断当全量用 | 返回里 `truncated=true`（实测巨型仓库 71,638 条即为此值） | 放弃全树，改单层 `contents/{目录}` 逐层点取；架构分层判断（维度④）降级为「抽样判断」并在条目里标注 |
| 5 | base64 原文落盘 | 落盘字节数比接口 `.size` 大约 1/3；文件里没有语法正确的开头 | 用正文的管道重取；条目里的「本地路径」字段核对文件名与上游路径 |
| 6 | 许可证误判为「无」 | `licenseInfo`／`.license` 为 null 或 `other`／`NOASSERTION` | 走三级补查（本页 6.3 节）：根目录文件 → README 声明；仍无才落「无 License，不可抄码」 |
| 7 | 上游漂移（内容变了） | 条目里的 `Updated` 与你实际看到的文件不符；复核条件跑不通 | 以检索日期为准重跑取证，并在原条目追加「复核记录」而不是覆盖——保留历史判断 |
| 8 | 结论没回写 | `DOCS_INDEX` 里没有这一条；磁盘有文件但文档无条目（勾稽不上） | 先补条目再补内容；条目缺了，这份下载等于匿名资产 |
| 9 | 中文写成问号 | 正文 §7 第 6 项验收：中文字符数 > 0 且问号数 = 0 | 改用 Python 指定 utf-8 重写；不要走 PowerShell 管道传中文（正文「工作流 §6 编码注意」第 1 条） |
| 10 | 多副本漂移 | md5／sha256 指纹不一致（实测本页两种副本差 2 行、391 字节） | 以权威库为准整体同步，逐份校验（正文版本引用块的纪律） |
| 11 | 整仓克隆打爆磁盘 | 大仓库 clone 到系统盘默认位置，几百 MB 起步（实测 555 MB 一例） | 遵守 §4 矩阵第 5 行：选择性下载关键文件；落盘位置先定，不写系统盘 |
| 12 | Private／保密越界 | 作者明示过「不开放复用」，而你已下载 | 立即停止使用并删除本地副本，条目改为「仅记录思路」；这是 §4 矩阵第 4 行的回滚路径 |

**恢复的总原则**（本页组织，[推演]）：**这套流程的每一步都可重放（重放＝用同一条命令再取一次），所以失效不需要「猜」——只需要重跑对应命令并比对指纹或数值**。第 12 章末尾给出的九条复核命令就是这个原则的落地，任何一条跑不通都能立刻定位到章。

## 第 11 章 例行体检：怎么验证它真在生效

本 skill 没有「自动衰减」这类机制，所以体检的含义是：**验证这套 SOP 有没有真的在约束行为，还是只躺在文件里**。

### 11.1 六条探针（探针＝只检查不改东西的脚本或命令）

| # | 探针 | 命令形状 | 判定它「真在生效」的样子 |
|---|---|---|---|
| P1 | 配额可用 | `gh api rate_limit --jq '.resources.core'` | 能读出 `limit`（实测 5,000）与 `remaining`；说明鉴权在，不是匿名 60 次的降级路 |
| P2 | 元数据字段名正确 | `gh repo view <某公开仓库> --json stargazerCount,licenseInfo,primaryLanguage` | 有 JSON 返回，不报 Unknown JSON field |
| P3 | 树可读且知道完整度 | `gh api repos/{o}/{r}/git/trees/HEAD?recursive=1 --jq '{n:(.tree\|length),truncated:.truncated}'` | `truncated=false`；为 true 时说明靶子过大，需换点取 |
| P4 | 解码管道通 | `gh api repos/{o}/{r}/contents/{p} --jq '.content' \| base64 -d \| head -1` | 第一行是真实源码语法，不是一串 base64 字符 |
| P5 | 许可证三级补查通 | 元数据 → `gh api repos/{o}/{r}/contents`（列根目录）→ README 原文搜 `License` | 任一级给出明确许可证即停；三级全空才允许写「无 License」 |
| P6 | 沉淀真的落了 | 在工程文档里搜 `{owner}/{repo}`；`DOCS_INDEX` 里数条目 | 文档条目数 ≥ 磁盘参考目录数（勾稽） |

- P6 是**最关键的一条**，也是唯一不能靠命令行完成的：它要求「这次分析在别人（或下一次的你）眼里可找到」。前 5 条全绿、P6 空，就是典型的「流程执行了，产出没沉淀」。

### 11.2 生效性抽查（建议每轮分析结束后做，成本 5 分钟）

1. 随机挑一条**已登记**的仓库条目，不看正文只按条目里的字段复现一次取证——复现得了＝条目自洽。
2. 检查条目里 `License` 字段与「License 警示」是否**同时**存在（只有前者、没有后者的仓库，正是最容易出事的那批）。
3. 检查是否有任何文件的**内容仍是 base64**：`ls` 参考目录，看文件大小是否与接口报告的原始字节数量级一致（本页 5.1 节的 36% 膨胀比就是尺子）。
4. 检查中文问号：把分析报告读一遍，问号（`?`）成片出现＝§6 的编码纪律被绕过了。

### 11.3 本 skill 自身的版本体检（每升版一次）

- 正文 frontmatter 有重复的 `metadata` 顶层键（[实测]：同一份 frontmatter 里出现两次 `metadata:`，两次都含 `agent_created: true`，第二次才带 `version: 1.1.0`）。多数 YAML 解析器（把配置文本读成结构化数据的工具）以最后一次为准，因此版本号仍读得到，但**这是隐患**：换更严格的解析器可能直接报错或丢字段。修法：两个键合并为一个 `metadata`。本页不改权威库（不在写入权限内），只如实登记。
- `CHANGELOG.md` 的 v1.1 节三个小标题里，「解决了什么」「怎么解决的」两条**原文标注「未记录」**（[实测] 出处：`CHANGELOG.md`「v1.1」节）。本页不替它编造变更理由，第 15 章「诚实留档」再记一次。

## 第 12 章 端到端走查：把一个真实公开仓库读成能用的东西

**靶子仓库（真实可访问）**：`godotengine/godot-demo-projects`，地址 <https://github.com/godotengine/godot-demo-projects>，是 Godot 引擎官方的演示与模板工程集合。以下所有数字都是本页取证当天（2026-10-09）用真实命令跑出来的，复核方法在章末。

### 12.0 前置：§1 识别工程上下文（先问自己在哪个工程里）

假设当前工程是一个 Godot 游戏项目：技术栈标记文件是 `project.godot`（Godot 项目的入口配置文件，正文 §1 把它和 `package.json`／`requirements.txt`／`Cargo.toml` 并列为「用什么栈」的判据文件）；参考资产约定放 `reference_repos/`；文档体系为单文档（一份分析主文档＋`DOCS_INDEX.md`）。三条都确认了才往下走。

## 第 13 章 反模式清单：12 种「不要这样用」

| # | 反模式 | 后果（说清是哪一层塌了） |
|---|---|---|
| 1 | 只读 README 就下结论「这仓库没东西」 | 取证层塌：维度④架构、维度③设计都藏在目录与源码里，README 只讲功能不讲取舍 |
| 2 | 匿名直连硬跑批量任务 | 拉取层塌：配额打到上限后返回空／403，批量结论集体失真（本页 4.2 节） |
| 3 | 照抄正文的 `--json stars` 并把报错当成「仓库不存在」 | 排障方向整个跑偏：真正的问题只是字段名（本页 4.3 节） |
| 4 | `Accept: raw` 之后顺手加 `--jq` | 拿到报错却找不到原因（本页 4.4 节） |
| 5 | `licenseInfo` 为 null 就直接判「无 License」 | 判断层塌：冤枉一份 MIT 仓库，或漏读 README 里的 CC BY-SA（本页 6.3 节） |
| 6 | 元数据显示 `Other`／`NOASSERTION` 就当宽松许可 | 边界层塌，最贵的一种：法律结论建在一个占位字符串上（本页 6.3 节） |
| 7 | base64 原文落盘，文件名照样起好 | 保真层塌：几周后才暴露，且上游信息已丢失（第 5 章） |
| 8 | 下载文件不带来源前缀 | 溯源能力塌：文件与仓库对不上号，改名与清理全线冻结（第 8 章） |
| 9 | 对 >100 MB 仓库直接 clone 全库 | 磁盘与时间双塌，且大头是你不会看的资产；还容易把缓存写进系统盘（本页 6.4 节） |
| 10 | 把 star 数当价值等级 | 判断层塌：星级不再能解释「为什么值得抄它」（本页 7.3 节） |
| 11 | 分析结论只写在对话里，没进文档与索引 | 沉淀层塌，整套流程白跑：下一次会话归零（第 9 章） |
| 12 | 用 GPL 仓库的源码「翻译」成自己项目的代码 | 边界层塌：机械转译不改变衍生性质，正文对 GPL／AGPL 明写「不抄码转译」（§4 矩阵第 2 行） |

**一条总原则**：这套 SOP 允许你「看不值钱」，不允许你「不知道自己能用什么」。所以第 4、5、6、12 条（都是边界与判据类）排在第 1、10 条（效率类）之前——**判错法律比看错价值贵得多**。

## 第 14 章 速查表（Cheat Sheet）

**七步**：识别上下文 → 查询 → 价值五维 → License 六行 → 文档更新 → 编码验证 → 6 项清单。

**四字段取证**：元数据（`gh repo view --json stargazerCount,licenseInfo,primaryLanguage,description,repositoryTopics`）／目录树（`git/trees/HEAD?recursive=1`，看 `truncated`）／README（`readme -H Accept:...raw`，**别加 `--jq`**）／关键源码（`contents/{p} --jq '.content' | base64 -d`）。

**三级许可证补查**：`licenseInfo` → 根目录 LICENSE／LICENSE.md／COPYING → README 的 License 节 → 全空才判「无 License」。`Other`／`NOASSERTION` 当 null 处理，必须读原文。

**六行下载矩阵**：MIT／Apache／CC0＝全量可用 ｜ GPL／AGPL＝只读 README，不下源码不转译 ｜ 无 License＝只下骨架＋`_NO_LICENSE` ｜ Private＝零下载 ｜ >100 MB＝点取不 clone（注意 REST `size` 单位是 KB）｜ 纯文档索引＝在线浏览记 URL。

**五维**：可直接用／可转译／设计提炼／架构分层／视觉规范（并行独立，不串行）。**六档**：★★★★★ → ☆（☆也要写下为何无用）。

**两条红线**：禁止商用素材绝不纳入；保留所有权利的参考代码不整段进可发布构建。

**命名**：`{Repo缩写}_{原名}`，同仓统一前缀，保留原扩展名。

**验收数字**（复算方法在第 12 章）：鉴权配额 5,000 次／小时、搜索 30 次／分钟、匿名 60 次／小时（正文断言，未独立实测）；示例仓库 9,633 star／MIT／GDScript／555 MB／树 4,645 条未截断／单文件 1,357 字节→base64 1,843 字符；巨型仓库树 71,638 条且截断。

**30 秒回忆法**：四问四查——**能不能用**（License 六行）／**值不值得看**（五维六档）／**怎么拿回来**（gh 四字段＋解码）／**沉到哪里**（条目模板＋索引＋清单）。

### 15.2 description 长度与三个并存的上限（不许合一）

本库口径对描述字段长度**同时**记录着三个不同来源的数字，各自含义不同，本页按纪律并列保留：

| 值 | 来源口径 | 用途 |
|---|---|---|
| **1,024** | 开放标准与上传校验 | 规范层允许的上限 |
| **1,536** | 某宿主常驻清单的截断位 | 装载层实际截断的位置 |
| **200** | 某帮助中心的上传口径 | 平台侧的更严口径 |

本支 294 字符：**未超 1,024 与 1,536，超出 200 那一档**。这条差异要如实登记，不要说「合规」也不要说「超限」——三个口径各自对应不同环节。本页不修改正文（不在写入权限内）。
