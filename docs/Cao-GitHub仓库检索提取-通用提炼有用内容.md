# Cao-GitHub仓库检索提取（github-repo-extract v1.1）

> [← 返回总目录](../README.md#skills-index)

参考开源项目这件事，大多数人卡在四个地方。匿名 API 每小时 60 次请求，翻两个仓库就被掐断。License 凭感觉判断，雷埋进项目里等爆。分析结论散在对话里，下一轮归零。看懂多少算多少，最后什么都没变成自己的。

这个 skill 是一条标准流水线，四个坑各有一层对应的设计。怎么拉、允不允许用、值不值得看、看完沉到哪。

## 拉取，先解决限流

首选 gh CLI 鉴权拉取，配额问题直接消失。域名被 hosts 拦截或 gh 不可用时，用 Python urllib 绕 DNS 直连 api.github.com 兜底。元数据、目录树、README、关键源码各有对应命令，规则里给了对照表。

这里埋着一个最隐蔽的坑。contents 接口返回的 content 是 base64 编码，直接落盘的话，文件名正常，大小看着也对，打开全是乱码。而且你可能几周后要用那段代码才发现。规则写死了先解码再落盘，这个坑踩过的人才知道有多浪费。

## License，把"感觉没事"变成查表说话

下载决策矩阵一次判清。MIT、Apache、CC0 可全量下载。GPL、AGPL 只读 README 学方法论，不下载源码不抄码转译。无 License 只学方法论，文件标上 NO_LICENSE。作者标 Private 的只参考公开理念，一个文件都不下载。

矩阵里还埋着一个 API 陷阱。licenseInfo 字段经常返回 null，多数时候仓库其实有 License，只是作者把 LICENSE 文件放在根目录，元数据里没标。直接判无 License 会冤枉仓库，判反了会惹麻烦。所以规则要求 null 时必须额外查根目录的 LICENSE 或 COPYING 文件再判定。

外加一条硬红线，禁止商用的素材绝不纳入工程。抄代码一时爽，License 出事是真麻烦，这条矩阵就是防它的。

## 价值，五个维度分开打分

"这个仓库对我有没有用"是个坏问题，因为答案全凭感觉。拆成五个独立维度就清楚了。能不能直接使用，资产、组件、模型拿来就用。能不能跨语言转译，C 的思路搬到 GDScript。有没有设计可提炼，核心算法和架构决策。架构分层可不可参考。视觉规范可不可借鉴。打完分从核心参考到无用分六档，哪个仓库值几个星，表说了算。

## 沉淀，强制结论落盘

分析完不落盘，下一轮归零。所以流程第一步就确认文档体系，没有就建议建一个 DOCS_INDEX 再开始分析，结论按工程类型沉进 docs/。下次接着看，不用从头翻。

## 跟手动翻的区别

| 手动参考 | 这套流水线 |
|---|---|
| 匿名 API 每小时 60 次 | gh CLI 鉴权，配额不是问题 |
| License 凭印象，雷埋进项目 | 决策矩阵查表，null 陷阱已排 |
| base64 落盘几周后才发现乱码 | 解码规则写死 |
| 结论在对话里蒸发 | 强制沉淀进文档体系 |
| 好不好用凭感觉很牛 | 五维分开打分，六档价值等级 |

## 什么时候不用

不是 GitHub 仓库的普通网页抓取，那是另一类活。只想看看 README 了解概念，在线浏览就行，不用起流水线。
