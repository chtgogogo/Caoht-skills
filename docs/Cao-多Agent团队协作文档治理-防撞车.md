# Cao-多Agent团队协作（multi-agent-team-governance v1.3）

> [← 返回总目录](../README.md#skills-index)

## 五分钟速览

如果只有五分钟，记住这六句。

1. AI 之间缺的从来不是实时通信，是写下来的规矩。纯 Markdown 三层治理，零依赖，复制几个文件就开张。
2. 三层各杀一个问题。决策真相源杀重复追问，协作契约杀文件互踩，异步信箱杀沟通缺失，看板（可选）杀进度不透明。
3. 拍板只在一个地方，DECISIONS.md 的待拍板区。用户拍板一次，全员生效。
4. 编辑锁带时间戳心跳，超 24 小时没心跳视为过期，别人可抢占。会话崩了不会把文件占死。
5. 决策失效分两种。替代型只留一行指针，抛弃型确认无引用后直接删。活跃区只写「现在是什么」。
6. 规模分三档，一两个 AI 用轻量档几乎零负担，五个以上上体检脚本。小项目不被重流程拖垮。

一句话概括设计目标，**用文档纪律替代开会拉群，让多个 AI 干活不撞车、用户不被重复问**。

## 它在解决什么问题

多 AI 一起干活，撞车的方式就那么几种。

| 故障 | 表现 | 对应层 |
|---|---|---|
| 文件互踩 | 两个 AI 改了同一个文件，后写的把先写的盖了 | 协作契约 + 编辑锁 |
| 重复追问 | 你跟 A 解释过一遍需求，C 又来问一模一样的问题 | 决策真相源 |
| 决策打架 | 三个 AI 对同一个方案做出三个不同决定，各写进各的文档 | 统一决策入口 |
| 幽灵决策 | 决策早被推翻了，结论还躺在文档里被引用着 | 决策生命周期 |
| 进度失衡 | 某个成员在瓶颈处死磕，别的成员干等 | 交接原则 |

一般的解法是上多 Agent 框架，装依赖、起服务、学 API，折腾一晚上，协调成本比活本身还重。这个 skill 的判断不同，规矩用文档写下来就够了。

## 三层治理详解

**L1 决策真相源 DECISIONS.md，杀重复追问。** 任何需要用户拍板的事，禁止在各自对话里问，登记进这一个文件去重。每条决策带状态，活跃区只有 `approved`（生效）和 `todo`（待拍板）两种。被推翻的不许静默覆盖，走生命周期流程。

**L2 协作契约，杀文件互踩。** 每个角色的文件边界（ownership）写死，跨边界改动先加编辑锁。锁这个设计有两个巧处。一是带时间戳心跳，超 24 小时没心跳视为过期，别人可以抢占，所以一个会话崩了不会把文件占死。二是锁是明文写在文件里的，grep 一下全项目的锁尽收眼底，谁在改什么一目了然。

**L3 异步信箱，杀沟通缺失。** 跨 AI 的请求投递到 `沟通/<接收人>/X对Y.md`，处理完移进 `已处理/` 子目录。巡检只 ls 信箱根目录、绝不递归已处理区，信箱再多开销也是恒定的。

**L4 状态看板（可选，大型模式）**，任务进度一览，谁在做哪条、什么状态。

信道分工避免重叠。决策类进 DECISIONS，文件改动类走编辑锁，协作请求走信箱，瓶颈告知直接在当前对话里告诉用户。

## 决策生命周期，v1.3 的一次重要简化

活跃区只记录「现在是什么」，不记录「曾经是什么」。决策失效分两种形态。

**替代型（有新决策接棒）**，新结论按正常流程登记新条目，禁止写「3D俯视角肉鸽（之前的2D横板格斗被推翻）」这类历史叙述。旧条目从活跃区移除，历史区只留一行 `D-01（已替代→D-05，日期）`。为什么留这一行，其他 Agent 的对话记忆里可能还引用旧编号，一行指针让它能查到「D-01 已废、去向 D-05」，避免「查无此事」的幽灵引用。

**抛弃型（作废且无接棒）**，先 grep 全项目确认没有任何主文档引用它，然后直接删除条目，连指针都不留。

**这条简化是怎么来的**。原来的规则要求决策被推翻时写完整的替代沿革，实战发现没人看，负担还重。治理纪律太重了没人遵守，等于没有。规则自己也要接受这条检验。

配套还有决策压缩，活跃区生效条目超过 30 条就把历史区整体并入归档文件，主文件回到只含现行决策的「小而准」状态。

## 交接原则，把「卡住」转化为「让位」

某成员在自己主责区死磕时，浪费的是轮次，拖垮的是整体进度。规则要求在该让位时主动让位，两种情况必须告知用户，自身陷入瓶颈（反复尝试无进展、缺关键依赖），或判断更适合他人接手。

告知必须结构化，给出交接卡，卡点原因、已尝试方案（避免接手人重试）、建议接手人、接力信箱位置、下一步建议。切换会话的接手人零上下文也能开工。

## 规模自适应，三档各配各的

| 档位 | 适用 | 建什么 | 体检 |
|---|---|---|---|
| 轻量 | 1~2 agent / 小项目 | 一个决策文件 + 一页契约 + 单文件信箱 | 不跑 |
| 标准 | 3~5 agent | L1~L3 全套 | 可不跑 |
| 大型 | >5 agent / 长周期 | L1~L4 + 体检脚本 | 定期跑 |

轻量档有个强制升级阈值，单文件信箱信件超过 20 条、或最早未处理信超过 7 天，必须升级为标准模式拆信箱文件夹。单文件信箱本质仍是「中央派工单」，硬阈值防止它悄悄长成 token 黑洞。

治理体检脚本查五类病，过期锁、重复决策、角色名漂移（信箱/契约/分工矩阵三处不一致）、信箱积压、看板与执行跟踪矛盾。

项目收尾还有退役流程，决策回灌主文档（让知识脱离治理文件也能被后人读到）、清退所有锁、契约封存、信箱归档。治理文件不会无限堆积变成新的垃圾场。

## 治理本身也要接受治理

v1.3 的简化（上面讲过）是一个例子，另一个例子是新人 onboarding 的改动。早期要求新成员读全部决策文件，后来改成按主责 grep，只读命中条目再扫一遍活跃区标题，历史区与归档不用读。检查单从「读全文」变成「grep 自己的」，成本差一个量级，拦截效果没变。

## 实战数字

这套机制提炼自一个真实的多 AI 游戏项目，天倾。10 个 agent 角色加用户本人，契约转正 v1.0，决策收敛到 D-01 到 D-83，信箱双向收发 225 封（截至 2026-09-12）。

每个版本对应一次事故。v1.1 加锁的超时和抢占，因为出现过会话崩了锁还占着。v1.2 加结构化交接卡和 Windows 兼容，因为切换会话时接手的 AI 两眼一抹黑。v1.3 的简化刚才说了，来自「没人看的历史叙述」。

## 跟直接上框架的区别

| 框架路线（CrewAI、AutoGen 这类） | 这套文档治理 |
|---|---|
| 装依赖起服务学 API，成本前置 | 复制几个 md 就开张 |
| 通信在黑盒里，出问题没法审 | 每条决策每封信都是明文 |
| 换框架等于重来 | 规矩是文档，跟框架宿主解耦 |
| AI 想起沟通才沟通 | 决策入口和信箱是流程强制 |
| 小项目也被拖累 | 三档自适应，轻量档几乎零负担 |

它跟交付流水线是配套的，流水线的台账三区制和断点续传，底层就是这套治理的信箱与契约机制。

## 什么时候不用

单 AI 的普通项目，没有协作就没有治理。两个 AI 一次性的小配合，口头说清楚比建三个文件快。
