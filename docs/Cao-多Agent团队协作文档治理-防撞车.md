# Cao-多Agent团队协作（multi-agent-team-governance v1.3）

> [← 返回总目录](../README.md#skills-index)

## 事故现场

你开了三个 AI 窗口一起干活：A 写功能、B 改配置、C 补文档。半小时后回去一看——

A 和 B 改了**同一个文件**，后写的把先写的覆盖了；你跟 A 解释过一遍你的需求，现在 C 又来问一模一样的问题；最绝的是，三个 AI 对"项目用什么方案"做出了三个不同的决定，各自写进了各自的文档，谁也不知道哪个是准的。

再往前一步：你想让它们不打架，去上了多 Agent 框架——装依赖、起服务、学 API，折腾一晚上，发现协调成本比活本身还重。

这个 skill 的赌注是：**AI 之间不需要实时通信，它们需要的是一套写下来的规矩。** 纯 Markdown，三层治理，零依赖。

## 三层治理，各堵一个痛点

**L1 · 决策真相源（DECISIONS.md）**——堵"用户被重复追问"。任何需要你拍板的事，禁止在各自对话里追问，必须登记进这一个文件去重；你拍板一次，全员生效。每条决策带生命周期：`approved / todo / superseded / revoked`——被推翻的决策不许静默覆盖，要标记并新建条目重走拍板，原负责人把结论回灌主文档。**项目里最怕的就是"旧决策还在暗中生效"的幽灵状态，生命周期字段就是专杀它的。**

**L2 · 协作契约**——堵"多人改同一处"。文件 ownership 划清边界 + **编辑锁带超时与抢占**：改非自己主责的文件先加锁，锁带时间戳心跳，超 24h 没心跳视为过期可抢占——不会出现一个崩掉的会话把锁占死。

**L3 · 异步信箱（沟通/<角色>/）**——堵"实时沟通缺失"。跨 AI 的请求走信箱投递，闭环即归档；巡检只 ls 根目录、绝不递归已处理区，省 token。

外加一条**交接原则**：某成员在瓶颈处死磕时，必须主动告知并建议切换到更合适的成员，不许原地烧 token。附结构化交接卡：卡点是什么、试过什么、建议谁接、信投哪了——切换会话零摩擦。

## 规模自适应——它没有变成重流程的原因

| 档位 | 建什么 | 适合 |
|---|---|---|
| 轻量（1-2 AI） | 一个 DECISIONS.md + 一页契约 + 单文件信箱 | 小项目 |
| 标准（3-5 AI） | L1~L3 全套 | 常规多人协作 |
| 大型（>5 AI） | + 状态看板 + `governance_check.py` 体检 | 长周期项目 |

体检脚本查五件事：过期锁、重复决策、角色名漂移、信箱积压、看板与执行跟踪矛盾。项目收尾有**治理退役**流程：决策回灌主文档、清退锁、契约封存、信箱归档——治理文件不会无限堆积变成新的垃圾场。

## 实战账单

这套机制不是设计出来的，是打出来的。它提炼自一个真实的多 AI 游戏协作项目（天倾）：**10 个 agent 角色加用户本人，契约转正 v1.0，决策收敛到 D-01~D-83，信箱双向收发 225 封**（截至 2026-09-12）。

每个版本号背后都是一次真实事故。v1.1 加编辑锁超时/抢占——因为出现过会话崩了锁还占着；v1.2 加结构化交接卡和 Windows 兼容——因为切换会话时接手的 AI 两眼一抹黑；v1.3 简化决策生命周期——因为实战发现"替代型决策记新结论就行、历史叙述是负担；抛弃型决策 grep 确认没引用后直接删"，**治理纪律本身也要接受治理：太重了没人遵守，等于没有。**

## 和"直接上多 Agent 框架"比，差在哪

| 直接上框架（CrewAI / AutoGen 类） | 这套纯文档治理 |
|---|---|
| 装依赖、起服务、学 API，协调成本前置 | 零依赖，复制几个 md 就开张 |
| 通信在黑盒里，出问题没法审 | 每条决策/每封信都是明文，可回溯可审计 |
| 换框架等于重来 | 规矩是文档，跟任何框架、任何宿主解耦 |
| AI 想起沟通才沟通 | 决策入口+信箱是流程强制，不靠自觉 |
| 小项目也被框架拖累 | 三档自适应，轻量档几乎零负担 |

它跟交付流水线还是配套的：流水线的台账三区制、断点续传，底层就是这套治理的信箱与契约机制——已在流水线的 depends/ 里存了逐字副本。

## 什么情况别用

- 单 AI 普通项目——没有协作就没有治理，别给自己加仪式；
- 两个 AI 一次性的小配合——口头说清楚比建三个文件快。
