# 多 Agent 团队协作文档治理 · 完整详解手册

> 一句话版本：好几个 AI 同时往同一批文件里写，怎么保证谁也不把谁覆盖、用户不被同一个问题问三遍、机制越用越省而不是越用越肥——这套 skill 给的就是这个答案。

---

## 第 0 章 五分钟速览

1. **三份纯 Markdown 治理文件替代「开会／拉群」**：`DECISIONS.md`（决策真相源，L1）＋ `团队分工与协作契约.md`（协作契约，L2）＋ `沟通/` 信箱文件夹（异步信箱，L3），再加可选的 `状态看板.md`（进度看板，L4）。零依赖、零服务，复制几个文件就开张。[实测：SKILL.md「核心设计：三层治理（+可选第四层）」表]
2. **四条核心纪律写进契约**：编辑锁（带心跳与超时抢占）、统一决策入口（拍板一次全员生效）、信箱投递（闭环即归档）、瓶颈交接（不让任何成员在卡点死磕）。[实测：SKILL.md「四条核心纪律（必须写进契约）」节]
3. **编辑锁是明文标记**，一条 grep 命令扫出全项目谁在改什么；`状态:wip`（进行中）的锁距心跳超 **24 小时**视为过期，任何 agent 可抢占——加锁者会话崩了也不会把文件占死。[实测：契约模板.md §3「编辑锁机制（带超时与抢占）」]
4. **决策活跃区只有两种状态**：`approved`（生效）与 `todo`（待拍板）。失效决策替代型进历史区只留一行指针、抛弃型经 grep 确认无引用后直接删除零记录——活跃区永远只写「现在是什么」，禁写「曾经是什么」的历史叙述。[实测：SKILL.md「决策生命周期（替代即换血 · 抛弃即删除）」节]
5. **信箱的 token 保卫战**：巡检只列信箱根目录、绝不递归 `已处理/`；轻量模式的单文件信箱 `沟通/投递.md` 超过 **20 条信**或**最早未处理信超 7 天**，强制升级成按角色拆文件夹的标准信箱——因为单文件信箱本质是一张「中央派工单」，会悄悄长成每轮全读的 token 黑洞。[实测：SKILL.md「规模自适应」强制升级阈值条；信箱说明.md「使用纪律」]
6. **规模自适应三档**：1~2 个 agent 用轻量档（几乎零负担）、3~5 个用标准档（三层全套）、>5 个或长周期用大型档（加 L4 看板＋定期跑 `scripts/governance_check.py` 七项自动体检）。[实测：SKILL.md「规模自适应」段]
7. **它有完整生命周期**：从步骤 0 收集信息开张、新人 onboarding 五步检查单入伙，到项目收尾时五步「治理退役」（决策回灌→清锁→契约封存→信箱归档→体检收尾），机制本身不会变成新的垃圾堆。[实测：SKILL.md「治理退役（项目收尾）」节；「新人 Onboarding 必读检查单」节]

**一句话设计目标**：用写下来的文档纪律替代 agent 之间不存在的实时通信，让多路并行不互相撞车（撞车＝两边同时改同一处、互相覆盖）、用户只在一个地方拍板、治理文件越用越准而不是越用越肥。

## 第 1 章 这套系统在解决什么问题

### 1.1 前提：agent 之间根本没有电话

多数 agent 宿主环境里，两个会话之间**没有任何实时通信通道**——甲窗口不知道乙窗口此刻在干什么，唯一的共享面就是磁盘上那批文件。SKILL.md「概述」节把这写成设计前提：它不依赖 agent 之间的实时通信（大多数环境本来就没有），而是用三份治理文件加信箱文件夹替代「开会/拉群」。[实测：SKILL.md「概述」第一段]

也就是说：文件既是工作成果，也是**唯一的通信信道**。谁改了文件而别人不知道，通信事故就发生了。

### 1.2 故障 → 表现 → 解法对照表

| # | 故障 | 具体表现 | 本 skill 的解法 | 证据出处 |

### 1.3 为什么不用多 agent 框架来解决

直觉方案是上一个编排框架：起服务、装依赖、配消息总线。这套 skill 的判断相反——**协调机制的复杂度不能压过干活本身**。[推演] 反例来支撑：一个 2~3 个 agent 的小项目若引入实时通信框架，光是维护消息通道、处理消息丢失、给每个 agent 装客户端，开销就已经超过项目总量；而本机制里「甲要告诉乙一件事＝往乙的信箱写一个 md 文件」，失败模式只剩「文件写没写」这一种可肉眼验证的形态。轻量档的存在（1~2 agent 只建 2 个文件、信箱退化单文件）就是这一判断的制度化：机制成本随规模缩放，而不是一刀切。[实测：SKILL.md「规模自适应」轻量模式条]

### 1.4 出身：真实项目提炼，不是纸面设计

本 skill 提炼自一个真实跑通的多 agent Godot 游戏协作项目：契约转正到 v1.0、决策收敛出约二十条已拍板条目、信箱完成双向投递，机制经实战验证可落地（来源项目名与条目编号涉隐私，此处一律抽象）。[实测：SKILL.md「概述」版本注记段；CHANGELOG.md「v1.0 · 初版」节的来源记录]

## 第 2 章 术语表

每个术语后面跟一句大白话，先建立语言，再谈机制。

| 术语 | 大白话解释 |
|---|---|
| **撞车** | 两边同时改同一处、互相覆盖——后写的把先写的盖掉，谁都不知道。 |
| **对账** | 两处数字逐条比能不能对上（如「预期 5 个段落」vs「文件里实际 grep 出 5 个」），对不上就有事。 |
| **纯追加** | 只在文件末尾加新段落、绝不改动旧段落的写法；旧段落一字不动，别人的内容就不会被碰掉。 |
| **台账** | 按时间顺序一段一段累积记录的文档（进度台账、投递信箱），天然是纯追加型文件。 |
| **工作树** | git 管理下磁盘上那份正在编辑的文件本体（区别于仓库里存的历史快照）。 |
| **索引** | git 暂存区里准备下一次提交的快照；`git add` 就是把工作树内容登记进索引。 |
| **真相源** | 某类信息唯一认可的存放处；别处出现的都算副本，冲突时以真相源为准。 |
| **编辑锁（EDIT_LOCK）** | 写在文件里的明文一行标记，声明「我正在改这一段」，别人读到就不并行改。 |
| **wip / done** | 锁的状态字段：`wip`＝work in progress，正在改；`done`＝改完（示例中的登记形态）。 |
| **心跳** | 加锁者定期更新的「我还活着」时间戳；长任务每 ≤12 小时续一次，防止被误判成死锁。 |
| **过期锁／抢占** | `wip` 锁距最后一次心跳超过 24 小时视为人已不在，任何 agent 可接管该文件继续改。 |
| **接管行** | 抢占者追加进原锁的一行说明「由 X 于 T 接管（原锁超时）」，让抢占行为留痕可查。 |
| **主责（ownership）** | 每个文件/模块登记唯一负责 agent，即「这块地皮归谁管」。 |
| **接力区** | 契约 §7 的一段，各 agent 在此认领职责、留言协商，像车间的交接班白板。 |
| **统一决策入口** | 所有待拍板事项只进 `DECISIONS.md` 一处；用户只在这一个地方回答，答案全员生效。 |
| **号位（决策/任务编号）** | `D-xx` 决策号与 `T-xx` 任务号，条目被引用的身份证号；作废也要保证「查有去向」。 |
| **回灌** | 决策有了新结论后，把所有还写着旧结论的文档逐份同步更新，让真相源和引用处重新一致。 |
| **幽灵引用** | 某编号已被删除或作废，但别处文字还写着它、照它开工——查无此事却仍在起作用。 |
| **替代型／抛弃型** | 决策失效的两种形态：有接棒者叫替代（旧条进历史区留一行指针）；作废且无人接棒叫抛弃（确认无引用后直接删，零记录）。 |
| **投递／巡检** | 投递＝往对方信箱文件夹写一封信；巡检＝每次开工先列一遍自己信箱根目录。 |
| **闭环** | 一封信「回执已收＋无后续待办＋对应决策已决/任务已交接」三条件全满足，才算办完。 |
| **已处理/ 归档** | 每个信箱下的子目录，闭环信移进去；任何巡检只列根目录、绝不递归进去，省 token。 |
| **派工单** | 工头写一张单子所有人围着看的旧模式；这里指轻量单文件信箱的退化风险——所有人每轮全读一张大单。 |
| **漂移** | 同一名词（角色名、任务状态）在不同文件里写法慢慢不一致，像表格线悄悄歪了。 |
| **探针** | 只读取检查、不修改任何东西的命令或脚本，如 `grep` 查锁、体检脚本。 |
| **判据** | 可执行的判定标准——一条命令跑出来对/错，不靠感觉。 |
| **token／上下文** | 模型一次能装进脑子的文字量；「读全文」吃 token，「grep 命中段」省 token。 |
| **启发式** | 近似规则——不保证精确但够用（如按标题行「数」信箱里的信件条数）。 |
| **信箱变聊天记录** | 把不需要对方行动的话也往信箱投递，让收件箱膨胀成噪音堆——反模式。 |
| **治理体检** | 定期用脚本扫锁残留、重复决策、角色名漂移、信箱积压等慢性病的自动化检查。 |
| **sha256 校验** | 算文件的「指纹数字」，两份副本指纹逐字一致才算同步完成。 |
| **幂等** | 同一操作重复做，结果不变（如「把锁状态改成 wip」连做两次，文件看起来一样）。 |
| **退役** | 项目收尾时把治理文件有序封存（回灌→清锁→契约归档→信箱归档），机制体面退场。 |

## 第 3 章 结构与分层详解

### 3.1 四层总表

| 层 | 文件 | 职责 | 解决什么 | 谁主责 |
|---|---|---|---|---|
| **L1 决策真相源** | `DECISIONS.md` | 所有待拍板/已拍板决策的唯一入口，去重登记；含生命周期状态 | 用户被重复追问 | 决策主责角色 |

| **L4 状态看板（可选）** | `状态看板.md` | 任务进度一览，谁在做哪条、什么状态 | 进度不透明 | 启用时定 |

[实测：SKILL.md「核心设计：三层治理（+可选第四层）」表；治理文件的主责归属见契约模板.md §2 Ownership 表示例行]

**为什么是四层不是两层**：L1 与 L2 分别管「说的方向」和「写的领地」，正交不可合并——决策入口里塞编辑锁，会把拍板文件变成锁记录堆。L3 存在是因为 L1 只管「需用户拍板的」，agent 之间大量**不需要拍板的协作请求**（要个接口名、催个规格）没有去处；不建信箱，它们就会回流成对用户的第 N 次追问。L4 做成可选，是因为「谁在做哪条」在 3~5 人规模里可以从 DECISIONS 的执行跟踪节反推，只有大型档才值得独立维护一张看板；信箱说明.md 明文「小项目用 DECISIONS 的 Wave 即可，大项目加独立看板」，且体检脚本 [5] 专门盯两处状态互相矛盾（看板漂移）。[实测：信箱说明.md「状态约定」节；governance_check.py 头部说明第 5 项]

### 3.2 规模自适应：三档各建什么

| 档位 | 适用 | 建的文件 | 是否跑体检 | 关键退化 |
|---|---|---|---|---|
| **轻量** | 1~2 agent／小项目 | `DECISIONS.md` ＋ 一页浓缩契约 ＋ 单文件 `沟通/投递.md` | 不跑 | 契约只保留 §1/§2/§3/§4 四节，§5/§8/§9 浓缩为一句「详见 skill」；不建 L4 |
| **标准** | 3~5 agent | L1~L3 全套（按角色建信箱子文件夹） | 可不跑 | — |
| **大型** | >5 agent／长周期 | L1~L4 ＋ 治理体检脚本 | 定期跑 | — |

[实测：SKILL.md「规模自适应」段；裁剪细节见契约模板.md §10「规模自适应」]

**档位判断的先后顺序**（步骤 0 收集信息时确认）：根目录 → 角色列表 → 是否需要 L4 → 规模档位。顺序不能倒：SKILL.md「步骤 0」原文写着「不要跳过收集直接建文件——角色和根目录决定模板里填什么；规模档位决定建几层」。角色没定就建信箱文件夹，建完只能改名重投；档位没定就上全套，等于给两人的项目套五层流程。

### 3.3 建立顺序：步骤 0→3 流水线

生成治理骨架本身也有防事故顺序（SKILL.md「工作流」四步）：

1. **步骤 0 收集**：项目根目录、角色列表（用 AskUserQuestion 多选常见原型：设计师/技术美术/工程师/架构/测试/项目管理，可自填）、是否要 L4、规模档位；
2. **步骤 1 防重复建设扫描**：先 Glob/Read 查同类治理文件（`团队分工与协作契约.md`、`DECISIONS.md`、`沟通/`、`团队分工与协作公约.md`、`待决事项看板.md`、`状态看板.md` 等六个示例名）；已存在→不重建，读现状、经用户确认合并补缺；发现多套冲突→发重定向说明一并入；
3. **步骤 2 按模板生成**：读 `references/` 三份模板按角色填充；
4. **步骤 3 播种与收尾说明**：契约 §7 接力区放「请各 agent 认领」引导；每个信箱子文件夹放一份 `README.md` 写明「这是谁的收件箱」；给用户的说明必须讲清三件事——拍板只看 DECISIONS 待拍板区、看对接翻信箱、开工先读信箱加锁。

[实测：SKILL.md「工作流」全部四步]

步骤 1 排在建文件**之前**不是客套：本 skill 治的第一号病就是撞车，而「同一个项目出现两套治理文件」是最高形态的治理撞车——两套规矩并存时，两个 agent 各照一套执行，还都认为自己合规。

### 3.4 信道分工：一件事该走哪个文件

四条信道各管一类事，互不重叠（SKILL.md「信道分工（避免重叠）」节与契约模板.md §8 两处一致）：

```
需用户拍板？               → DECISIONS.md（不进信箱）
改别人的文件/跨段改自己的？ → 编辑锁（契约 §3）
协作请求/信息传递/任务接力？ → 信箱 沟通/<接收人>/（轻量模式追加 沟通/投递.md）
卡在瓶颈要换人？            → 直接在当前对话告知用户（不进信箱、不进 DECISIONS）
```

**为什么要单列「不进信箱」**：瓶颈告知的受众是**用户本人**，且需要**立即换窗口**这个物理动作；信箱是「对方下次开工才看」的慢信道——急事走慢信道等于没发。

### 3.5 冲突裁决顺序（契约 §5）

1. 用户拍板结论（最高优先级，覆盖一切）；
2. 文件主责 agent 的当前版本；
3. 多 agent 无法一致 → 提交 `DECISIONS.md` 升级条目，由用户裁决；
4. 评审建议与新决策冲突 → 以新决策为准，评审方负责标注「已撤销」。

[实测：契约模板.md §5]

注意第 2 条的含义：**平时「谁的地盘听谁的」，僵持才升级到用户**。这让用户只做例外裁决、不做日常仲裁——否则用户又变回被两方拉架的瓶颈。

### 3.6 新人 Onboarding 五步检查单

异步环境里新 agent（或用户新拉一个角色）加入已运行的项目，最容易「凭空开工」造成重复/冲突。五步：

1. **按主责 grep 决策，不读全文**：`grep -n "<我的角色名>\|<我的主责文件名>" DECISIONS.md` 只读命中条目，再扫一遍已拍板区标题；历史区与归档不用读；
2. 读契约 §2 Ownership，认领主责文件/模块并在 §7 接力区注明；
3. 读自己信箱（轻量模式读 `沟通/投递.md` 中 @我的部分），处理未读；
4. 跨块改动先按 §3 加锁；发现过期锁（>24h）按抢占规则接管并在锁内备注；
5. 确认自己负责条目的决策没有失效（旧措辞：状态不是 `superseded`/`revoked`；新枚举下的实际动作见第 6.4 节），避免基于已废决策开工。

[实测：SKILL.md「新人 Onboarding 必读检查单」；第 1 步的 grep 化是 v1.3 改动，动因见 CHANGELOG.md v1.3「全量读取/膨胀/反复消耗」三批评]

第 1 步为什么强制 grep 不读全文：新人的 token 预算应该花在自己那块地的上下文上；决策库全读一遍，还没开工先被喂饱——「读全文」恰恰是 v1.3 整批优化要消灭的动作形态。

## 第 4 章 L2 核心机制：编辑锁（带超时与抢占）详解

### 4.1 锁长什么样：五要素一行式

统一格式为「角色 | 时间 | 改动摘要 | 状态 | 心跳」，按文件类型换注释符：[实测：契约模板.md §3「锁标记格式」（原文称「统一四要素…建议带心跳」，心跳计入完整形态即五要素）]

| 文件类型 | 注释语法 | 锁示例 |
|---|---|---|
| Markdown / HTML | HTML 注释 | `<!-- EDIT_LOCK: 某角色 | 2026-10-09 14:02 | 追加进度段 | 状态:wip | 心跳:2026-10-09 14:02 -->` |
| GDScript / Python | `#` 行注释 | `# EDIT_LOCK: 某角色 | 2026-10-09 14:02 | 重构信号处理 | 状态:wip | 心跳:2026-10-09 14:02` |
| TypeScript / JS / C# / C++ | `//` 行注释 | `// EDIT_LOCK: 某角色 | 2026-10-09 14:02 | 改接口签名 | 状态:wip` |

锁是**明文写在被保护文件内部**的，不是外部登记表。为什么这样设计：外部表本身又是一个要并发修改的文件，用表管锁等于再造一个撞车点；明文锁与内容同生共死，`grep` 一条命令就能「看到」全项目的实时占用图，天然自带广播效果。[推演——其失效场景也可举出：若锁登记在外部表，则「加锁」动作自己也需要加锁，鸡生蛋死循环；且任何 agent 没先读表就动文件，表立刻失真]

### 4.2 什么时候必须加锁

规则原文两条（契约模板.md §3「规则」小节）：

1. 要修改**非自己主责**的文件 → 先在目标段落首部加锁并写当前时间戳；
2. 对自己的主责文件做**结构性/跨段落**改动 → 也要加锁。

第 2 条常被忽略但同样关键：主责意味着「平时归我」，不意味着「别人此刻没在读」。结构性改动（挪段落、重排编号）会让正按旧结构引用的协作 agent 引用落空，所以哪怕自己的地皮、动大了也得挂牌。改动完成并移除锁；跨多段时，每段独立加锁或段首统一加一处。[实测：契约模板.md §3 规则第 1、3 条；SKILL.md「四条核心纪律」第 1 条「改完移除」]

### 4.3 读到别人的锁怎么办

读到带 `状态:wip` 锁的段落时，**不要同时改**，两个合法选项：先留接力说明等对方释放；或协商合并（把你想改的内容作为待合并留言写进锁内）。[实测：契约模板.md §3 规则第 3 条；SKILL.md「四条核心纪律」第 1 条「读到有效 wip 锁不并行改」]

### 4.4 心跳与超时抢占：锁的防死锁半生命周期

一个会话可能随时崩掉。只有「加锁—释放」两个动作的锁，持有者一崩，文件就被占到天荒地老（死锁＝资源被无人认领地锁住）。所以锁制度带了时间参数：[实测：契约模板.md §3「超时与抢占（防死锁）」]

- **心跳**：加锁者做长任务时**每 ≤12 小时**更新一次心跳时间戳，证明「我还在改」；
- **过期**：任何 `wip` 锁距其心跳超过 **24 小时**未更新 → 视为过期锁，任何 agent 可**抢占**；
- **抢占动作**：在原锁内追加一行 `> 由 <接管者> 于 <时间> 接管（原锁超时）`，改写心跳续锁后继续改；
- **抢占前置协商**：若不确定原改动是否已完成，先在锁内留协商说明，等原 owner 在对话/信箱回应；仍无回应**且已超时**才接管；
- **无心跳的锁**：体检脚本 [1] 把「有 wip 但没有心跳时间戳」单独列为问题（无法判断是否过期，建议补全），而不是当作健康。[实测：governance_check.py check_locks 函数的 `if not hb` 分支]

**为什么是 12h／24h 这对数**：[推演] 心跳间隔取超时窗口的**一半**，等价于「连丢两次心跳才判死」——只丢一次（比如夜间会话被挂起 13 小时）时 13h＜24h 仍有效，不会误抢；人真没了则最多 24 小时就能被接管。把心跳压到 1 小时会逼人频繁碰文件（每次续心跳本身就是一次写，可能撞车）；把超时放到 72 小时，一个崩掉的会话就能把核心文件锁死三天，进度失衡比死锁本身更贵。误判代价和漏判代价的比值，就锚在 1:2 这组参数上。具体什么输入会出问题：若改成心跳 6h/超时 48h，则 6~48h 窗口里原 owner 其实已崩、别人却不敢动（漏判拖两天）；反过来心跳 12h/超时 13h，一次普通的隔夜挂起就被误抢，原 owner 回来继续写、接管者也写了——**双活撞车**，两边都以为自己持锁，比死锁更难发现。

### 4.5 全局锁探针：开工三查里的第二查

SKILL.md「Agent 工具级执行指令（省 token，别整文件读）」节给出开工前的 shell 查法，代替「挨个打开文件读」：[实测：该节代码块；同款指令在契约模板.md §3「Agent 自检指令」重复出现，两处逐字同文]

```bash
# 查自己信箱（只看根目录，绝不递归 已处理/）
ls 沟通/<我的角色简称>/                 # PowerShell: dir 沟通\<我的角色>\

# 查全局有效锁（Bash）
grep -r "EDIT_LOCK:.*状态:wip" --include="*.md" --include="*.py" --include="*.gd" .

# 查全局有效锁（Windows PowerShell，无 grep 时用）
Get-ChildItem -Recurse -Include *.md,*.py,*.gd | Select-String "EDIT_LOCK:.*状态:wip"
```

第三条「查待拍板事项」在正文里**只留了注释意图、没有命令本体**——已知缺口，第 15.6 节如实登记；实操可用 `grep -n "待拍板" DECISIONS.md` 之类补齐（含义：只取那一节的命中区块，不读全文）。[实测：SKILL.md 该节代码块第三段仅一行注释；判据：对照同块前两组「注释＋命令」的成对格式，第三组缺右半]

### 4.6 锁的第二职业：来源标注

契约模板.md §4 铁律 4 规定：决策登记方把结论同步到相关文档时，要在相关文档用 `EDIT_LOCK` 标注来源。也就是说锁这个标记体系身兼两职——占用广播（§3 用途）与改动溯源（§4 用途）。同一套「grep 可见」的基础设施，第二次复用零成本。[实测：契约模板.md §4 铁律 4]

### 4.7 加锁-改-撤锁的原子三步（操作卡片）

```
1) 查：grep 全局 wip 锁 → 目标段落无他人锁
2) 加：段首插入五要素锁行（含当前时间戳与心跳）
3) 改完撤：写完立即移除锁行；交班前再 grep 一次「自己的署名＋状态:wip」应为空
```

三步是对第 12 章正面走查的压缩表述；[推演] 漏第 3 步的后果最隐蔽：残留锁不报错、不挡自己，只挡**别人**——直到 24h 后被抢占接管，你的改动来历在接管行里说不清。

## 第 5 章 L1 核心机制：统一决策入口 DECISIONS.md 详解

### 5.1 四条铁律逐条拆

契约模板.md §4 的四条铁律是整个 L1 的骨架：[实测：契约模板.md §4；SKILL.md「四条核心纪律」第 2 条]

| 铁律 | 原文要求 | 堵住的事故 |
|---|---|---|
| 铁律 1 禁止分散追问 | 需用户拍板的事**禁止**在 agent 自己对话里直接问，必须先登记进「待用户拍板」区 | 用户被甲乙丙各问一遍同一问题 |
| 铁律 2 去重 | 同一决策只登记一次；登记前先搜 `DECISIONS.md` 有无同类条目，有则补充而非新建 | 同一问题两个条目挂着两个负责人，用户答了 A 没答 B |
| 铁律 3 一次拍板全员生效 | 用户对某条目拍板一次即对全员生效，任何 agent **不得再次追问同一问题** | 乙没看到甲的对话记录，把已决问题重新问一遍 |
| 铁律 4 登记方负责同步 | 登记方把结论同步到相关文档、标记 `已决`，并在相关文档用 EDIT_LOCK 标注来源 | 拍板了但只有真相源改了、各文档还写着旧方案 |

**为什么铁律 3 需要明文写「不得再次追问」**：agent 的默认行为是「不确定就问用户」，这是个体最优；但对多 agent 系统，每个「再确认一遍」都转嫁给用户。铁律把「查真相源」置于「问人」之前——问之前先去 `DECISIONS.md` 搜，答案大概率已经在那儿。

**铁律 2 的搜索为什么重要**：[推演] 两个 agent 各自遇到同一阻塞是并行工作的常态而非意外；没有「登记前先搜」，待拍板区会长出双胞胎条目（体检脚本 [2] 就是专门事后抓这种漏网对的，相似度 ≥0.5 报警，见第 9.3 节）。

### 5.2 已拍板决策条目：五要素

每条 approved 决策固定五字段（决策看板模板.md §1 的 D-01 示例逐字段，原文注语「每条含『结论 / 实现指向 / owner / 状态 / 回灌』五要素」）：

| 字段 | 内容 | 为什么不能省 |
|---|---|---|
| **结论** | 用户拍板的那句话 | 没有结论的决策条目没有执行价值 |
| **实现指向** | 落点文件/模块 | 防止「拍了板没人知道改哪」 |
| **owner** | 谁负责落地 | 无 owner 的决策等于没拍 |
| **状态** | `approved` 或 `todo` | 状态是「能不能照它开工」的唯一开关 |
| **回灌** | 已回灌位置 / 待回灌 | 决策被替代时旧结论清场的进度条（见第 6 章） |

[实测：决策看板模板.md §1]

### 5.3 其余区块的分工

`DECISIONS.md` 的完整分区（决策看板模板.md 全部 7 节，数法：按模板二级标题 §0~§6 计数）：§0 协作纪律红线 5 条；§1 已拍板决策；§2 分工矩阵（owner 边界，防撞车）；§3 待拍板决策表（列：ID/决策/候选方案/负责人/状态）；§4 执行跟踪（按 Wave/里程碑分组）；§5 待用户提供（用户承诺后续给的素材挂账处）；§6 历史区（失效决策的指针）。[实测：决策看板模板.md 各节标题]

两个值得单独点名的设计：

- **§0 第 2 条「动手前认领」**：修改任何文件/代码前，先在 §3/§4 执行跟踪把对应条目状态改为 `doing` 并写明 owner，改完改 `done`。这是**任务粒度**的防撞车，和编辑锁的**文件段落粒度**互补——锁管「此刻谁在写」，认领管「这条活儿归谁」。
- **§0 第 4 条「验证铁律」**：代码改动后跑验证探针（探针＝只检查不改东西的命令），**不自报通过**；验证由主理人/用户独立确认。针对的故障是 agent 的自我汇报幻觉（「已完成」但没人看过），把「谁宣布成功」和「谁做的」强制分离。[实测：决策看板模板.md §0 第 2、4 条]

### 5.4 用户角色：为什么全系统只留一个人类

契约模板.md §1 角色表第一行固定是「用户｜主脑/最终拍板人｜定方向、拍板决策、提供素材」。所有机械裁决（3.5 节顺序第 2、3 条）都在 agent 之间消化，只把**例外**升级到用户。整个 L1 本质是给「一个人对多个 AI」这种拓扑设计的带宽限流器：用户的注意力是系统里最稀缺的资源，统一入口保证每份稀缺资源只花在一个从未回答过的问题上。[推演——其成立前提有原文佐证：SKILL.md「概述」痛点 2 即「用户被甲问完乙又问同一件事」]

## 第 6 章 决策生命周期：替代即换血 · 抛弃即删除

这一章是 v1.3 的主菜，回答一个此前版本没答好的问题：**决策作废之后，旧记录怎么死**。

### 6.1 总原则：活跃区只写「现在是什么」

`DECISIONS.md` 活跃区只记录现行有效结论，不记录「曾经是什么」。v1.3 之前流行的写法被明令禁止：像「3D 俯视角肉鸽（之前的 2D 横板格斗被用户推翻）」这类**括注式历史叙述**（示例照抄自 SKILL.md 禁令原文，只用于说明格式）不再允许出现——新旧不共存，活跃区永远只写现行结论，读者不需要也不应该知道旧方案。[实测：SKILL.md「决策生命周期」节替代型第 1 条；CHANGELOG.md v1.3「做了什么」记录该禁令]

为什么禁历史叙述：[推演] 两个原因。其一，旧方案描述对执行者是纯噪音——没人会去实现「之前的 2D 横板」；其二，历史叙述会自我繁殖——每个转述者都会用自己的话重讲一遍旧故事，决策库每双周胖一圈，全胖在没用的档案上。这正是 CHANGELOG.md v1.3 记录的升级动因：用户质疑「信箱=派工单变体」后拍板四项优化，针对的病灶就是「决策与信箱记录越用越肥（历史叙述膨胀、反复消耗 token）」。

### 6.2 替代型（有新决策接棒）：三步

1. 新结论按正常流程登记**新条目**（`D-xx` ＋结论五要素），禁写历史叙述；
2. 旧条目从活跃区移除，历史区只留一行：`- D-01（已替代→D-05，2026-09-18）`，不保留旧结论正文；
3. **主文档回灌**：原 owner **48 小时**内把新结论同步回所有引用旧决策的主文档（设计稿/代码注释），防止「文档还写着旧方案」；完成后在「回灌」字段填已回灌位置。

[实测：SKILL.md「决策生命周期」节；决策看板模板.md §1「生命周期规则（v1.3）」与 §6 历史区格式（该行式示例即模板原文格式）]

**为什么历史区要留一行指针而不是全删**：其他 agent 的**对话记忆**里可能还引用旧编号（如「依据 D-01 开工」——对话历史是改不了的既成事实）。一行指针让它在 `DECISIONS.md` 里查得到「D-01 已废、去向 D-05」，避免幽灵引用（编号查无此事，引用却还在起作用）。除这一行外不留任何旧内容。[实测：SKILL.md「为什么替代型要在历史区留一行指针（而不是全删）」段]

**为什么回灌限 48 小时**：[推演] 回灌拖过一天，就会出现「新开的对话窗口按未回灌的旧设计稿开工」的事故；48h 给原 owner 留了一个跨日会话的执行余量，又短于多数项目的双周节奏，保证回灌在下一次大动土之前完成。具体反例：若回灌无限期，D-05 生效两周后，按 D-01 旧结论写的代码注释还挂在那里——新人 onboarding 检查单第 5 步查真相源查到了新条目，可实际读到的设计稿还是旧的，检查单和文档打架，等于没查。

### 6.3 抛弃型（作废且无接棒）：先 grep 再删，删就删净

1. owner 先 `grep` 全项目搜**决策编号与关键词**，确认没有任何主文档引用它；
2. 无引用 → **直接删除条目，不留任何记录**；有引用 → 先清理引用，再删除。

[实测：SKILL.md「决策生命周期」节抛弃型；决策看板模板.md §6 注语「抛弃型（作废无接棒）不进历史区」]

和替代型的分野逻辑：**指针的价值＝还有人正拿着旧引用**。替代必有接棒，说明这条线还活着，旧号必须能查到去向；抛弃＝这条线整个死了，若已 grep 证明无处引用，留任何记录（包括一行指针）都是纯负重。顺序不能反——先删后 grep 会把还活着的引用变成断头路；先清引用再删，两头都干净。

### 6.4 状态枚举的收敛史（一处版本张力，诚实说明）

现行状态枚举：活跃区**只有** `approved`（生效）与 `todo`（待拍板）两种；失效条目一律**离开**活跃区（替代型进历史区一行式，抛弃型直接删除）。[实测：SKILL.md「状态枚举」段；决策看板模板.md §1「状态枚举（活跃区只有两种）」]

这是 v1.3 的简化。v1.1 引入生命周期时靠 `revoked` 等状态标记作废决策，SKILL.md「四条核心纪律」第 2 条至今仍写着「决策被推翻须走『生命周期』流程标记 `revoked`，不得静默覆盖」——在新语义下应理解为「走生命周期流程完成出区动作」，而不是「在活跃区挂 revoked 状态」。同理，onboarding 检查单第 5 步的「确认状态不是 `superseded`/`revoked`」按新枚举的实际操作是：**确认条目还在活跃区且为 approved；若已在历史区见指针，改按新号办**。两处措辞滞后于枚举简化，属版本注记未逐句改写（第 15.6 节登记）。[实测：SKILL.md 纪律 2 与「状态枚举」段、新人检查单第 5 步三处对照；CHANGELOG.md v1.1「决策生命周期（撤销/修订）」→ v1.3「生命周期简化」演化轨迹]

「不得静默覆盖」这条底线为什么必须保住：[推演] 静默覆盖＝旧结论原地被改写。原地改写会让所有拿着旧引文的人对不上账（引文还在、原文已变）；「新条目＋旧条目出区＋一行指针」让每一步都可 grep 追溯——覆盖是无痕的，换血是有痕的。

### 6.5 决策压缩：防越用越肥的第三道闸

活跃区 `approved` 条目超过 **30 条**或**每两周一次**，把历史区整体并入 `DECISIONS_归档.md`，主文件顶部留一行「历史决策见归档」；压缩后主文件回到只含现行决策的「小而准」状态。体检脚本 [7] 监控活跃区规模（按 `状态[:：]approved` 的出现次数计数）。[实测：SKILL.md「决策压缩」段；决策看板模板.md §1「压缩规则」；governance_check.py check_decisions_size 函数]

为什么「>30 条」与「双周」取**或**：30 条是**空间阈值**（活跃区读一遍开始心疼 token），双周是**时间阈值**（防止条目增长慢、但历史指针持续累积）；任一先到即执行，不攒批。为什么压缩只是搬家不是删除：一行指针体系仍可追溯——替代型防幽灵引用的功能不因瘦身而失效；归档文件本身不再被日常巡检读取，token 成本留在活跃区、历史成本沉到冷存。

### 6.6 一个决策条目的完整一生（时间线示例）

```
D-12 登记（todo，候选 A/B）
  → 用户在 DECISIONS.md 拍板 → approved，填五要素
  → 48h 内回灌引用它的两份设计稿，「回灌」字段更新为已回灌位置
  → （未来）玩法改版，D-12 被 D-19 替代
  → D-19 正常登记；D-12 移出活跃区，历史区留一行：D-12（已替代→D-19，日期）
  → 双周压缩：历史区整体并入 DECISIONS_归档.md，主文件顶部一行指路
```

## 第 7 章 L3 核心机制：异步信箱与归档纪律详解

### 7.1 标准信箱：目录结构与信件命名

```
{项目根}/沟通/
├── {角色A简称}/      ← 角色A 的收件箱（别人对 A 说话的地方）
│   ├── {B简称对A简称}.md   ← 待办信留在根目录
│   └── 已处理/             ← 闭环信归档在这
├── {角色B简称}/
└── 用户/             ← 可选：用户对全员/某角色的留言
```

命名约定：`沟通/<接收人简称>/<说话人简称>对<接收人简称>.md`。例：着色器开发者要对技术美术说话 → `沟通/技术美术/着色器开发者对技术美术.md`；同一对多次通信在文件名加序号或日期后缀（`着色器开发者对技术美术_2026-07-27.md`）。角色用**简称**命名子文件夹。[实测：信箱说明.md「目录结构」「信件命名」两节]

为什么文件名写全「X对Y」：收信人扫一眼目录就得到「谁找我、找了几次」的信息，不用开文件；且发信是**只在对方目录新建文件**的动作——新建不触碰任何既有内容，撞车面为零。信箱信道天然安全的原因恰恰在这：写信＝造新文件，改旧文件才危险。

信件建议结构五字段：来源／日期／主题／正文／涉及文档与引用（文件＋§ 段落、`DECISIONS.md` 编号）。接力信专用格式在正文里再细分三字段：卡点原因（缺依赖/超能力范围/反复尝试无进展）、已尝试方案（简述，**避免接手人重试**）、建议接手人。[实测：信箱说明.md「信件结构（建议）」「🔄 接力信格式」]

「已尝试方案」字段的用意：接力最怕接手人把弯路重走一遍；把「试过什么、为何不通」随信交接，失败信息就从沉没成本变成交接资产。

### 7.2 使用纪律：读根目录、闭环归档

- 所有人**每次开工先读自己信箱文件夹（仅根目录）**，处理未读；
- 每个信箱下设 `已处理/` 子目录；信件**闭环**后由接收人（或发件人经确认）`mv`（移动命令）进 `已处理/`；
- **闭环三条件**（全满足才算办完）：回执已收 ＋ 无后续待办 ＋ 对应决策已决/任务已交接；
- **待办信留根目录**：仍挂起、需我方行动、或等上游规格/接线的信不归档，直到闭环；
- agent 巡检只 `ls` 信箱根目录、**绝不递归 `已处理/`**；要翻历史才进去。

[实测：信箱说明.md「使用纪律」节；SKILL.md「四条核心纪律」第 3 条「闭环即归档」]

**为什么不递归已处理**：不归档的话，信箱信数随日单调增长，每次巡检都得重读全部旧信，token 开销线性上涨；归档后巡检成本恒定为「活跃信数」。这是整个 skill 里最直白的一个省钱设计。体检脚本 [4]「信箱积压」的实现与这条纪律精确咬合：它基于**非递归** `os.listdir`（只列一层目录的读取方式）只扫各信箱根目录，已归档信不会被误判为积压；信箱说明.md 还专门警告「若将来改为递归扫描，须显式跳过 `已处理/`」——脚本行为与人工纪律必须同向，否则脚本会把守规矩归档的人误报成积压大户、把不归档的人反而报不准。[实测：governance_check.py check_mailbox_backlog 函数；信箱说明.md「体检脚本须知」]

积压判据的实现细节：信里既无 `状态:done` 也无「已处理」字样 → 列为未处理项。也就是说「处理完了标一下」不是礼貌，是**机器要读的标记**。

### 7.3 轻量模式：单文件信箱与强制升级阈值

轻量档（1~2 agent）不建按角色子文件夹，改为单一文件 `沟通/投递.md`，所有人往里追加信件，主题行用 `@<接收人>` 标注目标（例：`主题：@技术美术 着色器接口确认`）。不强制 `状态:done`，但建议处理后在主题加 `[已处理]`。[实测：信箱说明.md「轻量模式（单文件信箱）」节；SKILL.md「规模自适应」]

**强制升级阈值**：投递.md 信件超过 **20 条**或最早未处理信超过 **7 天**，必须升级为标准模式（拆信箱文件夹）。SKILL.md 原文点破深层理由：单文件信箱本质仍是「中央派工单」，靠硬阈值防止它悄悄长成 token 黑洞（体检脚本 [6] 会报警）。[实测：SKILL.md「规模自适应」轻量模式子弹]

**为什么是 20 条／7 天**：[推演] 20 条来自体量——轻量模式的读法是每轮全读一个文件，20 条 × 每条约 5~6 行 ≈ 百行级，逼近「不该再整读」的临界，与脚本 [6] 的 150 行兜底阈值（见 7.4 节）互为表里；7 天来自时效——单文件模式下未处理信对**所有人**每轮可见，一封信压过 7 天说明要么活儿没了、要么该拆信道了，两种都值得升级而不是继续挂着。具体反例（若没有阈值）：两人项目做成单文件，半年后 90 条信，每轮开工全读 400 行——治理文件自己成了最大的 token 消耗源，恰好复刻了它要消灭的病。

### 7.4 体检脚本怎么数「一封信」：启发式与其边界

脚本 [6] 对投递.md 的计数方式：按 `^#{2,3}\s`（二级/三级标题行）数封信，**>20** 报警；同时用**总行数 >150** 兜底；任一超标即报警。[实测：governance_check.py check_light_mailbox_size 函数；常量 LIGHT_MAILBOX_ITEMS=20、LIGHT_MAILBOX_LINES=150]

**为什么要双阈值**：标题计数会被两种书写习惯击穿——信不写标题只堆正文（条数永远不超、行数暴涨），或每信拆一堆小标题（条数虚高）。行数兜底管前者，条数阈值管后者；两个口径同时漏掉的写法基本不存在。[推演——脚本源码注释自称「启发式（按 markdown 标题计数）」，作者明知计数近似，用第二口径对冲；具体反例：一封 130 行的巨型信，条数 4 不报、行数逼近 150 兜底线，下一封再来就越线]

### 7.5 与记忆日志的协同（append-only 的出处）

信箱说明.md「与记忆日志协同省 token（重要）」节把同一套纪律延伸到 agent 的每日记忆日志：日志按天滚动、只留近 N 天（**建议 7**）在根目录，更早的移入 `memory/archive/` 冷存；所有 agent 会话加载**只扫根目录，不扫 archive**；**日志只 append（防并发互冲），绝不 `Write` 整体覆盖他人段落**；长期事实（决策/红线/约定）抽到 `MEMORY.md` 或 `memory/*.md` 子文件做索引，不堆在每日日志里。[实测：信箱说明.md 该节；「纯追加」的完整走查见第 12 章]

「日志只 append、绝不整体重写」是防**丢更新**（lost update：后写者拿着旧快照整体回写，把中间别人写的新内容抹掉）的根规则——第 12 章的反面场景就是它被违反时的样子。N=7 与信箱的 7 天升级阈值同值：都是「一周内的活跃记忆整读，更早的只配被检索到名字」这条分界线在不同文件上的投影。[推演——两处同值的佐证：信箱说明.md 写「建议 7」、SKILL.md 写「7 天」]

### 7.6 L4 看板字段与状态约定

`状态看板.md` 推荐六列：任务ID（`T-xx`）｜任务｜owner｜状态（todo/doing/done/blocked）｜关联决策｜备注（blocked 必须写阻塞原因/等待谁）。可与 DECISIONS §4 执行跟踪二选一或合并；小项目用 Wave 即可。看板末尾可选 Mermaid 甘特图（图内条 id 如 `t01` 与看板表任务 ID 如 `T-01` 是两套编号、互不冲突——Mermaid 的 id 只是甘特条内部引用名）。[实测：信箱说明.md「二、进度看板」节]

`blocked` 是交接原则在看面上的落点：目标成员被切换过去时，一眼看到的不是空任务行，而是「卡在哪、等什么」——这就是「让切换零摩擦」的最后一公里。

### 7.7 信箱防腐蚀三规

常见陷阱清单里与信箱直接相关的三条：信箱只放「需要对方行动/知悉」的内容，闲聊不进（信箱变聊天记录）；角色名三处统一（信箱文件夹、契约角色表、分工矩阵），否则投递错位；锁不释放别人就一直不敢动。[实测：信箱说明.md「三、常见陷阱」第 3、4、5 条]

## 第 8 章 交接原则：不让任何人在瓶颈处死磕

### 8.1 它治的病：协同推进失衡

多 agent 并行时，若某成员在自己主责区死磕，既浪费轮次又拖垮整体，导致成员间进度差距过大。本原则要求 agent 在**该让位时主动让位**——把「卡住」转化为「让用户去下一个成员那里」。[实测：SKILL.md「交接原则」节首段（原文「解决『协同推进失衡』」）]

为什么把交接做成纪律而不是美德：agent 没有动力承认卡住（自报困境在其评价体系里是负分），不写规则时默认行为就是无限重试。交接原则实质是**给「认输」定义合法出口**：满足触发条件、按格式交接，就算尽职——继续死磕反而是违规。

### 8.2 触发条件（满足任一即必须告知用户）

1. **自身陷入瓶颈**：在自己主责任务上连续受阻（反复尝试无进展、缺关键依赖/信息、方案被卡死），且短时间内预计无法突破；
2. **更适合他人接手**：判断该任务交给另一成员推进更高效（对方有专长、已具备前置上下文、或接力比原地强攻更顺）。

[实测：SKILL.md「交接原则」触发告知两条；契约模板.md §9 同文]

### 8.3 触发后的三个动作

- **当前对话窗口**用自然语言明确告知用户：卡点是什么、为什么、建议切换到哪个成员/会话，并给一句「建议下一步」（例：「这块数值平衡交给【数值策划】接力更顺，建议你切到 TA 的会话推进」）；
- 若启用治理机制：按信箱规则把接力请求投递到目标成员信箱（`沟通/<接收人>/X对Y.md`，轻量模式追加 `沟通/投递.md`）；
- 若启用 L4 看板：把自己的任务标 `blocked` ＋ 备注阻塞原因/等待谁。

[实测：SKILL.md「必须做的行为」段]

**为什么瓶颈告知走对话而不是只走信箱**：切换会话是**用户**的物理动作，信箱是「对方下次开工才看」的慢信道。这与 3.4 信道分工第 4 行（瓶颈→直接对话，不进信箱、不进 DECISIONS）严格呼应；信箱那一步是给**接手人**准备的上下文，不是给用户的通知。

### 8.4 交接卡：让切换会话零摩擦的结构化输出

```markdown
### 🔄 交接卡：[当前任务] -> [目标角色]
- **卡点原因**：[缺依赖 / 超能力范围 / 反复尝试无进展]
- **已尝试方案**：[简述，避免接手人重试]
- **建议接手人**：[目标角色]
- **接力信箱**：已投递至 `沟通/[目标角色]/[我的角色]对[目标角色].md`
- **下一步建议**：请切换到 [目标角色] 的会话，TA 开工时会读到接力信。
```

[实测：SKILL.md「交接卡格式」代码块；契约模板.md §9 附同款]

五个字段各挡一种损耗：卡点原因挡「用户反复问怎么了」；已尝试方案挡「接手人重走弯路」；建议接手人挡「用户不知道该切哪」；接力信箱挡「接手人没有上下文还得回来问」；下一步建议把整次交接压缩成**一个可执行动作**。交接卡与接力信的关系：卡是给用户的（决定切谁），信是给接手人的（切过去能开工），同一事件的两个受众面。

### 9.1 用法与退出码

| 1 | 发现问题（逐项打印后给出计数结论） |

[实测：governance_check.py 模块 docstring「用法」「退出码」；main 函数目录不存在时 return 2 的路径]

定位：大型模式或项目混乱时用；轻量/标准模式可不跑（SKILL.md「治理体检（可选自动化）」节末注语）。Windows 编码防御：脚本启动即对标准输出/错误流做 `reconfigure(encoding="utf-8", errors="backslashreplace")`（打不出的字符转义显示而非崩溃），外层 try/except 保证老解释器不报错（CHANGELOG.md v1.2「体检脚本 Windows 编码」即此项）。[实测：main 函数开头 reconfigure 块]

### 9.2 [1] 过期锁

扫描方式：`os.walk` 递归遍历全项目，扩展名覆盖 `.md/.py/.gd/.ts/.js/.cs/.cpp/.gdshader` 八类（前三类同开工三查的 grep 面，后五类是脚本扩编），文件含 `EDIT_LOCK` 字样即解析锁行。三分支判定：[实测：main 函数锁扫描循环；check_locks 函数]

1. `状态:wip` 且**无心跳时间戳** → 报「发现 wip 锁但无心跳时间戳（无法判断是否过期，建议补全）」；
2. `wip` 且心跳距今 >24h（`WIP_TIMEOUT = timedelta(hours=24)`）→ 报「过期锁」并附已挂起小时数；
3. 其余（done、无 wip 状态、锁不含状态词）→ 不报。

正则细节：`LOCK_RE` 取 `EDIT_LOCK:` 之后到注释符结尾（`-->`、`*/` 或行尾），兼容三种注释语法；`HEARTBEAT_RE` 抓 `心跳:` 后的时间；时间解析接受「年-月-日 时:分」与纯「年-月-日」两种格式（纯日期锁按当日 0 点起算，精度较糙——所以锁格式规范里要求带时分）。

### 9.3 [2] 重复决策

只在**待拍板区**比较：截取「待拍板」起、到下一个二级标题为止的区块，取表格行第 2 列作标题；两两做 **Jaccard 相似度**（两组关键词的交集个数 ÷ 并集个数，0~1），**≥0.5 判疑似重复**。分词规则：连续 ≥2 个汉字算一个词、≥3 个字母算一个词。[实测：check_dup_decisions 与 _tokens 函数]

为什么阈值取 0.5：[推演] 共享不到一半关键词视为「巧合相近」放过——假阳（明明不重复却报警）会淹没真重复；过半相同视为「在说同一件事」报警——宁可让人肉眼再确认一次。具体反例：若阈值降到 0.3，「战斗手感调优目标」与「战斗数值成长曲线」这类只共享「战斗」的互补决策会被成天误报，看两三次后人就开始无视整份报告——误报养出「狼来了」，比漏报更杀工具。

### 9.4 [3] 角色名漂移（普适升级 v2）

**设计目标（源码注释原文）**：以「信箱文件夹名」为权威角色名、契约 §1『成员与角色』表为定义来源，通过（a）仅扫描指定 section 的表格、（b）噪声过滤、（c）归一化比对，彻底消除旧版把分隔线/D 编号/文件路径/分类名误判为角色的 **67 处误报**。[实测：governance_check.py check_role_drift 上方设计注释块]

三层防误报机制：

- **限定信源**：契约只取「成员与角色」标题下**第一张表**的首列；DECISIONS.md 默认**不参与**角色定义（多为散文引用，易误报），需 `--decisions-roles` 显式开启；
- **噪声过滤**（`_is_role_cell`）：跳过表格分隔线（`---`/`:---:`）、已知表头词（成员/角色/ID/区块/任务/决策/分类/路径/主责/协作/来源等）、`D-08`/`T-03` 式编号、含 `/` `\` `.md` 的路径、纯数字、长度 >16 的字符串；另用人形关键词（用户/主脑/人/user/human/team/团队）剔除人类行；
- **归一化比对**（`_norm_role`）：去已知前缀（`godot`）、去尾随数字再比——「技术美术」与「技术美术1」归一后同形，报出「同一角色多种写法，建议统一为信箱文件夹名」。

之后做**双向缺失检查**（信箱有而契约无 / 契约有而信箱无），且仅在无写法冲突时才补报，避免重复噪声。[实测：check_role_drift 与三个辅助函数逐一可查]

67 处误报的教训被明文写进源码注释当防回归路标——检测器自己也撞过车，这是「机制经实战打磨」最硬的内部证据。

### 9.5 [4] 信箱积压

轻量模式：投递.md 全文既无 `状态:done` 也无「已处理」→ 报「可能存在未读积压」，不再逐封判。标准模式：遍历每个角色信箱**根目录**（`os.listdir` 非递归，绝不进 `已处理/`）的 .md 文件，两种标记都没有即逐条列为未处理。[实测：check_mailbox_backlog 函数]

### 9.6 [5] 看板漂移

仅当项目根存在 `状态看板.md` 才启用：数出状态列为 `blocked` 的任务行，提醒人工核对 DECISIONS §4 执行跟踪是否同步标注阻塞原因。注意它**不自动判定矛盾**，只把两处该同步的点列出来给人看——状态语义太灵活，机器硬判假阳率高，这里有意停在「提醒」层（保守边界见 15.6 缺口 6）。[实测：check_board_drift 函数]

### 9.7 [6] 轻量信箱规模 ＆ [7] 决策规模（v1.3 新增）

[6]：投递.md 按二三级标题数封信 >20 **或** 总行数 >150 → 报警并建议升级标准模式（报警文案原文含「单文件信箱本质是中央派工单」）。[7]：`DECISIONS.md` 中 `状态[:：]approved` 出现次数 >30 → 报警并提示执行决策压缩（历史区并入 `DECISIONS_归档.md`、替代型改一行式指针、抛弃型直接删除）。[实测：check_light_mailbox_size、check_decisions_size 函数与两个常量]

CHANGELOG.md v1.3 记录了这两项的验收证据：造 22 封信＋35 条决策的超标样本实测报警、exit 1；同条目「三处同步落地」指 SKILL.md、决策看板模板、governance_check.py 三个文件同版本改齐——**机制、模板、检测器**任何一处落后都会造成「规矩写了没人查、查了报不准」。[实测：CHANGELOG.md v1.3「怎么解决的」段]

### 9.8 🔴 逐项恒真与恒红点名：这把尺子什么时候量不到东西

> 两个词先说明白。**恒真判据（永远绿）**＝"命令没报错就算过"，可它压根没测到东西，于是永远给你绿灯；**恒红判据**＝不管有没有问题它都响，于是没人再看它。**报警疲劳（狼来了效应）**＝假警报多了以后真警报被一起忽略——这是恒红最贵的下游成本。这一节的每一条都附「什么输入会让它失灵」。

#### 9.8.1 两次复跑（2026-10-09，只读执行，不改任何文件）

| 复跑 | 拿什么当扫描根 | 脚本输出 | 退出码 | 这条实测说明什么 |
|---|---|---|---|---|
| A | **这个 skill 包自己的目录**（它自带 `SKILL.md` 与契约模板，里面有锁格式示例和 grep 示例） | `[1] 编辑锁检查：发现 7 处问题`，7 条全是「发现 wip 锁但无心跳时间戳」；[2][3][7] 打「跳过」；[4][6] 打 OK | **1** | 7 处**全是假警报**：命中的是 `SKILL.md`「Agent 工具级执行指令」里的 grep 示例行（2 处）与契约模板 §3 的锁格式示例行（3 处）＋契约 §3 末尾的 grep 示例（2 处）。检查器把**教我怎么加锁的那几行字**当成了真的锁。[实测] |
| B | 包内 `scripts` 子目录（一份**治理文件都没有**的目录） | [1][4][6] OK，[2][3][5][7] 跳过，结论行「治理健康，无发现问题」 | **0** | 一个连 `DECISIONS.md`、契约、信箱都不存在的目录，体检结论是**健康**。"没得查"和"查了没问题"共用同一个 0。[实测] |

#### 9.8.2 七项检查的失灵面逐条（判据→恒真条件→恒红条件）

| 检查项 | 判据一句话 | 什么时候**永远绿**（测不到东西） | 什么时候**永远红**（不管三七二十一报） |
|---|---|---|---|
| [1] 过期锁 | 锁体里状态是 `wip`，且心跳超 24 小时 | ①状态写成中文（`状态：进行中`／`状态：占用中`）→ 判据只认 wip 这个词，这把锁**永不被判过期、永不被报告、却真实占着文件**；②心跳写在**明天**（时钟漂移或笔误年份）→ 差值为负，永不过期；③锁写在 `.html`／`.json`／`.toml` 里 → 八类扩展名表（`.md/.py/.gd/.ts/.js/.cs/.cpp/.gdshader`）不覆盖，而契约 §3 **明文允许** Markdown/HTML 注释锁；④文件不是 UTF-8 编码 → 读取异常被 `except` 静默 `continue`，整份文件对检查器不存在 | ①文档示例行被当真锁（复跑 A 的 7 条）；②模板占位符 `心跳:<YYYY-MM-DD HH:MM>` 全是字母没数字 → 正则抓不到 → 报"无心跳"，而**错误文案本身是错的**（心跳写了，只是格式不合），照文案去补会补出第二条不合式的；③锁扫描 `os.walk` 全项目递归、**不排除** `已处理/` 与 `归档/`，退役归档后旧锁被永久反复点名 |
| [2] 重复决策 | 待拍板区表格里两两标题的关键词重合率 ≥0.5 | 🔴 **结构性永远绿**：判据从全文第一个「待拍板」三字开始取区块。而决策看板模板 §1 的说明行「状态枚举…`todo` 待拍板」**出现在 §3 待拍板表之前**，于是区块起点落在 §1 尾巴上，一直取到下一个二级标题为止。实测在模板正文上跑这段抽取：起点字符位 779、抽到的区块里**表格行数 0**；同一文件真实的 §3 表有 4 行。区块里没有行 → 两两比较无从发生 → 无论你怎么重复登记都是 OK。[实测] 另外三种绿：①两条**同号位不同主题**（`D-21` 被两个窗口各领一次）——`_is_role_cell` 甚至专门把 `D-`/`T-` 开头的单元格排除掉，全脚本没有任何一处比较 ID 列；②两条**同结论不同措辞**（都用近义词写"要不要连击"）——重合率 0，不报；③标题是短英文（如 `UI 2D or 3D`）——分词规则要求汉字≥2 或字母≥3，这种标题抽出的词元集合为空，代码直接 `continue` 跳过这一对 | 两条标题字面高度相近但其实是互补议题（"战斗手感调优目标" vs "战斗手感验收标准"）→ 过半重合即报警，需要人工确认（这一条是有意为之，见 9.3） |
| [3] 角色名漂移 | 信箱子文件夹 ↔ 契约 §1『成员与角色』表首列 | ①前置条件是**契约与 DECISIONS 两份都找到**才执行；`find` 只查根目录**一层**，治理文件被放进子目录（很常见的 `治理/DECISIONS.md`）→ 整项打"跳过"，还顺手让 [2][7] 一起失明；②契约按 §11 退役被改名成 `团队分工与协作契约_归档.md`，或项目用的是 `SKILL.md`「步骤 1」点名的变体名"公约" → 契约找不到 → 漂移检查永不运行。**注意**：两套纪律文件并存正是本 skill 警告的事故场景，而这恰恰是检查器瞎掉的时刻；③目录名硬编码为 `沟通`，改名（`Mailbox`／`信箱`）即整项静默通过 | ①按信箱说明.md §一 建议建了 `沟通/用户/` 信箱 → 人形关键词过滤**只作用在契约侧**，信箱侧原样入集合，于是「信箱文件夹「用户」未在契约§1 角色表列出」每次必报；②轻量档（单文件信箱）没有角色子文件夹 → 必报"角色无信箱文件夹"（已记 15.6 缺口 7） |
| [4] 信箱积压 | 信里出现 `状态:done` 或 `已处理` 就算处理过 | 🔴 **整份文件一个子串判据**：`投递.md` 模式下全文只要出现过"已处理"三个字（哪怕是收件箱 README 的说明句、或某封信正文里写"这事我已处理过三次"），**整本信箱**判为无积压，其余未读信全部隐形。实测逻辑演示：一段"这是技术美术的收件箱。处理完的信 mv 进 已处理/ 目录。" → 判为不积压。而 `SKILL.md`「步骤 3」正要求在每个 `沟通/<角色>/` 放一份说明用法的 README——**守规矩建的 README 里那句归档说明，替整个信箱把积压检查做绿了** | 反过来，信里写的是**全角冒号** `状态：done`（中文写作者的自然习惯）→ 判据是半角硬编码子串，匹配不到 → 这封信**永远被列为未处理**，实测演示为"flagged=True"。一个 `not in` 子串同时造出恒真与恒红两个方向，因为它比的是字符而不是字段 |
| [5] 看板漂移 | 表行第 3 列是 `blocked` | 正则要求 blocked 落在**特定列序**（任务、任务名、blocked）。看板列序按信箱说明 §二 是「任务ID｜任务｜owner｜状态」——`blocked` 在**第 4 列**；照模板建的看板，判据的第 3 列位置摆的是 owner → 抓不到 → 永远绿。[推演]（具体输入：把 12.1 的看板行原样写进 `状态看板.md`，跑脚本，[5] 打 OK） | 抓到 blocked 时它只提醒"请人工核对 DECISIONS §4"，本身**不判矛盾**（有意保守，见 15.6 缺口 6） |
| [6] 轻量信箱规模 | 二三级标题数 >20 **或** 总行数 >150 | 🔴 信件数按 `^#{2,3}` 标题行计数，而信箱说明.md §一 推荐的信件结构（`来源／日期／主题／正文／涉及文档与引用`）**一行标题都没有** → 标题数恒 0，20 条这条阈值**实际不可达**；只剩 150 行兜底。[推演]（具体输入：21 封按推荐格式写的短信、每封约 5 行、共约 110 行 → 既不到 20 条（判据读的是标题）也不到 150 行 → SKILL.md「规模自适应」要求"必须升级为标准模式"的场景，脚本一声不响。另：`>20` 是严格大于，正好 20 封也不报）；另外用 `####` 或粗体当信件分隔的项目同样恒 0 | **`SKILL.md`「规模自适应」明文写着"体检脚本 [6] 会报警"的那半条——"最早未处理信超过 7 天"——脚本里根本不存在**：全脚本唯一的时间解析只服务心跳判过期，没有任何一处读信件的 `日期：` 字段做差值比较。7 天阈值是纯人工纪律，却以"脚本会报警"的口气写在正文里。[实测：通读脚本七项实现，无日期比较路径] |
| [7] 决策规模 | 全文 `状态[:：]` 后接 approved 的出现次数 >30 | 数的是**全文出现次数**，不切活跃区/历史区/归档；反过来，把状态写成 `已生效`、`状态 = approved`（等号、带空格）都数不到 → 计数偏低，永远不到 30。[推演]（具体输入：40 条决策全用 `状态 = approved` 排版 → [7] 恒 OK，而 `SKILL.md`「决策压缩」的 30 条线早已越过）。文档里"每两周压缩一次"这半个触发条件同样无实现（脚本不记时间状态） | 若模板的说明句里出现一次 `状态：approved`（当前决策看板模板 §1 的 owner 行就带着一次），计数从第 0 天就虚高 1——小项目里 29 条真决策会被报成 30 附近，属可忽略的边界噪声 |

#### 9.8.3 一处需要更正的旧表述

本页 9.2 段写"时间解析接受『年-月-日 时:分』与纯『年-月-日』两种格式（纯日期锁按当日 0 点起算）"。更正：那第二个格式分支**永远走不到**——抓心跳的正则本身要求日期后面必须跟 `HH:MM`，只写日期的心跳根本不被认定为心跳，于是直接落进"无心跳"那条报警分支，压根轮不到时间解析。这条不影响使用，但影响你判断"只写日期的锁会怎样"：**它会红，不会绿**。[实测：抓心跳的正则与解析函数逐一对照]

#### 9.8.4 所以这份报告该怎么读（三条硬规矩）

1. **看见 0 先找"跳过"**：`结论：治理健康` 只有在**七项全部打印 OK**（而不是"跳过"）时才算证据。任何一项打了"跳过"，那次运行的含义是"有一维没查"，不能写进"体检通过"。[推演]——具体反例就是 9.8.1 的复跑 B。
2. **把 [1] 的计数先做减法**：报告里凡是锁体片段含 `EDIT_LOCK`、`<YYYY`、`--include=`、或来自 `references/契约模板.md`／`SKILL.md` 自身的，是示例噪声；只有指向你项目正文文件的那些才算数。
3. **验尺子比读尺子重要（变异检验）**：随手造一个"应该红"的样本，看它真红不红——加一把 `状态:wip` 且心跳写昨天中午的锁 → [1] 必须点名；把同一句待拍板标题在 §3 表里抄两行 → [2] 必须点名（按 9.8.2 的判据，它现在**不会**红，这就抓到了一把坏尺子）；造 25 封无标题信件 → [6] 必须点名（也不会红）。凡是"造了该红的样本它不红"，说明这一维是恒真，**这一维的检查结果一律不许当证据**。[推演]（方法本身来自本页对"探针＝只检查不改东西的脚本"的要求：探针要能被反证。）

## 第 10 章 失效与恢复：这套机制自己怎么坏、坏了怎么修

治理机制也会腐化。逐个列：故障模式 → 怎么发现 → 怎么退。

| # | 故障模式 | 发现方式 | 恢复动作 |
|---|---|---|---|
| 1 | **死锁**：加锁者会话崩了，`wip` 锁挂着 | 24h 后任何人的开工三查 grep 到旧锁；体检 [1] 直接点名 | 按 4.4 抢占：追加接管行、改心跳、继续改；原改动不明先协商留言 |
| 2 | **无心跳锁**：加了锁忘了续心跳 | 体检 [1] 专报「wip 锁但无心跳」 | 补心跳或改判过期；根因是没按五要素写全锁，回契约 §3 格式照抄 |
| 3 | **丢更新**：agent 读旧全文→整体重写，别人内容蒸发 | 对账（第 12.2 节实录）；若项目在 git 管理下，`git diff`（比较工作树与上次提交快照的命令）会显示大段消失行 | 找回被盖段落的底稿（对方窗口历史）重新纯追加；重申「绝不 `Write` 整体覆盖」 |
| 4 | **幽灵引用**：旧决策号还有人引用 | 别的 agent 开工说「依据 D-01」而活跃区查无 D-01 | 历史区一行指针给出去向；若历史区已被压缩归档，去 `DECISIONS_归档.md` 追 |
| 5 | **悬空引用**：抛弃型删除后冒出旧引用 | 有人照已删编号干活 | 说明删除前 grep 没做净（抛弃型第 1 步的前提被跳了）：补 grep 清引用，按新决策重开条目 |
| 6 | **两套纪律打架**：契约＋公约并存 | 步骤 1 扫描就该拦住；漏拦后发现两文件条款矛盾 | 重定向合并（SKILL.md 步骤 1 原文：「发出重定向说明让其一并入」），存续文件顶部标「原 X 已并入」 |
| 7 | **信箱积压/膨胀** | 体检 [4]（未处理计数）与 [6]（规模阈值） | 逐封按闭环三条件判定、mv 进已处理；超阈值就升级拆文件夹 |
| 8 | **角色名漂移** | 投递投进没人看的目录、体检 [3] | 以信箱文件夹名为权威统一三处（信箱说明.md 陷阱 5 明文） |
| 9 | **看板与真相源矛盾** | 体检 [5] 列出 blocked 行提醒人工核对 | 以 DECISIONS 为准改看板，或按契约 §5 顺序升级用户裁决 |
| 10 | **多宿主副本漂移** | 两宿主对同一纪律行为不一；历史上靠事后比对才发现（SKILL.md「副本落点」节事故注记） | 逐字同步＋sha256 校验＋各跑 quick_validate；先验明是否本就是同一文件的链接（CHANGELOG.md v1.3 实例：「另一份副本」实为同一文件链接、无需同步） |
| 11 | **开工三查第三查无命令** | 自己拼命令时愣住：正文只给意图没给命令 | 用 `grep -n "待拍板" DECISIONS.md` 之类补齐（已知缺口，见 15.6 缺口 1） |
| 12 | **体检节列举与脚本不同步** | SKILL.md「治理体检」节列 5 项、脚本实跑 7 项（[6][7] 系 v1.3 补，正文列举未回写；两检查在「规模自适应」「决策压缩」两节已被分别点名） | 以脚本 docstring 的 7 项清单为准，不影响执行（15.6 缺口 2） |

[实测：第 1~10 行各对应表内所引章节；第 11、12 行为本次通读六份文件对照发现的内伤，判据位置已逐行注明]

**失效规律的总括**：这套机制几乎不防「恶意」，它防的全是**遗忘、崩溃、不知情**三种善意事故。所以恢复动作一律是「留痕＋对账＋重贴」，而不是「回滚＋惩罚」。

## 第 11 章 例行维护：怎么验证它真在生效

### 11.1 定期体检节奏（大型模式）

- **频率**：至少随决策压缩节奏双周一次；项目出现「已经乱了」「文档互相矛盾」「谁改的忘了」时随时跑一次补救（这三句正是 SKILL.md frontmatter 的补救触发词）。
- **动作**：`python scripts/governance_check.py --root <项目根>`，读报告、清问题、再跑到 exit 0。
- **退役前**：治理退役第 5 步强制跑一次，确认无过期锁/未决决策残留，再封存。

[实测：SKILL.md「治理体检」「治理退役」两节；契约模板.md §11 第 4 步]

### 11.2 轻量档不跑脚本时的四个手动探针

轻量/标准模式可不跑脚本，但「不跑脚本」不等于「不检查」——四个手工 grep/ls 就是脚本的穷人版：[实测：SKILL.md「Agent 工具级执行指令」开工三查 ＋「决策压缩」段的脚本 [7] 计数法，以下为等价手替]

```bash
# 1) 全局有效锁（应只剩今天的）
grep -rn "EDIT_LOCK:.*状态:wip" --include="*.md" .

# 2) 活跃决策条数（数出来 >30 就该压缩）
grep -c "状态[:：] *approved" DECISIONS.md

# 3) 自己信箱根目录（只看根，不进已处理）
ls 沟通/<我的角色>/

# 4) 待拍板区是否被重复登记（同名/近名标题扫一遍）
grep -n "^| D-" DECISIONS.md
```

（若项目在 git 管理下：工作树＝磁盘上正在编辑的这份文件；索引＝暂存区里准备下次提交的快照；`git show HEAD:<文件路径>`＝取上次提交的底来看。都是只读命令，探针型动作。）

### 11.3 「机制真在生效」的三种证据

装完 skill 后怎么确认不是心理安慰？看三样东西在不在长：

1. **锁记录**：协作两周后，`grep` 应能看到历史锁被规范地加了又删（契约 §3 与 §4 铁律 4 的双用痕迹）；一次都没有＝要么没人跨区改动、要么纪律没被执行；
2. **拍板集中度**：用户新回答的问题应能在 `DECISIONS.md` 找到对应条目；用户「在对话里随口答的板」变少＝铁律 1 生效；
3. **信箱根目录大小**：稳定不涨（闭环信持续进 `已处理/`）；只涨不消＝归档纪律没跑，先去查信箱积压。

[推演——这三条判据是对「四条核心纪律」与归档规则的反向验证设计。具体什么输入会让它露馅：新 agent 加入两周、DECISIONS 待拍板区仍空，而用户已在三个对话里各答过一次同一类问题——说明铁律 1 没被执行，给该成员补 onboarding 检查单。]

### 11.4 退役与追溯

项目冻结/合并/移交时按五步有序退役（决策回灌→清退锁→契约封存→信箱归档→体检收尾），细节与归档命名见 15.1 表；**回灌**排在第一步的用意：让有效决策脱离「治理专用文件」进入 README/设计主文档/架构说明，后人不开治理目录也能读到真相。[实测：SKILL.md「治理退役（项目收尾）」五步]

### 11.5 可达性核对：正文引用的每个文件与每个章节，到底存不存在

「空门」＝规矩里让你去读/去跑的那个文件或那一节**根本不存在**。它比笔误危险：执行的一方顺着链接找不到东西时，通常的行为是"那这条大概是可选项"，于是**一条硬纪律静默降级成建议**，而全过程没有任何一方报错。核对法（两条通道各走一遍，别拿一次空搜索结果就断言"没有"）：先按文件名模式匹配递归列一遍全库，再用递归文件列举复核一遍总数；然后从正文里把所有 `references/…`、`scripts/…` 形式的链接与所有「§数字」形式的章节引用抓出来，逐条对回实际文件名与实际章节号。

2026-10-09 实测结果（两条通道给出同一个 7，递归文件总数＝`SKILL.md` + `README.md` + `CHANGELOG.md` + 3 个 references + 1 个 scripts）：

| 被引用的对象 | 出处 | 存不存在 | 判定 |
|---|---|---|---|
| `references/契约模板.md`、`references/决策看板模板.md`、`references/信箱说明.md` | `SKILL.md`「步骤 2」「决策生命周期」「参考资料」三处、契约 §8、README | **存在，文件名逐字一致** | ✅ 通路正常 |
| `scripts/governance_check.py` | `SKILL.md`「治理体检」「产出文件清单」「步骤 3」、契约 §10、信箱说明.md 两处 | **存在，逐字一致** | ✅ 通路正常 |

## 第 12 章 端到端走查：双窗口同改一本追加式台账

这是全页最重要的一章。场景取自真实高频事故：**轻量档项目，一本纯追加的共享台账（信箱），两个 agent 同时在写**。走查分正反两版：先走一遍按规矩的完整流程，再走一遍不守规矩怎么撞车、怎么发现、怎么恢复。所有命令可照抄；角色用甲、乙代称，宿主与路径全部抽象。

### 12.0 场景设定

**T2 14:02 甲写·第一步：加锁。** 在文件末尾追加锁标记行：

### 12.2 反面流程：不加锁的整体重写，撞车实录

同一起点（21 行、3 封信），两人偷懒：

**T1 14:01 甲**：读全文（21 行）→ 在脑内拼出「旧 3 封＋自己新段」的 27 行文本 → 14:07 用 `Write` 整文件覆盖落盘。**T2 14:03 乙**：几乎同时读全文——**读到的是 21 行的旧底**（甲 14:07 才写完）→ 乙拼出「旧 3 封＋自己的新段」共 26 行 → 14:09 整文件覆盖落盘。**后写的乙用 14:03 的旧底盖掉了甲 14:07 的成果**——甲的信从磁盘上凭空消失。这就是撞车的完整形态：没有任何一方「删过」甲的段落，它就是没了。

**怎么发现（14:10，甲交稿前对账自检）：**

```bash
grep -c "^## " 沟通/投递.md          # 实测 4，期望 5 —— 少了一段
grep -n "接线范围确认" 沟通/投递.md    # 命中 0 —— 我的信没了
wc -l 沟通/投递.md                    # 26 ≠ 33
```

若项目在 git 管理下再加一刀（`git diff` 直读工作树与上次提交快照的差异）：

```
- ## 10-09 @工程角色 接线范围确认：只接 3 个战斗信号     ← 消失行现形
```

**怎么恢复：**

1. 找回底稿——甲那段文字在甲自己的窗口历史里，本就是甲写的；
2. 甲**纯追加**回去（此刻先重读一遍确认 26 行是最新底，末尾加 6 行 → 32 行……注意：乙的段已在其中，不再动它）；
3. 重跑 T6 五判据（此时 32 行、5 段）全过；
4. **复盘归因**：事故根因不是「乙手贱」，而是①两个动作都走了「读全文→整体写回」的危险路径，②共享台账写入没走锁。契约 §3 若被遵守，T3 那步 grep 会让乙在 14:05 就停手。

**事故→规矩映射（本走查带出的三条军规）**：

| 教训 | 对应规矩 | 出处 |
|---|---|---|
| 追加型文件绝不整写 | 「日志只 append……绝不 `Write` 整体覆盖他人段落」 | 信箱说明.md「与记忆日志协同省 token」节 |
| 动共享文件先查锁再加锁 | 开工三查第 2 查＋五要素锁格式 | SKILL.md「Agent 工具级执行指令」；契约模板.md §3 |
| 写后对账用数字不用眼睛 | 段数/行数/命中数三判据 | 本章 T6；[推演] 原文只给了锁与归档规矩，对账清单是把它们拧成判据的补强 |

### 12.3 变体推演：如果甲加锁后崩了呢

T2 之后甲的会话 14:08 崩掉，锁挂着没撤。时间线：

- **14:09 乙查锁**：见 wip、心跳 14:02 → 未超 24h → **仍要退避**（宁可空等，不可并行）；
- **15:10 乙再查**：心跳 68 分钟前，仍未过期，继续退避；
- **次日 15:00（心跳后 >24h）**：锁过期 → 乙抢占：在原锁位置追加 `> 由乙于 2026-10-10 15:00 接管（原锁超时）`＋新心跳 → 检查甲有无半截内容（崩前甲只落了锁行、没写成正文段）→ 清掉孤立锁行、续写自己的段；
- 同一夜，体检脚本 [1] 也会把这把锁点名成「过期锁(心跳 …, 已 25h)」。

[推演——各时间节点取自契约模板.md §3「超时与抢占」与脚本常量 WIP_TIMEOUT=24h 的明文参数，场景构造为推演补全] 锁超时机制的意义就体现在这条时间线：**崩溃者不能永远占着文件，但活着者也拿不走还没过期的文件**。

### 12.4 变体推演：号位抢占——两窗同时领 `D-21`（本页要求点名的一类撞车）

> 号位＝编号位置，"下一个空号归谁"。这一类比覆盖写更阴：文件没坏、行数没少、没有锁被违反，坏的是**两个窗口各写了一行不同的内容、却共用同一个编号**，于是编号失去了寻址能力（"依据 D-21 开工"这句话不再指向唯一条目）。

同一起点：`DECISIONS.md` §3 待拍板表现有最大号 `D-20`，共 2 行待拍板。

| 步 | 甲（设计角色窗口） | 乙（工程角色窗口） | 此刻磁盘 |
|---|---|---|---|
| S1 14:00 | `grep -n "^| D-" DECISIONS.md` → 看到最大 D-20 | 同一命令，同样看到 D-20 | §3 有 D-18／D-19／D-20 |
| S2 14:01 | 判"下一个是 D-21"，起草 | 判"下一个是 D-21"，起草 | 无变化——**这一步没有任何独占动作**，两个人都在读同一个快照 |
| S3 14:02 | 把新行**纯追加**在表尾 | — | 出现第一个 D-21（甲的主题） |
| S4 14:03 | — | 也**纯追加**在表尾（它 14:00 读到的表尾已经过期，但它只追加、不覆盖，所以没伤到甲） | 出现**两个** D-21，内容不同 |
| S5 14:05 | 用户回一句"D-21 选 A" | 同一时刻用户回一句"D-21 选 B" | 两行都"已拍板"，答案相反 |

关键判断：**追加式写法在这里是对的**（乙没有吞掉甲的行，两行都在，第 12.2 节那种覆盖事故没有发生），但它只能保证"内容都在"，保证不了"编号唯一"。号位分配缺的是一个**原子的取号动作**（原子＝中间状态不给别人看见，要么全做完要么一点不做），而纯文本方案给不出原子。三道可行的补法，强度递增：

1. **取号即占号（最省）**：S3 落盘的不只是内容，先落一行**占位**（`| D-21 | （甲起草中，勿用） | — | 甲 | todo |`），落完立刻回读一次确认自己那行在、且 D-21 只有 1 行。别人 S2 的 grep 会看到 D-21 已被占，自然取 D-22。[推演]（失效输入：两窗在同一秒都完成占位写入——概率极低但非零；所以还要配第 3 步的反查。）
2. **号位带前缀，把命名空间切开**：各角色取自己前缀的号（`D-设计-07`／`D-工程-11`），从根上避免抢同一个号；代价是"用户拍板只看一个区"的整齐度受损。
3. **事后消解（本支现况唯一支持的路线）**：接受偶尔同号，靠 §5 冲突裁决顺序把矛盾升级给用户，然后把其中一条改号为 `D-21a` 或顺延 `D-22`，并在历史区留一行指针防幽灵引用。[实测：契约 §5 四条裁决顺序、`SKILL.md`「决策生命周期」替代型一行指针]

**体检脚本能不能看见这次事故？看不见。** [实测] 逐项核过：[2] 只比标题的关键词重合率、从不读 ID 列（辅助函数 `_is_role_cell` 甚至把 `D-`/`T-` 开头的单元格显式排除）；[7] 只数 `approved` 出现次数；没有任何一项做"编号重复"或"编号跳号"检查。所以这一维的结果**永远绿**（恒真判据），照 9.8.4 第 3 条的变异检验法：造两行同号的待拍板条目跑一次，脚本不红 → 当场证明这一维没尺子。

**最终产出形状（做对了应该长这样）**——两行都在、编号唯一、状态一致：

```
## 3. 待拍板决策
| ID   | 决策                     | 候选方案        | 负责人 | 状态     |
|------|--------------------------|---------------|--------|----------|
| D-18 | 主界面是否竖屏             | A竖 / B横      | 设计   | approved |
| D-19 | 存档粒度                 | A按关 / B按点  | 工程   | todo     |
| D-20 | 音效是否可关               | A可 / B不可    | 设计   | approved |
| D-21 | 战斗是否加连击             | A加 / B不加    | 甲     | todo     |   ← 甲的，占位在 S3 已生效
| D-22 | 信号接线范围先接 3 条还是 6 条 | A三 / B六  | 乙     | todo     |   ← 乙的，S2 看到 D-21 已占故顺延
```

### 12.5 变体推演：替换范围把邻居整行圈进去（吞行）

> 吞行＝你只想改自己那一行，但定位串里带上了**别人的整行**当上下文，写回时那一行被你的旧副本替换掉，于是整行消失或被打回旧值。追加式共享文件最容易中这一枪，因为里面的行**天生长得像**（同一张表二十行都是 `| … | todo |` 的形状），为了让匹配唯一，人的本能就是"多带两行上下文"。

现场（同一张 §3 表，D-20 那行属于设计角色、此刻正被设计窗口改成 `approved`）：

- 工程窗口要加一行 D-23。它的定位串写成「`| D-20 | 音效是否可关 | A可 / B不可 | 设计 | todo |` 这一整行」＋在后面插自己的行。
- 14:00 它读到 D-20 是 `todo`；14:04 设计窗口把 D-20 改成 `approved`；14:05 工程窗口落盘。
- 两种结局，都坏：**运气好**——定位串（含 todo 的 D-20 行）在今天的文件里已不存在 → 替换失败报错 → 被迫重读，虚惊一场；**运气差**——D-20 那行恰好没被改（改动发生在别处，比如只在这行下面插了一行）→ 定位成功 → 写回的字符串把 D-20 连同它下面的邻居一起按**14:00 的旧内容**落盘 → 别人 14:04 之后的成果整行蒸发，而工程窗口的日志显示"操作成功"。[推演]（这就是"别人的历史证据被邻居的替换范围吞掉"的完整机制）

**怎么写才不会伤到别人（唯一安全式）**：定位串里**一行别人的内容都不许出现**。要么在文件/表格末尾做纯追加（锚点取"我自己即将写出的那行"或"文件最后一段是我认得的空行/分隔线"），要么用"自己那行的整行文本"当锚点并在它下面插新行。判据很硬：**你写回的字节里，凡是别人的行，必须与你读到的字节逐字相同——最好是根本不写它。**

**改后逐行反查（可照抄，四条判据，成本 2 个工具轮次）**：[推演]——包内没有任何一节写过这套清单，它是本页根据"纯追加为什么比整份重写安全"倒推出来的最小验证动作；能成立的原因是**追加的写入集合只有新增行**，所以"有没有伤人"能从"整份文件两两对比"降级成几条便宜的数字检查（勾稽＝两处数字能对上）。

```bash
# 前置：动手前先存两个数（改前基线）
wc -l DECISIONS.md && grep -c "^| D-" DECISIONS.md

# 写完立刻反查
grep -c "连击" DECISIONS.md          # 判据1：我的关键串命中 1（>1 说明号位或主题撞了，回 12.4）
grep -c "音效是否可关" DECISIONS.md   # 判据2：邻居的关键串仍在（命中 1；命中 0 就是吞行了，立刻停手回滚）
wc -l DECISIONS.md                    # 判据3：行数增量 == 我这次加的行数（多了就是覆盖，少了就是吞）
grep -n "^| D-" DECISIONS.md          # 判据4：编号序列没有重复
```

判据 2 是这一套里唯一直接回答"**别人的行还在吗**"的动作，也是本支最缺的那一环：它不需要版本库、不需要锁、不需要通信，一次 grep 就够。反查发现的每一次"命中 0"都要当事故处理（停手、找回底稿、按 12.2 的恢复三步重贴），而不是"我再补一次写进去"——补写会把别人的历史证据变成你的记忆复述，细节一定会错。

**为什么这套动作比"整份重写"安全（原理，一句话）**：整份重写把安全性寄托在"我读到的那一刻到落盘的这几分钟里没人写过"这个**你自己无法验证**的前提上；纯追加＋逐行反查把安全性换成"我的写入集合不含别人的行"＋"落盘后逐条抽查仍在"这两个**你自己能证伪**的判据。这就是"幂等"（同一动作重复做，结果不变——追加做两次会多两行，所以先查后写让它回到幂等）在共享文件上的实际用法。

### 15.2 字段与枚举规范

- 决策状态枚举：**仅** `approved`／`todo`（活跃区）；失效走「出区」而非挂状态。执行认领态 `doing`/`done` 属 DECISIONS §0-2 与 §4 执行跟踪；看板态 `todo/doing/done/blocked` 属 L4。三套状态各管各的表，别互相套用。[实测：SKILL.md「状态枚举」；决策看板模板.md §0/§4；信箱说明.md「状态约定」]
- 信件标记：`状态:done` 或「已处理」字样**有一个**即被脚本认可——历史信件可以事后补标而不必重写（幂等：补标几次结果一样）。[实测：check_mailbox_backlog 判定串]
- blocked 必须注明：阻塞原因／等待谁；备注缺失的 blocked 在看板上等于哑弹。[实测：信箱说明.md 状态约定；SKILL.md「必须做的行为」]

### 15.3 多宿主副本同步纪律

装进多个 agent 宿主（宿主＝各个跑这个 skill 的程序环境）时：各 skills 目录放**逐字一致**副本；`name` 保持 `multi-agent-team-governance` 不变；任一副本改动 → 整体同步其余 → **sha256 逐字校验** → 各跑一次 `quick_validate.py`。事故注记：历史上发生过漏同步冷存档、靠后续比对才发现——所以校验是硬规矩不是建议。另案：v1.3 曾查明两宿主目录里的「另一份副本」实为**同一文件的链接**（指向同一份磁盘内容），无需同步——先验明是否同一文件、再决定要不要同步，避免把「本来同一份」误操作成分叉。[实测：SKILL.md「副本落点与维护须知」及注语；CHANGELOG.md v1.3「怎么解决的」末句]

### 15.4 冷启动与最小验证

- 安装：整目录复制到 skills 目录、重启即得（README.md「安装」节）。
- 冷启动首验：用**标准档**建三件套 → 手动演第 12 章走查 → `python scripts/governance_check.py --root .` 应 exit 0 且各项 OK/跳过合理；**轻量档不跑脚本**（设计如此），若跑会见 [3] 报「角色无信箱文件夹」的结构性误报——见 15.6 缺口 7 与 12.1 T7 的实例输出。
- 触发词面：description 的触发词覆盖正反两种开口（「建立协作机制」是建、「项目已经乱了」是修）；单 agent 普通项目、无需协作治理时**不触发**——别给独狼项目套三层治理。[实测：SKILL.md frontmatter description；README.md 门面对照]

### 15.5 安全与隐私红线（治理文件特有）

1. **治理文件全员明文可读**：`DECISIONS.md`、信箱、看板都在项目根目录里，对所有 agent 与任何翻目录的人可见——**不得把凭据/密钥写进任何治理文件**（结论字段写「密钥走环境变量注入」这类指路句即可，样例值一律 `<你的密钥>` 占位）。[推演——skill 原文未写此条，但「文档即会议记录」原则意味着所有写入都是广播；具体反例：把某个平台的 token 贴进信件「涉及文档与引用」栏，该 token 从此对项目所有读者、以及后续每一次上下文加载永久暴露]
2. **对话原文不入档**：回灌/登记写**结论**不写**聊天实录**，防止把个人化称呼、私密上下文固化进广播文件。[推演——与 §6.1 禁历史叙述同构：档案只留决策属性，不留人的痕迹]
3. **本手册的抽象纪律**：凡涉及队内代号、宿主名、盘符路径、记忆库结构，公开页一律抽象为「某个 agent」「某位队友的窗口」「某个宿主」「本机知识库」——公开仓库不留环境指纹。

### 15.7 工程纪律的元层：这套 skill 自己守的规矩
