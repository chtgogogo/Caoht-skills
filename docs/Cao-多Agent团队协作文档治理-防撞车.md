# Cao-多Agent团队协作文档治理（multi-agent-team-governance v1.2）

> [← 返回总目录](../README.md#skills-index)

## 一句话

让多个 AI Agent + 你本人协作一个项目时**不撞车、不重复追问、不原地死磕**：一套纯文档化的治理机制，不需要任何 Agent 之间的实时通信。

## 它解决什么问题

- 两个 Agent 同时改同一个文件，互相覆盖，谁改的都查不到；
- 用户被甲问完同一个问题，乙又来问一遍——每次都要重复回答；
- 某个 Agent 在自己的瓶颈上死磕，其他成员干等，整体进度失衡；
- 项目跑久了文档互相矛盾、决策被静默推翻，谁也不知道哪条还算数。

## 核心机制：三层治理（+可选第四层）

| 层 | 文件 | 解决什么 |
|---|---|---|
| L1 决策真相源 | `DECISIONS.md` | 所有待拍板/已拍板决策的唯一入口：用户拍板一次全员生效，告别重复追问 |
| L2 协作契约 | `团队分工与协作契约.md` | 角色表、文件 ownership、编辑锁规则、冲突裁决 |
| L3 异步信箱 | `沟通/<角色>/` | 跨 Agent 请求走投递，替代"开会拉群" |
| L4（可选） | `状态看板.md` | 谁在做哪条，进度不透明时上 |

**四条核心纪律**：
1. **编辑锁（带超时与抢占）**：改非自己主责文件先加锁，超 24h 无心跳他人可接管；
2. **统一决策入口**：需用户拍板的事禁止各自追问，登记进 DECISIONS 去重；
3. **信箱投递 + 闭环归档**：信件处理完移入 `已处理/`，巡检只看根目录省 token；
4. **交接原则**：卡住或判断他人更合适时，主动输出结构化"交接卡"建议用户切换会话，不原地死磕。

**进阶设计**：决策生命周期（approved/superseded/revoked，修订须重拍板 + 48h 回灌主文档）、新人 Onboarding 检查单、规模三档自适应（轻量/标准/大型）、治理体检脚本、项目收尾退役流程。

## 和同类方案比，差在哪

| 方案 | 问题 | 本 skill |
|---|---|---|
| 依赖 Agent 间实时通信/共享内存 | 大多数环境根本没有这些能力 | **纯文档化**，任何能读写文件的 Agent 都能用 |
| 共享文件夹但无规则 | 照样互相覆盖 | 编辑锁 + ownership 明确到文件 |
| 决策记在聊天记录里 | 推翻、追溯全靠考古 | 决策有生命周期状态与回灌责任人 |
| 流程一刀切 | 小项目被重流程拖垮 | 轻量模式只建两个文件 |

## 3 分钟上手

1. 复制文件夹到 skills 目录（见[总目录](../README.md#skills-index)）；
2. 对 Agent 说"给这个项目建多 Agent 协作治理"，它会先问清角色/规模/根目录再生成；
3. 项目已经乱了？说"帮我做一次治理体检"，它会先扫描已有的治理文件做合并补救，绝不推倒重建。

## 实战绩

提炼自真实跑通的天倾（Godot 游戏）多 Agent 协作项目：契约转正 v1.0、决策收敛到 D-01~D-20、信箱双向投递——机制经过长周期实战验证，不是纸面设计。v1.1/v1.2 的每个新特性（锁超时、决策撤销、交接卡）都对应一次真实事故。

## 适用 / 不适用

- ✅ 2 个以上 Agent 分工做同一个项目的任何场景（写书/做游戏/搞研究）；
- ✅ 项目已经混乱需要抢救的场景（补救流程内置）；
- ❌ 单 Agent 单线程任务——上这套是自我折磨。
