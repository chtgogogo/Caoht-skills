# Cao-多Agent团队协作（multi-agent-team-governance v1.2）

> [← 返回总目录](../README.md#skills-index)

## 一句话

给"多个 AI 角色 + 你本人"一起干活的项目，装一套纯文档的协作规则。不开会、不拉群、不依赖实时通信——因为大多数环境本来就没有实时通信。

## 它解决什么问题

- **两个人同时改同一处。** agent A 在改这个文件，agent B 也在改，后写的把先写的盖掉了。
- **你被反复追问同一件事。** 甲问一遍"这个字段叫什么"，乙又问一遍，你答了五次。真正该问一次的事，被问成了 N 次。
- **决策散落各处，说不清最终定的是什么。** 三份文档里对同一个接口有四种写法，谁也不知道哪个是准的。
- **某个成员卡在瓶颈上死磕。** 一个人啃一个啃不动的活，其他人闲着，整体进度被拖住。

## 核心机制

**三层治理文件。**

第一层是**决策真相源**（`DECISIONS.md`）——所有拍过板的事都记在这里，按编号排（D-01、D-02……）。任何文档跟它冲突，以它为准。第二层是**协作契约**，写清每个角色的职责范围、边界、以及四条纪律。第三层是**异步信箱**（`沟通/` 文件夹），角色之间需要传话时往对方信箱投一条，不靠实时对话。

**四条纪律。**

**编辑锁。** 动手改文件前先上锁，锁带超时和抢占机制——万一持有者挂了，别人可以抢过来，不会永久卡死。

**统一决策入口。** 需要用户拍板的事，统一在一个地方问，不各自去问。

**信箱投递。** 角色之间只通过信箱传话，各自读自己的信箱。

**交接原则。** 卡在瓶颈上不许死磕，写一张交接卡把活交给更合适的角色。

**决策是有生命周期的。** 决策可以被撤销、被修订，改动留痕，不是只增不改的日志堆。

**规模自适应。** 三个角色的小项目和十个角色的大项目，治理的厚度不一样，分轻量、标准、大型三档。

**治理体检。** 配一个脚本检查治理文件是否完整、有没有冲突，跑一遍就知道这套机制还在不在正常工作。

## 天倾项目里跑出来的东西

这套机制不是设计出来的，是打出来的。它提炼自一个真实的 Godot 游戏协作项目（天倾），那个项目里有 10 个 agent 角色加用户本人一起干活。

跑完之后留下的痕迹是实的（截至 2026-09-12）：

- 协作契约从 v0.1 提案走到 **v1.3 生效**
- 决策累积到 **D-01 ~ D-83**，83 条拍板记录，每条都能追溯到谁在什么时候拍板的
- 异步信箱累计 **225 封信**，分布在 10 个角色信箱里，双向投递不是单向摆设

**决策真相源长什么样。** 每条决策占一行、编号递增，文件顶部按时间挂一排编辑锁：

```
<!-- EDIT_LOCK: 游戏设计师 | 2026-07-28 | 新增 D-21 护甲系统 / D-22 召唤v1.5 | 状态:done -->
<!-- EDIT_LOCK: 技术美术   | 2026-08-10 | D-35 敌人占位换自研像素精灵 + PaletteSwap 染色 | 状态:done -->
<!-- EDIT_LOCK: ZCode      | 2026-09-11 | §1 追加 D-81（主理人九条拍板） | 状态:done -->
```

一行锁交代四件事：**谁**（游戏设计师）、**什么时候**（2026-07-28）、**动了什么**（新增 D-21/D-22）、**完没完**（done）。二十来条锁按时间排开，就是一部完整的改动史——不需要额外的 changelog，也不会有"这个改动谁做的"扯皮。

**信箱里的信长什么样。** 命名本身就是一条流水线：`<发件人>对<收件人>_<主题>_<日期>.md`，不用打开就能看懂。

一封发给用户的白话拍板信：

```
# ZCode 对主理人：D-49 §十一 五分叉拍板清单（白话选择题）

> 每题都是二选一/三选一，直接回「1A 2B…」即可，ZCode 落地。
> 每题附我的推荐与理由。

## 1️⃣ 注入偏向（S2）——花钱"指定下局更容易注入某个道种"

| 选项 | 含义 |
|---|---|
| A 不启用（推荐 ✅） | 开局注入保持纯随机。理由：方向性太强会压缩开局多样性…… |
| B 启用 | 花 30~50 灵骸买一次偏向（概率提升，非必带） |
```

形态本身就是答案：**把决策做成了选择题**。用户不需要读上下文、不需要写长句，回一句"1A 2B"就能拍板。这是"统一决策入口"纪律落地后的样子——所有要用户拍板的事汇总成一封，而不是十个 agent 各自来问一遍。

还有一封"交付信"，格式反过来——先给结论，再给证据，最后列诚实边界：

```
# 主理人信箱 · D-83 夜批交付信

> 结论先说：昨晚文档里设想的 166 张新卡……已全部落进游戏数据，
> 全部门禁绿灯，提交号 9ab68bf。你睡醒后直接开机试玩就行。

## 二、质量门证据（全部真跑，非"应该可以"）
- GATE2 全套：RUNALL_RESULT total=24 failed=0
- schema 严格门：SCHEMA_NODES=703 DANGLING_REFS=0
- 提交：工程仓 9ab68bf（207 文件，+9066 行）

## 三、你要知道的四件事（诚实边界）
1. 约 48 张是"休眠卡"：依赖还没造的引擎模块，效果要等模块落地才生效。
2. 条件卡触发条件暂记在描述里，现在可能偏强，试玩时别被吓到。
```

"诚实边界"这一节是整封信最值钱的地方——主动交代哪里还没做完，而不是报喜不报忧。配合"验证铁律"（不许自报通过，验证由用户独立确认），这套机制才真的可信。

**一次真实的同步事故。** 那套规则在多个宿主上各放一份副本，本来要求逐字一致。有一次只改了一处没同步冷存档，结果不同宿主上的行为开始不一致，靠事后比对才发现。这件事直接催生了现在的"副本同步"条款——规则里写明多宿主副本必须逐字校验。

**交接卡长什么样。** 卡住的时候不硬扛，写一张结构化的交接卡：

```
🔄 交接卡：[当前任务] -> [目标角色]
- 卡在哪：具体到文件和行，不写"做不下去"
- 试过什么：已尝试的路径，避免接手的人重复踩
- 建议下一步：为什么这个角色更适合接
- 需要什么：接手方需要的前置信息
```

卡写清了，接手的人五分钟能进入状态；写不清，交接就变成了二次踩坑。

## 和同类方案比，差在哪

| 常见做法 | 本 skill |
|---|---|
| 靠实时通信协调（大多数环境根本没有） | 纯文档化：真相源 + 契约 + 异步信箱 |
| 决策散在各文档，互相矛盾 | 单一决策真相源，编号排序，冲突以它为准 |
| 谁在改什么没人知道 | 编辑锁标记，带超时与抢占 |
| 用户被各个 agent 反复追问 | 统一决策入口，同一件事只问一次 |
| 卡住了硬扛 | 交接原则 + 结构化交接卡 |
| 决策只增不改 | 决策生命周期：可撤销、可修订、留痕 |
| 小项目也套重治理 | 轻量 / 标准 / 大型三档自适应 |
| 机制失效没人发现 | 治理体检脚本定期校验 |

## 3 分钟上手

1. 把文件夹放进 skills 目录（见[总目录](../README.md#skills-index)）；
2. 说"多个角色一起做项目""防止撞车""建立协作机制"之类的话触发；
3. 它会先用提问的方式收集信息（几个角色、项目规模、有没有已有文档），再生成三层治理骨架；
4. 生成前会先做一次防重复建设扫描——如果你已经有类似文档，它会在原有基础上补齐，而不是另起一套。

## 实战绩

提炼自真实跑通的多 agent 协作项目（天倾）：契约 v1.3 生效，决策累积 83 条，信箱收发 225 封、10 个角色信箱全部在用。v1.1 补进编辑锁超时抢占、决策生命周期、新人 onboarding、规模自适应、治理退役和体检脚本；v1.2 补进结构化交接卡、工具级指令、看板甘特图和 Windows 编码兼容。

上面那次冷存档漏同步事故、以及"决策只增不改导致翻不出最新版"的困扰，都是实战里撞出来的。

## 适用 / 不适用

- ✅ 多个 agent 角色协作的项目；用户本人也在其中拍板的项目；已经出现"文档互相矛盾""谁改的忘了"这类症状的项目
- ❌ 单 agent 的普通项目（一个人干活不需要这套治理）
