# 测试证据形态规范 · 完整详解手册

---

## 第 0 章 五分钟速览

1. **它不教「怎么写测试」，它规定「测试的证据长什么样才算数」**。正文开篇的定位句与「一句话」小节把这件事钉死：**跑不跑不是重点，能不能拿出原始输出才是重点**。
2. **五条铁律，缺一条就算「未验证」**（正文第一节标题逐字：「五条，缺一即视为未验证」）。五条分别管证据的**物质性**（落盘）、**因果性**（改前改后各跑一次）、**可追溯性**（指标必须能反查到某一行原始输出）、**诚实性**（改断言要分类声明）、**有效性**（回归测试必须能失败）。
3. **判据（可执行的判定标准——一条能被机器回答「通过／不通过」的规定）有两种白拿的假安全**：**恒真判据**（怎么写代码它都绿，永远不出事）和**恒红判据**（怎么改代码它都红，永远不能交差）。这两件事是第 7 章的全部内容，也是这套纪律最容易被外人忽略的一半。
4. **一条判据值不值得信，只看一个问题：什么输入会让它红？** 答不出来，它就是恒真的。第 7 章的 7.4 节给了能当场照做的六步检验法（指认对象 → 真源清点 → 三分类 → 改写 → 变异检验 → 留档）。
5. **数字必须成对出现**：改前一份、改后一份。只有「改后」那一份，只能证明「现在是这样」，证明不了「是这次改动让它变成这样的」。两份数字一样也算有效结论，但必须真的各跑过两次。
6. **别人（含另一个 AI）报的数字，一律索要输出文件**（正文第四节三条）。拿不到就标「未验证」——因为「AI 审 AI」有共享盲区，交叉核对不等于证据独立。
7. **验收口径一旦交付就锁死**：附属模板明确「skill 后续升级不追溯已归档项目」，理由是「中途换标准等于移动球门」。

一句话设计目标：**把「我试过了」变成「这里有一张别人能自己核对的单子」——并且保证这张单子上的每一条勾，都是一件真可能打叉的事。**

## 第 1 章 这套系统在解决什么问题

正文「版本」节把 v1.0 的起因写成三件同时发生的事，另加执行前的环境坑，凑成七类具体故障。**注意：这三件事的共同点不是「有人撒谎」，是「没人核对过」**——正文第四节结尾逐字：「两者都不是撒谎，是『没人核对过』」。

| 故障 | 表现 | 本 skill 的解法 |
|---|---|---|
| **① 归档复制改数** | 某次修复的「结果归档」，是把上一版结果文件复制一份、改掉里面一个数字，文件尾部还残留着旧的文件名 | 铁律 1（输出必须落盘＋禁止复制上一次结果冒充本次）；验收模板 T1 第三行（`diff` 两版＋看文件尾部残留） |
| **② 引用幻觉** | 一份安全审查报告引用了一个**根本不存在的提交号**（一串 7 位短哈希），没人当场核对过 | 铁律 3（每个数字要能追溯到某行原始输出）＋抗幻觉纪律「结论必须可证伪」 |
| **③ 空口总结** | 变更日志里写「全套件 396 passed」，但没有任何原始输出可查 | 铁律 1＋铁律 3；第四节「要求把输出重定向到文件并给出文件路径」 |
| **④ 假失败（环境缺件）** | 漏拷模型权重目录，2 个测试直接报错——错误信息说的是代码问题，真实原因是环境没备好 | 第二节「执行前三查」第 1 条，并要求把**跳过条数**写进报告 |
| **⑤ 并行互删** | 两个测试进程共用同一个测试数据库，互相删表，结果是 **37 failed**；把它们隔离开跑，**0 failed** | 第二节「执行前三查」第 2 条：先 `--collect-only` 只看收集不执行，再跑全量；共享库的套件禁止多进程并行 |
| **⑥ 副本缺目录** | 在代码副本里跑测试，但测试断言要读原仓库才有的前端目录（正文实例是断言 `web/src/**` 的测试），于是红——红的是被测路径，不是代码质量 | 第二节「执行前三查」第 3 条：确认被测代码引用的是**你要测的那一份** |
| **⑦ 断言悄悄变松** | 修复之后有断言从 `==` 被改成 `<=`，混在「口径同步更新」里一起报上去，看报告的人以为只是数字跟着改了 | 铁律 4：A 类（口径重算）与 B 类（断言弱化）必须分开声明，B 类要单独列出并给理由 |

**⑦ 和 ③ 是这套纪律里最值钱的两条**，因为它们对应的故障「看起来完全正常」：一份写满数字的报告、一条变松后永远绿的测试，都不会主动报错。**没有任何机制会替你说「这条测试已经没有意义了」**，所以必须把「证据长什么样」写成硬要求。

第 7 章会把「⑦」推到它的极端形态：一条恒真判据，就是**永远不会报错的测试**。

## 第 2 章 术语表（每个词后面一句大白话）

下面这些词，中文行话（某个圈子里的简称）也算术语，必须解释。表里的「位置」列指到具体文件与小节，不写行号。

| 术语 | 一句大白话 | 在本体系里的位置 |
|---|---|---|
| **判据** | 一条能被机器直接回答「过／不过」的规定，不是人写的感想 | 全篇核心；「铁律 5」、模板「第 0 节」都在判它 |
| **恒真判据** | 一把永远显示「合格」的尺子：代码写成什么样它都绿 | 本页对「铁律 5（回归测试要能失败）」的展开，见第 7 章 |
| **恒红判据** | 一把永远显示「不合格」的尺子：代码修得再好它也红，最后大家学会无视它 | 同上，第 7 章下半部 |
| **鉴别力** | 一条判据能不能把「对」和「错」分开；不能分开就是白给的 | 第 7 章 7.4 第 3 步「三分类」的核心判据 |
| **断言（assert）** | 测试代码里写的一句「这里必须等于 X」，一不等于就当场上报失败 | 铁律 4、铁律 5 的操作对象 |
| **红／绿** | 红＝这次测试失败了；绿＝这次测试通过了。来自终端输出的红字绿字 | 铁律 2 的「红-绿对照」 |
| **落盘** | 把东西真的写成硬盘上的一个文件，而不是只在对话里说一嘴 | 铁律 1 的关键词 |
| **转述** | 由人或 AI 口头复述一遍数字，没有留下原始文件 | 第四节专门防这个 |
| **孤儿数字** | 报告表格里有、但在任何原始输出文件里搜不到的那个数 | 模板 T3 的「零孤儿数字」 |
| **总体输出行** | 测试跑完后那行汇总，例如 `396 passed, 2 skipped, 0 failed in 167.44s` | 铁律 3 要求必须一起贴出来 |
| **skipped（跳过）** | 这条用例被合法地没跑（比如缺依赖就跳过）；它不算通过，也不算失败 | 三查第 1 条：跳过条数必须写进报告 |
| **回归（回归测试）** | 改完东西之后，把老用例重新跑一遍，确认没把已经好的地方碰坏 | 铁律 5 |
| **现状快照** | 一条测试只记录「今天是这样」，并不能证明「当初那个 bug 真的存在过」 | 铁律 5 要求的标注语；模板 T5 第二行 |
| **反向工程（断言值倒着抄）** | 先跑出结果，再把那个结果抄进断言里当期望值 | 「铁律 5」的 ⚠️ 警示，实例 `assert total == 40.0` |
| **口径重算（A 类改断言）** | 规则本身变了，期望值跟着按新规则重算 | 铁律 4 A 类；实例 60.0→56.25 |
| **断言弱化（B 类改断言）** | 把严的要求放松（`==` 改成 `<=`），好让新行为过关 | 铁律 4 B 类：「弱化不是错，藏起来才是」 |
| **幂等** | 同一件事重复做，结果不变；做十次和做一次一模一样 | 用于判据改写与复制检测，见 4.3 与第 13 章第 2 条 |
| **探针** | 只检查、不改动任何东西的小命令或小脚本 | 第 11 章体检清单全是探针型命令 |
| **变异测试** | 故意把代码改坏，看测试会不会红；不红就说明这条测试什么都没盯 | 第 7 章 7.4 第 5 步的检验手段 |
| **勾稽** | 两处数字能互相对上（比如改前改后的用例总数应该相等） | 第 11 章「总数守恒普查」 |
| **`--collect-only`** | 让测试工具只列出「我准备跑哪些用例」，一条都不真执行 | 三查第 2 条 |
| **diff** | 把两个文件逐行并排比，只把不一样的地方列出来 | 模板 T1、T4 的判定方法 |
| **grep** | 在一个文件里搜关键词，把命中的那几行拎出来 | 铁律 3 的反查手段、第 11 章普查手段 |
| **时间戳** | 文件「最后一次被写入」的时刻，操作系统自动记着 | 模板 T2「before 不是事后补造」靠它 |
| **提交（commit）** | 把当时代码的一个存档点登记进版本库，并拿到一串编号 | 模板 T2 用它和文件时间戳比对 |
| **退出码** | 命令跑完后系统偷偷留下的一个编号：0＝顺利，非 0＝出事了 | 第 7 章「空套件假绿」要用它，别只看有没有红字 |
| **空套件** | 一条用例都没被收集到，于是「0 failed」——看着最绿，实际什么都没测 | 第 7 章恒真形态之三 |
| **假失败** | 代码没问题，但因为环境缺件而报错 | 三查整节的目的 |
| **抖动（flaky）** | 同一段代码不变，测试有时绿有时红 | 第 10 章失效模式 G |
| **F1 / 命中率** | 命中率＝猜中的比例；F1＝把「猜中的准不准」和「该找到的找全没」合成一个 0 到 1 的分数 | 铁律 3 点名的指标类型 |
| **版本锚定** | 交付时用哪一版标准，就永久按那一版判，后来的新版不追溯 | 附属模板开头「版本锚定」段 |
| **可证伪** | 一个说法必须能指出「看到什么就算它错了」；指不出来就只是观点 | 与抗幻觉纪律共用；恒真判据正是「不可证伪的测试」 |
| **契约** | 双方交付时共同认可、事后不许单方改的规矩 | 模板用这个词解释为什么不追溯升级 |

## 第 3 章 结构与分层详解：八个层次各堵哪种漏

### 3.1 层次总表

数法说明：按正文的一级小节（`##` 标题）从上到下列，加附属模板共 **8 层**（L0–L7）。

| 层 | 在文件哪里 | 管什么 | 明确不管什么 | 为什么必须单独一层 |
|---|---|---|---|---|
| **L0 定位层** | 标题下开头的 blockquote（正文里以 `>` 起手的引用块） | 声明「不教怎么写测试，只规定证据长什么样」；给出「一句话」 | 不重复讲测试语法 | 防止读者把它当成测试工具教程读；同时声明它是抗幻觉准则「外部证据优先，形成验证闭环」的**执行细则** |
| **L1 铁律层** | 第一节「核心铁律（五条，缺一即视为未验证）」 | 证据本身的合格标准 | 不管该不该跑、什么时候跑 | 这一层是判「有没有验证」的唯一硬线，缺一即退回未验证 |
| **L2 前置层** | 第二节「执行前检查（三条，防环境假象）」 | 跑之前把环境钉牢 | 不管证据格式 | 因为环境没钉牢时，红的原因会指向错误的地方，后面所有证据都在解释一个假现象 |
| **L3 产出层** | 第三节「报告格式（模板）」 | 报告该有几段、每段填什么 | 不管项目管理流程 | 「能不能被复现」是判定标准，而模板就是为了让别人能复现 |
| **L4 通道层** | 第四节「对『AI 跑测试』的专门规定」（三条） | 由人或 AI 代跑时怎么索取证据 | 不假定 AI 会撒谎 | 转述一定会走样；这一层把「不信转述」写成流程而不是态度 |
| **L5 自查层** | 第五节「反模式清单（照这个自查）」（7 行） | 常见失效的自检 | 不解释新原理 | 每条都在前面章节有正向说法，这里只是「反面照一遍」 |
| **L6 边界层** | 第六节「与其它规则的边界」（4 行） | 哪些事不归本 skill 管 | 不越界抢活 | 没有边界层，同一件事会有两套规矩打架（例：该不该跑归编码纪律，跑完的证据归这里） |
| **L7 模板层** | 附属件 [验收模板-证据完整性.md](../A-Cao-测试纪律-测试证据形态规范/references/验收模板-证据完整性.md)，6 节共 **17 个勾选框** | 把 L1 的五条铁律变成能逐项打勾的验收表 | 不评价代码好不好 | 铁律是「道理」，模板是「动作」；数法见 3.4 |

### 3.2 每层的存在理由（挑四个关键的）

**L1 为什么是五条而不是三条或八条** `[推演]`：五条各自对应一种**独立可发生**的失效，彼此不能互相覆盖——落盘管「证据是否存在」，红绿对照管「因果是否成立」，总体输出行管「数字是否可追溯」，分类声明管「变更是否诚实」，能失败管「测试是否有意义」。前四条即使全做到，第五条不做，你仍然会得到一份**每个数字都有出处、但整条测试什么都没盯住**的报告。具体会出问题的输入：一次修复只跑前后两遍、两遍都绿、报告里贴齐了两行汇总——四条全过；而那条用来证明修复的新测试，期望值是修复后从实现里抄出来的，把实现改回坏的版本它照样绿。这就是第五条存在的唯一理由。

**L2 为什么放在「铁律」之后而不是最前面** `[推演]`：这一节开头逐字写的是「跑之前先过这三条，否则失败原因会指向错误的地方」——它按语义是「时间上最先」，但按重要性排在铁律之后，因为**读者要先知道什么算合格证据，才知道为什么要防假失败**。

**L4 为什么要单列「对 AI 的专门规定」** `[实测]`：正文这一节自己回答了：「**为什么单列这一条**：转述会走样」，并给了两个已发生实例（复制改数、引用不存在的提交号）。这一条对人也成立，但正文之所以点名 AI，是因为 AI 报出的数字**语法完美、格式规整、看起来比人更像有证据**，更容易被直接采信。

**L7 为什么必须有独立模板文件** `[实测]`：模板开头自称「本文件是验收模板」，用法是「把本文件喂给 AI Agent，让它逐节执行，每项给出『通过／阻断／不适用＋证据』」。铁律层是**陈述句**，验收层必须把它翻译成**动作**——这就是附属件存在的全部理由（它 5,168 字节，比正文的三分之一还多一点，因为它把每条铁律拆成了「判定方法」与「通过标准」两栏）。

### 3.3 判定顺序（别跳）

```
0. 这是不是一次「修复／优化／对比／对外声称」？        → 不是 → 本 skill 不介入（纯代码风格讨论不触发）
1. 环境三查（L2）过不过？                              → 不过 → 先修环境，别急着读红字
2. 证据有没有落盘文件？（铁律 1）                      → 没有 → 直接判未验证，后面不必看
3. 改前改后两份在不在？时间戳合不合理？（铁律 2）      → 只有一份 → 结论只能写「现状」，不能写「修好了」
4. 每个数字能不能在文件里搜到那一行？（铁律 3）        → 搜不到 → 该数字删掉或标未验证
5. 断言改动分没分类？B 类有没有单列理由？（铁律 4）    → 混报 → 视为「测试变松」未申报
6. 这条测试有没有在改前红过？（铁律 5）                → 没红过 → 必须标「现状快照，非回归证据」
7. 这条判据有没有鉴别力？（第 7 章六步）               → 恒真 → 改写判据，而不是接受这个绿
8. 对外声称前跑一遍 L7 的 17 项                        → 有阻断项 → 四选一处置，不许「先记着」
```

为什么这个顺序：**越靠前的越便宜**。第 2 步只要看一眼有没有文件路径；第 7 步要故意改坏代码再跑一遍。能在便宜的地方拦住的，就不要留到贵的地方。

### 3.4 附属模板的 17 项怎么数的

数法：只数模板各节**表格里的数据行**（每行末尾带 `☐` 勾选框），不数表头、不数小节标题。

### 3.5 什么时候进场（触发口径）

`[实测]` frontmatter 的 `description` 字段列了触发面：写测试、跑测试、改测试、评测集设计、指标汇报、A/B 对比、修复后验证，以及口头声称「更快了／更准了／修好了／跑过了」；用户说「跑个测试、验证一下、修好了吗、快了多少、准了多少、加个回归测试、这个指标可信吗」时触发。同一字段还写明：即使用户没说「跑个测试」，在四个下游场景（验收官、评审计划、交付流水线、五模板的交付纪律）里本纪律同样生效。

`[推演]` 反过来划边界：正文**没有**任何「何时可以放宽铁律」的条款（我把 SKILL.md 与附属模板全文读过，未检索到此类表述）。所以「随便跑个一次性脚本看看」能不能不落盘，只能这样判——**看这个数字会不会进任何给别人看的地方**。会进报告、进变更日志、进对外承诺，五条一条不免；纯粹自己瞄一眼、结论不落地成任何文字，才谈得上放宽。具体会出问题的输入：把「自己瞄一眼」的那次结果顺手写进周报——数字一进对外文本，它就已经是证据了，哪怕跑的时候没打算留。

## 第 4 章 铁律 1 与铁律 3：证据的物质性和可追溯性

这两条一起讲，因为它们是同一件事的两端：铁律 1 要求**证据必须是一个东西**，铁律 3 要求**每个数字都能回到那个东西里去**。

### 4.1 铁律 1 · 输出必须落盘

正文给的命令形状（原文照抄）：

```bash
python -m pytest tests -q > evidence/pytest_after_20260924.txt 2>&1
```

这条命令里每个零件都在做事，对完全没写过代码的人逐个拆开：

| 零件 | 大白话 |
|---|---|
| `python -m pytest` | 用 Python 自带的「测试执行官」去跑测试（pytest 是最常见的一个测试执行工具） |
| `tests` | 要跑的目录，里面装着一条条测试用例 |
| `-q` | 少打字：只要汇总，别把每一步的流水账都印出来 |
| `>` | 把本该印在屏幕上的字，改存成一个文件（这就是「落盘」） |
| `2>&1` | 把「报错专用通道」（术语叫 stderr，程序出错时走的那条通道）也一起塞进同一个文件。**没有这一段，最常见的失败信息恰好不在文件里** |
| `evidence/` | 专门放证据的目录名（正文用的就是这个名） |
| `pytest_after_20260924` | 文件名三段式：`<工具>_<阶段>_<日期>`，阶段取 before／after |

**为什么文件名里必须带日期** `[实测]`：因为「沿用哪一次」必须能被写清楚。正文禁止句逐字：「**禁止**把上一次的结果文件复制成这一次的（哪怕数字本该相同）——要么重跑，要么在报告里明说『沿用 X 月 X 日的结果，本次未重跑』」。要能明说，前提就是文件名自己带着日期。

**为什么日期是 20260924 这种 8 位紧凑数字** `[推演]`：三个理由，都能当场验证——① 目录里按名字排序就是按时间排序（`20261009` 一定排在 `20260924` 后面），带分隔符或写成「9月24日」就排不对；② 没有 `.` `/` `-` 就不会和文件扩展名、路径分隔符混在一起；③ `grep 20260924` 一次搜到所有相关证据，写「9/24」会同时命中日期、比例、版本号，噪音大。具体会出问题的输入：一个目录里同时有 `after_9-24.txt`、`after_2026-9-24.txt`、`after_sept.txt` 三种命名，第三次归档时没人知道哪份是「上一次」。

**报告里写的是路径，不是转录的数字**：这句是铁律 1 的核心。差别在于——写数字，别人只能信你；写路径，别人可以自己去开那个文件。正文的判定标准（第三节末）把这一点说成了一个问题：**别人拿着这份报告，不看你的代码、只听你的话，能不能自己复现出同样的数字？不能 → 证据不合格。**

### 4.2 铁律 3 · 报指标必须给总体输出行

要求（正文逐字要点）：报百分比／命中率／F1，必须同时贴出产生它的原始汇总行，例如：

```
396 passed, 2 skipped, 0 failed in 167.44s
```

**为什么连 `2 skipped` 和 `167.44s` 都要一起抄** `[推演]`：这两个看起来最没用的字段，恰好是唯一能识破两种假绿的东西。

- `skipped`（跳过的条数）暴露**分母被动过**。若某轮有 2 条合法跳过、用例总数 398，真实通过率是 396/398 ≈ 99.5%；如果有人只报「396 passed」而把分母按 396 算，通过率就变成 100%，而这一个百分点是白拿的。具体会出问题的输入：把缺依赖的 2 条改成 skip，「全过了」这句话依然成立。
- 耗时暴露**到底跑没跑**。167.44 秒说明真跑了；如果那行是 `no tests ran in 0.01s`（一条用例都没收集到），那「0 failed」是最危险的绿——它同时是「什么都没测」和「什么都没测出问题」。第 7 章把它列为恒真形态之三。

**表格里每个数字要能追溯到某一行原始输出**：这条在模板 T3 里被写成了两个可执行动作——「逐个数字反查产生它的原始汇总行」与「表格数字逐一在落盘文件中定位」，通过标准是「**零孤儿数字**」。可操作化写法：

```bash
# 把报告里出现的数字逐个回搜到证据文件；搜不到的就是孤儿
grep -n "396" evidence/pytest_after_20260924.txt
grep -n "167.44" evidence/pytest_after_20260924.txt
```

`-n` 是把命中的行号也印出来，方便验收者现场指认（这是**一次性线索**，不是长期引用，与页眉的引用纪律不冲突）。

### 4.3 这两条合起来防的是什么

防的不是懒，是**转述的自我实现**。一旦「跑完了，全过了」这种话被接受过一次，下一次汇报的成本就变成零，因为不需要生成任何东西。落盘要求把成本固定在「必须真的跑一次并留下文件」上——这也是**幂等**（重复做结果不变）在这里的意义：同一份报告如果被要求重做，重做的产物应当是一份新文件，而不是一次复制。复制出来的文件在「数字层面」是幂等的（看起来一模一样），在「来源层面」是致命的（它没有对应任何一次执行）——第 13 章第 2 条就是专门抓这个。

## 第 5 章 铁律 2：改前改后各跑一次（红-绿对照）

### 5.1 为什么是「两份」而不是「跑很多次取平均」

正文表格的分工写得很清楚：

| 阶段 | 要求 | 作用 |
|---|---|---|
| 改之前 | 跑一次，存 `*_before_<date>.txt` | 证明**问题真实存在**（红） |
| 改之后 | 跑一次，存 `*_after_<date>.txt` | 证明**改动确实生效**（绿） |

`[推演]` 铁律 2 要解决的是**因果**问题，不是**精度**问题。「396 条通过」是一个精度陈述；「从 2 failed 变成 0 failed」才是一个因果陈述。多次重复只提升精度，一次都不提升因果；只有「改动前会红」这个观察，才能把「问题曾经存在」钉住。所以这里规定的是 2 份，而不是 3 次取平均。反过来说，如果同一份改动跑了两遍结果不一样（抖动），铁律 2 的两份文件会直接把这个矛盾暴露出来——这也是为什么必须是两份不同时间戳的文件。

### 5.2 「两份数字完全相同」是有效结论

正文逐字：「两份数字**完全相同也是有效结论**（说明该改动不影响这条路径），但**必须真的跑过**才能这么说。」

这句话的锋利之处在于它同时给了**出口**和**门槛** `[推演]`：允许你写「没变化」，但要求你**为「没变化」也付出两次运行的成本**。为什么专门要提这个情形：因为「改了但没效果」是人最不愿意报告的结果，最常见的偷懒方式就是「既然预期相同，那就沿用上一次的文件」。门槛把这条路的成本抬到和真跑一样高。

模板 T2 第三行为它配了具体核查：「两份数字相同时的处理——相同也算通过，但确认两份都是真跑（时间戳不同）／**未用同一份文件冒充两次运行**」。

### 5.3 before 文件能不能事后补造

模板 T2 第二行给的方法：「比对 before 文件时间戳与修复提交的时间（`git log -1 --format=%ci <修复提交>`）」，通过标准是「**before 时间早于修复提交**」。

`[实测]` 这是整套设计里少数带「防作弊」味道的一条，它防的动作很具体：改完代码、跑一次全绿，然后**倒回去**在旧代码上补跑一次、存成 before 文件。补造出来的 before 往往只会有一种形状——它是绿的，而真正的 before 应该是红的。所以核对时间戳，实质是在核对「红这件事发生的时间」早于「修」这个动作。

`[推演]` 一个更省力的替代核对（本页建议，正文没有写）：真正的 before 里必须包含**修复对象的失败签名**——具体到那条测试的名字出现在失败列表里。事后补造的人补的时候「他已经修好了」，很可能整份都是绿的。所以在报告里要求 before 那一段**必须写出失败项的名字**（正文模板正是这么写的：「（失败项：test_A, test_B）」），是一个成本极低的防伪设计。

### 5.4 只有 after 一份时，你的结论只能写成什么样

`[实测]` 正文给了唯一的合法写法：只有「改后」一份 → **无法证明改动解决了问题**，只能证明「现在是这样」。落到文字上，合法句式是「当前状态为 396 通过」；非法句式是「已修复」。这条区别看起来像咬文嚼字，但它是对外承诺的分界线：**「已修复」是一个可证伪的因果主张，「当前是这样」只是一个观察**。前者需要两份证据，后者只需要一份。

## 第 6 章 铁律 4：改断言必须分类声明（A 类与 B 类）

### 6.1 两类的定义与要求（正文表格逐字口径）

| 类型 | 含义 | 要求 |
|---|---|---|
| **A · 口径重算** | 行为语义变了，期望值按新语义同步更新 | 说明「哪条语义变了 → 期望值从多少改到多少」 |
| **B · 断言弱化** | 把强断言放松（如 `==` 改 `<=`）以适配新行为 | **必须单独列出并给理由**，不得混在 A 里一笔带过 |

正文实例（第三节报告模板里）：

- A 类：`test_x: 60.0→56.25`，语义说明是「中性分不再进分子」。
- B 类：`test_y：total == raw×k → total <= raw×k`，理由必须自己写。

### 6.2 为什么「弱化」和「重算」必须分开报

`[推演]` 两者的**风险方向不同**。A 类改的是数字，风险是「改错了」；B 类改的是**判定的强度**，风险是「以后再也抓不到这类错」。一份把两者混在一起、只写「同步更新 4 处期望值」的报告，看的人无法知道其中有一处从「必须相等」放松成「不超过」。**放松之后测试永远绿，但它已经没有能力抓到超出上限的回归**。具体会出问题的输入：后来引入一个真 bug，让 `total` 变成 `raw×k×2`（明显超了），但因为断言已经是 `<=`，而且分母算法也同时错了，这条测试照样绿——而报告里没有任何一处写着「这条断言以前是等号」。

`[实测]` 正文对这件事的态度写在那句加粗的判词里：**「弱化断言本身不是错，藏起来才是。」** 并把主动申报定义为专业动作：「主动写明『我把等式断言降级为不等式，因为……』是专业动作」。这是这套纪律里少见的「不禁止、只强制公开」的设计——因为断言弱化有时确实是对的（新行为允许一个区间时，等号断言就必须降级），禁止它只会把人推向偷偷改。

### 6.3 B 类的三个高危信号（本页补充，标 `[推演]`）

1. **比较符变松**：`==` → `<=`／`>=` → `>` → `!=`；`in`（属于某个候选列表）的候选列表被扩大。模板 T4 第三行「重点盯比较符变松的改动」就是这条。
2. **容差变大**：`abs(a-b) < 0.01` 改成 `< 1`。这在浮点数（带小数点的数，算出来天生有一丁点误差）计算里最常见，也最难看出。
3. **删断言而不是改断言**：正文没有为它单列一类，本页把它当作 **B 类的极端形态**处理（删掉一条断言＝把该项要求放松到「完全不管」），必须照样申报 `[推演]`。具体会出问题的输入：一次重构里「顺手清理」了 6 处断言，报告的 A 类写了 3 处口径重算、B 类写 0 处——因为删除没被归进 B 类，于是它在报告里消失了。**注意：这一归类是本页的解释，正文口径里没有单列「删断言」，这是本页主动补的，不是原规则。**

### 6.4 怎么让 diff 替你说话

模板 T4 第一行的判定方法：`git diff <修复前> <修复后> -- '**/test*'`，通过标准是「报告所列与实际 diff 一致」。这是一条**双向核对**：报告说的 diff 里要有，diff 里的报告都要说到。只有前者时，漏报不会被发现；只有后者时，多报（声称改了其实没改）不会被发现。`'**/test*'` 这个匹配写法的作用是把所有子目录下的测试文件都圈进来，避免藏在深层目录里的测试文件被漏看。

## 第 7 章 铁律 5：回归测试要能失败——恒真判据与恒红判据

这一章是全支 skill 的灵魂。铁律 5 只有两句要求，但它把「测试有没有意义」这件事第一次变成了可判定的东西。

### 7.1 铁律 5 的原文要求

正文逐字：新增的测试，如果是用来证明「某个 bug 已修复」，必须能回答：**修复前它会红吗？**

- **能**：在改前那份输出里指出它（红）→ 这才是**回归证据**。
- **不能／未验证**：必须在报告里标注「**本次测试是现状快照，非回归证据**」。
- ⚠️ **警惕反向工程**：先跑出结果、再把结果抄进断言（`assert total == 40.0` 里的 `40.0` 就是跑出来的），这种测试**只能防止未来改坏，不能证明当初修对了**。要区分「它现在通过」和「它曾经失败」。

把这三行翻译成一句最朴素的话：**一条永远不会红的测试，等于一句永远不会被推翻的话——它什么也没说。**

### 7.2 恒真判据：怎么写都永远绿

**大白话定义**：一把电子秤，你放砖头它显示「合格」，放砝码它显示「合格」，什么都不放它还是显示「合格」。它称的不是重量，是「有没有东西摆在那儿」。

下面五型覆盖了绝大多数恒真判据。每型给「看起来像什么」和「为什么它永远绿」。`[推演]`（这是本页对铁律 5 的展开分类，正文没有分这五型；每型的「什么输入能让它红」统一在 7.4 给方法）。

**型一 · 存在型**：只问「有没有」，不问「对不对」。

```python
assert result is not None          # 函数返回任何鬼东西都绿
assert len(items) >= 0             # 长度永远 >= 0，这句在字面上就是恒真
assert os.path.exists("report.md") # 文件里只写一行垃圾也绿
assert "登录" in html              # 那两个字在页面的隐藏模板里本来就有
```

**型二 · 否定型（最危险）**：只问「没出事」。它的致命之处在于：**「零命中」有两种完全不同的解释——真的干净，或者尺子根本没伸进去。** 这两种解释在输出上一模一样，肉眼无法分辨。

```bash
# 判据：日志里错误关键字必须为 0 条
grep -c "ERROR" app.log        # 日志路径写错 -> 命令本身在报错，但你只看那个数字 -> 0 -> 绿

# 判据：HTTP 服务活着就算通
curl -s -o /dev/null -w "%{http_code}" "<你本机服务的基础地址>/"
# 200 只证明"有人接了这个请求并回了话"；回的是空壳页、是错误页，照样 200
```

**型三 · 空转型**：判据根本没被执行，却表现为「通过」。

```python
def check_total_is_right():   # 函数名不是 test_ 开头 -> 测试执行官根本不收集它，断言永远不被执行
    assert total == 60.0
```

```bash
python -m pytest tests -q     # 目录名拼成 tesst -> 输出 "no tests ran in 0.01s"
                              # 若判据写成"输出里没有 failed 字样" -> 永远绿
```

这就是为什么 4.2 强调**耗时字段必须一起抄进报告**：0.01 秒和 167.44 秒是两个世界。**退出码（命令跑完后系统偷偷留下的编号，0＝顺利，非 0＝出事）也要一起看**：只搜红字、不看退出码，就会把「什么都没跑成」读成「全过了」。

**型四 · 同义反复型**：用被测对象自己当期望值。

```python
assert add(2, 3) == add(2, 3)                 # 永远真，哪怕 add 返回 0
assert get_score() == expected_from_same_code # 期望值也是从同一份实现算出来的
```

铁律 5 点名的「反向工程」就是这个型的温和版本：**期望值不是从规格推出来的，是从跑出来的结果抄回来的**（`assert total == 40.0` 里的 40.0）。它不是假的，只是**它没有能力在它要防的那件事上变红**。

**型五 · 边界过松型**：区间宽到包含了所有可能的值。`assert total <= 10000`（真值永远远小于它）、`assert status in ["ok", "error", "unknown"]`（候选就是全部可能）、`assert score > 0`（合法下限本该是 60）。

### 7.3 恒红判据：怎么写都永远红

**大白话定义**：门禁规定「刷卡后屏幕上必须显示 1999 年 1 月 1 日」才算通过。这个条件永远不满足，于是全公司开始翻窗。到第三天，没有人再看屏幕上的红灯了——**红灯不再是一个信号，而是噪音。**

恒红的危害和恒真正相反：恒真是**假安全**（把没验证的说成验证过了），恒红是**毁掉整个判据体系的可信度**，并且会诱发一个具体事故——见 7.5。

五个型（同样 `[推演]`，每型说清「为什么它绿不了」）：

**型一 · 尺子本身写错**：条件不可能被满足，或者满足它的方式根本不存在。

- 用**目录／文件的数量**去判「结构齐全」：判据写成「根目录下必须有 4 个库目录」，可后来新增了一个库变成 5 个，或者其中一个改了名字——于是它恒红，而代码质量一点没变。**按数量判齐全，是恒红最常见的诞生方式**：数量是「实现细节」，会随手变；齐全是「语义要求」，不该变。正确写法是把它换成语义式点名：「下列每一个**应当存在**的库目录，都必须存在且非空」——从「数几个」改成「点名要哪些」。
- 浮点直接比相等：`assert score == 0.1 + 0.2` → 右边算出来是 0.30000000000000004，永远不等于 0.3。代码改一万遍它都红。合法写法是比容差（`abs(a-b) < 0.000001`）。
- 把「今天」硬编码进判据：期望文件名必须是 `report_20260924.txt`。第二天起恒红。
- 大小写与路径分隔符：在文件名不区分大小写的系统上写成区分大小写的判据，或用 `\` 去匹配已被规范化成 `/` 的记录，同属这一型。

**型二 · 环境缺失型（＝正文三查第 1 条的假失败）**：`[实测]` 正文实例——漏拷 `models/weights/`（模型权重目录）导致 2 个测试假失败，补上后全过。外部服务没起、固定测试图不在、数据库连不上，判据就恒红，**而红字说的是代码的错**。这是恒红里最贵的一型，因为它会把人引去改本来正确的代码。

**型三 · 目标移动型**：期望值锚死在历史快照上。`assert 收集到的用例数 == 396`。套件是活的，加一条新测试它就红。它不是抓 bug 的判据，是「不许成长」的判据。

**型四 · 把合法状态判死**：合法的 skip 被判成失败（`assert case.outcome == "passed"` 一遇到跳过就红）；或者一个允许两种正确表述的结果，判据只认其中一种。

**型五 · 副本缺层型**：`[实测]` 正文三查第 3 条的实例——在副本目录里跑，但断言要读 `web/src/**`，而副本里根本没拷这一层，于是恒红。红的不是代码，是**你测错了对象**。

### 7.4 可操作方法：一条判据在什么输入下会红

这是本章要交付的东西——不是「要写好测试」这句口号，而是**当场能做的动作**。核心只有一句话：

> **给出一条判据，同时必须给出一个具体的输入，使得把这个输入喂进去它会红。**
> 给不出来 → 恒真，改写它。
> 给出来的是「任何输入都红」 → 恒红，先审尺子，别改代码。

`[推演]` 下面六步是本页把铁律 5 展开成的操作规程（正文给了「修复前它会红吗」这一个问题，没有分步；分步、三分类问句与「正例校验」是本页补充，标为推演，但每一步都可当场执行，不需要额外工具）。

**第 0 步｜先确认它真的跑了。** 看三样：收集到的用例数 > 0、输出里有具体测试名字、总耗时不是 0.01 秒那种量级。任一样不对，先别讨论判据——**你现在评估的是一个不存在的测试。**

**第 1 步｜指认被断言对象，填这个空：**

> 「如果 ______ 变了，这一条就会红。」

填不出、或填进去的是「如果程序崩了」→ 恒真嫌疑。注意填空的内容必须是**语义**（中性分被算进分子了）而不是**实现细节**（某个变量名改了）。

**第 2 步｜到真源实地清点，不要凭记忆。** 「应当是多少」必须从权威来源（需求文档、接口约定、实际目录清单）取出来，而不是「我记得是 4 个库」。模板第 0 节 0.2 的「收集数与报告一致」、T1 的「确认路径真实存在」，都是这一步的具体化。

**第 3 步｜三分类落位。用两个问句，答案只有是／否：**

- 问句 A：**把实现故意改坏，它会不会红？** 不会 → 恒真。
- 问句 B：**喂一个明显正确的输入，它会不会绿？** 不会 → 恒红。
- 两个都会 → **有鉴别力**，这才是可用判据。

（这两个问句就是「鉴别力」的可执行定义，也是本章全部内容的压缩版。）

**第 4 步｜按型改写。**

| 现型 | 改写方向 | 改写后长什么样 |
|---|---|---|
| 存在型 | 从「有没有」升级到「是什么」 | `assert result is not None` → `assert result.total == 56.25 and result.count == 4` |
| 否定型 | **配一次正例校验**（见下） | 「日志里 0 条 ERROR」必须同一轮里先证明这条命令能在一份故意含 ERROR 的样本上命中 ≥1；命不中则本轮记红、拒绝给绿 |
| 空转型 | 判据改成读退出码＋收集数 | 「输出里无 failed」→「退出码为 0 **且** 收集数等于报告的数」 |
| 同义反复型 | 期望值换成独立来源 | 40.0 必须由手算或规格推出，并在注释里写清算式；否则明写「这是快照断言」 |
| 边界过松型 | 收窄到规格给的合法区间 | `<= 10000` → `== 56.25`；`> 0` → `>= 60 且 <= 100` |
| 数量型恒红 | 「数几个」改成「点名要哪些」 | 「有 4 个库目录」→「下列 4 个具名目录逐一存在且非空」 |

**否定型为什么要正例校验**：因为它的问题是「零」的两种解释不可区分。唯一可靠的区分办法是**在同一轮里造一个非零**：准备一个已知含 3 条 ERROR 的小样本，对同一条命令跑一遍，必须报 3。报 0 就说明这条命令本身处在坏的状态——于是这一轮的「0」不许当绿。**这条规则把「恒真的绿」变成了「必须红一次的绿」**，是防假通过最省力的机制。

**第 5 步｜变异检验（mutation test，故意把代码改坏，看测试会不会红）。** 三个标准靶子，任何一条真实判据都能套：

1. **语义靶**：把被修的那个规则原样改回去（把「中性分不进分子」改回「进分子」）。有鉴别力的测试必须红。全绿 → 这批测试什么都没盯住这次修复。
2. **常数靶**：把一个不该动的数字挪一格（分母 16 → 15）。相关数值断言应当红。
3. **自证靶**：把断言里的期望值改一格（`== 56.25` → `== 56.24`）。**这条必须红**——如果它不红，说明这条断言压根没被执行（回到第 0 步的空转型）。

每次变异都要**落盘一份输出**（改坏→跑→存文件→复原→再跑确认回到基线），因为这本身就是一次铁律 2 的红绿对照；**变异检验自己不留证据，它和它要审的东西会犯同一个错。**

**第 6 步｜留档一句话。** 在测试文件旁边（或验收报告里）写下：「本条判据在 ______ 输入下会红」。下一个读者因此不必重推。**这一句是整套纪律里唯一直接生成「知识」的动作**，前面五步都在防止假知识进入记录。

### 7.5 恒红的正确处理顺序（以及它为什么会出事故）

`[推演]` 一条恒红判据的第一次处置，几乎总是「删掉它」——这常常是对的。事故发生在删的过程中：**恒红判据旁边往往就挂着一条有鉴别力的判据，而人是在同一屏红字里做取舍的，于是顺手一起删。** 具体会出问题的输入：某个测试文件里有 4 条断言，1 条因路径写错而恒红，另 3 条健康；为了让套件变绿，整条测试被注释掉。之后半年里那 3 条所防的回归再也没被抓到过，而「0 failed」的历史曲线看起来前所未有地干净。

所以恒红的处置顺序应当是：

```
① 先审尺子（第 2 步的真源清点：「应当」是不是取错了）
② 再审环境（正文三查：缺件、并行、副本路径）
③ 造一个「应当绿」的最小输入，看能不能让它绿
④ 造不出来＝判据本身错 → 改判据；能绿＝判据没错 → 是你现在喂进去的东西不对
⑤ 只改那一条，绝不清空整个测试文件
```

第 ③ 步是关键自证：**如果你无法为一条判据构造出「它能绿」的场景，它恒红；如果你无法构造出「它能红」的场景，它恒真。** 这两句话合起来就是本章的全部。

## 第 8 章 执行前三查与 AI 通道：红的原因可能不在代码里

### 8.1 三查（正文第二节表格逐字口径）

| # | 检查 | 为什么 | 三查在防哪一种恒红 |
|---|---|---|---|
| 1 | **外部依赖是否就位**：模型权重／固定测试图／数据库／外部服务 | 缺它们会产出**假失败**；若缺失需跳过，把**跳过条数**写进报告 | 型二（环境缺失型）——实例：漏拷权重目录 → 2 个测试假失败 |
| 2 | **套件能否独立跑**：先 `--collect-only` 确认收集数，再跑全量 | 共享测试库的套件**禁止多进程并行** | 型二＋互扰——实例：两个测试进程互删库，37 failed vs 隔离 0 failed |
| 3 | **路径是否隔离**：在副本里跑时，确认被测代码引用的是**你要测的那份** | 副本缺目录会导致「读源码」类测试失败 | 型五（副本缺层型）——实例：断言 `web/src/**` 的测试在缺该目录的副本上恒红 |

`[推演]` 三查的真实职能不是「保证成功」，而是**保证红字有意义**。三查不过时，一条红字既可能来自代码缺陷也可能来自环境缺陷，于是它不再是判据——这时连「恒红」都算不上，因为**连尺子在哪都不确定**。这也解释了为什么三查排在铁律之前跑（见 3.3 判定顺序第 1 步）：它是给判据通电。

为什么恰好三条 `[实测]`：三查对应的正是「失败原因会指向错误的地方」的三个来源——**外部世界缺件、并发互相污染、测了错的目录**。这三类彼此不可归并：补拷权重不能让并行变安全，路径隔离也不会让被删的表恢复。

附属模板把这三条原样搬成「第 0 节 · 验收前置（环境三查，防假失败污染结论）」，并给每条配了「判定方法＋通过标准＋结果框」——注意它的标题措辞：**「污染结论」**，不是「导致失败」。这说明这一层的目的是保护**证据的有效性**，不是保护**运行的成功**。

### 8.2 对 AI（和他人）报结果的专门规定（正文第四节三条）

1. **要求把输出重定向到文件**，并在回复里给出文件路径——不接受「跑完了，全过了」这种转述。
2. **报的数字必须能在文件里看到对应行**；看不到 → 标「未验证」。
3. **另一个 Agent 报的测试结果同样适用**：索要输出文件，拿不到就是未验证。

第 3 条后面那句理由值得单独看：「**AI 审 AI 有共享盲区，交叉验证不等于证据独立。**」 `[实测]` 这一句否定了一个看似合理的替代方案（让第二个 AI 复核第一个 AI 的口述）。为什么复核不等于独立证据 `[推演]`：两个模型读的是同一段转述文本，它们会**一致地相信同一个错误**——一致的是「相信」，不是「观察」。要独立，就得让第二个读者去开那个文件；文件是同一份，所以证据链真的分叉了。**独立性的来源是「不同的物理输入」，不是「不同的脑子」。**

`[实测]` 第四节结尾的两个已发生实例，是这一层的实证基础：一次修复的结果归档是复制上一版改一个数字、文件尾部残留旧文件名；另一份安全报告引用了不存在的提交号。并给出定性：**「两者都不是撒谎，是『没人核对过』。」** 这句是本 skill 全部存在的理由——它把治理对象从「动机」换成「流程」：不需要假设谁在骗人，只需要要求证据可开。

## 第 9 章 报告格式：四段模板与它的判定标准

正文第三节给的模板，形状（照抄，字段名即模板字段）：

```markdown
### 怎么验证的

**改动前**：`evidence/pytest_before_20260924.txt`
  → `2 failed, 394 passed, 2 skipped`（失败项：test_A, test_B）

**改动后**：`evidence/pytest_after_20260924.txt`
  → `396 passed, 2 skipped, 0 failed in 167.44s`

**期望值变更**（若有）：
- A 类口径重算：3 处（test_x: 60.0→56.25，语义：中性分不再进分子）
- B 类断言弱化：1 处（test_y：`total == raw×k` → `total <= raw×k`，理由：……）

**回归说明**：新增 test_z 为**现状快照**，改动前未验证它是否失败，非回归证据。
```

### 9.1 为什么是这四段

`[推演]` 四段＝五条铁律在「一份文档里」的最小落地：段一、段二承担铁律 1＋2（两个路径＋两行汇总）；段三承担铁律 4（A／B 分类）；段四承担铁律 5（快照声明）。铁律 3（可追溯）不是一段，而是**贯穿段一、段二的写法要求**——每段都写成「文件路径 → 那一行原文」，所以它没有自己的段号。

数法说明：模板段数＝4（`改动前`／`改动后`／`期望值变更`／`回归说明`），按加粗字段名计数。

### 9.2 模板里最值得学的一处细节：把「不算回归证据」写进模板

段四的措辞（「**本次测试是现状快照**，非回归证据」）是整份模板里唯一一个**主动削弱自己结论**的位置 `[实测]`。为什么必须有它：因为大多数新加的测试确实是快照——先修好，再照着修好的行为写断言。**如果没有这一行，写报告的人只有两个选择：夸大（说它是回归证据）或者闭口不提（让读者自己以为）。** 提供第三个合法出口，是让诚实变便宜的唯一办法。这跟铁律 4「弱化不是错，藏起来才是」是同一个设计哲学：**不禁止不完美，禁止不完美被隐藏。**

### 9.3 判定标准（正文第三节末，逐字）

> **别人拿着这份报告，不看你的代码、只听你的话，能不能自己复现出同样的数字？不能 → 证据不合格。**

把它当成一把可执行的尺子用：报告里每一个数字，问一句「一个不认识这个项目的人，凭这句话能不能自己得到它？」。「396 passed」不能（他不知道跑哪个目录、用哪条命令）；「命令 X，输出文件 Y，第 N 行」能。**这就是「充分复现信息」的定义——命令、对象、期望位置三件齐。**

## 第 10 章 失效与恢复：这套证据体系怎么坏、怎么发现、怎么退

`[推演]` 本章把正文第五节（反模式清单）与「版本」节的三件起因，重组成「失效—发现—退路」三段式；铁律正文只给了「不许这样」，没有系统给「怎么知道自己已经这样了」。每条都标出对应出处。

| 失效模式 | 它怎么表现出来 | 怎么发现（可执行动作） | 发现后怎么退 |
|---|---|---|---|
| **A 证据链断在转述** | 报告只有一句话「全过了」 | 索要路径；报告里的数字在文件里 grep 不到 → 就是孤儿数字（T3） | 四选一处置（10.2）；最常见是「删数字」 |
| **B 复制改数** | 两版结果文件除个别数字外结构一致；文件尾部残留旧文件名 | `diff` 相邻两版（T1 第三行）；比时间戳（T2 第二行） | 重跑并如实说明「上一版是复制的」 |
| **C 判据恒真化** | 套件历史上从未红过；改坏代码全绿 | 第 7 章两个问句＋变异三靶 | **改写判据而不是接受这个绿**；改写后重跑 before／after |
| **D 恒红堆积** | 有几条「一直红」的用例，大家口头豁免 | 问「它绿过一次吗」；构造最小正确输入（7.5 第 ③ 步） | 先审尺子再审代码；只改那一条，不清空文件 |
| **E 环境假失败** | 红字指向代码，实际缺依赖；skip 数突增 | 三查（模板第 0 节 0.1–0.3）；对比本次 skip 数与上次 | 补件后重跑；确实缺的把跳过条数写进报告 |
| **F 用例总数不守恒** | 改前 398 条、改后 397 条，却都「0 failed」 | 勾稽：before 的 `failed+passed+skipped` 应等于 after 的同三项之和（模板数字 2+394+2＝398，396+2+0＝398 ✓） | 找回消失的那条；若确认被删，按 B 类弱化申报 |
| **G 抖动（时红时绿）** | 同一提交，两次结果不同 | 铁律 2 的两份文件若同码不同果，立刻暴露 | 不许「重跑一次绿了就报绿的」；查外部依赖与时序 |
| **H 口径与弱化混报** | 「同步更新 4 处期望值」 | `git diff` 与报告逐条对（T4 第一行）；盯比较符变松 | 把 B 类拆出来单独给理由 |

### 10.1 一个容易被忽略的失效：铁律 3 反过来用

铁律 3 要求「每个数字都能回到原始行」。还有一种失效是**原始行本身不是这次跑的**（即铁律 1 被形式满足、实质绕过：文件是真的，但日期是旧的）。所以「可追溯」要追两层：数字 → 文件，文件 → **本次命令执行**。模板 T2 的时间戳核对，正是在追第二层。

### 10.2 阻断项的处置：四选一，且不许「先记着」

`[实测]` 模板「验收结论」逐字：「阻断项处理四选一：**重跑／补证据／删数字／降级表述**（如改标『现状快照』）。**不许『先记着』。**」

这四条的价值在于它是一个**封闭集合** `[推演]`：处置必须落进这四格之一，而第五种（「先记着，回头补」）被明文禁止——因为「回头补」在真实项目里的完成率接近零，它只是让报告带着一个未知项被发出去。四个合法选项里，**「删数字」和「降级表述」是两条诚实的退路**：不删又不降级，就是声称已验证；降级表述（把「已修复」改成「当前是这样」）正好对应 5.4 的合法句式。

### 10.3 归档后的恢复：版本锚定不追溯

`[实测]` 模板开头「版本锚定」段与结论段各写了一次：复制到项目后**锁定当前版本**（v1.0，2026-09-24），「skill 后续升级不追溯已归档项目」；理由是「**验收标准是交付时的契约，中途换标准等于移动球门**」。

`[推演]` 为什么必须「不追溯」而不是「尽量补齐」：因为追溯修订会造成一个无法审计的状态——用今天的口径去判昨天的交付，昨天所有「通过」都会神秘地变成「阻断」，历史结论集体失效，而没有人能解释这些变化。契约性优先于最优性。代价是**模板必须随项目一起归档**，否则几年后没人知道当时用的是哪一版（模板结论段末行写的正是「项目归档时本文件随版本锁定」）。

## 第 11 章 怎么验证这套纪律真在生效（例行体检）

本 skill **没有配套自动化脚本**——附属件只有一份 Markdown 模板（依据：库内该目录下 `references/` 里仅 `验收模板-证据完整性.md` 一个文件，无脚本件）`[实测]`。所以体检是**手工命令清单**。数法：下面 7 项，每项都是一条能直接敲的命令＋一个判定。

| # | 普查项 | 命令形状（探针：只检查不改动） | 判红条件 | 红了做什么 |
|---|---|---|---|---|
| 1 | **孤儿数字普查** | 把报告表格里的数字逐个 `grep -n` 到 `evidence/` 下 | 有任一数字搜不到 | 删该数字或补跑 |
| 2 | **复制改数普查** | `diff evidence/pytest_after_<旧日期>.txt evidence/pytest_after_<新日期>.txt` | 两版仅个别数字不同，或尾部残留旧文件名 | 重跑；如实说明 |
| 3 | **时间戳普查** | before 文件时间 vs 修复提交时间（模板 T2 给的方法） | before 晚于修复提交 | before 作废，结论降级为「现状」 |
| 4 | **收集数普查** | `python -m pytest tests --collect-only -q` | 收集数与报告数不等 | 查是不是有用例被删／被改名（型三恒真） |
| 5 | **总数守恒普查** | 比对前后两份文件的 `failed+passed+skipped` | 两者不等 | 找回消失用例，或按 B 类申报删除 |
| 6 | **skip 率普查** | `skipped / 总数`，与上一次比 | 比例升高却没写原因（本页建议：任一次比上次多出 skip 就要一句解释）`[推演]` | 补解释或补依赖 |
| 7 | **恒真普查** | 随机抽 5 条判据做变异检验（7.4 第 5 步） | 改坏不红 | 按 7.4 第 4 步改写判据 |

### 11.1 怎么验证「纪律本身」还在

上面 7 项查的是**一次证据**的合格度。查「这套 skill 装进 AI 之后到底改变了什么行为」要看另一个信号 `[推演]`：

- **正向信号**：最近一次修复类汇报里，出现了 `evidence/...txt` 这样的路径，并且路径下文件真实存在。
- **失效信号**：汇报里只有总结句；或者出现了「已修复」却没有 before 文件；或者「期望值变更」这一栏永远空着，即使 diff 里明明有断言被改。
- **最隐蔽的失效**：报告形状完全合规，但所有 before 文件都是绿的（＝铁律 2 被形式满足、实质绕过）。查法：抽查 before 里是否包含失败项名字（5.3 的办法）。

一项便宜的强制手段 `[推演]`：把「**修复类汇报必须包含 4 个加粗段名**」写进提交检查表——**格式强制比内容强制更难绕过**，因为缺段是当场可见的，而内容是错的需要读者具备领域知识才看得出来。

## 第 12 章 端到端走查：一次带判据审查的完整修复

场景取自正文第三节模板里的实例字段（`60.0→56.25`、语义「中性分不再进分子」、`test_z 现状快照`）。**下面的数字与文件名形状取自 SKILL.md 报告模板的示例值 `[实测]`；步骤串与判据审查部分是本页为讲解补全的走查 `[推演]`，命令形状可照抄。**

### 第 1 步｜需求与改动

项目里有个算总分的函数，规则改了：**中性分不再计入分子**。因此同一份输入，总分应从 60.0 变成 56.25。要交付的改动是分子计算那一段。

### 第 2 步｜执行前三查（正文第二节）

```bash
python -m pytest tests --collect-only -q > evidence/pytest_collect_20260924.txt 2>&1
ls tests/fixtures models/weights            # 外部依赖（固定测试图、模型权重）在不在
```

收集数应当是 **398**（改前那行的 2 failed + 394 passed + 2 skipped ＝ 398）。对不上就先别跑——数字不对说明测的不是你以为的那套用例（三查第 2、3 条）。

### 第 3 步｜改前跑一次，存 before

```bash
python -m pytest tests -q > evidence/pytest_before_20260924.txt 2>&1
```

产出形状（文件尾部）：

```
FAILED tests/test_score.py::test_total_after_semantic_change - assert 56.25 == 60.0
FAILED tests/test_score.py::test_neutral_not_in_numerator - AssertionError
2 failed, 394 passed, 2 skipped in 171.02s
```

这两条红就是铁律 2 要的「**问题真实存在**」。注意 before 那行有没有 `in ...s` 不重要，但**总数 398 必须在**，否则下一步的勾稽对不上。

### 第 4 步｜改代码，改后跑一次

```bash
python -m pytest tests -q > evidence/pytest_after_20260924.txt 2>&1
```

```
396 passed, 2 skipped, 0 failed in 167.44s
```

勾稽检查（第 11 章第 5 项）：396＋2＋0 ＝ **398** ✅ 与改前总数相等，说明没有用例被顺手删掉，也没有把失败的偷偷改成 skip。这一步只用一个减法，却拦住了 F 类失效。

### 第 5 步｜断言改动分类（铁律 4）

```bash
git diff <修复前> <修复后> -- '**/test*' > evidence/test_diff_20260924.txt 2>&1
```

对照 diff 逐条落进两栏：

- **A 类口径重算 3 处**：`test_x: 60.0 → 56.25`，语义「中性分不再进分子」。三处同一语义，一处列语义、三处列数字。
- **B 类断言弱化 1 处**：`test_y: total == raw×k → total <= raw×k`，理由必须自写（例：新语义下总分变为不超过 raw×k 的区间）。这一处**绝不能塞进 A 类**——它改变的是判定强度。

### 第 6 步｜新增 test_z 的诚实标注（铁律 5）

test_z 是修完之后照着新行为写的。问一句：**「修复前它会红吗？」**——它在修复前根本不存在，所以没机会红。合法写法就是模板那句：**「新增 test_z 为现状快照，改动前未验证它是否失败，非回归证据。」**

### 第 7 步｜判据鉴别力审查（第 7 章六步，这里是本页加上去的那一半）

**0. 它真跑了吗**：`test_z` 出现在 collect 列表里，耗时不是 0.01 秒级 ✅
**1. 指认对象**：「如果**中性分又被算进分子**，test_z 会红」——填得出来 ✅
**2. 真源清点**：新规则原文写「中性分不进分子」；按定义手算得 56.25，与断言里的 56.25 独立相符 ✅。**这一步是关键：期望值 56.25 有独立来源，不是跑出来抄的**；若来源只有「跑出来就是这个数」，就得按铁律 5 的 ⚠️ 处理。
**3. 三分类**：改坏会红吗？→ 做变异 M1（下）。喂对的能绿吗？→ 当前就是绿的 ✅
**4. 改写**：若 M1 全绿，说明 test_z 是恒真的，按 7.4 表格改写（把「不为空」型写法换成 `assert total == 56.25`）。
**5. 变异检验，三个靶子，每个都落盘**：

```bash
# M1 语义靶：把"中性分不进分子"改回"进分子"
python -m pytest tests/test_score.py -q > evidence/mutation_M1_20260924.txt 2>&1
# M2 常数靶：把不该动的分母 16 改成 15
python -m pytest tests/test_score.py -q > evidence/mutation_M2_20260924.txt 2>&1
# M3 自证靶：把断言期望值改一格 56.25 -> 56.24
python -m pytest tests/test_score.py -q > evidence/mutation_M3_20260924.txt 2>&1
```

预期：M1 **红**（test_z 与 test_x 至少一条红）；M2 **红**；M3 **必红**（M3 不红＝这条断言根本没执行，退回第 0 步）。每次变异后都要**复原并再跑一次基线**，确认回到 396 passed——否则变异检验自己就留下一份被污染的代码。
**6. 留档**：在 test_z 上方写一行注释：`# 本判据在"中性分被计入分子"（变异靶 M1）时变红`。

### 第 8 步｜跑一遍附属模板（17 项）

把 `references/验收模板-证据完整性.md` 复制到项目根改名 `ACCEPTANCE.md`（模板「执行方式」说的用法），逐节填「通过／阻断／不适用＋证据」。本例的产出形状：

```markdown
## 验收报告 · 测试证据完整性（锚定 v1.0，20260924）
第 0 节 前置三查：0.1 通过（权重目录已就位）｜0.2 通过（收集数 398 与报告一致）｜0.3 通过（未并行、路径在本仓库内）
T1 输出落盘：3/3 通过（3 个路径均存在；grep 396 → 命中 after 文件）
T2 改前改后：3/3 通过（before 含 2 条 FAILED；文件时间早于修复提交）
T3 指标可溯源：2/2 通过（零孤儿数字）
T4 断言分类：通过（A 类 3 处、B 类 1 处，与 diff 逐条一致）
T5 回归要能失败：1 项降级表述——test_z 标为现状快照；test_x/test_y 在 before 里红过，为回归证据
变异检验：M1 红 ✅｜M2 红 ✅｜M3 红 ✅（三份输出均在 evidence/）
结论：通过（无阻断项）

```

### 第 9 步｜对外汇报文本（正文第三节模板，可照抄）

四段按第 9 章模板填，只多一句：「判据鉴别力已用三个变异靶检验，M1／M2／M3 均变红，输出见 `evidence/mutation_M*_20260924.txt`。」

**走查全图**：三查 → before（拿到红）→ 改 → after（拿到绿）→ 勾稽 398 → diff 分 A／B → 快照如实标注 → 判据鉴别力审查（指认／真源／三分类／改写／变异／留档）→ 17 项模板 → 落盘四段报告。**前一半证明「我做了」，后一半证明「这条证据不是白给的」。**

## 第 13 章 反模式清单（照这个自查）

前 7 条＝正文第五节表格条目（`[实测]`）；第 8 条起为本页补充（`[推演]`，每条给一个具体会出问题的输入）。

| # | 反模式 | 为什么不行 |
|---|---|---|
| 1 | 只报「全过了」无原始输出 | 无法复现，等于没验证 |
| 2 | 复制上次结果文件当本次归档 | 一旦被核对（对比两版 diff／看文件尾部残留）即穿帮 |
| 3 | 改前没跑，只有改后 | 无法证明改动解决了问题 |
| 4 | 断言值来自「跑出来之后抄进去」 | 只能防未来退化，不能证明当初修对 |
| 5 | 口径重算与断言弱化混在一起报 | 掩盖了「测试变松了」这个事实 |
| 6 | 拿「环境不同」解释差异而不给两份输出 | 环境假设本身需要证据 |
| 7 | 在多进程下并行跑共享库套件 | 失败原因会指向错误的地方 |
| 8 | **把恒真判据当验收标准** | 它永远不会红，所以永远「已满足」；一条不能失败的判据，被满足时不携带任何信息。具体输入：验收写「服务返回 200」，服务返回 200 但页面是空壳，交付「通过」而功能为零 |
| 9 | **只报 passed 不报 skipped** | 通过率的分母被偷偷换小。具体输入：396/398 ≈ 99.5% 被报成 100% |
| 10 | **把「没报错」当「通过」** | 否定型判据的零命中有两种解释。具体输入：日志路径拼错 → `grep -c ERROR` 得 0 → 绿 |
| 11 | **测试函数名不以 `test_` 开头** | 测试执行官不收集它，「0 failed」是空套件的必然结果。具体输入：一次改名重构后收集数掉到 0，从此全绿 |
| 12 | **为了让套件变绿而清空／注释掉整个测试文件** | 恒红判据被处置时把邻居一起删了（7.5）。具体输入：4 条断言里 1 条恒红，全文件被注释，此后半年那 3 条所防的回归无人拦截 |
| 13 | **一次改 20 处断言、只写一句「口径同步」** | 铁律 4 的 A／B 分类失效，弱化被批量隐藏。具体输入：20 处里夹着 3 处 `==`→`<=`，报告里完全看不见 |
| 14 | **报告里的数字四舍五入或含糊化（「约 99%」「基本全过」）** | 无法反查原始行，是孤儿数字的软性版本。具体输入：99.5% 写成「约 100%」，读者以为零缺陷 |
| 15 | **以「我本地是好的」结尾而不留本地输出** | 第 6 条的强化版：本地不落地，这条主张就永久不可检。具体输入：换一台机器复现不出来，谁也说不清当时看到了什么 |
| 16 | **凭记忆写路径、提交号、版本号** | 正文「版本」节的已发生实例：报告引用了不存在的提交号。凭记忆写出来的都是转述，转述必须当场核对 |
| 17 | **让第二个 AI 复核第一个 AI 的口述，以此代替看文件** | 「AI 审 AI 有共享盲区，交叉验证不等于证据独立」（正文第四节逐字） |

## 第 14 章 速查表（Cheat Sheet）

**主表：一张表把全貌捞回来**

| 层 | 要问的那一句 | 合格的形状 | 不合格的信号 |
|---|---|---|---|
| 铁律 1 落盘 | 证据是个文件吗？ | `evidence/pytest_after_20260924.txt` | 「跑完了，396 passed」 |
| 铁律 2 红绿 | 改前那份在哪？ | before 含失败项名＋时间早于提交 | 只有 after；或 before 全绿 |
| 铁律 3 溯源 | 这行数字搜得到吗？ | `396 passed, 2 skipped, 0 failed in 167.44s` | 只有百分比，无汇总行 |
| 铁律 4 分类 | 有几处变松了？ | A 类 3 处（60.0→56.25）＋B 类 1 处给理由 | 「同步更新 4 处」 |
| 铁律 5 能失败 | 修复前它会红吗？ | 在 before 里指出那条红的测试 | 现状快照冒充回归证据 |
| 三查 | 红字的原因会不会是环境？ | 依赖就位／先 collect／路径正确 | 缺权重带来的 2 条假失败 |
| AI 通道 | 文件能给我吗？ | 路径＋文件里看得到那一行 | 转述；另一 AI 的口述复核 |
| 模板 | 17 项都处置完了吗？ | 通过／阻断／不适用＋证据 | 出现「先记着」 |
| **恒真判据** | **什么输入会让它红？** | 答得出，且变异检验真的红 | 答不出／改坏代码全绿 |
| **恒红判据** | **什么输入会让它绿？** | 能构造出绿，且只改那一条 | 「这条一直红，不用管」 |

**30 秒回忆清单**

1. 跑不跑不是重点，能不能拿出原始输出才是重点。
2. 五条缺一＝未验证：落盘／前后各跑／给汇总行／断言分类／能失败。
3. 两个问句测鉴别力：**改坏会不会红？喂对的能不能绿？** 都会＝可用。
4. 「没有红字」和「没测」长得一模一样；退出码＋收集数＋耗时，三样一起看。
5. 弱化不是错，藏起来才是；快照不是罪，冒充回归证据才是。
6. 数字要勾稽：改前改后的 `failed+passed+skipped` 总数必须相等。
7. 验收标准是契约：锚定 v1.0 归档后不追溯升级。
8. 处置只有四格：重跑／补证据／删数字／降级表述；不许先记着。

## 第 15 章 工程与安全规范

> 本章的「库 ↔ 仓库」差额是 2026-10-09 上午快照的实测记录；同日下午 17 支本体已按 [CONTRIBUTING.md](../CONTRIBUTING.md) 第一节追平并在仓库侧脱敏。下面的数字原样保留，作为那次追平的历史凭据，不代表当前状态。

### 15.1 命名与目录规范

| 对象 | 规范 | 为什么 |
|---|---|---|
| 证据目录 | `evidence/`（正文实例用名） | 报告里只出现一种前缀，便于统一 grep 与统一忽略 |
| 证据文件名 | `<工具>_<阶段>_<日期>.txt`；阶段取 before／after／collect／mutation_M1… | 可排序、可读，一眼判断能不能当本次证据用 |
| 日期写法 | 8 位紧凑数字 `20260924` | 见 4.1 的三个理由 |
| 变异输出 | `mutation_<靶号>_<日期>.txt` | 变异检验也是「一次运行」，同样要落盘（第 12 章第 7 步） |
| 验收报告 | `<项目根>/docs/acceptance/证据完整性验收_YYYYMMDD.md` | 模板「执行方式」与「验收结论」两处都写了这个路径，照它 |
| 项目内模板副本 | `<项目根>/ACCEPTANCE.md` | 模板开头指定「新项目把它复制到项目根」 |

### 15.2 字段规范（一份修复类汇报的最小字段集）

四段名固定：**改动前／改动后／期望值变更（A 类、B 类分列）／回归说明**（数法：按正文第三节模板里的加粗字段名）。每段内最小字段：文件路径、那一行原文、失败项名称（before 段必有）、理由（B 类必有）。**缺任一字段，即触发对应铁律不满足。**

### 15.3 防护：把这套纪律用在公开仓库时的红线

这一条是本手册自己的安全要求，不是 skill 正文内容 `[推演]`，但对「证据落盘」尤其致命，因为**原始输出是全世界最容易夹带隐私的东西**：

- 命令输出常含**绝对路径、用户名、机器名、端口、数据库连接串**——落盘文件若要对外，先做抽象化（写「本机 skill 库」「仓库内 `../<目录>/SKILL.md`」这类相对写法）。
- 凭据一律不进证据文件与报告；需要占位时写「凭据／密钥」四个字加 `<你的密钥>` 这种形状，不放任何真实值。
- 内部项目代号、提交号原值、AI 助手的称呼、记忆库的目录名与条目编号，都不进对外文档；本页通篇遵守，连正文里那串 7 位短哈希也只做抽象描述。
- 自检探针（只检查不改东西的命令）：`grep -E "[A-Za-z]:[\\/]"` ——在对外文件上跑一次，命中即需抽象化。

### 15.4 冷启动：一个项目第一次装这套纪律要做的四件事

1. 建 `evidence/` 目录，并想清楚**证据要不要入库**：要对外声称的必须入库（否则一年后没人能核对），纯临时的可以忽略 `[推演]`。具体会出问题的输入：`evidence/` 被整体忽略，半年后「当初那 396 passed 的原始输出」永久不可得，整段历史结论退化为转述。
2. 把 `references/验收模板-证据完整性.md` 复制到项目根改名 `ACCEPTANCE.md`，并在文件头写下「锚定 v1.0」。
3. 用一次真实修复走完第 12 章九步，产出两份真文件——**这套纪律只能通过一次完整演练装进去**；只读不练的下一次仍然是「全过了」。
4. 给最关键的 3 条判据做一次变异检验，并把「它在什么输入下会红」那句话留档在测试文件旁边。

### 15.5 与其它纪律的边界（正文第六节逐字口径）

| 管什么 | 归属 |
|---|---|
