# Cao-资深工程师五模板（senior-engineer-playbook v1.0）

> [← 返回总目录](../README.md#skills-index)

## 五分钟速览


1. 五种高频工程场景各配一套「固定视角 + 固定交付清单」，命中场景自动路由，交付不缺项、不跑偏。
2. 原版是社交平台流传的五条「资深工程师提示词」，靠 AI 扮演资深工程师。这个 skill 把扮演转译成了清单，念咒语变成了照单干活。
3. 三条内嵌纪律比清单本身还值钱，数字不脑补、不讨好、只问「缺了会白干」的问题。
4. 与编码行为准则叠加生效，九条纪律一条不少，不是二选一。
5. 命中几个场景读几个模板，只命中一个就只读一个，省上下文。

一句话概括设计目标，**同一个请求，没结构拿到 demo，有结构拿到产品**。

## 它在解决什么问题

让 AI「帮我做一个待办事项应用」，你大概率拿到一个 HTML 文件，一个输入框，一个列表，能加能删，然后没了。没有数据存储，没有验证，没有部署说明，也没有下一步建议。你拿到一个 demo，不是产品。

原因在于请求和交付之间没有结构。AI 按自己觉得「差不多」的粒度交付，缺什么全看运气。

| 故障 | 表现 | 对应机制 |
|---|---|---|
| 交付粒度随机 | 要产品给 demo，缺什么全看运气 | 固定交付清单，逐项可验收 |
| 编造数字 | 张口就是「支持 5000 QPS」 | 数字不脑补，没给量级就分档给 |
| 讨好式反馈 | 想法有缺陷也说好 | 不讨好，缺陷直说带解法 |
| 琐碎问题轰炸 | 每个小选型都来问你 | 只问缺了会白干的问题 |

## 五套清单各对一个场景

| 你说 | 它走哪套 | 交付什么 |
|---|---|---|
| 帮我做一个应用或工具 | ① 构建 | 选型加理由、目录结构、核心实现、持久化、验证结果、已知限制、下一步 |
| 分析这段代码，帮我改进 | ② 审查 | 正确性、可读性、性能、安全逐维过，问题按严重度分级 |
| 为什么报错，修不好 | ③ 根因 | 复现、定位、假设验证、修复加防复发，四阶段 |
| 设计一个系统，要扛多少用户 | ④ 架构 | 容量估算、瓶颈分析、分层设计、扩展路径 |
| 我有个想法，值不值得做 | ⑤ 计划 | 目标拆解、MVP 边界、里程碑、风险清单 |

拿不准②还是③的判据，用户要「整体分析改进」走②，抓「某一个 bug」走③。五套还能串成完整生命周期，想法进计划（⑤），计划进构建（①），构建出问题走根因（③），做完了走审查（②）。

每个模板是一份细则文件，命中才读对应那一份。这是它自己的渐进披露，五套全量加载是浪费，绝大多数请求只命中一个场景。

## 三条内嵌纪律详解

**数字不脑补。** 架构题问能扛多少用户，你没给量级，AI 倾向于编一个精确数字显得专业，张口就是支持 5000 QPS。这里明文禁止，占位数字没给就标「未知」，给分档方案，千级、万级、十万级各自怎么设计。为什么这条这么狠，编造的精确数字是最危险的一类幻觉，它看起来像知识，你会拿去做决策。

**不讨好。** 你的想法有缺陷，直接说，带上解法，绝不为让你开心把问题说轻。讨好式反馈的代价是滞后的，缺陷在写码阶段爆出来，返工的账比当时一句「不太好」贵得多。

**只问缺了会白干的问题。** 给谁用、存不存数据、部署到哪，这种必须问。无关紧要的选型自己定，说一句理由就开工。AI 最招人烦的习惯之一是拿琐碎问题轰炸你，这条把提问额度花在刀刃上。

## 转译和照抄的区别

| 原版提示词 | 这个 skill |
|---|---|
| 一大段文字，人找场景手动套用 | 触发词自动路由，命中场景自动读对应模板 |
| 角色扮演指令，「你现在是资深工程师」 | 交付清单，每项产出物可检查可验收 |
| 放在备忘录里，换个工具就丢 | 跟编码行为准则叠加生效，纪律一条不少 |
| 没有验证要求 | 交付完整实现必须实际跑通，读退出码 |
| 不告诉你该问什么 | 必须问什么、什么自己定，边界写死 |

角色扮演依赖 AI 演得像，清单只看东西交没交齐。**这是转译里最关键的一步**，把「人格暗示」换成「可验收的产出物清单」，交付质量从碰运气变成照单检查。

收尾还有一张交付自检单，对应模板的交付清单逐项齐了没有（真不需要的项要注明为什么省略）、代码类产物实际运行验证过没有、占位数字有没有编造、有没有预埋用户没要的功能。

## 什么时候不用

纯闲聊、纯写作这类零代码任务，不触发。明确只是一个具体小功能的改动，走交付流水线的轻量档更合适，那边有台账和断点续传。触发面同样遵守「宁多勿少」，拿不准时触发，多读一个模板的代价远低于交付跑偏的代价。
