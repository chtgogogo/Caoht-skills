## 第 1 章　这套系统在解决什么问题

### 1.1 它堵的第一现场

做 Agent（会自己调工具、自己循环、自己决定下一步的 AI 程序）的人都会撞上同一批墙，而且撞的方式惊人地一致：不是「代码有 bug」，是「代码没 bug，系统照样跑飞」。这类故障有个共同点——**它错在行为层，不在语法层**。写码检查工具看不见它，单元测试测不出它，因为它跑通一次不代表跑通一百次。[推演]（具体失效输入：一个「总结本周文档」的 Agent，工具调用全部返回 200、日志一行错误没有，但它连着 40 轮都在读同一份文件——按传统 bug 判据这系统「一切正常」，按预算判据它已经该被掐了。）

本库干的事，就是把这类「行为层会怎么死」预先穷举成清单，并把业界已有的病名和药方挂上去。

### 1.2 故障 → 表现 → 本库的解法（对应分区见表）

| 故障（第一现场的样子） | 表现（你观察到的东西） | 本库的解法（走到哪一格） |
|---|---|---|
| 反复调同一个工具、没有进展 | 任务既不成功也不报错，token 一路涨 | `01-failure-modes/FM-循环与终止` 给它名字（活锁，即「一直动但没往前」），`02-patterns` 给计数器级三条：迭代上限 + 状态指纹（把每轮状态压成一个能比对的短摘要，两轮一样就算没进展）+ 熔断器（连着失败 N 次就整段停手） |
| 一晚上烧掉意料之外的费用 | 第二天账单爆炸，日志里没有单点错误 | `FM-成本与预算`：成本失控、重试风暴；药方是预算上限与重试退避（失败后隔越来越久再试，别立刻硬撞） |
| Agent 执行了不该执行的操作 | 它删了别人的数据、发了不该发的邮件 | `FM-安全与权限`：越权、提示注入（把指令写进被读的内容里，让模型误把它当上级的命令）、困惑代理人（代理被外部文本指挥去替主人办事）；药方是权限门（先问「这个动作谁批的」再放行）与工具白名单 |
| 上下文（模型一次能带的资料体积）满了，质量跳水 | 越到后面越忘前面的、开始自相矛盾 | `FM-上下文与状态`：上下文爆炸、回注丢失（压缩完又把关键内容重新塞回上下文的动作没做成）；药方是压缩策略 + 会话上限 |
| 两个任务同时改同一份东西 | 结果时对时错、复现不了 | `FM-并发与顺序`：竞态（两件事抢同一个资源）、写覆盖丢失 |
| 失败之后要么不重试要么无限重试 | 偶发失败被放大成整单失败，或一次失败拖成十分钟 | `FM-错误与恢复`：幂等（重复做结果不变）没做、退避没做、恢复点没有 |
| 功能测试全过，真实用户一上就出事 | 「本地好好的」 | `05-checklists/上线前检查`：硬门禁（不合格就不许放行）＋「凌晨三点十问」式的拷问清单 |
| 出了事说不清是谁批的、改了哪一步 | 复盘只有一句「AI 干的」 | `FM-治理与合规`：审计痕迹断链、责任归属空位；药方是决策日志与验收留痕 |

### 1.3 为什么不能用普通「bug 清单」代替

三条区别，决定了这支库必须独立存在：

- **失败点不同**：普通 bug 清单管「代码写错了」，本库管「代码写对了但系统会失控」。第 1.1 节那 40 轮同文件的例子就是典型——没有任何一行代码是错的。[推演]
- **判据不同**：普通缺陷靠断言（assert，就是「这里必须等于 X 否则报错」）判定；Agent 失控大多要靠**计数与趋势**判定（第几轮了、花了多少 token、指纹有没有变），所以本库大量对策长得像预算表而不是像 if 语句。
- **复用方式不同**：Agent 死法在不同项目间几乎原样重演，所以给它起对名字就等于拿到别人修过的药；业务 bug 各家不同，起名字没有这层收益。这就是术语表（`03-terms`）在这支库里承担重活的原因，它的风险见第 7 章。

### 1.4 它明确不管什么

`SKILL.md` 的边界节把三类推出去了：纯前端页面、纯脚本、纯数据分析（与 Agent 无关）；「只会问答的简单机器人」也犯不上过八项门禁——门槛跟着风险走。[实测] 这条边界很重要，否则这支库会被拿去给一个 Hello World 加八页检查表，那种用法本身就是第 13 章的反模式。

### 3.2 七类条数的实测总账（43，不是 41）

还有一个同源的漏：`SKILL.md` 的编号规则那一行列了 `LOOP-`/`ERR-`/`COST-`/`SEC-`/`CTX-`/`CONC-` 六个前缀，**没有 `GOV-`**，而 GOV 类现有 10 条、是七类里最大的一格。这条会让「按编号规则给新死法编号」的人直接编不出号。[实测]

### 3.3 分层的判定顺序：谁说了算

`SKILL.md` 的「库内治理（源与视图，改库前必读）」一节定了三层，实际执行顺序是这样：

1. **想改知识 → 只能改 `01-failure-modes`**。现象／术语／根因／对策／检查问题的权威版本全在这；新增条目编号接续该类最大号。
2. **改完 01 → 再同步 02／03／05**。这三格分别叫药柜（对策的实现细节）、字典（术语的一句话解释）、问卷（检查问题按场景重组）。它们头部带派生声明（写明「本文件从 01 派生，不要在这里改知识」）。只改视图不改 01＝违规。
3. **`04` 案例集与 `06` 提问模板是独立资产**，不派生自 01，各自维护——好处是案例可以写 01 里没有的事，代价是案例集里出现的编号一旦 01 改名就会悬空。[推演]（具体失效输入：把 `LOOP-2 活锁` 改名为 `LOOP-2 无进展活锁`，04 案例与 05 检查表里的裸编号不会报错，只会静默指不到东西。）
4. **追加前先查重**：往 01 加新条目前先到 03 术语表查重，业界已有名字的概念优先收进现有死法的相关字段，而不是另起炉灶。

这套治理防的正是它自己要讲的死法——同一知识五处副本各说各话（第 10 章会把这当成「这支库自己的失效模式」来写）。

### 3.4 入口为什么长成一张路由表

`SKILL.md` 主体是一张「什么时候读哪个文件（对号入座，只读命中项，省 token）」的八行表：设计时→`05/设计时检查`；命中某条死法要查根因→`01` 里对应那**一个**类别文件；挑对策看最小实现→`02`；说不出专业名字→`03`；想看别人怎么死→`04`；上线前→`05/上线前检查`；已经出事→`05/排错时检查`；怕有盲区→`06` 两个模板。

这里的设计取舍值得讲透：**它把「按主题切好的七个文件」和「八种现场意图」解耦**。如果八种意图各自对应一整包内容，AI 每被触发一次就要把 94 KB 全读进来；路由表让一次任务只命中一格，命中类别文件（最小的 `COST` 那格 2,998 字节，最大的 `GOV` 那格 10,549 字节），这就是渐进披露（一层层按需展开，别一上来把所有细节都倒进上下文）在文件结构上的落法。[实测]

分区名的两制也顺手记一下：`01` 里七个文件名用「`FM-` ＋中文主题」，条目编号用大写英文前缀；`02`/`03`/`04`/`05` 里的条目用「字母-数字」（`P-01`、`R-01`、`F-01`）。混排的代价是检索面（能搜到的那串字符的集合）不统一——搜 `LOOP-2` 命中，搜 `loop2` 或 `L2` 都不命中。

## 第 4 章　41 种失败模式与七分类：按主题切还是按频率切，以及每类的早期征兆

> 章名沿用任务简报传下来的「41」，但实测是 **43 条**。这个数字之争本身就是本章的一条结论，别再当成笔误——判读见 4.2 与第 15 章。

### 4.1 七类总账（数法：数 `### X-N ` 标题行）

|---|---|---|---|

| 错误与恢复（ERR） | 5 | 3,985 | 出错不可怕，可怕的是错得没人知道、错了一直重来、错了留一地垃圾 |
| 成本与预算（COST） | 4 | 2,998 | 任务可能最终能完成，但代价是天文数字；成本失控最阴险——它不报错，等你收到账单才知道 |

43 条的分布很不均匀：最大的 GOV 一格（10 条、10,549 字节）比最小的 COST 一格（4 条、2,998 字节）大 3.5 倍。[实测] 原因在版本史上看得很清楚——v1.0.0 的骨架是六类（没有 GOV），GOV 是 v1.1.0「企业级扩充」整格长出来的，之后「41→43」那次扩容又全落在 GOV 里（GOV-9、GOV-10）。**新知识没有均匀分布，它成格地长在一个主题上**，这是按主题切的结构最典型的行为。

### 4.2 为什么按主题切，而不是按发生频率切

这是这支库结构上最大的一个决定，取舍必须摊开讲。

**按主题切（现在的做法）买到的三样东西：**

1. **穷举这件事才能做完**。五步工作流第 1 步要求「逐项问一遍我这个 Agent 会不会这样死」——只有封闭的、彼此尽量不重叠的主题格才能当清单逐项打勾。按频率排序的清单会不断重排，打勾记录立刻就作废。[推演]（具体失效输入：你今天按「上个季度事故统计」排出的 Top 10，下季度成本类事故归零、循环类暴涨，榜一变了；上一轮项目留的《风险清单表》里的编号和新榜对不上，两份产出的勾稽（两处数字能对上）全部失效。）
2. **和检索入口对得上**。`SKILL.md` 的路由表按「你正在做的事」发牌：设计时→设计时检查；已出事→排错时检查；命中某条要查根因→**七类里对应的那一个文件**。这个「对应类别那一个文件」的寻址方式，前提就是类别是主题稳定的。按频率切的库没法回答「我现在在设计，该读第几名到第几名」。
3. **稳定引用**。`LOOP-2`、`GOV-9` 这种编号一旦发出去就不该改含义（案例集、检查表、别人的《风险清单表》都在引它）。频率序号天生要变，主题编号不会。

**按主题切亏掉的三样东西，以及库里的补丁：**

1. **答不了「哪个最常见」**。全包只有两处定性频率线索：GOV 类首句引外部分类法的结论「大多数 Agent 失败不是基础设施问题，而是任务没说清楚」，以及 SEC 类首句「安全类往往一次致命」。前者是发生频率，后者是严重度——库把**频率轴换成了严重度轴**来用。[实测]
2. **同一根因被切散**。「提前收工」（LOOP-6）和「假成功」（ERR-3）其实是一件事的两面：模型自述完成、错误被代码吞掉；「上下文爆窗」（CTX-1）和「重复调用浪费」「上下文重复传输浪费」（COST-3/4）是同一件事的两种代价。库靠每条的「相关」字段做跨格缝合（`LOOP-6` 的相关字段直接写了 `ERR-3`），这是主题切唯一的补救手段，也是它的软肋——缝不缝得住靠人自觉。
3. **颗粒度失衡**（4.1 那 3.5 倍）。按频率切的库会自然把热门项拆细；按主题切则会让某个主题一旦重要就整格膨胀，膨胀到 GOV 这种 10 条规模时，其实已经该再切二级了，而库没切。[推演]（具体失效输入：合规团队要加「数据主体访问权」和「模型卡披露」两条，按编号规则它们会接成 GOV-11、GOV-12，一个文件里堆 12 条企业级条目，路由表那句「读命中项省 token」就变成「一命中就得读最厚的一格」。）

**结论**：主题切是对的，但要清楚它把「频率」这条信息挤到了类首句的一句定性描述里。真想要频率，得靠你自己的事故台账——库的 `04-incidents` 有 11 个案例但没有统计，第 11 章会讲这缺口怎么补。

### 4.3 每类的早期征兆：在哪个阶段就能看出要犯

这一节回答「什么时候该怀疑」。方法：每条死法的「检查问题」字段本来就写成了**能不能当场答出来**的形式，答不出＝征兆已经出现。下表按阶段排，`[实测]` 指征兆能在包内某条的检查问题／类首句里指到原文。

| 最早可辨识阶段 | 类别 | 早期征兆（在这一阶段就能看出的样子） |
|---|---|---|
| **规格期**（一行代码没写） | GOV | 任务描述交给新人、他不追问就能开工吗；验收标准写不成一句机器可判的断言（assert，就是「这里必须等于 X 否则报错」）→ GOV-1 已成立。多 Agent 方案里说不出「每个 Agent 一句话唯一职责」→ 角色错位。 |
| 规格期 | SEC | 权限清单同时给了「读私有数据 ＋ 读外部不可信内容 ＋ 对外发送」三项，且是按单个能力审的、没按通路审 → SEC-7 三要素齐备，事故只是时间问题。 |
| 规格期 | GOV | 写不出「这个系统没测过的真实业务变异形态清单」（红字、单位换算、混税率这类），或对外只报一个全集数字不分段 → GOV-10。 |
| **编码期**（正在搭主循环） | LOOP | 循环里数不出「第几轮」＝没有迭代上限；判停依据是「这轮和上轮输出一模一样」＝活锁必漏（模型每轮措辞都会漂）；每处「等待」没有到期时间 → LOOP-1／2／3／4。 |
| 编码期 | ERR | 重试是同法重试（同样的调用原样再来一次）且无退避；工具报错被 `try/except` 吞成「继续走」→ ERR-1／ERR-3。 |
| 编码期 | CTX | 任务状态只写在对话上下文里、没落盘 → CTX-3；开发时靠看屏幕输出当日志、没有按任务串起来的 id → CTX-5；工具返回全量塞进历史、历史只增不减 → CTX-1。 |
| 编码期 | SEC | Agent 拿的是管理员级凭证；调用前没有工具注册表比对；日志直接记完整请求参数 → SEC-1／SEC-5／SEC-3。 |
| 编码期 | CONC | 出现了第二个执行流（并行工具调用、多 Agent、同一份文档两个写手），而写入没有串行化或锁 → 整类 5 条一次性上桌。 |
| **联调／试运行期** | CTX | 跑到第 10 轮开始往 JSON 外面加解释文字、换字段名 → CTX-4；第 50 轮已经答不出第 1 轮的目标 → CTX-1 已发生。 |
| 试运行期 | SEC | 在真实工具集上出现没注册的工具名、编出来的文件路径或 id → SEC-5；接第三方工具时审批绑定的是「当时的定义」，而没有任何变更告警 → SEC-6。 |
| 试运行期 | COST | 单次任务的 token／墙钟（挂钟时间）分布没有上限报警；同一份大文件在一轮里反复进出 → COST-1／COST-4。 |
| **上线后** | GOV | 「改完手动试了几个例子」当成验证过了、上一版和这一版同一批考题的通过率说不出数字 → GOV-6 静默漂移已经在跑；变更全量生效且没有 10 分钟内能一键回退的开关 → GOV-7。 |
| 上线后 | COST／ERR | 账单或耗时曲线出现无单点错误的爬升 → COST-1／COST-2；偶发失败被重试放大成整单失败 → ERR-2 重试风暴。 |
| 上线后 | GOV | 复盘时一小时答不出「这条危险操作谁批准的、依据哪版指令」→ GOV-2 审计断层。 |

一句话概括这张表的用法：**征兆比故障早两个阶段**。LOOP/ERR 的征兆在写代码时就能看出来（有没有计数点），GOV 的征兆在写代码之前就看得出来（规格能不能变成断言），而 COST/CTX 的后半段只能等真实流量。这就是为什么 `05-checklists` 必须按四个时机分挡而不是合成一张长表——第 9 章展开。

### 4.4 条目格式：七字段，多一个「案例」字段

`SKILL.md` 定了向 01/02 追加条目的七字段格式：**现象／术语（业界名）／根因／对策／最坏后果／检查问题／相关**。[实测] 抽象描述它的职能：现象是入口（你观察到的），术语是检索键（拿它去搜业界解法），根因是对付对象（药打在哪），对策是出口（指向 02 的哪几条），最坏后果是给严重度定级用，检查问题是可执行判据（也是 4.3 那些征兆的来源），相关是跨格缝线。

两处格式越界值得记下来，因为它们都是**在格式里塞了不该塞的东西**的实例：

- **GOV-9／GOV-10 多出一个「案例」字段**，且内容带内部项目名与日期。格式没升级（七字段变八字段），但条目已经这么写了；`04-incidents` 另有它的标注规范。本页不抄那两处的项目名与日期，只保留机制：GOV-9 讲「护栏代码存在、测试全绿，但生产调用路径根本不经过它」（熔断器没人调用、退避装饰器是死代码、预算闸门没接到入口），GOV-10 讲「考卷没造出来的场景，系统行为其实是未定义的，但所有人以为会处理」。[实测]
- **类首句自带的条数没有跟着条目长**。`FM-循环与终止.md` 的类首句写「先过这 5 条」，同一文件实际有 LOOP-1…LOOP-6 六条。[实测] 这是 `SKILL.md` 那条「扩容防漂移」铁律的第二处违反——第一处是 41／43（第 15 章逐条对账）。**任何把数量写进散文的做法，都会在下一次扩容时变成假话**；数字只该存在于索引表里，正文只该说「本类全部条目」。

### 4.5 这一章的数法声明

- 43＝在 `references/01-failure-modes/` 七个文件里，以行首 `### ` 加「大写前缀-数字」形式出现的标题行数之和，按前缀分桶得 6/7/5/6/4/10/5。
- 「七类」＝该目录的文件数（一文件一类），与 `SKILL.md` 五步工作流、路由表里说的「七类」一致。
- 入口文档里与之矛盾的数（41／43）与类内自述矛盾的数（5／6）都在第 15 章逐条登记，本章只转述判读。

## 第 5 章　26 条对策模式：怎么与失败模式配对，一次事故进来怎么走到该用的那条

### 5.1 药柜的条目格式与索引

`02-patterns/对策模式库.md` 自述格式是四段：**是什么／防哪条死法／最小实现／常见误区**，文件开头另有一张「索引」表（编号／对策／术语／一句话）。P-01…P-26 连续无缺号，26 条与 `SKILL.md` 自述的「26 种对策」**对得上**。[实测]（数法：数文件里 `### P-` 开头的标题行，得 26；再与索引表行数比对，一致。）

「最小实现」这一栏是这格药柜的价值所在——它不停在「应该做预算控制」这种正确的废话上，而是给到可直接抄的形状：累计每次调用的 usage、设硬上限、超限立即收尾报告，库里举例 $2 或 200k token。「常见误区」栏更狠，专治**装了但没用**：例如 P-07 说「软预算（只告警不停）管不住失控的循环」，P-04 说「只给单次调用设超时、不给整体设，可以无限次『每次都不超时』地跑下去」。这两句讲的其实都是恒真防护（怎么测都显示通过，因为它压根不会红）。[实测]

### 5.2 配对是双向书写的，但两向并不互认（本章最重要的实测发现）

死法与对策之间的连线在库里存在**两套**，而且用的是两种标识：

- **正向（01 → 对策）**：`01` 每条的「对策」字段用**中文药名**写，例如 LOOP-2 写「迭代上限 ＋ 状态指纹做进展判据 ＋ 熔断器」。
- **反向（02 → 死法）**：`02` 每条的「防」字段用**死法编号**写，例如 P-02 写「防 LOOP-2、LOOP-3」。

于是从一条死法出发找药，靠的是「中文药名 → 肉眼看索引表 → 找到对应 P 编号」这一跳，而不是硬链接。**这一跳能不能对上，取决于 01 里写的中文名字和索引表里的中文名字是否逐字相同**。[实测] 已经能看到漂移的例子：`01` 的 GOV-1 标题是「弱规格与角色错位」，而 P-25 的「防」字段把它写成「GOV-1 规格失控」——编号还指得对，名字已经变了。[推演]（具体失效输入：新增一条对策时按名字去 01 找「规格失控」，找不到，于是又建一条 GOV-11 重复药；两条同义条目从此各说各话，正是 `SKILL.md` 治理节要防的那件事。）

**覆盖率复算**（数法：把 26 条「防」字段里的 FM 编号全抄出来去重，得 33 个编号；再和 4.1 的 43 条全集求差）：

| 类 | 类内条数 | 被 02 反向登记 | 无药编号 |
|---|---|---|---|
| LOOP | 6 | 5 | LOOP-5 任务膨胀 |
| ERR | 5 | 5 | — |
| COST | 4 | 4 | — |
| SEC | 7 | 5 | SEC-2 提示注入、SEC-7 致命三要素 |
| CTX | 6 | 6 | — |
| CONC | 5 | 1 | CONC-2 顺序错乱、CONC-3 消息风暴、CONC-4 死锁与责任真空、CONC-5 信息截留 |
| GOV | 10 | 7 | GOV-4 合规越线、GOV-9 纸面防线、GOV-10 评测集边界幻觉 |
| **合计** | **43** | **33** | **10 条** |

要讲清楚这**不等于「43 条里有 10 条没解」**：这 10 条的 01 「对策」字段都写了解法（CONC-3 写了定向通信＋消息预算＋攒批，GOV-9 写了接线清单核对＋端到端防御测试＋防线注册表）。缺的是**药柜里没有把它们做成独立一格**——也就是「有方子、没成药」。后果很实际：按第 3 步「到 02 查最小实现」走的人在 SEC-2 那里会撞空，因为 `02` 全文没有出现 `SEC-2`／`SEC-7`／`CONC-2`／`CONC-3`／`CONC-4`／`CONC-5`／`GOV-4`／`GOV-9`／`GOV-10` 这些编号中的任何一个（本页已逐串 grep 核实）。[实测]

三处缺口最值得盯：

1. **SEC-2 提示注入没成药**——而它是 `SKILL.md` 的 description 触发词之一，是招牌症状。库里最近的替药是 P-09（输入校验）和 P-10（权限门），但都只「防 SEC-5／SEC-1／SEC-4」，语义上覆盖不了「外部内容触发动作」这条通路；SEC-2 自己要求的「指令与数据分离」在 02 里没有对应格。
2. **GOV-9 纸面防线没成药**，而这条死法讲的正是「防线代码存在、生产路径不经过它」。换句话说，**药柜对它的处理方式，就是它自己描述的那种病**：01 里有方子、02 里没接线。[推演]（具体失效输入：有人照 01 的 GOV-9 去做「防线注册表」，到 02 查最小实现查不到，于是自己随手写一份；下次改 01 时没人记得改那份散件，注册表本身变成新的纸面防线。）
3. **CONC 整类只剩一格药**（P-08、P-15 都只指 CONC-1）。多 Agent 场景一旦上桌，四格要靠自己按 01 的方子配药，而 01 的方子只有一句话（如 CONC-2「显式依赖声明＋前置产物存在性校验」），没有 02 那种「最小实现／常见误区」的深度。这与 4.2 说的「GOV 整格后来长出来」是同一件事的另一面：**库在扩容时优先长清单，没同步长药柜**。

### 5.3 一次事故进来，怎么走到该用的那条药

完整检索路径五跳（第 12 章会把这条路径用一个具体故障走一遍）：

1. **症状 → 类**。用 `SKILL.md` 路由表的「你正在做的事」定挡：已经出事（卡住／烧钱／乱删东西）→ `05-checklists/排错时检查.md`；这条路由是按**观察到的现象**分的，不需要你先知道病名。
2. **类 → 条目**。进 `01` 对应那一个文件，按每条的「现象」字段做匹配（现象栏是入口，写得像现场描述而不是定义）。三条循环类要在这一步分清：做法一模一样地重来＝LOOP-1；看着很忙、每轮略有不同＝LOOP-2；每轮都变一点点专门骗过检测＝LOOP-3。
3. **条目 → 药名**。读该条的「对策」字段，拿到一串中文药名。
4. **药名 → P 编号**。在 `02` 索引表按中文药名找编号；**找不到就是 5.2 那 10 条无药编号之一**，此时兜底动作是：直接按 01 的「对策」字段自建，并按七字段格式回写。
5. **组合顺序**（这一步库里没写，是从各条「最小实现」的动词归纳出来的，标 `[推演]`）：**先止血，再判据，再计数，最后升级**。止血＝P-06 熔断／P-10 权限门（先让它不能再造成伤害）；判据＝P-02 状态指纹或 P-03 进展度量（先定义什么算「没进展」，否则熔断阈值是拍脑袋）；计数＝P-01 上限／P-04 超时／P-07 预算；升级＝P-17 换路／P-18 转人工。顺序不能倒：先装计数器再定判据，会得到一个既拦不住真故障又爱误杀的开关。

一个真实的对号范例（LOOP-2 活锁，库里给的完整链条）：现象「反复调同一个工具，看着很忙实际原地打转」→ 术语 Livelock／Non-progress detection → 根因「每轮输出略有不同，骗过了『完全相同』检测」→ 对策「迭代上限＋状态指纹做进展判据＋熔断器」→ 落到 P-01＋P-02＋P-06 → 因为根因已经点明「输出漂」，P-02 的指纹必须只收语义状态（这正是它的误区栏）→ 若还想防 LOOP-3，再加 P-03。**一条死法的根因栏决定了对策的参数取值**，这是「配对」真正的含义：不是病名对药名，而是病理对剂量。[实测]

### 5.4 26 条对策自身的分层

不按类按「动手时机」重排一次，第 8、9 章的四个时机挡会用到这份分层：

- **设计期就要定的**（改代码骨架）：P-01、P-03、P-08、P-09、P-13、P-15、P-16、P-24、P-25。
- **实现期顺手装的**（几行代码）：P-02、P-04、P-05、P-06、P-07、P-11、P-14、P-17、P-18。
- **上线动作**（不在代码里，在流程里）：P-19、P-20、P-21、P-23、P-26。
- **选型决定**（影响架构）：P-12、P-22。

这张重排的价值在于：`02` 是按**编号顺序**（大致按症状类）排的，而工程师的待办清单是按**时机**排的；第 9 章那四张检查表做的就是这个重排，所以「05 是 01 的视图」这句话可以扩一句——**05 同时也是 02 的另一种排法**。

## 第 6 章　计数器级优先：为什么迭代上限／预算上限／超时这几行代码比复杂检测算法划算

### 6.1 这条原则在库里是怎么写的

`02-patterns/对策模式库.md` 开头的使用说明把它定为选型原则：**计数器级（几行代码）永远优先于检测算法级——先挡住 80% 的死法，剩下的再上复杂手段**。[实测] 同一条原则在 `SKILL.md` 的五步工作流第 3 步（选药）里也出现一次，两处口径一致。

术语先钉住：**计数器级**＝判据是一个能数的数（第几轮、花了多少、等了多久），比较是一个大小关系，实现在循环外面，不看模型内容；**检测算法级**＝要靠语义判断、模型自评、聚类、异常检测之类才能得出的结论。

### 6.2 「计数器级」这一族有哪几条

`02-patterns` 里属于这一族的条目（按各条「最小实现」字段的写法判）：

| 对策 | 数的是什么 | 最小实现的动作（摘意） | 阈值举例（库内原文给的值） |
|---|---|---|---|
| P-01 迭代上限 | 轮次 | 主循环加计数器，超过 `MAX_STEPS` 立即停 | 25 步；且要求**总步数上限＋单工具调用次数上限**两层都上 |
| P-04 超时与截止 | 秒 | 单次调用包超时、整个任务设总截止、等待一律带 `deadline` | 单次 60 秒／整体 10 分钟 |
| P-05 指数退避 | 重试次数 n | 等待 `min(base*2^n, cap)`，加随机抖动，超上限转熔断 | 1s→2s→4s→8s 封顶 60 秒；重试 3~5 次 |
| P-06 熔断器 | 每个工具的连续失败数 | 达阈值打开熔断，一段时间直接拒绝并告知模型换路；冷却后半开试一次 | 连挂 5 次／熔断 5 分钟 |
| P-07 预算控制 | token／金额 | 每次调用后读 usage 累计，硬上限超限立即收尾报告 | $2 或 200k token |
| P-03 进展度量（半计数器级） | 剩余待办数、完成比例 | 指标必须非增，连续 3 轮不降判无进展 | 3 轮 |
| P-02 状态指纹（半计数器级） | 哈希是否相同 | 每轮序列化关键状态取哈希，存最近 5 个，与历史全同→判死循环 | N=5 |

为什么把 P-02／P-03 标成「半计数器级」：它们的**判据形式**仍是可数的比较（哈希等不等、指标降没降），但需要先定义「什么进指纹」「什么算进展」，这一步是设计活不是几行代码。[推演]（具体失效输入：把带时间戳的字段算进指纹——每一轮都不同，永不相等，判据恒真不触发，熔断器形同虚设；库在 P-02 的「常见误区」里正是这么警告的：指纹只收语义状态，不收噪声字段。）

### 6.3 为什么划算：五条机理

1. **它不看内容，所以不怕模型变招**。检测算法级的判据建立在「输出长什么样」上，而模型每轮措辞天然会漂——`LOOP-3 假进展` 这条死法就是专门用来吃这个漏洞的（每轮换措辞、挪顺序，绕过「完全相同」检测）。计数器的判据建立在「做了多少次」上，漂不掉。[实测]
2. **它在循环外面，不消耗一次推理**。任何「让模型自己判断该不该停」的方案都要多花一次调用，而多花一次调用本身就是要防的那件事（COST-1 的根因正是「没有边跑边累计消耗」）。用花钱的办法防花钱，逻辑上就绕了。
3. **它可复核**。第 12 轮被掐掉这件事，日志里是一行能核对的数字；「模型自己觉得不对劲」在日志里是一句没法核对的话。这支库把「出事能查案」当一条死法来管（CTX-5 不可观测），计数器级判据天生满足它的取证要求。
4. **它写在哪都不会错**。一个 `step_count` 常量、一个 deadline、一个 per-tool 失败计数——没有依赖、没有训练数据、没有版本兼容问题，因此在 GOV-8 配置漂移、ERR-5 依赖变更那两条死法面前最稳。
5. **误杀代价有界，漏杀代价无界**。计数器早停的代价是「本来第 26 轮能做完」；漏判的代价是 4.3 里那条一晚 500 美元。在两种错误不对称时，选那个错得起的。

**几行代码划算多少**，可以给个粗算：装 3 条计数器级（P-01 上限＋P-04 超时＋P-07 预算）≈ 十几行、零依赖、覆盖 02 里被 5 条以上对策共同指向的 COST-1／COST-2／LOOP-1／LOOP-4／ERR-2 这一片高频区。[实测]（按各条「防」字段反向统计）。相比之下，做一个「语义进展判定器」要选嵌入模型、定阈值、建标注集、还要按 P-21 给它本身配回归测试——它的成本结构与它要防的那类故障反而同构（先花钱才能防花钱）。

### 6.4 但计数器级会误杀，库给了三条对冲

不能只讲优点，否则第 13 章的反模式「把上限当质量保证」就会发生：

- **到期要说人话**。P-01 的误区栏：只设上限不设「到期时说什么」＝停了也没用——必须交代停在哪、已完成产物在哪。[实测]
- **软预算管不住失控循环**。P-07 误区：只在开始时看一眼价格表、或只告警不停手，等于没有预算；必须**边跑边累计＋硬上限**。
- **上限设太大等于没设**；**只给单次调用设超时、不给整体设**，可以无限次「每次都不超时」地跑下去。[实测] 这两条是典型的「装了但恒真」（怎么测都显示通过）——第 11 章会把它们做成可执行的自检项。
- **对真慢的合法任务要留活口**：P-03（指标下降就继续，哪怕轮次多）、P-18（置信度低才升级人工）负责放行真活，P-20（影子模式）负责先看清放量节奏。所以计数器和算法级不是替代关系，是**先上计数器、再用算法级补它误杀的那一小块**。[推演]（具体失效输入：一个合法的「批量识别 3,000 张发票」任务，每轮处理 100 张、需 30 轮；`MAX_STEPS=25` 会在第 26 轮把它掐了并报告「未完成」。修法是让上限跟着任务规模走——`MAX_STEPS = 预计轮数 × 1.5`，或按 P-03 用「剩余待办数」当停手条件而不是轮次。）

一句话总结本章的取舍：**计数器级买的是「一定拦得住、且拦得住的时候解释得清」，付出的是「偶尔拦错」；检测算法级买的是「拦得准」，付出的是「它自己就是一条新的死法」。** 先上前者，是这个库对「什么时候该写第一行防护代码」的回答。

## 第 7 章　术语速查表与外部对齐：100+ 词条的价值，和它退化成「装样子的清单」的风险

### 7.0 这一格干的是全包唯一一件别处干不了的事

`01` 回答「这是什么病」，`02` 回答「吃什么药」，只有 `03-terms/术语速查表.md` 回答第四种问题：**「这病在业界叫什么」**。这不是装饰性格子，它是一条检索通路（检索通路＝你能顺着它走到包外资料的那条路）：使用者最常见的处境是「我看到了一个现象，但说不出它叫什么」，说不出名字就只能凭印象瞎搜，搜回来一堆对齐论文而不是能落地的做法。命名一旦拿到，别人修过的药就直接进入视野——所以第 8.2 步把「命名」放在「选药」之前，整条流水线的检索效率都压在这一格上。[实测]

也正因为它是**通路**而不是**内容**，它的坏法很特别：文件还在、行数还多、看着挺全，但路走不通。这种坏法肉眼看不出来，本章 7.6 给一把能量出来的尺子。

### 7.2 条目数的三种口径，和为什么必须并列写

同一个「术语表有多大」，三个地方给三个数，**不许合一**：

1. `SKILL.md` 自述：**100+ 术语**（写的是「100+」而不是一个确定值）。[实测]
2. 表体实测：**119 行**（词条 ≤119，见 7.1 的数法声明）。[实测]
3. `CHANGELOG.md` 的 v1.1.0 节里那条容量叙述：写的是「两组共 110+」，而同一份 CHANGELOG 的 v1.0.0 节自述术语表是 32 条——**起点与增量对不上，库自己在 CHANGELOG 里挂了一条勘误说明「历史条目不回改，以本勘误为准」**。[实测]

判读：`100+` 与 `119` 不打架（119 > 100），但它是**用一个不会过期的写法掩盖一个会过期的事实**——「100+」永远为真，所以它不承担「扩容后要回来改」的义务。这类写法在第 4.4 节（类首句自带条数）和第 15 章（容量数字进散文）会再遇到两次，是同一种病的三个标本。**数字只该存在于索引表里，散文里只该说「全部条目」**。[推演]（具体失效输入：某次对外汇报引用「本库收录 100+ 术语」，评审人追问「具体多少、按什么数法」，你回表里数出 119，其中 7 行是分节名——三个数撑不起一个断言，报告的可核性当场塌掉。）

### 7.3 「详见」列是承重墙：回链可达性复算

`详见` 列承担两件事：**把词条钉回某条死法**（内链），从而让「看到现象→查到条目→顺回 `01` 读七字段」这条链闭合。它一旦不指路，词条就退化成一行漂亮的解释。实测四类坏法：

| 坏法 | 实测样子 | 后果 |
|---|---|---|
| **死法查无词条** | 43 条死法里 **7 条在术语表里没有任何回链**：`CTX-4`、`LOOP-3`、`COST-1`、`COST-2`、`ERR-1`、`GOV-9`、`GOV-10`。[实测] | 从条目这一头走不到词条，从词条那一头也走不到条目——双向都断。 |
| **最新两条一个词都没进表** | `GOV-9`／`GOV-10` 的九个新概念（纸面防线、接线缺口、死代码防线、覆盖缺口、分布漂移、评测盲区、纵深防御、端到端测试、越界未覆盖一类）**逐字搜索全部不命中**本表。[实测] | 这一条最伤：库里最新、最能打的两条死法，**从「我看到的现象」出发搜不到**。而「知道现象、不知道名字」正是这套库宣称要治的病。 |
| **`详见` 写的不是地址** | 2 行按机读口径不可解析（一行指向清单里的第 8 号门禁，一行指向一个本库根本没有的类别名）；按人工严口径是 3 行（第三行把「多 Agent 架构」这种自由词混进了编号位）。两种口径都对，差别在尺子只认「大写前缀-数字」形式。[实测] | 指向清单序号那类尤其坑：清单是视图、会变、而且它把「字典」接到了「问卷」上而不是接到「病理」上。 |
| **术语 → 另一个术语** | 3 行的 `详见` 指向**另一个词条**而不是指向死法条目，形成词条之间的环。[实测] | 查 A 跳 B、查 B 跳 A，**跳出库的那条路断了**——这是本章 7.6 判据 1 的直接反例。 |
| **一词两个住址（自认双址）** | `Deadlock` 的 `详见` 写成「CONC-4 / LOOP-4」；`PII`（个人可识别信息）那行写成「SEC-3 / GOV-4」。[实测] | 严格说不算断链，算**词典诚实地承认了分类不 MECE**（MECE＝相互独立、完全穷尽）。危害在第 10 章腐坏路径 7：同一个词两处各给一条强度差一个量级的处置（PII 一处教你打码、一处要你出数据流图加供应商协议审查）。 |

一句总结 7.3：**这张表的外链（前三列）基本合格，内链（第四列）有四分之一到三分之一的里程是断的或绕的**。

### 7.4 与外部分类法的对齐：`SKILL.md` 把权威性押在哪、押住了没有

`SKILL.md` 的一句话节把本库的定位写成「术语收录对齐业界权威分类」，并点了四个来源。逐个核对齐情况（这是第 1 章「为什么不能用普通 bug 清单代替」第三条的兑现现场：既然复用靠名字，名字就得是从业界借来的）：

| 被引来源 | 借到了什么 | 对齐质量 |
|---|---|---|
| **MAST**（多 Agent 系统失败分类法，论文编号 `arXiv:2503.13657`） | 三大类的骨架 | **分类骨架真借到了**：规格类落到 `GOV-1`、代理间失准落到 `CONC-5`、任务验证落到 `LOOP-6`，三处条目里都写明了对应关系。**但条数错了**：包内有**两处**写「16 种失败模式三大类」，而本项工程当日实访该论文页、摘要逐字写的是 **14 种独特失败模式／3 大类／1,600 多条人工标注轨迹／7 个主流多 Agent 框架**。[实测] 也就是说引用面是对的，引用的那个数不对（详见 7.5 与第 15 章）。 |
| 某大厂的多 Agent 失败模式分类 | 用来支撑「企业级那类不是自创」 | **未检索到一手页面**，当日只见到二手中文转述。[实测] 概念可用，权威撑不住。 |
| MCP 工具安全通报（工具投毒／拉地毯／困惑代理人三个概念的出处） | `SEC-6`／`SEC-7` 的命名来源 | **通报原文未取到**。三个概念本身与条目描述一致、不是编的，但引用无法自证。[实测] |
| 「致命三要素」（私有数据 × 不可信内容 × 对外通道同时具备） | `SEC-7` 的病名 | **原帖当日返回 404**，站内检索无结果。[实测] 这一条尤其要注意：它是全包最常被拿去对外讲的一个词。 |
| 另外两个业界清单类仓库（LLM 安全／鲁棒性方向） | CHANGELOG 里用来做「对齐声明」 | **均未检索到**（逐仓直查与检索串都取不到数）。[实测] |
| OWASP LLM 风险清单／MITRE ATLAS／FMEA 的 RPN／Google SRE 复盘 | **本库借了它们的机制，却一处都没有引用它们**：全库搜这四个名字零命中（只有 `SRE` 一词和案例集里一个 `postmortem`）。[实测] | 这是反向的对齐缺陷——不是引错了，是**用了没登记**。所以「你这条排序依据哪个标准」这个问题，库内无法回答（排序规则的机制分析见第 6 章）。 |

**对齐质量的总判读**：分类维度对齐做得到位（三大类都能落到具体条目，不是贴标签），**引用面全线不合格**（四个权威三个取不到一手，一个数写错，四套借了机制的方法论一个都没登记）。这不是虚荣心问题——第 15 章会说清它的机制根因：术语层和死法层没有「来源／版本／访问日期」列，所以**没有任何字段承载「我是什么时候、按哪个版本引的」**，引用当然会烂而无感。

### 7.5 当日可达来源核查（可达性不许沿用旧结论）

本页所有「实访」都遵守一条纪律：**外部来源的可达性每次引用前当日重测**，因为屏蔽状况会变。当日（2026-10-09）的实测口径：

| 来源面 | 当日结果 | 本页怎么用 |
|---|---|---|
| 某官方模型平台的 skills 文档页 | 跟随重定向后落在**区域不可用提示页**＝仍不可用 | **禁用作证据**；本页凡需官方规范原文处一律不引这一支。 |
| 同一文档的另一个域（文档站的 skills 页） | 301 跳转后可达，取到正文 | **可达**：需要官方规范条款时用这一支。[实测] |
| 开放标准站 `agentskills.io` | **带 `www` 前缀当日不解析**（直连失败）；**裸域**跳转后可达、正文可取 | 引用一律写**裸域**。[实测] 这个差别很实用：同一个域名，加前缀就是取不到，取不到容易被误记成「这个来源不可用」。 |

三件必须并列、不许合并的长度口径（它们来自不同层面，混成一个数就会假装解决了）：**1,024** 字符＝开放标准与上传校验器的上限；**1,536**＝某些宿主常驻清单里 description 与补充字段**合并后**的截断线；**200**＝某上传入口的口径。本库 description 实测 557 字符：**前两个口径合规、第三个超 2.8 倍**。[实测] 这条与术语表的关联是：`SKILL.md` 的 description 里那串必触发关键词表，就是**把术语表的一部分抄进了常驻清单**当索引用——所以第 2.3 节那张业界术语表同时是「description 的构成件」和「`03` 的样本」，两处口径要一起改（改哪一处的工程后果见第 15 章）。

### 7.6 退化判据：怎么一眼看出术语表已经变成「装样子的清单」

「装样子的清单」＝看着齐全、实际不给路的表。本页给四条可执行判据（判据＝能机械回答「过／没过」的标准），按严到松排；**四条全中就是已经退化，中一条就是正在退化**：

1. **外搜可达性判据（最硬，因为它测的是这张表对包外的贡献）**：随机抽 10 行，把「术语」列那串英文原样丢进搜索引擎。**判据：至少 7 行能搜到与「中文」列所写含义一致的外部做法**。搜不到有两种可能——词条是生造的，或者「中文」列解释的方向偏了。两种都算退化。[推演]（具体失效输入：抽到某行写着「软预算」，外部搜不到任何对应工程做法，因为那是本库自造的中文词；使用者拿它去搜，一小时白费，还不如直接读 `02`。）
2. **内链可解析率判据（可当场算）**：`详见` 列里含「合法编号」的行数 ÷ 词条数。**合法编号**＝`大写前缀-数字` 且该编号在 `01` 里真的存在。本表实测 43 条死法有 7 条完全无回链、另有 2～3 行写的不是地址、3 行是词条互指。**低于六成就算退化**（六成本页给不出实测支撑，是按「多数词条该能被顺回条目」的用法门槛定的经验线，标 `[推演]`；具体失效输入：拿这张表做导航，每 5 次顺链有 2 次落在空处，用的人第三次就不查表了，表白养）。
3. **新鲜度判据（最容易被忽略，也最致命）**：**最近一次扩容新增的条目，在术语表里有没有对应词条**。本表实测答桉是「一个都没有」（GOV-9/GOV-10 的 9 个新概念逐字搜索零命中）。[实测] 这条为什么单列：**知识库最值钱的部分恰好是最新那几条**，而最新那几条在检索层是隐形的——于是这个库对它自己最有卖点的两个字完全不可发现。判据写成一句可执行的话：**「新增条目当日，表里必须新增或补挂词条；否则扩容视为未完成」**。
4. **引用可核性判据（防它变成一堆二手传闻的堆放处）**：凡词条的解释里出现**外部数字或外部权威名**（「某分类法有 N 种」「某人提出」），该行必须带**来源＋访问日期**两个字段。本表**没有这两列**，所以按本条判据是全表红——包括那两个写着「16 种」的位置（数还是错的）。[实测] 这条判据同时是第 15 章 P 级改进的依据：把 `04-incidents` 已有的标注规范（性质标签＋置信度）上收到术语层。

一句操作口径：**前三条测「这张表还能不能用」，第四条测「这张表说的话还能不能信」。**

### 7.7 这张表的正确用法与不适当用法

- **该这么用**：① 当**外搜钥匙**——这是它最难被别处复制的价值：拿到英文名，去搜业界成熟做法，比在本库四个分区里绕一圈更快。② 当**术语对齐契约**——团队评审时用「这叫 livelock 不这叫死循环」把讨论钉住。③ 当**扩容查重闸**——治理规矩第 4 条正是「往 `01` 加新条目前先到 `03` 查重」，这是全包唯一一处**防条目自增**的入口闸。[实测]
- **不该这么用**：① 别当**权威引用源**对外讲——它的引用面有 7.4 那三处取不到一手、一处数错，拿去面试会被追问穿。② 别当**导航唯一入口**——7.6 判据 2/3 说明它的内链会落空。③ 别在它里面找**最新条目**（7.6 判据 3，实测找不到）→ 直接读 `01` 对应文件。
- 与第 13 章反模式 6、第 15 章外部引用条同源，用法违规的具体后果在两处各写一次，不在此重复。

## 第 8 章　五步工作流：穷举 → 命名 → 选药 → 查漏 → 门禁，每步产出什么、跳过会漏什么

`SKILL.md` 的五步工作流是这支库唯一的「执行序列」；其余六格全是它的查询对象。逐步拆开，每步给：输入、动作、产出形状、跳过的漏口。

### 8.1 第 1 步 穷举

- **输入**：一个还没写代码的 Agent 设计（哪怕只是一段需求）。
- **动作**：打开 `05-checklists/设计时检查.md`，按七类逐项问「我这个 Agent 会不会这样死」。该文件自述的规矩是：**每一项都要留下结论——命中（附对策）或不命中（附为什么不会发生）**，「不命中也要说理由，直接跳过等于没查」。[实测]
- **产出形状**：一份带括号编号的勾选表，每行末尾是死法编号（如 `（LOOP-5）`），行后跟一句结论。
- **体量的真相**：这张表 61 行、约 5,116 字节，问题按七类分节（`## ` 分节 7 个），勾选行 **41 问**（数法：数该文件以 `- [ ]` 开头的行）。SEC 类 7 问、GOV 类 10 问，一问可覆盖两条编号（如「（LOOP-2/3）」「（CONC-3/4）」）。**它是 43 条的重组视图，GOV-9／GOV-10 在这张表里各有一问**，条数与 01 对得上：41 问 → 43 编号，差的 2 个来自两问合并。[实测]
- **跳过的漏口**：`SKILL.md` 这一步写的数量是 **41 条**（第 3.2 节已核实实际 43 条）。照入口文档做穷举的人会漏掉两条——而且漏的正好是最新长出来的那类（企业级）。**这就是把容量数字写进流程指令的代价**：清单会自己长大，指令不会自己更新。
- **另一条更要命的漏口**：`05/排错时检查.md` 与 `04-incidents` 完全不提 GOV-9／GOV-10（grep 实测：这两个编号在排错时检查里 0 次命中）。也就是**「已经出事了」那条路径拿不到最新两条死法**——出事场景本来最可能撞上的偏偏是这两条（纸面防线、评测集边界）。详见第 9 章。

### 8.2 第 2 步 命名

- **输入**：上一步命中的那条（一串现场描述）。
- **动作**：读 `01` 对应类别文件里那条的「术语」字段，拿业界名；或直接翻 `03-terms` 反查。
- **产出形状**：一句「这条死法叫 XXX / YYY」，其中至少一个英文名是可搜索键。
- **为什么这一步不能省**：库里给的理由是「问题有了名字，才能搜到现成的药——你不需要发明解法，只需要知道这病叫什么」。翻译成检索语言：**命名把一次「凭现场印象瞎搜」换成一次「按键精确查」**。「rug pull（拉地毯，指工具审批通过后被作者偷改成恶意版本）」这种词一旦拿到，你能直接搜到「工具定义指纹锁定」这类成熟做法；拿不到，你会去写一个自造的检测器，而那个检测器本身又是一条新死法（见 5.2 的 GOV-9）。[推演]（具体失效输入：Agent 读了外部网页后开始执行网页里写的指令，你只会搜「AI 不听话」，搜到一堆对齐论文；正确键是 indirect prompt injection（间接提示注入），搜到的是指令数据分离＋外部内容触发动作过白名单，当天能落地。）
- **跳过的漏口**：不命名就直接选药，会选到「同类但不同因」的药——LOOP-1（同法重试）和 LOOP-2（有活动无进展）看起来都是「停不下来」，但前者要 P-17（换策略），后者要 P-02／P-03（先有进展判据）。装错药＝装了个永远不会触发的开关（恒真，怎么测都显示通过）。

### 8.3 第 3 步 选药

- **输入**：死法编号（如 LOOP-2）＋ 它的「对策」字段里的中文药名。
- **动作**：到 `02-patterns` 索引表按中文药名对上 P 编号，读那一条的「最小实现」和「常见误区」；**优先级由库直接规定：计数器级先上**。
- **产出形状**：一段可以直接抄的实现要点（阈值数字来自库里给的示例：25 步、60 秒、10 分钟、连挂 5 次、$2／200k token），外加一条「本项目实际取值」。
- **撞空怎么办**：走到第 5 章 5.2 那 10 条「无药编号」时，`02` 里查不到——此时按库的治理规则，方子在 `01` 的对策字段里，自建并回写。库里没写这条兜底路径，这是流程上的一处真空（不是内容错误，是**没给断链时的走法**）。[推演]（具体失效输入：SEC-2 命中，照第 3 步去 `02` 找「指令与数据分离」，索引表 26 行里逐行看没有这味药，工作流到这一步断了；实践者最可能的动作是随手写个正则过滤外部内容，然后以为自己有护栏——正好落进 GOV-9。）

### 8.4 第 4 步 查漏

- **输入**：写完的代码（或整份设计稿）。
- **动作**：喂给 `06-prompts` 两个模板，让 AI 扮演挑剔的 SRE／安全工程师再列一遍问题，做差距分析（哪些已有防护、哪些在裸奔）。
- **产出形状**：一张差距清单——「已有防护项 / 裸奔项 / 无法判定项」三列，裸奔项回落到第 3 步补药。
- **为什么必须换一双眼睛**：前三步是**同一个人按同一份清单**在查，漏的是「你没想到的」；这一步是**换个提示词角色**去生成清单没有的项。这一步和第 7 章的术语表构成一对张力：清单只能穷举它写下的东西，模板负责碰那些没写下的。
- **跳过的漏口**：跳过＝把「库的覆盖面」误当成「系统的风险面」——这正是 GOV-10（评测集边界＝能力边界幻觉）对使用者自己的那一版。库自己也在犯：它的 16 条触发评测题里没有任何一条问的是治理合规类（详见第 11、15 章）。

### 8.5 第 5 步 门禁

- **输入**：准备上线的版本＋前四步的全部产出。
- **动作**：过 `05-checklists/上线前检查.md` 的「凌晨三点十问」＋硬门禁（基础八项，涉及真实用户／合规时再加企业级四项）。[实测]
- **产出形状**：`SKILL.md` 交付自检节钦定的《风险清单表》，七列：**编号／现象／严重度／术语／解法／修复成本／本轮是否处理**。[实测] 这一列设计是有讲究的：「本轮是否处理」是**允许欠账但必须登记**的那一列——没有它，检查表会退化成「全勾才算过」的假绿。
- **硬约束**：`SKILL.md` 要求「未上线的产物注明『仅设计评审』」，即**没跑的项必须显式声明没跑**，不许留空。这条与第 15 章的「诚实留档」同源。
- **跳过的漏口**：跳过门禁＝把「上线验收记录表」这一步（第 9 章的第四挡）省掉，于是事后无法回答 GOV-2（审计断层）那条检查问题——「随机抽一条危险操作，能在一小时内答出谁批准的吗」。

### 8.6 五步为什么是这五步：一条轴和两次换视角

把五步摆到一根「你离故障还有多远」的轴上看：穷举（离故障最远，纸面）→ 命名（把现象翻译成可检索的键）→ 选药（把键翻译成代码）→ 查漏（换成对手视角）→ 门禁（换成值班人／审计员视角）。**中间两步是「查库」，两头和倒数第二步是「换视角」**。所以五步真正的机制不是「查一份清单」，而是**在四个位置轮流怀疑自己**：设计者、命名者、实现者、审查者。少任何一步，就少一种怀疑方式——这也是「跳过会漏什么」的总答案。

一个可核对的顺序约束：第 3 步必须在第 2 步之后。原因在 5.3 说过——**每条死法的根因字段决定了对策的参数取值**（LOOP-2 的根因写了「每轮输出略有不同，骗过完全相同检测」，这条根因直接规定 P-02 的指纹不能收噪声字段）。跳过命名直接选药，你会装上一个阈值凭空的正则开关，测不出它到底挡的是哪条死法。

## 第 9 章　四张检查表：为什么按设计时／排错时／上线前／上线验收四个时机分挡

### 9.0 一句话先摆住：四张表不是四份知识，是同一批知识的四种问法

`01` 里那 43 条死法只有一份。`05-checklists` 的四张表做的是同一件事：**把同一批「检查问题」按你此刻站在流程的哪一格重新排一遍**。所以「`05` 是 `01` 的视图」（第 3.3 节）这句话在本章要扩成两句：视图不只是「抄了一份」，它是**换了主谓宾的一份**——`01` 的主语是「这种系统会怎么死」，四张表的主语分别是「你现在正在设计／你已经出事了／你准备放行／你要签字」。[实测]

「挡」这个字在本章的用法：把四张表当成四道闸门（挡＝不合格就不许往下走的那道关口），每张闸门只在特定时刻落下来。为什么不能合成一张 60 行的长表，9.5 给四条理由。

### 9.1 四挡总表

| 挡 | 文件 | 字节 | 它挡的是哪一类失败 | 产出形状 | 这一挡要求的证据 |
|---|---|---|---|---|---|
| 第 1 挡 设计时 | `设计时检查.md` | 5,116 | 「你压根没想到要去防」——覆盖面失败 | 41 个勾选项，每项末尾带死法编号、项后带一句结论 | 无（此挡只有嘴，代码还没写） |
| 第 2 挡 排错时 | `排错时检查.md` | 2,338 | 「现场在，但你归错因」——归因失败 | 五步处置记录＋一条回写库的新条目 | 日志、账单、时间戳等外部痕迹 |
| 第 3 挡 上线前 | `上线前检查.md` | 3,730 | 「功能都过，真实一上就炸」——资格失败 | 十问答复＋门禁勾选（要填数值）＋七列《风险清单表》 | 配置项、阈值、一次真实 grep 的结果 |
| 第 4 挡 上线验收 | `上线验收记录表.md` | 4,843 | 「过了，但没人能证明为什么过」——留痕失败 | 抄进项目里的表格，逐格「结论＋证据」 | 文件位置或配置键，可被第三人复查 |

**四挡各挡一种失败，这是分挡的第一理由**：它们挡的是**四种不同的错误**，不是同一错误的四个阶段。覆盖面失败＝漏问；归因失败＝问对了但答错方向；资格失败＝答对了但拿不出数字；留痕失败＝数字有但没人签名。这四件事互相独立——一个项目可以四挡全过然后在新机器上因为换了个供应商而全线失效（GOV-5 模型漂移，供应商悄悄换模型／降配置，你没动代码，质量自己变了）。

### 9.2 第 1 挡：`设计时检查.md`（挡「漏问」）

- **结构**：按七类分节，41 个 `- [ ]` 勾选项（数法：数该文件以 `- [ ]` 开头的行；分节相加 5＋5＋3＋7＋6＋5＋10＝41），一问可覆盖两条编号（如「（CONC-3/4）」这种合并问）。**41 问压住 43 条**，压缩发生在「同一类里两条常被一起踩」的地方；把合并问里的斜杠编号展开再点，覆盖是 43／43、无缺口。[实测]（勘误：本页早前草稿在此写 36，是按旧快照估的数，与两种数法都不符，已按实测更正为 41。）
- **自述的规矩**：「每一项都要留下结论——命中（附对策）或不命中（附为什么不会发生），不命中也要说理由，直接跳过等于没查」。这句是本挡最有价值也最脆的一条：它把「没问」和「问了但不适用」区分开了，但**没规定这 41 条结论写到哪里、由谁收集**。[实测]（后果见第 11 章的「留痕落点」判据；第 13 章反模式 12。）
- **早期征兆用法**：本挡配合第 4.3 节的征兆表用——征兆比故障早两个阶段，规格期就该问 GOV 与 SEC 那几问，而不是等上线前才第一次问。
- **本挡的漏口**：`SKILL.md` 第 1 步写的数量是 41 条（实际 43），照入口做的人会少问两条，而且漏的正好是企业级那两条。[实测]

### 9.3 第 2 挡：`排错时检查.md`（挡「归错因」）

这是四张表里**唯一有真判据**的一张（判据＝能机械回答「过／没过」的标准），也是全库最像可执行规程的文件。三条硬货：

| 步 | 库给的东西 | 为什么它算判据 |
|---|---|---|
| 1 | 「没有日志可用？→ 这本身就是死法 CTX-5（不可观测），改用外部痕迹（账单、时间戳、调用记录）倒推」 | **把异常本身转成分类**。别人家的排错表遇到「没日志」只会卡住，这张表把它变成一个已知死法，于是「没证据」不再是流程终点而是分类起点。[实测] |
| 2 | 「同一工具＋同一参数出现 ≥3 次即命中 LOOP-1／LOOP-2」 | **带阈值的计数判据**，符合第 6 章的计数器级原则。3 次是个「误杀概率低、发现得早」的经验值；改成 2 次会误杀合法的两次重试（网络抖一次很正常），改成 10 次则 3～9 次那一档的循环全漏。[推演]（具体失效输入：一个带 3 次退避重试的调用，第 4 次仍失败——按 ≥3 判据它会被报成循环，实际是下游真挂了；所以这条判据必须和 P-06 熔断器的「连续失败计数」合起来看，单看会误杀。） |
| 3 | 「先止血再归因」 | 次序约束：先让它不能再造成伤害（掐掉、熔断），再谈找根因。 |
| 4–5 | 「新事故按七字段格式追加进 `01`」＋「回答三个问题：为什么护栏没拦住？哪个检查项该加？清单要不要加一问？」 | **闭环点**。本挡是唯一要求把结果写回库的挡，问的是防线不是人。[实测] |

**本挡的漏口有两条，都不是小洞**：

1. `GOV-9`／`GOV-10` 在本文件里 **0 次命中**（第 8.1 节已核）。也就是「已经出事了」这条路径拿不到库里最新、最锋利的两条死法——而真实事故里「护栏代码在但生产不经过它」（纸面防线）恰恰是半夜最常见的那类：白天所有测试都绿。[推演]（具体失效输入：Agent 一晚把同一封邮件发了 3,000 封，值班人照本挡走五步，归因到 LOOP-1 同法重试、补了迭代上限；真正原因却是熔断器配置挂在一个从来没被调用的分支上（GOV-9），本挡没有任何一问会把他引向这里。第二晚换个入口，事故重演。）
2. 「先止血」之后**没有残留取证条款**。手动 kill 掉进程，现场就没了，第 4 步的七字段追加只能凭记忆写。这与库对别人提的要求（CTX-5 要「结构化日志＋任务 id 串联＋能一句话还原」）正好相反——它对使用者的现场没提同样的要求。[推演]

### 9.4 第 3 挡：`上线前检查.md`（挡「资格」）

这一张是三层结构，三层各挡不同的事，别混着看：

| 层 | 内容 | 挡什么 | 为什么要单独一层 |
|---|---|---|---|
| A 凌晨三点十问 | 十个拷问式问题，每问必须答「靠什么护栏让这一问不成立」 | 挡「我们测过了」这句空话 | 它是**叙事性**的：把验收人换成半夜被叫醒的值班人，问题就从「功能对不对」变成「我能不能自救」。同一套检查换个主语，露出来的洞完全不同。[实测] |
| B 八项硬门禁 | 每项要求填**数值**（库里留的是空格式的「数值是 ____」／「token ____／金额 ____／时间 ____」） | 挡「有护栏」但说不出护栏在哪一档起效 | 把定性主张换成定量填空是这一层的要害：**没有数值的门禁等于没有门禁**，因为它永远可以被答「有有有」。第 6.4 节说的「上限设太大等于没设」「只给单次不给整体」在这一层被强制暴露。[实测] |
| C 企业级附加四项 | 只在「有真实用户／有合规义务／多租户／有供应商依赖」时上桌（库内编号 9～12，另有两个带字母后缀的追加项 12a／12b） | 挡「单机跑得好好的，一上企业级才要命」 | 触发条件是**发生条件**而不是故障部位，所以它必须独立成层——这正是第 4.2 节说的 GOV 类切分维度不同一在检查表层的投影。 |

**12a／12b 为什么用字母后缀**：为了不打断已有的 12 项编号序列——加字母而不重排号，历史引用才不会漂。[实测] 这个决定是对的，但它的代价在第 15 章登记：字母后缀接不进第 4 挡那套 `G1…G12` 的格子命名，于是最新两条门禁在留痕表里没有落点（9.5 末段）。
**七列《风险清单表》的产出定义在本挡**：编号／现象／严重度／术语／解法／修复成本／本轮是否处理（第 8.5 节）。其中「修复成本」用的是库里自定的三档：一个 if 级（计数器级，几行代码）／独立小模块级／改整体设计级，本挡还配一条反舞弊逼问——**报「改整体设计」的人得回答「计数器级真的挡不住吗？最小反例是什么？」**。这一句是整张表设计质量最高的地方：它把「用复杂度逃避十行代码」做成了一个当场要答的问题。[实测]

### 9.5 第 4 挡：`上线验收记录表.md`（挡「无法自证」）

- **它是全包唯一明确要求把内容抄到项目里去的文件**（自述落点是项目根目录下的验收档案，第 11 章的跨会话判据全靠它）。[实测]
- **两个设计值得单独夸**：
  1. **格子二选一**：每项只能填「已设＋数值＋证据」或「不适用＋理由」，不允许留空。留空＝没做，这一条把「假绿」（怎么勾都显示通过）从表结构上堵掉了，是四张表里唯一做到这点的。[实测]
  2. **派生版本锚定**：复制到项目里时锁定当时的库版本，库以后升级不追溯已归档项目。这是**承认知识有生效区间**的正确直觉（知识库会自己长大，你三个月前勾过的表勾的是当时的库）。[实测]
- **两个缺口**：
  1. 企业级门禁只有 `G9…G12` 四格，**12a／12b 没有格子**——照这张表逐格填完并宣布「门禁全过」的项目，会静默丢掉库里最新两条企业级死法。不是「可能丢」，是**想勾也没处勾**。[实测]
  2. 表头的版本锚写的是 `v1.1.1（2026-09-23）`，而 `CHANGELOG.md` 记 v1.1.1 是 09-24（09-23 是上一版 v1.1.0 的日期）。锚定动作认真，锚定的值错了一天——这条进第 15 章的版本对账。[实测]

### 9.6 为什么必须按四个时机分挡，而不是按类别分挡、或者合成一张表

四条理由，前三条可执行、第四条是设计原理：

1. **证据可得性不同**（最硬的一条）。设计时你只有嘴，能给出的唯一证据是「打算怎么做」；排错时有日志和账单；上线前有配置项和阈值；上线后有签字和归档。**把四挡合成一张表，就会允许在第 1 挡拿「我们会记日志」来回答一个只有第 3 挡才能验证的问题**——勾是打上了，证据根本还不存在。这就是「意图被当成事实」的机制。[推演]（具体失效输入：设计阶段有人在「审计留痕」那格勾了「不命中，我们有日志」，代码还没写；三周后项目按这张唯一的表交付，没人再问第二遍；出事后照 GOV-2 那条检查问题反问「随机抽一条危险操作，能在一小时内答出是谁批准的吗」——答不出，而表上那个勾就是当初的依据。）
2. **每漏一格的代价不同**。第 1 挡漏一问＝少防一条死法，还能在第 3 挡补；第 3 挡漏一项＝带病上线；第 4 挡漏一格＝**事后无法定责**，前三种里唯一不可逆的是这个。分挡让人知道「哪一格现在不能省」。
3. **表的读者不同**：第 1、2 挡是给工程师自己看的作业；第 3 挡是给评审人看的判卷；第 4 挡是给三个月后出问题的人看的证物。让同一份文档同时服务三种读者，结果是三种读者都读不下去（`CHANGELOG.md` 把「决策原文」和「变更史」混在一个文件里、结果两边都读不起，是同一个病，第 10 章第 9 条腐坏路径）。
4. **分挡跟「谁有能力回答」走，不跟知识走**。第 4.3 节那张征兆表说了：LOOP/ERR 的征兆在写代码时就看得出来，GOV 的征兆在写代码之前就看得出来，COST/CTX 的后半段只能等真实流量。**既然可辨识时刻本来就不同，检查表就必须按时刻切**——按类别切的表（也就是 `01` 的七个文件）负责的是「查根因」，不是「查现在该问什么」。这两件事不冲突，是两套寻址：`01` 按部位索引，`05` 按时刻索引。[实测]

顺带一句可核对的覆盖关系：第 1 挡的 41 问压住 43 条（0 缺口，数法见 9.2）；第 3 挡的十问加十二项门禁只压到 16 个编号（其余 27 条不出现）；第 4 挡表内出现的死法编号是 14 个；第 2 挡只覆盖到 6 个编号——**四挡的疏密是刻意递减的（越往后越该是抽查而不是穷举）**，但第 2 挡那个 GOV-9/10 的洞不在这个递减设计里，那是漏的。[实测]

### 9.7 `06-prompts` 两份模板与四张表的分工

四张表问的是**库里已经写下的东西**；两份模板负责**库里没写下的**。这就是分工的全部内容，也是第 8.4 步（查漏）为什么不能被表替代。

| 模板 | 字节 | 它做的动作 | 关键约束（库内自述，摘意） |
|---|---|---|---|

1. **模板的产出必须回落到 `01` 的编号，否则无法勾稽**（勾稽＝两处数字能对上）。失效输入：只用 `06` 做查漏，AI 生成 20 条问题，项目照这 20 条装了防护；三个月后库扩了两条新的企业级死法，而你的项目档案里全是自由文本，**没人能算出没覆盖的是哪几条**——第 4.2 节说「稳定引用靠编号」，模板产出如果不落编号，就享受不到这个好处。
2. **模板不能替代第 1 挡，只能补第 1 挡**。失效输入：以为「让 AI 挑一遍比逐条问快」，于是跳过 41 问。AI 生成的问题偏向它记得的热门话题，**而库的价值恰恰在冷门那几条**（比如 CONC-5 信息截留：为省 token 砍掉传给下游的原始依据）；跳过表之后，冷门条目在整个项目里一次都没被问过。
3. **两份模板与四张表是并联关系，不是串联**。失效输入：把它当成「第 3 挡之前必须先做差距分析」，结果因为「还没跑过模板」而卡住上线——库从没规定这个顺序。正确用法：第 1 挡之后做一次模板（补覆盖面），第 3 挡之前做一次差距分析（补真实性）。

## 第 10 章　失效与恢复：这支库自己会怎么坏，以及 `04-incidents` 案例集怎么用

### 10.0 一句话先说透：一本讲别人怎么死的库，自己躺着十一条腐坏路径

前两章拆的是这支库**给别人**提供的诊断能力。本章拆它**自己**的病历。这件事有特殊的讽刺性：它收录的 `GOV-9`（纸面防线：护栏代码存在、测试全绿，但生产调用路径根本不经过它）和 `GOV-10`（评测集边界幻觉：考卷没造出来的场景，系统行为其实是未定义的，但所有人都以为会处理）——这两条正是它自己的确诊结果。[实测] 能用自己诊断自己，说明结构是对的；诊断完没吃药，说明缺一台执行器（第 11 章讲怎么给它补上，第 15 章讲为什么现在没有）。

「腐坏」在本章的用法：知识库不是二进制文件，不会突然打不开；它坏的方式是**内容还在、但内容与事实之间的关系断了**，而且断的时候没有任何东西报警。所以下面每条都写三样：怎么坏、包里现在有没有标本、坏的时候**早期征兆长什么样**（这是唯一能让你在自己库里提前发现的）。

### 10.2 腐坏为什么不报警：三条结构性原因

1. **它是纯文本库，没有装载校验**。宿主只提供「把文件读进上下文」，没有任何一处能「拒绝加载不一致的库」。所以不一致不会报错，只会在某个人照着流程走到第三步撞空时才现形（第 5.3 节第 4 跳）。[推演]（具体失效输入：给这个包加一次「上传校验」——格式全过：`name` 字符合规、description 未超上限、正文行数远低于五百行上限、分包结构正确、一层深引用。**没有一个校验器负责查「入口说 41、文件里 43」**。）
2. **视图是手抄的，不是派生的**。「源与视图」这套规矩本身是数据库规范化的思路（第 3.3 节），但规范化里视图是**自动**跟着基表变的；这里把自动那一步省掉了，只留下「记得要同步」的纪律。纪律的覆盖率等于「这次改的人想起来了」的概率。
3. **穷举型清单的漂移方向恰好是肉眼最不敏感的方向**。清单同步得最好的是「问卷」那一层（第 5 章覆盖率表里 05 是唯一满覆盖的），因为「少了一问」容易看出来；同步最差的是「药柜」和「字典」，因为**「少了一条药」不违反任何一条可见格式**——第 5.2 节那 10 条撞空就是这一类。

### 10.3 最锋利的一条：纸面防线的自指，和它给的解药

把 `GOV-9` 的原文描述和这个包的实际状态并排摆：

| `GOV-9` 描述的症状 | 本包对应的事实 |
|---|---|
| 护栏代码存在、测试全绿 | 「扩容防漂移」条款存在、变更史声明「全库 0 残留」 |
| 生产调用路径根本不经过它 | 没有任何脚本经过它——全库零可执行文件，条款的执行体是「改库的人记得去 grep」 |
| 它的对策：接线清单核对＋端到端防御测试＋防线注册表 | 本包需要的是：对账脚本（接线核对）＋一次能红的变异自检（端到端）＋一份机器可读的容量快照（防线注册表） |

三条对策，包内**一条都没实现**——而这个「一条都没实现」被它自己写成了条目、还编了号。[实测] 本页把这判定为**结构机会而不是道德缺陷**：一个诊断准到能诊断自己的分类法，说明它的抽象层级选对了（`GOV-9` 不是「Agent 特有的死法」，而是「任何靠文档维持纪律的系统共有的死法」，所以它也能套在库自己头上）；缺的只是把知识变成执行器那一步。这一步的具体做法在第 11 章写成可照抄的体检项。

### 10.5 案例集怎么用：抽象化是它能不能被复用的唯一开关

案例集的价值和它的风险在同一个地方——它写的是真实事故，所以有代入感；也因为是真实事故，所以**带着不可移植的细节**。直接用会撞三堵墙，抽象化就是把这三堵墙拆掉的动作：

**抽象化四步（照做即可）**[推演]（不做的失效输入：某人拿案例集里那条「客服机器人乱承诺赔偿」讲给自家风控听，风控第一句是「那是电商、我们没有退款接口」，讨论当场结束——案例被它的具体行业杀死了，而它本该讲的是「模型自述完成而错误被吞」这个根因）：

1. **剥三层，留一层**：剥掉主体（哪家公司）、剥掉载体（哪个渠道、哪个接口）、剥掉行业（哪类业务），只留**根因句＋后果句**。案例之所以能进库，就是因为它能被写成「在 X 条件下，没有 Y 就会 Z」。
2. **换成本项目的名词再讲一遍**：把根因句里的主语换成你系统里的真实组件。换不动，说明你还没看懂这条死法。
3. **反向用比正向用更值钱**：不要问「这个案例像不像我的问题」，要问「**我的系统里有没有一条通路，能让这个案例的根因在我这儿成立**」。前者是相似度匹配（会骗人），后者是通路核查（能落判据）。
4. **按标注规范登记自己那一条**：新增案例时写性质标签与置信度，编号必须现场扫描取号。这一步是案例集从「故事集」变成「证据库」的分界——没有标注规范，五年后没人知道哪条是真事。

**三类用法，各配一条禁忌**：

| 用法 | 具体动作 | 禁忌 |
|---|---|---|
| 说服与代入 | 给非技术干系人讲「别人真的这样死过、代价是什么」，比讲 43 条清单有效得多 | 别把**构造案例**当真实事故引用（`F-01…F-04` 是为了讲清机制编的，没有发生过）。[实测] |
| 归因参考 | 出事时先翻案例集找「同类根因」，比从 43 条里现读快 | 别把它当**导航唯一入口**——第 10.6 节那 24 条没有案例的死法，从这里永远找不到 |
| 判据种子 | 每个真实案例反推一条「如果当时有 X 就能提前发现」，喂给检查表加问 | 别只读不写——读完不产出新问，这一格就永远是历史书 |

### 10.6 案例集与 `01`／`02`／`03` 的引用关系（实测总账）

引用面是单向的：每条案例写一行「**命中死法**」，里面列 `XXX-n` 编号指回 `01`。案例集不引用 `02`（药柜），`02` 也不引用案例——**药柜和病历之间没有连线**。[实测]

由此算出三个数（数法：把 11 例的「命中死法」行全部抽出编号去重，再与第 4.1 节那 43 条全集求差集）：

| 指标 | 数 | 占比 | 判读 |
|---|---|---|---|
| 有至少一个案例的死法 | **19** | 44.2% | 病历覆盖不到一半 |
| **无任何案例**的死法 | **24** | 55.8% | 「有病名、有病理、没病历」是常态而不是例外 |
| 四层全齐（药柜有格＋字典有回链＋问卷有一问＋病历有案例） | **12** | 27.9% | **真正可整条复用的完整链路只有 12 条**——这是对使用者最该记住的一个数 |

三个具体后果：

1. **24 条无案例意味着「可探测度」这条信息在库里是空的**，而它本该参与排序（第 6 章讲的「严重度 × 修复成本」两乘数，其实少了业界那套方法里的第三个乘数「现有手段能不能发现它」——第 15.6 节会看到这套库借了前两乘、漏了第三乘）。`_` 有病历这件事本身就是「这条死法见过几次」的代理指标。[推演]（具体失效输入：某团队照库里的「严重度 × 修复成本」排序做防护计划，把一条严重度高、修复便宜但**库里 0 案例**的死法排到最后，因为它没有故事可讲；三个月后它成为本项目第一起事故。）
2. **`LOOP-2` 只有构造案例、没有真实案例，而两份评测件里那条行为标准答案恰好要求命中 `LOOP-2`**——也就是说：**评测的期望结果建立在一条「无真实病历」的死法上**。[实测] 这不说明答案错，说明评测集的取材面（第 11 章）与库的内容面是两条没对齐的轴。
3. **`03` 里存在指向案例编号的行**（有词条的 `详见` 写成「某条死法 / 某个案例号」这种双指）。一旦腐坏路径 5 兑现（新案例撞号），这类行就同时指两条记录，从词条跳过去会拿到错的病历。[推演]

### 10.7 恢复：库已经坏了怎么退（五级降级阶梯）

发现腐坏靠第 11 章的体检；**发现之后怎么继续干活**靠这一节。五级，逐级往下退，每级都要显式说一句「退到哪一级了」：

1. **`02` 查无对策** → 回读 `01` 该条的「对策」字段。**这一步实测是有效的**：那 10 条在药柜撞空的死法，方子全写在 `01` 里（第 5.2 节），只是没做成独立一格——有方子、没成药。反直觉但重要：**`01` 的对策字段比 `02` 更全**。库里没有写这条兜底路径，本页替它补上。[实测]
2. **`01` 的对策字段也只有一句话**（如 CONC-2 那种「显式依赖声明＋前置产物存在性校验」）→ 用 `03` 拿英文检索键出包搜业界做法，回来后按七字段格式自建一条，并回写 `01`（治理规矩本来就是这么长出来的）。
3. **`03` 也搜不到**（7.6 判据 3 那 7 条断链之一，或最新两条）→ 直接读 `01` 对应文件全文，放弃表格导航。
4. **数字对不上**（41 还是 43、3 份还是 4 份）→ **一律以现场复数为准**，并把对不上的那处登记为缺陷。任何一处文档的自述数都不得当作真值。
5. **版本分不清**（三处自述互不指通）→ 以「库内正本文件的现场内容」为准；**不许用版本号判新旧**（第 15.2 节会给出为什么：仓库本体与库内正本版本号同为 `v1.1.1` 而字节差 −359，版本号在这里连「哪份新」都答不了）。

一条底线：**五级里任何一级都不许「沉默」**。走到第 3 级还查不到，正确产出是一句「本库暂无成文对策，已登记为缺口」＋新条目回写，而不是「库里没有这件事」。库对这 23% 的撞空目前给的回应恰恰是沉默——这是第 11.2 节把「撞空可见性」列为第一条体检项的原因。[推演]（具体失效输入：SEC-2 命中、`02` 撞空、无人声明缺口 → 实践者随手写一个正则过滤外部内容并在评审里报告「已做注入防护」；包外看这个项目的防护面是「有」，实际是一条库根本没登记的自制防线，也就是 `GOV-9` 的新个体。）

## 第 11 章　例行维护与体检：怎么验证它真在生效而不是躺在盘上

一个「查得到的库」和「用得上的库」不是一回事——前者只要文件在，后者要求它有回归装置。这支库恰好带了两件装置、也恰好暴露了它们的老化方式，本章按这两件事写。

### 11.1 库自带的两件体检仪（实测两件的内容形状）

| 件 | 条数 | 每条字段 | 测的是哪件事 |
|---|---|---|---|
| `eval_queries.json`（顶层） | 16 | `id`／`query`／`should_trigger` | **触发**：这句用户话该不该把库叫起来。8 条应触发（正例）＋8 条近义干扰（负例，例如「帮我写一个打印 1 到 100 偶数的 Python 循环」「解释熔断器在家用电路里的作用」） |
| `evals/evals.json`（子目录） | 3 | `id`／`prompt`／`expected_output`／`assertions[]` | **产出**：叫起来之后交付对不对。例如那条「翻页工具反复调两百多次、每页结果一样」的题，断言要求命中 `LOOP-2`、引用 Livelock、给立即止血动作、给状态指纹／迭代上限／熔断器组合、并提示按标注规范归档进 `04` |

两件都是 [实测]（条数字法：数 JSON 里 `"id"` 键出现次数——顶层 16 次、子目录 3 次；字段名逐条比对两份文件）。它们测的是**两个不同维度**，不是同一件事的两份拷贝——这点很重要，第 15 章会把「两份并存」的真实缺陷讲准（缺陷是**互不引用、编号撞车、入口未登记**，不是「重复」）。

`CHANGELOG.md` 的 v1.1.1 节登记了首轮实测结果：**应触发 8/8 全中（触发率 1.0）、近义干扰 0/8 误触发，双指标满分**；另有独立子代理对全文通读逐项核对数字，打分 94/100、A 级。同节还写了一条设计意图：「可验证性从无实测设计升级为有可重复的触发／输出回归测试产物，此后每次改 description 或内容都可回归验证，不再凭感觉」。[实测] 这句话是这支库区别于「一堆提示词」的地方——它给自己装了尺子。

### 11.2 但这把尺子今天量不到新长出来的东西（可当场复算的三处）

1. **触发覆盖面停在 v1.1.1 的靶子上**。库之后长了两次（v1.1.2 元教训节、2026-09-29 的 41→43），`eval_queries.json` 一条没加。实测：16 条题里**没有任何一条问的是企业级场景**（最接近的是「Agent 要接第三方 MCP 工具，有什么安全风险」，它测的是 SEC 类不是 GOV 类）。「8/8 满分」因此测的是旧能力——**这正是 GOV-10（评测集边界＝能力边界幻觉）对这支库自己的那一版**：考卷没造出来的场景，触发行为是未定义的，但所有人以为会触发。[实测]（具体失效输入：用户说「我们的 Agent 要上多租户，A 客户不能看到 B 客户的数据」——`SKILL.md` 的 description 里明写了「多租户」是必触发词，但评测集里没有这条正例；哪天改 description 时把「多租户」删了，这套题依然全绿。）
2. **`id` 命名空间撞车**：两份文件都用 `id: 1..N`，含义完全不同（`eval_queries.json` 的 `id:2` 是一句触发题，`evals/evals.json` 的 `id:2` 是一个行为断言）。任何「评测第 2 条过了吗」的对话都无法定位。[实测]
3. **断言里硬编码了死法编号**（`命中死法编号 LOOP-2`、`命中 GOV-3`）。库自己的编号规则是「新增接续最大号」，不会改旧号，所以这条风险目前低；但只要有一次改名或合并条目（`CHANGELOG` 的 ADR 里没禁止），这三条断言就会**静默指错**——它不会报错，只会判错。这就是本工程口径禁用行号引用、库内断言却在硬编码编号的同一类病。[推演]（具体失效输入：把 LOOP-3 并进 LOOP-2，`evals/evals.json` 那条断言仍写 LOOP-2 且仍「通过」，但它现在实际覆盖了假进展那条的判据，回归测试的含义变了而没人知道。）

### 11.3 视图勾稽：四条能机械跑的判据（本页给算法，不替库跑成绿）

「勾稽」＝两处数字能对上。库的治理规矩（先改 01 再同步视图）是纸面承诺，下面四条把它变成可判定的检查（判据＝能机械回答过／没过的标准）。这四条是本页给的工程建议，不是库里已有的脚本 [推演]，每条附「不跑会怎样」：

1. **容量勾稽**：`01` 七文件的 `### X-N` 标题行数 ＝ 入口文档与四张检查表里出现的每一个「条数」数字。本条今天**红**：同一句流程指令里 41，另一句里 43（第 3.2 节、第 15 章）。
2. **反向覆盖勾稽**：`02` 全部「防」字段里的 FM 编号并集 ⊇ `01` 全集。今天**红**：33／43，缺 10 条（第 5.2 节）。
3. **术语同步勾稽**：`01` 每条「术语」字段里的每个英文词，逐字在 `03` 里出现 ≥1 次。今天**红**：一批零命中（第 7 章实测）。
4. **留痕载体勾稽**：`05/上线前检查` 的门禁项集合 ＝ `05/上线验收记录表` 的行集合。今天**红**：6 项企业级附加 vs 4 行表格，掉的是 12a／12b（第 9.5 节）。

这四条的价值不在「发现红」，在于**红会随扩容自动出现**——只要库继续长，不跑勾稽就必然漂。而漂移的表现形式恰好是库自己讲的两条死法：GOV-6（没有基线的静默滑坡）、GOV-9（防线存在但没接线）。**知识库也在它自己的失败模式清单覆盖范围内**，这件事第 10 章展开。

### 11.4 一条必须写死的尺子教训：否定判据最容易恒真

「恒真」＝怎么测都显示通过。库的体检若要查「包里有没有垃圾件」，最常见写法是按后缀相等匹配（文件名结尾正好等于某个备份后缀那种）。**这种写法会永远绿**：真实的备份件尾巴不是那个后缀，而是后缀后面又挂了一段日期，于是「后缀等于」这条判据对它零命中，脚本欢快地报告「没有备份件」。[实测]（这条是 2026-10-09 主控方在本包上撞到的实例，细节见第 15 章的包卫生条。）

正确的写法只有一句：**否定型判据必须配一条正例校验**——同一个脚本里塞一个已知会被命中的样本，跑完检查「它确实命中了」，否则本轮的「没查到」不作数。本工程口径里这类要求叫「防假绿」；对知识库体检而言，它比多写几条检查更重要，因为**一个永远绿的检查会让人以为已经查过了**。

### 11.5 例行维护动作（改库的人要做的顺序，按库内规矩重摆一遍）

1. 先改 `01`（新增编号接续该类最大号），**同一次改动里顺手**把 `02`/`03`/`05` 对应格同步——治理规矩说的就是这一跳。
2. 数字类改动（条数、分类数）要**全库 grep 旧值**再逐处更新，这是 `SKILL.md` 「扩容防漂移」那一条的原文要求；今天它没被执行到底，于是留下 41／43 两个数并存。[实测]
3. 交叉引用（「见 XX-YY」「R-XX」）要对着索引表核验，不许凭记忆写——同样是那条规矩的后半句。库里自己就栽过一次：写 `SEC-6` 那条时把引用的案例号凭记忆写成 R-07，实际应为 R-05，`CHANGELOG.md` 的「元教训 2」把这次错记在案 `[实测]`——写的时候毫无感觉，回头读才发现指针断了。
4. `CHANGELOG.md` 追加要**带版本号**，别写裸日期节。2026-09-29 那次扩容只留了一个「日期式标题」的节（没有版本号），而 frontmatter 至今仍是 v1.1.1、最后一个带号节是 v1.1.2——这就是「三处版本自述各说各话」的直接成因（第 15 章对账表）。[实测]
5. 改了 `description` 触发词或正文能力面，**必须回头加对应评测题**，否则 11.2 的覆盖面缺口只会变大。库里没写这条纪律；本页把它列成维护项，因为它正是现有那份满分的评测件失效的方式。[推演]

### 11.6 「它真在生效」的三条可观测信号（对使用者，不是对库）

没有跑脚本也能判断这支库是不是躺在盘上：

1. **有没有《风险清单表》产出**。第 5 步门禁的强制交付物；没有它，说明只翻了清单没做决策。信号强度最高的细节是那张表里**有没有「本轮不处理」的行**——一个真跑过的项目一定会有欠账行（库里明写这行不许删，留着当已知风险台账）。全是「处理」＝大概率没真填。[推演]
2. **`01` 里有没有你项目新增的条目**。排错时检查第 5 步强制要求把根因按七字段回写进 `01`。用了三个月而库里一条没多，说明工作流只走了前三步。
3. **验收表里有没有落点**。`上线验收记录表` 要求每格填「护栏落点＋证据」；若交回来的表只勾了 ☐ 而落点列空着，就是「纸面验收」——同一支库在 GOV-9 里描述的那个病，用它自己的表格犯了。

第 14 章会把这三条压成一行，方便每次收工时扫一眼。

## 第 12 章　端到端走查：一个具体故障从进来到出去

本章只干一件事：**把第 5.3 那条检索路径用一条能照抄的输入真走一遍**，每步指到具体文件与字段名，最后给出产出的形状。场景是构造的（虚构工具名与数值），走法全部来自库内条文。

### 12.0 输入（可以直接贴给 AI 的那句话）

> 我们的工单整理 Agent 卡死了。日志显示从凌晨 03:12 起它反复调用翻页工具 `ticket.list`，两百多次，每页返回的都是同一批 50 条工单；token 已经烧到 180 万，任务没结束，也没报错。

三个信息点决定后面全部走向：**没报错**（排除 ERR-1 那种「工具持续失败」的显式路径）、**每页结果一样**（这是进展判据的核心证据）、**已经在烧钱**（COST 类同时成立）。

### 12.1 第 0 动作：先止血，再归因（`05/排错时检查` 第 2 步明文要求）

- **立刻手动 kill／触发 kill switch**，不要边查边跑——原文是「先止血再归因，不要让它在排查期间继续烧钱」。
- 停手后马上查现场残留（`ERR-4`）：这个任务是只读翻页，磁盘残留风险低；但如果它此前已经**回复过工单**，就属于有副作用的写操作，要按 `COST-3` 核对幂等键有没有盖住——否则重启会重复回复同一批工单（真实副作用，不是浪费钱那么简单）。
- 顺手记一条：**这一停就回答了上线前检查的 G8**（有没有总开关、停了之后现场是否干净或可恢复）。如果刚才发现「根本找不到 kill 的地方」，G8 当场不成立，这条要写进《风险清单表》。

### 12.2 定位与判循环（排错时检查第 1、2 步 → 归到具体死法）

按那张表的判据机械走：

1. **定位**：最后一行日志停在 `ticket.list` 的第 N 次调用 → 它「在跑」不是「没在跑」→ 按原文分岔去判循环，不去查依赖。
2. **判循环**（原文给的数：数最近 20 轮，同一工具＋同参数出现 ≥3 次即命中 LOOP-1/2）：本例 200 多次同参翻页 → **命中**。
3. **到底是哪一条，取决于它的指纹怎么算**——这是本例最值得抄的一个判据分叉（`[实测]` 依据在 LOOP-2／LOOP-3 两条的根因字段）：

| 它有没有装状态指纹 | 指纹里收了什么 | 命中的死法 | 为什么 |
|---|---|---|---|
| 没装 | — | **LOOP-2 活锁** | 没有任何无进展判据，光靠「看着在忙」当然停不下来 |
| 装了，只收语义状态（页码参数＋返回内容） | 每轮全同 | **LOOP-2**，且检测本该触发 | 说明计数／熔断没接进主循环 → 同时命中 **GOV-9 纸面防线** |
| 装了，但把 `request_id`、时间戳也收进去了 | 每轮都不同 | **LOOP-3 假进展** | 噪声字段掩盖了「其实啥也没干」，这正是 P-02 误区栏写的那件事 |

一句判读：**同样是「卡住」，三种现场对应三种修法**——第一种种计数器，第二种接线，第三种改指纹的取字段。归因错了会白装一层防护，而且新装那层本身又是一条死法。

4. **代价归因**：`COST-1` 的根因字段直接写着「循环类死法（LOOP-1/2）的代价最终都体现在这里」——所以 180 万 token 不是另一条病，是同一条病的账单面。12.6 的风险清单表里两者严重度不同、根因同一个。

### 12.3 命名（第 2 步工作流）：拿到能搜药的键

从 `01/FM-循环与终止` 抄出的权威键：**Livelock／Non-progress detection**（活锁／无进展检测），假进展那条是 **Pseudo-progress／Progress metric**；账单面那条是 **Budget governor**。这三个词一拿到，包外的成熟做法（无进展检测、熔断器语义、预算闸）都能直接搜到——这就是「问题有了名字才能搜到现成的药」的字面收益，也是 `03-terms` 存在的理由。

### 12.4 选药（第 3 步）：按「止血→判据→计数→升级」的顺序落五条

| 顺序 | 对策 | 库给的示例值 | 本项目的实际取值（走查里现填） | 为什么是它 |
|---|---|---|---|---|
| 1 | **P-06 熔断器**（止血） | 连挂 5 次、熔断 5 分钟、**人能收到通知** | 同一工具**连续 5 次零新增工单 id** → 暂时移出可用工具列表，并告警到值班群 | 判据从「失败次数」换成「无进展次数」，因为本例工具一直在「成功」返回 |
| 2 | **P-02 状态指纹**（判据） | 存最近 N=5 个 | 只收 `{页码参数, 返回条数, 返回内容哈希}`，**显式剔除** `request_id`／时间戳 | 12.2 表第三行的病就出在收了噪声字段 |
| 3 | **P-03 进展度量**（判据兜底） | 连续 3 轮不降判无进展 | 指标＝已见工单 id 去重数；连续 3 轮增量 0 → 判无进展 | 防 LOOP-3 绕过指纹（库在 LOOP-3 对策字段就是这么写的） |
| 4 | **P-01 迭代上限**（计数） | `MAX_STEPS=25` | 两层：**单工具 20 次**＋**全局 60 步**（200 页的真实规模下 25 会误杀，所以取「预计轮数×1.5」）；到期必须报告「已尝试 N 步、进展是什么、产物在哪」 | 库的误区栏：只设上限不设「到期说什么」＝停了也没用 |
| 5 | **P-07 预算控制**（计数） | $2 或 200k token | 单任务硬上限 300k token，**每次调用后读 usage 累计**，超限立即收尾 | 本例烧到 180 万说明根本没读 usage——「只在任务开始时看一眼价格表」正是 P-07 的误区 |
| 6 | **P-17 策略升级**（升级） | 同法失败 3 次强制换路 | 连续 3 次无增量 → 强制换策略（改用增量查询参数或上报人工），禁止第 4 次同样翻页 | 计数器只能停手，不能自救；这条负责「换路」 |

顺序不能倒装：先装计数器再定判据，只会得到一个「爱误杀又拦不准」的开关。**每条对策的阈值都来自 01 的根因字段，不是拍脑袋**——这是第 5.3 节那句「病理对剂量」的具体展开。

### 12.5 接线验证（第 4、5 步之间必须插的一格，因为本例的病就是它）

`01/GOV-9` 的检查问题原文是：「列出每条防线，从生产入口 grep 调用链——流量真的经过它吗？」本例走一遍：

- `MAX_STEPS` 这个常量在代码里存在、单测里也测过（直接调那个函数是绿的），但**主循环从来不调用它** → 生产路径不经过防线。
- 于是本例**同时命中两条死法**：LOOP-2（行为表现）＋ GOV-9（为什么装了还没挡住）。这不是凑数——`01/GOV-9` 的现象栏写的正是「熔断器没人调用、退避装饰器是死代码、预算闸门没接到入口……测试全绿因为测试测的是组件」。
- 复现证据的做法（可照抄）：从生产入口（真正的那个循环函数）出发 grep 每条防线的调用点，逐条登记「入口 → 组件」链路；再做一个端到端防御测试：**故意注入一个每页返回相同结果的桩工具，看任务会不会在第 20 次被掐停**。会停＝接线通；不停＝纸面防线。

### 12.6 产出形状（第 5 步门禁的交付物：《风险清单表》，七列，库里给了列名和示例行）

| 编号 | 现象 | 严重度 | 术语 | 解法 | 修复成本 | 本轮是否处理 |
|---|---|---|---|---|---|---|
| LOOP-2 | 200 多次同参翻页、无进展 | 高 | Livelock / Non-progress detection | P-01 迭代上限＋P-02 状态指纹（剔噪声）＋P-06 熔断 | 计数器级（约 10~20 行） | 是 |
| LOOP-3 | 每轮 request_id 变化绕过检测 | 高 | Pseudo-progress | P-03 进展度量（去重 id 增量，连续 3 轮为 0 判停） | 中等（需一个小模块） | 是 |
| COST-1 | 单任务 token 180 万、无实时累计 | 高 | Budget governor | P-07 每次读 usage、300k 硬上限、超限收尾报告 | 计数器级（约 5 行） | 是 |
| GOV-9 | 上限代码存在但主循环不调用；测试全绿 | **最高** | Dead code defense / Wiring gap | 接线清单核对＋端到端防御测试（注入同页桩工具验证会停） | 中等（要改测试入口） | 是 |
| ERR-4 | 强杀后遗留未释放的分页游标／锁 | 中 | Orphaned state | P-16 清理钩子（正常与异常退出都触发） | 中等 | **否**（登记为已知欠账，不删行） |
| SEC-4 | 该 Agent 能直接回复工单（外部可见、不可逆） | 高 | Human-in-the-loop | P-10 权限门三级：草稿先行＋不可逆必确认 | 架构级 | 否（本轮先关回复权限，只留读取） |

- 排序规则按库内原文：**严重度 × 修复成本，先做「高严重度＋计数器级」**——本例就是 LOOP-2 与 COST-1 那两行（合计约 15 行代码），这是性价比最高的三两件事。「本轮不处理」的行**不许删**，留着当已知风险台账。
- 「修复成本」三档的取词来自 `06/差距分析`：计数器级＝一个计数器或一个 if；中等＝需要独立小模块；架构级＝要改整体设计。报「架构级」要先回答那句逼问：「计数器级真的挡不住吗？挡不住的最小反例是什么？」本例 SEC-4 的答案是「挡不住」——因为要防的是外部可见的不可逆动作，不是重复调用。

同时产出**十问的复答**（`05/上线前检查` Q1／Q2／Q6 三问在这一事故上被现场证伪：Q1「5 分钟内怎么发现」实际是 4 小时；Q2「超预算了吗」没有实时告警；Q6「有用户在等它吗、等待有反馈吗」没有）——这三问的答复现在变成验收表里的落点行：心跳日志在哪个文件、预算阈值在哪个配置键、告警发到哪个渠道。

3. 新死法：**没有**——本例所有表现都被现有 43 条覆盖，这一步要**显式写下「未命中，因为……」**（这是设计时检查「不命中也要说理由」那条规矩在归档步骤的延伸）。

## 第 13 章　反模式清单：不要这样用这支库

每条给「错误用法 → 后果 → 库内哪一条本来就在讲这件事」。多数反模式的病根本库自己有药，只是没人接上（这正是 `GOV-9`）。

1. **只读 `SKILL.md` 那 75 行就以为「用过了」**。后果：一个具体故障进来，你手里只有路由表没有清单，仍然靠现场即兴。这支库的本体是 `references/` 里那 16 个文件、约 94,700 字节，`SKILL.md` 只是发牌员。
2. **把库当「上线前一次性过一遍的表」**。后果：打勾那一刻全绿，之后模型换了、prompt 改了、依赖升了，没有任何东西会再报警——这就是 `GOV-6` 无评估基线的静默漂移。库要求的用法是**每次改动都重跑第 3 挡**，并把考卷（固定样例集）留在项目里。
3. **穷举时「不命中」留空**。后果：跳过＝盲区伪装成已检查。`05/设计时检查` 用法规矩原文是「不命中也要说理由，直接跳过等于没查」——因为最危险的漏不是漏了想不到的，是漏了**你以为不可能但其实通着一条对外通道**的那类（13.4 的 SEC-7 就是典型）。
4. **照入口文档的「41 条」数一遍就宣布穷举完成**。后果：少问两条（GOV-9／GOV-10），而这两条恰好是企业级最容易确诊自己的那两条。**用清单，不要用清单的条数**——直接打开 `01` 的七个文件按标题行过。
5. **先上复杂检测算法，后补计数器**。后果：算法自身成为新故障源（它要模型自评＝多花一次调用、要阈值＝凭空拍、要标注集＝又一条 GOV-6 依赖）。库里两处（`SKILL.md` 第 3 步、`02` 使用说明）都把「计数器级永远优先」写成了硬规矩，违反它的代价不是「不够聪明」而是「挡不住还多一层没接线的代码」。
6. **装了上限但没写「到期说什么」**。后果：任务被掐停、用户拿到空白、日志里只有一行 `max steps reached`——可观测性等于零（`CTX-5`），而且没人知道这算故障。`P-01` 的误区栏专门写了这条。
7. **拿指纹的「输出有没有变」当进展**。后果：`LOOP-3` 假进展必漏——只要指纹里混了 `request_id`／时间戳这类噪声字段，每轮都「变了」，检测恒不触发（恒真）。修法是只收语义状态＋另设一个「离目标多远」的标量。
8. **在排错挡找安全类／治理类答案**。后果：耗掉凌晨三点的时间却查不到——那些病的证据不在现场（第 9.2 的覆盖矩阵显示排错挡 SEC／CONC／GOV 三类零覆盖）。正确做法：排错挡只做止血＋归因，安全与治理问题留到第 3、4 挡处理。
9. **把术语表当权威引用对外讲**。后果：被一句「来源呢、哪个版本」打穿。第 7 章当日核实已给出标本：外部分类法的**条数**在库内写错，且引用处没有「来源／版本／访问日期」字段可依附。用法：术语表当**搜索键的提供者**用（拿到英文名去搜原文），别当**引文**用。
10. **在视图（`02`／`03`／`05`）里改知识**。后果：下次从 `01` 同步时被覆盖，或更糟——留下两份各说各话。库的规矩写死了：只改视图不改 `01` ＝违规。同一类「在下游改而不动上游」的毛病，库里有实物教训：`SEC-6` 引用的案例号凭记忆写错（应为 R-05 写成 R-07），直到复读才被看见 `[实测]`。
11. **把验收表抄进项目后，又拿升级过的库去回填已归档项目**。后果：历史证据被现在的标准改写，审计链断裂（`GOV-2`）。`05/上线验收记录表` 的版本锚定条款正是为此写的：归档即锁定，库升级不追溯。
12. **给非 Agent 项目也上八项硬门禁**（纯前端页面、单脚本、纯数据分析）。后果：门槛成本压过收益，团队整体弃用这套库——这比不装更糟。`SKILL.md` 的边界节和验收表的配载标记都留了这个出口（非 Agent 项目整表标注不适用）。
13. **把 `06-prompts` 生成的问题硬套编号**。后果：只能问出库里已有的东西，第 4 步查漏当场失效（那两份模板刻意不带死法编号，实测引用数为 0~1，见第 9.6）。正确用法是让 AI 先自由列，再回过头给它们找编号；找不到编号的新问题就是候选新条目。
14. **口头引用「评测第 2 条」而不说文件名**。后果：两份评测件各自有 `id: 2`，含义完全不同（一个是触发题，一个是产出断言），沟通直接错档（第 11.2 第 2 条）。任何跨文件的编号引用都要带文件名。
15. **把《风险清单表》填成全部「本轮处理」**。后果：那张表失去了它真正的功能——**决策**。库里明写「本轮不处理的行不许删，留着当已知风险台账」；一张没有欠账行的表，大概率是没真填或者被事后美化过，验收时应当反过来追问「凭什么一条都不欠」。[推演]（具体失效输入：接手一个三个月前的验收单，全表「是」，但线上仍跑着裸权限的不可逆操作——说明当时是照着「让表好看」填的，不是照着风险填的。）

### 14.4 计数器三件套（第一晚就该装上的，库给的示例值）

## 第 15 章　工程与安全规范：三处版本自述、两份评测检索件、一枚备份件与仓库字节差

前面十四章讲「这条死法怎么治」；本章只讲一件事：**这支库作为一包要被分发出去的东西，它自己的元数据、包卫生（一个包里那些不该带上的副本、垃圾件、可定位信息）与安全边界，能不能让人相信**。这是本页唯一一处「库自己的条文救不了自己」的地方——第 10 章那些腐坏路径至少还能对到某条条文，这一章的三件事没有条文兜着。

### 15.1 三处版本自述的对账：一个缺项、两处不一致

| 位置 | 它自己报什么 | 能不能当版本证据用 | 为什么 |
|---|---|---|---|
| 入口文件头部元数据（frontmatter，即文件顶端那段机器读的键值） | `v1.1.1` `[实测]` | **能认身份，不能判新旧** | 同一个字符串在两枚内容不同的副本上都出现（15.2） |
| 入口正文那 75 行 | **未检索到**任何独立的版本号自述节 `[实测]` | 不能，正文对「我是哪一版」保持沉默 | 三处里这是空位，不是第三个答案 |
| `CHANGELOG.md`（20,189 字节） | 按文件顺序读到的**第一个带版本号小节是 `v1.1.2`** `[实测]` | 半能：它是「最新的**带号**节」，不等于「最新的**内容**节」 | 见下面那段结构说明 |

对账结论照实写：**元数据的 `v1.1.1` 与 CHANGELOG 的 `v1.1.2` 不一致**；而 CHANGELOG 里还有一个既晚于 `v1.1.2`、又完全没有版本号的日期式追加节（就是 41→43 那次扩容，附录把它登记为「只有日期标题、无版本号的那一节」）。所以三处不是「三个版本号互相打脸」，是**两个号 + 一次没号的真改动 + 一个空位**——比单纯的号不一致更难查，因为没有任何一处会报错。

🔴 为什么不能按「文件开头第一个版本标题」取最新 `[实测]`：这 20,189 字节的头部约一半不是版本叙事，而是六条决策记录（ADR＝「当时为什么这么定」的留痕条目）与四套外部框架的原文摘录；最新的**带号**节落在文件中部；最晚的**内容**改动以日期标题挂在尾部且不带号。按「开头第一个号」取会得出 `v1.1.2`，而它比尾部那次追加**更旧**。

[推演] 具体失效输入：选型会上有人问「这库还在动吗？要不要等下一版？」。查元数据答 `v1.1.1`（看着像半年没动），查 CHANGELOG 首节答 `v1.1.2`——两个答案都会让人以为「41 条变 43 条」那次扩容还没发生，而新增的 GOV-9／GOV-10 其实已经躺在包里，正是本包最承重的那两条。

**结论一句话**：在本包上，「版本号」这个字段已经不能回答「哪个新」这个问题，只能回答「两边都自称同一版」。可判别的只剩内容指纹与字节数（库内正本 md5 前缀 `4df6b31de8e4`、7,610 字节）。

### 15.2 仓库本体与库内正本：−359 字节，版本号完全相同

| 一侧 | 字节数 | 头部元数据报的号 |
|---|---|---|
| 库内正本（随包分发的那份入口） | 7,610 `[实测]` | `v1.1.1` |
| 仓库本体（同一支 skill 在代码仓库里的那份入口） | 7,251 `[实测]` | `v1.1.1` |
| 差额 | **−359** `[实测]` | **0** |

这就是**静默漂移**（silently drifted，指两份内容已经不一样，而你用来判身份的那个字符串一点没变，所以任何按号做的检查都不会报警）：号相同、字节不同，而且差 359 字节不是换行符风格能解释的量级 `[推演]`——359 字节按这个文件的中文密度约等于七八行条文，够删掉或补上一整条检查项。

后果分三层，逐层都能落地：

1. **锁版本这件事在本包上锁不住内容**。门禁 G12（供应商与模型版本锁定那类「把外部依赖钉死」的动作）要求锚一个稳定标识；如果你在项目的验收表里写「库版本 v1.1.1」，你钉住的是一枚**两边共用、却不指向唯一内容**的字符串。[推演] 具体失效输入：A 团队从仓库取、B 团队从包里取，同一句「按 SEC-7 的第三条」在两侧指向不同措辞，双方都认为自己合规，排错时互相甩日志——这条冲突在库的任何一张检查表里都没有格子。
2. **本页的引用规则因此必须收窄**。本页所有「来自哪一侧」的判断都按口径复测表报字节，而不是按号；「仓库那份是不是较旧」这种因果说法**本页不写**——359 字节的正负方向只说明两侧不同，不说明谁先谁后（未检索到第三方时间证据）。
3. **修法很小但必须写**：锚值字段该填「内容散列 + 字节数」，号只当给人看的标签。这一格现在的写法（锚一个日期式版本号）锚的是不可判别的字段——这是 9.5 说的「派生版本锚定」那条规矩，在元数据层自己犯了同一个病。

### 15.3 那枚日期式 `.bak` 备份件：一个包卫生缺陷，加一把失效的尺子

**第一层事实（缺陷本身）** `[实测]`：递归 21 个文件里混着一枚入口文件的备份副本，后缀不是干净的 `.bak`，而是在 `.bak` 后面又挂了一段日期。它的字节数是 7,618，比正本 7,610 多 8 字节——**连「字节级副本」都算不上**，是第三份内容略有差异的文本。对读者的实际影响有三条：同一份条文在包里出现两处、两处可以各自漂；检索时会命中两遍；它会随「整包分发」一起外流。而用复制文件来做版本管理，本身就与库里 ADR-5「单一事实源、禁止知识多副本各说各话」那条硬约束相反——**这条包卫生缺陷犯的正是本库自己立的规矩**。

🔴 第二层事实更值得写：**发现它的过程中，第一版检查尺子是失效的** `[实测]`。主控方第一版「垃圾件扫描」按「后缀**正好等于** `.bak`」匹配，对本包零命中，于是全库报告里写的是「无备份件」——一个假绿（false green，指检查报「通过」但问题就在眼前）。原因只有一个字符的差距：真实后缀后面多挂了日期。

抽象成可复用的判据（这条适用于任何「扫全库看有没有 X」的否定结论）：

- **用「相等」来证明「不存在」，只要真实命名有变体，这条判据就永远绿。** 相等匹配只能证明「完全长成这样的东西没有」，而你要证的命题是「任何形式的这种东西都没有」——两个命题不等价，差的那一截就是漏口。
- 修法一：**改成子串／前缀／后缀匹配**（后缀里只要出现 `bak` 就命中），并且**把变体列成清单**而不是只写一条模式。[推演] 具体失效输入：后缀在 `bak` 之后又接了一个点和一串日期（原文件名此处刻意不抄全）；`x.md,old` 与 `x copy.md` 连「后缀含 bak」都逃过——所以子串匹配是必要条件，不是充分条件。
- 修法二：**正例校验**（先自己造一个已知该被抓的东西放进去，确认尺子真的会红，再拿它去扫）——这一步不能省，因为它把尺子从「返回绿的」变成「能返回红的」。
- 修法三：**变异自检**（拿着已知样本，把它的名字改出几个花样：尾巴加日期、大写 `.BAK`、结尾加 `~`、去掉点号），尺子必须**每个变异都仍然命中**；只要有一个变异不命中，就说明这条否定结论的覆盖面是按你的想象画的，不是按现实的。
- 这三条与第 11.4「否定判据最容易恒真」那条教训是同一个病的两种表面：**判据只覆盖了出题人想到的输入，于是永远给出通过的答案**。

隐私处理说明（本页自己的规矩，也是给读者的示范）：按公开分发红线，这里只写「存在一枚日期式 `.bak` 备份件」这个**类别**，不抄它的完整文件名、也不抄那串日期——判据是「读者拿到这串字符能不能定位到我这台机器上的一个具体东西」，能，就不能写。字节数与内容散列可以公开，因为它们只指向内容，不指向路径。

### 15.4 两份评测检索件的逐条比对：题库齐了，秤一根没有

11.1 已给两件各自的形状，这里只做**比对与勾稽**（勾稽＝两处数字能不能互相对上）。

| 比什么 | 顶层那份（1,747 字节） | 子目录那份（1,777 字节） |
|---|---|---|
| 测的是哪一层 | **触发层**：给定一句人话，应当把哪个文件取出来 | **行为层**：真的被触发之后，产出里必须出现什么 |
| 条目形状 | 16 条「输入 → 期望文件」的检索题 | 3 个用例，每例配 4 条**散文式断言**（人写的自然语言判句，不是可判定的表达式） |
| 编号 | 自成 `id: 1..N` | **也**自成 `id: 1..N` |
| 有没有跑测的东西 | 无 runner（没有可执行脚本）、无阈值（没写「几条算过」）、无结果件（没有任何一次跑过的记录） `[实测]` | 同左，三项全缺 |
| 互认 | 不引用对方 | 不引用对方；两份都不在入口那八行路由表里 `[实测]` |

四条比对结论：

1. **编号冲突是本包最容易咬人的一条** `[实测]`：两套完全不同的题共用同一形状的主键，口头说「评测第 2 条挂了」无法定位到哪个文件。这就是 13 章第 14 条反模式的成因，也是「跨文件引用必须带文件名」这条规矩存在的理由。
2. 🔴 **负例与自己写的必触发词字面相撞** `[实测]`：顶层那份里，标为「不该触发本库」的一条负例，用的说法是「家用电路熔断器」；而入口元数据那段描述（决定它什么时候被自动取用的那句话）里，必触发词表就含「熔断器」三字。任何按关键词做自动命中的宿主，都会在这条负例上**触发本库**——负例当场失效。这条不是「负例设计得太难」，是**题目和路由串在同一份包里互相不知道对方的存在**。
3. **正例覆盖不到触发面** `[实测]`：被当作正例那批里，8 条中有 7 条不含那几个必触发词。于是这套题实际测的是语义相似度，测不到关键词命中；反过来说，第 2 条那种字面碰撞永远不会被自己的题抓到。
4. **派生声明与实物不对账** `[实测]` + `[推演]`：`CHANGELOG.md` 把这两件的引入登记成「质量体检升级」，并给出「可回归验证」这类能力宣称；但回归（regression＝改动之后重跑同一套题，确认老功能没坏）要成立需要三样：固定的题、跑题的东西、上次跑的结果。包里只有第一样的一半。所以那句宣称**在本包状态下不可核**——注意结论的分寸：不是「评测是假的」，而是「**评测这套防线没接线**」，正是 GOV-9 描述的那个病，出现在它自己的体检仪上。按官方写作规范的建议配比（8–10 条正例 + 8–10 条负例），顶层那份 16 条的量级够用；不足的是「负例被自己的触发词打穿」和「没有一次真跑过」这两件事，不是条数。

| `references/` 与 `evals/` 两处的正文逐条内容 | 本轮按取证边界未逐条读；凡涉这两处的数字只取自已复核的检索产物，取不到的一律写「未检索到」，不补数、不补分类名 |

### 15.7 分发前必须过的一道脱敏检查

把这支库当**对外产物**发出去时（贴进公开文档、随仓库分发、交给供应商），有三类内容不该带出去，且本包现状带着其中两类：

1. **可定位串**：绝对路径、真实账号名、对具体人的称呼、机器生成的带日期备份件名。判据照 15.3 那句——能定位到这台机器上的一个具体东西，就是泄漏。清除成本会被那枚副本放大：同一条串出现在两个文件里，清了一处漏一处（这是「多副本」在**安全**层面的代价，不只是条文漂移）。[推演] 具体失效输入：脱敏脚本按文件清单逐个跑，但备份件不在清单里（它不在路由表上，也没人把它当正文），于是整包发出去后仍能搜到原始路径。
2. **凭据形状**：本包**未检索到**任何密钥、令牌形状的内容 `[实测]`；但库里大量出现「不要打印 API Key」这类句子，一旦被人直接复制示例去跑，风险来自复制行为而不是包本身。
3. **不可核的外部宣称**：本包对外部分类法条数写错的标本（第 7 章那处，外部分类法摘要给 14 条、库内两处写 16 条 `[实测]`）在**内部使用**时只是个小错，一旦进客户交付物或合规文档就变成可被一句「来源呢」打穿的实质问题。规矩：凡引外部数据，必须带「来源 + 版本 + 访问日期」三件套，这三样字段在术语表的四列结构里并不存在，只能靠引用者自己补。

一句收束：**这一章的四件事（号不一致、字节已漂、备份件带着副本外流、评测只有一半）合起来就是 GOV-9 那句话的自证**——写下来的防线，和生产路径上真的会经过它的防线，中间那一格没人接线。第 11.3 那四条勾稽判据、15.3 那三条尺子修法，是给这一格能拿出来的最小实现（最小实现＝不引入新模块、只补几条检查动作的版本）。

### 15.8 接力补测：把 −359 拆到字节、把时间排到分钟

这一小节是接力窗口在本章落盘之后追加的现场复算，**不改动上面任何一节的结论**；它的作用是把 15.2 那句 [推演]（「359 字节约等于七八行条文」）换成实测分解，并补三条时间台账。每条都写出计数方法，复核者跑不出同样的数就按本页重测规则重测。

**一、−359 的逐字节构成** `[实测]`。先把两侧正文里的路径串一律替换成同一个占位符（本页的隐私规矩顺手提供了个免费好处：去掉路径后两侧差异面立刻缩到 3 处），再逐行对照：

1. 「一句话」那行的容量数字：库 `43 种死法` ／ 仓 `41 种死法`；
2. 交付自检那一项：库 `43 种死法（七类）逐项问过` ／ 仓 `41 种…`；
3. 库有、仓无一条 `- **扩容防漂移**：…` 整行，实测该行 **367 字节**；
4. 「副本落点」那一行两侧都只写路径，占位符化后文本**完全相同**，但原始长度不同：仓侧比库侧长 **8 字节**（两处落点写法的字符数不一样），不属语义差。

于是 **367 − 8 = 359**，与差额逐字节对齐、没有余额。最锋利的一格不必论证：仓侧缺的那一行，正是「扩容防漂移」这条规矩本身；仓侧留着的那两个 41，正是这条规矩要抓的东西——**缺规矩的那一份，恰好表现出规矩要防的病**，这是这条规矩在自己包外副本上的一次自我对照实验。

同时把「库内正本是不是干净的那一侧」也钉死：正本自身的容量自述共 3 处，`43` 出现 2 次、「七类死法（**41 条**）」出现在五步工作流第 1 步；`references/05-checklists/上线验收记录表.md` 另有一处「库里 41 条没有的」。而 `CHANGELOG.md` 的 2026-09-29 节自述「SKILL.md 容量数字 41→43 全库 0 残留」——同一次实测在两个文件里各命中 1 处，**该声明当场为假**。成因不神秘：那一节自己列的同步清单只有「上线前检查（12a/12b）＋设计时检查（GOV 节两条）」两项，验收表和五步工作流都不在清单里，所以「全库」这两个字是被漏项撑出来的，不是被检查过的。

**二、差额不止入口文件：整包台账** `[实测]`。两侧文件清单一一对齐（各 20 个文件，库内多出那枚备份件才到 21），总字节 126,024（库，不含备份件）vs 109,412（仓），差 **−16,612**，五项相加正好吻合、无余额：

| 文件（仓 − 库） | 差额 | 缺的是哪一次改动 | 现场判据 |
|---|---|---|---|
| `CHANGELOG.md` | −12,452 | v1.1.2 节与 09-29 节，外加整段 ADR 常驻节 | 68 行 vs 184 行；`ADR-` 命中数 仓 0／库 8 |

**三、时间台账：两处的时间都不能当版本证据** `[实测]`。① 仓侧 20 个文件的修改时间全挤在同一分钟（2026-09-25 01:25）；整目录复制会把所有时间戳重置成复制时刻，所以「仓侧时间更早」只证明了复制发生在何时，证明不了内容诞生在何时——这正是 15.2 拒绝写「谁较旧」这个因果的实物依据。② 库侧自己错三格：09-29 那次扩容落盘的四个文件（变更记录＋治理清单＋上线前检查＋设计时检查）修改时间都是 09-30 凌晨 01:32，**标题写的却是 09-29**，按标题排时间轴会错一格（跨午夜作业）；入口正本 09-30 20:27，比变更记录晚约 19 小时，即最后一次动正文没有回写任何记录（正文同时留着 41 和 43 就是那次动过的痕迹）；两份评测检索件的修改时间同为 09-24 00:07，与 v1.1.1 同批——此后库长过两次身体，考卷一分钟没动。

**四、覆盖面零命中（给 15.4 补一个可复跑的数）** `[实测]`。① 09-29 新增的四个概念词（纸面防线／接线／变异空间／评测集）合并去查三处：入口正文 0 命中、顶层那份 16 条题面 0 命中、`references/06-prompts/` 两份 0 命中——新死法既没进触发关键词，也没进考卷，也没进提问模板的维度。② 字面相撞复算：把入口必触发词表整表拿去比 16 条题面，只有 2 条命中，1 条正例（问「什么是熔断器，我做的 Agent 需要吗」）、1 条负例（「熔断器在家用电路里的作用」，标着不该触发却含必触发词）；正例 8 条里 7 条不含任何字面必触发词，与 15.4 第 3 条一致。③ 「没有跑测的东西」复算：包内递归 21 个文件的扩展名分布是 18 份 markdown＋2 份 json＋1 份尾巴为一串 8 位数字的备份件，**可执行脚本 0 份**；顺带，那枚备份件按点号切出来的「扩展名」就是那串日期——它正是 15.3 那把失效尺子的活标本：按「后缀等于 `.bak`」去匹配，它连被扫到的机会都没有。

一句收束：本节没有新增任何「应该改包里哪一行」的建议（那是包主人的事），只把本章的四处结论从「两侧不同」推进到「差多少、缺哪次改动、时间对不对得上」——**差额可分解、时间可复核、覆盖面可复跑**，这三条是本章能被别人验的唯一理由。
