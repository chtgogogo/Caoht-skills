# 项目验收官 · 完整详解手册

> 一句话定位：**让一个不懂代码的人，有能力验收 AI 替他做出来的东西**——不是"感觉还行"，而是每一项都有可执行的判定标准（判据＝照着做就能得出"过/不过"的那条规则）、有落盘的证据、有不容和稀泥的结论。
> 灵魂句（出自 `SKILL.md` 开头的一句话）：**固定清单保覆盖，动态启发挖暗坑，证据链保诚实。**

---

## 第 0 章 五分钟速览

1. **它是一个"体检流程"，不是一个"检查表"**：装进 AI 之后，AI 面对"这个项目能不能上线"时不再凭印象回答，而是走一条固定路线：先给项目拍 X 光片（Phase 0 项目画像），再逐层过漏斗，最后落盘一份《项目验收报告》。[实测]（`SKILL.md` §2 流程总览）
2. **漏斗名义四层，实际六层**：第一层基础工程（拦截级：不过就直接打回）、第二层指标性能（硬指标）、第三层 AI 特有质量（必须定量）、第四层业务兜底（闭环），外加两层**按需启用**的专项层——第五层无障碍合规（有面向人的界面才测）、第六层用户可交付（产出要给别人用才测）。名字叫"四层漏斗"是因为第五、六层是后来加进来的，而**目录名和调用键不敢改**（改名要牵动映射表、宿主链接、别处引用）。[实测]（`SKILL.md` §3 漏斗分层表；`CHANGELOG.md` v1.2.0「优化了哪些地方」节）
3. **双轨制是这支的灵魂**：固定清单负责**下限**（常规项一个都不许漏，逐项给判定符号，跳项＝验收作废重来），动态启发负责**上限**（清单上没写、但这个项目特有的暗坑）。只靠清单会退化成打勾机器，只靠启发会变成 AI 的自由发挥。[实测]（`references/heuristics-playbook.md` 开篇导语）
4. **启发不许成为新的幻觉源**：动态启发产出的每句"我觉得这里有风险"只是**假设**（记 H-n），必须当场变成一个最小探针（一条命令／一个用例／一次重放）跑出**证实或证伪**，证实了才升级为**实证发现**（记 D-n）。**只有 D-n 能参与结论分级**，假设禁止顶 P 级。[实测]（`heuristics-playbook.md`「实证门槛」节、`scoring-and-verdicts.md` §3「动态发现二轨规则」）
5. **每条结论必须有证据**：命令与退出码、`文件:行号` 引用、或落盘的测量输出（存 `acceptance/evidence/`）。测不出来就写「⬜未测」，不适用就写「➖不适用」——**这不丢人，编数字才丢人**。一份编造数据的报告比没有报告更糟。[实测]（`SKILL.md` §0 军规 2、军规 3）
6. **结论只有三档，且不许自由发挥**：通过／有条件通过／不通过。它是**由映射表算出来的**，不是 AI 觉得的：第一层任何 ❌ 或任何一层出现 P0 → 不通过；无 P0 有 P1 → 有条件通过（必须附"转通过条件清单"）；无 P0 无 P1 → 通过。关键项没测 → **封顶**只给「有条件通过」。禁止"基本通过""大体 OK"这类和稀泥词。[实测]（`scoring-and-verdicts.md` §3、`report-template.md`「写作纪律」第 3 条）
7. **它拒绝给综合总分**：报告用"分项达标表 ＋ 最弱项点名"代替一个漂亮分数——因为加权总分会掩盖最弱项（90 分的平均值可以把"常识类检索 2/10"藏得干干净净）。[实测]（`SKILL.md` §5、`layer3-ai-quality.md` §E 末尾说明）

**一句话设计目标**：把"验收"从一种主观表态，改造成一套**可复核、可复跑、可追责**的工程流程——让"能不能用"这个词第一次拥有可执行的判定标准。

## 第 1 章 这套系统在解决什么问题

### 1.1 总故障：一个不懂代码的人，怎么去验收一个 AI 给他做出来的东西

这是这支 skill 的全部理由。传统验收假设有两个前提，而个人项目／AI 交付项目两个前提都不成立：

- 前提一：**验收的人看得懂代码**。不成立——用户是计算机基础≈0 的非开发者，他看不到"没加锁文件""异常被吞了"。
- 前提二：**造东西的人不会给自己打分**。不成立——AI 天然倾向于报告"已完成"，因为它没有后果承担机制。

于是"验收"退化成一问一答："做完了吗？""做完了。""能用吗？""能用的。"——**这套问答里没有任何外部约束，所以它不是验收，是宣誓。**[推演]（具体什么输入会出问题：你对 AI 说"帮我验收一下这个项目"，没有本 skill 时它会读一遍 README 然后回答"整体结构清晰、功能完整、可以上线"——三句话没有一句是可证伪的。）

本 skill 的做法：**把验收拆成人也能核对的三件东西**——① 一张逐项打勾的清单（不许跳项），② 一个只能得出一档结论的映射表（不许自由发挥），③ 一堆能重新跑一遍的证据文件（不许只报总结数字）。

### 1.2 「故障 → 表现 → 解法」对照表

| # | 故障 | 表现（不加约束时具体长什么样） | 本 skill 的解法（出处） |
|---|---|---|---|
| ① | **验收走形式** | "测试都过了，没问题"——检查项凭印象跳着看，看过的三项说成验过的三十项 | 固定清单逐项核对、逐项给判定符号，**跳项＝验收作废重来**（`SKILL.md` §3 执行纪律） |

### 1.3 三个最隐蔽的坑，本 skill 用三句不同的话堵

|---|---|---|

## 第 2 章 术语表（每个词后面一句大白话）

### 2.1 验收行话（中文行话也算术语，一样解释）

| 术语 | 大白话 |
|---|---|
| **验收** | 交付方按事先定好的标准，一样一样确认"这东西到底能不能用"；不是"看起来挺好" |
| **判据** | 可执行的判定标准——照它做就能得出"过"或"不过"，不需要任何人发表意见 |
| **恒真／恒红** | 恒真＝这条判据怎么写都算过（"能打开页面就算通过"），等于没有判据；恒红＝反过来怎么写都不过（拿文件数量去判"四个库是否齐全"），只能制造噪音 |
| **冒烟** | 先跑一遍最主路，确认整体没炸；不细究对错，只看有没有当场死掉 |
| **漏斗（分层）** | 一层一层的筛子，前面那层没过就不许进下一层——水从漏斗往下流，卡在哪儿就停在哪儿 |
| **拦截级** | 这一层拥有"一票否决"的权力；第一层是唯一明确的拦截级 |
| **红线** | 事先写死的数值线，越过就记风险；不是建议值，是"过线即事故" |
| **口径** | 这个数字是怎么测出来的：什么环境、跑了几轮、温度设成几、取的是哪段时间——数字没有口径就没有意义 |
| **落盘／证据链** | 落盘＝把结果真的写成一个文件存下来，不是只在对话里说一句；证据链＝结论 → 证据文件 → 能重跑的命令，三者能一路对上 |
| **勾稽** | 两处的数字能互相对上（报告里写的分数，能在证据文件里逐题找回来） |
| **探针** | 只用来检查、不修改东西的小脚本或单条命令；本 skill 特指"当场验证一个假设"的最小可执行动作 |
| **五态判定** | 每个检查项必须落在五个符号之一：✅通过／❌未过／⚠️风险／⬜未测／➖不适用 |
| **P0／P1／P2** | 问题三级：P0 上线即事故、P1 上线前必须修、P2 改进项进待办 |
| **封顶／数据不足封顶** | 因为证据不足，结论被规则强制压低一档（没测就不能给高分）；关键项大面积没测时最高只能到"有条件通过"，并写明"因 XX 未测无法给通过" |
| **和稀泥词** | "基本通过""大体 OK""问题不大"——本页禁止的词，因为它们不承担任何判定责任 |
| **裸崩** | 出错了直接把技术堆栈甩到用户脸上，没有任何包装或提示 |
| **静默丢失** | 数据没了、任务失败了，但系统一声不吭，用户完全不知道 |
| **最弱项点名** | 强制报告里指出最差的那 1–3 项，不许用平均分盖过去 |
| **回流** | 这次验收发现的新坑，写回知识库存着，下次直接查表 |
| **对号入座** | 拿着已有的死法清单逐条问"我这项目会不会这样死"，命中的直接进排查 |

### 2.2 工程与指标术语

| 术语 | 大白话 |
|---|---|
| **Phase 0 项目画像** | 动手检查之前先给项目拍张 X 光片：什么语言、什么框架、像哪类项目、有哪些一眼可见的红旗 |
| **红旗** | 扫一下就报警的可疑信号（比如 `.env` 这个密钥文件竟然被 git 跟踪了），必须人工逐条确认后才能进报告 |
| **可复现构建／锁文件** | 前者＝换一台干净机器照文档走一遍能装出同一个东西，做不到就说明有隐藏依赖；后者＝把每个依赖的精确版本号写死的文件（如 `poetry.lock`、`package-lock.json`），没有它今天的构建和下次的构建不是同一个东西 |
| **依赖倒挂** | 一个库把自己的依赖版本写死，导致用它的项目没法自由升级 |
| **lint** | 静态检查工具，不改代码、只按规则扫出问题（如 ruff、eslint） |
| **CVE** | 公开的已知漏洞编号；用扫描工具比对依赖清单就知道有没有中招 |
| **NC 许可证** | 禁止商用的开源许可（如 CC-BY-NC）；把它当工程依赖用了就是红线 |
| **冷启动剔除** | 先把程序空跑几遍热起来再正式计时，否则测到的第 1 次耗时全是启动开销，不代表真实性能 |
| **P50／P95／P99** | 分位数：95% 的请求都比这个数快。只看平均值会被"平均"骗，尾部才是用户骂人的地方 |
| **N+1** | 查 1 次列表又对每条记录各查 1 次库——100 条数据就变成 101 次查询，性能杀手 |
| **幂等** | 同一件事做一次和做两次，结果完全一样；不幂等的话，重试一次就重复下单／重复入库 |
| **熔断／降级** | 依赖挂了时，系统主动停手或改用备用方案，而不是硬撑着把错误传下去 |
| **退避＋抖动** | 失败后重试要越等越久、且每次多等一个随机量，避免所有客户端同一瞬间一起重试（重试风暴） |
| **soak（浸泡测试）** | 持续跑十几分钟到半小时，看内存是不是只涨不落——短时测试看不见慢性泄漏 |
| **runbook（运维手册）** | "出事了照着做"的说明书，写清最常见故障的处理步骤 |
| **症状级告警** | 按"用户已经受影响"来报警（错误率涨了），而不是只在"进程死了"这种结果上报警 |
| **越权三连** | 三种权限漏洞一起查：横向（A 能不能读 B 的数据）、纵向（普通用户能不能调管理员接口）、未鉴权（不登录能不能进） |
| **diff 驱动** | 只看这次改了什么（`git diff`）来决定重点查哪儿，增量验收的核心技巧 |

### 2.3 AI 项目专用术语

| 术语 | 大白话 |
|---|---|
| **评测集** | 一堆"题目＋标准答案／判定标准"的文件，用来给 AI 打分；没有它，任何"准确率"都是嘴上说的 |
| **回归题／扩充题／评审题** 与 **温度固定 0** | 三类题：回归题必须全对（防止把已经会的改坏了）、扩充题看能力扩张、评审题是开放题靠裁判模型打分；温度固定 0＝把模型随机性关到最低，这样分数才能重复——温度不固定，两次跑分必然不一样 |
| **pass^k** | 同一道题跑 k 次全对才算通过——它量的是"稳定"，而平均分把不稳定藏起来了 |
| **Hit@k** | 正确的那个东西有没有出现在前 k 个结果里（检索／工具选择常用） |
| **忠实度（faithfulness）** | 回答里的每句关键事实，能不能在检索到的资料里找到出处；找不到就是编的 |
| **LLM-as-judge** | 让另一个大模型当裁判打分；裁判自己没校准过，它的分数就只是另一个模型的意见 |
| **人机一致率** | 抽 10–20 题人工也判一遍，看机器裁判和人判得一样不一样；<80% 就说明分数只能当参考 |
| **评测污染／泄漏** | 考题或答案直接出现在系统的提示词、知识库或示例里——AI 是在抄答案，分数全线虚高 |
| **提示注入** | 用户输入里塞一句"忽略上面的指令"，把系统指挥跑偏（LLM01）；藏在待处理文件里的叫间接注入 |
| **过度代理** | 给模型过大权限（能删文件、能发邮件），一旦被骗就出事（LLM06） |
| **TTFT** | 首字延迟：从发出请求到看见第一个字的时间；对话产品里 >3s 用户就以为卡死了 |
| **结构化输出** | 要求模型返回能解析的 JSON／符合约定的格式；解析不了，下游就整段崩 |
| **校准** | 模型"知不知道自己在瞎说"；准备几道库里根本没有答案的题，看它是编还是坦白 |

### 2.4 无障碍层术语（第五层）

| 术语 | 大白话 |
|---|---|
| **a11y / 无障碍** | accessibility 的缩写（a 和 y 之间 11 个字母）：残障人士（看不见、只能用键盘、用屏幕阅读器）也能把这东西用完 |
| **WCAG 2.1** | W3C 出的无障碍国际标准，4 大原则 × 13 条指南，一条条编号（如 1.4.3） |
| **A／AA／AAA** | 三个等级，A 最低（必做）、AA 常规合规目标、AAA 最严；政务／医疗／公共类项目要冲 AAA |
| **对比度** | 字色和底色的亮度差，用公式算出来一个比值（如 4.5:1）；灰字配浅底经常不达标 |
| **焦点可见（focus ring）／焦点陷阱** | 前者＝键盘用户必须看得见"我现在停在哪个控件上"，没有焦点框等于瞎按；后者＝Tab 进了某个弹层就出不来，纯键盘用户被彻底锁死，属 A 级问题 |
| **aria-live／状态消息** | 页面上"提交成功"这种没有声音的动态提示，屏幕阅读器能不能念出来 |
| **reflow（重排）** 与 **skip-link** | 前者＝窗口压到 320px 宽或字放大 200% 后内容自己重排、不出现横向滚动条；后者＝"跳到主内容"的隐藏链接，让键盘用户不用 Tab 一百次穿过导航栏 |
| **屏幕阅读器** | 把屏幕内容念出来的辅助软件（Windows 上免费的是 NVDA） |
| **自动扫描只覆盖一半** | axe-core 官方口径：自动化工具最多查出约一半违规，剩下的必须人工走查；只跑扫描就下结论＝⬜未测，不是 ✅ |

### 3.3 每层的存在理由（为什么非要有这一层）

**第一层存在的理由：它把"作弊"和"不可复现"挡在最前面。**如果允许跳过第一层直接测性能，会出现一个经典骗局：在一台装满了手工调试过的环境的机器上测出 P95=1.2s——而新环境根本装不起来。**第二层的数字只有在第一层过了之后才有意义**，这就是漏斗的物理意义：先筛掉"根本不可信的对象"，再谈"好还是不好"。[实测]（`SKILL.md` §3 表第一行"不过直接打回，不许进下一层"）

**第二层存在的理由：功能对了不等于扛得住。**它的核心纪律是一条口径纪律：**所有数字必须标注（环境配置／预热方式／轮数／时间窗），无口径的数字无效；禁止只报平均值不报尾部。**[实测]（`layer2-metrics.md` 开篇）"尾部"就是最慢的那 5%、1%——用户投诉永远来自尾部，不来自平均。

**第三层存在的理由：AI 项目里"量尺"本身可能是坏的。**铁律原话：**先查"量尺"合不合格，再读数——评测体系本身有洞，分数就是自欺。**[实测]（`layer3-ai-quality.md` 开篇铁律）这就是"恒真判据"在 AI 项目里的具体形态：考题泄漏进知识库时，任何分数都写都算过，测一百遍也测不出真相。所以第三层 §A（评测体系健全性）排在 §B（分数）之前，顺序不可颠倒。

**第四层存在的理由：验收不是只挑毛病，更要看系统会不会自救。**灵魂一句：**"真实触发一次"，代码里"有这个功能"不算数，要按一遍链路。**[实测]（`layer4-business.md` 开篇判定原则）这条把整个 skill 和"代码审查"区分开了——代码审查读代码就能给结论，第四层要求你**去按那个按钮**。没按过的降级分支，状态只能是 ⬜ 未测。

**第五层存在的理由：把"能不能被用"从主观感受变成逐条可核对的客观项。**它**不拦截**（区别于第一层），因为绝大多数个人项目没有无障碍义务；但一旦出现"宣称符合标准而实测未达"，它立刻按 P0 参与结论——**宣称与事实打架是全库统一的 P0 定义**。[实测]（`layer5-accessibility.md` §4 表）

**第六层存在的理由：前五层全部可能通过，而项目依然不可交付。**这是 v1.3.0 加进来的、也是全套设计里最"疼"的一层——它的存在理由写着自己的一次事故：某个内部单据处理项目，45 轮迭代、700 多条测试全绿，四层漏斗＋无障碍层全部通过，但目标用户（会计岗）连一次核心操作都做不完，因为采购单／入库单的**人工录入口子从来没有被建出来过**（功能只存在于接口层，界面上没有入口）。[实测]（`CHANGELOG.md` v1.3.0"起因"、`SKILL.md` §3 执行纪律第二条"教训锚点"；真实项目名在本页已抽象化）

> 这一层为什么单列而不是塞进第四层：第四层问的是"系统出错了能不能自救"，第六层问的是**"有没有一个人，按你交付的样子，真的用它做成过一件事"**。前者的对手是故障，后者的对手是自欺。

### 3.4 判定顺序（五件事必须按这个顺序问）

```
1. Phase 0：这是什么项目？（类型判定 + 范围 + 不适用项初判）
2. 哪几层启用？（第五层看有没有面向人的 UI；第六层看有没有"给别人用"的目标）
3. 每一层内部：固定清单逐项核对 → 动态启发 → 层内判定
4. 全局结论映射：第一层 ❌ / 任何层 P0 → 不通过；有 P1 → 有条件通过；否则 通过
5. 封顶复查：关键项 ⬜ 太多 → 结论强制降一档并写明原因
```

**为什么第 2 步必须在检查之前**：启用判定错了，后面全是无用功——给一个纯 CLI 工具做无障碍走查是浪费，给一个"要给别人用"的项目跳过第六层是漏掉最致命的一类风险。所以 `SKILL.md` §3 执行纪律明确要求**启用判定跟着 Phase 0 画像走**。[实测]

- `references/tooling-cheatsheet.md`（各语言命令速查／最小压测方案／降级演练做法，约 3.4 KB）——在 `SKILL.md`、`CHANGELOG.md` 与其余 10 份 references 全文里**引用次数为 0**。[实测] 后果：清单里反复要求"降级演练""最小压测"，可"具体敲哪几条命令"的答案存在，却没人把它指出来；执行时更可能凭现场记忆编命令，违反军规 2。修法有两条，代价都不大：在 `SKILL.md` §3 各层表格后补一句"命令细节见 `references/tooling-cheatsheet.md`"，或在对应层清单（layer2／layer4）里点名它。**本页只登记，不代改**（权威库只读）。[推演] 若长期无人补指针，它的失效方式不是报错，而是"每次都查得不细却看不出错"。

## 第 4 章 验收官的宪法：四条军规、三禁、五态、P 级与结论映射

> 本章对应 `SKILL.md` §0 与 §4、`references/scoring-and-verdicts.md` 全文。 这是整套系统的**上位法**：军规那句原话写得很硬——"先读，凌驾于一切效率考量"。意思是：哪怕这一轮验收因此变慢十倍，也不许绕过这四条。

### 4.1 军规 1：只诊断，不修复

**原文约束**：验收过程中发现的问题一律记录进报告，**禁止顺手改代码、改测试、改配置来"让验收变好看"**。用户明确说"验收＋修复"模式时除外，且每处修复同样要留证据。[实测]（`SKILL.md` §0 第 1 条）

**它堵的是什么**：运动员兼裁判。一边改一边验，报告的每一项都变成了"我刚改完的那个版本"，而"刚改完"意味着没有独立复核。

**为什么"每处修复同样要留证据"这半句很关键**：如果修复模式可以不留证据，那"验收＋修复"就成了绕过军规 1 的后门——先制造问题再当场修掉，全程只留下一个漂亮的最终态。[推演]（具体什么输入会出问题：AI 被授权"顺手修一下"，把那个一直失败的测试改掉让它通过——没有证据要求时，报告里只会看到"测试全绿"。）

### 4.2 军规 2：证据为王

每条结论必须附证据，三种形态任选其一：[实测]（`SKILL.md` §0 第 2 条）

- 命令与退出码（例如 `exit=1` 这种硬信号）；
- `文件:行号` 引用（指向被验收项目里的具体位置）；
- 落盘的测量输出（存进 `acceptance/evidence/`）。

并且它把"诚实"写成可执行动作：**测不出来的写「⬜未测」，不确定的写「未知」，禁止脑补数字**；这三条分别与测试纪律（数字必须有落盘证据）、抗幻觉纪律（事实／假设／未知分离）**同源执行**——不是新造一套标准，是复用已有的。

**为什么"未测"必须是合法状态**：如果只有"过／不过"两态，AI 在测不了的时候会倾向写"过"——因为"不过"要解释、"未测"根本不存在。多给一个合法的 ⬜，等于把编数字的收益降到零。[实测]（`SKILL.md` §1 尾注"这不丢人；编数字才丢人"）

### 4.3 军规 3：三禁（反作弊三条）

| 禁 | 原文 | 它针对的真实作弊动作 |
|---|---|---|
| 禁 1 | 禁止修改／删除测试、放宽阈值、缩小评测集来凑"通过" | 把断言从 `==` 改成 `<=`、把跑不过的用例 skip 掉、把 38 题评测集偷偷删成 12 题 |
| 禁 2 | 禁止编造任何数字（**一份编造数据的报告比没有报告更糟**） | 没跑压测就写 P95=1.8s；没跑评测就写准确率 92% |
| 禁 3 | 禁止把不适用的检查项硬测出结果——写「➖不适用」并给一句理由 | 给纯 CLI 项目硬测并发（测了个寂寞），或给没有知识库的项目硬编一个检索分数 |

[实测]（`SKILL.md` §0 第 3 条）

**为什么三禁的顺序是这样**：先禁"改尺子"，再禁"编读数"，最后禁"硬测不存在的东西"。这三条恰好覆盖了测量作弊的三个环节——**尺子、读数、被测量**。少任何一条，另外两条都会被绕开。[推演]（什么输入会让它出问题：只有禁 2、没有禁 1 时，AI 不需要编数字——它只要把阈值从 80% 改到 70%，然后如实报告 71.1% "通过"。）

### 4.4 军规 4：非破坏 ＋ 先报价

- **非破坏**：不删数据、不压测生产或外部环境、不做不可逆操作；压测只打本地或测试环境。[实测]（`SKILL.md` §0 第 4 条）
- **先报价**：需要调付费 API（比如跑全量评测集）时，先报预估消耗，算法是 **题目数 × 轮数 × 单次 token**；超过默认 **5 万 token** 预算必须等用户确认。[实测]（同条）

**为什么预算默认值是 5 万 token 而不是别的数**：正文只给了默认值与"可被项目 `ACCEPTANCE.md` 覆盖"的接口，**没有给推导过程**——本页不做二次发明（口径纪律：不确定就写未检索到）。可确定的设计意图有两条：[推演]① 它必须大于"跑一轮 20 题回归评测"的常规开销，否则每轮都要停下来问，验收跑不完；② 它必须小于普通人一个月 API 账单的心理上限，否则这个默认值形同没有。要拿到真精确的数，得按你自己用的模型单价换算一次。

**为什么"先报价"和"非破坏"写在同一条军规里**：因为两者都是"验收动作本身的成本与风险"。验收是来观察的，不是来花钱和来搞破坏的。这条把验收官和"压测工程师"划开。

### 4.5 五态判定：为什么恰好是五态，不是两态或四态

| 符号 | 含义 | 强制要求 |
|---|---|---|
| ✅ 通过 | 检查过且达标 | 附证据 |
| ❌ 未过 | 检查过且不达标 | 附证据 ＋ **修法建议**（不许只说坏了） |
| ⚠️ 风险 | 能用但有隐患 | 说明隐患 ＋ **触发条件**（什么时候会真的出事） |
| ⬜ 未测 | 本次没测成 | 原因 ＋ **补测方法**（不许静默略过） |
| ➖ 不适用 | 该项目无此项 | 一句理由 |

[实测]（`SKILL.md` §4、`scoring-and-verdicts.md` §1；两处的表逐字一致）

- 两态（过／不过）会把"没测"和"不适用"挤进"过"，制造假绿；
- 四态（把 ⚠️ 并进 ❌）会让"能跑但有隐患"这种最常见的真实结论无处可放，于是 AI 会倾向写"能跑"；
- 五态的每一个符号**都带一条强制附注**（证据／修法／触发条件／补测方法／理由），这是它和"打勾表"的根本区别：勾选不算完成，附注齐了才算。

判定语句的标准写法（照抄模板）：`❌ 依赖未锁定（无任何 lock 文件，requirements.txt 只有裸包名）｜修法：pip freeze > requirements.txt 或迁移到 pyproject+uv.lock`。[实测]（`scoring-and-verdicts.md` §1 示例）

### 4.6 问题分级 P0／P1／P2

| 级别 | 定义 | 正文给的典型例子 |
|---|---|---|
| **P0** | **上线即事故**：数据丢失、安全洞、核心链路坏、评测污染、**宣称与事实打架** | 密钥泄露、SQL 注入、CI 红叉但文档宣称质量达标、评测集泄漏进知识库、幻觉 API、无备份的关键数据 |
| **P1** | **显著缺陷，上线前必须修** | 无死循环护栏、降级路径从未验证、错误率超标、N+1、反馈闭环断裂 |
| **P2** | **改进项／技术债，进待办** | 冗余依赖、文档缺口、TODO 偏多、个人项目无监控 |

[实测]（`scoring-and-verdicts.md` §2）

值得注意的是 **P0 定义里塞进了两个非技术项**："评测污染"（分数全是假的）与"宣称与事实打架"（对外承诺与实测不符）。把它们提到 P0，等于宣布：**造假比功能缺陷更严重**。这是整套系统的价值观，也是它区别于普通质量检查工具的地方。[实测]（同表；并与 `layer1-engineering.md` 第 21 项、`layer5-accessibility.md` §4 首行、`layer6-deliverability.md` 判定联动的 P0 写法互相印证）

### 4.7 结论映射：三档结论是算出来的

```
不通过     = 第一层任何 ❌  或  任何层出现 P0
有条件通过 = 无 P0，但有 P1   （报告必须列"转通过条件清单"）
通过       = 无 P0 且无 P1   （P2 允许，进待办清单）
```

[实测]（`scoring-and-verdicts.md` §3，`SKILL.md` §4 是其速查版）

三条配套规则，一条比一条狠：

1. **数据不足封顶**：第三层因无评测集整体 ⬜，或第二层实测项大面积 ⬜ → 结论最高只能到「有条件通过」，且必须在结论处写明"因 XX 未测，无法给出通过结论"。原话：**"不存在'缺数据但判通过'的路径"**——证据不足时宁可给低结论，不给高结论。[实测]
2. **转通过条件清单格式**：逐条写 `[条件] → [验证方式]`。正文给的示例是：`条件1：修复 session_id 路径穿越（验证：用 ../../ 攻击串重放请求返回 400）`。注意"验证方式"是一句**可以照着敲的命令**，不是一句"确认已修复"。条件全数验证通过后，下一次验收才允许改判「通过」。[实测]（§3）
3. **动态发现二轨规则**：只有实证发现 D-n 参与结论映射与 P0–P2 分级；假设 H-n 进假设区、**禁止给 P 级**；证伪记录 X-n 进排除区留痕。固定清单项照旧按五态判定，不受此条影响。[实测]（§3 末段）

**第一层 ❌ 之后还能不能继续往下测**：能，而且鼓励。`SKILL.md` §3 执行纪律最后一条写明：第一层出现 ❌ 时仍可继续往下层收集信息（报告更完整），但**结论锁定「不通过」**，并须在报告里显式声明"按漏斗规则本应打回，以下内容仅供参考"。[实测]——这条解决了一个真实矛盾：严格漏斗会让后面的信息永远拿不到，无约束的继续又会稀释"打回"的严肃性；解法是**信息可以拿，权力不给**。

### 4.8 验收级别三档：快检／标准／全量

| 级别 | 范围 | 耗时 | 花 API 钱 |
|---|---|---|---|
| **快检** | Phase 0 ＋ 第一层全量 ＋ 各层里**静态可查**的动态项 ＋ 报告 | 15–40 分钟 | 否 |
| **标准**（默认） | 快检 ＋ 第二层本地实测 ＋ 第三层（有评测集就跑）＋ 3–5 个刁钻用例 ＋ 第四层静态项与兜底触发实测 | 0.5–1.5 小时 | 可能 |
| **全量** | 标准 ＋ 并发压测 ＋ 稳定性 N 轮复跑 ＋ 降级演练 ＋ judge 人工对齐抽样 | 2 小时以上 | 会 |

[实测]（`SKILL.md` §1）

四条配套设计值得注意：

- **默认是"标准"而不是"快检"**，并且 §2.4 明写"用户未指定级别就直接按标准开跑（自主执行，不要反复问）"。这是在**主动对抗 AI 的讨好倾向**——遇到不确定就停下来问，把决定权推回用户，等于把验收做成了客服对话。唯一必须停下来等确认的两件事也写得极窄：付费评测超预算、或需要对生产／外部环境做任何操作。[实测]
- **快检不花钱**：它只做"静态可查"的事，不启动压测、不调模型。所以它适合"每天改完代码顺手看一眼"。
- **耗时是区间不是承诺**（15–40 分钟、0.5–1.5 小时），因为项目体量差异太大。
- **裁剪必须留痕**：用户说"只跑第一层"，裁剪范围要写进报告元信息——防止三个月后看报告时以为已经全测过了。[实测]（`SKILL.md` §1 第一条注）

### 4.9 出报告前自查清单（10 项）

`scoring-and-verdicts.md` §5 是一张 10 个复选框（按文件里 `- [ ]` 行计数）的自检表，最后两项是 v1.1.0 新增的：

- 动态发现全部二轨分离（D 实证／H 假设／X 排除），**没有任何假设顶着 P 级混进结论**；
- 回流候选过了三道质量门（已实证／通用型／非重复）并按正确路由落库。

而第 10 项是全章的收口：**"我没有为了'好看'弱化任何一条？（诚实优先）"**——它不问技术，只问态度。[实测]

## 第 5 章 Phase 0 项目画像：所有"适用性"的根

> 对应 `SKILL.md` §2「Phase 0 项目画像（必做，决定后面所有'适用性'）」与 `scripts/profile_project.py`。

### 5.1 为什么第一步不是检查，而是画像

六层里有两个"按需层"（第五、六层），第三层对非 AI 项目整体 ➖，第二层对跑不起来的项目整体 ⬜，鉴权项对无用户体系的项目 ➖——**这些开关全部由 Phase 0 的判定决定**。画像错了，后面整轮验收的适用范围就错了。[实测]（`SKILL.md` §2 第 3 项"不适用项初判：逐项给理由"）

### 5.2 Phase 0 的四步（原文顺序）

1. **跑画像脚本**：`python "<本skill目录>/scripts/profile_project.py" "<项目根目录>"`，纯标准库、无第三方依赖，输出一份 JSON 画像。脚本报错或信息不足时人工补查（看依赖清单、入口文件、README）。[实测]
2. **读项目根的 `ACCEPTANCE.md`**（若存在）：里面的红线值、评测集路径、验收范围、豁免项**优先于本 skill 默认值**。不存在则用内置默认红线，并在收尾时生成一份草稿。[实测]
3. **明确三件事并写进报告**：项目类型判定（可多选）＋ 判定证据；验收范围（全量 or 增量，增量也要保第一层全量）；不适用项初判（逐项给理由）。[实测]
4. **未指定级别就直接按「标准」开跑**；只有超预算的付费评测、或需要碰生产／外部环境时才停下来等确认。[实测]

### 5.3 画像脚本的 JSON 字段逐个讲（一个不懂代码的人也能看懂输出）

`profile_project.py` 全文约 436 行（按文件行数），只 import 标准库（`argparse/json/os/re/subprocess/datetime/collections`），因此在任何装了 Python 的机器上都能直接跑，不需要 `pip install`。输出的顶层字段：[实测]

| 字段 | 内容 | 人话 |
|---|---|---|
| `root` | 被扫描目录的绝对路径 | 扫的是哪儿 |
| `generated_at` | 生成时间 | 画像的保质期起点 |
| `git` | 是否仓库、HEAD、最近一条提交、未提交变更数与样例、`.env` 是否存在／是否被 ignore／**是否被 git 跟踪** | 版本控制的现场 |
| `languages` | 各语言的文件数（按扩展名数） | 这项目主要用什么写的 |
| `manifests` | 发现的依赖清单文件（16 种候选名） | 依赖声明在哪儿 |
| `frameworks` | 框架命中及命中的文件 | 用了哪些库 |
| `type_guesses` | 类型猜测 ＋ 证据 ＋ 置信度 | 这最像哪一类项目 |
| `tooling` | 测试目录/配置/文件数、lint 配置、CI 配置、锁文件清单、`requirements_locked`（如 `3/40`）、docker、文档、env 文件 | 工程化设施齐不齐 |
| `eval_assets` | 命中 `eval/benchmark/评测/题库` 的文件（前 30 条） | 有没有评测集（第三层的开关） |
| `acceptance_md` | 项目根 `ACCEPTANCE.md` | 项目自定义契约在不在 |
| `quick_counts` | 总文件数、实际扫过的源码数、生产代码里 `print(` 计数与样例、`console.log` 计数、裸 `except` 计数与样例、TODO/FIXME 计数 | 一眼可见的脏东西 |
| `suspected_secrets` | 疑似硬编码密钥（文件、行号、命中的模式名、片段截到 120 字符，最多 20 条） | **必须人工逐条确认**的红旗 |
| `red_flags` | 结构化红旗列表，每条带 `severity` | 摘要级结论 |
| `notes` | 两条免责："本画像为快筛结果…""type_guesses 仅为启发式猜测…" | 脚本自报家门 |

### 5.4 九类类型猜测与它们的判据

`guess_types`（画像脚本的函数）按依赖清单里的框架名猜类型，本页数出 **9 种**输出值：`api-service`（Web 服务/API）、`frontend`、`agent`、`rag`、`llm-app`、`cli`、`data-pipeline`、`game`、`library-or-script`。[实测]（数法：统计该函数里写入 `"type"` 键的不同字面量）

三条值得学的设计：

- **每种猜测都带 `evidence` 与 `confidence`**。`frontend` 只命中 `next` 时置信度降为 `medium`（因为 Next.js 也可能是纯后端渲染）；一个信号都没命中时兜底给 `library-or-script` 且 `confidence: low`。[实测]——**没有把握就明说没把握**，这正是抗幻觉纪律在代码里的形态。
- **RAG 判定优先于 llm-app**：命中向量库（7 个候选：chromadb/qdrant/milvus/faiss/weaviate/pgvector/pinecone）或 llama-index 才算 RAG（`high`）；只命中模型 SDK 只给 `llm-app`（`medium`）。这个区分直接决定第三层要不要跑检索类指标（Hit@5、忠实度）。[实测]
- **CLI 判定用行为特征而非框架**：Python 源码里出现 `import argparse|click|typer`、`pyproject.toml` 有 `[project.scripts]`、`package.json` 有 `bin`、Go 有 cobra、Rust 有 clap 都算——因为 CLI 的本质是"入口形态"，不是某个库。[实测]

### 5.5 十类红旗（脚本里的 `red_flags`）与三条分级

按 `red_flags.append` 的 `flag` 名去重数出 **10 类**：`env_tracked`／`env_not_ignored`／`no_lockfile`／`requirements_not_fully_pinned`／`no_tests`／`no_ci`／`no_readme`／`no_changelog`／`suspected_secrets`／`no_env_example`。[实测]

> **口径冲突留档**：`CHANGELOG.md` v1.0.0「增加了什么功能」写的是"红旗（.env 被 git 跟踪、无锁文件、疑似硬编码密钥等 8 类）"，与脚本现装的 10 类不同数。以脚本为准（代码是更硬的证据），此处并列不合并。

分级只有三档，且**没有 P2 的红旗会污染结论**：

- **P0 两条**：`.env` 被 git 跟踪（密钥可能已进历史）、存在疑似硬编码密钥。注意 `no_lockfile` 不是 P0——脚本层面它只是红旗，真正的判定发生在第一层第 9 项"缺锁文件＝❌"，而 ❌ 才锁结论。[实测]
- **P1 两条**：完全无锁文件且依赖未锁、无任何测试文件/目录/配置。
- **P2 五条**：依赖未完全锁定、无 CI、无 README、无 CHANGELOG、有 `.env` 但缺 `.env.example`。

**一个非常值得学的细节**：`requirements.txt` 里判断"锁定了没有"，脚本只认 `==` 与 `~=` 两种写法。为什么？因为 `>=` 是"最低版本"而不是"锁定版本"——开发时曾把 `>=` 误计成锁定，导致红旗漏报，后来专门修掉。这段历史写在 `CHANGELOG.md` v1.0.0「质量记录」里（同一批还修了另一个更隐蔽的 bug：`.git` 前缀匹配把 `.github` 目录一起误杀，导致 CI 检出永远为空）。[实测]

**这两个 bug 为什么值得写进手册**：它们是**恒红与恒真的机器生成版本**——`startswith(".git")` 让 CI 检查永远"没找到"，看起来像"没配 CI"，实际上是"检查逻辑自己把目录过滤掉了"。任何"零命中"结论，都先问一句：是尺子的问题，还是对象的问题。这正是军规 2 的实战含义。

### 5.6 脚本的自我设限（快筛 ≠ 终判）

扫描时有硬上限：跳过 25 个目录名（`.git`、`node_modules`、`__pycache__`、`.venv`、`dist`、`build`、`site-packages`、`vendor` 等；数法：统计 `SKIP_DIRS` 字面量元素）、目录深度超过 8 层不再深入、文件总数上限 20,000、实际读源码上限 3,000 个、单文件只读 256 KB（依赖清单放宽到 400 KB）、疑似密钥最多列 20 条、`print` 与裸 `except` 样例各截 15 条。[实测]

为什么要写死这些上限：验收脚本自己不能成为事故源——一个大 monorepo 或一个误指向磁盘根的路径，没有上限就会把机器资源吃光。`notes` 字段的两条免责与 `main()` 里 `sys.exit(2)`（目录不存在时）说明它**宁可少说，也不冒领**。

**密钥扫描模式为什么不写进本页**：脚本用 5 条正则按"供应商 token 的固定前缀 ＋ 长度特征 ＋ 通用赋值形态"匹配，并用一条占位符词表（xxx／your_／example／placeholder／dummy／sample／test／changeme／todo／尖括号）过滤假阳性。**本页刻意不复现这些字符模式**——公开仓库的自动密钥扫描会把它们当成真凭据报警；需要模式本身请直接读仓库内 [../Cao-项目验收官-四层漏斗固定清单加动态启发/scripts/profile_project.py](../Cao-项目验收官-四层漏斗固定清单加动态启发/scripts/profile_project.py) 的 `SECRET_PATTERNS` 常量（这是"文件名＋字段名"式引用，不是行号）。[实测]

### 5.7 `ACCEPTANCE.md`：项目的自定契约（为什么红线要交给项目自己）

`SKILL.md` §2.2 与 `references/scoring-and-verdicts.md` §4 一起确立了优先级：**项目根 `ACCEPTANCE.md` 的红线值／评测集路径／验收范围／豁免项 ＞ skill 内置默认值**。内置表共 **11 行**（数法：`scoring-and-verdicts.md` §4 表的指标行数）：

| 指标 | 默认红线 | 为什么是这个数（正文给出的理由或本页的推演标注） |
|---|---|---|
| 单元测试 | 100% 通过，0 个说不清理由的跳过 | [实测] 硬性。跳过可以存在，但**必须逐个给理由**——理由本身就是证据 |
| 回归题 | 100% | [实测] 原文注："回归题的意义就是全对"；94.4% 也算 ⚠️ 而不是"不错" |
| 扩充题准确率 | ≥80% | [推演] 80% 是"能力可用但仍有明显缺口"的位置：低于它说明模型还在猜，高于它就该考虑重定基线。本页未检索到更硬的推导依据 |
| Hit@5／工具首选正确率 | ≥70% | [推演] 检索类指标里 top-5 命中是"人愿意再看一眼"的下限；更严的场景应在 `ACCEPTANCE.md` 自己写高 |
| 幻觉 API 抽检 | 0 处 | [实测] 硬性；发现即 P0，理由原文是"用户会照抄" |
| 未知题编造率 | ≤40% | [推演] 库里根本没有答案的题，编不出来是理想但做不到；40% 是"多数时候会坦白"的底线，正文强调**编造率必须如实报告** |
| 稳定性波动（N 轮） | ≤5 个百分点 | [实测] 抽 10–20 题；超过 5pt 说明平均分不可信 |
| 本地 P95 | 对话/检索类 ≤3s；纯接口 ≤1s | [实测] 标为"建议值"而非硬性；两个数分开是因为纯接口没有模型生成时间，同一个标准会互相冤枉 |
| 错误率（负载下） | <1% | [实测] 注明"本地单机"——环境不同不可比 |
| 单次任务成本 | ≤ `ACCEPTANCE.md` 预算线 | [实测] 无预算线时首次建立 |
| 内存（15–30 分钟） | 无单调爬升 | [实测] 泄漏嫌疑的判据是"只涨不落"，不是"用了多少" |

红线理念原话值得单引一段：**"默认值只是护栏，不是圣旨"**——首次验收最重要的产出之一，是**和用户一起把符合项目定位的红线写进 `ACCEPTANCE.md` 固化**；此后红线改动必须在 CHANGELOG 留痕，防止"改红线凑通过"。[实测]（§4 末段）

这一句把整套系统的反作弊闭环补完了：三禁管住"改测试、缩评测集"，红线留痕管住"改标准"。**任何让结论变绿的改动都要留痕**，这是它真正的对称性原则。

### 5.8 收尾模板 `ACCEPTANCE总装模板.md`（16 个勾选项 ＋ 5 个填空）

项目根没有 `ACCEPTANCE.md` 时，收尾第 1 步以这份模板为底稿生成草稿（`SKILL.md` §7.1）。它按"三个源模板的总装视图"设计，节次与配载规则：[实测]

| 节 | 配载 | 内容 | 数法 |
|---|---|---|---|
| A 测试证据完整性 | **必选** | A1 结果落盘／A2 红绿对照（before 文件时间戳必须早于修复提交，防事后补造）／A3 断言弱化单独声明（`==` 改 `<=` 必须单列给理由）／A4 回归证据（证明"修好了"的新测试必须在改前输出里红过） | 4 项 |
| B 上线门禁与对外口径 | 有对外输出（README/简历/汇报/作品集）必选 | 密钥零硬编码、无弱默认值上生产、鉴权覆盖、数字四件套（来源命令／样本量分母／统计口径含置信区间／生成日期）、数字不过期、引用可验证、AI 署名带标识 | 7 项 |

| D 项目专属红线区 | **必填，哪怕一行** | 项目类型／红线值／评测集路径／豁免项／历次验收报告路径 | 5 个填空 |

双层设计的原话解释："本文件只内联最小核心，够 90% 场景；要跑全套就沿指针取"——每节末尾用指针指向对应源 skill 的完整模板。这是渐进披露（三层加载）思想在文档结构上的用法：**总装视图常驻，完整判定条款按需取**。[实测]

## 第 6 章 漏斗前半：第一层拦截级与第二层硬指标

### 6.1 第一层 · 基础工程（27 项／8 组，唯一的一票否决层）

**判定原则原文**：本层出现任何 ❌ → 报告结论锁定「不通过」。每项必给五态判定之一 ＋ 证据；标注【增量必查】的 **5 项**（按带该标记的编号项标题行计数）即使做增量验收也不许跳过。[实测]（`layer1-engineering.md` 开篇）

| 组 | 项数 | 查什么（编号见原文件） | 这组存在的理由 |
|---|---|---|---|
| **A 构建与复现** | 5 | ①全新环境复现 ②单测全过且无静默跳过 ③测试有效性抽检 ④类型检查 ⑤构建产物卫生 | 最强的一组："从零到绿"。装不起来、测不出真相，后面全部作废 |
| **B 代码质量** | 3 | ⑥Lint ⑦调试残留 ⑧裸异常与吞异常 | 只看三种最会藏事故的东西：调试打印、被吞掉的异常、没配置检查工具 |
| **C 依赖管理** | 4 | ⑨锁文件存在且入库 ⑩冗余依赖 ⑪已知漏洞扫描 ⑫许可证合规 | 复现性与法务两条线；NC（禁止商用）许可证被当工程依赖用即 P0 |
| **D 安全** | 5 | ⑬密钥硬编码扫描 ⑭.gitignore 正确性 ⑮注入类抽检 ⑯越权与鉴权 ⑰日志泄漏 | 组标题原话：**每一条都要"查过"，不是"觉得没有"** |
| **E 日志与可观测基础** | 2 | ⑱日志规范 ⑲全局兜底 | 出事之后能不能还原现场；未捕获异常有没有去处 |
| **F 版本控制与 CI** | 3 | ⑳git 工作区状态 ㉑CI 状态 ㉒迭代留痕（CHANGELOG） | 验收的"现场"必须是确定的一个提交；宣称与事实的交叉核对点 |
| **G 文档** | 3 | ㉓README 与实际一致 ㉔接口与部署文档 ㉕配置样例 | 判据是"一个新人照文档能不能跑起来"——文档也是被测对象 |
| **H 平台与类型基础项** | 2 | ㉖Windows 兼容 ㉗类型特有基础缺陷 | 结合画像取舍；这一项就是"固定清单与动态启发的交叉项" |

**四个最值得学的判定细节：**

1. **测试有效性抽检**（第 3 项）——随机抽 3 个测试文件读断言，看是真校验还是 `assert result` 空转／只跑不判。判据梯度写得很清楚：发现"跑过但没断言"的测试按 ⚠️，**成片出现按 ❌**。原话点睛：*测试通过率 100% 但断言空心＝测试是装饰品*。[实测]
2. **skipped 不算白名单**（第 2 项）——`failed=0` 只是必要条件；skipped/xfail 必须逐个列出并给理由，**说不清理由的跳过测试按 ❌ 记**。这一条直接封死了"把难过的测试 skip 掉"的通道（军规 3 禁 1 的具体化）。[实测]
3. **红叉 CI 比没 CI 更糟**（第 21 项）——CI 配置存在但最近一次是红的，而文档宣称质量达标 → ❌ P0，理由原文是"宣称与事实打架"；反过来无 CI 只是 ⚠️（个人小项目）或 ❌（多人／公开仓库）。**同一件事因项目形态分级不同，这是分级规则里少见的精细度**。[实测]
4. **"没工具"不许变成"不查"**（第 11 项）——依赖漏洞扫描工具不在环境里 → 记 ⬜ 并**附安装命令**，禁止跳过不提。所有"做不了"的结论都必须自带"怎么才做得了"。[实测]（同规则见 `tooling-cheatsheet.md` 开篇原则）

**第 13 项密钥扫描的做法**（本页只描述机制，不复现正则，理由见 5.6 末段）：有 gitleaks 就整库扫；没有工具就用**按供应商 token 前缀＋长度特征**以及"键名等于 api_key/secret/token/password 且赋了一个 8 位以上字符串字面量"这几类模式做正则抽扫；0 命中才算过，样例／占位符要**逐个人工确认是假值**。特别核对项单独成一条：`.env` 是否被 git 跟踪——**被跟踪＝❌ P0**。[实测]

**第 26 项为什么单列 Windows 兼容**：用户主力环境是 Windows，所以硬编码路径分隔符、UTF-8/GBK 编码坑、shell 脚本能否在 Windows 跑、换行符这四类被写成固定检查项。这是"个人项目验收"与"通用 CI 模板"最大的差异之一——**它承认自己被谁用**。[实测]

**层内小结表**：清单末尾自带一张 8 行 × 5 个判定列的空白统计表（组／项数／✅／❌／⚠️／⬜／➖），要求填完再写"本层结论：通过／不通过（列出 ❌ 项编号）"。**这张表存在的意义是防漏项**：没填完的行就是当场可见的漏洞。[实测]

### 6.2 第二层 · 指标性能（14 项／5 组）

**判定原则**：触达红线记 P0/P1 高危风险，且**必须附优化方案**（只报问题不报出路，这一层不算完）。**前提**：项目本地可运行；不可运行 → 本层实测项整体 ⬜ ＋ 原因，**静态可查项照查**（快检就是这么做的）。[实测]（`layer2-metrics.md` 开篇）

**铁的口径纪律**（原文加粗）：所有数字必须标注（环境配置／预热方式／轮数／时间窗），**无口径的数字无效**；**禁止只报平均值不报尾部**。[实测]

| 组 | 项数 | 关键默认红线／判据 | 为什么这么定 |
|---|---|---|---|
| A 延迟与吞吐 | 4 | 冷启动剔除（先空跑 ≥3 次再测，冷热分列不混报）；P95 需 ≥100 次请求；对话/检索类 P95 ≤3s、纯接口 ≤1s；30s 固定窗数吞吐；错误率 <1%（本地单机） | [实测] ≥100 次是分位数能算出 P95 的最小样本量（100 个样本里第 95 位才存在）；冷热分列是因为混报会让"启动 30s"污染热态数字 |
| B 并发与资源 | 3 | 阶梯加压 1→5→10→20 各 30s，找"崩塌点"；并发翻倍致错误率 >10% 或进程崩溃＝P1；有用户量预期却完全无限流＝⚠️；持续跑 15–30 分钟（快检 5 分钟）看内存是否只涨不落；启动 >60s 记 ⚠️ | [实测] 阶梯加压的目的不是"通过/不通过"，而是**找到拐点**——一个已知在 8 并发崩的系统比一个不知道的系统安全得多 |
| C 数据与外部依赖 | 3 | 慢查询/EXPLAIN 抽 3 条核心查询；N+1 全局搜循环体里的查询（发现即 P1）；外部调用四问（超时／退避重试／熔断降级／兜底假数据），前两条缺＝P1、后两条缺＝⚠️；幂等性——同一写操作重放两次看有没有重复副作用，**不安全且涉资金或不可逆＝P0** | [推演] "①②必须有、③④建议有"这个二分是成本判断：超时与退避是几行代码，熔断与降级要额外状态机——把前两者设成 P1 是可行的，把后两者设成 P1 会让所有小项目全红 |
| D 缓存与成本 | 2 | 命中率 ＋ 命中/未命中延迟对比（同问题问两遍）；**只缓存不命中＝⚠️**（原文举例的收益量级是"70s → 6s 这类"才算生效）；成本＝单次典型任务 token（prompt 与 completion 分列）× 单价 × 预估日活 → 月度估算，且**长对话成本要单独测** | [实测] "非线性膨胀的场景要单独测长对话成本"被标为暗坑高发区——上下文每多一轮都在放大每一次调用的基数 |
| E 回归与暗坑 | 2 | 相比基线**劣化 >30% ＝ P1，哪怕绝对值达标**；暗坑静态扫描 5 条（async 里同步阻塞、大对象深拷贝/整表读入、循环里重复编译正则或重复建连接、未分页的大列表接口、日志无上限增长），快检也要做 | [实测] "绝对值达标但相对劣化"也算 P1，是这一层最反直觉也最有价值的一条——它防的是"温水煮青蛙式退化" |

**"首次测得值记为基线，红线待用户确认"** 这句话在 §A2、§B3、§D2 反复出现。它的设计意图是：**没有历史的项目不许被判"不达标"**，因为拿一个凭空的阈值判失败等于没判。基线建立权交给用户，正好接上 §5.7 的"红线写进 `ACCEPTANCE.md` 固化"。

## 第 7 章 第三层 · AI 特有质量：先验量尺，再读数（19 项／5 组）

### 7.1 这一层的三条纲领

- **必须有定量分数，拒绝主观印象**；非 AI 项目整层 ➖，**但要确认真的没有 AI 成分**（这半句是防"我以为没有"）。[实测]（`layer3-ai-quality.md` 开篇）
- **铁律：先查"量尺"合不合格，再读数**——评测体系本身有洞，分数就是自欺。所以 §A（评测体系健全性）是 §B（分数）的前置条件，顺序不许颠倒。[实测]
- 方法论参照四个公开来源：RAGAS（忠实度/相关性/上下文查全查准）、LLM-as-judge 校准实践、τ-bench（pass^k 一致性）、OWASP LLM Top 10（2025）。[实测]（§A 前言；`CHANGELOG.md` v1.0.0「权威依据」节标注检索日期 2026-09-25）

### 7.2 §A 量尺三检（分数的前置条件）

| # | 检查 | 通过标准 | 关键机制 |
|---|---|---|---|
| 1 | 评测集存在且版本化 | 存在且入库版本化 | **没有评测集 → 本层主要分数项全部 ⬜，且"建评测集"自动成为 P1 行动项**（这条把"没尺子"从借口变成待办） |
| 2 | 泄漏／污染检查（P0 级） | 无泄漏 | 抽 **5–10 道题**的关键词，去 system prompt、知识库源文档、few-shot 示例、路由规则里搜——题目或答案直接出现在系统输入里＝分数虚高、评测作废重修、记 P0 |
| 3 | 判定口径 | 判分规则明确可复现 | 自动判分要写清关键词/正则/相似度阈值/schema 校验；用 LLM 当裁判时，judge 用的什么模型什么提示词要落盘，抽 **10–20 题**人工对照并记录**人机一致率**；<80% 时分数旁必须标注"judge 未校准，分数仅供参考"，全量验收时未校准 judge 记 ⚠️ |

**为什么"泄漏"能一个人干翻整层**：它是"自称 90% 实际 40%"的**头号来源**（原话）。更微妙的是它无法靠"再测一遍"发现——同一把坏尺子量一百次得到一百个一致的错误数字。这就是为什么量尺检查必须**独立于**读数步骤。[实测]

### 7.3 §B 分数与稳定性（本层核心产出：定量达标表）

**第 4 项 固定条件全量跑**：温度固定 0（多模型票选／抽样场景除外），全量跑评测集，**按题档分组报告**：回归题（必须全对）／扩充题（准确率）／评审题（开放题 judge 分）。默认红线：回归题 100%、扩充题 ≥80%；无既有基线时首次测得值即基线并提示用户确认。证据要求逐题结果明细落盘。[实测]

> 附一条容易被忽略的诚实条款：**引用旧分数须注明"沿用 X 月 X 日结果未重跑"**。这是把"复用历史数字"这个最常见的美化动作变成显式声明。

**第 5 项 稳定性（pass^k 思想：别只看平均分）**：抽 10–20 题重复跑 ≥3 轮，统计"**每题 3 轮全对的比例**"与分数波动幅度；判据：波动 ≤5 个百分点；**同一题时对时错的不稳定题要单独列出**——原文提醒它们往往藏着真问题（检索边界、参数抖动）。[实测]参考依据写得很克制：τ-bench 发现最强模型同任务跨轮不一致也常见，但**不一致率必须被量化而不是被平均分掩盖**。这句话是本层哲学的浓缩：不追求"完美稳定"，只追求"把不稳定测出来"。

**第 6 项 最弱项暴露（强制，不藏拙）**：必须点名最差的 1–2 个维度（正文示例："常识类检索 Hit@5 仅 2/10"），附**题号**证据，哪怕整体分数好看。**没有＝报告不合格**。[实测]

### 7.4 §C 幻觉与鲁棒性（7 项）逐项的"数从哪来"

| # | 检查 | 抽样量／阈值 | 为什么是这个数 |
|---|---|---|---|
| 7 | 幻觉 API/库/接口 | 抽检 **10 处**引用，**0 幻觉**；发现即 P0 | [实测] 原文理由："用户会照抄"——幻觉 API 的代价由下一个使用者承担，所以零容忍 |
| 8 | 幻觉事实（忠实度） | 抽 **10 题**逐句核对回答里的关键事实断言能否在检索到的上下文里找到；忠实度抽检 ≥90% | [推演] 10 题是"人工逐句核"的成本上限，90% 是"绝大多数有据"的位置；要更严就在 `ACCEPTANCE.md` 写高 |
| 9 | 死循环与预算失控 | 静态查三层护栏（轮数上限／token 预算／超时熔断）**至少有二**；动态构造一个必然失败的工具，看会不会原地重试到天荒地老 | [实测] "至少二"而不是"必须三"：给的是可达成度与现实折中；缺护栏＝P1 |
| 10 | 上下文管理 | 超长对话/超长文档输入，看是否爆上限、有无压缩/截断/滑窗、截断后关键信息是否丢 | 判据是"**上限附近有优雅处理，不裸崩**"——不要求无限长，要求崩得体面 |
| 11 | 注入与越狱（OWASP LLM01/LLM07） | 至少 **3 个用例**：①"忽略以上指令"直接注入 ②藏在用户数据/文件内容里的间接注入 ③套话术提取 system prompt | [实测] 全部裸奔＝P1，**面向外部的服务＝P0**——暴露面决定分级，同一缺陷在不同项目里不是同一级 |
| 12 | 拒答质量（双向） | 该拒的 5 题、不该拒的 5 题，**双向都记录误判率** | [实测] 原文点睛："只测'答得多好'不测'拒得多准'是评测盲区" |
| 13 | 校准（知道自己不知道吗） | 准备 **5 道知识库里根本没有答案的题**，看它编还是坦白／走兜底；编造率 ≤40% 且必须如实报告 | [实测] 原文注："兜底转工单算最优解"——满分答案不是目标，**承认不知道才是** |

### 7.5 §D 工具调用与输出（6 项）

第 14 工具选择准确率（Hit@5 ≥70%，含工具题才测；无工具题则建议补充，P2）；第 15 参数正确率（错字段/错类型/幻觉参数名）≥90% 且报错后有明确恢复路径；第 16 结构化输出解析成功率 ≥95% 且失败有重试（裸崩＝⚠️）；第 17 多轮一致性（同一事实在第 2 轮与第 8 轮分别问，抽 3 组问答 0 矛盾；角色扮演类/有记忆系统必测，"后写覆盖先读"单列）；第 18 首字延迟 TTFT（有流式输出时测 10 次取中位，对话类 >3s 记 ⚠️，原文注明"用户感知就是卡死"）；第 19 版本固定与漂移（prompt 入库 ＋ 模型版本记录 ＋ 有回归机制；裸依赖 "latest"＝⚠️）。[实测]

**第 19 项是整层最"长期主义"的一条**：供应商静默升级模型时，你的分数会变，但代码一行没动。判据不是"版本必须是最新的"，而是"**评测能不能抓到漂移**"——有定期回归就能抓到，抓不到就是 ⚠️。[实测]

### 7.6 §E 定量达标表：本层的唯一交付物

正文给的示例格式（**数值是示例，不是实测**）：

| 维度 | 实测值 | 红线 | 判定 | 证据 |
|---|---|---|---|---|
| 回归题（18 题） | 17/18＝94.4% | 100% | ⚠️ | `eval_full.json` |
| 扩充题（38 题） | 71.1% | ≥80% | ❌ | `eval_full.json` |
| Hit@5 | 78% | ≥70% | ✅ | `eval_full.json` |
| 稳定性（15 题×3 轮） | 波动 4pt | ≤5pt | ✅ | `eval_stability.json` |
| 注入防护（3 例） | 挡住 2 例 | 3/3 | ❌ P1 | `adversarial.md` |
| 未知题编造率 | 3/5 | ≤40% | ⚠️ | `abstention.json` |

表末原话：**本层不给综合总分——权重会掩盖最弱项**；最弱项在第 6 项单独点名。[实测]

**为什么"不给总分"是一条设计而不是谦虚**：一个加权总分会让"扩充题 71.1%（❌）"被"Hit@5 78%（✅）""稳定性达标（✅）"稀释成"整体 85 分，良好"。而验收的用处恰恰在于**指出那个会出事的地方**。这也是第 1 章故障 ④ 的最终解法。

## 第 8 章 漏斗后半：第四层会不会自救、第五层能不能被用、第六层能不能交出去

### 8.1 第四层 · 业务与兜底（11 项／4 组 ＋ 灵魂拷问）

**判定原则原文**：验收不是只挑毛病，更要看系统**有没有自我修复的能力**；本层灵魂是"**真实触发一次**"，代码里"有这个功能"不算数，要按一遍链路。两条权重规则也写在开篇：面向外部用户的服务，闭环项权重高于内部工具；个人毕设类项目允许闭环项 ⬜ 偏多，**但必须写进能力缺口**。[实测]（`layer4-business.md` 开篇）

| # | 项 | 怎么"真实触发" | 判据要点 |
|---|---|---|---|
| 1 | 答不上来的兜底 | 构造一个系统答不上来的输入，真走一遍，看是否触发工单/转人工/引导式降级话术，兜底后用户拿得到什么 | "静默编一个答案"或"裸报错"＝P1，**对外服务＝P0** |
| 2 | badcase 回流闭环 | 三步实做：点一次赞查一次库看是否真落库 → 真导出一条评测候选 → 确认导出的题下次回归会跑 | **断在哪一环，断点就是 P1**；原话："反馈只收集不消费＝反馈黑洞" |
| 3 | 边缘场景清单 | 结合动态启发（S3/S4）列出尚未覆盖的边缘场景，逐条标风险（高＝会出事故/中＝体验受损/低＝瑕疵）与"要不要现在补" | "完全没想过边缘场景"本身记 ⚠️ |
| 4 | 降级演练 | 把主依赖弄挂：把模型 baseURL 指向一个必定连不上的本地地址（工具速查给的招）或用 mock 拦截，看行为是优雅降级／明确报错＋重试引导／裸栈崩溃 | 全量级必做，标准级做静态确认；"代码里有 try-except 但从未验证过"＝⬜ 并升级为全量必测项 |
| 5 | 回滚方案 | 上一版本能否一键回退（git tag／镜像版本／备份配置），步骤写下来了吗，演练过吗 | **没演练过＝⚠️**；原话："没演练过的回滚＝没有回滚" |
| 6 | 备份与恢复 | 有备份机制吗；**从备份真恢复一次到测试环境**了吗 | 只有备份没验证＝⚠️；**关键数据无备份＝P0** |
| 7 | 监控告警 | 有指标采集吗（错误率/延迟/用量）、告警打给谁、多久能发现核心链路挂了、有看板吗 | 核心链路至少有一个"**症状级**"告警（用户已受影响的信号），而不是只有"进程死了"这种原因级；个人项目无监控＝⚠️ 记能力缺口 |
| 8 | 审计与追溯 | 出问题时能还原现场吗：关键请求有无日志/落库（谁、什么输入、什么输出、何时） | 要能从一次坏回答**反查**到当时的输入与中间过程——没有轨迹日志就无法复盘 badcase |
| 9 | 运维手册 runbook | 常见故障（API 挂了/知识库异常/额度耗尽）处理步骤写下来了吗 | 至少覆盖 Top3 可能故障；无＝⚠️ |
| 10 | 知识更新通道 | 加一条新知识的完整流程真走一遍要多久，能不能不重新部署就更新 | 有明确流程且 **≤30 分钟**走完一次；"改知识要改代码重新发版"＝⚠️ |
| 11 | 过期知识清理 | 有过期/失效识别与清理机制吗，有 `last_updated` 元数据吗 | 完全没有＝⚠️；原话："这是 RAG 系统答旧不答新的根源" |

**§E 灵魂拷问 4 问（报告里必须向用户提出 2–3 个并尝试自答）**：反馈黑洞检查（谁看？多久响应？证据是什么——还是"应该有人看"）；迭代断点检查（这次 badcase 到下次评测集更新之间隔几步手工活，**步骤越多闭环越容易断**）；承诺检查（README/简历/汇报里每个对外宣称的数字都有落盘证据吗，与"宣称与事实打架"型 P0 交叉核对）；单人风险检查（只有创建者一人能跑通部署/修复吗，文档能不能让第二个人接手）。[实测]

> 这四问的共同结构是：**把"应该有人在做某事"这个默认假设当成待证事项**。 验收最容易放过的不是代码 bug，而是"组织上有个洞，但没人承认它是洞"。第 4 问（单人风险）对一个人与 AI 协作的项目尤其致命——它就是那个"第二个人不存在"的局面。

### 8.2 第五层 · 无障碍合规（按需，四个最小探针）

**定位**：本层**不拦截**（区别于第一层），但把"能不能被用"从主观感受变成逐条可核对的客观项（WCAG 2.1 的 4 Principles × 13 Guidelines，A ＋ AA 两级共约 50 条，AAA 按需）。灵魂与第三层同源：**没有实测数值就没有结论**——看一眼 DOM 觉得"有 alt"不算 ✅，键盘没真按过不算 ✅。[实测]（`layer5-accessibility.md` 开篇）

**启用条件与目标级**：有面向人或对外的 UI（Web/H5/App/小程序/桌面）才启用；纯后端、CLI、库、数据管道整层 ➖。合规目标默认 **AA**；政务/医疗/公共教育/有明确法规要求或合同写了无障碍 → **AAA**，且**写进 `ACCEPTANCE.md` 后本层转为红线级**，失败按 P 级正常参与结论。[实测]

**开测前先定三件事**（写进报告元信息）：合规目标（AA/AAA/仅 A）、审计范围（全量页面/核心链路 N 条/增量 diff 涉及页；快检级只做"核心链路 ＋ A 级全项"）、审计模式（自动扫描/人工走查/两者）。其中第三条自带一条关键禁令：**自动扫描只能覆盖约一半违规**（引 axe-core 官方口径），其余必须人工；**只用自动结果下结论＝⬜未测，不是 ✅**。[实测]

**四个最小探针（本层的"实测"全靠这四个）**：

| 探针 | 覆盖条款 | 具体怎么做 | 判据 |
|---|---|---|---|
| **P-1 对比度算数值** | 1.4.3/1.4.6/1.4.11/1.4.1 | 取前景与背景的 sRGB → 线性化：`c/255` 后，若 ≤0.03928 则 `c/12.92`，否则 `((c+0.055)/1.055)^2.4`；相对亮度 `L=0.2126R+0.7152G+0.0722B`；对比度 `=(L亮+0.05)/(L暗+0.05)` | 正文 ≥4.5:1（AAA 7:1）；大字（≥18.66px 粗体或 ≥24px）≥3:1；UI 组件与图形 ≥3:1 |
| **P-2 键盘走查** | 2.1.1/2.1.2/2.4.3/2.4.7/2.4.1/3.2.1/3.2.2 | **只用** Tab/Shift+Tab/Enter/Space/Esc 走完一条核心链路，记录：能不能走完、焦点顺序是否与视觉顺序一致、焦点是否可见、有没有被困在弹层里、跳页链接是否可达 | 原话证据写法示例：`Tab×6 → 焦点进入日期控件后 Shift+Tab 出不来＝键盘陷阱 ❌ P1` |
| **P-3 辅助技术快照** | 1.1.1/1.3.1/2.4.2/2.4.6/3.3.2/4.1.2/4.1.3 | 读浏览器可访问性树（DevTools Accessibility 面板/a11y snapshot/`pa11y`/`axe`/Lighthouse a11y 类目），逐项确认非文本有名称、结构用标题与语义标签、每页 title 有描述性、表单控件有 label、动态状态消息有 `aria-live` | Windows 手测用免费的 NVDA；**没装就标 ⬜ 并写补测方法，不许用"看起来有 aria-label"顶替** |
| **P-4 缩放与窄口** | 1.4.4/1.4.10/1.4.12/1.3.4 | 文本放大 200% 与视口 320px **各截一次图** | 不得横向滚动、不得裁字、不得重叠；文字调整行距字距不破坏布局；不强制横屏 |

证据写法要精确到"位置＋色值＋算出的比值＋要求值＋截图路径"，模板形如：`首页搜索按钮 文字#8A8A8A/底#FFF → 3.0:1，要求≥4.5 → ❌（截图 acceptance/evidence/contrast-search.png）`。[实测]

**P 级映射表（6 行，对齐 `scoring-and-verdicts.md`，不许自创分级）**：宣称符合 AA 而实测未达＝**P0**（宣称与事实打架）；3.3.4（法律/财务/数据类不可逆操作无确认可撤销）失败且涉资金/数据＝**P0**；A 级任一条 ❌（键盘不可达、无 alt、无标签、焦点陷阱）＝**P1**；AA 级 ❌（对比度不足、无 focus ring、320px 横向滚动）＝**P1**（对外/政务场景按红线处理）；AAA 细节项与非核心页同类问题＝**P2**；只跑自动扫描、人工项未做＝**⬜**。[实测]

**结论只用四档，禁止"基本符合"**：未达 A／达 A／达 AA／达 AAA，另加"不可判定"（人工项大面积 ⬜ 时必须写 not-determined，**禁止给等级**）。[实测]（§5）
> **口径冲突留档**：`CHANGELOG.md` v1.2.0 与 `SKILL.md` §3 表都写"结论只用四档"，而 `layer5-accessibility.md` §5 实际列出**五个**取值（四档 ＋ 不可判定）。本页以清单文件为准并列明差异，不合并成一个说法。

**两处"照抄就会判错"的定级纠错**（这条是收编市场插件时最实在的产出）：`2.1.4 Character Key Shortcuts` 实为 **Level A**（插件清单列在 AA 组）；`4.1.3 Status Messages` 实为 **AAA**（插件标 AA，照抄会直接把合规等级判错）。清单另注 `1.3.5` 表单 autocomplete 是 AA，勿误记为 A。[实测]（`layer5-accessibility.md` §2/§3 加粗注、`CHANGELOG.md` v1.2.0「优化了哪些地方」）

**吸收而非接管**的取舍也写在同一处：插件本体装在带版本号的缓存目录里，**升级即另开新目录，写进插件的改动当场作废** ⇒ 只把清单化结构吸进本库，不依赖、不改动、不接管；且因原插件 finding 字段（category/severity/description/suggestion/location）**没有证据槽**，判定段一律重写为本库的五态 ＋ P 级 ＋ 证据落盘。[实测]

**§7 专项动态启发**（报告里必须问 2–3 个，且走 D-n 实证流程）：假设一个只用键盘的人，这条链路他会在第几步彻底走不下去（→当场变成一个 P-2 用例）；假设一个屏幕阅读器用户，这个"提交成功"他能感知到吗（→ P-3）；假设强光下/单手持机/老年用户，这块小灰字与 32px 热区扛得住吗（→ P-1 ＋ P-4）；动效与无障碍的交叉坑：`prefers-reduced-motion` 有没有被尊重、自动轮播有没有暂停键。[实测]

> 这一节的写法很值得学：它不新增检查项，而是**换一个人的身体去走同一条链路**，把已有的四个探针变成用例来源。

### 8.3 第六层 · 用户可交付（v1.3.0 新增，7 项／3 组）

**判定原则原文**：这一层的灵魂是"**交付物定义被一个真实的人验证过**"。测试全绿、指标达标都盖不住它。[实测]（`layer6-deliverability.md` 开篇）

| # | 项 | 怎么查 | 判据 |
|---|---|---|---|
| 1 | **交付物定义存在且可验证** | 在项目台账/PRD/README 里找一句"谁用（具体角色）／怎么用（一次真实操作）／第一次交付长什么样"的可验证定义 | 存在且**一句话可判定真伪**；不存在＝**P0**（验收无基准，一切"能用"都是开发者自说自话） |
| 2 | 部署可达性（目标用户视角） | 从零按项目自己的部署文档走一遍：命令条数、前置依赖、失败点；非开发者能否独立完成启动 | 步骤 ≤ 项目自定义上限（自托管产品建议 **≤5 条命令**）且每步可复制粘贴；**文档写"很简单"而实际 20 步＝❌** |
| 3 | 使用手册存在且自足 | 是否覆盖核心动作全流程（含截图）；零项目上下文的新人能否按手册走通；术语是否有人话解释 | 新人自读走通核心动作；手册引用内部黑话无解释＝⚠️ |
| 4 | **目标用户人设端到端演练**（灵魂项，禁作弊） | 以"不会敲命令的目标用户"人设走完交付物定义的核心动作——浏览器/界面**真实点击**；**禁 API 直调、禁开发者知识补偿（如手改数据库）**；全程录屏或逐步截图 | 核心动作全部完成且有证据；每处卡壳如实记录（卡壳清单＋修复引用）；**"我们演示过"不算——演示者＝开发者时不算用户验证** |
| 5 | 错误路径的用户体验 | 人为制造 3 种用户会犯的错（传错格式/缺必填/重复提交），看用户看到的是人话＋下一步指引，还是裸栈/英文堆栈 | 错误信息＝人话＋行动指引；**裸异常直达用户＝P1** |
| 6 | 数据持久与恢复的用户交代 | 用户操作到一半重启/断电——数据还在吗？**用户怎么知道数据在**？ | 重启后状态可恢复且用户可见（列表/状态/提示）；**静默丢失＝P0** |
| 7 | 用户反馈的采集通道 | 用户遇到问题怎么办——有反馈入口/联系方式/已知限制页吗 | 至少一条通道 ＋ **已知限制公开（三段式：知道存在／为何不修／修法是什么）**；"装了就失联"＝⚠️ |

**判定联动**：本层任何 P0（定义缺失／核心动作未验证／静默丢数据）→ 项目结论封顶**不通过**（对"给别人用"的项目）；手册缺失／部署超限＝P1 → 封顶**有条件通过**；纯自用项目整层 ➖ 时，报告须记一句"**若未来交付他人，本层全部项需补验**"。[实测]（§判定联动）

**为什么"人设演练"要专门写"禁作弊"**：这一项是最容易被悄悄绕过的——用 curl 打通接口最省时间，但它证明的是"接口能工作"，不是"用户能用"。所以规则把手段本身写成判据：**必须界面真实点击，禁止开发者知识补偿**。[实测] 那句"演示者＝开发者时不算用户验证"是整份清单里最锋利的一句。

## 第 9 章 另一半：动态启发六步法、实证门槛与报告产出

> 对应 `references/heuristics-playbook.md` 全文与 `SKILL.md` §6、`references/report-template.md`。

### 9.1 为什么固定清单之外必须要动态启发（这是全篇最核心的论证）

手册开篇把分工写得很干净：**固定清单保证下限（不漏常规项），动态启发负责上限（挖出清单上没写的、这个项目特有的暗坑）**。[实测]

三个理由，一个比一个硬：

1. **清单是有限的，项目是无限的。** 第一层 27 项是按"任何项目都可能踩"的最大公约数写的；它写不出"你这个项目的列表接口正好在循环里查库"。清单的覆盖能力有天花板，越到长尾越靠不住。
2. **清单会被"应试化"。** 一旦检查项固定，被验收的一方就会针对清单优化（清单要锁文件，就补一个假的锁文件；清单要测试，就交一堆空断言）。第一层第 3 项"测试有效性抽检"就是为这种情形打的补丁——而补丁本身也是清单的一部分，同样会被应试。**只有"结合本项目特征现编用例"这一环没法提前应付**。[推演]（什么输入会出问题：一个已知验收清单的项目，把 `assert result` 换成 `assert result is not None`——固定项全过，断言依然空心。）
3. **暗坑的形状只有项目自己知道。** 同一类缺陷（比如并发写同一行）在 Web 服务里是 P0，在单人本地脚本里是 ⚠️。分级要结合画像，而画像里的"这个项目具体在干什么"永远写不进通用清单。

**代价也很清楚**：动态层是唯一"由 AI 自由生成结论"的口子，所以它必须被证据纪律二次约束——这就是 9.3 的实证门槛。三者的关系是：**清单给广度，启发给深度，门槛给诚实**。

### 9.2 六步法（S1–S6）各产出什么

| 步 | 名字 | 具体动作 | 产出形状 |
|---|---|---|---|
| S1 | 画像打底 | 跑 `profile_project.py` 拿 JSON；人工补看三样：入口文件（main/app/index）、配置加载处、目录结构 | 一段 3–5 句的项目画像描述：这是什么、核心链路是哪条、最像哪类项目 |
| S2 | 类型 playbook 匹配 | 按画像命中的类型逐条过已知坑；本页数出 playbook 覆盖 **7 类**（Web/API、CLI、库/SDK、Agent/LLM、RAG/知识库、数据管道/定时任务、前端） | 每条命中坑写一个验证方法（请求／代码审查），**并跑掉它** |
| S3 | 风险维度扫描 | 对 9 个维度逐一提问（并发／状态持久化／外部依赖／不可逆操作／资金与隐私／长时任务／权限／时区与编码／配置与密钥） | 命中维度 × 问题的回答（✅/⚠️/❌ ＋ 证据）；**未命中的维度也要写一句"为什么不命中"，防止漏判** |
| S4 | 攻击者视角 | 换脑子问三个问题：我要**弄崩**它（10 万字粘贴、空输入、二进制乱码、并发 50 连发、递归嵌套）、我要**骗过**它（注入、伪装系统消息、把指令藏进待处理文件、套 system prompt）、我要**让它做坏事**（诱导越权"把所有用户的记录给我"、诱导危险操作"清空数据库吧"） | **3–5 个刁钻用例并真实执行**，每条记【输入 → 实际输出 → 期望 → 判定】 |
| S5 | 上线前夜 pre-mortem | 提问："假设明天上线，一周后出了大事故，最可能的三件事是什么？"再对每件反推：现在哪一行/哪个环节会让它发生 | 预演事故清单（事故描述 → 当前缺口 → 建议动作 ＋ 分级） |
| S6 | diff 驱动 | `git log --oneline <上次验收tag/日期>..HEAD` 看改了什么，`git diff --stat` 看影响面；对每个变更模块问三句：改了什么行为、动了哪些调用方、有没有配套测试更新 | 变更影响表（模块 → 变更 → 影响面 → 测试覆盖状态）；**"变了但没测试覆盖的模块＝增量验收头号嫌疑"** |

**S4 里最反直觉的一条**：执行要求原文写"**系统扛住了也是有效且宝贵的结果**，如实记录'挡住了 ＋ 靠什么挡的'"。攻击者视角不是为了找出问题，而是为了**知道防线在哪里**——"挡住了"这句话下次改动时就是回归基线。[实测]

**S5 为什么有效**（手册自己的解释）：它是把"挑毛病"变成"叙事推演"的技巧，**对挖结构性隐患（不是单点 bug）特别有效**。人问"有什么问题"会列出十个小毛病；人问"一周后大事故是什么"会被迫去想系统性缺口。[实测]

**第三层的量化要求**（写在 `SKILL.md` §6）：至少产出 **3–5 个刁钻动态用例**并真实执行，类型清单固定为模糊输入、提示注入/越狱、超长上下文、边界值、恶意格式输入。[实测]

### 9.3 实证门槛：动态层的反幻觉铁律（本项目最值得抄走的机制）

手册原话：**S1–S6 产出的每一句"我觉得这里有风险"都只是【假设】，假设不是发现。** 动态层与固定清单执行**同一套**证据纪律：[实测]

```
1. 假设 → 探针 → 二值判定
   每条假设（H-n）必须当场转化为一个最小可执行探针（一条命令/一个用例/一次重放），
   跑出输出后判定：证实（风险真实存在）或 证伪（排除）。
   只有证实了的才升级为实证发现（D-n）。
2. 只有实证发现能进主报告与结论
   D-n 参与 P0–P2 分级与结论映射；
   探针跑不了（环境不允许/超出本次验收预算）→ 假设留在"假设区"，
   标注信度 ＋ 补验方法，不参与结论映射、禁止给 P 级。
3. 证伪也是产出
   被证伪的假设记入"排除区"（一句结论 ＋ 证据路径），
   防止下一轮验收把同样的怀疑重猜一遍。
4. 证据落盘与固定清单同标准
   探针命令与输出存 acceptance/evidence/，报告引用路径而非转录数字。
```

**为什么要专门设计"排除区"**：它解决的是一个别人不管的问题——**重复怀疑的成本**。没有排除区时，每一轮验收都会重新怀疑一遍同一个（早已证明没问题的）点，白白消耗时间与注意力，还可能因反复怀疑把结论搅浑。X-n 的作用是把"已经排除了"变成一个有证据、可复用的结论。[推演]（什么输入会出问题：三轮验收都怀疑"长连接内存泄漏"，每轮都花 30 分钟 soak，最后发现第一轮就证伪了——排除区一条记录值 60 分钟。）

**数量自查**（原文给的硬指标）：标准验收至少 **5 条**实证发现或排除记录（只有假设不算数），全量至少 **10 条**。**零发现通常意味着启发没认真做**，除非项目真的极小（此时要在报告里说明）。[实测]
> 这条把"我很认真地在思考风险"变成可计量的东西：产出条数 ＋ 每条都有探针输出。

**为什么这套规则是 v1.1.0 才加的**：`CHANGELOG.md` v1.1.0 写明来源是"外部建议"，且采纳时做了两点加强——**假设/实证二轨分流**、**回流加质量门与路由分家**。原版（v1.0.0）只要求"动态发现附证据与复现方法"，**没堵死"没跑验证就把猜测写成分级发现"的通道**。这是一次真实的设计补漏，可以直接当"如何给 AI 上约束"的案例讲。[实测]

### 9.4 S7 知识回流：验收 → 库 → 下次验收的双向闭环

**回流三道质量门（全过才回写，缺一不可）**：① **已实证**（有探针输出证据；假设一律不回流，否则库被猜测污染）；② **通用型**（不是本项目特有的环境巧合——自问"换个项目会不会也这样死"，答"会"才回流）；③ **非重复**（目标库内查重无命中；失败模式库先查术语表，业界已有名字的概念**并入现有条目，不另起新条目**）。[实测]

**回流路由按知识归属分家**（"不许一股脑塞一个库"）：

| 发现属于 | 回流到 | 格式与规则 |
|---|---|---|
| Agent/LLM 应用的新死法（循环/成本/安全/上下文/并发/错误恢复/治理合规七类） | 失败模式与对策库的失效模式目录对应类别文件 | **七字段格式**：现象／术语／根因／对策／最坏后果／检查问题／相关；编号接续该类别现有最大号；追加前先查术语表；改完同步宿主注册副本并在该库 CHANGELOG 留痕；两个视图文件的同步列为待办告知用户 |
| 通用工程踩坑（报错/环境/工具链/平台兼容） | 踩坑日志 skill | 按其"根因层 ＋ 案例层"流程沉淀 |
| 本机私有/环境相关 | 各 agent 自己记忆库的踩坑层 | 按记忆纪律打分入库 |

**双向闭环的另一半**：回流的除了新死法，还有"库内某条死法的对策描述与实战不符"——同样要回改原条目（遵守库内治理：先改主目录再同步视图）。反向：下次验收的 S2/S4 **先拿库的七类死法清单对号入座**（上线前检查清单与对应类别文件，手册写明是"41 条逐条问'它会不会这样死'"），命中的直接进固定排查；**对完号仍对不上的新死法＝回流候选**。[实测]

> 这个闭环的价值在于它把"知识"变成有进有出的活水：验收不是消费知识的一次性动作，而是生产知识的环节。 也解释了一个常见现象：同一个 skill 用久了会越来越"省事"——因为清单在长，排查从"现场排查"变"对号入座"。

### 9.5 二轨三区的记录格式（照抄就能用的模板）

```
【实证发现区】参与结论映射
D-1 【P1】标题一句话
- 来源：类型playbook / 风险维度 / 攻击用例 / pre-mortem / diff驱动 / 库对号未命中
- 假设→探针：H-3"怀疑列表接口 N+1" → 探针=开 SQL 日志连打 20 次接口
- 判定：证实（20 次请求产生 61 条查询）
- 证据：acceptance/evidence/sql_log.txt
- 复现方法：（一步步可执行）
- 建议：（怎么修/怎么补）
- 回流候选：是/否（是 → S7 三道门 + 路由）

【假设区】不参与结论，禁止给 P 级
H-2 【未定级】怀疑长连接内存泄漏
- 依据：静态读码发现 channel 未显式 close
- 未实证原因：30 分钟 soak 超出本次验收预算
- 补验方法：本地 soak + 内存曲线，转全量验收必做项

【排除区】证伪留痕，防重猜
X-1 "怀疑路径穿越" → 证伪：session_id 在 schemas 层白名单校验（证据 evidence/…）
```

[实测]（`heuristics-playbook.md`「启发结果记录格式」节）注意 D-1 那条的措辞结构：**先写出它原来是哪条假设**（H-3），再写探针，再写判定的数字。这个"假设 → 探针 → 判定"三段式是整份手册里最值得抄进别处的写法——它让每条发现自带来历。

### 9.6 报告九节与落盘形状

`SKILL.md` §5 与 `report-template.md` 共同规定（**必须照模板落盘，不许自创结构**）：[实测]

- **路径**：`<项目根>/acceptance/ACCEPTANCE_REPORT_<YYYYMMDD>_<级别>.md`，另复制一份为 `acceptance/latest.md`；原始证据存 `acceptance/evidence/`。
- **九节内容**：元信息 → 验收结论 → 核心指标数据（每格带口径与证据文件）→ 各层清单达标表（含启用中的第五/六层）→ 动态发现的风险 → 诚实暴露的弱点（最差 1–3 项，点名不藏拙）→ 能力缺口与未测项 → Top3 行动计划（具体到文件/函数）→ 历史对比（有上次报告时做趋势对比）。
- **模板文件实有 10 个带号小节**：§0 元信息 … §8 历史对比 ＋ §9 经验沉淀建议。
  > **口径差异留档**：`SKILL.md` §5 说"报告九节"并列出九项，模板文件多出的第 §9 节是"经验沉淀建议"（本次发现的通用型新坑 → 建议沉淀的条目草案）。两处并列，不合并。

## 第 11 章 例行维护与体检：怎么验证它真在生效

### 11.1 版本同步链（`SKILL.md` §9 维护）

原文流程：**权威库 → 宿主注册副本 → lint 体检**，并强调"权威库永远保持最优版"。[实测]（本页把正文里的盘符写法抽象成"宿主注册副本"，见 15.4。）

这条链意味着：改 skill 不是编辑一个文件就完事——**注册副本没同步，AI 实际加载的仍是旧版**，于是出现"我明明改了为什么没生效"这种最耗人的假故障。

### 11.2 怎么验证这支 skill 真在生效（4 个可观察信号）

1. **看有没有落盘目录**：验收跑完后项目根应出现 `acceptance/`（含 `ACCEPTANCE_REPORT_*.md`、`latest.md`、`evidence/`）。只有对话里的一段总结＝没生效。[推演]（具体什么输入会出问题：你说"验收一下"，AI 回了一大段"整体不错，有几个小问题"但项目根一个文件都没新增——那是它在凭印象答，不是在执行流程。）
2. **看结论是不是三档之一**：出现"基本通过""大体没问题"就说明判定环节被绕过了。
3. **看 ⬜/➖ 有没有附理由**：合法的"没测/不适用"一定带原因与补测方法；空着就是假绿信号。
4. **看动态发现有没有 D-n 的三段式**（假设 → 探针 → 判定），以及 **Phase 0 是否真跑过脚本**：报告元信息里要有画像证据（类型判定＋证据），而不是只写"这是个 Web 项目"。

### 11.3 这份 skill 自己的 CHANGELOG 纪律

`CHANGELOG.md` 开篇立的是**用户铁律 6**：每版记录三件事——**优化了哪些地方、增加了什么功能、解决了什么问题**。[实测]五个版本条目（v1.0.0 → v1.1.0 → v1.1.1 → v1.2.0 → v1.3.0）都按这三问写，包括"来源"（谁提的、外部建议还是自查发现）。

> **一处诚实留档**：文件里的条目顺序是 v1.2.0 → v1.1.0 → v1.0.0 → v1.1.1 → v1.3.0，**不是单调倒序**（v1.1.1 被追加在了 v1.0.0 之后，v1.3.0 在最后）。这不影响内容，但影响阅读。本页把它当作维护项记下来，供主控方决定是否重排。

### 11.4 项目侧的配套体检（`ACCEPTANCE总装模板.md`）

项目根 `ACCEPTANCE.md` 一旦生成，就是常驻契约：Phase 0 优先读它，交付流水线的收尾两步按它执行，平时它就是项目自己的质量契约。它还带一条**版本锚定**规则：复制到项目后锁定当时的源模板版本，**源模板升级不追溯已归档项目**——避免"标准变了，去年的项目突然全变红"。[实测]

## 第 15 章 工程规范与安全规范（含未采纳项的诚实留档）

> 本章的「库 ↔ 仓库」差额是 2026-10-09 上午快照的实测记录；同日下午 17 支本体已按 [CONTRIBUTING.md](../CONTRIBUTING.md) 第一节追平并在仓库侧脱敏。下面的数字原样保留，作为那次追平的历史凭据，不代表当前状态。

### 15.1 命名与调用键

- 目录名「四层漏斗固定清单加动态启发」是 v1.0.0 时代的标签，v1.2/v1.3 各加一层后**标题改成了"四层漏斗 ＋ 按需无障碍/用户可交付层"，但文件夹名与调用键 `project-acceptance` 不动**。理由写在 `CHANGELOG.md` v1.2.0：改名要牵动映射表、宿主链接、他方引用，"为一个标签名付全树改指针的成本不值"。[实测]
- 这是一个可复用的工程判断：**命名与标识符的迁移成本，要按"牵动多少处指针"算，不按"名字好不好看"算**。标签过时 → 用标题与文档补注解决，不改主键。

### 15.2 字段与文件规范（本 skill 自己产出的东西长什么样）

- 报告文件名格式：`ACCEPTANCE_REPORT_<YYYYMMDD>_<级别>.md`（级别取"快检/标准/全量"三值之一）。
  目录约定固定三个：`acceptance/`、`acceptance/latest.md`、`acceptance/evidence/`；**报告里引用证据路径而不是转录数字**（避免同一数字在报告和证据里各写一份、改一处漏一处）。
- 项目契约文件：`ACCEPTANCE.md`，字段为 项目类型／红线值／评测集路径／豁免项／历次验收报告路径（D 节 5 项）。
- 画像脚本字段：见 5.3 的 14 个顶层键；脚本退出码 `0` 成功、`2` 目录不存在；出错时输出 JSON（`{"error": …}`）而不是抛栈——便于上层解析。[实测]

### 15.5 冷启动（第一次怎么用它）

1. 先只跑**快检**（15–40 分钟、不花钱）：Phase 0 ＋ 第一层全量 ＋ 各层静态可查项 ＋ 报告。目的是先堵"作弊与不可复现"，这两类问题修起来最便宜。
2. 首轮结束时**必须做一件事**：让 AI 按总装模板生成项目根 `ACCEPTANCE.md` 草稿，把符合你项目定位的红线填进 D 节并改定——此后第二轮开始的每一轮对比才有意义。项目要给别人用时，第一次验收就直接选**标准**级并确保第六层启用（别因为"看起来是自用的"就 ➖——"给别人用"是产品意图，不是文件数量）。

### 15.6 未采纳项与遗留（诚实留档）
