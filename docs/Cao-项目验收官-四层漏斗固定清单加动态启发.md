# Cao-项目验收官（project-acceptance v1.1.0）

> [← 返回总目录](../README.md#skills-index)

## 五分钟速览

1. 一句话，像严苛的验收官一样给项目做全量体检——**固定清单保覆盖，动态启发挖暗坑，证据链保诚实**。
2. 四层漏斗，基础工程（拦截级）→ 指标性能 → AI 特有质量 → 业务兜底，第一层不过直接打回。
3. 四条军规凌驾一切效率考量：只诊断不修复、证据为王、三禁反作弊、非破坏先报价。
4. 每个检查项五态判定（✅❌⚠️⬜➖），「未测」和「不适用」是合法结论，编数字才是死罪。
5. 动态启发挖出的隐患先落为【假设】，必须当场跑出最小探针证实，才升级为【实证发现】参与分级——启发不许变成新的幻觉源。
6. 产出落盘的《项目验收报告》，结论只有三档（通过/有条件通过/不通过），不给虚假的综合总分——权重会掩盖最弱项，用分项达标表加最弱项点名代替。

## 它在解决什么问题

项目做完想检查一下，常见的失败形态有五种。

| 故障 | 表现 | 对应设计 |
|---|---|---|
| 验收走形式 | 「测试都过了，没问题」——检查项凭印象跳着看 | 固定清单逐项核对，跳项=验收作废重来 |
| 结论靠感觉 | 「整体挺稳的吧」——没有分项判定 | 五态判定 + 结论映射，不许自由发挥 |
| 报喜不报忧 | 报告全是优点，最差的地方被综合分掩盖 | 强制「诚实暴露的弱点」节，最差 1-3 项点名 |
| 暗坑靠拍脑袋 | 「感觉并发有问题」——感觉停留为感觉 | 动态启发六步 + 实证门槛，感觉必须变成用例跑出结果 |
| 修复污染验收 | 验收时顺手改代码「让验收变好看」 | 军规 1 只诊断不修复；军规 2 证据为王 |

## 四条军规详解

**只诊断，不修复。** 验收中发现的问题一律记录进报告，禁止顺手改代码、改测试、改配置来「让验收变好看」。这条防的是验收者与被验收者的角色混同——一边改一边验，等于运动员兼裁判。用户明确说「验收+修复」模式时除外，且每处修复同样要留证据。

**证据为王。** 每条结论必须附证据：命令与退出码、`文件:行号` 引用、或落盘的测量输出（存 `acceptance/evidence/`）。与测试纪律（数字必须有落盘证据）、抗幻觉纪律（事实/假设/未知分离）同源执行。测不出来的写「⬜未测」，不确定的写「未知」——**这不丢人，编数字才丢人**。

**三禁（反作弊）。** 禁止修改/删除测试、放宽阈值、缩小评测集来凑「通过」；禁止编造任何数字；禁止把不适用的检查项硬测出结果。第三禁看着多余，实际是给 AI 的——它太想给每个格子填上内容了，「➖不适用 + 一句理由」是合法且更诚实的答案。

**非破坏 + 先报价。** 不删数据、不压测生产环境、不做不可逆操作；压测只打本地或测试环境。需要调付费 API 跑评测时，先报预估消耗（题目数 × 轮数 × 单次 token），超 5 万 token 预算等用户确认。

## 四层漏斗详解

| 层 | 定位 | 判定规则 |
|---|---|---|
| 一 · 基础工程 | **拦截级** | 出现任何 ❌ → 结论即「不通过」，后续层仅供参详（报告更完整，但按漏斗规则本应打回） |
| 二 · 指标性能 | 硬指标 | 触红线 → P0/P1 风险 + 优化方案 |
| 三 · AI 特有质量 | 灵魂 | 必须定量拒绝主观：分数对比红线 + 稳定性 + 最弱项点名 |
| 四 · 业务兜底 | 闭环 | 兜底链路必须**真实触发一次**验证，不看不测不算数 |

**结论映射不许自由发挥**：不通过 = 第一层任何 ❌ 或任何 P0；有条件通过 = 无 P0 但有 P1（必须列转「通过」的条件清单）；通过 = 无 P0 无 P1。另有一条关键的**数据不足封顶**——关键项「未测」太多（尤其第三层整体没跑）时，结论最高只能给「有条件通过」，并写明因什么未测而无法给通过结论。这条堵住了「没测完硬说通过」的后门。

**Phase 0 项目画像**决定所有「适用性」：先跑 `profile_project.py`（纯标准库，输出语言/框架/项目类型/工具链/红旗的 JSON 画像），再读项目根的 `ACCEPTANCE.md`——里面的红线值、评测集路径、豁免项**优先于 skill 默认值**（与三个验收模板的配载机制天然兼容）。三档验收级别（快检 15-40 分钟 / 标准默认 / 全量 2 小时+）按需选，用户没指定就直接按标准自主开跑，不反复问。

## 动态启发：固定清单之外的另一半

固定清单保证下限（不漏常规项），动态启发负责上限（挖清单上没写、这个项目特有的暗坑）。六步：画像打底 → 项目类型 playbook 匹配 → 九个风险维度逐维扫描（并发/状态/外部依赖/不可逆/资金隐私/长时任务/权限/时区编码/配置密钥）→ 攻击者视角（我要弄崩它、黑进它、骗过它，从哪下手）→ 上线前夜 pre-mortem → git diff 影响面聚焦。

核心思想是**每一步启发都要产出可执行的用例或检查点**，不允许停留在「感觉这里有风险」。第三层强制产出 3-5 个刁钻动态用例并真实执行（模糊输入、提示注入、超长上下文、边界值、恶意格式），「它扛住了」也是有效结论。

**实证门槛是动态层的反幻觉铁律**：启发产出先落为【假设 H-n】，假设不算发现——必须当场转化为最小探针跑出「证实/证伪」，证实才升级为【实证发现 D-n】参与结论映射与 P 分级。跑不动的假设进报告「假设区」（标补验方法，不给 P 级），证伪的进「排除区」防重猜。

## 新死法回流，双向闭环

验收中发现库里没有的新死法（尤其 Agent/LLM 域），过三道质量门（已实证/通用型/非重复）后按七字段格式回流失败模式库 `01-failure-modes`；通用工程坑沉淀踩坑日志；本机私有坑进记忆 PITFALL。配合生态互认（开工先拿失败模式库七类死法对号入座），形成「库→验收→库」的循环——验收官每次干活都在给知识库喂新料。

## 跟邻居们的边界

| skill | 分工 |
|---|---|
| 交付流水线 | 管过程（做到哪、怎么验收每张卡）；本 skill 管**放行**（整个项目能不能交）。流水线第⑬⑭步的产出正是本 skill 第一层的输入 |
| 测试纪律 / 抗幻觉纪律 | 证据形态与结论规范的执行细则，验收全程同源遵守 |
| 踩坑日志 / 缺陷诊断 | 逐个 bug 的根因诊断归它们；本 skill 只定位与分级，不深入修 |
| 失败模式与对策库 | 库→验收（对号入座）+ 验收→库（新死法回流），双向闭环 |
| 项目根 ACCEPTANCE.md | 用户红线/评测集/豁免项的存放地，优先级高于 skill 默认值；没有则验收官生成草稿 |

## 什么时候不用

日常开发中的单点修 bug、跑一次测试、写一段代码——那是过程纪律的活。只想看某一维（只查安全/只看性能），直接用对应 skill 或裁剪范围（裁剪必须写进报告元信息）。
