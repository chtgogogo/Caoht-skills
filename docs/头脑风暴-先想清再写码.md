# 头脑风暴（brainstorming v1.1.0）

> [← 返回总目录](../README.md#skills-index)

## 五分钟速览

如果只有五分钟，记住这六句。

1. 一次只问一个问题，每问必带推荐答案加理由加备选的代价。这是整个设计的灵魂。
2. HARD-GATE 硬闸，设计获批前不许写任何代码、不许搭项目骨架，项目再简单也一样。
3. 每个方案必须如实列出已知缺陷和翻车场景，只说优点等于卖文创收智商税。
4. 无情践行 YAGNI，第一版能砍的全砍。
5. 产出是一份落盘的设计纪要（规格），它是下游的原料，交付流水线的 PRD 直接从它生成。
6. 问题数量不写死，简单的想法两三轮收敛，复杂的多磨几轮，轮数跟想法复杂度走。

一句话概括设计目标，**动手之前，把你随口一句话磨成一份你亲自批准过的完整设计**。

## 它在解决什么问题

让 AI 做项目最大的成本，是它把你随口一句话当圣旨开写。你说了句帮我做个记账 App，它两小时后交付一个完整的记账 App。记什么账，它猜的。给谁用，它猜的。技术栈它挑了自己最熟的，而你其实想借这个项目学 Rust。猜错方向写两千行，比开工前问一句贵一百倍。

磨设计是必须的，但磨设计有两种常见的失败形态。一种是 AI 一个问题都不问，直接干。另一种反过来，一口气抛十个问题，目标用户、核心功能、平台、商业策略，你看着就想关窗口。

| 故障 | 表现 | 对应设计 |
|---|---|---|
| 不问就写 | 需求全靠猜，方向错了全盘返工 | 一次一问 + 每问带推荐 |
| 问题轰炸 | 十连问，用户想关窗口 | 一次一问，问题间有依赖链 |
| 零基础答不上 | 裸问「目标用户是谁」，你干瞪眼 | 每问带推荐答案与分析 |
| 只说优点 | 设计文档全是好话，坑留给写码阶段爆雷 | 强制列缺陷 |
| 聊着聊着跑偏 | 磨设计滑进实现细节 | HARD-GATE 硬闸 |

## 每问带推荐，是整个设计的灵魂

裸问是这样的，「目标用户是谁」。你答不上来，因为你自己也没想清楚，这正是需要磨的地方。AI 干等，你干瞪眼，一轮对话什么都没推进。

带推荐是这样问的，「我推荐先做给自己用，理由是记账需求自己最懂，能最快闭环验证。如果做家庭共享账本，复杂度翻三倍，第一版不划算。同意吗」。你点头，或者说要后者，就锁定了。

这个设计同时解决了两个人群的问题。不会表达需求的人，拿到了现成的判断，点头或摇头就能推进。会表达的人，省掉一轮来回。而且推荐必须带理由和备选的代价，AI 不能偷偷替你决定，你保有完整的知情权。用户选了非推荐项时，先确认是否理解了取舍再继续。

**一次一问**的道理在依赖链。问题之间有依赖，前面的答案决定后面问什么。一口气问十个问题，等于放弃了这个依赖链，也放弃了追问的机会。

## 强制列缺陷与 HARD-GATE

**强制列缺陷。** 设计文档常见的毛病是只写优点，坑全留给写码阶段爆雷。这里定稿前必须列出已知缺陷和取舍，你不接受某条，退回上一步换方案。丑话必须说在写码之前。

**HARD-GATE 防跑偏。** 磨设计聊着聊着容易滑进实现细节，这里设了硬闸，在呈现设计并获得批准之前，不得调用任何实现类 skill、不得写任何代码、不得搭项目骨架。还有一条反模式条款专门防「太简单了不需要设计」，每个项目都要走这个流程，待办清单、单函数工具、配置改动全都算。简单的项目恰恰是最容易被「想当然」坑掉的地方。设计可以很短，真简单的话几句话即可，但你必须呈现它并拿到批准。

## 流程与产出

九步检查清单按序走，探索项目上下文 → （适时才提）可视化伴侣 → 澄清问题 → 提 2-3 个方案带取舍 → 呈现设计 → 写设计文档到 `docs/specs/` → 规格自审（占位符/矛盾/歧义/范围四查）→ 用户审阅规格 → 转入实现规划。

磨需求的焦点是目的、约束、成功标准，还要问「明确不做什么」。这份设计纪要不是聊天的总结，是下游的原料。交付流水线的 PRD 直接从它生成，磨设计就是那条十四步流水线的第一步。提问技巧里融合了 mattpocock 的 grill-me（推荐答案、决策树），原文副本已随交付流水线落档。

有个贴心的可选件叫可视化伴侣。不主动提，等某个问题确实「用看的比用说的更清楚」（真实原型、布局、图表问题）时，单独发一条消息提议，用户拒绝就不再提。逐题判断走浏览器还是终端，需求问题和取舍清单用文字，原型和布局对比才开浏览器。

## v1.1 是怎么来的

来自一场真实的磨设计。用户提了个游戏想法，旧版裸问，用户只能一句句描述自己的想法，中途还推翻了原方案重来。升级后重跑同类对话，每问必附推荐加理由加备选的代价，用户三次点头一次改选，四轮收敛。定稿时列了三条已知缺陷，用户对其中一条当场说不能接受，回到上一步换了方案。

那条缺陷如果留到写码阶段才发现，代价是一周的返工。

## 什么时候不用

需求已经写成文档并且评审过了，直接进实现。改 bug、调参数，没有设计可磨。你明确说别问了直接做，它尊重，但会坚持至少列一次缺陷清单，这是底线。
