# 头脑风暴（brainstorm v1.1.0）

> [← 返回总目录](../README.md#skills-index)

你随口说了一句，帮我做个记账 App。

AI 当圣旨开写。两小时后给你一个完整的记账 App。记什么账，它猜的。给谁用，它猜的。数据存哪，要不要多端同步，全是它猜的。技术栈它挑了它最熟的，而你其实想借这个项目学 Rust。

猜错方向写两千行，比开工前问一句贵一百倍。

但反过来，另一个极端也折磨人。有的 AI 会一口气抛给你十个问题，目标用户是谁，核心功能是什么，平台是什么，商业策略是什么。你看着就想关窗口。

这个 skill 走中间那条路。一次只问一个问题，而且每个问题都带推荐答案。

## 它跟"让 AI 问清楚再做"的差别

裸问是这样的，目标用户是谁。你答不上来，因为你自己也没想清楚，这正是需要被磨的地方。

带推荐是这样问的。我推荐先做给自己用，理由是记账需求自己最懂，能最快闭环验证。如果做家庭共享账本，复杂度翻三倍，第一版不划算。同意吗。

你点头，或者说要后者，就锁定了。不会表达需求的人得到了现成的判断，会表达的人省了一轮对话。这个设计把盘问从审讯变成了选择题，是整个 skill 的灵魂。

其他几处差别。

一次一个问题和一口气十个问题的区别，在于问题之间有依赖，前面的答案决定后面问什么。

设计文档只写优点是常见病，这里强制列缺陷。定稿前必须列出已知缺陷和取舍，你不接受某条，就退回上一步换方案。丑话必须说在写码之前。

问题数量不写死。简单的想法两三轮收敛，复杂的想法多磨几轮，轮数跟想法复杂度走。

## 流程

磨需求。一次一问，逐层收敛。做什么，给谁用，核心闭环是什么，明确不做什么。第一版能砍的全砍，这条是 YAGNI 红线。

磨方案。核心机制怎么实现。这里有个 HARD-GATE，聊着聊着开始讨论具体实现细节时拉回设计层，实现是下一步的事。

列缺陷。定稿前强制过一遍。

出设计纪要。落盘一份文档。它不是聊天的总结，是下游的原料，交付流水线的 PRD 直接从它生成。

提问技巧里融合了 mattpocock 的 grill-me，推荐答案、决策树这些绝活。原文副本已经随交付流水线落档，不存在原 skill 丢了这套就废的问题。

## v1.1 是怎么来的

这次升级来自一场真实的磨设计。用户提了个游戏想法，旧版裸问，用户只能一句句描述自己的想法，中途还推翻了原方案重来。升级后变成每问必附推荐加理由加备选的代价。重跑同类对话，用户三次点头一次改选，四轮收敛。方案定稿时列了三条已知缺陷，用户对其中一条当场说不能接受，回到上一步换了方案。

那条缺陷如果留到写码阶段才发现，代价是一周的返工。

## 什么时候不用

需求已经写成文档并且评审过了，直接进实现。改 bug、调参数，没有设计可磨。你明确说别问了直接做，它尊重，但会坚持至少列一次缺陷清单，这是底线。
