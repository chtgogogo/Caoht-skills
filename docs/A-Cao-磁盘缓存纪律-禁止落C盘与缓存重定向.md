## 第 0 章 五分钟速览

1. **它管一件极窄但极贵的事**：东西写到哪个盘（磁盘分区）上。代码怎么写、测试怎么算、结论怎么下，分别归另外三支纪律管，四件互不重叠（`SKILL.md` 第七节「与其它三件纪律的边界」）。
2. **动手前先定落盘位置**，不是装完了再后悔。原文的原则句很硬：先问"这个工具默认写哪"，而不是事后发现系统盘少了 20G（`SKILL.md` 第一节末句）。
3. **缓存重定向（把工具默认写入位置改到别处）靠环境变量**，而且是"用这个工具之前"就设好。模型权重（训练好的模型参数大文件）类工具一旦先下载后设变量，几十 GB 已经砸在系统盘上了。
4. **老旧程序强制写系统盘时，用目录联接把它"拐走"**：程序以为自己还在读写原位，实际数据落在数据盘（`SKILL.md` 第二节，Windows 自带命令 `mklink /J`）。
5. **迁移前必须先做幂等检测（重复做结果不变，所以先查"是不是已经做过了"）**，这是原文用 ⚠️ 标出的"最容易出错的一步"：已经是正确链接还再挪一次，会把已经在别处的数据再复制一份甚至套嵌成环（`SKILL.md` 第三节）。
6. **它自带一个真能跑的体检脚本**（只检查、不改东西的脚本）`disk_check.py`，查四件事：环境变量是否已重定向、系统盘用户目录里是否藏着 ≥1GB 的可疑缓存、已知缓存位置是否已被正确拐走、各盘剩余空间是否低于阈值。红黄绿三档结论，退出码 0/1/2 给外面的定时任务（哨兵＝定时替你检查的脚本）消费。
7. **2026-10-06 它长出第二种能力**：从"预防端"（别往系统盘写）扩到"治理端"（系统盘已经胖了怎么瘦）。核心心法八个字：**先量后删、钻层定性**——一层层钻到能判断"这是删了会重长的缓存，还是删了回不来的用户数据"那一层，才允许动手（`SKILL.md` 第八节）。

一句话设计目标：**让任何一次落盘都不落在系统盘上；万一已经落了，用一套不会误删用户数据的流程把它搬走并证明搬干净了。**

## 第 1 章 这套系统在解决什么问题

先说清楚"这不痛"的错觉：系统盘被塞满，不会弹一个框告诉你"是某个模型权重干的"。它的表现是别的东西开始坏——更新装不上、软件启动变慢、休眠恢复失败、临时目录写不进东西。而排查的人往往去查病毒、查软件坏了，绕一大圈才看见磁盘满了。

| 故障 | 具体表现 | 本 skill 的解法 |
|---|---|---|
| **① 工具默认路径吞掉系统盘** | 装个 Python 依赖包、拉一次模型，系统盘悄无声息少 10–30GB；用户只看到"磁盘可用空间"红了 | 前置判定 + 环境变量重定向（`SKILL.md` 第 0 节、第一节；脚本第 1 项查这六个变量） |
| **② 老旧程序只认固定原位，不给选项** | 某些安装程序硬编码往系统盘用户目录写，界面上根本没有"选位置"这一步 | 目录联接转移术：挪数据 → 删空原位 → `mklink /J` 指过去（第二节；脚本第 3 项验指向） |
| **③ 同一批数据被反复挪、越挪越多** | 好心的人（或 AI）第二次执行迁移，把已经拐走的目录又复制一份，出现"缓存里嵌缓存"、体积翻倍、程序读写报错 | 幂等检测三态判定表，第三节被 ⚠️ 单独标出来；判据是先查"当前是不是已经是链接且指向正确"，是就**立即停止** |
| **④ 清理时误删用户数据** | 名字像缓存的目录其实装着真东西：聊天数据库、浏览器登录态、AI 代码索引。删掉之后不是"重新生成"，是永久丢失 | 构成定性判据表（看目录里是什么，不看目录叫什么）+ 处置三分类里 C 类「拍板交用户」+ 报告必含**勿动清单**（第八节） |
| **⑤ 只看一层就下结论，删错了/没删对** | 扫到某聊天软件目录 1.5GB 就说是缓存；真钻下去才发现里面 1.1GB 是网页内核的缓存副本，另 0.4GB 是账号数据 | 三层钻取漏斗 L1 广度 → L2 定位 → L3 定性，明确"禁止只扫一层就下结论"，并留了一条实录反例（第八节 1、2 小节） |
| **⑥ 大规模写入前不看余量** | 几十 GB 数据集写到一半失败，剩下半截临时文件，两处（目标盘＋系统盘）一起脏 | 写入前用 PowerShell 一条命令列各盘剩余空间；目标盘不足则**立即停、报告用户**，禁止未确认的跨盘写入（第五节） |
| **⑦ 规则存在但 AI 想不起来用** | 这条纪律原本只是一份上游规则文件里的文字，不在技能库内，AI 不会自动触发；"幂等检测"全靠人记 | 封装成带触发描述的 skill ＋ 把"承诺有但其实不存在"的体检脚本真的补上，让判据可执行（`SKILL.md` 版本节 v1.0 条目、变更日志 v1.0 条目） |

**⑦ 是这支 skill 存在形态本身要解决的故障**，也是它和另外三支纪律最大的不同点：它不只是"讲道理"，它带了一把尺子（脚本）。原文在 v1.0 条目里写得很直白——上游文件**承诺有 `disk_check.py` 但文件并不存在**，所以封装时"并补上"（`SKILL.md` 版本节）。`[实测]` 该论断来自 `SKILL.md` 版本节 v1.0 条与变更日志 v1.0 条的同一句表述。

## 第 2 章 术语表

| 术语 | 一句大白话 |
|---|---|
| **系统盘 / 非系统盘** | Windows 装在哪一号盘就是系统盘（俗称 C 盘）；其余分区统称非系统盘／数据盘，是本 skill 里所有落盘的目标位置 |
| **落盘** | 数据真的写到硬盘上（区别于只在内存里过一下） |
| **缓存** | 程序算过／下过之后存的一份副本，下次图快不用再折腾一次 |
| **再生型缓存** | 删了以后程序自己会重新长出来的那类文件（网页缓存、GPU 缓存等），删它的代价是"下次慢一点" |
| **用户数据** | 删了就回不来的东西：登录态、聊天库、自建索引、下载历史 |
| **重定向** | 把工具的默认写入位置改到别处，一般靠设环境变量（操作系统层面告诉程序"该往哪写"的开关） |
| **环境变量** | 系统或用户存的一张"名字＝值"的配置表，程序启动时来查；本项目里查的是六个缓存位置开关 |
| **模型权重** | 训练好的神经网络参数文件，动辄几 GB 到几十 GB，是吞盘头号大户 |
| **虚拟环境** | 给某个项目单独圈出来的一套 Python 依赖，不和别的项目混着用；它的文件夹位置也归本 skill 管 |
| **目录联接（Junction）** | Windows 的一种"这个文件夹其实是别处的入口"机制，程序进这个门实际到了另一个盘；老程序兼容性比符号链接好，所以原文优先用它 |
| **符号链接（Symlink）** | 同类的"指向别处"机制，`mklink /D` 建；对某些旧程序和某些读路径的代码不如联接稳 |
| **重解析点（Reparse Point）** | 文件系统里给"我自己不放数据、只放一条指向"这种目录记的账；`fsutil reparsepoint query` 就是去翻这笔账，精确判断某路径是不是链接 |
| **幂等** | 同一件事做一次和做两次，最终结果一样；所以动手前先查"是不是已经做过了" |
| **体检（脚本）** | 只读、只报告、不改你任何文件的检查程序；本支的 `disk_check.py` 全部动作只有"数文件大小、读环境变量、读链接指向" |
| **哨兵** | 定时替你跑体检的机制（比如挂到系统计划任务上），本身不动东西，只负责"到点看一眼并记录" |
| **判据** | 可以照着执行的判定标准，含具体数值和具体比较方向；"别占太多"不是判据，"剩余低于 15GB 判红"才是 |
| **阈值** | 判红的那条线；脚本里默认是系统盘剩余 15GB，可用 `--threshold` 改 |
| **钻层定性** | 一层层往目录深处看，直到能说出"这一层里装的是缓存还是数据"为止 |
| **建道** | 本支处置三分类里的 B 类处置：不停在"删一次"，而是给持续再生的大缓存修一条永久通道（junction）搬到数据盘 |
| **勿动清单** | 清理报告里必须列出的一栏：这次判断"不能删"的目录及理由，专门给下次（或别人）防误伤用 |
| **落点族** | 同一类软件的缓存集中出现在哪几种目录形态（如用网页技术打包的桌面软件、用 Chromium 内核的应用）；认族比记具体路径管用 |
| **处置三分类 A/B/C** | A＝直接清（再生缓存与垃圾）；B＝建道（持续再生的大块头）；C＝拍板（用户数据、系统件、拿不准的，列清单交用户，不许擅自删） |
| **退出码** | 脚本跑完留给系统的一个数字，外面的人（或定时任务）靠它判断结果；本脚本 0＝全绿、1＝有 FAIL、2＝有 WARN |
| **注册表 hive（分区）** | Windows 存配置的那本大账本被分成几块：当前用户那一块、本机全局那一块；环境变量可能只写在里面，进程环境里查不到 |
| **再生产**（与"再生型缓存"区分） | 指清理完之后程序又把它写回来了，所以只做一次删除等于没做——这就是 B 类"建道"存在的理由 |
| **WebView2 / 内核复用** | 系统提供的一块可被很多软件共用的浏览器渲染组件；进程列表里出现它，**不代表**浏览器正在运行 |
| **UNC 路径** | 以两个反斜杠开头的网络共享地址；脚本的盘符判断对这种写法不具备识别能力（见第 10 章） |

> 计数说明（本页自己数的数字都按此数法）：环境变量开关 **6 个**（按脚本 `ENV_TARGETS` 字典的键数）；可疑相对路径 **9 条**（按脚本 `USER_SUSPECTS` 列表元素）；联接扫描关键字 **14 个**（按脚本 `scan_junctions` 内元组元素）；定性判据表 **5 行**（按 `SKILL.md` 第八节第 2 小节表行）；处置分类 **3 类**；落点族 **6 项**（按第八节第 6 小节分号切分）。

## 第 3 章 结构与分层：四类规则 + 一条判定顺序

### 3.1 全支结构总表

`SKILL.md` 正文只有 149 行，但里面其实叠了四种性质不同的东西。分清这四种，才知道哪句能改、哪句不能改。

| 层 | 对应章节 | 职能 | 为什么单独一层 |
|---|---|---|---|
| **L0 触发与核心层** | frontmatter 的 `description` 字段、第 0 节「核心（每轮必守）」 | 让 AI 在正确的时机想起这条纪律，并保证每轮对话至少守住两条硬规则 | 规则写得再全，想不起来用＝零。`description` 里逐个列举触发场景（下载／克隆／建虚拟环境／拉模型权重／装依赖／写缓存／解压安装包／落盘大文件），就是把"想起用"这件事交给检索而不是交给自觉 |
| **L1 预防层** | 第一节（缓存与环境重定向）、第四节（临时文件即时清理）、第五节（空间预警） | 让数据**一开始就不进系统盘** | 预防的成本是"提前设一个变量"，治理的成本是"钻三层＋搬几十 GB＋怕删错"，差着一个数量级 |
| **L2 治理层** | 第二节（目录联接转移术）、第三节（幂等检测）、第八节（C 盘体检瘦身标准流程） | 已经落在系统盘上的，怎么安全搬走、怎么安全瘦身 | 治理动作会碰真实文件，必须自带刹车（幂等检测、占用核查、C 类拍板），否则它是二次事故源 |
| **L3 工具与验证层** | 第六节（体检脚本）＋ `scripts/disk_check.py` | 把上面所有判据变成一条命令能给出的红／黄／绿 | 人（和 AI）会记错判据；可执行脚本不会。v1.0 的封装动机正是"原来只有文字，全靠人记" |

`[实测]` 该分层是本页对 `SKILL.md` 章节职能的归并（章节名逐条对上）；层级名 L0–L3 为本页起的代号，原文没有这套编号。**原文里并不存在"层"这个概念**，它只有八节平铺的规则——这点要在第 15 章「未采纳项」里诚实记着：分层的坏处是让人以为可以只读某一层。

### 3.2 判定顺序：一次要写文件时的执行流

规则平铺着读容易，执行时必须串成一条顺序。**依次问，第一个命中的就按它做**：

```
1. 这次操作会不会产生文件？            不会 → 本支不适用（frontmatter 明确排除"纯文本推理、不碰文件系统的任务"）
2. 会产生 ≥1GB 级的东西吗？            会 → 先做第五节的空间预警（查各盘余量），再往下
3. 这个工具的默认写入位置在哪？能改吗？ 能改 → 第一节：用前设环境变量，指到数据盘
4. 不能改（老程序硬编码系统盘）？        第二节：转移术四步（停进程 → 挪数据 → 删空原位 → mklink /J）
5. 执行第 4 步之前                     第三节：幂等检测三态判定；已正确 → 立即停止，绝不重复移动
6. 清理/瘦身场景                       第八节漏斗：L1 广度 → L2 定位 → L3 定性 → 处置三分类 → 验证收尾（含勿动清单）
7. 任何时刻想确认全局状态               第六节：跑体检脚本，看退出码
```

> **为什么这个顺序不能换**：第 5 步必须夹在第 4 步前面而不是后面——链接建好之后再发现"原来早就建过了"，数据已经被复制了两份，回滚比前进更麻烦。`[推演]` 反例：直接对已是联接的路径执行"移动＋建链"，`mklink /J` 会在联接指向的真实目录**内部**再建一个同名联接，形成 `<数据盘>\AI_Cache\hf\hf` 这种套嵌；之后工具按缓存变量写文件，写进内层联接，外层目录体积统计看起来"没变"，实际多副本已经产生。判据：`dir` 输出里目标位置出现 `<JUNCTION>` 标记，就该停在这一步。

### 3.3 与另外三支纪律的边界

`SKILL.md` 第七节给了一张四行归属表，本页照录并解释为什么这么切：

| 管什么 | 归属 | 为什么不会撞车 |
|---|---|---|
| 东西写哪个盘、缓存怎么重定向 | **本 skill** | 它只碰"路径与位置"这一个维度，不评价代码质量、不评价证据质量 |
| 代码怎么写 | `A-Cao-编码行为准则-写码改bug审查重构` | 编码纪律管修改范围与验证，不会去管依赖缓存落在哪 |
| 测试证据长什么样 | `A-Cao-测试纪律-测试证据形态规范` | 它管原始输出落盘与改前改后对照；本 skill 反过来给它一个约束：证据文件也别落系统盘 |
| 结论怎么下 | `A-Cao-抗幻觉纪律-结论必须可证伪` | "C 盘应该没事了"这句话是不是可证伪，归抗幻觉；"用哪条命令证明它没事"，本支第 9、11 章给了 |

**与共享行为准则的分工**（`SKILL.md` 第七节末句）：共享准则文件第 8 节只放**一句话核心**（每轮必读、必须短），本文件放**完整命令与步骤**（按需加载）。这就是为什么正文里同一件事会有"一句版"和"整节版"两处——不是重复，是渐进披露（索引常驻、细节按需读，省上下文）。

## 第 4 章 机制一 · 落盘前置判定与统一目录约定（第 0 节）

### 4.1 第 0 节只有两条，但它是"每轮必守"

原文第 0 节标题写着「核心（每轮必守）」，只有两件事：

1. **所有下载／克隆／虚拟环境／模型权重／日志／解压产物，默认写非系统盘**；严禁系统盘用户目录下的 `Downloads`（浏览器默认下载位置）、`.cache`（各家工具的缓存总入口）这类默认路径。`[实测]` 见 `SKILL.md` 第 0 节第 1 条。
2. **在非系统盘建统一目录**：工程类放 `<数据盘>\AI_Projects`，缓存类放 `<数据盘>\AI_Cache`。`[实测]` 见 `SKILL.md` 第 0 节第 2 条，原文自己标注这是"本机约定"。

### 4.2 为什么是这两个目录名，而不是一个

| 目录 | 装什么 | 为什么单独分 |
|---|---|---|
| `<数据盘>\AI_Cache` | 会被工具自动写、能再生、能整片搬走的东西：pip 缓存（Python 装包时留的包副本）、模型权重、npm 缓存（前端包管理器的副本）、虚拟环境默认根 | 它的生命周期由**工具**决定，不由你决定：你不清它就一直长。所以要一个"专门给它"的位置，方便一次性重定向、一次性体检、一次性算体积 |
| `<数据盘>\AI_Projects` | 克隆的仓库、建好的工程、解压出来要留着的东西 | 它的生命周期由**你**决定，删了就真没了。混在缓存目录里，等于把自己的代码放进"迟早要清一片"的篮子 |

> `为什么这么分` 这条是 `[推演]`：原文只给了两个目录名，没写分栏理由。**具体什么输入会让它出问题**：若只有 `AI_Cache` 一个目录，把克隆的仓库也放进去，那么下次按第八节处置 A 类清"能再生"的大块头时，一句"缓存目录里的老东西删了吧"就会连带删掉真实仓库——分目录就是把误删半径预先切开的最小代价做法。

### 4.3 "≥1GB" 这条线为什么是 1GB

`description` 字段里把"操作会产生 ≥1GB 文件"列为**强制自查**的触发条件；脚本里对应两条线是 1024MB（可疑目录膨胀判定）与 50MB（实体目录未拐走判定）。三条数的分工：

| 数 | 出现在 | 含义 | 换一换会怎样 |
|---|---|---|---|
| **1GB** | `description` 触发线、脚本第 2 项 `size >= 1024` MB | "这件事值得你在动手前专门停下来定位置" | `[推演]` 调到 10GB：一次 `npm install` 加一个中型模型（约 4–7GB）就不触发自查，攒三次才红，而单次写入足以让系统盘跌破 15GB 阈值。调到 100MB：每次装个包都触发一轮全盘扫描，人开始屏蔽提示，判据失去执行力 |
| **1024 MB**（同 1GB，脚本用 MB 表达） | `check_user_dirs` | 系统盘用户目录里"单个可疑项"的膨胀报警线 | 与触发线保持一致是有意的：**同一个数字在两处能对上**（勾稽＝两处数字能对上、互相印证），这样"AI 该自查的时机"和"脚本会报红的时机"是同一个时机 |
| **50 MB** | `scan_junctions` | 实体缓存目录"还没拐走"的报告线，比 1GB 低 20 倍 | 因为拐走的动作成本极低（挪一次＋建一条链接），所以这里宁可早报、多报。`[推演]` 若也设 1024MB，一个 300MB 的 `AppData\Local\pip` 实体目录会永远隐身，而它会随每次装包继续涨，最终变成第 8 章那种要钻三层才能处理的大块头 |

> 数值复算说明：`1024` 与 `50` 来自脚本源码 `disk_check.py` 的 `check_user_dirs`、`scan_junctions` 两处比较式（按 `# ≥1GB 才算"异常膨胀"`、`# 实体且 ≥50MB 才值得报` 两行注释可对照），`1GB / 15GB / ≥1GB 触发` 来自 `SKILL.md` frontmatter 与第四、五节文本。`[实测]`

### 4.4 统一约定的隐性收益：让"检查"变成一句话

一旦缓存只可能出现在两个目录下，"我机器上有没有东西乱写"这个问题就从"全盘扫描"降级成"查六个变量指哪 ＋ 查两个根目录的一层子项"——这正是脚本第 1、3 项能跑得这么快的前提。`[推演]`（脚本本身注释了"深度受限，避免全盘慢扫"，说明慢扫是它刻意回避的方案；反例输入：把缓存放在十个互不相干的位置，脚本的两根扫描会大面积漏报，而漏报会给出"第 3 项：未发现候选缓存目录"这种看起来像绿的输出——见第 10 章 10.1 第 5 条）。

## 第 5 章 机制二 · 缓存与环境变量重定向（第一节）

### 5.1 六个开关逐个讲

`SKILL.md` 第一节给了一张三行表（pip／npm-pnpm／HuggingFace ＋ 一行"其它"），脚本的 `ENV_TARGETS` 把它扩成 6 项。**表里没写全、脚本里写了**，这是本页要摊开的一处口径不一致（详见第 15 章）：

| 环境变量 | 管谁 | 不设的后果 | 出处 |
|---|---|---|---|
| `PIP_CACHE_DIR` | Python 包管理器 pip 的下载包副本 | 每个包装完都留一份 wheel 副本，几百 MB 起步；系统盘用户目录下的 `AppData\Local\pip\Cache` 会长到 GB 级 | 表格＋脚本，`[实测]` |
| `npm_config_cache` | 前端包管理器 npm 的缓存 | 项目一多，`AppData\Local\npm-cache` 轻松上 G | 表格＋脚本，`[实测]` |
| `PNPM_HOME` | pnpm（npm 的一个替代管理器）的全局 store 位置 | store 是所有项目共享的包仓库，一旦落在系统盘，它只增不减 | 表格＋脚本，`[实测]` |
| `HF_HOME` | HuggingFace 生态（模型权重与数据集的下载入口）的总缓存根 | **原文用粗体强调：下载模型前先设，否则权重直落系统盘**。单个模型 1–30GB，这是单次数额最大的故障 | 表格＋脚本＋README 收录行，`[实测]` |
| `TORCH_HOME` | PyTorch 预训练权重与Hub 缓存 | 很多"跑个 demo"的仓库会顺手拉几百 MB 到几 GB 的 backbone 权重，用户不知道 | 仅脚本 `ENV_TARGETS`，正文表格未列，`[实测]`（依据脚本源码） |
| `XDG_CACHE_HOME` | 类 Unix 通用缓存规范（XDG 定义的"缓存该放哪"的标准位置）在 Windows 上被某些工具读取的开关 | 一批遵循 XDG 的命令行工具默认往系统盘用户目录的 `.cache` 写 | 仅脚本 `ENV_TARGETS`，正文表格未列，`[实测]` |

正文表格还给了 pip 的一条替代写法：`pip install --cache-dir <数据盘>\...`，即**不改全局、只改这一次**。`[实测]` 见第一节表格 pip 行「说明」列。

### 5.2 为什么"设变量"要发生在"用工具之前"

重定向不是搬家：变量只影响**此后新写入**的位置，不会自动把已存在的缓存挪走。于是有两个时刻，成本差很多：

- **用之前设**：零风险，新文件直接进数据盘。
- **用完再设**：老数据还压在系统盘上，你必须再走第六节的转移术（挪＋删空＋建链）；而且这时系统盘已经被占过了——最坏情况是那次大下载本身就把盘写满、下载失败，你连"挪走"的机会都没有。

`[实测]` 原文对 HF 的措辞正是「**下载模型前**先设」，就是在把这条时间约束钉在最危险的场景上。

### 5.3 变量的"三级读取"：为什么脚本不能只看进程环境

脚本的 `env_get` 函数按三级找：① 当前进程的环境 → ② 注册表里**当前用户**那一块的 `Environment` → ③ 注册表里**本机全局**那一块的会话管理器环境段。函数 docstring（函数第一段说明文字）原话：「只读进程级会误报"未设置"」。`[实测]`

| 你在哪设的 | 进程环境能看到吗 | 新开的终端能看到吗 | 脚本三级读取的结果 |
|---|---|---|---|
| 临时 `set`／`$env:` | 能（仅那个进程树） | **不能** | 在**那个终端里**跑才绿；换个终端跑变黄 |
| 图形界面里写进"用户环境变量" | 当前已运行的进程不能 | 能（重新登录／新开进程才继承） | 进程级查不到 → 靠第②级查到，正确报绿 |
| 写进"系统环境变量" | 同上 | 能 | 靠第③级查到 |

> 为什么这条值得单开一节：`[推演]` 如果脚本只读进程环境（很多同类脚本就是这么写的），你在图形界面设好了 `HF_HOME`，然后在**AI 助手的既有终端**里跑体检，它会报"未设置"→ 黄。你被自己的判据骗了一次，最坏后果是又设一遍、或以为自己没设成而去做多余的迁移。三级读取就是把这个假黄消掉。

### 5.4 脚本第 1 项的三态：为什么"未设置"只是黄

`check_env` 对六个变量分三堆：`moved`（已指向非系统盘）／`bad`（值里含系统盘盘符）／`missing`（查不到）。分配规则：

- `bad` 非空 → **FAIL（红）**。这是明确违规：缓存正躺在系统盘上。
- `missing` 非空 → **WARN（黄）**，并附一句「未用到的工具可忽略」。
- `moved` 非空**且** `bad` 为空 → **OK（绿）**。

`[实测]` 以上分支顺序取自 `check_env` 函数体的三次 `if`；请注意第三个条件是 `moved and not bad`——也就是说**只要有任何一项红，第 1 项就不会同时给你一条绿**，避免"3 项已好／1 项违规"被读成"总体不错"。这是一处刻意的判据设计。

为什么 `missing` 只黄不红：六个变量对应六个工具，一台只做前端的项目机器可能永远装不了 PyTorch。**把"没装"报成违规，判据就失去了区分力**（恒红＝怎么改都红，人就不看了）。`[推演]` 具体反例输入：新机器一个变量都没设、也确实一个 Python 工具都没装，若 missing 判红，体检开局就是红，而机器实际上毫无风险；用户会立刻得出"这脚本在瞎报"的结论，从此不跑它。

## 第 6 章 机制三 · 目录联接转移术与幂等检测（第二、三节）

### 6.1 转移术四步，顺序是硬的

遇到**强制写系统盘固定路径**的老旧程序（界面上不给你选安装位置、代码里路径写死）：

```
1. 停掉占用进程            ← 不停就挪：文件被锁，挪一半失败，原位还剩一半
2. 把已生成数据移到数据盘   ← 先复制后确认，别直接 cut
3. 删除系统盘原目录（**必须已空**） ← 非空删不掉，也不是链接该有的样子
4. 管理员权限执行 mklink /J "<系统盘>\原路径" "<数据盘>\实际路径"
```

`[实测]` 四步与「必须已空」的强调均见 `SKILL.md` 第二节步骤 1–4；`mklink` 需管理员权限是该命令的 Windows 系统行为（本支文本隐含"管理员执行"四字）。

**效果句**原文写得很妙：「程序以为还在读写 C 盘，实际数据已落非系统盘。」`[实测]` 第二节末。

### 6.2 `/J` 与 `/D`：为什么优先前者

| 写法 | 建出什么 | 大白话 | 原文取向 |
|---|---|---|---|
| `mklink /J` | 目录联接（junction） | 文件系统级"入口"，老程序普遍认它，且不需要本机开启开发者模式 | **优先用 /J**，原文注「兼容性更好」 |
| `mklink /D` | 符号链接（symlink） | 更"正统"的指向，但一些老程序、一些库的路径解析函数会拒绝它，或者解析出的字符串形式不一样 | 只作说明，不推荐 |

> 术语：**reparse point（重解析点）**＝文件系统给这类"我里面不放数据、只放一条指向"的目录记的那笔账。联接与符号链接都是重解析点，只是记账里标的类型不同——这也是第 7 章检测为什么能用一条命令统一识别的原因。`[实测]` 见第三节 `fsutil reparsepoint query` 一句。

### 6.3 幂等检测：三态判定表（⚠️ 全支最重的一小节）

原文把这一节标成「最容易出错的一步」，因为它防的不是外人，是**第二次热心的自己（或第二次执行的 AI）**。

先查，两条命令（`SKILL.md` 第三节代码块）：

```powershell
dir <目标路径>                      # 看输出里有没有 <JUNCTION> / <SYMLINK> 标记
fsutil reparsepoint query <路径>    # 精确查询是否为重解析点：不是会直接报错，是则打印指向信息
```

判定与动作（原文三行表，本页逐行加"为什么"）：

| 当前状态 | 规定动作 | 为什么必须这样 |
|---|---|---|
| **已是链接且指向正确的非系统盘** | **立即停止，绝不重复移动／建链接** | 已经达成目标；再动一次只制造副本或套嵌链接（见 3.2 的推演反例） |
| **是实体目录且占空间** | 才执行「移动 + 建链」 | 只有这一格是"前进"，其余格都是"停"或"退" |
| **是链接但指向错误位置** | 先 `rmdir` 删链接（**不是 `rmdir /s`**），再重建 | `rmdir` 不带 `/s` 时只拆"入口"，不进去删里面的真实数据；带 `/s` 会递归，递归进联接就可能把数据盘那侧的真目录一起删掉 |

> `[实测]` 三条状态与动作逐字对应 `SKILL.md` 第三节表；「不是 `rmdir /s`」是原文加粗强调。
> **为什么单拎 `rmdir /s`**：这是本节唯一一条"做错了会永久损失"的动作。联接删错了可以重建，目标目录里的数据删错了不可逆。

### 6.4 幂等检测在脚本里的影子

脚本的 `scan_junctions` 把"检测"做成了批量版：对每个候选目录判三种情形，输出三条不同结论（绿＝已正确拐走、黄＝链接仍指向系统盘、黄＝实体目录且 ≥50MB 未拐走）。它就是 6.3 三态表的机器版。逐行拆解见第 9 章 9.6；**两者判据顺序不同**这点也在那里说（原文的表把"指向错误"列在第三行，脚本对"链接指系统盘"与"实体未拐走"都归黄但文案不同）。

## 第 7 章 机制四 · 临时文件即时清理与空间预警（第四、五节）

### 7.1 第四节只有两句话，管的是一类容易被忽略的脏

- 任务产生的临时解压、中间产物，**完成后主动清理**。
- 解压安装包后无需保留立即删；不在桌面遗留大文件。

`[实测]` 见 `SKILL.md` 第四节。为什么它单独一节而不是并入"缓存"：缓存是**工具**写的、会自己回来；临时产物是**这次任务**写的、任务结束就没人管了，属于"没人负责"的那一类，最容易在桌面、下载目录里堆成几 GB 的孤儿。`[推演]`（原文未写理由；具体反例：一次"解压安装包看看里面有什么"留下 3GB 解压目录在桌面，一周后另一轮清理时因为不知道是不是"还有用"而不敢删，最后靠钻层定性才判掉——这就是本节要求"完成后立刻删"的价值。）

与第八节的接口：临时产物在处置分类里属于 A 类（直接清），因为它不是任何程序在维护的状态。

### 7.2 第五节：写入前的余量判据

原文给了一条可直接照抄的 PowerShell 命令，输出每个文件系统盘的 Name／FreeGB／UsedGB（保留 1 位小数）：

```powershell
Get-PSDrive -PSProvider FileSystem | Select-Object Name,@{n='FreeGB';e={[math]::Round($_.Free/1GB,1)}},@{n='UsedGB';e={[math]::Round($_.Used/1GB,1)}}
```

配套动作只有两条，但都很硬：

1. **目标盘不足 → 立即停、报告用户**。`[实测]` 第五节第 2 条。
2. **禁止未确认的跨盘写入**：不许"目标盘不够那我先写到别的盘"这种自作主张。`[实测]` 同上。

> **为什么把"跨盘"也禁**：跨盘写入会让一次任务的产物分散到两个位置，事后清理要重建一遍"这次都写了什么"的知识——而那次任务的知识正是本支最贵也最容易丢的东西。禁掉它，等于强制把落盘位置保持在**动手前**就谈定的那一个。

**脚本第 4 项是这条判据的可执行版**：默认阈值 15GB，只对系统盘判红；其余盘位只列出体积、不参与判红。这条不对称是有意还是遗漏，第 9 章 9.7 与第 15 章「未采纳项」各说一次。

### 7.3 阈值 15GB 为什么是 15

`[推演]`（脚本常量 `WARN_FREE_GB = 15.0`，`[实测]` 存在；**取这个数的理由原文与脚本都没写**，下面是本页给的解释与两个反向例子）：

- 系统盘上有一批"不是你申请、但一定会来吃"的固定开销：Windows 功能更新（临时需要数倍于自身体积的空间）、休眠文件（把内存内容写盘的巨型文件，按内存大小成比例）、虚拟内存分页文件、崩溃转储。留 15GB 大致够一次中等更新 ＋ 一次崩溃转储同时发生而不失败。
- **调小到 2GB 会怎样**：体检在系统盘只剩 3GB 时仍然绿，此时一次 8GB 的模型下载直接把盘写到 0，更新与程序同时报错，而且失败点在最不该失败的位置（系统盘）。
- **调大到 60GB 会怎样**：在一台只有 40GB 余量的机器上开局就红，且无论你怎么清都消不掉这个红——恒红的判据等同于没有判据，人会开始无视所有红。

> 这条与第 4 章 4.3 的 1GB 是**两个不同层次的线**：1GB 管"这次动作要不要先定位置"，15GB 管"这台机器现在安不安全"。别把它们合成一条，也不要在文档里互相引用。

## 第 8 章 机制五 · C 盘体检瘦身标准流程（第八节，2026-10-06 实战沉淀）

这一节是 v1.1 增补的内容，也是全支篇幅最长、密度最高的一节。它的定位句写在开头：**触发＝用户说「C盘满了／瘦身／体检／清理」**；心法＝**先量后删、钻层定性**；并且提前给自己打了补丁——「**落点会随软件更新漂移，判据不变——吸纳思路，不背路径**」。`[实测]` 逐字见第八节引言。

### 8.1 三层钻取漏斗

| 层 | 干什么 | 命令形状 | 停止条件 |
|---|---|---|---|
| **L1 广度** | 四大主战场各扫一轮，只看一层、按体积倒序取前 20 | `du -sh <根>/* \| sort -rh \| head -20`（du＝量目录体积，df＝看盘余量，Git Bash 里可用） | 拿到"谁大"的候选名单 |
| **L2 定位** | 对可疑大目录**钻一层** | 同上，根换成那个目录 | 拿到"大头在这个子目录里"的指认 |
| **L3 定性** | 继续钻，**直到能判断是缓存还是数据那一层为止** | 逐层看目录名构成 | 说出"这一块是删了会重长的缓存"或"这一块是用户数据" |

四大主战场（原文括号列举，均为系统盘用户目录与公共程序数据区之内的位置）：用户根目录、`AppData\Local`（本机生成的缓存与临时区）、`AppData\Roaming`（跟随用户漫游的应用数据，**很多真数据在这**）、`ProgramData`（所有用户共享的程序数据）。`[实测]` 见第八节第 1 小节 L1 行。

**原文自带的实例**（这是本支最好的教学材料，因为它给的是"钻到第几层才实锤"）：某聊天办公软件目录 1.5G → 钻到 `aha/users` → 再钻到 `profile_explorer` → 再钻到 Service Worker 才看到 1.1G，**这才实锤是缓存**。`[实测]` 见 L3 行括号内实例（原文把软件名写在路径里，本页按隐私红线抽象为"某聊天办公软件"）。

> 为什么"禁止只扫一层就下结论"要写进规则：`[推演]` 反例输入——只看 L1，"某聊天办公软件 1.5G"这一行会同时包含缓存（1.1G，可删）与账号数据（0.4G，禁删）。一层判断只有"大小"这一个信息量，而处置需要的是"可再生性"这个信息量；两者之间差着两层目录。

### 8.2 定性判据表：看构成，不看名字

原文第 2 小节是一张五行表，本页照录并逐行翻译成人话：

| 构成特征（目录里长什么样） | 定性 | 处置 | 大白话 |
|---|---|---|---|
| `Cache` / `Code Cache` / `GPUCache` / `Service Worker` / `Dawn*` / `GrShaderCache` | **再生缓存** | 删 | 网页／图形技术打包的软件留下的"算过的副本"，删了下次自己长回来 |
| `installer.exe` / `patch` / `pending`（更新器目录**内**） | **旧更新包** | 删，**留目录** | 更新器装完不删自己用的安装包，一版压一版；但那个空壳目录是更新器要用的，删目录会让更新器坏 |
| `Temp` / `CrashDumps` / `node-gyp` / 陈旧 `MessageBus` 日志 | **垃圾** | 删 | 临时／崩溃转储／编译原生扩展的中间产物／过期流水，没人负责回收 |
| `logs/` | **流水账** | 删 **或 建道** | 只增不减的日志：要么定期删，要么干脆把整个目录联接走，让它长到数据盘去（这就是处置 B 类） |
| `IndexedDB` / `Local Storage` / `Screenshot` / `*.sqlite` 聊天库 / 下载历史 / AI 索引(projects) / `tools/` / NGX 模型 / `Package Cache` | **用户数据或程序本体** | **禁删** | 网页应用的小数据库与键值存储、截图、聊天数据库、下载历史、AI 给代码建的本机索引、工具本体、装包器的反向备份、模型文件——删了要么丢数据，要么程序直接坏 |

`[实测]` 五行逐条对应第八节第 2 小节表格。

**原文附了一条实录反例**，是整节最值钱的一句：「`Roaming/uv` 名字像 uv 缓存，钻层实为**已装工具本体**——名字像≠是，先定性再动手。」`[实测]` 见第八节第 2 小节末尾 ⚠️ 行（uv＝Python 包管理器的一种；本例只保留机制，不保留本机路径）。这条反例同时说明两件事：

1. **目录名的语义不可信**：工具缓存与工具本体常常同名不同层（一个在 `Roaming`，一个在数据盘自建目录）。
2. **脚本的关键字白名单也会栽在这里**：`scan_junctions` 就是靠目录名里含不含 14 个关键字来筛候选的——它能筛出 `uv`，但**判不出"这是缓存还是本体"**（定性是 L3 的活，脚本只做到 L1）。两处必须配套用，见 9.6。

### 8.3 占用核查前置：分清"本体在跑"和"内核被借用"

- 清理前 `tasklist`（列当前进程）确认目标程序**已关**。`[实测]` 第八节第 3 小节。
- 浏览器要分清两个进程名：`msedge.exe`（浏览器本体进程，可以清它的缓存）与 `msedgewebview2.exe`（**被其他软件复用的网页内核**，它出现在列表里**不代表浏览器正在运行**）。`[实测]` 同上，原文括注逐字如此。

> 为什么这条要单列：`[推演]` 具体反例——你看到 `msedgewebview2.exe` 有 20 个进程，判"Edge 在跑，别清"，于是每次体检都跳过浏览器缓存，那个几 GB 的 `Cache` 目录永远清不掉；反过来，若把它当成"Edge 本体"硬清，可能让某个正在用它渲染界面的桌面应用在下次启动时白屏。两种误判都来自同一件事：**进程名 ≠ 谁在用它**。

### 8.4 处置三分类 A / B / C

| 类 | 适用对象 | 动作 | 刹车在哪 |
|---|---|---|---|
| **A 直接清** | 8.2 表中"再生缓存／垃圾"两类 | 删 | 只在 L3 定性完成后才允许 |
| **B 建道** | 持续再生的大缓存、大日志 | 走第六节转移术全流程：**幂等检测 → 关进程 → 删（空）→ `mklink /J` → 跨盘写测试** | 幂等检测在最前；**跨盘写测试**在最末（不写一次就不知道链接真在干活） |
| **C 拍板** | 用户数据、系统件、任何拿不准的 | **列清单 + 建议交用户**，禁擅自删 | "拿不准"三个字就是触发条件；把不确定性交回给它的主人 |

`[实测]` 三分类逐条见第八节第 4 小节。注意 B 类比第六节的四步**多了两头**：前面加"幂等检测"、后面加"跨盘写测试"——因为第八节是从实战回收里补写的，它假设你要连着做几十次处置，所以把"别重复"和"要验证"钉进了流程。这是 L1 规则与 L2 流程的一处真实差异，值得记下来。

### 8.5 验证收尾五件事

原文第 5 小节一口气列了五项：

1. **df 前后对比**——量化的回收证明（不是"看起来清爽了"）。
2. **联接写测试**——往链接目录写一个文件，确认它真的落到数据盘（用余量变化或目录体积确认）。
3. **报告落盘必含勿动清单**——写清楚这次判定不能删的东西与理由，**防下次误伤**。
4. **记忆／账本留痕**——把这次的判据与结论沉淀下来。
5. （收尾即"未确认不做下一步"，与第五节的"禁止未确认的跨盘写入"同构。）

`[实测]` 第 1–4 项逐字见第八节第 5 小节；第 5 点是本页对第 4 节末「记忆/账本留痕」与第五节联动的归纳，属 `[推演]`。

> **勿动清单为什么是强制项而不是可选项**：`[推演]` 反例输入——清理报告只写"回收 9.6G"，三个月后系统盘又紧了，新的一轮（或另一个 agent 会话）看到那个"看起来没用的 4GB 目录"，历史里没有任何一处说它曾被判为"AI 索引，禁删"，于是被删；损失的不是空间，是用户重新索引全部项目的那几个小时。**勿动清单是一份写给未来的否定知识**（"这条路不要走"），它的价值只在第二次清理时才兑现。

### 8.6 常见落点族：认族而不是背路径

原文第 6 小节列了六类"下次换个软件也照用"的形态：

| 族 | 落点形态 | 用法 |
|---|---|---|
| **网页技术打包的桌面软件**（Electron 系） | `Roaming/<应用标识>`（内含 `logs/` 与 `Cache`）＋ `Local/<应用>-updater`（`installer.exe` 堆积） | 见到这类形状就直奔 8.2 表第 1、2 行 |
| **Chromium 内核应用** | `User Data/Default/{Cache 族}` | 8.2 表第 1 行；同时先做 8.3 的进程分清 |
| **国内聊天／办公软件** | `patch` 目录＝补丁包堆积 | 删包、留目录 |
| **日志目录** | `logs/` | A 类删，或 B 类建道 |
| **国内版与国际版路径不一致** | 目录名带 `CN` 之类后缀，**不能按国际版经验猜** | 用 `find -iname` 实测定位 |
| **更新器目录内的 pending** | 更新未完成时留下的暂存 | 只删目录**内**的安装包，不动目录 |

`[实测]` 见第八节第 6 小节（原文用"Electron 系""Chromium 内核应用"等词，本页保留框架名——它们属通用技术名词，不构成隐私）。

> 这六类正是引言那句「**吸纳思路，不背路径**」的具体化：软件会更新、目录名会变（`[推演]` 反例：某应用改版后把缓存从 `Roaming/<id>/Cache` 挪到 `Local/<id>/Cache`，你背下来的路径就变成一条"扫不到东西所以没事"的假绿）；但"再生缓存的构成特征"和"钻到能定性为止"这两条不变。

## 第 9 章 机制六 · 体检脚本 `disk_check.py` 逐段拆解

附属件那 1 个就是它：`scripts/disk_check.py`，245 行、8,497 字节（本页按 `wc -l` 与文件系统大小自数，数法见此处）。它是 `SKILL.md` 第六节承诺的那把尺子。

### 9.1 性质：纯只读

**它不改你任何东西。** 从代码上清点它用到的全部外部动作：`os.walk`（遍历目录）、`Path.stat().st_size`（取文件大小）、`os.readlink`（读链接指向）、`winreg.OpenKey/QueryValueEx`（读注册表两个分区的环境变量段）、`shutil.disk_usage`（读盘余量）。**没有任何**删除、移动、写文件、改变量的调用。`[实测]`（依据脚本函数体内实际出现过的调用清点）

这个性质决定了它可以被随便跑、可以被定时任务跑、可以被别人拿去验证你的说法——**"跑一下看看"的代价是零**，这是它相对于"手工检查十二处"最大的工程价值。

### 9.2 用法三条与一个解释器坑

`SKILL.md` 第六节给的调用形状（原文里写的是本机绝对路径，**本页按红线抽象为仓库相对路径**）：

```powershell
# 常规体检（只体检、不动作）
py ..\A-Cao-磁盘缓存纪律-禁止落C盘与缓存重定向\scripts\disk_check.py

# 附带列出系统盘用户目录的可疑大目录（只报告，不删）
py <同上路径>\disk_check.py --scan-user

# 换判红线（低于多少 GB 报警）
py <同上路径>\disk_check.py --threshold 20

# 给别的程序消费
py <同上路径>\disk_check.py --json
```

三个要点：

1. **`--scan-user` / `--threshold` / `--json` 三个参数，全部可选**，参数解析方式是"在命令行列表里找这个字符串"（`in args` ＋ `args.index(...)+1` 取值），没有短参、没有校验、`--threshold` 跟的值不是数字时**静默回落**到默认值。`[实测]` 见 `main` 函数体。
2. **退出码语义**：`0`＝全绿，`1`＝存在 FAIL，`2`＝存在 WARN。**红优先于黄**（`main` 末尾先 `if fails: return 1`，否则才 `return 2 if warns else 0`）——所以黄不会盖住红，哨兵只需按"非 0 即要看一眼、1 是硬违规"分级。`[实测]`
3. **解释器坑（本支文本的一处真实缺陷）**：原文第六节的示例用 `python` 起脚本，并用绝对路径点名。在某些 Windows 机器上，`python` 是系统商店的占位程序，敲下去**什么都不检查、直接非零退出**；换 `py`（Windows 自带的 Python 启动器）才可靠。`[实测]` 本页撰写机器上实测：`py` 可用（3.12 系），裸 `python` 无输出并以非零码退出。改进建议记在第 15 章。

### 9.3 顶部配置区：四组常量

| 常量 | 值 | 含义 | 换掉的后果 |
|---|---|---|---|
| `SYSTEM_DRIVE` | 单个盘符字母＋冒号（原文写死为系统盘那个字母） | 所有"在不在系统盘"判断的唯一基准 | 把 Windows 装在别的盘位的机器上，**全部判据反向**：真正的系统盘被认成数据盘（绿），数据盘被认成系统盘（红）。见 10.1 第 6 条 |
| `WARN_FREE_GB` | `15.0` | 空间判红线（默认，`--threshold` 可覆盖） | 见 7.3 |
| `ENV_TARGETS` | 6 个键（见 5.1 表） | 第 1 项要查的缓存开关 | 加一个键＝多查一个工具；键值里的中文描述会原样出现在报告里，所以**描述文本就是给人看的证据** |
| `USER_SUSPECTS` | 9 条相对路径 | 第 2 项要量的位置 | 每条都以"用户主目录之下"为根，路径写在 `Path` 拼接的右侧 |
| `JUNCTION_TARGETS` | 2 条完整路径（**含真实用户名，本页抽象为：用户主目录下的 `.cache` 与 `AppData\Local` 下的 `pip` 两处**） | **注释说"已知需要检查是否为 junction 的路径（按需补充）"——但脚本里没有任何函数读它，它是一条死配置** | 见 10.1 第 1 条，这是本支最实在的一处"文档与实现不一致" |

`[实测]` 常量清单与取值逐一对应脚本 25–55 行区段；`JUNCTION_TARGETS` 的"定义后无引用"由全文件文本检索确认（除定义行外零出现）。

### 9.4 第 1 项 `check_env`：环境变量是否已重定向

流程：对 6 个变量各走 `env_get`（三级读取）→ 分 `moved`／`bad`／`missing` 三堆 → 按 5.4 的规则出红／黄／绿。判"在系统盘"的函数是 `is_on_system_drive`：取路径的盘符部分、转大写、看是不是以 `SYSTEM_DRIVE` 开头。

报告形状（逐字取自脚本的字符串拼装）：

```
FAIL [1] 环境变量重定向：<N> 项仍指向系统盘
        <变量>=<值> → 仍在系统盘
WARN [1] 环境变量重定向：<N> 项未设置（未用到的工具可忽略）
        <变量>(<中文描述>)
OK   [1] 环境变量重定向：<N> 项已指向非系统盘
```

**每条消息前缀的 `[1]`／`[2]`／`[3]`／`[4]` 是"四查"的编号**，不是序号也不是严重程度——这让外部程序（或人）能把同一项的红黄绿归到一行看。`[实测]`

### 9.5 第 2 项 `check_user_dirs`：系统盘用户目录是否异常膨胀

九条可疑位置（脚本 `USER_SUSPECTS` 原样，均为用户主目录下的相对路径）：

| 相对位置 | 它是什么 |
|---|---|
| `AppData\Local\pip\Cache` | pip 的包副本 |
| `AppData\Local\npm-cache` | npm 缓存 |
| `AppData\Local\pnpm` | pnpm 的 store |
| `.cache\huggingface` | 模型权重总入口 |
| `.cache\torch` | 预训练权重 |
| `.cache\pip` | pip 的另一处副本（与上第一条并存是有意的：不同安装方式写不同位置） |
| `Downloads` | 浏览器默认下载位置（第 0 节点名严禁的那一个） |
| `.conda\pkgs` | conda 环境管理器的包缓存 |
| `AppData\Local\Temp` | 用户临时区 |

逻辑三条，值得逐条看：

1. 根取自 `USERPROFILE`（环境变量里"用户主目录"那一项），**取不到时回落到系统盘的默认用户模板目录**（脚本写的兜底值形如 `系统盘\Users\Default`）。`[实测]`
2. 对每条：存在 **且** `is_symlink()` 为假 → 走 `dir_size_mb` 递归求和；`size >= 1024`（MB）才计入"可疑"。
3. 汇总成**一条** WARN（而不是九条），文案末尾直接给处置：「设环境变量重定向；已生成的先迁移再建 junction」。

> **第 2 项是全支把 L1 与 L2 缝在一起的地方**：报告不只说"这里大了"，还说"照哪一节做"。`[实测]` 见 `check_user_dirs` 的字符串拼装。

### 9.6 第 3 项 `scan_junctions`：批量幂等检测

脚本 docstring 自己交代了设计：「遍历系统盘用户目录下常见缓存位置（**深度受限**，避免全盘慢扫）」。

```
两个根：用户主目录下的 .cache ，以及 AppData\Local
只看一层子项（iterdir，不递归下钻）
名字里含 14 个关键字之一才处理：
  cache / pip / npm / pnpm / huggingface / torch / runtimes / opencode
  chroma / memory / hyperframes / conda / yarn / uv
（注释原话：只看缓存／运行时类目录，跳过普通程序目录）
```

三分支：

| 情形 | 判据代码逻辑 | 结论 |
|---|---|---|
| 是链接（`is_symlink()` 或 `is_junction()`）且 `os.readlink` 读到的前两个字符**不是**系统盘盘符 | 已正确拐走 | **OK**，逐条列出"路径 → 指向" |
| 是链接但指向以系统盘盘符开头 | 拐错了（链接指回系统盘） | **WARN** 文案「链接仍指向系统盘」 |
| 不是链接，是实体目录，且 `dir_size_mb >= 50` | 还没拐走 | **WARN** 文案「实体目录 <体积> MB（未拐走）」 |

WARN 汇总末尾的处置文案：「数据移至非系统盘 → 删空原目录 → mklink /J 重建」——第六节四步的压缩句。`[实测]`

两条设计张力（不是缺陷，是取舍，但要讲清）：

- **关键字是子串匹配，不是等值匹配**：`"cache" in name.lower()` 这类判断会连带命中任何名字里含这些片段的目录。`[推演]` 具体反例：某应用把用户数据目录命名为 `<某应用>MemoryBrowser`，因为含 `memory` 子串就会被拉进"缓存类候选"并报"实体目录 500MB 未拐走"，建议你去建道——而它装着用户数据，建道可以，**照 8.2 判据删它就是事故**。所以第 3 项的输出**必须**先过一遍第八节定性，脚本只负责"把候选端出来"。这一点在原文里没有任何提示，是本页要补的最重要一句。
- **14 个关键字里含 `uv`、`memory`、`opencode`、`hyperframes` 这类本项目常用名**：白名单里混着"通用工具名"（pip/npm/torch/conda/yarn/cache）与"本机环境里观察到的具体工具名"。前者是普适判据，后者是**经验补丁**——每遇到一个新的乱写位置的工具，就往元组里加一个词。`[实测]`（元组内容即证据）；这条演进方式记进第 15 章「未采纳项／技术债」，因为它是"吸纳思路不背路径"那句宣言的反面：**白名单本身就是在背路径**。

### 9.7 第 4 项 `check_free_space`：各盘余量

- 试探五个盘位字母（脚本写死一个五个字母的字符串，逐个拼成"该盘根目录"看是否存在）。`[实测]`
- 对存在的盘都输出一行 `<字母>: 剩余 GB / 总量 GB`，但 **只有系统盘那个字母参与判红**：`if letter == "C" and free_gb < threshold`。
- 判红 → **FAIL**，文案「空间预警：系统盘低于阈值」并附「清理 + 重定向，禁止未确认的大规模写入」（第五节的行为约束被搬进了报告文案）。
- 否则 → **OK**，并且这条 OK **把各盘余量全串在括号里**打印出来——所以绿也不是没有信息量的，它是"顺手把 df 做了"。

> 只有系统盘判红是合理的保守选择：本支的全部痛感都在系统盘。但 `数据盘被写到 0` 同样会让一次大下载失败。`[推演]` 具体反例输入：数据盘只剩 5GB 而系统盘剩 100GB，你要拉一个 30GB 模型 → 第 4 项给绿，第 1 项也给绿（变量确实指向数据盘），体检"全绿"，下载在 17% 处失败，留下半截缓存。补法很轻（把判红条件从"等于系统盘字母"改成"目标盘或任意盘"），但**未被实现**，见第 15 章未采纳项；在实现之前，这条判断仍要靠第五节那句"动手前先查"人肉补位。

### 9.8 输出形状（默认文本模式与 `--json`）

文本模式：先全部 OK、再全部 WARN、最后全部 FAIL（**按严重程度分块，不按检查顺序**），每行前缀两个空格 ＋ `OK  `/`WARN `/`FAIL `，末尾一条 56 个短横线的分隔线，再一行汇总：

```
  OK   [1] 环境变量重定向：3 项已指向非系统盘
  OK   [4] 空间预警：各盘均在阈值之上（<盘余量清单>）
  WARN [2] 系统盘用户目录可疑项（≥1GB）
          <抽象路径>\Downloads  4.2 GB
          处置：设环境变量重定向；已生成的先迁移再建 junction
  FAIL [4] 空间预警：系统盘低于阈值
          仅剩 8.3 GB（阈值 15.0 GB）
          处置：清理 + 重定向，禁止未确认的大规模写入
--------------------------------------------------------
体检结果：OK 2 / WARN 1 / FAIL 1
```

（上块是**形状示例**，数字与条目为本页按代码逻辑构造的教学样本，不是某台机器的实测输出；`[推演]` 构造依据：`main` 的打印顺序、消息模板与退出码分支。）

`--json` 模式：同一份三个列表被改成 `{"ok": [...], "warn": [...], "fail": [...]}`，`ensure_ascii=False`（中文原样输出不转义）＋缩进 2。**没有机器可读的指标字段**——体积数字埋在文案字符串里，所以外部程序想按数字做趋势图只能靠正则抠文案。`[实测]`（`json.dumps` 调用形状）

### 9.9 红／黄／绿总账（哪一项能给出哪种结论）

| 四查 | 能给 FAIL | 能给 WARN | 能给 OK | 判红线的数值 |
|---|---|---|---|---|
| [1] 环境变量 | 是（值仍在系统盘） | 是（未设置） | 是（且无红才出） | 无阈值，纯位置判断 |
| [2] 用户目录膨胀 | **否** | 是（≥1GB 项） | 是 | **1024 MB** |
| [3] 重定向指向 | **否** | 是（拐错／未拐走） | 是（含"未发现候选"这种绿） | **50 MB** |
| [4] 空间预警 | 是（系统盘低于阈值） | 否 | 是 | **15 GB**（可 `--threshold` 改） |

`[实测]` 逐项对照四个函数里的 `fails/warns/oks.append` 调用。

> 读这张表的正确方式：**只有第 1、4 项能判红**。也就是说"体检结果：OK 2 / WARN 2"这种输出**已经是最坏情况的一部分**——缓存已经胖了、链接还没建，但脚本不会因此让哨兵报"故障"，只报"待办"。这是设计与痛感的分工：红留给"正在违规"和"机器不安全"，黄留给"该干活了"。

## 第 10 章 失效与恢复：它怎么坏、坏了怎么发现、发现后怎么退

### 10.1 六条"假绿"路径（体检全过但问题还在）

每条都给"具体什么输入会让它出问题"。术语：**假绿＝判据在尺子本身写坏时永远返回"没毛病"**。

1. **死配置 `JUNCTION_TARGETS`**：脚本顶部声明了两条"已知需要检查是否为 junction 的路径"，注释还说"按需补充"，但**没有任何函数引用它**。`[实测]`（全文件检索除定义外零出现）`[推演]` 后果输入：你往这个列表里补了一条真正要盯的路径（比如某个必须建道的应用数据目录），补得很认真，跑体检，它一条相关结论都不给——第 3 项只扫那两个根的一层子项。你以为你在保护一处，其实你在保护零处。**发现方式**：改完配置后故意把那条路径指向系统盘，看是否变黄；不变就是没生效（这就是变异检验）。
2. **`--scan-user` 名不副实**：函数 `check_user_dirs(scan)` 的 `scan` 参数**只影响结尾那句"（已扫描）"**，九条目录的尺寸计算**无论带不带这个参数都在跑**。`[实测]`（函数体里 `scan` 仅出现在 OK 文案的字符串拼接处；`big` 的构造不受它控制）而脚本 docstring 与 `SKILL.md` 第六节都写着"附带扫描"。`[推演]` 后果：使用者以为不带参数更快更安全，于是"只跑常规体检"的习惯并不能减少任何磁盘遍历；反过来，指望"带 `--scan-user` 才做的深扫"这种分层保护是**没有的**。真正的差异只在报告文案上。
3. **相对路径值被判"已移出"**：`is_on_system_drive` 用 `Path(p).drive` 取盘符——相对路径的 `drive` 是空字符串，空串不会以系统盘盘符开头，于是落到 `moved` 那一堆。`[实测]`（比较式）`[推演]` 触发输入：某人把 `PIP_CACHE_DIR` 设成 `cache\pip`（不带盘符的相对值，指向未定），体检回「[1] 1 项已指向非系统盘」→ 绿。而实际写入位置取决于当前工作目录，很可能仍在系统盘。**这是本脚本最容易踩的一条假绿**，因为它把"我没写清楚"读成了"我做对了"。
4. **`dir_size_mb` 静默吞权限错误**：外层与内层都 `except OSError: pass`，读不到的目录贡献 0 字节，函数照常返回一个数。`[实测]`（两处 try/except）`[推演]` 触发输入：某个受保护的大缓存目录（例如别的用户或程序锁定的位置）里躺着 12GB，体检进程无权遍历 → 报"无 ≥1GB 的可疑缓存"→ 绿。**体积数字看起来精确（一位小数），但它可能是"无权读取"的另一种写法。**
5. **"未发现候选缓存目录"这条绿**：第 3 项在两个根都不存在、或一层子项里没有任何关键字命中时，走 `oks.append("[3] 重定向检查：未发现候选缓存目录")`。`[实测]`（第三个 if 分支）`[推演]` 触发输入：机器上缓存全在 `AppData\Local` 的**二层以下**（脚本只看一层），或某工具把缓存放在 `ProgramData` 下（脚本不扫这个根）→ 一句"未发现候选"看起来像"检查过了，没东西"，实际是"没看着那儿"。**这条是三层漏斗"禁止只扫一层就下结论"的反面教材，而它恰好写在体检脚本里。**
6. **盘符硬编码**：`SYSTEM_DRIVE` 与第 4 项里那个字母判断都写死在源码里，脚本还按一个固定的五个字母串试探盘位。`[实测]`（两处常量与那个字母串）`[推演]` 触发输入：系统装在别的盘位，或数据盘在字母串之外的盘位（例如第六个分区）→ 前者让所有判断反向，后者让余量根本不进报告。

### 10.2 脚本自己跑不起来（最常见的两种）

| 症状 | 根因 | 退法 |
|---|---|---|
| 敲 `python disk_check.py` 后**直接非零退出、无任何体检输出** | `python` 在部分 Windows 上是商店占位程序；`SKILL.md` 第六节的示例命令正是这个写法 | 换 `py`（Windows 的 Python 启动器）；**没有输出 ≠ 全绿**，先看退出码是不是脚本返回的 0/1/2 三个值之一（`[实测]` 本页机器实测：`py` 可用、裸 `python` 无输出） |
| 抛 `AttributeError: is_junction` 之类的属性错误后中断 | `Path.is_junction()` 是较新版本 Python 才有的方法，`scan_junctions` 里那行只包了 `except OSError`，接不住方法不存在 | 用够新的解释器跑（本机 3.12 系可用，`[实测]`）；或把这一项当"看不了"，退回第三节手工 `dir` ＋ `fsutil` 两条命令判（`[推演]` 触发输入：旧机器上只有 3.8／3.10 的解释器） |
| 注册表读不到 → 明明设过的变量报"未设置" | 三级读取里前两级都取不到（值只存在于**另一个**已运行进程的环境里） | 在设了变量的那个终端里跑，或注销后重开；这不是脚本错，是环境变量的可见范围（5.3） |

### 10.3 转移术中途坏了怎么退

四步是一个"事务"，最坏的两个断点：

| 断点 | 状态 | 退法 |
|---|---|---|
| **第 2 步挪数据时断电／空间不足** | 原位还在（可能半残），数据盘有一份不完整的副本 | **先删数据盘那份不完整的**，回到"原位为唯一真相"，重跑第 2 步；绝不允许"两边都留着半截"继续第 3 步——第 3 步会把唯一完整的那份删空 |
| **第 3 步删了原目录、第 4 步没建链接**（比如忘了管理员权限） | 程序现在指向一个不存在的路径，一写就报错 | 立刻用管理员权限补第 4 步；数据盘那份仍在，损失只在"程序这段时间报错" |
| **链接指向的位置后来被删了**（断链） | `dir` 仍显示 `<JUNCTION>`，但进去报"路径不存在"；`fsutil reparsepoint query` 能读到旧指向 | 幂等检测第三态处理：`rmdir` 拆链接（**不带 `/s`**）→ 数据盘重建实际目录 → 重建链接。切勿在有数据盘真实内容时误用递归删除 |

`[推演]` 三行的"退法"由第二、三节的步骤与三态表推得；`[实测]` 断链症状与 `rmdir`／`fsutil` 判据见第三节代码块与第三行表。

### 10.4 怎么知道"这条纪律失效了"

失效不表现为报错，表现为三句用户问话：

1. **「为什么系统盘又掉了 10G？」** → 说明有新的工具走了默认路径，而它的缓存变量不在那 6 个里。补法：第一节"其它"行那句——任何默认往用户目录 `.cache` 写的工具，**先查它的缓存环境变量**，指到非系统盘；然后（可选）把它加进脚本关键字或 `ENV_TARGETS`。
2. **「上次不是清理过了吗？」** → 说明被清的是再生产缓存（8.2 第 1 行）却没有做 B 类建道；`[实测]` 第八节处置三分类里 B 类的存在理由正是"持续再生的大缓存"。
3. **「我的东西怎么没了？」** → 最严重的一种，说明 C 类没拍板或被跳过了。此时立刻停止一切清理，把 8.5 的**勿动清单**翻出来对：如果清单里有它，说明这次没照流程；如果清单里没有它，说明 L3 定性做浅了——**流程要修，先别修目录**。

## 第 11 章 例行体检：怎么验证它真在生效

"验证一条纪律真在生效"比"跑一次脚本"难，因为纪律的效果是**没发生的事**（系统盘没被吃）。给三层可执行做法。

### 11.1 三个节奏

| 节奏 | 动作 | 为什么是这个频率 |
|---|---|---|
| **装机／接手新机器一次** | 设 6 个变量 → 跑一次体检（带 `--scan-user`）→ 把报出的实体目录逐个走第八节漏斗 → 建两个统一目录 | 第一次是全量摸底，之后只需增量 |
| **每次大下载／大克隆之前** | 第五节那条 `Get-PSDrive`；确认目标盘是数据盘且余量 > 预计体积 ×2 | 事前一次动作的成本是 5 秒，事后回收 9.6G 的成本是一整个下午（`[实测]` 变更日志 v1.1 条记载那次实战回收量级） |
| **每月／每周一次（哨兵）** | 把脚本挂到系统计划任务上定时跑，只记退出码与 `--json` 输出 | 脚本纯只读（9.1），定时跑零风险；红黄趋势比单次结论有用 |

> 哨兵的具体形态：一条计划任务，动作是"`py <脚本路径> --json` 的输出追加进一个日志文件"。`[推演]`（原文只给用法，没给定时化做法；但 `--json` ＋ 稳定退出码这两件设计，本身就是为无人值守准备的——`[实测]` 见 9.2、9.8。）

### 11.2 两条变异检验（自证判据不是恒绿）

**判据要能红**，否则等于没有判据。这两条是本页给的自测法，做完要恢复现场：

1. **让第 1 项红一次**：临时把 `PIP_CACHE_DIR` 指到系统盘用户目录下的一个空目录（例如 `系统盘\Users\<用户名>\pip-probe-tmp`），跑体检 → 必须出现 `FAIL [1] ... 仍在系统盘`，退出码 1 → 删掉那个临时目录、恢复变量。红不出来就说明读取链或判盘符逻辑坏了（10.1 第 3、6 条）。
2. **让第 2 项黄一次**：在 `Downloads` 或某个可疑位置放一个 1.2GB 的临时大文件，跑 `--scan-user` → 必须列出该位置与 GB 数 → 立刻删掉探针文件。它同时验证了"遍历真的在跑、体积真的在算"，顺带证伪 10.1 第 2 条（带不带 `--scan-user` 都该黄）。

> 这两条是**测试纪律**里"改前改后各跑一次、原始输出落盘"在本支的具体化：探针的输出要留在报告里，不然下次没人知道判据当年是活着的。

### 11.3 体检报告的最小骨架（照抄可用）

```
【磁盘体检】<日期>  退出码 <0/1/2>  命令 <py ... --scan-user>
系统盘余量：<X.X> GB（阈值 15.0）  数据盘余量：<Y.Y> GB
[1] 环境变量：<N> 已移出 / <N> 未设 / <N> 违规        ← 违规项逐条列 <变量>=<值>
[2] 可疑大目录（≥1GB）：<列表或"无">
[3] 重定向状态：已拐走 <N> 处 / 未拐走 <N> 处 / 拐错 <N> 处
本次处置：A 类删除 <明细+回收量>；B 类建道 <链接路径 → 目标路径 + 跨盘写测试结果>；C 类待拍板 <清单>
勿动清单（禁删，写给下次）：<路径 + 一句为什么>
下次复查：<日期或触发条件>
```

**勿动清单那一栏不许空着写"无"**：只要跑了第八节漏斗，就一定有 C 类；写"无"通常意味着定性没做（见 8.5 的推演反例）。

## 第 12 章 端到端走查：一句真实需求，从判定到产出形状

**场景（可照抄的真实输入）**：用户对 AI 说——

> 「帮我跑通一个本地语音转文字的小工具，模型尽量用现成的。**别占我系统盘**。」

下面是这一句话进来之后，本支规定要走的每一步、每步的动作与判据。命令里的路径全部是占位写法。

### 步骤 1 · 识别触发（frontmatter `description`）

句中出现"跑通一个工具＋装依赖＋用现成模型"，命中 `description` 列举的「建虚拟环境／拉模型权重／装依赖／落盘大文件」。⇒ 本支生效，**并且**与编码纪律同时生效（沾代码），两者不冲突（第七节归属表）。

### 步骤 2 · 定落盘位置（第 0 节两条硬规则）

- 工程目录：`<数据盘>\AI_Projects\speech-demo`（克隆与代码产物）
- 缓存目录：`<数据盘>\AI_Cache\hf`、`<数据盘>\AI_Cache\pip`
- 判据：这次会产生 ≥1GB 吗？语音模型权重普遍在 1–15GB 级 ⇒ **会** ⇒ 进步骤 3。

### 步骤 3 · 空间预警（第五节）

```powershell
Get-PSDrive -PSProvider FileSystem | Select-Object Name,@{n='FreeGB';e={[math]::Round($_.Free/1GB,1)}},@{n='UsedGB';e={[math]::Round($_.Used/1GB,1)}}
```

形状与判读：

```
Name FreeGB UsedGB
<系统盘>   118.4  356.2     ← 系统盘健康（>15GB），但它不是本次目标
<数据盘>    76.0  820.0     ← 目标盘：预计 12GB < 76GB×0.5 ⇒ 通过
```

不通过的分支：目标盘不足 ⇒ **立即停、报告用户**，禁止改投别的盘（第五节）。

### 步骤 4 · 重定向（第一节，在装与下之前）

```powershell
$env:HF_HOME       = "<数据盘>\AI_Cache\hf"
$env:PIP_CACHE_DIR = "<数据盘>\AI_Cache\pip"
```

- 判据（脚本第 1 项同款）：变量值**不得**以系统盘盘符开头。
- 想持久化：写进用户环境变量（脚本第②级能读到；当前已开进程读不到，见 5.3 表）。
- 只做一次不想改全局：`pip install --cache-dir <数据盘>\AI_Cache\pip ...`（第一节 pip 行）。

### 步骤 5 · 下载前的一次幂等检查（第三节，别嫌啰嗦）

```powershell
dir "<数据盘>\AI_Cache\hf"                    # 里面已有内容吗？
fsutil reparsepoint query "<系统盘>\Users\<用户名>\.cache"   # 报错=不是链接；打印=是链接，看指向
```

三态对号（第三节表）：已是正确链接 → **停**，不再建；实体且占空间 → 走步骤 7；链接指错 → `rmdir`（不带 `/s`）后重建。

### 步骤 6 · 装依赖与拉权重（观察写入位置）

装完后跑一次体检，看的是"新写入有没有跑到系统盘去"：

```powershell
py <仓库内路径>\disk_check.py --scan-user
```

本次真实会出现的形状（示例）：

```
  OK   [1] 环境变量重定向：2 项已指向非系统盘
  WARN [3] 重定向检查：1 处未拐走或拐错
          <系统盘>\Users\<用户名>\.cache 实体目录 1240 MB（未拐走）
          处置：数据移至非系统盘 → 删空原目录 → mklink /J 重建
  OK   [4] 空间预警：各盘均在阈值之上（...）
--------------------------------------------------------
体检结果：OK 2 / WARN 1 / FAIL 0
```

读法：**这是黄不是红**（0 个 FAIL ⇒ 退出码 2），含义是"变量设对了，但历史上已经有 1.2GB 压在系统盘，需要建道"。

### 步骤 7 · 把那 1.2GB 拐走（第二节四步 ＋ 第八节 B 类）

```
1) 停占用：确认没有任何 Python／模型加载进程在使用 .cache 里的文件
2) 幂等检测：dir + fsutil → 判为"实体目录"，继续（若判为已正确链接，此处立刻结束）
3) 移动：把 .cache 整体移到 <数据盘>\AI_Cache\redirected\dot-cache
4) 删空原目录（必须已空）
5) 管理员执行： mklink /J "<系统盘>\Users\<用户名>\.cache" "<数据盘>\AI_Cache\redirected\dot-cache"
6) 跨盘写测试：往链接路径里新建一个测试文件 → 到数据盘那侧看它是否出现 → 删除测试文件
7) 复检：再跑一次步骤 6 的命令，第 3 项应变成 OK
```

### 步骤 8 · 收尾（第四节 ＋ 8.5）

- 删临时解压产物（安装包解压出来的那份，不再需要就当场删）。
- 前后 `df` 对比（或第 4 项的余量行）→ 记下回收量。
- **写勿动清单**：本次钻层判出的"看着像缓存但不是"的位置（例：某工具目录下钻到第三层发现是已装工具本体，不是缓存）。

### 最终产出形状（给用户的那份东西）

```
落盘位置：工程 <数据盘>\AI_Projects\speech-demo
         缓存 <数据盘>\AI_Cache\{hf, pip}
本次新增占用：数据盘 +12.4 GB，系统盘 0（并把原有 1.24 GB 拐走）
验证：体检退出码 0；[3] 由 WARN→OK；跨盘写测试通过
判红线：系统盘剩余 <15GB（当前 <118.4GB>）；单个可疑缓存 ≥1GB
勿动清单（下次别删）：<数据盘>\AI_Projects 全部；<某工具目录> 内 <已装工具本体子目录>（名字像缓存，实为本体）
待你拍板（C 类）：系统盘内 <某应用> 2.1GB 的 logs/，建议建道而非删除
```

**这条走查的判据自查**：每一步都能被一句命令或一条红黄绿证实；没有任何一步依赖"我记得应该没事"。

## 第 13 章 反模式清单（不要这样用）

| # | 反模式 | 后果（说清是怎么坏的） |
|---|---|---|
| 1 | **先下载、再设 `HF_HOME`** | 权重已经按默认位置写进系统盘，变量只影响此后新写入；你得额外走一遍转移术，而那次下载本身可能已经把盘写满、连"搬"的机会都没有 |
| 2 | **不做幂等检测就执行"移动＋建链"** | 第三节 ⚠️ 点名的那件：已经拐走的目录被再复制一份，出现套嵌链接／双副本；此后写入进哪一侧变成不确定的事，体积统计还看着"正常" |
| 3 | **用 `rmdir /s` 删一个联接** | 递归会穿过入口删掉数据盘那侧的真实内容——本意是"拆个门"，实际是把门后面的房间烧了。**永远只 `rmdir` 不带 `/s`** |
| 4 | **把体检脚本当清理工具用** | 它是纯只读的（9.1）；期待它"顺手清一下"会让人以为报告了就是处理了。黄条不会自己变绿，处置是第二、八节的动作 |
| 5 | **只扫一层就判"这 1.5GB 是缓存，删"** | 第八节 L3 存在的理由；那 1.5GB 里可能 1.1GB 是缓存、0.4GB 是聊天库或账号数据。原文用实录反例把这条钉死了 |
| 6 | **靠目录名判性质**（"叫 cache 就能删"、"Roaming 下的一定是缓存"） | 8.2 的 `uv` 反例：名字像缓存，钻下去是已装工具本体，删了程序直接坏。**判据是构成，不是名字**；脚本第 3 项也是靠名字筛的，所以它的输出必须再过一遍定性 |
| 7 | **把缓存与工程混进同一个目录** | 4.2 推演的那条：一次"清缓存"的手势会连带删掉真实仓库；分栏是误删半径的最小切分 |
| 8 | **看到 `--scan-user` 就以为没带它就不会读盘** | 10.1 第 2 条：参数只改一句文案，九处目录无论带不带都在遍历。**别把"少写一个参数"当权限边界** |
| 9 | **把"无输出"读成"没问题"** | 10.2 第一条：解释器不对时脚本根本没跑。判据是退出码落在 0/1/2 里，不是屏幕上有没有红字 |
| 10 | **拿"体检全绿"当"C 盘没事"的唯一证据** | 四查里第 2、3 项只覆盖两个根的一层子项、关键字之外的工具不认；全绿只说明"判据覆盖范围内没发现"。系统盘余量行才是那台机器的真实体温 |
| 11 | **未确认就跨盘写入** | 第五节明文禁止；产物分散两处后，"这次都写了什么"只能靠重新考古，第八节回收流程被迫重跑一遍 |
| 12 | **删完就走，不留勿动清单** | 8.5 的推演反例：三个月后另一轮清理（或另一个会话）把同一批用户数据再删一次。**勿动清单是唯一能让"这次定性"活到下次东西** |
| 13 | **用它管"代码怎么写／测试怎么算／结论怎么下"** | 第七节四件互不重叠；本支越界只会稀释触发面，让"东西写哪"这条真正要守的规则被淹在无关文本里 |
| 14 | **把这条纪律当文字记住、不跑脚本** | v1.0 的封装动机（版本节）：只有文字时"幂等检测全靠人记"。既然带了尺子，判据就该由尺子给出——这也是第 11 章两条变异检验的动机 |

（本表 14 条，为本页自数，数法＝表体行数。）

## 第 15 章 工程与安全规范

### 15.1 命名与形态规范

| 项 | 本支的做法 | 为什么这样定 |
|---|---|---|
| 库内目录名 | 中文全称、把结论写在名字里：`A-Cao-磁盘缓存纪律-禁止落C盘与缓存重定向` | 名字即检索面：`禁止落C盘` 与 `缓存重定向` 两个短语是用户最可能自然说出的话 |

### 15.2 字段与输出契约（脚本对外承诺了什么）

- **消息前缀 `[1]`–`[4]`** 是"四查"编号（不是严重程度）；外部解析靠它归组。`[实测]`
- **退出码三值** 0/1/2，红优先于黄。`[实测]`
- **`--json` 三个键** `ok`/`warn`/`fail`，值为字符串列表，中文不转义。`[实测]`
- **未提供的契约**：没有稳定的数字字段（体积埋在文案里）、没有短参、没有 `--help`、参数值非法时静默回落默认值。所以别把它当可编排的 API，它是给人和哨兵看的一张纸。`[推演]`（依据 9.2、9.8 的实现事实；具体限制输入：想用"数据盘剩余 GB"画趋势图，`--json` 给不了，只能正则抠中文文案，而文案一改脚本升级就断图）

### 15.3 防护红线（安全侧）

1. **脚本零写操作**：只有遍历／stat／readlink／注册表读／disk_usage（9.1）。这条是"能挂定时任务、能让别人拿去自查"的前提。
2. **删链接只 `rmdir`，永不 `rmdir /s`**（第三节第三态）。
3. **第 3 步"删原目录"的准入条件＝目录必须已空**（第二节），非空即中止回去查为什么还有文件。
4. **C 类禁擅自删**：用户数据、系统件、拿不准的一律列清单交用户（8.4）。
5. **报告必含勿动清单**（8.5）——防下一次的自己误伤。
6. **未确认不跨盘写入**（第五节）。
7. **本机路径不进公开文档**：正文里出现的绝对路径（含真实用户名的两条联接检查路径、第六节的调用示例）在公开页一律抽象为「系统盘／数据盘／`<用户名>`／占位模板」。本页遵守此线，仓库里也不留盘符绝对路径。
