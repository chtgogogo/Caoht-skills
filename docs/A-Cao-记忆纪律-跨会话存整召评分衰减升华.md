# A-Cao-记忆纪律（memory-scoring-lifecycle v3.5）

> [← 返回总目录](../README.md#skills-index)

## 一句话

跨会话记忆的完整生命周期规则——什么该记、值多少分、什么时候衰减、什么条件下升级成铁律，全部定死。

## 它解决什么问题

- **记忆堆成一个文件。** 越攒越大，每次开场都得整份读一遍，token 全烧在加载上。
- **什么都记，等于什么都没记。** 流水账里翻不出重点，真正重要的教训被淹没。
- **同一个坑反复踩。** 上次犯过的错，换个场景又犯一遍——没有机制把它提取成规则。
- **换了个 agent 就清零。** 规则和存储绑死、路径写死，换个宿主得从头再来。

## 为什么这套东西值得用

三条底层判断，整套规则都是从它们推出来的：

**一、记忆的成本是按「每次会话」重复付的。**
记忆文件每轮开场都要读一遍。所以"能记多少条"不是关键，**"常驻的那部分有多轻"才是**。这就是索引与正文分离的原因——索引永远压在 2000 token 以内，细节只在你真的问到时才展开。

**二、记忆的价值在「取」不在「存」。**
存一万条但翻不出来，等于零。所以每条记忆都挂三层触发词（现象 / 实体 / 本质）加同义词，再配一张路由表做到 O(1) 直达——从任何一个角度问，都能落到那一条。

**三、教训的价值在「不再犯」，不在「记下来」。**
光记录不提炼，同一个根因会换个壳再犯一遍。所以设了升华：同一个根因签名累计满 3 次，自动升级成铁律写进 CORE，之后每次会话强制加载。

## 和市面 9 个主流方案比，多了什么

先给结论：

> 这 9 个方案**没有一个**是为"纯文件 + 人肉维护"这种场景设计的——它们全都要数据库和常驻服务。所以策略是**抄思想，不抄架构**。

抄来的思想，一家一条：

| 方案 | 它擅长什么 | 我拿走了什么 |
|---|---|---|
| Claude Code MEMORY.md | 纯 Markdown 文件承载记忆，带容量红线与渐进披露 | **骨架来源**：纯 MD、容量红线、索引常驻细节按需 |
| Generative Agents | 给记忆算重要性 / 相关 / 新鲜三维分，定期 Reflection 反思 | 三维改造成 **V/R 双轨评分**；Reflection 改造成 **升华** |
| mem0 | 自动抽取事实，冲突时用新记忆取代旧记忆 | **supersedes 版本链**、冲突软删除 |
| Zep / Graphiti | 时序知识图，双时间模型（发生时间 + 记录时间），失效而不删除 | **失效而非删除**的双时间语义 |
| A-MEM | 记忆之间自行建立链接、互相演化 | **记忆互相演化**的思路 |
| MemoryOS | 按热度分层，热记忆晋升到高层 | **热度驱动晋升** |
| MemoryBank | 用艾宾浩斯遗忘曲线做时间衰减 | **时间衰减** |
| MemOS | 把记忆当成有状态的生命周期对象 | **生命周期状态机** |
| MemGPT / Letta | 分层记忆 + AI 自主换页 | 分层与按需换入的思想（架构不采纳） |

**明确不抄的四类**——它们都要额外依赖：

- **向量数据库 / 图数据库**：引入即意味着要跑一个常驻服务，纯文件场景扛不住；
- **常驻进程定时衰减**：记忆维护应该是"用到时才做"，不是后台常开；
- **复杂多超参调优**：参数越多越难维护，评分公式必须能手算；
- **全量 Embedding 向量化**：规模没到那一步，性价比为负。

**多大规模才值得上重武器**：条目 60 条以下，目录表格 + 触发词就够；60~200 条加话题分段；**超过 200 条才值得考虑 Embedding**。绝大多数个人场景根本到不了 200 条。

**我比它们强的两处**（这两点业界普遍做得不好）：

- **遗忘区归档**：冷记忆是"移进遗忘区"而不是删掉——业界多数方案要么硬删、要么永久占位。
- **二次判定召回**：不是一次检索定生死，命中后还要过一遍二次判定，够格的才真正加载。

**它们比我先有的两处**（已经补上）：

- **冲突处理**：两条记忆互相矛盾时怎么办——补了 supersedes 版本链；
- **升华**：从零散教训里提炼出规则——补了同根因累计 3 次升华。

## 核心机制

**三记五不记。** 写入前先过筛子。本质层的必写，细节按需，另外明确列了不该记的几类（临时状态、一次性的工具输出之类）。

**V/R 双评分。** 每条记忆算两个分：

- V（价值）= 5 + 影响(0/10/20) + 复发(0/5/15) + 成本(0/5/15) + 稀缺(0/10) + 强调(20)
- R（相关）= 相关度(精确 6 / 沾边 3 / 弱 1) + 新鲜度(7 天内 4 / 30 天内 2 / 更早 0)
- 排序分 = (V/10)×0.6 + R×0.4

**三层触发词。** 每条记忆挂上现象、实体、本质三层触发词，外加同义词。从任一角度检索都能命中。

**路由表 + 渐进披露。** 索引常驻，O(1) 直达；先读头部摘要，需要细节才展开全文。命中时 V 加 2~8、strength 加 1。

**升华。** 同一个根因签名累计出现 3 次，自动升级成铁律写进 CORE，之后每次强制加载。

**规则与存储解耦。** 规则只维护一份，各 agent 在自己位置建自己的 store，规则里不含任何 agent 专属路径。

## 一个真实的评分例子

做技术核查时，我犯过两次同一个错：看到数据模型和接口定义里有某个字段，就断定这个功能真实存在。

第一次，我据此反驳了"把这条功能描述删掉"的建议，坚持它是对的。
第二次，深查代码才发现那个字段在前端根本没被调用过——只是预留。

两次的根因一模一样：**字段存在不等于功能实现**。

放进评分公式算一遍：

- 影响 20 —— 对外描述里写了不存在的能力，被追问时是硬伤
- 复发 15 —— 同一个错犯了两次
- 成本 15 —— 描述已经散落到多个文档，返工要挨个改
- 稀缺 10 —— 这类陷阱不常见，值得单独记一笔

V = 5 + 20 + 15 + 15 + 10 = 65。

这条现在躺在"教训"层，根因签名累计到 3 次就会升华成铁律——之后每次做功能核查，都会强制先查调用链末端，而不是只看模型定义。

## 和同类方案比，差在哪

| 常见做法 | 本 skill |
|---|---|
| 记忆全堆一个文件 | 索引常驻 ≤2000 token，细节按需加载 |
| 无差别全记 | 三记五不记，写入前过筛 |
| 记了就不管 | V/R 评分 + 时间衰减 + 分数排序 |
| 犯错只记不提炼 | 同根因累计 3 次升华成铁律 |
| 换 agent 记忆清零 | 规则与存储解耦，各建各的 store |
| 检索靠全量重读 | 路由表 O(1) 直达 + 渐进披露 |

## 3 分钟上手

1. 把文件夹放进 skills 目录（见[总目录](../README.md#skills-index)）；
2. 第一次用要先冷启动：在自己的记忆位置建 `MEMORY.md`，顶部放常驻引导卡，第一条记"我是谁"；
3. 说【记忆纪律 v3.1】作为启发词触发；
4. 维护脚本 `memory_maintain.py` 复制到你自己的 `tools/` 目录下运行。

## 实战绩

规则从 v1.0 迭代到 v3.5（入口命名保持 v3.1 不变，避免破坏既有触发链），在 WorkBuddy、Codex 等多个宿主上实跑。

上面那条「字段存在 ≠ 功能实现」来自真实事故，现在做技术核查会先查调用链末端。整套评分、衰减、升华机制也都在日常使用中真跑过，不是纸面设计。

## 用了之后，实际会得到什么

- **上下文成本恒定。** 索引常驻且永不膨胀（超量就归档加压缩），会话越长省得越多。不像"全堆一个文件"，成本会随条目数线性上涨。
- **不会丢东西。** 过时的记忆标记失效、冷门的移进遗忘区，都还能被二次召回捞回来——不是删掉。
- **会自己进化。** 同一个坑踩满 3 次自动升华成铁律，不用手动整理，它自己长规则。
- **换宿主不失效。** 规则只维护一份，store 各建各的，规则里不含任何 agent 专属路径。换到 Claude Code、Codex 还是 WorkBuddy，规则照用。
- **每一步可审计。** 每条记忆为什么是这个分、为什么排到前面，公式都摆在那儿，能手算验证——不是黑箱排序。

## 适用 / 不适用

- ✅ 需要跨会话累积长期记忆的 agent；记忆条目变多、检索开始变慢的场景；想把踩坑经验沉淀成规则的场景
- ❌ 单次会话的临时任务；不需要长期记忆的一次性对话
