# A-Cao-记忆纪律（memory-scoring-lifecycle v3.5）

> [← 返回总目录](../README.md#skills-index)

AI 的跨会话记忆普遍是这么死的。一开始是个小文件，什么都往里记，三个月后变成上千行的怪物。每个新会话开场整份读一遍，token 烧掉一大截，里面大半内容跟本次对话无关。想找一条旧记忆，记不得关键词，翻不出来。同一个坑换个场景，全价重踩。换一个 AI 宿主，从头再来。

这套规则针对这四个死法各有一层设计，什么该记、记了值几分、怎么翻得出来、什么时候升级成铁律，全部定死。

## 四个问题，四层设计

**记太多，怎么办。** 写入前先过筛，三记五不记。本质层的教训必写，临时状态、一次性工具输出这类明确不记。每条记忆还要算 V/R 两个分，V 是价值，由影响、复发概率、修复成本、稀缺度累加，R 是相关度乘新鲜度，排序分按权重合成。分数是手算得出来的，不是黑箱。分数低的自然沉底。

**记忆文件越写越肥，怎么办。** 索引与正文分离。常驻的只有一张极轻索引，硬性压在 2000 token 以内，细节条目按需展开。索引超量就归档加压缩。于是开场成本恒定，不随记忆总量线性上涨。这是整套设计的地基，记忆的成本是按每次会话重复付的，省这里的钱才是真省。

**记了翻不出来，怎么办。** 每条记忆挂三层触发词，现象层、实体层、本质层，外加同义词，配一张路由表直达。你从任何一个角度问，现象对不上实体对，实体对不上本质对，总能落到那一条。命中之后还有一道二次判定，够格才真正加载，避免一次检索定生死。

**同一个坑反复踩，怎么办。** 升华机制。同一个根因签名累计出现三次，自动升级成铁律写进 CORE，之后每次会话强制加载。这个设计的前提是承认一个事实，光记录不提炼，教训只是躺在文件里的字，提炼成规则它才开始保护你。而且升华是数据自己触发的，不用你记得去整理。

另有一处容易忽略的巧思，规则与存储解耦。规则全文只维护一份，里面不含任何本机路径，各 AI 宿主在各自的位置建自己的记忆库。换 Claude Code、Codex 还是 WorkBuddy，规则照用，记忆不失效。

## 市面上的方案为什么没直接用

mem0、Zep、MemGPT、Generative Agents 这些都研究过一遍。结论是它们没有一个是为纯文件加人肉维护设计的，全部要数据库和常驻服务。所以策略是抄思想不抄架构。

| 方案 | 拿走了什么 |
|---|---|
| Claude Code MEMORY.md | 骨架，纯 MD 加容量红线加渐进披露 |
| Generative Agents | 三维评分改造成 V/R 双轨，Reflection 改造成升华 |
| mem0 | supersedes 版本链，冲突软删除 |
| Zep / Graphiti | 失效而非删除的双时间语义 |
| MemoryBank | 艾宾浩斯时间衰减 |
| MemoryOS | 热度驱动晋升 |

四样明确不抄，向量库图数据库、常驻进程定时衰减、多超参调优、全量 Embedding，全要额外依赖。个体量参考，超过两百条才值得考虑 Embedding，多数人一辈子到不了。

两处业界普遍做得不好、这里补上的，冷记忆移进遗忘区而不是硬删，还能二次召回。也有两处别人先有、后来补齐的，冲突处理和升华。

## 一个真实的评分例子

同一个错犯过两次。看到数据模型里有某个字段，就断定功能真实存在。第一次据此反驳了别人的修改建议，第二次深查才发现那个字段前端根本没调用过，只是预留。

根因一样，字段存在不等于功能实现。放进评分公式算，影响 20，对外描述写了不存在的能力。复发 15，犯了两次。成本 15，描述散落多个文档。稀缺 10，这类陷阱不常见。V = 5 + 20 + 15 + 15 + 10 = 65，进教训层。再犯一次就升华成铁律，之后每次功能核查强制先查调用链末端。

## 什么时候不用

单次会话的临时任务，不需要长期记忆就别建这套。条目不到十条的，一个目录表格就够。
