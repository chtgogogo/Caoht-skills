# A-Cao-记忆纪律（memory-scoring-lifecycle v3.5）

> [← 返回总目录](../README.md#skills-index)

用 AI 干活超过一个月的人，多半有这么一个文件，叫 MEMORY.md 或者别的名字，里面堆着 AI 的长期记忆。去数数多少行了，几百行很正常，上千也不稀奇。

然后注意一个事实：每次开新会话，这个文件都要整个读一遍。它越肥，你每个会话开局烧掉的上下文越多，而且里面大半内容跟这次对话没关系。

更难受的在后面。记了一堆，出事的时候翻不出来。你隐约觉得 AI 之前犯过类似的错，记在哪了？想不起关键词就等于没有。同一个坑换个场景，全价再踩一遍。

这套规则管的是记忆的完整生命周期，什么该记、记了值几分、什么时候衰减、什么条件下升级成铁律，全部定死，不靠 AI 每次现场发挥。

## 三条底层判断

整套规则是从三条判断推出来的，先摆出来，你可以自己检验后面的设计合不合理。

**一、记忆的成本是按每次会话重复付的。** 所以关键不在能记多少条，在常驻的那部分有多轻。索引永远压在 2000 token 以内，细节只在被问到时才展开。

**二、记忆的价值在取不在存。** 存一万条翻不出来等于零。每条记忆挂三层触发词，现象、实体、本质，外加同义词，再配一张路由表直达。从哪个角度问都能落到那一条。

**三、教训的价值在不再犯，不在记下来。** 光记录不提炼，同一个根因换个壳再犯一遍。所以有升华机制，同一根因累计三次，自动升级成铁律写进 CORE，之后每次会话强制加载。

## 九个主流方案研究下来，一个都没直接搬

mem0、Zep、MemGPT、Generative Agents、MemoryOS 这些都看了一遍。结论是他们没有一个是为纯文件加人肉维护的场景设计的，全部要数据库，要常驻服务。所以策略是抄思想，不抄架构。

| 方案 | 拿走了什么 |
|---|---|
| Claude Code MEMORY.md | 骨架。纯 MD 文件，容量红线，索引常驻细节按需 |
| Generative Agents | 三维评分改造成 V/R 双轨评分，Reflection 改造成升华 |
| mem0 | supersedes 版本链，冲突软删除 |
| Zep / Graphiti | 失效而非删除的双时间语义 |
| MemoryBank | 艾宾浩斯时间衰减 |
| MemoryOS | 热度驱动晋升 |
| MemGPT / Letta | 分层按需换入的思想，架构本身不采纳 |

四样东西明确不抄，向量库和图数据库、常驻进程定时衰减、多超参调优、全量 Embedding，全部要额外依赖，个人场景扛不住。顺便给个体量参考，超过两百条才值得考虑 Embedding，大多数人一辈子到不了。

有两处是业界普遍做得不好、这里补上的。冷记忆是移进遗忘区而不是硬删，还能二次召回。检索命中的要过二次判定，不是一次检索定生死。也有两处是别人先有、后来补齐的，冲突处理和升华。

## 一个真实的评分例子

做技术核查的时候，同一个错犯过两次。看到数据模型里有某个字段，就断定这个功能真实存在。第一次据此反驳了别人的修改建议。第二次深查才发现那个字段前端根本没调用过，只是预留。

两次的根因一样，字段存在不等于功能实现。

放进评分公式算一遍。影响 20，对外描述写了不存在的能力，被追问是硬伤。复发 15，犯了两次。成本 15，描述散落在多个文档，改起来费劲。稀缺 10，这类陷阱不常见。V = 5 + 20 + 15 + 15 + 10 = 65，进教训层。

再犯一次就升华成铁律。到时候每次做功能核查，都会强制先查调用链末端，而不是只看模型定义。

## 用起来是什么样

上下文成本恒定。索引常驻且不膨胀，超量就归档加压缩。那种全堆一个文件的做法，成本随条目数线性涨。

东西不丢。过时的标失效，冷门的进遗忘区，都能被二次召回捞回来。

它自己会进化。同一个坑踩满三次自动升华，不用你记得去整理。

换宿主不失效。规则共享一份，各 agent 各建各的 store，规则里不含本机路径，Claude Code、Codex、WorkBuddy 照用。

每一步可审计。一条记忆为什么是这个分，公式摆在那，能手算。

## 什么时候不用

单次会话的临时任务，一次性对话，不需要长期记忆就别建这套。条目还不到十条的，一个目录表格就够，别过度工程。
