# A-Cao-技能调度（useskill v2.5）

> [← 返回总目录](../README.md#skills-index)

## 五分钟速览

如果只有五分钟，记住这六句。

1. 库里只注册这一个 skill，所有调用请求都过它。Agent 不用记任何别的名字。
2. 调度走固定状态机，引用清点 → 点名直连 → 本地检索 → 市场兜底，不许凭「我觉得我会」跳步。
3. 一条消息里的全部 skill 指称必须逐一清点归宿，命中第一个不许跳过剩下的（State 0，来自真实漏检事故）。
4. 你说「全面调用」「尽可能用」，进入穷举模式，一次 IO 读全库映射表，沾边的全挑出来。
5. 每次调度强制输出报告，挑了谁、排除了谁、为什么，逐条可核对。
6. skill 本体只在唯一权威库放一份，其他宿主放逐字一致副本，防漂移。

一句话概括设计目标，**让 skill 调用从「看 AI 心情」变成「走确定的路」**。

## 它在解决什么问题

skill 装多了之后，有五个具体故障。

| 故障 | 表现 | 本 skill 的对应解法 |
|---|---|---|
| 该调不调 | Agent 觉得自己能力够了，绕过 skill 直接干，效果打折 | 唯一入口 + 状态机强制检索（§状态机） |
| 记不住名字 | 库里上百个 skill，靠 Agent 背名字必然漏 | 按中文文件夹名前缀匹配映射表，泛指词一查即中 |
| 装多了撑爆上下文 | 每轮加载全部 skill 描述，token 烧掉一大截 | 指针索引，浅层抉择后才深读那一个 |
| 一条消息多个指称 | 点名了 A，顺嘴说了句「按 B 的理念」，B 漏触发 | State 0 引用清点，逐一归宿（§引用清点） |
| 调度黑箱 | 漏调发现不了，误调不知道该骂哪 | 强制调度报告 + 调用统计（§透明性） |

其中「该调不调」最隐蔽。AI 莫名自信是默认状态，光在规则里写「要多用 skill」没有用，得让绕过这条路在结构上走不通。

## 状态机详解

### State 0 · 引用清点（每次调度第一步，硬性前置）

把用户本条消息里的全部 skill 指称列成清单，分三类，逐一写明归宿。

1. **显式路径**，给出了目录或文件路径，直接定位。
2. **点名 name**，给出了调用键或中文文件夹名。
3. **泛指能力词**，「XX skill」「按 XX 的理念」以及任何「某领域 + skill」合成词。

**为什么必须有这一步**。规则原话是「State 1 命中只消费一个显式引用，禁止因已命中而跳过剩余泛指引用的解析」。这条来自 2026-09-11 的生产事故，前端风格任务，用户点名了一个 skill，末尾又带了句「按前端设计 skill 的理念」。调度器命中点名那个就直接开跑，后半句被当成同一个东西，库里另外三个前端 skill 一个没触发，用户当场发现。在那之前没人想过一条消息里会有两个指称。

### State 1 · 点名直连

有明确路径或 name 的直接执行。存在的意义是让最常见的请求走最短的路径。本机缺失就跳市场兜底。

### State 2 · 本地检索

泛指的说法（比如「按前端设计规范来」）走这条。索引优先，查映射表做**中文文件夹名前缀匹配**。库内文件夹名就是中文功能名，泛指词往往就是前缀，「前端设计」对应「前端设计指南-美观现代UI规范」，一查即中，成本极低。映射表没命中再扫各 SKILL.md 的 name 加 description 做语义匹配。还不中，跳市场兜底。

**为什么不直接语义猜**。语义匹配会漏，前缀匹配是一查即中。索引一次 IO 等于浏览全库目录，这是库越大越省的设计。

### State 2-EX · 穷举模式

用户说「全面调用」「尽可能用」时启用。读映射表全表，按当前任务关键词逐行比对，所有相关候选全部列出，宁多勿少但禁止塞明显无关的。多 skill 命中时按任务阶段排序执行（规范/设计 → 实现 → 审查/打磨），每个命中的 skill 都要实际读了 SKILL.md 才允许声称「用了」。

**为什么这个门要用户自己开**。穷举是宽口径，会多读内容多花 token。它该是用户的显式授权，不是 Agent 的自作主张。这个入口是 v2.4 加的，在那之前状态机里没有这个门。

### State 3 · 市场兜底

本地没有就去 GitHub 找，找到先过安全审计再装，真找不到就明说，不硬凑。下载落非系统盘。

## 异常降级三步

被调 skill 出错（超时 / API 异常 / 死循环）时按序走。

1. 参数修正重试一次，同 skill 换保守参数。
2. 同级降级一次，换功能相近的备选 skill。
3. 硬终止上报，立即停止，不静默掩盖，回复末尾输出错误与已尝试路径。

**为什么不无限重试**。重试烧的是用户的钱和时间。三次机会用完还不行，说明问题大概率不在参数上，继续撞墙只会更糟。

## 透明性为什么是强制的

调度这东西最怕黑箱。它挑了谁、排除了谁、为什么，你都不知道的话，漏调了你发现不了，误调了你也不知道该骂哪。所以每次调度结束强制输出标准报告块，已调用、引用清点、触发原因、检索路径、异常与降级五项，逐条可核对。引用清点那行要求列出消息内全部指称的归宿，出现「漏检」即为违规。

配套还有调用统计（v2.5 起脚本化）。跑一条命令完成 +1、改日期、降序重排、缺行自动建。用户问「哪些 skill 最常用」，直接读统计文件就能答。哪些 skill 在吃灰，一目了然。

## 跟其他方案的区别

| 常见做法 | 这里的设计 | 差在哪 |
|---|---|---|
| 靠 Agent 自觉调用 | 总开关强制过状态机 | 自觉靠不住，规则靠得住 |
| 全量加载所有 skill 描述 | 指针索引，浅层抉择后按需深读 | 库越大越省，开场成本恒定 |
| 泛指需求靠语义猜 | 中文文件夹名前缀匹配映射表 | 猜错就漏，前缀是一查即中 |
| 一条消息命中一个就完事 | State 0 逐一清点全部指称 | 多指称不再漏 |
| 调用过程不可见 | 强制调度报告 + 调用统计 | 漏调误调都能追责 |
| 中文名和调用键混作一团 | 文件夹中文给人看，name 字段英文给机器 | 两套名字互不干扰 |

## 实战绩

2026 年 7 月起在实际项目使用，库内 skill 上百个。漏检事故催生 State 0，穷举需求催生 State 2-EX，v2.5 把调用统计和维护体检（创建/修改 skill 后必跑 lint_skill.py 体检器）都脚本化了。每个版本对应一次真实使用里暴露的问题。调度器在各宿主放逐字一致副本，本体只在唯一权威库一份，防漂移。

## 什么时候不用

纯打招呼、闲聊、单行知识问答，短路直连，不该触发。库里只有一两个 skill 的话直接说名字更快，总开关是给规模准备的。
