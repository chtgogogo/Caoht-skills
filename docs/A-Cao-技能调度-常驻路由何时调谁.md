# A-Cao-技能调度（useskill v2.4）

> [← 返回总目录](../README.md#skills-index)

skill 的调用全看 Agent 自觉，这里有个绕不开的死结。需要用 skill 的时候，Agent 总觉得自己能力已经够了，不调。你想让它直接按名字调，又记不住库里几十个 skill 的名字。两头堵。

于是有了这个设计：做一个总开关。库里只注册这一个 skill，所有调用请求都过它。Agent 不用记任何别的名字，只管触发它。它内部按固定状态机强制执行检索，该查库就查库，不许凭"我觉得我会"跳过。AI 莫名自信偷懒这条路，被规则堵死了。

装得越多还有第二个问题。很多框架每次对话都要加载全部 skill 的信息，几十个 skill 的描述塞进上下文，token 烧掉一大截。useskill 的处理是指针索引。平时只读一层浅表的映射表做抉择，判断出真正需要的 skill，才去深读那一个的完整内容。按需读取，按需加载，库再大开场成本也是恒定的。

## 状态机怎么走

**State 0，引用清点。** 用户一条消息里可能同时点了好几个 skill，一句显式的，一句泛指的。常见的失败是命中第一个就开跑，后面的泛指直接漏掉。所以这一步强制先把消息里所有指称列成清单，三类，显式路径、点名 name、泛指能力词，逐一写明归宿，一个都不许漏。规则原话：State 1 命中只消费一个显式引用，禁止因已命中而跳过剩余泛指引用的解析。

**State 1，点名直连。** 有明确路径或 name 的直接执行。这一步存在的意义是让最常见的请求走最短的路径。

**State 2，本地检索。** 泛指的说法，比如"按前端设计规范来"，走映射表按中文文件夹名前缀匹配，一查即中。不扫全库，不靠语义瞎猜。

**State 2-EX，穷举模式。** 你说"全面调用""尽可能用"，它就一次 IO 读完整张映射表，沾边的 skill 全挑出来，按任务阶段排序执行。这个入口是用户要出来的，有人就是想把库里相关的都翻一遍，v2.4 之前状态机里没有这个门。

**State 3，市场兜底。** 本地没有就去 GitHub 找，找到先过安全审计再装。真找不到就明说，不硬凑。

## 为什么每次都要交调度报告

调度这东西最怕黑箱。它挑了谁、排除了谁、为什么，你都不知道的话，漏调了你发现不了，误调了你也不知道该骂哪。所以每次调度结束强制输出报告，候选清单、纳入理由、排除理由全在里面，逐条可核对。顺带还统计每个 skill 的调用次数和最近调用，哪些 skill 在吃灰，一目了然。

## 一次真实事故

2026 年 9 月 11 日，前端风格任务。用户消息里点名了一个 skill，末尾又带了句「按前端设计 skill 的理念」。调度器命中点名那个就直接开跑，后半句被当成同一个东西，库里另外三个前端 skill 一个没触发，用户当场发现。

State 0 就是这场事故的直接产物。在那之前，状态机默认一次命中就够了，没人想过一条消息里会有两个指称。

## 跟其他方案的区别

| 常见做法 | 这里的设计 | 差在哪 |
|---|---|---|
| 靠 Agent 自觉调用 | 总开关强制过状态机 | 自觉靠不住，规则靠得住 |
| 全量加载所有 skill 描述 | 指针索引，浅层抉择后按需深读 | 库越大越省，开场成本恒定 |
| 泛指需求靠语义猜 | 中文文件夹名前缀匹配 | 猜错就漏，匹配是一查即中 |
| 调用过程不可见 | 强制调度报告 | 漏调误调都能追责 |
| 中文名和调用键混作一团 | 文件夹中文，name 字段英文，映射表互查 | 两套名字互不干扰 |

## 什么时候用不上

纯打招呼、闲聊、单行知识问答，短路直连，不该触发。库里只有一两个 skill 的话直接说名字更快，总开关是给规模准备的。

## 跑了多久

2026 年 7 月起在实际项目使用，库内 skill 上百个，版本走到 v2.4。漏触发事故和穷举模式都来自真实使用，规则在多个宿主的副本上逐字一致，防漂移。
