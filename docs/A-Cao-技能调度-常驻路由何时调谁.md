# A-Cao-技能调度（useskill v2.4）

> [← 返回总目录](../README.md#skills-index)

给 AI 装了一堆 skill，三个月后回头数一数，真正被调用过的往往只有三四个。剩下的那些从来没派上用场，原因是 AI 根本想不起来它们存在。它挑工具靠印象，哪个名字眼熟用哪个，哪个最近用过用哪个。你库里那个其实更对口的 skill，从装进去那天起就没被检索过一次。

这个 skill 把"该用谁"从凭印象变成走流程。一条固定的状态机，五步。

## 它怎么走

**State 0，引用清点。** v2.3 加的，也是最难加的一步。开工前先把用户这句话里所有 skill 指称列成清单，显式路径、点名 name、泛指能力词三类，逐一写明归宿。为什么要加这一步，后面那场事故会讲。

**State 1，点名直连。** 有明确路径或 name 的，直接读 SKILL.md 执行，不绕路。

**State 2，本地检索。** 泛指词走映射表，按中文文件夹名前缀匹配。用户说"前端设计"，映射表一查就中，成本接近零，不用扫全库。

**State 2-EX，穷举模式。** v2.4 加的。用户说"全面调用""尽可能用"，就全库扫一遍：一次 IO 读完整张映射表，沾边的全挑出来，宁多勿少，再按任务阶段排序执行。

**State 3，市场兜底。** 本地没有就去 GitHub 找，找到先过安全审计再装。真找不到就明说，不硬凑一个敷衍。

每次调度结束输出一份调度报告，候选了哪些、纳入谁、排除了谁、理由是什么，全写在里面，你可以逐条核对它这趟是怎么想的。

## 一场真实的事故

2026 年 9 月 11 日，一个前端风格任务。用户消息里点名了一个 skill，末尾还带了一句「按前端设计 skill 的理念」。

调度器命中点名那个就直接开跑了，后半句被当成了同一个东西。库里另外三个前端 skill 一个都没触发。用户当场发现，质问为什么。

State 0 就是这次事故的直接产物。现在规则里的原话是：State 1 命中只消费一个显式引用，禁止因为已经命中就跳过剩余泛指引用的解析。

一个月后加穷举模式，起因同样是真实使用。有人问能不能把库里相关的 skill 都挑出来，原来的状态机没有这个入口，一句"全面调用"才把它加上了。

## 它解决了哪些别的做法解决不了的

| 场景 | 通常的下场 | 走这套流程之后 |
|---|---|---|
| 一条消息里点名一个 skill 又顺带提了另一个 | 命中第一个就开跑，后半句蒸发 | 清点出全部指称，逐个安排归宿 |
| 泛指的说法，比如"按设计规范来" | 靠语义猜，猜错就漏 | 映射表前缀匹配，中文文件夹名直接命中 |
| 用户想看看库里还有什么能用的 | 没有入口 | 穷举模式全库扫描，按阶段排序 |
| 事后被问"你为什么用了这个" | 答不上来 | 调度报告里候选和排除理由都在 |
| 想知道哪些 skill 在吃灰 | 无从统计 | 调用次数和最近调用一直记着 |

另外说一个工程细节。库里的文件夹用中文说明书名，安装器认的却是英文 name 字段，两套名字对不上是所有 skill 库的通病。这里用双轨制处理，文件夹保持中文好认，name 字段固定英文不改动，映射表负责两边互查。

## 什么时候用不上

纯打招呼、闲聊、单行知识问答，这类任务短路直连，不该触发调度。库里只有一两个 skill 的话，直接说名字更快，流程本身是给规模准备的。

## 用了多久

2026 年 7 月开始在实际项目里跑，到 v2.4 已经三个月，库内 skill 上百个。前面那场漏触发事故和穷举模式的需求都来自真实使用。规则同时维护在多个宿主的副本上，逐字一致，防止改一处忘一处。
