# A-Cao-技能调度（useskill v2.4）

> [← 返回总目录](../README.md#skills-index)

## 一句话

所有 skill 调用的唯一前置调度器。「该用哪个 skill」这个判断，不允许凭印象，必须过一个固定的状态机。

## 它解决什么问题

- **装了一堆，用的时候想不起来。** 库里上百个 skill，被反复调用的永远是熟悉的那几个，其余的等于不存在。
- **凭印象匹配，该用的没上。** 用户说"按前端设计的理念来做"，模型随手挑了个名字最像的，库里真正的三个前端 skill 一个没动。
- **调了什么说不清。** 事后被问"你为什么用这个"，答不上来，也没法复核。
- **名字对不上就卡住。** 库里的文件夹是中文说明书名，调用键是英文 `name` 字段，两边对不上只能靠猜。

## 核心机制

调度分五个状态，逐个往下走。

**State 0 · 引用清点**（v2.3 新增，硬性前置）。先把用户这条消息里所有的 skill 指称列成清单，分成显式路径、点名 name、泛指能力词三类，逐一标注归宿。这一步专门防"快路径惯性"——命中了第一个引用就开跑，把后面的泛指词漏掉。

**State 1 · 点名直连。** 有明确路径或 name 的，直接读 `SKILL.md` 执行。

**State 2 · 本地检索。** 泛指能力词走映射表 `__SKILL详细名映射表.md`，按中文文件夹名前缀匹配。用户说"前端设计"，库里正好有「前端设计指南-美观现代UI规范」，一查即中，成本极低。索引缺失或过时才退化成扫全库的 `name` + `description`。

**State 2-EX · 穷举模式**（v2.4 新增）。用户说"全面调用""尽可能用"，就进全库扫描：读映射表全表（一次 IO 等于浏览整个目录），按关键词逐行比对，相关的全挑出来，宁多勿少，再按任务阶段排序执行。

**State 3 · 市场兜底。** 本地没有就去 GitHub 找，找到先过安全审计再装；找不到就如实说没有，并问用户要不要自建。

调完强制输出调度报告，候选清单、纳入与排除的理由全写进去，用户能逐条复核。

## 一次真实的漏触发事故

2026-09-11，一个前端风格任务。用户的消息里既有明确点名的 skill，也夹着一句「按前端设计 skill 的理念」。

调度器命中了点名那个，就直接开跑了——把「按前端设计 skill 的理念」当成了同一个东西。

结果库内另外三个前端 skill 一个都没触发，用户当场质问。

这次事故直接催生了 State 0。规则里现在的原话是：**State 1 命中只消费一个显式引用，禁止因已命中而跳过对剩余泛指引用的解析。**

一个月后 v2.4 又补了穷举模式，起因是同一个人问"能不能把相关的 skill 都挑出来"——原来的状态机压根没有这个入口。

## 和同类方案比，差在哪

| 常见做法 | 本 skill |
|---|---|
| 模型凭印象挑一个 skill | 固定状态机：清点 → 直连 → 检索 → 兜底 |
| 命中一个引用就开跑 | 一条消息里多个指称逐一清点，禁止快路径惯性 |
| 泛指词靠语义猜 | 映射表按中文文件夹名前缀匹配，一次命中 |
| 调完不吭声 | 强制输出调度报告，含引用清点与排除理由 |
| 调用无记录 | 统计调用次数与最近调用，能回答"哪些 skill 最常用" |
| skill 名与调用键混作一团 | 文件夹用中文说明书名，`name` 字段是稳定不变的英文调用键 |

## 3 分钟上手

1. 把文件夹放进 skills 目录（见[总目录](../README.md#skills-index)）；
2. 说一句"调用 skill""找 skill"即可触发；任务超出自身能力时它也会自动激活；
3. 想让它把全库相关的都翻一遍，说「全面调用 useskill」；
4. 每次调度结束，回复末尾会带一块调度报告。哪条看不懂，直接问。

## 实战绩

2026 年 7 月起在真实项目里跑了三个月，版本从 v1.0 迭代到 v2.4。库内 skill 上百个，调度报告和调用统计一直在用。v2.4 的规则同时维护在多宿主副本上，逐字一致，防止规则漂移。

上面那次漏触发事故、以及后来加穷举模式的诉求，都来自实际使用，不是设计时想出来的。

## 适用 / 不适用

- ✅ 装了多个 skill、需要判断"该调谁"的场合；任务超能力需要外部能力的场合；本地没有得去市场找的场合
- ❌ 纯打招呼、闲聊、单行知识问答——这类任务会短路直连，不触发调度
