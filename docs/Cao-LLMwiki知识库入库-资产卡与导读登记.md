# 知识库存量入库流水线 · 完整详解手册

> **本文件是自包含的**：只读这一份，就能理解整套「往一个多人共写的 Obsidian 库里登记资料」的规矩为什么长这样，不需要再翻别的文件。

> 本页**不描述那个库的实际内容**，只描述流程形状；凡是只能靠现场查才知道的值（上游地址、许可证原文、版本号号位），一律留成占位槽，不替它编数。

## 第 0 章 五分钟速览

1. **它管的是一件很具体的事**：用户指着一个软件、一个仓库、一份资料说「这个也记进库里」，AI 要把它变成库里一条**可被以后检索到的、格式合格的记录**，而且不能弄坏别人正在写的东西。入库＝把资料登记进知识库。
2. **七步管线，顺序不许换**：认库 → 读规矩 → 分流 → 写卡 → 登记 → 追加版本节 → 收尾三连。少任何一步，库就出现「存了但检索不到」或「改了但没人知道」。
3. **规矩不在本支正文里，在库里的三份文件里**。本支正文自己写明：那三份文件是唯一真源（冲突时以库内为准），它只是一副流程骨架；而且要求**当场报告差异**，不许偷偷按骨架硬来。
4. **两道闸门决定收不收**：五不收（五条一票否决的门槛）＋ 三分法（决定内容落到哪个文件的三选一）。
5. **卡片有硬格式**：元数据块里**六行字段必须在场**（体检脚本按行存在性判红，不是按「必填五项」判），首行面包屑导航（页面顶部的返回链接行）必须写，双链（`[[某某页]]` 这种站内链接）只能指向真实存在的页。体检＝只检查不改东西的脚本。
6. **登记是最容易漏的一步**：新卡必须在导读页（库里那张路由表页）并列进组行、补触发词；新建组还要同时改进底部组清单，**只写一处就报黄项**。孤儿卡＝建了卡但没被索引收到的卡片。
7. **这一支最值钱的不是格式，是并发纪律**：五个 AI 同时写同一批文件，所以它反复强调纯插入（只在顶部加新段、绝不改旧段）、号位先现查已提交＋未提交两处、只按自己的路径提交、以及三条「会让检查工具假绿」的尺子失效坑。

一句话设计目标：**让「随手记一个东西进库」变成一条谁跑都长一样、跑坏了当场就能被体检报出来的流水线，同时保证五家共用一个库时互相不踩。**

## 第 1 章 这套系统在解决什么问题

先说清楚场景：这不是「一个人写笔记」，而是**一个本地库被五个 AI 窗口同时当工具箱用**。故障大多来自这个前提。

| 故障 | 表现 | 本流水线的解法 |
|---|---|---|
| **① 写进死库** | 库被换过一次，旧库还在硬盘上当冷备（封存不再维护的备份副本），目录名长得一样；AI 检索到旧路径就写进去，写完没人知道，等于蒸发 | 第 0 步「认库」：活跃库／封存库两张表，并且明写「别只信本文」，要现查提交记录与更新痕迹 [实测] 本支正文「0. 先认库」节 |
| **② 存了但检索不到** | 卡片建好了，导读页那行没加，半年后任何一次检索都找不到它 | 第 4 步「登记」＋体检的孤儿卡黄项 [实测]「4. 登记」节 |
| **③ 卡片形状不一，脚本没法校验** | 有人写五个字段有人写三个，体检只能人肉看 | 六字段行硬格式，缺行直接判红 [实测]「3. 写卡」节 |
| **④ 按常识填事实** | 上游地址、许可证这种「觉得自己知道」的字段最容易错，错了还看起来很规范 | 「事实必须实测，禁止按常识填」；查不到就写「未核实」 [实测]「3. 写卡」节 |
| **⑤ 五家互相吞改动** | AI 甲随手 `git add -A`，把 AI 乙没写完的半截文件一起提交了；或者乙把 CHANGELOG（变更记录文件）整段替换时漏抄了甲那一节 | 只按路径 add、追加式文件的纯插入纪律、替换范围不许圈进邻居段 [实测]「5. CHANGELOG」节＋「6. 收尾三连」节＋「7. 多人共写防线」节 |
| **⑥ 检查工具假绿** | 体检脚本本身跑不起来（或被管道吃掉退出码），报告看起来「一切正常」 | 三条尺子失效坑（中文检索静默零命中／解释器占位 stub／反斜杠路径吞字符）＋ 正例校验（先塞一个已知存在的样本，它没中就判这把尺子作废） [实测]「7. 多人共写防线」节 |
| **⑦ 功劳记错家** | 留痕脚本有个默认宿主标识，漏传参数就把别家 AI 的引用记到默认那家名下，热度榜从此失真 | `--host` 之类必须显式给；且「覆盖宿主」榜只从原始日志解析，禁止手写报告 [实测]「6. 收尾三连」第 1 步 |
| **⑧ 越用越胖、越用越乱** | 什么都能塞，长文一堆、重复一堆、NC 许可（禁止商业使用的许可）的东西被拿去商用 | 五不收门槛 ＋ 冷卡只列不删 ＋ 超大文件体检项 ＋ 硬红线四条 [实测]「2. 分流」节＋「9. 硬红线」节 |

**其中 ⑤ 和 ⑥ 是这一支独有的**：单用户库不会有「邻居段被吞掉」这种事故。所以本支正文用最大篇幅（「7. 多人共写防线」节，6 条 🔴 规则）写这件事——写手册时也不能把它当成脚注略过。

## 第 2 章 术语表

这一支的术语密度高，且大多是**中文行话**，不解释就等于没写。

| 术语 | 一句大白话 |
|---|---|
| **入库** | 把一份资料正式登记进知识库，让它以后能被检索到 |
| **活跃库 / 封存库** | 还在被写、还有提交记录的库／已经停止维护、只准读不准写的旧库 |
| **体检** | 只检查、不修改文件的那个脚本；跑完出一份红黄绿报告 |
| **红项 / 黄项** | 红＝硬性不合格必须改；黄＝可疑但不致命，可以如实说明后放行 |
| **资产卡** | 一个对象（一个软件／一个仓库／一份资料）对应一页卡片，写清它在哪、能干啥、什么许可 |
| **地图行** | 「本机资产地图」里的一行，回答「这台机器上装了什么、在哪」，不单独配卡 |
| **导读页** | 库里的路由表：一张「什么触发词该去看哪几张卡」的总索引 |
| **触发词组** | 按「干什么活」给卡片分组的组；组名就是路由表里那一行 |
| **组清单节** | 导读页底部那份「库里现在一共有哪几个组」的名单，和上面的总索引表必须同步 |
| **孤儿卡** | 卡建了但没进任何索引，检索永远碰不到它 |
| **面包屑** | 页面顶部那行「回首页｜回导读｜回所在分区」的导航行 |
| **双链** | 用 `[[页名]]` 写法在库内互相指；死链＝指的页不存在 |
| **纯插入** | 只在文件顶部加新段落，绝不改动任何旧段落 |
| **号位** | 版本节那一行开头的版本号；五个 AI 同时新增版本节会撞号 |
| **在途改动** | 别人改了但还没提交（git 术语：工作树里的未提交内容） |
| **numstat 对账** | 用 `git diff --numstat` 看每个文件新增了几行、删了几行，用「删除行数」判断自己有没有误伤别人 |
| **正例校验** | 先拿一个已知必然存在的东西去试你的检查命令，它试不出来就说明命令本身废了 |
| **静默失败** | 不报错、退出码也「成功」，但实际什么都没做——最难查的一类 bug |
| **五不收** | 五条一票否决：对不上任何一条「该收」的理由就不入库 |
| **三分法** | 三条落地路径选一条：地图行／资产卡／项目档案 |
| **NC 协议** | Non-Commercial：允许个人学习使用，禁止商用 |
| **FSL-1.1-MIT** | Fair Source 许可的一种：红线是「别拿它做竞争性商业产品」，自用、教学、科研都算可接受 |
| **热度榜** | 从留痕日志解析出来的「哪几张卡真被用过」排名 |
| **冷卡** | 长期零命中且长期没核对的卡，只列成候选，不自动删 |
| **降权归档** | 把冷卡移出主检索路径、挪进归档区；必须用户点头 |
| **宿主地图页** | 「我这台 AI 宿主环境现在是什么状态」的一页，谁的地盘谁更新自己那页 |
| **复核节奏（快／中／慢三档）** | 给检索到的智慧卡定「多久要回来复查一次」 |
| **三验** | 收权威原文前的三次核验：来源、完整性、许可 |
| **留痕** | 把「这次任务实际用了哪几张卡、为什么用」写进日志，给热度榜喂数据 |
| **派生物** | 本体（卡片）之外的下游产物：导读行、组清单行、版本节、宿主地图状态 |

## 第 3 章 结构与分层：一条七步管线，一个真源三层文件

### 3.1 七步总表

本支正文的「Overview（总览）」节把流程压成一行：**认库 → 读规矩 → 分流 → 写卡 → 登记 → 追加版本节 → 收尾三连**。[实测]

| 步 | 干什么 | 判据（怎么算做完） | 跳过的代价 |
|---|---|---|---|
| 0 认库 | 确认写的是活跃库，不是封存库 | 现场查提交记录与文件更新痕迹 | 全部白干（写进没人看的库） |
| 1 读规矩 | 读库内三份真源文件 | 单次检索不超预算（下面 3.3 讲为什么是那个数） | 格式与库内现行规范冲突 |
| 2 分流 | 五不收闸门 ＋ 三分法定落点 | 五不收逐条对上、落点唯一 | 噪音进库／同一件事两张卡打架 |
| 3 写卡 | 按硬格式建卡，事实实测 | 六字段齐、面包屑在、双链实存 | 体检红项 |
| 4 登记 | 导读页两处同步（建组则三处） | 组行并列＋触发词扩＋组清单同步 | 孤儿卡黄项 |
| 5 版本节 | CHANGELOG 顶部倒序纯插入 | 新节在最上方 `## v` 之前，邻居节零改动 | 吞掉他人历史证据 |
| 6 收尾三连 | 留痕 → 体检 → 只提自有路径 | 体检红 0 黄 0（或黄项如实说明） | 功劳记错家／报告文件脏在途 |

### 3.2 真源三层：为什么本支正文敢写「以库内为准」

本支正文把规矩放在库里的三份文件，并声明它们是唯一真源 [实测]「Overview」节末段：

| 层 | 角色（本页不写字面文件名） | 管什么 |
|---|---|---|
| 规则层 | 库根的 agent 规则文件（社区常见约定名 `AGENTS.md`，属通用约定不算库指纹） | 调度法、分工红线、五不收、格式约定、留痕规范、数据安全 |
| 路由层 | 入口区的**导读页** | 触发词组路由表 ＋ 底部组清单节 |
| 形状层 | 入口区模板目录里的**资产卡模板** | 卡片长什么样 |

**为什么这么设计**（本支正文自己给了理由）：库被五个 AI 持续改动，任何把库内文件抄成快照的做法**必然过时** [实测]。
[推演] 反面输入：如果本支正文写死「库里现有 8 个组」，某天有人新建一个组，AI 照正文就会认为「没有这个组，我自己开一个」，于是库里出现两个近义组（比如「代码理解」与「代码认知」各一份），路由表分裂、同组冲突自洽项报黄——这正是它为什么只写「一律现查，别抄快照」这一句，而把组名单留给现场。

### 3.3 判定顺序：先问三件事，再动手

本支正文的顺序不是随便排的，实际是一条**短路判定链**：

```
0. 我写的是活跃库吗？        —— 不是 → 停，改成从封存库捞内容按现行规范重录
1. 库内现行规矩我读到了吗？  —— 没有 → 先读三件套，别凭记忆
2. 五不收有没有一条把它挡掉？—— 挡掉 → 不入库，向用户说明理由
3. 三分法它属于哪一类？      —— 判据是「回答什么问题」，不是「它是什么」
4. 卡片能不能过体检？        —— 六字段/面包屑/双链/日期格式，四项缺一即红
5. 索引同步了吗？            —— 导读组行 + 触发词 +（若建组）组清单
6. 版本节插对位置了吗？      —— 纯插入，删除行数为 0
7. 三连跑完了吗？            —— 留痕（显式宿主）→ 体检 → 只按路径提交
```

[实测] 这条链是把本支正文「0 → 1 → 2 → 3 → 4 → 5 → 6」各节的门槛串起来的读法；链上每一环的原始规则见对应章节（本手册第 4–9 章）。

## 第 4 章 认库与读规矩：两个数——2000 与 2

### 4.1 为什么第 0 步是「认库」而不是「读规矩」

[实测]「0. 先认库」节给的是两张表（一个活跃库、一个 2026-09 封存的冷备库），并且对封存库写了一句很硬的处置规则：**只读；要内容就捞出来、按本库规范重录，绝不回旧库写**。

为什么不能「就地继续用旧库」[推演]：旧库没有体检脚本在跑、没有提交记录在长，写进去的任何东西都不会被校验、不会被别人看到；更糟的是，以后 AI 检索到旧库那张「看起来格式正常」的卡，会把过期的上游地址当真值用。所以「捞出来重录」比「原地续写」多花一次工，但换来的是**每条现存记录都被现行体检摸过**。

[实测] 本支正文还专门不信任自己：「判活跃/封存别只信本文」，要求现查提交记录（最近几条）与变更记录文件的更新痕迹。这是把「文档会过时」这件事写成了动作，而不是一句感叹。

### 4.2 分工红线：什么东西不归本库管

[实测]「0. 先认库」节末与「9. 硬红线」节都写了同一条：**行为记忆（怎么干活、踩过的坑、会话记忆）不进本库**，进各家 agent 自己的记忆 store（一个 agent 一套、互不共享的长期记忆文件区）。本库只存**资料与资产**。

[推演] 混了会怎样：具体输入——AI 把「上次我用 sed 改坏了文件」这条踩坑写进资产卡区。三个月后另一位 AI 查「ffmpeg 怎么用」，检索命中这张踩坑卡，把「禁止 sed 原地改写」当成 ffmpeg 的属性读了。两类东西的**生命周期和读者都不一样**：资料跟着上游变，坑跟着你的工具链变；把它们放进同一张路由表，触发词组必然互相污染。

### 4.3 必读三件套与 2000 token 预算

[实测]「1. 进库必读三份」节给出预算：**单次检索超 2000 token（模型一次能读的文本量单位，粗算 1 个汉字约 1–2 token）就强制停**，并且要**向用户说明「可能有遗漏」**。

**为什么是这个数量级** [推演]：三件套是「每次入库都要重读」的固定成本。不设上限的话，一次「登记一个小工具」可能演变成把整个导读页加十几张卡全读一遍，任务本身还没开始，上下文（模型这一轮能装的东西）已经被吃掉大半；等真正开始写卡，前面读到的规矩已经在上下文边缘被挤掉——表现就是「明明读过还是写错格式」。2000 这个数的定位是「够读三件套＋两张卡，不够读一个组的全部卡」，它用**强制停机**把「无限读」逼成「先动手、不够再补」。

**为什么超了要报告而不是自己砍** [推演]：预算是硬约束，超了就必须有取舍，取舍就可能有漏读；把「可能有遗漏」说出来，是把风险转移给用户判断，而不是让 AI 悄悄降低质量。

### 4.4 三步调度法：查表 → 至少读 2 张 → 没命中才补卡

[实测] 库定的硬规则三拍：

1. **查表找组**：拿用户的说法去导读页路由表匹配触发词组。
2. **命中组内至少读 2 张卡再动手**——本支正文给的理由括注是**同型去偏**（避免把单张卡的个性化写法当成整组的规范）。
3. **没命中才按五不收判断要不要补卡**。

[推演] 只读 1 张卡会出什么事：具体输入——用户说「把某 3D 软件接到 AI 的桥接仓库记一下」。AI 命中「工具接入」组，只读到组里一张老卡，而那张老卡的 `source` 字段当时填的是**下载站链接**（早期习惯）。AI 照抄这个写法，新卡也填了下载站；体检的断链项可能不报（链接是真的），但半年后那张卡的「上游」已经不是上游了。**读第 2 张卡的价值不在多一条信息，在于给你一个「同一字段还有另一种写法」的信号**——两张不一致，AI 就必须去查真源或至少停下来问。

[实测] 本支正文还有一句：「组清单会增会变，一律现查，别抄快照」——和第 3.2 节的「不写死快照」是同一条纪律的两处落点。

## 第 5 章 分流闸门：五不收 ＋ 三分法

### 5.1 五不收：逐条对上才收

[实测]「2. 分流」节列出五条门槛，措辞是「**逐条对上才收**」（也就是每一关都要过，不是命中一条就放行）。

| # | 门槛 | 挡掉什么 | 为什么值得单独一关 |
|---|---|---|---|
| 1 | 与 AI 协作无关不收 | 纯人类兴趣资料（教程收藏、生活笔记） | 这个库的导读页是给 AI 干活用的路由表；无关资料进来会挤占触发词，命中率下降 |
| 2 | 来源核实不了不收 | 转述、截图、来路不明的「据说」 | 卡片有 `source` 字段；核实不了的地址必然变成死链，且没法复查 |
| 3 | NC 协议不商用 | ——见下方 5.2，这条最容易被读反 | 合规闸门，不是收录闸门 |
| 4 | 只存长文不配卡不收 | 把整篇 PDF／长网页扔进库就算完 | 检索走的是导读表，没卡＝没入口；长文进了库也等于没进 |
| 5 | 重复不收 | 已有同对象的卡 | 两张重叠的卡会让同组内的两张「说法不一样」，体检有专门的自洽项 |

### 5.2 第 3 条最容易读反：NC 不是「一律不收」

[实测] 本支正文在第 3 条后面紧跟一个括注，写得很细：**NC＝非商业许可，个人学习可以下载收藏，卡片必须如实标注，并写明「仅个人学习，禁商用、禁入对外交付工程」**。

所以正确读法是：**NC 不挡收录，挡的是「拿它去商用／放进对外交付物」**。
[推演] 读反的代价：AI 如果把这条理解成「NC 一律不收」，它会拒绝登记一大批很有用的学习资料（这类资料常常就是 NC），用户会觉得「这库怎么什么都不让存」；反过来如果理解成「NC 也收，收进来随便用」，那才是真出事——某天这个素材被塞进一个交付出去的项目里。**这条规则的杀伤力全在「如实标注」四个字上**：卡片的 `license` 字段和正文明示，是未来任何一次使用时的唯一防线。

### 5.3 三分法：按「回答什么问题」选落点

[实测]「2. 分流」节的三分法表，判定轴不是「这是什么东西」，而是**「这条内容回答哪个问题」**：

| 回答的问题 | 落点（本页用角色名，不写字面目录名） | 是否配卡 |
|---|---|---|
| 这东西装在哪、能干嘛 | **本机资产地图** | ❌ 只加行，不配卡 |
| AI 干活时该想起哪个仓库／资料 | **资产卡区**，一组一对象一张卡 | ✅ 配卡 |
| 这是用户自己的工程还是外部工具 | **项目档案** | ❌ 不算工具登记 |

[实测] 三分法第三条给了一个**可执行的判据**：`git log` 零提交、或没有上游（没有远程仓库可指回去）＝用户自有工程，不当工具登记。

**为什么地图行不配卡** [推演]：地图回答的是「这台机器上有什么」，天然是清单，条目数量级远大于卡片。如果每个装好的工具都配一张卡，卡区会被上百条「本机路径」淹没，而路由表是按卡组织的——那时触发词组里一半的卡其实只是「装了个软件」，AI 检索到的东西和它的任务无关。典型进地图的例子（本支正文举的类别）：编辑器／引擎类软件、多媒体处理工具、命令行下载器、内网穿透工具、以及各类**缓存重定向目录**（把包管理器缓存从系统盘挪走的那些路径）。

**为什么项目要单立一类** [推演]：用户自己的工程会被 AI 误当「外部工具」登记，然后某天 AI 按工具逻辑建议「拉个上游最新版覆盖它」；工程没上游、没版本号可对齐，这种建议直接致命。项目档案区记录的是「这是他自己做的」，属于**保护性标注**。

### 5.4 命名惯例

[实测] 新卡命名照既成惯例：`组名-对象名.md`（例：某「生产」组的某代码认知工具、某「教程」组的某大模型入门手册）。

**为什么前缀是组名而不是日期或编号** [推演]：双链与体检的断链检查都按文件名找；`组名-` 前缀让「同一组的卡」在文件列表里天然相邻，人肉扫一眼也能看出组内有没有重复——正好服务五不收第 5 条。日期前缀会把同组打散，编号前缀需要额外分配一个「不发号」的机构。

### 5.5 另一类入库：检索智慧与权威原文（字段口径不同！）

[实测]「8. 另一类入库」节处理的是「AI 联网检索到的优秀设计／权威资料／行业数字」。这类**不收进资产卡区，字段口径也不同**：

| 项 | 资产卡（第 6 章） | 智慧卡（本节） |
|---|---|---|
| 元数据键 | group／source／local／license／last_checked／status | title／来源 URL／检索日期／`last_check`／复核条件／`deps` |
| 正文要求 | 用法段能照做＋静默失败坑 | 大白话一句话＋要点＋适用场景＋**反例边界** |
| 复核 | 超 90 天未核对报过期 | 按**快／中／慢三档**定复核节奏 |
| 共同要求 | 实测取证 | 来源核实、NC 如实标注 |

[实测] 注意 `last_checked`（资产卡）与 `last_check`（智慧卡）**拼写不同**——这是「同名不同物」陷阱：把资产卡的字段名抄进智慧卡，那个区的校验逻辑就认不出日期行。
[推演] 具体失效输入：AI 顺手把一张行业数字卡按资产卡格式建了，`group` 填了个资产卡的组名，于是导读页那张组的行里多了一张「不是工具」的卡；下次 AI 按「找工具」路由到它，读到的是一段数字，任务没进展还吃掉了预算。
[实测] **反例边界**（「什么时候不适用」）是必写项，正文给的防的是「一条正确经验被无限外推」。细则现查该分区自己的 README（说明文件）。

[实测] 权威原文另走一个分区（工具书性质），并且**三验**：来源验（只收官方域名，记下确切 URL）、完整验（文件大小与官方发布一致）、许可验（NC 不收），三验记录写进该子目录的 README。
**为什么三验只给原文、不给卡** [推演]：卡是摘要，摘要错了以后能改；原文一旦收进来就是「被当作权威」的物件，来源不官方、字节不完整（截断的 PDF）、许可不允许，任何一条都会让整个分区失去「可以直接引用」的地位。完整验用「大小与官方发布一致」这种**可机械比对**的口径，也正好避开「内容对不对」这种没法判的问题。

## 第 6 章 卡片形状：六字段、面包屑、双链、实测取证

### 6.1 为什么是「六字段行」不是「五必填」

[实测]「3. 写卡：硬格式」节专门加了括号强调：这是**体检脚本的实际校验口径**，不是「五必填」。校验的两层：

- **行存在性**：六行必须在场——组（`group`）、来源（`source`）、本地路径（`local`）、许可（`license`）、核对日期（`last_checked`）、状态（`status`）；少写一行**直接判红**。
- **值非空**：除 `local` 外，其余五项还必须有值。

[实测] 关键豁免：`local` **允许留空值，但字段行不能少**——纯在线的资产写「仅在线」或干脆留空值。

**为什么「留空」比「不写」好** [推演]：体检脚本只能看文本，看不出「意图」。整行缺失时，脚本无法区分两种情况：① 这东西真的没有本地安装（正确），② AI 忘了填（错误）。把 `local` 定义成「行必在、值可空」，就把这两件事分开了：**行在＝我已经考虑过本地路径这个维度**。这个设计对整个库是一致的——同一节还留了一个可以为空的 `superseded_by`（被谁取代）字段，同样是「有这行＝我知道它可能被取代」。

### 6.2 元数据块形状（照抄骨架，值留槽）

[实测] 本支正文「3. 写卡」节给的骨架（本页把值全部换成占位槽，因为真实值必须现场取）：

```yaml
---
type: asset-card
group: <触发词组名>
source: <上游仓库／官方地址，取自 git remote -v 的实测值>
local: <本地路径；纯在线卡写"仅在线"或留空值>
license: <取自 LICENSE 原文首行的实测值；查不到写「未核实」>
status: active
superseded_by:
last_checked: <YYYY-MM-DD，四位年-两位月-两位日>
tags: [资产卡, <触发词组名>]
---
```

[实测] `tags` 有位置约定：第一个＝类型，第二个＝触发词组名。
**为什么 tags 也带组名**（组名重复出现在 `group` 和 `tags` 两处）[推演]：笔记软件里 tag（标签）是「跨页聚合」的入口，`group` 字段只有脚本会读；两处都写，人才点标签时也能凑齐一组卡。代价是两处可能不一致——体检的同组自洽项正好能兜住这种情况。

### 6.3 日期格式：为什么严格到「能不能解析」

[实测] `last_checked` 必须是 `YYYY-MM-DD`，否则体检报「无法解析」红项；超过 **90 天**未核对报「过期」。

**为什么是 90 天** [推演]：这一列的是「我上次确认这条还活着是什么时候」。上游软件的节奏大致是「几周一个小版本、一个季度一个明显变化」。设 30 天：五个 AI 根本刷不动，报告常年一片过期，过期警告就变成噪音，噪音警告等于没有警告。设 365 天：一个仓库一年里可以换维护者、换许可证、删掉 AI 依赖的那个入口，卡片还写着 active。「90 天」是**在「报告仍然可读」和「过期不至于骗人」之间的折中**。
**为什么还要单独管「无法解析」** [推演]：如果脚本对格式宽松的日期直接放行，AI 会写成「2026/3/5」「5 分钟前」「上次查的」，然后过期计算静默失效——这是典型的「不报错但不生效」。

### 6.4 面包屑：逐页扫的第一件事

[实测] 卡片正文首行是面包屑（页面顶部的返回导航行），格式形如：

`> 🏠 [[首页]] ｜ 📖 [[导读页]] ｜ 📁 <所在分区>`

（本支正文里那行写的是库内真实页名与分区字面名；本页只给形状，不复制字面名。）体检**逐页扫**这一行 [实测]。

**为什么要逐页强制一个返回链接** [推演]：这类库的真实使用方式不是「从首页一层层点进来」，而是「检索直接命中一张卡」。命中之后人/AI 是被**空降**到一个孤立页上的；没有顶部那行返回，下一步动作只能靠上下文猜——要么关掉，要么乱点双链。面包屑把「空降」变成「有来路可回」，同时也是给双链死链检查准备一个每页都存在的最小链接集。

### 6.5 双链只能指向真实存在的页

[实测] `[[文件名]]` 只能指向真实存在的文件，体检按**全库 Markdown 页**判死链；拿不准就用只读方式核对目标文件存在。

**为什么明令禁止「靠反复跑体检来试错」** [实测]：本支正文在这条后面直接写了「副作用见 §6」——因为体检会**重写当月体检报告文件**，那文件是被版本控制跟踪的。[推演] 于是「我试一下这个链接对不对」的代价是：报告文件被改一次、git 里多一处未提交内容、下一轮体检又报「有未提交内容」黄项、你还得连它一起提交。试错成本从「一次脚本运行」升级成「污染一处被跟踪产出」。正确做法是用只读手段（列目录、直接读文件）确认目标存在。

### 6.6 事实必须实测：三条差点写错的故事

[实测]「3. 写卡」节要求：上游地址取 `git remote -v`，许可证取 `LICENSE` 文件**原文首行**；查不到就写「未核实」。本支正文还留了三条自曝的记录（本页隐去具体产品名，机制本身不受影响）：

1. **某引擎类工具的发布目录里根本没有 LICENSE 文件**——按常识写「它的许可」就错了，因为那个位置压根没有许可文本。
2. **某下载器类工具的打包版只附带第三方依赖的许可证**——`LICENSE` 文件存在，但那份文本是别的项目的，照着首行抄就等于把别人的许可证抄成它的。
3. **某多媒体处理工具常被按常识写成「GPL」，实测原文是 GPL-3.0**——类别对、具体版本不对，而商用义务恰好写在版本上。

**为什么这三条值得进手册**：第 3 条最阴——AI 写「GPL」时它觉得自己做了实测（确实是 GPL 家族），体检也不会报，但下游要判断「用 GPL-3.0 的东西要承担什么义务」时，一个模糊的类别词直接失效。[推演]「查不到就写未核实」这条恰恰是防线：**「未核实」是一个诚实且可复算的状态，错的常识是一个看起来合格的状态。**

[实测] 同节还要求：许可证的**商用边界要引条款原文写清**，本支正文给的示例是 FSL-1.1-MIT 的红线＝「做成竞争性商业产品或服务」，而自用／教学／科研／服务均可。
**为什么要求引原文**：许可证名字只是个指针，同名不同版本义务不同；把「红线是哪句话」抄进卡片，未来 AI 判断能不能用时不需要再去抓那份文本。

### 6.7 用法段要能照做，且必须单列「静默失败坑」

[实测] 命令、安装方式、产物、参数默认值都取自 README（项目说明文件）的**实测行**；并单列「静默失败坑」——那种**不报错却不生效**的边界。

**为什么「静默失败坑」被点名** [推演]：卡片的其他字段出错，人看一眼能发现（地址不对、许可不对）。静默失败不一样：AI 照卡片敲命令，命令成功了、退出码 0，但实际什么都没发生（参数拼错被忽略、路径不存在被吞、写到了错误的盘）。这种坑**只有踩过的人才知道要写**，因此它的密度正好是这类库最值钱的资产——本支正文原话是「那种不报错却不生效的边界最值钱」。这也和第 7 章「反例边界」、第 10 章「假绿尺子」是同一个世界观：**最危险的不是失败，是不报告的失败。**

## 第 7 章 登记：导读两处同步（本流程最容易漏的一步）

[实测] 本支正文给这一节加了「最容易漏的一步」的标题——这不是谦虚，是这一节真的只有两条动作，但两条都在**另一个文件**里，写完卡之后人的注意力已经离开那儿了。

### 7.1 动作一：总索引表那一行「并列」，不覆盖

[实测] 找到目标组那一行，把新卡并列进「目标」列（用 ＋ 连接），并在「说明」列写清各张卡的口径差异（本支正文给的示例口径：网上选中的／本机已有的／某张专卡）。**同组并列展示，不覆盖旧条目。**

**为什么特别强调「不覆盖」** [推演]：具体输入——组里已有一张「外部同类工具」卡，AI 新建了一张更强的，最省事的编辑就是把目标列改成新卡。这一改的破坏是**不可见的**：旧卡还在库里（体检不报孤儿卡，因为它还被别的地方引用），但从路由表消失了；下次用户问「那个以前用的工具」，检索到的是新卡，旧知识被静默下架。**「并列」而不是「替换」，是因为这类库里「哪张更适合此刻」是情境判断，不该由新建卡的那一刻替未来所有情境做主。**

### 7.2 动作二：触发词列要扩

[实测] 按新卡内容补触发词（本支正文的例子：新增「代码认知／仓库索引／AI 记忆层」这类说法）。
[推演] 只加卡不加词＝这张卡只有靠组里别的卡的词条顺路才被读到；用户下次直接用新卡的说法提问，路由表命中旧卡，AI 读完两张旧卡就动手了——第 4.4 节的「至少读 2 张」在这种情况下反而**浪费了预算去读不该读的**。触发词是入口，不是注释。

### 7.3 动作三（只有建了新组才触发）：两处必须同步

[实测] 新组名必须**同时**进总索引表和底部「触发词组清单」节；只写一处，体检报「导读组清单不同步」黄项。

**为什么要两份组名单**（一张表里已经有组行了，底部还有一份清单）[推演]：两张表服务两种读法——总索引表是「有触发词时去哪找」，底部清单是「库里一共有哪些组、我是不是该新开一个」。第二种读法在「决定要不要建组」这一步用，而那时 AI 手里没有触发词，扫不到索引表的行。两份都保留、并要求同步，本质是**用一次同步成本换两个检索入口**。代价就是这一条黄项专门盯着它。

### 7.4 用卡时发现过期 → 当场修

[实测]「4. 登记」节末：用卡时发现内容过期，**当场修 ＋ 刷 `last_checked` ＋ 提交**，不许「知道错了先记着」。

**为什么禁止「先记着」** [推演]：具体输入——AI 读一张卡发现上游地址已经 404，心里记下「回头修」，继续做正事。「回头」从来不会到：会话结束后这个念头就消失了，而卡片还写着 active，且这次读卡会让热度榜给它记一次命中，**于是它看起来更可靠了**。「当场修」把修正绑在唯一有证据的时刻（你正好读了它、正好知道它错），代价是把一次小改动插进当前任务——所以本支还要求这次改动连着走提交（见第 9 章），否则修了等于没修。

## 第 8 章 追加式文件纪律：CHANGELOG 顶部倒序纯插入

这一章是「五个 AI 共写」这件事最集中的地方，也是本支正文里 🔴 标记最密的一节。

### 8.1 排序方向：新节在上

[实测]「5. CHANGELOG」节：版本节按**时间倒序**排；新节插在标题与格式说明行之后、**当前最上方那个 `## v` 节之前**；文件末尾那句「后续版本按时间倒序追加在上方」的 HTML 注释**不动**。

**为什么倒序** [推演]：正序文件追加在末尾，而末尾是并发写最容易撞车的位置（两个人同时 append，后写的会覆盖或需要重读整个文件）。倒序把写入点搬到**文件开头几行**，编辑动作变成「在第一个版本节前插入」，不需要知道文件多长、也不需要碰尾部。顶部注释行是「人类读者的路标」，动了它就等于改了别人的阅读锚点。

### 8.2 版本节写法：一行标题＋三小节

[实测] 标题写法 `## v<X.Y.Z>（YYYY-MM-DD）<一句话主题>`，正文三小节：**优化了什么／新增了什么／解决了什么问题**——本支正文明确这三小节是「库的铁律格式」，不是建议。

[推演] 为什么固定三问而不是自由发挥：三问正好覆盖「改动类型」的三个不同可验证面——改了旧的（可能影响别人）、加了新的（可能撞号）、修了问题（应能指出原来那个问题）。自由格式时，AI 倾向于写「更新了若干内容」，那种句子三年后读等于没读。

### 8.3 号位先现查，而且查两处

[实测] 🔴「号位先现查再定」（理由写在括号里：五个 AI 同时在写这一个文件）：**已提交记录（HEAD，即最近一次 commit 的内容）与工作树（磁盘上当前实际内容）都要查**，只查已提交的会漏掉别人尚未 commit 的同号节。本支正文给的就是两条命令的形状：

```bash
git -C <库路径> show HEAD:CHANGELOG.md | head -6      # 已提交那一版的最上方几行
grep -n "^## v" <库路径>/CHANGELOG.md | head -6        # 磁盘当前版的所有版本节
```

（路径是占位槽；本页不写真实路径。）

**为什么必须两处都查** [推演]：具体输入——AI 乙改了 CHANGELOG 还没提交，磁盘上已经出现 `## v0.42.0`；AI 甲只查 `show HEAD`，看到的最上方还是 `v0.41.x`，于是甲也定 `v0.42.0`。甲写完提交，乙稍后提交，历史里出现两个 `v0.42.0`——**没有任何工具会报错**，只能靠人读。这就是「号位并发」问题的全部残酷性：冲突是静默的，发现是滞后的，回滚是伤别人的。

[实测] 这条纪律和「谁的地盘谁更新自己那页」（第 9.4 节）是同一族防御：**把并发冲突切成互不相交的所有权，切不开的地方就现场查、双处查。**

### 8.4 编辑手法：整块插入，绝不把邻居圈进替换范围

[实测] 🔴 用编辑工具的「替换」时，把新节**整块插到旧首节之前**，绝不把邻居版本节圈进替换范围。本支正文给的后果判断很硬：要逐字重抄就**必漏抄**＝吞掉他人历史证据，**且零报错**。

[推演] 说清这个失效路径：替换操作的输入是「原文一段 → 新文一段」。如果 AI 把旧首节那一整块也抄进「原文」里（为了让匹配唯一），那它必须在「新文」里把同一块**逐字重写一遍**。在几十个字符的中文标题＋三小节正文里，漏抄一行、改一个标点，工具不会报错——它就以为「原样保留了」。这类事故的特点：**改动越小越安全，改动越"完整"越危险**。正确形状是让替换锚点只落在「标题行与第一个版本节之间」那一条空行上，新旧文本的差别只有你新加的那块。

### 8.5 对账：纯追加类删除列必须为 0

[实测]「7. 多人共写防线」节把对账分成两类判据，不许一刀切要求「删除行为 0」：

| 改动类型 | 判据 | 说明 |
|---|---|---|
| **纯追加类**（版本节新节、地图新行、清单节） | `git diff --numstat` 的**删除列必须为 0** | 只加新段，一行都不该消失 |
| **就地改行类**（导读表某组那一行扩写） | 删除列＝**预期改行数**（改 1 行就是 1/1），并逐条确认邻居组行原样还在 | 因为改写一行必然表现为「删一行＋加一行」 |

**为什么要分两类** [推演]：如果对所有改动都要求「删除 0」，那第 7.2 节的「扩写触发词列」就永远过不了自查——它会诚实地报出 1/1，AI 于是学到「这个判据是噪音」，然后把整个判据废弃，连真正的吞段事故也一起放过。**判据一旦被证明会误报，人就再也不信它了**，所以宁可拆成两条各自精确的规则。

## 第 9 章 收尾三连：留痕 → 体检 → 只提自有路径

[实测]「6. 收尾三连（顺序不能换）」节共 4 步（三连 ＋ push 门闸）。本页只讲接口形状，不写库内脚本的字面文件名。

### 9.1 第一步：留痕

[实测] 留痕脚本接受三类信息：**用了哪几张卡**（卡片清单）、**这次是什么任务场景**（场景）、**是哪个宿主在用**（宿主标识）。其中：

- 🔴 **宿主标识必须显式给**。脚本的默认值是**某一家 AI 的代号**（本页不写那个代号），漏传就把别家 AI 的功劳记到这一家名下，「覆盖宿主」榜永远不出现你家。
- [实测] 「覆盖宿主」榜是从库内**原始使用日志**实际解析出来的，**禁止手写报告**。
- [实测] `--scene` 里必须写「**同组只用其一**」的选择理由（月度体检会抽查）；**浏览未用不计**，只记实质引用／查证／参照。

**为什么「默认值是他家名字」这件事被标 🔴** [推演]：这类默认值是历史遗留（脚本第一家使用者写的），它的危险在于**不会报错**：漏传参数，命令成功、日志写入、热度榜更新，只是署名永远错。而热度榜的用途之一是决定谁是「真在用这个库的人」，署名错掉的那家会在月度体检里被当成「不活跃」，进而影响归档建议——一个参数漏传，经过两级放大变成决策错误。
**为什么禁止手写报告** [推演]：手写「我这次用了 5 张卡」和脚本从日志解析出来的数，两者会分叉；一旦允许手写，任何人可以造出一个好看的榜，整套热度数据的用途（判断哪些卡真的被用、哪些是冷卡）就归零。
**为什么「同组只用其一」要写理由** [推演]：热度的价值在于「哪张卡在这个组里赢得了使用」。不写取舍理由，日志只记了「用了 A」，下一个人看到 A 有热度就用 A，其实那次只是顺手。**同组并列的卡之间，选择理由比选择结果更有信息量**——这也是第 7.1 节「说明列要写清各张卡口径差异」的镜像：登记时写差异，使用时写取舍。

### 9.2 第二步：体检

[实测] 体检脚本两种模式：**不带参数＝无条件出报告**；`--schedule` 是给计划任务（系统定时调用）用的门闸，**手工跑别加**（加了它可能在某些条件下直接跳过，你就拿到一份「没跑」的空报告）。

[实测] 两个副作用要求：① 它会**重写当月体检报告文件**（文件名带年月），那文件被版本控制跟踪，所以跑完要**连着一起提交**，否则下一轮又报「git 有未提交内容」黄项；② **一轮跑一次就够，别反复跑脏它**。

[推演] 「手工别加 `--schedule`」的风险形状：AI 想「稳妥一点，按标准流程带上参数」，脚本的门闸条件（例如「今天已经跑过了」）成立，于是它直接退出、报告没更新、退出码还是 0——AI 读旧报告以为刚跑过。这是**「参数让检查变成空转」**的经典形状，和第 6.7 节的静默失败同源。

### 9.3 第三步：提交与 push 门闸

[实测] 提交前先 `git status --short` 看清在途（别人改了没交的东西），然后**只按路径** add；🔴 **禁 `git add -A`／`git add .`**（会把别人的在途改动一起提交）；commit 信息照既有风格写「版本号＋改动面」。

[实测] 第 4 条单独是门闸：**push（推到远端）先问用户**。本支正文的理由：远端是**五个 AI 共用的门面**，没有明确指令不推。

**为什么 push 要人点头而 commit 不要** [推演]：commit 只进本地历史，出错可以原地补一次提交改掉，影响面是这台机器上这几个窗口；push 一旦出去，另外几家 AI 的本地就出现了「别人已经交的东西」，回滚要协调多方，而且如果那批改动里含不该公开的路径或凭据，撤回窗口极短。**「不可逆程度」决定要不要人确认**——这条也解释了第 9.4 节为什么把「谁更新哪页」切成不相交的所有权。

### 9.4 宿主地图：谁的地盘谁更新自己那页

[实测]「7. 多人共写防线」节最后一条：宿主地图区里每家 AI 有自己的那页，**谁的地盘谁更新自己那页**（内容包括本机的自检时间戳与收尾链的真实状态）；进库发现自己那页缺失或未登记，**当场补**。

**为什么「真实状态」要写在自己页而不是共享页** [推演]：共享文件是并发冲突的全部来源（第 8 章整章都在处理它）；把「高频变动、只有我自己知道」的信息切到私有页，共享页只剩「必须共享」的那部分，冲突面被结构性缩小。这页同时兼任一个作用：别人扫一眼你的页就知道你那侧的体检/提交链是不是通的——**把不可见的状态显式化，省掉跨窗口沟通**。

## 第 10 章 失效与恢复：这一支特有的「假绿」问题

### 10.1 三条尺子失效坑（本支正文用 🔴 标的那三条）

[实测]「7. 多人共写防线」节列了三条本机环境导致的**检查工具静默失效**：

1. **中文关键词传给 shell 里的 `grep` 会静默零命中**。本支正文给的实测形状：六个中文词全报「没有」、退出码 0、无报错；而同一棵目录树用 Python 全库扫却数出了命中。处置：核对中文行是否存在，要么**直接读文件**，要么**写成 `.py` 脚本再跑**；非用 shell 不可时，先塞一个**已知存在**的中文词做正例校验——**正例没中就判这把尺子作废**。
2. **本机跑 Python 只用 `py`，禁用 `python`／`python3`**。原因：后两者指向应用商店的占位 stub（一个假的、只为提示你去商店装真身的可执行文件），零输出＋退出码 **49**，接上管道后退出码被吃掉＝**静默假成功**。
3. **别把 Windows 反斜杠路径写进内联脚本**（`py -c` 或 heredoc 里，`\t` 会被当制表符吞字符、`\202` 被当八进制转义）。处置：路径落成 `.py` 文件再跑，或用正斜杠／`chr(92)`（用代码生成一个反斜杠字符）。

**为什么这三条被放在「共写防线」而不是「环境说明」** [推演]：因为它们破坏的不是单次操作，而是**你对「有没有问题」的判断能力**。第 1 条让你以为「这行没写」，于是你去重复写；第 2 条让你以为脚本跑过了，于是你把体检结论当绿；第 3 条让路径解析到奇怪的位置，于是「文件不存在」的结论是假的。**写坏了能改，判断坏了会一路错到底**——所以它们被归入和「撞车」同级的风险。

### 10.2 第四条：原地改写与丢弃报错绝不同条

[实测] 🔴 **禁裸 `sed -i`（原地改文件的流编辑器）叠 `2>/dev/null`（把报错吞掉的 shell 写法）**；对**不可再生的原始输出**（命令回显、真实调用记录）二次写入前先复制，改完数行数对账。

[推演] 失效输入：`sed -i 's/旧/新/' 某日志 2>/dev/null`。如果那个文件是中文路径、或 sed 表达式在这个平台上不合法，报错被吞进黑洞，文件原样不动，退出码看着像成功。你以为日志已经修好了，继续往下做决策；而那份原始回显恰恰是「唯一副本」——命令回显不会自己再产生一次，写坏了就永久没了。**「绝不不同条」的价值是把「出错时你能看见」变成结构性保证，而不是靠记得。**

### 10.3 改完本体只算改了一半

[实测] 🔴 新卡建完后，**派生物四类**逐类核对：**导读总索引那一行**、**组清单那一行**、**CHANGELOG 那一节**、**自己那页宿主地图状态**——本支正文原话「缺一类就漏一类」。

**为什么要用「四类」而不是「记得都改」** [推演]：四类分布在三个不同文件里，且各有各的触发条件（组清单只在**新建组**时要动）。这类「条件性派生物」正是遗漏高发区：常规情况下有三类要改，偶尔第四类也要改，人的心智模型会稳定地漏掉那个「只有特殊情况才改」的。**把易漏项写成固定四类清单，让漏掉的概率从「注意力」问题变成「勾了没有」问题。**

### 10.4 它怎么坏、怎么发现、发现后怎么退

| 坏法 | 怎么发现 | 怎么退 |
|---|---|---|
| 写进了封存库 | 该库没有新提交、体检报告没动，但本地文件时间戳变了 | 不回旧库写：内容捞出来按现行规范在新库重录 [实测]「0. 先认库」 |
| 卡片有但检索不到 | 体检「孤儿卡」黄项 | 补导读两处（＋若建组的组清单） [实测]「4. 登记」 |
| 邻居版本节被吞 | 纯追加类 numstat 删除列不为 0 | 从上一次提交取回那段，重做**整块插入**；不要试图手工补抄 [实测]「5.」＋「7.」 |
| 号位撞车 | 月度体检／人读到两个同号节 | 后写的那家改号，并在节内一句说明「因号位冲突调整」；绝不删别人的节（推断自「只按路径提交＋删除列为 0」的纪律）[推演] |
| 热度署名错家 | 「覆盖宿主」榜里没有你家 | 之后每次显式传宿主标识；历史错账不改（改了就不是从日志解析的了）[推演，前半 [实测]] |
| 体检报告脏在途 | 下一轮体检报「git 有未提交内容」黄项 | 连报告一起提交；别反复跑体检 [实测]「6. 收尾三连」 |
| 冷卡越积越多 | 体检「冷卡候选」列出来（**只列不删**） | 降权归档**必须用户确认** [实测]「9. 硬红线」 |

## 第 11 章 例行维护与体检项含义

### 11.1 体检项一张表（本支正文列了 14 项）

[实测]「6. 收尾三连」节末行把体检项一次性列出。本页按「它抓什么／为什么要它」逐条讲；行话后面跟大白话。

| 体检项 | 抓什么 | 为什么单列一项 |
|---|---|---|
| 断链 | 双链指向不存在的页 | 死链会让「顺着链接去找证据」的动作直接失败 |
| 垃圾文件 | 临时件、编译产物（如 `__pycache__`、`.pyc` 这类 Python 跑出来的缓存）、编辑器备份 | 它们会被当内容扫，污染检索结果 |
| 面包屑 | 首行导航行缺失 | 空降页无法返回（见 6.4） |
| 孤儿卡 | 卡存在但没被任何索引收到 | 这是「白干」最常见的形状 |
| frontmatter 六字段 | 六行是否在场、除 `local` 外是否有值 | 元数据是脚本唯一能读的东西 |
| 导读组清单同步 | 总索引表与底部清单两处组名是否一致 | 见 7.3，两份名单服务两种读法 |
| 过期卡 | `last_checked` 超 90 天 | 见 6.3 |
| 热度榜与日志健康 | 原始使用日志有没有在写、能不能解析 | 热度榜是归档建议的唯一输入，日志断了就等于体检瞎了 |
| **注入点存活** | 本支正文只列了项名，**未给判定口径（未检索到细节）** | 按名字最可能的读法是「把库内容喂给 AI 的那个入口／索引环节还在不在」[推演]；本页不编造它的算法 |
| 宿主地图时效 | 各家自己那页的自检时间戳是不是太旧 | 见 9.4，把「状态不可见」变可见 |
| 同组冲突自洽 | 同组并列的卡之间说法是否矛盾 | 五不收第 5 条放行过的东西，靠这项兜底 |
| 冷卡候选 | 90 天零命中＋未核对（双条件）的卡 | **只列不删**——见 11.3 |
| 超大文件 | 单文件超 **500 KB** | 见 11.2 |
| git 未提交 | 有改动没进版本库 | 库是五个 AI 的共享状态，未提交＝别人看不到 |

### 11.2 为什么阈值是 500 KB 和 90 天

[推演] 500 KB：这一项限制的不是「重要资料」而是「整份原文塞进卡区」的行为（对应五不收第 4 条：只存长文不配卡不收）。Markdown 纯文本里，一份超 500 KB 的文件基本就是「把书搬进来了」；它会让全库扫描类工具（断链检查、逐页面包屑检查）的时间线性变差，还会被检索误命中，把几百行的正文一次性灌进上下文。阈值故意设得**比绝大多数真卡大一截**，这样正常卡永远不会被误报。
90 天：见 6.3——同一把尺（「多久没被确认」）用在字段值和收录决策两处。

### 11.3 冷卡与「绝不自动删」

[实测]「9. 硬红线」节：**归档区永不删**；冷卡（90 天零命中＋未核对，**两个条件同时**满足）只能列候选，**降权归档必须用户确认**，热度数据绝不自动删东西。

**为什么是双条件** [推演]：只用「零命中」会误杀——某张卡处理的是一年一遇的场景（例如「换机时怎么迁库」），今年一次没被读到不代表它没用。加上「未核对」这个第二条件，把「最近有人看过并确认它有效」当成豁免：只要 `last_checked` 是新的，说明有人为它负责，就不算冷。
**为什么必须人点头** [推演]：降权归档是**改变检索可达性**的操作，一旦归档，未来的 AI 检索不到它，于是它更零命中，于是更该归档——这是一个**自锁回路**（自动执行时它会自己喂自己）。热度数据只能当线索，不能当扳机。

### 11.4 怎么验证这条流水线真在生效（本支没有「装完就生效」的概念）

它不像某些 skill 靠提示词常驻改变行为，它是一条**动作序列**。验证方式全是可查的：

1. **库内痕迹**：新增的卡有没有对应导读行；CHANGELOG 新节是不是在最上方。
2. **git 痕迹**：`git status --short` 收尾后是否只剩别人的在途；`git diff --numstat` 删除列是否符合该改动类型的判据。
3. **体检结论**：红 0 黄 0；黄项要么修掉、要么如实说明（本支正文的快速自检清单第 8 条就是这个口径）[实测]。
4. **署名抽查**：「覆盖宿主」榜里有没有你家——没有，基本就是留痕参数漏传了。
5. **月度抽查**：`--scene` 里的同组取舍理由有没有写（本支正文写明月度体检会抽查这条）[实测]。

[实测] 本支正文末尾是一份 **9 条快速自检清单**（收尾前逐条打勾），本页第 14 章把它并进速查表。

## 第 12 章 端到端走查：一条输入跑完七步

> 🔴 口径要求这一章必须是「具体输入 → 逐步动作 → 产出形状」。
> **诚实交代**：本走查是把本支正文「0–6」各节的规则串起来的**演练**，标记为 [推演]；对象用一个中性代称 `demo-repo`（真实对象名与真实路径属指纹，不进公开页）。凡是只能由实测得到的值（上游地址、许可证字符串、号位、日期），本页一律留成 `<…>` 槽并注明**去哪儿取**——这是纪律要求的写法，不是省略。

**输入（用户原话形状）**：「刚才网上看到的那个把仓库变成 AI 能读的索引的项目，也记进 obs。」

### 步 0 认库

```bash
git -C <活跃库路径> log --oneline -3          # 有近期提交 → 是活跃库
ls -l <活跃库路径>/CHANGELOG.md               # 时间戳新 → 还活着
```
结论 [实测 步 0]：写活跃库。**表现不合格的走法**：跳过这一步，直接按记忆里的路径写——那正是封存库的目录形状。

### 步 1 读规矩（预算 2000）

读三件套：库根 agent 规则文件 → 导读页（找到「代码理解」这一组）→ 资产卡模板。
命中组后**读 2 张卡**：一张「外部同类工具」卡、一张「本地实现」卡。
观察：两张卡的 `license` 写法一张写「MIT」一张写「MIT License (Expat)」→ 说明这一组对许可证字符串没有严格统一；本支正文的「取 LICENSE 原文首行」优先。**这一步就是「至少读 2 张」起作用的地方**——只读一张会让我照抄第一种写法并以为全库如此。

### 步 2 分流

五不收逐条：
- 与 AI 协作有关？✅（它就是把代码喂给 AI 的）
- 来源核实得了？✅（本地已有克隆目录）
- 许可 NC？✅ 不是 NC（下步实测）
- 只存长文不配卡？✅ 要配卡
- 重复？⚠️ 组里那张「外部同类工具」卡是**另一个项目**，不重复 → 继续，但登记时要在说明列写清两者差异。

三分法：回答「AI 干活时该想起哪个仓库」→ **资产卡区**。
命名：`代码理解-demo-repo.md`（组名-对象名）[实测 §2]。

### 步 3 写卡（先取实测值）

```bash
git -C <本地克隆路径> remote -v          # → 填 source
head -1 <本地克隆路径>/LICENSE            # → 填 license（原文首行）
```
取不到就写「未核实」[实测 §3]。产出形状：

```markdown
---
type: asset-card
group: 代码理解
source: <git remote -v 的实测值>
local: <本地克隆路径；纯在线才写"仅在线"或留空>
license: <LICENSE 原文首行；查不到写「未核实」>
status: active
superseded_by:
last_checked: <今天，形如 YYYY-MM-DD>
tags: [资产卡, 代码理解]
---

> 🏠 [[首页]] ｜ 📖 [[导读页]] ｜ 📁 <所在分区>

## 是什么
（一句话大白话）

## 用法（照做可用）
- 安装：`<取自 README 实测行>`
- 运行：`<命令 + 参数默认值>`
- 产物：`<生成什么、落在哪>`

## 静默失败坑
- `<不报错但不生效的边界>`（例：输出目录不存在时不建目录也不提示——**这条必须有，缺它这段等于没写**）
```

自检：六行齐（group／source／local／license／last_checked／status）✅；`local` 若有值不能瞎编路径；面包屑首行 ✅；页内所有 `[[…]]` 目标先用只读方式确认真实存在 ✅（**不靠反复跑体检来试**）。

### 步 4 登记（两处，本例不建组）

导读页总索引「代码理解」那一行：

- 改前形状：`… 目标： [[代码理解-旧卡A]] ＋ [[代码理解-旧卡B]] ｜ 说明：网上选中的／本机已有的`
- 改后形状：`… 目标： [[代码理解-旧卡A]] ＋ [[代码理解-旧卡B]] ＋ [[代码理解-demo-repo]] ｜ 说明：网上选中的／本机已有的／<本例：把仓库索引进内存供 AI 查的那类>`

**旧条目一个都没删**（并列，不覆盖）。触发词列补：`仓库索引／代码认知`（按本例内容）。
本例没新建组 → 底部组清单**不动**（如果动了，反而制造不同步）。
对账（就地改行类）：`git diff --numstat` → 导读页那一行应报 **1/1**，并逐条确认**邻居组的行原样还在** [实测 §7]。

### 步 5 追加版本节

```bash
git -C <库路径> show HEAD:CHANGELOG.md | head -6
grep -n "^## v" <库路径>/CHANGELOG.md | head -6     # 两处都查，号位才敢定
```
号位：若磁盘上已出现 `v<某个号>`（别人没提交），我就往后一号。产出形状：

```markdown
## v<下一个号>（<今天>）新增代码理解组一张仓库索引类资产卡

### 优化了什么
- （本例可写「无」——诚实写无，比编一条改动好）

### 新增了什么
- 资产卡：代码理解-demo-repo（六字段齐、上游与许可实测）

### 解决了什么问题
- 「AI 要读大仓库时缺一张索引类工具的卡」
```
编辑手法：把整块插到**标题/格式说明行之后、当前最上方那个 `## v` 之前**；替换范围**不含任何邻居节**。末尾那条「按时间倒序追加在上方」的注释不动。
对账（纯追加类）：numstat 删除列 **= 0**，否则立刻回查是不是圈进了旧段 [实测 §5/§7]。

### 步 6 收尾三连

1. **留痕**：调留痕脚本，三个参数都给全——卡片清单 `代码理解-demo-repo`、场景「给 AI 读大仓库补索引工具（同组另有两张，选它因为本例对象已在本地克隆，另两张是外部项目）」、**宿主标识必须显式传**（不传会落到默认那家名下）。
2. **体检**：不带参数跑一次（**不加计划任务门闸**）。一轮一次。
3. **提交**：`git status --short` 先看别人的在途 → 只 add 自己的四条路径（新卡、导读页、CHANGELOG、当月体检报告）→ commit 信息照风格「`v<号> 新增代码理解组资产卡`」。**当月报告必须连着提**，否则下轮报未提交黄项 [实测 §6]。
4. **push**：停下，问用户。「远端是几家共用的门面」——不自作推 [实测 §6]。

### 收尾后对照 9 条自检清单

[实测] 本支正文末尾的清单逐条可打勾：① 写的是活跃库 ② 过了五不收且落点对 ③ 六字段齐／日期格式对／面包屑在／双链实存 ④ 许可与上游是实测值，缺的写「未核实」 ⑤ 导读组行并列、触发词已扩、（若建组）清单同步 ⑥ 新节在最上方版本节之前、邻居未动 ⑦ 留痕带了宿主、场景写了取舍 ⑧ 体检红 0 黄 0（或黄项说明）⑨ 只 add 自有路径、未代提交他人、未擅自 push。

## 第 13 章 反模式清单

每条都写清「这样会怎样」，全部来自本支正文某一条规则的负向读法。

1. **把本支正文当成库规矩、照抄进卡片** —— 唯一真源是库内三件套；抄骨架进库等于把一个会过时的快照钉死在卡里。[实测]「Overview」
2. **抄一份组清单进自己的笔记/脚本** —— 组会变，抄的那一刻就开始腐烂；下次照旧清单判断「这个组不存在」而新建一个近义组，路由表分裂。[实测]「1. 进库必读」
3. **命中组后只读 1 张卡就动手** —— 把单张卡的个性化写法当成全组规范（同型去偏失效）。[实测]「1.」
4. **超过 2000 预算继续读** —— 上下文被规矩吃满，写卡时字段照样漏；且用户看不出你读了半天。[实测]「1.」
5. **按常识填 `license`／`source`** —— 三条自曝事故全在这一类；「未核实」是唯一诚实的兜底。[实测]「3.」
6. **`local` 没有值就把整行删掉** —— 六行缺一行直接红；空值表达「已确认无本地」，缺行表达不出任何事。[实测]「3.」
7. **日期写成「上次查的」「2026/3/5」** —— 报「无法解析」，过期计算从此静默失效，卡永远显示有效。[实测]「3.」
8. **靠反复跑体检来验证双链对不对** —— 每次运行都会重写被跟踪的当月报告，你制造了一处未提交改动和一个下一轮黄项。[实测]「3.」＋「6.」
9. **导读组行里把旧条目替换成新卡** —— 旧卡静默下架但文件还在，体检不报；某天用户问起旧工具，检索答不上来。[实测]「4.」
10. **建了新组只改进总索引表** —— 「导读组清单不同步」黄项；下一个 AI 判断「无此组」又建一遍。[实测]「4.」
11. **发现卡片过期，想着「回头再改」** —— 没有回头；而且这次读卡还会给它记一次热度命中，让它看起来更可靠。[实测]「4.」
12. **为了让替换唯一，把邻居版本节也圈进替换范围** —— 逐字重抄必漏抄，吞掉他人历史证据，且**零报错**。这是本支最贵的一条。[实测]「5.」
13. **只查已提交历史就定号位** —— 别人未提交的同号节看不见，历史里出现两个同号版本节。[实测]「5.」
14. **留痕漏传宿主标识** —— 默认值把他家名字写进日志，你家在「覆盖宿主」榜里永远缺席。[实测]「6.」
15. **手工跑体检时带上计划任务门闸参数** —— 门闸可能判定「今天跑过了」直接空转，你读的是旧报告却以为是新结论。[实测]「6.」
16. **`git add -A`／`git add .`** —— 把别人的半成品一起提交，从此那份改动的责任记在你头上。[实测]「6.」
17. **不问就 push** —— 远端是几家共用的门面；含敏感内容的提交一旦推出去，撤回窗口极短。[实测]「6.」
18. **把所有改动都要求「删除行为 0」** —— 就地扩写必然 1/1，判据被证明会误报，于是整个判据被废弃，真事故也一起放过。[实测]「7.」
19. **用 `python`／`python3`、或 `sed -i` 叠 `2>/dev/null`** —— 检查工具变成假绿；不可再生的原始输出被原地写坏。[实测]「7.」
20. **把踩坑/偏好写进本库** —— 分工红线在库根规则文件里；混进资产卡区会污染触发词组，让「找工具」读到「找教训」。[实测]「0.」「9.」
21. **把 NC 素材放进对外交付工程** —— 五不收第 3 条的括注明确要求卡片写「禁商用、禁入对外交付」；标注是唯一的现场防线。[实测]「2.」
22. **依据热度自动删卡／自动归档** —— 冷卡只列候选，降权必须用户确认；自动执行会形成「归档→检索不到→更零命中→更该归档」的自锁回路。[实测]「9.」

## 第 15 章 工程规范、安全规范与本页的匿名化

> 本章的「库 ↔ 仓库」差额是 2026-10-09 上午快照的实测记录；同日下午 17 支本体已按 [CONTRIBUTING.md](../CONTRIBUTING.md) 第一节追平并在仓库侧脱敏。下面的数字原样保留，作为那次追平的历史凭据，不代表当前状态。

### 15.1 命名与字段规范汇总

[实测] 本支正文的命名口径只有一条：`组名-对象名.md`。字段规范见 6.2 的骨架。这里补两条从规则里读出来的隐含约定：

- **可空但必在**：`local`、`superseded_by` 允许空值 —— 「我已经考虑过这个维度」用行的存在来表达。
- **随句可解析**：日期严格 `YYYY-MM-DD`、许可证严格取原文首行。共同原则是**脚本能机械判定**，凡是「人读得懂但脚本判不了」的写法都被拒。

### 15.2 安全规范（凭据与不可逆操作）

[实测]「9. 硬红线」四条：① **密钥／密码／token 绝不写入本库任何文件**；② 归档区永不删；③ 外部仓库克隆区不进版本库；④ 与记忆库分工不混。
本页对应做法：全篇不出现任何凭据形状，需要示例值的地方一律写 `<你的密钥>` 这类占位；不出现远端账号、不出现盘符路径。

### 15.3 冷启动：一家新 AI 第一次进这个库要做什么

本页把各节要求拼成一份**第一天动作表**（每行都有出处，不是发明）：

| 序 | 动作 | 出处 |
|---|---|---|
| 1 | 现查哪个库是活跃的（提交记录＋变更记录更新痕迹） | 「0. 先认库」 |
| 2 | 读三件套；单次检索不超 2000 | 「1. 进库必读」 |
| 3 | 查宿主地图区，**自己那页缺失或未登记就当场补** | 「7. 多人共写防线」末条 |
| 4 | 开工第一件事 `git status --short`，记下别人的在途文件 | 「7.」首条 |
| 5 | 跑一次体检拿**基线**红黄项（一次，不反复跑） | 「6.」第 2 步 |
| 6 | 之后每次入库：宿主标识显式传、只按路径 add、push 先问 | 「6.」 |

[推演] 漏第 3 步的后果：没有自己那页，就没有任何地方写着「这家的收尾链跑没跑通」，别人以为你家在用，其实你家从来没提交过留痕；等热度榜出来，新来的一家被默认「不活跃」，第一次真要归档建议时反而没人给它说话。
