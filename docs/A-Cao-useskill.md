# Skill 调度器 · 完整详解手册

---

## 第 0 章 五分钟速览

1. **它不产出任何东西。** 全库唯一一支「元层调度器」：交付物是别人的 skill 做的，它只回答一个问题——**"这句话该由哪支 skill 来干"**，然后去把那一支读出来。[实测]（SKILL.md 第一节标题句："本 skill 是所有具体 skill 调用的**唯一前置调度器**"）
2. **它管的是"想不起来用"这个病。** 装了 175 支 skill（数法见 3.4），Agent 依然会凭"我觉得我会"直接动手——调度器把"先查有没有现成的 skill"从自觉变成硬流程。
3. **五步状态机**：State 0 引用清点 → State 1 点名直连 → State 2 本地检索 →（授权时）State 2-EX 穷举全库 → State 3 市场兜底。不许跳步。[实测]
4. **一条消息里可能有多个 skill 指称，必须逐一清点归宿。** 命中第一个不许跳过剩下的——这条（State 0）是 2026-09-11 一次真实漏检事故换来的。[实测]
5. **寻址按 `name` 字段（调用键），不按文件夹名。** 文件夹是给人看的中文说明书名。这一条让它天然不满足开放标准里「name 须等于父目录名」那一项（详见 15.1，本支事实，不替全库遮）。[实测]
6. **失败只给两次机会**：换保守参数重试 1 次 → 换同级备选 1 次 → 硬终止上报，禁止静默掩盖。[实测]
7. **每次调度强制留痕**：回复末尾贴「Skill 调度报告」块（5 个字段），并给调用统计表 +1。报告里缺「引用清点」行＝违规。[实测]

**一句话设计目标：让"用哪个 skill"这个决定不再依赖 Agent 记性好不好，而是变成一条有清单、有去向、有回执、可被用户逐条复核的固定流程。**

| 故障 | 表现（用户看到的样子） | 本调度器的解法 | 出处 |
|---|---|---|---|
| **① 装了不用** | 库里明明有前端设计 skill，Agent 直接自己写了一版很 AI 味的样式；用户问"你不是有 skill 吗" | 触发条件写死：任务"超出自身基础能力"就必须先调度，不许自认为会 | SKILL.md 第一节·触发第 3 条 [实测] |

| **③ 只挑一个，覆盖不足** | 用户说"全面调用"，Agent 还是只挑了一支最像的 | **State 2-EX 穷举模式**：读全库映射表逐行比对，相关候选**全部**列出并写进报告 | SKILL.md 第二节·穷举模式；CHANGELOG.md v2.4 条目 [实测] |
| **④ 找不到就装死** | 本地没有对应 skill，Agent 用一句"我没有这个能力"把话题结束，也不说能不能装 | State 3 市场兜底：GitHub 检索 → 问用户要不要下载、下到哪 → 未命中也要如实说"暂无可用 skill"并提议用 `skill-creator` 自建 | SKILL.md 第二节·State 3 [实测] |
| **⑤ 失败被静默吞掉** | 被调 skill 报错，Agent 悄悄回退到"自己随便写一版"，用户以为 skill 生效了 | 三连降级（参数修正 → 同级备选 → 硬终止上报），最后一步**强制**在回复末尾写出错误与已尝试路径 | SKILL.md 第四节 [实测] |
| **⑥ 事后无法复核** | 用户不知道刚才到底用了哪支、为什么排除别的 | 透明性报告块 + 调用统计表：挑了谁、排除了谁、各自归宿，全在明面上 | SKILL.md 第五、六节 [实测] |

## 第 2 章 术语表

| 术语 | 一句大白话 |
|---|---|
| **调度器 / 元层 skill** | 自己不干活、只负责决定"这活交给谁"的一层。像前台，不是技师。 |
| **调用键（`name` 字段）** | skill 的英文 ID，机器用来找它的那个词；跟给人看的中文文件夹名可以不一样。 |
| **权威库 / 库根** | 全部 skill 本体所在的那一个目录。本调度器规定"只有一个"，别处只放副本。 |
| **宿主注册副本** | 各个 AI 宿主自己那个技能目录里的同款文件拷贝，目录名必须等于调用键。 |
| **映射表** | 一张四列表（中文文件夹名 ↔ 调用键 ↔ 标题 ↔ 功能说明），等于全库目录的索引视图；读它一次≈浏览完整库。 |
| **引用清点（State 0）** | 开工前先把用户这句话里提到的所有"某 skill / 某技能"指称列成一张清单，一条条交代去向。 |
| **显式路径 / 点名 name / 泛指能力词** | 指称的三个档次：给了地址 / 给了名字 / 只给了"某个领域的 skill"这种模糊说法。 |
| **快路径惯性** | 找到第一个能用的就收工、不再看剩下的那个惯性。State 0 专门防它。 |
| **穷举模式（State 2-EX）** | 用户说了"全面/尽可能"这类授权语时，把整库扫一遍、相关的全挑，而不是挑一个。 |
| **前缀匹配** | 拿泛指词去撞中文文件夹名的开头（"前端设计"→"前端设计指南-…"），成本极低的第一跳。 |
| **市场兜底（State 3）** | 本地确实没有时，去外部仓库找现成 skill，并问用户要不要装。 |
| **降级** | 首选路走不通时按预定顺序退回次选，不是原地硬试也不是直接放弃。 |
| **同级备选** | 功能相近的另一支 skill——换马不换事。 |
| **硬终止** | 两次补救都失败就停手并如实上报，禁止悄悄改用"自己随便写一版"。 |
| **透明性报告** | 每次调度后附在回复末尾的 5 行留痕块，用户能逐条复核。 |
| **幂等** | 同一件事做两次，结果和做一次一样（这里指：统计表脚本重复跑不会把次数乱加）。 |
| **对账 / 双份一致性** | 把两处应该相同的文件逐字比一遍，看能不能对上。 |
| **判据** | 可执行的判定标准——能被跑出来、能分出通过还是失败的那种标准。 |
| **回链** | docs 页第一行那条"返回总目录"链接；仓库体检脚本靠它判断详解页是否合格。 |
| **常驻** | 每次会话自动加载、不用点名。frontmatter 里 `priority: high` 与描述中的"（常驻）"就是这个意思。 |

## 第 3 章 结构与分层详解：一台调度器的五个零件

正文七个数字小节（一到七）读起来像清单，实际职责是**五层**。分层不是排版，是排优先级：外层决定要不要进来，内层决定进来后怎么走。

### 3.1 分层总表

| 层 | 正文出处 | 职责 | 存在理由（删掉会怎样） |
|---|---|---|---|
| **L1 准入层** | 第一节·触发与短路 | 判断"这次要不要走调度"，以及打招呼类任务直接放行 | 没有它，每句"你好"都要扫一遍库，白烧 token |
| **L2 清点层** | 第二节·State 0 | 把这条消息里的全部 skill 指称拆成清单并分类 | 没有它，多指称消息只会被消费一个（＝v2.3 事故） |
| **L3 寻径层** | 第二节·State 1/2/2-EX/3 | 按"点名→本地→穷举→外部"由近及远找落点 | 没有它，就退回"凭印象猜一支" |
| **L4 容错层** | 第三节·路径解析 ＋ 第四节·异常处理 | 库在哪、找不到怎么办、被调 skill 挂了怎么办 | 没有它，一次失败就变成静默改道或原地死循环 |
| **L5 留痕层** | 第五节·报告 ＋ 第六节·统计 ＋ 第七节·维护 | 事后能被复核、能被度量、能被维护 | 没有它，整套流程无法证伪——你只能信它 |

### 3.2 判定顺序（这是全文最重要的一张流程）

```
消息进来
  │
  ├─ 属于"纯打招呼 / 闲聊 / 单行知识问答 / 简单总结"且不涉及外部工具？
  │        └─ 是 → 短路：直接正常对话，不进状态机
  │
  └─ 否（显式说要用 skill / 任务超出基础能力 / 兜底阈值命中）
         │
         ▼
     State 0  引用清点（每次调度第一步，硬性前置）
         │   拆成：① 显式路径  ② 点名 name  ③ 泛指能力词
         │
         ├─ 清单里有①或② ──► State 1 DIRECT_MATCH
         │       解析路径读目标 SKILL.md 执行
         │       本机缺失 ──────────────────┐
         │                                  │
         ├─ 清单里有③，或名字未知但任务明确 ─► State 2 LOCAL_SEARCH
         │       1) 查映射表，泛指词先撞中文文件夹名前缀
         │       2) 无索引/未命中 → 扫各 SKILL.md 的 name + description 做语义匹配
         │       3) 选中 → 读 SKILL.md 执行
         │       无匹配 ────────────────────┤
         │                                  │
         ├─ 用户说过"全面 / 尽可能" ────────┤
         │       State 2-EX 穷举：读映射表全表逐行比对，相关候选全列
         │                                  ▼
         │                          State 3 MARKET_FETCH
         │                                  外部检索 → 问用户是否下载
         │                          命中 ─► 审计门 ─► 标准安装 ─► 回 State 1
         │                          未命中 ─► 如实告知 + 建议 skill-creator 自建 + 反问需求
         │
         ▼
     执行期出错？ → 第四节三连：保守参数重试1次 → 同级备选1次 → 硬终止上报
         ▼
     收尾：第五节贴调度报告 → 第六节跑 usage_update
```

**注意两条边的形状**：State 1 和 State 2 都往 State 3 汇聚，State 3 命中后又**回跳 State 1**——这是全文唯一一处循环边（外部装完当成本地点名）。[实测]（State 1「本机缺失 → 跳 State 3」、State 2「无匹配 → 跳 State 3」、State 3「命中 → … → 回 State 1」）

### 3.3 各层的"为什么是这一层"

- **L2 为什么必须在 L3 之前，而不是并行？** 因为 State 1 是**短路的**：一旦命中就有活干了，剩余指称再也不会被看第二遍。把清点提到前面，等于在注意力被占用之前先把清单落到纸上。[实测]（State 0「无论后续走哪个 State」）
- **L3 为什么把"读映射表"排在"扫目录"之前？** 一句话：一次 IO 换整库视图。映射表 182 行 / 54,694 字节（实测：`wc` 数全文），一次读入等于把 175 个目录全部浏览过；逐个扫 `SKILL.md` 要开 175 次文件。省的是**开文件的次数**，不是字节数——穷举模式仍然要把这张表整个读进上下文（成本账见 6.4）。
- **L4 为什么单独一层？** 因为"库在哪"是可变的（换机器、换宿主），而"找不到时怎么办"是恒定的。把寻址（第三节）和容错（第四节）分开写，改路径不用改逻辑。[实测]（第七节："调度逻辑升级 → 只改本 SKILL.md"）
- **L5 为什么必须存在？** 元层 skill 有个天然麻烦：**它无法自证被用过**。用户看不到"调用"这个动作，只看得到结果。报告和统计就是为了把不可见的动作变成两笔可对账的账。

### 3.4 本层的三个基数（数法写清，便于复算）

| 数 | 值 | 数法 |
|---|---|---|
| 状态数 | **5**（State 0 / 1 / 2 / 2-EX / 3） | State 0/1/2/3 各是一个 `###` 三级标题（4 个）；2-EX 是正文里带"State 2-EX"字样的粗体小节（1 个） |
| 映射表覆盖行数 | **175** | 以 `| ` 开头的行共 176 行，减去 1 行表头；对照实测「顶层目录中存在 SKILL.md 者共 175 个」→ 当前覆盖率 100%，无缺行、无孤儿行 |
| 统计表数据行 | **52** | 统计文件里以 `| ` + 数字开头的行数（文件共 58 行）；榜首正是 `useskill` 自己 |

> 这三个数**不是**口径基准表里"17 支 Cao skill"的那个分母。全库带 SKILL.md 的目录有顶层口径与含嵌套口径两套数，本页只用上面 175 / 52 / 5 这三个当场可复算的数，不与其他口径混写。

## 第 4 章 State 0 · 引用清点：一条消息里可能有几个 skill？

这是这支 skill 最"有想法"的一节，也是最容易在别处被删掉的一节（因为它不产出、只拖慢第一步）。

### 4.1 指称三分类

| 类别 | 用户话长什么样 | 归宿 |
|---|---|---|
| **① 显式路径** | 「按 `<库根>/某某目录/SKILL.md` 来做」——给了地址 | 直接定位，走 State 1 |
| **② 点名 name** | 「用 impeccable 检查」「按 senior-engineer-playbook 走」——英文调用键或中文文件夹名 | 按第三节解析，走 State 1 |
| **③ 泛指能力词** | 「按前端设计 skill 的理念」「用数据分析的 skill」「Frontendskill」「XX 指南」「用/按/参考 XX 的理念/规范/方法」 | 走 State 2 |

**③ 的判定面被刻意写宽**：正文说"及任何'某领域 + skill'合成词"。这是**宁可误伤也不能漏**的设计——把误判成本放在"多查一次映射表"（极低），而不是放在"漏掉一支"（v2.3 已经付过一次学费）。[实测]

### 4.2 快路径惯性防御（本节的核心机制）

正文原话的约束力在这两句：**State 1 命中只消费一个显式引用**，**禁止因已命中而跳过对剩余泛指引用的解析**。

它把"命中"当成一种**消耗品**：一条点名 = 一次消费额度。额度用完，剩下的指称必须继续走 State 2。不这么做会漏什么——见下面这条真实事故的重演：

> **v2.2 生产事故（2026-09-11，前端风格任务）** [实测]（SKILL.md State 0 段内注记 ＋ CHANGELOG.md v2.3「解决了什么」）
> 用户消息里点了一支 skill，同时泛指了「按前端设计 skill 的理念」。Agent 点名直连成功后，把那句泛指**等同于已经点名的那支**，结果库内三支前端 skill 全部漏触发，被用户质问。

为什么恰好是三支？实测库内"前端"字头目录确实有三个：`前端设计指南-美观现代UI规范`（调用键 `frontend-design`）、`前端开发-写页面组件实现`（`frontend-dev`）、`高品质前端设计-精工UI工具集`（`impeccable`）。泛指词「前端设计」按前缀匹配只会稳命中第一支，另外两支要靠"清单还没清完"这个动作去捞——一旦 Step 0 被跳过，它们就永久沉底。**这就是"不这么做会漏什么"的实物答案：不是漏一支，是漏一整个语义族。**

### 4.3 清点结果去哪儿了

清单不是内部草稿，它被要求**出现在交付物里**：第五节报告块的「引用清点」字段，"消息内全部 skill 指称 → 各自归宿（已调用 / 不适用＋原因）；出现「漏检」即为违规"。[实测]

这条设计把 State 0 从"提示词里的道德要求"变成"可判定的违规"：用户只要数一下报告里列了几条指称、对一下自己原话，就能验。少一条＝违规，不需要读源码就能抓。这是全篇**唯一自带判据的机制**（判据＝可执行、能分出对错的判定标准）。

### 4.4 本节未定义的东西（如实记，不替它圆）

- **未定义"零指称"分支。** State 0 假设消息里有指称。若 L1 的兜底阈值（连续 2 次工具调用失败）触发、而消息里一个 skill 词都没出现，清单就是空的——空清单往下走是 State 2，但正文没写"此时用什么关键词去检索"。**[推演]** 具体出问题的输入：用户只说"你怎么又卡住了"（第 3 轮无实质进展），Agent 手里没有指称、也没有任务关键词，映射表 175 行无从比对 → 实际行为大概率退化成"再试一次刚才的错招"，调度器名义上进来了、等于没进。修法：State 0 应补一条"零指称时从失败的那次工具调用名与参数里反推任务类型"。
- **未定义指称之间的冲突消解。** 一条消息同时点名 A 和泛指 B，且 A、B 功能重叠，没有规定谁先。

## 第 5 章 State 1 & State 2：点名直连与本地检索

### 5.1 State 1 · DIRECT_MATCH（已知名字快路径）

**条件**：清点清单中存在 ① 显式路径 或 ② 点名 name 的引用。
**动作**：按第三节解析路径读目标 `SKILL.md` 执行；本机缺失 → 跳 State 3。

两个要点：

1. **"执行"的含义是读正文，不是"我知道有这个东西"。** 穷举模式那条"每个命中 skill 都要实际读取其 `SKILL.md` 后才允许声称'用了'"对 State 1 同样成立（正文写在 2-EX 第 3 条，但语义上是全局约束）。**[推演]** 不这么写会出什么：用户说"用 frontend-design"，Agent 读不到该文件却凭名字里的"前端设计"直接产出样式，报告照样能写"已调用"——名字成了遮羞布。这条"读了才算用了"把声称钉在一次文件 IO 上，是可验的。
2. **"本机缺失 → 跳 State 3" 与 State 2 的"无匹配 → 跳 State 3" 是同一条边的两个入口。** 换句话说：点名点了个不存在的名字，不会直接问用户，而是**先去市场找**。这是有意的（用户点名的东西很可能就是网上某个公开 skill），但代价是：拼错一个名字（`impecabble`）不会得到"你是不是想说 impeccable"的确认，而是得到一次外部检索。**[推演]** 出问题的输入：「用 impecabble 审一下」→ State 1 缺失 → State 3 GitHub 检索一个拼错的词 → 无命中 → 告知"暂无可用 skill"+ 建议自建。整条链路把一次纯拼写错误升级成了"库里没有这个能力"的错误结论。

### 5.2 State 2 · LOCAL_SEARCH（本地语义检索）

**条件**：清单中有 ③ 泛指能力词，或名字未知但任务类型明确。
**动作三步**，顺序不许换：

| 步 | 做法 | 为什么排在这 |
|---|---|---|
| **1. 索引优先** | 查映射表（中文文件夹名 ↔ name ↔ 功能）。**泛指词先按"中文文件夹名前缀"匹配** | 一次 IO 换全库；正文点明"一查即中，成本极低，禁止跳过" |
| **2. 目录兜底** | 无索引 / 未命中时，扫唯一库下各 `SKILL.md` 的 `name` + `description` 做语义匹配 | 索引会过时，目录不会骗人；但 175 次开文件，所以只当兜底 |
| **3. 选中执行** | 读该 `SKILL.md` 执行；无匹配 → 跳 State 3 | — |

**为什么"前缀匹配"值得单独写进正文？** 因为中文文件夹名本身就是"功能名-副标题"结构（例：`前端设计指南-美观现代UI规范`），用户随口说的领域词几乎总是这段中文的开头。这是一条**用命名规范换来的检索加速**：命名规范（前缀＝功能域）和检索协议（先撞前缀）互为前提。代价也在这里——一旦某个目录改名不带功能域前缀，State 2 第一跳就哑火，只能退到语义匹配。[实测]＋[推演]

**一个被埋没的细节**：权威库根目录同时存在映射表的 `.md` 版和 `.csv` 版（实测：两个文件都在，`.md` 182 行 / 54,694 字节）。正文只指定 `__SKILL详细名映射表.md` 一个真源。`.csv` 是给人看/给工具读的导出物。**[推演]** 出问题的输入：有人改了 `.csv` 没改 `.md`，Agent 按正文只读 `.md` → 用户看到的表格和 Agent 用的表格不一致，双方都以为自己没错。修法：正文补一句"`.csv` 为派生物，不作为检索入口"。

### 5.3 库根怎么定（第三节：唯一库 ＋ 自动发现）

优先级从高到低，实测正文列了 3 条：

1. **环境变量 `WORKBUDDY_SKILLS_PATH`**（非标目录时用它覆盖）——唯一的"可搬迁"口子。
2. **唯一权威库**（正文写成一个具体盘符路径；本页按公开库红线不复述）。
3. **兜底标准路径**：`~/.workbuddy/skills/`、`./skills/`、`~/.codex/skills/`——**注意正文对这条路径的限定非常硬**："仅用于找本调度器自身，不用于找 skill 本体"。

第 3 条这个限定是整节的关键。它承认"调度器可能被任何宿主从任何标准位置加载"，但**禁止**把宿主技能目录当成本体库——否则会出现"用户目录里那 3 支副本被当成全库"的致命降级。**[实测]**（原句照抄含义，路径抽象化）

**核对结果（实地找过，不凭印象）**：`~/.workbuddy/skills/` 存在；`~/.codex/skills/` 在本机**不存在**；`./skills/` 取决于当前工作目录。也就是说三条兜底路径当前只有一条常亮。**[实测]**

**定位本体的两条方法**（第三节后半）：
- 主路：查映射表拿中文文件夹名 → 读 `<库根>/<中文文件夹名>/SKILL.md`
- 兜底：`grep -rl "^name: <调用键>" <库根>`

这条 grep 兜底**是 name ≠ 目录名这件事的救命索**。没有它，按调用键找目录会直接失败（`impeccable` 这个键对应的目录叫 `高品质前端设计-精工UI工具集`）。**[实测]**

### 5.4 副本同步规则（第七节末尾那条注记）

v2.2 定调：**各宿主各放一份逐字一致副本（`useskill` 文件夹），真正的本体只在权威库；不要在别的技能目录里维护第二套。** [实测]

CHANGELOG.md v2.2 记录了这条规则换来的教训：2026-09-09 的一次全库评审把"双份已分叉"列为最高优先级，理由是"**调度器是全局单点……入口坏毒全局**"。一次一条改动要同时改两处、还要删多余目录、改映射表两行，验收标准是"useskill 全库唯一"。[实测]

这一句也解释了**为什么宿主副本的目录名必须等于调用键，而权威库不必**（详见 15.1）。

## 第 6 章 State 2-EX · 穷举模式：用户说"全面"的时候到底发生什么

### 6.1 进入条件：一句"授权语"就够

四条触发词（实测逐条）：「全面调用 useskill」「全面使用 useskill」「尽可能用 useskill」「把相关的 skill 都挑出来」。写清了"**无需其他引用**"——也就是说它可以**跳过 State 0 的清单**直接开扫。[实测]

**为什么要把授权做成"一句话触发"？** 因为宽口径筛选的**责任**在用户。挑 20 支里有 15 支没用，是浪费上下文；用户不背书，Agent 不敢挑。授权语的作用就是把"宁多勿少"的代价正式转移到下指令的人身上——这是一个**权限设计**，不是检索设计。

### 6.2 四条动作

| # | 动作 | 关键约束 |
|---|---|---|
| 1 | **全库浏览** | 读映射表**全表**（一次 IO≈浏览整个目录）。只有表缺失或"明显过时"才退化为真扫各 `SKILL.md` 的 name＋description |
| 2 | **相关性筛选** | 按当前任务关键词**逐行**比对，"把所有相关候选**全部**列出"——宁多勿少（拿不准倾向纳入），**但禁止把明显无关的塞进上下文** |
| 3 | **分阶段使用** | 多支命中按任务阶段排序：**规范/设计 → 实现 → 审查/打磨**。每支都必须真读过 `SKILL.md` 才允许声称"用了" |
| 4 | **透明可见** | 候选清单 ＋ **纳入/排除理由** 全部写进调度报告的「引用清点」行，用户可逐条复核 |

第 3 条那个阶段序是本章最有工程味的一笔：**先规范、再实现、后审查**。它隐含了一个前提——同一个前端任务可能同时命中设计类、实现类、精修类三支 skill；乱序执行会让"审查"发生在"实现"之前，审一个还不存在的东西。有了阶段序，穷举出来的多支 skill 才不是一堆并列的噪音，而是一条流水线。[实测]（原文"规范/设计 → 实现 → 审查/打磨"）

### 6.3 "宁多勿少"和"禁止无关"是同一条规则的两面

这两句并排写在一起，看着自相矛盾，实际是**同一个判断的两个成本端**：
- 漏一支的代价：用户已经明说"全面"，漏了＝违背指令（v2.4 的存在理由就是"覆盖不足"）。
- 多读的代价：每支 skill 的正文回注（＝把内容重新塞回上下文）会挤占后面的推理空间。

正文给的处理办法不是"读全部正文"，而是**用 name＋description 做宽筛（便宜，只在索引上比），只把过关的候选纳入清单**。真正回注正文的仍然只有分阶段排序后那几支。这条隐含的"两级漏斗"是本章最容易被读者看漏的设计。[实测]＋[推演]

### 6.4 穷举模式的账（为什么"读全表"可以接受）

- 映射表全文 **182 行 / 54,694 字节**（实测 `wc`）。中文字符约占 3 字节，粗算 ≈1.8 万字符量级，回注进上下文是一笔**真实但不小**的开销。
- 对照组：逐个开 175 个 `SKILL.md` 取 frontmatter。按每支 frontmatter 约 10–15 行、正文平均 8–20 KB 估，光是"只读头"也要 175 次工具调用——**次数成本远大于字节成本**。
- 结论：读一张表＝1 次 IO 换 175 行视图，**穷举模式的正确姿势**；正文把"才退化为实际扫描"写得非常克制，就是这个原因。[实测]（"它就是全库目录的索引视图，一次 IO 等于浏览整个目录"）

**不做全表、只按关键词查一条会漏什么**：用户说"全面调用 skill 帮我扒一个开源仓库"，关键词直查"仓库"会命中 `Cao-GitHub仓库检索提取-通用提炼有用内容`（调用键见映射表），但**漏掉**同一族的「按特定游戏引擎定制的专用配置版」——它的目录名和调用键里都没有"仓库"以外的可搜线索（CHANGELOG.md 的实战记录里，穷举模式命中的正是这种专用变体，本页按公开库红线不复述其带人名前缀的原文目录名）。这就是全表 vs 关键词查的差别：**全表捞的是"名字里没有你要的词、但干的是你要的事"的那一支。**[实测]（CHANGELOG.md 实战记录条目）＋[推演]

### 6.5 穷举模式没写的三件事

1. **没写上限。** "相关的全挑出来"没有条数天花板。**[推演]** 出问题的输入："全面调用 skill 检查这个小程序"——沾"小程序/检查/代码/审查"的目录一大片，清单可能 15+ 支，每支都要读正文（第 3 条要求），一次调度吃掉整个会话预算。修法：授权语下加"最多 N 支、超出先列名不读正文"。
2. **没写相关性判据。** "按当前任务关键词逐行比对"——关键词从哪来、命中几个算相关，全凭 Agent 感觉。
3. **没写穷举结果是否计入统计。** 第六节说"每次**成功调度**一个 skill 后"更新——穷举列了 8 支、实际执行 3 支，加 3 还是加 8？正文没写。**[推演]** 后果：统计表的"最常用"排名会随解释口径漂移，用户问"哪些 skill 最常用"时给出的答案不可复现。

## 第 7 章 State 3 · 市场兜底，以及一道装错了名字的安全门

### 7.1 正文写的三步

| 步 | 内容 |
|---|---|
| 检索 | "GitHub 检索相关 skill"，**询问用户**是否下载以及下载位置；下载/克隆**一律落非系统盘** |
| 命中 | 提示用户 → 经 `skills-security-check` 审计 → 标准安装 → **回 State 1** |
| 未命中 | 如实告知「暂无可用 skill」，建议可用 `skill-creator` 自建，并向用户提问、协助搭建 |

三条值得停下来的地方：
- **"询问用户"是硬门。** 不是"找到就装"。装第三方 skill＝往本机注入一段会改变 Agent 行为的指令，这条把决定权留在人手里。[实测]
- **"下载一律落非系统盘"** 是全篇唯一的**磁盘安全约束**，写在这而不是写在全库通用规范里——因为只有兜底这一步会真的往磁盘写东西。[实测]
- **未命中不许直接结束**，还要"向用户提问，协助搭建"。这是把"没有"变成"我们一起造一个"，`skill-creator` 是这条支线的出口。

### 7.2 🔴 引用核对：这道审计门在当前库里指向一个不存在的 skill

正文要求外部 skill 安装**前**必须过一个叫 `skills-security-check` 的审计器。我实地核对（四种找法都找了，不凭印象）：

| 找法 | 结果 |
|---|---|
| 顶层目录里找同名目录（含名含 security/安全/审计 的目录逐一目视清点） | **无**任何名为 `skills-security-check` 的目录 |
| 全库 grep frontmatter `^name: skills-security-check` | **零命中**——没有任何一支 skill 的调用键是这个名字 |
| 全库 grep 调用键含 "security" 者 | 唯一命中 `name: security-audit`，而它**不是顶层 skill**，是某支游戏工作室 skill 内部 `references/workflows/` 下的一个嵌套工作流副本，不在调度器的寻址面上 |
| 🔴 反查**谁在引用**这个键（2026-10-09 主控方复跑：Python 遍历全库 329 份 `SKILL.md` 逐份读正文，`grep -r` 会跳嵌套子树且零报错，故换通道） | 命中**两份引用**：本支 State 3，以及 `SkillHub安装审计-装社区skill含安全审查`（调用键 `skillhub-install-audit`）正文里的「加载 `skills-security-check`（若未注册则手动审）」。也就是说这个不存在的键被抄进了第二支 skill，而那一支还留了活口（"若未注册则手动审"），本支没有 |

**结论：`skills-security-check` 是一个悬空引用，且已被两支 skill 共用。**[实测]（State 3 命中步；核对方式为上表四种找法，均实地执行；调用键全库零同名，正文引用两处）

库内**真正**承担"装外部 skill 前先审"职责的两支是：

- `SkillHub安装审计-装社区skill含安全审查`（调用键 `skillhub-install-audit`）：从社区站安装到本机权威库的固定流程，含校验嵌套 SKILL.md、按 P0/P1/P2 扫外联/执行/凭据。
- `技能完整性审计-分类分级评估`（调用键 `skill-integrity-auditor`）：对任何新增/安装/导入/更新/自写的 skill 做强制安全审计（完整性、提示注入、数据外泄、持久化、跨 skill 写入、未声明远程下载、硬编码凭据）。

这条缺陷为什么严重——它不是"名字写错了"这么轻：
1. **它是唯一的安全门。** 外部代码进本机权威库之前，正文只设了这道闸。闸的名字找不到对应闸门，等价于**状态机上写着一道实际不存在的闸门**。
2. **失败模式很坏。** Agent 走到这一步会查不到 `skills-security-check` → 按 State 1「本机缺失 → 跳 State 3」的规则，它会**又回到 State 3 去找这个审计 skill**——一个以"找审计 skill"为动作的循环，而且此时用户的原任务已经被搁置。这是本支状态机里唯一一条**可能自我咬合**的路径。[推演]（具体输入：「有没有人做过 PDF 表格提取的 skill，找个装上」→ State 3 命中外部 skill → 执行审计步 → 找不到 `skills-security-check` → 该缺失本身又触发跳 State 3）
3. **修法很便宜**：把 State 3 那一个词换成 `skill-integrity-auditor`（覆盖范围最贴合"任何新增/安装的 skill 强制审计"），或写成"经库内任一安全审计 skill（`skill-integrity-auditor` / `skillhub-install-audit`，按来源选择）"。名字改动不影响状态机形状，是纯字符串修复——**所以它一直没被发现的概率极高，也最该现在修。**

### 7.3 description 与正文的第二处错位：`find-skills` 是谁的兜底？

frontmatter 的 description 写「本地无匹配转 **find-skills** 市场兜底」，但正文 State 3 的检索动作只写「GitHub 检索相关 skill」，**通篇没有出现 `find-skills`**。实地核对：

- `find-skills` **确实存在**，但它的目录是 `场景技能匹配器-自然语言推合适skill`（又是一个目录名 ≠ 调用键）。
- 它的实际定位不是"市场"，而是**场景驱动＋关键词双模式的技能发现工具**，从官方内置、本地已装、SkillHub、社区站、GitHub 等**六层联合搜索**并推荐、支持一键安装——按它自己 description 的说法，它已经替代了官方原查找器。
- 同库里还有第三台路由器：`技能路由匹配器-…`（一支以人名作调用键的工程任务路由器，人名按红线不复述），职责是"不知道该用哪个 skill 时，按想法→打磨→拆票→实现→审查推荐执行顺序"——**与 useskill 的 State 2 / 2-EX 职责重叠**。

于是有一串实话要摊开：
- **口径错位**：description 把 `find-skills` 说成"市场兜底"，正文的兜底只查 GitHub。`[实测]`
- **映射表是第三个版本**：映射表里 useskill 那一行的功能说明写的是"市场兜底（**无 find-skills 则略过**/GitHub 检索兜底）"——这句话在 SKILL.md 正文里根本不存在。也就是说同一支 skill 的 description 存在**三份措辞不一致的副本**（frontmatter / 映射表 / 仓库副本）。`[实测]`
- **"无则略过"暴露了作者的犹豫**：正文写"转 find-skills"，映射表补"无 find-skills 则略过"——说明这一句从来没有被做成确定的状态转移。`[推演]`（具体输入：在一台没装 `场景技能匹配器` 的机器上，本地无匹配 → 按 description 该转 find-skills → 该 skill 不存在 → 按映射表"略过" → 落到 GitHub 检索。三条路径三种结论，Agent 走哪条取决于它先读到哪份文本。）
- **元层打架**：一支"唯一前置调度器"的兜底里嵌着另外两台路由器（`find-skills` 与那台人名键任务路由器），而正文从未规定谁先谁后。"唯一入口"这个宣称在**外部引用层**上是不成立的——它是唯一入口，但入口后面挂着三台调度器。`[实测]`＋[推演]

## 第 8 章 第四节 · 异常处理与降级：失败只给两次机会

正文对被调 skill 出错（超时 / API 异常 / 死循环）规定了三步，**每步各一次**：

| 序 | 动作 | 次数 | 语义 |
|---|---|---|---|
| 1 | **参数修正重试** | 1 | 同一支 skill，换保守参数（＝往限制更多、更安全的方向调） |
| 2 | **同级降级** | 1 | 换功能相近的备选 skill，**换马不换事** |
| 3 | **硬终止上报** | 1 | 仍失败立即停止，不静默掩盖，回复末尾写出错误与已尝试路径 |

### 8.1 为什么是 2 次补救，不是 1 次、不是 3 次

- **1 次不够**：三类已知错误（超时、API 异常、死循环）里，超时和 API 异常往往一次保守重试就能过；死循环则**重试同一支必然再循环**——所以必须有"换一支"这一档。两档各治一类错误，缺任何一档都会有一类错误无解。`[实测]`（正文列的三类）＋`[推演]`
- **3 次以上有害**：调度器是**元层**，它的一次重试会套在被打 skill 自己的重试外面，形成两层退避相乘。上限 2 次把最坏路径封在"2 次额外尝试 + 1 次上报"，不会滚成长循环。`[推演]`（具体输入：一支需要外网 API 的 skill 在限流中，若无上限，用户会看着 Agent 反复调它直到会话结束。）
- **"保守参数"这四个字是全章最有内容的一处**：它没说"重试"，说的是**把参数往保守方向调再试**。同一条错误，激进参数→保守参数是唯一能改变错误概率的单次动作。`[实测]`

### 8.2 三条都没定义的分支（如实记）

1. **备选 skill 从哪来。** 正文只说"换功能相近备选"，没说从映射表挑、还是从上一次穷举清单挑。`[推演]` 后果：降级目标可能是一支**从未被读过**的 skill，正好踩破"读了才算用了"那条约束。
2. **降级后要不要重新过 State 0。** 换了一支 skill 意味着任务边界变了，但第四节没要求重跑清点。
3. **State 3 自身的失败没有降级。** 第四节只管"被调 skill 出错"。市场检索失败（网络不通、GitHub 不可达、用户拒绝下载）三条路都不覆盖——正文唯一的出口是 State 3"未命中"分支，但"网络挂了"不等于"未命中"。`[推演]` 具体输入：断网状态下说"找个没装过的 skill 装上" → State 3 检索失败 → 无对应错误分支 → Agent 自由发挥，多半谎报"库里和市场上都没有"。

## 第 9 章 第五、六、七节 · 报告、统计、维护：把不可见的动作变成三笔账

元层调度的根本困境是**它没有产出物**。这一章的三个机制，本质是给一台前台装上打卡机。

### 9.1 透明性报告块（第五节，强制）

"每次经本 skill 触发调度后，回复末尾追加标准块"。实测字段 5 个：

| 字段 | 内容要求 | 它能被验证吗 |
|---|---|---|
| **已调用** | skill 名，**无则写 `无`** | 能——对照统计表当天有没有 +1 |
| **引用清点** | 消息内**全部** skill 指称 → 各自归宿（已调用 / 不适用＋原因）；**出现「漏检」即为违规** | ✅ 能——用户数自己原话里几个指称即可 |
| **触发原因** | 三选一：显式指令 / 任务匹配 / 兜底激活 | 能——对着第一节自问 |
| **检索路径** | 引用清点→… / DIRECT_MATCH / LOCAL_SEARCH / MARKET_FETCH | 能——这是状态机的实际轨迹 |
| **异常与降级** | 正常 / 简述降级动作 | 能——对照第八三连 |

两处设计值得点名：
- **"无则 `无`"是强制填空。** 空着不写和写"无"是两件事：前者可能压根没走调度，后者明确宣告"走过了、结论是没有"。`[实测]`
- **「引用清点」行自带判据。** 全篇唯一一处把违规定义写进字段的机制——它把 State 0 从道德要求变成了可抓现行。**[实测]**

### 9.2 调用统计（第六节）：从手改表到一条龙脚本

**流程**：每次**成功调度**一个 skill 后，更新库根的 `__usage_stats.md`。首选跑脚本：

```text
py <库根>/__tools/usage_update.py <被调度的name>
```

脚本一条龙做四件事（实测脚本自述）：**次数 +1、最近调用改今天、按次数降序重排、缺行自动建行**。只有脚本不可用（换机器等）才退回手动三改。[实测]

为什么值得为一张 52 行的小表专门写脚本？正文自己给了理由："统计文件很小，多读一次不费 token"——而真正的理由是**排序**：手动改 +1 之后必须把表重新按次数降序排，这是最容易漏的一步，一漏就永久破坏"最常用的排最上面"这个读取契约。脚本把"改数 + 重排"绑成一个动作，**幂等**（＝重复做结果不变：同一名字跑两次只是次数加二，表仍然降序）。[实测]＋[推演]

三个可核对的实测数字（数法：文件内以 `| ` + 数字开头的行数）：
- 数据行 **52**；文件共 58 行 / 2,240 字节。
- 榜首正是 **`useskill` 自己**（次数最多的一行）。**[实测]** 这件事要如实说：一台调度器把自己的调用记进了"哪些 skill 最常用"的榜首——它当然最常用（每次都要过它），但这意味着用户问"我最常用哪支**干活**的 skill"时，这张表的第一名是无效答案，需要从第 2 行读起。
- 表头自述是「每次调度后 +1 · 宁多勿少」。**"宁多勿少"与正文"每次成功调度"是两种口径**（成功才记 vs 多记），实测两者并存。

**统计的三条已知偏置**（不遮）：
1. **失败不计数** → 一支总失败的 skill 在表上永远"没人用"，而它可能恰恰是最该被修的那支。`[推演]`（具体输入：某外部 skill 每次调用都在 State 3 审计门前失败，统计表零行；用户问"哪些最常用"时它完全隐形。）
2. **State 2 里"读了但没用上"的候选不计数** → 读正文是成本，不产生收益记录。
3. **穷举模式的计数口径未定**（见 6.5 第 3 条）。

### 9.3 维护（第七节）：四个钩子

| 变更 | 要求动作 |
|---|---|
| 新增 / 删除 / 改名 skill | 同步更新库根映射表（**调用键 `name` 字段保持稳定**） |
| 创建 / 修改 skill 后 | **必跑体检器** `py <库根>/__tools/lint_skill.py <skill目录>`，**PASS 才算完工** |
| 分类索引过时 | 改库外的分类索引目录（正文写了具体位置；本页按红线不复述） |
| 调度逻辑升级 | **只改本 SKILL.md** |

体检器实测自述的检查项（读脚本文件头注释得到，不是猜）：

| 项 | 内容 |
|---|---|
| A | `SKILL.md` 存在、frontmatter 完整（`name`/`description` 必备） |
| B | `name` 为 kebab-case（小写连字符式命名）；**宿主注册副本目录名 == name**（宿主发现机制要求） |
| C | `description` 长度 **20~1024**（过短触发差，过长挤占元数据上下文） |
| D | `metadata.version` 存在（缺 → 警告） |
| E | **双份一致性**：带 `--host` 时按映射表配对，逐字 diff 权威本体与宿主副本 |
| F | **映射表覆盖度**（`--all` 时）：库内每支必须在表里有行，缺行判 FAIL；表里指向的目录不存在判警告 |

退出码 0＝全通过，1＝有 FAIL（警告不计）。**这条是第五节之外第二处自带判据的机制**——"PASS 才算完工"把一个流程结束条件变成了能被机器判定真/假的标准（判据）。[实测]

**检查项 B 是理解 15.1 命名问题的钥匙**：体检器只在**宿主注册副本**这一层要求"目录名 == name"，对权威库目录名没有任何要求。也就是说"目录名 ≠ 调用键"在本库不是疏漏，而是**有意维护的双层命名**——库目录用中文说明书名给人看，宿主副本目录用调用键给机器发现。开放标准的合规性只在宿主层兑现。[实测]

`__tools` 实测有 3 个脚本：`lint_skill.py`、`usage_update.py`、`sync_cdrive.py`。前两个被第七/六节引用；**第三个未被本 SKILL.md 引用**（可能是全库通用工具）。[实测]

## 第 10 章 失效与恢复：它怎么坏、怎么发现、发现后怎么退

一支不产出东西的 skill 坏掉时，症状永远不是报错，而是**该发生的调用没发生**。下面按"失效形态 → 怎么被发现 → 怎么退"逐条列。

| # | 失效形态 | 症状 | 怎么发现 | 发现后怎么退 |
|---|---|---|---|---|
| **F1** | **安全门悬空**（State 3 引用的 `skills-security-check` 库内不存在，见 7.2；同一个键还被另一支装外部 skill 的流程引用了一次） | 外部 skill 未经任何审计就被安装；或 Agent 在审计步原地打转 | 走到 State 3 时按调用键 grep 全库，零命中即暴露；再用 Python 全库扫正文反查**有几处在引用**它（实测两处） | 把**两处**那个词都换成真实存在的审计 skill（`skill-integrity-auditor`）。纯字符串修复，不动状态机——只改一处会留下第二道空门 |
| **F2** | **映射表漂移**（新增/改名 skill 没同步表） | State 2 第一跳哑火，只能靠语义匹配捞；穷举模式把新 skill 整个漏掉 | 跑 `lint_skill.py <库根> --all`，F 项缺行直接判 FAIL | 补表行；改名场景要同时确认调用键未变（第七节："调用键保持稳定"） |
| **F3** | **表里陈旧行**（表有行、目录已删） | 按表解析到一个不存在的目录 → State 1 缺失 → 误跳 State 3 去市场找一个本地曾经有过的东西 | lint F 项判警告（不 FAIL，**这是它的弱点：警告不改退出码**） | 删行；或确认该 skill 是被改名而非被删 |
| **F4** | **双份分叉**（宿主副本与权威本体不一致） | 同一个 skill 在不同宿主上行为不同；改一处不生效 | `lint_skill.py <库根> --all --host <宿主技能目录>` 的 E 项逐字 diff | 以权威库为准覆盖副本；副本目录名必须等于调用键（B 项）。这条事故 2026-09-09 真发生过并被列为最高优先级（CHANGELOG.md v2.2 与实战记录） |
| **F5** | **快路径吞掉泛指**（State 0 被跳过） | 用户点了两支，只有一支被用；一切"看起来正常" | 看报告「引用清点」行条目数 vs 原话指称数；少一条即违规 | 退回 State 0 重跑清点；这条已由 v2.3 做成硬性前置，属于"已知病、已上疫苗" |
| **F6** | **库根写死**（第三节第 2 优先级是一个具体盘符路径） | 换机器/换盘符后第 2 条整体失效；而第 3 条兜底路径被明文禁止用于找本体 → **本体全库不可寻址** | 现象是"所有 skill 都找不到"，而不是某一个找不到——这个"全灭特征"是识别 F6 的关键 | 用第 1 优先级：设环境变量 `WORKBUDDY_SKILLS_PATH` 指向真实库根。**这是正文早于第 2 优先级留好的活口**，F6 有官方解，不用改文件 |
| **F7** | **仓库副本的库根已死**（公开仓库那份 SKILL.md 指向一个本机不存在的旧库根，见页眉） | 用户从 GitHub 装了这支，Agent 按第 2 优先级去找一个不存在的目录 | diff 权威库与仓库副本（9 行差异全是路径） | 公开副本的库根**本来就不该写死**——正解是让它只依赖 `WORKBUDDY_SKILLS_PATH` 与宿主相对路径（见 15.5 建议） |
| **F8** | **兜底阈值无计数器**（第一节"连续 2 次工具调用失败 / 某子任务 3 轮无实质进展"没说谁来计数） | 调度器该自动进场时不进场；Agent 自己数，通常数不清 | 观察：明明连续失败多次，回复里始终没有调度报告块 | 只能靠会话内自觉，或改成显式计数落盘（未采纳项，见 15.6） |
| **F9** | **description 与正文分叉**（`find-skills` 只在描述里、`skills-security-check` 只在正文里） | 常驻清单（＝宿主每次会话自动加载的那份短列表）只显示 description，用户读到的承诺与实走的 State 3 不是一回事 | 对照 frontmatter / 映射表行 / 仓库副本三份措辞（实测三份不一致，见 7.3） | 以 frontmatter 为准回写正文，或反过来；**但三处必须收敛成一处** |
| **F10** | **统计表偏置**（只记成功、调度器自计榜首） | 用户按表问"哪个最常用"得到带偏的答案 | 看第一行是不是 `useskill`（实测正是） | 读表时跳过调度器自身行；长期方案是把"成功/失败/仅读取"三态分开记（未采纳项） |

**共同形状**：F1/F2/F3/F4 能被脚本抓到（lint 的 A/B/E/F 项），F5 能被报告抓到（引用清点行），F6/F7/F8/F9/F10 只能靠人看。**这支 skill 的可观测性是分裂的**——有脚本的部分很硬，没脚本的部分（阈值计数、描述一致性、统计偏置）完全靠维护者记得。

## 第 11 章 怎么验证它真在生效（无"体检"概念的 skill 的体检法）

调度器没有"衰减""遗忘"这类可体检对象，它的体检＝**证明流程真的被走过，而不是被跳过**。四层法，从零成本到高成本。

### 11.1 第一层 · 零成本肉眼法：看尾巴

每次调度后回复末尾必须有那块 5 字段报告（第五节）。**判据：该出现而没出现 ＝ 违规**。这是最便宜的检验，不需要跑任何工具。

- 抽查要点：`已调用: 无` 有没有被写成空白；`触发原因` 三选一有没有真的选；`引用清点` 条目数是否等于用户原话里的指称数。
- **一个可复跑的自检实验**：发一条**故意含 2 个指称**的消息——一支点名的库内 skill ＋ 一句「按某某领域 skill 的理念」。若报告里只交代了 1 条归宿，State 0 没生效（＝v2.3 事故复活）。这条实验直接打在核心机制上。[实测]（判据来自第五节字段定义）

### 11.2 第二层 · 一次命令：全库体检

```text
py <库根>/__tools/lint_skill.py <库根> --all
```

A–D 逐支跑、F 项查映射表覆盖度。**实测当前状态**：映射表 175 行、库内顶层含 `SKILL.md` 的目录 175 个（数法见 3.4），两者逐一对上 → 此刻 F 项应无缺行。
加上 `--host <某个宿主的技能目录>` 可把 E 项（双份逐字一致）也跑掉；**F4 这类分叉只有这一层能抓**，肉眼永远看不见。

### 11.3 第三层 · 三张账互相勾稽（勾稽＝两处数字能对上）

| 账 | 位置 | 能对上什么 |
|---|---|---|
| 报告账 | 回复末尾报告块 | 本次声称调用了谁 |
| 统计账 | 库根 `__usage_stats.md` | 该 skill 的「最近调用」日期今天有没有被改 |
| 索引账 | 库根映射表 | 被调用者确实在库里有行、调用键拼写一致 |

三账对不上就有问题：报告说调了、统计没 +1（漏跑脚本，或脚本路径不可用）；统计 +1 了、映射表没行（表滞后，F2）；表里有行但调用键对不上（改名未同步，第七节的"调用键保持稳定"被破坏）。
**这套勾稽是本章的实质内容**——因为调度器不产出物，唯一能证明它工作过的就是这三笔旁证。

### 11.4 第四层 · 静态合规（引用键与副本）

- `name` 是否 kebab-case、宿主副本目录名是否等于 `useskill`（B 项）。
- description 长度：**实测 208 字符**（数法：取出 `description:` 冒号后整行文本，按 Unicode 码点逐个计数，含冒号后那一个前导空格；**把首尾空格 strip 掉是 207**——两种数法差的就是那个空格，都写明，别让读者自己猜哪种算法）。对照 **lint 的 20~1024 门**：通过。**但三个上限值口径不同、不许合一**：开放标准与上传校验用 **1,024**（也是本库体检器自己写的上限）、某宿主的常驻清单截断阈值是 **1,536**、某帮助中心的上传口径是 **200**。208/207 对前两者安全，**对 200 这一口径是超的**（超 7～8 字符）。这是本支一个真实存在的、取决于按哪家口径算的边界问题，如实记。[实测]（2026-10-09 主控方复跑，换 Python 逐码点数法）
- 版本史顺序：**实测倒序但 v2.3 与 v2.4 位置互换**（SKILL.md 版本史小节列序为 v2.5 → v2.3 → v2.4 → v2.2；CHANGELOG.md 是 v2.5 → v2.4 → v2.3 → v2.2 正确）。两者又同日发布于 2026-09-11，**发布次序在正文里已不可考**。这是一条纯排版缺陷，也是"同一信息两份文本"的又一处代价。[实测]

### 11.5 例行节奏建议（正文没有，本页补的，标为推演）

- 每次改 skill：跑 11.2 的单目录体检（第七节已强制）。
- 每周：跑一次 `--all` 查覆盖度与双份一致性（**[推演]** 理由：F2/F4 的成因是"改了一处没改另一处"，与改动频率同频，按周足够；但按会话跑更保险）。
- 每月：抽 1 次 11.1 的双指称自检实验（**[推演]** 理由：State 0 是最容易被模型"忘记"的一环——它不产出、只增加步骤，属于最先被跳过的动作；不主动测就永远不知道它什么时候哑了）。

## 第 12 章 端到端走查（完整示例）

### 12.1 主走查 · 穷举模式 ＋ 多指称并存

**第 0 步 — 用户原话（可照抄）**

**第 1 步 — L1 准入判定**

```

2) 相关性筛选（按任务关键词：落地页 / 样式 / 现代 / 前端 / UI / 审查）：

**第 5 步 — 分阶段排序执行（规范/设计 → 实现 → 审查/打磨）**

```

阶段 B 实现       → frontend-dev         读正文，按其写法改样式文件
阶段 C 审查/打磨  → impeccable           读正文（第 3 步已读），按清单复审
阶段 C′ 待定      → humanizer            仅当落地页有文案才启用，否则撤回清单并记理由

规则：每支都必须真读过 SKILL.md 才允许在报告里声称"用了"
```

**第 6 步 — 收尾留痕（第五节 ＋ 第六节）**

回复末尾贴：

```

- **已调用**: `frontend-design`, `frontend-dev`, `impeccable`

                   排除 海报设计（静态海报，非网页样式）、图表设计（任务无图表）
- **触发原因**: 显式指令（穷举授权）＋任务匹配（样式改动超出基础把握）
- **检索路径**: 引用清点→DIRECT_MATCH(impeccable)→LOCAL_SEARCH/State 2-EX 全表→分阶段执行

### 12.3 支线 B · 市场兜底（State 3）与那道坏掉的门

**第 0 步 — 用户原话（可照抄）**

```

```
State 3
 ├─ GitHub 检索相关 skill
 ├─ 命中 → 提示用户，并问两件事：下不下、下到哪
 │        （硬约束：下载/克隆一律落非系统盘）
 │        → 用户同意
 │        → 「经 skills-security-check 审计」
 │           🔴 实测：该调用键在库内零命中（无同名目录、无同名 name）

 │           两种失败行为：
 │             (a) Agent 查不到 → 跳过审计直接装（安全门形同虚设）
 │             (b) Agent 把"审计 skill 缺失"当成"本机缺失" → 依 State 1 规则

 │        → 若审计真跑通（用替代品）→ 标准安装 → 回 State 1
 └─ 未命中 → 如实告知「暂无可用 skill」

**这条支线的诚实结论**：兜底链路的**两端都是好的**（问用户、落非系统盘、未命中也不装死、还有自建出口），**中间的闸是空的**。这不是设计思路问题，是一个字符串写错了 —— 也正因为它只是一个字符串，它躲过了所有肉眼检查。

## 第 14 章 速查表（Cheat Sheet）

**一句话**：不产出交付物、只决定"这句该谁干"的前台；清单先落纸、路径由近及远、失败两次封顶、事后必留痕。

| 状态 | 触发长相 | 一句话 |
|---|---|---|
| State 0 | 每次必走 | 先把指称拆成 ①路径 ②点名 ③泛指 |

## 第 15 章 工程与安全规范

> 本章的「库 ↔ 仓库」差额是 2026-10-09 上午快照的实测记录；同日下午 17 支本体已按 [CONTRIBUTING.md](../CONTRIBUTING.md) 第一节追平并在仓库侧脱敏。下面的数字原样保留，作为那次追平的历史凭据，不代表当前状态。

### 15.1 命名合规：`name` 与目录名不等——这一支的事实

| 字段 | 实测值 |
|---|---|
| frontmatter `name` | `useskill` |
| 权威库目录名 | `A-Cao-useskill` |
| 仓库 docs 页名 | `A-Cao-useskill.md`（＝目录名，符合本仓库"文件名＝目录名逐字"约定） |
| 是否满足开放标准「`name` 须等于父目录名」 | **不满足**（差一个 `A-Cao-` 前缀） |

**但这条"不合规"要拆成两层说，否则会写错**（实测得到，非辩护）：

1. **本库是有意做双层命名的。** 库目录 = 中文说明书名（给人看，带 `A-`=常驻、`Cao-`=自创的前缀体系）；宿主注册副本目录 = 调用键（给机器发现）。库内第七节与第三节都明文"定位 skill 本体按 `name` 字段，不是文件夹名"——正文自己承认了这层错位，并配了 grep 兜底与映射表两道桥。
2. **本库的体检器只检查宿主层。** `lint_skill.py` B 项写的是"**宿主注册副本目录名 == name**"，对权威库目录名无任何要求。所以"标准合规"在**发布/注册这一层是兑现的**，只在权威库这一层不兑现。
3. **CHANGELOG 里还有一条反向教训**：实测记录显示这个带前缀的目录名**是维护者有意为之**，曾被误当冗余改掉、又改回，并留下"见到 A-/Cao- 前缀先查命名规范，不要当冗余修掉"的告诫。**[实测]**（CHANGELOG.md 勘误条目）

**本页的结论写法**：不写成"它违规了"，也不写成"它没问题"，而写成——**"权威库层不满足该条开放标准，合规性靠宿主副本层兑现；代价是必须有映射表 ＋ grep 兜底两座桥，桥一断（映射表滞后，F2）按目录名寻址的 Agent 就全瞎。"** 全库 17 支带 Cao 前缀的 skill 都有同样的错位，本页只陈述这一支的事实。

### 15.2 字段与 frontmatter 实测

```yaml
name: useskill              # kebab-case，通过 lint B
description: …208 字符…      # 通过 lint C（20~1024）；对 200 字符口径超限
metadata:
  agent_created: true        # 本库自创标记（全库约定，非开放标准字段）
  version: v2.5              # 在 metadata 下，不是顶层 version（lint D 检查的是 metadata.version）
  priority: high             # 常驻 + 高优先：宿主清单里靠前
```

**注意 `priority: high` 的机制含义**：**[推演]** 元层 skill 必须比它调度的对象更容易被看到，否则"前置调度器"这个定位不成立——一旦宿主按优先级裁剪常驻清单，被裁掉的应该是一支干活 skill，不该是入口。所以 `priority: high` 与描述里那句"（常驻）"是同一个决心的两处表达。

### 15.4 冷启动：新机器 / 新仓库第一天要做的六件事

```
1. 建权威库目录，把本 skill 放进去（目录名带不带前缀都行，name 必须是 useskill）
2. 设环境变量 WORKBUDDY_SKILLS_PATH 指向真实库根
   ← 不做这步，第三节第 2 优先级那条写死的盘符路径在新机器上必然指空（F6）
3. 生成映射表（中文文件夹名 ↔ name ↔ 标题 ↔ 功能说明），确认每支有行
   ← 判据：py <库根>/__tools/lint_skill.py <库根> --all 的 F 项
4. 建 __usage_stats.md（表头三列：次数 / skill(name) / 最近调用），首行可以是 useskill 自己
5. 在宿主技能目录放逐字一致副本，副本目录名 = useskill
   ← 判据：lint --all --host <宿主目录> 的 B 项 + E 项
6. 修 State 3 的审计门引用（换成 skill-integrity-auditor）——冷启动是改它最便宜的时刻
```

**冷启动第一天就能验生效**：跑一次 11.1 的双指称自检消息，看报告里有没有两条归宿。
