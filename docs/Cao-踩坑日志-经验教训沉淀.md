# Cao-踩坑日志（pitfall-log v1.3.0）

> [← 返回总目录](../README.md#skills-index)

修过的 bug 会再犯，原因有两层。

第一层是笔记没用。记过，图省事写了"已修复"三个字，修在哪、为什么错、怎么好的，全忘了。第二次撞上，全价重踩。

第二层更阴险，根因会伪装。同一个根因换个症状出现，你认不出它是老熟人。一个真实案例，中文编码这一个根因，在同一个仓库里炸了两次，前后差 12 天。第一次是中文 .ps1 被 GBK 解码成乱码，看起来是"写脚本的坑"。第二次是中文路径传给 git，误删了整个 docs/ 目录，看起来是"git 命令的坑"。症状八竿子打不着，按案例平铺记录，这两条永远看不出是一回事。

v1.3 加根因层，就是冲着第二层来的。

## 根因层是整套设计里最值钱的一步

结构是三层。一份极轻索引 pitfall-log.md，每次会话都读，所以绝不内联完整条目，索引只存指针。roots/ 目录放根因文件，一个根因一个。pitfalls/ 目录放案例文件，一条坑一个，按需加载。

关键在根因层。上面那两条案例提出来之后归成同一个根因，中文跨进程边界上，UTF-8 和 GBK 的编码假设不一致。识别信号提炼成一句话，中文出现在跨进程边界，先怀疑编码，再怀疑逻辑。下次它变成配置文件里的中文再来，你就能认出它。

检索顺序也跟着设计走。先命中根因，拿到通用对策。根因层不够用，再往下翻该根因挂着的具体案例找灵感。多条不相干的案例挂在同一个根因下，规律自己就显出来了，这是平铺时间线永远做不到的。

## 索引不会变成新的怪物

踩坑日志最容易死的方式，是变成第二个越写越肥的记忆文件。这里的防线是索引有界，超过约五十条，冷条目归档到 pitfalls/archive/，索引里只留一个指针。索引每次会话都读，所以它必须永远保持极短，这条纪律是整个结构省 token 的关键。

案例文件还有一节强制写的，「能否借鉴」。上下文、根因、解法都只解决这一次，只有这一节把一次性修复变成可迁移的经验。贴一段真记录的收尾，某次清理差点删掉被硬编码依赖的工具：

> 判定能不能删的顺序应当是，一查有没有被引用，grep 全项目。二查能不能重建，缓存和生成物通常可以，唯一副本不行。三查是不是真的过时，对比时间戳和内容，而不是看名字。涉及删除时优先隔离到待确认目录，同盘移动瞬时且完全可逆。

## 命中计数，防止日志变成自我感动

记了一堆坑，哪些真救过场？没度量之前，答案是不知道。记录的人觉得有用，可它从来没被翻出来过呢。

所以 v1.2 加了命中计数，而且判定定得刻意的严。真检索了，真翻看了，真从中获益了，问题真解决了，四个条件同时成立才加一。事后发现两条坑同根因，不算。宁可少记不要虚高，虚高的数字等于没有数字。

计数还是一座桥。某条案例命中三次以上，或者某个根因下案例攒够三条，自动升华进记忆 CORE 的铁律区，之后每次会话强制加载。哪类问题值得升级成规则，让数据自己说话。

计数上线时的数字是 0。这个 0 没什么好遮的，它恰恰说明在这之前，日志里没有任何一条被证明过有用。

## 边界划清的两个原因

只管沉淀查阅，bug 的即时诊断走诊断流程，不管。原始记录在这里，跨 agent 共享，不评分不衰减，反复出现升华成铁律的才进记忆 CORE。这两个边界是 v1.1 补的，因为实际出现过同一个坑记两遍、该诊断的活被记成流水账。

## 目前的家底

9 条案例收在 6 个根因下。RT-001 中文编码，RT-002 依赖隐式上下文，RT-003 静默失败，RT-004 凭外观归类，RT-005 绕过工具机制手工干预，RT-006 环境拦截误判为代码缺陷。三个模板在 assets/ 里，复制过去改改 frontmatter 就能起一套自己的日志。
