# Cao-踩坑日志（pitfall-log v1.3.0）

> [← 返回总目录](../README.md#skills-index)

## 一句话

一套省 token 的踩坑沉淀法。教训不进"越写越大的那个文件"，而是极轻索引常驻上下文、每条坑拆成独立文件按需加载。

## 它解决什么问题

- **教训全塞一个文件。** 攒到几十条，每次会话开头都得整份读一遍，没踩坑的对话也在付这个 token 成本。
- **踩过的坑找不回来。** 记得"之前好像遇到过"，但想不起关键词，翻不出来，只能重踩一遍。
- **只记了"怎么修的"，没记"为什么"。** 换个场景，同一个根因换个样子再来一遍。
- **多个 agent 各记一份。** 甲踩的坑乙不知道，重复交学费。

## 核心机制

**结构是三样东西。** 一份 `pitfall-log.md` 索引，加两层明细：`roots/` 放**根因**（一个根因一个文件）、`pitfalls/` 放**案例**（一条坑一个文件）。

**索引保持极短。** 分两张表——先把**根因索引表**摆在最上面，下面是按根因分组的案例清单。索引每次会话都读，所以绝不内联完整条目，这是它随体量增长仍然省 token 的关键。

**根因文件四节。** 一句话根因、**识别信号**、通用对策、挂载案例。

**案例文件五节。** 上下文、为什么（根因）、解法、**能否借鉴（通用规律）**、来源。

「能否借鉴」仍是整套东西里最值钱的部分。前四节只解决"这一次"，只有它把一次性修复变成可迁移的经验。

## 为什么把根因单独拎出来

**从坑里能捞出的最大价值，不是"这次怎么修的"，而是"为什么会踩、下次怎么一眼认出来"。**

同一类问题会在毫不相干的场景反复出现。看这个真实例子——**中文编码**这一个根因，在同一个仓库里炸了两次：

| 日期 | 症状 | 表面看像什么 |
|---|---|---|
| 2026-09-03 | 中文 `.ps1` 被 GBK 解码成乱码，引号被吞、语法崩溃 | 像是"写脚本"的坑 |
| 2026-09-15 | 中文路径传给 git，误删了整个 `docs/` 目录 | 像是"git 命令"的坑 |

一个出在脚本文件里，一个出在命令行参数里，症状毫不相干。但根因是同一个：**中文跨进程 / 跨工具时，UTF-8 与 GBK 的编码假设不一致**。

如果只按案例平铺时间线，这两条永远看不出关系——下次换成"配置文件里的中文"，照样还得再踩一次。有了根因层，它们的识别信号被提炼成一句话：**中文出现在跨进程边界上，先怀疑编码，再怀疑逻辑**。

所以这套结构是：**根因是一级公民，案例挂在它下面**。检索时先命中根因、拿到通用对策；根因层不够，再往下翻具体案例找灵感。

**索引有界。** 超过约 50 条，冷条目归档到 `pitfalls/archive/`，索引里只留一个指针。索引本身不会长成新的巨型文件。

**边界划清楚。** 这个 skill 只管"沉淀和查阅"。真正的 bug 诊断流程交给专门做诊断的 skill，避免职责重叠。跟记忆系统里的 PITFALL 层也有分工：原始记录在这里（跨 agent 共享、不评分不衰减），反复出现、升华成铁律的才进记忆 CORE。

## 一条真实的坑长什么样

下面这条就躺在日志里（`pitfalls/2026-09-03-删目录前先验证硬编码引用.md`），节名与结构如下（末尾还有「来源」「命中记录」两节，此处略）：

```
# 坑：清理「看起来像缓存」的目录前没验证引用，差点删掉被硬编码依赖的工具

## 上下文
整理 DeepSeek-work 工作区时，把 _tools/pnpm/（21M）归类为「本地缓存副本」，
准备连同另外 4 项（合计 683M）一起隔离清理。

## 为什么（根因）
它长得像缓存：不过是某个目录里 npm 装出来的一份 pnpm 副本。
但它实际被两个插件安装脚本硬编码引用：
  install-dsh-better-sidebar.ps1:6   $pnpmDir = 'D:\...\_tools\pnpm\node_modules\.bin'
误判的根源是按外观归类，而不是按引用关系判断——「像缓存」不等于「没有用」。

## 解法
删除或移动任何目录前，先全项目 grep 该路径名：
  grep -rn "_tools\|<目录名>" --include=*.ps1 --include=*.json --include=*.md .
本次靠这一步保住了 _tools；其余 4 项确认无引用后才隔离，安全腾出 662M。

## 能否借鉴（通用规律）
判定「能不能删」的顺序应当是：
1. 有没有被引用（grep 全项目，含脚本、配置、文档）
2. 能不能重建（缓存、生成物通常可以；唯一副本不行）
3. 是不是真的过时（对比时间戳与内容完整性，而不是看名字）
另外，涉及删除时优先隔离到 _待确认删除/ 而不是直接删——同盘移动瞬时且完全可逆。
```

最后那段"能否借鉴"才是这条记录真正的价值。下次做任何清理，第一步就会先问"引用查了没有"。

## 现在日志里记了什么

截至 2026-09-15，**8 条案例收在 6 个根因下**——根因就是检索入口：

| 根因 | 一句话 | 挂着的案例 |
|---|---|---|
| **RT-001** | 中文出现在跨进程 / 跨工具边界 → 先怀疑编码 | 中文 .ps1 被 GBK 解码；中文路径让 git 误删整个 `docs/` |
| **RT-002** | 依赖隐式上下文（cwd / 工作目录 / 会话状态） | `node -e` 从 cwd 找依赖；重命名根目录后 PTY 会话起不来 |
| **RT-003** | 静默失败——失败与成功长得一模一样 | `$pid` 是只读自动变量，赋值静默失败 |
| **RT-004** | 凭外观 / 直觉归类判断，而不是查引用、查证据 | 「长得像缓存」不等于没用，删目录前先 grep |
| **RT-005** | 绕过工具自身机制，手工干预 | 手写修 pnpm junction，3053 个链接全删光 |
| **RT-006** | 把环境 / 策略层的拦截误判为代码缺陷 | 本环境跑 pnpm install 必被拦截，重试无用 |

注意 **RT-001 和 RT-002 各挂着两条案例**——这正是根因层的作用：**两条案例单看毫不相干，归到同一根因下才显出规律**。

## 命中计数：哪条真的救过场

**截至目前，真正被检索命中并解决过问题的：0 条。**

这个"0"恰好说明了为什么要加计数——在此之前，"这条坑到底有没有用"是没法度量的：记录者觉得写了有用，但用没用上、用了几次，谁也说不清；想判断哪条够格升华成铁律，只能凭感觉。

v1.3.0 的规则定得很严，**四个条件同时成立**才算：

1. 真的**发生了检索**——去读了索引；
2. 真的**翻看了具体记录**——至少读了对应的根因文件或案例文件；
3. 从记录里**获得了启发**，并用它解决了当前问题；
4. 问题**真的解决了**。

**明确排除：事后发现"这两个坑同根因"不算命中。** 没有检索、没有翻看、没有从中获益，只是事后归类而已——**同根因 ≠ 命中**。

只扫到没用上、或最后没解决，都不算。**宁可少记，不要虚高**——虚高的数字等于没有数字。

计数落在两处：索引的 `🔥N` 给人一眼看，文件 frontmatter 的 `hits` 是权威值，文末 `## 命中记录` 留明细（哪次、什么场景、解决了什么）。**两层各自独立计数**：只走根因层 → 根因 +1；深读案例获益 → 案例 +1。

**升华触发（满足任一）**：某条案例 hits ≥3，或某个根因下案例数 ≥3 → 标 `⭐` 并同步进记忆 CORE 铁律区，此后每次会话强制加载。

这就是"记了一堆"和"沉淀成规则"之间那座桥：让数据自己说出**哪类问题值得升级**，而不是靠人拍脑袋。

## 和同类方案比，差在哪

| 常见做法 | 本 skill |
|---|---|
| 教训内联在一个文件 | 索引常驻 + 每条坑独立文件，按需加载 |
| 索引跟着条目一起膨胀 | 索引有界，超量归档到 archive/ |
| 只记症状和修法 | 强制写"根因"与"能否借鉴" |
| 各 agent 各记一份 | 单一事实源，多 agent 共享同一份日志 |
| 位置随意改 | 存储位置先跟用户确认再固定，索引路径不断 |
| 和 bug 诊断混在一起 | 只管沉淀与查阅，诊断交给专门的 skill |
| 记了不知道有没有用上 | 命中计数：真解决了问题才 +1，≥3 次自动升华进记忆铁律 |
| 案例平铺，同类问题看不出关系 | 根因层 + 案例层：同一根因挂多条案例，识别信号提炼成一句话 |

## 3 分钟上手

1. 把文件夹放进 skills 目录（见[总目录](../README.md#skills-index)）；
2. 第一次用，先跟它确认日志存放位置（默认 `D:\Deepseek-ALL\踩坑日志`，但它会先问，不写死）；
3. 报 bug、踩坑、反复排查同一个问题时触发记录；也可以直接说"看看踩坑记录"来查阅；
4. 想让它主动记，就说"解决完这个帮我记一条"。

## 实战绩

从 `D:\_ai_memory_sync` 的原型提炼成通用 skill，品牌中性，多 agent 共用一个日志根。目前日志里 **8 条案例 / 6 个根因**、累计命中 0 次——计数刚上线，从零开始攒。

v1.1.0 补了两条边界说明：与 bug 诊断 skill 的分工、与记忆 PITFALL 层的分工。这两条来自实际使用中的困惑——一开始确实出现过"同一个坑记两遍"和"该诊断的活被记成流水账"的情况。

v1.2.0 加命中计数，起因是发现"记了多少"能统计、"用上了多少"不能——日志可能记了一堆从没被翻出来过的坑。加上计数后，哪条坑真救过场有了证据，够格升华成铁律的也会自己浮出来。

v1.3.0 加根因层，起因很具体：写这一版时刚踩了个新坑（中文路径让 git 误删目录），事后一归类才发现——**它和五天前那条"中文 .ps1 乱码"是同一个根因，可两条记录摆在一起根本看不出关系**。这正是只有案例层会漏掉的东西：单看都是孤立事故，归到一起才是规律。于是把根因从案例里"提"出来，单独成层。

## 适用 / 不适用

- ✅ 反反复复踩同一类坑的场景；多个 agent 协作、需要共享教训的场景；想积累可迁移经验而不只是修完就忘的场景
- ❌ 一套标准流程就能解决的问题；需要即时诊断定位的 bug（那个走诊断流程，不走这里）
