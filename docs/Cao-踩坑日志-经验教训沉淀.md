# Cao-踩坑日志（pitfall-log v1.2.0）

> [← 返回总目录](../README.md#skills-index)

## 一句话

一套省 token 的踩坑沉淀法。教训不进"越写越大的那个文件"，而是极轻索引常驻上下文、每条坑拆成独立文件按需加载。

## 它解决什么问题

- **教训全塞一个文件。** 攒到几十条，每次会话开头都得整份读一遍，没踩坑的对话也在付这个 token 成本。
- **踩过的坑找不回来。** 记得"之前好像遇到过"，但想不起关键词，翻不出来，只能重踩一遍。
- **只记了"怎么修的"，没记"为什么"。** 换个场景，同一个根因换个样子再来一遍。
- **多个 agent 各记一份。** 甲踩的坑乙不知道，重复交学费。

## 核心机制

**结构就两样东西。** 一份 `pitfall-log.md` 索引，加一个 `pitfalls/` 目录，每条坑一个文件。

**索引保持极短。** 一行一条，新条目在最上面：

```
YYYY-MM-DD | 记录者 | 标签1,标签2 | 一句话标题 | → pitfalls/YYYY-MM-DD-<slug>.md
```

索引每次会话都读，所以绝不内联完整条目——这是它随体量增长仍然省 token 的关键。

**条目按六节写。** 坑是什么、上下文、根因、解法、**能否借鉴**、来源。

第六节是整套东西里最值钱的部分。前五节只解决"这一次"，只有"能否借鉴"把一次性修复变成可迁移的经验。

**索引有界。** 超过约 50 条，冷条目归档到 `pitfalls/archive/`，索引里只留一个指针。索引本身不会长成新的巨型文件。

**边界划清楚。** 这个 skill 只管"沉淀和查阅"。真正的 bug 诊断流程交给专门做诊断的 skill，避免职责重叠。跟记忆系统里的 PITFALL 层也有分工：原始记录在这里（跨 agent 共享、不评分不衰减），反复出现、升华成铁律的才进记忆 CORE。

## 一条真实的坑长什么样

下面这条就躺在日志里（`pitfalls/2026-09-03-删目录前先验证硬编码引用.md`），完整结构：

```
# 坑：清理「看起来像缓存」的目录前没验证引用，差点删掉被硬编码依赖的工具

## 上下文
整理 DeepSeek-work 工作区时，把 _tools/pnpm/（21M）归类为「本地缓存副本」，
准备连同另外 4 项（合计 683M）一起隔离清理。

## 为什么（根因）
它长得像缓存：不过是某个目录里 npm 装出来的一份 pnpm 副本。
但它实际被两个插件安装脚本硬编码引用：
  install-dsh-better-sidebar.ps1:6   $pnpmDir = 'D:\...\_tools\pnpm\node_modules\.bin'
误判的根源是按外观归类，而不是按引用关系判断——「像缓存」不等于「没有用」。

## 解法
删除或移动任何目录前，先全项目 grep 该路径名：
  grep -rn "_tools\|<目录名>" --include=*.ps1 --include=*.json --include=*.md .
本次靠这一步保住了 _tools；其余 4 项确认无引用后才隔离，安全腾出 662M。

## 能否借鉴（通用规律）
判定「能不能删」的顺序应当是：
1. 有没有被引用（grep 全项目，含脚本、配置、文档）
2. 能不能重建（缓存、生成物通常可以；唯一副本不行）
3. 是不是真的过时（对比时间戳与内容完整性，而不是看名字）
另外，涉及删除时优先隔离到 _待确认删除/ 而不是直接删——同盘移动瞬时且完全可逆。
```

最后那段"能否借鉴"才是这条记录真正的价值。下次做任何清理，第一步就会先问"引用查了没有"。

## 现在日志里记了哪些坑

截至 2026-09-03 共 7 条，全是"换个项目还会踩"的通用坑：

| # | 标签 | 坑 | 一条经验 |
|---|---|---|---|
| 1 | PowerShell/编码 | 中文 .ps1 不带 BOM 被 GBK 解码成乱码，引号被吞 | 中文 .ps1 一律存 UTF-8 with BOM |
| 2 | 清理/引用安全 | 「长得像缓存」不等于没用 | 删目录前先 grep 硬编码引用 |
| 3 | 沙盒/构建 | 本环境跑 pnpm install 必被策略拦截 | 直接转交用户终端，别反复重试 |
| 4 | pnpm/依赖 | 手写修复 junction 会全删光且建不回 | 让 pnpm 自己重建，别手写 |
| 5 | Node/验证 | `node -e` 从 cwd 找依赖，不是脚本所在目录 | 验证前先 Set-Location |
| 6 | PowerShell/陷阱 | `$pid` 是只读自动变量，赋值静默失败 | 别和保留变量撞名 |
| 7 | 路径迁移/PTY | 重命名项目根目录后 PTY 会话起不来 | 根目录改名要预判工具会话失效 |

## 命中计数：哪条真的救过场

**这 7 条里，截至目前真正被检索命中并解决过问题的：0 条。**

这个"0"恰好说明了为什么要加计数——在此之前，"这条坑到底有没有用"是没法度量的：记录者觉得写了有用，但用没用上、用了几次，谁也说不清；想判断哪条够格升华成铁律，只能凭感觉。

v1.2.0 起的规则，定得很严，三条同时成立才 +1：

1. 查阅时**真检索命中**了这条坑；
2. 它的经验**确实被用于**解决当前问题；
3. 问题**真的解决了**。

只扫到没用上、或最后没解决，都不算。**宁可少记，不要虚高**——虚高的数字等于没有数字。

计数落在两处：索引行的 `🔥N` 给人一眼看，条目 frontmatter 的 `hits` 是权威值，文末 `## 命中记录` 留明细（哪次、什么场景、解决了什么）。**累计 ≥3 次 → 升华进记忆 CORE 铁律区**，此后每次会话强制加载。

这就是"记了一堆"和"沉淀成规则"之间那座桥：让数据自己说出**哪条坑值得升级**，而不是靠人拍脑袋。

## 和同类方案比，差在哪

| 常见做法 | 本 skill |
|---|---|
| 教训内联在一个文件 | 索引常驻 + 每条坑独立文件，按需加载 |
| 索引跟着条目一起膨胀 | 索引有界，超量归档到 archive/ |
| 只记症状和修法 | 强制写"根因"与"能否借鉴" |
| 各 agent 各记一份 | 单一事实源，多 agent 共享同一份日志 |
| 位置随意改 | 存储位置先跟用户确认再固定，索引路径不断 |
| 和 bug 诊断混在一起 | 只管沉淀与查阅，诊断交给专门的 skill |
| 记了不知道有没有用上 | 命中计数：真解决了问题才 +1，≥3 次自动升华进记忆铁律 |

## 3 分钟上手

1. 把文件夹放进 skills 目录（见[总目录](../README.md#skills-index)）；
2. 第一次用，先跟它确认日志存放位置（默认 `D:\Deepseek-ALL\踩坑日志`，但它会先问，不写死）；
3. 报 bug、踩坑、反复排查同一个问题时触发记录；也可以直接说"看看踩坑记录"来查阅；
4. 想让它主动记，就说"解决完这个帮我记一条"。

## 实战绩

从 `D:\_ai_memory_sync` 的原型提炼成通用 skill，品牌中性，多 agent 共用一个日志根。目前日志里 7 条坑、累计命中 0 次——计数刚上线，从零开始攒。

v1.1.0 补了两条边界说明：与 bug 诊断 skill 的分工、与记忆 PITFALL 层的分工。这两条来自实际使用中的困惑——一开始确实出现过"同一个坑记两遍"和"该诊断的活被记成流水账"的情况。

v1.2.0 加命中计数，起因是发现"记了多少"能统计、"用上了多少"不能——日志可能记了一堆从没被翻出来过的坑。加上计数后，哪条坑真救过场有了证据，够格升华成铁律的也会自己浮出来。

## 适用 / 不适用

- ✅ 反反复复踩同一类坑的场景；多个 agent 协作、需要共享教训的场景；想积累可迁移经验而不只是修完就忘的场景
- ❌ 一套标准流程就能解决的问题；需要即时诊断定位的 bug（那个走诊断流程，不走这里）

## 版本

v1.2.0：新增「命中计数」——真被检索命中且解决了问题才 +1，索引 `🔥N` 与条目 frontmatter `hits` 双写，文末留命中明细；命中 ≥3 次自动升华进记忆 CORE 铁律区；明确「全处同步」铁律（规则、模板、索引、条目、发布页任一处升级，全部同步）。
