# Cao-踩坑日志（pitfall-log v1.3.0）

> [← 返回总目录](../README.md#skills-index)

## 一个问题

"这个 bug，你上个月是不是修过一次？"

修过。但修在哪、当时为什么错、怎么修好的——全忘了。笔记记过？去翻，记的时候图省事写的是"已修复"，三个字。于是同一个坑，第二次全价重踩。

比这更隐蔽的是**根因伪装**：同一个根因，换个症状出现，你根本认不出它是"老熟人"。看这个真实案例——**中文编码**这一个根因，在同一个仓库里炸了两次，前后只差 12 天：

| 日期 | 症状 | 表面看像什么 |
|---|---|---|
| 09-03 | 中文 `.ps1` 被 GBK 解码成乱码，引号被吞、语法崩溃 | "写脚本"的坑 |
| 09-15 | 中文路径传给 git，误删了整个 `docs/` 目录 | "git 命令"的坑 |

一个在脚本文件里，一个在命令行参数里，症状毫不相干——**如果按案例平铺记录，这两条永远看不出是一回事**。直到把根因提出来才显形：中文跨进程边界上，UTF-8 与 GBK 的编码假设不一致。识别信号提炼成一句话：**中文出现在跨进程边界，先怀疑编码，再怀疑逻辑。**

下一次它变成"配置文件里的中文"再来，你就认得它了。这套 skill 的全部价值就在这：**根因是一级公民，案例挂在它下面。**

## 结构长什么样

三样东西：一份极轻索引 `pitfall-log.md`（每次会话都读，所以**绝不内联完整条目**——这是它随体量增长仍然省 token 的关键）+ `roots/` 根因文件（一个根因一个）+ `pitfalls/` 案例文件（一条坑一个，按需加载）。

**根因文件四节**：一句话根因、**识别信号**、通用对策、挂载案例。
**案例文件五节**：上下文、为什么（根因）、解法、**能否借鉴**、来源。

「能否借鉴」是整套东西最值钱的一节——前四节只解决"这一次"，只有它把一次性修复变成可迁移经验。看一条真记录的收尾（某次清理差点删掉被硬编码依赖的工具）：

> 判定「能不能删」的顺序应当是：① 有没有被引用（grep 全项目）；② 能不能重建；③ 是不是真的过时（对比时间戳，而不是看名字）。涉及删除时优先隔离到 `_待确认删除/`——同盘移动瞬时且完全可逆。

下次做任何清理，第一步就是"引用查了没有"。

## 命中计数：说实话的部分

**截至计数上线时，真正被检索命中并解决过问题的：0 条。**

这个 0 恰好说明为什么要有计数——之前"这条坑有没有用"根本没法度量，记录者觉得有用，可从没被翻出来过呢？v1.3 的判定故意定得严：真检索了 + 真翻看了 + 真从中获益 + 问题真解决了，四条同时成立才 +1。事后发现"这俩坑同根因"不算——**宁可少记，不要虚高，虚高的数字等于没有数字**。

然后是那座桥：某条案例命中 ≥3 次，或某根因下案例 ≥3 条 → 自动标 ⭐ 升华进记忆 CORE 铁律区，此后每次会话强制加载。**哪类问题值得升级，让数据自己说话，不靠人拍脑袋。**

## 和"随手记个 notes"比，差在哪

| 你现在的做法 | 这套日志 |
|---|---|
| 教训记在一个越写越肥的文件里 | 索引常驻有界（超 50 条归档），案例独立文件按需加载 |
| 记"怎么修的"三个字 | 强制写根因 + 识别信号 + 能否借鉴 |
| 同类坑各记各的，看不出关系 | 根因层把多条案例拧成一条规律 |
| 记完从不回头看 | 命中计数 + 自动升华，日志自己进化成规则 |
| 多个 AI 各记一份互不知道 | 单一事实源，多 agent 共用 |
| 笔记和 bug 诊断混作一团 | 只管沉淀查阅，诊断归诊断流程，边界写死 |

## 什么情况别用

- 一套标准流程就能解决的问题——不值得记；
- 需要即时定位的 bug——那走诊断流程，这里是沉淀层，别拿日志当调试器。

## 实战绩

9 条案例收在 6 个根因下（RT-001 中文编码、RT-002 依赖隐式上下文、RT-003 静默失败、RT-004 凭外观归类、RT-005 绕过工具机制手工干预、RT-006 环境拦截误判为代码缺陷）。三个版本各对应一次真实痛点：v1.1 因为"同一坑记两遍"补边界说明；v1.2 因为"记了多少能统计、用上了多少不能"加命中计数；v1.3 因为上面那个"中文编码 12 天炸两次"的亲历，把根因从案例里提出来单独成层。

三个模板（案例/根因/索引）可直接复制起一套自己的日志，见 [assets/](../Cao-踩坑日志-经验教训沉淀/assets/)。
