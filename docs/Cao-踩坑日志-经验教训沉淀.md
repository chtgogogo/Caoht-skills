# Cao-踩坑日志（pitfall-log v1.3.0）

> [← 返回总目录](../README.md#skills-index)

一个问题。这个 bug，你上个月是不是修过一次？

修过。但修在哪、当时为什么错、怎么修好的，全忘了。笔记记过吗？记过，图省事写的是"已修复"三个字。于是同一个坑，第二次全价重踩。

比这更亏的是根因会伪装。同一个根因换个症状出现，你认不出它是老熟人。看这个真实案例，中文编码这一个根因，在同一个仓库里炸了两次，前后差 12 天。

| 日期 | 症状 | 表面看像什么 |
|---|---|---|
| 09-03 | 中文 .ps1 被 GBK 解码成乱码，引号被吞，语法崩溃 | 写脚本的坑 |
| 09-15 | 中文路径传给 git，误删了整个 docs/ 目录 | git 命令的坑 |

一个在脚本文件里，一个在命令行参数里，症状八竿子打不着。按案例平铺记录的话，这两条永远看不出是一回事。直到把根因单独提出来才显形，中文跨进程边界上，UTF-8 和 GBK 的编码假设不一致。识别信号提炼成一句话，中文出现在跨进程边界，先怀疑编码，再怀疑逻辑。

下次它变成配置文件里的中文再来，你就认得它了。v1.3 把根因从案例里单独拎出来成一层，起因就是这次亲历。

## 结构

三样东西。一份极轻索引 pitfall-log.md，每次会话都读，所以绝不内联完整条目，这是它随体量增长还省 token 的关键。roots/ 目录放根因文件，一个根因一个。pitfalls/ 目录放案例文件，一条坑一个，按需加载。

根因文件四节，一句话根因、识别信号、通用对策、挂载案例。

案例文件五节，上下文、为什么（根因）、解法、能否借鉴、来源。

「能否借鉴」这一节是整套东西里最值钱的。前四节只解决这一次，只有它把一次性修复变成可迁移的经验。贴一段真记录的收尾，某次清理差点删掉被硬编码依赖的工具：

> 判定能不能删的顺序应当是，一查有没有被引用，grep 全项目。二查能不能重建，缓存和生成物通常可以，唯一副本不行。三查是不是真的过时，对比时间戳和内容，而不是看名字。另外涉及删除时优先隔离到待确认目录，同盘移动瞬时且完全可逆。

下次做任何清理，第一步就是查引用。

## 命中计数，说实话的部分

计数上线时，真正被检索命中并解决过问题的，0 条。

这个 0 恰好说明了为什么要加计数。在此之前，一条坑到底有没有用没法度量，记录的人觉得有用，可它从来没被翻出来过呢？v1.3 的判定定得很严，真检索了，真翻看了，真从中获益了，问题真解决了，四个条件同时成立才加一。事后发现两条坑同根因，不算。宁可少记不要虚高，虚高的数字等于没有数字。

然后是这座桥。某条案例命中三次以上，或者某个根因下案例攒够三条，自动标星升华进记忆 CORE 的铁律区，之后每次会话强制加载。哪类问题值得升级，让数据自己说话，不靠人拍脑袋。

## 跟随手记个 notes 的区别

| 你现在的做法 | 这套日志 |
|---|---|
| 教训记在一个越写越肥的文件里 | 索引常驻有界，超五十条归档，案例独立文件按需加载 |
| 记"怎么修的"三个字 | 强制写根因、识别信号、能否借鉴 |
| 同类坑各记各的，看不出关系 | 根因层把多条案例拧成一条规律 |
| 记完从不回头看 | 命中计数加自动升华，日志自己长成规则 |
| 几个 AI 各记一份互不知道 | 单一事实源，多 agent 共用 |
| 笔记和 bug 诊断混作一团 | 只管沉淀查阅，诊断归诊断流程，边界写死 |

## 什么时候不用

一套标准流程就能解决的问题，不值得记。需要即时定位的 bug，走诊断流程，这里是沉淀层，别拿日志当调试器。这两个边界说明是 v1.1 补的，因为实际出现过同一个坑记两遍、该诊断的活被记成流水账的情况。

## 目前的家底

9 条案例收在 6 个根因下。根因编号 RT-001 到 RT-006，中文编码、依赖隐式上下文、静默失败、凭外观归类、绕过工具机制手工干预、环境拦截误判为代码缺陷。三个模板（案例、根因、索引）在 assets/ 里，复制过去改改 frontmatter 就能起一套自己的日志。
