# A-Cao-编码行为准则（coding-behavior v1.2）

> [← 返回总目录](../README.md#skills-index)

## 两个你肯定见过的场面

**场面一。** 你让 AI 改一个错别字。它改完了——顺便把整段代码重排了格式，"优化"了两个变量名，还删了一段它认为没用的注释。你打开 diff 愣了三秒：我就让你改一个字。

**场面二。** 它报错后说"应该可以了"。你问：跑过吗？它沉默两秒，说：没有。

这两件事背后是同一个真相：**AI 写代码的默认行为是"省事"，而不是"对"。** 猜一个理解比问你一句省事；顺手优化周边比只改一行省事；说"应该可以"比真跑一遍省事。每一条都省它的事，每一条都花你的时间。

这个 skill 就是六条纪律，逐条堵死这些"省事"。

## 六条纪律，每条都是从坑里长出来的

**思考优先。** 需求模糊先问，禁止猜了继续干。猜错方向写两千行，不如开工前问一句。

**极简。** 只做明确要求的事。禁止预埋"以后可能用到"的功能——要一个加法函数，就别给我一个带泛型、可配置、带日志的运算框架。

**外科修改。** 只改与任务直接相关的行。这条就是场面一的直接产物——它来自一次真实事故：改 bug 顺手改了无关代码，返工的时间比修 bug 本身还长。

**目标驱动。** 动手前先定"什么现象出现算做成"。没有成功标准的任务，做到最后连"做没做成"都无法判定。

**验证纪律。** 声称完成前必须实际运行、读完整输出和退出码。没跑过不许说"应该可以"。以及最值钱的半句：**同一个问题连败 3 次，立刻停下重新分析**——这条来自一次连试十几次都没定位到问题的真实经历，硬磕十几次的代价本来可以在第 3 次就止住。

**遇错先查坑。** 报错、反复失败、反常现象，先检索踩坑日志的根因层再动手。很多坑你（或你的其他 AI）已经踩过并写了通用对策——别一上来就闷头从零排查，把旧学费当新学费再交一遍。

触发面故意放得很宽：**只要沾代码就触发**，拿不准时一律触发。纪律这东西，触发十次九次多余、漏掉一次致命，那就宁可九次多余。

## 和"往 CLAUDE.md 里贴规则"比，差在哪

现在流行往项目的规则文件里贴一堆"你要谨慎、你要优雅"——问题是大而空的形容词 AI 根本执行不了。区别在这里：

| 常见写法 | 这套纪律 |
|---|---|
| "写代码要严谨优雅" | "实际运行、读完整输出和退出码，没验证不许说完成"——可判定，可执行 |
| 一条大而全的行为准则 | 六条各堵一个具体坏习惯，每条都能说出它来自哪次事故 |
| 规则躺在文档里靠 AI"记得" | 沾代码即触发，宁多勿漏 |
| 从不提错误处理 | 连败 3 次强制停下 + 遇错先查坑，失败有出口 |
| 规则引用外部文件，换台机器就失效 | 六条全部内联正文——这是 v1.1 用一次真事故换的：规则挂在某个本机绝对路径下，别人 clone 下来读不到，skill 整个失效 |

## 什么情况别用

- 纯闲聊、写作、翻译——零代码任务不触发，也不该触发；
- 你明确要大范围重构/格式整理——直接说，它会放宽"外科修改"的约束，纪律服务于你而不是绑住你。

## 实战绩

六条全部从真实踩坑里长出来，不是抄的模板。"连败 3 次停下"背后是一次十几次的硬磕；"禁止顺手大扫除"背后是一次返工事故；"内联正文"背后是一次换机失效。v1.2 加入第 6 条后，与踩坑日志形成闭环：前五条管"怎么做"，第六条管"从哪找答案"。
