# A-Cao-编码行为准则（coding-behavior v1.2）

> [← 返回总目录](../README.md#skills-index)

让 AI 改一个错别字。它改完了，顺手把整段代码重排了格式，"优化"了两个变量名，还删了一段它觉得没用的注释。你打开 diff 看半天，就想问一句：我只让你改一个字。

还有更常见的。它说"应该可以了"。你问跑过吗。它承认没有。

这两件事背后是同一个习惯，AI 写代码默认怎么省事怎么来。猜一个理解比问你一句省事，说"应该可以"比真跑一遍省事。每一条都省了它的事，时间花在你的返工上。

这个 skill 是六条纪律，一条堵一个具体的坏习惯。

## 六条纪律

**思考优先。** 需求模糊先问，不许猜了继续干。猜错方向写两千行的返工成本，够你回答一百个问题。

**极简。** 只做明确要求的事。要一个加法函数，就不许给一个带泛型、可配置、带日志的运算框架。

**外科修改。** 只碰跟任务直接相关的行。这条来自一次真事，改 bug 的时候顺手改了无关代码，返工时间比修 bug 本身还长。

**目标驱动。** 动手前先定好"什么现象出现算做成"。没有成功标准的任务，做完连有没有做成都没法判定。

**验证纪律。** 声称完成之前必须实际运行，读完整输出和退出码。没跑过就不许说"应该可以"。这条里还有半句最值钱的：同一个问题连败三次，立刻停下来重新分析。它来自一次连试十几次都没定位到问题的经历，那十几次的浪费本来第三次就能止住。

**遇错先查坑。** 报错、反复失败、结果反常，先去翻踩坑日志的根因层，看这个坑是不是已经有现成的对策了，再决定要不要自己排查。前五条管怎么干活，这条管去哪找答案。

触发面故意放得很宽。只要沾代码就加载，拿不准时一律触发。纪律这种东西，触发十次九次是多余的，漏掉一次是致命的，那就宁可多余。

## 一条 v1.1 的教训

最初五条纪律写在单独的 references 文件里，SKILL.md 引用那个文件的路径。看起来更整洁，对吧。问题是路径里有本机目录，别人 clone 下来文件根本不存在，整个 skill 直接失效。

所以 v1.1 把五条纪律全部内联进正文。文件结构上难看了一点，换台机器就能用。这算这个仓库里反复出现的一个主题，规则必须跟着文件走，文件必须跟人走。

## 跟"往 CLAUDE.md 里贴规则"的区别

现在流行往项目规则文件里写"你要严谨、你要优雅"。问题是大而空的形容词 AI 执行不了，它自己觉得严谨了，你没觉得。

| 常见写法 | 这里怎么写 |
|---|---|
| 写代码要严谨优雅 | 声称完成前实际运行，读完整输出和退出码，没验证不许说完成 |
| 一大段综合行为准则 | 六条各堵一个具体毛病，每条说得出它来自哪次事故 |
| 规则靠 AI 自己想起来 | 沾代码就触发，宁多勿漏 |
| 没有失败时的出口 | 连败三次强制停下重新分析，遇错先查坑 |

区别说到底就一条，好的约束写得出来"怎么算做到了"，坏的约束只有形容词。

## 什么时候不用

纯闲聊、写作、翻译这类零代码任务，不触发。你要做大范围重构或者格式整理，对话里说一声就行，它会放宽外科修改的约束。纪律是给你服务的，不是绑住你的。
