# 编码行为准则 · 完整详解手册

> 章号说明：在标准 15 章骨架上，把「核心机制」区（第 4–9 章）扩成第 4–12 章——九条纪律每条单独成章；后续章号顺延至第 19 章，**职能与顺序不变**。

---

## 第 0 章 五分钟速览

1. 这是一支**约束 AI 写码习惯**的 skill（skill＝带说明书的能力包，装进 AI 后改变它在某类任务里的行为），不是"你要认真"的口号。
2. 九条各堵一个省力动作：不问就猜、预埋功能、顺手大扫除、没有成功标准、没跑过就说修好了、报错硬磕、自吹提升、补丁盖症状、代码散落。
3. 每条都配**「怎么算做到」的判据**（判据＝可执行的判定标准）——AI 能宣布自己严谨，没法假装跑过测试。
4. 触发面放到最宽：**沾代码就加载，拿不准一律触发**；宁九次多余，不漏一次。
5. 九条**内联**（写在本体正文、不靠外链），换机器 clone 就能用。
6. 它是一步步长出来的：v1.1 五条 → v1.2 加「遇错先查坑」→ v2.0 吸收外部守则扩到九条 → v2.1 补降级路径与回写闭环 → v2.2 补一句指路。每次加条都先在实战里疼一次。
7. 它只管**不犯这九种错**，不管代码漂不漂亮（那是「资深工程师五模板」的活，两支叠加不冲突）。

设计目标一句话：**把 AI 每次"怎么省事怎么来"的冲动，换成一条条能当场检查的硬规矩。**

## 第 1 章 这套系统在解决什么问题

### 1.1 病根是一个词：省事

AI 写码的默认策略是"这一下看起来最省力"：

- 猜一个理解，比问你一句省力；
- 说"应该可以了"，比真跑一遍省力；
- 重排整文件，比只改一行省力；
- 预埋一个"以后用得上"的框架，比承认只需要一个函数省力。

**每一次省事，买单的都是你的返工时间。** 所以这不是最佳实践清单，而是**九张针对具体省力动作的罚单**：每条都必须写得出"怎么算做到"，否则就又变成一句不可证伪的"要严谨"——它自己觉得严谨了，你没觉得，谁也没法裁定。

### 1.2 故障 → 表现 → 本 skill 的解法

| 故障（省力动作） | 你看到的表现 | 对应纪律 |
|---|---|---|
| 不问就猜 | 需求含糊就猜方向，写完两千行，方向错则整段作废 | ① 思考优先 |
| 预埋功能 | 要一个加法函数，交付一个带配置层的运算框架 | ② 极简 |
| 顺手大扫除 | 改错别字，捎带重排全文件、改两个变量名、删一段注释 | ③ 外科修改 |
| 做完无法判定 | 干完了，但没人说得清"做成"长什么样 | ④ 目标驱动 |
| "应该可以了" | 从没运行过就把"修好了"当结论 | ⑤ 验证纪律 |
| 从零硬想 | 一个报错磕半小时，而这套经验早被记录过 | ⑥ 遇错先查坑 |
| 自说自话 | 声称"更快更准"，只有一个数字、没有原始输出 | ⑦ 证明优先 |
| 补丁盖症状 | 现象消失，根因还在，半年后变第二个 bug | ⑧ 溯源调试 |
| 改一处动全身 | 一个功能横跨五六个文件，同一条规则抄三份 | ⑨ 结构自觉 |

## 第 2 章 术语表

| 术语 | 大白话 |
|---|---|
| 本体／触发面／内联 | 本体＝写给 AI 看的规则正文；触发面＝什么任务会加载它；内联＝内容写在同一文件里不靠外链 |
| 判据 | 可执行判定标准：满足才算做到，不满足当场露馅 |
| 幂等 | 重复做结果不变（同一测试跑三次不会三次不一样） |
| 回归 | 改完把老用例重跑一遍，确认没把别处弄坏 |
| 探针 | 只检查、不修改任何东西的脚本或动作 |
| 复现／根因 | 复现＝能稳定重演出问题的最小步骤；根因＝连问几层"为什么"才到的那一层 |
| 红／绿／恒真判据 | 测试失败叫红、通过叫绿，先让它红才知道这测试真能抓到缺陷；无论对错都显示通过的检查＝没有检查 |
| 对抗式审查／消融 | 前者＝假设自己改动是错的、专门找能让它翻车的输入；后者＝把新加的零件拆掉重跑评测，分数掉了才证明零件值钱 |
| 边界用例 | 空值、只有一个、超大、非法值这类边缘输入 |
| 评测集／F1／样本量 | 评测集＝一批有标准答案的输入输出对；F1＝把"查得全"与"查得准"合成一个分数；样本量＝参与统计的条数，越小涨几个点越可能只是运气 |
| diff | 改动前后对比出的"哪几行变了"清单 |
| 内聚／耦合／单一事实源 | 内聚＝一件事的代码住一起；低耦合＝只走明面接口、不伸手进别人抽屉；单一事实源＝同一条常量只出现在一个文件，其他地方一律 import（引用它） |
| 熔断 | 撞到条件就强制停下当前动作，不许硬磕 |
| 渐进披露／上下文 | 索引常驻、细节按需才读；上下文＝AI 一次能"看见"的信息总量，塞满就丢了前面的 |
| 退出码／stderr | 退出码＝程序结束时留给系统的数字，0 通常成功；stderr＝专写错误的输出通道 |
| 悬空引用／副本漂移 | 前者＝规则指向的东西不存在，执行到那步静默失效；后者＝两个拷贝版本不再一致，不同入口读到不同规矩 |
| 奥卡姆剃刀／勾稽／宿主 | 能不加就不加（已被现有条目覆盖的新守则不再新开一条）；勾稽＝两处数字能对上；宿主＝装载并调度这些 skill 的工具程序 |

## 第 3 章 结构与分层详解

### 3.1 文件与字段

| 件 | 职能 | 为什么必须有 |
|---|---|---|
| `SKILL.md` | frontmatter＋触发原则＋触发范围＋九条＋执行＋版本注记 | AI 真正读进去的唯一部分 |
| `CHANGELOG.md` | 每版做了什么、解决了什么、怎么解决的 | 纪律会改，改的理由丢了就会被"好心优化"掉 |

- frontmatter 四字段：`name: coding-behavior`（调度层点名用的短名）、`description`（触发词清单＋"拿不准一律触发"＋触发后执行九条，**决定它会不会被加载**）、`metadata.agent_created`、`metadata.version: v2.2`。
- 分区顺序：`触发原则 → 触发范围 → 九条纪律（全部内容在这一节）→ 执行（按九条干／要更细才读共享源／简单任务可跳流程）→ 版本注记`。
- 本支**没有脚本、没有 references、没有 assets** [实测]。这本身是设计表态：规则越依赖外部件，越容易在换机器时静默失效（第 13 章失效 2）。
- `description` 的长度上限**三值并存，本页不合一**：1,024（开放标准与上传校验）／1,536（某宿主常驻清单截断）／200（某帮助中心上传口径）。本支刻意把触发词写满，赌的是"宁可被截断、不要漏触发"；实际落在哪个上限之下**未实测该宿主、未检索到确切数** [推演]（若按 200 截断，被截掉的正是"拿不准一律触发"与"纯闲聊不触发"的收口——既更容易漏触发，又更容易误触发）。

### 3.2 触发范围为什么要列到 36 个词

- 五类共 **36 个词**（数法：按该节五个项目符号逐条、以顿号清点＝写/生成 7、改/修 8、审/重构 6、设计 9、分析答疑 6）[实测]。
- AI 判断"这算不算写码"靠**语义距离**，不是分类学：用户说"这段 `select` 有没有坑"，句里没有一个字是"代码"，但"写 SQL""代码审查"在清单里，命中即加载。
- 结论 [推演]：**清单是把语义距离换成关键词命中率**，最土也最可靠。

### 3.3 三层加载，与"自足"的真实含义

| 层 | 内容 | 何时被读 | 缺失后果 |
|---|---|---|---|
| 1 | `description` | 常驻宿主清单 | 不触发＝等于没装 |
| 2 | 九条本体 | 触发后整份读入 | 无（本体自足） |
| 3 | 共享源的展开解释 | 只在"要更细"时才读 | 正文自陈：缺失不影响使用 |

- [实测]「执行」第 1 步写"本文件自足，无需外部依赖"；`CHANGELOG.md` 的 v1.1 节记着这次搬迁：**早期纪律写在外部引用文件里，看着整洁，换台机器那文件不存在，skill 直接报废**。
- 一处要摊开的张力 [推演]：⑥的执行其实依赖另一支踩坑日志 skill 或它的索引文件，所以"自足"的准确含义是**规则文本自足**（读得到、想得起来），不是执行过程零依赖。出问题的情形：新机器上第一次遇到报错任务，若连索引文件都不存在，AI 在⑥上要么原地打转、要么静默跳过，而且不报告。

### 3.4 九条的执行时序（谁先谁后）

| 阶段 | 纪律 | 留下的产物 |
|---|---|---|
| 动手前 | ①④⑨，修 bug 类再加⑧ | 【事实/假设】清单＋成功标准＋改动文件数预估＋复现方法 |
| 动手中 | ②③ | 每行可辩护的 diff |
| 遇错时 | ⑥、⑤ 的熔断分支 | 一次索引检索动作＋停下换假设的记录 |
| 交付前 | ⑤⑦ | 原始输出与退出码＋反例边界结果＋（效果类）消融对照 |
| 交付后 | ⑥ 回写、⑦ 扩散扫描 | 一条新沉淀记录＋同类毛病的横向清点 |

[推演]（正文未画流程图，此表由本页按每条的动作词归纳。）用处是**判断哪条该在什么时候冒出来**：还没动手就去翻踩坑日志，时序反了；跑完测试不做消融就宣布"更快了"，缺的是交付前那一步。

## 第 4 章 纪律①「思考优先」——堵「不问就猜」

**原句要点**[实测]（「九条纪律」第 1 条）：不确定先问、禁止猜了继续干；动手前想清楚再落键；交付前列出所有不自信的点，结论分【事实／假设】并标置信度，证据不足写「未知」。

- **堵的翻车**："把这个页面优化一下"这句话里有四个空洞——优化哪个维度（速度／视觉／文案）、哪个页面、目标是多少、怎样算成功。
- AI 不问就得自己填四个洞，每个都按"最常见情况"猜，**四项独立猜对的概率是各概率之积**，很容易一路全猜错还写完。
- 赌注：问一句的成本是几百字，猜错方向的成本是两千行。
- **违反会怎样**：不是"这次白干"这么轻，是三个连锁——① 你基于错误方向给反馈，它再按错的改一轮；② 已交付的代码被当成既成事实舍不得删，最后长成四不像；③ 你开始分不清哪些结论是查来的、哪些是猜的，因为回答里两者混排、语气完全一样。
- **深一层**：`CHANGELOG.md` v2.0 节记录"列出不自信的点"被**并进①的尾巴**而不是新开一条（奥卡姆剃刀挡住了一次膨胀，否则九条变十三条）。它真正的价值是给 AI **一个合法说"不知道"的出口**——规则若只要求"要准确"，模型没依据时不会留白，它会拿一个看着合理的假设把洞填上，因为留白显得失职。
- [推演] 不给「未知」这档会怎样：回答满篇"通常／一般来说／可能"，看着谨慎，一句都核对不了。
- **怎么算做到**：动手前有"我理解要做的是…，其中 A、B 未定"且未定项后面跟着问题；交付前有【事实】／【假设】两栏清单、每条【假设】带置信度、**至少允许一行"未知"**。不问它的核对法＝随机挑一条【假设】追问"依据是什么"，若其实查过就该挪进【事实】，分错栏等于没做。

## 第 5 章 纪律②「极简」——堵「预埋未来功能」

**原句要点**[实测]（第 2 条）：只做明确要求的事，禁止预埋未来功能、禁止顺手大扫除。

- **堵的翻车**：要一个两数相加的函数，交付一个带运算符注册表、配置注入、异常包装的"运算框架"——动机通常是讨好。
- 预埋代码的代价**不在写的那一刻，而在下一次改动时结算**：它没被任何需求覆盖、也没被测试覆盖，是**未验证代码**；下一个人读它时判断不出"这是给谁用的"，只能全读一遍；下次改需求时它是最大的不确定源——改它怕有隐形调用者，不改它又挡路。
- **违反会怎样**：代码量与"完成感"脱钩——看着做了很多，能验收的部分不变。
- **②与③的分工**（最常被混谈）：② 管**无中生有**，③ 管**动了既有物**；一个防炫技、一个防洁癖。合成一条的话 AI 通常只守住一半——重排了全文件却觉得自己很克制，因为它"没新增功能"。
- **怎么算做到**：diff 里每段新增代码都能回答"哪句需求要求它存在"，答不出就删；交付文本里不出现"顺便加了…将来可以用"，这句话本身就是②的自供状。
- [推演] 反例输入：用户明确说"顺手抽成可复用工具函数"。此时②让位于显式指令；正文没写这条例外（未检索到），故为本页补充——**显式授权能覆盖②③，覆盖不了⑤⑦**：预埋的东西一旦写了，照样得跑、得给证据。

## 第 6 章 纪律③「外科修改」——堵「顺手大扫除」

**原句要点**[实测]（第 3 条）：只改与任务直接相关的代码，不碰无关行，改动面最小化。

- **堵的翻车**：改一个错别字，却顺手重排整段格式、"优化"两个变量名、删一段注释。看着更整洁，实际三处崩：
- **diff 失去可评审性**：真改动 1 行、diff 里 400 行。评审者要么硬看 400 行，要么放弃评审——两种都是没有评审。这就是"无关改动稀释要紧行"的具体机制。
- **回归范围炸开**（回归＝改完把老用例重跑一遍）：格式重排理论不改行为，但碰了一个字符串常量、一行条件的换行，行为就可能变；而"哪些老用例要重跑"已无法圈定，只能全跑或赌它没事。
- **协作污染**：格式化把别人未提交的改动搅进来，`git blame`（每行是谁哪次改的）整片指向你这次提交；将来查"这行为什么这么写"，指向一次根本无关的改错字。
- **这条是被抗议过才补的**：本支版本注记里 2026-09-14 那次升级给它**只加了边界**——`CHANGELOG.md` 原文就"＋边界"两个字。它不是天然常识，是踩过之后写进去的。
- **怎么算做到**：逐行自问**"不改这一行，任务会不会失败？"**（会→留，不会→删，不需要任何工具）；提交前数一遍 diff 行数、交付里写明"真改动 N 行、其余为上下文"（数法：按 diff 的 `+`／`-` 行计数）。
- 想收拾房间就另开一次任务、标题写"仅格式化、不改行为"，然后**跑全量回归**——把偷偷做的动作变成显式做的动作。显式授权能放宽②③，放宽不了⑤⑦，因为后两者的判据是外部事实不是偏好 [推演]。

---

## 第 7 章 纪律④「目标驱动」——堵「做完无法判定」

**原句要点**[实测]（第 4 条）：动手前先定可验证的成功标准（什么现象出现＝做成了）。

- **堵的翻车**："帮我加个登录功能"。做完你说"没做，因为没记状态"，它说"做了，因为页面能跳"——两边都没错，只是从来没约定过"做成"长什么样。
- **为什么排在⑤⑦之前**：没有成功标准，⑤"实际运行验证"就没有验证对象（跑什么？），⑦"每句提升后面指得出证据"就没有可证伪的命题（相对什么算提升？）。④的职能是**把整条流程的验收口钉死，让后面两条有力可使**。
- **深一层** [推演]：把"让列表加载更快"翻成可验证标准，要一路问——几毫秒？什么数据量？谁的机器？和哪个时刻比？翻到第二问多半发现"这需求本身还没想清楚"。这就是④与①的闭环：**定标定不出来就得回去问**。
- 只有描述没有数字的标准（"明显变快"）等于没有标准；合格形状要么带可测数字，要么带可观察现象（"点'已退款'后返回集合里不再出现未退款单"）。
- **怎么算做到**：动手前的文本里有一行以"成功标准＝"开头，且这句话能被一个不问它意见的检查回答"是／否"；核对法是交给第三个人问"照它能不能判断做完了"，答不上来就重写。
- [推演] 反例输入：探索型任务"先试试这个第三方库行不行"——它的产出就是"行不行"，标准应写成"跑通最小样例并给出三条限制"；把④硬套成"必须有性能数字"会让探索任务无法开工。

## 第 8 章 纪律⑤「验证纪律」——堵「应该可以了」，附带一个熔断

**原句要点**[实测]（第 5 条）：声称完成前必须实际运行验证、读完整输出与退出码；未验证禁说"应该可以／修好了"；同一问题连败 3 次立即停下重新分析，不许硬磕。里面焊着两个机制。

### 8.1 机制 A：读完整输出与退出码

- 退出码＝程序结束时留给系统的数字，0 通常表示成功；stderr＝专写错误的那条输出通道。
- 正文点名它，是因为 AI 看命令结果最常犯的错是**只看输出的第一段**：报错常写在 stderr、写在最后二十行，或根本不写在文字里，只体现为"stdout 一片祥和、退出码是 1"。
- **违反会怎样**：它说"跑过了，没问题"，实际跑的是另一个入口、在别的目录跑、或压根没成功，只是自己没读完；你据此交付，用户先发现。
- "未验证禁说'应该可以／修好了'"把**措辞**也纳入纪律——措辞最易核对，一句"应该可以"就是当场可抓的违规，不需要读代码 [实测]。这是九条里最容易执行的判据。

### 8.2 机制 B：连败 3 次熔断

- **这条救过的时间可能比其他几条加起来还多。** 机制：同一问题连败三次，说明你对它的**理解模型是错的**——三次尝试全都建立在同一个隐含假设上而全失败了，此时第 4 次成功的机会并不比第 1 次高，只是换了姿势。
- 为什么是 **3** 不是 5？[推演]（校准依据未检索到，正文只给数字）一次失败可能手滑，两次可能环境抖动，**三次同类失败已足够否证"我的模型是对的"**；取 5 多烧两次成本，取 2 会在真正只差一步的偶发问题上过早放弃。
- **什么输入会让这个数出问题**：网络抖动、偶发时序竞争、要预热的外部服务——这类**纯靠重试就会成功**，第 3 次熔断反而提前止损。
- 所以熔断的正确理解是**"换手段"不是"停工"**：⑤的熔断必须接上⑥。正文把⑥紧跟在⑤后面不是排版巧合——**两条共用同一个"3"，为的就是让熔断必须有出口**。

### 8.3 怎么算做到

- 声称完成那段话旁边必须有：跑的是什么命令、完整输出的关键片段、退出码——缺一即未验证。
- 改前／改后各跑一次，而不是只跑改后（来自配套的测试纪律，见 [测试纪律详解手册](A-Cao-测试纪律-测试证据形态规范.md)）。
- 熔断的可核对形状＝第 3 次失败后的回答里出现"先停下重新分析"，并换了一个**不同的假设**，而不是又试一次同类做法。

## 第 9 章 纪律⑥「遇错先查坑」——唯一一条会自己失效的纪律

**原句要点（节引）**[实测]（第 6 条）：遇报错／反复失败／反常现象，**先检索踩坑日志**（skill 不可用时直接读索引文件）：先扫「根因索引表」比对识别信号，对得上就照通用对策试，不够再翻该根因下的案例；**反复出现／连败 3 次的 bug，动手前强制翻一次**；修完把新坑沉淀回去（通用坑记共享踩坑日志，本机私有坑记本地踩坑记录）。这条最长，因为它是**四件事焊在一起**。

**件一·顺序＝先根因后案例**

- `扫根因索引表 → 比对识别信号 → 命中就读该根因的通用对策 → 试；不够再翻该根因下的案例找灵感`。
- **识别信号**（出现哪些迹象就该往这里想）是整张表最有用的部分——它是"提前认出来"的钩子；**通用对策**是不针对具体案例的做法，最好能直接照做。
- 这个顺序就是渐进披露（结构见 [踩坑日志详解手册](A-Cao-踩坑日志-经验教训沉淀.md) 与 [该支正文](../A-Cao-踩坑日志-经验教训沉淀/SKILL.md)）：上下文只花在真正命中的那条上。

**件二·降级路径（v2.1 补）**

- 版本节 v2.1 注记写明为什么补：踩坑日志那支此前**没注册到宿主**（宿主＝装载调度 skill 的工具程序），⑥里的引用成了**悬空引用**。
- 这是本支最有意思的一次失效：**规则依赖的外部件缺失时，规则不是报错，而是静默跳过**——你完全看不出它没查坑，因为它的回答和"查了但没查到"一模一样。
- 修法是把硬依赖改软依赖：skill 不可用时直接读那个索引文件本身。

**件三·强制触发升级（v2.1 补）**

- 原措辞只是"遇报错先检索"。但**真需要检索的时刻，恰恰是"已经试着自己想而想不通"的时刻**，而那正是最不可能停下来查的时刻（再试一次就要成了）。
- v2.1 于是把"反复出现／连败 3 次"单列成**动手前强制翻一次**，把触发条件钉死在⑤那个数字上 [实测]。

**件四·回写闭环（v2.1 补）**

- 修完按性质分流：跨机器通用的坑进共享踩坑日志，只有这台机器、这套环境才有的坑进本地记录。
- **不写回的成本可以量化**：下一个同类 bug 的排查成本全额重付一遍。查坑是"花别人的钱"，回写是"往这个账户存钱"；只查不写，账户三个月就空了。

**怎么算做到**：回答里出现一次**具体检索动作**（读了哪个文件、扫了哪张表、命中或没命中哪条根因），而不是"我考虑了常见原因"；判据形状＝交付末尾一句"沉淀：新记 1 条／命中已有 1 条／无需沉淀（原因）"。

## 第 10 章 纪律⑦「证明优先」——对抗式审查＋消融＋一句指路

**原句要点（节引）**[实测]（第 7 条）：声称「修好了／更快了／更准了」之前先当自己的对手——假设改动是错的，主动找反例、跑边界、构造让它翻车的输入；效果类改进（性能／精度／召回）必须做消融：拆掉新加的零件重跑评测，分数掉了才证明零件值钱，没掉就删掉；检验＝每句「有用／提升」后面都指得出可复现证据；修完一类缺陷后横向「同类毛病别处还藏几份」→ `same-root-cause-sweep`（同根因扩散扫描；反直觉纪律，不扫＝只修了一半）。

**为什么自己查自己必然放水**

- 它既是作者又是评审，天生倾向确认自己的改动有效。机制是——写代码时建立的那套"我为什么这么改"的叙事，读自己 diff 时会被当成证据复用：它看不出哪里可能错，因为那个地方正是它精心构造出来的合理解释。
- 对抗式审查是一次**强制反转**：把问题从"这有没有问题"换成"请构造一个让它出错的输入"，答案空间完全不同；跑边界（空值、只有一个、超大、非法值）是其中最容易执行的子动作。
- v2.0 新开这条的原因 `CHANGELOG.md` 说得直接：旧条目管"做对的过程"，缺"证明做对了"这道关卡，**而 AI 自查是放水的**。

**消融为什么非做不可**

- 加了条过滤规则，准确率 58.8 涨到 62.9。这 4.1 个百分点可能来自四件事：新规则、同批其他改动、评测集小样本波动、评分脚本被顺手改了。不做消融，这四种**在数据上完全无法区分**。
- 形状：基线＝改前那版跑评测集存原始输出；实验＝改后那版（同集同机同数据）；消融＝仅去掉新零件再跑一次。判读：实验 > 消融 ≥ 基线 → 零件值钱；消融 ≈ 实验 → 零件是噪音，删。

**一个该打在自家的自我打靶** [推演]

- v2.0 的实战依据是一个检索类项目（本仓库正文里写作失物招领系统）两轮迭代、40 对评测集、F1 58.8%→62.9%。
- `CHANGELOG.md` 声明这条纪律源自该实战，但**没记录当时是否真按本节要求做过消融**（未检索到）；而且 40 对样本上的 4.1 个百分点约合 1.6 对的变化，落在抽样波动里，**只是方向性证据**。
- 也就是说：v2.0 新开的"必须有可复现证据"，自身依据并不满足它自己的门槛——这不是推翻它，恰恰说明它最该被用在自己身上。
- 会出问题的情形：拿 40 条小评测集连做三轮"改进"，每轮涨两三个点，三轮后手里是一条完全无法解释的曲线。

**v2.2 那句指路是整支 skill 最新的一次疼**

- 版本节 v2.2 注记 [实测]：第 7 条末尾补挂"修完一类缺陷→`same-root-cause-sweep`"，括号里写着原因——**该件调度统计为 0**。那件 skill 干的是从一个已修缺陷推到同类其余实例：抽象成一条可判定的不变式，再派只读探针横向清点同一类毛病在别处还藏几份。
- 背后是一条对 skill 系统自身的洞见：**一条只能靠 AI"自己想起来"的纪律就是不存在的**；调度统计为 0 就是"不存在"的证据，修法不是写得更详细，而是把入口指路句写进常驻条文。
- "不扫＝只修了一半"之所以**反直觉**：修完一个可见缺陷会带来"这事结了"的完成感，而"别处还有几份"没有任何可见症状，所以永远感觉不着急 [推演]。

**怎么算做到**：每句"有用／提升"后面指得出命令、原始输出在哪、对比两侧各跑了几次，指不出就删掉这句或改成"未验证"；效果类改动的交付里必须有消融那一行，缺此行视为未完成；修完一类缺陷的交付里有一句"同类扩散：扫了 X 处，命中 N 处／确认 0 处（依据…）"。

## 第 11 章 纪律⑧「溯源调试」——三连问与「半年后第二个 bug」

**原句要点**[实测]（第 8 条）：修 bug 三连问，一问不过就不许动手写补丁——复现了吗（先造稳定复现步骤）→ 测试红了吗（先让测试失败）→ 根因是什么（连问三层为什么）；治根因不治症状；往旧结构上打补丁前先问「半年后会不会变成第二个 bug」；说不出复现方法的修复视为未验证。

### 11.1 三问是**顺序**，不是清单

| 问 | 堵的动作 | 跳过的后果 |
|---|---|---|
| 复现了吗 | 直接读代码找"可疑处" | 偶发问题被当必现问题修；改完"这次没出现"只是概率没变 |
| 测试红了吗 | 写测试并让它一次通过 | 得到一条**恒真判据**——代码对错都显示通过，等于没测试 |
| 根因是什么 | 在症状处加一层判断／兜底 | 症状被压住，根因在别处继续发作 |

"一问不过就不许动手写补丁"是这条的硬处：它把三问做成**闸门**而不是参考意见。让测试**红一次**是在验证它具备鉴别力（能不能区分对错）；一个从没红过的绿色测试毫无价值——永远不报红的尺子，量什么都没量过。

### 11.2 「连问三层」长什么样（通用形状，不含真实机器信息）

```
症状：接口 500，日志 connect timeout → 一层：为什么超时？服务没在监听
二层：为什么没监听？启动脚本没被调用 → 三层：为什么没被调用？
那一步只写在部署文档里，不在任何脚本／流水线里 → 根因：这一步靠"人肉记忆"，不靠代码
```

症状层修法＝把超时调大（更糟）；一层修法＝手动起服务（今天就复发）；根因层修法＝把那一步落进脚本，并让"是否在监听"成为流水线里一个会报红的探针（探针＝只检查不改东西的脚本）。

### 11.3 「半年后第二个 bug」在恶化什么

每层补丁都是对旧结构的一次"默认它是对的"的背书。三个月后新人读到的是"原逻辑＋三条互不知情的兜底"，改任何一条都怕碰另外两条，于是第四条兜底出现。**这时你会发现 bug 修不完、但代码行数一直在涨**——那就是⑧长期缺位的长相。

### 11.4 与邻居的分工

- ⑧ vs ⑤：⑧管**动手前**（先弄清病根），⑤管**交付前**（跑过了才算）；过了⑧不能免⑤。
- ⑧ vs ⑥：⑥去别人的记录里找答案，⑧自己把这个 bug 的链挖到底。通常先⑥（一分钟认出老坑，省掉整套三连问），再⑧（没人踩过才走复现→红→根因）——正文把⑥写在⑧前面就是这个顺序。
- ⑧ vs ⑦：⑧保证**改的是病根**，⑦证明**改动真有效且没夸大**。
- 更正式的疑难缺陷与性能回退诊断循环不在本支，由另一支承接（frontmatter 短名 `diagnosing-bugs`，本仓库当前未收录它）；本支⑧只规定"不许跳过三问就写补丁"。

### 11.5 怎么算做到

- 修复说明里必有一段"复现方法"：具体输入＋观察到的错＋（修后）观察到的对；说不出复现方法，**按正文直接判未验证**。
- 复现脚本要幂等（重复跑结果不变）：同一输入跑三次都红才算稳定复现。
- 根因那栏必须还能被"再问一次为什么"问倒——问不出说明已经到底。
- [推演] 无测试基建时的合法降级：用一次性复现脚本充当测试，**仍要求红→绿两个状态**（正文未写此降级，是本页对⑧与⑥降级路径同构的推断）。会出问题的情形：并发时序缺陷单次运行无法稳定复现，此时"红"的判据换成"N 次运行出现 M 次"，仍须给原始输出，不许凭印象说"经常"。

## 第 12 章 纪律⑨「结构自觉」——高内聚、低耦合、单一事实源

**原句要点**[实测]（第 9 条）：一件事的代码住一起（内聚）；模块之间只走明面接口、不伸手进别人抽屉（耦合）；同一条常量／规则只许出现在一个文件里，其他地方一律 import（单一事实源）；动手前自问「改这个功能要动几个文件」——超过 3 个先停下画草图再决定。

**三种结构病**

- **内聚不足**：一个功能的代码散在四处。后果：改一个功能要在四个文件做四次同性修改，漏掉那处不会立刻报错，会在某个用户按了某个按钮之后才报。
- **耦合过高**：A 直接读 B 的内部变量、猜 B 的数据形状（不走出 B 的接口）。后果：B 重构自己的内部实现，A 就坏了，而 B 根本不知道 A 存在。**这类 bug 最难查，因为改动和报错不在同一个模块。**
- **单一事实源缺失**：同一条阈值／文案／评分口径在三个文件各抄一份。后果：改两处漏一处，前端显示一个数、后端算出另一个数，两个数字对不上（勾稽＝两处数字能对上）。`CHANGELOG.md` 的 v2.0 节把这次整理列为该版三大实战案例之一：散落的打分口径归进一个被各处引用的口径文件。

**「超过 3 个文件先停」里的 3**

- 为什么是 3？[推演]（校准依据未检索到，正文只给数）1 个不用想，2 个能肉眼核对，**3 个开始需要一张地图**——文件间的两两牵连已是三条边，此时"改这个会不会影响那个"的脑内模拟误差明显上升。它不是好坏分界线，而是**从"随手改"切到"先画草图"的成本拐点**。
- **什么输入会让它出问题**：一个改名任务天生要动 12 个文件，但风险极低（机械替换＋全量回归），这时"超 3 先停"给出的是错误信号。正确执行是把草图内容换成"这是机械改动、覆盖方式是全局替换＋回归"——**停下这步照做，但草图结论是"放行"**；这条要求的是停一下，不是不许改。

**为什么最容易被跳过**：②③管单点改动是否克制，⑨管改动落点是否合理；⑨是唯一要求**动手前先画一张图**的纪律，而画图的成本立刻发生、收益三个月后才发生。它和⑧那句"半年后会不会变成第二个 bug"配套：若同一规则存在三份，你根本无法"改到根上"，只能三处都打补丁——那半年后的第二个 bug 就是**必然结果，而不是风险**。

**怎么算做到**：动手前的文本里有一句"预计改动 N 个文件：A（…）、B（…）"（数法：列出文件相对路径清单后计数），N>3 时旁边必须还有一份草图（模块与接口关系，五行以内即可）；新写的常量／阈值／口径串交付前做一次全文检索，自问"这词在仓库里是第几份"，第 2 份及以上就改成引用——可核对判据：同一字符串命中文件数＝1。

## 第 13 章 失效与恢复：这套规矩自己会怎么坏

讲**纪律本身**怎么坏；1–5、7、9 都在版本注记或 `CHANGELOG.md` 里真发生过。

| # | 失效模式 | 怎么发现 | 怎么退／修 | 证据 |
|---|---|---|---|---|
| 1 | **漏触发**：沾代码却没加载 | 事后看形状：无【事实/假设】分标、没跑验证 | "拿不准一律触发"兜底；仍漏就补触发词 | [实测] |
| 2 | **依赖悬空**：纪律指向的东西不存在 | 造一个报错任务，看它有没有真去读索引 | v2.1：注册该件＋**加降级路径**，硬依赖改软依赖 | [实测] v2.1 |
| 3 | **副本漂移**：本体／宿主副本／共享源不一致 | 比对三处 `version` 与内容指纹 | 同步改＋核指纹；正文"两处编号一致"就是防这个 | [实测] v2.0／v2.1 |
| 4 | **纪律膨胀**：外部守则整包粘贴 | 每条的遵守率同时下滑 | 奥卡姆剃刀筛：**并入而不新开** | [实测] v2.0 |
| 5 | **写了却从不被调用**：调度统计为 0 | 看调度统计，0 就是"不存在" | 把入口指路句写进常驻条文（v2.2 干的事） | [实测] v2.2 |
| 6 | **口头遵守**：宣布"我很严谨"而无产物 | 核对产物：清单／复现方法／原始输出 | 每条都配"怎么算做到"，判据要留下**第三方能查的东西** | [推演] |
| 7 | **过度教条**：改错字也走全套 | 改动 1 行却附一份流程报告 | 正文自开出口："简单任务…不必走全部流程" | [实测]「执行」 |
| 8 | **被绕过**：把大改自称"简单任务" | 出口只举两例、**没有判据** | 本页补充收口：出口只对"改动 ≤1 行且不改行为"开放 | [推演] |
| 9 | **静默自夸**：说"更快了"却没有两侧输出 | 索要输出文件，拿不出即未验证 | ⑦硬判据：每句"提升"指得出可复现证据 | [实测] 第 7 条 |

一处要摊开的**内在张力** [实测]：「执行」第 1 步声明"本文件自足，无需外部依赖"，⑥却依赖外部记录。两句不矛盾（文本自足 ≠ 执行零依赖），但若有人照"零依赖"去裁剪、删掉那两处指针，⑥会**无声退化**成"自己想"。

这也解释了公开页为什么把路径**抽象掉而不是删掉指针**：指针的作用域是编辑它的那台机器；删掉它，这条纪律在公开仓库里就少了一半可执行性。

## 第 14 章 怎么验证它真在生效（体检）

本支**无可执行体检脚本**（附属件只有 `CHANGELOG.md`，没有 scripts；带脚本体检的是别支），故本章按口径要求改写为"怎么验证它真在生效"，用三个探针（探针＝只检查不修改的动作）。

- **探针 1·触发探针**：问一句**刻意避开清单原词**的话，如"这段 `select` 写得有没有坑"（没出现"代码""审查"）。绿＝按纪律形状走（先确认目标、分【事实/假设】、动手前给改动文件数）；红＝直接给结论、无分标 → 触发面靠字面词命中、语义覆盖不足，需补词或依赖宿主模糊匹配。
- **探针 2·产物探针**：造一个必然报错的小任务，看四件事有没有发生——读完整输出与退出码、连败三次后停下、停下之后**去翻索引**、收尾问一句要不要沉淀。关键：**必须造一个"第三次才失败"的场景**，否则永远测不到熔断。
- **探针 3·依赖与版本探针**：核对本体 `metadata.version` 与版本节最新一条同名；核对本仓库跟踪的正文与权威库正文是否同版本（本页页眉就是这条探针的一次输出记录：库 v2.2／仓库 v2.1）；核对本支引用的两样外部件此刻是否存在——任一"引用了但不存在"＝失效模式 2 当场复现。
- 频率：每次改 `description` 或本体后跑探针 1、2；每次新增联动 skill、每次给 skill 库搬家之后跑探针 3；平时每季度抽查一次 [推演]。
- 顺手一条：在仓库根跑自带的 `python library_check.py`（本仓库确有该脚本 [实测]），它能扫全库清单与回链，但管不到纪律内容。

## 第 15 章 端到端走查（一条可照抄的输入）

> 项目名与文件路径都是本页编的通用形状，不含任何真实机器信息。

**输入（可逐字发给 AI）**：

> "订单列表筛选有问题，我选了'已退款'，结果里还是混着没退款的单子；另外这页打开挺慢的，一起看下。"

- **步 0 触发**：命中触发范围"改 bug／排查／优化"→ 加载九条。
- **步 1 ④定标**：A（筛选）＝选中"已退款"后返回集合里不存在非已退款记录；B（慢）＝先测当前值再谈目标——**"挺慢"是症状不是标准**。
- **步 2 ①列不自信的点**：

```
【事实】筛选走 status 字段；接口返回 items 数组
【假设】后端按单值等值过滤（置信度 中）→ 数组被当单值解析＝A 的根因候选
【假设】"慢"与筛选无因果（置信度 低）→ 未知：慢在数据量，还是同一请求被串行发了两次？
【未知】是否有缓存层掩盖错误结果（未检索到）
要问的一句：这是状态多选还是单选？单选却混返与多选解析错，修的不是同一个地方
```

- **步 3 ⑧第一问（复现）**：写只读复现探针 `repro_filter.py`——调列表查询函数喂 `status="refunded"`，断言每条 status 都等于 refunded，打印实际分布（不碰业务代码）。跑一次 → **红**（分布里混着 12 条 `pending`），同时证明判据有鉴别力；再跑两次，三次都红 → 稳定复现且**幂等**。
- **步 4 ⑧第二问**：把那条断言搬进 `test_order_filter.py::test_refunded_only`，确认它在旧代码上是红的；红 → 它从此是这条 bug 的哨兵。
- **步 5 ⑧第三问（连问三层）**：为什么混入？→ 拼条件时把 status 当字符串等值比较。为什么当字符串？→ 前端多选提交数组、接口层直接透传。为什么透传？→ 接口层没有参数形状校验，约定只写在注释里。**根因＝契约没被代码化。**
- **步 6 ⑥查坑（步 3 报红那一刻就该做）**：扫共享踩坑日志的根因索引表，比对识别信号"筛选条件失效／多状态混返"。命中→照通用对策试（省半小时）；未命中→继续步 5、修完在步 11 沉淀；该 skill 不可用→走降级路径直读索引文件。
- **步 7 ②③动手**：只改接口层那 3 行（把 `status` 归一成集合再过滤），不顺手重排、不预埋"多字段组合筛选"。diff 自检：4 行改动（含 1 行注释），逐行能回答"不改它任务会不会失败"。
- **步 8 ⑨结构判定**：改动文件数＝2（接口层＋测试）→ 不超 3，免草图。但自问"参数形状的约定现在有几份"→ 注释一份、代码一份 → 删注释那份，让代码成为单一事实源。
- **步 9 ⑤验证**：跑 `test_order_filter.py` 全量 → 绿，读**完整输出**与退出码（不只第一行）；再跑老用例（回归）确认"未付款""部分退款"没被改坏；退出码 0 才算过。B（慢）：给出改动前后**两次实测并排**的原始输出；没做对照就不许说"变快了"，只说"耗时 620ms，本次改动未触碰该路径"。
- **步 10 ⑦证明**：对抗式自查，构造三个让它翻车的输入——`status=[]`（空数组）、`status="hacked"`（非法值）、分页与筛选同时存在，各附一条输出；若为 B 加了缓存就必须消融（拆掉缓存重跑，耗时没变 → 缓存白加、删）；再横向扫"同类毛病别处还藏几份"→ 全仓搜"数组当单值比较"，命中用户列表一处 → **报告但不擅自改**（③）。
- **步 11 ⑥回写**：步 6 未命中即新坑——通用部分进共享踩坑日志，本机私有部分（比如只在这台机器存在的缓存层）进本地记录。

**产出形状（交付模板，可照抄）**：

```
成功标准  A：选中"已退款"后返回集合内无非已退款记录 —— 已达成（原始输出见证据）
          B：首屏耗时实测值 620ms；本次改动未涉及该路径，不宣称变快
根因      接口层把多选数组当单值等值比较；契约形状只写在注释里，未代码化
改动      外科式 4 行：src/api/orders.py 归一 status 后按集合过滤；
          tests/test_order_filter.py 新增哨兵用例
证据      复现＝改前红（分布含 12 条 pending）→ 改后绿；复现脚本三次一致（幂等）

          对抗＝空数组／非法值／分页＋筛选同现，各有输出
          扩散＝同类"数组当单值"另命中 1 处（用户列表），未改，等你决定
不自信的点 【假设】前端始终提交数组（置信度 中）→ 若有入口提交单值，归一逻辑要再确认
          【未知】是否有缓存掩盖结果（未检索到）
```

## 第 16 章 反模式清单（不要这样用）

1. **把九条当口号念一遍**：开头写"我将遵循编码准则"、全程无产物形状——纪律沦为装饰（失效 6）。
2. **用"我觉得挺严谨"代替判据**：核对只要一句"你的证据文件叫什么"，答不出即未做。
3. **一次改十个文件还说"顺手清理"**：diff 不可评审、回归范围无法圈定；要清理就另开"仅格式化"任务并跑全量回归。
4. **没跑过就说"应该可以了"**：⑤明令禁止这句话本身，它就是当场可抓的违规证据。
5. **只看输出第一段就宣布成功**：报错常在 stderr、在最后二十行，或只体现为退出码非 0。
6. **连败第 4 次还换姿势硬磕**：三次同类失败已否证你的模型；熔断要接⑥换手段，不是停工。
7. **遇报错先脑补二十分钟不查坑**：真需要检索的时刻，恰是最不想停下来检索的时刻——这就是⑥被写成"强制"的全部理由。
8. **报指标只报一个数**（"58.8 涨到 62.9"）：没有样本量、两侧原始输出、消融对照，就推不出"改动有效"。
9. **把运气当功绩**：效果类改进不做消融；拆掉零件分数不掉，那零件就是噪音，按正文应当删。
10. **把外部守则整包粘进规则文件**：不做奥卡姆筛选就搬别人八条，条数膨胀、每条分到的注意力变薄，遵守率全线下降。本支的做法是筛掉四项、并入一项、新开三项。
11. **在纪律里硬编码盘符路径或记忆条目编号**：一搬家或一重编号就全部悬空（失效 2 的成因），公开仓库更绝不能带路径。
12. **让简单任务走全套，或反过来把"简单任务"当万能后门**：正文开了出口却没给判据，于是"重写整个模块"也能自称简单——本支最实的两个反向漏洞（见 18.5）。
13. **只在讨论时遵守、提交时不遵守**：纪律的核对点在 diff 与输出上，不在对话语气上。
14. **修完一个可见缺陷就结案**：别处那几份没有任何症状，完成感会让你永远觉得不着急——不扫＝只修了一半。

## 第 18 章 工程与安全规范

### 18.1 命名、字段与引用形态

- 目录名带体系前缀（`A-Cao-编码行为准则-写码改bug审查重构`）便于人按主题浏览，`name: coding-behavior` 给调度层点名——人点名时两种都认，脚本引用用短名。
- 文件名固定：`SKILL.md` 本体、`CHANGELOG.md` 迭代记录；`description` 必须**同时写清"什么时候触发"与"触发后干什么"**，否则加载了也不知道该执行什么。
- 引用禁止行号；论断标 `[实测]`／`[推演]`，`[推演]` 必须附"什么输入会让它出问题"；不确定写「未检索到」，禁止编项目名、URL、版本号、规范条款。

### 18.2 副本同步 [实测]

- 同一套九条存在于三处：本体、宿主副本、共享源。改动要**同步改并核指纹**（版本注记里出现过"与权威库双副本同步改""md5 一致"这样的字句）。
- **编号要对齐**：正文那句"两处编号一致"，防的就是同一条在两个文件里叫不同序号。
- 历史上真漂过一次：宿主副本停在 v1.1、库里已到 v1.2，`CHANGELOG.md` 记了一次"登记宿主副本向库同步"；这类漂移很难查，症状是"它有时守有时不守"。
- 共享源属记忆规则区，默认按**只读铁律**处理；正文那句"已于某日同步九条"记录的是一次**用户明确授权之后**才解除只读——授权前不动它。

### 18.3 冷启动（新机器／新 clone）

- 只 clone 仓库即可用：九条全在 `SKILL.md` 里，读得到就执行得了。
- 外部件缺失时⑥按降级路径直读索引文件；索引也没有时⑥退化、其余八条照常——这就是"文本自足"的真实边界。
- 冷启动第一件事：跑第 14 章三个探针，确认触发面在这个宿主上真命中、外部件此刻存在。

### 18.4 公开仓库的隐私红线

本仓库是公开仓库，而权威库正文天然带机器指纹，所以：

- **不写盘符绝对路径**：一律"本机 skill 库""共享踩坑日志索引""仓库内相对链接"；本支正文那两处指针在本页全部抽象化。
- **不写记忆条目编号与存储目录名**：写成"一条工作记忆记录""某次事故""本地踩坑记录"。
- **不写任何 agent 代号与宿主产品名**：写成"某个 agent""宿主"。
- **凭据**：本支不涉及；若举例只写"凭据／密钥"四个字，样例值用 `<你的密钥>` 占位。
- 允许例外：通用工具名与环境事实（Windows、Git Bash、`py`、GitHub 等），不构成隐私。
- 🔴 反面教训：**公开页页眉不要照抄库里的路径**——本仓库跟踪的旧正文仍带着一条指向已作废机器的路径指针，它会跟着仓库一起公开出去；本页不模仿，也不去改它（不在本页写入权限内）。
