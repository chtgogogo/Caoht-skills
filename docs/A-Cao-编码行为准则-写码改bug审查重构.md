# A-Cao-编码行为准则（coding-behavior v1.2）

> [← 返回总目录](../README.md#skills-index)

让 AI 改一个错别字，它改完了，顺手重排了整段格式，"优化"两个变量名，还删了段它觉得没用的注释。让它修 bug，修完说"应该可以了"，你问跑过吗，它承认没跑。

这些行为的根子是一个东西。猜一个理解比问你一句省事，说"应该可以"比真跑一遍省事。AI 写代码默认怎么省事怎么来，而它的每一次省事，买单的都是你的返工时间。

光骂没有用，得有约束。这个 skill 是六条纪律，每条针对一个具体的坏习惯，写了"什么算违反"和"怎么算做到"。

## 六条各堵什么

**思考优先**，堵"不问就猜"。需求模糊先问，猜错方向写两千行的返工成本，够你回答一百个问题。

**极简**，堵"预埋功能"。要一个加法函数，不许交付一个带泛型、可配置、带日志的运算框架。

**外科修改**，堵"顺手大扫除"。只碰跟任务直接相关的行。这条来自一次真事，改 bug 时顺手改了无关代码，返工时间比修 bug 本身还长。

**目标驱动**，堵"做完无法判定"。动手前先定"什么现象出现算做成"，没有成功标准的任务，做完连有没有做成都说不清。

**验证纪律**，堵"应该可以了"。声称完成前必须实际运行，读完整输出和退出码。这条里还埋着半句最值钱的：同一个问题连败三次，立刻停下重新分析。它来自一次连试十几次都没定位到问题的经历，那十几次的浪费，第三次就能止住。

**遇错先查坑**，堵"从零排查"。报错、反复失败、结果反常，先翻踩坑日志的根因层，看这个坑是不是已经有现成对策。前五条管怎么干活，这条管去哪找答案。

## 两个设计决策

**触发面故意放得很宽。** 只要沾代码就加载，拿不准时一律触发。这里算过一笔账：纪律触发十次，九次是多余的，漏掉一次是致命的，宁可九次多余。大多数 skill 的问题是想不起来调用，这个 skill 反着来，把漏触发降到零。

**六条全部内联正文。** 最初五条纪律写在单独的引用文件里，看起来整洁。换台机器别人 clone 下来，那个文件根本不存在，skill 直接报废。v1.1 把纪律全部搬进正文，文件结构难看了点，跨机器就能用了。规则必须跟着文件走，文件必须跟人走。

## 跟"往规则文件里贴要求"的区别

现在流行在项目规则文件里写"你要严谨、你要优雅"。这类话 AI 执行不了，它自己觉得严谨了，你没觉得。区别在于这里每条纪律都写得出"怎么算做到"。

| 常见写法 | 这里怎么写 |
|---|---|
| 写代码要严谨优雅 | 声称完成前实际运行，读完整输出和退出码 |
| 一大段综合行为准则 | 六条各堵一个毛病，每条说得出它来自哪次事故 |
| 靠 AI 自己想起来 | 沾代码就触发，宁多勿漏 |
| 失败了没有出口 | 连败三次强制停下，遇错先查坑 |

## 什么时候不用

纯闲聊、写作、翻译这类零代码任务，不触发。你要做大范围重构或格式整理，对话里说一声，它会放宽外科修改的约束。纪律是给你服务的，不是绑住你的。
