# A-Cao-编码行为准则（coding-behavior v2.1）

> [← 返回总目录](../README.md#skills-index)

## 五分钟速览


1. 九条纪律各堵一个具体的坏习惯，每条都写得出「什么算违反」和「怎么算做到」，没有一条是「你要严谨」这种空话。
2. 触发面故意放得极宽，只要沾代码就加载，拿不准时一律触发。宁多勿漏。
3. 九条全部内联在本体正文里，不依赖任何外部文件，换机器 clone 下来就能用。
4. 和踩坑日志、记忆纪律、五模板是联动的。遇错先查坑是其中一条纪律，不是可选建议。
5. 同一问题连败三次必须停下重新分析。这条救过的时间比其他八条加起来还多。

一句话概括设计目标，**把 AI 写码时每次「怎么省事怎么来」的冲动，换成一条条可检验的硬规矩**。

## 它在解决什么问题

让 AI 改一个错别字，它改完了，顺手重排整段格式，「优化」两个变量名，还删了段它觉得没用的注释。让它修 bug，修完说「应该可以了」，你问跑过吗，它承认没跑。

这些行为的根子是一个东西。猜一个理解比问你一句省事，说「应该可以」比真跑一遍省事。AI 写代码默认怎么省事怎么来，而它的每一次省事，买单的都是你的返工时间。

| 故障 | 表现 | 对应纪律 |
|---|---|---|
| 不问就猜 | 需求模糊，猜个方向写两千行 | ① 思考优先 |
| 预埋功能 | 要个加法函数，交付一个运算框架 | ② 极简 |
| 顺手大扫除 | 改错别字捎带重排全文件 | ③ 外科修改 |
| 做完无法判定 | 干完了，但没人说得清「做成」长什么样 | ④ 目标驱动 |
| 应该可以了 | 没跑过就说修好了 | ⑤ 验证纪律 |
| 从零排查 | 报错硬磕，翻遍踩过同样的坑的记录 | ⑥ 遇错先查坑 |
| 自说自话 | 声称「更快更准」，拿不出证据 | ⑦ 证明优先 |
| 打补丁盖症状 | 修了表层，根因还在，半年后变成第二个 bug | ⑧ 溯源调试 |
| 改一处动全身 | 一个功能横跨五六个文件，牵一发动全身 | ⑨ 结构自觉 |

## 九条纪律详解

每条给出「堵什么毛病」和「怎么算做到」。做到的判定标准比纪律本身更重要，因为 AI 可以宣布自己「很严谨」，但没法假装自己跑过测试。

**① 思考优先。** 不确定先问，禁止猜了继续干。动手前先想清楚方案再落键。交付前列出所有不自信的点，结论分【事实】和【假设】并标置信度，证据不足就写「未知」。算过一笔账，猜错方向写两千行的返工成本，够你回答一百个问题。

**② 极简。** 只做明确要求的事，禁止预埋未来功能，禁止顺手大扫除。预埋的代码不是资产，是下次阅读时的噪音和下次修改时的风险。

**③ 外科修改。** 只改与任务直接相关的代码，不碰无关行，改动面最小化。这条来自一次真事，改 bug 时顺手改了无关代码，返工时间比修 bug 本身还长。评审一个 diff 的时候，每一行无关改动都在稀释真正要紧的那几行。

**④ 目标驱动。** 动手前先定可验证的成功标准，什么现象出现等于做成了。没有成功标准的任务，做完连有没有做成都说不清。

**⑤ 验证纪律。** 声称完成前必须实际运行验证，读完整输出和退出码。未验证禁说「应该可以/修好了」。这里埋着半句最值钱的，**同一问题连败三次，立刻停下重新分析，不许硬磕**。它来自一次连试十几次都没定位到问题的经历，那十几次的浪费，第三次就能止住。连败三次说明你对问题的理解模型是错的，再多试几次只是换着姿势错。

**⑥ 遇错先查坑。** 报错、反复失败、反常现象，先检索踩坑日志（skill 不可用时直接读索引文件），先扫根因索引表看识别信号对不对得上，对得上就照通用对策试。v2.1 把这条升级成闭环，反复出现或连败三次的 bug，动手前强制翻一次踩坑日志，修完把新坑沉淀回去（通用坑记踩坑日志，本机私有坑记自己 store 的 PITFALL）。前五条管怎么干活，这条管去哪找答案，别重踩别人踩过的坑。

**⑦ 证明优先。** 声称「修好了/更快了/更准了」之前先当自己的对手。假设这个改动是错的，主动找反例、跑边界、构造让它翻车的输入。效果类改进必须做消融实验，拆掉新加的零件重跑评测，分数掉了才证明零件值钱，没掉就删掉。检验标准一句话，每句「有用/提升」后面都指得出可复现证据。Prove it, don't tell me。

**⑧ 溯源调试。** 修 bug 三连问，一问不过就不许动手写补丁。复现了吗（先造稳定复现步骤），测试红了吗（先让测试失败），根因是什么（连问三层为什么）。治根因不治症状。往旧结构上打补丁前先问一句，半年后它会不会变成第二个 bug。说不出复现方法的修复视为未验证。

**⑨ 结构自觉。** 一件事的代码住一起（高内聚），模块之间只走明面接口、不伸手进别人抽屉（低耦合）。同一条常量或规则只许出现在一个文件里，其他地方一律 import（单一事实源）。动手前自问「改这个功能要动几个文件」，超过三个先停下画草图再决定。

## 两个设计决策

**触发面为什么故意放宽。** 只要沾代码就加载，拿不准时一律触发。这笔账是这么算的，纪律触发十次，九次是多余的，漏掉一次是致命的，宁可九次多余。大多数 skill 的问题是想起不来调用，这个 skill 反着来，把漏触发降到零。

**为什么全部内联正文。** 早期纪律写在单独的引用文件里，看起来整洁。换台机器别人 clone 下来，那个文件根本不存在，skill 直接报废。后来把纪律全部搬进正文，文件结构难看了点，跨机器就能用了。规则必须跟着文件走，文件必须跟人走。更细的展开解释才读共享源，共享源缺失不影响本体使用。

## 版本演进的两条主线

九条不是一次写出来的。v1.1 是五条（思考优先/极简/外科修改/目标驱动/验证纪律），v1.2 加「遇错先查坑」启动钩子。v2.0 吸收 Karpathy 八原则（GitHub 六万+ Star 的 AI 编程守则）扩成九条，新增证明优先、溯源调试、结构自觉，实战依据是失物招领系统 v12/v13 迭代（四十对评测集驱动，F1 从 58.8% 到 62.9%）。v2.1（2026-09-23）给第六条补了降级路径和沉淀闭环，修掉了踩坑日志此前未注册到宿主导致的悬空引用。

每次扩条的规律是一样的，先在实战里疼一次，再问「哪条纪律能拦住它」。

## 跟「往规则文件里贴要求」的区别

现在流行在项目规则文件里写「你要严谨、你要优雅」。这类话 AI 执行不了，它自己觉得严谨了，你没觉得。区别在于这里每条纪律都写得出「怎么算做到」。

| 常见写法 | 这里怎么写 |
|---|---|
| 写代码要严谨优雅 | 声称完成前实际运行，读完整输出和退出码 |
| 一大段综合行为准则 | 九条各堵一个毛病，每条说得出它来自哪次事故 |
| 靠 AI 自己想起来 | 沾代码就触发，宁多勿漏 |
| 失败了没有出口 | 连败三次强制停下，遇错先查坑再动手 |
| 修完就完了 | 新坑沉淀回踩坑日志，形成闭环 |

## 什么时候不用

纯闲聊、写作、翻译这类零代码任务，不触发。你要做大范围重构或格式整理，对话里说一声，它会放宽外科修改的约束。纪律是给你服务的，约束你自己也可以解除。
