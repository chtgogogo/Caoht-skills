## 第 0 章 五分钟速览

1. **目标**：同一个请求，没结构时拿到一个能跑的 demo（演示品），有结构时拿到一个能推出、能维护、能扩展的版本。
2. 它只做一件事：给五种高频工程场景各配一套**固定视角＋固定交付清单**——①构建应用 ②审查现有代码 ③找 bug（缺陷）真根因 ④设计可扩展架构 ⑤想法转计划。路由全在 `SKILL.md`「第一步：对号入座（选模板）」那张五行表。
3. **不是角色扮演**：`SKILL.md` 开篇条与 `CHANGELOG.md`「v1.0 初版」同说一句——原版是社交平台流传的五条"你是资深工程师"提示词，本支把它转译成可逐项验收的产出物清单：触发后不是念模板，是按清单干活。
4. **主体极短、细则外挂**：正文只 42 行，五套清单各占一个文件，命中哪个场景才读哪个（渐进披露＝不相关细节不进上下文，省 token（计费单位）就是省钱）。
5. **六条横切纪律盖在所有模板之上**：照守编码纪律／只问会白干的问题／数字不脑补／验证纪律／磁盘红线／不讨好。
6. **收工一张 4 项自检单**（`SKILL.md`「交付自检」）。
7. **三个硬数字**：交付件数按模板 8／5／6／9／10；找 bug 的输入 5 个；同一问题**连败 3 次必须停手**。

> 面试版一句话：这不是攒了五段提示词，而是**把五种交付的成功标准外化成清单，再用六条纪律堵住 AI 最爱犯的六种偷懒**。

## 第 1 章 这套系统在解决什么问题

你说"帮我做个记孩子读书打卡的小应用"。AI 给一个网页：输入框＋列表，能加能删，然后没了——没存储、没验证、没"怎么跑起来"、没下一步。根因不在能力，在**请求与交付之间没有结构**：它按自己"差不多"的粒度收工，缺什么全看运气。

| 故障 | 表现 | 解法（出处） |
|---|---|---|
| 交付粒度随机 | 要产品给 demo | 固定件数清单 8／5／6／9／10（各模板"交付"节） |
| 编造数字 | 没说量级就报"支持 5000 QPS" | 纪律 3＋④「四个输入」缺就分档 |
| 讨好式反馈 | 伪需求也说"很棒" | 纪律 6＋⑤「缺陷直说」红旗句式 |
| 提问方向错 | 反问"React 还是 Vue"，不问给谁用 | 纪律 2＋①「第 1 步」只许问三项 |
| 未验证就声称 | "应该可以了"，其实没跑 | 纪律 4＋①"验证不过＝未完成"＋③铁律 |
| 顺手大扫除 | 让它看问题，它改了全部代码风格 | ②第 4 件"外科修改，只动相关行" |
| 修表不打补丁 | 同一 bug 修三次还犯 | ③信条"治标不治本的修复，是下一个 bug 的预订" |
| 只看末行报错 | 几十行栈只读最后一行 | ③"读完整报错栈和日志，不许只看最后一行" |

**第一条最关键**：其余七条是"别做错"，它是"做完整"。清单只能保证不缺项，**项里填真货还是编货**由横切纪律管——这就是正文把「路由表＋通用纪律＋自检单」三块放在一起的原因，缺一块另两块都失效。[实测]

## 第 2 章 术语表

### 2.1 本支自己的词

- **模板①–⑤**＝"这次要交出哪几样东西"的固定单子，不是话术；**交付清单**＝单子上的条目。
- **对号入座（路由）**＝听关键词决定用哪张单子；**视角**＝假装自己是谁来干：全栈／进陌生项目的新人／调试工程师／架构师／产品经理。
- **降级条款**＝项目太小时某件允许换轻量版，但必须注明为什么；**分档方案**＝不知量级就按 ≤千／≥万 各给一套。
- **权衡取舍行**＝每个重大决定补一句"换来什么、代价是什么"；**红旗**＝硬伤告警句式：红旗＋为什么是问题＋怎么绕开。
- **占位符 `[数字]``[数据]`**＝留给真实数据的空格，没填就不许假装填了。
- **串联／接力**＝五张单子首尾相接；⑤拍板后直接进①，不用重讲需求。

### 2.2 行话（中文行话也要解释）

- **判据**＝可执行的判定标准，能一句话回答"够不够"；**量级**＝数量的位数（百／千／万／十万），不是精确值。
- **渐进披露**＝平时只读薄索引，命中才加载细节；**落盘**＝真写成文件存进硬盘，不是只在对话里显示。
- **退出码**＝程序跑完留给系统的数字，0 通常代表成功；**报错栈**＝崩溃时的"出事路线图"，全读才知道谁把谁带崩。
- **先红后绿**＝先写个能稳定复现问题的测试让它失败，修完再跑变通过；**外科修改**＝只碰相关那几行，不美化无关代码。
- **熔断**＝失败到约定次数就强制停机换思路；**过度设计**＝规模没到却上大规模方案，白付复杂度。
- **功能蔓延**＝该做最小版本却越加越多，最后做不完；**MVP（最小可行版本）**＝能验证"值不值得"的最小一坨功能。
- **北极星指标**＝只留一个、最能代表成败的数字；**幂等**＝重复做结果不变。
- **认知索引（AOCI）**＝大项目的"目录＋地图"，先读地图再读代码；**aligned**＝索引标"与当前代码一致"的状态值。
- **N+1 查询**＝查列表 1 次再为每行查 1 次，100 行＝101 次数据库往返；**循环依赖**＝A 需要 B、B 又需要 A，改一处崩两处。
- **魔法数字**＝代码里裸写个数字（如 `86400000`）没人知道含义；**O(n²)**＝数据翻 10 倍耗时翻 100 倍。
- **虚拟化列表**＝只渲染屏幕上那十几行，滚动时换着渲染；**探针**＝只检查不改东西的小脚本。
- **口径**＝一批文档共用的统一判定标准；**统稿方**＝统筹这批手册、定标准并实测数字的调度方（不是这支 skill 的一部分）。
- **正本／本体**＝同一个文件的两份拷贝：库内那份叫正本（权威原文），公开仓库里那份叫本体；**静默漂移**＝两份内容不同却都标同一个版本号，看不出谁新；**递归复测**＝把目录一层层全列出来重数一遍（只数第一层会漏东西）。
- **数法**＝这个数是怎么数出来的（按什么单位、什么分隔），同一份东西按不同数法能得到不同数字；**字节**＝文本占多少存储空间的单位，一个汉字在常见编码下占 3 字节。
- **勾稽**（两处数字能对上）、**回注**（把内容再塞回上下文）、幂等、探针——本支都不使用，原因见 9.3。

## 第 3 章 结构与分层：为什么主体只有 42 行

| 层 | 装什么 | 实测体量 | 加载时机 |
|---|---|---|---|
| L1 路由层 `SKILL.md` | 对号入座表＋3 条路由细则＋6 条纪律＋4 项自检 | 42 行／3,729 B | 触发即读，唯一必读 |
| L2 细则层 `references/` | ①–⑤ 各一份工作流＋清单＋纪律 | 10,418 B（2,545／1,742／1,937／1,777／2,417） | **命中才读** |
| L3 挂接层 | 编码纪律、测试纪律、AOCI、磁盘红线 | 0 B（只写"照守／遵循"） | 内容由被挂接那支负责 |

**每层为什么必须在**：L1 不装五套清单，因为全塞进去等于每次"改个按钮颜色"也强灌五套工程模板，注意力被条目稀释反而更易漏项；42 行不是写短了，是**只留决策信息**——走哪张单、什么先问、什么不许编、收工查什么。[推演] 反证输入＝"帮我把这个函数改一下"，这类小改动本不该读任何细则。L2 按**场景**命名（`build-app.md` 而非 `template-1.md`），因为路由发生在任务开头，那时只知道场景不知道走到哪步；用编号名会逼模型回头查表，多一跳就多一次跳错。[实测] L3 只写指针不抄正文，因为同一条纪律写两遍、改一处漏一处必然漂移。`CHANGELOG.md`（3,382 B）只记来源与变更，不参与执行。

**判定顺序**（命中多个场景时）：

```
1 听关键词，对照五行表，列出所有命中场景
2 命中几个读几个；只命中一个就只读一个（省上下文）
3 ②③拿不准用判据分家：要"整体分析改进"→②；抓"某一个具体 bug"→③
4 还不一定 → 宁多勿少（description 原文：宁多触发勿少触发）
```

第 4 条不含糊：多读一份细则的代价约 2 KB 上下文，选错模板的代价是一整份交付缺项，差两个量级。

**五张单子怎么串**：`⑤想法 →（你拍板）→ ①构建 →（出问题）→ ③根因 →（做完回看）→ ②审查`，④在①之前或之中按需插入（出处：`SKILL.md`「第一步」末条＋⑤「与模板①的接力」）。④的位置是本页[推演]：①「第 0 步」本身就是一次压缩版④，只有要容量权衡（用户量／并发／缓存）才把④单独拉出来走完整九件；会暴露它的输入＝"给一百人用的内部系统"，只走①会缺缓存策略、安全性、错误管理三件。

**触发词长什么样**：frontmatter `description`（实测 322 个字符；数法：冒号后到行尾逐 Unicode 字符计）写死五组关键词——①"做一个应用／新建项目／从零开发／上线"②"分析这段代码／代码审查／看懂陌生项目／重构／性能排查"③"为什么报错／修不好／反复出问题／根因／调试"④"架构设计／能扛多少用户／高并发"⑤"我有个想法／产品规划／MVP／路线图／值不值得做"；另两条元规则：点名"用模板／五模板／资深工程师模板"必触发、与 `coding-behavior`（编码纪律）叠加不冲突；纯闲聊、纯写作等零代码任务不触发。为什么关键词写在 `description` 而不是正文：它是宿主每次会话都要扫的那行常驻摘要，正文命中才加载，触发判断发生在"正文还没进上下文"那一刻。[实测]

## 第 4 章 模板①构建应用：八件套与"验证不过＝未完成"

**视角**＝高级全栈工程师；目标很硬：不是能跑的 demo，而是**可以推出、维护和扩展的最小版本**（`build-app.md` 开篇条）。工作流四步，原文标"顺序不可乱"。

**第 0 步 写码前先定需求与架构**：一句话定位＋功能清单（分"必须有／以后再说"）＋技术栈与一句理由＋文件结构树。为什么在前：先写码再补说明，说明必然变成对既有代码的事后辩护，"以后再说"那栏永远空着。

**第 1 步 缺重要信息才问**（只这三条，其余"自己定＋说一句理由就开工，不反问"）：①**给谁用／几人用**——原文理由"单机自用 vs 多人在线，架构差一个量级"：1 人不需要登录，2 人开始需要权限，10 人需要账号体系与并发；②**数据要不要持久化、要不要多端同步**——不存数据的应用是玩具，要同步就得先定"哪台是真相源"；③**部署形态：本机／局域网／公网**——决定网络暴露面与安全基线，公网无鉴权就是事故。[推演] 不写这条的样子：一次"做个记账小工具"收到"深色还是浅色""要不要 PWA"五六问，都不影响第一版能否交付。

**第 2 步 交付八件套**：

| 件 | 要求（原文要点） | 少了会怎样 | 降级条款 |
|---|---|---|---|
| 技术决策 | 每项一句理由；重大取舍列"选项＋建议"给你拍板 | 选型变黑箱 | — |
| 文件结构 | 目录树＋每个文件干什么 | 一堆文件不敢动 | — |
| 数据库模式 | 表／字段／关系 | 数据结构只能猜 | 小工具降级为"存储方案说明" |
| API 端点（接口） | 方法＋路径＋入参出参 | 前后端对不上 | 纯本地工具可省**并注明** |
| 界面结构 | 页面／组件清单与跳转关系 | 功能都在没人会用 | — |
| 完整实现 | 全量可运行，**不留"此处省略"** | 拿到残缺代码 | — |
| 安装说明 | 从零到跑通的命令序列 | 只有作者的机器能跑 | — |
| 测试 | 核心路径至少实跑一遍 | 无法证明真能跑 | — |

数法：八件＝「第 2 步」表的数据行数。为什么不是六件：这八件闭环"决策—结构—数据—接口—界面—代码—怎么跑—怎么证"，砍一件收工标准就退化成"看起来差不多"。**降级必须注明**——这是"允许小项目但不允许偷懒"的机关。

**第 3 步 验证后交付**：本机照安装说明跑一遍，**读完整输出与退出码**；Web 给可点开的本地地址（Markdown 链接）；**"验证不过＝未完成，不许说'应该可以'"**。为什么要完整输出与退出码：报错前往往已打几十行有效信息，只看末行会漏真因，而退出码是机器写的结论、比模型转述可信；为什么要可点开链接：那是非开发用户的验收入口。[实测]

**大工程的认知索引分支**（「既有项目上开发」）：根有 `aoci.txt`（那份地图）→ 改动**验证通过后**同步更新受影响条目再收工，原文流程"代码稳定 → 更新认知 → 置回 aligned"；理由照抄：**别让索引和代码漂移，索引过时比没有索引更害人**（没索引你会去读代码，有过时索引你会相信错的地图）。没有但看着像大工程 → 跑适配判定脚本（工具名 `aoci_fit.py`，路径不写）：AUTO 直接建／ASK 问你／SKIP 忽略，三档语义见第 5 章。

**两条本机红线**：① 项目建在**非系统盘**的工作目录并按项目建子目录，严禁落进系统盘默认路径（改写见 15.3；为什么重复写进构建模板：它是唯一大批量新建目录的场景）。② Node（JS 运行环境）两个已知坑：本机某证书工具开着会导致证书校验失败 → 设 `NODE_OPTIONS=--use-system-ca`（让 Node 改用系统证书库）并换国内镜像；puppeteer（无头浏览器库）要拉几百 MB 浏览器内核 → 加 `PUPPETEER_SKIP_DOWNLOAD=true` 跳过。这种"本机八卦"配进模板的理由：它们是真金白银的白干成本，装一次卡一次，新手会以为是自己的代码问题。[实测]

## 第 5 章 模板②审查现有代码：先看懂，再动刀

**视角**＝**刚加入一个陌生项目的资深工程师**（`review-code.md` 开篇条）。视角本身就是机制：它强制承认"我还不懂"，跳过的人会拿文件名猜结构。

**第 0 步 认知索引三档**：根有 `aoci.txt` → **先读索引再碰代码**，拿到架构／职责／数据流的大骨架后再回代码验细节；**索引与代码冲突时以代码为准**（原文理由：索引可能滞后）。没有 → 跑 `aoci_fit.py`：**AUTO**（大工程＋反复开发两信号都成立）直接建索引再干活、完成后告知用户；**ASK**（只有一个信号）弹窗问用户、等答复；**SKIP**（小项目）照常 Read/Grep 从零看懂。为什么分三档：**误建的成本（多扫一次）远小于误不建的成本（大项目里反复重新理解结构）**，所以"两信号才 AUTO、单信号才问你"是用保守换省钱。[推演] 会暴露它的输入＝8 万行但只改一次的项目：不回来改的项目建图是纯浪费。

**阶段一 分析七问**（逐项作答，用实际读到的证据；破折号后是它防的偷懒）：①架构如何组织（分层？单文件？入口在哪）——防"从最顺眼的文件开始读，读三个就开评"；②主要组件是什么（模块／类／函数各管什么）——防只报文件名不报职责；③数据如何流通（输入→存储→输出理出一条主线）——防讲不清一个请求走到哪儿；④哪些代码重复——防说"能优化"却指不出哪几处；⑤哪些结构问题（耦合／职责不清／循环依赖）——防把结构问题误报成 bug；⑥哪些性能问题（N+1 查询／循环里做重活／无缓存／重复 IO）——防没量数据就断言"慢"；⑦哪些维护风险（无测试／硬编码／魔法数字／过期依赖）——防只评当下不看将来。数法：七问＝「阶段一」编号条数。紧跟一条纪律："必须用 Read/Grep 实际读完相关代码再下结论，**禁止凭文件名猜**"——本模板最锋利的一刀，把"看起来像"从合格回答里剔掉。[实测]

**阶段二 交付五件**：

1. **架构总结**：**3–5 句**说清项目干什么、怎么组织。为什么卡 3–5：少于 3 句说不清"怎么搭的"，多于 5 句通常在复述代码＝还没提炼。
2. **按优先级排序的问题**：**P0 崩溃／丢数据 → P1 功能错 → P2 性能／结构 → P3 风格**，每条带证据（文件＋行位置）。为什么"丢数据"与"崩溃"并列 P0：不崩却静默丢数据比当场崩更贵，因为你会发现得更晚；为什么要带证据：没证据的清单第三方无法复核＝新一轮幻觉。
3. **重构计划**：先修哪些后修哪些，**每步能否独立验证**——把重构从一次性大爆炸拆成可回滚的小步。
4. **改进后的代码**：**外科修改，只动与问题直接相关的行，不顺手大扫除**。
5. **证明行为不变的测试**：**改之前**先跑通记录现有行为，**改之后**复跑对比。这是灵魂：重构唯一合格标准是"外部行为一模一样"，而"一模一样"要由两次运行结果对比出来，不是推理出来。

**两条关键纪律**：解释要通俗、多比喻，重点讲"**为什么这么写、为什么有问题**"而不是丢术语（原文这条绑在用户的求职处境上，本页抽象见 15.3；机制价值不依赖那个处境——看懂自己代码的人才能自己改，堆术语只是把依赖从代码转移到 AI）。**大重构先给计划让你拍板再动刀**——它放在"纪律"而非"清单"：清单管交出什么，纪律管**什么时候不许动手**。

## 第 6 章 模板③找真正根因：五输入、六交付、连败 3 次熔断

**视角**＝专注生产系统调试的高级工程师；**信条**（原文首行）："治标不治本的修复，是下一个 bug 的预订。"

**五个输入**（原则"能自己收集的不问用户"）：

| 输入 | 收集方式（原文要点） | 为什么这么定 |
|---|---|---|
| 相关代码 | Read/Grep 自己找，不要用户粘贴；根有 `aoci.txt` 先读索引定位可疑模块 | 让你粘代码是把工具该干的活外包；索引省掉盲搜 |
| 预期行为 | 用户描述；说不清就按常识＋文档推断并**标明是推断** | 预期缺失会导致验收标准缺失；标明才能事后推翻 |
| 实际行为 | 自己复现拿到，能跑就自己跑 | 你的描述是二手信息，转述常把现象抹平成结论 |
| 错误和日志 | **读完整报错栈和日志，不许只看最后一行** | 末行通常是"后果"，真根因在更上面 |
| 重现步骤 | **自己试出最小复现**，实在试不出才问 | 最小复现决定后面所有假设的质量 |

数法：五输入＝「五个输入」表数据行数。第三列标题是"收集方式"而非"由谁提供"——这个措辞把四条推向自查，只有"预期行为"可能问用户。[实测]

**交付六件**：①**真正发生了什么**——一两句白话讲现象背后的机制，多比喻；②**根本原因**——**区分表象（报错那一行）与根因（为什么会走到那一步）**，连问几个为什么问到不能再问；③**受影响的边界情况**——同一根因还会在哪炸，原文举空值／并发／大数据量／极端输入／时区编码，为什么单列：根因确认后同一片土里通常还埋着兄弟 bug；④**健壮的解决方案**——修根因不打补丁，并说明**为什么这个方案健壮、其他方案为什么不选**（后半句是关键，否则"为什么不选别的"永远没人答）；⑤**证明已解决的测试**——**复现脚本先红后绿**，或修复前后输出对比；⑥**无法验证的假设**——格式＝【假设】＋**置信度**＋**推翻条件**。第⑥件最特别：配"推翻条件"等于给未来的自己留一个检查点，那条件一出现结论必须重查——它把"我不确定"从免责声明变成可执行动作。[实测]

**两条铁律**：修复后必须实际运行验证、读完整输出与退出码，**未验证禁说"修好了"**；**同一问题连败 3 次立即停手重新分析方向，不许硬磕第 4 次**。为什么是 3 [推演]：1 次失败说明假设可能错，2 次说明方向可能错，第 3 次还在同方向重试几乎只剩"沉没成本"一个理由，而换方向代价（重读一遍代码）远低于一次无效修补引入的新 bug；取 4 偏晚、取 2 会在正常试错里就放弃。价值在于**可执行**——AI 不会自己判断"我很努力但方向错了"，但能数到 3。与 `Cao-失败模式与对策库` 的"对策优先上计数器级（迭代／预算／超时上限）"同源。

**真跑过的实战**（`CHANGELOG.md` 记实战的那一节；原标题含记忆层名，按隐私红线抽象）：某面板每次点击都全量重建 717 行界面，形成 O(n²)；改**虚拟化列表**后一次刷新从**约 8 分钟降到 6.5 毫秒**，记录明写是"用场景③根因法定位"的。[实测] 值得记住的理由：8 分钟→6.5 毫秒若只是"改完感觉快了"就属不可信汇报，这里给的是同一操作墙钟时间前后对照，恰好符合第⑤件的证据形态。

## 第 7 章 模板④设计可扩展系统：四输入分档与权衡取舍行

**视角**＝资深系统架构师；**核心命题**（原文首行）："架构没有标准答案，只有权衡取舍——每个决定都要说清代价是什么。"

**四个输入与缺失时怎么办**：预期用户数 `[数字]`——问用户要**量级**（百／千／万／十万），拿不到就**给分档方案**；流量 `[数据]`——按 用户数 × 人均请求 估算并**标明估算依据**；预算 `[数据]`——问一句云／服务器预算量级，未知按"个人开发者小预算"默认；限制 `[数据]`——本机环境约束（原文举了存储例子：某个盘只剩约 12 GB、项目写非系统盘、Windows 环境；载体抽象见 15.3）。

四个量级档为什么是这四个 [推演]：它们不是精度选择而是**决策分界点**——百级任何单机方案都够；千级开始有"单进程扛不扛得住"；万级逼出缓存与读写分离；十万级逼出无状态化与多实例；档更多只会让模型在档间反复权衡不产出。原文给的合格形态是"≤1 千用户方案 A，≥1 万用户方案 B"，即**分档必须是两套可比方案，不是折中一套**。「数字不脑补」在本模板被再强调一次（中段独立段）并明文**禁止编造精确值**；为什么两处都写 [推演]：架构是幻觉高发场景，"能不能扛"必须由数字回答，模型有强烈动机补一个显得专业的数——这是本支唯一一次把同一条纪律写两遍。

**交付九件**（数法＝「交付九件＋权衡」编号条数）：①总体架构（**文字版**架构图，模块→模块怎么连；图好看但看不出错，文字逼它把连接写清）②组件及职责（一句话"**负责什么、不负责什么**"，后半句是关键——扯皮几乎都发生在边界上）③数据流（一个典型请求从头走到尾）④API 设计（资源＋方法＋鉴权（谁能进）方式）⑤数据库模式（表结构＋**为什么这么拆**）⑥缓存策略（放什么、怎么失效；原文允许小系统答"**暂不需要，理由是……**"，连"不做"也要带理由）⑦安全性（鉴权／输入校验／密钥管理**至少覆盖三项**）⑧错误管理（报错怎么返回、日志记什么、**怎么降级**）⑨最小可行实现（第一步先落地哪个子集）。为什么第 9 件放进架构模板 [推演]：架构讨论最容易停在一张大而全的图上，把"第一步落地什么"列为交付物就强制把图和开工顺序连起来。

**灵魂要求：每个重大决定附一行权衡取舍**，原文标准样例（值得整段背去讲面试）：

> 选 SQLite（单文件数据库）不选 PostgreSQL（独立数据库服务）：换来零运维、随项目文件走，代价是并发写≈1，日活过千需迁移。

为什么格式是"换来 X，代价 Y"而不只是"我选 X"：它一行里给了选型、收益、代价，以及**代价的触发阈值**（日活过千）——阈值让决定变成可复查的东西，日后规模真过千，这行就是"当初约定该迁移"的凭据；[实测] 顺带解释了"并发写≈1"（SQLite 同一时刻基本只允许一个写操作）为什么可接受：写的人只有你一个时，它约等于不需要排队。

**两条纪律**：**不过度设计**——原文写法很硬，"单机自用的工具给分布式方案＝**违规**"、"架构档次对齐真实规模"，用"违规"这个词是为了让它可判定（清单漏项能看出来，风格过界也能看出来）；**涉及部署落地先查目标盘剩余空间再给存储方案**——容量估算不结合真实剩余空间就是纸上方案。

## 第 8 章 模板⑤想法转执行计划：十件、红旗、与①接力

**视角**＝资深产品经理；**灵魂条款**（原文首行）："**不要试图取悦用户**——想法有缺陷就直说，再说怎么解决。" 纪律 6「不讨好」在这份细则里被放大成整个模板的命根子。

**交付十件**（数法＝「交付十件」编号条数；括注是原文最锋利的半句）：①它解决的问题（**说不清痛点＝最大红旗**）②目标用户（谁用、什么场景、**频率多高**）③价值主张（**好一点点不算，要好到值得切换**）④必不可少的功能（**砍掉就不成立**的最小集合）⑤次要功能（v2 再说，**明确列出防功能蔓延**）⑥MVP（**写可验证的完成标准**）⑦初始架构（**档次对齐目标用户量级**）⑧开发路线图（按周／阶段排，**每阶段有可验收产出**）⑨风险（技术／市场／执行，**各配缓解办法**）⑩监控指标（北极星 **1 个**＋过程指标 **2–3 个**）。

- 为什么第 5 件要写"不做的功能"（十件里最反直觉的一件）：不写出来它会在开发中一个个自己长回来；写进文档标上 v2 等于给功能蔓延装了显式闸口。[实测]
- 为什么第 6 件强调可验证：MVP 最常见的死法是"做到差不多"——没有可验证标准就没人能宣布完成或未完成。
- 指标为什么 1＋2–3 [推演]：一个北极星逼你回答"到底靠什么算成功"，2–3 个过程指标回答"成功之前看什么判断趋势"；多了复盘变成读表，只剩一个则北极星长期不动时失去调整依据。

**红旗：本模板唯一的强制格式**。原文列四类硬伤（**伪需求／已有强势替代品／用户根本不会换工具／技术上不可行**，各堵一种自我感动），必须在**第一部分**指出：

> **红旗**：xxx。**为什么这是问题**：xxx。**怎么解决或绕开**：xxx；解决不了就建议放弃／转向。

四段里"怎么解决或绕开"最容易被跳过也最值钱——只报问题叫丧气，报问题＋路径才叫工程判断；原文紧跟"风险说透但给路：先讲清坑在哪，再给'**如果还是要做**'的最小验证路径"，保证红旗不等于否决。[实测] 为什么必须在第一部分：排到末尾时前面九件已经把坏想法包装成可行项目了——**顺序本身就是反讨好机制**。[推演] 暴露输入＝"我想做个全平台聊天应用"按末尾格式产出的计划书，读起来会像施工许可。

**落成文件与接力**：计划书要落成文件（项目目录下 `计划.md`），原文理由"方便留存和后续接着做"——只在对话里给的计划会话一结束就没了，接力的前提（那份可拍板的文档）不存在。**拍板后无缝衔接①从 MVP 开工**：⑤的输出形状恰好是①第 0 步要的输入（定位＋功能分级＋技术栈＋模块图）。

## 第 9 章 六条通用纪律与四项自检（横切层）

出处：`SKILL.md`「通用交付纪律（所有模板生效前先读）」6 条＋「交付自检（收尾过一遍）」4 项。**五套清单管形状，六条纪律管形状里填的是不是真货。**

1. **coding-behavior 照守**：原文"与编码五纪律叠加，思考优先／极简／外科修改／目标驱动／验证纪律，一条不少"。为什么要显式写：两支同时生效时模型会二选一，写死"叠加"就把选择权拿走；只引用不复制以免漂移。
2. **缺信息先问的边界**：只有"**缺了会白干**"的才问（原文举例：给谁用、数据要不要存、部署到哪），无关选型自己定＋一句理由。为什么用"会白干"当判据：它把提问成本（打断你）与提问收益（避免返工）放上同一架天平。
3. **数字不脑补**：占位符没给就标"未知"＋分档，**禁止编造精确值**。为什么最狠：编造的精确数字是**最危险的一类幻觉**——它长得像知识，你会拿它做决策。
4. **验证纪律落地**：交付"完整实现／测试／修复"必须**真跑通再声称完成**，并写明无法验证的假设。后半句（2026-10-02 联动审计补挂）把**证据形态**交给 `A-Cao-测试纪律`：原始输出落盘、改前改后各跑一次、禁只报总结数字。⚠️ 本仓库副本缺这后半句。分工：本支管"有没有跑"，测试纪律管"证据长什么样才算数"。
5. **磁盘红线**：新项目一律建在非系统盘工作目录；**大文件写入前先查目标盘剩余空间**。后半句为什么单列：容量类失败是延迟引爆的——写进去不报错，几周后满盘时整个环境崩。
6. **不讨好**：有缺陷、有坑就**直说＋给解法**，原文"绝不为让用户开心而弱化问题"。代价是滞后的：缺陷在写码阶段爆出来时，返工的账远贵于当时那句不好听的话。

| 自检四项（原文） | 兜住哪条 | 怎么查 |
|---|---|---|
| 清单逐项齐（真不需要的**注明为什么省略**） | 防粒度随机 | 数小节标题是否等于 8／5／6／9／10 |
| 代码类产物实际运行过，读了完整输出与退出码 | 防未验证声称 | 有没有贴运行输出或可点开链接 |
| 占位数字没有编造，未知项已标明 | 防编数字 | 抓任一精确数字反一句"这数是谁给的" |
| 没有预埋用户没要的功能 | 防功能蔓延 | 逐个功能回指⑤第 4 件 |

数法：4 项＝「交付自检」小节 checkbox 行数。注意第 1 项的括号——**"注明为什么省略"是区分"合法降级"与"偷懒漏项"的唯一办法**。

**本支无此概念清单**：

| 别处有的机制 | 本支 | 为什么没有 |

## 第 11 章 怎么验证它真在生效（本支没有体检器）

本支不含任何可执行脚本，因此**没有"体检"这个概念**（原因见 9.3 与 15.4）。本节回答另一件事：装完之后你怎么知道行为真变了。

- **骨架对得上件数**：数产出小节标题，①8／②5／③6／④9／⑤10；缺项须写明为什么省略。
- **重大决定带"换来 X，代价 Y"**：全文搜"代价"，架构回答里搜不到＝没走④。
- **数字要么你给的、要么"未知"＋分档**：抓任一精确数字反一句"我这告诉过你吗"。
- **有真跑过的痕迹**：要求贴运行输出（含退出码）或一个可点开的本地地址。
- **至少一条【假设】或红旗**："完整又全绿、零风险"却一条【假设】都没有，多半是风险扫描没做，而不是真没风险。

最后这条最能讲给面试官：本支把"承认不知道"做成了**必交产出物**，于是"全知全能的答案"反过来成了失效信号。

**三分钟抽查法**：拿任一"完整实现"类交付，只问自己——**"我知道下一步该我自己做什么吗？"** 走了①答得出（它交出安装说明＝从零到跑通的命令序列）；走了⑤答得出（每阶段有可验收产出、MVP 有完成标准）。答不出＝清单只交了骨架。

**版本对账（替代体检）**：无脚本就手工三步——① 看你安装位置那份 `SKILL.md` 的字节数；② 与页眉的 3,729 比；③ 不一致就重读你手上那份正文、逐条比六条通用纪律，**不要靠版本号判谁新**（本支两侧都写 v1.0 却差 146 字节，版本号在这条支上根本没有判别力）。字节差本身不值得追（多一个空格也算差），但**纪律条目缺失（F11）必须补齐**，因为它是行为差异的来源，不是排版差异。[实测]（页眉那条差异正是这三步查出来的：先看到 3,583，再回到通用纪律第 4 条才发现少的是后半句。）

## 第 12 章 端到端走查：一句话输入走到能开工

**输入（用户原话）**：

> 我有个想法：做一个提醒家里老人按时吃药的小工具，主要是到点提醒，最好子女在外面也能看到他有没有吃。帮我规划一下值不值得做。

**第 1 步 对号入座**：

```

     —— 这一跳省掉的上下文就是渐进披露的全部价值 [实测]
```

**第 2 步 ⑤十件的产出形状**：

```
1 它解决的问题   老人记不住＋子女不在场，漏药无人知（提醒容易，"知不知道吃了"没人管）
2 目标用户       1 位老人（用药者）＋1–3 位子女（查看者）；每天 2–4 个用药时刻；
                 频率＝每天；容错＝漏看一次就可能漏药

                 ｜子女端超时未回执告警          ← 砍掉任一即不成立
5 次要功能(v2)   药盒余量、多药方案、饮食禁忌、语音播报  ← 防功能蔓延
6 MVP 完成标准   连续 3 天模拟排程：12 个提醒全部按时触发、点击回执落盘、
                 超时 15 分钟未回执子女端可见。缺一条＝未完成
7 初始架构       单机文件存储＋本地服务；档次对齐（1 用药者＋≤3 查看者，非万级并发）
8 路线图         周1 排程与提醒内核｜周2 回执与落盘｜周3 子女端只读视图｜周4 真跑 3 天
9 风险           技术＝手机后台被系统杀进程导致不响（缓解：常驻设备＋失败即补发告警）
                 执行＝老人不会点"已吃"（缓解：单按钮、大字、可撤销）
```

**第 3 步 红旗（本例真会出现的那种）**：

> **红旗**：用户手里已有两个免费替代品（手机闹钟＋家庭群消息），"提醒"这一半没有切换价值。**为什么这是问题**：提醒类工具的成败不在提醒功能，而在**依从率能不能被第三方看见**；只做提醒＝做一个更好看的闹钟。**怎么绕开**：把定位收成一句话——"子女能远程确认老人吃了药"，只留回执＋告警主线，其余降级进第 5 件。**如果还是要做**：先不写代码，用共享日历＋一条微信手动模拟三天，看子女到底会不会去看。

这一段同时演示⑤「缺陷直说」、纪律 6「不讨好」、原文那句"风险说透但给路"。

**第 4 步 只问三类，其余自定**：

```
该问（缺了会白干）
  给谁用／几人用 → 输入已答（1 老人＋子女），据此定架构档次
  要不要持久化   → 要问："没吃这个事实要不要存下来供子女回看一周？"决定要不要数据库
  部署形态       → 必问："子女在外面看"意味着公网可达，直接牵出鉴权
不该问（自定＋一句理由）：前端框架、配色、命名、日志格式、用哪家免费托管
```

这里是本支最实用的一处：**你那句话把部署形态定了，但持久化没定**——不问会白干（做完才发现没法回看），全问就变成问题轰炸。

**第 5 步 接力①，第 0 步到第 3 步**：

```
第 0 步 定位＝让子女远程确认老人吃了药；必须有＝时刻表／提醒／回执／超时告警；
        以后再说＝余量、多药、语音；技术栈＋一句理由；文件结构树
        从④借来的权衡行：
          选 SQLite 不选 PostgreSQL：换来零运维、随项目文件走，代价是并发写≈1；
            本例写入源只有"老人点已吃"一个，日活过千才需迁移
          公网只读链接、不建账号体系：换来子女零安装，代价是链接即凭证 → 让它过期
第 1 步 见第 4 步（已问完）
第 2 步 八件套逐项：技术决策／文件结构／存储方案说明（按降级条款并注明理由）／
        API 端点（只读链接 2 个，方法＋入参出参）／界面结构（老人端 1 屏＋子女端 1 屏）／
        完整实现（不留"此处省略"）／安装说明（从零到跑通）／测试（核心路径实跑）
第 3 步 照安装说明跑一遍 → 看到服务起来、退出码 0 → 交出一个可点开的本地地址
        → 老人端点一次"已吃"，子女端刷新看见回执时间。跑不通就是未完成，禁说"应该可以"
        落盘前先查非系统盘工作目录剩余空间（纪律 5）
        自证不了的项写成【假设】＋置信度＋推翻条件：
        【假设】老人手机不会在息屏 30 分钟后杀进程；置信度中；推翻条件＝真机出现一次未响
```

**第 6 步 收尾自检单实样**：

```
[x] 八件套逐项齐 —— 第 3 件降级为"存储方案说明"，已注明理由（单一写入源）
[x] 代码类产物实际运行过 —— 附运行输出与退出码，附可点开本地地址
[x] 占位数字未编造 —— 只用你给过的"1 用药者＋≤3 查看者"，没编并发数
[x] 没预埋没要的功能 —— 余量等 5 项留在第 5 件（v2），一行代码都没写
```

**第 7 步 三周后它不响了（切③）**：自己找调度代码、复现"到点不响"、读完整报错栈、把排程缩到 1 分钟得到最小复现；然后按六件交付——白话机制（比喻：闹钟不是挂在手机上，是挂在一个已被系统关掉的程序上）→ 根因（表象"没响"，根因"后台进程被回收且没有任何补发路径"）→ 边界（空值／并发／时区／重启后未恢复排程）→ 健壮方案（持久化下次触发时间＋心跳自检＋超时补发，并说明为何不选"加个定时器"这种补丁）→ 复现脚本先红后绿 → 机型相关项标【假设】；未实机验证禁说"修好了"，连败 3 次就换方向。

这条走查（第 1 到第 7 步）覆盖这类项目最可能的三种请求形态——**想清楚、做出来、坏掉了**——并演示串联 ⑤→①→③。

## 第 13 章 反模式清单：不要这样用它

1. **拿它当提示词复读**：AI 照着"你是资深工程师"演一段，产出还是没结构。
2. **只命中一个场景却五份细则全读**：10,418 B 挤掉真正要读的代码与需求，质量反降。
3. **用②去看一个 bug**：交出一份七问式架构评论，bug 还在。判据：抓单个 bug 走③。
4. **用③去问整体改进**：六件里没有"重复代码／结构问题／维护风险"，你要的它不交。
5. **跳过第 0 步直接写码**（①"顺序不可乱"）：架构说明变事后辩护，功能蔓延从第一行开始。
6. **把降级条款当跳过许可证**：不注明理由就无法区分合法降级与漏项，自检第 1 项失效。
7. **不知道量级就编个精确数**（违纪律 3）：分档、成本、瓶颈全建在幻觉上，没人会怀疑"5000 QPS"。
8. **给单机自用工具上微服务／缓存／消息队列**（④明文＝违规）：复杂度白付，运维归你。
9. **只看报错栈末行下结论**：修掉的是后果不是原因，下周复发——③那句信条就是为此写的。
10. **同一方向硬磕第 4 次**：三次已证明假设可能整体错，第 4 次只在消耗你的时间与上下文。
11. **把伪需求的计划书写成"建议补充调研"**：红旗被稀释成小建议，你在错误方向上周密地开工。
12. **让⑤的计划只活在对话里不落成文件**：接力断裂（F9），下轮会话无从拍板、需求得重讲。
13. **指望它替你决定做不做**：五张单子全是交付形状，钱、时间、优先级归交付流水线与验收官那两支。
14. **拿②当代码审查替代品**：七问是"看懂并列出问题"，不是逐行安全审计；正式验收走验收官那支。

## 第 15 章 工程与安全规范（含诚实留档）
