## 第 0 章 五分钟速览

1. **它管的是"教训"这一种资产**：报错、失败、反常现象、反复排查不下的问题，解决之后要把「为什么会踩、下次怎么一眼认出来」写成能检索的条目——这套动作叫**沉淀**（把一次性的经验写成可长期检索的文件，而不是说完就忘）。
2. **两层结构，不是扁平台账**：**根因层**（一个共性病根一个文件）＋**案例层**（一次实际踩坑一个文件），案例挂在根因下面。**判同型**（判断两件事是不是同一个根因）靠**编号**，不靠关键词。
3. **索引极轻且每次会话都读**：常驻上下文的只有那份索引（一张根因表＋按根因分组的一行行案例标题），明细文件**命中才深读**。这就是**渐进式披露**（平时只给你看目录，需要时才展开正文）＋**回注**（把内容重新塞回 AI 的上下文窗口，塞多少花多少 token）。
4. **案例正文固定八段＋一个不许删的尾节**（v1.5.0 起）：现象／复现／现场代码／根因（机制）／修法／验证／能否借鉴／教训，后接单列「我自己引入的错」，没犯错也要写「无」——**空节比缺节可检查**。
5. **命中计数把"有用"从感觉变成数字**：判据是**因果要件**（在这条记录被看见之后、问题被解决之前，它真的帮上了忙就算命中，怎么看见的不限），唯一排除的是"问题早就自己修好了、事后才发现原来有过记录"。
6. **升华有两个轴**：同一条案例被真正用上 **3 次**（`hits ≥ 3`）→ 可升华；同一个根因下攒到 **7 条**案例（v1.5.1，由 3 改 7）→ 值得提炼成硬规则。**升华**＝把反复出现的规律提炼成一条不许商量的铁律，写进记忆库的常驻区，此后每次会话强制加载。
7. **它只管沉淀与查阅，不管诊断**：正式 bug 的诊断修复流程转给另一支诊断类 skill；它也**不评分、不衰减**（那是记忆库里另一层的事），两别各记各的，交叉时只放一行指针。

一句话概括设计目标：**让同一个坑换个马甲也被认出来，并且这件事随着记录变多而越来越省上下文，而不是越来越费。**

## 第 3 章 结构与分层详解：三层、三个读取预算

### 3.1 目录形状总表

SKILL.md『两层结构』给出的形状（路径按公开页规矩抽象化，`<log-root>`＝这套日志的存放根目录）：

```
<log-root>/                       # 共享日志根目录，位置稳定，第一次用先跟用户确认
├── pitfall-log.md                # 极轻索引：根因索引表 + 按根因分组的案例清单
├── roots/                        # 根因层（检索入口）
│   └── RT-<三位编号>-<slug>.md   # 一个根因一个文件
└── pitfalls/                     # 案例层（深读用）
    ├── _template.md              # 八段体裁的案例模板（从 assets/entry-template.md 复制）
    └── YYYY-MM-DD-<slug>.md      # 一条坑一个文件，日期开头
```

三层各自的读取预算（这是整套设计真正的成本账）：

| 层 | 装什么 | 读取频率 | 为什么这个频率 |
|---|---|---|---|
| **索引** `pitfall-log.md` | 根因表（4 列）＋按根因分组的案例清单（6 列），一行一条 | **每次会话都读** `[实测]`（SKILL.md『两层结构』：「每次会话都读，必须保持极短」） | 它一旦变大，成本就被会话数乘上；它必须"轻"不是审美要求，是预算要求 |
| **根因层** `roots/RT-*.md` | 一句话根因／识别信号／通用对策／挂载案例四节 | **命中才读** `[实测]`（『检索流程』第 3 步） | 根因数量增长远慢于案例数量（多个案例共一个根因），所以它是"值得单独一层"的那类信息 |
| **案例层** `pitfalls/*.md` | 八段全过程＋尾三节 | **根因层不够用时才深读** `[实测]`（『检索流程』第 4 步） | 最贵的一层（一条一份八段长文），只在需要"灵感"时打开 |

> **[实测] 判定顺序**：『检索流程』六步是一条强制顺序链：① 读索引 → ② 先扫根因索引表 → ③ 对上就读 RT 文件拿通用对策先试 → ④ 根因层不够才挑该根因下的具体案例深读 → ⑤ 解决了就给**真正帮上忙的那一个** +1 并告知用户 → ⑥ 一个都对不上就自己排查，解决后按『记录流程』记新的。
> 为什么顺序不许颠倒（不是洁癖）：**先翻案例会被具体细节牵着走**——案例里有当时的文件名、当时的绕行手段，照抄到一个新场景里往往是错的；根因文件里只有"识别信号＋通用对策"，天生就是为"提前认出来"准备的。SKILL.md『原则』第二条「根因优先」就是这条顺序的规则化表达。

### 3.2 每层为什么必须存在（缺一层会怎样）

**索引层**——存在的唯一理由是"每次会话都读"。
它把"这套日志里有没有我要的东西"这个问题的成本压到最低。若砍掉它，检索就要靠扫全目录（成本随记录数线性上涨）；若把它写厚（比如把八段正文的摘要也塞进索引），就等于把成本重新搬回每次会话，两层结构白做。`assets/index-template.md` 的 frontmatter 描述直说了这一层职责：「本文件只留极轻索引 + 指针，省 token」[实测]。

**根因层**——存在的理由是**判同型需要一个能挂东西的钩子**。
一个根因一个文件，编号固定，案例文件用 `root:` 字段指向它。这条链一建立，"这类问题出现了几次"就变成一个能机械数出来的数字（`cases` 字段），而升华触发条件（『升华』节的"某根因下案例数 ≥ 7"）正是靠这个机械数字才能被可靠执行。
**砍掉这一层会怎样**：只剩案例平铺，同类关系靠关键词字符串近似，"案例数"就没人能数清；触发条件退化成"我觉得这类挺多了"，升华机制形同虚设。[推演]，具体反例见第 5 章末尾。

**案例层**——存在的理由是**根因层的通用对策会不够用**。
『为什么分两层』写得很直白：「根因层解决不了，再往下翻具体案例找灵感」。灵感是具体细节给的，不是抽象规律给的——这也是为什么案例正文必须保留屏上原文、现场代码、当时的绕行手段，不许写成纯总结。
**砍掉这一层会怎样**（把明细直接写进根因文件）：根因文件会被撑成巨型混合体——一句话根因和八段全过程挤在一起，于是"命中才读根因层"这一步的成本优势同时崩掉，因为读一次根因就等于读完了它下面所有案例。[推演]：一条案例带 20 行代码块 × 同一根因下 7 条案例，根因文件就上百行，比原设计里"只读索引＋一份短根因文件"贵一个量级。

### 3.3 三层之间的两条引用链与两条一致性约束

```
索引 ──链接──> roots/RT-*.md ──frontmatter root:──> 案例文件
  └──分组标题（每个根因一节案例清单表）        └──文末「## 命中记录」表
```

两条一致性约束（都是 [实测]，来自 SKILL.md 原文）：

1. **案例数两边同步**（『记录流程』第 4 步）：索引的根因表更新案例数，案例清单在对应分组下加一行；根因文件的「挂载案例」表格「与索引保持一致」（『根因文件格式』第四节）。
2. **命中数两处同步、以文件为准**（『命中计数』）：frontmatter 的 `hits` 是权威值，索引 `🔥N` 是展示值，两者不一致时**以文件为准并回头修索引**。

> 为什么权威值放在文件而不是索引：索引是"每次会话都读"的那份，最容易在多会话并发写时被人改漏；文件各自独立、写冲突面小。**把权威放在冲突小的那一侧**，这是所有双写设计的通用取舍。[推演]：若反过来以索引为权威，两个会话各自记一条新坑、各自把某根因案例数从 3 改成 4，后写的那个会把前一个盖掉，索引显示 4 而磁盘上实际有 5 份案例文件——这种不一致只能靠第 11 章第 3 项体检（数文件）抓出来。

## 第 4 章 极轻索引：常驻的那一份，怎么写才算"轻"

### 4.1 索引的两块内容，根因表在前

SKILL.md『索引格式』规定索引只有两部分，且**根因索引在前**（并注明「与 `assets/index-template.md` 保持一致」[实测]）。

**① 根因索引表**（4 列，[实测] 数法：数模板表头 `|---|` 分隔段，`assets/index-template.md`「索引格式」节）

```
| 根因 | 一句话 | 案例数 | 命中 |
|---|---|---|---|
| `RT-00X`（`roots/RT-00X-<slug>.md`） | 中文出现在跨进程 / 跨工具边界 → 先怀疑编码 | 2 | 🔥0 |
```

**② 案例清单**（按根因分组，**组内新 → 旧**，6 列）

```
### RT-00X 中文出现在跨进程 / 跨工具边界

| 日期 | 记录者 | 标签 | 一句话标题 | 命中 | 文件 |
|---|---|---|---|---|---|
| YYYY-MM-DD | shared | 版本控制,中文路径 | 中文路径当子命令参数会误删整个目录 | 🔥0 | `详情`（`pitfalls/YYYY-MM-DD-<slug>.md`） |
```

> 表里那行案例是把权威库里一条真实事故**脱敏重写**后的形状：保留了技术细节（含中文的路径被当成子命令参数传给版本控制命令，结果是整个目录被删），抹掉了日期、记录者代号与可定位信息。公开页按此写法，不再复制原件。

### 4.2 四个字段各管什么

| 字段 | 规定 | 为什么这么定 |
|---|---|---|
| `根因` | Markdown 链接指向 `roots/RT-*.md` | 链接而不是纯文字：命中时 AI 要能一步跳进去读，不用自己拼路径（拼路径就是一次可出错的推理） |
| `记录者` | 助手标识／人名／`shared`，**用稳定短标识** [实测]（『索引格式』字段说明） | 多人共用一份日志时，出问题要能回溯"这段是谁写的"；但**公开页里这一律写成 `shared` 之类的中立标识**（本页隐私处理，见第 15 章） |
| `标签` | 逗号分隔关键词，"便于检索" [实测] | 标签是**索引内的二次筛子**：根因表命中失败时（新根因还没建），还能靠标签把候选案例捞出来 |
| `命中` | `🔥N`，N=0 也写 `🔥0`；`⭐`＝已升华 [实测] | 0 也要显式写：留空就分不清"没人用过"和"忘了填"，第 11 章体检就没法区分缺值和零值 |
| `案例数` | 整数，随每条新案例 +1 [实测]（『记录流程』第 4 步） | 它就是升华触发器的输入（≥7 那条），所以必须是机械可数的，不能是"大概几类" |
| `文件` | 详情链接 | 深读入口。索引唯一被允许的"正文泄露"就是一句话标题 |

### 4.3 "轻"是可以算出来的账

**为什么 50 条是那个"有界"阈值**（SKILL.md『原则』第五条「索引有界」：案例超 **~50 条**时把冷条目归档到 `pitfalls/archive/`，索引保留「→ archive/文件名」指针）[实测]。

我按上表的形状复算一遍（数法：每行按 4 个中文字段＋若干 ASCII 标点估；UTF-8 下一个中文字＝3 字节；中文近似 1 字 ≈ 1 token，ASCII 约 4 字符 ≈ 1 token）：

| 项 | 估算 |
|---|---|
| 一行案例清单 | 约 90–140 字节 ≈ 25–40 token |
| 50 行案例 + 分组标题 | 约 6–7 KB ≈ 1.5–2 K token |
| 根因索引表（假设二三十条根因） | 约 2–3 KB ≈ 0.8–1.2 K token |
| **索引常驻成本合计** | **约 2–3 K token，每次会话都付** `[推演]` |

> 这不是"官方数字"，是按形状估的量级——写明了数法便于你换成自己的尺子重算。`[推演]` 的反例输入：若把每条案例的「能否借鉴」段摘要也塞进索引（每段 60–100 字），索引立刻膨胀 3–5 倍，"每次会话都读"这件事就变成每次白扔几千 token；这时两层结构的省钱效果被索引自己吃掉了。**根因是"轻"这个字只适用于索引，不是适用于整套日志。**
> 50 这个数带波浪号（`~50`），SKILL.md 把它写成近似值而不是硬线 [实测]，因为它按"索引还能不能一眼扫完"定，不按字节定：50 行左右正好是一屏内可扫完的规模。[推演] 具体坏输入：如果按字节定阈值，一条带长 slug 的案例就能挤掉三条短案例的额度，索引行数与实际信息量脱钩，归档时机变得不可预测。

### 4.4 归档怎么做才不断链

『原则』第五条只给了两句指令（超 ~50 条归档、索引保留指针），落地要注意三件事，其中前两件是 [实测]（能从『全处同步铁律』『记录流程』推出为规则要求），第三件是 [推演]：

1. **移动文件不改编号**：根因编号「只增不改」（『根因文件格式』末句），案例文件名里的日期＋slug 同样不许改——别人（索引、别的案例、记忆层的指针）可能引用它，改名＝断链。
2. **索引留「→ archive/文件名」而不是删掉那一行**：删掉等于这条记录在检索面上彻底消失；留指针让"去归档区找找"成为可能。
3. **归档后要跑一次链接存活检查**（[推演]）：具体坏输入——案例被手动挪进 `pitfalls/archive/` 但索引里链接仍写 `pitfalls/YYYY-MM-DD-...`，AI 按索引去读会拿到"文件不存在"，于是它得出"这条记录丢了"，转而重新排查一个已经排查过的坑。这正是第 11 章体检第 6 项要堵的。

### 4.5 索引开头为什么有一条「实测注记」的位置

SKILL.md『案例文件格式』的分级判据段里出现了一句「见索引开头那条实测」，指向真实索引文件开头的一条经验记录（内容关于各家计数脚本认哪种字段写法）[实测]。也就是说：**索引文件不只是表格容器，它的开头允许存在"关于这套格式本身的实测备注"**——这是把"踩过的格式坑"就近记在最常见的入口文件上。

> **[推演] 为什么这样做有效**：格式类的错最容易在"下一次写索引"时重犯，而写索引那一刻 AI 正好在读这份文件；把备注放在别处（比如单独一份 README），写索引那一刻就看不到。这是"把教训放在触发动作现场"的通用做法。
> **已知漂移**：`assets/index-template.md` 的开头**没有**这条备注的位置（它开头只有 frontmatter、单一事实源提示、检索顺序、四条件命中判据），所以照模板新建的索引天生缺这一行 → 详见第 15 章未采纳／漂移清单第 3 条。

## 第 5 章 根因层与判同型：为什么用编号而不是关键词

### 5.1 根因文件的确切形状

复制 `assets/root-template.md`，命名为 `roots/RT-<三位编号>-<slug>.md`。frontmatter 5 个字段（数法：数模板里被替换成的那行元信息）[实测]：

```yaml
---
root_id: RT-00X
title: 一句话根因
cases: 2          # 该根因下挂了几条案例
hits: 0           # 该根因的通用对策被直接套用（未深读案例）的次数
escalated: false
---
```

正文四节（`assets/root-template.md` 的四个 `## ` 标题，与 SKILL.md『根因文件格式』一一对应）[实测]：

| 节 | 必须写到什么程度 | 这节存在的理由 |
|---|---|---|
| **一句话根因** | 这类问题的**共同病根**，一句话说清 | 它是索引表里"一句话"那一列的来源；一句话写不成，说明这个根因其实是两个根因 |
| **识别信号** | 出现哪些迹象就该往这里想 | SKILL.md 原文标注「**最有用的部分**，它是'提前认出来'的钩子」[实测]。识别信号是给**未来还没出事的时候**用的 |
| **通用对策** | **不针对任何具体案例**的做法，最好能直接照做 | "不针对具体案例"这句是硬要求：对策里一旦出现某个当时才有的文件名／参数，它就不能迁移到下一个场景 |
| **挂载案例** | 表格（日期／案例／命中），与索引保持一致 | 根因层的局部视图，避免每次都要回索引里按分组找 |

### 5.2 判同型靠编号，不靠关键词：四条理由

**判同型**＝判断眼前这件新事和已有的某条记录是不是同一个病根。这套系统的答案是：靠**编号挂载**（案例 frontmatter 写 `root: RT-00X`），不靠关键词聚类。四条理由：

1. **症状是最不稳定的东西**。SKILL.md『为什么分两层』给的原话：「同一类问题会在毫不相干的场景反复出现」——同一病根在两个场景里症状可以完全不一样，那"不一样"的部分恰恰是关键词检索用来匹配的部分。用关键词判同型，等于用最容易变的那个维度去判最稳的那个关系。
2. **编号是可引用的**。记忆层那边"只放一行指针（含根因号／日期）"（『与记忆 PITFALL 层的关系』存哪边的判据段）[实测]——指针能引用它，说明它是一个可寻址对象；关键词短语没法被引用，只能被重新猜一遍。
3. **编号让"案例数"可机械核算**。`cases` 字段、升华触发条件（≥7）、根因表"案例数"列三处都要求这个数是数出来的。关键词分组下，"这个类里有几条"永远是问出来的。
4. **编号只增不改，所以是稳定标识**。『根因文件格式』末句规定：根因编号按三位数**递增分配、只增不改**——别人可能引用它，改号就断链 [实测]（本页按公开页纪律只写编号形状，不复制任何真实编号）。

### 5.3 双挂面 `also_root`：一类坑确实属于两族

SKILL.md『案例文件格式』的分级判据段顺带提到「外加 `^also_root:` 双挂面」[实测]，说明真实库里出现过**一条案例同属两个根因**的情形（比如一次跨工具边界的编码事故，同时又踩了"依赖隐式上下文"那一族）。

> **[推演] 为什么必须有这个字段而不是"硬选一个"**：没有 `also_root` 时，写记录的人被迫二选一，于是两条同型事故会被分到两个族里，两个族的 `cases` 都少算一条——升华触发（≥7）被拖延，识别信号也少了一个来源。
> **具体什么输入会出问题**：某条案例本质同时是"跨进程边界编码"和"隐式工作目录依赖"两族的实例；只挂前者，下次遇到工作目录相关的排查就扫不到这条，白花时间重查。
> **已知缺口**：`assets/entry-template.md` 的 frontmatter 替换说明里**只列了 `root`／`hits`／`last_hit`／`escalated` 四行，没有 `also_root`** [实测]——即该字段是被"实测发现需要"补进规则正文，而模板侧尚未同步（见第 15 章漂移清单）。

### 5.4 「一类问题」而不是「一个问题」：建根因时唯一的判据

『记录流程』第 2 步（归因）：先在 `roots/` 找有没有现成的同根因文件——有就直接挂上去、案例数 +1；没有就新建，**注意想清楚"一类问题"，而不是"这一个问题"** [实测]。

这条一句话的规则其实是整套系统最容易写坏的地方。给你一个可执行的分辨方法（本页 [推演] 汇编，不是库内原文）：

```
把这条事故的具体工具名、具体文件名、具体参数全抹掉，
剩下的那句话还成立吗？
  ├── 成立 → 那就是"一类"，可以建根因文件
  └── 不成立 → 那是"这一个"，先挂到更抽象的族下面，或者干脆再想想
```

反例（写坏了的根因，[推演]）：把根因写成「某个版本控制命令在带中文的相对路径上会误删目录」——里面还留着具体工具名，于是下次同样的病根在"配置解析器吃掉中文注释"时永远命中不了；把它抽象成「**中文出现在跨进程／跨工具边界 → 先怀疑编码**」这一族（SKILL.md『索引格式』示例里就是这句话 [实测]），两次事故才真能聚到一起。

### 5.5 `root` 字段与「能否借鉴」段的分工（最常被混用的一处）

SKILL.md『案例文件格式』专门写了一句分工 [实测]：

> **`root` 说「这属于哪一类」，能否借鉴说「这一类里可迁移的规律」。**

翻译成操作语言：

| 位置 | 写什么 | 判同型时看哪个 | 升华时看哪个 |
|---|---|---|---|
| 案例 frontmatter `root:` | 一个编号（族归属） | ✅ 靠它 | 靠它数 `cases` |
| 案例正文第 7 段「能否借鉴」 | 一句可迁移的规律（跨任务跨项目还成不成立） | ❌ 不用它做机械判定 | ✅ 升华成铁律时，抄的就是这句话 |
| 根因文件「识别信号」 | 症状侧的钩子（长什么样就该想到这族） | ✅ 命中前先靠它 | ❌ |

> **[推演] 混用会怎么坏**：有人把"能否借鉴"写成「这次改成先转码再传参」——那是**本案例的具体修法**，不迁移；下次别的项目没有"传参"这一步，这条规律读起来就跟废话一样，`hits` 永远是 0，而 `cases` 已经攒到 7，于是它照样被升华，升华出一条谁也用不上的铁律。这个坏法不需要真实数据就能构造：任何一段"只能在那个场景里成立"的借鉴语，配上 ≥7 的案例数，就是它。

### 5.6 编号怎么发：递增、不回收、不复用

规则正文只写了"只增不改" [实测]，剩下的分配细节由本页补齐（[推演]，但都是"不写就会出事"级别）：

- **取当时最小未用号**：新建根因时扫一遍 `roots/` 目录取号，别凭记忆写（凭记忆＝幻觉高发点）。
- **不回收、不复用**：某个根因后来被证明不该独立成族，**也不许把它删掉再把号让给新根因**——历史条目、索引行、记忆层指针里可能还写着这个号，复用号会让它们指向错的东西。正确做法：在那个根因文件里写明"本族应并入 `RT-00Y`"，保留号本身。
- **[推演] 具体坏输入**：删掉 `RT-00B`、把 `RT-00B` 让给新根因，三个月后一条老案例的 `root: RT-00B` 就把人导向完全不相干的对策，照着做反而引入新 bug——这是编号系统里代价最高的一类自我伤害，且不会有任何报错提示它。

## 第 6 章 案例层八段体裁：每一段各拦一种"糊过去"

案例层是这套系统里唯一承载**全过程证据**的一层。v1.5.0（2026-10-03）把它从**五节**升为**八段**＋段后单列一节，来源是拆解某个外部项目的修复台账体裁（CHANGELOG.md『v1.5.0』条目的『解决了什么』段记了这个来源）[实测]。

### 6.1 标题行的形状与后果分级

标题行固定形状（`assets/entry-template.md` 第一行标题 [实测]）：

```
# 坑：{一句话标题} —— {最直接的后果} 🔴/🟠/🟡
```

**后果分级三档**，判据是**损失能不能挽回**（不是"看起来严不严重"）[实测]（SKILL.md『案例文件格式』分级判据段）：

| 级别 | 判据 | 例子（本页脱敏写法） |
|---|---|---|
| 🔴 | **不可再生损失**：数据被销毁、误删、写坏共享权威资产 | 一次实测事故：某条 142 行的原始命令输出被原地改写截断销毁，原文再拿不回来 |
| 🟠 | **结果错但可回滚**：静默假成功、范围跑偏、判据失灵 | 一次实测事故：脚本静默跑完并回报成功，实际只处理了一半对象，回滚重跑即可 |
| 🟡 | **只浪费时间**：绕路、误读、拼错路径后自查发现 | 一次实测事故：参数名记错，白查二十分钟，自己发现并改回 |

> **为什么要有分级**（原文话）：「有分级，同一根因下的多条案例才排得出先后」[实测]。分级的用处不是给单条案例贴标签，而是**让一族内的多条案例可比**——可比才能聚合，聚合才有升华的原料。
>
> **为什么不进 frontmatter**（这一条是全章信息量最大的设计说明）[实测]：原文说「各家计数脚本要认的是 `^root:` ／行内 `> root:` ／`^root_cause:` 三种写法（外加 `^also_root:` 双挂面），再塞一个新字段等于给五家的脚本各埋一次漏判」。
> 拆开讲：**frontmatter**（文件头那块 `---` 之间的机器可读字段）是所有自动脚本的解析入口；已经存在**五处**在数这些字段（数法：原文用词"五家"），它们各自硬编码了三种字段写法。此时新增一个分级字段，等于要求这五处脚本同时改；漏改任何一处的后果不是报错，而是**静默漏判**（脚本看不见新字段，继续按旧口径出数字）。放在标题行，人一眼可见、脚本不解析、不会漏判也不会报错。**结论：一个字段进不进 frontmatter，取决于"有没有脚本已经在这块地面上挖过"，而不是"它重不重要"。** [推演] 的具体坏输入：若把 `severity: red` 塞进 frontmatter，那五处计数脚本里凡按"整块 frontmatter 逐行匹配已知键"写的，就会把这个未知键当成解析失败信号，轻则跳过整条记录（命中统计凭空少几条），重则整份扫描脚本抛异常停摆。

### 6.2 八段逐段拆解：它拦的是哪一种糊弄

| # | 段名 | 原文要求（[实测]，SKILL.md『案例文件格式』八段表＋`assets/entry-template.md` 括注） | 这一段专门拦什么 |
|---|---|---|---|
| 1 | **现象** | 先一行上下文（当时在做什么／什么前提），再贴**屏上原文或具体数字**；**转述不算**——转述会把关键特征抹平 | 拦"事后合理化的复述"。人的记忆会自动把报错磨圆，两周后读起来"就是普通的一个失败" |
| 2 | **复现** | **最短命令序列**，别人照着跑能再撞一次；撞不出来就写「未能复现＋当时的条件」，**别留空** | 拦"无法确认是不是同一个坑"。缺这段，下次遇到相似症状无法验证同型 |
| 3 | **现场代码** | `文件:行` ＋关键片段，抄**改之前**那一版 | 拦"只留下修好后的漂亮版本"。改前的样子才是病根证据 |
| 4 | **根因（机制）** | 为什么坏，**不停在表象**；写**本案例**的具体机制；`root:` 字段才是归属的**根因族**，两者别混 | 拦"把症状当根因"。也拦"把族名当机制"（只写一句族标签，不解释本次为什么坏） |
| 5 | **修法** | 代码级改动＋**为什么这样切**（为什么改这里而不是别处） | 拦"改对了但说不清为什么对"。说不清就无法判断下次是否还该改这里 |
| 6 | **验证** | 修后的**实测输出／断言条数**；"改好了"三个字不算验证 | 拦"自我宣布成功"。这是全套八段里最直接对抗幻觉的一段 |
| 7 | **能否借鉴（通用规律）** | 换个任务／换个项目还会不会遇到，可迁移的规律是什么；**全篇最有价值的一段** | 拦"一次性修复"。这一没写，这条记录就只是一份日记 |
| 8 | **教训（一句可迁移纪律）** | 一句**下次能直接照做的命令句** | 拦"道理都懂但没法执行"。命令句＝可以直接当规则念出来的那种句子 |

段后**单列一节「我自己引入的错」**[实测]：修这个问题的过程中自己新引入的错（改 A 坏 B、把校验脚本自己写坏、误判了影响范围）。**没有就写「无」**——理由原文写得很硬：「**空节比缺节可检查**，缺节分不清是'没犯错'还是'没回头看'」。

再加两节收尾（`assets/entry-template.md` 里的『来源』『命中记录』）[实测]：

- **来源**：日期／哪个记录者／关联任务或对话。
- **命中记录**：固定表格 `| 日期 | 场景 | 解决了什么 |`，初始一行全是 `—`（占位破折号，不是留空）。

### 6.3 「我自己引入的错」为什么单独一段，而不是并进"修法"

[推演] 的解释（规则正文只给了要求，没给理由）：

1. **它是第二类数据**。修法记的是"怎么让问题消失"，这一段记的是"我这次动手又弄坏了什么"。前者面向问题，后者面向**自己这个操作者**。混在一段里，半年后只会被当成修改说明的一部分跳过。
2. **它直接服务同类二次事故**。CHANGELOG.md『v1.5.0』把"缺我自己引入的错"列为五节体裁四处断链之一，后果写得很具体：「修法自身引入的新错无处记，**同类二次事故重复发生**」[实测]。
3. **它是校验脚本最容易藏雷的地方**。「把校验脚本自己写坏」是这套日志体系里最讽刺也最常见的错：校验逻辑一坏，之后所有"绿"都是假的，而这批假绿不会自己暴露。

> 空节为什么必须写「无」：假设某人确实没引入新错，直接删掉这一节，那么体检时脚本统计"含该节的案例比例"会得到一个虚高的缺失率，你无法区分"这个人在撒谎／偷懒"和"这人真的干净"。写「无」是**把'没有'也变成一条有内容的记录**。

### 6.4 旧条目不追改：体裁升级只往未来生效

SKILL.md『案例文件格式』末段 [实测]：

- **旧条目不追改**：八段体裁（2026-10-03）之前入库的条目是**五节形态**（上下文／为什么（根因）／解法／能否借鉴／来源），**保持原样**。
- **理由不是省事，是防伪**：「补写『复现』『验证』等于替当年的自己编造证据，**那是伪造**。」
- **新坑一律八段**。
- **唯一允许的回填**：老条目**被命中时**，若当年留了原始回显，可就地补段并**注明补录日期**。

> **[推演] 这条规则的锋利之处**：它把"体裁统一"这个欲望压在了"证据真实性"下面。补录必须挂在"当年真的留了原始输出"这个条件上，且必须写日期——写日期是为了让后来人能分辨哪几段是当场记的、哪几段是事后回填的，可信度不同。
> **具体什么输入会让它出问题**（如果没有这条规则）：一位好心的维护者跑脚本给全部老条目补上 `## 2. 复现` 一节，内容是他根据上下文推测的命令序列。此后所有检索命中都以为自己拿到了可复现证据，照着跑撞不出来，于是得出"这条记录过时了"，把一条其实正确的根因判成废弃。

### 6.5 八段填全的硬要求，写在两个地方

『记录流程』第 3 步 [实测]：「复制 `assets/entry-template.md` 写案例，**八段填全＋『我自己引入的错』不许缺节**（没犯错就写『无』），frontmatter 写上 `root:`」。
『升华』节的**全处同步铁律**里补了一句 [实测]：「**条目结构升级只往未来生效**：历史条目一律不追改（见『案例文件格式』末段），需要同步的是**模板与规则本身**。」

> 两句合起来才是完整规则：**写新条目时不许缺节；改体裁时不许动老条目。** 前者管增量质量，后者管存量可信。

## 第 7 章 命中计数：把"这条有用"从感觉变成数字

### 7.1 为什么要有计数（原文给的理由）

『命中计数』开头 [实测]：「**能否借鉴**里写的规律有没有真救过场，光看记录看不出来。计数把'这条坑有用'从感觉变成数字。」

这条需求还牵出一个隐藏后果：**升华需要触发器**。『升华』节的两条触发条件（`hits ≥ 3`／`cases ≥ 7`）都是数字，其中第一个直接就是命中计数。没有计数，升华就只能靠"我觉得这条很重要"，而那正是这套系统要治的病。

### 7.2 判据的演化：从过程要件到因果要件

| 版本 | 判据形状 | 具体条文 | 出了什么问题 / 为什么改 |
|---|---|---|---|
| v1.2.0 | 有计数，"检索命中且真正解决问题才 +1" | SKILL.md『版本』与 CHANGELOG.md『v1.2.0』（命中 ≥3 次自动升华进常驻铁律区）[实测] | 粗 |
| v1.3.0 | **收紧为四条件**并明确排除"事后发现同源" | 四条件＝①真的检索了 ②真的翻看了具体记录 ③从中获得启发并用于解决 ④问题真的解决了（这套四条件仍逐字留在 `assets/index-template.md`「命中计数」节）[实测] | 四条件全是**过程要件**（要求特定的动作发生） |
| **v1.4.0（2026-09-26）** | **改为因果要件**，用户拍板 | 「在这条坑对应的问题被独立解决之前，踩坑记录（正文或索引元数据）被你看见，并对解决产生了实际助力——帮你找到方向，或直接修好了问题——就算命中」[实测] | 原四条件**误伤**了"干活途中撞见记录并被它纠错"这类真实命中：按四条件，没做检索动作＝不算，可它明明救了你 |

**新判据的三条关键放宽／收紧**（[实测]，均在『命中计数』节）：

- **怎么看见的不限**：主动检索到的、干活途中撞见的、误打误撞翻到的，都算。
- **明确不算的只有一种**：问题已经被**独立修好**（全程没参考任何记录），事后入库／复盘时才发现"原来已有记录 A"——纯事后归类。
- 一句话口诀（原文）[实测]：**同根因 ≠ 命中；解决之后才看见 ≠ 命中；解决之前看见并帮上忙 = 命中。**

**首例命中的形状**（脱敏重写，保留技术细节）[实测]：一次正在写库的会话，读索引准备归档新坑时，扫到两条旧案例的日期字段，**当场发现自己那份变更日志里的日期写错了**，当场改正——按新判据，这算命中（撞见即命中），两条案例各 +1。这件事正好证明四条件判据是错的：全程没有任何"检索动作"，但记录确实救了场。

### 7.3 虚高为什么等于没有

原文 [实测]：「只是扫到了没用上、或最后没解决，都不算。**宁可少记，不要虚高**——**虚高的数字等于没有数字**。」

> **[推演] 为什么虚高比零更糟**：计数是升华的输入。一条 `hits: 3` 但三次都是"扫到没用上"的记录会被升华成铁律，此后每次会话强制加载——于是一条没救过场的规律获得了最高优先级，还挤掉了真正常驻位里该放的别的规则。**低估的代价是少用一条好规则，虚高的代价是常驻区被一条坏规则占位并且没法被证伪。**

### 7.4 两处双写与冲突裁决

『命中计数』"计数落在两处，必须同步" [实测]：

| 落在哪 | 写法 | 地位 |
|---|---|---|
| **索引** | 案例行的 `命中` 列 `🔥N`（N=0 也写 `🔥0`）；根因表的 `命中` 列同理 | 展示值 |
| **文件** | frontmatter 的 `hits` | **权威值** |
| **文件** | 文末 `## 命中记录` 追加一行（日期／场景／解决了什么） | 明细账 |

> **冲突裁决**（原文）[实测]：「两者不一致时**以文件为准**，并回头修索引。」裁决理由见第 3.3 节末：索引的冲突面最大。

### 7.5 两层各自独立计数（最容易记错的一条）

『命中计数』末段 [实测]：

- 只走根因层（读了 RT 文件、用通用对策解决）→ **根因 +1**；
- 深读具体案例并获益 → **该案例 +1**；
- 两层都走了、都帮上忙 → **各 +1**。

字段侧的对应 [实测]：根因文件的 `hits` 注释是「该根因的**通用对策被直接套用（未深读案例）**的次数」，案例文件的 `hits` 注释是「检索命中并**真正解决问题**的累计次数（权威值）」，案例另有 `last_hit`（最近一次命中的日期）。

> **为什么必须分开数**：两个数回答两个不同的问题。**根因 `hits` 高**＝这族的通用对策本身就够用，案例层几乎没被打开，说明抽象做得好；**案例 `hits` 高而根因 `hits` 低**＝根因层的对策不够用，大家还是得靠具体案例找灵感，说明这一族的抽象太薄。混成一个数，这两种完全不同的病就分不出来了。[推演]（结论方向由两条 `hits` 定义支撑，混数的坏法见下）。
> **具体什么输入会让混数出问题**：某族下 9 条案例，每次都是靠翻到某一条具体案例的细节才解决；如果命中全记在族头上（根因 `hits` 一路涨），第 11 章体检里"该族抽象太薄"的信号永远不会亮，也不会有人回头去补那族的识别信号与通用对策。

### 7.6 告知用户这一步不是客套

『检索流程』第 5 步 [实测]：「解决了 → 按『命中计数』给**真正帮上忙的那一个** +1，**并告知用户**。」

> [推演] 这半句的实际功能是**审计**：告知之后用户能立刻指出"那其实不是它帮的忙"，把虚高掐在当场。计数系统最容易坏在没人复核，而这条把复核点放在了唯一还来得及复核的时刻。

## 第 8 章 升华机制与门槛：两个轴、一道同步铁律

### 8.1 触发条件（满足任一）

『升华』节 [实测]：

- 某条**案例** `hits ≥ 3` → 它已被反复验证；
- 某个**根因**下**案例数 ≥ 7** → 这类问题反复出现，值得提炼成规则。

第二条是 v1.5.1（2026-10-03）改的 [实测]：「用户令『规则改成攒满 7 条再升』，与 memory-scoring-lifecycle（记忆纪律那支 skill）v3.5-sc1.5 同步。**只改这一个数字**；命中判据、两层结构、案例八段体裁、索引格式均未动；`hits ≥ 3`（同一条记录被召回几次）与案例数是两个轴，保持 3。」

### 8.2 为什么是 3 和 7，为什么不能合成一个数

| 轴 | 阈值 | 数的是什么 | 为什么是这个数 |
|---|---|---|---|
| **召回轴** `hits` | 3 | 同一条记录被真正用上几次 | 三次才勉强排除"运气好撞上"：一次可能是巧合，两次可能是同一批工作反复，第三次才算跨场景成立 [推演]（原文只写「已被反复验证」，未给推导） |
| **规模轴** `cases` | 7 | 同一根因下攒了几条案例 | 由 3 改 7 的理由写在版本史里：**与记忆纪律那支 skill 对齐**，即同一个体系里"同一根因踩满几条才升"的数字必须一致，否则两支 skill 对同一件事给出不同门槛 [实测] |

> **为什么 3 改 7 时 `hits ≥ 3` 不许跟着改** [实测]：原文明确「两个轴，保持 3」。轴不同、分母不同：`hits` 的分母是"这条被召回几次"，`cases` 的分母是"这一族有几条"。把两个数字拉平反而制造错误直觉（以为"三条案例就够升"）。
> **[推演] 阈值太低的坏输入**（这也是当初 3→7 的实际动因方向）：某族刚攒 3 条就升华，写出来的"铁律"覆盖不住第 4、5 条反例；此后每次会话强制加载一条会被自己证据推翻的规则，还会压制后续该族信号的收集。攒到 7 条才升，等于要求规律先在更大样本上不被反驳。

### 8.3 升华的三个动作

『升华』节"动作" [实测]：

1. **索引对应行标 `⭐`**；
2. **文件置 `escalated: true`**（根因文件则标注已升华），**记升华日期**；
3. **同步写入记忆库的常驻铁律区**——此后每次会话强制加载；编号接在那个大区已有的序号后面，**来源注上根因号与案例 slug**（本页不复制真实编号／真实文件名）。

> **第 3 步为什么必须有**：升华的定义就是"从'查了才知道'变成'不查也常驻'"。只打 `⭐` 不写进常驻区，这条规律仍然只在被检索到时才生效——那就没升华，只是打了个勾。
> **来源注记为什么重要**：常驻铁律区是每次会话都加载的最贵区域。注了来源，将来这条铁律出问题时可以**回到那族案例核对它是不是被过度概括了**（第 8.2 节那个坏输入的现实版本）；没注来源的铁律没法回溯，也没法被证伪。
> **已知问题**：CHANGELOG.md『v1.5.0』条目的『顺带登记两处已知漂移』段明确记录，动作第 3 步那句里的记忆区地址属于**旧址**、现值待核实 [实测]——本页因此**不复制任何真实路径**，只讲清"写进常驻铁律区"这件事本身。

### 8.4 全处同步铁律：一条一清单

『升华』节末段 [实测]：「本 skill 的**规则、模板、索引格式、条目结构**任一处升级，所有副本必须同时改——本机 SKILL.md、`assets/` 下模板、log-root 下的 `_template.md`、现有索引与条目、以及**对外发布的详解页**。改一半等于埋雷：下次照旧模板写出的条目会和新格式对不上。」

把这句压成清单（列名为本页 [推演] 汇编，条目内容全部来自原文）：

| # | 副本 | 升级时要不要动 | 依据 |
|---|---|---|---|
| 1 | 权威库 `SKILL.md`（规则正文） | 要 | 『全处同步铁律』点名 |
| 2 | 权威库 `assets/entry-template.md` | 条目结构升级时要（v1.5.0 就改了它 [实测]） | CHANGELOG.md『v1.5.0』本轮同步清单 |
| 3 | 权威库 `assets/root-template.md`／`index-template.md` | 根因层格式／索引格式升级时要 | 同上（v1.5.0 明确"根因层格式、索引格式、命中判据、升华条件均未变"） |
| 4 | 共享日志根目录下 `pitfalls/_template.md` | 要（它是实际写案例时复制的那份） | 『全处同步铁律』点名"log-root 下的 `_template.md`" |
| 5 | 现有索引与现有条目 | **不追改**（见第 6.4 节）——需要同步的是模板与规则本身 | 『全处同步铁律』末句 |
| 6 | 对外发布的详解页（就是本页这种） | 要 | 『全处同步铁律』点名"对外发布的详解页" |
| 7 | 宿主 skill 注册目录下的同名副本 | 若它是**目录联接**（junction，本体只有一份的投影），指向本库即自动同步，不用手改 | 『全处同步铁律』副本清点句 |

### 8.5 副本清点为什么不能靠肉眼：junction 陷阱

原文 [实测]：「副本清点别靠肉眼：宿主层那些挂载位**多为 junction**，指向本库即自动同步（判链用 `fsutil reparsepoint query` 的退出码，`os.path.islink` 对 junction 恒 `False`）；**改完实跑一次 md5 对账才算同步**。」

拆成三句人话：

- **junction（目录联接）**＝Windows 上"把一个目录投影到另一个位置"的链接，实体只有一份，看起来像两份。
- 为什么必须用 `fsutil reparsepoint query`（Windows 自带的查"重解析点"=查链接的命令行工具）的**退出码**（命令成功／失败的返回编号）来判：因为 Python 的 `os.path.islink`（判断"是不是符号链接"的函数）**对 junction 恒返回 `False`**——它会一脸正经地告诉你"这不是链接"，于是你把它当两份独立副本去手改，实际是在同一份文件上改两次或改错对象。
- 为什么最后必须**实跑一次 md5 对账**（取每份文件的指纹逐字比对）：因为"我以为同步了"和"逐字相同"是两件事。前一条漂移记录就是证据——CHANGELOG.md『v1.5.0』登记的本轮同步清单里，索引只改了"分工约定那一行"[实测]，说明同一次升级里存在"改了其中几处"的真实风险。

> **[推演] 具体坏输入**：一次体裁升级改了 SKILL.md 与 `assets/entry-template.md`，但共享日志根目录下的 `_template.md` 没改。此后所有新案例都从旧模板复制生成，缺「验证」段与「我自己引入的错」段；三个月后统计"有验证段的案例比例"，数字一路下跌，你会以为是记录质量在退化，其实是模板没同步。这类坏的恶劣之处在于**没有任何一步会报错**。

### 8.6 升华之后，这套日志和记忆库的分工就变了

『与记忆 PITFALL 层的关系』 [实测]：坑的**原始记录**记在踩坑日志（共享），反复出现的坑**升华成铁律**才进记忆库常驻区；**避免同一坑记两遍**。第 9 章展开这条边界。

## 第 9 章 边界与协作：它不管什么、谁跟它互认、挂不上怎么办

一支 skill 的成熟度，一半看它写了多少"我不管"。SKILL.md 用 v1.1.0（2026-09-14）和 v1.3.1（2026-09-23）两次专门补边界 [实测]，CHANGELOG.md 记了动因：批量规范化时要「明确本 skill 与其他 skill／记忆层的职责边界，**避免同一坑记两遍、避免与诊断流程撞车**」。

### 9.1 与正式 bug 诊断流程的分工

frontmatter 的 `description` 结尾 [实测]：「正式 bug 诊断修复流程转 diagnosing-bugs，本 skill 只管**沉淀与查阅**。」

| 阶段 | 谁管 | 干什么 |
|---|---|---|
| 出问题、要查了 | **本 skill** | 『检索流程』：读索引 → 扫根因表 → 读 RT 拿通用对策 → 必要时深读案例 |
| 对不上、要正经排查 | **诊断类 skill** | 假设—实验—取证那条链，本 skill 不提供 |
| 解决完、要留档 | **本 skill** | 『记录流程』五步，八段填全 |

> **为什么不顺手把诊断也做了**：诊断需要的是一整套"怎么设计实验、怎么取证"的方法，塞进一份沉淀系统会把它的正文撑大——而它的定位恰恰是**轻量**（frontmatter 第一句就是"轻量化的……沉淀系统"）[实测]。边界写清之后，两边各自都能保持小。

### 9.2 与记忆库自己那一层的分工

『与记忆 PITFALL 层的关系』 [实测]：

- **踩坑日志**＝**跨 agent 共享**的教训沉淀（谁踩谁记、大家都能查），**不评分、不衰减**。
- **记忆那一层**＝**某个 agent 自己**的记忆管理（给坑打分／衰减／升华成铁律）。

| 维度 | 踩坑日志（本 skill） | 记忆库的踩坑那一层 |
|---|---|---|
| 归属 | 共享，一份 | 每个 agent 各一份 |
| 会不会过期 | 不衰减，只归档（索引有界） | 按 TTL（存活期）衰减 |
| 有没有分数 | 只有命中数 `hits`，不评价值 | 有固有分＋情境分的双轨评分 |
| 升华去向 | 升华后**写入**记忆常驻铁律区 | 升华后写进自己的常驻区 |

> **"不评分、不衰减"是主动选择不评分** [推演]：一份跨 agent 共享的教训库如果按 TTL 衰减，就会出现"A 还记得、B 已经不记得"的分裂——共享的前提被打穿。所以衰减留给各自的记忆层去做，共享层只增不减、靠**归档**控制索引长度。
> **具体什么输入会让"共享层也衰减"出问题**：某条共享根因因为三个月没人命中而衰减消失，另一个刚上手的 agent 正好撞上它，检索不到，重踩一遍并且没人知道这是重复事故。

### 9.3 存哪边的判据（v1.3.1）：一条二分线

原文 [实测]：「通用／跨工具的坑（编码、版本控制、网络等）正文记**踩坑日志**；仅某 agent 环境私有的坑（其专属路径、配置）正文记**该 agent 自己的 store 那一层**。交叉相关时，另一方**只放一行指针**（含根因号／日期），**不复制正文**。」

```
这个坑换个环境还成立吗？
  ├── 成立（跨工具、跨机器、通用）      → 正文写进共享踩坑日志
  └── 只在某个 agent 的私有环境里成立    → 正文写进它自己记忆库的对应层
        └── 共享侧需要提到它时：只写一行指针（根因号 + 日期），不抄正文
```

> **为什么"一行指针"而不是"抄一份"**：抄一份＝两个事实源。日后正文改了一处，另一处变成过期版本，而检索时两份都会被读到，冲突由读者现场裁决——这正是『原则』第一条"单一事实源"要避免的漂移。指针只负责"引过去"，内容永远只有一份。

### 9.4 生效链：注册副本、互认指针、降级路径、巡检

这一段全部来自 v1.3.1『修复生效链断点』 [实测]（内容按公开页规矩抽象化，不写任何真实路径与宿主代号）：

| 环节 | 机制 | 原文记录的坏法 |
|---|---|---|
| **注册** | 宿主 skill 的加载目录下放一份同名副本，自然触发才会生效 | 此前未注册 → **自然触发停摆**（文件在库里躺着，AI 根本想不起来它） |
| **互认** | 记忆纪律那支 skill 的"兄弟 skill"节、编码行为准则那支的第 6 条，都内置了指向本 skill 的指针与**降级路径** | 外部只能靠硬编码路径直读它 |
| **降级** | skill 不可用时，直接读共享日志根目录下的索引文件 | 无降级 = 一旦挂载失效，整套检索归零 |
| **巡检** | 记忆库工具目录下一个巡检脚本会检查本 skill 的**注册存活**与**指针存活** | 「**lint 只查格式不查注册覆盖**」——所以这件事长期没人发现 |

> **[实测] 最后一行是全章最值钱的一句**：一个只会检查格式的检查器，会给你一个"一切正常"的世界，而真正的失效发生在"文件存在但没人加载"这一层。这直接导出第 11 章体检为什么要单列"触发存活"这项。
> **[推演] 目录前缀也是生效链的一部分**：CHANGELOG.md『v1.3.2』记录了权威库目录名加上前缀升级（按本机命名规则，那个前缀＝常驻注册类），动因是「已是每台 agent 本体的常驻户，命名仍是普通自创前缀会让 AI 误判它'靠调度即可'」——**名字里带着"是否常驻"这个信息**，是给调度器读的元数据。

## 第 10 章 失效与恢复：它怎么坏、怎么发现、怎么退

这套系统的失效模式有个共同特征：**几乎都不报错**。下面每条都写清"怎么坏 → 怎么发现 → 发现后怎么退"。

### 10.1 索引指错：日志根目录被挪走

- **怎么坏**：索引里的链接全是**相对路径**（`roots/RT-00X-....md`、`pitfalls/....md`）。根目录整体搬家时相对链接其实安全；坏在两种情形——① 只把 `pitfalls/` 挪走、索引留下；② 在新位置重建索引但沿用旧目录里的相对层级假设。
- **规则依据** [实测]：『原则』第五条「**位置稳定**：`<log-root>` 固定，索引路径才不会断」；『两层结构』那条同时要求「**第一次用先和用户确认存储位置，别写死**（换机器／换环境时可改）」，理由写得很直白：「路径保持稳定，索引才不会指错」。
- **怎么发现**：按索引逐行点开链接跑一次存活检查（第 11 章第 6 项）。
- **怎么退**：不要改历史条目里的任何东西，只在原位置留一份指向新位置的说明文件；索引里的相对链接保持不动。**"别写死"与"要稳定"这对看似矛盾的要求，真实含义是：位置由用户当场定一次，定了之后就不再动。**

### 10.2 计数虚高 / 漏判：判据被现场解释掉

- **怎么坏**：两条路径。① 主观放宽——"多少算受了一点启发"就往上报；② 机械漏判——计数脚本认的字段写法与文件里的实际写法不一致（第 6.1 节那三种写法 `^root:`／行内 `> root:`／`^root_cause:`，外加 `^also_root:` 双挂面，就是真实漏判史留下的痕迹 [实测]）。
- **怎么发现**：文件 `hits`（权威）与文末『命中记录』表行数应当一致——**每次 +1 都要在表里留下一行**，两者差值就是虚高计数 [推演]（这是由"两处同步＋追加一行明细"两条规则直接推出的可核算关系）。
- **怎么退**：以文件为准回修索引；被证明是"事后才发现已有记录"的那类命中，按唯一排除条款**冲销**，并在命中记录那行注明"冲销＋原因"。

### 10.3 格式漂移：改了一半

第 8.4／8.5 节已展开。这里只补"怎么退"：**发现漂移时，先改模板再改规则还是先改规则？** 答案来自 v1.5.0 的实际做法 [实测]（CHANGELOG.md 本轮同步清单：SKILL.md＋`assets/entry-template.md`＋根目录 `_template.md`＋索引那一行）——**一次动作里全部改完**，然后把详解页留给同一次同步（本页就是那次同步的产物）。**不许**"先改规则，模板下周补"，因为下周写的每一条新案例都在用旧模板，每写一条就多一处要回改的存量。

### 10.4 触发停摆：文件在、加载不上

见第 9.4 节。补一条 **[推演]** 的判别方法：判"生效"不能只看文件存在，要看**注册位是否存在且指向本体**（用 `fsutil reparsepoint query` 的退出码判，别用会恒 `False` 的那个符号链接判断函数）＋**降级路径是否可用**（真去读一次索引文件，读到了才算）。

### 10.5 存量被污染：好心回填

见第 6.4 节。恢复动作：一旦发现某批老条目被"补写"过复现／验证而没有注明补录日期，**把它们标为存疑**，并在索引分组里显式说明"以下条目证据不可信"。删掉它们反而更糟——删掉之后没人知道这里曾经有过什么。

### 10.6 双挂面漏挂：一族变瘦

- **怎么坏**：一条案例真属于两族，写的人被迫选一个（模板侧缺 `also_root`，见第 5.3 节），两族的 `cases` 各少一条。
- **可观察后果**：`cases` 是升华规模轴的输入 → 升华被推迟；更隐蔽的是识别信号不交叉——A 族的识别信号里没有"B 族症状也算"这一条，未来从 B 族症状进来的人根本扫不到 A 族。
- **怎么发现**：第 11 章第 4 项体检（同一案例的正文里提到两种病根描述，但 frontmatter 只有一个 `root`）。
- **怎么退**：就地补 `also_root`（这是**新增字段而不是改写既有证据**，不属于"追改"，与第 6.4 节不冲突）[推演]，同时把交叉关系写进两族各自的识别信号。

### 10.7 归档后指针悬空

见第 4.4 节第 3 条。恢复：把链接改指向归档目录（改**索引**里的链接是允许的——索引是展示层，不是证据层）。

### 10.8 识别信号被写成空壳

- **怎么坏**：根因文件里『识别信号』一节最容易被省（模板里那一节下面就是一个空的 `- ` 项目符号 [实测]，`assets/root-template.md`），一省，这一族就退化成"只有名字"。
- **后果**：『检索流程』第 2 步"先扫根因索引表——有没有哪个根因的**识别信号**对得上当前问题"直接失能；索引表里"一句话"那一列只能靠字面猜，判同型退回关键词匹配。
- **怎么发现**：第 11 章第 5 项（空信号节计数）。
- **怎么退**：从该族已有案例的『现象』段里回抽信号（案例里有屏上原文），补进根因文件——这是**允许的回填**，因为补的是根因层的抽象而不是历史案例的证据 [推演]。

### 10.9 一句话总结失效面

> 这套系统的坏法基本都是"**沉默的坏**"：格式漂移不报错、触发停摆不报错、漏判不报错、回填不报错。所以第 11 章的体检必须**主动去找红**，而不是等它红。

## 第 11 章 例行体检：怎么验证它真在生效

**先说清这一章的性质**：SKILL.md 里**没有**名为"体检"的章节 [实测]（数法：数正文里 `## ` 开头的一级节，共 13 个：何时使用／两层结构／为什么分两层／索引格式／根因文件格式／案例文件格式／检索流程／记录流程／命中计数／升华／原则／与记忆 PITFALL 层的关系／版本）。因此本章是**把散在各节的要求汇编成可执行规程**，整体标 [推演]；每条后面注明它由哪条 [实测] 规则导出。口径上这叫"空章如实标注"，不假装是原文。

### 11.0 第 0 步永远是正例校验

**正例校验**＝先拿一个**已知存在、已知应当被抓到**的东西去量这把尺子，确认它能报红／报绿，再拿它去量别的。

```
故意做一条一定不合规的样本（例如：案例文件不写 root 字段）
   ↓ 跑你的检查
   检查报红了 → 尺子可用，继续体检
   检查没报红 → 尺子坏了，先修尺子；本轮所有"一切正常"作废
```

> 为什么把这条放在最前 [推演]：本 skill 的失效面全是"沉默的坏"（第 10.9 节），一个本身写坏了的检查脚本会**稳定输出"零问题"**，而"零问题"读起来跟"真没问题"一模一样。不跑正例校验的体检等于没跑。
> 真实库里对这件事有过共鸣的痕迹 [实测]：『命中计数』那次判据修订，起因正是"干活途中扫到记录、被记录纠错"——即一次意外的正例暴露了尺子写错。

### 11.1 七项体检清单

# RT-00X 同一份文件既是证据又是产物 → 覆盖式写回必丢原件

## 一句话根因

把"读原始内容 → 加工 → 写回同一路径"当成一步操作：写模式一打开就清空原文件，
于是任何加工失败或过度加工，损失都直接落在唯一那份证据上，且不可回滚。

## 识别信号

- 代码里出现"先 open(p).read()、后 open(p,'w').write(...)"，两次路径是同一个变量
- 加工链里有截断 / 省略 / 摘要 / 脱敏 / 折叠一类"必然丢内容"的动作
- 产物与原件同名同目录，没有 `.derived`／`.bak` 一类的第二份
- 脚本没有 dry-run（空跑预览）开关，或没跑过 dry-run 就直接执行

## 通用对策

1. **证据只读**：原始输出先落到一个不再被写的文件里，之后所有加工只读它。
2. **加工结果写派生文件**，永不与原件同名（约定后缀，如 `.derived.md`）。
3. 确实必须原地改时，**改前先复制一份原件**，并在写之前打印"将被丢弃的行数"，
   非 0 就中止（把不可逆操作降级成可检查操作）。

# 坑：把 142 行原始命令输出就地截断成 60 行写回同一文件 —— 原始证据被不可逆销毁 🔴

## 1. 现象

当时在整理一份台账：某条命令的原始输出共 **142 行**，需要摘前 60 行入台账。
脚本跑完的屏上回显是 `written 60 lines`；随后想核对原文，打开该文件只有 60 行，
`wc -l` 报 **60**（应为 142），且无任何报错。

## 2. 复现

```sh
# 前置：造一个 142 行的文件，把它的行数记下来
python - <<'PY'
p = "<你的文件>"
lines = open(p, encoding="utf-8").read().splitlines(keepends=True)
assert len(lines) == 142, len(lines)
open(p, "w", encoding="utf-8").write("".join(lines[:60]))   # 关键：同一 p，覆盖式
PY
wc -l "<你的文件>"        # 得到 60，且原 142 行已无处可取
```

别人照着跑**能再撞一次**；若你手上没有 142 行的原件，可用任意长文件代替，结论不变。

## 3. 现场代码

`<台账脚本>:<行号>`，抄**改之前**那一版：

```python
src = open(path).read()            # 读的是证据
keep = truncate(src, 60)           # 加工必然丢内容
open(path, "w").write(keep)        # 写回的还是同一个 path —— 这里就是病根
```

## 4. 根因（机制）

`open(path, "w")` 在打开的那一刻就**清空**了文件（截断到 0 字节），此时新内容尚未写入。
所以从"清空"到"写完"之间，这份唯一证据处于消失状态：中途异常、截断过度、编码失败，
任何一种都会把"少几行"升级成"全没了"。
**不停在表象**：表象是"少了 82 行"；机制是"**同一份文件同时承担证据与产物两个角色**"，
于是可回滚操作被升级成不可回滚操作。（本节写本案例的具体机制；族归属在 `root:` 字段。）

## 5. 修法

拆成两个文件，并加"丢弃行数"闸门：

```python
raw = open(path, encoding="utf-8").read().splitlines(keepends=True)   # 证据只读
derived = path.replace(".md", ".derived.md")                          # 产物另存
dropped = len(raw) - 60
assert dropped == 0 or allow_drop, f"将丢弃 {dropped} 行，中止"
open(derived, "w", encoding="utf-8").write("".join(raw[:60]))
```

**为什么这样切**（改这里而不是别处）：不去加"写之前提醒一下"，因为提醒不阻断写入，
下次没人看提示照样执行；改在"path 只有一个用途"这一点上，把不可逆变成可检查。
也不是去别处加备份脚本——那需要在每个调用点都记得跑，而这里的两行改动一次覆盖全部路径。

## 6. 验证

改后实测（原始输出落盘，不转述）：

```
$ python <台账脚本> --check
lines_in_source: 142
derived_lines: 60
source_lines_after: 142
dropped_guard: armed
$ # 断言 3 条：源文件行数不变 / 派生文件行数==60 / 闸门处于装载态 → 3 passed
```

断言条数 **3 passed**；"改好了"三个字不算验证。

## 7. 能否借鉴（通用规律）

**凡"读一份权威文件 → 加工 → 写回同一路径"的操作，都是把可回滚变成不可回滚。**
判据可以机械化：执行写的那一刻，**除了目标文件之外还有没有第二份拷贝**？
没有，就是在赌运气。这条与具体工具、语言、场景无关——台账整理、配置改写、
知识库入库、批量格式化都属于同一类。

## 8. 教训（一句可迁移纪律）

**改证据之前先复制证据；加工结果一律写到派生文件，不写回原件。**

| 1 | **一上来就翻案例，不先看根因表** | 被当时的具体细节牵着走，把"那次那个绕行手段"照抄进新场景，越修越偏 | 检索流程强制先扫根因表（『检索流程』第 2 步；『原则』"根因优先"） |
| 2 | **把根因写成"这一个问题"** | 族里永远只有 1 条案例，`cases` 攒不起来，规模轴升华永不触发，下次换场景照样搜不到 | 建族前做"抹掉工具名文件名还成立吗"检验（『记录流程』第 2 步＋第 5.4 节） |
| 3 | **『现象』段写转述不贴原文** | 关键特征被记忆抹平，两周后这条读起来像"普通的一次失败"，同型再也对不上 | 「屏上原文或具体数字，转述不算」（『案例文件格式』第 1 段） |
| 4 | **『验证』段写"改好了"** | 自我宣布成功被当成证据，后续所有人基于一个没被证实的修法继续盖楼 | 实测输出／断言条数（第 6 段；v1.5.0 补这段的动因就是"『改好了』这句话被当成证据"） |

| 6 | **删掉『我自己引入的错』这一节** | 修法自身引入的新错无处记，同类二次事故重复发生；且缺节分不清"没犯错"还是"没回头看" | 没犯错就写「无」，**不许删节**（『案例文件格式』＋『记录流程』第 3 步） |

| 8 | **给"事后才发现已有记录"补 +1** | 命中虚高 → 假规律被升华进常驻区，挤掉真正该常驻的规则，且再也无法证伪 | 唯一排除条款；**宁可少记不要虚高**（『命中计数』） |
| 9 | **体裁升级时顺手回填历史条目** | 等于替当年的自己编造复现与验证证据，是**伪造**；后果是全库证据可信度崩塌 | 旧条目不追改；只有"当年留了原始回显"才就地补并注明补录日期（『案例文件格式』末段） |
| 10 | **改规则不改模板（或反过来）** | 下次照旧模板写出的条目与新格式对不上，计数与聚合集体失灵且不报错 | **全处同步铁律**：所有副本同一次改完，改完实跑 md5 对账（『升华』节末段） |
| 11 | **肉眼清点副本、用符号链接判断函数判 junction** | 把联接当成两份独立副本去改，或以为"没有副本"其实有；对账结论全错 | 判链用 `fsutil reparsepoint query` 的**退出码**，`os.path.islink` 对 junction 恒 `False`（同上） |
| 12 | **每个 agent 各写一份日志** | 两份内容漂开，检索要问"哪份是真的"，同一坑记两遍 | **单一事实源**＋所有 agent 共用一个 `log-root`（『原则』第一条＋『统一储存』条） |

## 第 15 章 工程规范与安全规范

### 15.1 命名规范（全部 [实测]，来自 SKILL.md 与两份模板）

| 对象 | 规则 | 为什么 |
|---|---|---|
| 根因文件 | `RT-<三位编号>-<slug>.md` | 三位数保证排序稳定（`RT-1` 会排到 `RT-10` 后面）；slug 让人不打开文件也能认出是哪族 |
| 案例文件 | `YYYY-MM-DD-<slug>.md` | 日期开头＝天然的组内新→旧排序键（索引案例清单就按这个排） |
| 模板件 | `_template.md`（下划线开头） | 在按字母排序的目录里排最前，且一看就知道不是内容文件；数案例数时要**显式排除**它（第 11 章第 1 项） |
| 归档目录 | `pitfalls/archive/` | 与内容层同级但不同目录，索引指针一句就能说明去向 |
| 记录者标识 | "稳定短标识"，可用助手标识／人名／`shared` | 公开页一律用 `shared` 这类中立标识（本页隐私处理，见 15.4） |

### 15.2 字段规范（谁能改谁不能改）

| 字段 | 位置 | 可变性 |
|---|---|---|
| `root_id`／根因文件名里的编号 | 根因层 | **只增不改**（改了断链） |
| `root` | 案例 frontmatter | 归错族时可以改指向，但**改后必须回修索引分组**，否则三处数字立刻不齐（第 11 章第 2 项） |
| `also_root` | 案例 frontmatter（规则正文提到、模板尚未列，见 15.3） | 新增即补挂，属追加，不是追改证据 |
| `cases` | 根因 frontmatter | 每挂一条 +1，机械维护 |
| `hits` | 两层 frontmatter | **权威值**；只能在真实命中时 +1，不能"估算" |
| `last_hit` | 案例 frontmatter | 每次命中改写为当次日期 |
| `escalated` | 两层 frontmatter | 单向 `false → true`（升华不可逆，若要撤销须在文件里写明撤销原因） |
| `created:`／`updated:` | 索引 frontmatter | `updated` 只增不删；`created` 写定不再动 |

### 15.3 冷启动（第一次开张要做什么）

```
1. 先跟用户确认 <log-root> 的位置——第一次用别写死（『两层结构』明确要求）
2. 建 roots/ 与 pitfalls/ 两个目录（『记录流程』第 1 步）
3. 复制三份模板：assets/index-template.md → pitfall-log.md
                  assets/root-template.md  → roots/RT-<最小未用号>-<slug>.md
                  assets/entry-template.md → pitfalls/YYYY-MM-DD-<slug>.md
   注意：模板顶部的 name/description/type 三行元信息要**替换成**各自规定的 frontmatter 字段
         （两份模板都在开头用一句括注交代了这件事 [实测]）
4. 第一条坑就老老实实八段填全——体裁的说服力是靠第一条就长对
5. 跑一次第 11 章体检（含第 0 步正例校验），确认尺子能用
```

> **[推演] 为什么第 3 步那句"替换元信息"值得单列**：三份模板顶部都带 `name`／`description`／`type` 这种**描述模板自身**的字段。忘了替换的话，实际条目文件的 frontmatter 里写着"我是模板"，所有按 `^root:` 之类模式扫的计数脚本对它一律无感——于是库里凭空多出一条"看不见"的记录，还占着一个日期文件名。

### 15.4 安全与隐私规范（公开仓库这一侧的纪律）

| 项 | 规定 |
|---|---|
| 盘符绝对路径 | 公开页**零出现**。写"共享日志根目录／本机 skill 库／宿主 skill 注册目录／用户目录下的宿主配置" |
| 条目编号 | 真实编号不复制，只写形状：`RT-00X`／`RT-<三位编号>`／`pitfalls/YYYY-MM-DD-<slug>.md` |
| 记忆库目录与条目号 | 不写真实目录名、不写常驻区真实文件名与真实序号；写"记忆库的常驻铁律区""编号接在已有序号之后" |
| 事故当事人标识 | 不写真名／代号，统一 `shared` 或"某个 agent""用户" |
| 事故本身 | **保留技术细节、抹掉可定位信息**：行数、命令形状、失败机制照写（见第 12 章），日期、路径、项目名、人一律抽象 |
| 凭据形状 | 本页未涉及；这套日志本身**不该存任何密钥**——记录里出现 token／密钥串时应就地替换为 `<你的密钥>` 再入库 |
| 允许保留 | 通用工具名与环境事实（Windows、`fsutil`、Git Bash、Python 判断函数名等），这些不构成隐私 |
