# A-Cao-踩坑日志（pitfall-log v1.3.1）

> [← 返回总目录](../README.md#skills-index)

## 五分钟速览


1. 结构是三层，极轻索引（每次会话都读）+ 根因层（检索入口）+ 案例层（深读用），细节按需加载省 token。
2. 根因是一级公民，案例挂在根因下面。检索先命中根因拿通用对策，不够再翻案例。
3. 案例里最值钱的字段是「能否借鉴」，它把一次性修复变成可迁移的规律。
4. 命中计数四个条件同时成立才 +1（真检索、真翻看、真获益、真解决），事后发现同根因不算。
5. 案例命中三次以上、或同根因攒够三条，升华进记忆 CORE 铁律区，每次会话强制加载。
6. 索引有界，超约五十条就归档冷条目，索引永远保持极短。

一句话概括设计目标，**同一个坑不踩第二次，换了个马甲也能认出来**。

## 它在解决什么问题

修过的 bug 会再犯，原因有两层。

第一层是笔记没用。记过，图省事写了「已修复」三个字，修在哪、为什么错、怎么好的，全忘了。第二次撞上，全价重踩。

第二层更阴险，根因会伪装。同一个根因换个症状出现，你认不出它是老熟人。一个真实案例，中文编码这一个根因，在同一个仓库里炸了两次，前后差 12 天。第一次是中文 .ps1 被 GBK 解码成乱码，看起来是「写脚本的坑」。第二次是中文路径传给 git，误删了整个 docs/ 目录，看起来是「git 命令的坑」。症状八竿子打不着，按案例平铺记录，这两条永远看不出是一回事。

| 故障 | 表现 | 对应设计 |
|---|---|---|
| 记了等于没记 | 只有「已修复」三个字 | 案例五节强制写全（上下文/为什么/解法/能否借鉴/来源） |
| 根因换马甲 | 同一个根因换个场景再炸 | 根因层，识别信号提前认出它 |
| 索引变怪物 | 记录越攒越多，每次读索引就烧 token | 索引有界 + 冷条目归档 |
| 日志自我感动 | 记了一堆，从没被翻出来过 | 命中计数，宁少勿虚 |
| 坑记了还是踩 | 100 条记录拦不住第 101 次 | 升华机制，反复验证的进铁律 |

## 根因层，整套设计里最值钱的一步

从坑里能捞出来的最大价值不是「这次怎么修的」，而是「为什么会踩、下次怎么一眼认出来」。

结构三层各管一段。`pitfall-log.md` 是极轻索引，每次会话都读，所以绝不内联完整条目，索引只存指针。`roots/` 目录放根因文件，一个根因一个。`pitfalls/` 目录放案例文件，一条坑一个，按需加载。

根因文件正文四节。**一句话根因**，这类问题的共同病根。**识别信号**，出现哪些迹象就该往这里想，这是最有用的部分，它是「提前认出来」的钩子。**通用对策**，不针对任何具体案例、能直接照做的做法。**挂载案例**，该根因下的案例清单。

上面那两条编码案例归成同一个根因后，识别信号提炼成一句话，中文出现在跨进程边界，先怀疑编码，再怀疑逻辑。下次它变成配置文件里的中文再来，你就能认出它。

检索顺序跟着设计走。读索引 → 先扫根因索引表 → 对上了读根因文件拿通用对策先试 → 根因层不够再翻该根因下的具体案例找灵感。多条不相干的案例挂在同一个根因下，规律自己就显出来了，这是平铺时间线永远做不到的。

根因编号 `RT-001`、`RT-002` 只增不改。别人可能引用它，改号就断链。

## 「能否借鉴」，把一次性修复变成可迁移经验

案例文件五节里，上下文、根因、解法都只解决这一次，只有「能否借鉴」把这次经历提炼成下次能用的规律。它和 `root` 字段的分工是，root 说「这属于哪一类」，能否借鉴说「这一类里可迁移的规律」。

贴一段真实记录的收尾。某次清理差点删掉被硬编码依赖的工具。

> 判定能不能删的顺序应当是，一查有没有被引用，grep 全项目。二查能不能重建，缓存和生成物通常可以，唯一副本不行。三查是不是真的过时，对比时间戳和内容，而不是看名字。涉及删除时优先隔离到待确认目录，同盘移动瞬时且完全可逆。

这段话在下一个清理任务里直接救场，就是它存在的意义。

## 命中计数，防止日志变成自我感动

记了一堆坑，哪些真救过场？没度量之前，答案是不知道。记录的人觉得有用，可它从来没被翻出来过呢。

判定刻意定得严。**四个条件同时成立才 +1**，发生了检索动作（真去读了索引）、翻看了具体记录（读了 RT 文件或案例文件）、从记录里获得了启发并用它解决了当前问题（不是「看着相关」就给分）、问题真的解决了。明确排除一条，事后发现「这两个坑同根因」不算命中，没有检索动作、没有翻看、没有获益，只是事后归类而已。

**宁可少记，不要虚高。虚高的数字等于没有数字。**

计数落在两处必须同步，索引行的 `🔥N`（0 也写 `🔥0`）和文件 frontmatter 的 `hits`（权威值）。根因层和案例层各自独立计数，只走根因层用通用对策解决，根因 +1；深读案例并获益，案例 +1；都帮上忙各 +1。

计数还是一座桥。某条案例命中三次以上，或某个根因下案例攒够三条，自动升华进记忆 CORE 的铁律区，之后每次会话强制加载。哪类问题值得升级成规则，让数据自己说话。

## 索引不会变成新的怪物

踩坑日志最容易死的方式，是变成第二个越写越肥的记忆文件。防线是索引有界，案例超约五十条，冷条目归档到 `pitfalls/archive/`，索引里只留一个指针。索引每次会话都读，所以它必须永远保持极短，这条纪律是整个结构省 token 的关键。

## 和记忆 PITFALL 层怎么分工

两套东西看着像，职责不同。踩坑日志是跨 agent 共享的教训沉淀，谁踩谁记、大家都能查，不评分不衰减。记忆 PITFALL 层是各 agent 自己的记忆管理，给坑打分、衰减、升华。边界是，坑的原始记录记踩坑日志（共享），反复出现的坑升华成铁律才进记忆 CORE，避免同一坑记两遍。

v1.3.1 定了「存哪边」的判据。通用、跨工具的坑（编码、git、网络这类）正文记踩坑日志。仅某 agent 环境私有的坑（专属路径、配置）正文记该 agent 自己的 store PITFALL。交叉相关时另一方只放一行指针，不复制正文。

三套 skill 双向互认。编码行为准则第⑥条内置了本 skill 指针和降级路径，记忆纪律 skill 里也挂了兄弟节点，巡检脚本会检查注册与指针存活。这是 v1.3.1 修的生效链断点，此前本 skill 没注册进宿主，自动触发停摆，外部只能靠裸路径续命。**规则写得再好，注册链断了就等于不存在**，这个教训本身也值得记下来。

## 目前的家底

9 条案例收在 6 个根因下。RT-001 中文编码，RT-002 依赖隐式上下文，RT-003 静默失败，RT-004 凭外观归类，RT-005 绕过工具机制手工干预，RT-006 环境拦截误判为代码缺陷。三个模板（索引/根因/案例）在 skill 的 assets/ 里，复制过去改改 frontmatter 就能起一套自己的日志。

## 什么时候不用

一次性 bug 的即时诊断修复走正式诊断流程，本 skill 只管沉淀与查阅，不管现场救火。没有踩坑历史的全新玩具项目，先攒两次疼了再建也不迟。
