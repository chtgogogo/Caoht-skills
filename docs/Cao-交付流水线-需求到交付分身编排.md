# Cao-交付流水线（delivery-pipeline v1.1.0）

> [← 返回总目录](../README.md#skills-index)

## 一种你大概率体验过的失控

让 AI 做个项目。它热火朝天干了两小时，你回头一看：写到哪了？不知道。做完了什么？说不清。中途会话断了想接着来——从头开始。最尴尬的是验收：它说"完成了"，你问"怎么验证的？"——没有验证这回事。

根源是三件事没做：**没有设计就开写**（聊两句就动手，返工三轮）、**计划是一个巨型文件**（所有任务塞一个 plan.md，AI 读一半丢一半）、**每步不留产出物**（这步的输出没落盘，下步的输入就没了）。

这个 skill 是一条十二步的总装流水线：**磨设计 → 选型 → PRD → 切卡 → 分身执行 → 验收 → 台账 → 收尾**。方法论站在 obra/superpowers 的肩上（苏格拉底磨设计、2-5 分钟实习生粒度切卡、双评审），做了完整的中文化和工程化改造。

## 四个设计，专治失控

**① 台账即断点存档。** 在做/待执行/做完+阻塞三区制，每张卡完成立即勾。任何时刻中断、任何时刻续传——启动第一件事是查台账："继续上次（从第 N 张卡接着来）还是开新的？"你再也不用向新会话解释"我们做到哪了"。

**② 验收先于实现。** 每张卡开工前，"怎么验证"必须已经写清（评测基线/测试脚本/肉眼清单，形式不限但必须写）。这是铁律不是建议——AI 说"完成了"的时候，验证动作早就摆在那了。

**③ 一卡一文件 + 派遣上下文最小化。** 每张任务卡独立文件（拒绝巨型计划文件），派子代理执行时只喂"该卡 + PRD 相关段 + 精确文件路径"，绝不喂全项目历史——token 花在活上，不花在噪音上。

**④ 按需加载（铁律 9）。** 主 SKILL.md 永远只有八十行——十二步索引是指针不是正文；进哪一步才读哪一步细则，一次只读一个；46 个文件的自包含依赖库只在顶替或查原文时才碰。**流水线本身就得先遵守"省 token"的纪律，才有资格管别人。**

## 上手时的真实体验

启动时它会先问四个问题、给推荐让你选：**A 轻量**（小改动五步走）/ **B 标准**（新功能九步）/ **C 企业**（全十二步+双评审）/ **D 跳步优化**（已有项目先扫短板，缺哪补哪）。另外支持**单步直调**——你只想要"切任务卡"这一步，说"帮我切卡"它就直接进，不逼你跑全流程。

选型阶段是分层深选：从目标约束到语言到框架到部署，每层 5-9 个候选、每个候选**明说缺陷**，最后综合调和冲突——不是替你拍板，是把拍板需要的信息摆齐。

## 和 superpowers / spec-kit 比，差在哪

说清楚：superpowers 是这套方法论的重要来源，本 skill 的 depends/ 里存着它全部 12 个相关 skill 的原文（MIT）。差异是改造方向：

| superpowers / spec-kit | Cao-交付流水线 |
|---|---|
| 英文方法论，工作流分散在 15 个 skill 里 | 中文一体化的十二步索引，步与步的产出→原料衔接写死 |
| 执行要么子代理要么单会话，重头跑 | **台账三区制断点续传**，任何会话任何时刻接续 |
| 面向"从零到 PR 合并" | **跳步优化模式**：已有项目扫短板、缺哪步跑哪步 + 单步直调 |
| 依赖你搭好它的框架环境 | 46 文件自包含（20 份方法论原文副本 + 16 个附属模板，锚定同一 commit），复制即用 |
| 验收是"测试要写" | **验收先于实现**：开工前基线就绪，适合连测试框架都没有的毕业生项目 |

## 什么情况别用

- 改一两行的小修补——直接改，杀鸡别用牛刀；
- 纯探索性 prototype（明天可能全推翻）——台账和卡文件制是给要交付的东西准备的；
- 连肉眼清单都不愿定的项目——"验收先于实现"会卡在第一步，这是故意的。

## 实战绩

v1.0 到 v1.1 由"构建它自己的过程"实测了核心环节：磨设计→选型→十二步索引按用户逐条拍板收敛；20+16 份依赖副本全量校验（69 处互引零失效）；期间抓出并修复了"CDN 缓存旧版与仓库 main 漂移"的真问题——这套自检流程自己就是流水线纪律的产物。
