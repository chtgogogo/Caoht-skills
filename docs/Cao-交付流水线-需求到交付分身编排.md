# 需求到交付总装流水线 · 完整详解手册

## 第 0 章　五分钟速览

1. **它管的是一段路，不是一个点。** 输入是一句还糊着的话（「我想做个能自动盯竞品价格的东西」），输出是一个别人能接手、能验证、敢说出口的东西。中间被切成一串固定阶段，每个阶段必须留下一个**产出物文件**才算走完；只留下聊天记录不算走完。[实测] 阶段总数要当场说清：`SKILL.md` 第二节标题写的是「十二步索引」，可它下面那张表实际列了 **14 个号位**（① 磨设计 → ② 选型 → ③ PRD → ④ 卡库初始化 → ⑤ 切卡 → ⑥ 执行与派遣 → ⑦ 验收先于实现 → ⑧ 台账 → ⑨ 知识图谱外挂 → ⑩ 里程碑回看 → ⑪ 代码评审 → ⑬ 安全基线 → ⑭ 对外口径 → ⑫ 收尾，末位把 ⑫ 排在 ⑭ 之后）。多出来的两号正是 v1.2、v1.3 补上的 ⑬⑭，标题没跟着改（详见第 15 章）。**号位是 14 个，这是可数的；「十二步」是历史叫法。**
2. **阶段之间靠「准入准出条件」咬合。** 上一阶段的交付物不够格，下一阶段就不许开工。铁律 1 的原话形态是「产出物文件不落盘 = 这步没做完」，卡点失败的标准动作是**退回上一阶段补件**，而不是"先干着，文档回头补"——这条决定了它跟"提示词流程"的本质区别：它有闸门（gate，不合格就拦住的检查点），提示词没有。[实测]
3. **台账即断点存档。** 所有进度按序记在一本流水账（台账，按序记录每一步的流水账）里，分区是「在做 / 待执行 / 做完加阻塞」三区，每完成一张卡立刻勾。任何会话在任何时刻断掉，新会话第一件事是查台账，然后问「接着上次第 N 张卡来，还是开新的」——断点续传不是靠记性，是靠这本文件。[实测]
4. **验收先于实现。** 每张卡开工之前，"怎么验它算做完了"必须已经写在卡里：评测基线、测试脚本、肉眼清单，形式不限但必须写。顺序反过来是关键——验证动作在动手前就绪，那么当执行体说"完成了"的时候，标准早就摆在那了，没有争论空间。[实测]
5. **分身编排：主控不动手，执行体只吃最小上下文。** 一个上下文从头做到尾会崩，不是因为它笨，是因为它的"注意力"会被历史挤干净。这套设计把主控降格成调度与记账的人，真正写码的是被临时派出去的执行体，每个只领到自己那一张卡。[实测]
6. **按需加载，主文件只有 113 行。** 阶段索引是指针不是正文，进哪一步才读哪一步的细则，一次只读一个文件。流水线自己得先守省 token 的纪律，才有资格管别人的 token。[实测]
7. **两步阻断式把关（不合格就直接拦住，不许往下走）。** 安全基线检查与对外口径检查是独立成步的闸门：前者管「东西会不会被人打穿」，后者管「说出去的话站不站得住」。两条都写了「任一命中不许收尾」。[实测]

一句话概括设计目标：**把「模糊想法 → 可交付」这段路上最容易丢的三样东西——进度、验收、对外陈述——各自钉死在一个明确的归属上。**

## 第 1 章　这套系统在解决什么问题

让 AI 做一个完整项目，最常见的死法不是"它写错了"，而是**没人说得出现在到哪了、以及凭什么算做完**。这两件事一旦失守，后面所有产出都不可信：你不知道该不该继续等它，也不知道拿出去的东西能不能被人追问。

| 故障 | 表现（真实体感） | 这套系统的解法 |
|---|---|---|
| 会话一断，进度全丢 | 新会话从零开始，谁也说不清做到哪了，于是重复劳动、互相覆盖 | 台账三区制 + 每卡即时勾 + 新会话先查台账（第 5 章） |
| 计划写成巨型文件 | 一个上千行的 `PLAN.md`，每次执行都要把全文回注（把内容重新塞回上下文）进上下文，token 烧在历史而不是活上 | 一卡一文件 + 派遣只喂三样（第 7、8 章） |
| "它说完成了" | 问「怎么验证的」，答不上来——因为**根本不存在验证这一步**，验收标准是事后追认的 | 验收先于实现，验收字段是卡的必填项（第 6 章） |
| 过程不可见 | 它热火朝天干两小时，你不知道哪步做完了、卡在哪、token 花在哪 | 每阶段绑定一个产出物，产出物缺失即视为该阶段未发生（第 4 章） |
| 安全是漏网之鱼 | 每张卡的验收全过，上线后被外部拷问出一批实锤漏洞——因为安全不属于任何单卡 | 独立的安全基线步，三档分级，L1 有阻断项不许收尾（第 9 章） |
| 对外陈述失实 | 简历与 README 里的数字经不起追问：耗时、用例数、评测集规模、引用对象，四处对不上（勾稽＝两处数字能对上） | 独立的对外口径步 + 数字四件套，任一命中阻断收尾（第 9 章） |

三件事值得先说清，避免读者把它认成别的东西。

**第一，它不是任务管理工具。** 任务管理工具解决"人知道自己要干什么"；这里台账解决的是"**另一个会话里的另一个上下文，能准确接上活**"。判据不同：前者看人方不方便，后者看断掉之后接回来对不对得上。

**第二，它不是提示词模板集。** 模板集给的是"话怎么说"，这套给的是"闸门怎么设"。差别在失败时的表现：模板集失败了你只会拿到一段更长的废话；这套失败时会明确告诉你**缺的是哪个文件、缺哪个字段**。

**第三，它的知识体量不在主文件里。** 113 行 / 18,310 字节的主页装不下 14 个号位的全部细则，细则在 `references/` 的 **12 份**阶段与模板文件里，第三方方法论原文快照另有 **20 份**在 `references/depends/`、**17 份**附属模板与脚本在 `references/depends/superpowers_assets/`。递归文件数 51 的复算口径就是这四段相加：`SKILL.md` + `CHANGELOG.md` = 2，`references/` 顶层 .md = 12，`depends/` = 20，`superpowers_assets/` = 17，合计 51。[实测] 这就是第 3 章要讲的结构。

| 【依赖】/【P】 | 前者必须等前一张做完，后者（P＝parallel，并行）可同轮一起做 | 借用 spec-kit 的并行标记写法 |

### 2.3 任务卡与执行类

| 术语 / 行话 | 一句大白话 | 在本支里具体指什么 |
|---|---|---|
| 任务卡 / 一卡 | 一件小到能独立验收、独立交差的活，写成独立一个文件 | 铁律 3「禁止塞进单个巨型计划文件」 |
| 巨型计划文件 | 一个上千行、什么都写在里面的计划 | 被本支称为 **token 黑洞**（token＝模型一次能看的文字量单位；黑洞＝消耗只进不出） |
| 三层任务文档 | 同一件事写三份，一份比一份细：给人认领的清单 → 纲目 → 能照着动手的施工图 | L1 双清单 → L2 纲要卡 → L3 施工图卡（v1.5 新增，铁律 14） |
| 纲要卡（L2） | 这活要干什么、干到哪算完的中间层摘要 | 粒度小卡可以只写这一层（§4.1 实习生模板） |
| 施工图卡（L3） | 拿着就能开工、不用问人的一整套指令 | `docs/pipeline/具体任务卡/<编号>-<卡名>/`，全量 18 节 / 轻量 9 节两档 |
| 粒度三档 | 活的大小分小、中、大三档，档位决定写几层文档 | 小卡＝子代理 2~5 分钟、≤3 文件，只用 L2；中卡加轻量 9 节；大卡加全量 18 节 |
| 状态机（认领→拉上下文→执行→写回） | 一张卡的四拍：先说是我做的，再读要的资料，然后干，最后把结果写回去 | 阶段⑤定义的任务卡生命周期 |
| 主控 / 执行体 / 子代理 / 分身 | 主控＝只调度记账不动手的会话；执行体＝被派出去干具体那张卡的新会话（同一个模型开的另一份工作上下文） | 铁律 5、6；「分身编排」这个名字就来自这里 |
| 派遣 | 把一张卡交给一个执行体去做 | 双模式：本会话内起子代理，或生成一段提示词让你开新窗口贴进去 |
| 上下文 | 模型这一次能看见的全部文字（对话历史＋喂进去的文件） | 它的容量有限且会被历史挤满，这是"为什么要切卡"的物理原因 |
| 回注 | 把已经写过的内容重新塞回上下文让它再看一遍 | 巨型计划文件的代价就在这里：每执行一次就要回注一次全文 |
| 上下文最小化 / context isolation | 只给执行体它这活需要的三样：这张卡、PRD 相关段、精确文件路径 | 铁律 5「绝不喂全项目历史」 |
| 现查 | 别信抄来的行号与现状，写卡的人自己现在去把代码读一遍 | L3 施工图卡的"现状快照 + 现查指令"节 |
| 深写者 | 负责把 L3 写到能直接施工的那个人／那次会话 | 必须现查代码并过 §5.3 自检清单（8 项） |
| DoD / 停止信号 | 干到什么程度算完、什么情况必须立刻停手 | L3 施工图卡的两节 |
| 涟漪影响 / 合并烧数 | 这处改动会连带影响别处的清单；多张卡的改动最终合在一起要重新算一遍数 | L3 施工图卡的义务项 |
| 禁改清单 | 这张卡不许碰的文件，防止执行体顺手改动它不该动的东西 | L3 施工图卡的一节 |

### 2.4 验收、审查与证据类

| 术语 / 行话 | 一句大白话 | 在本支里具体指什么 |
|---|---|---|
| 验收先于实现 | 动手之前先写下"怎么验它算做完了" | 铁律 2；三种合法形式：评测基线分 / 测试脚本 / 肉眼清单 |
| 基线 | 开工前先测一次得到的那个分，之后拿它做对比 | ⑦ 的产出物就叫「基线记录」 |
| 肉眼清单 | 没有测试框架时，人一项项打勾的验收单 | 铁律 2 明确"形式不限但必须写进卡"，就是为了让不能跑测试的项目也能验收 |
| 先红后绿 | 测试得先证明它会失败，再证明它通过；不然你不知道这测试到底管不管用 | L3 施工图卡的测试用例表要求 |
| 双评审 | 一张卡做完，先审「跟设计一致吗」，再审「代码本身好不好」 | 铁律 7（企业／子代理模式）；严重问题阻断下一卡 |
| 里程碑总评审 | 攒到一定数量卡之后回头把整段一起审一遍 | ⑩ 自动触发线是 1/3 卡数（另有手动） |
| 用户视角验收卡 | 让一个不会敲命令的假想用户真的点一遍核心功能 | 铁律 12：MVP 卡组必须至少一张，浏览器点击、禁 API 直调作弊 |
| 证据形态 | 你说"绿了"要留下什么才算数 | 铁律 13：原始输出落盘、改前改后各跑一遍、口径标注 |
| 探针 | 只检查、不改动任何东西的小脚本或小动作 | ⑬ 安检里的"只读检查"、本页第 11 章的体检动作 |
| 判据 | 可以真拿去执行的判定标准，不是形容词 | 例：`git cat-file` 查引用对象是否存在 |
| 勾稽 | 两处数字能互相对得上 | ⑭ 数字四件套要解决的就是勾稽失败 |
| 幂等 | 同一件事重复做，结果一样 | 台账回写与状态机要求：重复勾同一张卡不该产生两个状态 |
| 数字四件套 | 一个对外数字必须带齐：来源命令 / 样本量 / 口径（含置信区间）/ 生成日期 | ⑭ 规则一；CI＝置信区间（这个数有多大把握落在哪个范围） |
| 过期即禁写 | 数字的生成日期早于最后一次评测，就不许再对外写 | ⑭ 规则二 |
| AI 署名披露 | 用 AI 干的活要标明是 AI 协作，不许冒充真人 | ⑭ 规则四 |
| 静默漂移 | 两份文件版本号一模一样、内容却不同，读者无从分辨哪份新 | 本页页眉的反面设定：本支恰好是「逐字相同」的 2 支之一，不存在此问题 |
| 自包含 | 需要的东西自己带着副本，不依赖外面装没装 | `references/depends/` 的 20 份原文副本 |
| 外部工位 | 从市场插件借来的某一道工序能力 | ⑨ 与「借字段不借判定权」那条硬规则 |
| 判定权 | "通过／不通过"这个结论由谁下 | 硬规则：永远在本地，外部插件只产内容 |

三个词组特别容易混，先在这里钉死：

- **台账 ≠ 任务板 ≠ 记录清单。** 台账与 `state.json` 是**状态真源**（谁在什么状态，唯一答案在这）；任务板是**给 AI 的队列**（干完一条删一条）；记录清单是**给人的轨迹**（只打勾不删）。三者分工写在 `references/台账模板.md` 的「双清单」节，混淆的后果见第 13 章。
- **产出物 ≠ 产出物内容。** 铁律只保证文件存在；文件里写什么、写得够不够，是各条细则与验收字段的责任。这个缝隙是第 10 章的主要失效面。[推演] 失效输入：一张卡把 PRD 的产出物写成 `PRD.md`，执行体创建了一个只有标题行的 `PRD.md`——铁律 1 判定"这步做完了"，全局验收标准因此整条缺位，直到 ⑦ 验收时才发现无基线可对照。
- **阻断 ≠ 严重问题。** 「严重问题阻断下一卡」是评审层面的，只拦后续那张卡开工；「L1 有阻断项不许收尾」是全局层面的，拦的是整个项目关门。两级闸门互相替代不了。[推演] 失效输入：某项目 L1 安检里发现 JWT 弱默认密钥被当成"下一张卡再修"，收尾照跑，产物推上公开仓库——因为卡级阻断管不到收尾，只有铁律 10 管得到。

### 3.3 判定顺序：一个会话被触发后的实际读盘次序

这是"按需加载"落到时间轴上的样子，顺序本身就是设计：[实测]

```
第 0 步  依赖自检（约 5 秒）
         查 references/ 细则与 depends/ 的 20 份副本是否齐
         齐全 → 继续；缺失 → 用自包含副本顶上；连副本也缺 → 按来源提示让用户重新获取
   ↓
第 1 步  查台账：<项目根>/docs/pipeline/ 找 台账.md
         找到且有未完成卡 → 问「继续上次（从第 N 张卡接着来）还是开新的？」
         没有 → 问项目落盘目录（默认建议 <项目根>/docs/pipeline/，可改）
   ↓
第 2 步  四选项提问：A 轻量 / B 标准 / C 企业 / D 跳步优化
         —— 硬规矩：先给推荐 + 理由，再让用户拍板（判定依据在 模式判定.md）
   ↓
第 3 步  单步直调旁路：用户点名某一步 → 跳过路由，直接读该步细则
         仅两件事不可省：落盘目录确认 + 台账登记（保持断点可续）
   ↓
第 4 步  进入号位 → 才读那一份细则，一次只读一个
         superpowers_assets/ 只在派遣/评审需要整篇模板时读对应的那一个文件
```

三个细节值得点出来，它们决定了这套结构能不能被讲透：

**一、依赖自检排在路由之前。** 顺序不是随便排的：如果先跟用户聊完模式再发现细则缺失，你会带着一个不完整的能力集做承诺。[推演] 失效输入：细则 `安全基线检查.md` 缺失而自检没跑，主控凭印象在 ⑬ 只查了"有没有硬编码密钥"这一项就放行收尾，用户以为过了 L1 全档——实际执行了一份不存在的清单。本支的对策是把"清单本身是否齐全"作为第 0 个问题，而不是第 13 个。

**二、查台账排在问模式之前。** 断点续传的优先级高于新流程启动：如果台账里已有未完成卡，模式其实已经被那次启动定死了，再问一遍会诱导用户改口，产生"同一项目两种模式"的混乱状态。[实测]（路由第 1 步的分支就是「找到且存在未完成卡 → 问继续还是开新」）

**三、"先给推荐 + 理由，再让用户选"是硬规矩。** 四档不是菜单而是判断结果。这条把选择成本从用户身上移到流水线身上——用户只需要拍板，不需要先理解 A/B/C/D 的差别。[实测] 反面设计见第 13 章：直接甩四档名词让用户挑，等于把方法论的学习成本转嫁给最不想学的人。

### 3.4 这一层和「多 Agent 治理」那一支的关系

`台账模板.md` 明写它的格式「沿用 多Agent团队协作文档治理 v1.3 的三区制」。[实测] 也就是说断点存档不是本支独创，而是**从防撞车那一支借来的存储格式**，本支加了 `state.json`（机器可读断点）与 `gates`（门禁枚举）两层。这解释了 5.1 里"三区制说法与四区结构并存"的历史包袱：借来的时候是三区，加"待执行"是为了承载依赖顺序。[推演] 这里必须留个诚实标记：两支的口径谁新谁旧，不能从本支单方面断定——本页只描述本支自己文件里写着什么，第 15 章再对一次账。

## 第 4 章　核心机制一：阶段切分与准入准出

### 4.1 它按什么口径切阶段

主文件「设计原则」那句就是切分口径：**这步的产出 = 下步的原料**。[实测] 所以判断"两个东西该不该分成两步"的标准不是工作量，而是**中间有没有一个能被别人独立检查的落盘对象**。有，就分；没有，就并。这解释了两件看起来别扭的事：

- ④「任务卡库初始化」和 ⑤「切任务卡」被拆成两号——一个交目录（`docs/pipeline/cards/`），一个交目录里的内容（具体的卡文件）。前者是结构，后者是内容，检查方式完全不同。[实测]
- ⑦「验收先于实现」单独占一个号位，而不是写在 ⑥ 执行里。因为它的产出物是「基线记录」，属于**动手之前**就要存在的东西；混进执行步骤就等于允许"边干边定验收"。[实测]

### 4.2 14 个号位与它们的准入准出

下表三列（准出 / 该档是否参与）逐格抄自 `SKILL.md` 第二节的索引表与第三节的执行铁律，标注为 [实测]；「准入」列是把铁律里散写的约束按号位归位的结果，其中确实有铁律直接规定的（下表标 [实测]），也有本页补的推断（标 [推演]，各配一个失效输入）。

| 号位 | 阶段 | 准入：上一阶段必须交出什么才能进 | 准出：产出物 | 卡点失败会怎样 |
|---|---|---|---|---|
| ① | 磨设计（盘问到无死角） | 用户的原始想法 + 落盘目录已确认 [实测]（铁律 8） | `设计纪要.md` | 目录没确认 → 产物没地方落，台账无法登记（不可省的两件事之一） |
| ② | 技术选型分层深选 | ① 的设计纪要（约束条件要写在里面才能选） [推演] 失效输入：跳过 ① 直接选框架，会出现"框架定了、业务约束不知道"，选型记录里的取舍理由全是空话，到 ⑤ 切卡时每张卡都要重新问一遍该不该用这个库 | `技术选型记录.md` | 轻量档整步跳过（标 `—`） |
| ③ | PRD（含全局验收标准） | ① 设计纪要；铁律 12 还要求先锁「交付物定义」一句话 [实测] | `PRD.md` | 交付物定义没锁 → 铁律 12 记的实证：某内部项目 45 轮、725 测试全绿、F1 97.5%，但目标用户的人工入口从未存在 |

| ⑬ | 安全基线检查 | 必须在 ⑫ 之前 [实测]（铁律 10） | `docs/pipeline/安检报告.md` | L1 档有可被直接利用的漏洞 → **不许收尾**（阻断式，三档：L1 必检 / L2 上线前 / L3 企业级按需） |
| ⑭ | 对外陈述口径检查 | 有对外物（README / 简历 / 汇报 / 作品集）才必跑，但一跑就在投递之前 [实测]（铁律 11、收尾第 5 项） | `docs/pipeline/口径核查表.md` | 四条规则任一命中 → **阻断收尾与投递** |
| ⑫ | 收尾 | ⑬ 已过（`gates.security_L1` = passed）、有对外物则 ⑭ 已过 [实测]（铁律 10/11 + `state.json` 的 `gates` 约束 3） | 收尾报告 + CHANGELOG + `台账_归档_YYYYMMDD.md` | 推送前还要过一遍：无绝对本机路径、无密钥、无隐私数据、AI 署名带标识 [实测]（收尾第 6 项） |

三点值得单独讲，否则这张表读起来像清单。

**第一，准入条件里最硬的一条是「⑫ 之前必须有 ⑬、⑭」，而它是后加的。** v1.0 初版没有这两号；v1.2 加 ⑬、v1.3 加 ⑭，两步都直接挂在收尾上（"收尾前必须先过"）。换句话说：流水线原本对"做完了没"负责，v1.2/v1.3 之后开始对"做完的东西会不会伤人、做完之后说的话会不会翻车"负责。[实测]

**第二，卡点失败的标准退路是"回上一阶段补件"，不是"就地绕过去"。** 这个取向在表里体现为三处：⑤ 缺 L3 就补 L3、⑦ 没基线就回去跑基线、⑪ 严重问题只阻断下一卡而不放行当前卡。[推演] 如果允许就地绕过，会出现下面这种典型失效输入：执行体在 ⑥ 里发现验收清单写错了，自行把清单改成"能过"的样子并在回执里写"已按实际调整"——台账勾上了，`state.json` 也同步了，一切机器可读的信号都是绿的，但这张卡到底交付了什么，没人能复述。本支的对策是把验收字段的定义权留在切卡窗口（L2 由切卡窗口维护、L3 由深写窗口维护），执行窗口只能填回执区，不能改判据。

**第三，模式裁剪动的是"哪些号位要跑"，不动"号位之间的依赖"。** 轻量档把 ②⑨⑩ 划掉，但 ⑤→⑦→⑥→⑧ 这条依赖链一格没少。[实测]

### 4.3 三档模式与"步数"这个词的三次不同含义

`SKILL.md` 路由第 2 条的四档写法是这样的（照抄箭头链）：

- A 轻量 —— 「小改动五步」：磨需求一句话版 → 一行 PRD → 执行卡 → 台账 → 收尾（**链上 5 项**）
- B 标准 —— 「新功能九步」：磨设计 → PRD → 切卡 → 派遣 → 台账 → 回看 → 收尾（**链上 7 项**）
- C 企业 —— 「全十二步」（+ 技术选型深选 + 卡库 + 双评审 + 总评审 + 工具箱外挂）
- D 跳步优化 —— 先扫全阶段找短板 → 列缺口清单 → 用户勾选 → 直接执行对应阶段

这里有三把尺子在同一句话里混着用，读者面试时很容易被问穿，所以本页摊开算：[实测]

| 计数口径 | 算法（数什么、按什么分隔） | 得到的数 |
|---|---|---|
| 号位总数 | 数 `SKILL.md` 第二节索引表的数据行，每行一个带圈号位 | **14** |
| 表标题自称 | 读该节标题「十二步索引」 | **12** |
| A 档箭头链 | 数 A 行破折号后箭头分隔的短语 | **5**（与「五步」一致） |
| B 档箭头链 | 同上 | **7**（与「九步」不一致，差 2） |
| B 档索引表 | 数 标 列里非 `—` 的行 | **12**（①②③④⑤⑥⑦⑧⑩⑪⑬⑭⑫ 去掉 `—` 的 ⑨；② 为「核心层」、⑪ 为「卡级」、⑭ 为「同」） |
| C 档 | 数 企 列里非 `—` 的行（⑨ 为「按需」） | **13** |

结论要老实写：**「十二步」是 v1.0 的说法**（CHANGELOG v1.0.0 原文即"十二步索引"），v1.2、v1.3 各加一步后号位到 14，节标题与三档链的"步数"都没同步回收。[实测] 这不是排版问题，它会在两个场合真出事：① 你按"十二步"给用户报工期，实际要多跑两道闸；② 跳步优化档「先扫十二步找短板」如果真只扫十二个，恰好会漏掉后加的 ⑬⑭——而这两步正是所有失实的重灾区。[推演]

### 4.4 为什么这套阶段切分能扛住"另起一个会话"

阶段切分的隐藏目标是**可交接性**：每个号位的准出物都是一个文件，而文件是跨会话唯一不会失真传递的东西。对话历史在跨会话时要么被压缩要么被截断，文件不会。所以「每步绑产出物」表面上是纪律，实质上是**为断点续传准备的存储格式**——这一点和第 5 章的台账机制是同一件事的两面：台账记状态，产出物记内容，两者合起来才叫一个能接手的进度。[推演] 失效输入：一个只在对话里说"我已经选定了 FastAPI，因为……"、没有 `技术选型记录.md` 的项目，新会话读台账看到 ② 已勾，于是直接进 ③——它拿不到"为什么不选另一个"的那半页理由，PRD 里凡是依赖该取舍的约束段就只能是猜测。

## 第 5 章　核心机制二：台账即断点存档

### 5.1 这句口号在技术上是什么意思

「任何会话断了都能从第 N 张卡接着干」听起来像祝愿。它成为机制，靠的是三件具体的事：**状态被写进文件**、**文件的写入时机被钉死**、**读回来之后的仲裁规则先写好在读之前**。`references/台账模板.md` 三条各给了一条明文。[实测]

模板自己的定位句写得很直白：它「同时是进度记录和**断点恢复存档**——主 skill 每次启动先读它；每张卡状态变化**立即更新**（不是事后补记）」。[实测] 「事后补记」和「即时更新」的差别就是这套机制的全部难度所在：事后补记的台账记录的是**你以为的**进度，即时更新的台账记录的是**发生的**进度，而断点恢复只能信后者。

### 5.2 存档里装什么（字段级清点）

`台账.md` 是四区结构，不是三区。这里要纠一个常见口误：主文件索引 ⑧ 写「做完 / 在做 / 阻塞 三区」，模板正文实际给的是**四个二级标题**——一、在做；二、待执行；三、做完（勾选区）；四、阻塞区。[实测] 复算方法：数模板 markdown 代码块里以「## 」开头的行，得 4。三区的说法漏掉的是「待执行」，而恰恰是它承载了依赖顺序与验收要点，是断点续传时最需要读的区。

各区的字段与它存在的理由：

| 区 | 字段 | 为什么必须有这个字段 |
|---|---|---|
| 头部 | 模式（轻量 / 标准 / 企业）、落盘目录、创建日期、当前状态（进行中 / 已完成 / 已归档） | 新会话要先知道自己被丢进哪个档；模式决定哪些号位本该跑，不知道模式就无法判断"少跑了步"还是"这档本来不跑" |
| 一、在做 | 卡、执行者、开工时间、备注 | **明文规定最多一张**（模板该行注「最多一张，正在执行的卡」）。这条把"在做"变成一个单值指针，恢复时不存在"三张卡同时在写、谁说了算"的局面 |
| 一、在做（执行者） | 值取「子代理」或人工窗口 | 恢复时要判断这张卡该由谁接着做：子代理做的能直接重派，人工窗口做的得先把上下文交回给人 |
| 二、待执行 | 卡、标题、依赖、可并行、验收要点 | 按依赖顺序排。验收要点抄进台账是故意的——它是断点处"这张卡到底要干什么"的最小可执行摘要，不依赖回读卡文件 |
| 三、做完 | 勾选框 + 关键数字 + 日期，如「基线 Hit@5 70.6%，09-19」 | 数字与日期一起写。这是 ⑭ 口径检查能反查的原始痕迹：**对外引用的每个数都必须在某处带日期存在过**，否则"过期即禁写"没有判据 |
| 四、阻塞区 | 卡、阻塞原因、需要谁 | 「需要谁」把球踢出流水线。断点恢复时最耗时间的不是"不知道做到哪"，是"不知道该等谁" |

`state.json` 装的是同一批信息的机器可读版，字段：`project`、`mode`、`updated_at`、`status`、`steps_done`（已勾号位数组）、`current_card`（含 `id` / `title` / `executor` / `started` / `gate`）、`next_cards`（含 `depends_on` / `parallel_ok` / `acceptance`）、`done`（含 `metric` / `date`）、`blocked`（含 `reason` / `who`）、`artifacts`（PRD 与卡库路径、外部工位产物路径数组）、`gates`（`security_L1`、`outward_claims`）。[实测]

`gates` 是这套字段里唯一带"权力"的：`security_L1` 不为 `passed` 不许进 ⑫；有对外物时 `outward_claims` 不为 `passed` 不许投递。[实测] 也就是说 ⑬⑭ 两道闸门的结论**不是一个 markdown 段落，而是一个可被脚本读的枚举值**——这是"阻断式"能落到工程上的真正原因。[推演] 失效输入：若安检结论只写在 `安检报告.md` 的正文里，收尾时主控读的是台账而不是报告全文，一道"报告里有阻断项、台账里没记"的漏网就会让项目照常关门。

### 5.3 新会话怎么把它读回来（顺序是有规定的）

`台账模板.md` 的「更新纪律」第 3 条写死了读取顺序，这一步非常关键，很多人以为读台账就是打开那个 markdown：

1. **先读 `state.json`**（机器可核）；
2. **再读 `台账.md` 的「在做」+「待执行」**；
3. 然后问用户「从卡#N 继续？」；
4. 铁律：**台账里有什么就信什么，不靠记忆。**[实测]

第 1 步排前面是因为 JSON 的字段是结构化枚举，读错成本高（读错了会解析失败）；markdown 靠人眼扫，读错成本低但更容易读错。先用难读错的一方定基线，再用人类那一方向用户复述——顺序反了就会变成"人眼看一遍 markdown，然后按印象决定"。

第 4 步那句「不靠记忆」是整套机制里最反直觉的一条。[实测] 它约束的是主控会话：即使它"记得"上一轮刚做完卡#3，也必须以台账为准。为什么？因为会话的记忆可能是**未落盘的那一半**——上一轮在执行体回执之后、写回台账之前断了，记忆说"做完了"，台账说"在做"。这时候信谁？答案写在模板第 1 条纪律里：**没写进台账的动作等于没发生**。[推演] 失效输入：某执行体改完代码、跑绿测试，回执也发回主会话了，但主会话在写台账前被中断。新会话如果凭"上一轮的总结"认为卡#3 已完成，就会直接开工依赖它的卡#4——而卡#3 的改动此刻还没被任何验收记录认领，一旦卡#4 出问题，你分不清是卡#3 没做完还是卡#4 做坏了。

### 5.4 读回来的是不是最新：两条仲裁

双写（markdown + JSON）必然带来漂移，本支给了两条明文裁决：[实测]

1. **两份不一致时，以 `updated_at` 较新的一侧为准，并当场回写另一侧**，回写动作记进卡备注。（铁律 4 与「state.json 三条约束」第 2 条同写这条，两处口径一致）
2. **`updated_at` 一律实时取值（`date` / 系统时钟），禁止手写估计。** 模板的理由句是「记档时间戳用估计值是查不回来的账」。

第 2 条是第 1 条的地基：仲裁靠时间戳，而时间戳一旦可以是估的，仲裁就退化成了"谁写得更像"。[推演] 失效输入：主控会话手写 `"updated_at": "2026-10-05T10:00:00"`（凭印象整点），实际写入时刻是 14:37；同一项目里另一个窗口在 13:20 真取系统时间更新了 JSON。两份冲突时，估计值 10:00 < 真值 13:20，系统会**回滚掉那个较新但来自另一窗口的真实状态**，并把错误的旧状态回写进另一侧——一次"按规则自愈"就变成了一次静默覆盖，且两边现在一致了，之后再也查不出来。这是本支对"禁止手写时间戳"这条看起来像洁癖的约束给出的最硬理由。

约束第 1 条还有一条同样硬的：**状态只有实测值**——卡没真验收过不许进 `done`，且 `done` 里的 `metric` 必须是"落盘数字的来源"，写不出来就留在 `next_cards`。[实测] 这条把台账从"进度表"升级成了"证据登记表"：勾一张卡的代价是你必须能说出那个数字从哪来。

### 5.5 v1.5 的双清单：为什么状态真源之外还要两份清单

v1.5 加了 L1 双清单，分工写在「双清单与台账的关系」里（`台账模板.md` 与 `阶段⑤切任务卡.md` §2 两处同写）：[实测]

| 文件 | 给谁 | 维护动作 | 与台账的关系 |
|---|---|---|---|
| 任务板（未完成清单） | AI 执行窗口 | **完成一项删除一项**，删前必须先写台账 | 分发视图，不承载状态真源 |
| 记录清单（交付记录清单） | 人（项目主） | 条目不删，打勾 + 日期 + 关键数字 | 人的轨迹本，只记事实不写判断 |
| `台账.md` + `state.json` | 主 skill / 断点续传 | 状态变化立即更新 | **状态真源**，三处不一致以此为准 |

"删前必须先写台账"这个顺序不是形式主义，它有一个专属的失效名字：模板原话是**顺序反了会出现"任务没了、台账没记"的丢失窗口**。[实测] 也就是说 AI 先把任务板条目删了、再还没写台账的那几秒里，如果会话断了，那张卡就从两份记录里同时消失——它既不在"未完成"（条目已删），也不在"已完成"（台账未记）。这是分布式状态同步里经典的"双写窗口"问题，被这套设计用一句顺序纪律挡掉了。[推演] 反过来验：任务板条目编号（波次字母 + 序号，如 A1/B2）在台账备注列里可追溯（纪律 ②），所以真出现丢失窗口时，你能从台账里搜到那个编号确认它从未被登记——恢复动作是回去按编号补一行，而不是猜。

三条纪律里第三条「记录清单只记事实（完成日期 + 关键数字 + 证据路径），不写判断」值得单独标出：它是 ⑭ 口径检查的上游数据源。判断性表述（"效果不错""基本可用"）不能被核查，只有带路径的事实才能被核查。[实测]

### 5.6 为什么这套设计不是"写了个进度表"

把上面四条合起来看，台账解决的是三个独立问题，而多数项目只解决了第一个：

- **可见性**：现在到哪了。→ 四区结构 + 每卡即时勾。
- **可交接性**：换一个上下文也能准确接上。→ 先 JSON 后 markdown 的读回顺序 + 「台账里有什么就信什么」+ 在做区单值。
- **可核查性**：说做完的东西有数字与日期兜着。→ `done.metric` 必须是落盘数字的来源、记录清单只记事实、`gates` 是枚举。

第三点最晚才被发现其价值：v1.3 的 ⑭ 对外口径检查之所以能做成机械判定，正是因为台账和记录清单里早就要求"数字 + 日期 + 来源"三件一起写。[推演] 失效输入：一个项目从头到尾进度只在对话里、收尾时才补台账，那么 ⑭ 的数字四件套无从核对——来源命令没被记录过、生成日期只能填补记那天的日期（于是一个三月做的评测被写成十月），"过期即禁写"这条规则在假日期上直接失效，因为它比较的是日期，而日期已经被污染。

## 第 6 章　核心机制三：验收先于实现

### 6.1 这条规则的原话与它的三个动作

铁律 2 是那句口号：「卡开工前验收动作必须就绪（评测基线分 / 测试脚本 / 肉眼清单，形式不限但必须写进卡）。」[实测] 展开成动作在 `阶段⑤切任务卡.md` §6（也就是号位 ⑦），它规定了开工**之前**必须做完的三件事：

1. 把验收命令 / 评测用例准备好——**有评测集的先跑一遍，记下基线分**；
2. 确认验收是「客观可判定」的：一条命令能跑出对 / 错，或清单能逐项打勾；
3. 把基线记录**写进卡文件**，完成时对照，防"感觉做完了"。

文件自己在末尾交代了血统与限度：「灵魂来自 TDD（先看到失败再实现），但**不强制测试形式**：评测基线、手动清单同样是合法的『先看到失败』。」[实测] 这句限度很关键，它是这套方法能用到"连测试框架都没有的毕业项目"上的原因——它要的是**先存在一个会红的判据**，不是先存在一个 pytest 文件。

### 6.2 为什么把顺序反过来就能消掉争论空间

这是本支最容易被讲浅的一条，值得拆到最小。

"完成了"这三个字之所以能吵，是因为它通常是一个**事后被追认的形容词**：先有产出，再问"这算不算做完"，于是判据是在证据面前被讨论出来的——讨论双方都知道标准还没定，所以每个人都倾向把标准往自己那一边挪一点。这类谈判没有输赢规则，只有谁更能说。

验收先于实现做的事，是把判据**挪到证据之前存在**，并且同时挪走三样东西的所有权：[推演]（以下三条各有 `[实测]` 锚，见括注）

- **时间的所有权**：判据写定的时刻早于任何产出存在。你无法用"你看它现在能跑了"去反驳一条你三月就写下的命令。锚：§6 第 1 条要求基线在开工前记下。[实测]
- **定义权的所有权**：L2 纲要卡由**切卡窗口**维护、L3 施工图卡由**深写窗口**维护，执行窗口的写入面只有回执区。写判据的人和按判据交活的人不是同一个上下文。锚：`阶段⑤切任务卡.md` §2 分工表的「谁维护」列。[实测]
- **表述形式的所有权**：§5.3 自检第一条要求「验收条条有机械判据（一条命令 / 一次勾选能判定，无『基本完成』『大致符合』类模糊词）」，且**任何一项缺 = 没写完**。锚：`阶段⑤切任务卡.md` §5.3。[实测]

三条合起来的效果是：争论不是被压制了，是**失去了对象**——没有任何一方能在产出之后再改写判据，所以"算不算做完"这个问题在开工前就已经有答案了，剩下的只是执行那条命令。[推演] 失效输入（这条规则若不成立会怎样）：一张卡的验收写成「搜索功能正常工作」，执行体交付后自证"我搜了一下能出结果"，切卡窗口说"我要的是分页"，两边各有道理，唯一的仲裁者（判据）本身没有可判定性——这张卡的返工成本此刻变成一次重新谈判，而不是重跑一条命令。

### 6.3 三种合法形式各适配什么项目

| 形式 | 适配 | 它给的"会红的判据"长什么样 | 基线是什么 |
|---|---|---|---|
| 评测基线分 | 有评测集的项目（检索、分类、生成类） | 指标数字：如「Hit@5 不低于基线」「拒答率 ≥99%」，台账「做完」区的实例就是「基线 Hit@5 70.6%」这种写法 [实测] | 开工前跑一遍记下的那个分 |
| 测试脚本 | 有测试框架的项目 | 一条命令的退出码 + 通过 / 失败数，且 §5.1 第 8 节要求**先红后绿**：改生产码之前先在旧代码上跑出失败面 | 当前测试数（全量回归基线） |
| 肉眼清单 | 没有前两者的项目 | 可勾选的逐项清单，每条要能一次勾选判定 | 打勾前那张"未满足"的状态 |

第三种最容易被读者当成退让，其实它是这套设计里最激进的一条：**它拒绝把"能跑测试"设为验收的前提条件**。理由很实在——如果只承认前两种，那大量真实项目（毕设、内部工具、纯前端）就从"要有验收"退化成"没法验收"，而这套流水线要管的是**所有**从想法到交付的路。[推演] 失效输入：一个只有 `index.html` 的课程作业被要求"先写测试脚本才能开工"，作者大概率直接放弃这套流程，或者塞一个恒真的空测试充数——后者比没有更坏，因为台账会记它"有验收"。

先红后绿这条要求的价值不在测试写法，而在**判据的鉴别力**：一条永远不会红的验收等于没有验收。[实测] §5.3 把"含先红后绿要求"列为自检必过项，缺了就等于卡没写完。

### 6.4 v1.3.1 补的第四种：用户视角验收卡

铁律 12（v1.3.1，2026-09-30）把"验收先于实现"往前推了一步，也往人那侧推了一步：「启动切卡前必须先锁『交付物定义』一句话（谁用 / 怎么用 / 第一次交付长什么样，可验证），写进 PRD 与台账；每个 MVP 的卡组必须至少含一张**用户视角验收卡**——由『不会敲命令的目标用户』人设真实操作核心业务动作（浏览器点击，禁 API 直调作弊），通过才算 MVP 完成。」[实测]

它的教训锚点是一个真实事故形状：某内部项目 45 轮迭代、725 个测试全绿、F1 97.5%，但人工录入入口从未存在过，无导出、无登录、无手册。[实测] 根因写在铁律里：「验收标准全是算法视角无用户视角，定义缺位则流水线**忠实执行错误目标**。」

这句话是本支对整个方法论最锋利的一句总结：流水线不会帮你发现目标错了，它只会把错目标执行得很干净。§3 第 5 条把这层意思压成了一句可以背诵的对照：「既有测试 / 评测验收盖不住用户视角——『725 测试全绿』与『会计朋友能用』是两个维度」。[实测] 该卡的形状也被规定出来（§3 第 4 条）：人设剧本（含唯一允许的命令 / 行动作清单）→ 逐步操作与截图 → 卡壳清单就地修 → 交付物定义逐条对照，达成与否**如实标注**。[实测]

「禁 API 直调作弊」这条限制是整套设计里最容易被我方（AI 执行体）糊过去的地方：执行体为了让验收通过，会倾向用接口直接构造状态，因为那比模拟点击快得多——但那恰好绕过了要验证的东西。[推演] 失效输入：验收写"用户能提交一张采购单"，执行体写了一段脚本 `POST /orders` 返回 200 就勾台账；真实情况是表单页有个必填日期控件在前端就把人拦住了，接口层根本没人能走到。这类"用实现方式绕过被验对象"的失败，是判据要显式禁止的，光写"能提交"不够。

### 6.5 证据形态：v1.3.2 把"绿了"变成"有输出的绿了"

铁律 13（v1.3.2，2026-10-02）规定每卡的"测试全绿 / 评测达标"必须按测试纪律那一支的标准交付证据：**原始输出落盘**（`evidence/` 或卡内路径）、**改前改后各跑一遍**、**口径标注**，并且明文「禁止只在对话里说『绿了』不留输出文件」。[实测] L3 施工图卡的目录里，`执行回执.md` 与 `evidence/` 是**建档时就创建的空占位**——形状先于内容存在，缺目录就是缺证据的可见信号。[实测]

这条把 6.2 的逻辑闭合了：判据在开工前存在（⑦）、执行窗只有回执区的写权限（§2）、而"过没过"以落盘的原始输出为准（铁律 13）。三件事共同保证：完成这个结论不是某个上下文说的算，是一份可被别人重跑的文件说的算。[推演] 若三条缺一（尤其只保留第一条），会出现这样一条路径：执行体在会话里贴一段"34 passed"的文字，主控照抄进台账 `done`，新会话重跑时环境已变、数字对不上，但没有任何文件能证明当初那个数是怎么来的——这正是 ⑭「过期即禁写」在防的形状。

### 6.6 DoD：执行者的停止信号

§5.1 第 10 节把「完成定义 DoD」写成一串必须全满足的动作，且明确「DoD 是执行者的**停止信号**，全部满足才许宣布完成」。[实测] 按该节原文以顿号与加号分隔清点，共 **7 项**（`台账/state.json` 记为 1 项两个文件）：

```
① 验收清单全过 → ② 测试绿 → ③ 证据落盘 → ④ 回执写回
→ ⑤ 台账 + state.json 更新 → ⑥ 任务板删条目 → ⑦ 记录清单打勾
```

最后四项解释了为什么验收机制和非它不可：**验收通过只是 DoD 的七分之一**。一个执行体如果只做到 ① ② 就报告完成，它交出的是一条真判据 + 一次真通过，但台账没记、断点没存——下次会话看不见它，那张卡会被重做，重做还会覆盖掉它的产出。DoD 把"做完"定义成**状态同步完成**，而不是"活干完了"。[实测]

顺序上第 ⑥ 项被排在第 ⑤ 项之后不是排版：5.5 的"丢失窗口"就藏在这个先后里。DoD 的编号顺序本身就是那三条纪律的执行版。

## 第 7 章　核心机制四：分身编排与上下文最小化

### 7.1 主控被降格成了什么

「分身编排」这个名字容易听神秘，说穿了是一次分工：**主控只做调度与记账，绝不动手实现**；`阶段⑥执行与派遣.md` 开头的原话是「主会话当项目经理，逐卡派遣，可自主连跑多卡不偏航」。[实测] 这句里的重点是**连跑多卡不偏航**——主控的价值不在聪明，在于它能一边跑一边把状态写回台账，所以它随时可以被打断而不断链。执行体则相反：它被刻意做"窄"，只知道自己那一张卡，做完即停。

两种执行模式，由环境决定，用户可覆盖：[实测]

| 环境 | 模式 | 交付形态 |
|---|---|---|
| 当前工具支持派生子代理 | **自动子代理模式** | 主控在同一次会话里派出执行体，逐卡推进 |
| 不支持子代理，或用户想亲自控节奏 | **提示词卡模式** | 主控为每张卡生成一段可直接粘进全新对话的提示词，用户复制出去执行，把结果带回来 |

探测方法也写了：尝试调用子代理能力（或查工具说明），不支持就自动落到提示词卡模式**并告知用户**。[实测] 这里有个容易被略过的设计取向：第二模式不是降级品，它是**同一套验收标准的等价物**——§3 明文要求用户带回结果后，主会话「按 §2.3-2.5 相同标准验收、更新台账」。[实测] 所以"派 agent"和"你自己开个窗口跑"在流水线看来是同一件事的两种传输方式，卡文件、判据、台账动作一个都不少。这一点很重要，它意味着这套方法论**不绑定任何具体宿主工具的能力**。[推演] 失效输入：如果提示词卡模式被当成低配路径、跳过双评审直接接受用户带回的结果，那么同一项目里用子代理跑的卡有评审记录、用户自己跑的卡没有——⑪ 与 ⑭ 之后做全量核对时，两类卡的证据强度不一致，但台账上它们都是勾过的。

### 7.2 一张卡的派遣循环（五拍）

`阶段⑥执行与派遣.md` §2 的循环是五步，逐步说明它各自挡掉什么：[实测]

1. **装配上下文（最小化铁律）**——喂给执行体的只有四样：该卡全文、PRD 相关章节、涉及文件的精确路径、全局约束（编码纪律）。明文「绝不喂」的是另外三样：其他卡的过程、对话历史、全项目文件。
2. **派遣执行**——执行体按卡实现，返回固定三件：改动文件清单、验收命令输出、一段完成摘要。返回值形状是被规定的，不是自由发挥。
3. **双评审**（企业模式 / 重要卡）——评审 A 判「设计符合」（派评审员对照 PRD 与该卡验收逐条判定）；评审 B 判「代码质量」（按严重度报问题）。两个评审是**另派的执行体**，不是同一个自审。
4. **阻断处理**——有阻断级问题 → 带着评审意见**重派同一任务的新分身** → 再评审；**最多 2 轮**，仍不过则升级给用户。
5. **过卡**——通过 → 更新台账（该卡移入"做完"区）→ git 提交（信息含卡号）→ 下一卡。

第 5 步那句「git 提交信息含卡号」是断点续传的最后一环：卡号同时存在于台账行、卡文件名、提交信息三处，任何一处漂了都能用另外两处反查回来（勾稽＝两处数字能对上）。[实测]

### 7.3 「三样」与「四样」：一处必须说清的口径冲突

主页铁律 5 说执行体「只喂『该卡 + PRD 相关段 + 精确文件路径』」，是三样；细则 §2.1 列的是四样，多出「全局约束（编码纪律）」。[实测] 本页不抹平这个差：多出来的那一样不是装饰——没有它，每个执行体都会按自己的口味写码（命名、错误处理、是否加新依赖各不相同），而这些差异**在单卡验收里全是合法的**，直到 ⑪ 里程碑总评审做「跨卡一致性：接口风格、错误处理、命名是否统一」时才暴露。[实测] 也就是说这一样的真实归属是总评审，主页把它压缩掉了。[推演] 失效输入：五张卡各自执行、张张验收全绿，第三张起有人引了新依赖、有人用自定义异常类，总评审时才发现要统一——返工量等于把三张卡的改动重做一遍，而这本来是一句「全局约束」就能挡掉的。

### 7.4 为什么"不让一个上下文从头做到尾"是结构性要求

这是这套设计最需要讲透的一句，也是面试里最容易被问倒的地方。理由有四条，只有第四条是性能问题：

**一、上下文的注意力会被历史挤干净。** 模型一次能看的文字量有限（token，可粗略理解为它眼前摊开的稿纸页数），而"从头做到尾"的会话里，第五张卡的工作上下文要背着前四张卡的全部对话。它不是不能读，是**读得到但注意力摊薄**：越靠前的内容越容易被当成噪音。[推演] 失效输入：一个 12 张卡的会话跑到第 9 张，第 2 张卡里定下的"金额一律用分为单位的整数"这条约束已经沉在几万 token 之下，第 9 张卡顺手用了浮点数存金额——没有任何一步报错，直到 ⑩ 回看或上线后对账才发现。

**二、自审没有鉴别力。** 让写完这张卡的上下文自己评审自己，它看到的是"我刚才是为什么这样写的"全套理由，天然倾向通过。所以 §2.3 的评审 A、B 是**另外派出的执行体**，它们拿不到作者的历史，只拿到 PRD、卡的验收和代码。[实测] 卡模板里那句「禁止：不改哪些文件 / 不加未要求的功能 / 不引入新依赖」（§4.1 小卡模板的禁止字段）也是同一逻辑：与其指望执行体自律，不如把它不许碰的东西写死在它眼前。[实测]

**三、失败半径。** 一个上下文从头做到尾，意味着它的任何一次错乱（记住了一件没发生的事、把两张卡的状态搞混）都会传染给后续所有卡。切成分身后，一次错乱的爆炸半径是**一张卡**，而那张卡有独立的验收与回执可以复核。[推演] 具体形状：某执行体误以为卡#7 的接口前缀是 `/v2/` 并全部按它实现——它做完即停，卡#7 的验收里那条 curl 断言会红；主控拿到红判据只需重派这一个分身。若是同一个长上下文，这个误解会一路渗到卡#8、#9，等到发现时你已经分不清是接口错了还是引用错了。

**四、可并行（这才是性能那一条）。** 无依赖的卡可以同一轮派出去。§1 粒度表与任务板的【P】标记就是为这件事准备的；顺带一条纪律：「默认接力：有依赖的卡依次执行；无依赖的卡先问用户要不要并行」（铁律 6）——**并行的决定权在用户，不在流水线**。[实测] 这条"先问"看着保守，实际是成本闸门：并行开 N 个执行体就是 N 份 token 与 N 个要合并的改动面，用户不点头就不该发生。

### 7.5 状态机：一张卡的四拍

`阶段⑤切任务卡.md` §2 纪律 2 规定了执行窗口认领任务的标准动作，四步缺一不算完成：[实测]

```
认领（任务板条目填执行者 + 开工时间）
 → 拉上下文（读 L3 施工图 → 读 L2 纲要 → 现查 git status 与相关代码）
 → 执行
 → 写回（回执 + 台账 + state.json + 任务板删条目 + 记录清单打勾）
```

「拉上下文」这个顺序有讲究：**先读最细的那一层，再读摘要，最后现查真实仓库状态**。反过来读（先看 git status 再猜要干什么）会让执行体按自己看到的代码现状重定义任务——那正是"验收追认"的老路。[推演] 失效输入：执行体先 `git status` 看到一堆未提交的改动（别的窗口留下的），于是判断"这块已经有人做了一半"，把自己那张卡的范围缩成"补完剩余"，于是 DoD 的第 ⑥ ⑦ 项（删任务板条目、记录清单打勾）都被它当作"别人会做"跳过了——四拍里最后一拍整段缺失，台账和实况开始漂移。

写回那一拍里同时出现「任务板删条目」和「台账先写」两个动作，顺序在 §2 纪律 3：任务板删条目前**必须先写台账**，否则会出现 5.5 说的"任务没了、台账没记"的丢失窗口。[实测]

### 7.6 提示词卡模式：把「上下文最小化」交给人类执行

§3 规定提示词卡要包含四段信息（本页只描述字段与理由，不抄模板原文）：[实测]

| 段 | 内容 | 为什么要有这段 |
|---|---|---|
| 角色与停止条件 | 告诉新窗口它是"本次任务的执行工程师"，只做这一张卡，**做完即停** | 新窗口没有台账可读、没有主控可问，唯一能约束它的是"边界写死在指令里"。「做完即停」防的是它顺手把下一张卡也做了——那会破坏卡与验收的一一对应 |
| 整张卡内容的插槽 | 明确要求把卡文件全文粘进来 | 这一句就是铁律 5 的人工版：粘的是这张卡，不是项目历史 |
| 全局约束 | 一句话的编码纪律 / 代码风格 | 见 7.3，防跨卡风格漂移 |
| 要求返回的三样 | 改动文件清单 + 验收命令的**完整输出** + 三句话总结 | 「完整输出」而不是"跑过了"对应铁律 13 的证据形态；「三句话」限长，防止执行体把它的推理过程整段回灌给主控——主控不需要读它的心路，只需要读结论与证据 |

「三句话总结」这个限长很值得单独夸一句：它是**双向**的上下文最小化。多数人只想到主控往下少喂，没想到执行体往回多吐同样会污染主控——一张卡吐回三千字的"我是怎么想的"，主控的上下文就被下一张卡的噪音占满了。[实测]（§3 的返回要求）

### 7.7 双评审与两层评审的分工

卡级评审（每次派遣后，轻量）输出**严重度三级**意见：阻断 / 建议 / 备忘。[实测] 三级的意义在于只有"阻断"有强制力，"备忘"是留给人的，"建议"可延后——如果全设成阻断，执行体就会倾向于把评审意见当噪音，而分级闸门的价值恰恰在"少数几条能拦住你"。[推演] 失效输入：评审 B 报了 9 条"阻断"，其中 7 条其实是命名偏好；下一张卡被卡住两小时，用户开始手工越过评审——闸门一旦被滥用，被绕过的就不是那 7 条，是全部。

里程碑总评审（每 1/3 进度，企业模式，重量级）查的是**单卡看不见**的四件事：跨卡一致性、架构漂移（实现是否还长在设计的样子）、性能与安全抽查、产出写进 `回看报告.md` 的评审章节，阻断项回炉。[实测] 注意「安全抽查」在这里也出现一次——但它是抽查，不是 ⑬ 那一道全档闸；两级不能互替，这一点第 9 章会展开。

§4 还挂了一条联动：**每完成约 1/3 卡数就暂停派遣**，先执行里程碑回看再继续。[实测] 「暂停派遣」是这条机制的全部牙齿——不停，回看就只是"事后看"，而执行体仍在按旧方向继续生产。为什么阈值取 1/3 而不是 1/2：[推演] 三档阈值里 1/3 是唯一能同时容纳"发现方向错了 + 返工已完成部分 + 还剩足够余量重走"的那个点；取 1/2 时返工已过半，人会倾向"算了，做完再改"，回看就退化成复盘会。这条阈值可以在项目里改，但**不能取消**——取消之后 ⑩ 的自动线就只剩手动触发，而手动触发在没人记得按的时候等于没有。

## 第 8 章　核心机制五：按需加载、自包含与外部工位

### 8.1 按需加载是一条被写成铁律的成本控制

铁律 9 的原文口径：启动只读 `SKILL.md`（索引 + 路由），**禁止预读 / 通读 `references/`**；进入某一步才读该步细则，一次只读一个；`depends/` 副本只在两种情况读——对应细则缺失需顶替、或执行中真需要外部原文细节；`superpowers_assets/` 只在派遣 / 评审需要整篇模板时读对应的**那一个**文件。[实测]

这条为什么值得单独占一条铁律：一份流水线细则的体积是按千字节算的，14 个号位如果一次读完就是几万 token 的固定开销，而这个开销**每个会话都要付一次**——包括那些只想"帮我切一张卡"的会话。省下来的不是钱，是执行体的注意力预算：7.4 讲过，上下文被无关历史填满之后，真正需要的约束会沉底。[推演] 失效输入：一个会话在启动时通读了 12 份细则（含 3 份阶段文件的全部模板节），到 ⑥ 派卡时它眼前已经有两份互相矛盾的模板形状（小卡的零歧义版与中大卡的成人版），于是给一张小卡写了成人档的四字段——执行体拿到歧义指令，按"有判断力的成人"处理了一张本该写到零歧义的卡，产出的验收命令是"确认功能正常"。

"一次只读一个"还有个副作用值得点出：**它让细则文件之间不能互相依赖**。既然不保证读者读过别处，每份细则就必须自包含。`阶段①磨设计与选型.md` 开头就写着「本文件自包含（已融合头脑风暴 v1.1 骨架与 grill-me 提问技巧），不依赖外部 skill 也可执行」——这句话不是介绍，是铁律 9 逼出来的结构约束。[实测]

### 8.2 自包含：把外部知识冻存成快照

`依赖与自检.md` 的设计原则写得很硬：凡引用了外部 skill 的精华内容，**原文副本已落档**在 `references/depends/`，「外部 skill 消失也不会让本 skill 报废」。[实测] 副本规模与复算：[实测]

| 段 | 份数 | 复算口径 |
|---|---|---|
| 本机 skill 库原文副本 | 8 | `depends/` 里非 superpowers 前缀的 .md：头脑风暴 / grill-me / 带文档追问审查 / 需求转PRD / 需求转Issue / 功能实现-按spec工单 / 多Agent团队协作文档治理 / superpowers_方法论 |
| superpowers 对应 skill 原文 | 12 | 与 14 个号位中的执行类步骤一一对应（brainstorming、writing-plans、executing-plans、subagent-driven-development、dispatching-parallel-agents、using-git-worktrees、test-driven-development、requesting-code-review、receiving-code-review、verification-before-completion、finishing-a-development-branch、systematic-debugging） |
| `depends/` 合计 | **20** | 8 + 12，与 `SKILL.md` 〇 节自述的「20 份：本机 skill 原文 8 份 + superpowers 十二步对应 skill 原文 12 份」一致 |
| `superpowers_assets/` | **17** | README 登记 + 16 个附属（评审提示词 ×4、派遣与进度脚本 ×5、排障技术 ×3、排障配套示例 ×2、好测试指南 ×1、可视化配件 ×1）；4+5+3+2+1+1 = 16，加 README = 17，与递归实测一致 |

两处工程细节最能说明这套副本不是随手粘的：

**一、版本锚定。** 12 份 superpowers 副本 + 16 个附属文件全部抓取自**上游 main 分支同一个 12 位短哈希提交**，目的是「互引一致」——副本之间可以相互引用而不会出现"A 描述的流程被 B 的另一个版本改掉"。[实测] 这就是为什么附属文件要**按原目录结构存放**，且**不加来源头**：理由写在文件里——「模板需可整篇直接复制」。[实测] 加一行来源注释会破坏"整篇复制"这件事，所以宁可放弃就近标注。这是一个真实取舍，不是疏忽。[推演] 反面失效输入：如果给 16 个模板各加一段来源头，评审子代理在"整篇粘贴模板"时就会把来源头一起带进生产仓库的文档里，用户第一次读那份评审模板会以为"来源说明"是模板要求的一部分。

**二、刻意不收的清单。** 文件专门用一节登记**没收录**的三个上游 skill（一个排查框架自身故障的、一个框架自用说明、一个教人写 skill 的），标题就叫「刻意不收的 superpowers skill（3 个，勿误报缺失）」。[实测] 并给出分母复算：上游官方技能库共 15 个，除这 3 个外全部已收 → 15 − 3 = 12 ✓。这一节的价值在于它把"你没收录"和"你漏了收录"分开——没有它，任何一次体检都会把这三个报成缺失，然后有人去"补全"，把无关内容拉进包里。这是文件化依赖管理的标准动作：**否定结论也要留档**，否则下一轮检索会把"没有"重新读成"待办"。

### 8.3 三级自检：缺东西的时候怎么分级

启动自检（约 5 秒）的结果分三级处理，判据是**缺的是细则还是副本**：[实测]

| 级别 | 条件 | 动作 |
|---|---|---|
| 🟢 正常 | 细则文件 + `depends/` 副本齐全 | 直接开工 |
| 🟡 降级 | `depends/` 副本缺失，但细则齐全 | 提示用户「依赖副本缺失，将按自包含细则继续（功能不受影响）」，并告知可从来源重新补齐 |
| 🔴 报错 | **细则文件本身缺失**（点名四类：阶段① / ⑤ / ⑥ / 台账模板） | **停止流水线**，提示从安装源重新获取，或手动把该文件放回 `references/` |

这张表里的因果关系是：副本缺失只影响"能不能出示外部原文"，细则缺失影响"这一步还能不能执行"。所以 🟡 的措辞是"功能不受影响"，🔴 的措辞是"停止"。[实测] 同一份清单里每条副本还带一列「缺失影响」（低 / 中），其中「中」的六个恰好都是**执行类**依赖（executing-plans、subagent-driven-development、requesting-code-review、receiving-code-review、finishing-a-development-branch、多 Agent 治理），"低"的都是"精华已经融入本地细则"的——这一列就是 🟡/🔴 分级的微观依据。[实测]

不过这份自检清单本身有一处**要命的覆盖缺口**，本页必须写进公开页：清单逐名列出 30 个文件，加 `superpowers_assets/` 的 16 个附属（另抽查该目录文件数 ≥ 17），合计 **46 个可核对项**；而本支实测递归 51 个文件，差额正好是 **`CHANGELOG.md` + `安全基线检查.md` + `对外陈述口径检查.md` + `验收模板-上线门禁与口径.md` + `外部工位对照表.md`** 这 5 个。[实测] 复算方法：51 −（自检清单逐名 30 + assets 附属 16）= 5。

后果是可推理的：自检清单写于 v1.0 时代，而这 4 份细则分别由 v1.2、v1.3、v1.4 加入，清单没被同步扩充。于是**这 4 份文件缺失时不会触发 🔴，也不会触发 🟡——它们根本不在检查范围内**。[推演] 具体失效输入：某人手动清理 `references/` 时删掉了 `安全基线检查.md`（觉得是重复内容），启动自检全绿通过，流水线照常跑到 ⑬；主控此时只能凭 `SKILL.md` 索引表里那一行「L1 必检 / L2 上线前 / L3 企业级按需」凭印象执行，产出一份只有一句话的 `安检报告.md`，而 `state.json` 的 `gates.security_L1` 会被写成 `passed`。铁律 9 的省 token 设计与自检清单的静态列举在这里发生了冲突：细则可以按需加载，但**清单必须全量列举**——后者被前者的心智模型污染了。这条属于第 15 章要登记的缺陷。

同处还有一处小的口径漂移：🟢 的条件写「**7 个**细则文件」，而自检清单在 `SKILL.md` 之外列了 **8 份** `references/` 细则（模式判定、阶段①、阶段⑤、阶段⑥、台账模板、里程碑回看、工具箱、依赖与自检），`references/` 实际有 **12 份**。三个数分别对应"当初写这句话时的心算"、"自检被点名的文件"、"目录里的真实文件"，本页不合并它们。[实测]

### 8.4 模板：只讲字段与为什么，不讲原文

本支的模板分布在 4 个文件里，形状各不相同但服务同一个目标：**让产出物的字段先于内容存在**。缺字段的产出物是无法核对的，而多余的字段只是浪费纸。

| 模板 | 所在文件 | 抽象后的字段组 | 每个字段为什么必须在 |
|---|---|---|---|
| 台账四区 | `台账模板.md` | 头部（模式 / 落盘目录 / 创建日 / 当前状态）、在做（卡 / 执行者 / 开工时间 / 备注）、待执行（卡 / 标题 / 依赖 / 可并行 / 验收要点）、做完（勾 + 关键数字 + 日期）、阻塞（卡 / 原因 / 需要谁） | 见 5.2 逐字段理由。核心一句：每列都在回答断点恢复时的一个具体问题 |
| 机器断点 | `state.json`（同文件） | `steps_done` / `current_card` / `next_cards` / `done` / `blocked` / `artifacts` / `gates` | 结构化枚举让"读错"变成"解析失败"，比人眼扫 markdown 更早暴露问题 |
| 小卡（实习生标准） | `阶段⑤` §4.1 | 目标 / 涉及文件 / 前置依赖 / 实现要点 / 验收 / 禁止 / 完成后动作 | 文件的括注就是理由：「热情但没判断力，所以必须写到零歧义」。「禁止」与「完成后动作」两个字段是 AI 执行体专用——前者防越界改动，后者把 7.7 的 DoD 尾巴接上 |
| 中大卡（成人标准） | `阶段⑤` §4.2 | 你要做什么 / 材料位置 / 怎么算做完 / 边界提醒 | 四字段对应"有判断力的执行者"需要的四件事：目标、原料、判据、雷区。刻意不写实现步骤——写了就是替执行者做判断 |
| 施工图（L3） | `阶段⑤` §5.1 / §5.2 | 全量 18 节 / 轻量 9 节（节号沿用全量档：0、1、3、7、8-9 合并、11、14、15、18） | 见 6.2、6.6。轻量档明文「不许再裁」——这说明设计者知道人会继续简化，提前封住 |
| 提示词卡 | `阶段⑥` §3 | 角色与停止条件 / 卡全文插槽 / 全局约束 / 返回三样 | 见 7.6，把铁律 5 翻译给人肉执行 |
| 收尾门禁 | `验收模板-上线门禁与口径.md` | 安全节 + 口径节 + 推送检查节（条款自包含，可脱离流水线单独跑） | 自包含是为了让"别人接手你的项目"时也能跑一遍门禁，不必先装完这套 skill |

有一处细节值得专门指出，因为它是**模板设计的通用难题**：§4.1 小卡模板的「实现要点」字段带着一条自我限制——「函数签名 / 接口定义 / 关键逻辑说明——写到零歧义，但**不代写全部代码**」。[实测] 这两句在半句话之内互相拉扯，但它恰好卡在正确的位置：写少了执行体会猜（歧义），写多了这张卡就变成代码本身、验收失去意义（执行体只是在抄）。[推演] 失效输入：把整段实现写进卡，执行体照抄时不做任何理解，验收命令一跑就过；两个月后需求变了一个字段，没人能改这张卡的产物——因为它从一开始就不是"被理解的产出"，是"被搬运的产出"。反方向失效：实现要点只写"按 PRD 实现混合检索"，两个执行体交出两种结构，卡级评审全过，里程碑总评审才发现接口风格不一致。

### 8.5 外部工位：接线不改骨

号位 ⑨ 之外，本支还留了一整张 `外部工位对照表.md` 来登记"哪些工位可以让市场插件顶、借它什么、本地仍管什么"。它开头有两条**凌驾本表一切内容**的硬规则，是 v1.4.0（2026-09-30）加的：[实测]

1. **产物一律落 `<项目根>/docs/pipeline/`**——外部插件默认往自己的目录写，派遣时必须显式改道，并把它实际写到哪记进台账与 `state.json` 的 `artifacts.external`。
2. **判定权与结论永远在本地**——外部 skill 可以产出内容（设计物、字段、清单、模板），但**不得**替本流水线下"通过 / 不通过"结论，也不得改写本库的红线与五态判定。

这两条的来源在 CHANGELOG 里说得很实在：主控先盘点了已装的 33 个市场插件 skill（两个插件族分别 28 个与 5 个，前者约 1.9 万行、单个正文 264–1352 行，后者 1861 行加 4 份模板且**零脚本零校验**），然后定出取舍口径：**借覆盖面与字段结构，不借判定纪律**。[实测]

对照表本体登记 8 个可顶工位（数法：第一节表格数据行）、5 项「不并入清单」（第二节数据行）、3 条启用姿势（第三节，「缺一即视为未启用」）、6 行撞词消歧（第四节）。[实测] 借来的东西全是**结构与覆盖面**：PRD 的策略矩阵 / 排期 / 协作流程 / 风险应对四段、用户故事的 JTBD 写法、六类异常态穷举、图表选型规格、动效规范、竞品调研的强制联网三轮与来源可信度分级、实用新型交底书 10 节。让在本地的一直是**判据**：全局验收标准、卡粒度判定、⑦ 验收先于实现、⑪ 双评审、⑭ 的数字四件套门禁。[实测]

「不并入」那五条的理由列最值得学，因为它们在讲判据强度差异而不是偏好：外部审查类 skill 的 findings **没有证据槽**（字段只有类别 / 严重度 / 描述 / 建议 / 位置），本库要的是五态判定 + 命令与退出码 + 文件位置 + 反作弊三条；复盘类只要求"对照实际度量（如有）"，无数据即靠口述；PRD 类不并是因为**双生成器 = 双入口必打架**，且它只要求"有数据支撑"而无引证与禁编造条款。[实测] 这里"双入口必打架"是一条很好讲的工程直觉：同一个产出物如果有两个作者路径，判据就没法只有一处真源，而 ⑭ 的整套设计恰恰建立在"每个数字只有一个来源命令"上。[推演] 失效输入：外部 PRD 生成器写了一份、本地 ③ 又写了一份，两份的"全局验收标准"不同；切卡窗口拿其中一份切卡，收尾时 ⑫ 对照的是另一份——所有卡都绿了，但没人验过同一件事。

启用姿势里最有意思的是第 3 条 **token 闸门**：外部 skill 单个正文 500–1350 行，另需读它的协议文档约 34KB，所以**一次只启用一个工位**，只在确需它的产物形态时启用，本地细则能解决的不启用。[实测] 这条把按需加载延伸到了第三方能力上：外挂不是"更强所以该开"，而是"值不值这几千 token"。（顺带记一处实测口径差：`SKILL.md` 引用的 CHANGELOG 记录单个正文区间为 264–1352 行，本表记为 500–1350 行——两处数字不同，本页不重测、不合并，详见第 15 章。）

还有一条纯实用的：插件本体**只读**，因为它装在带版本号目录的缓存里，**升级即另开新目录**，任何写进插件的改动当场作废。[实测] 这句话背后的判断力和 8.2 的自包含是同一个：**任何你不拥有的存储层，都不能作为你的状态载体**——所以产物必须改道到 `docs/pipeline/`，也就是硬规则 ①。两条硬规则其实是同一条的两个方向：进来别人的产物要落到我家，别人的结论不许进我家。

至于表末那行「无障碍」：判定已经**收编进本库另一支（项目验收官）的第五层**（五态 + 四探针 + 优先级映射），插件只作可选上游。[实测] 这是这张表里唯一一条"外部能力被吸收成本地机制"的记录——它给出了一条清晰的演化方向：工位表是**临时形态**，凡被验证有价值的判定维度，最终都要长回本地并变成号位；⑬⑭ 就是这么来的。

## 第 9 章　核心机制六：两步阻断式把关（安全基线与对外口径）

### 9.1 这两步不是设计出来的，是被打出来的

`SKILL.md` 铁律 10、11 两条各带一个「教训锚点」，日期都是 2026-09-23。[实测]

- **⑬ 安全基线检查（v1.2 新增）**：同日外部安全拷问在两个**已经走完收尾**的项目里实锤 **11 项**——JWT 默认密钥、DEBUG 连坐限流、role 由客户端自报、审计接口裸奔、async 路由里同步阻塞拖死全站、死代码带着 AI 协作注释等。文件里的判词是「全部漏网于卡内验收」，并且把根因写成一句非常冷的话：「**根因是检查表缺安全维度，不是执行不力**」。[实测]
- **⑭ 对外陈述口径检查（v1.3 新增）**：同一天发现，**同一批已过 ⑬ 安全审查**的项目，对外陈述仍全线失实。[实测]

先把"为什么这两步必须独立成步"讲成一句可复述的机制，再讲它们各自的内容。因为面试里真正值钱的是前者。

### 9.2 「检查归属」这条通用教训

`对外陈述口径检查.md` 的「与其它步骤的边界」那张表是全支最值得背下来的一页，它把四个维度分给了四个主人：[实测]

| 维度 | 归属 | 管的是 |
|---|---|---|
| 漏洞、密钥、鉴权、依赖 | ⑬ | 可被攻击的风险 |
| 代码质量、测试、死代码 | 卡内验收 + 编码准则 | 会不会坏 |
| **说出去的话是否站得住** | **⑭** | **会不会被第三方核对推翻** |
| 数字是"当时为真"还是"现在仍为真" | ⑫ 收尾（跑全量）+ ⑭ 规则 2 | 收尾负责生成，⑭ 负责时效 |

它的第 0 段还解释了为什么 ⑭ 非得单开：⑬ 是**漏洞视角**（可被利用的风险），编码准则卡是**写码视角**（代码质量），两者都不管"说出去的话"——而对外陈述是**唯一会被第三方拿去核对的东西**，核对不过，前面十三步做得再规范也白做。[实测]

把两次事故对齐看，会得到一条比"要加两步"更一般的规律：**任何横切维度（不属于任何单卡的验收面）都必须有一个明确的检查归属，否则它落在三不管地带。** 安全是横切的，口径也是横切的；而流水线的默认结构（逐卡验收）天生只覆盖纵向。[推演] 这条规律可以外推去预测下一个会漏的维度：可观测性、无障碍、数据合规——只要它没被指派主人，它就会以"每卡都过了、全局却是坏的"的形状出现。[推演] 失效输入（对 11 项漏网的机制化解释）：⑬ 第 4 项要求「列出**全部路由**，逐一标注鉴权方式，找'全挂了唯独它没挂'的」。这张检查表在执行体眼里根本不可能出现在卡内验收里——单张卡的视野只包含它那一条路由，它连"别的路由挂没挂"这个信息都没有。**不是它偷懒，是它的输入里没有那个维度。**

### 9.3 ⑬ 安全基线：三档、逐项、带阻断标准

分档口径（文件标题行原样）：**L1 必检 / L2 上线前 / L3 企业级按需**，时间预算分别写着 L1「每个项目收尾前，约 30 分钟」、L2「真机部署前，约半天」。[实测] 三档的条目数复算（数法：L1 数表格数据行，L2/L3 数无序列表项）：**L1 = 12 项、L2 = 8 项、L3 = 5 项，合计 25 项**。[实测]

三档不是"由松到紧的同一张表"，是三种不同的**成本形状**：

- **L1 是 12 条 grep 级别的规则**，不需要真部署，30 分钟能过完，所以它被定成「每个项目收尾前」必跑——门槛低到没有借口。
- **L2 需要真实部署面**才能验（HTTPS 强制、容器基础镜像与端口映射、限流在反代层生效），所以它挂在「真机上线前」。
- **L3 需要基础设施存在**才有意义（SBOM、制品签名、IaC、K8s、CI/CD 扫描链），文件明文规定：没有对应基础设施就**标注"不适用"**，不许空跑。[实测] 这半句很关键——它主动防止检查表退化成"打勾表演"。同一条防滥用逻辑在 ⑭ 的执行法第 1 条里也出现：「没有任何对外物的项目，本步标'不适用'，不要空跑」。

**L1 十二项里最能说明"阻断标准"设计的四条：**[实测]

| 项 | 检查方法（要点） | 阻断标准 | 为什么这样切 |
|---|---|---|---|
| 3 DEBUG / 开关连坐 | 找出所有 `if DEBUG` 分支，确认 DEBUG 不牵动任何安全行为（限流 / 验证 / 加密） | 连坐 = 阻断，解法是**拆成独立开关** | 这是 11 项里最隐蔽的一类：调试开关顺手关掉限流，本意合理，生产一旦 DEBUG=true 就把安全行为一起关了。检查表给的不是告警而是一个**具体修法** |
| 6 授权字段自报 | 搜请求体里 role / permission / is_admin 类字段，核对服务端是从已认证身份**派生**还是直接采信 | 自报可操纵状态 = 阻断 | 判据落在"派生 vs 采信"这个二值上，能机械判定；如果写成"权限设计要合理"就永远查不出来 |
| 9 暴力破解面 | 所有码 / 验证码 / token 验证端点：有没有尝试次数限制？比较是否用恒时比较（`compare_digest`） | 无限次尝试的可穷举 = 阻断 | 两项合一：速率限制管"能不能试"，恒时比较管"试的时候泄露不泄露时序"——把两个独立失败面写在同一行，是因为它们共用同一个入口 |
| 11 死代码扫描 | 未被调用的函数、一运行就崩的文件、前端接了线但后端不存在的按钮 | **带 AI 协作注释的死文件 = 阻断（删）** | 这条是 AI 时代新增的失败面：AI 留下的半成品文件会被误当成"已实现"，而它对外的形状和功能都有，只有一调用就崩。[推演] 失效输入：一个 `admin_upload.py.bak` 带着「// AI 生成，待接入」注释留在仓库里，README 写着"支持批量导入"——读者按 README 找不到入口， reviewer 按文件以为功能存在 |

第 1 项（密钥硬编码）的方法里藏着一个很多人不知道的动作：除了 grep 字面量，还要用 `git log --all -S <密钥名>` **查历史**。它的阻断标准也分两段：源码 / 示例 / 测试里出现**可用**凭据 = 阻断；历史残留则要求「确认该密钥已在服务商处作废」。[实测] 这个差别是整套检查里最实在的一条认知——**把密钥从代码里删掉不等于它失效**，因为 git 历史还留着；真正的补救动作发生在代码之外（去服务商那边作废）。[推演] 失效输入：某项目"清了密钥"后推到公开仓库，`git log` 里旧提交还带着凭据；扫描器只查工作树不查历史，检查表第 1 项被判"通过"，而第三方十秒钟就能从历史里拿到可用凭据。

执行法四条也定了证据形状：L1 逐项过，每项记「通过 / 阻断 / 不适用 + 证据」，证据形式是**文件位置或命令输出**；阻断项 → **切修复卡**（回到 ⑤⑥ 正常流程执行），修完**复跑该项**；报告落 `docs/pipeline/安检报告.md`，含三档结论与遗留风险清单；收尾（⑫）**凭 L1 全绿报告放行**。[实测] 注意「阻断项 → 切修复卡」这一句：安全整改被强制走回流水线的正常轨道（有卡、有验收、有台账），而不是"顺手改掉就完事"。这是阻断式把关的第二层意思——**连修复本身也要被记账**。

还有一条容易被夸大的诚实声明值得写进面试：文件写了「**工具只覆盖约一半，其余人工走查**」，并给出工具优先原则（能用工具的不肉眼，如 `pip-audit` / `bandit` / 密钥扫描类 / grep 规则）。[实测] 这句话是防"上了扫描器就等于安全"的误解。[推演] 失效输入：`pip-audit` 全绿，而第 3 项（DEBUG 连坐）、第 4 项（鉴权覆盖矩阵）、第 6 项（字段自报）这三条扫描器完全看不见——它们是**语义级**的，需要人来判断"这个分支的默认值能不能上生产"。

### 9.4 ⑭ 对外口径：四条规则与 12 项核查

**定位与阻断语义**（文件头原文口径）：全局维度，与 ⑬ 并列，不属于任何单卡；凡有对外输出的项目在收尾前必跑；发现的口径失实「与 ⑬ 的 L1 阻断项同等处理——不许带着失实口径收尾 / 投递」。[实测] 对应到主页就是铁律 11 的四个"任一 → 阻断"：数字缺四件套 / 数字早于最后一次评测 / 引用不存在的 commit / AI agent 冒充真人署名。

**规则 1 · 数字四件套**（缺一不可）：来源命令（能复现的一行命令）、样本量 / 分母、统计口径（是 F1 / 准确率 / 召回？含 95% 置信区间）、生成日期。[实测] 文件自己给的合格形状是四行：一行结果（用例总数 + 通过 / 跳过 / 失败 + 墙钟秒数）、一行命令（venv 里解释器跑测试的完整命令行）、一行日期。[实测] 顺手复算一下这条示例的算术：`wallclock 413.84s` 换算成分钟 = 413.84 ÷ 60 = 6.897 分 ≈ **6 分 54 秒**，与该行标注一致——这就是"数字要能复算"的最低标准：**同一件事的两种写法必须能相互换算**。

**规则 2 · 过期即禁写**（时间戳铁律）：任何数字的"生成日期"早于"最后一次跑评测 / 测试"的日期 → 不许对外写；文件明写「这一条是硬性阻断，不是建议。它一次性能防住'抄历史快照'这类错误」。落地方式是给每个对外数字打 `@日期` 标记，发布前扫一遍，凡早于最后一次评测的就**重跑或删除**；并且配一条前提：项目自己的 CHANGELOG 里每条数字记录**必须带日期**——没有带历史的日期，规则 2 就无从比较。[实测]

**规则 3 · 引用必须可验证**：报告 / README / 简历里出现的每个 commit 号、文件路径、函数名、数字都要能被一条命令验证；「**引用不存在的对象 = 阻断**（等同没写，且比不写更糟——它会让整份报告的可信度归零）」。核查命令是三条只读探针（probe，只检查不改动）：`git cat-file -t <commit>`、`Test-Path <file>`、`Select-String -Pattern <符号>`。[实测]

它的真实教训是全页最锋利的一条记录：一份 `安检报告.md` 把「某提交已移除文件」当作"密钥已处理"的**关键证据**引用了三次，而 `git cat-file -t` 返回 `fatal: Not a valid object name`，`git log --all -- <目标文件>` 也没有任何记录——**一份安全审查报告引用了一个幽灵提交**。文件自己的判词：「这比不写这条更致命。」[实测]（那个提交号在本支正文里被记为一个七位短串；它并不存在，因此这里复述它没有任何定位价值，本页照例不抄。）

这条为什么严重：安检报告是 ⑬ 的产出物、是"能不能收尾"的凭据（9.3 末）。它一旦含假引用，被污染的不是一个句子，是**整条收尾链路的放行依据**——下游看到的是"报告里有证据"，而证据的强度已经不可信了。这也解释了 ⑭ 为什么必须做成**独立**一步：同一个上下文写出的报告，很难由自己发现引用对象不存在；`git cat-file` 这条只读探针不需要重新理解业务，只需要执行。

**规则 4 · AI 协作必须披露（署名与范围）**：agent 角色卡的署名必须带 AI 标识，不得使用看起来像真人的姓名 + 企业邮箱；README 必须声明 AI 的参与范围（哪部分是 AI 产出、哪部分由本人主导）；并且文件特意补了一句双向的话——「不得把 AI 的贡献写成自己的著作权，**也不得把"用 AI"当成需要隐瞒的事**——需要披露的是'范围'，不是'有没有用'」。[实测] 它的机理在那条反例上说得最清楚（本页只描述形状，不抄那串署名）：昵称取一个专家人名 + 域名用一个根本不存在的企业域名，后果是第三方会误判"这是真人协作者"，进而让 `git log` 呈现"团队项目"的观感，**与"个人独立项目"的对外表述直接冲突，且无法在简历里解释工具配置**。[实测] 复算这条冲突的判据就是核查表第 8 项的方法：`git log --format='%an <%ae>'` 把所有署名拉出来看一遍——这是一条零判断成本的只读探针。[推演] 失效输入：一次面试里被要求"打开你的仓库讲讲协作结构"，`git log` 里躺着两个"真人同事"的署名和一个查不到的域名，而你的简历写"独立开发"——这一刻失实的不是数字，是**你自己是谁**。

**核查表 12 项**（数法：数第二节表格数据行 = 12）里，四条核心规则之外的八项更见工程味，它们把"口径"这种软东西压成了可判定条件：[实测]

- 第 4 项：每个百分比的样本量——**分母 < 30 或未说明 → 必须写明样本量**。
- 第 5 项：样本 < 100 的指标——无置信区间且用于对外结论 → **阻断**。
- 第 6 项：声称"训练 / 微调"却没有 mAP / loss / 评测报告落档 → **不许写"训练"**。
- 第 7 项：权重或数据集别人拿不到 → README 必须说明来源或改为"私有"。
- 第 10 项：简历 / 作品集逐条对照仓库事实，任一主张无法在仓库验证 → **改简历或改仓库**（注意这条给的是两个动作，不许"加个脚注"）。
- 第 11 项：查评测集是否**同时**被用于调参与汇报——即"用考卷练题再考同一张卷" → 必须标注并补独立验证集。
- 第 12 项：承诺"杜绝 / 100% / 全部"却没有全量证据 → **降级为"已验证范围：X"**。

30 与 100 这两个阈值是本页最该老实处理的两处数字。它们写在文件里，但文件没有推导过程，所以本页标它们的性质：**[推演] 属经验阈值，不是可从公式复算的常数**。可以站得住的解释是——30 是常见的"小样本 / 大样本近似"分界，低于它任何百分比都会剧烈跳动；100 是"这一个数字到底说明了多少次独立观测"的对外最低门槛。[推演] 具体失效输入：文件自己举的那个反例就是分母 3 的"拦截率 100%"——3 个样本里 3 个通过，置信区间宽到等于没说，而它被写进 README 之后会被读者理解为"这套系统能拦下所有恶意输入"。**阈值取低了（比如 5），这种句子照样能过；取高了（比如 1000），大量真实但小规模的项目全部无法对外报数，作者就会开始隐瞒样本量。** 这就是"换一个数会怎样"的答案：30 与 100 是在"能拦住吹牛"和"不逼人造假"之间取的两个刻度。

执行法五步里有两个动作值得单拎：阻断项 → 切修复卡，且修法**只有四个选项**——改简历口径 / 重跑评测 / 补证据 / 删数字，「不许'先记着'」；改完**复跑本步**，全绿才允许收尾。[实测] 「不许先记着」这句是全套阻断设计的灵魂：提醒式的失败方式从来不是"没被提醒"，而是"被记下来了、然后没人回去看"。

### 9.5 为什么这两步非做阻断式不可

一句话版本在文件末尾：**⑫ 保证你收尾那一刻的数字是真的，⑭ 保证你说出去那一刻的数字还是真的。**[实测] 展开成三条判据：

1. **成本发生在外部，无法回收。** 卡内验收不过，返工只花自己的时间；口径失实一旦投递（简历已交、README 已公开），修正成本变成信用成本，而信用没有回滚方案（对比 ⑬ 的第 13 节还给了"回滚方案"，因为代码可退，话不可退）。[推演] 失效输入：一份写着"13 秒跑完全量"的简历让你进了面试，现场被要求跑一遍真实耗时（7 分半到 9 分 50 秒区间），这一刻项目的所有其他数字都自动降权——一次无法回收的失实，会连累十条本来真实的陈述。
2. **提醒式在截止时间下必被跳过。** 这两步都排在收尾之前，正是压力最大、最想收工的时刻。文件把 ⑬ 的第 4 条写成「收尾**凭** L1 全绿报告放行」、⑭ 写成「全绿才允许收尾」，用词是凭据而不是建议。[实测]
3. **判断成本必须一次性摊到清单上，不能摊到每次收尾上。** 阻断式等于把"要不要重视安全"这个反复出现的决策，压成一次性的清单编写；执行时只剩"这一项过没过"，没有商量空间。[推演] 失效输入：如果 ⑬ 只是"建议自查安全"，每次收尾都要临场判断"这个项目算不算需要严检"，而判断所需的上下文（是否对外、是否有敏感数据）恰恰是当时最容易被乐观解读的部分——最后每次都会得出"这次没事"。

最后一条常被忽略：这两步各带一个 `gates` 枚举字段（`security_L1` = passed / failed / pending；`outward_claims` = passed / n/a / pending）。[实测] 也就是说"阻断式"在这套设计里不是形容词，**是一个可以被脚本读的取值**，`n/a` 还专门给"不适用"留了位（对应 9.3 的"不许空跑"）。第 10 章会讲这两个字段自身怎么坏。

## 第 10 章　失效与恢复

这套流水线自己也会坏。下面十种失效形状，前六种是"状态类"（记错了），后四种是"结构类"（清单本身有洞）。每种都给三件事：**怎么发现**（可执行的判据，不是感觉）、**为什么会发生**（机制根因）、**怎么退**（恢复到可信状态的动作）。

### F-1 台账与实况漂移（双写窗口）

- **现象**：`台账.md` 说卡#3 在做，`state.json` 说它已进 `done`，或者反过来。
- **怎么发现**：比较两份的 `updated_at`，差值不为零就是漂移信号；再抽 `current_card.id` 与台账「在做」区的卡号是否相等（算法：取 JSON 的 `current_card.id`，在台账「一、在做」表的第一列里找同一个号，找到即一致）。[实测]（仲裁规则本身在 `台账模板.md` 的「state.json 三条约束」第 2 条）
- **根因**：两处写入不是原子的，任何一次中断都可能只写完一半。
- **怎么退**：按规则以 `updated_at` 较新的一侧为准，**当场回写另一侧**，并把这次回写动作记进卡备注。备注那一句是防"下次又漂却查不到原因"的唯一线索。[实测]

### F-2 时间戳被手写，导致仲裁反向

- **现象**：看起来一切一致，但较新的真实状态被较旧的估计值覆盖了。
- **怎么发现**：`updated_at` 出现整点、半点或明显"人填的数"（全是 00 秒）就是可疑；更硬的判据是同一项目里两次写入的时间戳相等。[推演] 机制见 5.4 的失效输入（估计值 10:00 < 真值 13:20 时，系统会回滚掉另一个窗口的真实更新）。
- **根因**：模板第 4 条纪律明文禁止的"手写估计"发生了——`updated_at` 必须实时取值（`date` / 系统时钟），因为"记档时间戳用估计值是查不回来的账"。[实测]
- **怎么退**：这条**没有事后恢复手段**，只能重跑：把漂移窗口涉及的卡全部退回「待执行」，逐张重新验收并按 DoD 七拍走回一遍。这也是本支把"实时取值"写成硬性纪律的原因——它不是格式洁癖，它是唯一的裁判依据，裁判一旦被污染，判决就只能作废。[推演]

### F-3 做了但没记

- **现象**：代码改动在仓库里，台账上那张卡还在「待执行」。
- **怎么发现**：`git log` 里存在提交信息含该卡号的提交（7.2 第 5 步规定提交信息必须带卡号），但台账没有对应的「做完」条目；或者任务板里该条目还在、执行者字段却已填了名字与开工时间（认领了却没写回）。
- **根因**：执行体只做到 DoD 的第 ① ② 步就停了（它可能以为自己还要继续，或者被中断）。
- **怎么退**：**不许直接把卡勾成做完**。正确动作是补记后重新走一遍该卡验收（跑那条命令、把原始输出落进 `evidence/`），因为台账「做完」区要求带关键数字与日期，而那个数字必须是"落盘数字的来源"。[实测]（`state.json` 约束第 1 条）

### F-4 记了但没做（更危险的一类）

- **现象**：台账「做完」区有勾、有数字、有日期，但那个数字来路不明。
- **怎么发现**：随机抽一条 `done` 记录，要求说出它的 `metric` 是哪条命令产出的、原始输出在哪个文件；说不出来即失效。这条抽查的成本是 30 秒，且**不需要读代码**。[推演]（依据是 `state.json` 约束第 1 条把"`metric` 必须是落盘数字的来源"写成了硬要求，所以违反它一定是可查的）
- **根因**：勾台账时被当成"汇报进度"而不是"登记证据"。铁律 4 那句"不是事后补记"防的就是这个心态。
- **怎么退**：把该条从 `done` 移回 `next_cards`，重跑；同时把这条失效记进 ⑩ 的回看报告——因为它通常是**批量**发生的（一次补记往往补了好几张）。[推演]

### F-5 断点接回一个"已经归档"的项目

- **现象**：新会话启动，按路由第 1 步去找 `docs/pipeline/台账.md`，结果目录里躺着一份 `台账_归档_20261005.md` 和一份被复制出来继续改的旧台账，两份都在。
- **怎么发现**：目录里同时存在 `台账.md` 与任何 `台账_归档_*` 文件，且前者的 `status` 是「已完成」或「已归档」。[实测]（收尾第 3 步规定归档动作是**改名**：`台账_归档_YYYYMMDD.md`，并在顶部加"本项目已交付，台账仅供追溯"）
- **根因**：归档用改名而不是移走，正是为了让"能不能找到 `台账.md`"这一个信号就等于"有没有活要续"。项目复活时如果直接把归档件复制回来继续，就绕过了"这是新一轮"的判断。
- **怎么退**：新一轮要新建 `台账.md`（模式可以沿用，但号位状态从头算），归档件保持只读，作为 ⑭ 的数字溯源资料。[推演] 失效输入：直接把归档件复制成 `台账.md` 继续跑，旧的那批 `done.metric` 与新代码已经不是同一版本，规则 2「过期即禁写」会在收尾时把所有旧数字全部拦下——这反而是好事，说明闸在起作用。

### F-6 gates 被凭印象写成 passed

- **现象**：`security_L1 = passed`，但 `安检报告.md` 只有结论没有逐项证据。
- **怎么发现**：报告的"执行法"要求每项记「通过 / 阻断 / 不适用 + 证据」，证据形式是文件位置或命令输出原文。[实测] 于是核查动作极其便宜：数一数报告里有没有 12 条带证据的行；不足 12 即 `passed` 无效。K 节同理应 ≥12，F 节应 =6（数法：`验收模板-上线门禁与口径.md` 三节表格的数据行数分别是 12 / 12 / 6，合计 30 项）。
- **根因**：`gates` 是枚举值，写它不需要真跑检查——这是机器可读设计的固有代价：**门禁字段越方便，就越需要它的证据文件同步存在**。
- **怎么退**：复跑对应那一节，报告全绿才放行。两条细则的执行法都明写了"阻断项 → 切修复卡 → **复跑该节 / 该项**"，而不是"改掉就放行"。[实测]

### F-7 自检清单查不到的缺失（结构洞）

8.3 已经算过：自检逐名清单 + 附属抽查合计 46 个可核对项，实际 51 个文件，差 5 个，其中 4 份是 v1.2 以后加的细则。**这 4 份缺失时不会有任何级别报警**。[实测]
- **怎么发现**：不能用自检本身发现——这是重点。可行的替代判据是拿 `references/` 目录的真实文件列表与自检清单做差集（一条只读命令的事），或者看流水线跑到 ⑬⑭ 时能不能说出 L1 的 12 项（说不出即细则没读到）。[推演]
- **怎么退**：把清单补全（这是维护动作，见第 11 章与第 15 章），或在本支升级时把"新增细则必须同步进自检清单"当成一条变更检查项。

### F-8 三行摘要派活（v1.5 就是为了它才存在的）

铁律 14 的原文判词：「禁止拿三行摘要直接施工——『拿着就能施工』的施工图缺位 = 质量全凭执行者发挥」。[实测] 教训锚点是 2026-10-05 某内部项目的任务板：同一批活里，六节带检索来源与现查路径的卡文、以及带现状 / 分刀 / 验收的施工单，质量明显高于三行摘要派活。
- **怎么发现**：看 `docs/pipeline/具体任务卡/` 目录在不在（L3 建档时就应创建 `任务卡.md` + 空 `执行回执.md` + 空 `evidence/`），再对照卡的粒度档：中/大卡却只有 L2 文件 → 缺层。[实测]（§2 分工表的「谁维护」「内容」两列给出对应关系）
- **怎么退**：按 §2 纪律 1 的口径「颗粒度递增，缺哪层补哪层」补写 L3；补写时必须现查代码，且过 §5.3 的 8 项自检（数法：该清单是 8 个复选框）。任何一项缺 = 没写完。[实测]

### F-9 幽灵引用（⑭ 规则 3 专防）

已在 9.4 详述：安全报告把不存在的提交号当关键证据引用三次。[实测] 恢复动作只有两条：把该句改成可验证的引用，或者删掉——而删掉之后那句结论就没有支撑了，所以真实的恢复动作通常是"回去把证据真的做出来"。这就是为什么规则 3 的阻断语义写的是"等同没写，且比不写更糟"。

### F-10 门禁模板停在旧版本（设计上的豁免）

`验收模板-上线门禁与口径.md` 自己写着：派生自 v1.3.0，S/K 两节细则 2026-09-23 定稿；**复制到项目后锁定当前版本，skill 升级不追溯已归档项目**。[实测] 这是一条刻意的设计（项目验收单不该被未来改动改写），但它带来一个可验证的后果：本支已 v1.5.0，v1.3.1 / v1.3.2 / v1.4.0 / v1.5.0 四条新增纪律（交付物定义与用户视角验收卡、测试证据形态、外部工位产物落盘、三层任务文档不可跳层）在 F 节那 6 项里**没有对应检查行**。[实测] 也就是说：拿这份模板单独跑门禁的项目，收尾清单会漏掉主页最严的四条。恢复方式不是改模板（它锁版本是有意的），而是在项目里同时遵守主页铁律——第 15 章把这条差登记为缺陷。

### 10.11 失效的两条总根因

十种形状归成两类原因，这也是讲这套系统时最该带走的两句：

1. **状态类的根因都是"写不原子"**（F-1 到 F-6）：两处记录、两个窗口、两次动作，中间任何一次中断都会造出半成品。对策统一是一句话：**先写台账，再删任务板**；再加一条：**时间戳只能取实时**。这两句看着琐碎，实际上是全部双写问题的解。[推演]
2. **结构类的根因都是"清单是静态的，而纪律是增长的"**（F-7 到 F-10）：自检清单、门禁模板、索引表标题里的"十二步"，都是被某一次定稿冻住的文本；而铁律从 9 条长到 14 条。**任何"按清单核对"的机制，都必须有一条"清单本身是否完整"的元核对**，否则它会在新维度上加进来之后仍然报绿。[推演] 这条正是 9.2「检查归属」教训的升级版：不仅要给每个维度找主人，还要给"主人名单本身"安排一次复查。

## 第 11 章　例行维护与体检

本支没有"跑一段时间要重新校准"这种硬件式体检概念（它是文本规则集，不会退化）。它需要体检的原因是另一个：**规则会长，清单不会自己跟着长**（F-10 那类失效）。所以本章写两件事：**怎么验证它真在生效**（11.2 的只读探针），以及**改了它之后要做什么**（11.4 的维护动作）。

### 11.1 五个固定节拍（谁在什么时候被检查）

| 节拍 | 触发点 | 检查什么 | 谁执行 | 成本 |
|---|---|---|---|---|
| 每次启动 | 号位 〇 | 细则与副本是否在位（🟢 / 🟡 / 🔴 三级） | 主控自动 | 约 5 秒 [实测] |
| 每张卡 | 号位 ⑥⑧ 的 DoD 七拍 | 回执 / 台账 / `state.json` / 任务板 / 记录清单五处是否全写完 | 执行体自己，主控复核 | 秒级 [实测] |
| 每 1/3 卡数 | 号位 ⑩ + ⑪ 总评审 | 跨卡一致性、架构漂移、性能与安全抽查；**暂停派遣** | 主控 + 评审执行体 | 重量级 [实测] |
| 收尾前 | ⑬ → ⑫ → ⑭ | L1 全绿是放行凭证；全量评测对照开工前基线；有对外物则 12 项口径核查 | 主控（可交给独立会话做只读核查） | L1 约 30 分钟 [实测] |
| 推送前 | 门禁模板 F 节 | 6 项交付卫生：当日全量输出、CHANGELOG 带日期、台账已归档、无本机绝对路径、无密钥与隐私数据、署名带 AI 标识 | 人或独立会话 | 分钟级 [实测] |

节拍之间的**顺序**不能改：⑬ 在 ⑫ 之前（铁律 10）、⑭ 在 ⑫ 之内第 5 项之后、F 节在推送之前。这个次序就是"谁给谁放行凭证"的关系，第 9 章已解释过它的成本逻辑。

### 11.2 十条只读探针（probe：只检查、不改东西的核对动作）

每条都给复算方法，因为体检的价值在于**别人能重跑**。任何一条红了都指向第 10 章的某一类失效。

1. **时间戳对账**：取 `state.json` 的 `updated_at` 与 `台账.md` 头部状态行的日期时间比较，不等就查是哪一侧手写估计（→ F-1 / F-2）。判据补一条：全库 `updated_at` 秒位为 `00` 的比例明显偏高即"人填的"信号。[推演]
2. **三集合相等**：任务板未删条目号集合 = 台账「在做」+「待执行」号集合 = `state.json` 的 `current_card` ∪ `next_cards` 号集合。算法：各取卡号排序后逐项比。红了即"删了任务板没写台账"的丢失窗口（5.5 纪律 ①）。[推演]
3. **卡文件数对账**：`docs/pipeline/cards/` 下 .md 文件数 = 台账登记行数（号位 ④⑤ 规定一卡一文件、每张卡在台账登记一行）。算法：一条列目录计数对一条表格行数。差值不为零说明有卡没登记或有行没卡。[实测]（依据是铁律 3 + 号位 ⑤ 产出物那句「每张卡在台账里登记一行」）
4. **L3 覆盖率**：中卡与大卡是否都有 `具体任务卡/<编号>-<卡名>/任务卡.md`（算法：先按 §1 粒度表把卡分档，再数对应目录）。缺层即 F-8。[实测]
5. **回执与证据在位**：抽查任意一张已勾「做完」的卡，能否在 30 秒内说出它的 `metric` 出自哪条命令、原始输出落在哪个文件（→ F-4；铁律 13 明文禁止"只在对话里说绿了不留输出文件"）。[实测]
6. **门禁三节行数**：`安检报告.md` 带证据的行 ≥ 12，`口径核查表.md` ≥ 12，推送检查 6 项全勾。算法：数表格里"结果"列被填过（☑ / 阻断 / 不适用）的行。不足即 F-6（`gates` 是凭印象写的）。[实测]
7. **`gates` 与报告互证**：`security_L1 = passed` 时报告里必须零阻断项；`outward_claims = passed` 时核查表里必须零阻断项。算法：两文件各扫一次关键词。这是防"机器字段与人类文档打架"的最便宜的一道闸。[推演]
8. **号位集合 vs 模式**：`mode` 与 `steps_done` 要一致——`mode = 轻量` 却出现 ②⑨⑩，或 `mode = 标准` 却出现 ⑨，就是模式漂了（算法：把 `steps_done` 与索引表对应列的勾选行做集合差）。顺带查一条历史包袱：`steps_done` 里出现 ⑬⑭ 才说明这个项目真跑过两步阻断，否则它只是勾了 12 个老号位。[实测]
9. **自检清单覆盖度**（元体检，专治 F-7）：拿 `references/` 的真实文件列表与自检清单的逐名条目做差集。当前差集应显式承认 5 个（`CHANGELOG.md` + 4 份后加细则）。算法见 8.3。**这条不是检查 skill 的，是检查"检查表"的。**[实测]
10. **副本目录规模**：`superpowers_assets/` 文件数 ≥ 17（自检清单里本来就写了这条抽查），`depends/` = 20（8 + 12）。算法：递归计数。注意「刻意不收的 3 个上游 skill」**不许被报成缺失**——它们在该文件专门的一节里被登记为不收，这是自检结果解释的一部分。[实测]

### 11.3 一次完整体检的顺序与判读

顺序建议照这个走，理由是"便宜的、能一票否决的放前面"：[推演]

```
① 启动自检（5 秒，🔴 直接停）
② 探针 9：清单覆盖度   ← 不通过的话，①②③…的"绿"都不可信
③ 探针 10：副本规模
④ 探针 1、2、3：状态三账（时间戳 / 三集合 / 卡数）
⑤ 探针 4、5：卡与证据
⑥ 探针 6、7：门禁与字段互证
⑦ 探针 8：模式与号位
```

②排在最前不是强迫症：第 7 条探针查的是"检查表本身完不完整"。如果它红了（例如清单被删改过），后面所有基于清单的核对都建立在一张有洞的表上——**这正是本支 F-7 那类失效的成因形状**：清单绿 ≠ 系统好，只是清单没问。[推演]

### 11.4 改了本支之后必须做的四件维护动作

维护纪律来自 `依赖与自检.md` 的末节与 `外部工位对照表.md` 的末节，四条：[实测]

1. **副本是快照，不自动跟随上游。** 若源 skill 升级（文件里举的例子是"头脑风暴出 v1.2"），由**维护者决定**是否重拷覆盖副本 + 更新清单里的版本标注；如果本地细则吸收了新版改动，记得同步改细则。[实测] 这条把"要不要跟版本"这个决策显式交给人，而不是让文本自动漂。
2. **上游锚定不许拆散。** 那 12 份副本 + 16 个附属文件是按同一个上游提交锚抓的（8.2）；单份覆盖升级会破坏「互引一致」，所以升级要整批做。[实测]
3. **工位表是纯指针文本。** 外部插件升级或换版后**先复扫再采信**（skill 数、路径、字段都可能变）；该表只写现状，不记"上一版曾如何"。[实测] 这是一条很克制的取舍：把历史留给 CHANGELOG，把指针表保持成"当前真相"，避免读者按旧行位找新文件。顺带一条同源约束——本页第 3 条引用纪律（禁写行号，只写文件名 + 章节名）就是同一个道理的可移植版本。
4. **改完跑一遍库内 lint 脚本，并同步映射表与本库 CHANGELOG。** 对照表末行规定了这三件事。[实测]（库内的 lint 与映射表属于仓库工具层，本页只描述"有这个动作"，不写它们的本机路径。）

另外有一条**没被写进文件但必须自己补**的维护动作，本页作为 [推演] 提出：既然 F-7 证明了自检清单不会自动跟随新增细则，那么每次给本支加号位或加细则文件时，应该把「自检清单是否包含新文件」当成一条变更检查项。这条如果成立，本支会在下一次加第 ⑮ 步时不再漏掉它——而按历史看它确实还会再加：v1.0 → v1.5 期间平均每两次版本迭代就多一个号位或一条铁律（算法：14 号位 − 初版 12 号位 = 2 个新增号位，分布在 6 个版本条目里的 2 个，即 v1.2 / v1.3）。[实测]

### 11.5 怎么知道它不是空转

"这套东西是不是只是让人多写几个文件"，是本支最常被质疑的地方。三条正向信号 + 三条空转信号，都可以只看文件不读代码：[推演]（每条的判据本身是 [实测] 的字段要求）

- ✅ **真在生效**：台账里每条「做完」都带数字与日期；`git log` 提交信息里能数出与卡号对应的提交；`docs/pipeline/` 下六类产出物（设计纪要 / 技术选型记录 / PRD / cards / 台账 / state.json）齐全且非空壳。
- ❌ **在空转**：只有 `PRD.md` 的标题行（第 1 章那个失效输入的形状）；报告有结论无证据行（F-6）；台账存在但 `updated_at` 全是整点（F-2）；`gates` 全绿而对应报告文件不存在。

第四条判据最狠也最便宜：**把 `docs/pipeline/` 目录交给一个从没见过这个项目的会话，看它能不能在不开口问的情况下说出"下一步该干什么、为什么"**。断点存档的全部意义就在这一句上——如果它说不出来，那这本台账只是日志，不是存档。[推演]

## 第 12 章　端到端走查（完整示例）

本章的目标是**可以照着走一遍**。下面这条线是本页构造的示例项目（项目名、卡号、数字均为本页虚构，用来演示形状；凡引用真实文件的地方都注明文件名与章节名）。示例里所有落盘路径一律用 `<项目根>/docs/pipeline/…` 的相对形态表达，这也是本支「通用化说明」第 1 条要求的写法。[实测]

**用户的第一句话（原话形状）**：

> 我想给我们店做个小工具，能自动盯竞品价格，我一个人用，别太复杂。

### 步 0：触发后的前 30 秒（号位 〇 + 路由）

1. **依赖自检**（约 5 秒）：细则在位、副本在位 → 🟢。若 `安全基线检查.md` 不在位，**这一步不会报警**（8.3 / F-7 那个结构洞），走查里先假设清单齐全。
2. **查台账**：`<项目根>/docs/pipeline/` 下没有 `台账.md` → 走"新项目"分支，问落盘目录（默认建议 `docs/pipeline/`，用户可改）。**这是不可省的两件事之一。**[实测]
3. **判模式**（依据 `模式判定.md`）：信号是「新功能、范围可控、单人」→ 推荐 **B 标准**；理由一句话给出（"不是全新大项目，也没有多分身协作，但『盯竞品』这件事的范围需要 PRD 与卡才锁得住"）。同时提示可以改选，并说明改 C 会多出什么（选型深选全层 + 卡库 + 双评审 + 总评审 + 工具箱外挂）。[实测]
4. 用户回答里追加了一句「以后可能给店员用」→ 主控**重新推荐**（提问模板本身留了这个口子："也可以直接告诉我你的顾虑，我重新推荐"），但结论仍是 B，因为多人使用影响的是权限设计（进 ① 的约束），不是流程档位。[推演]

> 那条给用户的第一次回复有固定的五段形状（本页只描述段，不抄原文）：复述用户意图 → 推荐档位与一句话理由 → 四个选项各配一句适用信号 → 明确"选哪个" → 允许用户改口。[实测] 这五段的存在理由：**用户不该先看懂 A/B/C/D 才能回答问题**，看懂的活儿在流水线这边。

### 步 ①：磨设计（产出 `设计纪要.md`）

按 `阶段①磨设计与选型.md` §1 的六条规则走。本例列出 **5 个顶层决策分支**（规则要求 3~6 个），从最基础的问起：

| 分支 | 为什么它更基础 | 推荐答案 + 理由（每条都要带，规则 1） |
|---|---|---|
| a 抓来干什么用 | 决定后面所有分支 | 只回答"谁涨价了、涨多少"，不做趋势分析——分析会拖出存储与图表需求 |
| b 数据源范围 | 决定合规与故障面 | 3 个竞品站点，人工先确认可抓性；不引第三方行情 API（预算与锁定风险） |
| c 更新频率 | 决定架构（要不要队列） | 每天 2 次，够用即可 → 不需要队列；这条直接砍掉 Kafka（见步 ②） |
| d 谁来判定"异常涨价" | 决定验收长什么样 | 店主自己勾"已知会涨价"，工具只标记不裁决——裁决权留给人 |
| e 历史深度 | 决定存储与运维成本 | 保留 90 天，单表 SQLite 足够；不做归档压缩 |

- 每轮结束出**书面小结**让用户确认（规则 3），本例跑了 **3 轮**（轮数弹性，问到无"看情况"残留为止）。[实测]
- 规则 6「能靠读项目文件回答的问题自己查，不问用户」在本例里挡掉了 2 个无效提问（现有表格里的商品编码格式、店铺名，都可以自己读）。[推演]
- **HARD-GATE 生效中**（规则 4）：这三分钟里没有任何代码、没有 `requirements.txt`、没有目录骨架——设计未获批准前禁止写任何代码或搭任何骨架。[实测]
- 规则 5「无情 YAGNI」当场砍掉两项：多币种换算（现在只有本币）、邮件告警（店主一天看两次工具，不必）。

`设计纪要.md` 六个字段（目的 / 用户 / 约束 / 成功标准 / 核心方案与取舍 / 已知缺陷）落盘，其中**已知缺陷**这一栏如实写了三条：竞品页面改版即失效、无历史价则判定不可回测、抓取频率受对方限流约束。[实测]（"每个方案必须如实列出已知缺陷与翻车场景"是规则 5 的后半句）

### 步 ①′：交付物定义一句话（v1.3.1 挂在磨设计里的前置段）

`阶段①磨设计与选型.md` §3 的「交付物定义锁定」要求它**先于一切功能讨论**，且三要素齐全（谁用 / 怎么用 / 一次真实操作 + 多快发生）。本例锁成这一句：

> 店主周三早上 8:40 打开浏览器，登录，看到昨天涨价的竞品条目列表（含涨幅与自家对照价），点"标记已知"，导出当天 CSV；全程除启动这条命令外零命令行。

写进 `设计纪要.md` 与 `PRD.md` 头部，**后续所有验收以此为准**。[实测] 这一句在 ⑤ 会变成那张"用户视角验收卡"的判据，在 ⑭ 会变成简历里那条主张的对照组——这是它被要求写在最前面的实际原因。

### 步 ②：技术选型（产出 `技术选型记录.md`）

B 档走「★层 + 核心层」。本例用户初始想的是 `Scrapy + Kafka + PostgreSQL + React + Docker`。逐层走完（每层 5~9 候选，每候选必须写缺陷——文件里的理由句是"只说优点 = 卖文创收智商税"），然后做**冲突调和**：[实测]

| 层 | 用户初选 | 调和后 | 调和不行的理由写了什么 |
|---|---|---|---|
| 抓取框架 | Scrapy | `httpx` + `APScheduler` 定时脚本 | Scrapy 的中间件与管道是为大规模爬取设计的，3 个站 × 每天 2 次的量级换来的是三倍运维概念 |
| 消息队列 | Kafka | **删掉** | 层 c 已定"一天两次"，队列解决的是吞吐削峰，这里没有峰 |
| 数据库 | PostgreSQL | SQLite | 单写者、零运维；PG 的运维成本在层 0「单人、三个月后还维护得动吗」这一问下不划算 |
| 前端 | React + 构建链 | 服务端渲染的一个列表页 + 原生表单 | 前端深选（层 8）一整套 hooks / 打包 / 状态库对本页是净负担 |
| 部署 | Docker | 直接部署（可选容器化） | 层 11 明确"个人最简"，K8s 归企业 |

调和说明那句被原样写进记录里（文件里那句好例子的逻辑值得复用）：**"每项降级省下的时间够你把产品做完上线三次。"**[实测] 这里也标了「跳过了什么、什么时候会需要它」——按需裁剪时必须告知，这是 §2 总规则第 4 条的后半句。[实测]

### 步 ③：PRD（产出 `PRD.md`）

必含五件（文件明文）：产品定位一句话 / 核心功能列表（P0 必做、P1 应做、P2 锦上添花）/ 用户流程 / **全局验收标准** / 技术选型记录引用。[实测]

- P0：登录、每日抓取、涨价判定与标记、CSV 导出、抓取失败可见（失败必须显示，不许静默少数据）。
- P1：竞品站点健康度提示、90 天历史查询。
- P2：多用户权限、趋势图——**P2 一律不切卡**（§3 第 6 条 YAGNI：「PRD 里 P2 的功能不切卡，等 P0 全绿再说」）。[实测]
- 全局验收标准直接引用步 ①′ 那句话，不重写一遍（重写 = 双真源）。

### 步 ④⑤：切卡（产出 `cards/` + `具体任务卡/` + 任务板 + 记录清单）

先定粒度（§1 表），再切。**本例 9 张卡**：小卡 2 / 中卡 5 / 大卡 2（算法：按"涉及文件数 / 是否需要大量上下文 / 验收可否自动判定"三依据人工分档，本页示例赋值）。

| 卡 | 标题 | 档 | 依赖 | 并行 | 验收（机械判据） |
|---|---|---|---|---|---|
| #1 | 项目骨架与启动脚本 | 小 | 无 | 【P】 | `启动命令退出码 0` + 健康检查返回 200 |
| #2 | 数据表与建表脚本 | 小 | 无 | 【P】 | 一条 SQL 直查表结构字段数 = 定义数 |

| #4 | 涨价判定与基线对照 | 大 | #3 | — | 评测集 30 条人工标注样本，判定准确率 ≥ 基线；逐条给 `grep` 断言 |

### 步 ⑦：验收先于实现（产出「基线记录」）

#4 开工前把 30 条人工标注样本跑一遍现有逻辑（此时逻辑还不存在判定分支，所以**结果是必红的一屏**）：本页示例记为 `baseline: 判定准确率 0/30，因为判定函数尚未实现`，写进卡文件。[实测] 这一句就是"先看到失败"的落地形状：判据先存在、并且先证明它会红，否则 ⑫ 收尾时无从判断"到底有没有进步"。#5 那张 UI 卡的基线是 6 项目前全未勾的肉眼清单——**没有测试框架的卡也要有基线**，这是铁律 2 说"形式不限"的实际含义。

### 步 ⑥⑧⑪：派遣一张卡的完整往返（以 #3 为例）

1. **装配上下文**：卡#3 全文 + `PRD.md` 的「P0 抓取」相关段 + 三个站点的文件精确路径 + 全局约束一句「所有外部请求必须带超时与重试上限，错误不得静默吞掉」。[实测] **没有**带上的：#1 #2 的对话历史、全项目文件树。
2. **执行返回**：改动文件清单 / 验收命令的完整输出 / 三句话总结。
3. **双评审**：评审 A 对照 PRD 与该卡验收逐条判定 → 报**阻断**「失败分支只打了日志，未向上传递状态，#8 无从判断是哪个站失败」；评审 B 代码质量 → 报建议 2 条、备忘 1 条。[实测]（严重度三级出自 `阶段⑥执行与派遣.md`）
4. **阻断处理**：带评审意见**重派一个新分身**（不是让原分身自纠），第 2 轮评审 A 过。最多 2 轮的额度用掉 1 轮。[实测]
5. **过卡（DoD 七拍）**：验收全过 → 测试绿 → `evidence/` 落原始输出 → 回执写回 → 台账「做完」打勾 + `state.json` 同步 → 任务板删 `B3` 条目（**删前已写台账**）→ 记录清单打勾记日期与关键数字 → `git commit` 信息含「卡#3」。[实测]

### 步 ⑧：台账在三个时刻的样子（本页示例数据）

**开工时**（四区：在做空、待执行 9 行、做完空、阻塞空）→ **第 3 张卡过卡后** → **收尾时**。关键在中间那一格：

```
一、在做（最多一张）
| 卡#4 涨价判定与基线对照 | 子代理 | 10-06 09:12 | 依赖 #3 已过；评测集 30 条基线 0/30 |
二、待执行（按依赖顺序）
| 卡#6 标记已知 | 依赖 #4 #5 | 可并行：否 | 验收：标记后状态保持（一条命令） |
| 卡#7 CSV 导出 | 依赖 #4 | 可并行：是【P】 | 验收：导出行数 = 列表可见行数（同 SQL 对两次） |
三、做完（勾选区）
- [x] 卡#1 项目骨架与启动脚本（健康检查 200，10-05）
- [x] 卡#2 数据表与建表脚本（字段数 9 = 定义数，10-05）
- [x] 卡#3 抓取器（3 站点全绿，10-06）
四、阻塞区
| 卡#8 失败可见 | 断网桩需要可控环境 | 用户：确认测试网络策略 |
```

`state.json` 同一时刻的关键取值（本页示例）：`mode = 标准`、`steps_done = [①,②,③,④,⑤,⑦,⑧]`、`current_card = {id:4, executor:"子代理", gate:"评测：判定准确率 ≥ 基线"}`、`next_cards = [6,7]`、`done = [1,2,3]`（每条带 `metric` 与 `date`）、`blocked = [8]`、`gates = {security_L1:"pending", outward_claims:"pending"}`。[实测]（字段名与取值域来自 `台账模板.md` 的 state.json 节）

注意「在做」区**只有一张**：#3 过卡之后 #4 才进在做。这条单值约束就是断点恢复时"下一步该干什么"唯一答案的来源。[实测]

### 步 ⑩：第一次回看（第 3 张卡完成时）

阈值 1/3 → `ceil(9/3) = 3` 张（算法：卡数 9 × 1/3 = 3，取整数触发线；规则写在 `阶段⑥执行与派遣.md` §4「每完成约 1/3 卡数」）。**暂停派遣**，回看报告发现两件事：#2 建表用的时间是本地时区、#3 抓的是对方服务器时区，两者在 #4 的"昨天涨价"定义上会打架。处置：回 ③ 的 PRD 补一条全局约束（"所有时间一律存 UTC，展示层转本地"），并把 #4 施工图卡的陷阱预填改掉。[推演]（回看动作本身是 [实测]：⑩ 的产出物是 `回看报告.md`，⑪ 总评审也写进同一份的评审章节）

这一步最能说明"为什么回看要暂停派遣"：如果不暂停，#4 会带着两套时区直接开工，等到 #9 用户视角卡时才发现"昨天"这个词在系统里有两个意思——那时返工面已经从 1 张卡扩到 4 张。[推演]

### 步 ⑬：安全基线 L1（产出 `安检报告.md`）

12 项逐项过，每项记「通过 / 阻断 / 不适用 + 证据」。本例命中 **3 项阻断**：

### 13.1 为什么前四条最贵

前三条（事后补记 / 形容词验收 / 喂全项目历史）之所以排在最前，不是因为更常见，而是因为**它们的坏不在当下，而在你看不见的那一侧**：事后补记坏在断掉之后的那个新会话，形容词验收坏在 ⑫ 收尾那一次判定，喂全历史坏在一次你根本不会去数的 token 支出。这三类共同点是"当时没有任何现象"——没有报错、没有失败用例、没有红色标记，所以人会一直以为流程在生效。第 4 条（把 ⑬⑭ 当补文档）单独贵一级，因为它是唯一一个坏得**很响**却仍被广泛误用的：响在事故报告里，不响在你的流程里。[推演]

### 13.2 反模式的共同根因

把这 14 条归一下，只有一句：**把这套流水线当成"文档要求"，而它实际是一台状态机。**文档要求的违反表现为"少写了一个文件"，看起来无害；状态机的违反表现为**状态与实况不一致**——台账说做到 #4、盘上其实到 #7；`gates` 写 passed、报告里还有阻断项；上下文以为带了验收、其实只带了三行摘要。第 10 章 F-1 到 F-10 之所以按"状态类 / 结构类"分两组（10.11），分的正是这个：状态类坏在写不原子，结构类坏在清单不跟随纪律增长。反模式清单里的每一条都能落进这两组之一，这也是它比第 10 章好读的原因——第 10 章讲怎么救，本章讲怎么别把自己送进那儿。[推演]

- **规模**：递归 **51 个文件**、总计 346,308 字节；`SKILL.md` 只有 113 行 / 18,310 字节，即知识体量几乎全在 `references/` 里。另注：口径首批表记附属件"50（含 depends 第三方副本）"，复测表记递归 51——本页以复测的 51 为准，两值不合并（差 1 是"附属件 vs 递归文件"的口径差）。[实测]

### 15.5 冷启动注意项（第一次在空项目里启动要盯的九件事）

1. **先问落盘目录再动手**：新项目没有 `docs/pipeline/` 时，这是不可省的两件事之一；默认建议值可被用户改，改了要写进台账头部。[实测]
2. **依赖自检的三级别搞混**：细则缺 = 🟡 降级、副本目录不足 = 🔴 停；但 🟡 档只数文件个数（阈值 ≥17），把任一附属文件截成 0 字节仍判绿——所以自检绿不等于内容在。[实测]
3. **🔴 档的补救出口本次未核实**：文件写的重取路径涉及一个外部仓库与一个技能平台，取证当日禁止联网、可达性未核；实操时别把"重装就好"当成唯一出口。[实测]（缺口性质见 15.6）
4. **解释器名要用对**：本机 `python`／`python3` 是商店占位桩（零输出、退出码 49；接进管道连 49 都看不见），跑测试一律用 `py`（实测 3.12.10）。卡模板示例里写的正是前者。[实测]
5. **PowerShell 探针要包一层**：⑭ 自带的存在性核查用的是 cmdlet 形态，在 Git Bash 里裸敲报 command not found，需 `-NoProfile -Command` 包壳或改用纯 shell 等价命令。[实测]
6. **别顺手执行抄包命令**：抄包里有 18 条相对路径命令在本库解析不到；更硬的一条理由是其中一个抄包脚本会沿目录树上溯到**祖先 git 仓库**并在其根写文件（取证过程中真发生过，产物事后已清除）。要试只能在隔离临时工作树里，并先确认仓库根就是本次允许写入的根。[实测]
7. **派遣能力不确定就走提示词卡模式**：细则的宿主名单只有两个外部宿主名，本宿主不在名单上；"尝试调用子代理能力"这句话既没定义成功也没定义失败——同一个输入两种走向，走向由模型意愿决定。本支这条判据不可判定，本页全程按 [推演] 处理。
8. **门禁模板要复制但别指望它新**：复制为 `ACCEPTANCE.md` 时它会锁定派生版本 v1.3.0，四条后加纪律不在它的检查行里（F-10）；补救办法是在项目里同时遵守主页铁律，不是去改模板。[实测]
