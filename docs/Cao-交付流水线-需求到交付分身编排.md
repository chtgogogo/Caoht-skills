# Cao-交付流水线（delivery-pipeline v1.1.0）

> [← 返回总目录](../README.md#skills-index)

让 AI 做个项目，常见死法有三种。会话一断，进度全丢，新会话从头来，因为你和它都说不清做到哪了。做完没法验收，它说完成了，问怎么验证的，没有验证这回事。过程不可见，它热火朝天干了两小时，你不知道哪步做完了哪步没做，token 烧在哪了也不知道。

这些死法有个共同根源，没有一个贯穿全程的骨架。这个 skill 就是那个骨架，十二步总装流水线，磨设计、选型、PRD、切卡、分身执行、验收、台账、收尾。方法论站在 obra/superpowers 的肩上，磨设计的对话方式、切卡的实习生粒度、双评审都来自它，在这个基础上做了完整的中文化和工程化改造。

## 四个核心设计

**台账即断点存档。** 所有进度记在一个三区台账里，在做、待执行、做完加阻塞，每张卡完成立即勾。它是实时存档不是事后补记，所以任何会话任何时刻断掉，新会话第一件事查台账，问你是继续上次从第 N 张卡接着来，还是开新的。断点续传的问题从机制上消失了。

**验收先于实现。** 每张卡开工之前，怎么验证必须已经写在卡里，评测基线、测试脚本、肉眼清单，形式不限但必须写。顺序反过来是关键，验证动作在开工前就绪，AI 说完成了的时候，验收标准早就摆在那了，没有争论空间。

**一卡一文件加派遣上下文最小化。** 每张任务卡是独立文件，不许塞进单个巨型计划文件，巨型文件是 token 黑洞。派子代理执行时只喂三样，该卡、PRD 相关段、精确文件路径，绝不喂全项目历史。token 花在活上，不花在噪音上。

**按需加载。** 主 SKILL.md 永远只有八十行，十二步索引是指针不是正文，进哪一步才读哪一步细则，一次只读一个。流水线自己得先守省 token 的纪律，才有资格管别人。

## 对已有项目友好

大多数流水线工具默认你从零开始，可最常见的诉求是手里已经有个项目，只想补某个环节。所以启动路由有四档，轻量、标准、企业、跳步优化。跳步档先扫十二步找短板，列缺口清单让你勾，缺哪步跑哪步。也支持单步直调，你说帮我切卡，它直接进步⑤，不逼你跑全程。

选型阶段是分层深选，从目标约束到语言到框架到部署，每层五到九个候选，每个候选明说缺陷，选完调和冲突。它不替你拍板，它把拍板需要的信息摆齐。

## 跟 superpowers 和 spec-kit 的关系

superpowers 是方法论的重要来源，这个 skill 的 depends/ 目录存了它全部 12 个相关 skill 的原文快照，MIT 协议，版本锚定同一个 commit。改造方向见下表。

| superpowers、spec-kit | Cao-交付流水线 |
|---|---|
| 英文方法论，工作流分散在 15 个 skill 里 | 中文一体化十二步索引，步与步的产出接原料写死 |
| 执行重头跑 | 台账三区制，任何会话任何时刻接续 |
| 面向从零到 PR 合并 | 跳步优化，已有项目缺哪步跑哪步 |
| 依赖先搭好框架环境 | 46 个文件自包含，20 份原文副本加 16 个附属模板，复制即用 |
| 验收是测试要写 | 验收先于实现，测试框架都没有的毕业项目也能用 |

## 什么时候不用

改一两行的小修补，直接改。纯探索的 demo，明天可能全推翻的那种，台账和卡文件制是给要交付的东西准备的。连肉眼清单都不愿意定的项目，验收先于实现会卡在第一步，这是故意的。

## 目前到哪了

v1.0 到 v1.1。副本体系全量校验，69 处互引零失效。期间抓掉一个问题，CDN 缓存的旧版和仓库 main 有漂移，三个附属文件在真实仓库已改名，改用 GitHub API 以固定 commit 重拉解决。这套自检流程自己就是按流水线纪律跑的。
