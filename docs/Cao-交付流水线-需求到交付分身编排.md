# Cao-交付流水线（delivery-pipeline v1.1.0）

> [← 返回总目录](../README.md#skills-index)

让 AI 做个项目，它热火朝天干了两小时。你回头一看，写到哪了，不知道。做完了什么，说不清。中途会话断了想接着来，从头开始。最尴尬的是验收，它说完成了，你问怎么验证的，没有验证这回事。

翻回去找原因，一般是三件事没做。没有设计就开写，聊两句就动手，方向错了返工三轮。计划是一个巨型文件，所有任务塞一个 plan.md，AI 读一半丢一半。每一步都不留产出物，这步的输出没落盘，下步的输入就没了。

这个 skill 是一条十二步的总装流水线，磨设计、选型、PRD、切卡、分身执行、验收、台账、收尾。方法论站在 obra/superpowers 的肩上，磨设计的对话方式、切卡的实习生粒度、双评审都是从它那来的，在这个基础上做了完整的中文化和工程化改造。

## 四个设计

**台账即断点存档。** 在做、待执行、做完加阻塞，三区制，每张卡完成立即勾。启动第一件事是查台账，问你是继续上次从第 N 张卡接着来，还是开新的。你不需要向新会话解释我们做到哪了。

**验收先于实现。** 每张卡开工之前，怎么验证必须已经写清楚。评测基线、测试脚本、肉眼清单，形式不限，但必须写在卡里。这是铁律。它的好处在收尾时最明显，AI 说完成了的时候，验证动作早就摆在那了。

**一卡一文件。** 每张任务卡是独立的文件，不许塞进单个巨型计划文件。派子代理执行时只喂三样东西，该卡、PRD 的相关段落、精确文件路径。绝不喂全项目历史，token 花在活上，不花在噪音上。

**按需加载。** 主 SKILL.md 永远只有八十行，十二步索引是指针不是正文。进哪一步才读哪一步的细则，一次只读一个。流水线自己得先守省 token 的纪律，才有资格管别人。

## 上手时的样子

启动时它先问四个问题，给推荐让你选。轻量档，小改动五步走。标准档，新功能九步。企业档，全十二步加双评审。跳步优化档，已有项目先扫短板，缺哪步补哪步。

跳步档值得多说一句。大多数流水线类工具默认你从零开始，可现实里最常见的诉求是手里已经有个项目，只想补某个环节。这里可以单步直调，你说帮我切卡，它直接进步⑤，不逼你从头跑。

选型阶段是分层深选。从目标约束到语言到框架到部署，每层五到九个候选，每个候选明说缺陷，选完再调和冲突。它不替你拍板，它把拍板需要的信息摆齐。

## 跟 superpowers 和 spec-kit 的关系

先说清楚，superpowers 是这套方法论的重要来源。这个 skill 的 depends/ 目录里存着它全部 12 个相关 skill 的原文快照，MIT 协议，版本锚定在同一个 commit。下面是改造方向。

| superpowers、spec-kit | Cao-交付流水线 |
|---|---|
| 英文方法论，工作流分散在 15 个 skill 里 | 中文一体化十二步索引，步与步的产出接原料写死 |
| 执行要么子代理要么单会话，重头跑 | 台账三区制，任何会话任何时刻接续 |
| 面向从零到 PR 合并 | 跳步优化模式，已有项目缺哪步跑哪步 |
| 依赖先搭好它的框架环境 | 46 个文件自包含，20 份方法论原文副本加 16 个附属模板，复制即用 |
| 验收是测试要写 | 验收先于实现，开工前基线就绪，测试框架都没有的毕业项目也能用 |

## 什么时候不用

改一两行的小修补，直接改，杀鸡别用牛刀。纯探索的 demo，明天可能全推翻那种，台账和卡文件制是给要交付的东西准备的。连肉眼清单都不愿意定的项目，验收先于实现会卡在第一步，这是故意的。

## 目前到哪了

v1.0 到 v1.1。副本体系经过全量校验，69 处互引零失效。期间抓出并修掉一个问题，CDN 缓存的旧版和仓库 main 有漂移，三个附属文件在真实仓库里已经改名，改用 GitHub API 以固定 commit 重拉了解决。这套自检流程自己就是按流水线纪律跑的。
