# 企业级交付差距审判官（四层门槛 + 三态证据 + 施工路线）

> 一句话：像最挑剔的企业采购一样审判项目——**它能不能直接交给企业真实业务用？差哪些？先补哪个？要多久？**
> 产出：一份落盘的《企业级交付差距报告》：四层门槛判定 + 逐项差距（每条带三态证据）+ 风险排序 + 分阶段施工路线。
> **本文件是流程入口**，只放判据框架与取证口径。行业判据、探针命令清单、外部标准映射、报告模板全在 `references/`，按 §9 路由表按需读取——不必通读。

---

## 0. 审判官七条军规（先读，凌驾于一切效率考量）

1. **回代码取证，禁止照抄文档待办**。文档里的"待办清单"是**时间快照**，只有代码是**现状**。每一句"XX 未做/已做"都必须有 `文件:行号` 或命令原始输出支撑。这是本 skill 存在的第一理由（§0.1）。

2. **只审判，不施工**。发现差距一律记录进报告，**禁止顺手改代码把它"补上"让报告好看**。用户明确说"审判+施工"时除外，且施工另立步骤、单独留证据。

3. **区分「做不到」与「不需要」**。四层门槛里，第二层多数靠客户给料、第三层一半是资质与运维组织——不是代码问题。报告必须把这类明确标出，而不是笼统列成"待办"。

4. **证据只有三态：已验证 / 未找到 / 未验证**（细则 §2）。`grep` 无结果只能得**未找到**，永远得不来「未实现」；配置文本在场只能得**未验证**，永远得不来「已生效」。绝不脑补数字，也绝不把"我没查"写成"它没有"。与 `A-Cao-抗幻觉纪律`、`A-Cao-测试纪律` 同源执行。

5. **外部判据必须联网取，且五要素齐全**：来源（机构 + 报告名/标准名 + **版本号或标准年号**）／发布日期／我方检索日期／适用范围／可信度。缺任一要素就写「未采到」，**不编、不用训练记忆里的"我印象中是"顶包**（模型知识有截止日、会记错版本号）。

6. **区分「行业普遍状况」与「本项目的差距」**。"90% 企业做不到 X" 是行业背景，只有本项目探针同样缺 X 时才写成"本项目的差距"。**行业数据用来定严重度，代码探针用来定有无**——两把尺子不可混用。

7. **存在 ≠ 生效**。任何"文件里写了 / 代码里有 / 端点定义了"都要过 §2.4 的三步（加载确认 → 目标部署版本确认 → 运行行为观察），缺任一步只能记**未验证**。

### 0.1 军规 1 的由来（30 秒版）

2026-10-08 实战复盘：初版差距清单照抄项目旧文档的"待办表述"列出 8 项"现在就该做"，回代码逐项核实后发现 **8 项里 5 项早已完成**——那份文档自己头部就写着「已全部处置」。**正确姿势：文档的"待办"只用来生成假设，代码用来验证假设。** 完整复盘与八类误判对照见 `references/probe-library.md` §七。

## 1. 四层交付门槛模型（纵向判据：本项目能走到哪一层）

**核心认知（必须在报告开头讲清，这是本 skill 的灵魂）**：

> **"企业级"不是一条线，是四道门槛，每道门槛考的东西完全不同。**
> 所以不要笼统说"还差得远"——要说清楚"差在哪一层、那一层考什么、谁决定能不能过"。

| 层 | 门槛性质 | 谁决定能不能过 | 典型判据 |
|---|---|---|---|
| **第一层：演示与试用** | 工程能力 | **项目方自己** | 能跑通全流程、公网可访问、有操作文档、测试绿 |
| **第二层：单企业内部试点** | 外部资源 | **客户给不给** | 真实数据样本、企业系统对接（ERP/银行）、真实 ROI 数字、客户身份体系 |
| **第三层：正式生产（每天在用）** | 运维 + 资质 | **组织能力，不是代码** | 并发与高可用、监控告警、合规资质（等保等）、备份恢复演练、故障响应 SLA |
| **第四层：多客户 SaaS** | 商业模式 | 需要才做 | 多租户隔离、计费、多可用区 |

**判定纪律**：
- 每层给明确结论：✅已过 / 🔶部分 / 🔴未过 / ⬜不适用。**「⬜不适用」是范围判断（这层根本不该做），不是证据态**，不许拿它顶替「未找到」或「未验证」。
- **层结论由该层各判据的三态汇总而来**：该层只要有一项落在「未验证」，这一层就**不得判 ✅已过**（只能 🔶部分，并写明缺哪一步）；有一项「未找到」则必须同时给出 §2.3 的三件套，否则报告不成立。
- 第二层要特别标注"哪几项靠客户给"；第三层要特别标注"哪几项不是代码问题"（资质、SLA）——这是本 skill 最有价值的判断。

## 2. 证据三态制（本 skill 的取证口径，最高优先）

### 2.1 三态定义（只有这三个态，第四个都不许造）

| 态 | 什么时候用它 | 必须记录 | 禁止写成 |
|---|---|---|---|
| ✅ **已验证** | 有一手证据直接支撑结论：代码行、命令原始输出、运行观察、书面材料 | 证据位置（`文件:行号` 或 命令+原始输出片段）+ 取证时间 | — |
| ✅**已验证（范围受限）** | 能力确实存在，但只覆盖部分场景/部分数据/部分环境 | 覆盖到哪、没覆盖到哪、边界怎么来的 | 写成不打折的「已实现」 |
| ❓ **未找到** | 按规定范围检索后没拿到证据。**这只说明"我没搜到"**，不说明它不存在 | §2.3 三件套（搜索范围／关键词／未检查范围） | **「未实现」「没有这个能力」「缺失」** |
| ⬜ **未验证** | 有线索但证据不足以支撑结论：配置文本在场、注释里提到、端点定义了但没采样点、依赖装了但没配 | 已有线索 + 缺哪一步 + 补验证需要什么 | **「已做」「已生效」「已配置」** |

### 2.2 能力可能藏身的六个位置（要下「未实现」就得先走完六处）

静态搜索不是最终证明。同一项业务能力有六种常见落点，**只搜第 1 处就判"未做"是本 skill 原先最大的方法缺陷**：

| # | 位置 | 典型形态 | 怎么查 |
|---|---|---|---|
| 1 | **本仓库源码内联实现** | 自己写的函数/类 | `grep -rn` 源码根 |
| 2 | **依赖库自带** | `tenacity`/`urllib3 Retry`/`resilience4j`、校验库、认证库 | 读依赖清单（`requirements*.txt`/`pyproject.toml`/`package.json`/锁文件）+ 该库官方能力页 |
| 3 | **框架/平台内建** | Web 框架自带会话与 CSRF、数据库自带约束与超时、云服务的限流与压缩 | 查所用框架/中间件**版本号**与默认行为（要看版本，默认值会变） |
| 4 | **代理层/网关/中间件** | 鉴权、限流、重试、压缩、缓存配在 nginx / API 网关 / service mesh / LB | 查**部署目录与基础设施配置**，不是查应用源码 |
| 5 | **动态配置与运行时数据** | 配置中心、数据库参数表、环境变量、feature flag、ERP 侧配置 | 查**运行环境的实际值**，仓库里的默认值不代表线上 |
| 6 | **生成代码与构建产物** | migration 生成的 schema、脚手架产物、IaC、镜像内文件 | 查构建产物/部署清单/镜像，而非源码 |

**规则**：六处都查过且无痕迹，才允许写「**未实现（在本报告检查范围内）**」，并且必须留一句翻案条件——例如"若客户侧 ERP 已提供审批流，本结论作废"。剩下任何一处没查，结论只能是 ❓未找到。

**🔴 同一能力两种实现给同一个业务判断**（这是外部审查给的验收题，也是本条的核心）：
"失败重试"这项能力，A 项目写在应用代码里（`for attempt in range(3)` + `sleep`），B 项目来自依赖（`tenacity` 装饰器）或网关配置（nginx `proxy_next_upstream`）。审判结论两句都是"**具备重试能力；待查退避策略、最大次数与幂等性**"——**不许因为"没在 B 项目源码里搜到 retry 字样"就把它判成未实现**。判据是业务能力，不是关键词命中。

### 2.3 「未找到」必须带的三件套（写不出来就不许用这个态）

```
| 判据项 | 搜索范围（查了哪些目录/文件类型/依赖清单/部署件） | 关键词（全部，含中英同义词与常见别名与库名） | 未检查范围（跳过了什么、为什么） | 下一步要怎样才能查到 |
```

- **搜索范围**要具体到能复跑（`backend/app/`、`deploy/`、`requirements.txt`），不写"全项目"。
- **关键词**要能自证不是搜错词：至少给中英两组 + 该项能力在主流库/框架里的常见名字（如 retry / backoff / 重试 / 退避）。
- **未检查范围**要对齐 §2.2 里还没查的位置，并写明阻碍（无访问权限／需要真实环境／需要客户提供）。

### 2.4 存在 ≠ 生效（三步确认，缺任一只能记「未验证」）

| 步 | 要确认什么 | 取证方式举例 |
|---|---|---|
| 1 **加载确认** | 这份配置**真的被运行时读到了** | 进程启动参数（`-c` / `--config`）、`include` 指令链是否指向该文件、环境变量是否指向该路径、**实际部署里这个文件在不在**（不是仓库里在不在） |
| 2 **目标部署版本确认** | 跑着的**就是含这条配置的那个版本** | 镜像 tag / 构建号 / `git rev-parse HEAD` ↔ 发布记录对账；容器内文件哈希与仓库比对 |
| 3 **运行行为观察** | 外部或内部**看得到行为变化** | 带 `Accept-Encoding: gzip` 发一次请求看响应头有没有 `Content-Encoding: gzip`；指标曲线变化；日志出现该路径的执行痕迹 |

**同构陷阱四条**（同一个错误的四张脸，v1.2.0 前本 skill 自己犯过）：
- 配置文件里有 `gzip on;`（未注释）≠ 已生效 → 差三步
- 代码里有函数定义、没有调用点 ≠ 已实现该行为 → 差调用链
- 定义了 `/api/metrics` 端点 ≠ 有数据 → 差采样点是否在链上
- 有测试文件 ≠ 测试被执行过 → 差运行记录或 CI 记录

> 🔴 **订正声明**：本 skill v1.1.1 及更早的主文与探针库里写过"命中 `gzip on;` 行首无 `#` ⇒ 已生效"。**那句话是错的**——未注释的配置行最多证明"这行文本在文件里"。v1.2.0 起改为上表三步，旧表述已在 `references/probe-library.md` 同步订正。

## 3. 探针取证五步

```
1. 定假设  —— 从文档/经验生成"它可能没做 X"的假设；同时默认 X 可能藏在 §2.2 六处之一
2. 写探针  —— 设计能证实或证伪的命令（先想清楚"什么输出算已验证、什么算未找到"）
3. 跑探针  —— 实际执行，原始输出落盘（只报总结数字不算证据）
4. 判读    —— 按 §2.1 三态下结论；配置/部署类判据再过 §2.4 三步
5. 记账    —— 已验证→证据位置；未找到→§2.3 三件套；未验证→缺哪一步
```

**探针命令清单不在本文件**：通用形态见 `references/probe-library.md` §二，组合取证链 §三，**六个藏身位逐处探针 §四（下「未实现」前必走）**，业务场景探针 §五，联网探针 §六，反面案例集 §七。**按项目技术栈改写，不要照抄**（路径、后缀、关键词都要按实际调）。

## 4. 联网取证（外部判据：本项目"没有的"同行有没有？法规要不要？）

> 探针看"本项目现状"，联网看"外部要求"。只有探针 ⇒ 不知道这件事有多要紧；只有联网 ⇒ 不知道自己中没中招。

### 4.1 三条固定检索线（每次审判必跑）

| 线 | 检索什么 | 落进报告哪一节 |
|---|---|---|
| **① 法规/标准线** | 该项目品类的最新合规要求与生效时间（含标准号与年号） | §三 合规阻塞 |
| **② 竞品功能线** | 同赛道玩家的**业务功能清单**（做什么能力、集成什么系统、持有什么认证） | §五 竞品对照 |
| **③ 失败案例线** | 该品类真实落地失败/翻车原因（为什么试点变不了生产） | §六 场景判别 + §七 施工路线"坑"栏 |

### 4.2 五条判读铁律

1. **外部数据只能定严重度，不能定有无**（"行业 90% 缺 X" ≠ "本项目缺 X"）。
2. **五要素齐全**：来源＋版本/年号＋发布日期＋检索日期＋适用范围，再加可信度档位（一手／二手／未采到）。**无来源的外部数字一律不进报告**。
3. **凡引用标准/框架必须带版本号**：写"OWASP ASVS"要写成 `OWASP ASVS 5.0.0`（或当时核实到的版本），写"等保"要写标准号年号。版本一变，条款号与判据一起变。
4. **优先一手来源**：法规查官方原文，标准查正文/官方仓库，竞品查官网功能页与第三方评测（G2/Capterra），**不采信二手转述**；引不到原文就标 `二手`。
5. **检索不到就写检索不到**，并注明用了哪些检索词——**绝不用模糊记忆冒充检索结果**。

### 4.3 外部判据锚与标准映射

**一手锚可查的**（ASVS 的 Web 安全映射、NIST AI RMF 的 AI 风险治理映射、等保/ISO 27001/SOC 2/EU AI Act 时间线）每条都带**版本号或标准年号 + 发布机构 + 是否强制 + 适用范围 + 可证实性档位**（✅本窗直读一手／🟡检索所得待复核／⚠️无一手锚）。**一手锚采不到的**（Production Safety Framework 的"八域 32 控制"、七个生产就绪门、五域评估）在同一个文件里已被**降级为提问清单**——只用来提醒"该问什么"，**禁止写成"本项目符合/不符合某框架"**，也禁止拿去给项目打分。

**主文只留一句使用纪律**：**这些框架是"该问什么"的提问清单，不是合规声明**。没读过某框架正文就不要声称"本项目符合它"；符合与否只能由 §2 三态证据决定。

## 5. 审判执行流程（八步）

> **全局顺序**：认路 → 初判 → 联网取尺子 → 代码取证 → 场景判别 → 打标签 → 风险排序 → 落盘复检
> **关键**：Step 3（联网）在 Step 4（探针）**之前**——先知道外面要求什么，探针才知道重点查什么。

**Step 1 · 项目画像**：技术栈、规模（代码量/测试数）、部署形态；找出项目**自己已声明的边界**（如 README「当前栈是演示规模的最适配解」——这是诚实的证据，要在报告里肯定）；记 `git rev-parse HEAD` 与工作区在途数；记项目品类（决定 Step 3 搜什么、有没有对应行业包）。

**Step 2 · 四层门槛初判**：按 §1 给四层初始判定，此时允许粗判，Step 4 逐项证实。

**Step 3 · 联网取尺子**：跑 §4.1 三条线 → 产出「外部要求清单」（五要素齐全）+「竞品功能对照表」半成品（本项目列留空待 Step 4 填）；同时按 §4.3 核对本品类该参考哪几个框架锚。

**Step 4 · 逐项探针取证**（最耗时也最值钱）：
1. 生成假设（默认"可能没做"，且默认能力可能藏在 §2.2 六处之一）
2. 设计探针 → 执行 → 原始输出落盘
3. 按 §2.1 三态判读；配置/部署类判据过 §2.4 三步；未找到的记 §2.3 三件套
4. **必须覆盖的维度**（按层展开，按项目实际裁剪）：
   - 第一层：跑通性、可访问性、文档完备度、测试状态（**测试文件在 ≠ 跑过**）
   - 第二层：真实数据 vs 合成数据／对接的是通用替身还是客户真实系统／商业数字是实测还是折算／身份体系是白名单还是企业 IdP／**有没有改前改后基线**
   - 第三层：并发与状态存哪／数据层与迁移成本／可观测（有指标端点？有告警？失败只有开发者能解释吗）／合规资质（等保？数据出境？SOC 2？按版本年号登记）／运维（备份演练？SLA？能回滚？）／**韧性**（外部依赖挂了有没有超时/重试/降级——注意重试可能来自依赖库或网关）
   - 第四层：多租户、计费、多可用区（多数项目应判"明确不做"）
5. 收尾：把 Step 3 的竞品对照表补齐"本项目"列。

**Step 5 · 业务场景贴合度判别**：有行业包 → 按包的判别清单逐条跑（AP 类见 `references/industry-ap-finance.md` §一 七条）；无行业包 → 用 §4.4 通用四问。这一步回答"跑得通 ≠ 用得上"。

**Step 6 · 区分「做不到」与「不需要」**：每项差距打标签——🧩 能力问题（项目方能解）／🤝 资源问题（要客户给）／🏛️ 资质问题（要认证与组织）／⬜ 目标不匹配（明确不需要）。**打 ⬜ 必须写理由**（如"竞品面向跨国企业，本项目面向国内中小企业，不需要 196 国支付通道"）。这一标签是报告的灵魂：它把"我还不够好"转成"我知道差什么、也知道缺的那部分不是我写代码能补的"。

**Step 7 · 风险排序 + 施工路线（两轴，不许混）**

- **第一轴＝风险**：`风险 = 影响 × 发生可能性 × 暴露范围`，三个因子各取 1–3 档，乘积分级：

  | 因子 | 1 档 | 2 档 | 3 档 |
  |---|---|---|---|
  | **影响**（一旦发生后果多重） | 可容忍（体验下降、可事后补） | 明显损失（人工兜底、交付延迟、数据需返工） | 严重（资金/合规/客户数据事故，或不可逆的错误动作） |
  | **发生可能性**（当前使用强度下多快会碰到） | 罕见（需异常输入或极端负载） | 周期性（每周/每月碰到） | 常态（日常流程每天经过） |
  | **暴露范围**（波及多广） | 单人/单模块 | 单企业内多部门 | 多客户／对外接口／不可逆写入面 |

  乘积 ≥18 ⇒ **P0**，9–17 ⇒ **P1**，≤8 ⇒ **P2**。**每档取值必须写依据**（一句话即可：来自哪条探针证据或哪条外部判据）；**写不出依据就记「未评估」，不许凭感觉给 3**。判据来自"未找到/未验证"的项，风险分只能标注为「下限估计（证据不全）」。
- **第二轴＝施工便利性**：① 不依赖外部资源的先做 ② 能对外讲清价值的先做 ③ 需客户配合的往后排。
- **两轴冲突时分别写清**："风险最大的是 X（哪怕它要等客户给料），现在最先能动手的是 Y"。**禁止把便利性排序冒充成风险排序。**
- 阶段划分照旧：**阶段一 现在就能做**（不依赖外部）／**阶段二 有第一个真实客户后**／**阶段三 规模与合规**（按需）。每项给：动作 + 验收标准 + 工作量量级 + 坑（坑必须结合 Step 3 失败案例线）。

**Step 8 · 落盘 + 复检**（三条机械检查，一条不过就回炉）：
- 所有「已验证」结论都能指向 `文件:行号` 或原始输出 → 否则回 Step 4
- 所有「未实现／未做」字样：核对 §2.2 六处是否全部走完且留了翻案条件 → 否则降级为「未找到」并补三件套
- 所有「已生效／已配置」字样：核对 §2.4 三步是否有两步以上证据 → 否则降级为「未验证」
- 所有外部判据五要素齐全 → 否则回 Step 3 或标 `未采到`
- 报告落盘后**必须回读一遍**（回读＝重新打开文件读，不是"我记得写了"）

## 6. 报告骨架（十一节；完整填空模板与落盘检查清单见 `references/report-template.md`）

```
零、总判断（一句话结论 + 四层判定表 + 关键洞察 1-3 条）
一、第一层 演示与试用
二、第二层 单企业内部试点（逐项：三态证据 + 怎么做 + 验收 + 工作量 + 坑 + 标签）
三、第三层 正式生产（硬阻塞 / 合规阻塞 / 运维阻塞 分列）

六、业务场景贴合度判别（行业包清单或通用四问）
七、分阶段施工路线（风险三因子表 + 便利性第二轴，两轴分开写）
八、差距话术（可直接用于汇报/面试）
九、自测题
十、证据索引（主张 | 三态 | 证据位置 | 搜索范围/关键词/未检查范围 | 来源五要素）
十一、诚实声明（判据截止与代码基线 / 检索清单 / 未找到项 / 未验证项 / 本报告不是施工令）
```

## 7. 输出纪律

1. **报告必须落盘**，不能只在对话里讲。路径默认 `<项目文档目录>/企业级交付差距报告-YYYYMMDD.md`，或用户指定。
2. **每条结论带三态之一**，没有证据的结论宁可不放。
3. **状态有时间戳**。报告头部写「判据截止 YYYY-MM-DD HH:MM」+ 代码基线 sha——代码会变，这份报告是快照。
4. **不承诺工期**。工作量写量级（如"2-3 天"），注明"为估量级，非承诺值"。
5. **对外数字受项目自身口径约束**（若项目有《对外数字口径表》等唯一数字源，一律以其为准）。
6. **外部判据五要素随文带上**（来源/版本/发布日/检索日/适用范围），并给可信度档位。**无来源的外部数字一律不写进报告。**
7. **「未找到」要让读者看得出你搜了什么、没搜什么**（§2.3 三件套进证据索引表）。
8. **联网检索清单留在报告 §十一**（实际执行的检索词 + 采用来源），让人能复核"外面的尺子是哪天量的"。

## 8. 与其他 skill 的分工

| skill | 管的范围 | 与本 skill 的分工 |
|---|---|---|
| **Cao-项目验收官** | 「现在质量合不合格」 | 验收官是**体检**（这个功能对不对、有没有 bug）；本 skill 是**差距地图**（离企业级还差哪些路 + 施工路线） |
| **Cao-评审计划（plan-review）** | 「这份计划能不能开工」 | 🔴 **对象不同**：plan-review 审**尚未实施的方案/计划**（承诺—机制—验收是否对应、阻塞项解除条件）；本 skill 审**已经存在的代码资产**离企业级交付差什么。同一份材料既可被两者审时，先 plan-review（能不能开工）后本 skill（开完工还差多少） |
| **Cao-交付流水线** | 「从需求到交付的过程管理」 | 本 skill 出的分阶段路线可以喂给流水线的阶段表；流水线管执行，本 skill 只审判不施工（军规 2） |
| **A-Cao-抗幻觉纪律** | 结论必须可证伪 | 本 skill 军规 1/4/5 与其同源；§2 三态就是它在"审计场景"的落地形态 |
| **A-Cao-测试纪律** | 测试证据形态 | 报告里任何"测试绿/跑过"的表述按测试纪律的证据长样落盘（原始输出、改前改后各跑一次） |
| **A-Cao-资深工程师五模板** | 构建/审查/根因/架构/计划 | 本 skill 出的施工路线，真正动手时按五模板对应模式执行 |
| **WebSearch / WebFetch（工具）** | 联网外部判据 | §4 定义"搜什么、怎么判、怎么落进报告"，工具只负责执行 |

**协同建议**：先跑**项目验收官**（确认现状质量），再跑**本 skill**（判差距与路线），两者证据可互相复用。

## 10. 一句话升格为「含联网的全量审判」

用户说以下任何一句，**直接跑 Step 3 联网 + 全八步**（不许只跑探针就交报告）：

- 「联网看看我们和竞品差什么」
- 「查查最新要求，我们还差哪些」
- 「同行业都做到哪一步了」
- 「这项目放到市场上算能交付吗」

**执行**：§4.1 三条线 → §4.3 核对框架锚 → 按 §4.2 五要素落表 → 合进报告 §五/§六/§七。
