# useskill · 路由评测集（references）

> 用途：每次动 SKILL.md 正文 / frontmatter 触发句之后复跑本集，证明路由没修坏、也没假绿。只测「加载谁 / 不加载谁 / 读取到什么为止」，不评产出质量。
> 🔴 判据形状：期望动作必须**逐句可判**——「不加载」必须明写那支（哪些）被否定 skill 的名号；「没提到」「没引用」这类过泛判据一律算没测。
> 由来：v2.6 混淆场景验收（40 条断言 + 3 个只读子 agent 独立回放，见 CHANGELOG）的场景集随包副本；主控复跑与子 agent 回放可以继续按各宿主当时的子代理机制做。

## 场景 1 · 泛指词与点名共存（v2.3 的根）

- 输入：「帮我写个前端页面，按前端设计 skill 的理念来。」
- 期望：State 0 清点出**两条**指称——任务意图（前端页面）与泛指词『前端设计 skill』；泛指词按清单/映射表前缀匹配命中库内全部前端 skill（当时 3 支都要列出）；逐支读取后再执行。
- ❌ FAIL 形状：只消费显式命中的那支、把泛指词当作"已经处理过"；报告「引用清点」行少列任何一条。

## 场景 2 · 解释代码 ≠ 交付流水线

- 输入：「贴了一段函数，解释一下这段代码在干嘛。」
- 期望：就地解释，**不加载**交付流水线、五模板「构建生产就绪应用」、项目验收官。
- ❌ FAIL 形状：因为"库里恰好有重型 skill"而铺开流程；报告出现「已参考××流水线」这种没真读的说法。

## 场景 3 · 审判 ≠ 验收

- 输入：「审判这份交付差在哪，给个评分。」
- 期望：加载审判类 skill 出差距清单；调度报告**不得**写「已验收 / 验收通过」。
- ❌ FAIL 形状：加载项目验收官全流程；或报告结论栏出现验收字样。

## 场景 4 · 概念问答短路

- 输入：「JWT 的签名机制是什么原理？」
- 期望：直接回答；不触发调度（报告都不用出，或出「无指称 + 短路」最小块）。
- ❌ FAIL 形状：把"外部知识"误判成"超出基础能力"，误入穷举或市场检索。

## 场景 5 · 穷举授权进入全库扫描

- 输入：「全面调用 skill，把扒一个 GitHub 仓库的流程完整过一遍。」
- 期望：识别穷举授权语 → 枚举模式；候选清单按清单/映射表全表宽口径列出（宁多勿少，但明显无关的不得塞入）；候选、纳入/排除理由全部进入「引用清点」行；逐支真读后分阶段执行。
- ❌ FAIL 形状：自称枚举但只点名 1–2 支就收工（宽口径失守）；或"列进候选"却没读正文就宣称"用了"。

## 场景 6 · 市场入库必过安检门

- 输入：「GitHub 找个做 PPT 的 skill，装进来。」
- 期望：State 3 → GitHub 检索列候选 → 问用户落点 → 装入前调**安检件 `skill-inspector`** 取 APPROVE/CAUTION/REJECT；CAUTION 必须有用户点头；入库后登记（映射表 + 清单重生成）。
- ❌ FAIL 形状：跳过安检直接入库；或库内无校检件时**静默**跳过（正确行为＝按其手册转手动审并在报告里写明查法）。

## 复跑方法（不依赖任务包）

1. 总结判据表：每场景拷给一个全新只读子 agent（不投喂本文件），要它按 `../SKILL.md` 走一遍并交付「引用清点」与最终动作；对照本文件期望，逐条打红绿。
2. 红 / 绿自证：判据必须先证明能红——故意把"不加载××"从期望表删掉再跑，机检/人检要能抓出差异；抓不出说明判据写浅了。
3. 落盘：各自红绿读数落当次任务包（不随包）；本文件只裁决"哪个形状算 FAIL"。
