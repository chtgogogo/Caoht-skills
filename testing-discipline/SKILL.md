# 测试纪律（证据形态规范）

> **本 skill 的定位**：它不教"怎么写测试"，它规定"**测试的证据长什么样才算数**"。
> 它是《抗幻觉与批判性验证准则》第 3 条（"外部证据优先，形成验证闭环 → 记录命令/环境/输入/输出"）的**执行细则**，与 `coding-behavior`（编码行为准则）第 5 条"验证纪律"、第 7 条"证明优先"配套使用。
>
> **一句话**：**跑不跑不是重点，能不能拿出原始输出才是重点。**
>
> **交付单位**：一次执行 = 一份最小运行记录（第一节铁律 6，七字段）+ 对应类别的证据清单（第七节）。只贴汇总行不交记录，算半份证据。
>
> **本机适配**：若本技能目录存在 `personal.local.md`，读取它并按其中的值覆盖本文件的默认路径 / 盘符 / 偏好；
> 不存在则按本文件写的通用默认值走——缺这个文件不是错误，不要因此停下来询问。

## 一、核心铁律（六条，缺一即视为未验证）

### 铁律 1 · 输出必须落盘

```bash
# 正确：重定向到文件，文件名带日期与阶段
python -m pytest tests -q > evidence/pytest_after_20260924.txt 2>&1
```
- 报告里写的是**文件路径**，不是转录的数字。
- **禁止**只写"跑完了，396 passed"这类总结而无原文。
- **禁止**把上一次的结果文件复制成这一次的（哪怕数字本该相同）——要么重跑，要么在报告里明说"沿用 X 月 X 日的结果，本次未重跑"。

### 铁律 2 · 改前改后各一次（红-绿对照）

任何"修复/优化"类改动，必须有两份输出：

| 阶段 | 要求 | 作用 |
|---|---|---|
| 改之前 | 跑一次，存 `*_before_<date>.txt` | 证明**问题真实存在**（红） |
| 改之后 | 跑一次，存 `*_after_<date>.txt` | 证明**改动确实生效**（绿） |

- 只有"改后"一份 → **无法证明改动解决了问题**，只能证明"现在是这样"。
- 两份数字**完全相同也是有效结论**（说明该改动不影响这条路径），但**必须真的跑过**才能这么说。

**四类场景下「改前那一份」分别从哪来**——一刀切要求"改前改后都跑"，在新项目、跑不起来的旧版本、纯文档改动、紧急修复四类里都会失真：

| 场景 | 改前那份怎么取 | 取不到时的合法写法 |
|---|---|---|
| **新项目 / 新写的测试** | 在功能尚未实现（或改动尚未落地）的状态下先跑一遍新测试，它必须红 | 改动已落地：把代码退回改动前的提交（检出到副本目录）再跑；仍取不到 → 按下一行走"基线不可用" |
| **旧版本跑不起来**（依赖失效、数据集流失、环境重建后无法复现） | 只能拿到"改后"这一份 | 记「基线不可用：缺 X（依赖 / 数据 / 环境），改前状态无法复现」；结论只许写「当前满足 Y」，不许写「提升了 Z」 |
| **文档 / 配置修改**（没有可执行的测试基线） | 本就不存在测试意义上的改前 | 证据换成可观察的等价物：链接检查、示例命令实跑、渲染或 lint 输出、仓库体检退出码；报告里写明「本次为文档/配置改动，无测试基线」 |
| **紧急修复（先止血）** | 允许先交付、后补对照 | 允许改前那份暂缺，但报告首行必须标「缺改前对照，原因：紧急止血」并另立一条补测待办；缺就是缺，不许让它读起来像做过 |

🔴 **「基线不可用及原因」是一份合法记录；补写一份不存在的前测结果是伪造。** 这份记录必须给三件：① 不可用的具体原因（少了什么、为什么补不回来）② 结论因此被降级成哪一档（现状快照／方向性观察／未测）③ 什么条件下能补上对照。三件缺一，别人就分不清"没跑"是客观限制还是偷懒。

### 铁律 3 · 报指标必须给总体输出行

- 报百分比 / 命中率 / F1，必须同时贴出产生它的**原始汇总行**（如 `396 passed, 2 skipped, 0 failed in 167.44s`）。
- 禁止只报手抄进表格的百分比，而不给产生这个百分比的那行输出。
- 表格里的每个数字，要能追溯到**某一行的原始输出**。
- 🔴 **汇总行只证明"这一次运行结束了"，不证明业务指标提升。** 要声称"提升了"，除了产生它的原始行，还要另给三件：指标定义与分母口径、数据来源（哪个数据集、哪次运行）、项目若维护唯一口径表（例：`docs/numbers.md`）则指向它并说明是否已同步。三类检查（正确性／性能／模型效果）各自的证据要求见第四节——**只有正确性检查允许拿"全过了"当结论**。

### 铁律 4 · 改断言必须分类声明

修复导致既有断言需要改动时，必须区分两类并显式标注：

| 类型 | 含义 | 要求 |
|---|---|---|
| **A · 口径重算** | 行为语义变了，期望值按新语义同步更新 | 说明"哪条语义变了 → 期望值从多少改到多少" |
| **B · 断言弱化** | 把强断言放松（如 `==` 改 `<=`）以适配新行为 | **必须单独列出并给理由**，不得混在 A 里一笔带过 |

> **弱化断言本身不是错，藏起来才是。** 主动写明"我把等式断言降级为不等式，因为……"是专业动作。

### 铁律 5 · 回归测试要能失败

新增的测试，如果是用来证明"某个 bug 已修复"，必须能回答：**修复前它会红吗？**

- **能**：在改前那份输出里指出它（红）→ 这才是**回归证据**。
- **不能 / 未验证**：必须在报告里标注"**本次测试是现状快照，非回归证据**"。
- ⚠️ **警惕反向工程**：先跑出结果、再把结果抄进断言（`assert total == 40.0` 里的 `40.0` 就是跑出来的），这种测试**只能防止未来改坏，不能证明当初修对了**。要区分"它现在通过"和"它曾经失败"。

### 铁律 6 · 每次执行留一份最小运行记录（七字段）

铁律 1～5 管的是"结果输出"，本条管的是"这次运行本身"——没有它，别人拿到你的原始输出也不知道是在什么状态下跑出来的。七个字段缺一个，这份证据只能算半份：

| # | 字段 | 必须具体到什么程度 | 为什么 |
|---|---|---|---|
| 1 | **代码版本** | 版本库：完整提交号（40 位）＋工作区是否干净（`git status --porcelain` 有无输出，脏就写 dirty=true）；无版本库：被测文件的 sha256 前 12 位 | 只说"改后"不说"哪个改后"，别人回不到同一状态 |
| 2 | **命令** | 真正跑通的那一条，逐字粘贴（解释器＋参数＋被跑对象＋重定向目标） | 换参数＝换测试；"我跑了 pytest"不等于跑的是同一批用例 |
| 3 | **环境** | OS 与版本、解释器**绝对路径＋版本**、关键依赖版本（lockfile 哈希或依赖清单）、并发与硬件设置（性能类必填） | 同一台机器上 `python`／`py`／`python3` 可能是不同版本、装不同依赖集，这是"我这能跑你那红"的头号来源 |
| 4 | **退出码** | 原始退出码数字；接了管道（`| head`、`| tee`）时要在管道之外另取一次 | 管道会把退出码吃掉，报出来的 0 可能不是被测命令的 0＝静默假成功 |
| 5 | **时间** | 开始与结束（带时区）＋墙钟耗时 | 判证据新旧、判性能是否可比都靠它 |
| 6 | **数据集版本** | 评测集／样本的来源与标识：提交号、manifest 哈希、行数＋抽样方式＋随机种子；无法版本化时写"快照描述＋取数时间"并标 **不稳定** | 分母换了，百分比就失去可比性 |
| 7 | **产物位置** | 原始输出文件路径、报告路径、被改动产物位置；大文件写明存放处与保留期 | 证据要拿得到；只存在于对话里的输出不算证据 |

- 模板在 `assets/最小运行记录模板.md`，复制填写即可。
- **填不满的字段写「未记录＋为什么」**，不许留空，更不许估一个数填进去。
- 一次执行一份记录（改前、改后各一份），不要合并成"一份记录两次数"。

## 二、执行前检查（三条，防环境假象）

跑之前先过这三条，否则失败原因会指向错误的地方。

| # | 检查 | 为什么 |
|---|---|---|
| 1 | **外部依赖是否就位**：模型权重 / 固定测试图 / 数据库 / 外部服务 | 缺它们会产出**假失败**。若缺失需跳过，把**跳过条数**写进报告。（实例：漏拷 `models/weights/` 导致 2 个测试假失败，补上后全过） |
| 2 | **套件能否独立跑**：先 `--collect-only` 确认收集数，再跑全量 | 共享测试库的套件**禁止多进程并行**（两个 pytest 互删库 → 37 failed vs 隔离 0 failed） |
| 3 | **路径是否隔离**：在副本里跑时，确认被测代码引用的是**你要测的那份** | 副本缺目录会导致"读源码"类测试失败（如断言 `web/src/**` 的测试） |

## 三、报告格式（模板）

任何"修复/优化"类汇报，按这个格式写：

```markdown
### 怎么验证的

**改动前**：`evidence/pytest_before_20260924.txt`
  → `2 failed, 394 passed, 2 skipped`（失败项：test_A, test_B）

**改动后**：`evidence/pytest_after_20260924.txt`
  → `396 passed, 2 skipped, 0 failed in 167.44s`

**期望值变更**（若有）：
- A 类口径重算：3 处（test_x: 60.0→56.25，语义：中性分不再进分子）
- B 类断言弱化：1 处（test_y：`total == raw×k` → `total <= raw×k`，理由：……）

**回归说明**：新增 test_z 为**现状快照**，改动前未验证它是否失败，非回归证据。
```

**判定标准**：别人拿着这份报告，**不看你的代码、只听你的话**，能不能自己复现出同样的数字？不能 → 证据不合格。

## 四、对"AI 跑测试"的专门规定

**AI 可以跑测试。** 但证据通道必须落盘，规则如下：

1. **要求 AI 把输出重定向到文件**，并在回复里给出文件路径——不要接受"跑完了，全过了"这种转述。
2. **AI 报的数字，必须能在文件里看到对应行**；看不到 → 标「未验证」。
3. **另一个 Agent 报的测试结果同样适用**：索要输出文件，拿不到就是未验证。（AI 审 AI 有共享盲区，交叉验证不等于证据独立。）

> **为什么单列这一条**：转述会走样。已发生实例：某次修复的"结果归档"是把上一版结果文件复制后改了一个数字，文件末尾还留着旧文件名；另一份安全报告引用了**不存在的提交号**。**两者都不是撒谎，是"没人核对过"。**

## 五、反模式清单（照这个自查）

| 反模式 | 为什么不行 |
|---|---|
| 只报"全过了"无原始输出 | 无法复现，等于没验证 |
| 复制上次结果文件当本次归档 | 一旦被核对（对比两版 diff / 看文件尾部残留）即穿帮 |
| 改前没跑，只有改后 | 无法证明改动解决了问题 |
| 断言值来自"跑出来之后抄进去" | 只能防未来退化，不能证明当初修对 |
| 口径重算与断言弱化混在一起报 | 掩盖了"测试变松了"这个事实 |
| 拿"环境不同"解释差异而不给两份输出 | 环境假设本身需要证据 |
| 在多进程下并行跑共享库套件 | 失败原因会指向错误的地方 |
| 补写一份没跑过的"改前"输出 | 伪造基线比没基线更糟——它让结论读起来像有对照 |
| 拿测试汇总行当业务提升证据 | 汇总行只证明这次运行结束了，证明不了指标变了 |
| 单次运行的数字当稳定指标／波动范围靠估计 | 随机指标的幅度必须由真实重复算出来 |
| 未经授权就跑烧钱、长时间、真连外部服务的评测 | 授权边界是硬约束，要跑先报价钱与钟点 |
| 原始日志里留着 token / 密钥 / 带签名的 URL | 日志一进版本库即等同泄露，事后删也被 git 历史接住 |
| 记录字段留空不写原因 | 空字段分不清"没测"还是"忘了写"，一律写「未记录＋原因」 |

## 六、与其它规则的边界

| 管什么 | 归属 |
|---|---|
| 该不该跑、什么时候跑 | `coding-behavior` 第 5 条「验证纪律」、第 7 条「证明优先」 |
| 事实 / 假设 / 未知 的分类与置信度 | 《抗幻觉与批判性验证准则》 |
| **跑完之后，证据长什么样** | **本 skill** |
| 对外汇报的数字口径（样本量/日期/引用可验证） | 交付流水线第 ⑭ 步「对外陈述口径检查」 |
| 检查该跑多广、能不能跑（花钱／长时间／联网） | **用户与宿主的现场授权优先**；本 skill 只规定"没跑就要写未测"，不自行扩大也不自行省略 |
| 评测集怎么建、分母怎么剔、判分到什么等级 | 项目验收官的指标层；本 skill 只管这些数字**交出来的证据长什么样** |

## 七、三类检查分开定证据

同一份改动可能同时涉及三类，**各配各的证据，不许用正确性证据替性能或效果说话**——`396 passed` 证明不了"快了 30%"，也证明不了"准了 5 个点"。

| 类别 | 回答的问题 | 必需证据（齐了才算） | 典型不合格 |
|---|---|---|---|
| **① 正确性检查** | 结果对不对 | 用例集及其来源（谁定的、覆盖哪些要求）、断言↔要求的对应表、原始通过/失败/跳过计数行、失败项的最小复现命令、数据集版本、退出码 | 只报"全过了"；跳过项没说明；合成样本被写成真实数据 |
| **② 性能比较** | 快了多少 / 省了多少 | 两次运行**同机同数据集**（环境字段不一致就写"不可比"）、计时边界（从哪一步量到哪一步）、warm-up（正式计时前的空跑）与迭代次数、重复次数与波动范围、被控变量清单（除被测项外其余什么都没变） | 换了机器或换了数据集，两个数字直接相减；一次运行的平均值当结论 |
| **③ 模型效果评估** | 准了多少 / 好多少 | 评测集构成与抽样方式、匹配规则与分母口径（哪些算 N/A 被剔除）、样本量、随机种子与重复次数、指标波动范围、失败样本可逐条回看 | 只报总体百分比不给分母；拿同一批样本反复改提示词直到分数上去（测试集泄漏） |

- 判自己属于哪一类：改动动的是"对不对"（①）、"多少时间／多少钱"（②）、还是"准不准／好不好"（③）；跨类就各交一份。
- 逐项清单模板在 `assets/三类检查证据清单模板.md`。
- 🔴 **只有①允许拿"全过了"当结论**；②③的结论必须是"数字＋口径＋波动"三件一起出场。

## 八、随机性明显的指标：样本量、重复次数、波动范围

LLM 输出、并发计时、抽样评测、含掷骰的数据生成，都属"随机性明显"。报这类数字必须记三件：

| 要记 | 写法示例 | 为什么 |
|---|---|---|
| **样本量 n** | `n=120 张（70 干净合成／30 加噪合成／20 真实收据）` | 分母决定可信度；不写 n 的百分比没法比较 |
| **重复次数 r** | `同一命令重复 3 次` | 一次运行只证明"发生过"，不证明"稳定是这样" |
| **波动范围** | `三次取值 84.2%／85.0%／85.8% ⇒ 84.2–85.8%`（算得出标准差或置信区间就给） | 没有范围，就判断不了"提升"是不是噪声 |

四条硬规矩：

1. 单次运行的数字必须标「单次，未重复」。
2. **提升幅度要和波动范围比**：两次数字之差落在各自波动范围内 ⇒ 只能写「未见稳定差异」，禁止写「提升了 x%」。
3. n 或 r 偏小时（经验参考：样本 <30 或重复 <3，**不是通用临界值**，按本项目方差调整）结论降级为「方向性观察」，并写明还差多少才能定量级。
4. 能设随机种子就设并记录取值。🔴 波动范围只能由那几次真实运行算出来，算不出来就写「未测波动」——**不许填"±2%"这种没来源的漂亮数字**。

---

## 九、检查广度按修改范围选，测试授权优先

跑多广由改动半径决定，一刀切"全量回归"和"改一行就不跑"都是错的：

| 修改范围 | 建议检查广度 | 不能省的那一条 |
|---|---|---|
| 文档／注释 | 链接与渲染检查、示例命令实跑、仓库体检退出码 | 别声称"没影响"：要么跑，要么写「未验证」 |
| 一行配置／常量 | 受影响路径的直接检查＋覆盖该路径的一条既有测试 | **配置存在 ≠ 生效**：要有"它真被加载了"的确认 |
| 模块内部（接口不变） | 该模块测试＋一条端到端冒烟（走通主流程的最小检查） | 冒烟不能省，接口没变但行为可能外溢 |
| 公共接口／数据结构／迁移 | 全量回归＋上下游调用点清单 | 迁移要带"回退方案能真跑"的证据 |
| 模型／提示词／评分口径 | 固定评测集＋抽样人工复核＋分母口径声明 | 口径一变，历史数字全部不可比，必须在报告头部声明 |

**授权高于本 skill 的任何一条**：

- 用户或宿主写明「不许跑 X／不许联网／不许烧 token」→ **不跑**，报告里写「因授权未执行，指标未测」。**未测不是失败，是一个状态**；把它编成数字才是失败。
- 长时间、花钱、调真实外部服务的评测：跑之前先报预计钟点与花费，超出授权范围先问一次，不自行扩大。
- 授权只覆盖被点名那一次——上次批准过不等于这次自动批准。

## 十、日志的脱敏、体积与保留

完整日志要长期保存，就必须先解决"里面有密钥、太大、没人清"这三件事。

- 🔴 **凭据不入日志**：token、API key、密码、私钥、数据库连接串、带签名参数的 URL，一律不得进落盘日志与截图。做法：命令里用**环境变量名**引用密钥（不在参数里写明文）；重定向前先想一遍"这份输出里会不会带出密钥"。
- 落盘后自检一次，命中即掩码后重写，并在报告里写明"日志已掩码"：

```bash
grep -Ein "api[_-]?key|token|secret|password|private key" evidence/run_20261013_login.txt
```

  未脱敏的原始文件**不得进版本库**——git 历史会永久留着它，工作区删干净了也还在。
- **体积**：原始输出可以截断，但**汇总行、失败段、退出码这三样必须在场**；记录里写明截断规则（例：头 50 行＋尾 50 行＋全部失败块）与完整件的存放位置。
- **保留期**：默认保留"最近一批＋被结论引用的那批"，更早的压缩归档；**不可再生的证据永久保留**——判据是"拿同一条命令还能不能再跑出来"（真实外部服务回包、一次性故障现场属不可再生）。归档压缩后要把新路径写进记录，否则等于删了。

## 十一、记录落点与命名（通用默认）

- 项目内沿用它**既有**的证据目录（常见两种：`<项目根>/docs/evidence/`、`<项目根>/acceptance/evidence/`），不要为一次测试新开第三个。
- 一次执行一份记录，命名 `run_<YYYYMMDD>_<任务短名>_<before|after>.md`；原始输出与记录同目录，记录里用相对路径指它。
- 对外引用的数字若有唯一口径表（例：`docs/numbers.md`），评测跑完同步它，并在记录里指它。
- 本机真实路径、既有口径表位置、宿主解释器差异见本技能目录 `personal.local.md`——存在则读并覆盖本节默认值，不存在就按本节走，**缺这个文件不是错误**。

## 十二、什么算"一份合格的证据包"

判据一句话：**另一位维护者只读你的记录，能自己重跑，并且知道哪些改善已经证明、哪些尚未证明。** 交出去前对着两个问题自查：

1. **每一步我怎么自己重跑？** → 命令、环境、数据集版本、产物位置四件齐（缺件写"未记录＋原因"）。
2. **哪些是已证明的？** → 按三态分账，禁止混排：

| 态 | 成立条件 | 允许的措辞 |
|---|---|---|
| **已证明** | 有改前改后对照＋原始输出＋退出码，随机类指标另带样本量与波动范围 | "在 X 集（n=…，r=…）上从 A 到 B，波动 …" |
| **现状快照** | 只有改后一份，或基线不可用（已写原因） | "当前为 B；改前无法取得（原因…），故不声称提升" |
| **未测** | 因授权、缺件、缺时间而未跑 | "未测：…；补齐条件是 …" |

> 🔴 这三态与《抗幻觉纪律》的事实／推断／待验证是**两把不同的尺子**：那把量"结论的可信度"，这把量"证据齐不齐"。同一句话可能可信度高但证据不齐（现场看过了却没落盘），两边都要如实标，不许互相折算。
