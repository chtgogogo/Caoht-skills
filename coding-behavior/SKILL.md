# 编码行为准则（任务专用）

> 触发原则：**宁多触发，勿少触发**——沾代码就进来。但**进来不等于全流程**：流程轻重由第一节判，判错方向的代价比少跑几条检查大。
> 本文件自足，无脚本、无外部前置件；引用到别的技能时，**不在场就按本文件自己的判据走完**（见第五、八节）。
> 本机坐标（记忆域根、共享踩坑日志根、本 store 落点、调度接线、波动带默认次数）见本技能目录 `personal.local.md`——存在则读并覆盖文中的通用默认值，**缺这个文件不是错误**。

## 一、先判形态，再选流程

两个轴别混：**流程轻重**（要不要展开第三节的工作流）与**能不能写盘**（这一轮准不准碰文件）。改一行配置＝轻流程但**要**写盘；解释一段代码＝轻流程且**零**写入。

| 这一轮实际在干什么 | 流程 | 写盘 | 交付必须长什么样 |
|---|---|---|---|
| 改行为／加功能／修 bug | 共通九条 ＋ **调试流**（落键前先造红灯：测试或最小程序先失败） | 只改点名处 | 改动清单 ＋ 一次红灯证据 ＋ 一次绿灯证据 |
| 改一个确定值（一行配置／常量／文案，改前就知道正确答案） | **轻流程**（九条，不展开工作流） | 只改那一行 | 改前实测读数 ＋ 改后回读；跳过回读＝未验证 |
| 重构（只换结构，行为要一模一样） | **重构流** | 按改动面 | 改前改后对账（行为基准未变） |
| 优化／**删除与瘦身**（性能、成本、行数） | **优化流**（第 0 步先定评价维度） | 按改动面 | 维度与基线 ＋ 波动带 ＋ 改前改后各一次 ＋ 三态结论 |
| 只读：解释代码、分析项目、答技术题、审方案不给补丁、纯配置问答 | **轻流程** | 🔴 **零写入** | 结论 ＋ 证据坐标（`文件:行`）＋ 未验证项 |
| 非代码（闲聊／写作／翻译） | 不触发本 skill | — | — |

🔴 **只读档的硬边界**：用户只要分析时，不许顺手改、不许顺手"大扫除"、不许预埋将来的功能——产生额外修改就是跑偏。
🔴 **"改一个确定值"不豁免风险判断**：靠列举键名判不住（「缓存上限算不算『之类』？」答不出）。改前先做一次**行为对调试验**：把这个值改回去，程序除了这个数变大变小之外**还有没有别的表现不同**——会不会多开一条连接、连到别处、放行一类请求、动到已存的数据。答「有」，或答不出（说不清这个键被谁读）⇒ 按第二节三问判，命中就先出计划；答「没有，它就是个数」⇒ 留在轻流程。命中三问之后**只多出一份短计划**（第二节），这一档仍然不展开第三节的工作流——计划与那格的证据形状是**叠加**关系，不是二选一。
🔴 **轻流程那格「改前实测读数 ＋ 改后回读」的取证动作**：改前把含旧值的那行**原样**摘进交付并带 `文件:行`；改后**重新读取同一位置**，再原样摘新行。同名值在一份文件里出现多处时，靠行号证明改的是哪一处。轻流程不要求落盘成文件，也不要求跑程序——「重新读取被改对象」就是这一档的「实际运行」（九条第 5 条在此的口径）。
🔴 **删除比很多重构更不可逆**：凡删码／删配置／删数据，都要有可退落点（一次提交或一份实体副本，二者都行，一个都没有就别动手），并按第二节判要不要先出计划。

## 二、要不要先出计划：按影响面判，不按文件数判

「超过三个文件就停下」这类机械门槛作废——它量不到风险，20 行的接口改动比 5 行的注释危险得多。动手前过三问，**命中任一 ⇒ 先出一份短计划（改什么／谁在用／怎么退）并过一遍，再落键**；三问全否 ⇒ 直接干，不必先出计划、也不必先问「可以吗」。命中多条不打折、也不重复计数——这三问只用来决定「要不要先出计划」，不用来给改动分级。

1. **接口变化**——改的是别人在调的东西：函数签名与返回形状、字段名与枚举值、URL 与路由、消息／事件格式、默认值的语义、公开类与导出符号。判据：**既存调用方应当不需要改代码**（向后兼容）；要破坏它，就得给出弃用路径或双轨（新旧同时可用）的过渡方案。
2. **数据迁移**——存量数据或存量文件要跟着变形状：库表结构、落盘文件格式、配置结构、索引与缓存键、序列化协议。上面只是例子，这问只有一句判据：**已经躺在盘上／库里的旧东西，改完以后还能不能被正确读出来**——不能就是命中，按下面句式走（先加不减 → 双写 → 回填 → 迁完再收，新旧两种数据在同一时刻都能被读，且有可执行的回退）；`RENAME`／`DROP` 一步换形＝违约。
3. **影响范围**——改动会穿出这个模块：跨模块／跨仓库依赖、并发与权限、凭据与密钥、资金与订单的**业务口径**（数字含义、对账规则；文件名带 `Order` 不算命中）、不可逆外部动作（推远端、发消息、删数据、改线上配置）、需要别人配合改他那一份。**取证动作**：改完后**别人／别处那份东西的行为会不会跟着变**——要指得出**具体哪一个**（哪一个程序、哪一个模块、谁的哪一个下一步动作）；指不出具体哪一个，这问就判否（「看着像跨仓库」不算命中，和「文件名带 `Order`」同理）。算「会」的例子：会被别的 Agent **当作执行依据**读的技能正文（它照着这条干活，改了它它的动作就变）、被别人 import 的模块、线上在跑的配置。🔴 别把这问用成「凡改文档都算高风险」：只改正文措辞、或改一个没有任何程序读取的写死数值，且说不清谁的下一步动作会变 ⇒ 判否，留在轻流程（取证动作照第一节那格交）。

> 文件数是**提示信号之一**，不是门槛：改动散在很多文件上确实值得先看一眼，但决定要不要出计划的是上面三问。
> 用户已经给过范围和授权的事不重复盘问（重复询问＝误伤，见第五、六节）。
> **「不确定先问」（九条第 1 条）的分界线**：只问**只有用户能补的事实**——目标不在场、需求有两条以上合理解读、这一轮准不准写盘没说清。凡是本文件自己能判的（属哪一档、要不要先出计划、缺件怎么办），问出口就说明没读完本文件；**判据的缺口不许转嫁给用户**。

**双轨件的豁免与收口**：为向后兼容而临时并存的新旧两套，**不算**「预埋未来功能」（它是上面判据 1 的显式要求），但必须带收口三件——谁负责切、凭什么信号判定可以收（如「旧字段读请求数连续 7 天为 0」）、什么时候收。**写不出收口信号的双轨＝违约**，比不留双轨更糟。

## 三、三条独立工作流（各走各的，不共用一套）

### A. 调试流（bug／报错／反常现象）

0. **先查坑**：先检索踩坑日志（技能 `pitfall-log`，调用键同名；不在场就直接读它的索引文件），比对「根因索引表」的识别信号，对得上就照通用对策试；反复出现／连败 3 次的 bug，动手前强制翻一次。
1. **允许先止血**：线上正在疼（服务不可用、任务卡死、别人被你挡住）时，**可以先采取有明确回退方式的缓解措施**（回滚那笔改动、关掉开关、走降级路径），不必先查到根因。缓解三件齐才算合规，缺一件就写「缓解未记账」并继续查：
   - 退路**在场且未过期**（旧提交还在、开关真能关、旧版本还能拉起）——线上正疼时不要求先演练一遍，但没演练就在留痕里写明「退路未演练」；
   - 影响面说得出（谁会被影响、能不能撤回）；
   - 留痕：写明「已缓解、根因未查」＋后续项。
   🔴 **缓解不是结案**。根因分析随后必须补，补不齐就明说「带伤运行」——「先止血后查因」不等于止完血就不查。
2. **复现**：先造出稳定复现步骤；造不出来就继续缩小范围，别写补丁。
3. **测试先红**：让失败以一条可重跑的断言存在（没有测试框架就一条最小程序）；说不出复现方法的修复，视为未验证。
4. **根因**：三连问（为什么会这样 → 为什么到这里才这样 → 为什么它会到这里）；治根因不治症状，往旧结构上打补丁前先问「半年后会不会变成第二个 bug」。
5. **最小补丁**：只改与根因直接相关的行。
6. **验证**：改前改后各跑一次，原始输出落盘；证据长什么样按 `testing-discipline` 走（不在场就守最低三句：原始输出留文件、改前改后各一份、只报汇总数不算证据）。
7. **同类扩散扫描**：修完一类缺陷，横向问「同类毛病别处还藏几份」。有 `same-root-cause-sweep`（同根因扩散扫描）就用它；**没有这支技能也要自己扫**——列出同形代码的候选位置逐个看，扫不动就写明「本次只查了 X 处，其余未检查」，不许因为找不到工具就跳过这一问。
8. **沉淀**：见第七节（先候选，再决定入不入库）。

### B. 重构流（改结构，不改外部行为）

1. **先钉行为基准**：一组「同样输入 ⇒ 同样输出」的对照（已有测试集就用它，没有就先跑一遍把结果录下来）。
   - **基准钉在外部可观察面**：调用方／用户看得见的那一层——接口载荷与字段值、落盘内容、界面行为、既有日志与指标口径。内部类型、方法签名、文件划分本身**不算**行为，动它们是重构；动上面那层是改行为。
   - 一次任务里两段同时出现（既挪内部结构、又动载荷形状）⇒ **按段分账**：动载荷那段按「改行为」交证据（对新形状先红后绿），其余那段按基准全绿对账；两份证据都要有，不许用一份盖另一份。
   - 钉不出基准 ⇒ 这不是重构，回到改行为档。
2. **一次一小步**，每步重跑基准；禁止在重构里顺手加功能、顺手改「命名以外的行为」。
3. **改前有可退落点**：一次提交／一份实体副本，一个都没有就别开工。
4. **改完对账**：基准全绿 ＋ 改动面核对（不该动的文件确实没动，用 `git diff --stat` 这类清单证明）。
5. 命中第二节三问的重构（改公开接口签名、挪数据存放位置）＝**先出计划**，计划里必须写「调用方怎么跟着改」或「怎么让调用方不用改」，二选一，不许含糊。

### C. 优化流（性能／成本／精度／内存／删除与瘦身）

0. **先定评价维度**（这一步没做完，后面全是无效劳动）：从 正确性／延迟／吞吐／单位成本／内存／可维护性 里点名 1–2 个主维度，并写下**接受哪个维度变差**（维度常互相权衡：更快往往更占内存或更难维护）。没标维度的「优化」按未完成处理。
1. **定基线与波动带**：同一套东西**重复跑（不得只跑一次）**，次数与带宽算法见本机适配层（通用下限＝3 次，带宽要写明用的是最大最小差还是标准差）。判「有没有变」要跟**波动带**比，不是跟单次读数比——环境噪声足以翻转一次对比的结论；差值落在带内叫「没测出来」，不叫「没作用」。
2. **改前改后各跑一次**，原始输出落盘（细则走 `testing-discipline`）。
3. **消融**（拆开验证零件值不值）：撤掉新加的零件重跑，看主维度掉不掉。**「撤掉后分数没掉」不直接等于「该删」**，先过四问：
   - 差值是否宽到落在波动带**之外**？
   - 测的是不是当初定的主维度？（用内存换延迟，只看延迟就会误判内存零件没用）
   - 这个零件是否承担**未来约束或安全网**职责——正确性、安全、兼容、可观测、可回退？这类东西平时不产出分数，出事才产出；**要证它有用得用靶场景测**：专门构造一批它负责的那类输入，做带／不带对比。用通用评测集测不出它，不算它没用。
   - 删它省下什么、谁付维护成本？省的是行数、付的是下次排查时间，要写明这笔交换。
4. 四问过完才下结论，三态之一：**删／留／证据不足待测**。「证据不足」是合法结论，不许包装成「没用」；🔴 但**待测态必须带出口**——写清补测动作（一句可执行的话）、谁跑、什么时候跑。没有出口的「待测」＝搁置，不许当结论交付。
5. 每句「有用／更快／更准／它没用」后面都指得出可复现证据（Prove it, don't tell me）。

## 四、共通九条（编号与名称稳定，外处按条号引用；每条一句短规则）

1. **思考优先**：不确定先问，禁止猜了继续干；交付前列出不自信的点，分【事实／假设】标置信度，证据不足写「未知」。
2. **极简**：只做明确要求的事，禁止预埋未来功能、禁止顺手大扫除（兼容双轨件按第二节豁免，但带收口三件）。
3. **外科修改**：只改与任务直接相关的行，不碰无关行，改动面最小化。
4. **目标驱动**：动手前先定可验证的成功标准（什么现象出现＝做成了）。
5. **验证纪律**：声称完成前必须实际运行、读完整输出与退出码；未验证禁说「应该可以／修好了」；同一问题连败 3 次立即停下重新分析，不许硬磕。
6. **遇错先查坑**：报错／反复失败／反常现象先按 A 调试流第 0 步检索踩坑日志，查过就在回复里引用它；修完按第七节**两步**沉淀，不直接写用户记忆域。
7. **证明优先**：声称「修好了／更快了／更准了」前先当自己的对手——假设这个改动是错的，主动找反例、跑边界、构造让它翻车的输入；效果类改动按 C 优化流做消融（先定维度、看波动带、过四问，不是「分数没降就删」）；修完一类缺陷后横向扫一遍同根因。
8. **溯源调试**：复现 → 测试红 → 根因，三问不过不许写补丁；线上正在疼时允许先做有退路的缓解（A 流第 1 步），但缓解不等于结案。
9. **结构自觉**：一件事的代码住一起（高内聚）；模块之间只走明面接口（低耦合）；同一条常量／规则只出现在一个文件里，别处一律 import（单一事实源）；要不要先停下画草图，按第二节三问（接口／数据／影响范围）决定，**不按文件数**。

## 五、与相邻技能的边界（一次任务只认一个主流程）

| 这一轮实际在干什么 | 主流程归谁 | 本 skill 这一轮提供什么 |
|---|---|---|
| 看懂一段代码／定位问题／要一份结构化交付 | `senior-engineer-playbook`（五模板）对应模板 | 只交共通九条 ＋ 只读零写入边界；模板清单形状不重抄（五模板不在场时，交付直接按第一节只读行那三格走：结论＋`文件:行`＋未验证项） |
| 具体改哪几行、怎么改不跑偏 | **本 skill** | 全套（第一～四节） |
| 正式疑难缺陷与性能回退的完整诊断循环 | `diagnosing-bugs`（缺陷诊断） | 让位；A 调试流是它不在场时的兜底 |
| 整个项目从需求到交付的多阶段编排（切任务卡／台账／断点续传／验收闭环） | `delivery-pipeline`（交付流水线） | 让位；只作为每一步的执行纪律，不再另起一套流程 |
| 审还没动工的计划能不能开工 | `plan-review`（评审计划） | 不触发本 skill 的重流程；本 skill 只管动工之后 |
| 已建成的项目达不达标 | `project-acceptance`（项目验收官） | 无关；别拿九条去当验收清单 |
| 踩过的坑怎么沉淀、怎么查 | `pitfall-log`（踩坑日志） | 第七节的写入边界以它为准 |
| 结论怎么下、话怎么说出口 | `anti-hallucination-discipline` | 并行守，内容不重复 |
| 测试／评测证据长什么样 | `testing-discipline` | 并行守：本 skill 管「该不该跑、什么时候跑」，它管「跑完证据什么形状」 |
| 文件写哪个盘、缓存往哪重定向 | `disk-cache-discipline` | 并行守 |

🔴 **让位目标不在场时不空转**：上面点名的外部件只要在本机找不到，本 skill 就自己按通用判据把这一轮走完，不停在「找不到那支技能」上，不报错退出、不反问用户；交付里写一行「X 不在场，本轮按通用判据走完」即可。
🔴 **别同时加载两套完整清单**：重复的纪律文件只多交一份上下文税（占窗口又挤掉正题），还容易两条规则互相打架。触发词重叠时先按本表归口，并在交付开头写一行「本轮主流程＝X，本 skill 只补 Y」。
🔴 **本表多行同时命中怎么办**（改的正是别的技能的文件＝既命中「具体改哪几行」又命中那个域的「并行守」行）：**主流程＝产出这一轮那一样东西的行**——要交付的是一处改动 ⇒ 本 skill 主、外部件并行守；要交付的是解释／清单／结论 ⇒ 外部件主、本 skill 只交共通九条。其余命中行一律降到「并行守」，它的操作定义＝**守它的判据（不写出违它的东西），不跑它的流程**，也不因并行守多开一轮确认。判据从哪来＝当场去读那一支技能的相关段落——**读不算写盘**，只读档也允许；读不到就按上一条「不空转」在交付里写明未守。
已授权事项不重复盘问：用户已点名的技术栈／范围／口径直接照用，不再开一轮确认。

## 六、不应触发本 skill 的反例

本表只判两件事：**本 skill 触发不触发、触发后走多重的流程**。主流程归口一律看第五节表——两处对同一个场景说法不同时，**以第五节为准**（例：「带我看懂这个函数」触发本 skill 的轻流程，但交付形状的主流程归五模板②）。

| 场景 | 处置 | 为什么 |
|---|---|---|
| 「这段代码什么意思」「带我看懂这个函数」 | 触发，走**轻流程**（只读档）：零写入、给 `文件:行` 坐标 | 用户要的是解释，额外改动就是越权 |
| 纯配置问答（「这个键叫什么」「能不能设成 0」） | 轻流程；真要落盘改值，回第一、二节按影响范围判 | 问答零风险，写盘不一定 |
| 这个方案值不值得做／需求怎么切 | `plan-review` 或五模板⑤ | 还没到写码 |
| 给项目出验收结论 | `project-acceptance` | 本 skill 没有「达标」这条轴 |
| 只是跑一次已有测试、汇报指标 | `testing-discipline` 为主 | 不产生代码改动 |
| 拿一次评测读数论证「某组件可以删」 | 走 **C 优化流**（先维度、看波动带、过四问、出三态） | 这不是"只汇报指标"，是删除决策 |
| 闲聊、写作、翻译、无代码的文档改写 | **不触发** | 零代码 |

## 七、经验沉淀：两步走，不直接写用户的记忆域

1. **先形成候选记录**（本轮就能写完）：现象／命令／现场输出／被排除的错误猜测／当下结论——本轮没执行过的项写「无」，不许编。放在本轮产物里（任务包的证据目录、改动说明、或交付正文），**不落任何记忆库**。🔴 但**只读／零写入档（第一节）下只有「交付正文」这一个落点**——候选记录不新建文件、不建目录，在这种轮次里落盘本身就是违约。
2. **由维护策略决定入不入库**：
   - 谁的域谁写：本机私有坑进**这个人自己的** store PITFALL；跨 Agent 通用的坑走 `pitfall-log` 的根因层＋案例层；跨 Agent 重大变更记 SHARED 台账（ledger）。
   - 入库前先查重：同根因已有条目就挂到它下面、加一条命中，别再新起一条；库自己带的确定性工具优先用工具写，别手抄计数。
   - 🔴 **未经允许不写**：用户记忆域、别人的 store、共享正本，都需要任务里已有授权或对方明确同意；没授权时**只交候选记录**，并写一句「待你决定是否入库」。
   - 判据一句话：**这条经验三个月后对别人还有用吗？** 只对这一轮有用的，留在本轮产物里就够，入库＝给以后的检索加噪声。

## 八、执行顺序与缺件降级

判形态（第一节）→ 判要不要先出计划（第二节）→ 走对应工作流（第三节）→ 全程守共通九条（第四节）→ 与别人重叠时按第五节归口 → 沉淀走第七节两步。

| 引用的东西 | 不在场时怎么办 |
|---|---|
| `pitfall-log` 技能 ＋ 它的索引文件 | 自己问三句：这个报错像不像已知坑？本机最近改过什么？先试最小安全对策。查完照第七节记一条候选 |
| `testing-discipline` 技能 | 守最低三句：原始输出留成文件、改前改后各跑一次、只报汇总数不算证据 |
| `same-root-cause-sweep` 技能 | 自己在改动点周围列候选位置逐个查（A 流第 7 步）；查不动就写明未检查范围 |
| `senior-engineer-playbook`／`plan-review`／`delivery-pipeline`／`project-acceptance`／`diagnosing-bugs` | 按第五节「不空转」条款，本 skill 自己走完这一轮，不停在找技能上 |
| `personal.local.md`（个人适配层） | 全部按本文件的通用默认值走，不报错、不追问路径 |
| **要改／要解释的目标文件本身不在场**（路径不存在、盘没挂、文件被改名） | 按原样报告「找不到」，并列出你**实际试过**的路径；不许凭记忆描述它的内容、不许猜它现在在哪。这属于「只有用户能补的事实」（第二节分界线），可以直接问——不算盘问。这一轮的「证据坐标」＝你实际试过的路径清单本身 |
| 共享源 `行为准则\编码行为准则.md` | 无影响——本文件自足，共享源只是历史参考 |

需要更细的展开解释时，才读共享源 `<你的共享层>\记忆规则\行为准则\编码行为准则.md`（**历史原文**，冲突一律以本文件为准）。

## 九、本轮判据的外部锚点（可信度档位：✅ 直读一手／🟡 待复核）

- 第二节「既存调用方应当不需要改代码」← Google API 改进提案 **AIP-180 Backwards compatibility**（✅）；弃用要有窗口 ← **Kubernetes Deprecation Policy**（✅）。
- 第二节数据迁移「先加不减→双写→回填→迁完再收」← PlanetScale《Safely making database schema changes》expand-contract 法（✅，厂商一手工程文，非中立标准）；「已提交的迁移不要回改」← Rails Guides《Active Record Migrations》（✅）。
- A 流第 1 步「先止血后查因」← Google **SRE Workbook** 第 9 章 Incident Response「先阻止影响、再找根因」（🟡 摘录经中文镜像互证，sre.google 本环境直连失败）。
- C 流第 1 步「波动带」← Mytkowicz 等《Producing Wrong Data Without Doing Anything Obviously Wrong!》ASPLOS 2009（✅ 结论级，正文 403）＋ SPEC 词汇表 `variability`／geometric mean 条目（✅）。
- C 流第 3 步「删组件不能只看分数」← Sculley 等《Hidden Technical Debt in Neural Learning Systems》NIPS 2015（🟡 仅采到摘要级）。
- 第二节「文件数是信号之一」← Anthropic《Claude Code: Best practices》把「改动跨多文件」列为 plan mode 有用情形之一（✅）——所以本文件不把文件数当门槛，但不把它写成无意义。
