# 踩坑日志（Pitfall Log）

一种**省 token** 的踩坑 / 经验教训沉淀方式：维护一份**极轻索引**，加**根因层**与**案例层**两层明细，而不是把所有教训内联进同一个会越写越大的文件。核心价值是「渐进式披露」——索引常驻上下文，细节按需加载。

## 何时使用

**查阅（先想这一步）：**

- 遇到报错 / 失败 / 反常现象 / 反复排查不下的问题 → **先去检索**，别一上来就改代码。
- 用户说「看看踩坑记录 / 教训 / 之前怎么解决的 / 有没有类似的坑」。

**记录：**

- 踩了一个非显然的坑、或想沉淀一个可复用经验 → 记一条。
- 解决完一个棘手问题后，主动提议帮用户记一条。

## 两层结构

```
<log-root>/
├── pitfall-log.md              # 极轻索引（单一事实源）：根因索引表 + 分组的案例清单
├── roots/                      # 根因层：一个根因一个文件（检索入口）
│   └── RT-<三位编号>-<slug>.md
├── pitfalls/                   # 案例层：一条坑一个文件（深读用）
│   ├── _template.md            # 完整复盘（八段）
│   ├── _template-lite.md       # 轻量记录（四段）
│   └── YYYY-MM-DD-<slug>.md
└── _candidates/                # 升华候选区：够阈值先进候选，闸门过了才提升
    └── C-RT-<编号>-<序>-<哈希>.md
```

- `<log-root>`：**本机现值写在 `personal.local.md`**（随机器/环境而变的私有配置，不写进公开正文）；第一次用先和用户确认存储位置。**路径保持稳定，索引才不会指错。**
- **索引**（`pitfall-log.md`）：每次会话都读，必须保持极短。
- **根因层**（`roots/RT-*.md`）：**检索先落到这里**——一句话根因、识别信号、通用对策。
- **案例层**（`pitfalls/*.md`）：完整过程与细节，根因层不够用时才深读。
- **候选区**（`_candidates/`）：见「升华＝候选 → 验证 → 提升」。

## 随包工具（确定性维护，别手抄数字）

`scripts/pitfall_log.py` 是这层结构的**唯一写入通道**——登记、计数、自检、提升都走它；手改索引属于例外，改完必须 `check` 复核。

```
py scripts/pitfall_log.py --root <log-root> init                                  # 建骨架（索引＋roots/＋pitfalls/＋_candidates/＋两份模板）
py scripts/pitfall_log.py --root <log-root> add --title … --root-cause RT-0NN \
        [--kind full|lite] [--severity 红|橙|黄] [--make-root "一句话根因"] \
        [--also-root RT-0MM] [--date YYYY-MM-DD] [--author …] [--tags …] [--summary …] [--body-file F]
py scripts/pitfall_log.py --root <log-root> hit --case <事件ID> --scenario … [--solved …] [--date …]   # 案例层命中
py scripts/pitfall_log.py --root <log-root> hit --root-cause RT-0NN --scenario …                        # 根因层命中
py scripts/pitfall_log.py --root <log-root> counts [--apply] [--prose] [--json]   # 默认干跑只打印计划
py scripts/pitfall_log.py --root <log-root> check [--json]                        # 索引↔事件记录↔根因文件 自检
py scripts/pitfall_log.py --root <log-root> promote --scan                        # 到阈值 → 生成候选
py scripts/pitfall_log.py --root <log-root> promote --gate C-RT-009-01-xxxx [--apply]
```

`--root` 必填、不给默认当前目录（防止量错库还一片绿灯）；`--root` 指向不存在的目录直接非 0 退出，不假建。退出码：0＝正常／1＝`check` 见红、或写后读回验收不过、或 `promote --gate … --apply` 闸门没过／2＝用法错、库不合规／3＝候选文件不在场（先 `--scan`）／4＝同一事件 ID 换内容被拒／5＝抢锁失败。


## 为什么分两层

**从坑里能捞出来的最大价值不是"这次怎么修的"，而是"为什么会踩、下次怎么一眼认出来"。**

同一类问题会在毫不相干的场景反复出现。比如"中文编码"这个根因，一次是 PowerShell 脚本乱码，一次是 git 命令误删整个目录——症状完全不一样，根因是同一个。如果只按案例平铺，这两条永远看不出关系，下次换个场景照样踩。

所以：**根因是一级公民，案例挂在根因下面**。检索时先命中根因 → 拿到通用对策与识别信号；根因层解决不了，再往下翻具体案例找灵感。

## 索引格式

两部分，**根因索引在前**（与 `assets/index-template.md` 保持一致）：

**① 根因索引表**

```
| 根因 | 一句话 | 案例数 | 命中 |
|---|---|---|---|
| [RT-001](roots/RT-001-xxx.md) | 中文出现在跨进程 / 跨工具边界 → 先怀疑编码 | 2 | 🔥0 |
| [RT-002](roots/RT-002-xxx.md) | 依赖隐式上下文（cwd / 工作目录 / 会话状态） | 2 | 🔥0 |
```

**② 案例清单（按根因分组，组内新 → 旧）**

```
### RT-001 中文出现在跨进程 / 跨工具边界

| 日期 | 记录者 | 标签 | 一句话标题 | 命中 | 文件 |
|---|---|---|---|---|---|
| 2026-09-15 | 小鲸鱼 | Git/中文路径 | 中文路径当 git 子命令参数会误删整个目录 | 🔥0 | [详情](pitfalls/xxx.md) |
```

- `记录者`：谁记的（助手标识 / 人名 / `shared`）。用稳定短标识。
- `标签`：逗号分隔关键词，便于检索。
- `命中`：见「命中计数」。`🔥0` = 还没被用上；`⭐` = 已升华。
- 案例分组的标题级别**两/三/四级都认**（现役库用 `## RT-022 …`，模板用 `### RT-009 …`）。级别写死会让「分组指向缺失根因」这条自检在真实库上永远不响——2026-10-13 对账时就是这么漏掉 RT-022 的（有分组、`roots/` 无本体）。

## 两个指标：都不手填

| 指标 | 含义 | 唯一的数从哪里来 |
|---|---|---|
| **案例数**（`cases`） | 该根因下攒了**几件不同的事** | `pitfalls/*.md` 现扫，按事件指纹去重后的条数 |
| **命中**（`hits` / `🔥N`） | 这条记录**实际帮上忙几次** | 文件末尾「命中记录」表的**行数**现扫（根因表的数＝本文件命中行＋下挂案例命中行） |

两轴不同轴，别混：案例数多 ≠ 有用；命中多 ≠ 该升华。**`counts --apply` 一次把索引、`roots/`、案例三侧的数字全部重算刷新，`check` 负责指出漂移。**

为什么不手填：同一个事实散在索引表、根因表、根因文件 frontmatter、案例 frontmatter 四层，四层各写一次＝四次写错的机会，而它对读者看起来全是"官方数字"。现役库 2026-09-30 那段"索引写 3／文件写 2"的漂移备注就是历史证据。

### 口径对照表（每个指标先问这三件事，再决定怎么数）

手抄数字之所以会漂，不是因为没人记账，而是因为**同一个名字在库里存在好几种口径**——手抄的人心里有一种，读的人心里有另一种。工具的做法是把口径钉死在唯一一处（`derive(root)`，`--json` 可看全部分项）。下面每一行都是现役共享库里真实存在过的形状，不是假想题（逐行可在合成库上复现，断言 A34／A35／A36）：

| 说法 | 手抄时的自然读法 | 工具的读法（唯一尺子） | 为什么这样定 |
|---|---|---|---|
| 「案例文件数」 | 数 `pitfalls/` 里的 `.md` | `*.md` 总数 **减掉 `_` 开头的模板**（`_template.md`／`_template-lite.md`） | 模板不是坑；把模板算进分母，"案例数"就和一个谁都没登记过的数字打架 |
| 「表行数」 | 案例数＝索引表有几行 | **不等于**文件数：`also_root` 双挂时一条文件在两个分组各占一行 | 表行是「挂载」，文件是「事件」；混用会让"少了几行"这种告警常年误响 |
| 「命中」 | frontmatter 里那个 `🔥N` | 只看条目自己的「命中记录」表行数 | 手写数字是快照；表行是可回溯的一次次记录 |
| 根因表的命中数 | 把下挂案例的命中直接搬过来 | **根因自身命中 ＋ 下挂案例命中**（`hits_by_root = 本文件命中行 ＋ 各案例命中行`） | 两层独立计数（读了 `RT-*.md` 的通用对策就解决＝只加根因；照某条案例照搬＝加案例），漏一侧就少算 |
| 历史条目（`legacy`） | 「旧格式没救，跳过全部检查」 | 只退出 **R7 缺段**自检；`hits`／事件标记／挂载／死链**照样照数** | 铁律「旧条目不追改」禁止给它们补写「复现」「验证」（＝编证据），但没禁止数它们 |
| 元数据位置 | frontmatter 就一种 YAML | 三种形态都认：YAML `^root:` ＋ 行内引用块 `> root: RT-013 ｜ hits: 1` ＋ YAML `^root_cause:` | 现役库里三种并存；只认一种时"命中总数＝1"这类结论会当场算错（历史自查踩过两次） |
| 「已升华」 | `escalated: true` 像"这条坑重要" | 它是**提升之后的结果标记**，不是登记门槛：只在 `promote --gate … --apply` 过闸那一刻写进候选的「来源」案例，并给索引行加 ⭐ | `false` ＝还没被提升，属正常态，**不进红名单**。现役 46 条里 2 条 `true`／44 条 `false`——若把 `false` 当缺口，自检一开就 44 条假红 |
| 计数按哪个字段 | `^root:` 只会数到主根因 | 副挂面读 `^also_root:`，两者相加才是挂载数 | 索引头部那句"五条双挂"认领的是 frontmatter，**不是表行数**——想当分母用必须先现查 |

🔴 **行内形态「读到哪儿为止」也是口径的一部分**，不是"能读到就行"。现役库那条行内元信息写在**标题行下面**，而最初的实现是"一碰到第一个 `#` 就停" ⇒ 这条案例既挂不上根因、`hits` 也读不出来，`counts` 只能回一句「缺 YAML 头 ⇒ 未动」，`check` 的 R6 从此常驻红。现读法＝**从标题行之后读到第二个小节标题为止**，行内形态的 `hits` 同样由现扫回写。2026-10-13 第二次对现役共享库做只读对账（`counts` 干跑，零写入——跑前跑后全库 md5 清单逐字相同）：同一把尺子下 `RT-013 案例数 0 → 1`、挂载总数 49 → 50——**这条案例一直都在，只是从没被数过**；随之多出的那条红（R3／R4 点名 RT-013）不是新故障，是原来看不见的漂移第一次变得可见，修复归属库主。

一句话：**"这个数按什么数"这件事只能有一个答案，而且必须写在代码里、能被 `--json` 摊开看，不能写在人脑子里。**

### 事件唯一 ID 与幂等

每条案例正文头部带一行事件标记：

```
<!-- pitfall-event: 2026-10-13-并发写共享-md-读到中间态 | fp: 6f2a1c9d0b74 -->
```

- **事件 ID** ＝ `日期-slug(标题)`，同时是文件名 ⇒ 一条事件一个文件，文件名即主键。
- **指纹 `fp`** ＝ `sha1(标题 | 根因号 | 后果分级)` 前 12 位 ⇒ 判"是不是同一次事件"看指纹，不看文件名（换个记录者手打、标点不同都算同一件事）。
- **重复提交同一事件** ＝ 幂等 no-op：计数不变、正文不覆盖，打印「已在册」后返回 0。
- **同一 ID 但内容不同**（改了标题级信息）＝ 拒绝并退出码 4，要人裁决——静默覆盖会把别人写的那一版抹掉。
- 命中记录同样去重：**同一次命中连投三次只算一次**（判同键＝日期＋归一化后的场景文本）。

2026-10-13 之前的历史条目没有这行标记，工具照样按文件计数，只对它们放弃幂等保护（`check` 聚合成一条 R5 告警点名条数，不逐条刷屏）。

## 根因文件格式

复制 `assets/root-template.md`，命名为 `roots/RT-<三位编号>-<slug>.md`。文件头 frontmatter 记状态：

```yaml
---
root_id: RT-001
title: 中文出现在跨进程 / 跨工具边界 → 先怀疑编码
cases: 2          # 该根因下挂了几条案例
hits: 0           # 该根因的通用对策被直接套用（未深读案例）的次数
escalated: false
---
```

正文四节：

- **一句话根因**：这类问题的共同病根，一句话说清。
- **识别信号**：出现哪些迹象就该往这里想——**最有用的部分**，它是"提前认出来"的钩子。
- **通用对策**：不针对任何具体案例的做法，最好能直接照做。
- **挂载案例**：该根因下的案例清单（表格，与索引保持一致）。

根因编号 `RT-001`、`RT-002`… **只增不改**——别人可能引用它，改号就断链。

## 案例文件格式

复制 `assets/entry-template.md`，命名为 `pitfalls/YYYY-MM-DD-<slug>.md`。文件头 frontmatter：

```yaml
---
root: RT-001       # 挂在哪个根因下（必填）
also_root: RT-002  # 可选：副挂的第二个根因族（挂载数因此 ≠ 案例数，是对的）
hits: 0            # 由「命中记录」行数生成，不手填
last_hit: —        # 最近一次命中的日期
escalated: false   # 是否已提升成铁律（走候选→闸门，不是数到次数就翻）
kind: full         # 可选：full / lite / legacy；不写则工具按日期与形状推断
---
```

### 双模板：小事用轻量，大坑用完整

| | 轻量 `entry-lite-template.md` | 完整 `entry-template.md` |
|---|---|---|
| 段数 | 现象 / 根因 / 能否借鉴 / 教训 ＋ 来源 ＋ 命中记录 | 八段 ＋ 单列「我自己引入的错」 |
| 用在 | 🟡 只浪费时间、🟠 结果错但可回滚 | 🔴 不可再生损失，以及需要别人照着复现的坑 |
| 省掉的是 | 字数 | — |
| 不许省的是 | **证据**：现象段仍要贴屏上原文或具体数字；「能否借鉴」仍要写适用条件 | 全部 |

🔴 配了轻量模板会被工具**当场改判成完整复盘**并打印升格原因（`add --kind lite --severity 红` ⇒ `[gate] 🔴 不可再生损失不许用轻量模板 ⇒ 自动升为完整复盘（八段）`，`check` 另有 R7 一条报「🔴 用了轻量模板」）——不可再生损失的记录如果连复现都没有，下次换个人照样踩且拿不到证据链。轻量不等于含糊：适用条件空缺的轻量条目，永远进不了升华候选。

正文**八段**（v1.5.0 起；标题用 `# 坑：<一句话标题> —— <最直接的后果> 🔴/🟠/🟡`）：

| # | 段名 | 必须写到什么程度 |
|---|---|---|
| 1 | 现象 | 先一行上下文（当时在做什么 / 什么前提），再贴**屏上原文或具体数字**。转述不算——转述会把关键特征抹平 |
| 2 | 复现 | **最短命令序列**，别人照着跑能再撞一次。撞不出来就写「未能复现 + 当时的条件」，别留空 |
| 3 | 现场代码 | `文件:行` + 关键片段，抄**改之前**那一版 |
| 4 | 根因（机制） | 为什么坏，**不停在表象**。写**本案例**的具体机制；`root:` 字段才是它归属的**根因族**，两者别混 |
| 5 | 修法 | 代码级改动 + **为什么这样切**（为什么改这里而不是别处） |
| 6 | 验证 | 修后的**实测输出 / 断言条数**。"改好了"三个字不算验证 |
| 7 | 能否借鉴（通用规律） | **全篇最有价值的一段**（见下） |
| 8 | 教训（一句可迁移纪律） | 一句下次能直接照做的命令句 |

八段之后**单列一段「我自己引入的错」**：修这个问题的过程中自己新引入的错（改 A 坏 B、把校验脚本自己写坏、误判了影响范围）。没有就写「无」——**空节比缺节可检查**，缺节分不清是"没犯错"还是"没回头看"。

后果分级 🔴/🟠/🟡 只写在标题行、**不进 frontmatter**：各家计数脚本要认的是 `^root:` / 行内 `> root:` / `^root_cause:` 三种写法（外加 `^also_root:` 双挂面，见索引开头那条实测），再塞一个新字段等于给五家的脚本各埋一次漏判。判据按**损失能不能挽回**分：🔴 不可再生损失（数据被销毁、误删、写坏共享权威资产）／🟠 结果错但可回滚（静默假成功、范围跑偏、判据失灵）／🟡 只浪费时间（绕路、误读、拼错路径后自查）。有分级，同一根因下的多条案例才排得出先后。

「能否借鉴」和 `root` 的分工是：**`root` 说「这属于哪一类」，能否借鉴说「这一类里可迁移的规律」**。

**旧条目不追改**：2026-10-03 八段制生效之前入库的历史条目（2026-10-13 实测 35 条，形状不止一种：老五节「上下文 / 为什么（根因）/ 解法 / 能否借鉴 / 来源」、也有「现场还原 / 根因归位 / 通用对策 / 借鉴判断」，还有纯标题起步的）保持原样。补写「复现」「验证」等于替当年的自己编造证据，那是伪造。**新坑一律按下面两套模板之一**；老条目被命中时若当年留了原始回显，可就地补段并注明补录日期。

工具把这两种判据都实现了：`kind: legacy` ＝ 文件名日期早于生效日 **或** 形状命中老词表；legacy 条目**不参与缺段自检**（`check` 不对它报 R7）。别用「读起来像不像八段」当判据去改历史文件——那会把伪造的段落名安在没写过的内容上。

## 命中记录

| 日期 | 场景 | 解决了什么 |

## 检索流程（先根因，后案例）

1. 读 `pitfall-log.md`（极省）。
2. **先扫「根因索引表」**——有没有哪个根因的识别信号对得上当前问题。
3. 对上了 → 读那个 `roots/RT-*.md`，拿通用对策先试。
4. 根因层不够 → 再挑该根因下的具体案例深读，找灵感。
5. 解决了 → 按「命中计数」给**真正帮上忙的那一个** +1（`hit --case <事件ID>` 或 `hit --root-cause RT-0NN`），并告知用户。
6. 一个都对不上 → 自己排查；解决后按下面的流程记一条新的。

## 记录流程

1. 确定稳定的 `<log-root>`（现值见 `personal.local.md`；空库先跑 `init`，它会一次建好索引＋`roots/`＋`pitfalls/`＋`_candidates/`＋两份模板）。
2. **归因**：这个坑的根因是什么？先在 `roots/` 找有没有现成的同根因文件——
   - 有 → `add --root-cause RT-0NN` 直接挂上去（案例数由工具重算，不手 +1）；
   - 没有 → 想清楚"**一类**问题"而不是"这一个问题"，再 `add --root-cause RT-0NN --make-root "一句话根因"`。**不给 `--make-root` 时未知号一律拒绝**——凭一个可能打错的号凭空立族，会把后来人的检索带偏。
3. 写案例：`add --title … --severity … --kind full|lite [--body-file F]`。完整复盘走八段＋单列「我自己引入的错」（没犯错写「无」，不许删节）；轻量走四段。事件 ID 与指纹由工具生成写进正文，不用手打。
4. 索引同步**在同一次 `add` 里做完**：锁内更新案例清单行＋根因表＋按现扫刷新数字＋写根因文件的 frontmatter，最后写后读回重算一遍对不上就非 0 退出。`counts --apply` 是给"别人手改过／历史遗留漂移"用的刷齐通道，不是每次记录的必经步骤。
5. 收尾跑一次 `check`：红 0 才算这条真在册。

## 命中计数

**为什么要有计数。** 「能否借鉴」里写的规律有没有真救过场，光看记录看不出来。计数把"这条坑有用"从感觉变成数字。

**什么时候 +1。** 核心判据只有一条（v1.4.0 起放宽，用户 2026-09-26 拍板修订）：

> **在这条坑对应的问题被独立解决之前，踩坑记录（正文或索引元数据）被你看见，并对解决产生了实际助力——帮你找到方向，或直接修好了问题——就算命中。**

**怎么看见的不限**：主动检索到的、干活途中撞见的、误打误撞翻到的，都算。典型场景：

- 检索 → 读 `roots/RT-*.md` 或案例 → 套用对策解决 → 算；
- 没在检索，干活途中翻到某条记录，它纠出了当前工作中的错误 / 给了关键启发 → **也算**（2026-09-26 首例：写库会话读本日志索引归档新坑时，撞见两条案例的日期字段，当场纠出自己 CHANGELOG 的日期错误——撞见即命中）。

**明确不算的只有一种**：问题已经被**独立修好**（全程没参考任何记录），事后入库 / 复盘时才发现"哦原来已有记录 A"——纯事后归类而已。**同根因 ≠ 命中；解决之后才看见 ≠ 命中；解决之前看见并帮上忙 = 命中。**

只是扫到了没用上、或最后没解决，都不算。**宁可少记，不要虚高**——虚高的数字等于没有数字。

**计数落在哪：三侧同源。**

- **事件记录＝分母**：案例／根因文件末尾的 `## 命中记录` 表，一行＝一次命中。这是唯一手写的地方。
- **frontmatter 的 `hits`** 与 **索引表的 `🔥N`** 都是**派生物**，由 `counts --apply` 从上面那张表现扫生成；写它们的手改早晚会漂。
- 派生物与事件记录不一致时，**以事件记录为准**（`check` 报 R3／R4／R6 红，`counts --apply` 一把刷回）。

**根因层与案例层各自独立计数：**

- 只走根因层（读了 RT 文件、用通用对策解决）→ `hit --root-cause RT-0NN` → **根因 +1**；
- 深读具体案例并获益 → `hit --case <事件ID>` → **该案例 +1**；
- 两层都走了、都帮上忙 → 各 +1，但要**分两次记**：`--case` 与 `--root-cause` 互斥（一次调用只记一层），指望一条命令同时给两层 +1 会直接退出码 2。

## 升华＝候选 → 验证适用范围 → 提升

**为什么不能"数到次数就自动变永久规则"**：一条在 A 前提下成立的规律，攒够次数后被写成"所有任务都要 A"，等于把局部经验冒充普适规律——后来人会拿它去解释它解释不了的场景。次数只证明**值得验证**，不证明**适用范围**。

**三步：**

1. **进候选区**（到阈值只生成候选，不改任何规则）：
   `promote --scan` ⇒ 某根因下**案例数 ≥ 7**（2026-10-04 定案，勿回退勿另立数值），或某条案例**命中 ≥ 3**（召回轴，与案例数不同轴）→ 在 `_candidates/` 落一份 `C-*.md`。
   🔴 同一根因下有**几种不同适用条件**就分轨出**几个候选**，每个只覆盖自己那批案例；工具会照抄各案例的「能否借鉴」段，并在标题写明"本候选只覆盖 N 条"。
2. **验证适用范围**（人工填四要素，工具验完整性）：候选文件里 `适用范围`／`反例`／`边界`／`复核日期` 四段都不得留占位，其中
   - `反例` 写「无」＝没过闸——**没验证过它什么时候不成立，就还没验证成立**；
   - `边界` 含"所有任务 / 任何项目 / 永远 / 一律适用"这类**无边界措辞**＝没过闸；
   - `复核日期` 早于今天＝没过闸，先复核再提升（局部经验会过期，写个日期逼着回来重看）。
   跑 `promote --gate <候选编号>` 干跑看意见，逐条点名缺哪一段。
3. **提升**：`promote --gate <候选编号> --apply` ⇒ 候选状态改「已提升」、来源案例与根因文件置 `escalated: true`、索引对应行在**根因表与案例行两处**都加 `⭐`、候选里追加提升记录。工具在此过程中**拒绝**与已提升的异范围兄弟合并（同一根因 ≠ 同一条规则）。

**闸门没过就留在候选区继续攒**——这不是失败，这正是"固定次数自动升永久规则"被关掉的样子。

第 4 步是人做的、工具不代做：**把提升出来的铁律写进各 agent 自己的记忆 store CORE 铁律区**（路径见 `personal.local.md`；来源注 `RT-xxx` / 事件 ID）。共享踩坑日志不代写别人的 store。


**全处同步铁律。** 本 skill 的**规则、模板、索引格式、条目结构**任一处升级，所有副本必须同时改——本机 `SKILL.md`、`assets/` 下模板、log-root 下的 `_template.md`、现有索引与条目、以及对外发布的详解页。改一半等于埋雷：下次照旧模板写出的条目会和新格式对不上。**条目结构升级只往未来生效**：历史条目一律不追改（见「案例文件格式」末段），需要同步的是模板与规则本身。副本清点别靠肉眼：宿主层那些 `pitfall-log` 挂载位多为 **junction**，指向本库即自动同步（判链用 `fsutil reparsepoint query` 的退出码，`os.path.islink` 对 junction 恒 `False`）；改完实跑一次 md5 对账才算同步。

## 多 agent 同写一个库：纯文件系统的原子写与去重

坑的来源：五个 agent（加定时任务）往同一棵目录写，非原子写让读者拿到半截文件、甚至把空文件当成"没这条记录"。解法不上数据库，就用文件系统能给的两件东西——**独占创建**和**重命名**。

**四步，按顺序做：**

1. **抢锁**：`os.open(lock, O_CREAT | O_EXCL | O_WRONLY)` —— 独占创建，已存在就失败。锁文件里写自己的 PID 与时间戳；每完成一段活 `os.utime` 续一次心跳。
2. **判陈旧**：拿不到锁时看锁文件的最后修改时间，超过失效阈值（常量 `LOCK_STALE_SEC`＝120 秒）判定持有者已死，抢过来并**点名抢了谁**（打印锁里的 PID／时间）；没超阈值就退出码 5、一个字节都不写。
3. **写＝临时文件 + 原子替换**：同目录写 `*.pitfall-tmp-*` → 落盘 → `os.replace(tmp, target)`；覆盖前先留 `target.bak`。
4. **写后读回**：把刚写的文件**重新解析一遍**、把要生成的数字**再算一遍**，两者不符 ⇒ 从 `.bak` 回滚并非 0 退出。第 4 步是本工具在 Windows 上不敢省的一步。

去重靠前面那行事件指纹：**判重在锁内做**（锁外判重＝两个进程同时判到"不在册"然后各写一份，git 的 lockfile 也是这个顺序）。

**三条诚实边界（写进正文，别让读者以为有了锁就万无一失）：**

- 锁是**建议性的**（cooperative）：只约束也走这套工具的写入者。直接用编辑器保存、或用 `sed -i`／`open(w)` 改同一文件的人，锁管不住——所以别人手改之后仍有 `check` 兜底。
- `os.replace` 的原子性**没有被 Python 文档明文保证**（NTFS 上是单次目录项替换，实测可用；文档层面留了余地），所以第 4 步"读回再算"不是多余的偏执。
- 网络盘（NFS/SMB）上 rename 可能跨目录非原子 ⇒ **库放本地盘**，别放挂载盘。

**实测**（合成库，2026-10-13，断言编号见任务包 `evidence/卡14/_prove-out.txt`）：

- 同一事件连投三次 ⇒ 案例仍 1 个、正文 md5 未变（**A01**），换内容 ⇒ 退出码 4 拒绝覆盖（**A02**）；
- 三个进程并发各登记一条 ⇒ 三条全在册不丢事件（**A13a**），事后索引行数＝案例文件数、`check` 绿、无 `.pitfall-tmp` 残留（**A13b**）；
- 新鲜锁在场时后来者退出码 5 且案例数一字节没变（**A11**）；锁 mtime 超过残留阈值 ⇒ 被抢占并在输出里点名前任的 PID／时间（**A12**），办完事锁自撤不留残留（**A12r**）；
- 判据能不能翻红是另做一遍证明的：16 处「只改实现、不改断言」的变异探针（`_mutation_probe.py`，即故意把工具写坏看有没有断言叫）逐条点名该翻红的那条，16/16 抓到、无一条是恒真判据（怎么改都不会红的假判据）。


## 原则

- **单一事实源**：一份日志，不要各助手 / 各端各写一份导致漂移。
- **根因优先**：检索从根因入手，别一上来就翻案例。
- **渐进式披露**：索引常驻上下文，细节按需加载——这是它随体量增长仍省 token 的关键。
- **沉淀可迁移经验**：「能否借鉴」字段把一次性修复变成可复用知识。
- **位置稳定**：`<log-root>` 固定，索引路径才不会断。
- **索引有界**：案例超 ~50 条时，把冷条目归档到 `pitfalls/archive/`，索引保留「→ archive/文件名」指针。
- **统一储存**：所有 agent 共用一个 `log-root`（现值写在 `personal.local.md`），靠「单一事实源」避免各写一份漂移；**先和用户确认位置，别写死**。

## 与记忆纪律 / 记忆 PITFALL 层的关系（RT 号同源）

- **踩坑日志** = 跨 agent 共享的「教训沉淀」（谁踩谁记、大家都能查），不评分、不衰减。
- **记忆 PITFALL 层** = agent 自己的「记忆管理」（给坑打分 / 衰减 / 升华成铁律）。
- **边界**：坑的原始记录记在踩坑日志（共享）；反复出现的坑「提升成铁律」才进记忆 CORE。避免同一坑记两遍。
- **存哪边的判据（v1.3.1）**：通用 / 跨工具的坑（编码、git、网络等）正文记踩坑日志；仅某 agent 环境私有的坑（其专属路径、配置）正文记该 agent 自己的 store PITFALL。交叉相关时，另一方只放**一行指针**（含根因号/日期），不复制正文。
- 🔴 **RT 号同源（与记忆纪律共用一套受控词表）**：`roots/RT-*.md` 这套目录**就是**记忆纪律里 `root_cause_signature`（格式 `RT-xxx|一句话短语`）所引用的那张词表——同一个号在两边指同一件事，判"是不是同型坑"看号相同，不看短语措辞。因此：
  - 新建根因族只能落在这里（`add --make-root`），别在记忆侧另起一套编号；
  - 两边的升华阈值同为「同根因案例数 ≥ 7」（2026-10-03／10-04 先后定案，勿回退），召回计数同为 `hits ≥ 3`；
  - 记忆 store 的 PITFALL 层**满足工具的入库条件时**可以同一份脚本直接指过去（`--root <该 store 目录>`），不必维护两套计数与去重逻辑——收敛成一个工具、两套存储。入库条件是硬三条：该目录下要有 `roots/` 与 `pitfalls/` 两个子目录，索引文件名必须是 `pitfall-log.md`；缺任一条退出码 2 并点名缺什么（不静默建骨架）。**现状对照**：本机记忆 store 的 PITFALL 层是扁平的「`pit-NNN.md` ＋ `index.md`」，形态不符 ⇒ 现在指过去会被拒；要对齐得先把那个库搬成两层结构，搬家由该 store 的主人决定，本 skill 不动别人的库。
- **互认**：宿主注册位、log-root、记忆 store 的**本机具体路径全部写在 `personal.local.md`**（公开正文不嵌机器本地路径）；记忆纪律 skill 与编码行为准则 skill 均已内置本 skill 的指针与降级路径（skill 不可用时直接读 log-root 的 `pitfall-log.md`）。某宿主 侧 `patrol_check.py` 会巡检本 skill 的注册与指针存活——它的判据键（`name: pitfall-log`、`roots/` 目录名、log-root 索引）**不许改**，改了那条链路会亮红。
