# 踩坑日志（索引 + 两层明细）

> 自我学习账本，**统一单一事实源**。遇到坑 / 错 / bug / 特殊困难及最终解法 → 先在 `roots/` 归因（同根因就挂上去），再追加一条案例。

> 为什么这样做：记录越多，若全内联在一个文件里，每次阅读都会全量加载 → 越来越费 token。解法：**根因进 `roots/`、案例进 `pitfalls/`，一条一个文件**；本索引只留「根因表 + 一行案例摘要」。平时只读索引；检索时先看根因，再看案例。

## 🧭 检索顺序（先根因，后案例）

1. 读本索引 → 2. 先扫「根因索引表」，看识别信号有没有对得上的 → 3. 对上就读 `roots/RT-*.md` 拿通用对策 → 4. 不够再翻该根因下的具体案例找灵感 → 5. 解决了就给**真正帮上忙的那个** +1

## 命中计数（因果要件，v1.4.0 起）

> **在对应问题被独立解决之前**，踩坑记录（正文或索引元数据）被看见并对解决产生实际助力（找到方向 / 直接修好）＝算一次命中。
> 怎么看见的不限：主动检索、干活途中撞见、误打误撞翻到都算。
> **唯一不算**：问题已被独立修好（全程没参考任何记录），事后入库才发现"原来已有记录 A"——纯归类。

同根因 ≠ 命中；解决之后才看见 ≠ 命中；解决之前看见并帮上忙 = 命中。

## 两个指标都不手填

| 指标 | 含义 | 从哪儿生成 |
|---|---|---|
| 案例数 | 该根因下有几条**不同事件** | `pitfalls/*.md` 里的 `<!-- pitfall-event: … \| fp: … -->` 事件标记，按指纹去重后现扫 |
| 命中 🔥N | 「实际帮上忙」几次 | 案例／根因文件末尾「命中记录」表的**行数**现扫（同一次命中重复提交只留一行） |

改一处数字请跑：

```
py scripts/pitfall_log.py --root <log-root> counts --apply
py scripts/pitfall_log.py --root <log-root> check
```

`counts` 只从事件记录重算并原子替换（临时文件 + `os.replace` + 写后读回），`check` 报「索引 ↔ 事件记录 ↔ 根因文件」三侧漂移。**手填的数字一律视为可疑**——它要么和现扫对得上（那就不用填），要么对不上（那就填错了）。

## 升华＝候选 → 验证适用范围 → 提升（不是数到次数就自动变规则）

- 触发进**候选区**：某条案例命中数或某根因下案例数达到工具阈值（两根轴，别混用）。阈值以脚本为准（`promote --help` / `promote --scan` 输出可见现值），正文不抄数字防漂移。
- 候选件必须补齐**四要素**才允许提升：适用范围、反例（写「无」＝没验证过它什么时候不成立）、边界（不许写「所有任务／永远」这类无边界措辞）、复核日期（过期先复核）。
- 适用条件不同的同类案例**不得合并成一条无条件规则**；工具会分轨出候选、并拒绝与已提升的异范围兄弟合并。
- 命令：`promote --scan` 生成候选 → 填四要素 → `promote --gate` 验闸门 → `promote --apply` 落 ⭐。
