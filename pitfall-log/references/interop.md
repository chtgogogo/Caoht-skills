# interop — 与记忆体系互认、宿主巡检、发布链（v1.7.0)

## 与记忆 CORE 铁律区的分工与流向

本库（pitfall-log）与 agent 记忆体系各存一层，谁存哪边有判据：

| 内容 | 存哪里 | 判据 |
|---|---|---|
| 案例细节、证据链、复现验证 | 本库案例层（八段/四段） | 具体事件；越具体的越放案例层 |
| 根因识别信号＋通用对策 | 本库根因层（RT 文件） | 跨案例的可复用知识，但要证据支撑 |
| 升华后的铁律 | 记忆 CORE 铁律区 | **必须先过闸**（候选 → 四要素 → promote --apply），门没过不许进 CORE |

- RT 号同源：CORE 里引用铁律时**带回 RT-0NN 号**指向本库根因层，两个体系共用一套编号，不各编各的。
- 提升方向：`promote --apply` 后，铁律正文由人抄进 CORE，候选文件里的「提升记录」行给人照抄用。
- 回归方向：`check` R14 红色（复核过期） ⇒ 人要么重验候选并更新复核日期，要么降级；降级时 **CORE 铁律区同步摘除**对应条目——工具不代删 CORE（不在本库内），但 R14 会点名提醒。
- 摘除方向的另一半：本库 `retire` 只动自己的文件；如果退役对象曾被提升并抄进 CORE，**人必须连带撤 CORE 里的条目**（retire 输出会提醒）。

## 宿主巡检（junction 家族）

本机权威库被多个宿主以 junction 指向（改权威库即各家生效）。巡检时认这些判据键，它们是各宿主共用的「身份证明」：

- frontmatter `name: pitfall-log`（挂载键，不许改——历史会话、宿主索引都靠它）；
- 挂载目录名 `pitfall-log`；
- 索引文件名 `pitfall-log.md`；
- `roots/`＋`pitfalls/`＋`_candidates/` 目录骨架。

已知偏差（登记在 SKILL.md「命名与发布」节）：权威库目录名是本机中文命名规则，由发布映射统一到英文名——巡检若报「目录名与 name 不一致」，以映射机制豁免，不改 name。

宿主曾报过、已家族性解决的事（遇到同类报警先查这里再动手）：
- 启动器 `py` 不存在 → 正文统一 `python`，本机别名进 `personal.local.md`；
- 图标规范类 → assets 模板已带图标键；
- 中文目录报警 → publish_map 映射节处理。

## 发布链机制（不代写发布仓）

- 权威库（写作发生地）→ 发布仓：由 publish_sync 工具完成，目录名映射表见 publish_map 第七节（17 条规则）。
- 升级纪律见 `references/concurrency.md` 的「共享库与发布仓的同步纪律」节；要点：selftest 全绿 → check 红 0 → 同步 → md5 对账。
- agent 的角色边界：**只改权威库**；发布仓由用户手动跑同步工具触发（工作流约定），agent 不越写。

## 与 diagnosing-bugs skill 的分工

- 本库不管「怎么修 bug」的过程方法论（假设树、复现策略）——那是 diagnosing-bugs 的事。
- 本库管「修完之后」的沉淀（归因 → 建档 → 命中 → 升华）与「修之前」的查库。
- 交叉点：修 bug 过程结束时，diagnosing 会话应落一条本库案例（有棘手根因时）；查库命中时给根因层 +1。

## skill 不在场时的降级路径

1. 直接读 `<log-root>/pitfall-log.md` 索引（现值见 `personal.local.md`）。
2. 根因/案例文件照常读（纯 markdown，无格式依赖）。
3. 登记/计数/升华的写操作降级为手工＋事后 `counts --apply`（见 SKILL.md「降级路径」节）——手工档必须带事件标记行，否则幂等失效。
